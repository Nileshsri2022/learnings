1 · Basic HTML syntax — HTML kya hai, element ka anatomy, poora document

HTML (HyperText Markup Language) ek markup language hai — programming language nahi. Iska kaam: text aur content ko elements se wrap karke uski structure aur meaning define karna.

HTML kya karta hai

  • Structure deta hai: bina markup ke text ek hi line me beh jata hai. Wahi text <p> (paragraph) aur <ul><li> (list) me wrap karo to paragraph + bullet points ban jate hain.
  • Links banata hai — ek page se dusre page/resource tak jaana.
  • Media embed karta hai — images, video, audio page ke andar.
  • Data tables banata hai — rows aur columns me structured data.
  • Forms banata hai — user se input lena (search, order, feedback, payment).
  • CSS isko style karta hai aur JavaScript isko behaviour deta hai — lekin neeche wali structure hamesha HTML ki hoti hai.

Element ka anatomy — sabse basic building block

  • Ek element = opening tag + content + closing tag. Example: <p>Meri billi bahut cute hai.</p>
  • Opening tag <p> batata hai element kahan shuru hua; closing tag </p> (slash ke saath) batata hai kahan khatm hua.
  • Attributes = element ki extra settings/info, jo opening tag ke andar jaati hain — jaise charset, name, src.
  • Nesting: elements ek dusre ke andar ja sakte hain, lekin band ulta order me hone chahiye — jo sabse aakhir me khula, wahi sabse pehle band.
<!-- Sahi nesting: strong pehle band, phir em -->
<p>Meri <em>billi <strong>bahut</strong> cute</em> hai.</p>

<!-- GALAT nesting: tags ulta band hue -->
<p>Meri <em>billi <strong>bahut</em></strong> hai.</p>
Dhyaan do

Galat nesting invalid HTML hai. Browser DOM banate time khud correct kar deta hai — lekin hamesha waisa nahi jaisa tum chahte the. Isliye sahi markup likhna tumhari zimmedari hai, browser ki nahi.

Void (empty) elements

  • Kuch elements ke andar koi content nahi hota aur closing tag bhi nahi — inhe void elements kehte hain.
  • Examples: <br> (line break), <img> (image), <input> (form field), <meta>, <link>, <hr>.
  • End me trailing slash (<img />) optional hai — bina slash ke bhi bilkul sahi hai.
  • Yaad rakho: <script> void element nahi hai — use closing tag chahiye.

Attributes ke rules

  • Format: tag name ke baad space, phir name="value" — jaise <img src="cat.jpg" alt="Ek billi">.
  • Value ke around hamesha quotes lagao. Bina quotes ke value spaces ya special characters par toot jati hai.
  • Agar value ke andar hi quote chahiye to &quot; use karo.
  • Boolean attributes: kuch attributes ko value ki zaroorat hi nahi — sirf maujoodgi = true, gayab = false. Examples: disabled, required, checked, readonly, multiple, selected, autofocus.
  • class attribute elements ko group karta hai taaki CSS/JS unhe target kar sake — jaise class="figure".
  • Tags case-insensitive hain, lekin lowercase likhna best practice hai — hamesha lowercase hi likho.

Whitespace, entities aur comments — chhoti par important baatein

  • Whitespace collapsing: source code me kitne bhi spaces, newlines ya tabs lagao — browser render karte time unhe ek single space me badal deta hai.
  • Exception: <pre> ke andar whitespace jaisa hai waisa preserve hota hai.
  • Character references (entities): jab tumhe literal < ya > page par dikhana ho (tag ki tarah parse nahi karwana ho), to entities use karo:

  • Comments: <!-- ... --> — browser inhe ignore karta hai; page par nahi dikhte, sirf code me dikhte hain. Apne ya team ke liye notes chhodne ke kaam aate hain.

Poora document — DOCTYPE, html, head, body

<!doctype html>
<html lang="en-US">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width" />
    <title>Meri pehli page</title>
  </head>
  <body>
    <p>Yahan saara visible content aata hai.</p>
  </body>
</html>
  • <!doctype html> ek required preamble hai — har document ki pehli line. 1991/92 me doctypes error-checking ke rule sets se link hote the; aaj iska kaam bas itna hai: document sahi behave kare. Bas itna yaad rakho.
  • <html> = root element — poore page ka sab content iske andar wrap hota hai.
  • lang attribute page ki primary language set karta hai — <html lang="en-US">. Kisi hisse par alag language bhi de sakte ho, jaise <span lang="ja"> (codes ISO 639-1 ke hote hain).
  • lang ke fayde: screen readers sahi pronunciation use karte hain, aur SEO ko bhi help milti hai.
  • <head> = wo sab jo viewer ko dikhai nahi deta: title, metadata, CSS links, JS, charset.
  • <body> = sab kuch jo user ko dikhta hai: text, images, videos, games, playable audio.

Head ke andar kya-kya hota hai

  • <title> — page ka title jo browser tab me dikhta hai aur bookmark karne par use hota hai. Ek page par ek hi title. Ye <h1> se alag hai — h1 page ke andar dikhne wala heading hai.
  • <meta charset="utf-8"> — character set ko UTF-8 set karta hai, jo duniya ki lagbhag saari likhi languages ke characters handle kar leta hai. Na lagane ki koi wajah nahi — baad ki problems se bachata hai. (Purana ISO-8859-1 kam characters cover karta hai.)
  • <meta name="viewport" content="width=device-width"> — page browser ke viewport ki width par render hota hai. Iske bina mobile browsers page ko wide render karke shrink kar dete hain. Responsive design ke liye essential.
  • <meta name="author"> aur <meta name="description"> — author aur description; description search engines search results me dikhate hain (SEO). keywords meta ko search engines ignore karte hain — us par bharosa mat karo.
  • Open Graph: og:image, og:description, og:title — page social media par share ho to kaisa dikhe, ye control karte hain.
  • Favicon: <link rel="icon" href="favicon.ico"> — tab me dikhne wala 16×16px icon. / matlab site root; browsers /favicon.ico khud bhi dhoondh lete hain. Apple touch icon sizes: 167 / 180 / 152 / 120px.
  • CSS jodna: <link rel="stylesheet" href="style.css"> — head ke andar.
  • JS jodna: <script src="script.js" defer></script> — head ke andar. defer matlab: script page parse hone ke baad load/execute ho. Yaad rakho — <script> void element nahi hai, closing tag zaroori hai.

2 · Headings and paragraphs — Emphasis and importance, Lists, Advanced text features

Web ka zyada tar content text hai. Sahi text elements chunna sirf dikhne ke liye nahi hai — SEO, screen readers aur structure teeno is par depend karte hain.

Headings aur paragraphs

  • <p> = regular text ka paragraph — sabse zyada use hone wala text element.
  • <h1>–<h6> = 6 heading levels. <h1> = main title, <h2> = chapters, <h3> = sub-sections. Bilkul kitaab jaisa: main title → chapter titles → subtitles.
  • Ek page par ek hi <h1> rakho.
  • Heading order sahi rakho — levels skip mat karo (h1 ke baad seedha h4 nahi). Ek page par aam taur par max ~3 levels kaafi hain.
  • Structure kyun important hai: users pages ko scan karte hain — headings se cheezein jaldi milti hain.
  • SEO: search engines heading ke keywords ko zyada weight dete hain.
  • Accessibility: screen readers headings se page ka outline banate hain — blind users usi se navigate karte hain.
  • CSS/JS headings ko target kar sakta hai.
Common galti

<span> ko CSS se bada-bold karke heading jaisa dikhana heading banana nahi hai. Us span me koi semantics nahi — na SEO fayda, na screen-reader outline, na structure. Hamesha asli heading elements use karo.

Emphasis aur importance — em, strong, b, i, u

  • <em> = stress emphasis — sentence ka meaning badal deta hai. Screen readers ise alag tone me padhte hain. Default style italic hai — lekin sirf italic chahiye isliye <em> mat use karo.
  • <strong> = importance (default bold). Sirf bold chahiye isliye use mat karo. <em> aur <strong> ko nest karke aur zyada zor de sakte ho.
  • <b>, <i>, <u> asal me presentational the, lekin HTML5 ne inhe naye roles diye:
  • <i> = foreign words, taxonomic (scientific) names, technical terms — lang attribute ke saath use karo.
  • <b> = keywords, product names, lead sentence (pehla sentence jo dhyaan kheeche).
  • <u> = proper names, misspellings jaisi annotations.
  • Underline = hyperlink ki pehchan. Links ke alawa kisi text ko underline mat karo — users confuse hote hain.
  • Golden rule: element uske meaning se chuno, dikhne se nahi.

Lists — ul, ol, dl

  • <ul> = unordered list — jab order matter nahi karta (shopping list). Bullets ke saath dikhti hai.
  • <ol> = ordered list — jab order matter karta hai (recipe ke steps). Auto-numbered hoti hai.
  • Har item <li> ke andar jata hai.
  • Nested list hamesha parent list ke kisi <li> ke andar jati hai — bahar nahi.
  • <dl> = description list — terms + unki definitions, ya Q&A format ke liye.
  • <dt> = term (jo cheez define ho rahi hai); <dd> = description (default indented dikhta hai). Ek term ke multiple <dd> ho sakte hain.
<dl>
  <dt>HTML</dt>
  <dd>Web pages ki structure banane wali markup language.</dd>
  <dt>CSS</dt>
  <dd>Pages ko style karne wali language.</dd>
</dl>

Advanced text features — quotes, abbr, code, sub/sup, time

  • <blockquote cite="…"> = block-level quotation (default indented). <q cite="…"> = inline quotation (browser khud quote marks lagata hai).
  • cite attribute browser display nahi karta — source ko visible text me bhi dikhao.
  • <cite> = quoted resource ka title (default italic; iske andar link bhi ho sakta hai).
  • <abbr title="…"> = abbreviation. Pehli baar use par text me full form likho, ya chhote terms ke liye title me expansion do (jaise LGTM). <acronym> removed hai — kabhi use mat karo.
  • <address> = sirf nearest <article> ya <body> ki contact info ke liye — koi bhi random address daalne ke liye nahi.
  • <sup> / <sub> = superscript / subscript — 25th, C8H10N4O2, x2.

Code wale elements

  • <code> = inline code ke liye.
  • <pre> = whitespace preserve karta hai — code blocks ke liye <pre><code>…</code></pre> combo use karo.
  • <var> = variable, <kbd> = keyboard input, <samp> = sample output.

Machine-readable time

  • <time datetime="…"> dates/times ko machine-readable banata hai — search engines aur calendars ise samajh sakte hain.
  • Valid formats: 2016-01-20 (date), 2016-01 (month), 01-20, 19:30 (time), 19:30:01.856, 2016-01-20T19:30 (date+time), +01:00 (timezone offset), 2016-W04 (week).
<p>Concert <time datetime="2026-03-14T19:30">14 March ko 7:30 baje</time> hai.</p>

4 · Creating links — web ki neev

Hyperlink (<a href="…">) hi web ko web banata hai. Ek link kisi bhi file type ki taraf ja sakta hai — browser use handle na kar paye to open/download ka option deta hai.

Link basics

  • href = Hypertext Reference — link kahan jayega.
  • Koi bhi content link ban sakta hai — text, image, hatta ki poora block element bhi <a> ke andar ja sakta hai.
  • title attribute = sirf hover tooltip. Keyboard aur touch users use access hi nahi kar sakte — isliye important info kabhi sirf title me mat rakho, visible text me rakho.
  • Protocol (https://) likhna mat bhoolo — bina protocol ke link unexpected jagah ja sakta hai.

URL vs file path — sabse zyada confuse karne wala topic

  • Absolute vs relative: full URL = absolute (poora web ke hisaab se); /pdfs/… = usi domain ke hisaab se absolute; baaki paths current document ke URL ke hisaab se relative.
  • Portability ke liye apni hi site ke paths me domain mat likho — relative/root-relative rakho.
  • Default index.html: directory URL trailing / ke saath usi dir ki index.html load karta hai; bina / ke server use ek level upar ki file samajh sakta hai (servers redirect par differ karte hain).
  • Static websites me server URL ke pathname ko ek file se map karta hai — web content server ka filesystem nahi dekh sakta. Frameworks pages on-the-fly generate karte hain.

Document fragments — page ke andar jump

  • Kisi element ko id do, phir link me # ke saath wahi id use karo: contacts.html#mailing_address.
  • Same page ke andar bhi chalega: <a href="#mailing_address"> seedha us element par scroll kar dega.

Link text best practices

  • Screen readers links ko context se bahar padhte hain, aur SEO link-text ke keywords use karta hai — isliye link text khud bataye ki click karne par kya milega.
  • ✅ Good: “Download Firefox” · ❌ Bad: “Click here”.
  • URL ko text me repeat mat karo; “link” shabd mat likho; text chhota rakho.
  • Same text wale duplicate links alag jagah jaayein to confusion hota hai — avoid karo.
  • Download/stream/popup khulega to link text me pehle se warn karo. download attribute se download force + default filename de sakte ho: <a href="report.pdf" download="report.pdf">.
  • target="_blank" = nayi tab. Default = same tab. Nayi tab parallel browsing deti hai lekin disorienting bhi hai (back-button habit toot ti hai, screen-reader confusion). Common approach: external = new tab, internal = same tab, aur new-tab wale link par icon se cue do.

Navigation menu aur email links

  • Nav menu = links ki <ul>, har page par same. Jis page par khud ho, us page ka self-link hata do.
  • mailto: link email compose kholta hai. Address optional hai; parameters: ?cc=&bcc=&subject=&body= — pehle parameter se pehle ?, baaki ke beech &; values URL-encoded; multiple recipients comma se alag.
<a href="mailto:team@example.com?cc=boss@example.com&subject=Hello">Email bhejo</a>

3 · Structuring documents — semantic layout elements

Ek typical website ke hisse hote hain: header, navigation, main content, sidebar, footer. HTML ke paas in sab ke liye semantic elements hain — sahi element use karna screen readers ko “main navigation yahan hai, main content yahan hai” batata hai.

Semantic elements — kaun kya hai

  • <main> — page ka main content. Page par ek hi baar, seedha <body> ke andar.
  • <article> — self-contained content jo akele bhi sense banaye (blog post, news story, comment).
  • <section> — ek functionality/theme ka grouping; aam taur par heading se shuru hota hai.
  • Articles aur sections ek dusre ke andar nest ho sakte hain — article ke andar sections, section ke andar articles.
  • <aside> — indirectly related content: glossary, author bio, related links (sidebar).
  • <header> — agar <body> ka child hai to global page header; agar <article>/<section> ka child hai to us section ka header.
  • <nav> — sirf main navigation ke liye. Har link-group ko nav mat banao.
  • <footer> — footer content (copyright, contact, related links).
<body>
  <header>… site ka naam / logo …</header>
  <nav>… main menu …</nav>
  <main>
    <article>… ek blog post …</article>
    <aside>… related links …</aside>
  </main>
  <footer>… © 2026 …</footer>
</body>

div aur span — jab koi semantic element na mile

  • <div> = block-level, non-semantic container. <span> = inline, non-semantic container.
  • Dono class ke saath use hote hain — sirf tab, jab koi better semantic element exist hi na kare.
Div overuse warning

Har cheez ko div me lapetne se markup cluttered ho jata hai — padhna, maintain karna aur debug karna mushkil. Pehle semantic element dhoondo, div aakhri option hai.

br aur hr

  • <br> = line break — sirf fixed short lines ke liye (address, poem). Paragraphs banane ya spacing ke liye bilkul nahi.
  • <hr> = sections ke beech thematic break (topic badalne ka visual signal).

Coding se pehle — site planning

  • Information architecture: code likhne se pehle — common elements ki list banao, pages sketch karo, content brainstorm karo, card-sorting karo, sitemap banao.
  • Ye planning step hi baad me sahi semantic structure ki neev rakhta hai.

5 · Images in HTML — img, alt, figure · Responsive images

<img> ek void element hai — aur ek replaced element bhi: iska content aur size ek external resource se define hota hai. Kaam ka image tabhi hai jab src ke saath alt bhi ho.

img basics

  • src = image ka URL (relative ya absolute). Bina src ke koi image load nahi hogi.
  • Descriptive filename SEO me help karta hai — dinosaur.jpg > img835.png.
  • Images apne khud ke server par host karo (HTML wale hi server par). Relative URLs maintenance-friendly hain — domain move karne par links nahi tootte. Advanced setups CDN use karte hain.
Kabhi mat karo

Hotlinking — permission ke bina kisi aur ki site ki image ko apne src me point karna. Ye unethical hai (bandwidth ka bill unhe aata hai) aur risky bhi — image kabhi bhi remove ho sakti hai ya kisi sharmnaak cheez se replace ho sakti hai.

alt text — kab, kyun, kya likhein

  • alt = text description jo tab kaam aata hai jab image dekhi nahi ja sakti ya load slow hai.
  • Test trick: filename galat (misspell) karke dekho — browser image ki jagah alt text dikhayega.
  • Alt kyun important hai: screen-reader users; galat path; unsupported image type / text-only browsers (jaise Lynx); search engines alt ko queries se match karte hain; aur wo users jinhone data bachane ke liye images off ki hain.
  • Sawal hamesha ye: “Agar ye image na dikhe to user kya khoyega?” Ussi hisaab se alt likho:
CaseAlt ka rule
DecorationCSS background image use karo. HTML me laana hi pade to blank alt="" — screen reader ko time waste nahi karwana.
ContentWahi info brief alt me do — ya aur behtar, main text me hi sabke liye likho. Agar main text already describe kar raha hai to redundant alt mat do — alt="" rakho.
Link (image <a> ke andar)Accessible link text zaroor mile — ya to <a> ke text me, ya alt me.

  • Golden rule: images na dikhein tab bhi experience usable rahe.
  • title attribute images par recommended nahi — screen-reader support unpredictable hai, hover sirf mouse se hota hai, keyboard access nahi. Supporting info main article text me rakho.

width / height — layout shift rokne ke liye

  • width/height integers hote hain, pixels me, bina unit ke — image ka actual size do.
  • Kyun? HTML aur image alag requests me load hote hain. Bina size ke, image aate hi neeche ka text neeche jump karta hai (layout shift) — distracting, re-render costly, performance kharab.
  • Width + height dono ho to browser pehle se jagah reserve kar leta hai.
  • Image ke neeche koi content na ho to sirf width bhi chalega — height default auto rehta hai (aspect ratio maintain hota hai).
Resize ke liye nahi

Width/height ko image resize karne ke liye mat use karo: badi image chhoti dikhane par grainy/fuzzy + bandwidth waste; galat aspect ratio = distorted image. Pehle image editor me sahi size banao; page par size badalna ho to CSS use karo.

figure + figcaption — captions ka sahi tareeka

  • <div class="figure"> + <p> caption kaam to karta hai, lekin image aur caption ke beech koi semantic link nahi — 50 images hon to screen reader nahi bata sakta kaunsa caption kis image ka hai.
  • <figure> + <figcaption> use karo — semantic container jo figure ko uske caption se jodta hai.
  • Caption vs alt alag roles hain: caption unhe bhi fayda deta hai jo image dekh sakte hain; alt = image gayab ho to uski jagah kaam karta hai. Dono ek hi baat na kahen (image gayab hone par dono saath dikhenge).
  • Figure hamesha image hi nahi hota — koi bhi independent unit of content ho sakta hai: kai images, code snippet, audio, video, equation, table.
  • CSS background images sirf decoration ke liye hain — unme koi semantic meaning nahi, text equivalent nahi, screen readers ko invisible. Rule: image ka content me meaning hai → HTML <img>; sirf sajawat hai → CSS background.

Image licensing — use karne se pehle check karo

  • All rights reserved = default copyright. Explicit written permission chahiye, ya licence fee (one-time “royalty-free”, ya per-use “rights-managed”), ya use ko fair use / fair dealing tak limited rakho. Copyright notice ki zaroorat nahi — copyright automatically exist karta hai; koi notice/terms na dikhe to assume karo all rights reserved.
  • Permissive (MIT, BSD, Creative Commons): fee/permission nahi, lekin conditions vary karti hain — creator ko credit + source link; changes indicate karna; derivatives same licence par; no derivatives; no commercial use; licence ki copy include karna.
  • Copyleft (GPL, CC Share-Alike): derivatives par wahi licence lagega.
  • Public domain / CC0 = “no rights reserved” — free use. Records ke liye licence status ka proof (screenshot) rakh lo.
  • Permissive images dhoondhna: “public domain images” / “open licensed images” search terms, Google Images → Tools → Usage Rights, ya Flickr, Pixabay jaise repos (Picryl, The Noun Project permissive-only ke liye).

Responsive images — srcset, sizes, picture

Do alag problems hain, aur dono ke solutions bhi alag hain:

  • Problem 1 — Art direction: alag layouts ke liye alag cropped image chahiye. Desktop par wide landscape me beech me khada insaan, mobile par wahi image shrink hokar itni chhoti ki insaan dikhe hi nahi — behtar hai cropped portrait version jo zoom-in kare.
  • Problem 2 — Resolution switching: mobile par huge desktop image bhejna bandwidth waste hai; chhoti raster image badi karne par grainy hoti hai; high-resolution screens ko umeed se badi images chahiye.
  • Vector images kuch had tak help karte hain (chhoti, scale well — jahan ho sake use karo), lekin photos ke liye raster hi chahiye.

srcset + sizes (resolution switching — same image, alag sizes)

<img
  srcset="elva-fairy-480w.jpg 480w, elva-fairy-800w.jpg 800w"
  sizes="(width <= 600px) 480px, 800px"
  src="elva-fairy-800w.jpg"
  alt="Elva dressed as a fairy" />
  • srcset = comma-separated list: filename, space, phir intrinsic width w unit me (px nahi!). Intrinsic size = image ka asli size.
  • sizes = media conditions + slot width: (width <= 600px) space 480px. Last slot par koi media condition nahi — wahi default hai.
  • sizes me koi bhi length chalega (jaise 50vw) lekin percentage nahi.
  • Browser pehle match ke baad sab ignore kar deta hai — conditions ka order dhyaan se rakho.
  • Browser choose kaise karta hai: (1) screen size, pixel density, zoom, orientation, network speed dekhta hai; (2) sizes me pehli true media condition; (3) uska slot size; (4) srcset se slot ke barabar wali image — exact match na mile to slot se pehli badi wali, scaled down karke.
  • Example: 480px viewport → 480w image (63KB) banam 800px wali (128KB) = 65KB bacha. Kai images par ye bachat mobile par bahut badi ho jati hai.
  • Purane browsers srcset/sizes ignore karke src load karte hain — src hamesha fallback ke roop me rakho.
  • <meta name="viewport" content="width=device-width"> mobile browsers ko unki asli viewport width use karne par force karta hai.
  • Test kaise karein kaunsi image load hui: Firefox DevTools Network Monitor / Chrome Network panel (Chrome me cache disable karo). Viewport width console me: document.querySelector('html').clientWidth.

srcset with x-descriptors (same display size, alag resolutions)

  srcset="elva-fairy-320w.jpg, elva-fairy-480w.jpg 1.5x, elva-fairy-640w.jpg 2x"
  src="elva-fairy-640w.jpg" alt="…" />
/* CSS: img { width: 320px; } */
  • Yahan sizes ki zaroorat nahi — display size CSS se fix hai.
  • 1 device pixel per CSS pixel → 320w image (1x implied hai); 2 device pixels per CSS pixel → 640w (2x).

<picture> (art direction)

<picture>
  <source media="(width < 800px)" srcset="elva-480w-close-portrait.jpg" />

  • <img> src+alt ke saath zaroor do warna koi image nahi dikhegi — yahi default hai jab koi condition true na ho, aur <picture> na samajhne wale browsers ke liye fallback bhi.

6 · Video and audio content — vector graphics, iframe embedding

Purani plugin technology (Flash, Silverlight) ke security/accessibility problems ki wajah se wo obsolete ho gayi — uski jagah native <video>/<audio> + JS APIs ne li. YouTube/Vimeo jaise OVP aur Soundcloud jaise providers hosting + ready-made embed code de dete hain, taaki tumhari bandwidth na phoonke.

Video

<video src="rabbit320.webm" controls>
  <p>
    Your browser doesn't support HTML video. Here is a
    <a href="rabbit320.webm">link to the video</a> instead.
  </p>
</video>
  • src = video ka path (img ki tarah). <video> bhi ek replaced element hai.
  • controls = browser ka apna control interface. Users ko playback control kar pana hi chahiye (epilepsy wale users ke liye critical) — ya to controls use karo, ya JS API se apne controls banao. Minimum: start/stop + volume.
  • Fallback content = <video> ke andar wala paragraph — browser video support na kare to yahi dikhta hai; file ka direct link do.

Containers vs codecs — kyun multiple formats?

  • Container (OGG, WAV, MP4, WebM) = structure jo audio/video tracks + metadata rakhta hai aur batata hai ki channels kis codec se encoded hain.
  • Codec = track ko encode karne wala algorithm — audio tracks ke liye audio codec, video tracks ke liye video codec. Codecs raw media ko compress karte hain (raw audio/video behad bade hote hain).
  • WebM = aam taur par Vorbis/Opus audio + VP8/VP9 video (saare modern browsers). MP4 = AAC/MP3 audio + H.264 video (saare modern browsers). Ogg = Vorbis + Theora (Firefox/Chrome; WebM ne ise supersede kar diya).
  • Special cases: FLAC raw FLAC tracks me store hota hai (koi container nahi); “MP3 file” = MPEG-1 Audio Layer III, alag container nahi, hugely supported.
  • MP3 aur MP4/H.264 patent-encumbered hain (MP3 patents US me 2017 tak; H.264 kam se kam 2027 tak) — browsers huge licence fees dete hain; kuch sirf open formats prefer karte hain.
  • Har browser alag containers aur codecs support karta hai — isliye har media file multiple formats me do, warna common format na milne par play hi nahi hogi.
<video controls>
  <source src="rabbit320.mp4" type="video/mp4" />
  <source src="rabbit320.webm" type="video/webm" />
  <p>Fallback: <a href="rabbit320.mp4">video download karo</a></p>
</video>
  • <source> elements — browser pehla supported wala play karta hai.
  • type = MIME type, optional lekin advised — browser na samajhne wali files ko turant skip kar deta hai; bina type ke wo har file load/try karega (slow, wasteful).
  • WebM + MP4 saath me lagbhag saare platforms/browsers cover kar lete hain.

Video ke aur features

  • width/height (ya CSS) — videos apna native aspect ratio rakhte hain; ratio maintain na ho to video horizontally fill hota hai aur khaali jagah solid background colour se bharti hai.
  • autoplay = page load hote hi play. Use mat karo — annoying hai.
  • loop = khatm hone par dobara play (annoying — sirf sach me zaroori ho tab).
  • muted = default sound off. poster = play se pehle dikhne wali image (splash screen) ka URL.
  • preload (badi files ki buffering): "none" = no buffering, "auto" = media buffer karo, "metadata" = sirf metadata buffer karo.

Audio

  • <audio> bilkul <video> ki tarah kaam karta hai — <source>, controls, fallback, sab same.
  • Farak sirf itna: na width/height (koi visual component nahi), na poster. Baaki features same.

Captions / subtitles — WebVTT + track

  • Kis ke liye: deaf/hard-of-hearing users, shor wali jagah, library / sone wale partner ke paas, non-native speakers.
  • Format = WebVTT + <track> element. WebVTT ek text file hai jisme cues hote hain (text + dikhane ka time + limited styling/positioning).
  • Cue kinds: subtitles (foreign material ka translation), captions (dialog ka synchronised transcription + important sounds ka description), descriptions (blind users ke liye important visuals ka spoken description).
  • File WEBVTT se shuru hoti hai; numbered cues timestamps ke saath: 00:00:22.230 --> 00:00:24.606 + text. Extension .vtt.
  • <track> ko <audio>/<video> ke andar saare <source> elements ke baad rakho: <track kind="subtitles" src="subtitles_es.vtt" srclang="es" label="Spanish"> — kind = subtitles/captions/descriptions, srclang = language, label = readers ko language pehchanne me help.
  • Test karne ke liye local HTTP server par hosting chahiye; user CC button se subtitles on karta hai.
  • Bonus: text tracks SEO me bhi help karte hain (search engines text par thrive karte hain) aur video ke beech ke kisi spot par direct link bhi ban sakta hai.

Vector graphics — SVG

  • Raster = pixels ka grid (file har pixel ki jagah + rang batata hai): BMP, PNG, JPEG, GIF. Vector = algorithms (shape/path definitions); SVG web ka powerful vector format hai.
  • Zoom/enlarge par: PNG pixelate hota hai (har pixel kai screen pixels me phailta hai → blocky); SVG kisi bhi size par crisp rehta hai (algorithms scale hote hain).
  • Vector files raster equivalents se bahut halki hoti hain (har pixel ki info banam chand algorithms).
  • SVG ek XML-based language hai — markup jaisi, lekin elements shapes + effects define karte hain. SVG graphics ke liye hai, content ke liye nahi.
  • Basic shapes: <circle>, <rect>; complex: <path>, <polygon>; advanced: <feColorMatrix> (matrix se colours transform), <animate>, <mask>.
  • Simple SVG haath se code ho sakta hai; complex images mushkil ho jati hain — vector editor use karo (Inkscape, Illustrator; Inkscape ka Trace Bitmap photos ko approximate kar sakta hai).
  • SVG advantages: vector image ka text accessible rehta hai (SEO ko bhi fayda); har component ek element hai — CSS se style, JS se script ho sakta hai.
  • Disadvantages: complexity badhne par file size badhta hai aur browser processing time lagta hai; banana raster se mushkil ho sakta hai. Photos jaisi complex precision images ke liye raster behtar hai.
  • Editor-exported SVG deploy karne se pehle SVGO jaise optimiser se run karo.

Embedding — iframe, object, embed + security

  • History: frames (mid-late 90s) — site chhote HTML pages me banta tha master frameset me; slow downloads me help mili lekin problems zyada — ab use nahi hote. Plugins (Java Applets, Flash) <object>/<embed> se embed hote the — accessibility, security, file size ki wajah se fashion se bahar; browsers ne Flash support band kar diya.
  • <iframe> = ek poora web document dusre ke andar embed karta hai, <img> ki tarah. Third-party content ke liye best jo tum control nahi karte / khud implement nahi karna chahte: YouTube videos, Disqus comments, Google Maps, ad banners. (MDN ke khud ke live examples iframes use karte hain.)
  • Embed code provider se milta hai: YouTube par Share → Embed; Google Maps par Share or embed map.
  • iframe essentials: src = embed hone wale document ka URL; width/height; allowfullscreen = Fullscreen API se fullscreen; sandbox = heightened security (IE 10+); CSS border: none default border hatata hai.
  • Performance tip: iframe ka src JavaScript se main content load hone ke baad set karo — page pehle usable hoga, official load time (SEO metric) kam hoga.

Security — iframes attack vector hain

  • Iframes hackers ke liye common attack vector hain — page ko maliciously modify karna ya users se username/password निकलवाना.
  • Clickjacking = common attack: invisible iframe (tumhare doc me, ya tumhara doc attacker ki site me) user interactions capture karke gumrah/data churata hai.
  • MDN khud embedding block karta hai: console error “Refused to display … in a frame because it set 'X-Frame-Options' to 'deny'” — MDN ka server setting embedding disallow karta hai (apni pages ko kisi aur ki batane se rokna, clickjacking, bandwidth cost).

Embedding best practices (4 rules)

  • 1. Sirf zaroorat par embed karo. Rule: “You can never be too cautious. If you made it, double-check it anyway. If someone else made it, assume it's dangerous until proven otherwise.” IP bhi: zyada tar content copyrighted hai — bina ownership ya written permission ke display mat karo; licensed content ke terms follow karo (MDN CC-BY-SA hai — quote karne par proper credit zaroori).
  • 2. Hamesha HTTPS. Encrypted HTTP — transit me read/tamper mushkil. Saara content HTTPS hona chahiye (browsers HTTP par warn karte hain; HTTPS page me HTTP subresources load nahi hote; kai features HTTPS maangte hain). Certificate chahiye — zyada tar hosts default dete hain; Let's Encrypt free auto certificates deta hai.
  • 3. Hamesha sandbox attribute. Embedded content ko sirf utni permission do jitni uske kaam ke liye chahiye. Bina parameters wala sandbox = saari restrictions. Permissions ek-ek karke wapas add karo sirf jab absolutely required ho. Kabhi bhi allow-scripts + allow-same-origin ek saath mat do jab embedded content ka origin embedding page jaisa hi ho — wo attribute hata kar khud ko reload karke sandboxing band kar sakta hai. Aur: possibly-malicious (user-generated) content ko main site se alag domain se serve karo.
  • 4. CSP directives configure karo. Content Security Policy = security improve karne wale HTTP headers. Iframes ke liye server ko X-Frame-Options header bhejne ke liye configure karo taaki dusri sites tumhara content embed na kar sakein (clickjacking rokta hai) — MDN yahi karta hai.

embed / object aur PDFs

  • <embed>/<object> bhi external content embed karte hain, kabhi halke bhi (browser poora browsing context nahi banata). Historically plugins ke liye the — aaj lagbhag saare use cases <iframe> cover karta hai (zyada security features).
  • Minimum info: URL (src embed ke liye, data object ke liye), accurate media type, CSS pixels me height+width, fallback HTML (embed: supported nahi — <noembed> obsolete hai; object: opening/closing tags ke andar).
  • PDFs: iframe/object/embed ka dusra bada use case. Saare browsers PDFs natively render karte hain aur executable content ko already sandbox karte hain — embed karna generally safe hai; iframe par sandbox lagane ki zaroorat nahi (lagane se PDF viewer toot sakta hai).
  • PDF preview ke liye <iframe> top choice hai (loading="lazy", referrerpolicy milte hain); <object> sirf tab jab resource render na ho sakne par fallback chahiye; <embed> koi advantage nahi deta. CSP: iframe sources frame-src se, object/embed object-src se (aam taur par object-src 'none' rakho → iframe hi viable option).
  • Lekin PDFs me accessibility challenges hain aur chhoti screens par padhna mushkil — embed karne ke bajaye link karna aksar behtar hai.

7 · HTML table basics — HTML table accessibility ke saath, sirf tabular data ke liye

Table = rows + columns me structured data, jahan value row/column header ke association se samajh aata hai (kaun sa insaan → kitni umar; kaunsa din → kya timetable). Sahi bani table screen readers ke saath bhi achhi chalti hai — dekhne walon aur visually impaired users, dono ka experience better hota hai. Table ko effective banane ke liye CSS styling chahiye (HTML sirf structure deta hai).

Sabse badi rule

Tables SIRF tabular data ke liye — page layout ke liye KABHI nahi. Purane zamane me CSS support kamzor tha, isliye pages table se layout hoti thi (header row, content columns, footer row). Aaj modern browsers ka CSS solid hai — table layouts extremely rare hain. Kyun buri hain:

1) Accessibility ghata ti hai — screen readers tags padhte hain; layout-table markup unhe confuse karta hai.
2) “Tag soup” banta hai — complex markup, likhna/maintain/debug karna mushkil.
3) Automatically responsive nahi — proper containers (header/section/article/div) default parent ki 100% width lete hain; tables content ke hisaab se size hoti hain, devices par extra kaam padta hai.

Basic structure — table, tr, td, th

  • <table> sab kuch wrap karta hai.
  • Sabse chhota container = table cell <td> (“table data”). Ek row ke cells automatically ek hi row par align hote hain; har <td> = ek cell.
  • <tr> (“table row”) cells ko row me group karta hai — har agli row ko apna <tr> chahiye.
  • <th> (“table header”) = row ya column ke shuru ki special cell jo us row/column ke data ka type batati hai (jaise “Person”, “Age”). <td> jaisa hi hai, bas header denote karta hai. Default styling: bold + centred.
  • <th> ka fayda: cross-referencing easy + scope ke saath accessible — screen readers har header ko usi row/column ke data se jodte hain aur poori row/column ek saath padh sakte hain.

Spanning cells — colspan / rowspan

  • colspan / rowspan = bina unit ka number — cell kitni columns/rows me failega.
  • Example: <th colspan="2">Animals</th> 2 columns me failta hai; <th rowspan="2">Horse</th> 2 rows me.

Column styling — colgroup / col

  • <colgroup> <table> ka child hai, opening tag ke turant baad. Iske andar <col> elements left se columns ke groups represent karte hain.
  • <col span="2"> = 2 columns represent karta hai; style ya class jaise global attributes le sakta hai taaki CSS/JS target kar sake.
  • Limits: <col> par sirf limited subset of styles apply hote hain; baaki zyada tar deprecated hain. Paint order: table → col → tr → th/td — isliye row/cell styles column styles ko overwrite karte hain.

caption — table ka description

  • <caption> ko <table> ke andar, opening tag ke turant neeche rakho — table ke contents ka description.
  • Har reader ke liye useful (page scan karte hue turant samajh — table kaam ki hai ya nahi), khaas taur par blind users ke liye — bina kai cells sune decide kar sakte hain ki table detail me padhni hai ya nahi.
  • Deprecated summary attribute <table> par mat use karo — uski jagah <caption> hai (summary deprecated hai aur sighted users ko dikhta bhi nahi).

thead / tbody / tfoot

  • Ye teeno table ke header, body, footer sections mark karte hain.
  • Akele me ye screen readers ke liye table ko zyada accessible nahi banate, na visual enhancement dete hain — lekin CSS styling/layout ke liye bahut useful hain, jo accessibility improve kar sakta hai: lambi table me header/footer har printed page par repeat, body ek page par scrollable.
  • Order: pehle <thead> (header — aam taur par column headings wali pehli row; col/colgroup use ho to unke just neeche), phir <tbody> (main content), aakhir me <tfoot> (footer — jaise pichli rows ke sums wali final row).
  • <tbody> hamesha implicitly included hota hai — tum na likho to browser DevTools me khud add kar deta hai. Phir bhi structure/styling par control ke liye explicitly likho.
  • Example (spending record): thead = Purchase/Location/Date/Evaluation/Cost headers; tbody = item rows; tfoot = SUM row jisme colspan="4" hai taaki number Cost column ke neeche aaye. Bina in teeno ke, CSS selectors bahut complicated ho jate.

scope — screen readers ke liye header association

  • scope <th> par batata hai ki ye header exactly kin cells ka header hai.
  • scope="col" = column header. scope="row" = row header (jaise <th scope="row">Haircut</th>).
  • scope="colgroup" = kai columns ke upar header (jaise “Clothes” Trousers/Skirts/Dresses par, colspan="3" ke saath).
  • scope="rowgroup" = kai rows ke upar header (jaise “The Netherlands” rowspan="2" ke saath Amsterdam/Utrecht par).
  • Iske baad screen readers users ko poori column ya row ek saath padh kar suna sakte hain.

id + headers — scope ka precise (par heavy) alternative

  • Ek <th> kisi <td> ka bhi heading ho sakta hai aur kisi dusre <th> ka bhi — layered/grouped headers ke liye id + headers use hota hai.
  • headers = space-separated ids ki list (order matter nahi karta); har id kisi <th> ke unique id se match kare.
  • Steps: (1) har <th> ko unique id do; (2) subheading <th>s ko headers = high-level heading ka id do (trousers/skirts/dresses → headers="clothes"); (3) har <td> ko headers = uske row + column headers ke ids do — spreadsheet ki tarah: <td headers="belgium antwerp clothes trousers">56</td>.
  • Associations bahut precise milte hain — lekin markup bahut badh jata hai aur galti ki gunjaish zero hai. Zyada tar tables ke liye scope approach hi kaafi hai.

8 · Forms and buttons in HTML — web ko two-way banane wale

Links = navigate, media controls = consume — ye zyada tar one-way hai. Lekin users preferences set karte hain, taxi order karte hain, feedback dete hain, cheezein kharidte hain — iske liye chahiye buttons + forms. Web forms user aur website ke beech interaction ka main point hain: data server par processing/storage ke liye jata hai, ya client-side hi interface update karta hai (list me item add, UI show/hide).

Pehla form — 3 cheezein

  • (1) <form> wrapper — andar ke saare controls ek hi form ka hissa hain; submit par unka data saath jata hai. Har attribute optional hai, lekin action + method hamesha set karna standard practice hai.
  • (2) Ek ya zyada <label> + control pairs — control (<input>, <select>…) user ko data choose/enter karne deta hai jo server jayega; label batata hai kya data enter karna hai.
  • (3) Submit <button>.
  • action = data submit hone par kahan jayega (wo page jo data process karega). Baad me URL me /submit_page dikhega — 404 aana theek hai, wo page abhi exist nahi karti.
  • method = data transmission method. get data ko URL ke end par parameters ki tarah chipka deta hai: /some/url/submit_page?name=Bob&email=bob%40bob.com (@ → %40 ho gaya).
<form action="./submit_page" method="get">
  <p>
    <label for="name">Name (required):</label>
    <input type="text" name="name" id="name" required />
  </p>
  <p>
    <label for="email">Email (required):</label>
    <input type="email" name="email" id="email" required />
  </p>
  <p><button>Sign me up!</button></p>
</form>
  • Khali fields ke saath submit click karo → browser validation error dikhayega. Yahi browser ki default client-side validation hai.
  • Design pehle: code se pehle mockup sketch karo — sahi data maangna define karo. UX rule: form jitna bada, frustration utni zyada, users utne zyada bhaagte hain. Simple aur focused rakho — sirf wahi data maango jo absolutely chahiye.

<input> ke key attributes

  • type = sabse important attribute — control kaisa dikhega aur behave karega, yehi decide karta hai. text = default value, koi bhi value accept karne wala basic field. Browser type na pehchane to text par fallback hota hai.
  • name = data item ka naam — data name/value pairs me submit hota hai (name = attribute value, value = entered text). Client-side bhi aur server-side bhi important: server har data piece ko naam se handle karta hai.
  • id = element ki pehchan — control ko uske <label> se jodne ke kaam aata hai.
  • required = submit se pehle value zaroor ho — sirf un inputs par lagao jo sach me required hain, optional fields par nahi.
  • value = pehle render par pre-filled value (text/color par). Kuch inputs typed text se value nahi lete: type="color" = colour picker widget; type="radio" ko value chahiye taaki selected hone par kya submit ho ye pata chale.
  • required in action: khali submit → “Please fill in this field” (browser ke hisaab se text alag ho sakta hai). Galat email (“aaaa”) type="email" me → “Please enter an email address”.

<label> — accessible forms ki jaan

  • Label ka text sahi se bataye ki control kya data expect karta hai. Ye accessible forms ka sabse important element hai.
  • Explicit label: control ko id, label ko usi value ke saath for. Screen reader padhta hai: “Name, edit text”.
  • Implicit label: control ko <label> ke andar nest kar do — id/for ki zaroorat nahi. Dono theek hain, lekin explicit recommended hai: code complex hone par pehchan-na/understand karna easy, aur screen readers implicit labels ko hamesha sahi handle nahi karte. Implicit use karo tab bhi best practice hai for bhi set karo.
  • Label na ho / association na ho → screen reader padhta hai “Edit text blank” — bilkul helpful nahi.
  • Label ke fayde sabke liye: screen readers control milne par label text bolte hain (blind users ko pata kya enter karna hai); label text par click karne se control focus ho jata hai — bada hit area, mobile touch screens par khaas useful (radio/checkbox jaise chhote targets ke liye to aur bhi).
  • Ek widget par multiple labels possible hain lekin achhi idea nahi (kuch assistive tech struggle karti hai); zaroorat pade to widget + labels ko ek hi <label> me nest karo.
  • Required-field marker: rule ko use hone se pehle batao — form ke top par “Please complete all required (*) fields.” Taaki sighted + AT users dono * ka matlab pehle se jaan lein. Best: single label “Name *:” (do alag labels “Name:” + “*” nahi).

Form ko structure karna — fieldset, legend, sections

  • <form> ke andar structure/styling ke liye koi bhi HTML allowed hai. Common pattern: <h2> purpose bataye; har label/input pair + button alag <p> me (inputs/labels inline hote hain — bina wrapper ke sab ek hi line me chipak jayenge). <div>, <section>, <li> bhi chalte hain — bas semantically sensible ho (blockquote/aside/address ka sense nahi banta).
  • <fieldset> = same purpose wale widgets ka group (styling + semantic dono). Complex forms me aur kai checkboxes/radios group karne me khaas useful. <fieldset> par disabled lagao to andar ke saare controls ek saath disable ho jate hain.
  • <legend> opening <fieldset> ke turant baad — fieldset ke purpose ka formal description. Assistive tech legend ko andar ke har control ke label ka hissa banakar bolta hai (JAWS/NVDA: “Fruit juice size small / medium / large”). Radio buttons ka set hamesha fieldset me rakho.
  • Lambi forms ideally multiple pages me hon; single page majboori ho to related sections alag fieldsets me rakho — usability better hoti hai. Lekin fieldset ko abuse mat karo — screen reader se apna form “sun” kar dekho; odd lage to structure improve karo.
  • Multiple checkboxes/radios ke liye <ul>/<ol> ke andar <li> me label+widget wrap karna recommended hai. Complex forms ko <h1>/<h2> + <section> se structure karo — har functionality apni section me, radios ke liye fieldsets andar.
Strictly forbidden

Form ke andar form kabhi nest mat karo — unpredictable behaviour, bad idea. Haan, ek control <form> ke bahar bhi use ho sakta hai — default roop me wo kisi form se juda nahi hota, jab tak uske form attribute se explicitly bind na karo (control kisi dusre form ke andar ho tab bhi).

Payment form — structure ka real example

  • <h1>Payment form</h1> + <p>Please complete all required (*) fields.</p>
  • Section: Contact information — fieldset/legend “Title” with 3 radios <ul><li> me (Ace/King/Queen, values A/K/Q — implicit labels, input label ke andar nest, for ke saath); phir name (text, required), email (email, required), password (password, required) — har ek apne <p> me.
  • Section: Payment information — card type ke liye <select> (Visa/Mastercard/Amex); card number ke liye type="tel" (number nahi — number ka spinner UI nahi chahiye); expiration ke liye type="text" + placeholder="MM/YY" + pattern="^(0[1-9]|1[0-2])\/([0-9]{2})$" format test karne ke liye.
  • Final section: <button type="submit">Validate the payment</button>.

Buttons — <button> vs <input type="button">

  • <button> = push button, general-purpose — kisi bhi functionality ko trigger karne ke liye wire kar sakte ho. Tags ke beech ka text button ke andar basic browser styling ke saath render hota hai. Akele ye kuch nahi karta — form ke andar rakho ya JavaScript jodo.
  • <form> ke andar button ka DEFAULT = submit (invalid data validation se block na kare to form submit ho jayega).
  • type="submit" = explicitly submit (rarely declare karna padta hai — sirf tab jab multiple buttons hon aur submit wala mark karna ho).
  • type="button" = default kuch nahi karta — JS chahiye.
Reset button mat banao

type="reset" saara form data delete karke initial state par le jata hai. DON'T USE — annoying hai; users galti se lambi form submit karne ke bajaye poori saaf kar dete hain.

  • <input type="submit|reset|button"> equivalents exist karte hain lekin <button> ke muqable kai disadvantages hain — <button> hi use karo: <button> style karna easy hai, aur uska content full HTML ho sakta hai; <input> void hai, uska label sirf value attribute ka plain text.
  • disabled attribute button ko grey + unselectable kar deta hai (jaise penthouse booked ho / product out of stock). Kisi bhi form control par lag sakta hai, <button> samet.
Semantic elements hi kyun

Button ko <div> + CSS/JS se fake mat karo. Asli elements ke saath browser free deta hai: assistive tech/screen readers samajhte hain; keyboard-accessible by default (Tab / Shift+Tab se controls ke beech move); focus outline (focused element par blue outline) keyboard users ko batata hai wo kahan hain. Fake karoge to ye sab khud re-implement karna padega — aur elements users ki expectation jaisa behave bhi nahi karenge.

Basic native controls — text family ke behaviours

  • Text fields sabse basic widgets hain — kisi bhi data ke liye convenient. Dhyaan do: sirf plain text — rich text editing (bold/italic) native controls me nahi hoti; saare rich text editors custom widgets (HTML+CSS+JS) hote hain.
  • readonly = user value modify nahi kar sakta, lekin value form data ke saath bheji jati hai. disabled = modify bhi nahi, aur kabhi bheji bhi nahi jati.
  • placeholder = box ke andar brief description text. size = box ka physical size; maxlength = max characters. spellcheck attribute se spell-checking control hoti hai.
  • Single-line text: typed line breaks browser server bhejne se pehle remove kar deta hai. States: default / focused (focus ring) / disabled (grey/faded).
  • type="password" — har character dot dikhta hai. Koi special constraint nahi — ye sirf screen par value chhupata hai, UI feature hai. Data plain text me submit hota hai jab tak form securely na bheja jaye — form pages HTTPS par host karo; browsers insecure forms par warn karte hain.
  • type="hidden" — invisible control jo phir bhi server jata hai (jaise order place hone ka timestamp). User dekh/edit nahi sakta, focus kabhi nahi milta, screen reader notice nahi karta. name + value zaroor set karo (value JS se dynamically set ho sakti hai). Iska koi label nahi hona chahiye.
  • type="image" — <img> jaisa dikhta hai lekin click = submit. Image ke attributes + form button attributes dono. Apni value nahi bhejta — click ke X/Y coordinates bhejta hai (top-left = 0,0), do key/value pairs me: name.x aur name.y (GET → ?pos.x=123&pos.y=456). “Hot maps” ke liye convenient.
  • type="file" — server par files bhejne ke liye file picker. accept accepted file types constrain karta hai; multiple ek se zyada files. Mobile par camera/mic capture: accept="image/*;capture=camera", video/*;capture=camcorder, audio/*;capture=microphone.

Saare form elements ke common attributes

  • autofocus (boolean) — page load par auto input focus; ek document me sirf ek form-associated element par ho sakta hai.
  • disabled (boolean) — user interact nahi kar sakta; containing element (jaise fieldset) se inherit hota hai.
  • form — usi document ke kisi <form> ka id jisse associate karna hai (control kisi dusre form ke andar ho tab bhi).
  • name — form data ke saath submit hota hai. value — element ki initial value.

Checkbox aur radio — checkable items

  • Dono ki state unpar ya unke labels par click karke badalti hai; dono checked le sakte hain = page load par checked.
  • Submission rule (bahut important): zyada tar widgets name ke saath khali hone par bhi bheje jate hain; checkables sirf checked hone par value bhejte hain — unchecked → kuch nahi bheja jata, naam tak nahi. Checked lekin koi value nahi → naam value on ke saath jata hai.
  • Radio type="radio": purane radio buttons ke naam par — ek dabao, pichla pop-out. Same name = ek group; group me ek time par sirf ek hi selected. Submit par sirf checked radio ki value jati hai. Ek bhi checked na ho to poora pool “unknown state” me — koi value nahi jati. Ek baar check ho jaye to user bina form reset kiye sab uncheck nahi kar sakta.
  • Checkbox type="checkbox": on/off toggle — ek se zyada ek saath select ho sakte hain. Related items same name use karte hain (jaise vegetables: carrots/peas/cabbage, name="vegetable"). Form overview wale style me har checkbox ka alag name bhi hota hai — tab har checked box on bhejta hai (jaise yoga=on), value attribute se badal sakte ho (value="yes" → yoga=yes).
  • Hotel example: radios name="hotel" ke saath values ke saath — submit par hotel=economy jaisa pair. Har radio ka label us choice ko describe karta hai; overall choice <fieldset> + <legend> (“Choose hotel room type:”) se describe hoti hai. checked = load par pre-selected; radio group me ek option hamesha selected rehta hai.
  • CSS: load par checked wale :default pseudo-class match karte hain (baad me uncheck karne par bhi); abhi checked wale :checked. Checkbox ek toggle button hai — aksar toggle switch ki tarah restyle hota hai.
  • Usability/accessibility: related list ko <fieldset> + <legend> me rakho; har label/input pair apni list item me; label control ke turant pehle/baad; group instructions = legend ka content.

HTML5 input types — email, search, tel, url, number, range, date, color

  • type="email" — value valid email hona chahiye warna submit par browser error (“Please enter an email address”). multiple ek hi input me kai comma-separated emails allow karta hai. Touch devices email-friendly keyboard dikhate hain (@ key ke saath). Note: a@b default roop se VALID hai (intranet emails allowed) — alag behaviour chahiye to pattern use karo. Invalid email par CSS :invalid match hota hai aur JS me validityState.typeMismatch = true.
  • type="search" — search boxes. Text se farak sirf browser styling: kuch browsers rounded corners, kuch “Ⓧ” clear icon (field me value ho tab dikhta hai, click par clear; Safari ke alawa sirf focused hone par); dynamic keyboards “search” enter key ya magnifying glass dikha sakte hain. Values auto-save hokar site ke kai pages par auto-completion me reuse hoti hain.
  • type="tel" — phone numbers. Touch devices numeric keypad dikhate hain — jahan bhi numeric keypad useful ho wahan use karo, sirf phone ke liye nahi. Koi constraint enforce nahi hota (duniya ke phone formats bahut vary karte hain, letters bhi aa sakte hain) — constraints ke liye pattern.
  • type="url" — validation add karta hai: protocol na ho (jaise http:) ya URL malformed ho to browser error. Keyboards aksar colon/period/slash default keys me dikhate hain. Well-formed ≠ sach me exist karta hai!
  • type="number" — text field jaisa dikhta hai lekin sirf floating-point numbers; aam taur par spinner buttons; touch par numeric keyboard. min/max allowed values constrain karte hain, step spinner ka increment. Default step="1" → sirf integers valid; floats ke liye step="any" ya step="0.01". Examples: odd 1–10 → min="1" max="10" step="2"; 0–1 by 0.01 → min="0" max="1" step="0.01". Number tab use karo jab valid values ki range limited ho (age, height); range bahut badi ho (US ZIP 00001–99999) to tel behtar (numeric keypad, spinner UI nahi).
  • type="range" (slider) — number chuno jiska precise value important nahi (text fields se less accurate; jaise shopping site par max house price filter). Thumb mouse/touch/keyboard arrows se move hota hai. min, max, step set karna highly recommended. Sliders current value ka koi visual feedback nahi dete — <output> element use karo (<label> ki tarah for attribute leta hai). Value dikhana/update karna JS se hota hai: input event par output.textContent = price.value.
  • Date/time controls — calendar UI context-switching aur format confusion (1999/12/31 vs 23:59 vs 12/31/99) dono khatm karta hai. date = year/month/day picker (no time); datetime-local = date + time, no timezone; month = month + year; time = time (display 12-hour ho sakta hai lekin returned value 24-hour hoti hai); week = week number + year (weeks Mon–Sun; week 1 = saal ke pehle Thursday wali — Jan 1 shamil na bhi ho, pichle saal ke aakhri din shamil ho sakte hain). Sab min/max + step se constrain ho sakte hain (step ka matlab type ke hisaab se badalta hai). Example: <input type="date" min="2025-06-01" max="2025-08-31" step="7">.
  • type="color" — click par OS ka default colour picker khulta hai; returned value hamesha lowercase 6-digit hexadecimal colour hota hai.
  • Ye saari built-in validation helpful aid hai — samay bachata hai (turant pata chalta hai, server round-trip nahi) — lekin exhaustive security measure nahi: server-side validation hamesha karo (client-side band karna bahut easy hai).

Baaki controls — textarea, select, datalist, meter, progress

  • <textarea> = multi-line text field (<input> nahi). Users hard line breaks (return press) de sakte hain — wo submitted data me shamil hote hain.
  • Void-oddity: <input> void hai (koi closing tag nahi), <textarea> void nahi — proper closing tag chahiye. Isi liye default values ka tareeka alag hai: input → value attribute; textarea → opening/closing tags ke beech ka text. Textarea ke andar jo bhi ho (HTML/CSS/JS bhi) plain text render hota hai. (HTML/“rich” content capture ke liye non-form controls par contenteditable use hota hai.)
  • cols = average character widths me visible width (starting width; default 20); rows = visible rows (starting height; default 2). Text visually wrap hota hai; control default resizable hai (corner me drag handle) — CSS resize property se control: both (default), horizontal, vertical, none.
  • wrap: soft (default — rendered text wrap hota hai, submitted nahi), hard (cols zaroori — submitted bhi wrap hota hai), off (koi wrapping nahi).
  • Drop-down controls bina zyada UI space liye kai options se choose karwate hain. Do types: select box + autocomplete box. Interaction same: control activate karo → browser values ki list dikhata hai.
  • <select> + <option> (ye input type nahi hai). <select> saari choices wrap karta hai, id (label association) + name (submitted data name) leta hai. Har <option> ka value choose hone par submit hota hai; value na ho to option ka text use hota hai (value attrs zaroori nahi, lekin dikhne wale text se chhota/alag value bhejne ke liye useful — jaise value="banana", display “Big, beautiful yellow banana”).
  • Pehla option aksar <option value="">--Please choose an option--</option>. Kisi option par selected = load par selected. size = select ke unfocused hone par kitne options dikhte hain (default: ek value ki height).
  • <optgroup label="fruits"> options ko visually associated groups me baant ta hai (label options se pehle, aam taur par bold + alag nesting level par dikhta hai).
  • multiple <select> par = kai values select (desktop par Cmd/Ctrl+click). Multi-choice select drop-down nahi rehta — saari values ek saath list me dikhti hain, size widget ki height decide karta hai.
  • <datalist> + list attribute = form widgets ke liye suggested auto-completed values. <datalist id="mySuggestion"> ko kisi <input> se list="mySuggestion" se bind karo. HTML spec ke hisaab se kisi bhi user-input widget ke saath chal sakta hai — range inputs par supporting browsers har option value par tick mark dikhate hain; color inputs par customised palette. Browsers alag behave karte hain — progressive enhancement samjho, graceful degradation ensure karo.
  • <meter> = min/max se bounded range me ek FIXED numeric value ka visual representation. low/high range ko 3 parts me baant te hain: lower (min–low inclusive), medium (low–high exclusive), higher (high–max inclusive). optimum preferred part batata hai: optimum lower me → lower preferred, medium average, higher worst; optimum medium me → medium preferred, baaki average; optimum higher me → higher preferred, medium average, lower worst. Browsers bar ko colour karte hain: preferred = green, average = yellow, worst = red. Example (disk space, full hone par red): <meter min="0" max="100" value="75" low="33" high="66" optimum="0">75</meter>. Andar ka content unsupported browsers ke liye fallback + assistive tech ke vocalise karne ke liye hai.
  • <progress> = value jo samay ke saath max tak badalti hai: <progress max="100" value="75">75/100</progress> — jaise files download ka %, questionnaire ke filled questions. Andar ka content fallback + screen readers ke liye.

Client-side validation — poori kahani

  • Form validation = browser + server check karte hain ki data sahi format me hai aur app ki constraints ke andar hai. Messages jaise: “This field is required”, “Please enter a valid email address”, “Your password needs to be between 8 and 30 characters long and contain one uppercase letter, one symbol, and a number.” Valid → data server par submit (aam taur par DB me save); invalid → kya correct karna hai batane wala error message, phir dobara try.
  • Validate kyun (3 reasons): (1) sahi data sahi format me mile (galat/missing data par apps break hoti hain); (2) users ka data protect ho (secure passwords accounts bachate hain); (3) hum khud protect hon (malicious users unprotected forms ka misuse karke app ko damage kar sakte hain).
Warning

Client se server par aane wale data par KABHI bharosa mat karo — client-side validation kaam karne ke bawjood malicious user network request ko alter kar sakta hai.

  • Do types ki client-side validation: HTML form validation (attributes required + format define karte hain) aur JavaScript form validation (HTML validation ko enhance/customise). Kam ya bina JS ke bhi ho sakti hai. HTML validation JS se faster hai lekin less customisable — recommendation: robust HTML features se shuru karo, UX ke liye JS se enhance karo.

Validation attributes — recap

  • required — submit se pehle field bhara ho.
  • minlength/maxlength — textual data ki min/max length.
  • min/max/step — numerical inputs ke min/max values + minimum se shuru hone wala increment.
  • type — number/email/anya preset types apna format check laate hain.
  • pattern — required pattern define karne wala regex.
  • Data saare attribute rules follow kare → valid; warna invalid.

Valid vs invalid — browser kya karta hai

  • Valid element: :valid CSS pseudo-class match karta hai (valid elements ko style kar sakte ho); user ne interact kiya ho to :user-valid bhi; type/attrs ke hisaab se :in-range jaise aur UI pseudo-classes. Submit par browser form submit kar deta hai (koi aur cheez, jaise JS, na roke to).
  • Invalid element: :invalid match karta hai (+ interacted ho to :user-invalid; error ke type par :out-of-range). Browser submission BLOCK karta hai + error message dikhata hai (message error type ke hisaab se vary karta hai).
  • required wala element :required pseudo-class match karta hai; khali hone par submit nahi hota + error message; khali rehte hue :invalid bhi rehta hai. Radio group: same-named group ke kisi bhi ek radio par required ho to group valid hone ke liye ek checked hona chahiye (checked wala wahi hona zaroori nahi jis par attribute hai).
  • Sirf wahi data required karo jo sach me chahiye (gender/title sach me necessary hai?). Common practice: required controls ke labels ke baad asterisk (*) — achhi UX aur WCAG accessibility guidelines ke hisaab se required. Failed submit par invalid input ko focus milta hai + default error message (“Please fill out this field”).

pattern — regex se format

  • pattern ek regular expression expect karta hai. Regexp = text me character combinations match karne wala pattern — validation ke liye ideal.
  • Basics: a = ek a; abc = a phir b phir c; ab?c = a, optionally ek b, phir c (ac/abc); ab*c = a, optionally kitne bhi b, phir c; a|b = a OR b; abc|xyz = exactly abc ya exactly xyz.
  • Regexps case-sensitive hote hain — [Bb]anana|[Cc]herry banana/Banana/cherry/Cherry accept karta hai.
  • Non-empty value pattern se match na kare → :invalid. Empty + required nahi → invalid nahi.
  • Kuch input types ko pattern ki zaroorat nahi — email type khud well-formed email pattern se validate karta hai (ya multiple ke saath comma-separated list).

minlength/maxlength aur min/max ke fine points

  • minlength/maxlength saare text fields (<input> ya <textarea>) ki char length constrain karte hain. Value present ho aur minlength se chhoti ya maxlength se lambi ho → invalid. Browsers aam taur par maxlength se zyada type hi nahi karne dete.
  • Maxlength akela kaafi nahi — better UX: character count feedback accessibly do + user ko edit-down karne do (jaise social media char limit; JS solutions exist karte hain).
  • Length constraints kabhi report nahi hote agar value programmatically set hui ho — sirf user-provided input ke liye.
  • min/max (numeric + date types): range se bahar value → invalid. Arrows range se bahar nahi ja sakte; haath se out-of-range number daalo to invalid; number required na ho aur khali ho → valid. step default 1 hai → 3.2 jaisa float invalid ho jayega.

Constraint Validation API (JS)

  • HTMLButtonElement, HTMLFieldSetElement, HTMLInputElement, HTMLOutputElement, HTMLSelectElement, HTMLTextAreaElement (+ form) par methods/properties milte hain.
  • validationMessage — unsatisfied constraints batane wala localised message; element validation candidate na ho (willValidate false) ya valid ho to empty string.
  • validity (ValidityState object): patternMismatch (pattern match nahi), tooLong (maxlength se lamba), tooShort (minlength se chhota), rangeOverflow (max se bada — :out-of-range bhi), rangeUnderflow (min se chhota — :out-of-range bhi), typeMismatch (email/url ka bad syntax), valid (saari constraints pass), valueMissing (required lekin value nahi).
  • willValidate — true agar element submit par validate hoga.
  • Methods: checkValidity() (true/false; invalid ho to invalid event fire hota hai); reportValidity() (invalid fields ko events ke through report karta hai; onSubmit handler me preventDefault() ke saath useful); setCustomValidity(message) (custom error message → element invalid mana jata hai aur message display hota hai; standard constraints se aage ke JS validation failures ke liye).

Custom error messages

  • Native messages ke 2 drawbacks: CSS se restyle karne ka koi standard tareeka nahi; aur wo browser locale par depend karte hain (page ek language me, error dusri me).
  • Pattern: “input” event par — email.validity.typeMismatch ho to email.setCustomValidity("I am expecting an email address!"), warna setCustomValidity("") (empty = valid). Koi bhi control non-empty customError ke saath submission block karta hai.
  • Built-in validation extend karna: pehle setCustomValidity("") se reset; if (!email.validity.valid) return; (built-in checks pehle chalao); phir custom constraint add karo (jaise email @example.com par end ho → setCustomValidity("Please enter an email address of @example.com")).
  • Detailed custom example: <form novalidate> — novalidate browser ki automatic validation (error bubbles) OFF kar deta hai taaki tum custom messages khud DOM me dikha sako; ye Constraint Validation API ya CSS pseudo-classes ko disable nahi karta — khud check + style kar sakte ho. Error <span class="error" aria-live="polite"> me dikhao (aria-live screen-reader users ko message sunwata hai). JS: input par → valid ho to message/class clear, warna showError(); submit par → invalid ho to showError() + event.preventDefault(). showError() validity.valueMissing (“You need to enter an email address.”), typeMismatch (“Entered value needs to be an email address.”), tooShort (“Email should be at least X characters; you entered Y.”) check karta hai. API HTML+CSS se aage ka enormous UI control deta hai.
  • API ke bina (custom controls): JS se khud validate karo — decide karo: kya validation perform karni hai (string ops, type conversion, regex — tum par hai); invalid ho to kya karna hai (bhej dein? fields highlight? messages?); user ko correct karne me kaise help karni hai (up-front suggestions + clear errors frustration ghata te hain). Example: HTML spec ka email regex, isValidEmail() = non-empty + regex test. Khud banana mushkil nahi; generic cross-platform banana mushkil hai — libraries exist karti hain (jaise Validate.js).
  • Closing rules: custom styling/messages ke liye kabhi-kabhi JS chahiye, lekin hamesha user ke baare me sochna padta hai: explicit error messages dikhao; input format ke baare me permissive raho; error exactly kahan hai ye point out karo (bade forms me khaas taur par).

Form data bhejna — GET vs POST, enctype, security

  • Client/server architecture: client (browser) HTTP ke through server (Apache, Nginx, IIS, Tomcat…) ko request bhejta hai; server usi protocol se jawab deta hai. Ek HTML form = server ko data bhejne ke liye HTTP request configure karne ka convenient, user-friendly tareeka.
  • <form> ke saare attributes submit par bheji jaane wali request ko configure karte hain. Do sabse important: action + method.
  • action = data kahan jayega; valid relative ya absolute URL ho. Na diya ho to data form wale page ke URL par hi jata hai (current page). HTTPS action URL → form insecure HTTP page par host ho tab bhi data encrypted; secure page par HTTP action → browsers har baar security warning dikhate hain (data encrypted nahi).
  • Non-file controls ke names+values name=value pairs me & se jud kar bheje jate hain. action server par wo file ho jo incoming data (server-side validation samet) handle kar sake. Server respond karta hai — aam taur par data handle karke action wala URL load karta hai (nayi page load, ya same page ho to refresh).
  • HTTP request = header (browser capabilities ke baare me global metadata) + body (server ke process karne ke liye info). GET vs POST sabse common methods hain.

Files bhejna = special case

  • Files binary data hain; HTTP ek text protocol hai → special requirements. enctype = submitted request ke Content-Type HTTP header ki value (server ko batata hai kis tarah ka data bheja gaya).
  • Default application/x-www-form-urlencoded = “form data encoded into URL parameters”.
  • Files bhejne ke 3 extra steps: (1) method="POST" (file content URL parameters me nahi ja sakta); (2) enctype="multipart/form-data" (data kai parts me bant ta hai — ek har file ke liye + ek text data ke liye); (3) <input type="file"> control(s) shamil karo.
  • Note: servers files/HTTP requests ke size limits ke saath configure ho sakte hain taaki abuse roka ja sake.

Security — forms sabse common attack vector hain

  • HTML forms server attacks ke sabse common vectors hain — problems forms se nahi aati, isse aati hain ki server data ko kaise handle karta hai.
  • NEVER EVER apne users par bharosa mat karo — khud par bhi nahi (trusted user bhi hijack ho sakta hai). Server par aane wala saara data check + sanitise karo — hamesha, bina exception.
  • (1) Potentially dangerous characters escape karo (context/platform ke hisaab se vary karte hain; saari server languages me functions hain; executable code jaise lagne wale sequences par dhyaan — JS ya SQL commands). (2) Incoming data ki amount sirf zaroori tak limit karo. (3) Uploaded files ko sandbox karo — alag server par store, access sirf alag subdomain se ya aur behtar poori alag domain se.
  • Competent third party se security review karwao; ye mat assume karo ki tumne saari problems dekh li hain. Front-end dev ko data security model define nahi karna chahiye; client-side validation exist karti hai lekin server use trust nahi kar sakta (pata hi nahi client-side asal me kya hua).
  • Further reading (MDN ke hisaab se): Server-side website programming first steps; OWASP; Mozilla Web Security.

9 · Debugging HTML — browser jhooth nahi bolta, bas chup rehta hai

Errors do tarah ke hote hain: syntax errors (typos — program run hi nahi hota; syntax + error messages pata hon to aam taur par fix easy) aur logic errors (syntax sahi lekin code wo nahi karta jo tum chahte the; chalta hai par galat — zyada mushkil, kyunki koi error message source ki taraf ishara nahi karta). Debugging se comfort = language + tools se familiarity.

Browser HTML ko permissively parse karta hai

  • HTML interpreted hai, compiled nahi — element syntax Rust/JS/Python se easy hai.
  • Browsers HTML ko PERMISSIVELY parse karte hain — syntax errors ke bawjood page display ho jata hai. Browser ke paas built-in rules hain jo galat likhe (invalid/badly-formed) markup ko interpret karke khud valid markup me badal dete hain.
  • Achha bhi, bura bhi: kuch na kuch hamesha chal jata hai, lekin browser hamesha sahi guess nahi karta — isliye sahi markup pehle se likho.
  • Wajah: web ne decide kiya ki content publish hona perfect syntax se zyada important hai.
  • Example: galat nested <p>I didn't expect to find the <em>next-door neighbor's <strong>cat</em></strong> here!</p> ko browser ka rendered DOM nesting correct karke <em>… <strong>cat</strong></em> bana deta hai.

DevTools — tumhara sabse bada tool

  • Saare modern browsers me DevTools hain: rendered HTML examine karo, har DOM node ki CSS dekho, running JS dekho; live code edit karke effect turant dekho.
  • DOM inspector = pehla tab (Firefox “Inspector”, Safari/Edge/Chrome “Elements”, aam taur par default selected).
  • Nodes ko arrows ya cursor keys se expand/collapse karo (up/down move, right/left expand/collapse); node par hover/select karne se wo viewport me highlight hota hai; rendered DOM ko live edit bhi kar sakte ho.

3 common errors — pehchano

  • 1. Unclosed elements — <p> aur <li> bina closing tags ke: aksar infer ho jate hain, minor effect. Lekin unclosed <strong> = worse — effect failta hai: baaki poora text bold render hota hai; browser har alag text block ko apne <strong> me lapet ta hua document ke bottom tak jata hai.
  • 2. Badly nested elements — <strong>strong <em>strong emphasized?</strong> what is this?</em> ko browser fix karke <strong>strong <em>strong emphasized?</em></strong><em> what is this?</em> bana deta hai.
  • 3. Unclosed attributes — <a href="https://www.mozilla.org/> (closing quote gayab) = sabse badi problem: link render hi nahi hota; browser link element ko poora DELETE kar deta hai (document ka baaki hissa attribute value ki tarah nigal jata hai).

HTML Validator — W3C Markup Validation Service

  • validator.w3.org — HTML document do, report milti hai kya galat hai. Input: web address, file upload, ya direct input (Validate by Direct Input tab — poora document paste karo, sirf body nahi).
  • Error messages ke saath line + column numbers aate hain.
  • Common messages: “End tag li implied, but there were open elements” (koi element khula hai jo band hona chahiye tha; line/col closing tag ke hone ki jagah ke baad wali pehli line par point karta hai); “Unclosed element strong” (seedha usi par point); “End tag strong violates nesting rules” (bad nesting); “End of file reached when inside an attribute value. Ignoring tag” (cryptic — attribute sahi se form nahi hua, shayad file ke end ke paas; render na hua link hi clue hai); “End of file seen and there were open elements” (khule elements band karne hain; line numbers aakhri lines par); “Unclosed element ul” (misleading — ul band hai; asal wajah missing quote ki wajah se unclosed <a> hai).
  • Strategy: ek baar me kuch hi errors fix karo, har set ke baad revalidate karo — ek error fix karne se kai aur saaf ho sakte hain (domino effect).
  • Done = green banner: “Document checking completed. No errors or warnings to show.”

10 · Global attributes — <mark>, data-*, block vs inline: jo module me nahi tha, sab yahan

Ye section un chaar topics ke liye hai jo MDN ke Learn module me padhaye hi nahi jate — lekin “sab kuch cover” karna hai, to ye bhi yahi milenge, seedha MDN ke reference docs se: <mark>, global attributes ki poori list, data-*, aur block vs inline ka formal topic.

<mark> — highlighted / relevant text

  • <mark> us text ko mark karta hai jo current context me relevant hai — bilkul waise jaise highlighter pen se book me koi passage mark karna. Browsers default me ise yellow background + black text ke saath render karte hain (CSS se badal sakte ho).
  • Use case 1 — search results: user ne jo term search kiya, page me uske matches ko <mark> se highlight karo, taaki aankh seedha wahi jaye.
  • Use case 2 — quotes ke andar khaas hissa: kisi quotation/block quote me wo hissa jo original source me marked nahi tha, lekin reader ke liye special scrutiny chahta hai.
  • <mark> vs <strong> — confuse mat karo: <strong> = importance (ye baat mahatvapurna hai); <mark> = relevance (ye hissa abhi ke kaam ke liye relevant hai).
  • Syntax highlighting ke liye <mark> nahi — uske liye <span> + appropriate CSS hai. Emphasis ke liye bhi nahi — wo <em>/<strong> ka kaam hai.
  • <mark> par sirf global attributes lagte hain — koi special attribute nahi. Aur ye void element nahi hai: opening + closing dono tags mandatory hain.
  • Accessibility note: zyada tar screen readers <mark> ko announce nahi karte. Agar highlight ka matlab samajhne ke liye zaroori hai, to visually-hidden extra text (jaise “highlight shuru”) se wo matlab bhi do — sirf rang par bharosa mat karo.

data-* — apna custom data, element par hi

  • data-* attributes (custom data attributes) HTML aur uske DOM representation ke beech apni proprietary info exchange karne ka tareeka hain, jo scripts use kar sakti hain — jaise kisi product card par data-product-id, game sprite par data-x/data-y.
  • Naam ke rules (MDN ki recommendations): data- ke baad ka naam xml se shuru mat karo (future XML specs ke liye reserved), colon (:) mat use karo, aur capital letters mat use karo (lowercase rakho). Na mano to error nahi hoga — lekin dataset se access karna hai to naam JS property rules ke hisaab se hona chahiye.
  • JS me access — element.dataset: data- prefix hat jata hai aur kebab-case camelCase ban jata hai: data-user-id → dataset.userId; data-id → dataset.id. Dhyaan: data-test-1 jaisi hyphen-ke-baad-digit wali cheezein dataset me sahi recognize nahi hotin.
  • CSS me bhi use ho sakta hai: attribute selector [data-id] se select karo, aur content: attr(data-id) se value dikha bhi sakte ho.
  • Kab use karein: jab data sirf tumhare JS ke liye hai aur uske liye koi sahi existing attribute/element maujood nahi. Agar semantic tareeka exist karta hai (jaise date ke liye <time datetime="…">), to wahi use karo — data-* uska replacement nahi hai.
  • Security note: data-* page source me sabko dikhta hai — sensitive data (password, personal info, secrets) isme kabhi mat rakho.

Block vs inline — elements ka default behaviour

  • Normal flow me har element ya to block-level box banata hai ya inline-level box — dono ek saath nahi. Block boxes block formatting context me, inline boxes inline formatting context me participate karte hain.
  • Block elements ek ke neeche ek, vertically lagte hain — har naya block nayi line se shuru hota hai. By default ye inline direction ki saari available space le lete hain (poori width); width de do tab bhi agla element neeche hi aayega, side me nahi. Examples: <p>, <div>, <h1>–<h6>, <ul>, <section>, <header>.
  • Margin collapsing: do adjacent block boxes ke beech ki vertical distance unke margins se banti hai — aur vertical margins collapse hote hain: total dono ka sum nahi banta, bada wala margin jeet-ta hai (jaise top 20px + bottom 40px = beech me 40px).
  • Inline elements sentence ki direction me ek ke baad ek horizontally lagte hain. Jagah kam pade to box nayi line par break ho jata hai (jo lines banti hain unhe line boxes kehte hain). Horizontal margins, borders aur padding respect hote hain. Examples: <span>, <a>, <em>, <strong>, <code>.
  • Size ka farak: block elements par width/height kaam karte hain; inline elements ka box sirf content ke size ka hota hai — un par width/height apply nahi hote.
  • Replaced elements (<img>, <input>, <video>) default inline hote hain, lekin exception hain: in par width/height kaam karte hain, kyunki inka size external resource se aata hai.
  • Sabse important baat: block/inline element ka “swabhaav” nahi hai — ye uska default display hai, jo CSS se badal sakte ho (strong { display: block; } bilkul valid hai). Isiliye hamesha sabse sahi semantic element chuno, aur dikhne ka behaviour CSS par chhod do.
  • inline-block beech ka raasta hai: element inline ki tarah text ke flow me rehta hai, lekin block ki tarah width/height/margins sab le leta hai (ye CSS ka topic hai — CSS SPA me detail milegi).

11 · What's in the head? Web page metadata — <base>, <link>, <script>, <meta> ki poori kahani

Section 1 me head ki basics aayi thi — title, charset, viewport, description, favicon. Lekin MDN ke reference me head isse kahin zyada hai: <base>, <link> ke saare rel types aur resource hints, <script> ke async/defer/module ka exact behaviour, <style>, <noscript>, aur meta tags ki poori list. Sab yahan hai.

<base> — saare relative URLs ka aadhaar

  • <base href="…"> document ke saare relative URLs ke liye ek base URL set kar deta hai. Ek document me sirf ek <base> hona chahiye, aur wo head me un elements se pehle aana chahiye jo relative URLs use karte hain.
  • <base target="_blank"> saare links/forms ka default target bhi set kar sakta hai.
  • Side-effect samajh lo: <base> lagane ke baad sirf #fragment wale in-page links bhi base URL ke hisaab se resolve hote hain — badi sites par isiliye ise soch-samajh kar use karte hain, ya bilkul nahi.

<link> ke rel types — sirf stylesheet nahi

  • rel="stylesheet" — CSS jodna (sabse common). rel="icon" — favicon. rel="canonical" — duplicate pages me se asli (preferred) URL search engine ko batana; SEO ke liye important.
  • rel="alternate" — page ka dusra version: dusri language (hreflang ke saath), RSS/Atom feed (type="application/rss+xml"), ya dusra format.
  • rel="author", rel="license", rel="help" — document ke baare me sambandh batane wale kam-use-hone-wale rels; naam jaan lo.
  • Link par bhi rel hota hai: <a rel="noopener"> / noreferrer — target="_blank" ke saath nayi tab ko tumhare page ka window.opener access rokta hai (security); modern browsers _blank par noopener default maan lete hain, phir bhi explicit likhna achhi aadat hai. rel="nofollow" search engine ko kehta hai is link ko endorsement mat samjho (user-generated/spponsored links ke liye ugc/sponsored bhi hain).

Resource hints — browser ko pehle se hint dena (performance)

  • rel="dns-prefetch" — kisi dusre domain ka DNS pehle se resolve kar lo, taaki baad me wahan se resource laana tez ho.
  • rel="preconnect" — DNS + TCP + TLS, teeno pehle se setup kar lo; dns-prefetch se ek kadam aage. Jo domain pakka use hoga (jaise fonts), usi par lagao.
  • rel="preload" — current page ko isi navigation me pakka chahiye wala resource (font, hero image, critical CSS) sabse pehle fetch karo: <link rel="preload" href="font.woff2" as="font" type="font/woff2" crossorigin> — as batana zaroori hai, warna browser sahi priority nahi dega aur font double-download bhi ho sakta hai.
  • rel="prefetch" — agle navigation me kaam aa sakne wala resource idle time me la lo (preload se low priority). Pakka-na-ho to preload mat karo — galat preload bandwidth waste hai aur page ko slow karta hai.
  • rel="modulepreload" — JS module ko aur uski dependencies ko pehle se fetch/parse karna.

<style> aur <noscript>

  • <style> = document ke andar CSS. Chhote, page-specific styles ya critical CSS ke liye theek hai; badi styling hamesha external stylesheet me rakho (cache hota hai, kai pages share karte hain).
  • <noscript> = JavaScript band/off ho to dikhne wala content. JS par depend karne wale page par ek saaf message fallback ke roop me do — khaali page chhodna sabse bura hai.

Meta tags ki poori list — jo Section 1 me reh gayi thi

  • Viewport ki baaki keys: initial-scale=1 (shuru ka zoom), user-scalable (ise no mat karo — zoom rokna accessibility ke khilaf hai), viewport-fit=cover (notch wale phones par content safe-area tak failta hai).
  • <meta name="robots" content="noindex, nofollow"> — search engines ko is page ko index/link-follow na karne ka instruction (login ke peeche wale ya staging pages ke liye).
  • <meta name="theme-color" content="#c15f3c"> — mobile browser ki toolbar ka rang page ke theme se match karta hai.
  • <meta name="color-scheme" content="light dark"> — page dono schemes support karta hai; browser form controls/scrollbar ko usi hisaab se render karta hai.
  • Twitter/X cards: twitter:card, twitter:title, twitter:image — Open Graph jaisa hi kaam, us platform ke liye. (OG tags Facebook/WhatsApp/LinkedIn previews ke liye hain — Section 1 dekho.)

12 · <details>, <dialog>, <template>, <canvas> elements — aur unke dost

MDN ke element reference me 100+ elements hain. Curriculum wale sections me zyada tar aa gaye; jo bache the — khaas taur par interactive elements aur text ke chhote-magaram-important elements — wo sab yahan ek saath hain.

details + summary — bina JS ka accordion

  • <details> ek disclosure widget hai: andar ka content chhupa rehta hai, <summary> par click karne se khulta hai. Koi JavaScript nahi chahiye — bilkul is SPA ke FAQ jaisa behaviour, natively.
  • open attribute (boolean) = load par khula hua. Browser khud keyboard support aur focus deta hai — haath se banaya hua div-accordion ye sab nahi deta.
  • Summary hamesha pehla child rakho; wahi dikhne wala “heading” hai. Baaki content summary ke baad aata hai.
<details>
  <summary>Delivery kitne din me hogi?</summary>
  <p>2–3 working days.</p>
</details>

dialog — asli modal, browser ke saath

  • <dialog> = modal ya non-modal dialog box ke liye native element. showModal() se khulta hai to baaki page inert ho jata hai, focus dialog ke andar rehta hai, aur peeche ::backdrop pseudo-element se dim layer style kar sakte ho.
  • Esc dabane se modal khud band ho jata hai; close() method aur returnValue se pata chalta hai user ne kaunsa button chuna.
  • Dialog ke andar <form method="dialog"> rakho to submit karne par dialog bina JS ke band ho jata hai, aur dabaye gaye submit button ki value returnValue ban jati hai.
  • Haath ka banaya div-modal accessibility me aksar fail hota hai (focus trap, Esc, aria-modal sab khud karna padta hai) — pehle <dialog> hi chuno. Labs me iska live demo hai.

template + slot — Web Components ki neev

  • <template> ke andar ka markup parse hota hai lekin render nahi hota aur uske andar ki images/scripts run/load nahi hotin. JS template.content ko clone karke page me jahan chahe, jitni baar chahe daal sakta hai — list-item/card jaisi dohraayi jaane wali structure ke liye.
  • <slot> Web Components ke shadow DOM me ek placeholder hai, jisme component ka user apna content daalta hai (named slots ke saath alag-alag hisse).
  • Ye dono JS ke saath milkar Custom Elements banate hain — poori Web Components seekhna JS SPA ka topic hai; HTML ki taraf se bas ye jaan lo ki ye elements exist karte hain aur inka kaam kya hai.

canvas, map/area, search, menu, hgroup

  • <canvas> = JS se 2D/3D graphics draw karne ke liye ek drawing surface (games, charts, image editing). HTML sirf khaali canvas + fallback text deta hai; saari drawing JavaScript ki Canvas/WebGL API karti hai. Accessibility ke liye andar fallback content rakho.
  • <map> + <area> = image ke alag-alag hisso ko clickable banane wala image map (<img usemap="#…"> se judta hai). Aaj kal kam use hota hai (responsive images par coordinates mushkil hain) — naam aur kaam jaan lo.
  • <search> = naya semantic element — search controls ko wrap karne ke liye, bilkul <nav>/<main> ki tarah ek landmark. Andar aam taur par ek <form> hota hai.
  • <menu> = toolbar/context-menu jaisi commands ki list; render <ul> jaisa hi hota hai, matlab alag hai.
  • <hgroup> = ek heading + uske saath juda subheading/tagline paragraph — dono ko ek unit ki tarah group karta hai.

Text ke bache hue elements — data, dfn, edits, bidi

13 · Styling web forms — Advanced form styling, UI pseudo-classes, autocomplete

MDN ke Forms module ke aakhri teen bade topics bache the: forms ko style karna (aur uski mashhoor pareshaniyan), controls ko custom style karna, aur wo UI pseudo-classes jo form ki state ke hisaab se style badalti hain. Saath me autocomplete ki poori kahani — jo real-world forms me sabse zyada kaam aati hai.

Form styling ki buniyadi pareshaniyan

  • Fonts inherit nahi hote: form controls browser ki default font/settings use karte hain, page ki font nahi. Normal look ke liye khud likhna padta hai: button, input, select, textarea { font-family: inherit; font-size: 100%; }
  • Box sizing alag hota hai: controls historically content-box par chalte aaye hain jabki baaki layout border-box par — widths milaane ke liye controls par bhi box-sizing: border-box lagao.
  • Legend ki positioning sabse ajeeb hai: <legend> fieldset ke border par baithta hai aur use normal flow se hatana mushkil hota hai — isiliye kai designs legend ko float/position se sambhalte hain, ya fieldset ka border hi hata dete hain.
  • Controls teen category me bante hain (MDN ka classification): (1) Good — text fields, buttons: aaram se style ho jate hain. (2) Bad — checkbox, radio, color, range, file: browser/OS ke hisaab se style karna mushkil ya namumkin ke barabar; custom look chahiye to advanced technique (neeche) lagti hai. (3) Ugly/hard — <select> ki dropdown list, <datalist>, <progress>/<meter> ke andar ke hisse: inke internal parts par CSS lagbhag nahi pahunchta; asli custom dropdown aksar JS se banana padta hai (aur accessibility ka poora khayal rakhna padta hai).

Advanced styling — appearance: none aur custom controls

  • appearance: none control ki native OS styling hata deta hai — phir tum apna background, border, aur (checkbox/radio ke liye) apna check indicator khud banate ho. Lekin dhyaan: native styling ke saath uski kuch pehchan bhi gayi — checked state ko :checked ke saath khud dikhana padega.
  • Custom checkbox/radio ka pattern: asli input ko visually chhupao (lekin display:none mat karo — wo focus aur accessibility dono tod deta hai; opacity/position wali visually-hidden technique use karo), saath wale styled span/box ko :checked aur :focus ke hisaab se style karo. Keyboard focus dikhna hi chahiye — warna keyboard user kho jayega.
  • Range slider ke thumb/track ko style karne ke liye vendor pseudo-elements lagte hain (::-webkit-slider-thumb, ::-moz-range-thumb) — standard tareeka abhi bhi seemit hai, dono engines ke liye alag rules likhne padte hain.
  • File input ka button hissa ::file-selector-button se style ho sakta hai — puraani “label se chhupao” wali trick aaj bhi chalti hai, lekin ye pseudo-element saaf tareeka hai.
  • Search input ka cancel (×) button ::-webkit-search-cancel-button se control hota hai — non-standard hai, sirf progressive enhancement ki tarah use karo.

14 · WAI-ARIA basics — accessibility & SEO: HTML sabke liye

Semantic HTML seekhne ke baad do sawal bachte hain: ye page har user ke liye kaam karega kya (accessibility), aur search engine ise sahi samjhega kya (SEO)? Dono ka 80% jawab wahi hai — sahi HTML. Jo extra hai, wo yahan hai.

WAI-ARIA basics — kab, kyun, aur pehla rule

  • ARIA (Accessible Rich Internet Applications) HTML ko wo extra semantics deta hai jo native elements me nahi hai — khaas taur par JS se bane custom widgets (tabs, menus, live updates) ke liye.
  • Pehla rule: No ARIA is better than bad ARIA. Aur dusra: agar kaam ke liye native element exist karta hai (<button>, <nav>, <dialog>…), to wahi use karo — us par ARIA lagane ki zaroorat hi nahi. ARIA native semantics ko badal sakta hai lekin behaviour nahi deta: role="button" wala div click to hoga, lekin keyboard se chalega nahi — wo tumhe khud banana padega.
  • Roles batate hain element hai kya: role="tablist", role="alert", role="search"… Semantic elements ke implicit roles hote hain (<nav> = navigation landmark) — unhe dobara likhna redundant hai.
  • States & properties (aria-*): aria-expanded (khula/band), aria-checked, aria-disabled, aria-selected — widget ki current haalat, jo JS ke saath update hoti rehti hai.
  • Naam aur description: aria-label (element ka accessible naam, jab visible label na ho — jaise sirf-icon wala button), aria-labelledby (kisi dusre element ke text ko naam banana), aria-describedby (extra description ki taraf ishara — form ki hint/error text ke liye perfect jodi).
  • aria-hidden="true" element ko accessibility tree se hata deta hai (sirf sajawati icons ke liye) — focusable cheez par kabhi mat lagao. aria-live="polite" / "assertive" wale region ka content badalne par screen reader use suna deta hai — toast messages, form errors, search results count ke liye (Section 8 ke custom-error pattern me yahi use hua tha).
  • Landmarks: <header>=banner, <nav>=navigation, <main>=main, <aside>=complementary, <footer>=contentinfo — screen reader users in landmarks ki list se seedha kisi hisse par jump karte hain. Isi liye page par <main> ek hi, aur har <nav> ko aria-label se alag pehchan (“Main”, “Breadcrumb”) deni chahiye jab ek se zyada hon.

Roz ke accessibility rules — HTML level par

  • Skip link: page ke sabse pehle ek <a href="#main"> “Skip to main content” rakho — keyboard users har page par poori navigation Tab karke nahi guzarna chahte.
  • Har interactive cheez keyboard se chale: Tab order DOM order jaisa hi rakho; tabindex ke positive values se order mat bigaado (Section 10). Focus dikhna chahiye — outline ko bina replacement ke kabhi mat hatao.
  • iframe ko title do — screen reader user ko pehle se pata chale andar kya hai. Har form control ka label (Section 8), har image ka alt decision (Section 5) — ye teeno is section ki neev hain, yahan dohra nahi rahe.
  • Rang hi akela signal na ho: error sirf laal border se mat batao — text message bhi do (Section 10 me <mark> par bhi yahi baat thi).
  • Language har jagah sahi: lang page par, aur beech me bhasha badle to us hisse par bhi (Section 1) — screen reader ka uchchaaran is par chalta hai.

SEO — HTML level par kya matter karta hai

  • Ek page, ek saaf topic: ek <h1>, sahi heading order, semantic sections — search engine page ka outline bilkul waisa hi padhta hai jaisa screen reader.
  • Title + description: har page ka unique, saaf <title> aur meta description (Section 1) — search results me yahi dikhta hai, isiliye click wahi decide karta hai.
  • Canonical + hreflang: duplicate content par rel="canonical", multi-language pages par rel="alternate" hreflang="…" (Section 11) — engine ko sahi version dikhao.
  • Structured data: content ko machine-readable banana — HTML me microdata (itemscope/itemprop, Section 10) ya head me JSON-LD script. Isi se search results me rich results (ratings, price, FAQ) milte hain. Vocabulary: schema.org.
  • Performance bhi ranking hai: loading="lazy" (fold ke neeche ki images/iframes par), decoding="async", sahi width/height (CLS — Section 5), aur sirf zaroori resource par preload (Section 11).
  • loading ke values: eager (default — turant load), lazy (viewport ke paas aane par load). Hero/LCP image par lazy kabhi nahi — wo page ki sabse badi image ko hi slow kar dega; uske liye fetchpriority="high" hai.

Accessibility aur SEO alag-alag jaadu nahi hain — dono usi ek cheez ka inaam hain: sahi semantic HTML. Jo page screen reader ke liye saaf hai, wahi crawler ke liye bhi saaf hai.

15 · Content categories — nesting rules, Quirks Mode, aur jo kabhi use nahi karna

Aakhri section teen cheezon ke liye hai: elements ki categories (kis element ke andar kya ja sakta hai, iska system), nesting ke pakke rules, aur obsolete/deprecated elements ki list — taaki purana code dikhe to pehchan sako, aur khud kabhi na likho.

Content categories — har element kisi category ka hai

  • Metadata content — document ke baare me: <title>, <meta>, <link>, <base>, <style>, <script>, <noscript>, <template>. Ye head me rehta hai.
  • Flow content — body me aane wali lagbhag har cheez (<p>, <div>, <ul>, <img>…). Sabse badi category.
  • Sectioning content — heading-outline ka scope banata hai: <article>, <section>, <nav>, <aside>. Heading content = <h1>–<h6> + <hgroup>.
  • Phrasing content — text aur uske andar ke inline elements: <span>, <em>, <strong>, <a>, <code>… <p> ke andar sirf phrasing content ja sakta hai — yahi agle subsection ke sabse bade rule ki jad hai.
  • Embedded content — dusra resource andar laata hai: <img>, <video>, <audio>, <iframe>, <canvas>, <svg>.
  • Interactive content — user se interaction ke liye: <a href>, <button>, <input>, <select>, <textarea>, <details>, controls wale <video>/<audio>.
  • Ek element kai categories me ho sakta hai. Kisi element ke page par MDN uski “Content categories” aur “Permitted content” deta hai — naya element seekhte time yehi do line padhna sabse tez tareeka hai.

Nesting ke pakke rules — invalid HTML ki asal wajah

  • <p> ke andar block element nahi: <p>…<div>…</div>…</p> likhoge to browser <p> ko div se pehle khud band kar dega — DOM tumhare source se alag banega, aur CSS/Debugging dono confuse karenge.
  • Interactive ke andar interactive nahi: <a> ke andar <button> ya dusra <a>, aur <button> ke andar koi bhi interactive element — dono invalid hain. Click par kya hoga, ye undefined jaisa hai.
  • List ka rule: <ul>/<ol> ke seedhe children sirf <li> (aur script/template) — nested list kisi <li> ke andar hi jayegi (Section 2).
  • Table ka rule: <table> ke andar sirf usi ke hisse — caption, colgroup, thead, tbody, tfoot, tr. Bahar ka content browser table se pehle/bahar dhakel deta hai (ise foster parenting kehte hain) — layout achanak bigadta hai aur wajah source me dikhti nahi.
  • Form ke andar form nahi (Section 8) aur heading ke andar heading nahi — dono purane rules, phir se isiliye ki ye validator me sabse zyada pakde jate hain.

Standards mode vs quirks mode, aur HTML aaj kya hai

  • <!doctype html> na ho ya galat ho to browser quirks mode me chala jata hai — purane browsers ki galtiyon ki nakal, jisme CSS box model jaisi cheezein alag behave karti hain. Sahi doctype = standards mode. Yahi Section 1 wale doctype ka asal kaam hai.

16 · SVG element reference — gradients, patterns, filters, masks, text, animation

Section 6 me SVG ki basics aayi thi — shapes aur HTML me add karne ke 4 tareeke. Jo wahan sirf naam se aaya tha (<feColorMatrix>, <mask>, patterns, filters, <text>), wo sab ab yahan poora cover hai — taaki SVG ke liye bhi bahar na jana pade.

defs, g, use, symbol — structure ke tools

  • <defs> = jo cheezein khud render nahi hotin, sirf dusri cheezon dwara reference hoti hain — gradients, patterns, filters, masks, clip paths sab yahi rakhe jate hain.
  • <g> = shapes ka group — ek hi transform/fill/stroke poore group par ek saath lagta hai.
  • <symbol> + <use href="#icon"> = icon system ka standard pattern: icon ek baar define karo, <use> se kahin bhi, kitni bhi baar dubara use karo (SVG sprite). <use> external file se bhi reference kar sakta hai — icons.svg#search — lekin external references same-origin hone chahiye.

Gradients — linearGradient / radialGradient

  • <tspan> = text ke ek hisse ko alag position/style dena. <textPath href="#path-id"> = text ko kisi <path> ke curve par chalana.
  • Ek pakki seema: SVG text khud wrap nahi hota — lambi line ko todna ho to khud <tspan> se alag lines banani padti hain.

Animation — <animate> aur CSS

  • <animate> kisi attribute ko samay ke saath badalta hai (SMIL animation) — bina JS ke simple motion ke liye. <animateTransform> transforms ke liye, <animateMotion> path par chalane ke liye (path <mpath> se reference hota hai).

  • Motion accessibility: prefers-reduced-motion ka samman karo — ye CSS SPA ka topic hai, lekin SVG animation banate time ye baat yahi se yaad rakho.

19 · ARIA — roles, naam ka hisaab, aur APG widget patterns

Section 14 me ARIA ki basics aayi thi. Jo wahan “poori spec alag topic hai” keh kar chhoda tha — roles ki categories, accessible name ka hisaab, aur complex widgets (tabs, combobox, grid) ke APG (ARIA Authoring Practices Guide) keyboard patterns — wo sab ab yahan hai.

Roles ki categories

  • Landmark roles: banner, navigation, main, complementary, contentinfo, search, form, region — semantic elements ke implicit roles yahi hain (Section 14); role alag se sirf tab lagao jab native element na ho.
  • Widget roles: button, checkbox, tab, tablist, tabpanel, combobox, listbox, option, menu, menuitem, tree, grid, slider, switch, dialog, alertdialog — ye sab custom widgets ke liye hain, aur har ek ke saath uska keyboard behaviour tumhe khud banana padta hai.
  • Live/document roles: alert, status, log (live regions), article, list, listitem, table/row/cell (document structure).
  • Abstract roles (composite, structure, widget…) kabhi khud use nahi hote — ye sirf spec ki buniyad hain.

Accessible name ka hisaab — kaunsi cheez jeet-ti hai

  • Har interactive element ka ek accessible name hota hai — screen reader wahi bolta hai. Wo is order me decide hota hai: (1) aria-labelledby → (2) aria-label → (3) native tareeka (<label>, alt, element ka apna text) → (4) title (sabse kamzor — aakhri sahara).
  • Isi liye: form control par asli <label> hamesha aria-label se behtar hai; aur ek hi element par aria-label aur visible text alag-alag mat rakho — voice-control users dikhne wala naam bolte hain, sunai kuch aur deta hai.
  • aria-describedby naam nahi, description deta hai — hint/error text ko control se jodne ke liye (Section 14).

APG ka ek bada usool — Tab bahar, arrows andar

  • Complex widget ke andar ghusna-nikalna Tab/Shift+Tab se hota hai; widget ke andar ghumna arrow keys se. Isiliye poora widget Tab order me sirf ek stop leta hai — andar ke items par roving tabindex: active item tabindex="0", baaki sab tabindex="-1", aur arrows ke saath ye 0 ghumta rehta hai.
  • Enter/Space = activate, Esc = band/wapas, Home/End = pehla/aakhri item. Ye model desktop apps jaisa hai — user ko yahi expect hota hai.

20 · Sending form data — form ke us paar kya hota hai (server-side)

Section 8 me form data bhejna cover hua tha (GET vs POST, enctype, security). Jo wahan “scope se bahar” keh kar chhoda tha — server par data receive/process karna — uska poora overview ab yahan hai, taaki form ki kahani dono taraf se complete ho. (Asli server programming ek alag bada topic hai; yahan wo sab hai jo ek HTML seekhne wale ko jaanna chahiye.)

Request ka safar — ek nazar me

  • Browser HTTP request bhejta hai → server (Apache, Nginx, IIS, Tomcat…) use receive karta hai → server-side code string ko key/value pairs me parse karta hai → data validate/sanitise hota hai → kaam hota hai (database me save, email, calculation) → server ek response bhejta hai, aam taur par ek HTML page jo browser render kar deta hai.
  • Form ke action par wahi file/program hona chahiye jo incoming data handle kar sake — isiliye galat action par 404 aana aam baat hai (Section 8).

PHP me data lena — $_GET / $_POST

  • PHP me GET data $_GET aur POST data $_POST globals me milta hai: $_POST["say"] = form ke name="say" wale control ki value.
  • User ka data page me wapas dikhane se pehle htmlspecialchars() se escape karo — warna user tumhare page me apna HTML/JS ghusa sakta hai (XSS). Ye Section 8 wale “saara data check + sanitise karo” rule ka haath-wala roop hai.
  • PHP browser me nahi chalta — file ko browser me khologe to download offer hoga. Local PHP server chahiye: MAMP / XAMPP.
<!-- PHP (server par chalta hai) -->
<?php
  $say = htmlspecialchars($_POST["say"]);
  $to  = htmlspecialchars($_POST["to"]);
  echo "Server bola: $say $to";  // → Hi Mom
?>

Python / Flask me data lena

  • Flask me route define karo: @app.route('/hello', methods=['GET','POST']) — phir request.form['say'] se POST data milta hai, aur jawab ek template se render hota hai: render_template('greeting.html', say=…, to=…). Templates templates/ folder me rehte hain.
  • Setup: pip3 install flask → script run karo → browser me localhost par page khulta hai.

Frameworks — asal duniya me koi scratch se nahi likhta

  • Server languages (Perl, Java, .Net, Ruby, PHP, Python, Node) seedha use karna aaj uncommon hai — frameworks common hain: Python — Django/Flask/web2py/py4web; Node — Express/Next.js/Nuxt/Remix; PHP — Laravel/Laminas/Symfony; Ruby — Rails; Java — Spring Boot.
  • Frameworks form handling, validation, templating aur security ke ready-made, tested tareeke dete hain — phir bhi forms “hamesha easy” nahi hote, lekin scratch se banane se kahin easy zaroor hain.
  • Front-end developer ke liye zaroori samajh bas itni: form ka name hi server ki key hai, method hi batata hai data kahan milega (URL ya body), aur server kabhi client par bharosa nahi karta.

Uploaded files server par — sandbox rule

  • Files binary data hain aur HTTP text protocol hai — isiliye bhejna special case tha (POST + multipart/form-data, Section 8). Receive karna usse bhi zyada dhyaan maangta hai.
  • Servers files/requests par size limits ke saath configure hote hain taaki abuse roka ja sake.
  • Uploaded files ko sandbox karo: alag server par store karo, access sirf alag subdomain se — ya aur behtar, poori alag domain se. User ki upload ki hui file ko main site ke bharose par kabhi mat rakho.
  • Aur aakhri baat Section 8 wali hi, kyunki yahi sabse important hai: competent third party se security review karwao — ye mat assume karo ki tumne saari problems dekh li hain.

24 · Interview FAQs — current era ke HTML interviews ke liye

Har sawal ke jawab short aur to-the-point hain — interview me bolne layak. Kisi par click karo, jawab khul jayega. Ye sawaal MDN ke concepts par hi based hain.

HTML kya hai? Ye programming language hai kya?

Nahi. HTML ek markup language hai — elements se content ko wrap karke structure aur meaning define karti hai. Isme logic/conditions/loops nahi hote; behaviour JavaScript ka kaam hai, styling CSS ka.

Void (empty) elements kya hote hain? Examples do.

Wo elements jinke andar content nahi hota aur closing tag bhi nahi: <img>, <br>, <input>, <meta>, <link>, <hr>, <source>. Trailing slash (<img />) optional hai. Dhyaan: <script> aur <textarea> void nahi hain.

<!doctype html> kya karta hai?

Ye ek required preamble hai jo document ko sahi (standards) mode me behave karwata hai. Historically ye error-checking rule sets se linked tha; aaj bas itna yaad rakho — har HTML document ki pehli line yahi hoti hai.

Ek page par kitne <h1> hone chahiye, aur kyun?

Ek. H1 page ka main title hai. Headings ek outline banate hain (h1 → h2 → h3, levels skip kiye bina) jise users scan karte hain, search engines weight dete hain, aur screen readers navigation ke liye use karte hain. H1 jaisa dikhne ke liye styled <span> use karna galat hai — semantics gayab ho jate hain.

<em> vs <i>, aur <strong> vs <b> — farak kya hai?

<em> = stress emphasis (meaning badalta hai, screen reader tone badalta hai); <strong> = importance. <i>/<b> presentational the, HTML5 ne inhe narrow roles diye: <i> = foreign words/technical terms, <b> = keywords/product names. Rule: element meaning se chuno, dikhne (italic/bold) se nahi.

Semantic HTML kya hai aur divs se better kyun hai?

Semantic elements apne content ka meaning batate hain — <header>, <nav>, <main>, <article>, <section>, <aside>, <footer>. Fayde: screen readers landmarks se navigate karte hain, SEO better, code maintainable. <div>/<span> non-semantic hain — sirf tab use karo jab koi semantic element fit na ho. “Div soup” accessibility aur maintenance dono kharab karta hai.

<article> vs <section> — kab kaunsa?

<article> = self-contained content jo akele distribute ho sake (blog post, comment). <section> = ek theme/functionality ka grouping, aam taur par heading ke saath. Dono ek dusre ke andar nest ho sakte hain.

Absolute vs relative URL me kya farak hai?

Absolute = poora URL (https://example.com/a/b.html) — external links ke liye zaroori. Relative = current document ke hisaab se (../pdfs/x.pdf, projects/index.html). Root-relative (/pdfs/x.pdf) domain ke hisaab se absolute hai aur linking file move hone par bhi nahi tootta. Apni site ke andar domain mat likho — portability bachi rehti hai.

Alt text kyun important hai? alt="" kab sahi hai?

Alt unke liye hai jo image nahi dekh sakte: screen-reader users, image load fail, text-only browsers, data-saving mode — aur search engines alt ko queries se match karte hain. alt="" (blank) pure decoration ke liye sahi hai (behtar: CSS background image). Content image ho to alt me wahi info do jo image gayab hone par kho jayegi; main text already describe kar raha ho to redundant alt mat do.

<img> par width/height dene se layout shift (CLS) kaise rukta hai?

HTML aur image alag requests me load hote hain. Bina dimensions ke browser ko image ka size aane tak nahi pata — image load hote hi neeche ka content jump karta hai (layout shift, kharab UX + performance metric). Width+height (actual size) dene se browser pehle se aspect-ratio ke hisaab se jagah reserve kar leta hai. Resize ke liye inhe mat use karo — uske liye CSS hai.

srcset/sizes vs <picture> — kab kaunsa?

srcset+sizes = resolution switching: same image, alag sizes — browser slot size × DPR ke hisaab se sabse sahi (barabar ya pehli badi) candidate chunta hai. <picture> = art direction: alag viewports par alag cropped images, pehli true media condition jeet ti hai, aur final <img> mandatory fallback hai. JS se swap nahi kar sakte — browser images ko CSS/JS se pehle preload kar leta hai.

Video ke liye multiple formats kyun dete hain?

Har browser alag containers (MP4, WebM, Ogg) aur unke andar ke codecs (H.264, VP9, AAC, Opus) support karta hai. <source> elements do — browser pehla supported play karega. type attribute dene se browser unsupported files turant skip karta hai. WebM + MP4 milkar lagbhag sab cover ho jata hai. MP4/H.264 patent-encumbered bhi hai, isliye open formats (WebM) ka apna mahatva hai.

iframe ka sandbox attribute kya karta hai? Clickjacking kya hai?

sandbox embedded content ki permissions restrict karta hai — bina value ke saari restrictions ON. Permissions ek-ek karke wapas do, aur allow-scripts + allow-same-origin same-origin content par ek saath kabhi nahi (content sandbox hata kar khud ko reload kar sakta hai). Clickjacking = invisible iframe se user ke clicks capture karke use gumrah karna/data churana; bachav: X-Frame-Options / CSP headers, jo tumhari site ko dusri sites me embed hone se rokte hain (MDN khud 'deny' use karta hai).

Tables page layout ke liye kyun nahi use karni chahiye?

Teen wajah: (1) accessibility — screen readers layout-table markup se confuse hote hain; (2) tag soup — markup complex, maintain/debug mushkil; (3) responsive nahi — tables content ke hisaab se size hoti hain, jabki semantic containers default 100% width lete hain. Tables sirf tabular data ke liye hain. Layout ke liye CSS (flex/grid) hai.

scope vs id/headers — table accessibility me kab kaunsa?

scope (col/row/colgroup/rowgroup) <th> par batata hai wo kin cells ka header hai — zyada tar tables ke liye kaafi. id+headers layered/grouped headers ke liye bilkul precise associations deta hai, lekin markup bahut badh jata hai aur galti ki gunjaish zero hoti hai.

GET vs POST — asli farak kya hai?

GET: empty body, form data URL me append hota hai (?say=Hi&to=Mom) — address bar me sabko dikhta hai, URL length limits hain. POST: data request body me jata hai, URL saaf rehta hai. Isi liye: password/sensitive data kabhi GET se nahi; bada data bhi POST se. Files bhejne ke liye POST + enctype="multipart/form-data" mandatory hai.

Sirf client-side validation kaafi kyun nahi hai?

Client-side validation (HTML attributes + JS) sirf UX hai — instant feedback deta hai. Lekin JS band ho sakta hai, client code alter ho sakta hai, malicious user network request ko seedha badal sakta hai. Server par aane wala data hamesha wahi check + sanitise karo — kabhi trust mat karo. Dono chahiye: client feedback ke liye, server safety ke liye.

required vs readonly vs disabled?

required = submit se pehle value honi hi chahiye, warna browser block + error. readonly = user modify nahi kar sakta, lekin value submit hoti hai. disabled = user interact nahi kar sakta (greyed out) aur value kabhi submit nahi hoti. Fieldset par disabled lagane se andar ke saare controls disable ho jate hain.

Explicit vs implicit label — kaunsa better hai?

Explicit: control par id, label par for — recommended, kyunki code complex hone par clear rehta hai aur saari assistive tech sahi samajhti hai. Implicit: control ko <label> ke andar nest karna — kaam karta hai, lekin kuch screen readers hamesha sahi handle nahi karte; implicit use karo to bhi for set karna best practice hai. Label click karne se control focus hota hai — mobile par hit area badhta hai.

Radio vs checkbox ki submission behaviour me kya farak hai?

Dono sirf checked hone par submit hote hain (unchecked → naam tak nahi jata; checked bina value ke → on jata hai). Radio: same name = ek group, sirf ek selected, submit par usi ki value; ek baar select ho to bina reset ke sab deselect nahi ho sakte. Checkbox: kai ek saath on ho sakte hain — har ek apna data item hai.

Browser galat HTML ko phir bhi kyun render kar deta hai?

Kyunki browsers HTML ko permissively parse karte hain — built-in rules galat markup ko interpret karke DOM me valid bana dete hain (galat nesting auto-correct ho jati hai). Web ka philosophy: content publish hona perfect syntax se zyada important hai. Lekin browser ka guess hamesha tumhari intention nahi hota — isliye sahi markup likhna aur W3C validator (validator.w3.org) se check karna zaroori hai.

W3C Validator kya karta hai? Errors fix karne ki strategy kya hai?

Validator (validator.w3.org) poora document lekar line+column ke saath errors report karta hai. Strategy: kuch errors fix karo, revalidate karo, repeat — ek error fix hone se kai dependent errors khud saaf ho jate hain (domino effect). Kuch messages misleading hote hain (jaise “Unclosed element ul” ki asal wajah missing quote wala unclosed <a> ho sakta hai).

Form me <button> ka default type kya hai? Reset button kyun avoid karte hain?

Form ke andar <button> ka default type submit hai. Sirf custom behaviour chahiye to type="button" lagana padta hai — ye common interview trap hai. Reset button isliye avoid: users galti se lambi bhari form submit karne ke bajaye poori saaf kar dete hain — terrible UX. Aur <button>, <input type="submit"> se better hai kyunki uska content full HTML ho sakta hai aur styling easy hai.

pattern, minlength, min/max — validation attributes kaise kaam karte hain?

pattern = regex jo value ko match karna chahiye (case-sensitive; empty + not-required value invalid nahi hoti). minlength/maxlength = text ki char length (sirf user-typed input par report hote hain, programmatically set value par nahi). min/max/step = number/date ki range aur increment (default step 1 — floats ke liye step="any"). Invalid element :invalid match karta hai aur browser submission block karke message dikhata hai.

Constraint Validation API kya hai?

JS API jo form controls ki validity ko programmatically access deti hai: validity object (valueMissing, typeMismatch, patternMismatch, tooShort, rangeOverflow…), validationMessage, checkValidity(), reportValidity(), aur setCustomValidity(msg) custom errors ke liye. Custom UI chahiye to novalidate lagakar native bubbles band karo aur errors khud aria-live region me dikhao.

<input> vs <textarea> — ek ajeeb sa farak batao.

<input> void element hai — closing tag nahi, default value value attribute se aati hai. <textarea> void nahi hai — closing tag zaroori, default value tags ke beech ke text se aati hai, aur andar likha HTML bhi plain text ki tarah render hota hai. Textarea multi-line hai (hard line breaks submit hote hain), cols/rows starting size dete hain.

Form data submit hone par server tak kaise pahunchta hai?

Controls ke name/value pairs bante hain (name=Bob&email=bob%40bob.com — special characters URL-encoded). GET me ye URL ke query string me, POST me request body me jate hain. Server string ko parse karke key/value list banata hai (PHP me $_GET/$_POST, Flask me request.form). Isiliye har control ka name hona zaroori hai — bina name wala control submit hi nahi hota.

Modern interview favourite: image ke liye HTML hi kyun, CSS background kyun nahi?

Jis image ka content me meaning hai wo <img> honi chahiye — use semantics, alt text, SEO milta hai. CSS background images invisible hoti hain screen readers ke liye, unka koi text equivalent nahi — isliye wo sirf decoration ke liye hain. Aur responsive behaviour (srcset) bhi HTML images ko hi milta hai, kyunki browser unhe CSS/JS parse hone se pehle preload kar leta hai.

<figure>/<figcaption> vs alt text — dono ka role alag kaise hai?

figcaption ek visible caption hai jo image aur caption ko semantically jodta hai — unhe bhi fayda deta hai jo image dekh sakte hain. alt image ka replacement hai — image gayab ho to uski jagah kaam karta hai. Dono me ek hi text mat rakho: image fail hone par dono saath dikhenge aur duplicate lagega.

Accessibility ke liye form banate time top 3 cheezein?

(1) Har control ka sahi label association (for/id) — bina label ke screen reader “edit text blank” bolta hai. (2) Radio/checkbox groups ko <fieldset> + <legend> me rakho — legend har control ke label ka hissa bankar bola jata hai. (3) Fake controls mat banao — asli <button>/<input> keyboard access aur focus outline free dete hain; required fields ko * se mark karke rule pehle hi bata do (WCAG).

<meter> vs <progress> — farak?

<meter> = ek fixed value jo known range (min–max) ke andar hai, low/high/optimum ke hisaab se green/yellow/red hota hai (jaise disk usage). <progress> = ek value jo samay ke saath badal rahi hai max ki taraf (jaise download %). Dono ke andar ka text fallback + screen readers ke liye hota hai.

<datalist> vs <select>?

<select> user ko sirf diye gaye options me se chunne par majboor karta hai. <datalist> kisi <input> ko suggestions deta hai (list attribute se bind) — user suggestion chun bhi sakta hai aur apna custom value bhi likh sakta hai. Browsers isme alag behave karte hain, isliye datalist ko progressive enhancement samjho.

<mark> kab use karte hain? <strong> se farak kya hai?

<mark> = relevance — text jo current activity ke liye marked/highlighted hai (search-term matches, ya quote ka wo hissa jispar khaas dhyaan dilana hai); browsers use default yellow highlight dete hain. <strong> = importance. Syntax highlighting ke liye mark nahi — <span> + CSS use karo.

Global attributes kya hote hain? Kuch examples do.

Wo attributes jo har HTML element par lag sakte hain: id (unique identifier), class (CSS/JS grouping), title (tooltip), lang (language), dir (text direction), hidden (render nahi hota), tabindex (focus order), contenteditable, draggable, spellcheck, data-*… Poori list MDN ke Global attributes reference me hai — aur is SPA ke “Global attributes” section me.

data-* attributes kya hain? JS me kaise padhte hain?

Custom data attributes — element par apna data rakhne ke liye, jab koi sahi standard attribute na ho. JS me element.dataset se access: data-user-id → dataset.userId (data- prefix hat-ta hai, kebab-case camelCase ban jata hai). Naam lowercase rakho, colon mat use karo. Aur yaad rakho: ye page source me sabko dikhta hai — sensitive data kabhi mat rakho.

Block vs inline elements — farak kya hai? Kya CSS se badal sakte hain?

Block (<p>, <div>, <h1>–<h6>, <section>): nayi line se shuru, by default poori available width, ek ke neeche ek lagte hain, width/height kaam karte hain; adjacent vertical margins collapse hote hain. Inline (<span>, <a>, <em>, <strong>): text ke flow me horizontally lagte hain, jagah kam ho to line break ho jata hai, width/height kaam nahi karte. Ye sirf default display hai — CSS display se kisi bhi element ka behaviour badal sakte ho, isliye semantic element hamesha meaning se chuno.

async vs defer — interview ka sabse pakka sawal.

Dono script ko parsing ke saath parallel download karte hain. async: download khatm hote hi execute — order ki koi guarantee nahi, parsing rukti hai. defer: parsing poora hone ke baad, document order me execute hota hai. type="module" ka default behaviour defer jaisa hi hai. DOM par depend karne wali apni script ke liye defer/module; independent analytics jaisi script ke liye async.

Modal banane ke liye <dialog> hi kyun? Div se kya problem hai?

<dialog> + showModal() free deta hai: baaki page inert, focus dialog ke andar, Esc se band, ::backdrop styling, aur <form method="dialog"> se bina JS ke close + returnValue. Div-modal me ye sab — focus trap, Esc handling, aria-modal — khud banana padta hai aur aksar galat banta hai.

<details> kya hai? Accordion ke liye JS kyun nahi chahiye?

<details> ek native disclosure widget hai — <summary> par click (ya keyboard) se content khulta/band hota hai, open attribute state batata hai. Browser khud keyboard support aur semantics deta hai, isliye simple FAQ/accordion ke liye JS library bekaar hai.

ARIA ka pehla rule kya hai?

“No ARIA is better than bad ARIA” — aur isse pehle: agar native element exist karta hai to wahi use karo. role="button" semantics to deta hai lekin keyboard behaviour nahi; wo khud banana padega. Galat ARIA screen reader user ko gumrah karta hai, jabki bina ARIA ke kam se kam content padha to jata hai.

:valid/:invalid se error styling kyun problematic hai? Behtar kya hai?

:invalid page load hote hi match ho jata hai — user ne kuch kiya hi nahi aur field laal dikhta hai. Behtar hai :user-invalid, jo user ke interact karne ke baad hi match hota hai. Yahi modern form UX ka standard pattern hai.

autocomplete ke tokens kyun matter karte hain? new-password vs current-password?

Tokens browser/password-manager ko batate hain field hai kya, taaki sahi saved value bhare — galat token par manager galat cheez bharta hai aur user ko haath se bharna padta hai. Login par current-password (purana bhara jaye), signup/change par new-password (naya suggest/store ho) — yahi farak manager ko samjhata hai.

Kaunse HTML elements deprecated/obsolete hain? 4 naam aur unke replacements.

<center> → CSS alignment; <font> → CSS fonts; <acronym> → <abbr>; <frame>/<frameset> → CSS layout / <iframe>; <marquee> → CSS animation. Browsers purani web ke liye inhe render karte rehte hain, lekin ye invalid hain — naya code me kabhi nahi.

<p> ke andar <div> rakha to kya hoga?

Browser <p> ko div se pehle khud band kar dega, kyunki <p> ke andar sirf phrasing content ja sakta hai. Result: DOM source se alag, CSS selectors ajeeb behave karenge, aur validator error dega. Yahi content-category/nesting rules ka sabse common real-world example hai.

Quirks mode kya hai? Doctype se iska kya lena-dena hai?

Sahi <!doctype html> na ho to browser quirks mode me purane browsers ki galtiyon ki nakal karta hai (box model jaise behaviours badal jate hain). Sahi doctype = standards mode. Isiliye doctype har document ki pehli line hona sirf formality nahi, behaviour ka switch hai.

SVG me gradient / pattern / filter kaise lagta hai?

Teeno <defs> me id ke saath define hote hain aur shape par url(#id) se reference hote hain: fill="url(#grad)", filter="url(#blur)", mask="url(#m)". Gradient ke andar <stop> elements rang ke points hain; filter ke andar fe* primitives ki chain (jaise <feGaussianBlur>, <feColorMatrix>) hoti hai. Reference missing ho to shape paint hi nahi hota — ye common interview/debugging point hai.

MathML kya hai? Formula ki image kyun nahi lagani chahiye?

MathML maths notation ke liye markup hai — formula <math> ke andar <mi> (variable), <mn> (number), <mo> (operator), <mfrac>, <msqrt>, <msup> jaise elements se banta hai, aur browser use natively render karta hai. Image wala formula na accessible hota hai, na zoom par saaf, na copy/search ho sakta hai; MathML teeno deta hai.

APG tabs pattern me keyboard kaisa chalta hai? Roving tabindex kya hai?

APG ka usool: Tab widget ke bahar, arrows widget ke andar. Poora tablist Tab order me ek hi stop leta hai — sirf active tab tabindex="0", baaki tabindex="-1"; ←/→ dabane par ye 0 ghumta hai (isi ko roving tabindex kehte hain), Home/End kinaron par le jate hain, aur activation automatic (arrow = select) ya manual (Enter/Space) ho sakta hai.

Server par form data kaise milta hai? Ek example do.

Server string ko key/value pairs me parse karta hai aur har control ko uske name se deta hai: PHP me $_POST["say"] / $_GET["say"], Flask me request.form['say']. Page me wapas dikhane se pehle escape zaroor karo (PHP me htmlspecialchars()) — warna XSS. Aur asal projects me ye kaam frameworks karte hain: Django/Flask, Express/Next.js, Laravel, Rails, Spring Boot.
