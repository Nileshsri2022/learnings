01Requirements aur Design

Functional Requirements

Ticket booking system me user ko kya-kya karna chahiye — ye 6 features hain jo har interview me pehle poochhe jate hain. Inhe yaad rakhne ka tareeka: Search → Dekho → Hold → Pay → Confirm → History.

  • Feature 1 — Event search: User event ko title, location aur date ke basis par search kar sake. Jaise "SpiderMan, Bangalore, 25 Jan".
  • Feature 2 — Event details dekhna: Event ki poori detail — seat map, description, venue, showtime metadata (kab, kahan, kitne baje, kis type ki seats).
  • Feature 3 — Booking karna: User event ke liye booking kar sake — seats select karo, temporary hold banao. Hold ka matlab: seat 10–15 minute ke liye tumhare naam par block, tab tak koi aur usey nahi le sakta.
  • Feature 4 — Payment aur confirm: Payment poora karke booking confirm karo — ticket issue hoga aur booking confirmation milegi.
  • Feature 5 — Double booking rokna: Ek hi showtime me ek hi seat do baar book na ho — ye is system ki sabse strong consistency requirement hai. Isi par poora deep dive (Section 06.3) hai.
  • Feature 6 — Booking status, history aur notifications: User apni booking ka status/history dekh sake aur confirmation ke liye email/SMS notification mile.
Interview tip: Requirements batate samay hamesha pehle functional, phir non-functional bolo — aur har feature ke saath ek example de do (jaise "SpiderMan search"). Interviewer ko lagta hai tumne real product socha hai, sirf theory nahi.

02Requirements aur Design

Non-Functional Requirements

System kitna bada hoga, kitna fast hoga, aur kahan consistency chahiye, kahan nahi — ye teen sawaal har system design interview ki jaan hain.

Scale aur Latency

PointNumber / Detail
Scale100M DAU (Daily Active Users). Search/browse ka traffic bahut zyada, aur popular movie release ya concert sale par massive spike aata hai.
Read vs WriteRead >> Write — 90% searches, 10% bookings. Matlab system read-heavy hai; search ko bahut fast aur cache-friendly banana hai.
LatencySearch/browse: <200ms low latency. Booking/confirm: correctness-first — yahan thoda slow chalega, lekin galat booking bilkul nahi chalegi. Availability ko consistency ke liye trade kar sakte ho.

Consistency (CAP Theorem)

CAP theorem ke hisaab se ek hi jagah dono cheezein nahi mil sakti — isliye system ko do hisso me baant do:

  • Seat booking — Strong consistency (CP): Ek showtime ki ek seat ke liye NO double booking. Yahan consistency ke liye availability sacrifice karna acceptable hai — agar lock nahi mila to user ko error dikhao, lekin do logon ko ek seat kabhi mat do.
  • Search index — Eventually consistent (AP): Event search CDC se Elasticsearch me sync hota hai, 1–2 second ka lag acceptable hai. Nayi movie search me 2 second der se dikhe to koi problem nahi.
Yaad rakhne wala line: "Booking me CP, search me AP." Ye ek line bolte hi interviewer samajh jata hai ki tumhe CAP ka practical use aata hai.

05Requirements aur Design

High Level Design

Poora system 8 components ka hai. Neeche wala design diagram hi is lesson ka HLD hai — isme har box ek service ya datastore hai, aur har arrow ek data flow.

Diagram me jo dikh raha hai, uska matlab: Clients sabse pehle API Gateway se baat karte hain. Search ka raasta Search Service → Elasticsearch ki taraf jata hai. Event ka data Event Service → Cassandra me rehta hai, aur wahan se CDC → Kafka → Elasticsearch ke through search index sync hota hai. Booking ka raasta Booking Service → MySQL/PostgreSQL ki taraf jata hai, jiske saath Redis holds aur locks ke liye laga hai. Payment bahar ke Payment Gateway se hota hai, aur booking confirm hote hi Kafka par events nikalte hain jo notifications, analytics aur invoicing ko chalate hain.

ComponentKaam
Clients → API GatewayAuthentication, authorization, rate limiting, routing — har request yahin se andar aati hai
Search Service → ElasticsearchFast event/venue search, location-based queries — read-heavy kaam
Event Service → CassandraEvents, venues, showtimes ka source of truth; CDC publish karta hai Elasticsearch ke liye
Booking Service → MySQL/PostgreSQLSeat hold aur booking confirmation — ACID transactions ke saath
RedisShort-lived seat holds (TTL 10–15 min), high-QPS availability checks, distributed locks
Payment GatewayExternal payment processor (Stripe/Razorpay) — payment processing
KafkaEvent streaming — async operations: notifications, analytics, invoicing
CDC (Change Data Capture)Event database → Kafka → Elasticsearch — search index sync

Datastore chunne ki logic: Events ke liye Cassandra (write-heavy catalog, wide rows, high availability), bookings ke liye MySQL/PostgreSQL (ACID chahiye — paise aur seats ka mamla hai), search ke liye Elasticsearch (full-text + location queries), holds/locks ke liye Redis (in-memory speed + TTL).

Step 1: Event Search (Elasticsearch)

User search karta hai to request kahan-kahan se guzarti hai — aur search itna fast (<200ms) kaise rehta hai.

Example request:

http
GET /v1/search?q=SpiderMan&location=Bangalore&date=2026-01-25

Search Service Elasticsearch ko ye query bhejta hai:

elasticsearch query
{
  "query": {
    "bool": {
      "must": [{ "match": { "name": "SpiderMan" } }],
      "filter": [
        { "term": { "location": "Bangalore" } },
        { "range": { "date": { "gte": "2026-01-25" } } }
      ]
    }
  },
  "sort": [{ "relevance": "desc" }],
  "size": 20
}
  • CDC pipeline: Cassandra Event DB → Kafka → Elasticsearch indexer — search 1–2 second ke andar up-to-date rehta hai.
  • Response: [{ event_id, movie_id, title, artist_list[], description, venue, seat_types[], showtimes[], poster_url }]
  • Cache: Popular searches Redis me cache karo, TTL = 10 min — repeated queries aur bhi fast.
Interview-favorite

CDC kaise kaam karta hai — ye interviewers ko bahut pasand hai. Jawaab: Cassandra commitlog → Debezium → Kafka → Elasticsearch indexer. Eventual consistency (1–2s lag) search ke liye acceptable hai. Source DB available rehta hai, chahe ES indexer fail ho jaye.

Step 2: Event Details aur Seat Map

06.3Deep Dive — Low Level

Step 3: Seat Hold (CRITICAL — Double Booking Rokna)

Ye poore lesson ka sabse important step hai. Interview me agar ek hi cheez poochhi jaye to yehi poochhi jayegi: 100 users ek hi seat ke liye lad rahe hon to double booking kaise rokte ho?

Request: POST /v1/booking/reserve with { show_id, seat_ids: ['L12', 'L13'], user_id }

Booking Service validation — 2 cheezein: (1) seats available hain ya nahi check karo, (2) race condition rokne ke liye distributed lock lo.

Step 1 — Redis distributed lock

Har seat ke liye: SETNX lock:seat:{show_id}:{seat_id} {hold_id} EX 30 (30 seconds). Agar koi bhi SETNX 0 return kare (lock pehle se hai) → matlab koi aur user is seat ko hold kar raha hai → abort karo aur return karo 'Seats being held by another user'.

Step 2 — Database check with pessimistic lock

sql
SELECT seat_id, status FROM seats
WHERE show_id = {show_id} AND seat_id IN ('L12', 'L13')
FOR UPDATE

FOR UPDATE row-level lock lagata hai — is transaction ke chalte koi aur transaction inhi rows ko read/modify nahi kar sakta.

Step 3 — Validate saari seats available hain

Agar koi bhi seat ka status AVAILABLE nahi hai → Redis locks release karo, return karo 'Seats not available'.

Step 4 — Hold banao Redis me (fast check)

redis
SET hold:{hold_id} '{show_id, seat_ids, user_id, created_at}' EX 900   -- 15 min TTL
SET seat_hold:{show_id}:{seat_id} {hold_id} EX 900   -- har seat ke liye

Step 5 — Hold banao Database me (source of truth)

sql
BEGIN TRANSACTION;
INSERT INTO seat_holds (hold_id, show_id, seat_ids, user_id, expires_at, status)
VALUES ({hold_id}, {show_id}, ARRAY['L12','L13'], {user_id},
        NOW() + INTERVAL '15 minutes', 'PENDING');
UPDATE seats SET status = 'HELD', held_by = {hold_id}, held_at = NOW()
WHERE show_id = {show_id} AND seat_id IN ('L12', 'L13');
COMMIT;

Step 6 — Redis locks release karo

Har seat ke liye: DEL lock:seat:{show_id}:{seat_id}

Response: { hold_id, expires_at: '2026-01-25T15:30:00Z', total_amount: 600, seats: ['L12', 'L13'] }

Redis aur DB dono kyun? Redis fast concurrent hold attempts ke liye (10ms vs DB 50ms), DB ACID guarantees ke saath source of truth hai, aur Redis hold 15 min baad apne aap expire ho jata hai (manual cleanup nahi chahiye).

Critical — Warning

NEVER use Redis alone for seat booking. Hamesha database FOR UPDATE lock se validate karo. Redis fast rejection deta hai, lekin DB ACID guarantees ke saath source of truth hai. Dono ke bina, concurrent requests me double booking ho jayegi.

Warning

NEVER trust client-provided seat status. Hamesha DB/Redis se FOR UPDATE lock ke saath fetch karo. Malicious users request modify karke already-booked seats claim kar sakte hain. Server-side validation mandatory hai.

Interview-favorite

Interviewers HAMESHA poochhte hain: "Double booking kaise rokte ho?" Jawaab me 4 cheezein honi chahiye: (1) Redis SETNX distributed lock fast rejection ke liye, (2) PostgreSQL SELECT FOR UPDATE transaction ke andar ACID ke liye, (3) Redis lock auto-expire (30s) taaki deadlock na ho, (4) Dono mechanisms milkar zero double bookings guarantee karte hain.

06.4Deep Dive — Low Level

Step 4: Payment Processing with Idempotency

Payment me sabse bada darr: user se paise do baar kat jayein ya retry par do bookings ban jayein. Iska ek hi ilaaj hai — idempotency.

Request: POST /v1/booking/confirm with { hold_id, payment_method_id, idempotency_key: {hold_id} } — idempotency_key retry par double payment rokta hai.

Validation (confirm se pehle)

  1. Hold exists karta hai aur expire nahi hua: SELECT status, expires_at FROM seat_holds WHERE hold_id = {hold_id} — expire ho ya status PENDING na ho → error return karo.
  2. Payment pehle se process to nahi hua: SELECT * FROM bookings WHERE hold_id = {hold_id} — agar exists kare → existing booking_id return karo (idempotency).

Payment flow

  1. Payment intent banao Payment Gateway par: stripe.paymentIntents.create({ amount: 600, currency: 'INR', customer_id, metadata: { hold_id, user_id }, idempotency_key: {hold_id} })
  2. payment_url client ko return karo, user payment complete karta hai.

Payment webhook

POST /webhooks/payment with { hold_id, payment_id, status: 'success', amount } — (1) Signature validate karo (security), (2) Idempotency check: SELECT * FROM bookings WHERE payment_id = {payment_id} — agar exists kare to 200 return karo (already processed).

Booking atomically confirm karo

sql
BEGIN TRANSACTION;
INSERT INTO bookings (booking_id, hold_id, user_id, show_id, seat_ids,
  payment_id, total_amount, status, confirmed_at)
VALUES ({booking_id}, {hold_id}, {user_id}, {show_id}, ARRAY['L12','L13'],
  {payment_id}, 600, 'CONFIRMED', NOW());
UPDATE seats SET status = 'BOOKED', booked_by = {user_id}, booking_id = {booking_id}
WHERE show_id = {show_id} AND seat_id IN ('L12', 'L13');
UPDATE seat_holds SET status = 'CONFIRMED' WHERE hold_id = {hold_id};
COMMIT;

Uske baad: Redis hold delete karo — DEL hold:{hold_id}, har seat ke liye DEL seat_hold:{show_id}:{seat_id}. Kafka event publish karo: topic 'booking.confirmed' with { booking_id, user_id, show_id, event_id, seat_ids, amount, timestamp }.

Response: { booking_id, qr_code_url, booking_details: {...} }

Warning

NEVER skip payment idempotency. hold_id ko idempotency_key banao + bookings(hold_id) par UNIQUE constraint lagao. Iske bina, timeout ke baad payment retry par double booking aur double charge ho jayega.

06.5Deep Dive — Low Level

Step 5: Hold Expiry aur Auto-Release

User ne seats hold ki, payment nahi kiya, 15 minute nikal gaye — to seats apne aap wapas available honi chahiye. Iske liye do mechanisms ek saath kaam karte hain.

Redis TTL expiry (automatic)

15 minute baad Redis apne aap hold:{hold_id} aur seat_hold:{show_id}:{seat_id} keys delete kar deta hai — koi manual cleanup nahi.

Database sweeper job (har 1 minute)

Expired holds dhoondho:

sql
SELECT hold_id, show_id, seat_ids FROM seat_holds
WHERE status = 'PENDING' AND expires_at < NOW()

Har expired hold ke liye seats release karo:

sql
BEGIN TRANSACTION;
UPDATE seats SET status = 'AVAILABLE', held_by = NULL
WHERE show_id = {show_id} AND seat_id = ANY({seat_ids}) AND status = 'HELD';
UPDATE seat_holds SET status = 'EXPIRED' WHERE hold_id = {hold_id};
COMMIT;

Redis seat map cache invalidate karo: DEL seat_map:{show_id} — taaki agli baar fresh map bane.

Sweeper kyun chahiye? Redis expiry se DB update nahi hota — sweeper ensure karta hai ki DB aur Redis eventually consistent rahein. Aam taur par 1–2 min ka lag acceptable hai.

Tip

Hold expiry optimization: Redis TTL 15 min baad apne aap delete karta hai (zero overhead), DB sweeper har 1 min me sync karta hai, 1–2 min ka lag acceptable hai kyunki user ko expiry Redis se turant dikh jati hai. Isse har hold ko check karne ke mukable 90% cleanup overhead bachta hai.

Interview-favorite

Zaroor samjhana: Redis TTL + DB sweeper ka combination kyun? Redis automatic expiry deta hai bina kisi code ke, DB sweeper source of truth ke saath eventual consistency ensure karta hai, aur system tab bhi kaam karta hai jab sweeper temporarily fail ho jaye (Redis memory to saaf kar hi deta hai).

Step 6: Notification Flow (Kafka Event-Driven)

Booking confirm hote hi kaam khatm nahi hota — ticket, email, SMS, analytics, invoice — ye sab Kafka events se async hota hai, taaki booking ka response fast rahe.

Kafka topics: 'booking.confirmed', 'booking.cancelled', 'payment.failed'

Notification Service

'booking.confirmed' events consume karta hai: (1) User DB se user ka email/phone fetch karo, (2) QR code ke saath ticket generate karo — booking_id QR me encode hota hai, (3) SendGrid/SES se email bhejo — booking details + QR code attachment, (4) Twilio se SMS bhejo — booking confirmation aur show details.

Analytics Service

Wahi events consume karke track karta hai: booking conversion rate, popular shows, revenue per show, user behavior.

Invoice Service

Invoice PDF generate karta hai booking details ke saath, S3 me store karta hai, aur download link email se bhejta hai.

Kyunki Kafka beech me hai: Booking Service ko ye nahi pata ki email gaya ya nahi — wo sirf event publish karta hai. Notification Service down ho jaye to bhi booking nahi rukti; Kafka events ko baad me replay kar sakta hai. Yehi decoupling hai.

06.8Deep Dive — Low Level

Step 8: Cancellation aur Refund

Cancel karna bhi booking jitna hi careful kaam hai — refund policy, seat release aur idempotency teeno ek saath handle karne hote hain.

Request: DELETE /v1/booking/{booking_id} with { reason: 'user_requested' }

Validation

  1. Booking usi user ki hai ya nahi check karo.
  2. Cancellation policy: show_time − NOW() < 2 hours → no refund; < 24 hours → 50% refund; >= 24 hours → 100% refund.

Cancellation process (atomic)

sql
BEGIN TRANSACTION;
UPDATE bookings SET status = 'CANCELLED', cancelled_at = NOW(),
  refund_amount = {calculated_refund}
WHERE booking_id = {booking_id};
UPDATE seats SET status = 'AVAILABLE', booked_by = NULL, booking_id = NULL
WHERE booking_id = {booking_id};
COMMIT;

Refund initiate karo

Payment Gateway call karo: stripe.refunds.create({ payment_intent_id, amount: refund_amount })

Uske baad: Kafka event publish karo — topic 'booking.cancelled'. Notification bhejo — cancellation aur refund timeline ka email/SMS confirmation.

Duplicate cancel se bachav: Agar booking ka status pehle se CANCELLED hai to existing refund_id return karo — dobara refund mat karo. Refund API me booking_id ko idempotency key banao aur refunds(booking_id) par UNIQUE constraint lagao.

06.9Deep Dive — Low Level

Ye wo scenario hai jo interviewer sabse zyada pasand karta hai — 100 users, aakhiri 2 seats, ek hi millisecond. Ise timeline ke saath samjho.

Scenario: 100 users aakhiri 2 seats (L12, L13) book karne ki koshish karte hain, subah 10:00:00 baje, ek saath.

Q1: 100 users aakhiri seat ke liye ladein to double booking kaise rokte ho?

Ye is lesson ka number-1 interview question hai. Jawaab 5 steps me do — Redis lock + DB lock, dono.

Multi-layer approach

  1. Redis SETNX lock DB check se PEHLE: Har seat ke liye SETNX lock:seat:{show_id}:{seat_id} {hold_id} EX 30. Agar koi bhi 0 return kare (lock pehle se hai) → turant abort karo, 'Seats being held'. Ye fast rejection hai (<10ms) — expensive DB operations se pehle hi 99 users bahar.
  2. Agar saare locks mil gaye: DB query karo pessimistic lock ke saath: SELECT seat_id, status FROM seats WHERE show_id={show_id} AND seat_id IN (...) FOR UPDATE — ye row-level exclusive lock concurrent transactions ko wahi rows read karne se rokta hai.
  3. Validate karo saari seats AVAILABLE hain: Nahi hain to Redis locks release karo, return karo 'Seats not available'.
  4. Hold atomically banao: BEGIN TRANSACTION; INSERT INTO seat_holds (...); UPDATE seats SET status='HELD', held_by={hold_id} WHERE seat_id IN (...); COMMIT;
  5. Redis locks release karo: Har seat ke liye DEL lock:seat:...

Dono mechanisms kyun?

  • Redis fast concurrent rejection deta hai (100 users → 1 aage badhta hai, 99 ko <10ms me reject).
  • PostgreSQL FOR UPDATE transaction ke andar ACID + phantom reads se bachav deta hai.
  • Redis lock TTL = 30s — service crash ho jaye to apne aap release (koi deadlock nahi).

Example timeline

T=0ms: 100 users request bhejte hain. T=5ms: User A saare Redis locks le leta hai, Users B–Z fail (rejected). T=50ms: User A DB transaction aur hold creation complete karta hai. T=55ms: User A Redis locks release karta hai. T=60ms: Retry karne wale users ab attempt kar sakte hain — lekin seats ka status DB me 'HELD' hai.

Result: Zero double bookings, haarne walon ko fast rejection, crash se automatic recovery.

Q2: Redis holds with TTL kyun — sirf database expiry kyun nahi?

Redis TTL zero overhead automatic cleanup deta hai — aur speed bhi. 6 points me jawaab do.

  1. Performance: Redis seat availability checks ke liye 100K+ ops/sec handle karta hai, PostgreSQL ~10K ops/sec. Ticket sale spike me lakhon users ek saath seat maps check karte hain — Redis memory se <1ms me serve karta hai, DB 10–50ms leta hai.
  2. Auto-expiry: SET hold:{hold_id} {...} EX 900 15 minute baad apne aap delete ho jata hai — Redis cleanup ke liye koi background job nahi chahiye. DB me iske liye har 1 min me chalne wala sweeper job chahiye hota hai.
  3. Fast distributed lock: SETNX <1ms me atomic check-and-set karta hai multiple API servers ke beech — concurrent bookings me race condition rokta hai.
  4. Eventual consistency acceptable: Redis hold 15:00:00 par expire hota hai, DB sweeper 15:01:30 par seats ko AVAILABLE karta hai — 1–2 min ka lag acceptable hai kyunki user ko 'Hold expired' Redis se turant dikh jata hai.
  5. DB phir bhi source of truth: Redis fast check layer hai, DB ke paas ACID guarantees ke saath authoritative state hai — payment confirmation hamesha DB check karta hai, Redis nahi.
  6. Failure handling: Redis crash ho jaye to system DB-only mode me chalta hai (slow lekin functional). DB crash ho jaye to bookings rukti hain, lekin Redis me existing holds conflicts rokte rehte hain.

Trade-off: Network partition me Redis holds DB se drift kar sakte hain — sweeper job minutes me reconcile karta hai — lekin final booking confirmation hamesha DB ke against FOR UPDATE lock se validate hoti hai.

Storage: 1 hold Redis me ~500 bytes, 10K concurrent holds = 5MB (bahut chhota) — DB transaction logs ke mukable jo continuously badhte hain. Combination deta hai: speed (Redis) + durability (DB) + automatic cleanup (TTL).

Q3: CDC pipeline kaise kaam karta hai (Event DB → Elasticsearch)?

Change Data Capture search index ko fresh rakhta hai — 8 steps me poora flow.

  1. Source: Cassandra database events, venues, showtimes ka source of truth hai. Admin Event Service se events create/update karta hai jo Cassandra me likhta hai.
  2. CDC mechanism: Cassandra commitlog saare INSERT/UPDATE/DELETE operations capture karta hai.   3. Kafka as buffer: Durability aur replay capability deta hai, multiple consumers same events process kar sakte hain, Elasticsearch indexer slow ho to backpressure handle karta hai.
  4. Elasticsearch indexer consumer: Consumer group 'es-indexer' ke saath 'event.changes' topic subscribe karta hai. Operation insert/update ho to es.index(index='events', id=event.event_id, body=event.data), delete ho to es.delete(...). Bulk API use karta hai — 100 events batch karke har 2 second me index karta hai.
  5. Error handling: Failed indexing → exponential backoff ke saath retry. Persistent failures → dead letter queue (DLQ) me manual investigation ke liye. Consumer lag monitor karo — lag >1000 events ho to alert.
  6. Consistency: Eventual consistency, aam taur par 1–2 second ka lag (Cassandra write → Kafka publish → ES index). Search ko real-time nahi chahiye — user 2 second wait kar sakta hai nayi movie search me dekhne ke liye.

Q4: Payment failures aur refunds kaise handle karte ho?

Payment me 8 cheezein handle karni hoti hain — timeout, decline, refund, partial refund, duplicate webhook, aur reconciliation.

  1. Payment timeout: User confirm karta hai → Payment Gateway process karta hai → webhook delayed/lost ho jata hai. Hold 15 minute me expire hota hai. Background job check karta hai: SELECT hold_id, user_id FROM seat_holds WHERE status='PENDING' AND created_at < NOW() - INTERVAL '15 minutes' — payment na aaye to seats release karo (UPDATE seats SET status='AVAILABLE' WHERE held_by={hold_id}), 'payment.timeout' event publish karo → Notification Service 'Payment failed' email bhejta hai.
  2. Payment declined: Stripe webhook: POST /webhooks/payment with {status: 'failed', error: 'card_declined'} → (a) Idempotency check (duplicate webhooks handle karo), (b) Hold release karo: UPDATE seat_holds SET status='EXPIRED', UPDATE seats SET status='AVAILABLE', (c) 'payment.failed' publish karo → user ko reason + retry option notify karo.
  3. Refund request: User cancel karta hai: DELETE /v1/booking/{booking_id} → validate karo: (a) Booking user ki hai, (b) Cancellation policy: show_time − NOW() > 24 hours → 100% refund, 2–24 hours → 50% refund, <2 hours → no refund, (c) Duplicate cancellation roko: status CANCELLED ho to existing refund_id return karo.
  4. Refund atomically process karo: BEGIN TRANSACTION; UPDATE bookings SET status='CANCELLED', refund_amount={calculated}, cancelled_at=NOW(); UPDATE seats SET status='AVAILABLE', booked_by=NULL, booking_id=NULL; INSERT INTO refunds (refund_id, booking_id, amount, status='PENDING'); COMMIT;
  5. Async refund via Payment Gateway: stripe.refunds.create({payment_intent_id, amount}) — Stripe process karta hai (5–7 business days), webhook confirm karta hai: POST /webhooks/refund with {status: 'succeeded'} → UPDATE refunds SET status='COMPLETED'.
  6. Idempotency har jagah: Refund API ke liye booking_id ko idempotency_key banao — user 'Cancel' multiple baar click kare to bhi double refund nahi. refunds(booking_id) par UNIQUE constraint single refund per booking ensure karta hai.
  7. Partial refunds: 50% refund policy ho to original amount ka 50% ka payment intent banao, track karo: refunds.refund_type='partial', original_amount, refunded_amount.
  8. Webhook failures: Stripe webhook 3 baar exponential backoff ke saath retry karta hai. Sab fail ho jayein to Stripe API poll karo: stripe.refunds.retrieve({refund_id}). Reconciliation job daily chalta hai: bookings DB ko Stripe records se compare karta hai, discrepancies ko manual review ke liye flag karta hai.

Edge cases: Concurrent cancellation + showtime shuru ho gaya → cancellation reject karo ('Show already started'). User refund processing ke dauraan cancel kare → idempotency duplicate rokti hai, refund 'Already processing' dikhata hai.

Minimum interaction time: seat map par reservation se pehle 5 seconds (humans ko choose karne me time lagta hai). Mouse movement tracking: bots ke movement patterns unnatural hote hain ya bilkul nahi hote.
  5. Account verification: Booking se pehle email verification required. High-value events (concerts, sports finals) ke liye phone verification. Holds allow karne se pehle payment method pre-authorization (valid card verify karo).
  6. Progressive delays: Pehla hold attempt: immediate. Doosra attempt (cancellation ke baad): 30 second wait. Teesra attempt: 60 second wait — exponentially badhta hai. Jo accounts baar-baar hold karke bina payment ke release karte hain, unhe penalize karo.
  7. Automated bot detection: Machine learning model train karo: successful vs abandoned bookings, time patterns (bots 24/7 active, humans shaam ko concentrated), API access patterns (bots predictable sequences follow karte hain). Suspicious accounts flag karo: {suspicious_score: 0.85} → additional verification required.
  8. Hold limits: Per show per user maximum 10 seats (poore sections hoard nahi kar sakte). Saare shows me maximum 3 concurrent holds. Expired hold penalty: hold 3 baar lagatar expire ho to agle attempt se pehle 1 hour cooldown.
  9. Dynamic pricing during detection: Bot activity detect ho (jaise 5 min me 50 IPs se 100+ hold attempts) to temporarily prices 10–20% badhao (bots specific price points ke liye programmed hote hain). 'Verified user' discount enable karo (history wale real users ko original price).
  10. Post-booking validation: Payment ke baad verify karo: booking pattern normal hai, user IP payment card ke country se match karta hai, email/phone reachable hai (verification code bhejo). Suspicious bookings ticket issuance se pehle manual review ke liye flag karo.
  11. Enforcement: Detected bots: IP + fingerprint + account 24 hours ke liye block karo. Repeat offenders: permanent ban + bookings void karo. Payment processors ke saath collaborate karo: bot fingerprints platforms ke beech share karo.
  12. Honeypot seats: Fake 'available' seats inject karo jo sirf bots ko dikhte hain (HTML me hidden, render nahi hote). Honeypot seats select karne wale bots → turant flag aur block. Real users par koi asar nahi.

Real example: Taylor Swift concert — pehle minute me 500 IPs se 50K reservation attempts detect hue. Bot prevention activate hua: CAPTCHA + rate limiting + fingerprinting. Result: 95% bot requests blocked, real fans ko tickets mile, bots fake seats par resources waste karte rahe. Trade-off: Legitimate users ko thodi friction ho sakti hai (CAPTCHA, wait times), lekin high-demand events me fair access ke liye ye zaroori hai.

Q8: Booking transaction ke beech database down ho jaye to kya hota hai?

DB failure ka jawaab 12 points me — architecture, detection, failover, idempotency, aur recovery validation.

  1. Architecture: Primary DB (us-east-1) saare writes ke liye. Replica 1 (us-east-1, same region) synchronous replication ke saath (lag <1 second). Replica 2 (us-west-2, cross-region) asynchronous replication ke saath (lag <10 seconds). Health checks har 30 second me: TCP connect + simple query (SELECT 1).
  2. Failure detection: Primary 3 consecutive health checks fail kare (90 seconds), ya connection pool exhaust ho (saare connections timeout), ya application ko connection errors ya transaction rollbacks dikhein.
  3. Automatic failover: Orchestrator ya cloud-managed service (AWS RDS, Google Cloud SQL) failure detect karta hai. Replica 1 ko primary promote karta hai (2–3 minutes). DNS update hota hai naye primary endpoint par. Application automatically reconnect karta hai (connection pool retry logic).
  4. Transaction failure ke dauraan: User submit karta hai: POST /v1/booking/confirm with {hold_id, payment} → (a) Booking Service attempt karta hai: BEGIN TRANSACTION, (b) Database beech me mar jata hai → connection lost, (c) Transaction automatically rollback hoti hai (koi partial state nahi), (d) Service exception catch karta hai: DatabaseConnectionError, (e) 503 Service Unavailable return karta hai: { error: 'Temporary service disruption, please retry', retry_after: 60 }.
  5. Idempotency protection: Client 60 second baad same hold_id aur idempotency_key ke saath retry karta hai. Tab tak failover complete ho chuka hota hai (naya primary active). Retry succeed karta hai: SELECT * FROM bookings WHERE hold_id={hold_id} — agar exists kare (somehow failure se pehle complete ho gaya) to existing booking_id return karo, nahi to normally process karo.
  6. Outage ke dauraan Redis holds: Redis me seat holds kaam karte rehte hain. Users seats select karke holds bana sakte hain (Redis available rehta hai). Holds stored rehte hain lekin confirm nahi ho sakte (payment ke liye DB chahiye). Hold TTL (15 min) seats ko automatically release kar deta hai agar DB recover na ho.
  7. Outage ke dauraan read queries: Seat availability checks read replicas par route hote hain (unaffected). Search, browse, view events normally chalte hain (Elasticsearch + replicas se serve hote hain). Sirf bookings/payments blocked hote hain (write operations ke liye primary chahiye).
  8. Failover ke baad data consistency: Synchronous replica promote ho to zero data loss (last committed transaction tak). Asynchronous replica promote ho to last 1–10 second ke transactions ka potential loss. Reconciliation: Redis holds vs DB bookings check karo, orphaned holds cleanup karo.
  9. Payment handling: Payment Gateway ne payment process kar diya → user charged ho gaya lekin booking nahi bani. Solution: recovery ke baad reconciliation job chalta hai, orphaned payments dhoondhta hai: SELECT p.payment_id FROM payments p LEFT JOIN bookings b ON p.hold_id = b.hold_id WHERE b.booking_id IS NULL — bookings retroactively banata hai ya seats available na hon to refund karta hai.
  10. User communication: Real-time status: UI me dikhao 'System temporarily unavailable, retrying...'. Notifications: pending holds wale users ko temporary disruption ka email bhejo. Compensation: affected users ko discount ya free booking fee offer karo.
  11. Recovery validation: Failover ke baad data integrity verify karo: seat status consistency check karo, verify karo koi double booking nahi hui, Redis vs DB state reconcile karo, failure window ke transactions ka manual review karo.
  12. Preventive measures: Database connection pooling: retries ke saath connection losses gracefully handle karo. Circuit breaker pattern: failure rate >10% ho to booking attempts temporarily block karo. Graceful degradation: DB issues ke dauraan 'View only' mode dikhao (search kaam karta hai, bookings disabled).

Real scenario: Database primary raat 8:00 PM (peak time) par fail hota hai. Failover 8:01:30 PM par trigger hota hai, replica 8:03 PM par promote hota hai, bookings 8:04 PM par resume hoti hain. Impact: 3–4 minute ki booking unavailability, 20 users mid-transaction affected (sab retry se succeed hue), zero double bookings, zero lost payments (idempotency + reconciliation). Cost: Multi-region setup 30–40% infrastructure cost badhata hai — revenue loss se insurance hai (1 hour outage = $100K+ lost bookings).

Interview-favorite

Zaroor batana: Database failover strategy. Primary + synchronous replica (lag <1s) + async replica (lag <10s). Failover 2–3 minute me, zero data loss. Idempotency ensure karti hai ki recovery ke baad retries kaam karein.

Q9: QR code generation aur venue entry verification kaise implement karte ho?

QR code sirf ek image nahi hai — ye encrypted booking proof hai, jise venue gate par ek hi baar scan kiya ja sakta hai.

  1. QR code content: Encrypted booking_id + show_id + user_id + timestamp. Encryption: AES-256 with secret key (sirf backend aur venue scanners ke paas key hai). Format: encrypted_data = encrypt(json_string), QR me hota hai: {enc: base64(encrypted_data), v: 'v1'} — v future schema changes ke liye version hai.
  2. Generation on booking confirmation: Successful payment aur booking creation ke baad QR generate karo: data = json.dumps({booking_id, show_id, user_id, timestamp}), encrypted = aes_encrypt(data, secret_key), qr_img = qrcode.make(encrypted), S3 par upload karo: s3.upload_file(qr_img, bucket, f'qr_codes/{booking_id}.png'), DB me URL store karo: UPDATE bookings SET qr_code_url={s3_url} WHERE booking_id={booking_id}.
  3. Delivery to user: Email: QR code image + booking details attach karo. Mobile app: 'My Tickets' section me QR dikhao (offline kaam karta hai — QR locally stored hai). SMS: QR wale web page ka link bhejo.
  4. Venue entry flow: User gate par QR dikhata hai, venue staff mobile app ya handheld scanner se scan karta hai. Scanner bhejta hai: POST /v1/verify/qr with {qr_data, venue_id, timestamp}. Backend decrypt karta hai: booking_data = aes_decrypt(qr_data, secret_key). Validate karta hai: (a) Decryption successful (invalid QR → error), (b) Booking exists karti hai: SELECT * FROM bookings WHERE booking_id={booking_id}, (c) Booking confirmed hai: status='CONFIRMED', (d) Show abhi hua nahi hai: showtime > NOW(), (e) Pehle se checked in nahi hai: checked_in_at IS NULL, (f) Sahi venue hai: showtime.venue_id request wale venue_id se match karta hai.
  5. Check-in atomically: BEGIN TRANSACTION; UPDATE bookings SET checked_in_at=NOW(), checked_in_venue={venue_id} WHERE booking_id={booking_id} AND checked_in_at IS NULL; if affected_rows == 0: ROLLBACK; return 'Already checked in or invalid'; COMMIT; Response: {valid: true, user_name, show_name, seat_ids, booking_id}.
  6. Duplicate scan prevention: bookings(booking_id, checked_in_at) par UNIQUE constraint single check-in ensure karta hai. Dobara scan karne ki koshish (user do baar enter karna chahe) → query checked_in_at != NULL return karti hai → reject karo: 'Already checked in at {time}'. Fraud detection: ek hi QR multiple venues par scan ho to security review ke liye flag karo.
  7. Offline verification (optional): Poor connectivity wale venues ke liye poori booking details QR me embed karo: {booking_id, user_name, show_id, seat_ids, show_time, signature}. Signature: HMAC-SHA256(booking_data, secret_key) authenticity verify karta hai. Venue scanner signature ko offline validate karta hai, connectivity wapas aane par check-ins sync karta hai.
  8. QR code security features: Expiry: QR showtime ke 2 hours baad expire hota hai (reuse roko). One-time use: successful scan ke baad invalid ho jata hai. Tamper detection: koi bhi modification HMAC signature ko invalid kar deta hai. Rate limiting: per QR per minute maximum 5 scan attempts (brute force roko).
  9. Multiple tickets per booking: User 3 seats book kare to poori booking ke liye single QR code. Scanner dikhata hai: 'Booking for 3 seats: L12, L13, L14'. Entry coordinator 3 logon ko gate se andar jaane deta hai. Alternative: har seat ke liye alag QR generate karo (zyada granular tracking).
  10. Lost ticket handling: User phone bhool gaya ya email delete kar diya → venue staff lookup kar sakta hai: name + phone + booking_id (last 4 digits). Backend identity validate karta hai: phone number booking se match karta hai, 10 minute ke liye valid temporary QR generate karta hai: temp_qr = generate_temp(booking_id, expires_at=NOW()+10min) — user temp QR se enter kar sakta hai.
  11. Refund/cancellation handling: QR generate hone ke baad booking cancel ho jaye to QR invalid mark karo: UPDATE bookings SET qr_code_valid=false. Scanner reject karta hai: 'This ticket has been cancelled and refunded'.
  12. Analytics: Check-in metrics track karo: on-time vs late arrivals, no-show rate (booked lekin checked in nahi), popular entry gates (load balancing), fraud attempts (invalid QRs, duplicate scans).

Real example: 10K attendees wala concert — average check-in time: 3 seconds per person, peak entry rate: 500 people/minute (showtime se 30 second pehle), zero fraud incidents (secure QR + check-in validation), 98% check-in rate (2% no-shows). Additional features: push notification — 'Your show starts in 1 hour, have your QR ready', QR code styling — venue logo embed karo, colorful design (QR phir bhi scan hota hai), wallet integration — QR ko Apple Wallet / Google Pay me add karo quick access ke liye.

Interview FAQs

Ticket booking system par interview me poochhe jane wale 36 sawaal — lesson ke Q&A aur usse jude concepts se. Har answer Hinglish me, interview-ready.

Q01Ticket booking system design karne ka pehla step kya hota hai?

Pehle functional requirements likho (search, seat map, hold, payment, confirm, history), phir non-functional (100M DAU, 90% read, search <200ms, booking me strong consistency). Uske baad entities (User, Event, Venue, Showtime, Seat, SeatHold, Booking), phir APIs, phir HLD, aur aakhir me deep dive — seat hold aur concurrency. Interview me seedha HLD se shuru mat karo; requirements se shuru karo, interviewer ko lagega tum structured sochte ho.

Q02Double booking rokne ka sabse important mechanism kaunsa hai?

Do layers ek saath: pehle Redis SETNX distributed lock (har seat par, 30 sec TTL) — isse 100 me se 99 users <10ms me reject ho jate hain. Phir DB me SELECT ... FOR UPDATE pessimistic lock — transaction ke andar rows lock ho jati hain, koi phantom read nahi. Dono milkar zero double booking guarantee karte hain. Sirf ek mechanism use karoge to race condition reh jayegi.

Q03Redis lock ka TTL 30 seconds kyun rakha hai?

Lock sirf atomic check-and-hold ke liye chahiye, jo 50–100ms me ho jata hai. 30 second kaafi hai aur agar service lock lene ke baad crash ho jaye to lock apne aap expire ho jata hai — seat wapas available ho jati hai, koi deadlock nahi hota. Zyada TTL rakhoge to crash ke baad seat zyada der tak block rahegi; kam rakhoge to slow transaction ke beech me lock expire ho jayega.

Q04Seat hold 15 minute ka kyun hota hai?

15 minute user ko payment complete karne ke liye kaafi time hai, aur itna chhota hai ki seats zyada der tak block nahi rehti. Hold abandonment 30–40% hota hai — matlab 3–4 users me se 1 hold bina payment ke expire hone deta hai. Agar hold 1 ghanta ka hota to popular shows ki seats ghanton tak block rehti aur real buyers ko milti nahi. Redis TTL 15 min baad apne aap hold delete karta hai, DB sweeper 1–2 min me seats wapas AVAILABLE karta hai.

Q05Idempotency key kya hota hai aur hold_id ko kyun use karte hain?

Idempotency key ek unique key hai jo ensure karti hai ki ek hi operation dobara chale to bhi sirf ek baar execute ho. hold_id perfect idempotency key hai kyunki har hold unique hota hai. User payment par dobara click kare, ya network timeout ke baad retry ho, to Booking Service pehle bookings table me hold_id dhoondhti hai — booking mil jaye to wahi booking_id return kar deti hai, dobara charge nahi karti. bookings(hold_id) par UNIQUE constraint bhi isi liye hai.

Q06Payment webhook me signature validation kyun zaroori hai?

Webhook internet se aata hai — koi bhi fake POST bhejkar booking confirm karwa sakta hai. Payment gateway har webhook ko apni secret key se sign karta hai. Backend pehle signature verify karta hai, tabhi payment ko genuine manta hai. Uske baad idempotency check karta hai (payment_id pehle se process to nahi hua), phir booking confirm karta hai. Signature validation ke bina system payment fraud ke liye khula rehta hai.

Q07CDC kya hai aur Elasticsearch ko sync kaise karta hai?

Change Data Capture ka matlab hai database ke changes ko capture karke doosri jagah pahunchana. Cassandra ka commitlog har INSERT/UPDATE/DELETE record karta hai. Debezium ya custom CDC service commitlog ko tail karke change events banata hai aur Kafka topic 'event.changes' par publish karta hai. Elasticsearch indexer consumer un events ko padhkar index update karta hai — insert/update ho to document index karo, delete ho to hatao. Lag aam taur par 1–2 second hota hai, jo search ke liye acceptable hai.

Q08Search ke liye Cassandra ki jagah Elasticsearch kyun use karte hain?

Cassandra key-based lookups me fast hai, lekin full-text search, relevance ranking aur location-based queries me weak hai. Elasticsearch text ko analyze karke index karta hai — 'SpiderMan' search par relevance sort, location filter aur date range filter ek hi query me mil jate hain. Cassandra se aise queries ke liye poora table scan karna padta. Isliye Cassandra source of truth hai, Elasticsearch search ka engine hai, aur CDC dono ko sync rakhta hai.

Q09Events ke liye Cassandra kyun use karte hain, MySQL kyun nahi?

Events, venues aur showtimes ka data write-heavy catalog hai — admin bulk me events banata hai, aur data ko multiple regions me available rakhna hota hai. Cassandra wide rows aur high write throughput ke liye bana hai, aur partition tolerance me strong hai. MySQL/PostgreSQL bookings ke liye chahiye jahan ACID transactions zaroori hain (paise aur seats ka mamla), lekin event catalog me ACID ki utni zaroorat nahi — availability aur scale zyada important hai.

Q10Seats table ko show_id se shard kyun karte hain?

Har show ki seats independent hoti hain — ek show ki booking doosre show ko affect nahi karti. show_id se shard karne par har show ka data alag shard par jata hai, to popular show ka load ek shard par rehta hai aur baaki shows unaffected rehte hain. Sharding se horizontal scaling milti hai — shows badho to shards badhao. Agar user_id se shard karte to ek show ki seats alag-alag shards par bikharti aur seat availability query ke liye saare shards poochhne padte.

Q11Seat map cache ka TTL sirf 30 seconds kyun hai?

Seat map bahut frequently change hota hai — har hold, booking aur cancellation par seats ki status badalti hai. 30 second ka TTL matlab cache zyada stale nahi hota, phir bhi DB load 95% kam ho jata hai kyunki 30 second me hazaron users ek hi cached map padhte hain. Search results ka TTL 10 minute hai kyunki events slowly change hote hain. Rush ke time TTL 60 second tak badha sakte ho — thodi staleness acceptable hai.

Q12Read vs write ratio 90/10 ka system design par kya asar padta hai?

90% reads ka matlab hai system ko reads ke liye optimize karo — Elasticsearch search ke liye, Redis caching seat maps aur popular searches ke liye, read replicas DB reads ke liye. Writes (10%) kam hain lekin critical hain — unke liye strong consistency aur ACID chahiye. Agar ratio ulta hota (write-heavy), to caching kam useful hoti aur write path ki throughput pehle sochni padti. Is ratio ko interview me bolna dikhata hai ki tumne scale ke baare me socha hai.

Q13CAP theorem me booking CP aur search AP kyun hai?

CAP kehta hai network partition me consistency aur availability me se ek chunni hogi. Seat booking me consistency chahiye — double booking bilkul nahi chalegi, isliye CP: lock na mile to user ko error dikhao, lekin galat booking mat do. Search me availability chahiye — user ko hamesha kuch na kuch result dikhe, chahe 2 second purana ho, isliye AP: Elasticsearch thoda stale ho to bhi chalega. Dono requirements alag hain, isliye system ko do hisso me baanta gaya hai.

Q14Sweeper job kya karta hai aur har 1 minute kyun chalta hai?

Sweeper job expired holds ko DB me clean karta hai. Redis TTL sirf Redis keys delete karta hai — DB me seats ka status HELD hi rehta hai. Sweeper har 1 minute me SELECT karta hai: status='PENDING' aur expires_at < NOW() wale holds, unki seats ko AVAILABLE karta hai, hold ka status EXPIRED karta hai, aur seat map cache invalidate karta hai. 1 minute ka interval isliye hai taaki DB par load kam rahe aur 1–2 minute ka lag acceptable ho — user ko expiry Redis se turant dikh jati hai.

Q15Hold expire hone par seat turant available kyun nahi hoti DB me?

Kyunki Redis aur DB do alag systems hain — Redis ki key expiry se DB ko koi signal nahi milta. Redis hold 15:00:00 par expire hota hai, DB sweeper agle run (15:01:00–15:01:30) me seats ko AVAILABLE karta hai. Is 1–2 minute ke lag me user ko seat Redis se 'available' dikh sakti hai jabki DB me abhi HELD hai — lekin jab user hold karne ki koshish karta hai to DB validation (FOR UPDATE) sahi status batati hai, to koi galat booking nahi hoti. Ye eventual consistency hai, aur acceptable hai.

Q16Virtual waiting room kya hai aur kab use karte hain?

Virtual waiting room ek queue hai jo sale khulne se pehle users ko rokta hai. Jaise sale 12:00 PM par khulti hai, users 11:50 AM se waiting room join karte hain. 12:00 PM par system users ko batches me release karta hai — 1000 users/sec — har user ko expiry wala token milta hai. Isse 1M users ek saath DB par nahi toot te; traffic smooth ho jata hai. Cloudflare Waiting Room ya custom queue use kar sakte ho. Ye sirf bahut popular launches (Marvel premiere, concert) ke liye chahiye, normal days par nahi.

Q17Queue-based reservation synchronous hold se behtar kab hota hai?

Jab traffic spike me 1000 bookings/sec se zyada aa raha ho aur DB synchronous holds se meltdown ho raha ho. Queue-based me POST /reserve request ko Kafka topic par daal dete hain, aur 50 workers steady rate (100 reservations/sec) par process karte hain. User ko queue position aur estimated wait dikhta hai. Trade-off hai: user ko turant confirmation nahi milta, wait karna padta hai. Normal load par synchronous hold behtar hai (turant response), spike par queue behtar hai (system crash nahi hota).

Q18Bots ko rokne ke 3 sabse effective tareeke kaunse hain?

Pehla: CAPTCHA (reCAPTCHA v3, score >0.5) seat selection se pehle — automated scripts ko turant filter karta hai. Doosra: rate limiting — per user 10 minute me 3 hold attempts, per IP 10 requests/minute, per session 1 active hold — bot farms ko block karta hai. Teesra: device fingerprinting + behavioral analysis — canvas/WebGL/fonts se fingerprint banao, aur check karo ki user ne event details dekhi, seat map par 5 second bitaye, mouse movement human jaisa hai ya nahi. In teeno ke saath honeypot seats bhi lagao — fake seats jo sirf bots ko dikhti hain.

Q19Honeypot seats kya hoti hain?

Honeypot seats fake 'available' seats hoti hain jo HTML me hidden hoti hain — real user ko dikhti nahi, render nahi hoti. Bot scripts HTML parse karke seats select karte hain, to wo honeypot seats ko bhi select kar lete hain. Jaise hi koi honeypot seat select kare, system samajh jata hai ye bot hai — turant flag karo aur IP + account block karo. Real users par iska koi asar nahi hota kyunki wo honeypot seats dekh hi nahi sakte.

Q20QR code me booking_id encrypt karke kyun rakhte hain?

Agar QR me plain booking_id hota to koi bhi QR ko copy karke ya booking_id guess karke fake ticket bana sakta. AES-256 encryption se QR ka data sirf backend aur venue scanners hi padh sakte hain (unke paas secret key hai). QR me hota hai {enc: base64(encrypted_data), v: 'v1'} — booking_id, show_id, user_id aur timestamp encrypted form me. Koi bhi tampering HMAC signature ko invalid kar deti hai, aur QR showtime ke 2 hours baad expire ho jata hai.

Q21Ek QR code ko dobara scan karne se kaise rokte hain?

Check-in atomic transaction se hota hai: UPDATE bookings SET checked_in_at=NOW() WHERE booking_id={id} AND checked_in_at IS NULL. Agar affected_rows 0 aaye to matlab pehle se checked in hai — rollback karo aur 'Already checked in' return karo. bookings(booking_id, checked_in_at) par UNIQUE constraint bhi single check-in ensure karta hai. Ek hi QR multiple venues par scan ho to fraud detection ke liye flag karta hai.

Q22Venue me internet na ho to QR verification kaise hogi?

Offline verification ke liye QR me poori booking details embed karte hain — booking_id, user_name, show_id, seat_ids, show_time — aur HMAC-SHA256 signature (booking_data + secret_key). Venue scanner signature ko offline validate karta hai; connectivity wapas aane par check-ins sync ho jate hain. Online mode me backend decrypt karke DB se validate karta hai, offline mode me signature hi authenticity ka proof hai.

Q23Refund policy 100% / 50% / 0% ka logic kya hai?

Policy show se pehle ke time par based hai: show se 24+ hours pehle cancel karo to 100% refund — venue ko seat dobara bechne ka kaafi time hai. 2–24 hours pehle cancel karo to 50% refund — seat dobara bechna mushkil hai, isliye aadha paisa kata hai. 2 hours se kam bache hon to 0% refund — seat dobara bechna lagbhag impossible hai. Ye policy booking ke waqt user ko dikhani chahiye, aur refund calculation transaction me atomic honi chahiye.

Q24Payment timeout ho jaye to seats ka kya hota hai?

Hold 15 minute me expire hota hai. Background job check karta hai: status='PENDING' aur created_at 15 minute se purana wale holds — payment na aaya ho to seats ko AVAILABLE kar deta hai aur 'payment.timeout' event publish karta hai, jisse Notification Service user ko 'Payment failed' email bhejta hai. Redis TTL bhi 15 minute baad hold keys delete kar deta hai. User dobara booking kar sakta hai — lekin usko wahi seats milengi iski guarantee nahi.

Q25Duplicate webhook aaye to kya karte hain?

Payment gateways webhook ko retry karte hain — network issue ho to wahi webhook 2–3 baar aa sakta hai. Har webhook par pehle idempotency check karo: SELECT * FROM bookings WHERE payment_id={payment_id} — agar booking pehle se exists kare to turant 200 return karo, dobara process mat karo. Signature validation bhi pehle karo taaki fake webhooks reject ho jayein. Yehi pattern refund webhooks par bhi lagta hai.

Q26DB failover me zero data loss kaise ensure karte hain?

Primary ke saath synchronous replica rakho (same region, lag <1 second) — har write dono par commit hoti hai, to failover par zero data loss hota hai. Cross-region async replica (lag <10 second) disaster recovery ke liye hota hai — us par failover ho to last 1–10 second ka data loss ho sakta hai, isliye pehle sync replica ko promote karte hain. Failover 2–3 minute me hota hai, aur idempotency ensure karti hai ki retry karne wale users ki bookings duplicate na banein.

Q27Connection pooling spike me kyun zaroori hai?

Har API request agar naya DB connection banaye to connection banane me hi 10–50ms lag jayega aur DB ke connections khatm ho jayenge. Connection pool pehle se 200 connections khula rakhta hai — request aate hi ready connection milta hai. Spike me 250 API servers × 200 connections = 50K connections ho sakte hain, isliye pool size aur DB ke max connections ko spike se pehle badhana padta hai. Pool exhaust ho jaye to requests queue me wait karti hain ya timeout hoti hain.

Q28Seat map 1000+ seats ka ho to rendering kaise optimize karte hain?

Pehle: section-wise pagination — balcony, mezzanine, orchestra alag load karo, user section select kare tabhi uski 200–300 seats load karo. Doosra: virtual scrolling — DOM me sirf visible rows rakho. Teesra: pehle sirf summary bhejo (available count by type), poora grid tab dikhao jab user 'Select seats' click kare. Chautha: Redis cache 30s TTL — 10K requests/sec serve karta hai. Mobile par tap targets 40px rakho aur pehli 5 rows turant load karo, baaki lazy load.

Q29WebSocket seat map me kyun use karte hain?

Seat map real-time change hota hai — koi aur user seat hold kare to tumhare screen par wo seat turant yellow honi chahiye, bina page reload ke. WebSocket connection (ws://api/showtime/{show_id}/seats) par server seat status changes publish karta hai. Updates ko 2–3 second me batch karke bhejte hain taaki har seat ka alag message na aaye. Optimistic UI bhi hoti hai — tumhari selected seat turant 'SELECTING' dikhti hai, hold fail ho to revert ho jati hai.

Q30Rate limiting ke liye kaunse limits lagate hain?

Per user: 10 hold attempts per minute (aur bots ke liye 10 minute me 3 holds). Per IP: 10 requests per minute. Per session: ek time par 1 active hold. Token bucket algorithm use karte hain — burst allowed hai (1 second me 5 requests) lekin sustained rate limited hai. Spike me per user 30 second me 1 hold attempt kar dete hain. Limits API Gateway par lagte hain, taaki galat traffic services tak pahunche hi nahi.

Q31Booking confirm hone ke baad Kafka par kaunse events jate hain?

Teen topics hain: 'booking.confirmed' — notification, analytics aur invoice service consume karte hain. 'booking.cancelled' — cancel aur refund ke baad publish hota hai. 'payment.failed' — payment decline ya timeout par publish hota hai. Har event me booking_id, user_id, show_id, event_id, seat_ids, amount aur timestamp hota hai. Kafka decoupling deta hai — Booking Service ko nahi pata email gaya ya nahi, aur Notification Service down ho to bhi booking nahi rukti.

Q32Invoice service Kafka event se kya karta hai?

Invoice Service 'booking.confirmed' event consume karke invoice PDF generate karta hai — booking details, seat numbers, amount aur taxes ke saath. PDF ko S3 me store karta hai aur download link user ko email se bhejta hai. Ye kaam async hota hai, booking ke response ko slow nahi karta. Agar invoice generation fail ho jaye to event ko retry kar sakte hain ya dead letter queue me daal sakte hain.

Q33Admin showtime banate waqt seats kaise generate hoti hain?

Admin showtime banata hai to system venue ka layout fetch karta hai (rows, columns, seat types) aur generate_series se har seat ka record banata hai — INSERT INTO seats (seat_id, show_id, row, number, type, status) SELECT ... — saari seats status='AVAILABLE' se initialize hoti hain. Ek 500-seat cinema ke liye 500 rows ek hi query me banti hain. Uske baad 'event.created' Kafka event publish hota hai aur Elasticsearch indexer search index update karta hai, aur popular shows ke seat maps Redis me pre-warm kiye jate hain.

Q34Cache warm-up kya hai aur kab karte hain?

Cache warm-up ka matlab hai cache ko pehle se bhar dena, taaki pehla user bhi fast response paye. Event sale se pehle admin seat maps ko Redis me preload karta hai (seat_map:{show_id} keys), aur popular searches ko bhi cache karta hai. Bina warm-up ke pehle hazaron requests DB par padti hain (cache miss) aur response slow hota hai — spike ke time yehi DB ko gira sakta hai. Warm-up sale se 1 week pehle shuru karte hain jab showtimes banate hain.

Q35Graceful degradation ka matlab kya hai ticket booking me?

Jab system overload ho to non-critical features band karke core booking ko bachana. Jaise: real-time seat map updates band karo (sirf available count dikhao), recommendations aur personalization band karo, exact availability ki jagah 'High demand' message dikhao. Search aur booking chalte rahenge, sirf extra features band honge. Isse system crash hone se bachta hai aur users ko kam se kam ticket to mil jata hai.

Q36Hold abandonment 30–40% ka matlab kya hai business ke liye?

30–40% holds bina payment ke expire ho jate hain — user seats hold karta hai, phir decide karta hai ya payment fail ho jata hai. Business ke liye iska matlab hai ki hold ki hui seats 15 minute tak bech nahi sakte, to effective inventory kam ho jati hai. Isliye hold time 15 minute rakha hai (zyada lamba hota to loss aur badhta), aur popular shows me waiting room + queue use karte hain taaki abandoned holds se seats waste na hon. Conversion rate 15–20% hai — 100 searches me se 15–20 bookings banti hain.
