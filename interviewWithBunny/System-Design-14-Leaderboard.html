01Requirements

Functional Requirements

Pehle ye decide karte hain ki system ko karna kya hai — 5 features jo har leaderboard system me honi chahiye.

Functional requirements matlab: system user ke liye kya-kya karega. Is lesson me 5 features define ki gayi hain:

Feature 1 — Insert / Update / Delete

User list me data daal sake, update kar sake aur delete kar sake — chahe wo video ho, song ho, player ho, ya koi bhi dynamic list (E-dynamic list). Matlab leaderboard sirf read-only nahi hai; scores aate rehte hain aur change hote rehte hain.

Feature 2 — Top 10 query, region/group ke hisaab se

User query kar sake: Top 10 players by score/rank — aur wo bhi region ya group ke hisaab se. Jaise global top 10 alag, US ke top 10 alag, music category ke top 10 alag.

Feature 3 — Time periods: day, week, month

Leaderboard sirf all-time nahi hota. Time windows limited honi chahiye: day, week, month — aaj ka top 10, is hafte ka top 10, is mahine ka top 10.

Feature 4 — All-time rankings bhi

Time-bounded rankings ke saath-saath all-time rankings bhi dikhni chahiye. Matlab ek player ka overall rank bhi mile, sirf aaj ka nahi.

Feature 5 — Real-time updates

User ko real-time updates milni chahiye — stale leaderboard data nahi chalega. Top-K ki latency 1 second se kam honi chahiye, matlab score aate hi leaderboard update ho jaye.

Interview me aise bolo

"Pehle functional requirements: CRUD on scores, top-K query by region/group, day/week/month windows, all-time ranking, aur sub-second real-time updates."

02Requirements

Non-Functional Requirements

System kitne scale par chalega, kitna fast hoga, aur consistency ka kya scene hai — ye sab non-functional requirements me aata hai.

Scale

CheezNumber
Events1M req/sec — billions of songs/videos/players globally
UsersHundreds of millions — ek saath leaderboards aur trending lists query kar rahe hain

Performance & Consistency

  • CAP Theorem: Availability >> Consistency. Leaderboard ke liye availability consistency se zyada important hai — eventual consistency acceptable hai. Matlab agar ek user ko rank 100 dikhe aur dusre ko 101, to chalega; system down nahi hona chahiye.
  • Latency: 100ms top-K result nikalne ke liye. Near real-time updates, <1 second lag — isse "soft-real time" update kehte hain.
  • Accuracy: probabilistic acceptable. Trending list/rank accurate honi chahiye, lekin chhoti ranking errors tolerable hain — jaise rank 100 vs 101 ka farak acceptable hai.
Yaad rakhne wali baat: Leaderboard me perfect consistency ki zaroorat nahi hoti. Koi user ye check nahi karta ki uska rank exactly 43 hai ya 44 — lekin agar leaderboard 5 second purana dikhe, to user ko pata chal jata hai. Isliye availability aur low latency pehle, consistency baad me.

High Level Design (from image)

Poora system 5 components me bat-ta hai — clients, API Gateway, Score Service, Ranking Service, aur storage. Beech me Kafka sabko decouple karta hai.

Design diagram ke hisaab se flow aisa hai:

Components aur unka kaam

  • Clients / users → API Gateway & Load Balancer — authentication, authorization, routing, rate limiting. Har request pehle yahan se guzarti hai.
  • Score Service — score updates handle karta hai (views, likes, game scores), validate karta hai aur events publish karta hai.
  • Ranking Service — top-K rankings compute karta hai, read queries serve karta hai, aur Redis ZSET manage karta hai real-time rankings ke liye.
  • Score DB — saare score events ki persistent storage (historical data, source of truth).
  • Kafka — score updates ke liye event streaming; write path ko ranking computation se decouple karta hai.

06.1Deep Dive (LLD)

Step 1: Score Event Ingestion

Har score ki kahani ek event se shuru hoti hai — user video dekhta hai, client ek POST bhejta hai, aur Score Service use Kafka tak pahunchata hai.

Flow, step by step

1. User video dekhta hai. Client bhejta hai:

POST /api/v1/scores/view
{ video_id: 'V123', user_id: 'U456', timestamp: now(),
  metadata: { region: 'US', category: 'music' } }

2. Score Service validate karta hai:

  • Check karo video exist karta hai ya nahi.
  • Check karo user authenticated hai ya nahi.
  • Dedup: check karo kya same user ne last 5 minute me ye video dekh li hai (double-counting spam rokne ke liye). Redis me: GET view_dedup:{user_id}:{video_id} — agar key mil gayi to ignore karo (already counted). Nahi mili to SET view_dedup:{user_id}:{video_id} 1 EX 300 (5 minute TTL).

3. Kafka me publish karo — topic score.updated:

Kafka event
{ event_id: uuid(), video_id: 'V123', score_delta: +1,
  timestamp, region: 'US', category: 'music' }

4. Response: 200 OK — async processing hai, leaderboard update ka wait nahi karte. Client ko turant jawab mil jata hai.

Kafka partitioning — bahut important

Partition video_id ke hash se hoti hai. Isse ek hi video ke saare events same partition me jaate hain → ordering preserved rehti hai. Agar do events ek hi video ke liye alag order me process ho jayein, to score galat ho sakta hai — partitioning se ye race condition khatam ho jati hai.

Dedup kyun zaroori hai: bina dedup ke ek user baar-baar refresh karke apni video ko top par pahuncha dega. 5-minute window spam rokta hai, lekin genuine repeat views (5 min ke baad) phir bhi count hote hain.

06.2Deep Dive (LLD)

Step 2: Approach 1 — Redis Sorted Set (ZSET)

Redis ZSET leaderboard ka sabse fast tareeka hai — (member, score) pairs sorted order me rehte hain, aur har operation O(log N) me hota hai.

Diagram me likha hai: "1. Redis Sorted Set (sorted_set), One Sorted_Set (sorted = <id, score> pairs, sorted), leaderboard:music:IN:alltime, leaderboard:music:IN:90days". Matlab ek ZSET me (id, score) pairs sorted order me store hote hain.

Ranking Service Kafka se event padhta hai

Event: {video_id: 'V123', score_delta: +1, region: 'US', timestamp}. Phir 4 ZSETs update hote hain:

ZINCRBY — score badhao
ZINCRBY leaderboard:global:alltime 1 V123        -- all-time
ZINCRBY leaderboard:global:daily:2026-01-25 1 V123 -- daily
ZINCRBY leaderboard:US:alltime 1 V123              -- regional
ZINCRBY leaderboard:music:alltime 1 V123           -- category

Top-K query

User request: GET /api/v1/leaderboards/global/top?limit=10. Ranking Service chalata hai:

ZREVRANGE — top 10, highest first
ZREVRANGE leaderboard:global:alltime 0 9 WITHSCORES
--> [{video_id: 'V123', score: 1000000},
     {video_id: 'V456', score: 950000}, ...]
-- Time complexity: O(log(N) + K) — 10M items par bhi ~1ms

Apni rank nikalo

ZREVRANK — 0-based index
ZREVRANK leaderboard:global:alltime V123   --> 42
--> matlab rank #43 (0-based index + 1)
Response: {video_id: 'V123', rank: 43, score: 500000}

Pros / Cons (diagram se)

ProCon
Every rank and data instantly available (<1ms)Complete expensive — single node me rakhna padta hai, "ideal depth" possible nahi
Simple — sirf Redis commandsMemory intensive: 10M entries = ~1 GB per leaderboard
Atomic — ZINCRBY thread-safe haiNo persistence — Redis crash = data loss (replica ke bina)

Memory math — interview me ye number bolna

  • Har entry: ~100 bytes (video_id + score + ZSET overhead)
  • 10M entries: ~1 GB per leaderboard
  • 5 leaderboards (global, regional, daily, weekly, monthly): 5 × 1 GB = 5 GB — Redis me manageable hai
Yaad rakhna

ZSET ke 4 main commands: ZINCRBY (score badhao), ZREVRANGE (top-K nikalo), ZREVRANK (rank nikalo), ZSCORE (score nikalo). Sab O(log N) ya O(1) — isiliye 10M entries par bhi top-100 query <1ms me milti hai.

06.3Deep Dive (LLD)

Step 3: Time-Windowed Leaderboards

Ek hi leaderboard nahi hota — daily, weekly, monthly aur all-time, har ek ki apni Redis key aur apni TTL hoti hai.

Lesson me likha hai: "Time periods should be limited by: day, week, month". Har window ke liye alag ZSET banta hai:

Daily leaderboard

  • Key format: leaderboard:global:daily:{YYYY-MM-DD} — example: leaderboard:global:daily:2026-01-25
  • TTL: EXPIRE leaderboard:global:daily:2026-01-25 604800 — 7 days (1 week TTL, purane daily leaderboards auto-delete)
  • Update: har view par ZINCRBY leaderboard:global:daily:2026-01-25 1 V123

Weekly leaderboard

  • Key format: leaderboard:global:weekly:{YYYY}-W{WW} — example: leaderboard:global:weekly:2026-W04 (2026 ka week 4)
  • TTL: 90 days (last ~13 weeks rakho)
  • Update: weekly key par same ZINCRBY

Monthly leaderboard

  • Key format: leaderboard:global:monthly:{YYYY-MM} — example: leaderboard:global:monthly:2026-01
  • TTL: 365 days (last 12 months rakho)

All-time leaderboard

  • Key: leaderboard:global:alltime
  • No TTL — kabhi expire nahi hota, indefinitely badhta hai (isiliye pagination essential hai)

Time window ke saath query

Daily top 10
GET /api/v1/leaderboards/global/top?window=daily&date=2026-01-25&limit=10
--> ZREVRANGE leaderboard:global:daily:2026-01-25 0 9 WITHSCORES
--> aaj ka top 10

Weekly aggregation — batch job (diagram: "Periodic batch jobs")

Har Monday 12 AM par batch job chalta hai jo last 7 din ke daily ZSETs ko weekly ZSET me merge karta hai:

ZUNIONSTORE — 7 din ka sum
FOR date IN (last 7 days):
  ZUNIONSTORE leaderboard:global:weekly:2026-W04 7
    leaderboard:global:daily:{date} WEIGHTS 1
--> Weekly ZSET me daily scores ka sum aa jata hai
TTL ka logic: daily data 7 din baad kis kaam ka? Weekly data 90 din baad? TTL se purana data apne aap delete hota hai — memory bachti hai aur koi manual cleanup nahi chahiye.

Step 4: Regional & Category Leaderboards

Global top 10 sabko nahi chahiye — user ko apne region aur apni category ka top 10 chahiye. Iske liye key me region aur category bhi aata hai.

Diagram me example hai: leaderboard:music:IN:alltime — region aur category specific leaderboard.

Regional leaderboard

  • Event me region aata hai: {video_id, score_delta, region: 'US'}
  • Update: ZINCRBY leaderboard:US:alltime 1 V123
  • Query: ZREVRANGE leaderboard:US:alltime 0 9 — US ka top 10

Category leaderboard

  • Event me category aata hai: {video_id, category: 'music'}
  • Update: ZINCRBY leaderboard:music:alltime 1 V123
  • Query: ZREVRANGE leaderboard:music:alltime 0 9 — top 10 music videos

Combined filters

  • Regional + Category: leaderboard:music:US:alltime — US me top music videos
  • Regional + Category + Time: leaderboard:music:US:daily:2026-01-25 — aaj US me top music videos

Diagram me note hai: "littered by region" — leaderboards region ke hisaab se sharded hote hain, isolation ke liye.

Key explosion problem — ye interview me zaroor poochte hain

DimensionCount
Regions5
Categories10
Time windows4 (daily, weekly, monthly, alltime)
Total leaderboards5 × 10 × 4 = 200
Har leaderboard1 GB (10M entries)
Total memory200 GB — Redis Cluster handle kar sakta hai, lekin expensive!

Optimization — 3 tareeke

  • Lazy initialization: leaderboard tabhi banao jab pehla score aaye — saare combinations pehle se mat banao.
  • Expire unused leaderboards: agar 30 din se koi update nahi aaya, to delete kar do.
  • Separate Redis cluster per region: load isolate ho jata hai.
Warning — interview favorite

NEVER create all leaderboard combinations upfront. 5 regions × 10 categories × 4 windows = 200 leaderboards × 1 GB = 200 GB Redis memory. Lazy init + 30-day expiry use karo.

06.5Deep Dive (LLD)

Step 5: Approach 2 — TimeSeriesDB (InfluxDB)

Redis current rank batata hai, lekin 'pichhle 30 din me is video ki rank kaise badli?' — ye sawaal Redis nahi bata sakta. Iske liye TimeSeriesDB aata hai.

Diagram me likha hai: "TimeseriesDB (InfluxDB)" with Flink for stream processing.

Use case — kab chahiye?

Jab historical trend analysis chahiye, sirf current top-K nahi. Example: "Video V123 ki rank pichhle 30 din me kaise change hui?"

Data flow

Kafka score.updated → Flink stream processor → InfluxDB.

Flink processing:

  • Window aggregation: events ko (video_id, 1-minute window) se group karo, window me views count karo.
  • Output: {video_id: 'V123', views_in_minute: 1000, timestamp: '2026-01-25T10:30:00Z'}
  • Phir InfluxDB me write karo.

InfluxDB schema

PartDetail
Measurementvideo_scores
Tags (indexed)video_id, region, category — fast filtering ke liye
Fields (numeric)views_count, likes_count, score
Timestamptime — nanosecond precision
Write + Query
INSERT video_scores,video_id=V123,region=US views_count=1000,score=1500 1674382200000000000

-- Last 24 hours ka top 10:
SELECT SUM(views_count) as total_views FROM video_scores
WHERE time > now() - 24h GROUP BY video_id
ORDER BY total_views DESC LIMIT 10
-- Time: ~100ms (Redis ke 1ms se slow, lekin complex time queries handle karta hai)

Downsampling — storage bachane ka tareeka

  • 1-minute data: 7 din tak rakho
  • 1-hour data me aggregate karo: 90 din tak rakho
  • 1-day data me aggregate karo: hamesha ke liye rakho
  • Continuous queries auto-downsample karti hain:
Continuous query
CREATE CONTINUOUS QUERY cq_hourly ON leaderboard BEGIN
  SELECT SUM(views_count) INTO video_scores_hourly
  FROM video_scores GROUP BY time(1h), video_id END

Pros / Cons

ProsCons
Historical analysis (trend over time)Slow queries (~100ms vs Redis 1ms)
Efficient storage (compressed time-series)Real-time leaderboards ke liye suitable nahi (<1 sec latency)
Complex queries (percentiles, moving averages)Complex setup (Flink + InfluxDB vs sirf Redis)

06.6Deep Dive (LLD)

Step 6: Approach 3 — Hybrid (Redis + DB) [BEST PRACTICE]

Production me na sirf Redis chalta hai, na sirf DB — dono saath chalte hain. Redis reads ke liye, DB persistence ke liye, Kafka beech me. Yehi industry standard hai.

Diagram me likha hai: "3. Hybrid Approach — All write requests are queued in Kafka. Consumers update Redis ZSET in real-time. Write scores to durable DB (Spanner, Postgres, Cassandra). Redis serves reads, DB serves as fallback and historical source. Periodic jobs snapshot Redis → DB or vice versa for consistency."

Architecture

Kafka (events) → Redis Consumer (real-time) + DB Consumer (persistence) → Redis (reads, hot data) + DB (writes, cold storage, source of truth).

Write path

  • Score event → Kafka score.updated
  • Redis Consumer: Kafka se consume karo, ZINCRBY leaderboard:global:alltime 1 V123 — real-time update, <100ms lag
  • DB Consumer: Kafka se consume karo, INSERT INTO scores (video_id, score_delta, timestamp, region) VALUES ('V123', 1, now(), 'US') — durable write, eventual consistency

Read path

  • User query: GET /api/v1/leaderboards/global/top?limit=10
  • Pehle Redis try karo: ZREVRANGE leaderboard:global:alltime 0 9 WITHSCORES
  • Agar Redis miss ho (rare — jaise Redis restart hua ho), to DB se fallback: SELECT video_id, SUM(score_delta) as total_score FROM scores WHERE leaderboard_id='global' GROUP BY video_id ORDER BY total_score DESC LIMIT 10
  • Response: Top-10 list

Pros / Cons (diagram se)

ProsCons
Redis instantly reflects score changesComplex architecture (Kafka + Redis + DB = 3 systems)
No data loss (Kafka + DB persistence)Redis consumer lag ho to leaderboard stale ho sakta hai
Kafka, Redis Cluster aur DBs independently scale hote hainData Redis me nahi hai to DB query karni padti hai (slow fallback)
TTL on keys: 1 day/week/month ke baad expire

Consistency aur rebuild

  • Redis = latest (eventual consistency, Kafka se <1 sec lag)
  • DB = source of truth (saare events persisted)
  • Periodic reconciliation: nightly job Redis vs DB compare karta hai, mismatch ho to Redis rebuild karta hai

Step 8: Probabilistic Data Structures

Exact top-K har jagah zaroori nahi hota. 'Trending now' me rank 100 vs 101 se kisi ko farak nahi padta — aur approximate structures 100× kam memory me kaam kar dete hain.

Diagram me note hai: "Place to implement: Where we already know, the query before hand (means which dimension of data user is likely to view)" — matlab pre-compute wahi karo jo user dekhne wala hai.

Use case

Jab exact top-K zaroori nahi, approximate ranking acceptable ho — jaise "Trending now" jahan rank 100 vs 101 matter nahi karta.

Count-Min Sketch

  • Probabilistic counter — accuracy ke badle space bachata hai.
  • Size: 1 MB se billions of items track kar sakte ho (Redis me exact counts ke liye 1 GB chahiye).
  • Update: view event aate hi video_id ko multiple positions par hash karo, counters increment karo.
  • Query: video_id hash karo, counters padho, minimum lo → estimated count.
  • Error: overestimation possible (actual 1000 views, estimated 1050), lekin underestimation kabhi nahi.

HyperLogLog

  • Use case: distinct viewers count karna (cardinality) — jaise "10M unique viewers" (total views nahi).
  • Size: 12 KB se billions of unique IDs estimate karo, <2% error ke saath.
  • Update: PFADD video:V123:unique_viewers {user_id}
  • Query: PFCOUNT video:V123:unique_viewers → ~10,000,000

Bloom Filter

  • Use case: check karo ki video top-K me hai ya nahi (membership test).
  • Size: 1 MB se 10M items, 1% false positive rate.
  • Query: "Kya video V123 top-100 me hai?" → Yes (definitely) ya No (maybe — 1% chance false positive ho).

Top-K approximation algorithm — Heavy Hitters

  • Count-Min Sketch + Min-Heap se approximate top-K maintain karo.
  • Stream processing: millions of events/sec process karo, top-100 memory me rakho (heap size = 100 items).
  • Update: agar naye item ka estimated count heap ke minimum se zyada ho, to heap min ko replace kar do.
  • Query: heap return karo (approximate top-100).
  • Accuracy: exact top-100 se 95% overlap (5% kuch ranks se off ho sakte hain).

Step 9: Handling Score Ties

Video A aur Video B dono ke 1000 views hain — upar kaun? Tie-breaker ke 4 tareeke hain, har ek ke apne trade-offs.

Problem: Video A aur Video B dono ke 1000 views hain, to rank kaise decide karein?

Approach 1 — Timestamp tiebreaker

  • Store karo: ZADD leaderboard:global:alltime {score}.{timestamp} V123
  • Example: score=1000, timestamp=1674382200 → 1000.1674382200
  • Sorting: Redis float value se sort karta hai, pehle wala timestamp upar aata hai (1000.1674382100 > 1000.1674382200).
  • Result: Video A (1000 views, pehle post hua) upar, Video B (1000 views, baad me post hua) neeche.

Approach 2 — Lexicographic tiebreaker

  • Store karo: ZADD leaderboard:global:alltime 1000 V123 (sirf score).
  • Redis ZSET: agar scores equal hon, to member ko lexicographically sort karta hai (V123 < V456 alphabetically).
  • Result: deterministic ordering, lekin arbitrary — koi semantic meaning nahi.

Approach 3 — Secondary score

  • Composite score: primary_score × 1000000 + secondary_score
  • Example: views × 1000000 + likes — Video A: 1000 views, 50 likes → 1000050000; Video B: 1000 views, 30 likes → 1000030000
  • Store: ZADD leaderboard:global:alltime 1000050000 V123
  • Result: Video A upar (zyada likes tiebreaker ban gaye).

Approach 4 — Random tiebreaker

  • Chhota random value add karo: score + random(0, 1) — example: 1000 + 0.5 = 1000.5
  • Non-deterministic: same query tied items ke liye alag order de sakti hai.
  • Use karo jab order matter nahi karta (trending lists).
Interview favorite

Timestamp tiebreaker sabse common answer hai: score ko float banao — score + (timestamp / 1e12). Example: Player A 1000 points t=100 par → 1000.0000000001; Player B 1000 points t=200 par → 1000.0000000002. Player A upar (pehle pahuncha).

Step 10: Pagination for Large Leaderboards

Leaderboard me 10M videos hain aur user ranks 1000–1010 dekhna chahta hai (page 100). Offset aur cursor — dono pagination ke tareeke samajh lo.

Problem: leaderboard me 10M videos hain, user ranks 1000–1010 dekhna chahta hai (page 100).

Offset-based pagination

  • Query: GET /api/v1/leaderboards/global/top?offset=1000&limit=10
  • Redis: ZREVRANGE leaderboard:global:alltime 1000 1009 WITHSCORES — rank 1000–1009 ke items
  • Time complexity: O(log(N) + offset + K) — offset=1000, K=10
  • Performance: bade offsets par bhi efficient hai (offset=1M bhi Redis me <100ms)

Cursor-based pagination

  • First page: ZREVRANGE leaderboard:global:alltime 0 9 WITHSCORES → top 10 + cursor = last item ka score
  • Next page: ZREVRANGEBYSCORE leaderboard:global:alltime {cursor} -inf LIMIT 0 10 — cursor se kam score wale next 10 items
  • Advantage: page requests ke beech leaderboard update ho bhi jaye, to bhi pagination consistent rehti hai
  • Disadvantage: arbitrary page par jump nahi kar sakte — sequentially paginate karna padta hai

Rank jumping — "My rank" feature

  • User apni rank dekhna chahta hai: GET /api/v1/leaderboards/global/rank/V123 → rank = 50000
  • Surrounding entries nikalo: ZREVRANGE leaderboard:global:alltime {rank-5} {rank+4} — 5 upar + user + 4 neeche
  • Display: user apni position context me dekhta hai

Infinite scroll

  • Client last fetched rank track karta hai: offset = 0 → 10 → 20 → 30 (jaise user scroll kare)
  • Next page request: GET ?offset={offset}&limit=10
  • Stop: jab ZREVRANGE 10 se kam items return kare → leaderboard khatam
Kab kaunsa use karein: page numbers dikhane hon (page 100 par jump) to offset. Live leaderboard jahan scores badalte rehte hain aur duplicate/missing entries nahi chahiye, to cursor. Apni rank ke aas-paas dikhana ho to rank jumping.

Step 11: Decay / Time-Based Scoring (Trending Algorithm)

Purana viral video 10M views ke saath, naya video aaj ke 100K views ke saath — Trending me naya video upar hona chahiye. Yehi time-decay karta hai.

Problem: purana viral video 10M views rakhta hai, naya video aaj 100K views rakhta hai → naye video ko "Trending" me upar hona chahiye.

Time-decay formula (Hacker News algorithm)

Formula
score = raw_count / (age_in_hours + 2)^1.5

Worked example — numbers ke saath

VideoViewsAgeCalculationScore
Video A (purana viral)10,000,00030 din (720 hours)10,000,000 / (720+2)^1.5≈ 515
Video B (naya)100,0001 hour100,000 / (1+2)^1.5≈ 19,245

Video B upar rank karta hai (trending now) — 100× kam views hone ke bawjood, kyunki wo fresh hai.

Implementation

  • Batch job har hour chalta hai: last 7 din me update hue saare videos ke scores recalculate karo (purane videos trending se excluded).
  • Formula SQL me: SELECT video_id, view_count / POW(EXTRACT(EPOCH FROM (NOW() - created_at)) / 3600 + 2, 1.5) as trending_score FROM videos WHERE created_at > NOW() - INTERVAL '7 days'
  • Redis update karo: har video ke liye ZADD leaderboard:trending {trending_score} {video_id}
  • Purane entries expire karo: ZREMRANGEBYSCORE leaderboard:trending -inf {min_score_threshold} — threshold se kam score wale videos hata do.

Reddit Hot algorithm

Reddit Hot
score = log10(ups - downs) + (age_in_seconds / 45000)
  • Logarithm: diminishing returns — 10 vs 100 votes ka farak 100 vs 1000 se zyada hota hai.
  • Time factor: purane posts linearly decay hote hain.
  • Engagement aur recency ka balance karta hai.

Real-time decay

  • Problem: batch job hourly chalta hai, lekin beech me trending list stale ho jati hai.
  • Solution: ZSET me (raw_count, timestamp) store karo, read par score compute karo: ZREVRANGE → har entry ke liye score = calculate_decay(raw_count, timestamp) → score se sort karo → top-K return karo.
  • Trade-off: read path par zyada CPU, lekin scores hamesha fresh rehte hain.
Tip — interview favorite

Time-decay formula: trending_score = engagement / (age_in_hours + 2)^1.8. Naya viral video (3 hours purana, 500K views) purane popular video (7 din purana, 10M views) se upar rank karta hai. Recency aur engagement balance karne ke liye batch recompute hourly karo.

Step 13: Scaling & Performance Optimization

1M events/sec aur 100K queries/sec — ye numbers sirf sahi scaling techniques se possible hain. 9 techniques, ek saath.

1. Redis Cluster

  • Shard by leaderboard ID: {CRC16(leaderboard_id) mod 16384} → slot decide karta hai → slot node decide karta hai.
  • 10 nodes (5 masters + 5 replicas): har node ~1–2 GB handle karta hai, total 10 GB distribute hota hai.
  • Reads: replica par route karo (master par load kam).
  • Writes: master handle karta hai, replica par replicate karta hai.

2. Kafka partitioning

  • score.updated ko video_id hash se partition karo (100 partitions).
  • Consumer group: 100 consumers (1 per partition), parallel processing.
  • Throughput: 100 consumers × 10K events/sec = 1M events/sec.

3. Database sharding

  • Scores table ko video_id hash se shard karo (10 shards).
  • Har shard: 1M videos — query time kam (1M scan karo, 10M nahi).
  • Cross-shard queries: periodic batch jobs shards ke across aggregate karte hain.

4. Caching

  • Application-level cache: top-100 app memory me cache karo (har 10 sec refresh), 90% queries memory se serve hoti hain (Redis round trip nahi).
  • CDN: API responses edge par cache karo (1 min TTL), global users ko <50ms latency.

5. Read replicas

  • Redis: master ke 5 replicas, reads replicas par route karo (5× read capacity).
  • DB: 3 replicas, leaderboard queries replicas par route karo (primary sirf writes handle karta hai).

6. Materialized views

  • DB me: CREATE MATERIALIZED VIEW top_1000_daily AS SELECT ..., hourly refresh.
  • Queries: SELECT * FROM top_1000_daily WHERE rank <= 10 — instant, aggregation nahi.

7. Approximate queries

  • Top-K approximation ke liye Count-Min Sketch use karo — 100× kam memory, 95% accurate, trending lists ke liye kaafi.

8. Batch optimization

  • Redis ko batches me update karo: ZADD leaderboard:global:alltime {score1} {video1} {score2} {video2} ... — ek command se 100 items. Round trips 100× kam (100 commands → 1 command).

9. Connection pooling

  • Har app instance: 50 Redis connections, 50 DB connections — requests ke across reuse karo.
  • Redis pipelining: multiple commands ek network round trip me bhejo (ZADD + ZREVRANGE → 2 RTT ki jagah 1 RTT).

Approach Comparison — Deep Dive

Diagram me 3 approaches hain — Redis ZSET, InfluxDB, Hybrid. Har ek ke pros/cons, kab use karein, aur decision matrix, sab ek jagah.

Diagram me 3 distinct approaches dikhaye gaye hain, har ek ke pros/cons ke saath.

Approach 1 — Redis Sorted Set / ZSET

Data structure: ek ZSET per leaderboard (jaise leaderboard:music:IN:alltime), (entity_id, score) pairs score se sorted. Operations: ZINCRBY (score update, O(log N)), ZREVRANGE (top-K, O(log N + K)), ZREVRANK (rank, O(log N)).

Pros: (1) Har rank aur data instantly available (<1ms queries), (2) Simple implementation (sirf Redis commands), (3) Atomic operations (ZINCRBY thread-safe hai).

Cons: (1) Complete expensive — single node me rakhna padta hai, "ideal depth" possible nahi, (2) Memory intensive (10M entries = 1 GB per leaderboard), (3) No persistence (Redis crash = data loss, replica ke bina), (4) Historical analysis mushkil (sirf current state, no time-series).

Kab use karein: real-time leaderboards (gaming, live sports), small-medium scale (<100M entities), simple time windows (daily, weekly, monthly), low latency critical (<10ms).

Approach 2 — TimeSeriesDB (InfluxDB) with Flink

Data flow: Kafka → Flink (stream aggregation) → InfluxDB (time-series storage) → top-K query. Flink: window aggregation (1-minute windows), entity_id se group, events count, InfluxDB me output.

Pros: (1) Historical trend analysis (rank time ke saath kaise badli), (2) Efficient storage (compressed time-series, raw events se 10× kam), (3) Complex queries (percentiles, moving averages, downsampling).

Cons: (1) Slow queries (~100ms vs Redis 1ms), (2) Complex setup (Flink + InfluxDB + Kafka), (3) Real-time nahi (<1 sec lag Flink windowing se), (4) Exact rank nikalna mushkil (aggregation query chahiye).

Kab use karein: analytics dashboards (trend graphs), historical leaderboards (jaise "pichhle saal har mahine ke top songs"), large-scale time-series data (billions of events), jab exact real-time ranking critical nahi ho.

Approach 3 — Hybrid (Redis + DB + Kafka) [BEST PRACTICE]

Architecture: Kafka (events) → Redis Consumer (real-time ZSET updates) + DB Consumer (persistent writes) → Redis (reads) + DB (fallback/historical).

Write path: (1) Score event → Kafka, (2) Redis Consumer: ZINCRBY (real-time, <100ms lag), (3) DB Consumer: INSERT scores (persistent, eventual consistency).

Read path: (1) Redis ZREVRANGE try karo (fast, <1ms), (2) Redis miss ho to DB query karo: SELECT ... GROUP BY ... ORDER BY ... (slow, ~100ms), (3) Zaroorat ho to DB se Redis rebuild karo.

Pros: (1) Redis instantly score changes reflect karta hai (real-time), (2) No data loss (Kafka + DB persistence), (3) Saare components independently scale hote hain (Kafka partitions, Redis cluster, DB sharding), (4) TTL on keys (purane leaderboards auto-expire karke memory bachao).

Cons: (1) Complex architecture (Kafka + Redis + DB = 3 systems manage karne hain), (2) Redis consumer lag ho to leaderboard stale ho sakta hai, (3) Data Redis me nahi hai to DB query karni padti hai (slow fallback).

Kab use karein: production systems at scale (millions of users), real-time updates AND persistence dono chahiye, multi-dimensional leaderboards (regional, category, time windows), critical data jo lose nahi kar sakte.

  • "Place to implement: Where we already know, the query before hand (means which dimension of data user is likely to view)" — pre-compute sirf wahi leaderboards karo jo users actually query karte hain, unused dimensions par resources waste mat karo.

Q1. Real-time gaming leaderboard design karo — global aur regional top 100, millions of score updates per second kaise handle karoge?

Requirements: (1) Top 100 global, (2) Top 100 per region (US, EU, APAC), (3) Millions of score updates/sec, (4) <100ms query latency, (5) Score ties handle karo.

Architecture: Kafka (score events) → Redis Consumer (real-time ZSET) + DB Consumer (persistence) → Redis Cluster (reads) + PostgreSQL (backup).

Score update flow: (1) Player 1000 points score karta hai → game server bhejta hai POST /api/v1/scores with {player_id: 'P123', score_delta: 1000, region: 'US', match_id: 'M456', timestamp}. (2) Score Service validate karta hai: player exist karta hai, match active hai, duplicate check (Redis dedup, 5-min TTL). (3) Kafka me publish: topic score.updated with {player_id, score_delta: 1000, region: 'US', timestamp}, partition player_id hash se → per-player ordering preserved.

Redis Consumer (real-time): 100 consumer instances (1 per partition) — 3 ZSETs update karte hain: ZINCRBY leaderboard:global:alltime 1000 P123, ZINCRBY leaderboard:US:alltime 1000 P123, ZINCRBY leaderboard:global:daily:{YYYY-MM-DD} 1000 P123. Lag: event se Redis update tak <100ms.

DB Consumer (persistence): alag consumer group PostgreSQL me likhta hai: INSERT INTO scores (player_id, score_delta, region, timestamp, match_id). Eventual consistency, lag ~1 second — backup/analytics ke liye acceptable.

Query flow: GET /api/v1/leaderboards/global/top?limit=100 → (1) Redis: ZREVRANGE leaderboard:global:alltime 0 99 WITHSCORES — <1ms. (2) Enrich karo: har player_id ke liye details MGET player:P123 player:P456 ... (batch fetch Redis player cache se); cache miss ho to DB se SELECT username, avatar_url FROM players WHERE player_id IN (...). (3) Response: [{rank: 1, player_id: 'P123', username: 'ProGamer', score: 1500000}, ...]. (4) Total latency <10ms (1ms ZREVRANGE + 5ms MGET + 2ms serialization). Regional: GET /api/v1/leaderboards/US/top?limit=100 → ZREVRANGE leaderboard:US:alltime 0 99.

Score ties: timestamp tiebreaker — score ko float banao: score + (timestamp / 1e12). Player A: 1000 points t=1674382200 par → 1000.000001674382200; Player B: 1000 points t=1674382300 par → 1000.000001674382300. Player A upar (pehle pahuncha). Store: ZADD leaderboard:global:alltime {score_with_timestamp} P123.

Millions of updates/sec kaise: (1) Kafka: 100 partitions × 10K events/sec = 1M events/sec — partitions badha kar aur scale karo. (2) Redis Cluster: 10 master nodes (har ek 100K ZINCRBY/sec) = 1M ZINCRBY/sec; shard by leaderboard_id: hash(leaderboard:global:alltime) mod 10 → node 5. (3) Redis Consumer: 100 instances (1 per Kafka partition), Kafka lag dekh kar auto-scale (lag > 1 min ho to consumers badhao).

Redis optimization: (1) Pipelining: PIPELINE; ZINCRBY leaderboard:global:alltime 1000 P123; ZINCRBY leaderboard:US:alltime 1000 P123; EXEC; — 2 commands 1 network round trip me. (2) Lua script: EVALSHA se multiple ZSETs atomically update karo (ek fail ho to partial update nahi). (3) Memory: top 100 leaderboard = 100 entries × 100 bytes = 10 KB (tiny); global leaderboard (10M players) = 1 GB (manageable).

Disaster recovery: (1) Redis crash: saara ZSET data lost (in-memory only). (2) DB se rebuild: SELECT player_id, SUM(score_delta) as total_score FROM scores GROUP BY player_id, phir har player ke liye ZADD leaderboard:global:alltime {total_score} {player_id}. 10M players rebuild karne me ~10 minutes. (3) Redis persistence: RDB snapshots (har 5 min) ya AOF (append-only file) faster recovery ke liye.

Advanced features: (1) Player ki rank: GET /api/v1/leaderboards/global/rank/P123 → ZREVRANK leaderboard:global:alltime P123 — rank=42 mile to display #43. (2) Percentile: top 1% me ho? total_players = ZCARD leaderboard:global:alltime, percentile = (rank / total_players) × 100. (3) Surrounding players: ZREVRANGE leaderboard:global:alltime {rank-5} {rank+4} WITHSCORES — 5 upar + player + 4 neeche.

Monitoring: Kafka consumer lag > 1 min ho to alert (leaderboard stale), Redis memory > 80% ho to alert, query latency p99 < 10ms (SLA), hourly consistency check Redis top-100 vs DB top-100.

Production example: Fortnite jaisi architecture — 250M+ players globally, millions of concurrent matches, real-time leaderboards har kuch seconds me update, Redis Cluster (100+ nodes), Kafka (1000+ partitions), top 100 ke liye sub-10ms query latency.

Q2. YouTube Trending page design karo — top 50 trending videos, time-decay algorithm samjhao

Requirements: (1) Top 50 trending videos (hourly update), (2) Recency aur engagement ka balance (naya viral video purane popular video se upar), (3) Regional trending (US, UK, India), (4) Category trending (Music, Gaming, News).

Time-decay algorithm (Hacker News style): trending_score = engagement_score / (age_in_hours + 2)^gravity. Parameters: (1) engagement_score — weighted sum: views + (likes × 10) + (comments × 20) + (shares × 30). Weights: Shares > Comments > Likes > Views (stronger engagement signal ko zyada weight). (2) age_in_hours = (NOW() - published_at) / 3600. (3) gravity — decay rate (typically 1.5–2.0); zyada gravity = faster decay; YouTube likely gravity ≈ 1.8 use karta hai.

Worked example: Video A (purana viral): 7 din purana (168 hours), 10M views, 500K likes, 50K comments, 10K shares → engagement_score = 10,000,000 + (500,000×10) + (50,000×20) + (10,000×30) = 16,300,000; trending_score = 16,300,000 / (168+2)^1.8 = 16,300,000 / 1173 ≈ 13,895. Video B (naya rising): 3 hours purana, 500K views, 50K likes, 5K comments, 1K shares → engagement_score = 500,000 + (50,000×10) + (5,000×20) + (1,000×30) = 1,130,000; trending_score = 1,130,000 / (3+2)^1.8 = 1,130,000 / 11.8 ≈ 95,763. Video B upar rank karta hai — absolute engagement kam hone ke bawjood, kyunki wo trending now hai.

Architecture: Batch computation + Redis caching. Batch job (hourly): (1) Trigger: cron har hour :00 par (12:00, 13:00, 14:00). (2) Recent videos query karo: SELECT video_id, views, likes, comments, shares, published_at FROM videos WHERE published_at > NOW() - INTERVAL '7 days' — sirf last 7 din ke videos trending ke liye eligible. (3) Har video ka trending score calculate karo: age_in_hours, engagement_score, trending_score = engagement_score / POW(age_in_hours + 2, 1.8). (4) Sort karke top 1000 store karo: ORDER BY trending_score DESC LIMIT 1000. (5) Redis me likho: DEL leaderboard:trending (purana clear karo), ZADD leaderboard:trending {trending_score} {video_id} (1000 videos add karo), EXPIRE leaderboard:trending 7200 (2-hour TTL, agar next run me batch job fail ho jaye).

Regional trending: har region ke liye alag batch job — filter WHERE region IN ('US', 'CA', 'MX') North America ke liye, store ZADD leaderboard:trending:US {trending_score} {video_id}. Category trending: filter WHERE category='Music', store ZADD leaderboard:trending:Music {trending_score} {video_id}.

Query flow: GET /api/v1/trending?region=US&limit=50 → (1) Redis: ZREVRANGE leaderboard:trending:US 0 49 WITHSCORES — cache hit (99% requests) → <1ms me return. Cache miss (rare — batch job ke time ya Redis restart) → DB se fallback (on-the-fly recalculate, ~500ms slow). (2) Video details enrich karo: MGET video:V123 video:V456 ... (title, thumbnail, channel). (3) Response: [{rank: 1, video_id: 'V123', title: 'New Music Video', trending_score: 95763, views: 500K, ...}].

Real-time vs batch trade-off: (1) Batch (hourly update): simple implementation, kam compute (hour me ek baar recalculate, har query par nahi), staleness — trending list 1 hour tak purani ho sakti hai (most users ke liye acceptable). (2) Real-time (per-query calculation): hamesha fresh scores, high compute cost (1M videos har query par recalculate → 100ms query time). YouTube batch approach use karta hai (hourly ya daily updates).

Optimization: (1) Incremental computation — saare videos recalculate karne ki jagah sirf un videos ko update karo jinme last hour me engagement aaya (Kafka stream: view/like/comment events consume karo, trending score real-time update karo — hybrid). (2) Materialized view: CREATE MATERIALIZED VIEW trending_videos AS SELECT video_id, ..., REFRESH MATERIALIZED VIEW CONCURRENTLY (non-blocking), trending view ko query karo raw videos table ki jagah (10× fast).

Alternative: Reddit Hot algorithm: hot_score = log10(engagement) + (age_in_seconds / 45000). Logarithm: diminishing returns (100 vs 1000 engagement ka farak 10 vs 100 se kam hota hai). Linear time decay: purane posts steadily decay hote hain. Use case: jab engagement recency se zyada matter kare (Reddit front page YouTube trending se zyada stable rehta hai).

Monitoring: batch job duration > 10 min ho to alert (normally 5 min), trending consistency (manual check vs automated trending — viral videos dikh rahe hain ya nahi), regional coverage (har region me trending data ho, koi leaderboard khaali na ho).

Advanced: Personalized trending: (1) User ki watch history: SELECT categories_watched, channels_subscribed FROM user_behavior WHERE user_id={user_id}. (2) Relevant categories boost karo: user 80% time Music videos dekhta hai to Music videos boost karo — personalized_score = trending_score × (1 + category_affinity). (3) ML model: predict karo "kya user is trending video par click karega" — features: trending_score, user_watch_history, video_category, time_of_day.

Production: YouTube Trending page daily ya hourly update hota hai (real-time nahi), engagement signals + time decay ka combination use karta hai, regional aur category-specific trending, human moderators review karte hain (manipulation rokne aur quality ke liye), logged-in users ke liye ML-based personalization.

Q3. Redis ZSET vs database-based leaderboard compare karo. Kab kaunsa choose karoge?

Redis ZSET approach: Sorted set (ZSET) (member, score) pairs store karta hai, score se automatically sorted. Operations: (1) ZADD leaderboard {score} {member} — add/update, O(log N). (2) ZINCRBY leaderboard {increment} {member} — score badhao, O(log N). (3) ZREVRANGE leaderboard 0 9 — top-10, O(log N + K). (4) ZREVRANK leaderboard {member} — rank, O(log N). (5) ZSCORE leaderboard {member} — score, O(1). Example: ZADD leaderboard 1000 player1, ZINCRBY leaderboard 500 player1 (ab 1500), ZREVRANGE leaderboard 0 2 WITHSCORES → [(player1, 1500), (player2, 1200), (player3, 1000)].

Pros: (1) Blazing fast — saare operations <1ms (in-memory), top-100 query ~1ms 10M players par bhi. (2) Simple — sirf Redis commands, no SQL, no indexes, no query optimization. (3) Atomic — ZINCRBY thread-safe hai (race conditions nahi). (4) Built-in ranking — ZREVRANK bina scan ke rank deta hai. (5) Auto-sorted — manual sorting nahi chahiye.

Cons: (1) Memory only — default persistence nahi (RDB/AOF mitigate karta hai lekin 100% durable nahi). (2) Single machine limit — ek ZSET ek node ki RAM me fit hona chahiye (single ZSET shard nahi ho sakta); 100M players × 100 bytes = 10 GB (expensive Redis server chahiye). (3) No time-series — sirf current state, "pichhle hafte leaderboard kya tha?" query nahi kar sakte. (4) Limited queries — complex filters nahi kar sakte (jaise "California ke top players jo 2024 me start hue"). (5) Cost — Redis memory expensive hai (RAM disk storage se 10–100× mehenga).

Database approach (PostgreSQL/MySQL): Schema: CREATE TABLE leaderboard (player_id varchar PRIMARY KEY, score bigint, updated_at timestamp); CREATE INDEX idx_score ON leaderboard(score DESC); Top-10 query: SELECT player_id, score FROM leaderboard ORDER BY score DESC LIMIT 10; Score update: UPDATE leaderboard SET score = score + {increment} WHERE player_id = {player_id}; Rank nikalo: SELECT COUNT(*) FROM leaderboard WHERE score > (SELECT score FROM leaderboard WHERE player_id = {player_id}); (kitne players ka score zyada hai, wo count karo).

Pros: (1) Persistent — data disk par, crash survive karta hai (ACID transactions). (2) Scalable storage — disk RAM se sasta (10 GB disk << 10 GB RAM), 1B+ players store kar sakte ho. (3) Time-series — timestamp column add karo, historical leaderboards query karo ("1 Jan 2024 ke top players"). (4) Complex queries — region, category, date range se filter karo. (5) Mature ecosystem — backups, replication, monitoring well-established.

Cons: (1) Slow — top-10 query ~50–100ms (disk I/O, index scan), Redis se 100× slow. (2) Rank calculation expensive — rank query saare players scan karta hai jinka score zyada hai → O(N) time; 10M players par rank query ~500ms (real-time leaderboards ke liye unacceptable). (3) Concurrent updates — UPDATE row lock karta hai, popular players par high contention (score 1000s times/sec update hota hai). (4) Index overhead — score index har UPDATE par rebalance hota hai (writes slow).

Hybrid approach (Redis + DB): best of both worlds. Writes: score event → Kafka → (1) Redis Consumer: ZINCRBY leaderboard {increment} {player} (real-time), (2) DB Consumer: INSERT INTO score_events (player_id, score_delta, timestamp) (persistent log). Reads: (1) Redis try karo: ZREVRANGE leaderboard 0 9 (fast, <1ms), (2) Redis miss ho to DB query karo: SELECT player_id, SUM(score_delta) FROM score_events GROUP BY player_id ORDER BY SUM DESC LIMIT 10 (slow, ~100ms), DB result se Redis rebuild karo. Consistency: Redis latest scores reflect karta hai (<1 sec lag Kafka se), DB source of truth hai (eventual consistency, ~1–5 sec lag), nightly reconciliation job Redis vs DB compare karta hai, mismatch ho to Redis rebuild karta hai. Disaster recovery: Redis crash → DB se rebuild karo (10M players ke liye ~10 min, acceptable).

Decision matrix: Redis ZSET choose karo jab: (1) low latency chahiye (<10ms top-K queries), (2) leaderboard memory me fit hota hai (<100M players → <10 GB), (3) real-time updates critical hain (gaming, live sports), (4) simple use case (global top-K, complex filters nahi), (5) data loss risk tolerate kar sakte ho (RDB/AOF se mitigate karo). Database choose karo jab: (1) persistence chahiye (leaderboard data lose nahi kar sakte), (2) large scale (>100M players, >10 GB data), (3) historical queries chahiye ("pichhle mahine ke top players"), (4) complex filters (region, category, time ranges), (5) lower budget (disk storage RAM se 10× sasta). Hybrid choose karo jab: (1) low latency AND persistence dono chahiye, (2) production system millions of users ke saath, (3) complexity manage kar sakte ho (Kafka + Redis + DB), (4) multi-dimensional leaderboards (regional, category, time windows).

Materialized views (advanced DB approach): CREATE MATERIALIZED VIEW top_1000_players AS SELECT player_id, score FROM leaderboard ORDER BY score DESC LIMIT 1000; REFRESH MATERIALIZED VIEW top_1000_players; (hourly refresh). Query: SELECT * FROM top_1000_players LIMIT 10; (~1ms, pre-computed). Trade-off: freshness vs performance (view 1 hour stale ho sakti hai).

Sharding (DB approach scale karne ke liye): player_id hash se shard karo, score se nahi (score-based sharding hotspots banata hai → top players saare ek hi shard par). Top-K query: scatter-gather saare shards par → results merge karo → top-10 return karo. Expensive hai lekin billions of players tak scale karta hai.

Production examples: Gaming (Fortnite, PUBG): Hybrid (Redis real-time + DB persistence). Music (Spotify Top 50): Batch DB + Redis cache (hourly batch, top-1000 cache). Social media (Twitter Trends): Redis ZSET (short-lived trending, data lose ho to chalega). Finance (stock tickers): Database (ACID transactions aur audit trail chahiye).

Summary: Redis = fast lekin volatile, Database = slow lekin durable, Hybrid = dono ka best lekin complex. Latency requirements, data size, durability needs aur budget dekh kar choose karo.

FAQs — Interview Questions
36 interview FAQs — lesson ke concepts par, current-era interview style me. Har answer me numbers aur commands hain, sirf theory nahi.
Q01Top-K leaderboard kya hota hai aur ye normal list se kaise alag hai?
Top-K leaderboard ek ranked list hoti hai jo sirf top K entries dikhati hai — jaise top 10 players ya top 50 trending videos. Normal list se farak ye hai ki entries score ke hisaab se sorted hoti hain, scores real time me badalte rehte hain, aur list ko region, category aur time window (daily/weekly/monthly) ke hisaab se filter kiya ja sakta hai. Backend me ye Redis ZSET jaisi sorted data structure se serve hoti hai, taaki top-K query 1ms se kam me mil jaye.
Q02Redis ZSET kya hai aur leaderboard ke liye ye best kyun mana jata hai?
Redis ZSET (Sorted Set) ek data structure hai jo (member, score) pairs ko score ke hisaab se sorted order me rakhta hai. Leaderboard ke liye best isliye hai kyunki iske saare main operations O(log N) me hote hain — ZINCRBY se score badhao, ZREVRANGE se top-K nikalo, ZREVRANK se kisi ki rank nikalo, ZSCORE se score nikalo. 10M entries par bhi top-100 query 1ms se kam me milti hai, aur ZINCRBY atomic hota hai, isliye concurrent updates me race condition nahi hoti.
Q03ZADD aur ZINCRBY me kya farak hai?
ZADD ek member ko ek specific score ke saath add ya update karta hai — jaise ZADD leaderboard 1000 player1 se player1 ka score 1000 set ho jata hai. ZINCRBY existing score me increment add karta hai — jaise ZINCRBY leaderboard 500 player1 se score 1000 se 1500 ho jata hai. Leaderboard me har view ya like ek increment hota hai, isliye score updates ke liye ZINCRBY use hota hai, aur rebuild ya snapshot restore karne ke liye ZADD use hota hai.
Q04ZREVRANGE ka time complexity kya hai aur ye itna fast kyun hai?
ZREVRANGE ka time complexity O(log(N) + K) hai, jahan N total entries hain aur K limit hai. Ye itna fast isliye hai kyunki ZSET internally skip list + hash table se bana hota hai — skip list sorted order maintain karti hai, isliye top par jump karna O(log N) me hota hai aur phir K entries read karna O(K) me. 10M entries par bhi top-10 query lagbhag 1ms me milti hai, jabki database me ORDER BY ... LIMIT 10 ko index scan karna padta hai jo 50-100ms leta hai.
Q05ZREVRANK 0-based index kyun return karta hai aur rank kaise nikalein?
ZREVRANK member ki position 0-based index me return karta hai — matlab sabse upar wale member ka index 0 hota hai. Display rank nikalne ke liye isme 1 add karo: agar ZREVRANK 42 return kare to rank #43 hoti hai. Example: ZREVRANK leaderboard:global:alltime V123 se 42 mila, to response hoti hai {video_id: 'V123', rank: 43, score: 500000}. Ye O(log N) me hota hai, jabki database me rank nikalne ke liye COUNT(*) query O(N) scan karti hai.
Q06Redis vs Database leaderboard — kab kaunsa choose karein?
Redis ZSET choose karo jab latency 10ms se kam chahiye, leaderboard memory me fit hota hai (100M se kam players, 10 GB se kam), real-time updates critical hain aur simple top-K use case hai. Database choose karo jab persistence chahiye, scale 100M players se zyada hai, historical queries chahiye ya complex filters chahiye, aur budget kam hai kyunki disk RAM se 10 guna sasta hai. Dono chahiye — low latency aur persistence — to Hybrid approach use karo: Redis reads ke liye, Kafka events ke liye, DB writes ke liye.
Q07Hybrid approach (Redis + Kafka + DB) production me best practice kyun hai?
Hybrid me har component apna best kaam karta hai: Kafka score events ko decouple karta hai aur durability deta hai, Redis consumer real-time me ZSET update karta hai jisse reads 1ms se kam me milti hain, aur DB consumer saare events persist karta hai jisse data kabhi lose nahi hota. Agar Redis crash ho jaye to DB se 10 minute me rebuild ho jata hai. Saare components independently scale hote hain — Kafka partitions, Redis cluster, DB sharding — aur TTL se purane leaderboards auto-expire hote hain. Isiliye production gaming aur video platforms Hybrid hi use karte hain.
Q08Score updates seedha Redis me kyun nahi karte — Kafka beech me kyun chahiye?
Seedha Redis update karne se 3 problems hoti hain: pehla, agar Redis down ho to score events lose ho jayenge; dusra, write path aur read path couple ho jayenge — ek slow consumer poora system slow kar dega; teesra, ek hi event se multiple kaam karne hain — Redis update, DB persist, analytics — to har consumer ko alag se event chahiye. Kafka beech me buffer aur durable log ka kaam karta hai: Score Service turant 200 OK de deta hai, aur consumers apni speed se events process karte hain. Kafka lag monitor karke pata bhi chalta hai ki leaderboard kitna stale hai.
Q09Kafka partitioning entity_id hash se kyun hoti hai, timestamp se kyun nahi?
Partitioning entity_id ke hash se isliye hoti hai taaki ek hi video ya player ke saare events hamesha same partition me jayein — isse ordering preserved rehti hai. Agar events alag partitions me chale jayein to do consumers unhe alag order me process kar sakte hain aur score galat ho sakta hai. Timestamp se partition karne se same entity ke events alag partitions me bikhrenge aur ordering khatam ho jayegi. 100 partitions se 100 parallel consumers 1M events/sec handle kar lete hain.
Q10Duplicate views ya spam se score inflate hone se kaise rokte hain?
Dedup ke liye Redis me ek key use hoti hai: view aate hi Score Service check karta hai GET view_dedup:{user_id}:{video_id}. Agar key mil gayi to event ignore kar do — user ne last 5 minute me ye video dekh li hai. Nahi mili to SET view_dedup:{user_id}:{video_id} 1 EX 300 karo, matlab 5 minute ki TTL ke saath key set karo, aur event aage badhao. Isse ek user baar-baar refresh karke apni video ko top par nahi pahuncha sakta, lekin 5 minute ke baad genuine repeat view phir bhi count hota hai.
Q11Daily, weekly, monthly aur all-time leaderboards ki Redis keys kaisi hoti hain?
Har window ki alag key hoti hai: daily ke liye leaderboard:global:daily:{YYYY-MM-DD} jaise leaderboard:global:daily:2026-01-25, weekly ke liye leaderboard:global:weekly:{YYYY}-W{WW} jaise leaderboard:global:weekly:2026-W04, monthly ke liye leaderboard:global:monthly:{YYYY-MM} jaise leaderboard:global:monthly:2026-01, aur all-time ke liye leaderboard:global:alltime. Region aur category bhi key me aate hain, jaise leaderboard:music:IN:alltime ya leaderboard:music:US:daily:2026-01-25. Query karte time window se key banakar ZREVRANGE chalate hain.
Q12Har time window ki TTL kya hoti hai aur TTL kyun zaroori hai?
Daily leaderboard ki TTL 7 din hoti hai (604800 seconds), weekly ki 90 din (last 13 weeks), monthly ki 365 din (last 12 months), aur all-time ki koi TTL nahi hoti — wo permanent hoti hai. TTL zaroori isliye hai taaki purana data apne aap delete ho jaye aur Redis memory bhar na jaye. Bina TTL ke har din ka leaderboard hamesha rehta aur memory khatam ho jati. All-time leaderboard kabhi expire nahi hoti, isliye wo indefinitely badhti hai aur uske liye pagination essential hai.
Q13ZUNIONSTORE kya karta hai aur weekly leaderboard kaise banta hai?
ZUNIONSTORE multiple ZSETs ko ek naye ZSET me merge karta hai, unke scores ka sum karke. Weekly leaderboard banane ke liye har Monday 12 AM par batch job chalta hai jo last 7 din ke daily ZSETs ko union karta hai: ZUNIONSTORE leaderboard:global:weekly:2026-W04 7 leaderboard:global:daily:{date} WEIGHTS 1. Isse weekly ZSET me 7 din ke daily scores ka sum aa jata hai, aur ye ek atomic Redis command me hota hai — beech me koi partial state nahi dikhta.
Q14Key explosion problem kya hai aur isse kaise bachte hain?
Key explosion tab hoti hai jab har dimension combination ke liye alag leaderboard banta hai: 5 regions × 10 categories × 4 time windows = 200 leaderboards, aur har leaderboard 10M entries par 1 GB leta hai, to total 200 GB Redis memory chahiye — bahut expensive. Bachne ke 3 tareeke hain: lazy initialization — leaderboard tabhi banao jab pehla score aaye; expire unused leaderboards — 30 din se update nahi aaya to delete kar do; aur separate Redis cluster per region — load isolate ho jata hai. Interview me ye number — 200 leaderboards, 200 GB — zaroor bolna.
Q15Lazy initialization kya hai aur leaderboard me ye kyun use hoti hai?
Lazy initialization ka matlab hai koi cheez tabhi banao jab uski pehli baar zaroorat pade, pehle se nahi. Leaderboard me iska matlab hai ki saare 200 region-category-window combinations ke ZSET pehle se mat banao — jab kisi leaderboard par pehla score event aaye, tabhi uska ZSET bane. Isse memory bachti hai kyunki bahut se combinations kabhi query hi nahi hote — jaise kisi chhoti category ka kisi chhote region me monthly leaderboard shayad kabhi koi dekhe hi nahi.
Q16Time-decay formula kya hai aur ye trending me kaise kaam karta hai?
Time-decay formula Hacker News algorithm se aayi hai: score = raw_count / (age_in_hours + 2)^1.5. Iska matlab hai ki score views ko video ki age se divide karke milta hai — purani video ka score age ke saath ghat-ta jata hai. Example: 10M views wali 30 din purani video ka score lagbhag 515 hota hai, jabki 100K views wali 1 hour purani video ka score lagbhag 19,245 hota hai — isliye nayi video trending me upar aati hai. YouTube jaisi jagah par gravity 1.8 use hoti hai aur batch job har hour scores recompute karta hai.
Q17Hacker News time-decay aur Reddit Hot algorithm me kya farak hai?
Hacker News formula score = raw_count / (age_in_hours + 2)^gravity hai — isme age denominator me hoti hai, to purana content tezi se neeche girta hai aur gravity 1.5 se 2.0 ke beech hoti hai. Reddit Hot formula score = log10(ups - downs) + (age_in_seconds / 45000) hai — isme engagement ka logarithm liya jata hai, jisse diminishing returns milte hain, matlab 10 se 100 votes ka farak 100 se 1000 se zyada hota hai, aur time factor linear hota hai. HN recency ko zyada weight deta hai, Reddit engagement ko zyada stable rakhta hai.
Q18Score ties kaise handle karte hain — chaaron tareeke samjhao?
Tie handle karne ke 4 tareeke hain: pehla, timestamp tiebreaker — score ko float banao score + (timestamp / 1e12), jo pehle pahuncha wo upar; dusra, lexicographic — Redis scores equal hone par members ko alphabetically sort karta hai, deterministic lekin arbitrary; teesra, secondary score — composite score banao primary × 1000000 + secondary, jaise views × 1000000 + likes, to zyada likes wala upar; chautha, random — score me random(0,1) add karo, non-deterministic hota hai aur sirf trending lists me use hota hai jahan order matter nahi karta. Interview me timestamp tiebreaker sabse zyada poochha jata hai.
Q19Offset pagination aur cursor pagination me kya farak hai — kab kaunsa use karein?
Offset pagination me page number se jump karte hain: ZREVRANGE leaderboard 1000 1009 se rank 1000-1009 milte hain, aur offset 1M par bhi Redis me 100ms se kam lagta hai. Lekin agar page requests ke beech leaderboard update ho jaye to entries duplicate ya miss ho sakti hain. Cursor pagination me last item ka score cursor hota hai aur next page ZREVRANGEBYSCORE se milta hai — ye updates ke beech bhi consistent rehta hai, lekin arbitrary page par jump nahi kar sakte, sequentially chalna padta hai. Page numbers dikhane hon to offset, live leaderboard ke liye cursor behtar hai.
Q20Rank jumping kya hai aur 'My rank' feature kaise implement hoti hai?
Rank jumping ka matlab hai user ko uski rank ke aas-paas ki entries dikhana, poora leaderboard scroll karaye bina. Pehle ZREVRANK se user ki rank nikalo — jaise rank 50000. Phir ZREVRANGE leaderboard {rank-5} {rank+4} chalao, jisse 5 upar wali entries, user khud, aur 4 neeche wali entries milti hain. User apni position context me dekhta hai — kaun usse aage hai, kaun peeche hai. Ye 'My rank' feature gaming leaderboards me bahut common hai.
Q21Count-Min Sketch kya hai aur ye exact count se kaise alag hai?
Count-Min Sketch ek probabilistic counter hai jo accuracy ke badle memory bachata hai: 1 MB me billions of items track kar sakte ho, jabki Redis me exact counts ke liye 1 GB chahiye. Update karte time video_id ko multiple positions par hash karke counters increment karte hain, aur query karte time counters ka minimum lete hain — ye estimated count hota hai. Isme overestimation possible hai, jaise actual 1000 views par estimated 1050 aa sakta hai, lekin underestimation kabhi nahi hoti. Trending lists ke liye ye 100 guna kam memory me kaam kar deta hai.
Q22HyperLogLog kya karta hai aur ye unique viewers count karne me kaise madad karta hai?
HyperLogLog distinct values count karne ke liye hota hai — cardinality estimate karta hai. Example: '10M unique viewers' nikalna ho to total views nahi, distinct user IDs count karne hote hain. Sirf 12 KB memory me billions of unique IDs ko 2% se kam error ke saath estimate kar sakte ho. Redis me PFADD video:V123:unique_viewers {user_id} se user add karte hain aur PFCOUNT se estimate nikalte hain. Total views ke liye ye use nahi hota, sirf unique count ke liye.
Q23Bloom Filter leaderboard me kis kaam aata hai?
Bloom Filter membership test ke liye hota hai — ye batata hai ki koi item ek set me hai ya nahi. Leaderboard me iska use ye check karna hota hai ki kya video top-K me hai. 1 MB me 10M items ke liye 1% false positive rate ke saath kaam karta hai. Agar Bloom Filter kahe ki video top-100 me nahi hai, to ye pakka hai; agar kahe ki hai, to 1% chance hai ki galat ho. Isliye ye fast pre-check ke liye use hota hai, final answer ke liye nahi.
Q24Heavy Hitters algorithm se approximate top-K kaise nikalte hain?
Heavy Hitters me Count-Min Sketch aur Min-Heap ko combine karte hain: stream me millions of events/sec process karte hain aur top-100 ko memory me heap me rakhte hain. Har naye event par uska estimated count nikalte hain — agar wo heap ke minimum se zyada hai to heap min ko naye item se replace kar dete hain. Query par heap return kar dete hain jo approximate top-100 hota hai. Accuracy lagbhag 95% hoti hai — exact top-100 se 95% overlap, 5% kuch ranks se off ho sakte hain. Trending topics aur viral videos ke liye ye kaafi hai.
Q25InfluxDB kab use karna chahiye aur kab Redis hi kaafi hai?
InfluxDB tab use karo jab historical trend analysis chahiye — jaise 'video V123 ki rank pichhle 30 din me kaise badli' ya 'pichhle saal har mahine ke top songs'. Isme Kafka se events Flink se aggregate hokar InfluxDB me jate hain, aur downsampling se storage bachta hai — 1-minute data 7 din, 1-hour data 90 din, 1-day data hamesha. Lekin queries 100ms leti hain, Redis ki 1ms ke muqable. Sirf current top-K chahiye aur latency 10ms se kam chahiye to Redis hi kaafi hai.
Q26Downsampling kya hai aur time-series data me ye kyun zaroori hai?
Downsampling ka matlab hai purane high-resolution data ko low-resolution me aggregate karke store karna. Example: 1-minute level data sirf 7 din rakho, phir use 1-hour level me aggregate karke 90 din rakho, aur 1-day level data hamesha ke liye rakho. InfluxDB me continuous queries ye automatically karti hain. Isse storage 10 guna kam ho jata hai aur purane data par queries bhi fast rehti hain, kyunki kam points scan karne padte hain.
Q27Batch jobs kab use karte hain aur inki staleness ka kya matlab hai?
Batch jobs tab use karte hain jab real-time updates critical nahi hain — jaise monthly top songs ya annual top players. Cron job daily 2 AM par chalta hai, DB se top-1000 compute karta hai, leaderboard_snapshots table me store karta hai aur Redis cache me 24 hours ke liye rakhta hai. Staleness ka matlab hai ki leaderboard batch job ke beech purana ho sakta hai — agar job hourly chalta hai to list 1 hour tak purani ho sakti hai. Most users ke liye ye acceptable hai, aur incremental updates aur Spark parallelization se job ka time 1 hour se 10 minute ho jata hai.
Q28Materialized leaderboard snapshots kya hote hain?
Materialized snapshots pre-computed rankings hote hain jo ek table me store kiye jate hain — leaderboard_snapshots jisme leaderboard_id, rank, entity_id, score aur snapshot_date hote hain, aur composite primary key (leaderboard_id, rank) hoti hai. Batch job inhe periodic update karta hai. Query karte time aggregation karne ki zaroorat nahi — seedha SELECT rank, video_id, score FROM leaderboard_snapshots WHERE leaderboard_id='global_monthly_2026-01' ORDER BY rank LIMIT 10 chalao. Ye batch approach ka core hai aur cache ke saath 1ms se kam me result deta hai.
Q29Redis crash ho jaye to leaderboard kaise rebuild karte hain?
Redis in-memory hai, isliye crash par saara ZSET data lost ho jata hai. Rebuild DB se hota hai jo source of truth hai: background job chalata hai SELECT video_id, SUM(score_delta) as total_score FROM scores WHERE timestamp > now() - INTERVAL '7 days' GROUP BY video_id, aur har row ke liye ZADD leaderboard:global:weekly:{YYYY-W{WW}} {total_score} {video_id} karta hai. 10M entries rebuild karne me lagbhag 10 minute lagte hain, jo disaster recovery ke liye acceptable hai. RDB snapshots har 5 minute ya AOF enable karke recovery aur fast ki ja sakti hai.
Q30Redis aur DB ke beech consistency kaise check karte hain?
Nightly job Redis top-100 aur DB top-100 ko compare karta hai — agar mismatch 5 items se zyada ho to alert aata hai, kyunki iska matlab data corruption ya consumer lag hai. Iske alawa random sampling hoti hai: 1% scores ko randomly sample karke verify karte hain ki Redis DB se match karta hai. Ye validation monitoring ka hissa hai aur Hybrid approach me zaroori hai kyunki Redis aur DB eventual consistency par chalte hain — Redis me lag 1 second se kam aur DB me 1-5 second hota hai.
Q31Leaderboard system me kya-kya monitor karte hain aur alerts kab aate hain?
Chaar main metrics monitor karte hain: Kafka consumer lag 1 minute se zyada ho to alert — leaderboard stale hai; Redis memory 80% se zyada ho to alert — eviction ka risk hai; query latency p99 100ms se zyada ho to alert — queries slow hain; cache hit rate 90% se kam ho to alert — Redis effective nahi hai. Iske alawa Redis node down par auto-failover, Kafka partition offline par alert, DB replication lag 10 second se zyada par alert, aur batch job fail ya normal time se dugna time le to alert aata hai.
Q32Redis Cluster me sharding kaise hoti hai — 16384 slots ka kya matlab hai?
Redis Cluster me har key ko CRC16 hash karke 16384 slots me se ek slot milta hai, aur har slot ek node ko assign hota hai. Leaderboard sharding leaderboard_id se hoti hai — hash(leaderboard_id) mod 16384 se slot nikalta hai. Example setup me 10 nodes hote hain — 5 masters aur 5 replicas — har node lagbhag 1-2 GB handle karta hai aur total 10 GB distribute hota hai. Reads replicas par route karte hain taaki master par load kam ho, aur writes master handle karke replica par replicate karta hai.
Q331M score updates per second kaise handle karte hain?
Teen layers milkar 1M events/sec handle karte hain: Kafka me 100 partitions hote hain jo entity_id hash se bante hain, har partition 10K events/sec handle karta hai — total 1M events/sec. Redis side par 100 consumer instances hote hain, ek per partition, aur har consumer ZINCRBY karta hai jo O(log N) me 1ms se kam leta hai. Redis Cluster me 10 master nodes hote hain, har ek 100K ZINCRBY/sec karta hai — total 1M ZINCRBY/sec. Aur scale chahiye to partitions aur consumers badha do. Pipelining aur Lua scripts se multiple ZSET updates ek round trip me ho jate hain.
Q34Rank nikalne ke liye COUNT(*) query kyun nahi use karni chahiye?
Database me rank nikalne ke liye SELECT COUNT(*) FROM leaderboard WHERE score > {player_score} chalani padti hai, jo saare players ko scan karti hai jinka score zyada hai — 10M players par ye O(N) scan lagbhag 500ms leta hai, jo real-time leaderboard ke liye bahut slow hai. Redis me ZREVRANK O(log N) me rank deta hai, 1ms se kam me. Isliye rank ke liye hamesha ZREVRANK use karo, COUNT(*) kabhi nahi — ye interview me ek classic galti hai jo interviewer pakadta hai.
Q35Top-100 ko app memory aur CDN me cache karne se kya fayda hota hai?
Application-level cache me top-100 ko app memory me rakho aur har 10 second refresh karo — 90% queries memory se serve hoti hain, Redis round trip bhi nahi lagta. CDN par API responses ko edge par 1 minute TTL ke saath cache karo — global users ko 50ms se kam latency milti hai. Isse Redis aur DB par load bahut kam ho jata hai, kyunki zyada users wahi top-10 ya top-100 dekh rahe hote hain. Cache hit rate 90% se kam ho to alert aata hai, kyunki iska matlab caching effective nahi hai.
Q36Trending list ke liye real-time calculation aur batch computation me kaise choose karein?
Batch computation simple aur sasta hai — har hour ek baar saare videos ke trending scores recalculate karo aur Redis me cache karo, lekin list 1 hour tak purani ho sakti hai. Real-time calculation har query par fresh scores deta hai — ZSET se entries padho, har entry ka decay score compute karo, sort karo — lekin 1M videos par har query me 100ms lagta hai aur read path par CPU zyada lagta hai. YouTube batch approach use karta hai, hourly ya daily updates ke saath. Best combination hybrid hai — hourly batch plus Kafka stream se incremental updates, jisse list fresh bhi rehti hai aur compute bhi kam hota hai.
