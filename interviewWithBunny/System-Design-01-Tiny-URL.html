01.2 Functional Requirements

Functional requirements matlab system ko kya-kya karna chahiye — user ko dikhai dene wale features. Tiny URL ke 5 features hain, jinme se 2 core hain aur 3 optional.

Core features

  • Feature 1 — Short URL banao: Lambi URL se chhoti URL banao. Example: https://www.facebook.com/example-user/ → http://bit.ly/4kyLcpo. Ye system ka sabse pehla aur sabse zaroori kaam hai.
  • Feature 4 — Redirect karo: User jab short URL khole to use original long URL par redirect kar do — 301 ya 302 redirect ke through. Bina redirect ke short URL ka koi matlab nahi.

Optional features

  • Feature 2 — Custom URL: User apni pasand ka short code chun sake — jaise random 9i91c0 ki jagah mylink. Ye branding ke liye bahut use hota hai (jaise bit.ly/mylink).
  • Feature 3 — Expiration date: Short URL ek time ke baad expire ho jaye — 30 days, 1 year, ya koi date. Expire hone ke baad click karne par 410 Gone milega.
  • Feature 5 — Analytics track karo: Har redirect par click count, user metadata aur timestamps track karo — kitne clicks, kahan se aaye, kaunsa device tha.
Interview tip: Requirements batate time pehle core features bolo, phir optional. Aur interviewer se poochh lo — "kya custom URL aur analytics bhi chahiye?" — isse pata chalta hai ki tum scope clarify karte ho, seedha design pe nahi koodte.

01.3 Non-Functional Requirements

Non-functional requirements matlab system kitna bada, kitna fast aur kitna reliable hona chahiye. Ye numbers hi poore design ko shape dete hain — caching, sharding, replicas — sab inhi numbers ki wajah se aate hain.

Scale aur Latency

  • Scale — 100M DAU / 1B URLs: 100 million daily active users, 1 billion URLs stored. Redirect traffic massive hai — roz billions of redirects. Matlab reads, writes se 100 guna zyada hain (read:write ratio 100:1).
  • Latency — redirect <100ms: URL banate time aur redirect karte time latency low honi chahiye. Redirect to <100ms me hona hi chahiye — ideally cache hit par <2ms aur cache miss par ~50ms. Lesson me redirect ka target ~200ms bhi likha hai, lekin design goal <100ms hai.

Consistency aur Availability

  • Short URL uniqueness: Short URL unique hona chahiye — koi collision nahi. Do users ko kabhi same short URL nahi mil sakta. Ye sabse sakht requirement hai.
  • CAP Theorem — Availability >> Consistency: Availability, consistency se zyada important hai. Analytics ke liye eventual consistency acceptable hai — matlab click count thoda der se update ho to chalega, lekin redirect kabhi fail nahi hona chahiye.
Yaad rakhna: Redirect path par availability sabse upar hai — user link click kare aur redirect na ho, to service bekaar. Analytics eventual consistent ho sakta hai (thoda delay chalega), lekin short-code uniqueness par koi compromise nahi.

Numbers jo design decide karte hain

RequirementNumberDesign par asar

Stored URLs1B URLsSharding (10 shards × 100M)
Redirects per day1B/day (≈11.5K/sec avg, 115K peak)Redis cache, read replicas, CDN
Redirect latency<100ms (cache hit <2ms)90%+ cache hit rate target

Teen components

02.1 Step 1 — Counter + Zookeeper (Base62)

ID generation ka pehla tareeka — distributed counter. Challenge ye hai: har long URL ke liye 6-7 characters ka unique short code banao, bina kisi collision ke.

Honest note: Is step ki detail design diagram se li gayi hai — diagram me 'counter' with Zookeeper aur Redis dikhaya gaya hai.

Flow — step by step

  1. User submit karta hai: POST /s/url with {longURL: 'https://www.facebook.com/example-user/'}
  2. Server counter maangta hai: Zookeeper atomic increment — counter++ (example: counter = 3748547)
  3. Base62 encode: encode(3748547) → '9i91c0' (6 chars)
  4. Mapping store: INSERT INTO urls (short_url, long_url, created_at) VALUES ('9i91c0', 'https://www.facebook.com/example-user/', now())
  5. Cache: SET url:9i91c0 {longURL, metadata} EX 86400 (24 hour TTL)
  6. Response: {shortURL: 'http://bit.ly/9i91c0', longURL: '...'}

Base62 encoding — kaise kaam karta hai

  • Characters: [0-9a-zA-Z] = 62 chars (0-9: 10, a-z: 26, A-Z: 26)
  • Algorithm: num = 3748547; result = ''; while (num > 0) { result = chars[num % 62] + result; num = Math.floor(num / 62); } → '9i91c0'
  • Capacity: 62^6 = 56 billion unique URLs (6 chars), 62^7 = 3.5 trillion (7 chars)
  • Diagram note: Counter ki latency '2ms-3ms' likhi hai, aur counter values cache karne ke liye Redis dikhaya gaya hai.
Correction — lesson ka example galat hai: Lesson me likha hai encode(3748547) → '9i91c0', lekin sahi calculation se 3748547 → 'fJar' banta hai (4 chars). '9i91c0' actually 8,513,319,076 ka Base62 code hai. Ye lesson ki galti hai — Lab 1 (Base62 Encoder) me khud verify karo. Baaki lesson me jahan bhi '3748547 → 9i91c0' likha hai, wahi galat example repeat hua hai.

Zookeeper kya hai?

Zookeeper ek distributed, open-source coordination service hai — configuration management, naming, synchronization aur group services ke liye. Bade clusters banana aasan ho jaata hai. Yahan iska kaam: counter ki value maintain karna.

Zookeeper counter implementation

  1. Zookeeper node: /counters/url_counter with value = 0
  2. Atomic increment: zk.setData('/counters/url_counter', currentValue + 1) — saare servers ke liye guaranteed atomic
  3. Multiple servers: Saare encryption servers ek hi Zookeeper counter se padhte hain → koi collision nahi
  4. High availability: Zookeeper cluster (3-5 nodes), ek fail ho to baaki counter state maintain karte hain

Diagram me dikhta hai: multiple encryption servers (round robin load balancing) → Zookeeper counter → same counter value kabhi dobara use nahi hota.

CRITICAL: Short URL uniqueness NON-NEGOTIABLE hai. Zookeeper atomic counter uniqueness guarantee karta hai. Backup ke roop me DB me short_url par UNIQUE constraint mandatory hai.
Zookeeper tip: Diagram me '2ms-3ms' latency likhi hai. 3-5 node cluster (quorum = majority), leader election on failure. Atomic increment se koi collision nahi. Alternative: Snowflake — agar Zookeeper bottleneck ban jaye (>100K creations/sec).

02.2 Step 2 — Snowflake ID

ID generation ka doosra tareeka — Snowflake. Ye decentralized hai: har server apne aap ID banata hai, bina kisi coordination ke. Diagram me 'Snowflake' with workerID: 123, 234, 345 aur timestamp component dikhaya gaya hai.

Snowflake ID structure (64-bit)

BitsPartMatlab
1 bitUnusedHamesha 0
41 bitsTimestampCustom epoch se milliseconds — 2^41 ms ≈ 69 years
10 bitsWorkerIDHar server ki unique ID (0-1023) — 1024 workers
12 bitsSequenceEk millisecond me counter — 4096 IDs/ms/worker

Total: 64 bits = 2^64 unique IDs. Diagram ka formula: 2^41 / 365 / 24 / 3600 / 1000 = 69.73 years.

Example generation

  1. Current time: Jan 26, 2026 10:30:45.123 → ms since epoch: 189432045123
  2. WorkerID: Server 123
  3. Sequence: Is millisecond ki pehli ID → 0
  4. Combine: ID = (189432045123 << 22) | (123 << 12) | 0 = 792345678901234567 (64-bit number)
  5. Base62 encode: encode(792345678901234567) → 'aBc123XyZ' (10 chars)

Fayde

  • No coordination: Har worker independently ID banata hai (Zookeeper counter se alag)
  • Time-ordered: IDs monotonically badhte hain — nayi URLs ki ID zyada hoti hai
  • High throughput: 4096 IDs/ms/worker × 1024 workers = 4M IDs/sec
  • Decentralized: Workers ek doosre se baat nahi karte — koi single point of failure nahi

Nuksaan

  • Lambe short URLs: 64-bit number → Base62 me 10-11 chars (counter ke 6-7 ke mukable). Workaround: sirf lower 42 bits use karo → 7-8 chars (phir bhi 69 years + 1024 workers + 1 sequence).
  • Clock dependency: Synchronized clocks chahiye (NTP) — clock drift se collision ho sakta hai.

02.3 Step 3 — Hash / Encryption Logic

ID generation ka teesra tareeka — hash-based. Long URL ko hash karo, usme se 6-7 characters nikalo, wahi short code bana do. Diagram me likha hai: sha1(longUrl) -> (shortURL, 6, 7) -> response.

Flow — step by step

  1. User submit: POST /s/url with {longURL: 'https://www.facebook.com/example-user/'}
  2. Hash URL: hash = SHA1(longURL) = 'd3e8f9a2b1c4e5f6a7b8c9d0e1f2a3b4c5d6e7f8' (40 hex chars)
  3. Substring nikalo: shortCode = hash.substring(0, 7) = 'd3e8f9a' (7 chars)
  4. Collision check: SELECT COUNT(*) FROM urls WHERE short_url='d3e8f9a' — agar exist karta hai to try karo hash.substring(7, 14), (14, 21)… 5 attempts tak. Sab fail ho to hash(longURL + timestamp) use karo.
  5. Store: INSERT INTO urls (short_url, long_url)
  6. Response: {shortURL: 'http://bit.ly/d3e8f9a'}

Diagram note: 'Server — encryption (20%), decryption (80%)' — matlab workload read-heavy hai, encryption sirf 20% kaam hai.

Collision handling

  • Probability: SHA1 output space = 2^160. 7 chars from hash = 16^7 possible values. 1M URLs par collision probability ≈ (1M²) / (2 × 16^7) ≈ 0.000002% — bahut kam.
  • Agar collision ho: Hash ke agle 7 characters try karo, ya salt ke saath rehash karo: hash(longURL + random_salt).
  • Max retries: 5 attempts — sab fail ho to counter-based ID par fall back karo.

Fayde

  • No external dependency: Zookeeper nahi chahiye, koi coordination nahi.
  • Deterministic + deduplication: Same long URL → same hash → same short URL. User same URL dobara banaye to existing short URL return kar do.
  • Stateless: Koi bhi server bina DB query ke short URL bana sakta hai.

Nuksaan

  • Collision risk: Retry logic chahiye, counter se zyada complex.
  • Length guarantee nahi: Retry ke baad 8-9 chars bhi lag sakte hain.
  • No time-ordering: Random distribution — 'recent URLs' query karna mushkil.
NEVER skip collision handling: Simple hash ko bina retry ke short URL mat banao. 1M URLs par collision ≈ 0.01% (birthday paradox). Retry logic mandatory hai: substring(0,7), (7,14), (14,21) try karo ya timestamp salt append karo. DB UNIQUE constraint collision pakadta hai. Max 5 retries, phir counter par fall back karo.

02.4 Step 4 — Redirect Flow (301 vs 302)

Redirect flow matlab user short URL click kare to long URL kaise khule. Ye system ka sabse zyada chalne wala path hai — 1B redirects/day — isliye iska har millisecond matter karta hai.

Server redirect flow

  1. Short code nikalo: URL path se '9i91c0' extract karo (GET http://bit.ly/9i91c0).
  2. Redis cache check: GET url:9i91c0 → {longURL: 'https://www.facebook.com/example-user/', expiresAt: '2027-01-26'}. Cache hit (90% requests) → DB query skip.
  3. Cache miss: DB query karo: SELECT long_url, expires_at FROM urls WHERE short_url='9i91c0'. Nahi mila → 404 'Short URL not found'. Mila lekin expired (expires_at < now()) → 410 'Link expired'. Valid hai → cache me daalo: SET url:9i91c0 {longURL, expiresAt} EX 86400.
  4. Redirect return karo: HTTP 301 Moved Permanently with Location: https://www.facebook.com/example-user/.
  5. Browser redirect: Browser automatically long URL khol deta hai.

Diagram note: 'encrypt: 1ms' for encryption, '5ms' server-to-DB latency, total '=16ms + 16ms' round trip.

Performance numbers

  • Cache hit: <10ms (Redis lookup + redirect response)
  • Cache miss: ~50ms (DB query + Redis write + redirect)
  • 90% cache hit rate → average latency ~15ms

02.5 Step 5 — Custom Short URLs

Custom short URL matlab user apni pasand ka alias chune — jaise bit.ly/mywork. Diagram me database schema me customURL optional field dikhaya gaya hai.

Flow

User request bhejta hai: POST /s/url with {longURL: 'https://myportfolio.com', customURL: 'mywork'}

Server validation — 5 checks

  1. Length: 3-20 characters (minimum enforce karo taaki single-char URLs jaise 'a' na bane).
  2. Allowed chars: Sirf [a-zA-Z0-9-_] — koi special chars nahi, koi spaces nahi.
  3. Profanity: Blacklist ke against filter karo (jaise 'badword', 'spam').
  4. Availability: SELECT COUNT(*) FROM urls WHERE short_url='mywork' — agar exist karta hai to 409 'Custom URL already taken' return karo.
  5. Reserve: INSERT INTO urls (short_url: 'mywork', long_url: 'https://myportfolio.com', is_custom: true)

Response: {shortURL: 'http://bit.ly/mywork', longURL: 'https://myportfolio.com'}

Auto-generated se collision ka problem

  • Problem: Counter 'abc123' generate karta hai, baad me user custom 'abc123' maangta hai → collision.
  • Solution 1 — Separate namespaces: Counter range [0 - 100B] use kare, custom URLs strings hain (hyphens, underscores jo Base62 me nahi hote).
  • Solution 2 — Prefix: Custom URLs ko /c/mywork aur auto ko /a/abc123 prefix do.
  • Bit.ly approach: Koi prefix nahi — custom URLs auto-generation se pehle check hote hain (custom ko priority milti hai).

02.8 Step 8 — Caching Strategy (Redis)

Caching hi is system ki jaan hai — 90%+ requests Redis se serve hote hain, DB tak jaate hi nahi. Diagram me Redis '2ms' latency ke saath dikhaya gaya hai.

Interview me ye zaroor bolo: Redis caching (diagram me 2ms latency). Cache hit 90%+ → <2ms redirect. Cache miss 10% → DB query ~50ms. Write-through: INSERT DB → SET cache immediately. TTL 24 hours (popular URLs cached rehte hain). Bloom filter non-existent URLs ke DB queries rokta hai (5MB for 10M URLs).

Cache design

  • Key: url:{short_url} — example: url:9i91c0
  • Value: JSON {longURL, expiresAt, isCustom}
  • TTL: 24 hours (86400 sec) — popular URLs cached rehte hain, unpopular expire hokar memory free karte hain

Cache flow

  1. Redirect request: Redis se GET url:9i91c0 — hit ho to longURL return karo (<1ms).
  2. Miss ho to: DB query karo → result cache karo: SET url:9i91c0 {longURL, expiresAt} EX 86400 → longURL return karo (~50ms pehli request).

Cache hit rate — 90%+ ka target

  • Popular URLs: Roz hazaron baar click hote hain → hamesha cached (har access par TTL refresh hota hai).
  • Unpopular URLs: Mahine me ek baar click → cache me nahi bhi ho to chalega (DB 10% traffic handle kar leta hai).

Write-through cache

URL creation par: INSERT INTO urls (...) → turant SET url:{short_url} (...) EX 86400 (creation par hi cache karo). Isse pehla redirect bhi fast hota hai — koi cache miss nahi.

Cache invalidation

  • URL update: User longURL ya expiration badle → UPDATE urls → DEL url:{short_url} (invalidate, agli request rebuild karegi)
  • URL delete: DELETE FROM urls → DEL url:{short_url}
  • Expiration: Cron expired URLs delete kare → DEL url:{short_url}

Bloom filter optimization

  • Problem: Non-existent short URL par cache miss → DB query kuch nahi deti → wasted query.
  • Solution: Bloom filter (10M URLs ke liye 5MB, 1% false positive rate).
  • Check: bf.contains('xyz123') == false ho to turant 404 return karo (koi DB query nahi). == true ho to shayad exist karta hai → DB query karo.
  • Update: URL creation par bf.add(short_url) karo.

02.9 Step 9 — Load Balancing & High Availability

Load balancer

02.10 Step 10 — Security & Abuse Prevention

URL shortener abuse ka easy target hai — spam, phishing, malware links. Isliye security ko design me pehle din se daalna padta hai, baad me patch nahi.

NEVER skip malicious URL detection: URL creation se pehle Google Safe Browsing API use karo. Phishing patterns check karo (paypa1.com vs paypal.com — edit distance). Rate limiting

  • Per IP: 100 URL creations/hour — Redis: INCR rate_limit:{ip} EX 3600, count > 100 ho to 429 'Too many requests'.

02.12 Step 12 — Encoding Comparison (Base62 vs Base64 vs Hex)

Short code banane ke liye kaunsi encoding? Base62, Base64 ya Hex — teeno ka comparison. Interview me ye comparison direct poochha jaata hai.

Base62 — [0-9a-zA-Z] = 62 chars

  • Example: encode(3748547) → '9i91c0' (6 chars)
  • Pros: URL-safe (koi special chars nahi), human-readable, short output (62^6 = 56B URLs).
  • Cons: Case-sensitive (9i91c0 ≠ 9I91C0 — users galat type kar sakte hain).

Base64 — [0-9a-zA-Z+/] = 64 chars

  • Example: encode(3748547) → '9i91c+' (6 chars)
  • Pros: Base62 se thoda zyada compact, standard encoding (libraries available).
  • Cons: URL-safe nahi hai — + aur / ko escape karna padta hai (%2B, %2F → URL lambi ho jaati hai), kam readable.

Hexadecimal (Base16) — [0-9a-f] = 16 chars

  • Example: encode(3748547) → '392b23' (6 chars chhote numbers ke liye)
  • Pros: Case-insensitive (392b23 = 392B23), bahut simple.
  • Cons: Bade numbers ke liye bahut lambi — 16^6 = sirf 16M URLs (62^6 = 56B ke mukable). 1B URLs ke liye 8-10 chars chahiye.

Base62 hi kyun chuna gaya?

  • Optimal balance: URL-safe + short + readable — teeno ek saath.
  • 62^7 = 3.5 trillion URLs — decades ke liye enough.
  • Bit.ly, TinyURL, Google (goo.gl) — sab Base62 use karte hain.
  • Case-sensitive caveat: Case-insensitive systems ke liye lowercase-only variant [0-9a-z] (36 chars) use karo — 36^7 = 78B URLs, phir bhi enough.

03.2 ID Generation — Deep Comparison

Teeno approaches — Counter (Zookeeper), Snowflake, Hash-based (SHA1) — side by side. Diagram me teeno approaches dikhaye gaye hain. Interview me ye comparison direct poochha jaata hai.

Interview me ye zaroor bolo: Teeno approaches compared — Counter (Zookeeper): sabse chhote URLs 6-7 chars, sequential, 2-3ms overhead. Snowflake: decentralized, 10-11 chars, 4M IDs/sec, no coordination. Hash (SHA1): deterministic deduplication, same URL → same short code, 0.01% collision — retry chahiye. Choose karo: shortest URL (counter), highest throughput (Snowflake), deduplication (hash).

Approach 1 — Counter with Zookeeper

Flow: Server → Zookeeper: increment counter → 3748547 milta hai → Base62 encode → '9i91c0'.

  • Pros: (1) Sequential IDs (predictable, time-ordered), (2) Sabse chhote URLs (billions ke liye 6-7 chars), (3) Guaranteed uniqueness (atomic increment = koi collision nahi).
  • Cons: (1) Single point of coordination (Zookeeper chahiye, ~3ms latency add hoti hai), (2) Bottleneck — saare servers ek hi counter query karte hain (Zookeeper 10K+ req/sec handle karta hai), (3) Dependency — Zookeeper down ho to URLs nahi ban sakte (cluster se mitigate hota hai).
  • Kab use karein: Production systems jinhe sabse chhote URLs chahiye (Bit.ly, TinyURL yehi use karte hain), Zookeeper dependency acceptable ho.

Approach 2 — Snowflake ID

Flow: Server locally 64-bit ID banata hai (timestamp + workerID + sequence) → Base62 encode → 'aBc123XyZ'. Structure: [41 bits timestamp][10 bits workerID][12 bits sequence] = 69 years + 1024 workers + 4096 IDs/ms.

  • Pros: (1) No coordination (har worker independent), (2) High throughput (4096 IDs/ms/worker = 4M IDs/sec across 1K workers), (3) No single point of failure, (4) Time-ordered (IDs monotonically badhte hain).
  • Cons: (1) Lambe URLs (10-11 chars vs counter ke 6-7), (2) Clock dependency (NTP sync chahiye, clock drift = collision), (3) WorkerID management (har server ko unique ID dena padta hai).
  • Kab use karein: High-throughput systems, decentralized architecture, lambe URLs acceptable ho (Twitter tweet IDs ke liye Snowflake use karta hai).

Approach 3 — Hash-based (SHA1)

Flow: SHA1(longURL) → 'd3e8f9a2b1c4e5f6...' (40 hex chars) → substring(0, 7) → 'd3e8f9a'.

  • Pros: (1) Deterministic — same long URL → same short URL = deduplication; user same URL dobara banaye to DB check bina existing short URL return karo, (2) No external dependency, (3) Stateless.
  • Cons: (1) Collision risk (birthday paradox: ~1M URLs → 0.01% collision probability with 7-char hash) — retry logic chahiye: substring(7, 14), (14, 21) try karo, (2) URL length guarantee nahi (retry ke baad 8-9 chars), (3) No time-ordering.
  • Kab use karein: Systems jahan deduplication valuable ho, retry logic acceptable ho, creation volume kam ho (<1M URLs).

Collision handling — teeno ka

  • Counter: Koi collision nahi (atomic increment uniqueness guarantee karta hai).
  • Snowflake: Collision tabhi jab (timestamp, workerID, sequence) tuple repeat ho → unique workerID + clock sync chahiye.
  • Hash: Collision probability = (n²) / (2 × 62^k) — n=URLs, k=chars. k=7, n=1M → 0.01% collision → retry with different substring ya timestamp salt append karo.

Production choices

  • Bit.ly: Counter-based (Zookeeper-like system) — shortest URLs ko priority.
  • Twitter: Snowflake for tweets — high throughput > short length.
  • Google (goo.gl, discontinued): Hash-based with retry — deduplication ka fayda liya.
  • Hybrid approach: Normal users ke liye counter, API/high-volume users ke liye Snowflake (alag URL prefixes: /s/ vs /a/).

Migration strategy

  1. Start with counter (simple, reliable).
  2. Zookeeper bottleneck ban jaye (>100K URL creations/sec) → Snowflake par migrate karo (har server ko workerID allocate karo).
  3. Deduplication important ho jaye (same URLs baar-baar shorten ho rahe hon) → hash-based caching layer add karo (naya ID banane se pehle check karo ki long URL pehle se shorten hua hai ya nahi).

03.3 Scaling & Optimization — 12 Techniques

Scale karne ke 12 techniques — ek hi jagah, interview ke liye yaad rakhne layak list. Har technique ke saath uska number ya fayda likha hai.

  1. Base62 encoding: Sequential counter (3748547) ko short string ('9i91c0') me convert karo — 6 chars = 56B URLs, URL-safe aur human-readable.
  2. Redis caching: 90% cache hit rate, <10ms redirect latency, 24-hour TTL — freshness aur memory ka balance.
  3. Zookeeper counter: Distributed atomic counter — saare servers ke liye unique IDs guarantee, 3-5 node cluster for high availability.
  4. Snowflake ID: Decentralized generation, 4M IDs/sec, no coordination, 64-bit structure (timestamp + workerID + sequence).
  5. Database sharding: hash(short_url) se shard karo — 10 shards = 100M URLs each, billions tak scale.
  6. Read replicas: 1 master (writes) + 5 slaves (reads), read/write split — 1M redirects/sec handle karo.
  7. Bloom filter: 10M URLs ke liye 5MB filter — non-existent short URLs ke DB queries rokta hai, 1% false positive acceptable.
  8. Analytics partitioning: Monthly partitions (analytics_2026_01) — purana data S3 me archive karo, recent queries fast rakho.

04.1 Interview Q1 — Unique short URL kaise banayein?

Interview ka sabse favorite sawaal: "How do you generate unique short URLs? Compare different approaches (counter, hash, Snowflake)." Neeche poora jawab hai — teeno approaches implementation ke saath.

Note: Is jawab me Base62 example (3748547 → '9i91c0') lesson ke mutabik likha hai — sahi calculation section 02.1 me dekho: 3748547 → 'fJar' banta hai, '9i91c0' = 8,513,319,076 ka code hai.

Approach 1 — Counter with Zookeeper

Centralized distributed counter. Implementation:

  1. Zookeeper counter maintain karta hai: /counters/url_counter with current value (example: 3748547).
  2. Server ID maangta hai: zk.getData('/counters/url_counter') → 3748547, zk.setData('/counters/url_counter', 3748548) (atomic increment).
  3. Base62 encode: characters = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ'; num = 3748547; result = ''; while (num > 0) { result = chars[num % 62] + result; num = floor(num / 62); } → '9i91c0'.
  4. Store: INSERT INTO urls (short_url: '9i91c0', long_url: 'https://...').
  5. Response: {shortURL: 'http://bit.ly/9i91c0'}.

Uniqueness guarantee: Zookeeper atomic increment ensure karta hai ki do servers ko kabhi same counter value na mile — concurrent requests par bhi. Zookeeper cluster (3-5 nodes) Paxos consensus se consistency maintain karta hai; leader fail ho to naya leader elect hota hai, counter state preserved rehta hai.

Base62 capacity: 62^6 = 56.8 billion unique URLs (6 characters), 62^7 = 3.5 trillion (7 characters) — decades ke liye sufficient.

Pros: (1) Sabse chhote URLs (6-7 chars), (2) Sequential IDs (time-ordered, 'recent URLs' query kar sakte ho), (3) Guaranteed uniqueness (collision handling nahi chahiye), (4) Predictable capacity (pata hai kab aur chars add karne hain).

Cons: (1) Zookeeper dependency (2-3ms latency add hoti hai), (2) Bottleneck — saare servers ek hi counter query karte hain (Zookeeper 10K+ req/sec handle karta hai, read replicas se 100K tak scale), (3) Zookeeper down ho to URLs nahi ban sakte (cluster se mitigated).

Production: Bit.ly counter-based approach use karta hai.

Approach 2 — Hash-based (SHA1/MD5)

Long URL ko hash karo, substring nikalo:

  1. Hash URL: hash = SHA1('https://www.facebook.com/example-user/') = 'd3e8f9a2b1c4e5f6a7b8c9d0e1f2a3b4c5d6e7f8' (160 bits = 40 hex chars).
  2. 7 chars nikalo: shortCode = hash.substring(0, 7) = 'd3e8f9a'.
  3. Collision check: SELECT COUNT(*) FROM urls WHERE short_url='d3e8f9a' — count > 0 ho to agle 7 chars try karo: hash.substring(7, 14), (14, 21)… (5 attempts tak). Sab collide ho to timestamp append karo: hash(longURL + currentTimestamp).
  4. Store aur response: {shortURL: 'http://bit.ly/d3e8f9a'}.

Collision probability: SHA1 output space = 2^160; 7 hex chars = 16^7 = 268M possible values. 1M URLs par collision ≈ (1M²) / (2 × 268M) ≈ 0.002%. 10M URLs par ≈ 0.2% (retries chahiye).

Pros: (1) Deterministic — same long URL → same hash → same short URL; deduplication: user same URL dobara banaye to SELECT * FROM urls WHERE long_url='...' se existing short URL return karo (nayi creation nahi), (2) No external dependency, (3) Stateless, (4) Deduplication se storage bachta hai (10% URLs duplicates hain → 10% storage saving).

Cons: (1) Collision risk (retry logic complex), (2) URL length guarantee nahi (retry ke baad 8-9 chars), (3) No time-ordering, (4) Zyada DB queries (har attempt par collision check).

Production: Google ka goo.gl hash-based approach use karta tha (ab discontinued).

Approach 3 — Snowflake ID (Twitter-style)

Decentralized 64-bit ID generation. Structure: [1 bit unused][41 bits timestamp][10 bits workerID][12 bits sequence].

  • Timestamp (41 bits): Custom epoch (Jan 1, 2020) se milliseconds — 2^41 ms ≈ 69 years. Example: Jan 26, 2026 10:30:45.123 → ms since epoch: 189432045123.
  • WorkerID (10 bits): Har server ki unique ID (0-1023) — startup par assign hoti hai (config, environment variable, ya auto-assigned). 2^10 = 1024 workers.
  • Sequence (12 bits): Ek millisecond ke andar counter, har ms reset — 2^12 = 4096 IDs/ms/worker.

Generation: (1) Timestamp lo: ts = currentTimeMillis() - CUSTOM_EPOCH. (2) Sequence check: if (lastTimestamp == ts) { sequence = (sequence + 1) & 0xFFF; if (sequence == 0) wait until next ms; } else { sequence = 0; lastTimestamp = ts; }. (3) Bits combine karo: id = (ts << 22) | (workerID << 12) | sequence. Example: ts=189432045123, workerID=123, sequence=0 → id = 792345678901234567 (64-bit). (4) Base62 encode: 'aBc123XyZ' (10 chars).

Pros: (1) No coordination, (2) High throughput: 4096 IDs/ms/worker × 1024 workers = 4M IDs/sec, (3) No single point of failure, (4) Time-ordered, (5) Scalable (1024 workers tak).

Cons: (1) Lambe URLs: 10-11 chars (lower 42 bits use karke 7-8 chars tak la sakte ho), (2) Clock dependency (NTP sync chahiye, clock drift = collision), (3) WorkerID management (har server ko unique ID dena padta hai).

Production: Twitter tweet IDs ke liye Snowflake use karta hai.

04.2 Interview Q2 — 1B redirects/day, <100ms latency

Interview ka doosra bada sawaal: "How do you handle 1 billion redirects per day with low latency (<100ms)?" Jawab ka core hai — aggressive caching aur optimized architecture.

Interview me ye zaroor bolo: (1) Redis cache 90% hits <2ms, (2) 5 DB read replicas 10% misses handle karte hain (11.5K req/sec ÷ 5 = 2.3K/replica), (3) 100 app servers × 1K req/sec = 100K capacity (peak 115K), (4) CDN top 1000 URLs (80% traffic) edge par cache karta hai <50ms globally. Horizontally scale hota hai.

Scale calculation

  • 1B redirects/day = 1,000,000,000 / 86400 sec ≈ 11,500 req/sec average
  • Peak (10× average) = 115,000 req/sec traffic spikes ke time

Caching strategy (diagram me Redis 2ms latency)

  • Cache design: Key: url:{short_url} (example: url:9i91c0). Value: JSON {longURL, expiresAt, isCustom}. TTL: 86400 sec (24 hours).
  • Redirect flow: (1) User click: GET http://bit.ly/9i91c0. (2) Short code extract karo. (3) Redis lookup: redis.get('url:9i91c0') — mila to expiration check karo, expired ho to 410, warna 301 redirect. Latency: <1ms. (4) Cache miss (10% requests): DB query karo — nahi mila to 404, mila to cache me likho (redis.set(..., 'EX', 86400)) aur 301 return karo. Latency: ~50ms. (5) Browser automatically redirect karta hai.
  • Hit rate optimization: Target >90%. Popular URLs (viral link — 1M clicks/day) pehli request ke baad cached rehte hain, agle 999,999 requests cache se (<1ms each). Unpopular URLs (mahine me ek click) cache me nahi bhi ho to chalega — DB 10% traffic = 11.5K req/sec handle kar leta hai.
  • Write-through caching: URL creation par INSERT ke saath turant redis.set('url:' + shortURL, ..., 'EX', 86400) — pehla redirect bhi fast.

Database optimization

  • Read replicas: 1 master (writes) + 5 read replicas (reads). Read/write split: creation → master, redirects → replicas (round-robin). Har replica: 11.5K ÷ 5 = 2.3K req/sec (PostgreSQL ke liye aasan).
  • Connection pooling: Har app server: 50 DB connections (pool) — connection reuse se ~10ms overhead bachta hai. PgBouncer: 1000 app servers ke 100 connections ko DB ke 100 connections me multiplex karta hai.
  • Indexes: PRIMARY KEY on short_url (B-tree, O(log N) lookup). 1B URLs par index depth ≈ 4-5 levels, query time <10ms.
  • Sharding (agar zaroorat ho): hash(short_url) mod 10 → 10 shards, har shard 100M URLs. Short code se shard determine karo, request sahi shard par route karo.

Application server scaling

  • Redirect handling CPU-light hai (Redis lookup, JSON parse), I/O-bound hai (network calls). Servers: 100 servers × 1K req/sec = 100K req/sec capacity (peak 115K headroom ke saath).
  • Auto-scaling: CPU > 70% ho to servers add karo, CPU < 30% ho to hatao (Kubernetes CPU/memory metrics par auto-scale karta hai).
  • Load balancing: Round-robin — requests evenly distribute. Health checks har 10 sec — unhealthy servers pool se bahar. Sticky sessions NOT needed (stateless).
  • Redis cluster: Single Redis instance: 10K-50K req/sec (high scale par bottleneck). Redis Cluster: 10 master nodes + 10 replicas, short_url hash se sharding — har node 11.5K req/sec (total 115K req/sec). Har master ka 1 replica (failover).

Bloom filter optimization

Problem: User typo kare — http://bit.ly/xyz123 (exist hi nahi karta) → cache miss → DB query → kuch nahi milta → wasted query (1% requests = 1.15K req/sec). Solution: Bloom filter (10M URLs ke liye 5MB, 1% false positive). bloomFilter.contains('xyz123') == false ho to turant 404 (koi Redis/DB query nahi). True ho to shayad exist karta hai → Redis/DB query karo. Benefit: 1% unnecessary DB queries khatam = 1.15K req/sec bachta hai. False positives (1%) DB query karte hain — acceptable overhead.

CDN for popular URLs (optional)

Top 1000 sabse zyada click hone wale URLs ke 301 redirects CDN edge par cache karo (Cloudflare/Fastly — 200+ global locations). User request → CDN edge → cached redirect (origin server tak request hi nahi). Latency: <50ms globally (origin ke 100-200ms ke mukable). Benefit: Origin server load 80% kam (top 1000 URLs 80% traffic hain).

Latency breakdown

CaseBreakdownTotal
Cache hit (90%)Redis lookup 0.5ms + JSON parse 0.1ms + redirect response 0.5ms~1-2ms
Cache miss (10%)DB query 30ms + Redis write 0.5ms + redirect 0.5ms~31ms

Monitoring

p50, p95, p99 latency track karo: p50 < 5ms (median — mostly cache hits), p95 < 50ms (kuch cache misses), p99 < 100ms (DB queries — acceptable tail). Alert agar p99 > 100ms ho (investigate karo: DB slow? Redis down? Network issue?).

Result: System 1B redirects/day (115K req/sec peak) handle karta hai <100ms latency ke saath — 90%+ cache hit rate = most requests <2ms, 10% cache misses = <50ms, horizontally scale hota hai (servers/Redis nodes add karte jao).

04.3 Interview Q3 — Abuse prevention & rate limiting

Teesra bada sawaal: "How do you prevent abuse (spam URLs, malicious links) and implement rate limiting?" Jawab multi-layered defense hai — ek layer nahi, 6 layers.

Layer 1 — Rate limiting (spam URL creation roko)

  • Per-IP rate limiting: 100 URL creations per hour per IP. Implementation: Redis counter — POST /s/url par key = 'rate_limit:create:' + ip_address, count = redis.incr(key), count == 1 ho to redis.expire(key, 3600) (pehli request par 1-hour TTL), count > 100 ho to 429 'Too Many Requests, try again in X minutes'. Authenticated users ko bypass — higher limit (1000/hour), jo accounts banane ke liye encourage karta hai.
  • Per-user rate limiting (authenticated): 1000 URLs per day per user. DB counter — creation par SELECT quota_used, quota_limit FROM users WHERE user_id={user_id}, quota_used >= quota_limit ho to 429 'Daily quota exceeded, upgrade to premium'. UPDATE users SET quota_used = quota_used + 1. Reset daily: midnight par cron UPDATE users SET quota_used = 0.

Layer 2 — CAPTCHA challenge (bots detect karo)

  • Trigger conditions: IP 1 minute me 10 URLs banaye → CAPTCHA. IP ke 5 failed attempts → CAPTCHA. Nayi IP (first-time user) → risk score ke basis par optional CAPTCHA.
  • Implementation: Google reCAPTCHA v3 (invisible, user ko 0.0-1.0 score deta hai). Frontend: reCAPTCHA widget include karo, form submit par token = await grecaptcha.execute(SITE_KEY, {action: 'create_url'}), POST /s/url with {longURL, captchaToken: token}. Backend: Google se verify karo — https://www.google.com/recaptcha/api/siteverify. Score 0.0 = bot, 1.0 = human. Score < 0.5 ho to 400 'CAPTCHA failed' (image challenge dikhao), >= 0.5 ho to aage badho.

Layer 3 — Malicious URL detection (phishing, malware)

  • Blacklist check: Google Safe Browsing API — POST https://safebrowsing.googleapis.com/v4/threatMatches:find with threatTypes ['MALWARE', 'SOCIAL_ENGINEERING', 'UNWANTED_SOFTWARE']. response.matches.length > 0 ho to 400 'Malicious URL detected: ' + threatType. Cost: Free tier 10K lookups/day, paid tier 500K lookups/day.
  • Phishing pattern detection: Domain similarity check — user 'http://paypa1.com' submit kare (paypal.com ki jagah '1' instead of 'l'), edit distance: levenshteinDistance('paypa1.com', 'paypal.com') = 1 (bahut similar). Distance < 2 ho aur domain popular list me ho to suspicious flag karo. URL obfuscation check karo: IP addresses (http://192.168.1.1), excessive subdomains (http://login.secure.account.paypal-verify.com — red flag), long URL me hi shortener (http://bit.ly/... ko shorten karna = suspicious).
  • User reporting: Har short URL page par 'Report abuse' button. Submission: POST /api/v1/report with {shortURL, reason: 'phishing'/'spam'/'malware'/'inappropriate'}. Threshold: 10 reports → auto-flag for review; trusted users (verified accounts) ke 3 reports → auto-flag. Manual review: moderator dekhta hai — confirmed malicious → DELETE FROM urls + cache se DEL; false positive → reviewed mark karo, future reports ignore karo.

Layer 4 — Content scanning (uploaded pages)

Agar long URL user-uploaded content ki taraf point kare (jaise image hosting site), to content scan karo: Virus scan (ClamAV), Image moderation (inappropriate content ke liye). Flag ho to URL creation reject karo.

Layer 5 — Abuse monitoring aur automated bans

  • Metrics: URLs created per IP histogram (100s URLs banane wale IPs pehchano), 24 hours ke baad 0 clicks wale short URLs (likely spam), high report rate wale URLs.
  • Automated bans: IP 1 hour me 500 URLs banaye (rate limit ke bawjood, multiple IPs use karke) → IP range ban karo. User account 50 reported URLs banaye → account ban karo.
  • Honeypot: Fake short URLs banao (kabhi publicly share mat karo) — agar koi click kare to wo IP likely bot hai (URL space scan kar raha hai) → ban karo.

Layer 6 — URL validation

  • Protocol check: Sirf http:// ya https:// se start hona chahiye. Reject karo: javascript:alert('XSS'), data:text/html,<script>..., file:///etc/passwd.
  • Length check: longURL < 2048 chars (browser limit).
  • DNS check: Domain resolve karo (dns.lookup(domain)) — fail ho to 'Invalid domain' reject karo. Domain internal IP ho (192.168.x.x, 10.x.x.x) to reject karo (SSRF prevention).

Authentication & authorization

  • Optional login: Anonymous URL creation allowed (Bit.ly model) ya login required (enterprise model).
  • OAuth providers: Google, GitHub, Twitter (trusted identity).
  • Benefits: Apni URLs track karo (GET /api/v1/users/{userId}/urls), edit/delete karo (sirf creator modify kar sake), private URLs (sirf creator analytics dekh sake), higher rate limits (1000/day vs anonymous ke 100/day).
  • API keys: Programmatic access ke liye — user.api_key = generateRandomString(32), hash store karo (bcrypt.hash(api_key)). Usage: POST /s/url with header 'Authorization: Bearer {api_key}'. Rate limit per API key: 10K requests/day — redis.incr('api_key_quota:' + api_key_hash). Compromise ho to regenerate karo, purani key invalid.

Legal compliance

  • Terms of Service: Users agree karte hain ki malicious/spam URLs nahi banayenge — violation → account termination.
  • DMCA takedown: Copyright holders URL removal request kar sakte hain — verify karo → DELETE URL → creator ko notify karo.
  • Law enforcement: Legal requests (court orders) par URL creator identity share karni padti hai.

Result: Multi-layered defense — Rate limiting (100/hour per IP, 1000/day per user), CAPTCHA (bot detection, reCAPTCHA v3 scoring), Malicious URL detection (Safe Browsing API, pattern matching), User reporting (community moderation), Monitoring & bans (automated abuse detection) — spam 99% kam hota hai, legitimate users unaffected rehte hain, malicious URLs creation se pehle block ya baad me flag hote hain.

Rate limiting (abuse prevention): 100 URLs/hour per IP (Redis INCR with 3600 sec TTL), 1000/day authenticated users ke liye. 10 URLs/minute par CAPTCHA (reCAPTCHA v3 scoring). 500 URLs/hour banaye to IP ban. Malicious URL detection Safe Browsing API se. User reporting threshold: 10 reports → manual review.

Base62 matlab characters [0-9a-zA-Z] — total 62 chars. Kisi bhi number ko 62 se baar-baar divide karke remainder se short string banate hain. Lesson me example 3748547 → '9i91c0' likha hai, lekin sahi calculation se 3748547 → 'fJar' banta hai — '9i91c0' actually 8,513,319,076 ka code hai (ye lesson ki galti hai, Lab 1 me khud verify karo). Yehi use hota hai kyunki ye URL-safe hai (koi + ya / nahi), human-readable hai, aur chhota output deta hai — 62^6 = 56 billion URLs sirf 6 characters me, 62^7 = 3.5 trillion 7 characters me. Base64 thoda compact hai lekin + aur / URL-safe nahi hain, aur Hex (16 chars) ko 1B URLs ke liye 8-10 chars chahiye. Bit.ly, TinyURL aur goo.gl — sab Base62 use karte hain.
Zookeeper ek distributed coordination service hai. Counter ek node par store hota hai — /counters/url_counter — aur har increment atomic hota hai (zk.setData). Saare servers ek hi counter se ID lete hain, to do servers ko kabhi same value nahi milti — concurrent requests par bhi. Zookeeper cluster 3-5 nodes ka hota hai, quorum = majority, leader election hoti hai, aur counter disk par persist hota hai. Latency 2-3ms hoti hai. Agar Zookeeper down ho to URLs nahi ban sakte — isliye cluster aur UNIQUE constraint backup mandatory hai.
Snowflake Twitter-style decentralized 64-bit ID hai: [1 bit unused][41 bits timestamp][10 bits workerID][12 bits sequence]. 41 bits timestamp = custom epoch se milliseconds (2^41 ms ≈ 69 years). 10 bits workerID = har server ki unique ID (0-1023, total 1024 workers). 12 bits sequence = ek millisecond me counter (4096 IDs/ms/worker). Example: ts=189432045123, workerID=123, sequence=0 → ID = (ts << 22) | (123 << 12) | 0 = 792345678901234567, Base62 me 'aBc123XyZ' (10 chars). Throughput 4M IDs/sec tak ja sakta hai, bina kisi coordination ke.
Hash-based approach me SHA1(longURL) karke pehle 7 characters short code banate hain. Collision check ke liye DB me SELECT COUNT(*) karte hain — agar short code pehle se hai to hash ke agle 7 characters try karte hain: substring(7, 14), phir (14, 21), 5 attempts tak. Sab fail ho to hash(longURL + timestamp) use karte hain. 1M URLs par 7-char hash ki collision probability ~0.01% hoti hai (birthday paradox), 10M par ~0.2%. Isliye retry logic mandatory hai, aur DB UNIQUE constraint aakhri safety net hai. 5 attempts ke baad counter-based ID par fall back karo.
301 Permanent hai — browser redirect cache kar leta hai, agli clicks seedha long URL par jaati hain bina server request ke. Fayda: server load kam. Nuksaan: pehli click ke baad analytics nahi milti. 302 Temporary hai — browser cache nahi karta, har click server se guzarta hai. Fayda: har click track kar sakte ho. Nuksaan: server load zyada. Bit.ly 302 use karta hai kyunki use har click ki analytics chahiye. SEO aur permanent domain move ke liye 301 sahi hai.
1B/day matlab ~11,500 req/sec average aur peak 115,000 req/sec (10×). Core strategy: Redis caching — 90%+ hit rate, cache hit <2ms, cache miss ~50ms. Write-through cache: creation par hi cache bharo. Database: 1 master + 5 read replicas, read/write split — har replica 2.3K req/sec. App servers: 100 servers × 1K req/sec = 100K capacity. Bloom filter: non-existent URLs ke DB queries rokta hai (5MB for 10M URLs). CDN: top 1000 URLs (80% traffic) edge par cache — <50ms globally, origin load 80% kam. Monitoring: p50 <5ms, p95 <50ms, p99 <100ms.
Key: url:{short_url} — jaise url:9i91c0. Value: JSON {longURL, expiresAt, isCustom}. TTL: 24 hours (86400 sec). Flow: redirect request aaye to Redis se GET karo — hit ho to <1ms me longURL mil jata hai. Miss ho to DB query karo aur result cache me daalo (SET ... EX 86400). Write-through: URL creation par INSERT ke saath turant cache SET karo taaki pehla redirect bhi fast ho. Invalidation: URL update/delete/expiry par DEL url:{short_url} karo. Popular URLs har access par TTL refresh ki wajah se cached rehte hain, unpopular 24h me expire hokar memory free karte hain.
Bloom filter ek probabilistic data structure hai jo batata hai ki koi item set me hai ya nahi — 'nahi hai' ka jawab 100% sahi hota hai, 'hai' ka jawab kabhi-kabhi galat (false positive). 10M URLs ke liye sirf 5MB chahiye, 1% false positive rate. URL shortener me kaam: user typo kare (bit.ly/xyz123 jo exist nahi karta) to pehle Bloom filter check karo — false ho to turant 404, koi Redis/DB query nahi. True ho to shayad exist karta hai, DB query karo. Isse 1% unnecessary DB queries bachti hain (~1.15K req/sec). URL creation par bf.add(short_url) karna mat bhoolo.
Shard key hoti hai hash(short_url) mod N. Example: hash('9i91c0') mod 10 → shard 3. 10 shards hain to har shard 100M URLs handle karta hai, total 1B. Request aaye to short code se shard determine karo aur sahi shard par route karo — single-shard lookup fast hota hai. Cross-shard query sirf user ki URLs list karte time hoti hai (user_id se) — saare shards query karke aggregate karte hain, chhota result set hai to acceptable hai. Sharding ke saath har shard par apna index aur replica set hota hai.
Master-slave replication me master sirf writes handle karta hai (URL creation) aur slaves sirf reads (redirects). Is system me 1 master + 5 slaves hain. Read/write split: creation request master par jati hai, redirect requests slaves par round-robin se baant di jati hain. Har slave 11.5K ÷ 5 = 2.3K req/sec handle karta hai. Replication lag <1 sec acceptable hai — user URL banaye aur 1 sec tak redirect na ho to eventually consistent hai. Connection pooling (PgBouncer) se 1000 app servers ke connections DB ke 100 connections me multiplex hote hain.
Custom URL ke liye 5 validation checks hain: length 3-20 chars, allowed chars sirf [a-zA-Z0-9-_], profanity blacklist, availability check (SELECT COUNT(*) — exist ho to 409 'already taken'), phir reserve (INSERT with is_custom=true). Auto-generated se collision ka problem: counter 'abc123' generate kare aur baad me user custom 'abc123' maange. Solutions: separate namespaces (counter range [0-100B], custom strings me hyphens/underscores jo Base62 me nahi), ya prefix (/c/mywork vs /a/abc123). Bit.ly ka approach: koi prefix nahi — custom URLs auto-generation se pehle check hote hain, custom ko priority milti hai.
URL banate time expires_at store hota hai (jaise '2026-12-31 23:59:59'). Redirect ke time check hota hai: expires_at < NOW() ho to 410 Gone return karo 'This link has expired' message ke saath. Default expires_at = NULL hota hai (kabhi expire nahi). Cleanup ke liye roz raat 2 AM cron job chalta hai: 30 din se zyada purane expired URLs select karo, batch me 10K delete karo, aur har deleted URL ke liye cache se DEL url:{short_url} karo. Expired short URLs reuse ho sakte hain (hash space reusable hai). Storage bachta hai — 1B URLs me 10% delete karne se 100GB bachta hai.
Redirect ko block nahi karte — async logging use karte hain. Click hote hi event Kafka me publish hota hai (event_type: url_click, short_url, timestamp, metadata: ip, user_agent, referrer) aur Analytics Consumer baad me DB me insert karta hai. Redirect <10ms me respond kar deta hai. Real-time counters Redis me hote hain: INCR click_count:9i91c0 (total), HINCRBY daily hash (per-day), PFADD HyperLogLog (unique visitors). Hourly batch job analytics table aggregate karke urls.click_count update karta hai. Bahut popular URLs (>1M clicks/day) ke liye 10% sampling karte hain — storage kam, accuracy maintain rehti hai.
Redis counters se. Per IP: 100 URL creations/hour — key 'rate_limit:{ip}', INCR karo, pehli request par EXPIRE 3600 sec set karo, count > 100 ho to 429 'Too Many Requests'. Per user (authenticated): 1000/day — DB quota_used/quota_limit check karo, midnight par cron reset karta hai. Per short URL: 10K clicks/min (popular link se DDoS rokne ke liye). API keys: 10K req/day per key. Rate limit cross karne par 429 status code milta hai. IP 1 hour me 500 URLs banaye (limits ke bawjood) to IP range ban kar do.
Teen layers hain. Pehla: Google Safe Browsing API — URL creation se pehle POST karo, threatTypes MALWARE, SOCIAL_ENGINEERING, UNWANTED_SOFTWARE check karo, match ho to 400 'Malicious URL detected'. Doosra: phishing pattern — domain similarity (levenshtein distance, jaise 'paypa1.com' vs 'paypal.com' distance 1), IP-based URLs, excessive subdomains, aur long URL me hi shortener hona — sab red flags hain. Teesra: user reporting — 10 reports par manual review, trusted users ke 3 reports par auto-flag. Confirm malicious ho to DELETE URL + cache invalidate karo. Protocol validation bhi zaroori hai: javascript:, data:, file: schemes reject karo (XSS/SSRF prevention).
CAP Theorem kehta hai Consistency, Availability aur Partition tolerance — teeno ek saath nahi mil sakte. URL shortener me Availability >> Consistency chunte hain. Redirect path par availability sabse upar hai — user link click kare aur redirect na ho to service bekaar hai. Analytics ke liye eventual consistency acceptable hai — click count thoda der se update ho to chalega. Lekin short-code uniqueness par koi compromise nahi — wahan strong consistency chahiye (Zookeeper atomic counter ya DB UNIQUE constraint). Replication lag <1 sec acceptable hai isiliye.
Zookeeper counter chuno agar: sabse chhote URLs chahiye (6-7 chars critical), Zookeeper dependency acceptable ho, creation rate <100K/sec ho. Snowflake chuno agar: high throughput chahiye (>100K creations/sec), decentralization chahiye (koi coordination nahi), lambe URLs (10-11 chars) acceptable hon. Bit.ly counter use karta hai (shortest URLs), Twitter Snowflake use karta hai (tweets ke liye throughput). Hybrid bhi kar sakte ho: normal users ke liye counter (/s/ prefix), API/high-volume users ke liye Snowflake (/a/ prefix). Migration: counter se start karo, Zookeeper bottleneck bane to Snowflake par jao.
Do main nuksaan hain. Pehla: lambe short URLs — 64-bit number Base62 me 10-11 chars ka hota hai, counter ke 6-7 ke mukable. Workaround: sirf lower 42 bits use karo to 7-8 chars ho jate hain (phir bhi 69 years + 1024 workers + 1 sequence). Doosra: clock dependency — saare servers ke clocks synchronized hone chahiye (NTP). Clock drift ya clock peeche jaane se collision ho sakta hai. Teesra: workerID management — har server ko unique ID assign karni padti hai (manual config ya centralized registry). Inke bawjood high-throughput decentralized systems ke liye Snowflake best hai.
Base62 [0-9a-zA-Z]: 62 chars, URL-safe, readable, 62^6 = 56B URLs 6 chars me. Base64 [0-9a-zA-Z+/]: 64 chars, thoda compact lekin + aur / URL-safe nahi — escape karne par URL lambi ho jati hai. Hex [0-9a-f]: 16 chars, case-insensitive aur simple lekin 16^6 = sirf 16M URLs — 1B URLs ke liye 8-10 chars chahiye. Conclusion: Base62 optimal balance hai — URL-safe + short + readable. Case-insensitive system chahiye to Base36 [0-9a-z] use karo — 36^7 = 78B URLs, phir bhi enough hai.
Ek URL ≈ 610 bytes: short_url 10 bytes + long_url 500 bytes average + metadata 100 bytes. 1B URLs → 610 bytes × 1B = 610 GB (~600 GB). Indexes ka 30% overhead → 600 × 1.3 = 780 GB. Analytics: 200 bytes/click, 1B clicks/day = 200 GB/day, 90 days retention = 18 TB — monthly partitions aur S3 archive se manage karte hain. Interview me ye calculation haath se karke dikhana bahut impressive lagta hai — interviewer ko pata chalta hai ki tumne scale ke baare me socha hai.
Client → Load Balancer (round robin) → Multiple servers. Round robin requests evenly baantta hai (Server 1 → 2 → 3 → 1). Health checks har 10 sec ping karte hain — unresponsive server pool se hat jata hai. Sticky sessions ki zaroorat nahi kyunki servers stateless hain — koi bhi server koi bhi request handle kar sakta hai. URL creation CPU-bound hai (10 servers × 1000 req/sec = 10K/sec), redirects I/O-bound hain (100 servers × 10K req/sec = 1M/sec). CPU > 80% ho to auto-scale se servers add hote hain, < 20% ho to hat te hain.
Teen cases me cache invalidate karte hain. URL update: user longURL ya expiration badle → UPDATE urls → DEL url:{short_url} (agli request cache rebuild karegi). URL delete: DELETE FROM urls → DEL url:{short_url}. Expiration: cron expired URLs delete kare → DEL url:{short_url}. Write-through caching me creation par hi cache bhar diya jata hai (INSERT → SET cache), isliye pehla redirect bhi fast hota hai. TTL 24 hours hai — popular URLs har access par TTL refresh ki wajah se cached rehte hain.
Ye latency percentiles hain — p50 matlab median (50% requests isse fast), p95 matlab 95% requests isse fast, p99 matlab 99% requests isse fast. URL shortener me target: p50 < 5ms (mostly cache hits), p95 < 50ms (kuch cache misses), p99 < 100ms (DB queries — acceptable tail). Alert lagate hain: p99 > 100ms ho to investigate karo — DB slow hai? Redis down hai? Network issue hai? Interview me sirf average latency bolna kaafi nahi — percentiles bolne se pata chalta hai ki tum tail latency samajhte ho.
Teen conditions par: IP 1 minute me 10 URLs banaye, IP ke 5 failed attempts hon, ya nayi IP (first-time user) risk score ke basis par. Google reCAPTCHA v3 use hota hai — invisible hai, user ko 0.0-1.0 score deta hai (0.0 = bot, 1.0 = human). Score < 0.5 ho to image CAPTCHA challenge dikhate hain, >= 0.5 ho to aage badhne dete hain. CAPTCHA bots ko rokta hai jo millions of short URLs generate karke spam karte hain.
Chhe layers hain. Rate limiting (100/hour per IP, 1000/day per user). CAPTCHA (bot detection, reCAPTCHA v3). Malicious URL detection (Google Safe Browsing API + phishing patterns). User reporting (10 reports → manual review). Monitoring aur bans (IP histogram, 0-click spam URLs, honeypot fake URLs). URL validation (protocol check — javascript:/data:/file: reject, length < 2048 chars, DNS check, internal IP reject — SSRF prevention). Authentication (OAuth, API keys with 10K req/day limit). Legal compliance (ToS, DMCA takedown, law enforcement requests). Result: spam 99% kam, legitimate users unaffected.
Hash deterministic hota hai — same long URL ka hamesha same hash banta hai, to same short URL milta hai. User same URL dobara shorten kare to DB me long_url se check karke existing short URL return kar dete hain — nayi entry banane ki zaroorat nahi. Isse storage bachta hai: lagbhag 10% URLs duplicates hote hain, to 10% storage save hota hai. Counter aur Snowflake me har creation par naya ID banta hai, chahe URL pehle se ho — wahan deduplication ke liye alag se long_url par lookup karna padta hai.
Analytics table bahut fast badhta hai — 1B clicks/day × 200 bytes = 200 GB/day, 90 days me 18 TB. Partition BY RANGE (clicked_at) se monthly partitions bante hain (analytics_2026_01, analytics_2026_02). Fayde: recent queries fast hoti hain (sirf relevant partition scan hoti hai), purana data S3 me archive karna aasan hota hai, aur purane partitions drop karna fast hota hai (DELETE ki jagah DROP PARTITION). Index (short_url, clicked_at) time-series queries ke liye hota hai.
Chaos engineering matlab jaan-boojh kar failures inject karke dekhna ki system recover hota hai ya nahi. URL shortener me: random server kill karo (load balancer ko hatana chahiye), Zookeeper leader kill karo (naya leader <10 sec me elect hona chahiye, counter state preserved), network partition karo (replicas ko lag ke saath eventually consistent hona chahiye), Redis node kill karo (replica se failover). Load test bhi karte hain: 100K req/sec redirects simulate karo (JMeter, Locust) — latency measure karo aur bottlenecks pehchano. Edge cases test karo: expired URL redirect, custom URL collision, 2KB lambi URL, malicious URL detection.
Is lesson me relational database (PostgreSQL jaisi) use hoti hai — urls table me short_url PRIMARY KEY hai, analytics table me time-series index hai, users table me UNIQUE email hai. SQL isliye accha hai: strong consistency chahiye (uniqueness), joins kam hain lekin transactions aur indexes zaroori hain, aur partitioning support hai. NoSQL (jaise DynamoDB/Cassandra) bhi chal sakta hai scale ke liye — partition key short_url, lekin secondary indexes aur cross-shard user queries mushkil hote hain. Interview me dono ka trade-off bolo: SQL — consistency + indexes; NoSQL — massive write scale. Is design me SQL + sharding + read replicas kaafi hain.
Capacity se decide karo: 62^6 = 56.8 billion URLs, 62^7 = 3.5 trillion. Agar 1B URLs store karne hain to 6 chars kaafi hain (56B capacity), lekin growth aur safety margin ke liye 7 chars use karte hain (3.5T). Bit.ly 6-7 chars use karta hai. Snowflake IDs 64-bit hote hain to 10-11 chars ban jate hain — lower 42 bits use karke 7-8 chars tak la sakte ho. Hash approach me retry ke baad 8-9 chars bhi lag sakte hain. Interview me bolo: length capacity planning se aati hai — pehle estimate karo kitne URLs chahiye, phir chars chuno.
CDN top 1000 sabse zyada click hone wale URLs ke 301 redirects ko edge locations (200+ global) par cache karta hai. User request CDN edge par aati hai aur wahi se cached redirect mil jata hai — origin server tak request hi nahi jati. Latency <50ms globally hoti hai (origin ke 100-200ms ke mukable). Benefit: origin server load 80% kam ho jata hai kyunki top 1000 URLs 80% traffic hain. CDN sirf popular URLs ke liye use hota hai — har URL edge par cache karna practical nahi hai.
Diagram ke numbers: encryption 1ms, server-to-DB 5ms, total round trip '=16ms + 16ms' (server processing + DB query). Redirect flow: cache hit (90% requests) — Redis lookup 0.5ms + JSON parse 0.1ms + redirect response 0.5ms = ~1-2ms. Cache miss (10%) — DB query 30ms + Redis write 0.5ms + redirect 0.5ms = ~31ms. Average latency 90% hit rate par ~6.8ms hoti hai. URL creation: Zookeeper counter 2-3ms + Base62 encode <1ms + DB insert ~5ms + cache SET <1ms = ~10ms. Ye numbers interview me bolne se tumhara design credible lagta hai.
45-minute interview me roughly: 5 min requirements (functional + non-functional + scope clarify), 5 min API design, 10 min HLD (Client → Server → DB + data flow), 15 min LLD (ID generation ke 3 tareeke compare karke ek chuno, redirect flow, caching), 5 min schema + scaling (sharding, replicas, storage estimate), 5 min security + monitoring + edge cases. Har section ke baad interviewer se confirm karo — 'kya main aage badhun ya is par detail chahiye?' Time bacha to deep dive karo: Bloom filter, Snowflake bit layout, ya analytics pipeline. Ek line yaad rakho: Long URL → unique ID → Base62 → DB + Redis → redirect + analytics.
Teen critical alerts: error rate > 1% ho to alert (kuch toot raha hai), cache hit rate < 80% ho to alert (Redis issue ho sakta hai), Zookeeper down ho to alert (critical — counter unavailable hai to URLs nahi ban sakte). Metrics track karo: URL creation rate (spikes, capacity planning), redirect latency p50/p95/p99, 404 rate (broken links), 410 rate (expired links), 5xx errors, top 100 popular URLs. Dashboards: real-time (requests/sec, active connections, server health) aur historical (daily creation trend, redirect volume). Logs: access logs 7 days, error logs 30 days, audit logs 1 year retention.
Teen cheezein check karo, order me. Pehle DB: SELECT * FROM urls WHERE short_url='...' — entry hai ya nahi? Nahi hai to URL kabhi bani hi nahi (ya delete ho gayi). Doosra Redis: GET url:... — cache me hai? Cache stale to nahi hai? Teesra expiration: expires_at < now() to nahi? Agar entry hai aur valid hai to redirect slow kyun hai — cache hit hua ya DB gaya? DB replication lag check karo, network latency check karo. Counter collision ka doubt ho to Zookeeper counter value check karo aur DB me duplicate short_url dhoondo (UNIQUE constraint ki wajah se impossible hona chahiye). Har step par logs dekho — access logs me status_code aur latency likhi hoti hai.
