01Requirements

Functional Requirements

Functional requirements matlab — system ko user ke liye kya-kya karna chahiye. Interview me design hamesha yahin se shuru hota hai: pehle features tay karo, phir scale, phir design. Is platform ke 6 core features hain.

6 features — jo user ko dikhte hain

  • Feature 1 — Product search: user product ko title ya naam se search kar sake. Search fast hona chahiye, filters ke saath (category, price, rating).
  • Feature 2 — Product details: user kisi product ka poora detail dekh sake — description, image, available quantity, reviews aur rating.
  • Feature 3 — Add to cart: user quantity select karke item ko cart me daal sake. Cart session aur device ke paar bhi bana rehna chahiye.
  • Feature 4 — Checkout aur payment: user payment karke checkout complete kar sake. Payment exactly-once hona chahiye — double charge kabhi nahi.
  • Feature 5 — Order status: user apne order ki status check kar sake — confirmed, shipped, out for delivery, delivered.
  • Feature 6 — Limited stock: jin items ka stock limited hai, unki khareed ko manage karna — matlab overselling kabhi nahi honi chahiye. Ek hi aakhri item do logon ko becha nahi ja sakta.
Interview me kaise bolo: "Pehle 6 features likhta hoon — search, product view, cart, checkout/payment, order status, aur limited-stock handling. Ye scope tay karta hai; baaki sab (recommendations, reviews likhna, seller panel) v2 me jaayega." Scope bolna interviewer ko dikhata hai ki tum requirement ko samajh kar design kar rahe ho, seedha database par nahi kood rahe.

Ye 6 features hi aage ke har faisle ki jad hain: search ke liye Elasticsearch, cart ke liye Redis + PostgreSQL, limited stock ke liye Redis lock + reserved_qty, payment ke liye idempotency, aur status ke liye Kafka events.

Non-Functional Requirements

Non-functional requirements matlab — system kitna bada, kitna fast aur kitna reliable hona chahiye. Ye numbers hi batate hain ki simple design chalega ya distributed system chahiye.

Scale — kitna bada system

MetricNumberIska matlab
Orders per second10 orders/secNormal din ka load; flash sale me 100/sec tak jaata hai
Monthly Active Users10M MAUHar mahine 1 crore active users
Products100M+ products10 crore se zyada products, kai categories me
Search queries100K+ searches/secPeak (sale events) me har second 1 lakh se zyada searches
Concurrent users50K–100K normal, 1M sale meSale ke time 10 lakh log ek saath online

Performance aur availability

  • Low latency: product search filters ke saath 500ms se kam me jawab de. User search karte hi result chahiye — dheema search matlab sale kho dena.
  • CAP theorem ka faisla: searching aur items dekhne ke liye system highly available rahega, aur order place karne ke liye highly consistent rahega. Matlab search thoda purana data bhi dikha de to chalega, lekin order me galti nahi chalegi.
  • Inventory consistency: inventory updates ke liye strong consistency — limited stock items ki overselling bilkul nahi honi chahiye.
  • Payment reliability: payment exactly-once processing, idempotency ke saath — ek hi order ka paisa do baar kabhi nahi katna chahiye, chahe webhook do baar aa jaye.
Yaad rakhne wali baat: Search aur order ke liye alag consistency chahiye — yehi CAP ka practical matlab hai. Search eventual consistency (1–2 second purana data) se chal jata hai, lekin inventory aur payment ke liye strong consistency (ACID) zaroori hai. Interview me ye farak bolna bahut marks dilata hai.

Ye numbers aage ke design ko seedha shape dete hain: 100K searches/sec ke liye Elasticsearch + Redis cache, 100M products ke liye sharded index, aur strong consistency ke liye PostgreSQL + Redis lock.

03Requirements

Core Entities

Core entities matlab — system ke andar kaunsi cheezein (objects) hain aur unke andar kya fields hain. Entities tay ho jayein to API aur database schema apne aap nikal aate hain. Is system me 5 core entities hain.

5 entities aur unke fields

EntityFields
1. Useruser_id, name, email, password, address[], payment_methods[]
2. Productproduct_id, title, category, price, qty, currency, description, images[]
3. Cartcart_id, user_id, items (product_id, qty, price, currency)
4. Orderorder_id, user_id, items (product_id, qty, price, currency), total, status
5. CheckoutPayment flow ki tracking — checkout session, payment intent, status

Entities aapas me kaise judi hain

  • User → Cart: ek user ka ek active cart hota hai. Cart user_id se juda hai, session se nahi — isiliye mobile par daala item laptop par bhi dikhta hai.
  • Cart → Product: cart ke items me product_id hota hai — cart khud product ka data copy nahi karta, sirf reference aur us waqt ka price rakhta hai.
  • Cart → Order: checkout par cart ke items se order banta hai. Order banne ke baad cart khaali kar diya jata hai.
  • Order → Payment: har order ka ek payment hota hai; payment order_id se juda hai (yahi idempotency ki kunji hai — Section 06.5 dekho).
  • Product → Inventory: product catalog (kya bech rahe ho) aur inventory (kitna stock hai) alag hain — product MongoDB me, stock PostgreSQL me. Ye alagav hi overselling rokta hai.
Interview tip: Entities batate waqt fields ke saath unke type ka zikr bhi karo — qty integer hai, price decimal hai, address[] ek list hai. Isse interviewer ko lagta hai ki tumne schema socha hai, sirf naam nahi ginwaye.

Ab inhi entities se API nikalti hai: product search karega, cart add karega, checkout order banayega, payment process karega, aur status order ki haalat batayega — agla section.

05API aur HLD

High Level Design (from Image)

High Level Design matlab — poora system kaunsi services, kaunse databases, aur kaise jude hue hain. Ye section design diagram par aadharit hai; diagram me jo dikhta hai wo yahan prose me bhi likha hai.

Request ka rasta — client se database tak

  • Clients → API Gateway: saari requests pehle API Gateway se guzarti hain — authentication, authorization aur routing wahin hota hai. Gateway hi rate limiting bhi karta hai.
  • User Service → User DB (MySQL): user profiles aur authentication. MySQL isliye kyunki user accounts ko ACID aur relational integrity chahiye.
  • Search Service → Elasticsearch: full-text search filters ke saath; hot queries ke liye Redis cache. Search kabhi seedha database ko nahi chhoota.
  • Product Service → Product DB (MongoDB / DocumentDB): product catalog, flexible schema. Product me badlav CDC se Kafka ke raaste Elasticsearch tak pahunchta hai.
  • Cart Service → Cart DB (PostgreSQL): cart ki state — items ke saath product_id, qty, price, currency.
  • Inventory Service → Inventory DB (PostgreSQL): stock ki tracking; yehi stock ka source of truth hai, product_id par indexed.
  • Order Status Service → Order DB (MySQL): order ki lifecycle tracking — kab confirmed, kab shipped, kab delivered.
  • Checkout Service: orchestration karta hai — inventory check (Redis lock) → payment → order creation, isi kram me.
  • Payment Service → Payment DB: payment transactions aur Payment Gateway (Stripe/Razorpay) ka integration.

Beech me do shared cheezein

  • Kafka — event streaming: order.created, payment.success, inventory.updated, order.shipped jaise events. Services seedha ek doosre ko call nahi karte — events ke through baat karte hain, isliye ek service slow ho to bhi baaki rukte nahi.
  • Notification System: Kafka events consume karke email / SMS / push bhejta hai — "Order confirmed", "Order shipped", "Out for delivery", "Delivered".
  • Redis — teen kaam: cart caching, inventory locking (distributed lock), aur search result caching.
Interview me ye line yaad rakhna: "Har database apne kaam ke hisaab se chuna hai — User MySQL (ACID), Product MongoDB (flexible schema), Cart PostgreSQL (relational), Inventory PostgreSQL (source of truth), Order MySQL (ACID). Ek hi database sab jagah lagana sabse aasan aur sabse galat faisla hota."

Step 1: Product Search (Elasticsearch + CDC)

Search is system ki sabse zyada load wali cheez hai — peak par 100K queries/sec. Isliye search seedha database par nahi, Elasticsearch par chalta hai, aur product ka data CDC pipeline se ES tak pahunchta hai.

Search ka flow

  • User search karta hai: GET /v1/product/search?q=laptop&category=electronics&priceMax=1000&sortBy=rating
  • Search Service Elasticsearch se poochhta hai — full-text match + filters ek hi query me.
  • ES query kuch aisi hoti hai: multi_match laptop ko title^3, description aur category me dhoondhta hai — title ko 3x boost milta hai, kyunki title me milna zyada relevant hota hai. Filter me category = electronics aur price <= 1000 lagta hai, sort rating se descending, aur size: 20 matlab ek page me 20 results.
  • Response me har product ka product_id, title, category, price, qty, currency, image_url, rating aata hai.

CDC pipeline — search hamesha fresh kaise rehta hai

Product DB (MongoDB) → Sync Kafka → CDC Consumer → Elasticsearch indexing. Product me koi badlav — price, title, qty — to wo 1–2 second me search index me aa jata hai. Isi ko CDC (Change Data Capture) kehte hain.

  • CDC kyu? Product updates apne aap ES se sync hote rehte hain; Product Service ko ES ke baare me kuch jaanne ki zaroorat nahi. Agar ES down ho jaye to bhi MongoDB me writes chalte rehte hain, indexer baad me catch-up kar leta hai.
  • Caching: popular searches Redis me cache hoti hain, TTL 10 minute, key hoti hai hash(query + filters + sort). Top 10K queries cache se serve hoti hain — 60–70% searches database/ES tak jaati hi nahi.
  • MongoDB kyu: alag-alag product types ke alag attributes hote hain — mobile ke specs, book ke author — flexible schema isiliye chuna gaya.
Worked example: 100M products, 5 primary shards — har shard par 20M products. Query p95 100ms se kam. Aur Redis cache 60–70% queries sambhal leta hai, to ES par asal load sirf 30–40K queries/sec rehta hai.

Step 2: Product Details & Images

Search list se user jab kisi product par click karta hai, to poora detail page khulta hai. Ye read-heavy operation hai — isiliye yahan bhi cache-first soch hai.

Product detail ka flow

  • User product kholta hai: GET /v1/product/{product_id}
  • Product Service MongoDB se poochhta hai: db.products.findOne({product_id: ...})
  • Document structure kuch aisa hota hai: { product_id, title, category, price, qty, currency, description, images[], specifications: {...}, reviews_summary: {avg_rating, total_reviews} }

Images, reviews aur caching

  • Images: S3 me stored hain, unke URLs MongoDB me hain, aur serve CDN (CloudFront) se hote hain — global fast access, 95% cache hit, 50ms se kam latency.
  • Reviews: alag Reviews DB me hain. Aggregated rating Redis me cached rehta hai; poora detail reviews on-demand fetch hote hain — har page load par saare reviews laana bekaar hai.
  • Caching: product details Redis me cache hote hain, TTL 30 minute. Product update hote hi Kafka event se cache invalidate ho jata hai — purana price dikhna band.
  • Latency: cache hit par product page 50ms se kam, DB miss par bhi 200ms se kam.
Design ka usool: jo data baar-baar padha jata hai aur kam badalta hai (product detail), use cache karo; jo data har baar naya chahiye (stock), use source of truth se poochho. Detail page par dikhaya gaya qty bhi asal me inventory se sync hota hai — CDC ke through.

Step 3: Add to Cart (Redis + PostgreSQL)

Cart hybrid hai — PostgreSQL source of truth, Redis speed ke liye. Dono ki zaroorat isliye hai kyunki cart reads writes se 10x zyada hote hain: user checkout se pehle cart ko baar-baar kholta hai.

Add to cart ka flow

  • User item daalta hai: POST /v1/cart/add with {user_id, product_id, qty: 2}
  • Step 1 — Validate: Cart Service pehle check karta hai ki product maujood hai aur qty available hai (Inventory Service se poochh kar).
  • Step 2 — PostgreSQL update: INSERT INTO cart_items (cart_id, user_id, product_id, qty, price, currency) ON CONFLICT (cart_id, product_id) DO UPDATE SET qty = qty + 2 — matlab wahi item pehle se cart me ho to quantity badh jati hai, duplicate row nahi banti.
  • Step 3 — Redis cache: HSET cart:{user_id} product:{product_id} '{qty: 2, price: 899, currency: USD}' with TTL 7 days.

Cart padhna, badalna, hatana

  • Get cart: GET /v1/cart/{user_id} — pehle Redis (HGETALL cart:{user_id}), miss ho to PostgreSQL se lao aur Redis me cache karo. Redis hit ~1ms, PostgreSQL ~50ms.
  • Update quantity: PATCH /v1/cart/{cart_id}/items/{product_id} with {qty: 5} — PostgreSQL aur Redis dono update hote hain.
  • Remove item: DELETE /v1/cart/{cart_id}/items/{product_id} — PostgreSQL se row aur Redis se HDEL.
  • Cart DB schema (PostgreSQL): cart_id, user_id, items (product_id, qty, price, currency).
PostgreSQL cart ke liye kyu? ACID guarantees, relational structure (user → cart → items), aur complex queries (JOIN karke product ka title/image bhi la sakte ho). Redis sirf cache hai — agar Redis khaali ho jaye to bhi cart PostgreSQL se wapas ban jata hai. Cache kabhi source of truth nahi hota.

Guest cart (bina login) sirf Redis me rehta hai, TTL 24h; login karte hi wo user ke cart me migrate ho jata hai. Aur 30 din se inactive carts ko background job delete kar deta hai.

Step 4: Checkout — Inventory Check with Redis Lock (CRITICAL)

Ye poore design ka sabse critical step hai — aur interview me sabse zyada poochha jaane wala. Sawal hai: aakhri 1 item ko 100 log ek saath checkout karein to overselling kaise roko? Jawab hai: Redis lock pehle, phir database lock, phir reserve.

Checkout orchestration — 8 steps

  • Step 1: Cart items Cart DB se lao.
  • Step 2 — Redis lock: cart ke HAR product ke liye distributed lock lo: SETNX lock:inventory:{product_id} {checkout_session_id} EX 30 (30 second expiry). SETNX sirf tab 1 return karta hai jab lock pehle se kisi ke paas na ho.
  • Step 3 — DB check: lock mila to Inventory Service se poochho: SELECT qty FROM inventory WHERE product_id = ... FOR UPDATE — ye pessimistic lock hai, row-level exclusive lock.
  • Step 4 — Validate: qty >= cart_qty nahi hai to lock chhodo (DEL lock:inventory:{product_id}) aur error do: "Product X has insufficient stock".
  • Step 5 — Reserve (deduct nahi): saare products ka stock kaafi ho to reserve karo: UPDATE inventory SET reserved_qty = reserved_qty + {cart_qty}. Abhi qty ghatao mat — payment abhi hua nahi hai.
  • Step 6 — Order banao: INSERT INTO orders (..., status = 'PENDING_PAYMENT', created_at).
  • Step 7 — Lock chhodo: har product ka Redis lock delete karo: DEL lock:inventory:{product_id}.
  • Step 8 — Jawab do: client ko {order_id, payment_url} return karo.
CRITICAL — do lock kyu chahiye? Redis lock fast hai (1–2ms) — 100 concurrent checkout requests me se 99 ko shuru me hi rok deta hai. PostgreSQL FOR UPDATE ACID guarantee deta hai — transaction ke andar phantom reads nahi hote. Redis lock 30 second me auto-expire ho jata hai, to service crash ho jaye to bhi deadlock nahi hota.

reserved_qty ka matlab — ek example

qty = 10, reserved_qty = 3 ka matlab hai: warehouse me kul 10 hain, 3 active checkouts me phanse hain, to naye khariddaaron ke liye 7 available hain. Ye column hi dikhata hai ki checkout me pada item "available" nahi dikhna chahiye. Asli deduction sirf payment success ke baad hoti hai.

Example: qty=1, User A aur User B dono checkout dabate hain → A ka SETNX pass, B ka fail (wait karta hai) → A reserve kar leta hai → B ka SETNX pass hota hai jab A lock chhodta hai → B check karta hai: qty=0 (reserved=1) → "Out of stock" → koi overselling nahi.

Step 5: Payment Processing with Idempotency

Payment me ek hi niyam hai: ek order ka paisa ek hi baar katna chahiye — chahe user "Pay" do baar dabaye, chahe webhook do baar aa jaye, chahe network retry ho. Iske liye idempotency hai.

Payment ka flow

  • User payment_url par redirect hota hai — Payment Gateway (Stripe/Razorpay).
  • Payment Service payment intent banata hai, idempotency_key = order_id ke saath. Isi key ki wajah se wahi order dobara charge nahi ho sakta.
  • Gateway card charge karta hai, phir webhook bhejta hai: POST /webhooks/payment with {order_id, payment_id, status: 'success', amount}.

Webhook handler — 3 cheezein, isi kram me

  • 1. Signature validate karo: webhook ka signature check karo — bina iske koi bhi nakli webhook bhej kar order confirm karwa sakta hai.
  • 2. Idempotency check: SELECT * FROM payments WHERE order_id = ... — agar payment pehle se maujood hai to seedha 200 return karo (already processed). Dobara process mat karo.
  • 3. Transaction: BEGIN TRANSACTION; INSERT INTO payments (payment_id, order_id, amount, status='SUCCESS', timestamp); UPDATE orders SET status='PAYMENT_CONFIRMED', payment_id=...; COMMIT;

Payment success ke baad kya hota hai

  • Inventory deduct: UPDATE inventory SET qty = qty - {reserved_qty}, reserved_qty = reserved_qty - {reserved_qty} — ab asal stock ghata, reserved bhi chhuta.
  • Kafka events: payment.success aur order.confirmed topics par publish — Notification Service aur Warehouse sunte hain.
  • Cart saaf: DELETE FROM cart_items WHERE cart_id = ... — order ban gaya, cart ki zaroorat khatm.
  • Payment fail ho to: webhook payment.failed aata hai → reserved inventory chhodo (reserved_qty = reserved_qty - {cart_qty}), order status PAYMENT_FAILED.
NEVER inventory ko checkout me synchronously deduct karo. Reserve karo, deduct payment success ke baad. Agar user payment chhod kar chala jaye to reserved stock timeout (5–15 minute) par apne aap wapas aa jata hai — background job chhodta hai. Direct deduction ka matlab hota: payment fail hone par bhi stock gaya.

Step 6: Order Status Tracking (Kafka Event-Driven)

Order banne ke baad user ko har pal pata hona chahiye ki order kahan hai. Ye tracking Kafka events se chalti hai — har status change ek event hai, aur har interested service use sunti hai.

Order lifecycle — 6 states

PENDING_PAYMENT → PAYMENT_CONFIRMED → PROCESSING → SHIPPED → OUT_FOR_DELIVERY → DELIVERED

  • Status updates via Kafka: Order Status Service order.confirmed, order.shipped, order.delivered events consume karta hai aur Order DB update karta hai.
  • Warehouse: items pick karke POST /v1/orders/{order_id}/ship karta hai → Kafka par order.shipped publish hota hai.
  • Delivery partner: location aur status API se update karta hai → order.out_for_delivery Kafka par jata hai.
  • User status check: GET /v1/status/{order_id} → Order Status Service Order DB se poochhta hai: SELECT status, tracking_id, estimated_delivery FROM orders WHERE order_id = ...

Real-time updates — do tareeke

  • WebSocket: user tracking page kholte hi WebSocket connection banta hai; status change hote hi screen update ho jati hai (500ms se kam me event se screen tak).
  • Polling (fallback): WebSocket na chale to client har 30 second me GET /v1/status/{order_id} poochhta hai. Kam efficient hai, lekin har jagah kaam karta hai.

Notification flow

Kafka events → Notification System → Email / SMS / Push: "Order confirmed", "Order shipped", "Out for delivery", "Delivered". Har status change par user ko uske pasandeeda channel par khabar milti hai — aur cancellation par bhi: order cancel ho to stock wapas aata hai aur refund shuru hota hai (sirf PENDING_PAYMENT / PAYMENT_CONFIRMED / PROCESSING states me cancel allowed hai; SHIPPED ke baad nahi).

Step 7: Inventory Management & CDC (Source of Truth)

Inventory DB is system ki sabse sacchi jagah hai stock ke liye — diagram me is par likha hai "Qty-source of truth". Product catalog bata sakta hai ki item kya hai, lekin kitna bacha hai ye sirf Inventory DB batayega.

Inventory DB (PostgreSQL)

  • Columns: {product_id, qty, reserved_qty, warehouse_id, last_updated} — product_id par index hai, taaki checkout ke time lookup tez ho.
  • Stock aane par: naya stock aaye to UPDATE inventory SET qty = qty + {new_stock}, phir Kafka par inventory.updated event publish hota hai.
  • CDC pipeline: Inventory DB → CDC → Kafka → Redis cache aur Elasticsearch ka product qty update hota hai. Matlab search result me dikhaya gaya qty bhi isi se sync hota hai.
  • Redis caching: HSET inventory:{product_id} 'qty' {qty} 'reserved_qty' {reserved_qty}, TTL 5 minute — quick availability checks ke liye.
  • Low stock alerts: background job dekhta hai ki inventory.qty < threshold (jaise 10 units) to warehouse ko restock ka notification jata hai.
Overselling kaise rukti hai — teeno parat ek saath: (1) Redis lock race rokta hai, (2) reserved_qty checkout me phansa stock "available" nahi dikhne deta, (3) asli deduction sirf payment success ke baad hoti hai. Step 9: Search Optimization (Elasticsearch Architecture)

Search sirf "text dhoondho" nahi hai — relevance, filters, suggestions aur 100K queries/sec — sab ek saath chahiye. Ye section Elasticsearch ko production-ready banane ki detail deta hai.

Index mapping

Har field ka type tay hai: product_id: keyword (exact match), title: text (analyzed, full-text), description: text, category: keyword, price: float, qty: integer, rating: float, brand: keyword, images: keyword. keyword matlab exact value (filter ke liye), text matlab analyzed (search ke liye) — ye farak interview me aksar poochha jata hai.

Relevance badhane ke 3 tareeke

  • Synonyms: analyzer me synonyms configure karo — laptop = notebook, mobile = phone. User "notebook" likhe to laptop bhi mile — recall badhta hai.
  • Faceted search: aggregations se filters ke counts nikalte hain — brands ke terms, price ranges (to: 500, 500–1000, 1000+). UI me jo "Electronics (5000)" dikhta hai, wo yahin se aata hai.
  • Autocomplete: edge n-gram tokenizer se type-ahead suggestions — user type karte hi (300ms debounce) "laptop", "laptop bag", "laptop stand" sujhav aate hain.

Performance — numbers

  • ES cluster: 10 nodes, 5 primary shards, har shard ka 1 replica — sale events me 100K queries/sec sambhalta hai.
  • Caching: Redis top 10K search queries ke results cache karta hai, TTL 10 minute — 60–70% searches cache se serve hoti hain.
  • Sharding: product index category ya hash(product_id) se shard hota hai — parallel queries chalte hain.

Step 10: System Integration via Kafka (Event-Driven Architecture)

Kafka is system ki central nervous system hai. Services seedha ek doosre ko HTTP call karke nahi bandhte — events publish karte hain, aur jise chahiye wo sunta hai. Isse system loosely coupled rehta hai aur har service apni speed se scale hoti hai.

5 Kafka topics aur unke consumers

TopicKaun sunta hai
product.updatedES indexer, cache invalidator
order.createdInventory Service (stock reserve), Notification Service
payment.successOrder Service (status update), Inventory Service (stock deduct), Notification Service
order.shippedOrder Status Service, Notification Service, Tracking Service
inventory.updatedProduct Service (qty update), ES indexer, Redis cache updater

Event-driven design ke niyam

  • Consumer groups: har service ka apna dedicated consumer group hota hai — horizontal scaling aur fault tolerance milta hai. Ek service ke 10 instances honge to events unme bant jayenge.
  • Event schema: {event_id, event_type, timestamp, payload: {...}, metadata: {source_service, correlation_id}} — correlation_id se ek order ki poori kahani trace hoti hai.
  • Idempotent consumers: event_id se deduplicate karo — event replay ho jaye to bhi double processing nahi hogi.
  • Dead letter queue (DLQ): 3 retries ke baad bhi fail hone wala event DLQ me jata hai — manual investigation aur replay ke liye. Event kabhi chup-chaap kho nahi jana chahiye.
Kafka ke 4 fayde — interview me yehi bolo: (1) services decoupled rehti hain, (2) async processing — slow kaam (email bhejna) checkout ko rokta nahi, (3) event replay — debugging aur index rebuild ke liye, (4) har consumer apni speed se scale hota hai. Aur retention 7 din ka matlab: poora ES index Kafka se dobara banaya ja sakta hai.

CDC (Change Data Capture)

  • Product → ES: MongoDB → Kafka → Elasticsearch indexer — search 1–2 second me up-to-date rehta hai.
  • Inventory → Redis: PostgreSQL → CDC → Kafka → Redis cache updater — qty changes invalidate aur update hote hain.
  • CDC kyu? Source DB ko derived stores (ES, Redis) se decouple karta hai. Search/cache ke liye eventual consistency chalti hai, aur har store apni speed se scale hota hai.

Redis Lock Pattern — inventory ke liye critical

  • Lock acquisition: SETNX lock:inventory:{product_id} {session_id} EX 30
  • Purpose: aakhri item ko ek saath checkout karne wale multiple users ki race rokna.
  • Timeout: 30 second auto-expiry — service crash ho jaye to bhi deadlock nahi hota.
  • Pattern: Acquire lock → Check DB stock → Reserve → Release lock (fail hone par bhi release karo).

Kafka Event-Driven Architecture

Diagram me "Sync Kafka" Product, Inventory, Payment, Order aur Notification services ko jodta hai. 10Scaling aur Interview

Common Interview Questions

Lesson ke 10 sabse bade interview questions — har ek ka poora jawab. Ye wohi sawaal hain jo interviewer e-commerce design me sabse pehle poochhta hai. Inhe rattna nahi, samajhna hai — neeche har jawab ke steps diye hain.

Q1. Aakhri item ko multiple users khareedne ki koshish karein to overselling kaise roko?

Multi-layer approach — distributed lock + database pessimistic locking: (1) Checkout se pehle Redis distributed lock lo: har product ke liye SETNX lock:inventory:{product_id} {checkout_session_id} EX 30 — SETNX 0 de to wait karo ya "Another user is checking out this item" bolo; 1 de to aage badho. (2) Database pessimistic lock: SELECT qty, reserved_qty FROM inventory WHERE product_id=... FOR UPDATE — row-level exclusive lock. (3) Validate karo: qty kam ho to Redis lock chhodo, "Insufficient stock" bolo. (4) Reserve karo: UPDATE inventory SET reserved_qty = reserved_qty + {cart_qty} — available pool se hataya, deduct abhi nahi kiya. (5) Redis lock chhodo: DEL lock:inventory:{product_id}. (6) Order banao, status PENDING_PAYMENT. (7) Payment webhook success par asal deduction: qty = qty - {cart_qty}, reserved_qty = reserved_qty - {cart_qty}. (8) Payment fail ho to sirf reservation chhodo. Dono lock kyu? Redis lock fast hai (1–2ms) — 100 concurrent requests me se 99 ko shuru me hi rok deta hai; PostgreSQL FOR UPDATE ACID guarantee deta hai, phantom reads rokta hai. Lock 30 second me auto-expire hota hai, deadlock nahi hota. Example: qty=1, User A aur B dono checkout karein → A ka SETNX pass, B ka fail → A reserve karta hai → B ko "Out of stock" milta hai. Aur qty=10, reserved_qty=3 ka matlab: kul 10, 3 checkout me, 7 available.

Q2. Product search filters (category, price, rating) ke saath kaise implement karo?

Elasticsearch + CDC sync: (1) Index mapping me product_id: keyword, title: text, description: text, category: keyword, price: float, rating: float, brand: keyword, qty: integer. (2) CDC pipeline: MongoDB updates → Kafka product.updated topic → ES indexer consumer → 1–2 second me sync. (3) Search query: multi_match laptop ko title^3, description, brand me dhoondhta hai; filters — category: electronics, price: 500–1500, rating >= 4, qty > 0; sort rating desc; from: 0, size: 20. (4) Scoring: title^3 title match ko 3x boost deta hai. (5) Faceted search: aggregations se categories, price ranges aur brands ke counts — UI filters ke liye. (6) Autocomplete: edge_ngram tokenizer, har keystroke par (300ms debounce). (7) Synonyms: laptop → notebook, portable computer. (8) Caching: Redis popular queries cache karta hai, TTL 10 min, 60–70% cache se serve hota hai. (9) Performance: 10 nodes, 5 primary shards (100M/5 = 20M per shard), query p95 <100ms. PostgreSQL full-text kyu nahi? ES relevance scoring, fuzzy matching, synonyms aur faceted search ke liye bana hai — PostgreSQL ka tsvector iska muqabla nahi karta. Products ke liye MongoDB kyu? Alag categories ke alag schemas — flexible schema sparse columns aur NULL hell se bachata hai.

Q3. Shopping cart state sessions aur devices ke paar kaise manage karo?

Hybrid Redis + PostgreSQL: (1) Cart creation: login par check karo cart hai ya nahi, nahi to INSERT INTO carts. (2) Add to cart: product aur stock validate karo → PostgreSQL INSERT ... ON CONFLICT DO UPDATE SET qty = qty + 2 → Redis HSET cart:{user_id}, TTL 7 days. (3) Get cart: pehle Redis HGETALL (1ms), miss ho to PostgreSQL JOIN karke lao aur cache karo. (4) Update quantity: PATCH — PostgreSQL aur Redis dono update. (5) Remove: DELETE + Redis HDEL. (6) Cross-device sync: cart user_id se juda hai, session se nahi — mobile par daala item laptop par dikhta hai. (7) Guest cart: bina login session_id se, sirf Redis me, TTL 24h; login par user cart me migrate. (8) Cart expiry: 30 din inactive carts background job delete karta hai. (9) Price updates: price badal jaye to dono dikhao — "Added at $899, now $799". (10) Checkout par stock dobara validate karo. PostgreSQL kyu? ACID, source of truth, complex queries. Redis kyu? Reads writes se 10x zyada hain — 10K concurrent users × 100 reads/min = 1M reads/min, Redis <1ms me deta hai, PostgreSQL ~50ms me.

Q4. Cart se order confirmation tak checkout flow kaise handle karo?

Multi-step orchestration: (1) POST /v1/checkout — cart_id, shipping_address_id, payment_method_id. (2) Checkout Service: cart items lao → har product par SETNX lock lo (koi fail ho to abort, saare lock chhodo) → SELECT ... FOR UPDATE se inventory validate karo → reserved_qty badhao → total nikalo (SUM(price × qty) + shipping + tax) → transaction me order banao (PENDING_PAYMENT) → Redis locks chhodo → Payment Service se payment intent banao (idempotency_key: order_id) → client ko {order_id, payment_url, expires_at: now() + 15min} do. (3) User payment karta hai. (4) Webhook: idempotency check → transaction (payment INSERT + order PAYMENT_CONFIRMED + inventory deduct + cart clear) → Kafka events payment.success aur order.confirmed. (5) Consumers: Notification email bhejta hai, Inventory Redis cache invalidate karta hai, Warehouse pick list banata hai. (6) Payment timeout: 15 minute se zyada PENDING_PAYMENT raha to reserved stock chhodo, status PAYMENT_TIMEOUT. (7) Failures: inventory kam ho to order bane bina abort; payment fail ho to reservation chhodo; service crash ho to Redis locks 30s me expire. Performance: average checkout 2–3 second (lock ~10ms, DB ~50ms, payment intent ~200ms), 10K checkouts/min horizontal scaling se.

Q5. Product DB ko Elasticsearch se sync karne ke liye CDC kaise implement karo?

(1) CDC source: MongoDB oplog + Change Streams (db.products.watch([{...insert/update/replace/delete...}])); PostgreSQL ke liye logical replication + Debezium (WAL capture). (2) Kafka connector: Change Stream → Kafka Connect MongoDB Source Connector → topic product.changes, event schema {operation, product_id, fullDocument, timestamp}. (3) ES indexer consumer: group es-product-indexer — insert/update par es.index, delete par es.delete; 100 events buffer karke har 2 second me bulk index. (4) Error handling: ES fail ho to DLQ + exponential backoff retry; consumer lag >1000 events ho to alert aur auto-scale. (5) Initial load: pehle saare products bulk export karke ES me daalo, phir CDC shuru karo. (6) Consistency: eventual — update 1–2 second me searchable; Kafka partition product_id se hoti hai, to ek product ke updates order me process hote hain. (7) Performance: oplog tail <10ms, Kafka ~50ms end-to-end, ES bulk 10K docs/sec — kul lag 1–2 second. Dual writes kyu nahi? Tight coupling, transaction complexity (ES write fail ho to?), Product Service ko search ki jaankari chahiye hoti — CDC in teeno se bachata hai. Real-world: Amazon Kinesis Streams jaisi pipeline use karta hai, millions updates/hour, ES cluster 100+ nodes, lag p99 <5 second.

Q6. Payment integration idempotency aur webhook handling ke saath kaise design karo?

(1) Initiation: Checkout Service POST /v1/payments {order_id, amount: 1499.99, currency: USD, user_id, return_url}. (2) Payment intent: idempotency_key = order_id — Stripe ko stripe.paymentIntents.create({amount: 149999, currency: 'usd', metadata: {order_id, user_id}, idempotency_key: order_id}); Payment DB me INSERT INTO payments (..., status='PENDING'); client ko payment_url do. (3) User payment karta hai (3D Secure agar chahiye). (4) Webhook — sabse critical: Stripe POST /webhooks/payment bhejta hai; (a) signature validate karo (HMAC, webhook_secret) — replay aur forged requests rokti hai; (b) idempotency check — payment pehle se SUCCESS hai to seedha 200; (c) transaction SERIALIZABLE — payments UPDATE (sirf PENDING se SUCCESS), orders UPDATE, inventory deduct, COMMIT; agar affected_rows == 0 to ROLLBACK (concurrent webhook race haar gaya); (d) Kafka events publish karo; (e) Stripe ko 200 do. (5) Consumers: Notification, Inventory cache invalidation, Fulfillment pick list. (6) Failures: payment declined → PAYMENT_FAILED + reservation release; webhook timeout → Stripe 3 baar retry karta hai (exponential backoff), phir manual reconciliation ya Stripe API polling; DB fail → ROLLBACK + 500 → Stripe retry karta hai. (7) Idempotency ki 3 parat: order_id key, payments table par UNIQUE constraint, webhook se pehle status check. (8) Reconciliation: nightly job Payment DB ko Stripe API se milata hai. (9) Testing: stripe trigger payment_intent.succeeded se test karo — wahi webhook do baar bhejo, order ek hi baar process hona chahiye. Security: signature verification, HTTPS, 100 webhooks/min per IP rate limit, Payment DB ke alag credentials. Performance: webhook <200ms, 1000 payments/sec horizontal scaling se.

Q7. Order status track karo aur users ko real-time updates kaise do?

(1) Lifecycle: PENDING_PAYMENT → PAYMENT_CONFIRMED → PROCESSING → SHIPPED → OUT_FOR_DELIVERY → DELIVERED (optional RETURNED/CANCELLED). (2) State transitions Kafka events se: order.created, payment.success, warehouse POST /v1/orders/{order_id}/process → order.processing, ship par order.shipped (tracking_id, carrier, estimated_delivery ke saath), delivery partner order.out_for_delivery / order.delivered. (3) Topics: order.lifecycle (saare state changes), order.tracking (location updates); event schema me event_id, event_type, order_id, timestamp, payload. (4) Consumer groups: Order Status Service DB update + history table (order_status_history); Notification Service har change par email/SMS/push; Analytics Service metrics (avg delivery time, on-time rate). (5) Real-time: WebSocket — client WS /v1/orders/{order_id}/track kholta hai, backend Redis Pub/Sub channel order:{order_id}:updates se forward karta hai; ya polling fallback har 30 second. (6) Status API: GET /v1/status/{order_id} — current status + history dono deta hai. (7) Location tracking: delivery partner lat/lng bhejta hai → time-series DB (InfluxDB) → Redis Pub/Sub → client map par driver dikhta hai, ETA Google Maps Distance Matrix se. (8) Notifications: user opt-in/out kar sakta hai per channel. (9) Cancellation: SHIPPED ke baad cancel nahi; pehle cancel ho to stock wapas + refund + order.cancelled event. (10) SLA monitoring: on-time delivery %, PROCESSING me >24h phanse orders par alert, Grafana funnel. Performance: Kafka 100K order events/sec, status update <100ms, WebSocket 1M concurrent connections, user ki screen tak update <500ms.

Q8. High-volume flash sales (1 minute me 100K orders) kaise handle karo?

(1) Pre-sale: product par flash_sale=true, sale_start/end time, sale_quantity=1000; cache warm-up sale se 1 ghanta pehle (product details, images CDN + Redis me); dedicated read replicas; Checkout Service 5x scale (50 → 250 instances) sale se 10 minute pehle. (2) Virtual waiting room: sale se pehle users waiting room me (countdown timer, ~1M users queue me); sale shuru hote hi batches me chhodo (1000 users/sec, random token) — thundering herd rokne ke liye; token ke bina backend request nahi leta. (3) Inventory handling: flash_sale_inventory table — 1000 rows, status: available/reserved/sold, queue_position 1–1000; checkout par SELECT ... FOR UPDATE SKIP LOCKED — locked row mile to skip karke agla lo, contention khatm. (4) Queue-based checkout: checkout request seedha process nahi — Kafka checkout.requests topic me daalo (partition by product_id = FIFO); 50 workers steady rate par process karte hain (100 checkouts/sec); user ko dikhta hai "line me ho, position #523, wait ~5 min", WebSocket se position update hoti hai. (5) Timeout: 5 minute me payment na ho to reservation chhodo — background job har 10 second me check karta hai. (6) Rate limiting: per-user 1 checkout attempt per 10 second (Redis SETEX), per-IP 10 req/sec, checkout se pehle CAPTCHA. (7) Caching: product details 99% cache hit (1M users × 1% = sirf 10K DB queries); Redis counter DECR flash_sale:{product_id}:remaining — negative aaye to turant "Sold out"; counter har 5 second me DB se sync. (8) Payment: 100 orders batch me payment intents parallel me; confirmation async. (9) DB writes: 100 orders buffer karke ek transaction me INSERT (har 2 second) — load 100x kam; writes primary par, reads replicas se. (10) Post-sale: scale down, metrics analyze karo, waitlist ko restock alert do. Real-world: Amazon Prime Day — 10M products on sale, 100K orders/minute peak, waiting room 5M concurrent users gate karta hai, queue 50K checkouts/min process karta hai, 99.9% uptime, products <10 minute me sold out. Bina optimization ke: 100K concurrent checkouts → DB meltdown (deadlocks), Payment Gateway rate limit cross, overselling. Optimization ke saath: 1K users/sec andar, 100 checkouts/sec sustainable, SKIP LOCKED se no deadlocks, batch writes 500/sec comfortable, zero overselling.

Q9. Product recommendations aur personalization kaise implement karo?

Multi-strategy engine: (1) Data collection: Kafka topics — product.viewed, product.added_to_cart, product.purchased, product.searched; Flink/Spark Streaming aggregate karta hai (recent_views last 20, recent_searches last 10, purchase_history); user profile Cassandra me (user_id se partitioned). (2) Strategies: Collaborative filtering — user-based (Jaccard similarity, >50% overlap wale similar users ki khareed suggest karo), item-based ("Users who bought X also bought Y", co-purchase matrix: similarity(A,B) = 1000 / sqrt(purchases(A) × purchases(B))), matrix factorization (ALS — 100M users × 10M products sparse matrix ko user_factors 100M×50 aur product_factors 10M×50 me todo, score = dot product, top 100 per user Redis me, daily refresh). Content-based — product embeddings (BERT/Sentence Transformers, 768-dim vector), user profile vector = dekhe/khareede products ke embeddings ka average, cosine similarity se match, ES kNN search. Trending — last 24h me sabse zyada viewed (cold-start users ke liye), category trending hourly. Business rules — zyada margin wale products boost, overstocked (qty >1000) boost, sale/new arrivals priority. (3) Hybrid ranking: final_score = 0.4 × collaborative + 0.3 × content + 0.2 × trending + 0.1 × business, top 20 return karo. (4) Real-time: home page GET /v1/recommendations/home (trending, recommended, recently viewed, based on cart); product page par "Similar products" aur "Frequently bought together"; search ranking user history se personalize. (5) Serving: nightly batch pre-compute (Redis recs:{user_id}, EX 86400), real-time blending + diversity (10 ek jaise products mat dikhao), fallback cold start par global trending. (6) A/B testing: variant A/B, metrics CTR, add-to-cart rate, conversion, revenue per user; +5% conversion p-value <0.05 ho to 100% rollout. (7) Training: Spark job S3 data lake par (1 saal events, 10 TB), ALS weekly, BERT embeddings monthly; feature store (Tecton/Feast). (8) Privacy: logs me PII nahi (user_id hash karo), 20% recommendations nayi categories se (filter bubble nahi), explainability ("Based on your purchase of X"). (9) Performance: API latency <100ms p95, pre-computation 100M users × 100 recs = 10B recs/day, Spark job 4 ghante, Redis 100GB. Business impact: recommendations se 30–40% revenue, cart size +25%, bounce rate kam.

Q10. Disaster recovery aur data consistency strategy kya hogi?

Multi-region DR with tiered consistency: (1) Architecture: primary us-east-1, secondary us-west-2, tertiary eu-west-1. (2) Replication: MySQL (User, Order) — synchronous us-west-2 (hot standby, <1s lag), asynchronous eu-west-1 (warm standby, <10s lag), Aurora Global Database ya Group Replication; PostgreSQL (Cart, Inventory) — streaming replication with replication slots; MongoDB — multi-region replica sets, write concern majority (>=2 nodes). (3) Consistency tiers: Tier 1 — Strong (inventory, orders, payments): synchronous replication commit se pehle, ACID + 2PC agar services ke paar ho, idempotency + unique constraints; trade-off — writes 50–100ms slow, lekin ye operations kam frequency wale hain. Tier 2 — Eventual (catalog, search, cache): async replication 1–5s lag, ES CDC 1–2s, Redis invalidate via Kafka, <10s stale cache acceptable (5 second purana price dikh jaye to chalega). (4) Failover: Route53 health check har 30s; 3 consecutive failures (90s) → failover; DB promote 2–5 min; DNS update; Kafka MirrorMaker secondary cluster par; data loss <1s (Tier 1) / <10s (Tier 2). (5) Split-brain prevention: fencing (primary khud writes rok de), witness node eu-west-1 tiebreaker, Consul/etcd lock — ek hi region primary. (6) RTO/RPO: Tier 1 RPO <1s, RTO <5 min; Tier 2 RPO <10s, RTO <5 min; backups RPO <1h (hourly S3 Glacier), RTO <4h. (7) Testing: monthly DR drills, chaos engineering (low traffic 2–4 AM random instance kill), tabletop exercises. (8) Corruption recovery: point-in-time recovery (7 din), daily dumps (30 din retention), binlogs/WAL replay. (9) Kafka durability: replication factor 3, min.insync.replicas=2, retention 7 din — events se state rebuild ho sakta hai. (10) Monitoring: replication lag alert (>5s Tier 1, >30s Tier 2), DB metrics, order/payment errors, revenue/hour anomaly. (11) Validation: nightly reconciliation (Order DB vs Payment DB), inventory audit, financial reconciliation. (12) Cost: multi-region 60–80% extra infra cost — $1M/month extra vs 1 ghante outage me $10M revenue loss. Example: 2:00 PM outage → 2:01:30 health fail → 2:02 failover → 2:05 DB promoted → 2:06 DNS → 2:08 users secondary par → kul downtime <8 minute, data loss <1s.

Interview FAQs — E-Commerce Platform

Current-era interviews me e-commerce system design se poochhe jaane wale 36 sawaal — har jawab wahi hai jo is lesson ke sections me detail me samjhaya gaya hai. Kisi bhi sawaal par click karke jawab kholo.

Q01 E-commerce system design karte waqt pehle kya karna chahiye — seedha database ya requirements?
Pehle requirements — functional (6 features: search, product view, cart, checkout/payment, order status, limited stock) aur non-functional (10 orders/sec, 10M MAU, 100M+ products, 100K searches/sec peak). Iske baad entities (User, Product, Cart, Order, Checkout), phir API, phir HLD, phir deep dive. Seedha database par koodna interview me sabse badi galti hai — interviewer dekhna chahta hai ki tum scope samajh kar design kar rahe ho.
Q02 Overselling rokne ka sabse sahi tareeka kya hai?
Teen parat ek saath: pehle Redis distributed lock (SETNX lock:inventory:{product_id} EX 30) — race ko shuru me hi rokta hai; phir PostgreSQL SELECT ... FOR UPDATE pessimistic lock — ACID guarantee; phir reserved_qty column — checkout me phansa stock available nahi dikhta. Asli deduction sirf payment.success webhook ke baad hoti hai. Koi ek parat hat jaye to bhi baaki do bacha leti hain — isi ko defence in depth kehte hain.
Q03 Redis lock aur database lock — dono kyu chahiye, ek kaafi nahi?
Redis lock fast hai (1-2ms) — 100 concurrent checkout requests me se 99 ko shuru me hi reject kar deta hai, database tak load pahunchta hi nahi. PostgreSQL FOR UPDATE ACID guarantee deta hai — transaction ke andar phantom reads nahi hote aur row-level exclusive lock milta hai. Redis lock 30 second me auto-expire hota hai, to service crash ho jaye to bhi deadlock nahi hota. Ek fast filter hai, doosra final guarantee.
Q04 reserved_qty column ka kya kaam hai? qty se seedha deduct kyu nahi karte?
reserved_qty checkout aur payment ke beech ka stock hold karta hai. qty=10, reserved_qty=3 ka matlab: kul 10, 3 active checkouts me, 7 naye buyers ke liye available. Agar checkout par seedha deduct kar do aur payment fail ho jaye, to stock wapas laane ka alag kaam karna padega. Reserve karne se payment fail hone par sirf reservation chhodni hoti hai, aur 5-15 minute timeout par background job apne aap chhod deta hai.
Q05 Payment me idempotency ka matlab kya hai aur kaise implement karte hain?
Idempotency matlab: wahi operation dobara chalao to bhi ek hi baar asar ho. Payment me idempotency_key = order_id use hota hai — Stripe ko dobara call karo to wahi payment intent milta hai, naya charge nahi. Saath me payments table par order_id par UNIQUE constraint hai, aur webhook handler pehle status check karta hai — payment pehle se SUCCESS hai to seedha 200 return. Teenon parat milkar double charge rokti hain, chahe user Pay do baar dabaye ya webhook do baar aa jaye.
Q06 Webhook signature validate karna kyu zaroori hai?
Bina signature validation ke koi bhi tumhare /webhooks/payment endpoint par nakli POST bhej kar order confirm karwa sakta hai — bina paise diye. Stripe HMAC signature bhejta hai jo webhook_secret se verify hota hai; signature galat ho to request turant reject karo. Ye payment security ki pehli line hai, uske baad idempotency check aur transaction aate hain.
Q07 Product search ke liye Elasticsearch kyu, PostgreSQL full-text search kyu nahi?
Elasticsearch full-text search ke liye bana hai: relevance scoring (title^3 boost), fuzzy matching, synonyms (laptop = notebook), faceted search (aggregations se filter counts), aur autocomplete (edge n-gram). PostgreSQL ka tsvector basic matching karta hai, lekin ye sab nahi deta. 100K queries/sec peak par ES sharded cluster (10 nodes, 5 shards) p95 <100ms deta hai — PostgreSQL is load par search ke liye nahi bana.
Q08 Search me title^3 boost ka kya matlab hai?
Elasticsearch multi_match query me title field ko 3 guna zyada weight milta hai. 'laptop' search karne par jiska title me laptop hai wo description me laptop likhe product se 3x zyada score pata hai. Isi se relevant results upar aate hain — pehle laptop, phir laptop bag. Ye relevance tuning ka sabse aasan tareeka hai.
Q09 CDC kya hai aur product search me iski kya zaroorat hai?
CDC (Change Data Capture) matlab database ke badlav ko pakad kar doosri jagah sync karna. MongoDB me product update hote hi oplog/Change Stream se event Kafka topic product.changes me jata hai, ES indexer consumer use index karta hai — 1-2 second me search fresh ho jata hai. Dual writes (Product Service seedha MongoDB aur ES dono me likhe) galat hai: tight coupling, transaction complexity, aur ES down ho to writes ruk jayengi. CDC me Product Service ko ES ke baare me kuch jaanna hi nahi padta.
Q10 MongoDB products ke liye aur PostgreSQL inventory ke liye — ulta kyu nahi?
Products ke attributes har category me alag hote hain — mobile ke RAM/storage, book ke author/ISBN, kapdon ke size/color. MongoDB ka flexible schema iske liye perfect hai. Inventory ko strong consistency, ACID transactions aur SELECT FOR UPDATE (pessimistic lock) chahiye — ye PostgreSQL deta hai. Database ka chunav data ki nature se hota hai: flexible data ke liye document DB, paise/stock jaise critical data ke liye relational ACID DB.
Q11 Cart ke liye Redis aur PostgreSQL dono kyu chahiye?
Reads writes se 10 guna zyada hote hain — user checkout se pehle cart baar-baar kholta hai. Redis reads <1ms me deta hai, PostgreSQL ~50ms me. Lekin Redis sirf cache hai — source of truth PostgreSQL hai, kyunki cart updates reliable hone chahiye (ACID), aur Redis khaali ho jaye to bhi cart wapas ban jata hai. Likha PostgreSQL me jata hai, padha Redis se jata hai — yehi hybrid pattern hai.
Q12 Guest cart (bina login) kaise handle karte hain?
Bina login wale user ka cart session_id se juda hota hai aur sirf Redis me rehta hai, TTL 24 ghante. Login karte hi guest cart user ke cart me migrate ho jata hai — UPDATE cart_items SET cart_id={user_cart_id} WHERE cart_id={guest_cart_id}. Isse user ko dobara items dhoondhne nahi padte, aur bina login bhi shopping ka experience poora milta hai.
Q13 Checkout flow ke saare steps kram se batao.
Fetch cart items → har product par SETNX Redis lock lo → SELECT ... FOR UPDATE se inventory validate karo → reserved_qty badhao → total nikalo (price × qty + shipping + tax) → transaction me order banao (PENDING_PAYMENT) → Redis locks chhodo → payment intent banao (idempotency_key: order_id) → client ko {order_id, payment_url, expires_at: now()+15min} do. Phir webhook: idempotency check → transaction (payment INSERT + order PAYMENT_CONFIRMED + inventory deduct + cart clear) → Kafka events publish karo. Average checkout time 2-3 second.
Q14 Payment timeout ka kya hota hai — user 15 minute me pay na kare to?
Background job un orders ko dhoondhta hai jo 15 minute se zyada PENDING_PAYMENT me hain — unki reserved inventory chhod deta hai (reserved_qty ghatao), order status PAYMENT_TIMEOUT kar deta hai, aur user ko notification bhejta hai: 'Checkout expired, items returned to stock'. Isse stock hamesha ke liye phansa nahi rehta aur agla buyer wahi item khareed sakta hai.
Q15 Order status real-time me user tak kaise pahunchta hai?
Har status change Kafka event hai — order.shipped, order.out_for_delivery, order.delivered. Order Status Service events consume karke Order DB update karta hai, aur WebSocket ke through user ki screen turant update ho jati hai (<500ms). WebSocket na chale to fallback polling hai — client har 30 second me GET /v1/status/{order_id} poochhta hai. Notification Service bhi wahi events sun kar email/SMS/push bhejta hai.
Q16 Kafka is design me kya kaam karta hai? Seedha HTTP call kyu nahi?
Kafka services ko decouple karta hai — Checkout Service ko ye nahi jaanna padta ki Notification ya Warehouse kaun hai; wo bas payment.success event publish karta hai. Slow kaam (email bhejna) checkout ko rokta nahi, events replay karke debugging ya index rebuild ho sakta hai, aur har consumer apni speed se scale hota hai. HTTP call karne se services tightly coupled ho jati hain — ek slow ho to saare ruk jate hain.
Q17 Kafka consumer idempotent kyu hona chahiye?
Kafka event dobara deliver kar sakta hai — rebalance ya retry par wahi event phir aa sakta hai. Agar consumer idempotent nahi hai to payment do baar process hoga ya stock do baar deduct hoga. Isliye har event ka event_id store karke deduplicate karo — pehle se processed event_id dikhe to skip karo. Saath me DLQ rakho: 3 retries ke baad bhi fail hone wala event dead letter queue me jaye, chup-chaap kho na jaye.
Q18 Flash sale me 1 minute me 100K orders kaise handle karte hain?
Pehle waiting room — sale se pehle 1M users queue me, sale shuru hote hi 1000 users/sec andar (token ke saath) taaki thundering herd na ho. Phir flash_sale_inventory table — 1000 rows, SKIP LOCKED se contention-free allocation. Phir queue-based checkout — requests Kafka topic me, 50 workers steady 100 checkouts/sec process karte hain. Redis counter se turant 'Sold out' batao, rate limiting (1 checkout/10 sec per user) + CAPTCHA se bots roko, aur 100 orders batch me INSERT karo. Result: 99.9% uptime, zero overselling.
Q19 SKIP LOCKED kya hai aur flash sale me iski kya zaroorat hai?
PostgreSQL ka SKIP LOCKED matlab: SELECT ... FOR UPDATE SKIP LOCKED — jo row kisi aur transaction ne lock ki hai use skip karke agla available row lo. Flash sale me 1000 available rows aur 100K concurrent buyers honge — bina SKIP LOCKED ke saare ek hi row par lock ke liye ladenge (contention, deadlocks). SKIP LOCKED se har buyer ko turant koi na koi free row mil jati hai, koi wait nahi karta.
Q20 Virtual waiting room kya hota hai?
Sale shuru hone se pehle users ko ek waiting room page par rakha jata hai — countdown timer dikhta hai. Sale shuru hote hi room batches me users chhodta hai (1000/sec, random token ke saath). Isse backend par ek saath 1M requests nahi aati — load controlled rehta hai. Token ke bina backend request accept hi nahi karta, to koi seedha checkout URL hit karke line nahi tod sakta.
Q21 Product recommendations kaise kaam karti hain — collaborative filtering kya hai?
Collaborative filtering matlab: jin users ki pasand tumse milti hai, unhone jo khareeda wo tumhe suggest karo. User-based — Jaccard similarity se similar users dhoondho (>50% overlap). Item-based — 'Users who bought X also bought Y' (co-purchase matrix). Matrix factorization (ALS) — 100M users × 10M products matrix ko user aur product factors me todo, score = dot product. Iske saath content-based (embeddings, cosine similarity), trending aur business rules milakar hybrid score banta hai: 0.4×collaborative + 0.3×content + 0.2×trending + 0.1×business.
Q22 Cold start problem kya hai recommendations me?
Naye user ke paas koi history nahi hoti — na views, na purchases — to collaborative filtering kaam nahi karta. Iska hal hai global trending aur category trending dikhana, plus editorial curated products. Jaise-jaise user browse karta hai, real-time blending shuru ho jata hai. Isi ko cold start kehte hain, aur isiliye recommendation API me fallback hamesha hota hai.
Q23 CAP theorem e-commerce me kaise apply hota hai?
Search aur product dekhne ke liye availability chuno — thoda purana data chalega (eventual consistency, 1-2 second lag). Order, inventory aur payment ke liye consistency chuno — strong consistency (ACID) zaroori hai, chahe writes 50-100ms slow ho jayein. Ek hi system me do alag CAP faisle hote hain, feature ke hisaab se — yehi practical CAP hai, theory wala 'ek chunna' nahi.
Q24 Inventory ke liye strong consistency aur search ke liye eventual consistency kyu?
Inventory galat ho to overselling hoti hai — paise ka nuksan aur customer trust ka nuksan. Isliye inventory synchronous replication aur ACID ke saath strong consistency me rehta hai. Search me 1-2 second purana price ya qty dikh jaye to koi nuksan nahi — user ko farak bhi nahi padta. Isliye search eventual consistency se chal jata hai aur fast rehta hai.
Q25 Redis me kaunsi keys hoti hain aur unki TTL kya hai?
cart:{userId} HASH — TTL 7 din. product:{productId} STRING (JSON details) — TTL 30 min. search:{hash(query)} STRING (results) — TTL 10 min. inventory:{productId} HASH {qty, reserved_qty} — TTL 5 min. lock:inventory:{productId} STRING — EX 30 second. TTL isliye alag hai kyunki har data ki freshness need alag hai: cart hafte bhar chahiye, inventory 5 minute se zyada purana nahi chalega.
Q26 Search cache ki key hash(query + filters + sort) kyu hoti hai?
Kyunki wahi query alag filters ya sort ke saath alag result deti hai. Sirf query text se key banoge to 'laptop' price-low-to-high aur price-high-to-low dono ko wahi cached result mil jayega — galat. Hash me filters aur sort bhi daalne se har unique combination ki apni cache entry hoti hai. TTL 10 minute, top 10K queries cache se serve hoti hain — 60-70% hit rate.
Q27 Faceted search kya hai?
Faceted search matlab search results ke saath filter counts bhi dena — jaise 'Electronics (5000)', 'Books (3000)', price ranges, brands. Elasticsearch aggregations se ye counts nikalte hain. UI me jo left side checkboxes with counts dikhte hain, wo faceted search hai. Isse user ko pata chalta hai ki filter lagane par kitne results bachenge, bina filter lagaye.
Q28 Autocomplete (type-ahead) kaise implement karte hain?
Elasticsearch me edge n-gram tokenizer wala alag index banao — 'lap' type karte hi 'laptop', 'laptop bag', 'laptop stand' suggest hone lagenge. Client har keystroke par request bhejta hai lekin 300ms debounce ke saath — matlab user ruk jaye tabhi request jaye, har letter par nahi. Ye suggestions alag lightweight index se aate hain, main search index se nahi.
Q29 Disaster recovery me RTO aur RPO kya hote hain?
RPO (Recovery Point Objective) matlab kitna data kho sakta hai — Tier 1 (orders, inventory) ke liye <1 second (synchronous replication), Tier 2 ke liye <10 second. RTO (Recovery Time Objective) matlab kitni der me service wapas aayegi — dono tiers ke liye <5 minute (automated failover). Backups ka RPO <1 ghanta aur RTO <4 ghante hota hai. Example: 2 PM outage → 2:08 tak users secondary region par, kul downtime <8 minute.
Q30 Multi-region setup me split-brain kya hai aur kaise rokte hain?
Split-brain matlab network partition ke baad dono regions khud ko primary samajh kar writes lene lagen — data diverge ho jata hai. Rokne ke liye: fencing (primary region partition detect hote hi khud writes rok de), witness node (teesra region quorum tiebreaker), aur Consul/etcd distributed lock — ek waqt par ek hi region primary ho sakta hai. Bina iske failover se zyada nuksan ho sakta hai.
Q31 Order cancel karne par kya hota hai — stock aur refund ka?
Cancel sirf PENDING_PAYMENT, PAYMENT_CONFIRMED ya PROCESSING states me allowed hai — SHIPPED ke baad nahi. Cancel par order status CANCELLED hota hai, stock wapas aata hai (qty me order qty jod do), payment capture hua ho to gateway se refund initiate hota hai, aur Kafka par order.cancelled event jata hai — Notification Service 'Order cancelled, refund in 5-7 days' bhejta hai.
Q32 Database read replicas kya karte hain aur writes kahan jati hain?
Saari writes primary database par jati hain, reads replicas se serve hote hain — product views, order history jaise read-heavy queries. Isse primary ka load kam hota hai aur reads scale hote hain. Trade-off: replica par 1-2 second lag ho sakta hai (eventual consistency) — order history me 2 second purana data dikh jaye to chalega, lekin checkout hamesha primary se hota hai.
Q33 Orders table ko month se partition kyu karte hain?
100M orders/year — ek hi table me 200 GB/year badhta hai. Month se partition karne par har partition chhota rehta hai, purane months ke queries sirf apni partition scan karte hain, aur purana data archive karna aasan ho jata hai (poori partition drop karo). Query performance aur maintenance dono behtar hote hain.
Q34 Connection pooling kyu zaroori hai?
Har API request par naya database connection kholna bahut mehenga hai (TCP + auth, ~10ms). Pool me pehle se 200 connections khule rehte hain — request aate hi use lo, kaam khatm hote hi wapas do. Bina pooling ke 10K concurrent users par database connections khatm ho jayenge aur requests fail hone lagenge. Pool size 200 per API server tay hai is design me.
Q35 API rate limiting 1000 req/min per user kyu hai?
Abuse aur DDoS se bachav — koi ek user ya bot API ko flood na kar sake. Checkout jaise sensitive endpoints par aur bhi sakht limits hoti hain (flash sale me 1 checkout attempt per 10 second). Rate limit cross karne par 429 response milta hai. Ye sirf security nahi, capacity planning bhi hai — pata rehta hai ki peak load kitna hoga.
Q36 CDN product images ke liye kyu zaroori hai?
Product images bade hote hain aur har user har product ki image dekhta hai. CloudFront CDN se images edge locations se serve hoti hain — 95% cache hit, global latency <50ms. Bina CDN ke har image request S3 aur origin server tak jayegi — slow aur mehenga. Images S3 me stored hain, URLs MongoDB me, serve CDN se — ye teeno ka combo hai.
