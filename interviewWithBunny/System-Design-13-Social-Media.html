01Core Design · Lesson 13

1. Functional Requirements

Functional requirements matlab — system ko karna kya-kya hai. Interview me pehle ye 7 features ginwa do, phir scale ki baat karo. Har feature ke peeche ek service ya database chhupa hai, jo aage ke sections me khulta hai.

Feature 1 — Register aur login, profile ke saath

User email, password aur username se account bana sake, login kar sake, aur apni profile manage kar sake — bio, profile photo, settings. Ye User Service aur PostgreSQL ka kaam hai. Login par JWT token milta hai jo 7 din tak valid rehta hai.

Feature 2 — Post banao (text / image / video)

User text, photo ya video post kar sake. Multimedia content 500MB tak ka ho sakta hai. Post turant publish hota dikhta hai, lekin media ka processing (thumbnails, transcoding) background me async hota hai.

Feature 3 — Follow karo, social graph banao

User dusre users ko follow kar sake aur social graph bane. Friend request wala flow bidirectional connections ke liye hai — matlab dono taraf se connection. Follow karte hi followee ke recent posts follower ki feed me backfill hote hain.

Feature 4 — Like aur comment, nested threads ke saath

Post par like aur comment kar sake. Comments nested hote hain — matlab comment ke neeche reply, reply ke neeche reply (lekin max 3 levels tak, usse zyada UI complex ho jaata hai). Like idempotent hota hai — do baar click karo to bhi ek hi like gina jaata hai.

Feature 5 — Personalized feed, reverse chronological order

User ko un logon ke posts ki feed dikhe jinhe wo follow karta hai — reverse chronological order me, matlab sabse naya post sabse upar. Ye feed pehle se banakar Redis me rakhi jaati hai (fanout on write), isliye load karte hi turant mil jaati hai.

Feature 6 — Search: users, posts, hashtags

Users, posts aur hashtags search kar sake, real-time suggestions ke saath — jaise hi type karo, autocomplete suggestions aayein. Ye Elasticsearch se hota hai, fuzzy matching (edit distance 2) ke saath.

Feature 7 — Notifications

Har interaction par notification mile — like, comment, follow, mention. Ek hi post par 5 minute me kayi likes aayein to alag-alag notification nahi, ek aggregated notification milta hai.

2. Non-Functional Requirements

Non-functional requirements matlab — system kitne scale par, kitni speed se, aur kitna reliable hona chahiye. Interview me ye numbers yaad rakhna sabse zyada kaam aata hai, kyunki har design decision inhi numbers se justify hota hai.

Scale — kitna bada system hai

Field / CheezDetail
Daily Active Users500M DAU — total registered users 2 billion. Matlab har din aadha billion log app kholte hain.
Posts Volume100M posts / din — average 1.2K posts / second. Peak hours me isse kayi guna zyada.
Reads / Writes Ratio100:1 — users feed scroll karte hain, post bahut kam karte hain. Ye heavy read system hai, isliye saare optimizations reads ke liye hain.
Media StoragePetabytes total images/videos, roz 10TB upload hota hai. Media kabhi database me nahi, hamesha S3 me.

Performance — kitna fast hona chahiye

Field / CheezDetail
Feed load latency500ms — feed load hone me isse zyada nahi lagna chahiye (p95).
Like / comment latency<200ms — like ya comment dabate hi turant response.
Feed GenerationNormal users (<5K followers) ke liye fanout on write, celebrities ke liye pull model.
Media UploadAsync processing — upload karte hi confirmation mil jaata hai, transcoding background me chalta hai.

Reliability — kitna bharosemand hona chahiye

Field / CheezDetail
CAP TheoremAvailability >> Consistency — eventual consistency acceptable hai. Like count 5 minute ke liye 10 se galat ho to chalega, lekin feed down nahi honi chahiye.

Yehi wajah hai ki fanout on write kaam karta hai: ek baar slow write (post karte waqt) se 100x fast reads milte hain.
INTERVIEW FAVOURITE: Eventual consistency social media me acceptable kyun hai? Like count 5 minute ke liye thoda galat ho to koi nuksaan nahi. Feed me post 2 second late dikhe to chalega. Banking jaisa system hota to strong consistency chahiye hoti — social media AP side par hai CAP theorem me, availability + low latency ko priority milti hai, perfect consistency ko nahi.

3. Core Entities

Core entities matlab — system ke andar kaun-kaun se main data objects hain. In 5 entities se poora data model banta hai. Interview me inhe pehle ginwa do, phir section 8 me inka poora schema aata hai.

Entity 1 — User

Profile: user_id, username, email, bio, profile_pic_url, created_at. User PostgreSQL me rehta hai, kyunki profile data structured hai aur strong consistency chahiye (username unique hona hi chahiye).

Entity 2 — Post

Content: post_id, user_id, content (text / media URLs), created_at, visibility (public / friends / private). Post Cassandra me rehta hai — partition key user_id hai, kyunki posts likhe bahut jaate hain aur user ki timeline ek hi partition se nikalni hoti hai.

Entity 3 — Followers (Social Graph)

Bidirectional social graph: follower_id, followee_id, created_at. Ye graph batata hai kaun kisko follow karta hai. Isi graph se fanout hota hai — post aate hi iske saare followers ki feed update hoti hai. Graph DB ya PostgreSQL dono chal sakte hain.

Entity 4 — Like / Comment (Engagement)

Engagement data: reaction types (like, love, haha, wow, sad, angry), timestamps, metadata. Likes Cassandra me (high write volume), comments PostgreSQL me (nested structure ke liye parent_comment_id chahiye).

Entity 5 — Feeds (Precomputed Feed Cache)

Har user ki pehle se bani hui feed: feed_id, user_id, post_ids[], updated_at. Ye Redis me LIST ke roop me rehti hai — feed:{user_id} = latest 1000 post_ids. Feed load karna matlab sirf LRANGE chalana, koi heavy query nahi.

4. API Designing

API design matlab — client aur server ke beech ka contract. Teen groups hain: User Onboarding, Post Operations, aur Interactions. Har endpoint ke saath method, path aur kaam likha hai. Interview me ye table whiteboard par likhna sabse safe tareeka hai.

User Onboarding

Field / CheezDetail
POST /api/v1/users/registerNaya user account banao — email, password, username ke saath.
POST /api/v1/users/loginAuthenticate karo aur JWT token return karo (7 din ki expiry).
GET /api/v1/users/{user_id}/profileUser profile lao — follower / following counts aur posts count ke saath.
PUT /api/v1/users/{user_id}/profileProfile update karo — bio, profile pic, settings.

Post Operations

Field / CheezDetail
POST /api/v1/postsPost banao — {content, media_urls[], visibility, mentions[]} ke saath.
GET /api/v1/posts/{post_id}Ek post lao — engagement metrics (likes, comments count) ke saath.
PUT /api/v1/posts/{post_id}Post content update karo — sirf author edit kar sakta hai.
DELETE /api/v1/posts/{post_id}Soft delete — deleted mark karo, lekin analytics ke liye data rakho.
GET /api/v1/posts/feed?limit={limit}&amp;offset={offset}Personalized feed lao — pagination ke saath (infinite scroll).

Interactions

Field / CheezDetail
POST /api/v1/posts/{post_id}/likePost like karo — idempotent: dusri baar call karne par unlike ho jaata hai.
DELETE /api/v1/posts/{post_id}/unlikeLike hatao.
GET /api/v1/posts/{post_id}/commentsComments lao — pagination ke saath, nested threads supported.
POST /api/v1/comments/{comment_id}Comment ya reply add karo (kisi comment ka reply bhi).

Iske liye teen layers hain — client-side debounce (300ms), Redis check (like:{user_id}:{post_id} key), aur Cassandra composite primary key (post_id, user_id) jo duplicate row banne hi nahi deta.

5. High Level Design

High Level Design matlab — bade-bade boxes aur unke beech ke arrows. Client se request API Gateway par aati hai, wahan se alag-alag services par jaati hai, aur har service ka apna database hai. Diagram neeche section ke end me bhi hai.

Request ka flow — client se database tak

Field / CheezDetail

User Service &rarr; User DB (PostgreSQL)User profiles, credentials, settings — read replicas ke saath.
Content Service &rarr; Post DB (Cassandra)Posts store karta hai, user_id se partitioned, writes ke liye optimized.
Content Service &rarr; S3Media files (images / videos) — CDN se fast delivery.
Feed Service &rarr; Feed Cache (Redis)Pehle se bani hui feeds — hot data memory me.
Follower Service &rarr; Follower DB (Graph DB ya PostgreSQL)Social graph — bidirectional edges ke saath.

Diagram kya dikhata hai

INTERVIEW FAVOURITE: Interview me hamesha poochha jaata hai: 'Feed ke liye Redis kyun, database kyun nahi?' Jawaab: (1) Speed — Redis se LRANGE <10ms me, DB query 100ms+ leti hai. (2) Scalability — Redis 100K ops/sec handle karta hai. (3) Feed ephemeral data hai — kho jaaye to DB se dobara bana sakte hain. (4) DB load 90% kam ho jaata hai.

06.1Deep Dive (LLD) · Lesson 13

6. Deep Dive Design — Steps 1–5

Low Level Design matlab — har feature ke andar step-by-step kya hota hai. Ye 10 steps hain; pehle 5 yahan hain (registration, post creation, media processing, fanout, feed loading), baaki 5 agle section me.

Step 1 — User Registration & Login

  • Client bhejta hai: POST /api/v1/users/register with {username: 'user_rahul', email: 'user@example.com', password: 'hashed_password'}
  • User Service validate karta hai: username unique hai ya nahi (DB query), email format sahi hai, password strong hai (8+ characters, special chars).
  • Service banata hai: PostgreSQL me user record — bcrypt hashed password (cost factor 12), user_id UUID generate hota hai.
  • Service provision karta hai: Redis me khaali feed, Settings DB me default privacy settings.
  • Service return karta hai: {user_id, username, token} — JWT, 7 din ki expiry ke saath.
  • Login flow: password hash match karo, JWT banao {user_id, username, exp}, token return karo.

Step 2 — Post Creation

  • Client bhejta hai: POST /api/v1/posts with {content: 'Hello World!', media_files: [File], visibility: 'public', mentions: ['@user_meera']}
  • Content Service validate karta hai: JWT token, content length (<5000 chars), media size (<500MB), file types (JPEG, PNG, MP4).
  • Service upload karta hai: media S3 me, key pattern {user_id}/{year}/{month}/{uuid}.{ext}, S3 URLs return karta hai.
  • Service banata hai: Cassandra me post record — partition key = user_id, clustering key = created_at DESC, taaki user ki timeline queries fast hon.
  • Service publish karta hai: Kafka topic post.created par event {post_id, user_id, created_at, media_urls}.
  • Service return karta hai: {post_id, status: 'published', media_urls[]} turant — 202 Accepted. Fanout async hota hai, response ka wait nahi karta.

Step 3 — Media Upload & Processing

  • Client upload karta hai: multipart/form-data se, ya bade files (>100MB) ke liye presigned S3 URL se.
  • Content Service generate karta hai: presigned PUT URL (15 minute ke liye valid), client seedha S3 par upload karta hai.
  • S3 upload trigger karta hai: Lambda function async processing ke liye (image resizing, video transcoding).
  • Image processing: thumbnails bante hain — 150x150, 400x400, 1080x1080 (ImageMagick), S3 me store hote hain, CDN se serve hote hain.
  • Video processing: multiple resolutions me transcode — 360p, 720p, 1080p (FFmpeg), HLS format adaptive streaming ke liye.
  • Post Consumer Service: Kafka post.created ko poll karta hai, metadata nikalta hai (dimensions, duration), PostDB ko processed URLs se update karta hai.
DHYAAN DO: Media ko kabhi database me BLOB ke roop me store mat karo. S3 use karo object storage ke liye, database me sirf URLs rakho. BLOB storage: slow queries, mehengi replication, CDN support nahi. S3: sasta ($0.023/GB/month), durable (11 9's), CDN-friendly.
DHYAAN DO: Media ko upload ke waqt synchronously process mat karo. Video transcoding me 30 second se 5 minute lagte hain. Turant 202 Accepted return karo, processing async Lambda/queue se karo. User ko 'Processing...' status dikhega, complete hote hi notification milega. Synchronous karoge to API timeout + kharab UX.

Step 4 — Feed Generation (Fanout on Write)

  • Feed Service consume karta hai: Kafka post.created event {post_id, user_id, created_at}.
  • Service query karta hai: Follower DB se user ke saare followers (jaise 500 followers).
  • Service update karta hai: har follower ki Redis feed — LPUSH feed:{follower_id} {post_id}, LTRIM se latest 1000 posts hi rakhta hai.
  • Redis structure: LIST feed:{user_id} = [post_id_1, post_id_2, ..., post_id_1000], timestamp ke hisaab se sorted.
  • Celebrity handling: agar user ke >5K followers hain to fanout on write skip karo, pull model use karo (feed load karte waqt on-demand fetch).
  • Hybrid model: chhote users (<5K) push (fanout on write), celebrities pull (fanout on read), medium users (1K–5K) hybrid.
DHYAAN DO: Celebrities (millions followers) ke liye kabhi fanout on write use mat karo. 1 post = 10M writes — minutes lagenge aur system overwhelm ho jaayega. Hamesha pull model (fanout on read) use karo jab followers >5K hon.

Step 5 — Feed Loading (Pull Model)

  • Client request karta hai: GET /api/v1/posts/feed?limit=20&offset=0, Authorization header ke saath.
  • Feed Service check karta hai: Redis feed:{user_id} me cached feed hai ya nahi.
  • Cache hit: LRANGE feed:{user_id} 0 19 se 20 post_ids mil jaate hain — [post_123, post_456, ...].
  • Service fetch karta hai: PostDB se post details — batch query IN clause se — {content, media_urls, created_at, user_id}.
  • Service enrich karta hai: Like DB aur Comment DB se engagement counts, User DB se author details.
  • Cache miss: celebrities ya cold feeds ke liye FollowDB se followed users nikalo, unke recent posts PostDB se timestamp order me lao, result cache karo.
  • Service return karta hai: {posts: [{post_id, author: {user_id, username, profile_pic}, content, media_urls, likes_count, comments_count, created_at}], next_offset: 20}

Feed load ka worked example (section 12 me bhi hai): Step 1 Redis LRANGE = 10ms, Step 2 batch post fetch = 50ms, Step 3 user info = 30ms, Step 4 engagement counts MGET = 20ms. Total = 110ms — 500ms p95 target se bahut neeche.

06.2Deep Dive (LLD) · Lesson 13

6. Deep Dive Design — Steps 6–10

Steps 6–10: like/comment, follow/unfollow, notifications, search aur CDN/media delivery. Ye paanch steps user ke har interaction ko cover karte hain.

Step 6 — Like / Comment Interaction

  • Client bhejta hai: POST /api/v1/posts/{post_id}/like, JWT se user_id nikal kar.
  • Engagement Service check karta hai: Redis cache like:{user_id}:{post_id} — idempotency ke liye (double-like rokne ke liye).
  • Service likhta hai: Like DB (Cassandra) me like record — composite key (post_id, user_id, created_at).
  • Service increment karta hai: Redis counter INCR likes_count:{post_id} — PostDB se async sync har 5 minute me (write batching).
  • Service publish karta hai: Kafka topic post.liked par event — notification service ke liye.
  • Comment flow: same, lekin Comment DB me likhta hai — nested threads ke liye parent_comment_id field ke saath.
  • Denormalization: PostDB me like_count aur comment_count store hote hain fast reads ke liye — background job Like/Comment DB se update karta hai.
TIP: Likes ke liye idempotency critical hai. User slow network par like button 3 baar dabaye to bhi sirf 1 like record hona chahiye. Redis SETNX + Cassandra composite key (post_id, user_id) — dono layers race condition me bhi duplicate rokte hain.

Step 7 — Follow / Unfollow Operation

  • Client bhejta hai: POST /api/v1/users/{user_id}/follow, follower_id JWT se.
  • Follower Service validate karta hai: pehle se follow to nahi kar raha, khud ko follow to nahi kar raha, user exist karta hai ya nahi.
  • Service banata hai: Follower DB me record {follower_id, followee_id, created_at}.
  • Service update karta hai: counts — INCR followers_count:{followee_id} aur INCR following_count:{follower_id} Redis me.
  • Service trigger karta hai: backfill job — followee ke recent posts (last 100) follower ki Redis feed me daal do.
  • Unfollow: Follower DB se DELETE, counts decrement karo, followee ke posts follower ki feed se purge karo (LREM).

Step 8 — Notification Generation

  • Notification Service consume karta hai: Kafka topics post.liked, post.commented, user.followed.
  • Service check karta hai: user ki preferences — kis type ki notification chahiye (likes: true, comments: true, follows: true).
  • Service aggregate karta hai: 5 minute me kayi likes aayein to ek hi notification — [Name] aur 15 others ne tumhari post like ki.
  • Service publish karta hai: notification topic par {user_id, type, message, actor_ids[], post_id, created_at}.
  • Delivery: push notification FCM/APNS se, in-app notification Notification DB (PostgreSQL) me store hoti hai.
  • Read receipts: read mark karne par status update hota hai, 30 din baad cleanup.

Step 9 — Search Functionality

  • Client bhejta hai: GET /api/v1/search?q=user&type=users&limit=10
  • Search Service route karta hai: Elasticsearch cluster par, query DSL ke saath.
  • User search: username, name, bio fields par match — fuzzy matching (edit distance 2).
  • Post search: content field par full-text search, hashtag extraction, time-based boosting (recent posts upar).
  • Index updates: Post Consumer Service naye posts ko Elasticsearch me async index karta hai, Kafka ke through.
  • Autocomplete: username field par prefix query, suggest API se typeahead — popular searches Redis me cached.

Step 10 — CDN & Media Delivery

  • Media request: client maangta hai https://cdn.example.com/media/{user_id}/{uuid}.jpg
  • CDN (CloudFront) check karta hai: edge location cache — cache hit ho to turant return (<50ms).
  • Cache miss: CDN S3 origin se fetch karta hai, cache karta hai — images TTL = 30 din, videos TTL = 7 din.
  • Optimization: device ke hisaab se optimized image — mobile ko 400x400, desktop ko 1080x1080 (CloudFront Lambda@Edge se).
  • Video streaming: HLS manifest (m3u8) multiple bitrates ke saath, network speed ke hisaab se adaptive streaming.
  • Purge strategy: post delete hone par CDN cache invalidate karo API call se, S3 object lifecycle policy se delete ke liye mark karo.

7. Client-Side Components

Client-side components matlab — app ke andar user ko dikhne wale 7 hisse. Interview me backend ke saath-saath client ka bhi zikr karna achha impression deta hai, kyunki performance ka aadha kaam client par hota hai.

Component 1 — Feed UI

Infinite scroll, virtual scrolling performance ke liye, images lazy load hoti hain. Sirf wahi post render hota hai jo screen par dikh raha hai — 1000 posts ki list bhi smooth chalti hai.

Component 2 — Post Composer

Rich text editor, @mentions autocomplete, media upload progress bar ke saath. User type karte hi mention suggestions aate hain, upload ka progress dikhta hai.

Component 3 — Interaction Buttons

Optimistic UI updates — like button dabate hi turant animate hota hai, server ka wait nahi karta. Agar server se failure aaye to rollback ho jaata hai (like wapas hat jaata hai).

Component 4 — Media Player

Video player — adaptive bitrate streaming, thumbnail previews. Network slow ho to khud hi low quality par switch kar deta hai.

Component 5 — Notification Center

Real-time updates WebSocket ya SSE se, unread badge count ke saath. Nayi notification aate hi badge badh jaata hai, page refresh ki zaroorat nahi.

Component 6 — Search Bar

Debounced autocomplete (300ms delay) — har keystroke par request nahi jaati, user rukne par hi search hota hai. Recent searches locally cached rehti hain.

Component 7 — Profile Manager

Profile edit karo, privacy settings, account management — sab ek jagah.

9. Feed Ranking & Recommendation

Feed ranking matlab — 1000 cached posts me se pehle 20 kaun se dikhaye jaayein. Sirf time order kaafi nahi hota: recency, engagement aur author affinity — teeno ka weighted score banta hai. Aur fanout ke teen models (push / pull / hybrid) yahin decide hote hain.

Feed Ranking Algorithm

  • Trigger: user feed load karta hai, service Redis ya Pull model se candidate posts fetch karti hai.
  • Scoring: har post ka score teen cheezon se banta hai — (1) Recency: exponential decay (1 ghante se kam purana post = 1.0, 1 din purana = 0.5, 7 din purana = 0.1). (2) Engagement: likes_count × 0.3 + comments_count × 0.5. (3) Author affinity: close friends (jinse baar-baar interaction hota hai) ka weight 2x.
  • Ranking: posts sort hote hain composite score se — score = recency_score × 0.4 + engagement_score × 0.4 + affinity_score × 0.2
  • Diversity: kam-follow kiye gaye users ka content bhi feed me inject karo (10% of feed) — echo chamber na bane.
  • ML Model: advanced systems gradient boosted trees (XGBoost) use karte hain — click-through rate, watch time, shares par train karke engagement probability predict karte hain.
Ranking formula — yaad rakhne layak
score = recency_score x 0.4 + engagement_score x 0.4 + affinity_score x 0.2

recency:  <1 hour = 1.0 | 1 day = 0.5 | 7 days = 0.1  (exponential decay)
engagement: likes_count x 0.3 + comments_count x 0.5
 affinity: close friends = 2x weight
diversity: 10% feed kam-followed users se

Fanout Models Comparison

Field / CheezDetail
Push Model (Fanout on Write)User post karte hi turant saare followers ki feeds me push karo. Pros: fast read (feed pehle se bani hui), Cons: slow write (500 followers = 500 writes), storage heavy (1000 posts × 500 followers = 500K feed entries).
Pull Model (Fanout on Read)User feed load kare tab followed users ke posts on-demand fetch karo. Pros: fast write (single post write), koi storage overhead nahi, Cons: slow read (100 followed users ke posts query karo, sort karo, merge karo).
Hybrid ModelPush users ke liye <5K followers, Pull celebrities (>5K) ke liye, medium (1K–5K) ke liye mixed. Example: ek mega-celebrity (500M followers) pull use karta hai, normal user push, verified accounts (100K followers) hybrid.
ImplementationUser table me celebrity flag, Feed Service fanout se pehle check karta hai, celebrity posts ke liye pull model use karta hai.
TIP: Hybrid fanout model scale par critical hai. Push model (<5K followers) se instant feeds milti hain. Pull model (>5K) se write amplification rukta hai. Medium users (1K–5K) hybrid use karte hain: active followers ko push, inactive ko pull. Isse 99% users efficiently handle ho jaate hain.

Technique 1 — Database Sharding

Posts user_id se shard hote hain (1000 shards), Followers follower_id se. Isse horizontal scaling possible hoti hai — naya shard add karo, load baant do.

Technique 2 — Read Replicas

PostgreSQL ke 5 read replicas User reads ke liye (profile views). Writes sirf primary par jaate hain, 99% queries replicas se serve hoti hain.

Technique 3 — Redis Caching

Feed cache (TTL = 10 min), user profile cache (1 hour), like counts (5 min) — DB load 90% kam ho jaata hai.

Technique 4 — CDN for Media

Technique 5 — Lazy Loading

Infinite scroll ek baar me 20 posts load karta hai, images tabhi load hoti hain jab viewport me aayein. Initial page load 5s se 500ms par aa jaata hai.

Technique 6 — Kafka for Async

Technique 7 — Connection Pooling

Technique 8 — Denormalization

11. Common Interview Questions

Lesson ke 10 detailed interview Q&A — ye wahi sawaal hain jo interviewer sabse zyada poochhta hai. Har jawaab me numbers aur trade-offs hain; inhe ratna mat, samajh kar bolo. (Aur 36 short FAQs alag tab me hain.)

Q1 — Normal users ke liye fanout on write kyun, fanout on read kyun nahi?

Read-heavy optimization hai: social media ka read/write ratio 100:1 hai. Users feed 100x zyada padhte hain, post 1x karte hain. Fanout on write se: (1) Fast reads — feed pehle se Redis me bani hui, LRANGE 20 posts <10ms me deta hai. (2) Predictable latency — post creation me 500 followers tak fanout karne me 200ms lagte hain, lekin har feed load <50ms me hota hai. (3) Behtar UX — user ko feed generation ka wait nahi karna padta, instant scroll. Trade-off: write amplification (1 post = 500 writes) vs slow reads (100 users ke posts query karo, sort karo, merge karo = 500ms). Celebrities (10M followers) ke liye fanout on write impractical hai (1 post = 10M writes, minutes lagenge) — isliye pull model use hota hai, fans celebrity ke posts on-demand query karte hain.

Q2 — Feed generation me celebrity / hotspot problem kaise handle karoge?

Multi-tier approach: (1) User classification — User table me celebrity flag (>5K followers). (2) Hybrid fanout — <5K ke liye push (precompute feeds), >5K ke liye pull (on-demand fetch). (3) Feed merging — feed load karte waqt pushed posts (normal users) + pulled posts (celebrities) combine karo, timestamp se sort karo. (4) Caching — celebrity posts Redis me alag se cache karo, higher TTL (1 hour vs 10 min), saare followers same cache share karte hain. (5) Pagination — celebrity timelines paginated, followers ko latest 100 posts max dikhte hain. Example: user 90 normal users (pushed) + 10 celebrities (pulled) follow karta hai. Feed Service: LRANGE feed:{user_id} pushed ke liye, PostDB se celebrity posts, merge aur rank karo. Performance: combined latency 100ms (50ms pushed + 50ms pulled), pure pull 500ms leta.

Q3 — Cache aur database ke beech like counts consistent kaise rakho?

Eventual consistency with reconciliation: (1) Write path — user like kare to Like DB (Cassandra) me likho, Redis counter INCR likes_count:{post_id} karo. (2) Background sync — cron job har 5 minute me Like DB se actual count nikale (SELECT COUNT(*) GROUP BY post_id), PostDB ko authoritative count se update kare. (3) Cache invalidation — Redis count DB se >10% alag ho to cache invalidate karo, DB se reload karo. (4) Conflict resolution — DB source of truth hai, Redis best-effort cache hai. Edge cases: Redis key evict ho jaaye (memory pressure) to agla read DB se fetch karega, phir dobara cache hoga. Redis crash ho to saare counters lost — background job 5 minute me DB se rebuild kar dega. Accept window: counters ±5% tak galat ho sakte hain <5 minute ke liye — social media ke liye acceptable hai (financial system nahi hai). Alternative: Redis persistence (AOF + RDB) durability ke liye, lekin write latency 10ms se 50ms ho jaati hai.

Q4 — 1M followers wala user post kare to system overload kaise roko?

Rate limiting + async processing: (1) Classification — followers_count > 5K ho to user_id 'celebrity' tag karo, User table me store karo. (2) Bypass fanout — celebrity posts push fanout skip karke sirf PostDB me store hote hain. (3) Pull model — follower feed load kare tab celebrity ke recent posts (last 100) PostDB se query karo, normal pushed posts ke saath merge karo. (4) Async notification — 1M push notifications ki jagah notification aggregator ko bhejo, 'trending' notifications me batch karo. (5) Rate limiting — celebrity ko 10 posts/hour tak limit karo spam rokne ke liye. Implementation: Feed Service check karta hai poster.followers_count > 5K hai ya nahi — haan to sirf PostDB me likho, Kafka par 'celebrity.posted' event publish karo, fanout worker skip karo. Followers ko post tab dikhega jab wo feed load karenge (pull), unki feed me push nahi hoga. Notification Service 1000 sabse engaged followers ko turant bhejta hai, baaki ko aggregated daily digest milta hai. Isse bachta hai: 1M database writes, 1M Redis writes, 1M push notifications.

Q5 — Nested comment threads efficiently kaise handle karoge?

Hierarchical storage with lazy loading: (1) Database schema — Comment table me parent_comment_id (NULL = top-level, UUID = reply), tree structure banta hai. (2) Loading strategy — pehle top-level comments lao (WHERE parent_comment_id IS NULL LIMIT 20), replies tabhi lao jab user thread expand kare (WHERE parent_comment_id = {comment_id}). (3) Depth limit — max 3 levels (post → comment → reply, usse aage nesting nahi) — UI complexity rokne ke liye. (4) Denormalization — har comment me reply_count store karo, 'Show 5 replies' link bina counting ke dikh jaata hai. (5) Sorting — top-level likes_count DESC (best pehle), replies created_at ASC (chronological). Query optimization: composite index (post_id, parent_comment_id, created_at) se fast queries. Alternative: nested set model ya closure table complex hierarchies ke liye, lekin write complexity badh jaati hai. Example: post par 10K comments hain — pehle top 20 lao, user comment #5 expand kare to uske replies LIMIT 10 se lao, 'Show more' se pagination.

Q6 — Polling ke bina real-time notifications kaise implement karoge?

WebSocket + pub/sub pattern: (1) Connection — client app launch par Notification Service se WebSocket kholta hai, JWT se authenticated. (2) Subscription — server Redis pub/sub channel notifications:{user_id} ko subscribe karta hai. (3) Event flow — user A user B ki post like kare to Engagement Service Redis channel notifications:{user_B_id} par publish karta hai. (4) Push — us channel ko sunne wala Notification Service event le kar WebSocket se user B ke client ko JSON bhejta hai. (5) Fallback — client offline ho to notification Notification DB me store karo, reconnect par deliver karo. Scalability: 1M concurrent WebSocket connections = 1000 servers (1K connections each), Redis pub/sub 100K messages/sec handle karta hai, consistent hashing se user_id par load balance hota hai. Alternative: Server-Sent Events (SSE) one-way streaming ke liye (simpler), ya long polling (purane browsers ke liye fallback). Battery optimization: mobile apps persistent WebSocket ki jagah FCM/APNS push notifications use karte hain, WebSocket sirf active in-app users ke liye.

Q7 — Media upload failures aur retries kaise handle karoge?

Multi-stage upload with resumability: (1) Presigned URL — client POST /api/v1/posts/upload/init maangta hai, server presigned S3 PUT URL deta hai (15 minute valid), {upload_id, presigned_url} return karta hai. (2) Chunked upload — bade files (>100MB) multipart upload se, 5MB chunks me, parallel (10 concurrent). (3) Progress tracking — har chunk ka progress Redis me: upload:{upload_id} = {chunks_uploaded: [1,2,3], total_chunks: 20}. (4) Retry — failure par client GET /api/v1/posts/upload/{upload_id}/status se missing chunks poochhta hai, sirf missing parts dobara upload karta hai. (5) Finalize — saare chunks ke baad client POST /api/v1/posts/upload/{upload_id}/complete karta hai, server chunks ko S3 me assemble karke post banata hai. Timeouts: presigned URL 15 minute me expire, upload_id 24 ghante me (Redis TTL). Network resilience: exponential backoff (1s, 2s, 4s), 3 consecutive failures ke baad circuit breaker. Alternative: AWS SDK se direct S3 multipart upload, lekin progress tracking ka control kho jaata hai.

Q8 — Posts ke liye database partitioning strategy kya hai?

Multi-dimensional sharding: (1) Primary partitioning — Cassandra user_id se partition karti hai (partition key), hash(user_id) se posts cluster me distribute hote hain, har node ~1000 users handle karta hai. (2) Clustering — partition ke andar (created_at DESC, post_id) se sort hota hai, time-range queries fast hoti hain. (3) Global access — alag PostDB_indexed table, post_id primary key, direct post lookup (GET /posts/{post_id}) ke liye. (4) Replication — RF=3 high availability ke liye, QUORUM consistency reads/writes ke liye. Query patterns: user timeline (SELECT * FROM posts WHERE user_id = {id} LIMIT 20) single partition hit karta hai = fast. Feed generation (WHERE user_id IN (100 followees)) 100 partitions par fan-out karta hai = slow, isliye fanout on write se mitigate hota hai. Hotspots: celebrity users ki partition par load zyada hota hai — pull model se mitigate hota hai (followers celebrity partition ko query karte hain, follower feeds me write nahi hota). Scaling: nodes add karne par partitions 1000 se 2000 hote hain, Cassandra consistent hashing se automatically rebalance karta hai.

Q9 — User multiple baar click kare to duplicate likes kaise roko?

Multi-layer idempotency: (1) Client-side — like button 300ms debounce, click karte hi button disable (optimistic UI). (2) API level — Redis cache like:{user_id}:{post_id} check karo, exist kare to 200 OK return karo (already liked). (3) Database level — Cassandra composite primary key (post_id, user_id) uniqueness enforce karta hai, duplicate insert silently fail hota hai. (4) Transaction — Redis me atomic check-and-set: SETNX like:{user_id}:{post_id} success ho to DB me likho + counter INCR karo, fail ho to already liked. (5) Race condition — 2 parallel requests dono Redis check pass kar lein to bhi Cassandra constraint duplicate rokta hai, ek succeed hoti hai, dusri ko 409 Conflict milta hai. Implementation: POST /api/v1/posts/{post_id}/like Redis check karta hai, nahi mila to transaction start, Like DB me likho, Redis key set karo (TTL = 24h), counter increment karo, commit karo. Counters: INCR increment ke liye, DECR unlike ke liye, background job har 5 minute me DB se actual count sync karke drift fix karta hai. Edge case: Redis eviction se idempotency cache kho jaaye to user dobara like kar sakta hai — DB constraint duplicate row rokta hai, counter sahi increment hota hai.

Q10 — Privacy controls (public vs friends-only posts) kaise implement karoge?

Multi-layer visibility filtering: (1) Storage — Post table me visibility enum (public, friends, private). (2) Feed generation — fanout on write ke waqt poster aur follower ka relationship check karo, sirf tabhi push karo jab: visibility = public, ya (visibility = friends AND mutual follower hai). (3) Direct access — GET /posts/{post_id} check karta hai: public ho to allow, friends ho to verify karo requester poster ki friends list me hai, private ho to sirf author dekh sakta hai. (4) Feed filtering — pull model queries: SELECT * FROM posts WHERE user_id IN (followees) AND (visibility = 'public' OR (visibility = 'friends' AND mutual = true)). (5) Caching — privacy checks Redis me cached: friend:{user_A}:{user_B} = boolean (TTL = 1 hour). Friend determination: mutual follow check — Followers table me bidirectional edge (A follows B AND B follows A). Performance: privacy checks 10ms latency add karte hain, batch checking se mitigate hota hai (100 posts ek hi Redis MGET se verify karo). Alternative: fine-grained lists (close friends, acquaintances, custom lists), graph database me relationship tags ke roop me store karo.

FAQs — Interview Questions
Interview ki taiyaari ke 36 sawaal-jawaab — lesson ke concepts aur unse jude current-era topics. Har jawaab me numbers aur trade-offs hain. Kisi bhi sawaal par click karo, jawaab khul jaayega.
Q01Fanout on write kya hota hai, aur social media me ye kyun use hota hai?
Fanout on write matlab — user post karte hi us post ko uske saare followers ki feeds me pehle se daal do (Redis me LPUSH). Social media ka read/write ratio 100:1 hai, isliye ek baar slow write karke 100x fast reads milte hain. Feed load karna matlab sirf LRANGE chalana, koi heavy query nahi. Normal users (<5K followers) ke liye yehi best hai; celebrities ke liye pull model use hota hai.
Q02Fanout on read (pull model) kab use karna chahiye?
Jab poster ke followers bahut zyada hon — 5K se upar. Celebrity ka 1 post 10M followers ki feeds me push karna matlab 10M writes, jo minutes lega aur system ko overwhelm kar dega. Pull model me post sirf PostDB me likha jaata hai, aur follower feed load karte waqt celebrity ke recent posts on-demand fetch karta hai. Isse write amplification bilkul khatam ho jaata hai.
Q03Hybrid fanout model kya hai?
Teen tiers: chhote users (<5K followers) push, celebrities (>5K) pull, aur medium users (1K–5K) hybrid — active followers ko push, inactive ko pull. User table me celebrity flag hota hai, Feed Service fanout se pehle check karta hai. Isse 99% users efficiently handle ho jaate hain aur celebrity problem bhi solve hota hai.
Q04Feed ke liye Redis kyun use karte hain, database kyun nahi?
Chaar wajah: (1) Speed — Redis LRANGE <10ms me deta hai, DB query 100ms+ leti hai. (2) Scalability — Redis 100K ops/sec handle karta hai. (3) Feed ephemeral data hai — kho jaaye to DB se dobara bana sakte hain. (4) DB load 90% kam ho jaata hai. Feed precomputed list hoti hai — `feed:{user_id}` me latest 1000 post_ids, isliye load karna ek hi Redis command hai.
Q05Posts ke liye Cassandra kyun, PostgreSQL kyun nahi?
Posts write-heavy hain — 100M posts roz, 1.2K/sec average. Cassandra partition key `user_id` se posts distribute karta hai aur clustering key `created_at DESC` se user ki timeline ek hi partition se nikal jaati hai. PostgreSQL me itne writes par single primary bottleneck ban jaata. User profiles PostgreSQL me rehte hain kyunki wahan strong consistency aur unique username chahiye — alag data, alag database.
Q06Social graph ke liye Graph database kab use karte hain?
Jab relationships hi main query hon — 'mere dost ke dost kaun hain', 'mutual friends kaun hain', 'shortest path kya hai'. Graph DB me edges first-class citizens hote hain, traversal fast hota hai. Simple follow/unfollow aur follower list ke liye PostgreSQL (follower_id, followee_id) kaafi hai. Lesson me dono options diye hain — Follower DB Graph DB ya PostgreSQL.
Q07Kafka is design me kahan-kahan use hota hai?
Teen jagah: (1) `post.created` topic — post bante hi Feed Service ko fanout ke liye event milta hai. (2) `post.liked` / `post.commented` / `user.followed` — Notification Service ko events milte hain. (3) Async indexing — Post Consumer Service naye posts ko Elasticsearch me index karta hai. Kafka write ko propagation se decouple karta hai — post turant publish hota hai, baaki kaam background me hota hai.
Q08CDN media delivery me kaise kaam karta hai?
Client media maangta hai to CloudFront edge location check karta hai. Cache hit ho to <50ms me mil jaata hai — 95% requests aisi hi hoti hain. Cache miss par S3 origin se fetch karke cache karta hai (images TTL 30 din, videos 7 din). Device ke hisaab se optimized image milti hai — mobile ko 400x400, desktop ko 1080x1080 (Lambda@Edge se). Videos HLS format me adaptive bitrate se stream hote hain.
Q09Like idempotent kaise banate hain — user 3 baar click kare to 1 hi like kyun gina jaaye?
Teen layers: (1) Client-side — button 300ms debounce, click karte hi disable (optimistic UI). (2) API level — Redis key `like:{user_id}:{post_id}` check karo, exist kare to 200 OK return karo. (3) Database level — Cassandra composite primary key `(post_id, user_id)` duplicate row banne hi nahi deta. Race condition me bhi dono parallel requests me se ek succeed hoti hai, dusri ko 409 Conflict milta hai. Redis me atomic SETNX use hota hai.
Q10Nested comments efficiently kaise load karte hain?
Comment table me `parent_comment_id` hota hai — NULL matlab top-level, UUID matlab kisi comment ka reply. Pehle sirf top-level comments laate hain (`WHERE parent_comment_id IS NULL LIMIT 20`), replies tabhi load hote hain jab user thread expand kare. Depth max 3 levels tak. Har comment me `reply_count` denormalized hota hai, isliye 'Show 5 replies' bina counting ke dikh jaata hai. Composite index `(post_id, parent_comment_id, created_at)` queries fast banata hai.
Q11Search me Elasticsearch kyun, database LIKE query kyun nahi?
Database LIKE query full-table scan karti hai aur fuzzy matching, ranking, autocomplete nahi de sakti. Elasticsearch me content full-text index hota hai, username par autocomplete analyzer hota hai, hashtag keyword array hota hai, aur recency/popularity se boosting hoti hai. Naye posts Kafka se async index hote hain. Autocomplete <50ms latency deta hai, aur 10K searches/sec handle hote hain.
Q12Notification aggregation kya hai, aur kyun zaroori hai?
Ek post par 5 minute me 50 likes aayein to user ko 50 notifications bhejna spam hai. Isliye Notification Service aggregate karta hai — '[Name] aur 15 others ne tumhari post like ki' — ek hi notification. Aggregation window 5 minute ki hai. Isse notification volume bahut kam hota hai aur user experience behtar rehta hai.
Q13Media upload resumable kaise banate hain?
Presigned S3 URL (15 minute valid) + multipart upload. Bade files (>100MB) 5MB chunks me split hote hain, 10 concurrent upload hote hain. Har chunk ka progress Redis me track hota hai — `upload:{upload_id}`. Failure par client status API se missing chunks poochhta hai aur sirf wahi dobara upload karta hai. Saare chunks ke baad complete API call par server S3 me assemble karke post banata hai. Exponential backoff (1s, 2s, 4s) aur 3 failures ke baad circuit breaker.
Q14Rate limiting is system me kahan lagta hai?
API Gateway par — 1K requests/min per user. Post creation par — 100 posts/day per user (spam rokne ke liye). Follow par — 1000 follows/day (anti-spam). Celebrity par — 10 posts/hour. Rate limiting abuse aur accidental overload dono rokta hai, aur fanout amplification ko bhi control me rakhta hai.
Q15Posts ki sharding strategy kya hai?
Cassandra me partition key `user_id` hai — hash(user_id) se posts cluster me distribute hote hain, 1000 shards, har shard ~1M users. Partition ke andar clustering `(created_at DESC, post_id)` se time-range queries fast hoti hain. Global lookup ke liye alag PostDB_indexed table hai jisme `post_id` primary key hai. Replication factor RF=3 hai, QUORUM consistency use hoti hai.
Q16Cassandra me hot partition problem kya hai, aur iska solution kya hai?
Celebrity user ki partition par load bahut zyada hota hai — 1M followers usi partition ko query karte hain. Solution teen hain: (1) Pull model — load follower reads par distribute karo, write-heavy fanout par nahi. (2) Celebrity posts Redis me cache karo. (3) Hot partitions ke liye read replicas add karo. Nodes add karne par Cassandra consistent hashing se automatically rebalance karta hai.
Q17Eventual consistency social media me acceptable kyun hai, banking me kyun nahi?
Social media me like count 5 minute ke liye thoda galat ho to koi nuksaan nahi, feed me post 2 second late dikhe to chalega. Isliye CAP theorem me AP side chunte hain — availability aur low latency priority hai. Banking me paise ka hisaab galat nahi ho sakta, isliye wahan strong consistency chahiye hoti hai. Counters ka accept window ±5% hai, <5 minute ke liye.
Q18Denormalization kya hai, aur yahan kahan use hui hai?
Denormalization matlab counts ko pehle se store karke rakhna, har baar COUNT(*) query na chalana. Yahan `like_count`, `comment_count`, `followers_count`, `following_count`, `posts_count` Post/User tables me store hote hain. COUNT(*) 100ms+ leti hai, denormalized count 1ms me milta hai. Background jobs har 5 minute me counts ko Like/Comment DB se sync karte hain — eventual consistency accept karke speed lete hain.
Q19Feed ranking ka formula kya hai?
Composite score = recency_score × 0.4 + engagement_score × 0.4 + affinity_score × 0.2. Recency exponential decay se — <1 hour = 1.0, 1 din = 0.5, 7 din = 0.1. Engagement = likes × 0.3 + comments × 0.5. Affinity — close friends ka weight 2x. Plus feed ka 10% kam-followed users se inject hota hai taaki echo chamber na bane. Advanced systems XGBoost se engagement probability predict karte hain.
Q20Feed me diversity injection kyun karte hain?
Sirf high-engagement posts dikhoge to user ko hamesha wahi 10 log dikhenge — echo chamber ban jaata hai, naye creators kabhi discover nahi hote. Isliye feed ka 10% kam-followed users ka content inject karte hain. Isse discovery badhti hai aur long-tail creators ko bhi reach milti hai.
Q21Soft delete kya hai, aur posts ko hard delete kyun nahi karte?
Soft delete matlab post ko deleted mark kar do (`is_deleted = true`), lekin row database me rakho. Isse analytics, audit aur 'deleted post wapas lao' jaise flows possible rehte hain. Hard delete se data hamesha ke liye kho jaata hai aur references toot jaate hain. Media ko S3 lifecycle policy se baad me delete karte hain, CDN cache invalidate karke.
Q22JWT authentication is design me kaise kaam karta hai?
Login par server JWT token deta hai — `{user_id, username, exp}` — 7 din ki expiry ke saath. Har request me client Authorization header me token bhejta hai. API Gateway token verify karta hai, phir user_id services tak pahunchta hai. Password bcrypt se hash hota hai (cost factor 12), plain password kabhi store nahi hota.
Q23Presigned S3 URL kya hai, aur isse kya fayda hai?
Server ek temporary signed URL generate karta hai (15 minute valid) jisse client seedha S3 par upload kar sakta hai — file server se hokar nahi jaati. Isse server ka bandwidth aur load bachta hai, aur bade files (500MB tak) bhi fast upload hote hain. Upload ke baad S3 Lambda trigger karke thumbnails aur transcoding async karta hai.
Q24HLS streaming kya hai, aur video ke liye kyun use hota hai?
HLS (HTTP Live Streaming) video ko chhote segments me baant kar multiple bitrates (360p, 720p, 1080p) me serve karta hai, ek m3u8 manifest ke saath. Player network speed dekh kar bitrate switch karta hai — slow network par 360p, fast par 1080p. Isse buffering kam hota hai aur har device par smooth playback milta hai.
Q25Real-time notifications ke liye WebSocket kyun, polling kyun nahi?
Polling me client har kuch second me server se poochhta hai 'kuch naya hai?' — zyadatar baar jawaab 'nahi' hota, phir bhi request aur battery waste hoti hai. WebSocket ek baar connection khol kar persistent rakhta hai, server event aate hi push kar deta hai. 1M concurrent connections 1000 servers par handle hote hain. Fallback ke liye SSE ya long polling use hota hai, aur mobile par FCM/APNS push notifications.
Q26Follow karte hi naye follower ki feed me purane posts kaise aate hain?
Backfill job se — follow karte hi followee ke last 100 recent posts follower ki Redis feed me daal diye jaate hain. Isse naye follower ko khaali feed nahi dikhti, turant content mil jaata hai. Unfollow par LREM se followee ke posts feed se purge kar diye jaate hain.
Q27Cache stampede kya hai, aur feed cache me isse kaise bachte hain?
Cache stampede matlab — popular key expire hote hi hazaaron requests ek saath DB par toot padti hain. Feed cache me isse bachte hain: TTL staggered rakh kar, cache warming se (pehle se refresh kar do), aur celebrity posts ko shared cache me rakh kar — saare followers ek hi cached copy use karte hain, har follower ke liye alag query nahi hoti.
Q28Feed cache ka TTL 10 minute kyun hai, zyada kyun nahi?
Feed fresh content hai — 10 minute purani feed acceptable hai, lekin 1 ghante purani feed me user ko naye posts nahi dikhenge. 10 minute ka TTL freshness aur DB load ka balance hai. Profile cache 1 ghante ka hai kyunki profile kam badalti hai, like counts 5 minute ke hain kyunki wo baar-baar badalte hain.
Q29PostDB_indexed table alag se kyun chahiye?
Cassandra me posts `user_id` partition key se store hote hain — user ki timeline fast nikalti hai. Lekin `GET /posts/{post_id}` jaise direct lookup ke liye user_id pata nahi hota, isliye alag table chahiye jisme `post_id` primary key ho. Ye secondary index pattern hai — ek hi data do tarike se organize karo, alag-alag query patterns ke liye.
Q30Reaction types (like, love, haha) kaise store karte hain?
Likes table me `reaction_type` field hota hai — text: like, love, haha, wow, sad, angry. Primary key `(post_id, user_id)` composite hai, isliye ek user ek post par ek hi reaction de sakta hai. Reaction badalne par wahi row update hoti hai, nayi row nahi banti. Counts per reaction type background job se aggregate hote hain.
Q31Privacy filtering feed generation me kaise hoti hai?
Teen layers: (1) Storage — Post table me `visibility` enum (public, friends, private). (2) Fanout ke waqt — friends-only post sirf mutual followers ki feeds me push hota hai. (3) Direct access — `GET /posts/{post_id}` par check hota hai: public ho to allow, friends ho to friends list verify karo, private ho to sirf author. Privacy checks Redis me cached hote hain (`friend:{A}:{B}`, TTL 1 hour) aur batch MGET se 100 posts ek saath verify hote hain.
Q32Mentions (@user) kaise handle karte hain?
Post create karte waqt content se mentions extract hote hain (`mentions: set<uuid>` field me store hote hain). Mention kiye gaye users ko notification jaati hai — 'tumhe ek post me mention kiya gaya'. Post Composer me @ type karte hi autocomplete suggestions aate hain, aur mentioned users ke profiles link ho jaate hain.
Q33Is design ki cost optimization kya-kya hai?
Paanch badi bachat: (1) CDN 95% cache hit — 95% kam S3 reads, $10K/month bachat. (2) Redis caching — 90% kam DB queries, 10x kam DB instances. (3) Denormalization — COUNT(*) se bachat (100ms → 1ms). (4) Batch updates — like counts batch karne se 100x kam DB writes. (5) S3 lifecycle — 1 saal purana media Glacier me, 90% storage cost kam.
Q3499.99% uptime ka matlab kya hota hai?
Saale me sirf 52 minute downtime allowed hai. Iske liye chahiye: database replication (RF=3), read replicas, multi-AZ deployment, aur async processing taaki ek service down ho to bhi post creation na ruke. 99.99% ka matlab hai har component ka failure plan pehle se tayyar ho.
Q35100:1 read/write ratio design decisions ko kaise affect karta hai?
Har decision reads ke favour me jaata hai: fanout on write (slow write, fast reads), Redis feed cache, CDN, read replicas, denormalized counts, lazy loading. Writes ke liye async aur batching acceptable hai kyunki writes kam hote hain. Agar ratio ulta hota (write-heavy) to design bilkul alag hota — write-optimized stores aur kam denormalization.
Q36S3 ki 11 9's durability ka matlab kya hai?
99.999999999% durability — matlab 10,000 objects me se 1 object bhi 10,000 saal me khone ki probability bahut kam hai. S3 data ko multiple facilities aur devices par replicate karta hai. Isliye media ke liye S3 best hai — database me BLOB store karne se na durability milti hai, na CDN support, na itni sasti storage ($0.023/GB/month).
