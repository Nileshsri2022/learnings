01Overview

Cloud Storage kya hai — Overview

Google Drive ya Dropbox jaisi service ek distributed storage system hai — tumhari files ek hi machine par nahi, hazaron servers par chunks me banti hui, kai copies ke saath store hoti hain. Tumhe sirf ek folder dikhta hai; peeche upload, chunking, hashing, versioning aur sync ka poora pipeline chalta hai.

▶ Poora lesson video me hai

Is lesson ka source text bahut chhota hai (lagbhag 387 words) — gehri samajh video se milegi. Video zaroor dekho: System Design 18: Design Cloud Storage Platform | Google Drive | Dropbox | HLD | LLD (lagbhag 18 minute).

▶ YouTube par video dekho
One-liner — yaad karne ke liye: Initiate upload → chunk & hash → pre-signed URLs → parallel chunk upload → commit → metadata versioning → sync events to other devices (eventual).

Interview me jab bhi "Google Drive design karo" poochha jaye, yahi one-liner tumhara skeleton hai. Har step ke peeche ek reason hai: chunking bade files ko chhote tukdon me todta hai taaki parallel upload aur resume possible ho; hash har chunk ki pehchan hai — dedup aur integrity check dono isi se hote hain; pre-signed URLs client ko seedha blob store se baat karne dete hain, bina server ko beech me laaye; commit woh point hai jahan file "officially" exist karti hai; versioning har commit ko ek naya version banata hai; aur sync events baaki devices ko batate hain ki kuch badla hai.

Is lesson me kya-kya hai

  • Functional requirements — system ko kya-kya karna chahiye (upload, share, versions, sync).
  • Non-functional requirements — scale, durability aur consistency ke vaade.
  • Core entities — User, Folder, File, FileVersion, Chunk, FileVersionChunk — metadata ka schema.
  • Upload flow — resumable upload, step by step, diagram ke saath.
  • Deep dive: deduplication & validation — chunk-level dedup, metadata hi source of truth.
  • Deep dive: sync engine — watcher, delta, push/pull, conflicts.
Yaad rakhne wali baat: Cloud storage ka sabse bada design decision yeh hai ki blob store (actual file data) aur metadata DB (file ka naam, folder, version, chunk map) alag-alag hote hain — aur metadata hi source of truth hai, blob store nahi.

02Requirements

1. Functional Requirements

Functional requirements batate hain ki system kya karega — user ko kaun-kaun si cheezein dikhengi aur kaam karengi. Lesson ke 5 points:

  • Upload/download files (large files supported) aur folders banao — sirf chhoti files nahi; GBs ki files bhi upload/download honi chahiye. Isiliye chunking zaroori hai — poori 5 GB file ek request me bhejna practical nahi.
  • Resumable uploads (resume after disconnect) — internet toot jaye ya laptop band ho jaye, to upload phir se zero se shuru na ho. Jo chunks pehle se upload ho chuke hain, server unhe yaad rakhta hai (existingChunks) aur client wahin se aage badhta hai.
  • Share files/folders with permissions — kisi ko sirf dekhne ka haq (viewer), kisi ko edit ka (editor), kisi ko owner ka. Sharing metadata me permission entries ke roop me store hoti hai.
  • Version history (restore older versions) — file overwrite karne par purana content khatm nahi hota; har commit ek naya FileVersion banata hai, aur purana version restore kiya ja sakta hai.
  • Cross-device sync (push/pull updates) — laptop par file badlo to phone aur desktop par bhi update aaye — push (server bhejta hai) ya pull (device poochhta hai) se.
Interview tip: Functional requirements bolte waqt sirf list mat ginao — har ek ke peeche ka design implication bhi bolo. Jaise "resumable upload chahiye" bolte hi interviewer samajhta hai ki tumhe chunking + server-side chunk tracking chahiye.

Har requirement ka design matlab

RequirementDesign implication
Large file uploadChunking + parallel upload + pre-signed URLs
Resumable uploadChunk-level tracking (existingChunks), commit step
Sharing + permissionsMetadata me ACL/permission entries, access check har request par
Version historyFileVersion table, har commit = naya version
Cross-device syncChange events (Kafka), client watcher, delta upload

03Requirements

2. Non-Functional Requirements

Non-functional requirements batate hain ki system kaisa behave karega — kitna bada, kitna reliable, aur kitna consistent. Lesson inhe do groups me baant-ta hai: Scale & Durability, aur Consistency.

Scale & Durability

  • Scale: Billions of files; large total storage; multi-region — users karodon me, files arabon me, total data petabytes me. Ek region kaafi nahi — data kai regions me faila hota hai taaki latency kam ho aur ek region down ho to bhi service chale.
  • Durability: No data loss for stored blobs (multi-AZ/replication) — user ki file kabhi kho nahi sakti. Har blob ki kai copies banti hain — alag availability zones (multi-AZ) ya alag regions me. Ek disk ya ek data center kharab ho jaye, tab bhi data safe rahe.
Durability vs availability: Durability ka matlab hai data kabhi lost nahi hoga (11 nines jaisa vaada — 99.999999999%). Availability ka matlab hai service hamesha up rahegi. Dono ke liye replication chahiye, lekin durability ke liye copies ka alag-alag failure domains me hona zaroori hai.

Consistency

  • Metadata: Strong consistency for file/folder metadata operations — file ka naam badla, folder move kiya, share kiya — ye operations sabko ek hi order me, ek hi result ke saath dikhni chahiye. Do devices ek hi file ko alag naam na de payen. Isiliye metadata DB strong consistency deta hai.
  • Sync: Eventual consistency is acceptable for cross-device synchronization — laptop par file badli, phone par update aane me kuch second lag sakte hain — ye acceptable hai. Sync eventual ho sakta hai, lekin metadata strong hona chahiye.
Interview me yahi farq poochha jata hai: "Metadata strong kyun, sync eventual kyun?" — Kyunki metadata operations (rename, move, share) conflict-sensitive hain aur user ko turant sahi state dikhani hoti hai; sync ek background propagation hai jahan thodi deri chalti hai. Dono ko ek jaisa strong banana system ko slow aur mehenga bana dega.

04Data Model

3. Core Entities

Ye 6 entities metadata ka schema hain — poora system inhi ke aas-paas ghumta hai. Blob (actual file data) alag store hota hai; ye tables sirf metadata hain.

EntityFieldsKaam
Useruser_id, naam, quotaKaun hai, kitni storage use kar sakta hai
Folderfolder_id, parent_folder_id, owner_id, nameTree structure — har folder ka parent hota hai (root ka parent null)
Filefile_id, parent_folder_id, owner_id, name, size_bytes, current_version_idFile ka "current" pointer — hamesha latest version ki taraf ishara karta hai
FileVersionversion_id, file_id, created_at, created_by, size_bytesHar upload/commit ek naya version; purane versions restore ke liye safe rehte hain
Chunkchunk_id, object_key, size_bytes, checksumFile ka ek tukda; object_key batata hai blob store me kahan pada hai; checksum uski pehchan + integrity hai
FileVersionChunkversion_id, chunk_index, chunk_idMapping table — kaun sa version kin chunks se bana hai, kis order me (chunk_index)
Ye design kyun achha hai: File aur FileVersion alag hain, isiliye version history free me milti hai — naya version sirf nayi row hai, purani rows delete nahi hoti. Aur FileVersionChunk mapping ki wajah se do versions same chunk share kar sakte hain — yahi chunk-level dedup ki neev hai. File me ek chhota sa change hua to sirf badle hue chunks naye bante hain, baaki reuse hote hain.

Ek file download kaise hoti hai (entities se samjho)

  1. File se current_version_id nikalo.
  2. FileVersionChunk se us version ke saare chunks chunk_index order me nikalo.
  3. Har Chunk ka object_key lo aur blob store se chunk lao (ya pre-signed URL do).
  4. Chunks ko order me jod do — file taiyar. Har chunk ka checksum verify karo taaki corrupt data pakda jaye.

05Upload Flow

4. Upload Flow (resumable, matches diagram)

Upload ka flow 5 steps me hota hai — aur har step ka ek clear kaam hai. Ye flow design diagram se match karta hai.

  1. Initiate: client /files/upload/init call karta hai — fileName, fileSize, parentFolderId ke saath. Server ek upload session banata hai aur upload ID deta hai.
  2. Chunk & hash (client side): client file ko locally chunks me todta hai aur har chunk ka checksum nikalta hai (jaise SHA-256). Chunking client par hoti hai — server par nahi — taaki server ka load kam ho aur parallel upload possible ho.
  3. Signed URL: client chunk N ke liye signed URL maangta hai. Service check karti hai ki chunk pehle se upload hua hai ya nahi — agar haan, to dobara upload karne ki zaroorat nahi (yehi dedup ka pehla fayda hai) — aur URL return karti hai.
  4. Parallel upload + resume: client chunks ko parallel upload karta hai. Beech me connection toot jaye to reconnect par server existingChunks batata hai — client sirf baaki chunks bhejta hai, shuru se nahi.
  5. Commit: /files/upload/commit metadata + version + chunk map persist karta hai aur Kafka par sync event emit karta hai, taaki baaki devices ko pata chale.
Commit kyun alag step hai? Chunks upload hona aur file ka "exist karna" do alag cheezein hain. Jab tak commit nahi hota, file metadata me nahi aati — aadhe upload hue chunks dikhai nahi dete. Commit ek atomic point hai: ya to poori file dikhegi, ya bilkul nahi. Yehi strong consistency ka hissa hai.

Pre-signed URLs kyun?

Client seedha blob store (jaise S3) se baat karta hai — upload service beech me data pass nahi karti. Isse do fayde: (1) server ka bandwidth aur CPU bachta hai — GBs ka data server se nahi guzarta; (2) upload parallel aur fast hota hai. URL time-limited aur sirf us chunk ke liye valid hota hai, isiliye secure bhi hai.

06Deep Dive

5. Deep Dive: Deduplication & Validation

Dedup aur validation woh cheezein hain jo cloud storage ko sirf "file rakhne ki jagah" se zyada banati hain — storage bachta hai aur data bharosemand rehta hai.

  • Dedup chunk-level hota hai, content hash se: do files me same chunk ho (jaise ek hi video do users ne upload kiya, ya ek file ke do versions me zyada hissa same ho) to chunk ek hi baar store hota hai. Hash same = content same. Identical chunks files aur versions ke across reuse hote hain.
  • Blob store source of truth NAHI hai; metadata DB + version mapping authoritative hai: blob store me sirf chunks pade hain — unka koi matlab nahi jab tak metadata na bataye ki kaun sa chunk kis file ke kis version ka hissa hai. File ka "sach" metadata me hai. Blob delete ho jaye to metadata se pata chalega kya khoya; metadata kho jaye to blobs bekaar ho jayenge.
  • Validations: checksum verification (chunk ka hash match karo), size validation (file size wahi hai jo initiate me bataya tha), malware scan (async — upload rokta nahi, baad me scan hota hai), aur quota checks (user ki storage limit cross to nahi ho rahi).
File-level vs chunk-level dedup: File-level dedup sirf tab kaam karta hai jab poori file bilkul same ho. Chunk-level dedup tab bhi kaam karta hai jab file me sirf ek para badla ho — baaki chunks reuse hote hain. Isiliye Google Drive jaisi services chunk-level dedup karti hain. Trade-off: chunk chhota ho to dedup zyada, lekin metadata zyada; chunk bada ho to metadata kam, dedup kam.

Validation kab hoti hai?

ValidationKabKyun
ChecksumChunk upload parCorrupt ya aadha chunk pakdo
SizeCommit parFile poori aayi ya nahi, confirm karo
Malware scanAsync, commit ke baadUpload fast rakho; infected file baad me quarantine karo
QuotaInitiate aur commit parLimit cross karne wale upload ko pehle hi roko

07Deep Dive

6. Deep Dive: Sync Engine

Sync engine woh hissa hai jo Google Drive ko "folder" se zyada banata hai — ek device par badlav, sab devices par pahunchta hai.

  • Client watcher / local index: har device par ek watcher chalta hai jo local filesystem me changes detect karta hai — nayi file, edit, delete, rename. Local index batata hai kya badla hai, aur sirf delta (badla hua hissa) upload hota hai, poori file nahi.
  • Server change events — push ya pull: server har change ka event publish karta hai. Baaki devices ko ya to push se milta hai (server fanout karta hai — event sab connected devices ko bhejta hai) ya pull se (device time-time par server se poochhta hai "kuch naya hai?").
  • Conflicts — versioning + merge rules: do devices ne ek hi file ko offline edit kar diya to conflict hota hai. Iska hal versioning + merge rules hain — app-specific. Binary files (jaise video, zip) ke liye aam taur par last-writer-wins hota hai: jo baad me likha, wahi current version banta hai; haara hua version history me safe rehta hai, delete nahi hota.
Delta sync kyun zaroori hai: 5 GB ki video me 10 MB ka hissa badla to poori 5 GB dobara upload karna bekaar hai. Chunking ki wajah se sirf badle hue chunks upload hote hain — baaki chunks ka hash same rehta hai, server unhe pehchan kar reuse kar leta hai. Yehi chunking + hashing + dedup ka combined fayda hai.

Push vs Pull — kab kaun sa?

Push (fanout)Pull (polling)
KaiseServer event aate hi devices ko bhejta haiDevice interval par server se poochhta hai
LatencyKam — turant updatePolling interval jitni deri
CostServer ko har device ka connection rakhna padta haiKhali polls waste hote hain
KabOnline devices, real-time feelOffline se wapas aaya device, ya simple clients
Interview me bolne wali line: "Sync eventual consistency hai — isiliye push/pull dono chalte hain. Metadata strong hai — isiliye conflict ka final faisla versioning se hota hai, aur last-writer-wins binary files ke liye standard hai. Text files ke liye merge possible hai, binary ke liye nahi — isiliye version history safety net hai."

FInterview prep

Interview FAQs — 36

Lesson ke apne content se aur cloud storage ke standard system-design knowledge se — current-era interview questions. Note: lesson ka source text chhota hai; ye FAQs usse aage jaakar interview prep poori karte hain, lesson ka content nahi badalte.

Q01Cloud storage system design karte waqt pehla step kya hota hai?

Functional aur non-functional requirements clear karo. Functional: upload/download, resumable upload, sharing, version history, cross-device sync. Non-functional: billions of files ka scale, no data loss (durability), metadata strong consistency, sync eventual consistency. Requirements ke bina design bhatak jata hai — interviewer sabse pehle yahi dekhna chahta hai.

Q02Badi file ko ek hi request me upload kyun nahi karte?

5 GB ki file ek request me bhejna slow aur fragile hai — connection toot jaye to sab kuch dobara bhejna padega, aur server ko poori file memory me rakhni padegi. Chunking se file chhote tukdon me banti hai, chunks parallel upload hote hain, aur resume possible hota hai. Isiliye har cloud storage chunk-based upload karta hai.

Q03Chunk size kaise choose karte hain? Chhota ya bada?

Trade-off hai. Chhota chunk (1 MB) matlab zyada chunks — dedup behtar, resume fine-grained, lekin metadata zyada aur zyada requests. Bada chunk (16 MB) matlab metadata kam, lekin dedup kam aur ek chunk fail ho to zyada data dobara bhejna padega. Aam taur par 4 MB ke aas-paas sweet spot mana jata hai; kuch systems variable-size chunking bhi karte hain.

Q04Har chunk ka hash (SHA-256) kyun nikala jata hai?

Hash chunk ki pehchan hai. Teen kaam karta hai: (1) dedup — same hash matlab same content, dobara store karne ki zaroorat nahi; (2) integrity — download ke baad hash match karo, corrupt chunk pakda jata hai; (3) resume — server hash se pehchan leta hai kaun se chunks pehle se upload ho chuke hain.

Q05Pre-signed URL kya hota hai aur upload me iska kya fayda hai?

Pre-signed URL ek time-limited URL hota hai jo client ko seedha blob store (jaise S3) me ek specific chunk upload karne ki permission deta hai — bina server ke beech me aaye. Fayda: server ka bandwidth aur CPU bachta hai, upload parallel aur fast hota hai, aur URL expire ho jata hai to misuse ka risk kam hota hai.

Q06Resumable upload kaise kaam karta hai?

Client upload shuru karne se pehle initiate call karta hai aur server ek upload session banata hai. Har chunk upload hone par server use mark karta hai. Connection toot jaye to client reconnect par server se existingChunks poochhta hai — jo chunks ho chuke hain, unhe skip karke sirf baaki bhejta hai. Aakhir me commit call se file officially ban jati hai.

Q07Commit step alag kyun hai? Chunks upload hote hi file kyun nahi dikhti?

Chunks upload hona aur file ka exist karna do alag cheezein hain. Jab tak commit nahi hota, metadata me file nahi banti — aadhi upload hui file kisi ko dikhai nahi deti. Commit atomic point hai: metadata + version + chunk map ek saath persist hote hain. Isse ya to poori file dikhegi, ya bilkul nahi — aadhi file kabhi nahi dikhegi.

Q08Chunk-level dedup, file-level dedup se behtar kyun hai?

File-level dedup sirf tab kaam karta hai jab poori file bilkul same ho. Chunk-level dedup tab bhi kaam karta hai jab file me sirf ek hissa badla ho — baaki chunks reuse hote hain. Do versions ke beech ya do users ki similar files me bahut chunks common hote hain, isiliye chunk-level dedup zyada storage bachata hai.

Q09Metadata DB source of truth kyun hai, blob store kyun nahi?

Blob store me sirf chunks pade hain — unka koi matlab nahi jab tak metadata na bataye ki kaun sa chunk kis file ke kis version ka hissa hai, kis order me. File ka naam, folder, permissions, version — sab metadata me hai. Blob kho jaye to metadata se pata chalega kya khoya; metadata kho jaye to blobs bekaar ho jayenge.

Q10Metadata ke liye strong consistency kyun chahiye?

Rename, move, share jaise operations conflict-sensitive hain. Agar do devices ek hi file ko alag naam de den, to system ko ek hi final state decide karni hoti hai aur sabko wahi dikhani hoti hai. Strong consistency se metadata operations ka ek clear order banta hai aur user ko turant sahi state dikhti hai.

Q11Sync ke liye eventual consistency kyun acceptable hai?

Sync background propagation hai — laptop par file badli, phone par update aane me kuch second lagna acceptable hai. Har sync ko strong banana system ko slow aur mehenga bana dega, aur offline devices ke saath to strong consistency possible hi nahi. Isiliye sync eventual, metadata strong — dono ki zaroorat alag hai.

Q12Durability kaise ensure hoti hai — data kabhi lost kyun nahi hota?

Har blob ki kai copies alag availability zones (multi-AZ) ya regions me store hoti hain. Ek disk ya ek data center kharab ho jaye, tab bhi copies bachi rehti hain. Iske upar erasure coding bhi use hota hai — data ko pieces me baant kar parity ke saath store karna, jisse kam storage me bhi high durability milti hai.

Q13Push sync aur pull sync me kya farq hai?

Push me server change event aate hi connected devices ko bhejta hai (fanout) — latency kam, real-time feel. Pull me device time-time par server se poochhta hai kuch naya hai — simple hai, lekin polling interval jitni deri aur khali polls waste hote hain. Aam taur par dono chalte hain: online devices ko push, offline se wapas aaye device ko pull.

Q14Delta sync kya hai aur ye kyun zaroori hai?

Delta sync matlab sirf badla hua hissa upload karna, poori file nahi. 5 GB ki video me 10 MB badla to sirf badle hue chunks upload hote hain — baaki chunks ka hash same rehta hai aur server unhe reuse kar leta hai. Isse bandwidth aur time dono bachte hain; chunking + hashing ke bina delta sync possible nahi.

Q15Do devices ne ek hi file offline edit ki to conflict kaise solve hota hai?

Versioning + merge rules se. Binary files (video, zip) ke liye aam taur par last-writer-wins hota hai — jo baad me likha, wahi current version banta hai, aur haara hua version history me safe rehta hai, delete nahi hota. Text documents me merge possible hai. Conflict ka faisla metadata/versioning se hota hai, blob se nahi.

Q16Version history kaise implement hoti hai?

Har commit ek naya FileVersion row banata hai — version_id, file_id, created_at, created_by, size_bytes. File table me current_version_id pointer hota hai jo latest version ki taraf ishara karta hai. Restore matlab pointer ko purane version par le jana — purana data delete nahi hota. FileVersionChunk mapping batati hai har version kin chunks se bana hai.

Q17Sharing aur permissions kaise kaam karte hain?

Sharing metadata me permission entries ke roop me store hoti hai — kaun user ya group, kis file/folder par, viewer hai ya editor. Har request par access check hota hai: user ke paas permission hai ya nahi. Pre-signed URLs bhi time-limited hote hain taaki share kiya gaya link hamesha ke liye kaam na kare.

Q18Badi file download karte waqt kya hota hai?

Client File se current_version_id nikalta hai, FileVersionChunk se chunks chunk_index order me nikalta hai, har chunk ka object_key lekar blob store se chunk lata hai (ya pre-signed URL se parallel download karta hai), aur chunks ko jod kar file banata hai. Har chunk ka checksum verify hota hai. Range requests se download bhi resume ho sakta hai.

Q19Malware scan upload ko slow kyun nahi karta?

Malware scan async hota hai — upload aur commit rukte nahi. File pehle upload ho jati hai, scan background me chalta hai, aur agar file infected nikle to use quarantine kar diya jata hai ya download block kar diya jata hai. User experience fast rehta hai aur security bhi milti hai.

Q20Quota check kab aur kyun hota hai?

Initiate aur commit dono par. Initiate par check hota hai ki file size quota ke andar hai ya nahi — limit cross karne wale upload ko pehle hi roka jata hai, taaki aadha upload karke pata na chale ki jagah nahi hai. Commit par dobara check hota hai kyunki beech me user ne aur files upload ki ho sakti hain.

Q21Client watcher kya karta hai?

Har device par ek watcher process chalta hai jo local filesystem me changes detect karta hai — nayi file, edit, delete, rename. Local index batata hai kya badla hai. Watcher sirf delta upload karta hai aur server ko change events bhejta hai, taaki baaki devices sync ho saken.

Q22Kafka ka role cloud storage me kya hai?

Kafka change events ka pipeline hai. Commit hone par upload service Kafka par sync event emit karti hai — 'file X ka naya version aaya'. Sync service ye events consume karke baaki devices ko push karti hai (fanout). Kafka se events reliable aur ordered milte hain, aur agar sync service down ho to events kho nahi jate.

Q23Erasure coding kya hai aur replication se kaise alag hai?

Replication me poori file ki kai copies banti hain — 3 copies matlab 3x storage. Erasure coding me data ko k pieces me baanta jata hai aur m parity pieces banaye jate hain — k+m pieces me se koi bhi k pieces mil jayen to data recover ho jata hai. Kam storage me same durability milti hai, lekin read thoda mehenga hota hai. Cold/archival data ke liye erasure coding aam hai.

Q24Hot aur cold storage me kya farq hai?

Hot storage wo data hai jo baar-baar access hota hai — fast disks (SSD), zyada mehenga, kam latency. Cold storage wo data hai jo kabhi-kabhi khulta hai — sasta, slow retrieval. Cloud storage systems access pattern dekh kar data ko hot se cold me move karte hain (tiering), jisse cost kam hoti hai.

Q25File rename ya move karna sasta operation kyun hai?

Rename/move sirf metadata operation hai — File ya Folder table me naam ya parent_folder_id badal jata hai. Blob store ke chunks ko chhoone ki zaroorat nahi padti, isiliye GBs ki file ka rename bhi instant hota hai. Yehi metadata aur blob ko alag rakhne ka fayda hai.

Q26Ek hi file do users ne upload ki to kya hota hai?

Chunk-level dedup ki wajah se identical chunks ek hi baar store hote hain. Dono users ki files alag metadata entries hain, lekin unke FileVersionChunk mapping same chunk_id ki taraf ishara karte hain. Storage bachta hai aur kisi user ko pata bhi nahi chalta ki chunk shared hai.

Q27Offline edit ke baad device online aaye to sync kaise hota hai?

Device pehle server se pull karta hai — kya naya hai, kaun se versions badle. Phir apne local changes (delta) upload karta hai. Agar dono taraf same file badli hai to conflict detection chalta hai aur versioning/merge rules apply hote hain. Watcher aur local index milkar batate hain kya upload karna hai.

Q28Metadata DB ke liye SQL ya NoSQL — kya choose karen?

Metadata strongly consistent aur relational hai — folders ka tree, file-version-chunk relations, permissions. Isiliye SQL (jaise MySQL/Postgres, sharded) aam choice hai. File ka blob alag object store (S3 jaisa) me jata hai. Kuch systems metadata ke liye distributed SQL bhi use karte hain taaki scale aur strong consistency dono milen.

Q29Folder tree ko DB me kaise store karte hain?

Har Folder row me parent_folder_id hota hai — ye adjacency list model hai. Root folder ka parent null hota hai. Path nikalne ke liye parent chain ko upar tak follow karte hain. Bade scale par path materialized bhi store kiya jata hai taaki har baar chain na chalni pade.

Q30Thumbnail ya preview kaise generate hote hain?

Upload/commit ke baad ek async worker file ko read karke thumbnail ya preview banata hai — image ka chhota version, video ka frame, document ka pehla page. Ye bhi blob store me chunk/object ki tarah store hota hai aur uska reference metadata me rehta hai. Upload flow ko ye slow nahi karta kyunki async hai.

Q31Delete karne par file turant kyun nahi mit-ti?

Delete pehle metadata me soft-delete hota hai — file trash me jati hai, chunks abhi bhi store me rehte hain. Kuch din baad garbage collection un chunks ko delete karta hai jo kisi version se linked nahi hain. Isse accidental delete se recovery possible hoti hai aur dedup ke shared chunks galti se delete nahi hote.

Q32Download ke liye pre-signed URL upload jaisa hi kaam karta hai?

Haan, concept same hai — time-limited URL jo client ko seedha blob store se chunk download karne deta hai, bina application server ke beech me aaye. Download bhi parallel ho sakta hai: har chunk ki alag URL, sab ek saath download, phir jod do. Range request se download resume bhi ho sakta hai.

Q33Scale billions of files tak kaise karte hain?

Teen cheezein: (1) metadata sharding — files ko user_id ya file_id ke hisab se alag DB shards me baanto; (2) blob store ka horizontal scale — object store petabytes tak scale karta hai; (3) chunking + dedup — storage aur bandwidth dono bachte hain. Iske upar multi-region replication latency aur availability ke liye.

Q34Chunk ka hash client par compute hota hai ya server par?

Client par. File upload karne se pehle client khud file ko chunks me todta hai aur har chunk ka SHA-256 nikalta hai. Isse server ka load kam hota hai, aur client hash bhej kar poochh sakta hai ki chunk pehle se hai ya nahi — bina chunk upload kiye. Server sirf hash verify karta hai, dobara compute nahi karta.

Q35Interview me 'Design Google Drive' ka 2-minute summary kya bolen?

One-liner se shuru karo: initiate, chunk & hash, pre-signed URLs, parallel upload, commit, versioning, sync events. Phir requirements, phir entities (File, FileVersion, Chunk, mapping), phir upload flow, phir dedup aur sync deep dive. Aakhir me trade-offs bolo: metadata strong, sync eventual; chunk size ka trade-off; replication vs erasure coding. Ye structure 2 minute me poora design cover kar deta hai.

Q36Is lesson ke baad kaun se topics padhne chahiye?

Isi series me aage ke lessons — aur system design me: consistent hashing (data distribution ke liye), message queues (Kafka), distributed transactions (metadata atomicity), aur object storage internals (S3, GFS). Cloud storage ka design in sabka combination hai, isiliye inhe samajhna agle interviews me kaam aayega.
