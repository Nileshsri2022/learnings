01Lesson 07 — Proximity Search

01. Problem Statement

Proximity search ka matlab simple hai — user ki location (lat, lng) ke aas-paas, radius R ke andar, saare points of interest dhoondhna — restaurants, drivers, hotels — aur unhe distance ke hisaab se sort karke dena.

Yaad rakhne wali one-liner: QuadTree / Geohash spatial indexing → PostgreSQL PostGIS (GIST) → Elasticsearch geo_distance → Redis GEORADIUS → Haversine distance. Interview me ye ek line bol do, phir har approach ko detail me samjhao — poora answer isi flow me banta hai.

Example — seedha sa scenario

User San Francisco me hai — (37.7749, -122.4194) — aur 5 km radius me restaurants dhoondh raha hai. System ko wo saare restaurants lautane hain jo 5 km ke andar hain, distance ke hisaab se sorted.

Requirements — kya chahiye system se

  • <100ms query latency — user wait nahi karega, search turant aana chahiye.
  • Millions of locations ka support — chhota dataset nahi, crore ke scale par locations.
  • Accurate distance calculations — gol-gol andaza nahi, sahi doori chahiye.

Kahan use hota hai

  • Uber — aas-paas ke drivers dhoondhna.
  • Yelp — aas-paas ke restaurants dhoondhna.
  • Airbnb — aas-paas ke hotels dhoondhna.
  • Google Maps — nearby POIs (points of interest) dikhana.
Diagram me kya hai: Is lesson ka design diagram ek whiteboard-style sketch hai — upar QuadTree ka tree (root se 4 quadrants, phir unke 4-4 children) aur world map ka subdivision dikhaya gaya hai, beech me Geohash ke levels aur precision table, neeche restaurants table ka schema, SQL LIKE query aur PostGIS ke INSERT / ST_DWithin queries. 03Approach 1–5

03. Approach 1: QuadTree

QuadTree 2D space ko baar-baar 4 quadrants (NW, NE, SW, SE) me divide karta hai — jab tak har cell me points ki sankhya ek limit (max capacity, jaise 100 points per leaf node) se neeche na aa jaye. Ye ek in-memory spatial index hai.

QuadTree Structure

  • Concept: 2D space ko recursively 4 quadrants me divide karo, jab tak har cell me ≤ max_capacity points na rah jayein.
  • Tree structure: Har internal node ke 4 children hote hain; leaf nodes me asal location points store hote hain.
  • Example: World map → 4 quadrants me divide → har quadrant phir 4 me → ye tab tak chalta hai jab tak depth limit (jaise 20 levels) ya capacity na mil jaye.
  • Bounding box: Har node apne min/max lat/lng store karta hai — ye uski geographic bounds batata hai.

Search Algorithm

  • Input: Query point (lat, lng) aur radius R.
  • Step 1: Root node se shuru karo — check karo ki search circle node ke bounding box ko intersect karta hai ya nahi.
  • Step 2: Agar haan, to 4 children ko recursively search karo; agar nahi, to poora subtree prune kar do (skip).
  • Step 3: Leaf nodes par saare points collect karo aur Haversine formula se exact distance nikalo.
  • Step 4: Jin points ki distance ≤ R hai, unhe filter karo, distance se sort karo, top N results lautao.
  • Time complexity: O(log N + K) — K = number of results; pruning se 75%+ tree kat jata hai.

Insertion & Updates

  • Insert: Coordinates ke hisaab se tree traverse karke sahi leaf node dhoondho, point add karo.
  • Split: Agar leaf capacity (100 points) se zyada bhar jaye, to use 4 children me split karo aur points redistribute karo.
  • Update: Moving objects (drivers) ke liye — purani location remove karo, nayi location insert karo (2 operations).
  • Delete: Point ko deleted mark karo, space reclaim karne ke liye time-time par tree rebuild karo.

Pros & Cons

  • Pros: (1) Balanced tree me fast queries O(log N), (2) Sparse data ke liye efficient, (3) In-memory implement karna aasan, (4) Dynamic data (frequent inserts/deletes) ke liye achha.
  • Cons: (1) Distributed systems ke liye suitable nahi (tree ek hi server par), (2) Internal nodes ka memory overhead, (3) Splits par tree rebalancing, (4) Server restart par kho jata hai jab tak persist na kiya ho.
  • Best for: Game engines, hot regions ke liye in-memory caches, single server par <1M points.
  • Not for: Production databases (PostGIS use karo), billions of points (Elasticsearch use karo), distributed systems.

04Approach 1–5

04. Approach 2: Geohash

Geohash lat/lng ko ek base32 string me encode kar deta hai — aur uski sabse badi khaasiyat ye hai ki paas-paas ki locations ka common prefix hota hai. Isi liye simple SQL LIKE 'prefix%' se nearby search ho jata hai — bina kisi spatial extension ke.

Geohash Encoding Algorithm

  • Step 1: Latitude aur longitude ke bits ko interleave karo — lat = 37.7749 (binary: 01011010…), lng = -122.4194 (binary: 10011101…) → interleave → 0110011101010…
  • Step 2: Binary ko base32 me convert karo (0-9, a-z — a, i, l, o ko chhodkar) → San Francisco ke liye '9q8yy'.
  • Example: SF (37.7749, -122.4194) → geohash = '9q8yy9mz' (8 characters).
  • Precision: Length 1 = ±2500 km, 3 = ±78 km, 5 = ±2.4 km, 7 = ±76 m, 9 = ±2 m (poori table section 12 me hai).

Proximity Property

  • Key property: Nearby locations share common prefix.
  • Example: '9q8yy9mz' (SF downtown) aur '9q8yy9mt' (1 block door) — dono ka prefix '9q8yy9m' common hai.
  • Hierarchical: Maps par zoom levels jaisa — zoom out karo to chhota prefix use karo (9q8 = SF area), zoom in karo to lamba prefix (9q8yy9m = street level).
  • Isi se indexed geohash column par LIKE operator se efficient SQL queries banti hain.

Database Schema & Query

SQL — schema + index + query
CREATE TABLE restaurants (
  id SERIAL, name VARCHAR,
  lat DECIMAL, lng DECIMAL,
  geohash VARCHAR(12)
);
CREATE INDEX idx_geohash ON restaurants (geohash);

SELECT * FROM restaurants
WHERE geohash LIKE '9q8yy%';  -- ~2.4km box ke saare results

Radius to precision: 500m → 6 chars (±610m), 2km → 5 chars (±2.4km), 5km → 4 chars (±20km).

Diagram me schema: Design diagram me restaurants table ke columns dikhaye gaye hain — id (INT/UUID), name (VARCHAR), latitude (FLOAT/DOUBLE), longitude (FLOAT/DOUBLE), geohash (VARCHAR) — aur neeche wahi SELECT * FROM restaurants WHERE geohash LIKE 'sgkztus%' wali query badi likhi hui hai.

Edge Case: Neighbor Cells

  • Problem: Do points jo sirf 50m door hain, geohash boundary par hone se alag prefixes pa sakte hain — query ek ko miss kar degi.
  • Example: Point A: '9q8yyzzz', Point B: '9q8z0000' — 5th character alag hai, lekin doori sirf 50m.
  • Solution: Geohash library se 8 neighboring cells nikalo (N, NE, E, SE, S, SW, W, NW).
  • Query expansion: WHERE geohash IN ('9q8yy', '9q8yz', '9q8yx', '9q8yw', '9q8yv', '9q8yt', '9q8ys', '9q8yq', '9q8yu') — kul 9 cells.
  • Post-filter: Saare results par exact Haversine distance nikalo aur sirf wahi rakho jo asal circular radius ke andar hain.
Interview favourite — zaroor bolna

Geohash edge case interview me pakka poochha jata hai: boundary par points ke prefixes alag ho jate hain. Solution: 8 neighbor cells query karo (kul 9), phir Haversine se post-filter karo. Precision radius se chuno: 500m → length 6, 5km → length 4.

Pros & Cons

  • Pros: (1) B-tree index ke saath simple SQL (koi special extension nahi), (2) Kisi bhi database ke saath kaam karta hai (MySQL, PostgreSQL, MongoDB), (3) Human-readable (geohash ko URL me share kar sakte ho), (4) Zoom levels ke liye hierarchical.
  • Cons: (1) Circle ki jagah square area lautata hai (post-filter zaroori), (2) Edge case ke liye 9 cell queries chahiye, (3) Approximate (exact distance nahi), (4) Geohash cell ka size latitude ke saath badalta hai.
  • Best for: Spatial extension ke bina simple databases, distributed systems (shard karna aasan), approximate searches.
  • Example query: SELECT * FROM restaurants WHERE geohash LIKE '9q8yy%' → 500 candidates → Haversine filter → 200 jo exact 5km radius ke andar hain.

05Approach 1–5

05. Approach 3: PostgreSQL with PostGIS

PostGIS PostgreSQL ka spatial extension hai — source of truth ke liye sabse solid choice. GEOGRAPHY type par ST_DWithin se radius query aur GIST index se O(log N) lookup milta hai, Vincenty formula se exact distance ke saath.

PostGIS Setup

  • Install extension: CREATE EXTENSION postgis;
  • Data type: Sphere par lat/lng ke liye GEOGRAPHY(POINT, 4326) (meters me accurate distances) ya planar coordinates ke liye GEOMETRY (fast lekin kam accurate).
  • SRID 4326: WGS 84 coordinate system — standard GPS coordinates.
  • Example: CREATE TABLE restaurants (id SERIAL, name VARCHAR, location GEOGRAPHY(POINT, 4326))

Spatial Index: GIST

  • Create index: CREATE INDEX idx_location ON restaurants USING GIST (location)
  • GIST: Generalized Search Tree — R-tree structure banata hai, paas-paas ke points ko hierarchically bounding boxes me group karta hai.
  • Index structure: Root node → saare points ko cover karta bounding box → children subregions cover karte hain → leaves me individual points.
  • Query optimization: Sequential scan O(N) ki jagah index scan O(log N).

Radius Query with ST_DWithin

SQL — insert + radius query
INSERT INTO restaurants (name, location)
VALUES ('Taco Bell',
  ST_GeomFromText('POINT(77.5946 12.9716)', 4326));

SELECT name,
  ST_Distance(location,
    ST_GeogFromText('SRID=4326;POINT(77.6080 12.9700)')) AS distance
FROM restaurants
WHERE ST_DWithin(location,
  ST_GeogFromText('SRID=4326;POINT(77.6080 12.9700)'), 5000)
ORDER BY distance LIMIT 20;
  • ST_DWithin: Pehle bounding box se pre-filter karta hai (fast), phir exact distance check karta hai (slow lekin accurate).
  • ST_Distance: GEOGRAPHY type ke liye meters me distance lautata hai, Vincenty formula use karta hai (accuracy ±0.5mm).
  • Performance: GIST index ke saath 10M points par ~50-100ms.

Polygon & Complex Shapes

  • Polygon search: SELECT * FROM restaurants WHERE ST_Contains(ST_GeomFromGeoJSON('{polygon}'), location)
  • Use case: Kisi khaas neighborhood ke restaurants, ya irregular boundaries wale delivery zones.
  • GeoJSON polygon: { 'type': 'Polygon', 'coordinates': [[[lng1, lat1], [lng2, lat2], [lng3, lat3], [lng1, lat1]]] }
  • ST_Intersects: Check karta hai ki point kisi line/polygon ko intersect karta hai ya nahi.
  • ST_Buffer: Point/line ke aas-paas buffer zone banata hai (jaise road ke aas-paas 100m buffer).

Pros & Cons

  • Pros: (1) Exact distance calculations (Vincenty formula), (2) ACID guarantees, (3) Complex spatial queries (polygons, buffers, intersections), (4) Mature ecosystem, well-documented.
  • Cons: (1) PostgreSQL-specific (portable nahi), (2) Single server bottleneck (shard karna mushkil), (3) Real-time ke liye Redis se slow, (4) Extension install karna padta hai.
  • Best for: Location data ka source of truth, static locations (restaurants, hotels), complex spatial operations.
  • Scaling: Region se shard karo (US-West DB, US-East DB), queries ke liye read replicas.

06Approach 1–5

06. Approach 4: Elasticsearch Geo Queries

Elasticsearch distributed search engine hai — billions of documents par proximity + full-text search ek saath karta hai. geo_point mapping se location index hoti hai aur geo_distance filter se radius search.

Index Mapping Setup

JSON — index + document
PUT /restaurants
{ "mappings": { "properties": {
  "location": { "type": "geo_point" },
  "name": { "type": "text" },
  "category": { "type": "keyword" },
  "rating": { "type": "float" } } } }

POST /restaurants/_doc
{ "name": "Taco Bell",
  "location": { "lat": 12.9716, "lon": 77.5946 },
  "category": "Fast Food", "rating": 4.2 }
  • geo_point: lat/lng store karta hai, andar hi spatial index (BKD tree) bana deta hai.

Geo Distance Query

JSON — geo_distance + sort
GET /restaurants/_search
{ "query": { "geo_distance": {
    "distance": "5km",
    "location": { "lat": 12.97, "lon": 77.59 } } } }

-- distance se sort:
"sort": [ { "_geo_distance": {
  "location": { "lat": 12.97, "lon": 77.59 },
  "order": "asc", "unit": "km" } } ]

-- Response: { "_source": { "name": "Taco Bell" },
--              "sort": [ 0.5 ] }   (0.5 km distance)

Distance units: km, mi, m (meters), ft (feet).

Combined Filters (Proximity + Text + Facets)

JSON — bool query: pizza + 5km + Italian + rating ≥ 4.0
{ "query": { "bool": { "must": [
    { "match": { "name": "pizza" } } ],
  "filter": [
    { "geo_distance": { "distance": "5km",
        "location": {...} } },
    { "term": { "category": "Italian" } },
    { "range": { "rating": { "gte": 4.0 } } } ] } } }
  • Query execution: (1) Full-text search 'pizza' → 10K candidates, (2) Category filter → 2K, (3) Rating filter → 1K, (4) geo_distance → 50 results.
  • Aggregations: geo_distance agg se distance buckets milte hain — {'to': 1}, {'from': 1, 'to': 3}, {'from': 3, 'to': 5} — har bucket me count.
  • Use case: 'Pizza restaurants within 5km, rating ≥ 4.0, categorized by distance ranges'.

Geo Bounding Box (Faster for Large Results)

JSON — geo_bounding_box
{ "query": { "geo_bounding_box": { "location": {
  "top_left": { "lat": 13.0, "lon": 77.5 },
  "bottom_right": { "lat": 12.9, "lon": 77.7 } } } } }
  • Rectangular areas ke liye geo_distance se fast hai — distance calculation hi nahi hoti.
  • Use case: Map viewport ke saare restaurants (jab user map scroll karta hai).
  • Optimization: Pehle geo_bounding_box se candidates nikalo, phir exact circular radius ke liye geo_distance lagao.
Interview favourite — zaroor bolna

'Why Elasticsearch over PostgreSQL?' — Elasticsearch: horizontally scalable (billions of points), fast filtering (category + rating + distance), ~50ms p95. PostgreSQL: single server bottleneck, ~100ms, ACID guarantees. Use both: ES for reads, PG for writes.

Pros & Cons

  • Pros: (1) Horizontally scalable (nodes par shard), (2) Proximity + full-text search ek saath, (3) Fast aggregations/facets, (4) 100M documents par ~10-50ms latency.
  • Cons: (1) Eventual consistency (~1s refresh interval), (2) Zyada expensive (memory intensive), (3) Complex setup, (4) No ACID guarantees.
  • Best for: Search engines (Yelp, Google Maps), complex filtering, billions of documents, read-heavy workloads.
  • Scaling: Document count ke hisaab se auto-shard hota hai, petabytes tak scale kar sakta hai.

07Approach 1–5

07. Approach 5: Redis Geospatial

Redis geospatial commands sabse fast hain — <10ms. Andar se ye sorted set (ZSET) hota hai jisme score = location ka geohash hota hai. Isi liye ye real-time me hilte hue objects — Uber drivers, delivery agents — ke liye perfect hai.

Redis Geo Commands

Redis CLI
GEOADD drivers 77.5946 12.9716 'driver_1'
              77.6000 12.9800 'driver_2'
-- sorted set me store hota hai, geohash as score

GEORADIUS drivers 77.5900 12.9700 5 km WITHDIST ASC COUNT 10
-- returns [('driver_1', '0.5 km'), ('driver_2', '1.2 km')]

GEORADIUSBYMEMBER drivers 'driver_1' 2 km
-- driver_1 ke 2km andar ke saare drivers

GEOPOS drivers 'driver_1'
-- returns [(77.5946, 12.9716)]

GEODIST drivers 'driver_1' 'driver_2' km
-- returns 1.2 (km)

Update & Delete

  • Update location: Bas dobara GEOADD kar do naye coordinates ke saath (upsert operation).
  • Example: Driver move hua → GEOADD drivers 77.6100 12.9850 'driver_1' → existing entry update ho jati hai.
  • Delete: ZREM drivers 'driver_1' (geospatial data andar se sorted set me store hota hai).
  • Expire: Key par TTL set karo → EXPIRE drivers:online 3600 (1 ghante me auto-delete agar update na aaye).

Performance & Scaling

  • Time complexity: O(log N + M) — N = total points, M = results returned.
  • Latency: 10K points par ~1ms, 100K par ~5ms, 1M par ~10ms (sab in-memory).
  • Memory: ~50 bytes per point (lat, lng, member name, geohash) → 1M points ≈ 50MB.
  • Sharding: Multiple Redis instances use karo, region ya geohash prefix se shard karo (drivers:sf, drivers:nyc).
  • Persistence: Durability ke liye RDB snapshots ya AOF use karo — lekin aam taur par ye ephemeral hot data ke liye use hota hai.

Pros & Cons

  • Pros: (1) Sabse fast queries <10ms, (2) Real-time updates (drivers hilte rehte hain), (3) Simple API, (4) Hot/ephemeral data ke liye perfect.
  • Cons: (1) Sirf in-memory (millions of points ke liye expensive), (2) No complex filtering, (3) Restart par data lost (jab tak persist na ho), (4) Limited query capabilities.
  • Best for: Real-time moving objects (Uber drivers, delivery agents), active sessions, frequently accessed locations.
  • Hybrid approach: Redis hot data ke liye (active drivers) + PostgreSQL cold data ke liye (saare drivers) + har 60s sync.

08Distance aur Comparison

08. Haversine Distance Formula

Haversine formula do points ke beech great-circle distance nikalta hai — Earth ko sphere maan kar. Ye proximity search ki sabse neeche wali building block hai: QuadTree, Geohash aur Redis — sab ant me isi se exact distance nikaalte hain.

Formula & Implementation

Formula
a = sin²(Δlat/2) + cos(lat1) × cos(lat2) × sin²(Δlng/2)
c = 2 × atan2(√a, √(1−a))
distance = R × c

R = Earth radius = 6371 km (3959 miles)
  • Example: SF (37.7749, -122.4194) se LA (34.0522, -118.2437) → Haversine → 559 km.
  • Accuracy: ±0.5% error (perfect sphere maanta hai, jabki Earth asal me oblate spheroid hai).
Warning — degree ka farak samjho: NEVER assume 1 degree latitude = 1 degree longitude in distance. Latitude constant hai (111 km), longitude latitude ke saath badalta hai (equator par 111 km, poles par 0 km). Hamesha Haversine ya PostGIS ST_Distance use karo.

Optimization: Bounding Box Pre-filter

  • Problem: 1M points par Haversine nikaalna ~1 second CPU time leta hai.
  • Solution: Pehle bounding box se pre-filter karo → 90% points eliminate → Haversine sirf bache 10% par.
  • Bounding box: WHERE lat BETWEEN (user_lat - delta) AND (user_lat + delta) AND lng BETWEEN (user_lng - delta) AND (user_lng + delta)
  • Delta calculation: delta ≈ radius_km / 111 (rough conversion: 1 degree ≈ 111 km).
  • Example: 5km radius → delta = 5/111 ≈ 0.045 degrees → bounding box 1M se 10K tak filter karta hai → 10K par Haversine → <10ms.
Key optimization — interview me ye line bolni hai

Bounding box pre-filter Haversine se pehle: WHERE lat BETWEEN (user_lat - delta) AND (user_lat + delta) se 90% points eliminate ho jate hain, phir Haversine sirf bache 10% par. Delta ≈ radius_km / 111.

Warning: NEVER compute Haversine for every point. Pehle bounding box ya geohash se (index-based) pre-filter karo, phir Haversine sirf candidates par. Ek calculation sasti hai, lekin scale par expensive hai — 1M calculations = 1 second CPU.

Alternatives

  • Vincenty formula: Zyada accurate (ellipsoid ko account karta hai), ±0.5mm error, lekin 10x slow computation.
  • Euclidean distance: sqrt((x2-x1)² + (y2-y1)²) — sirf chhote areas par flat projection me, bahut fast lekin badi distances par inaccurate.
  • Manhattan distance: |x2-x1| + |y2-y1| — rough approximation, exact calculation se pehle quick filtering ke liye useful.
  • Database functions: PostGIS ST_Distance (GEOGRAPHY ke liye Vincenty), Elasticsearch (Haversine), Redis GEODIST (Haversine).

Interview favourite — ye comparison yaad rakho

Interviewers ALWAYS poochhte hain: 'Geohash vs QuadTree vs PostGIS?' 11. Common Interview Questions

Is lesson ke 10 core interview Q&A — ye woh sawaal hain jo interviewers baar-baar poochhte hain. Har answer ko poora padho; inhi 10 ke aas-paas FAQs tab me 36 sawaal bane hain.

Q1. Geohash kya hai aur cell boundaries par edge cases kaise handle karte ho?

Encoding: (1) lat/lng bits interleave karo → binary string → base32 me convert karo → 'sgkztus' (7 chars ≈ ±76m), (2) Precision table: length 5 = ±2.4km, length 7 = ±76m, length 9 = ±2m. Proximity property: Paas-paas ki locations ka common prefix hota hai ('sgkztus', 'sgkztur' dono ek hi area me). Edge case problem: Cell boundary par 50m door do points ke hashes alag ho jate hain ('sgkztzzz' vs 'sgku000' — 5th char alag). Solution: (1) Library se 8 neighbor geohash cells nikalo (N, NE, E, SE, S, SW, W, NW), (2) Kul 9 cells query karo (center + 8 neighbors): WHERE geohash IN ('sgkzt', 'sgkzu', 'sgkzs', ...), (3) Haversine se post-filter karke exact circular radius nikalo. Optimization: Badi precision (kam chars) use karo — bada box jo circle ko pakka contain kare — phir filter karo. Example: 5km radius → precision 5 (±2.4km cell) → single query → Haversine filter → exact results.

Q2. QuadTree vs Geohash vs PostGIS — kab kis ko use karte ho?

QuadTree: (1) Structure: Recursive 4-way partitioning, har node ke NW/NE/SW/SE children, (2) Search: O(log n) traversal, search circle ko intersect na karne wale subtrees prune karo, (3) Use: In-memory single server (<1M points), game engines, dynamic data, (4) Pros: Fast (<1ms), easy updates, (5) Cons: Distributable nahi, restart par kho jata hai, complex implementation. Geohash: (1) Encoding: Lat/lng → base32 string, prefix matching, (2) Search: SQL LIKE 'prefix%' B-tree index ke saath, 9 cells query karo (center + 8 neighbors), (3) Use: Simple SQL databases, distributed systems, approximate OK, (4) Pros: Kisi bhi DB ke saath, shard karna aasan, human-readable, (5) Cons: Box lautata hai circle nahi, edge cases. PostGIS: (1) Extension: GEOGRAPHY type, radius ke liye ST_DWithin, GIST spatial index, (2) Search: R-tree se O(log n), exact Vincenty distance, (3) Use: Static data, ACID needed, complex shapes (polygons), (4) Pros: Exact distance, mature, complex queries, (5) Cons: PostgreSQL-only, shard karna mushkil, ~100ms latency. Decision: QuadTree single-server in-memory ke liye, Geohash distributed approximate ke liye, PostGIS ACID + exact distance ke liye. Production: Hybrid — Redis Geo (hot data) + Elasticsearch (search) + PostGIS (source of truth).

Q3. Millions of locations ke liye proximity search kaise optimize karte ho?

Multi-layer optimization: (1) Spatial indexing: GIST index (PostGIS), geohash par B-tree, ya Redis GEORADIUS — O(n) scan se O(log n) lookup, (2) Bounding box pre-filter: lat/lng bounds nikalo, WHERE lat BETWEEN (lat-delta) AND (lat+delta) AND lng BETWEEN (lng-delta) AND (lng+delta) — expensive distance calc se pehle 90% eliminate, delta = radius_km / 111, (3) Caching: Hot locations ke liye Redis cache (har city top 1000), TTL = 10 min, 80% queries <5ms me, (4) Geographic sharding: Region (US-West, US-East, EU) ya geohash prefix se partition — per-shard dataset 5-10x kam, (5) Materialized views: Popular queries pre-compute karo (restaurants by city + 5km radius), hourly refresh, (6) Read replicas: Har region me PostgreSQL replicas, nearest replica par geo queries route karo, (7) Lazy distance calc: Pehle bounding box se top N lautao, exact distance sirf displayed results ke liye nikalo, (8) Result limit: Saare matches ki jagah LIMIT 20 — user waise bhi pehla page hi dekhta hai. Example: 10M restaurants → geohash prefix filter → 10K candidates → bounding box → 1K candidates → Haversine → 200 exact radius ke andar → sort → top 20 lautao → kul latency 50ms vs bina optimization 5000ms.

Q4. PostgreSQL PostGIS se proximity search implement karo — schema aur query dikhao.

Setup: (1) Install: CREATE EXTENSION postgis;, (2) Schema: CREATE TABLE restaurants (id SERIAL PRIMARY KEY, name VARCHAR(255), location GEOGRAPHY(POINT, 4326), category VARCHAR(100), rating DECIMAL(2,1)), (3) Index: CREATE INDEX idx_location_gist ON restaurants USING GIST (location), (4) Insert: INSERT INTO restaurants (name, location, category, rating) VALUES ('Taco Bell', ST_GeomFromText('POINT(77.5946 12.9716)', 4326), 'Fast Food', 4.2). Query: SELECT id, name, category, rating, ST_Distance(location, ST_GeogFromText('SRID=4326;POINT(77.6080 12.9700)')) AS distance_meters FROM restaurants WHERE ST_DWithin(location, ST_GeogFromText('SRID=4326;POINT(77.6080 12.9700)'), 5000) AND category = 'Fast Food' AND rating >= 4.0 ORDER BY distance_meters LIMIT 20; Explanation: (1) ST_GeogFromText: User location (77.6080, 12.9700) se geography point banata hai, (2) ST_DWithin: Bounding box se pre-filter karta hai, phir exact distance check ≤ 5000 meters, (3) ST_Distance: Vincenty formula se meters me exact distance, (4) GIST index: O(log n) spatial lookup, (5) Additional filters: category aur rating combined search ke liye, (6) Performance: 10M rows par ~50-100ms. Alternative (geometry — fast lekin kam accurate): GEOGRAPHY ki jagah GEOMETRY use karo, ST_MakePoint(lng, lat) use karo, distance degrees me milegi meters me nahi.

Q5. Redis GEORADIUS andar se kaise kaam karta hai aur kab use karna chahiye?

Internal implementation: (1) Data structure: Redis geospatial data ko sorted set (ZSET) me store karta hai — score = location ka geohash, member = location ID, (2) Geohash encoding: Andar lat/lng ko 52-bit geohash integer me encode karta hai, (3) GEORADIUS algorithm: (a) Center point ka geohash nikalo, (b) Radius ke liye geohash prefix range nikalo, (c) ZRANGEBYLEX se range ke saare members nikalo (O(log n)), (d) Har candidate ki exact Haversine distance nikalo, (e) Radius ke andar wale filter karo, distance se sort karo, (4) Time complexity: O(log n + m) jahan m = results. Commands: (1) GEOADD key lng lat member — add/update location, (2) GEORADIUS key lng lat radius km WITHDIST ASC COUNT 10 — circle search, distance sorted, (3) GEORADIUSBYMEMBER key member radius km — existing member ke neighbors, (4) GEODIST key member1 member2 km — do members ke beech distance. Kab use karo: (1) Real-time moving objects (drivers, delivery agents har 5s update karte hain), (2) Hot/ephemeral data (active sessions, current locations), (3) <10ms latency requirement, (4) <10M points (memory constraint), (5) High read frequency (100K queries/sec). Kab mat use karo: (1) Billions of points (RAM me bahut expensive), (2) Complex filtering (category, rating) — Elasticsearch use karo, (3) ACID persistence — PostGIS use karo. Hybrid pattern: Redis active drivers ke liye (10K online) + PostgreSQL saare drivers ke liye (1M total), har 60s sync.

Q6. Haversine distance kaise calculate karte ho aur bounding box pre-filter kyun use karte ho?

Haversine formula: (1) Purpose: Sphere (Earth) par do points ke beech great-circle distance, (2) Inputs: Point A (lat1, lng1), Point B (lat2, lng2), Earth radius R = 6371 km, (3) Formula: a = sin²((lat2-lat1)/2) + cos(lat1)·cos(lat2)·sin²((lng2-lng1)/2), c = 2·atan2(√a, √(1-a)), distance = R·c, (4) Implementation: Degrees ko radians me convert karo (π/180 se multiply), trig functions lagao, result km me, (5) Example: SF (37.7749, -122.4194) se LA (34.0522, -118.2437) → 559 km. Accuracy: ±0.5% error (sphere maanta hai, Earth ellipsoid hai). Bounding box optimization: (1) Problem: 1M points par Haversine = 1M trig calculations = ~1 second CPU time, (2) Solution: Simple lat/lng range check se pre-filter karo: WHERE lat BETWEEN (user_lat - delta) AND (user_lat + delta) AND lng BETWEEN (user_lng - delta) AND (user_lng + delta), (3) Delta: delta = radius_km / 111 (1 degree ≈ 111 km), 5km radius ke liye delta = 0.045 degrees, (4) Effect: Index scan se 90-95% points eliminate ho jate hain (fast), (5) Final step: Haversine sirf bache 5-10% par → kul time <10ms. Example: 1M points, 5km radius → bounding box 10K candidates tak laata hai → 10K par Haversine → <10ms vs bina optimization 1000ms.

Q7. 'Pizza restaurants within 5km, rating ≥ 4' ke liye Elasticsearch mapping aur query design karo.

Index mapping: PUT /restaurants { "mappings": { "properties": { "name": { "type": "text", "analyzer": "standard" }, "category": { "type": "keyword" }, "location": { "type": "geo_point" }, "rating": { "type": "float" }, "price_range": { "type": "keyword" }, "is_open": { "type": "boolean" } } } }. Index document: POST /restaurants/_doc { "name": "Taco Bell", "category": "Fast Food", "location": { "lat": 12.9716, "lon": 77.5946 }, "rating": 4.2, "price_range": "$", "is_open": true }. Search query: bool query — must: [ { "match": { "name": "pizza" } } ], filter: [ { "geo_distance": { "distance": "5km", "location": { "lat": 12.97, "lon": 77.59 } } }, { "range": { "rating": { "gte": 4.0 } } }, { "term": { "is_open": true } } ], sort: [ { "_geo_distance": { "location": { "lat": 12.97, "lon": 77.59 }, "order": "asc", "unit": "km" } } ], size: 20. Result: { "hits": { "hits": [ { "_source": { "name": "Pizza Hut", "rating": 4.5 }, "sort": [ 0.8 ] } ] } } (0.8 km distance). Aggregations (facets): price_facets (terms on price_range) aur distance_buckets (geo_distance ranges: to 1, 1-3, 3-5 km). Performance: 100M documents par ~20-50ms, horizontally scalable.

Q8. Geospatial data ko horizontal scaling ke liye kaise shard karte ho?

Sharding strategies: (1) Geographic sharding: Region se divide karo (US-West, US-East, EU-West, EU-East, Asia-Pacific), har region = alag database/cluster, location bounds ke hisaab se queries route karo. Pros: Simple routing, isolated failures. Cons: Unbalanced load (NYC me Montana se zyada restaurants), cross-region queries complex. (2) Geohash prefix sharding: Geohash ke pehle N characters se shard karo (pehle 2 chars = 1024 possible prefixes → 16 shards), consistent hashing se geohash prefix ko shard par map karo. Pros: Even distribution. Cons: Radius queries multiple shards par ja sakti hain. (3) Hybrid: Pehle region, phir uske andar geohash prefix — Example: US-East shard 1: geohash '9q', '9r' se shuru; US-East shard 2: '9w', '9x'. Query routing: (1) Query se location nikalo, (2) Geohash ya region determine karo, (3) Sahi shard(s) par route karo, (4) Agar query multiple shards par jaati hai (boundary ke paas bada radius), to sab par fan-out karo aur results merge karo. Example: NYC user (40.7128, -74.0060) 10km search kare → saare results US-East shard me; Philadelphia user (US-East/US-Mid border) 50km search kare → dono shards query karo, distance se merge karo. Cross-shard complexity: (1) Chhota radius (<10km): Aam taur par 1-2 shards, (2) Bada radius (>50km): 3-5 shards tak, scatter-gather pattern. Performance: Per-shard dataset 10x kam (10M → 1M), query latency 5x behtar (500ms → 100ms). Elasticsearch: Document ID se auto-shard karta hai, custom routing key se geohash routing possible hai.

Q9. Proximity searches ke liye caching strategy kya hai?

Multi-layer caching: (1) Result cache: Poori query results Redis me cache karo — key = hash(lat, lng, radius, filters), value = [location_ids], TTL = 5 min, identical repeated queries handle karta hai. Example: search {lat: 37.77, lng: -122.42, radius: 5km, category: Italian} → cache key: hash(37.77:-122.42:5000:Italian) → value: [id1, id2, id3, ...]. (2) Location cache: Popular/active locations Redis GEOSPATIAL me cache karo — GEOADD restaurants:hot:{city_id}, TTL = 10 min, 80% queries GEORADIUS se <5ms me, Eviction: LRU, har city top 1000 rakho. (3) Application cache: API servers me in-memory cache (Caffeine, Guava) bahut frequent queries ke liye, 100-element LRU cache, network hop ke bina <1ms me. (4) CDN cache: Static location data (restaurant metadata, images) edge locations par globally cache karo. Cache warming: (1) Background job query logs analyze karta hai, (2) Har city ke top 100 queries frequency se identify karta hai, (3) Peak hours se pehle Redis cache pre-populate karta hai. Invalidation: (1) Location update par: Us location wali saari cache keys invalidate karo — Redis Pub/Sub ya Kafka se invalidation event broadcast karo, (2) Pattern matching: Redis SCAN se location_id wali keys dhoondho, DEL se delete karo, (3) Time-based: Updates ke bina bhi TTL ke baad entries expire karo taaki indefinite staleness na ho. Example cache hit flow: User search karta hai → Redis result cache check → hit (2 min pehle identical query) → cached results lautao → <5ms latency. Cache miss flow: → Elasticsearch query karo → 50ms → result cache karo → user ko lautao.

Q10. Polygon-based searches kaise handle karte ho (jaise kisi neighborhood ke restaurants)?

Polygon search implementation: (1) PostGIS: SELECT * FROM restaurants WHERE ST_Contains(ST_GeomFromGeoJSON('{polygon}'), location), polygon format: GeoJSON {'type': 'Polygon', 'coordinates': [[[lng1, lat1], [lng2, lat2], [lng3, lat3], [lng1, lat1]]]} — loop close karna zaroori hai (first point = last point), GIST index containment queries ko O(log n) me support karta hai. (2) Elasticsearch: { "query": { "geo_polygon": { "location": { "points": [ {"lat": 12.97, "lon": 77.59}, {"lat": 12.98, "lon": 77.60}, {"lat": 12.97, "lon": 77.61} ] } } } } — 1000 vertices tak support, polygon automatically close hota hai. Optimization: (1) Bounding box pre-filter: Polygon ka min/max lat/lng nikalo (bounding rectangle), pehle WHERE lat BETWEEN min_lat AND max_lat AND lng BETWEEN min_lng AND max_lng se pre-filter karo (fast), phir exact containment check ST_Contains (slow) — candidates 90% kam ho jate hain, (2) Polygon simplification: Complex polygons (1000+ vertices) ke liye Douglas-Peucker algorithm se 100-200 vertices tak reduce karo, shape maintain rehta hai, queries 5-10x fast, (3) Pre-computation: Static zones (delivery areas, neighborhoods) ke liye har location ko zone_id assign karo — query ban jati hai WHERE zone_id = {id} (index se instant). Use cases: (1) Delivery zones: Restaurant polygonal area serve karta hai, (2) Geofencing: Driver dispatch sirf polygon boundary ke andar, (3) Neighborhood search: 'Greenwich Village' jaise irregular shape me restaurants. Performance: Simple polygon (10 vertices) 10M points ke saath → GIST index se ~50ms, Complex polygon (100 vertices) → ~200ms. Example: Uber Eats delivery zone → restaurant map par polygon banata hai → frontend GeoJSON me convert karta hai → backend zones table me store karta hai → orders sirf un customers se accept hote hain jo ST_Contains(delivery_zone, customer_location) me aate hain.

36 real interview sawaal — geohash, QuadTree, PostGIS, Elasticsearch, Redis, Haversine, sharding, caching aur polygon search par. Har jawaab lesson ke content se bana hai.
Q01Proximity search kya hota hai? Ek line me kaise define karoge?
Proximity search matlab user ki location (lat, lng) ke aas-paas, radius R ke andar saare points of interest dhoondhna — jaise restaurants, drivers, hotels — aur unhe distance ke hisaab se sort karke lautana. Example: user (37.7749, -122.4194) par hai aur 5km radius me restaurants chahta hai. Requirements: <100ms latency, millions of locations, accurate distance. Use cases: Uber drivers, Yelp restaurants, Airbnb hotels, Google Maps nearby POIs.
Q02Geohash kya hai aur ye kaam kaise karta hai?
Geohash lat/lng ko base32 string me encode karta hai. Pehle latitude aur longitude ke bits interleave kiye jate hain, phir binary ko base32 (0-9, a-z — a, i, l, o chhodkar) me convert karte hain. Example: SF (37.7749, -122.4194) ka geohash '9q8yy9mz' hai. Sabse badi khaasiyat: paas-paas ki locations ka common prefix hota hai — '9q8yy9mz' aur '9q8yy9mt' dono ka prefix '9q8yy9m' hai. Isi liye SQL LIKE 'prefix%' se nearby search ho jata hai, bina kisi spatial extension ke.
Q03Geohash ke cell boundary edge case ko kaise handle karte ho?
Problem: boundary par 50m door do points ke geohash prefixes alag ho sakte hain — jaise '9q8yyzzz' aur '9q8z0000' — to ek query me ek point miss ho jata hai. Solution: geohash library se 8 neighboring cells nikalo (N, NE, E, SE, S, SW, W, NW) aur kul 9 cells query karo — WHERE geohash IN (9 cells). Phir saare results par Haversine se post-filter karo taaki sirf exact circular radius ke andar wale points rahein. Radius ke hisaab se precision chuno: 500m ke liye length 6, 5km ke liye length 4.
Q04QuadTree kya hai aur iski search kaise kaam karti hai?
QuadTree 2D space ko recursively 4 quadrants (NW, NE, SW, SE) me divide karta hai, jab tak har leaf cell me points max capacity (jaise 100) se neeche na aa jayein. Har node apna bounding box (min/max lat/lng) store karta hai. Search: root se shuru karo, check karo search circle node ke bounding box ko intersect karta hai ya nahi — agar nahi to poora subtree prune kar do, agar haan to 4 children recursively search karo. Leaf par Haversine se exact distance nikalo, filter karo, sort karo. Time complexity O(log N + K) hai, pruning se 75%+ tree kat jata hai.
Q05QuadTree vs Geohash — kab kis ko chunoge?
QuadTree in-memory single-server ke liye best hai — <1M points, game engines, dynamic data, latency <1ms. Lekin distributed systems ke liye nahi hai, restart par kho jata hai. Geohash kisi bhi SQL database ke saath kaam karta hai, B-tree index se LIKE queries chalti hain, shard karna aasan hai aur human-readable hai — lekin ye square area lautata hai (circle nahi), edge case ke liye 9 cells chahiye aur approximate hai. Decision: single-server in-memory ho to QuadTree, distributed ya simple SQL ho to Geohash.
Q06PostGIS kya hai? ST_DWithin aur GIST index kaise kaam karte hain?
PostGIS PostgreSQL ka spatial extension hai. CREATE EXTENSION postgis se install hota hai. Location GEOGRAPHY(POINT, 4326) type me store hoti hai — SRID 4326 WGS 84 GPS coordinates hain. GIST index (CREATE INDEX ... USING GIST) R-tree structure banata hai — paas-paas ke points hierarchical bounding boxes me group hote hain, to query O(log N) me hoti hai. ST_DWithin pehle bounding box se pre-filter karta hai (fast), phir exact distance check karta hai. ST_Distance Vincenty formula se meters me exact distance deta hai (±0.5mm accuracy). 10M points par ~50-100ms latency milti hai.
Q07GEOGRAPHY aur GEOMETRY type me kya farak hai?
GEOGRAPHY type lat/lng ko sphere par treat karta hai — distances meters me accurate milti hain, Vincenty formula use hota hai (±0.5mm). GEOMETRY type planar (flat) coordinates par kaam karta hai — fast hai lekin kam accurate, aur distance degrees me milti hai meters me nahi. Rule: accurate real-world distances chahiye to GEOGRAPHY (POINT, 4326) use karo; sirf fast approximate planar calculations chahiye to GEOMETRY. Interview me ye farak bolna important hai.
Q08Elasticsearch me geo search kaise karte ho? geo_point aur geo_distance samjhao.
Elasticsearch me location field ka type geo_point hota hai — ye lat/lng store karta hai aur andar BKD tree spatial index bana deta hai. Query geo_distance filter se hoti hai: distance '5km' aur location (lat, lon) do. Sort ke liye _geo_distance use karte hain — response me sort array me distance aati hai, jaise 0.5 km. Combined queries bool query se banti hain — must me text match (pizza), filter me geo_distance + term (category Italian) + range (rating >= 4.0). Aggregations se distance buckets bhi milte hain. 100M documents par ~10-50ms latency, lekin eventual consistency (~1s refresh interval) hoti hai.
Q09Redis GEORADIUS andar se kaise kaam karta hai?
Redis geospatial data ko sorted set (ZSET) me store karta hai — score = location ka 52-bit geohash integer, member = location ID. GEORADIUS algorithm: pehle center point ka geohash nikalo, phir radius ke liye geohash prefix range nikalo, ZRANGEBYLEX se range ke saare members nikalo (O(log N)), phir har candidate ki exact Haversine distance nikalo, radius ke andar wale filter karo aur distance se sort karo. Time complexity O(log N + M) hai. GEOADD se add/update hota hai (upsert), GEOPOS se position, GEODIST se do members ki distance, ZREM se delete. Latency 10K points par ~1ms, 1M par ~10ms.
Q10Redis Geo kab use karna chahiye aur kab nahi?
Use karo jab: real-time moving objects hon (drivers har 5s update karte hain), hot/ephemeral data ho, <10ms latency chahiye, <10M points hon, high read frequency ho (100K queries/sec). Mat use karo jab: billions of points hon (RAM expensive), complex filtering chahiye (category, rating — Elasticsearch lo), ACID persistence chahiye (PostGIS lo). Hybrid pattern: Redis active drivers ke liye (10K online) + PostgreSQL saare drivers ke liye (1M total), har 60s sync karo.
Q11Haversine formula kya hai? SF se LA ki distance kaise nikli 559 km?
Haversine formula sphere par do points ke beech great-circle distance nikalta hai: a = sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlng/2), c = 2·atan2(√a, √(1−a)), distance = R·c, jahan R = 6371 km (Earth radius). Degrees ko radians me convert karo (π/180 se multiply). SF (37.7749, -122.4194) se LA (34.0522, -118.2437): a = 0.0382, c = 0.391, distance = 6371 × 0.391 = 559 km. Accuracy ±0.5% hai kyunki ye perfect sphere maanta hai, jabki Earth oblate spheroid hai. Zyada accuracy chahiye to Vincenty formula (±0.5mm) use karo, lekin wo 10x slow hai.
Q12Bounding box pre-filter kyun zaroori hai? Delta kaise nikalte ho?
1M points par Haversine nikaalna ~1 second CPU leta hai — har point par trig calculations hoti hain. Bounding box pre-filter se pehle simple lat/lng range check karte ho: WHERE lat BETWEEN (user_lat − delta) AND (user_lat + delta) AND lng BETWEEN (user_lng − delta) AND (user_lng + delta). Delta = radius_km / 111, kyunki 1 degree ≈ 111 km. 5km radius ke liye delta ≈ 0.045 degrees. Isse 90-95% points index scan se eliminate ho jate hain, Haversine sirf bache 10% par chalta hai — kul time <10ms. Ye interview me sabse zyada poochha jaane wala optimization hai.
Q131 degree latitude aur 1 degree longitude barabar kyun nahi hote?
1 degree latitude har jagah ≈111 km hota hai — constant hai. Lekin 1 degree longitude ≈ 111 km × cos(latitude) hota hai — equator par 111 km, lekin poles ki taraf kam hote-hote 0 ho jata hai, kyunki longitude lines poles par converge karti hain. Isi liye lat/lng ko seedha x-y plane maan kar Euclidean distance nikaalna galat hai. Hamesha Haversine ya PostGIS ST_Distance use karo. Ye galti interview me pakdi jati hai.
Q14Geohash precision table yaad rakho — length 5 aur 7 ka kya matlab hai?
Length 5 = ±2.4 km error, cell size 4.9 km × 4.9 km — neighborhood level. Length 7 = ±76 m error, cell 152.9 m × 152.4 m — building level. Poori table: length 1 = ±2500 km (country), 2 = ±630 km, 3 = ±78 km (city), 4 = ±20 km (district), 6 = ±0.61 km (street), 8 = ±19 m, 9 = ±2.4 m (sub-building). Radius se length chuno: 500m → length 6, 2km → length 5, 5km → length 4, 100m → length 7 (9 cells ke saath). Cell size hamesha radius se bada rakho, warna points miss honge.
Q15Production hybrid architecture kya hai — teen tiers samjhao.
Tier 1 — Redis (Hot Cache): har city ke top 1000 active/popular locations, TTL 10 min, 80% queries <5ms me serve karta hai. Tier 2 — Elasticsearch (Search Layer): 100M+ documents, complex filters (category, rating, text), ~50ms. Tier 3 — PostgreSQL PostGIS (Source of Truth): saari locations + metadata, writes aur rare queries, ACID, ~100ms. Write flow: client → PostgreSQL → async indexer → Elasticsearch → hot locations Redis me. Query flow: pehle Redis, miss ho to Elasticsearch, phir PostGIS. Drivers har 5s Redis update karte hain, PostgreSQL me batch sync har 60s.
Q16Geospatial data ko shard kaise karte ho?
Teen tareeke: (1) Geographic sharding — region se divide karo (US-West, US-East, EU), har region alag database/cluster, location bounds se routing. Pros: simple routing, isolated failures. Cons: unbalanced load, cross-region queries complex. (2) Geohash prefix sharding — geohash ke pehle N chars se shard karo (pehle 2 chars = 1024 prefixes → 16 shards), consistent hashing se map karo. Pros: even distribution. Cons: radius queries multiple shards par ja sakti hain. (3) Hybrid — pehle region, phir uske andar geohash prefix. Chhota radius (<10km) aam taur par 1-2 shards, bada radius (>50km) 3-5 shards — scatter-gather pattern. Per-shard dataset 10x kam hota hai, latency 5x behtar.
Q17Proximity search ke liye caching strategy kya hogi?
Multi-layer caching: (1) Result cache — poori query Redis me, key = hash(lat, lng, radius, filters), TTL 5 min, identical repeated queries serve karta hai. (2) Location cache — popular locations Redis GEOSPATIAL me (GEOADD restaurants:hot:{city_id}), TTL 10 min, 80% queries <5ms, LRU eviction, har city top 1000. (3) Application cache — API servers me in-memory LRU (Caffeine/Guava), 100 elements, <1ms bina network hop. (4) CDN cache — static metadata aur images edge par. Cache warming: background job top 100 queries per city identify karke peak se pehle pre-populate karta hai. Invalidation: location update par Redis Pub/Sub ya Kafka se broadcast karo, ya SCAN se keys dhoondh kar DEL karo, plus TTL se time-based expiry.
Q18Polygon-based search kaise karte ho — jaise delivery zone ya neighborhood?
PostGIS me: SELECT * FROM restaurants WHERE ST_Contains(ST_GeomFromGeoJSON('{polygon}'), location) — GeoJSON polygon me loop close karna zaroori hai (first point = last point), GIST index containment ko O(log N) me support karta hai. Elasticsearch me geo_polygon query hoti hai — 1000 vertices tak, polygon auto-close hota hai. Optimization: pehle polygon ka bounding box nikalo aur lat/lng range se pre-filter karo (90% candidates kam), phir exact ST_Contains. Complex polygons (1000+ vertices) ko Douglas-Peucker algorithm se 100-200 vertices tak simplify karo — 5-10x fast. Static zones ke liye har location ko zone_id assign karo — query WHERE zone_id = {id} ban jati hai, index se instant. Use cases: delivery zones, geofencing, neighborhood search.
Q19GIST index kya hai aur ye B-tree se kaise alag hai?
GIST (Generalized Search Tree) ek index framework hai jo R-tree structure banata hai — paas-paas ke points ko hierarchical bounding boxes me group karta hai. Root node saare points ka bounding box cover karta hai, children subregions cover karte hain, leaves me individual points. Query O(log N) me hoti hai — pehle bounding box intersect check, phir andar jao. B-tree sirf one-dimensional ordered values (numbers, strings) ke liye hota hai — jaise geohash column par LIKE queries. GIST multi-dimensional spatial data ke liye hai — points, polygons, containment, intersection queries. PostGIS me spatial queries ke liye GIST hi use hota hai.
Q20SRID 4326 kya hai aur ye kyun zaroori hai?
SRID 4326 WGS 84 coordinate system ka code hai — standard GPS coordinates (latitude/longitude) ka system. PostGIS me GEOGRAPHY(POINT, 4326) ka matlab hai location WGS 84 me store hai. ST_GeomFromText('POINT(77.5946 12.9716)', 4326) me 4326 hi SRID hai. Agar SRID galat ho to distances galat nikalti hain, kyunki database ko pata nahi hota coordinates kis system me hain. Interview me bol do: 4326 = WGS 84 = GPS standard.
Q21Elasticsearch me geo_bounding_box geo_distance se fast kyun hai?
geo_bounding_box sirf rectangular area check karta hai — point bounding box ke andar hai ya nahi, bas lat/lng range compare hoti hai, koi distance calculation nahi hoti. geo_distance har candidate ki exact distance nikalta hai (Haversine). Isi liye map viewport ke liye — jab user map scroll karta hai aur saare visible restaurants chahiye — geo_bounding_box best hai. Optimization pattern: pehle geo_bounding_box se candidates nikalo (fast), phir un par geo_distance lagakar exact circular radius filter karo.
Q22Vincenty vs Haversine — kab kis ko use karo?
Haversine fast hai — sphere maan kar great-circle distance nikalta hai, accuracy ±0.5%. Vincenty ellipsoid ko account karta hai — accuracy ±0.5mm, lekin computation 10x slow hai. Rule: aam proximity search, sorting aur filtering ke liye Haversine kaafi hai (Elasticsearch aur Redis bhi Haversine hi use karte hain). Jahan sub-meter accuracy chahiye — jaise surveying, precise PostGIS GEOGRAPHY queries — wahan Vincenty (PostGIS ST_Distance) use karo. Interview me bol do: Haversine fast + good enough, Vincenty exact + slow.
Q23Uber jaise system me drivers ki location real-time kaise track karte ho?
Drivers har 5 seconds me apni location Redis me GEOADD se update karte hain — upsert hota hai, purani location overwrite ho jati hai. Online drivers ki key par TTL lagate hain (EXPIRE drivers:online 3600) taaki inactive drivers auto-delete ho jayein. Nearby drivers dhoondhne ke liye GEORADIUS use hota hai — <10ms me aas-paas ke drivers distance ke saath mil jate hain. Har 60 seconds me batch sync se saari locations PostgreSQL PostGIS me persist hoti hain — Redis hot data, PostgreSQL source of truth. Sharding region ya geohash prefix se hoti hai (drivers:sf, drivers:nyc).
Q24Geohash LIKE query me 500 candidates mile, final 200 kaise bane?
Ye geohash ka square-vs-circle problem hai. LIKE '9q8yy%' se poora square cell milta hai (~2.4km box) — usme 500 restaurants ho sakte hain. Lekin user ko sirf exact 5km circular radius ke andar wale chahiye. Isi liye post-filter step hota hai: har candidate ki user se exact Haversine distance nikalo aur sirf distance ≤ 5km wale rakho — 500 me se 200 bachte hain. Ye do-step pattern interview me bolna zaroori hai: pehle index-based box filter (fast, approximate), phir exact distance filter (accurate).
Q25QuadTree me split kab hota hai aur moving objects kaise handle karte ho?
Jab kisi leaf node me points max capacity (jaise 100) se zyada ho jayein, to leaf 4 children me split hota hai aur saare points 4 quadrants me redistribute ho jate hain. Depth limit bhi hoti hai (jaise 20 levels) — uske baad split nahi hota. Moving objects (drivers) ke liye update = 2 operations: purani location remove karo, nayi location insert karo. Delete ke liye point ko deleted mark karte hain aur time-time par tree rebuild karke space reclaim karte hain. Tree rebalancing splits par overhead hai — ye QuadTree ka ek con hai.
Q26Elasticsearch eventual consistency ka matlab kya hai proximity search me?
Elasticsearch me document index karne ke baad wo turant search me nahi aata — refresh interval (~1 second) ke baad visible hota hai. Matlab restaurant add karne ke 1 second tak search results me nahi dikhega. Proximity search ke liye ye aam taur par acceptable hai — restaurant listings real-time nahi hoti. Lekin agar tumhe likhte hi padhna hai (read-your-writes) to PostgreSQL chahiye, jo ACID deta hai. Isi liye production hybrid me writes PostgreSQL me jati hain aur Elasticsearch search layer hota hai.
Q27Geo_point mapping me BKD tree kya karta hai?
Elasticsearch geo_point field ke liye andar BKD tree spatial index banata hai — ye multi-dimensional points ko efficiently organize karta hai taaki geo_distance aur geo_bounding_box queries fast chalein. BKD tree points ko dimensions ke hisaab se partition karta hai, jaise QuadTree karta hai lekin disk-based aur balanced tareeke se. Tumhe BKD tree ko manually configure nahi karna padta — geo_point type use karte hi Elasticsearch khud bana deta hai. 100M documents par bhi geo queries ~10-50ms me chalti hain.
Q28PostGIS me ST_DWithin aur ST_Distance me kya farak hai?
ST_DWithin boolean check hai — kya do geometries ek di gayi distance ke andar hain? Ye WHERE clause me use hota hai aur pehle bounding box se pre-filter karta hai (fast), phir exact check. ST_Distance asal distance value nikalta hai (meters me, GEOGRAPHY ke liye) — SELECT me use hota hai taaki results ko distance se sort kar sako. Pattern: WHERE ST_DWithin(..., 5000) se filter karo, SELECT ST_Distance(...) AS distance se sort karo. Dono ek saath use hote hain — pehla fast filter, doosra exact value.
Q29Geohash cell ka size latitude ke saath kyun badalta hai?
Geohash cells longitude direction me latitude par depend karte hain — kyunki 1 degree longitude ki asal doori cos(latitude) se badalti hai. Equator par cell lagbhag square hota hai, lekin poles ki taraf longitude compress hota hai to cells lambe-patie ho jate hain. Example: length 5 cell 4.9 km × 4.9 km equator ke paas square hai, lekin zyada latitude par width kam ho jati hai. Isi liye geohash approximate hai aur post-filter zaroori hai — cell size har jagah ek jaisa nahi hota.
Q30Millions of locations par lat/lng BETWEEN query kyun nahi chalani chahiye?
Simple WHERE lat BETWEEN ... AND lng BETWEEN ... bina index ke poori table scan karta hai — O(n). Millions of rows par ye seconds leta hai. Sahi tareeka: spatial index use karo — PostGIS me GIST index, geohash column par B-tree index, ya Redis GEORADIUS. Index ke saath lookup O(log n) ho jata hai. Bounding box BETWEEN tabhi use karo jab uske peeche index ho — warna wo bhi full scan hai. Interview me ye warning bolni hai: NEVER use simple lat/lng BETWEEN without spatial indexing for large datasets.
Q31Nearby search me LIMIT 20 kyun lagate ho? Saare results kyun nahi?
User waise bhi pehla page hi dekhta hai — 20 results ke baad wo scroll karega ya radius badhayega. Saare matches nikaalna (jaise 5km me 5000 restaurants) waste hai — sorting, serialization aur network cost badhta hai. Isi liye query me LIMIT 20 lagate hain aur lazy distance calculation karte hain — exact distance sirf displayed results ke liye nikalo. Pagination ke liye cursor-based approach use karo. Ye optimization Q3 ke 8-point answer ka hissa hai.
Q32Geofencing kya hai aur polygon search se kaise juda hai?
Geofencing matlab kisi polygonal boundary ke andar ya bahar hone ka check — jaise driver dispatch sirf ek zone ke andar, ya restaurant sirf apne delivery zone me orders accept kare. Implementation: zone ko GeoJSON polygon ke roop me store karo, phir ST_Contains(delivery_zone, customer_location) se check karo. Elasticsearch me geo_polygon query use hoti hai. Optimization: polygon ka bounding box pre-filter karo, complex polygons ko simplify karo, aur static zones ke liye har location ko zone_id assign karke query ko WHERE zone_id = {id} bana do — index se instant.
Q33Elasticsearch vs PostgreSQL — proximity search me kis ko chunoge?
Elasticsearch chuno jab: billions of documents hon, text + proximity search ek saath chahiye (pizza + 5km + rating), fast aggregations/facets chahiye, read-heavy workload ho — latency ~10-50ms, horizontal scaling. PostgreSQL (PostGIS) chuno jab: ACID chahiye, source of truth chahiye, complex spatial operations (polygons, buffers) chahiye, static data ho — latency ~50-100ms. Production me dono: ES reads ke liye, PG writes aur source of truth ke liye. Interview me ye trade-off bolna hi expected answer hai.
Q34S2 / H3 jaise systems geohash se kaise alag hain?
Geohash rectangular grid par based hai — cells latitude ke saath shape badalte hain aur boundary edge cases hote hain. H3 (Uber ka system) hexagonal grid use karta hai — har cell ke 6 neighbors equidistant hote hain, to edge cases kam hote hain aur har direction me uniform distance milti hai. S2 (Google ka system) sphere ko Hilbert curve se cells me divide karta hai — cells ka area zyada uniform hota hai. Is lesson me sirf Geohash aur QuadTree cover hain; H3/S2 ko interview me 'aage ka topic' kehkar mention kar sakte ho — agar interviewer poochhe to hexagon ka fayda bol do.
Q35Redis me 1M points kitni memory lete hain?
Redis me har point ~50 bytes leta hai (lat, lng, member name, geohash) — to 1M points ≈ 50MB. Capacity ~10M points per instance hoti hai (memory constraint) — uske baad sharding karni padti hai (region ya geohash prefix se). Compare karo: PostGIS GIST index table size ka ~10-20% hota hai, Elasticsearch geo_point ~16 bytes per location leta hai, QuadTree ka overhead ~100-200 bytes per node hota hai. Ye numbers section 13 ke key numbers se hain.
Q36Materialized views proximity search me kaise help karte hain?
Popular queries ko pre-compute karke rakh do — jaise har city ke liye 5km radius wale top restaurants. Ye materialized view hourly refresh hoti hai. Jab user wahi popular query kare, to calculation dobara karne ki jagah pre-computed result mil jata hai — latency bahut kam ho jati hai. Ye Q3 ke optimization list ka point 5 hai. Trade-off: data thoda stale ho sakta hai (hourly refresh), lekin read-heavy popular queries ke liye ye acceptable hai.
