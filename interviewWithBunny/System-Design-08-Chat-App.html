01Buniyaad

1. Functional Requirements

Chat app banane se pehle ye tay karna padta hai ki system ko kya-kya karna chahiye — matlab functional requirements. Interview me pehla sawaal hi ye hota hai: "System kya karega?" Is lesson me 8 features tay ki gayi hain, aur har feature ke peeche ek design decision chhupa hai.

8 features — ek-ek karke

  • Feature 1 — Register / Login: User phone number ya email se register aur login kar sake. Phone par OTP aata hai, email par password hota hai. Login ke baad JWT token milta hai jo 7 din tak valid rehta hai.
  • Feature 2 — One-to-one messaging: Do users ke beech text, image, video aur file bhejna. Ye sabse core feature hai — poora system isi ke aas-paas bana hai.
  • Feature 3 — Group messaging: Group banao, members add/remove karo, aur group admin controls (kaun add kar sakta hai, kaun remove kar sakta hai). Group ka design one-to-one se alag hota hai — ek message N members tak pahunchana padta hai.
  • Feature 4 — Media messages: Image, video — 100MB tak ki file bhej sakte ho. Media seedha server se nahi jaata, S3 presigned URL se upload hota hai (aage Section 06.6 me detail hai).
  • Feature 5 — Message history: Purane messages pagination ke saath nikalo — ek baar me 50 messages, phir scroll karne par aur. Poora history ek saath load karna system ko maar dega.
  • Feature 6 — Delivery aur read receipts: Single tick (sent), double tick (delivered), blue tick (read). Ye teen states hi chat app ki jaan hain — inke bina user ko pata hi nahi chalega message pahuncha ya nahi.
  • Feature 7 — Last seen status: User aakhri baar kab active tha — "Last seen 5 min ago" jaisa status dikhana.
  • Feature 8 — Online / offline status: Real-time presence indicator — saamne wala abhi online hai ya nahi, turant pata chalna chahiye.

Interview me ye kaise bolna hai

Seedha 8 features ginwa do, phir har feature ko ek line me uske design impact se jodo: "One-to-one messaging ke liye WebSocket chahiye, group messaging ke liye fanout chahiye, receipts ke liye status tracking chahiye, aur last seen ke liye heartbeat chahiye." Interviewer ko ye samajh aana chahiye ki tum feature ko sirf yaad nahi kar rahe — uska system par asar samajh rahe ho.

Yaad rakhne wali baat: Functional requirements hamesha user ki bhasha me likhe jate hain ("user ko ye karna chahiye"), implementation ki bhasha me nahi. WebSocket, Cassandra, Redis — ye sab baad me aate hain.

02Buniyaad

2. Non-Functional Requirements

Functional requirements batate hain system kya karega; non-functional requirements batate hain system kis scale aur kis quality par karega. Chat app ka poora design inhi numbers se tay hota hai — isliye ye section interview me sabse zyada puche jane wale numbers deta hai.

Scale — kitna bada system?

MetricNumberIska matlab
Total users1 Billion globallyPoori duniya ke users; user data PostgreSQL me
Daily active users (DAU)100MHar roz 100M log app kholte hain
Messages>100 Billion / day (1M+ msg/sec)Har second 10 lakh se zyada messages
Data volume100TB+ / dayText + media milakar roz 100TB se zyada
Concurrent connections10M–100M WebSocket connectionsEk hi time par karodo live connections

Performance — kitna fast, kitna reliable?

  • CAP Theorem — Availability >> Consistency: Chat app me availability sabse upar hai. Agar ek message doosre user ko 2 second late dikhe to chalega, lekin message bheja hi na ja sake to nahi chalega. Isliye eventual consistency acceptable hai — sab replicas turant sync hona zaroori nahi.
  • Message latency < 100ms: Online user ko message 100 millisecond se kam me milna chahiye. Lesson ka worked example batata hai ki asal flow sirf ~55ms leta hai (Section 12 me calculation hai).
  • Delivery guarantee — At-least-once: Message kam se kam ek baar to pahunchega hi — duplicate ho sakta hai, lekin lost nahi hoga. Duplicate ko message_id se dedupe karte hain. Exactly-once delivery chat jaise distributed system me bahut mehenga aur complex hota hai, isliye at-least-once + dedup hi sahi trade-off hai.
  • Highly reliable, no message loss: Message kabhi kho nahi sakta — isliye likhne ke do raste hain: Redis Stream (fast queue) + Cassandra (durable storage).
Interview tip: Numbers bolte time hamesha "kyun" bhi bolo — "100B messages/day ka matlab hai ~1.16M messages/sec, isliye hume write-optimized database (Cassandra) chahiye, read-optimized nahi." Number + uska design impact, dono bolo.

3. Core Entities

System ki duniya sirf 3 entities se banti hai. Interview me entities isliye puche jate hain kyunki inhi se database tables aur APIs nikalte hain — entity galat to schema galat, schema galat to poora design galat.

EntityFieldsKahan store hoti hai
Useruser_id, phone/email, username, profile_pic, last_seen, statusPostgreSQL (relational — profile, contacts, settings)
Message / Chatmessage_id, sender_id, receiver_id, content, type (text/image/video), timestampCassandra (write-heavy — 100B messages/day)
Groupgroup_id, name, members[], admin_ids[], created_atPostgreSQL (group metadata aur members list)

Har entity kyun zaroori hai

  • User: Pehchan ka sawaal — kaun bhej raha hai, kaun receive kar raha hai, aur wo online hai ya nahi. last_seen aur status presence system ki neev hain (Section 06.8).
  • Message: System ka sabse zyada likha jaane wala data. Iske fields se pata chalta hai ki message kis type ka hai, kab bheja gaya, aur kis state me hai (sent / delivered / read).
  • Group: Group chat ke liye alag entity isliye chahiye kyunki group ka ek message N members tak fanout hota hai — aur group ke members aur admins ka record alag se maintain karna padta hai.

Notice karo: message receiver_id group message ke liye null hota hai — group message me receiver ek user nahi, poora group hota hai. Isi liye Cassandra me group_messages ke liye alag table hai (Section 08).

API design me 3 groups hain — User operations, Messaging, aur Group operations. Dhyaan do: real-time kaam WebSocket (WS) se hota hai, baaki sab REST se. Ye farak interview me bahut pucha jata hai.

Diagram se extra APIs (image-only detail)

Lesson ke design diagram me do aur group APIs dikhaye gaye hain jo text me nahi hain — POST /v1/groups/{groupId}/add (member add karo) aur POST /v1/groups/{groupId}/remove (member hatao). 05High Level Design

5. High Level Design

High Level Design me 10 components hain. Flow seedha hai: Client → Load Balancer + API Gateway → alag-alag Services → unke Databases. Har service ka ek hi kaam hai, aur har service ka apna data store hai.

Diagram me kya dikhaya gaya hai

Diagram ke upar wale hisse me requirements, entities aur APIs likhe hain. Beech wale hisse (HLD) me user/client se requests LB + Gateway par aati hain, jahan authentication, authorization, routing aur rate limiting hota hai. Uske baad requests 3 services me batt ti hain: User Svc → UserDB, Chat Svc → Chat DB, Group Svc → Group DB.

Neeche wala hissa (LLD) detail me dikhata hai: CDN, User Svc → UserDB, Media Upload Svc → S3 (image/video), Msg Search Svc → Elastic Search, Group Svc → Group DB, Msg Svc, Chat Svc (WS) ke 3 instances, Redis Stream (messages, channel) → Notification Svc → FCM/APNS, Chat DB (Cassandra — writeDB, fields: id, chatId, messageId, senderId, receiverId, message, type, timestamp, deliveryStatus), Redis Cache — Websocket Registry (user1: webConnectConn1, TTL; user2, user3…), aur User management Svc jo user ka status aur last seen update karta hai.

Diagram ka 11-step Data Flow (sirf diagram me hai)

  1. User app kholta hai — WhatsApp WebSocket (request) backend ko jaata hai.
  2. Backend pehle check karta hai ki us user ka pehle se khula hua WebSocket connector hai ya nahi — hai to wahi return karo, nahi to naya banao.
  3. User1 message bhejta hai — send(msg, user1, user2).
  4. Chat service Redis check karti hai ki user2 active hai ya nahi.
  5. Agar active hai to message ko WebSocket server me daal kar push kar do; agar active nahi hai to Redis Stream (channel) me push kar do — offline mark karke.
  6. User1 ko single tick notification bhej do (sent).
  7. Agar user2 online hai to chat server channel ko subscribe karta hai, message consume karta hai aur receiver (user2) ko bhej deta hai.
  8. Message milne par user2 chat server ko acknowledgment bhejta hai.
  9. Chat Svc delivery/read receipt event ko sender (user1) ke Redis Stream (channel) me bhejti hai.
  10. Message Consumer Svc delivery/read receipt ko persist karta hai aur Chat DB me save karta hai.
  11. Group message ke case me Chat Svc pehle Group Svc se saare members check karti hai, phir Redis cluster se kaun online hai wo check karti hai — online hai to step 5 jaisa send karo, nahi to step 6 jaisa stream me daalo. Jab user kuch der baad online aata hai, to pehle Msg Svc se saare unread messages pull karta hai.

10 components — ek-ek karke

ComponentKaam
LB + API GatewayAuthentication, WebSocket upgrade, rate limiting — har request ka pehla gate
User Service → PostgreSQLUser profiles, contacts, settings store karta hai
Chat Service (WS) → WebSocket GatewayPersistent connections maintain karta hai, messages route karta hai
Group Service → PostgreSQLGroup metadata aur members manage karta hai
Media Upload Service → S3 (Blob)Images, videos, files store karta hai; delivery CDN se hoti hai
Message Service → CassandraMessages ka persistent storage — wide-column model
Redis StreamsOffline users ke liye message queue — online aate hi delivery
Redis CacheWebSocket registry (user_id → connection_id), online status, last seen
Notification Service → FCM/APNSOffline users ko push notification bhejta hai
ElasticsearchChat history me message search karta hai

Database chunne ki logic yaad rakho: User aur Group ka data relational hai (relations aur constraints chahiye) — isliye PostgreSQL. Messages ka data write-heavy hai (100B/day) — isliye Cassandra. Real-time lookup aur queue ke liye Redis. Search ke liye Elasticsearch. Har database apni strength ke liye chuna gaya hai — interview me yahi poochte hain.

06.1Deep Dive — Low Level

6.1 Registration & Login

Pehla step: user system me kaise aata hai. Register karte time phone number ya email — phone par OTP, email par password. Login ke baad JWT token milta hai jo har aage wali request me Authorization header me jaata hai.

Register flow

  1. User bhejta hai: POST /v1/user/register with {phone: '+1234567890'}
  2. User Service validate karti hai: phone number ka format sahi hai ya nahi, phir SMS se OTP bhejti hai (Twilio se)
  3. User OTP submit karta hai verification ke liye; service PostgreSQL me user record banati hai — {user_id: UUID, phone, username, created_at}

Login flow

  1. User bhejta hai: POST /v1/user/login with {phone, otp}
  2. Service OTP validate karti hai → JWT token generate karti hai — {user_id, exp: 7 days}
  3. Service return karti hai: {user_id, token, profile_data}
POST /v1/user/login — Response
{
  "user_id": "a1b2c3d4-...",
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "profile_data": { "username": "user_a", "phone": "+1234567890" }
}

JWT kyun: Token me user_id aur expiry (7 din) hoti hai, isliye har request par database me session check karne ki zaroorat nahi — gateway token verify karke user_id nikaal leta hai. 7 din baad token expire — dobara login karna padta hai.

06.2Deep Dive — Low Level

6.2 WebSocket Connection

Login ke baad client WebSocket connection kholta hai — ye connection tab tak zinda rehta hai jab tak user app band na kare ya network na toote. Isi ek connection par saare real-time kaam hote hain: message bhejna, message paana, presence, typing indicator.

Connection kaise banta hai — step by step

  1. Handshake: Client WebSocket handshake bhejta hai — WS /v1/connect with Authorization: Bearer {JWT}
  2. Validate: WebSocket Gateway JWT validate karta hai aur token se user_id nikaalta hai
  3. Register: Gateway connection ko Redis me register karta hai — HSET websocket_registry user_{user_id} {connection_id, server_instance, connected_at} — TTL=None (disconnect hone tak persistent)
  4. Status online: Gateway user ka status update karta hai — SET user:{user_id}:status 'online', aur Redis Pub/Sub channel user:{user_id}:presence par publish karta hai
  5. Subscribe: Client apne personal message channel messages:{user_id} aur presence updates ko subscribe karta hai
  6. Heartbeat: Client har 30 second me ping bhejta hai, server pong se jawab deta hai aur Redis me last_seen update karta hai
Redis — WebSocket Registry
HSET websocket_registry user_a1b2
  connection_id  "conn_9f31"
  server_instance "ws-gw-07"
  connected_at   "2026-01-20T10:00:00Z"

SET user:a1b2:status "online"
PUBLISH user:a1b2:presence {"status":"online"}
Yaad rakhne wali baat: Registry me connection_id ke saath server_instance bhi store hota hai — kyunki 100 gateway instances hain, aur message bhejte time system ko pata hona chahiye ki user kis instance se juda hai. Yehi sharding ka base hai (Section 10, Technique 1).

06.3Deep Dive — Low Level

6.3 One-to-One Message (Online)

Ye poore system ka sabse important flow hai — User1 User2 ko message bhejta hai aur User2 online hai. 8 steps, total ~55ms. Interview me ye flow bina ruke bolna aana chahiye.

  1. Send: User1 WebSocket se message bhejta hai — {type: 'text', receiver_id: user2, content: 'Hello', client_message_id: UUID}
  2. Validate: Chat Service check karti hai — User1 authenticated hai, receiver exist karta hai, content khaali nahi hai (<10KB text)
  3. Generate: Service server message_id (UUID) aur timestamp generate karti hai
  4. Lookup: Service Redis me check karti hai — HGET websocket_registry user_{user2} → connection_id mil gaya (User2 online hai)
  5. Deliver: Message turant User2 ke WebSocket connection par bhej diya jata hai (WebSocket Gateway ke through)
  6. Persist: Message Cassandra messages table me save hota hai — {message_id, sender_id: user1, receiver_id: user2, content, type: 'text', timestamp, status: 'delivered'}
  7. Receipt: User1 ko delivery receipt milti hai (double tick) WebSocket se
  8. Read: User2 jab message dekhta hai to read receipt bhejta hai — POST /v1/messages/{message_id}/read → status='read' update, User1 ko blue tick
WebSocket — Send Message
// Client -> Server
{ "type": "text",
  "receiver_id": "user2",
  "content": "Hello",
  "client_message_id": "c9d4e5f6-..." }

// Server -> Sender (delivery receipt)
{ "message_id": "m1a2b3c4-...",
  "status": "delivered",
  "delivered_at": "2026-01-20T10:00:00.055Z" }

Order notice karo: Deliver pehle hota hai, persist baad me — ya ulta bhi ho sakta hai, lekin lesson ke flow me delivery turant hoti hai aur Cassandra write saath-saath hoti hai. Dono me se koi bhi fail ho to at-least-once guarantee (Section 09) sambhal leti hai.

06.4Deep Dive — Low Level

6.4 Message (Offline Recipient)

Interview ka sabse favourite sawaal: "Recipient offline ho to message ka kya hoga?" Jawab ka structure yaad rakho — Redis Streams (queue) + Cassandra (persistence) + Push notification (alert). Teenon ek saath kaam karte hain.

  1. Send: User1 User2 ko message bhejta hai, jo offline hai
  2. Lookup: Service Redis check karti hai — HGET websocket_registry user_{user2} → null milta hai (offline)
  3. Queue: Service message ko Redis Stream me likhti hai — XADD stream:user:{user2}:messages * message_id {msg_id} sender_id {user1} content {text} timestamp {ts}
  4. Persist: Cassandra me bhi save hota hai (online case jaisa hi)
  5. Receipt: User1 ko single tick milta hai (sent — delivered abhi nahi)
  6. Push: Notification Service push notification trigger karti hai — FCM/APNS: "New message from User1: Hello"
  7. Reconnect: Jab User2 online aata hai — WebSocket connect hote hi service Redis Stream se unread messages pull karti hai — XREAD stream:user:{user2}:messages → WebSocket se deliver → acknowledge karke stream se delete → status 'delivered' update
Redis Stream — Offline Queue
XADD stream:user:user2:messages *
  message_id "m1a2b3c4-..."
  sender_id  "user1"
  content    "Hello"
  timestamp  "2026-01-20T10:00:00Z"

# User2 ke online aate hi:
XREAD COUNT 100 STREAMS stream:user:user2:messages 0
XDEL  stream:user:user2:messages m1a2b3c4-...
INTERVIEW FAVOURITE: Offline message handling ke 6 layers bolo — (1) Detection: registry me connection_id null = offline, (2) Redis Stream queueing: XADD se message stream me, (3) Cassandra persistence: Stream cache hai, Cassandra source of truth hai, (4) Push notification: FCM/APNS, (5) Reconnect par XREAD se fetch + deliver + XDEL, (6) Fallback: 7 din se purana message stream se expire ho gaya to Cassandra se nikalo.

06.5Deep Dive — Low Level

6.5 Group Messaging

Group messaging me ek message N members tak pahunchana hota hai. Sabse badi galti jo interview me log karte hain: har member ke liye message ki alag copy store karna. Sahi design: store once, fanout to many.

  1. Send: User group ko message bhejta hai — {group_id: 'group_123', content: 'Hello group'}
  2. Fetch members: Group Service Group DB se members nikaalti hai — SELECT members FROM groups WHERE group_id = 'group_123' → returns [user2, user3, user4, user5]
  3. Iterate: Service members list se guzarti hai, har member ka online status check karti hai
  4. Online members: Turant WebSocket se unke connections par deliver karo
  5. Offline members: Unke Redis Stream me likh do — stream:user:{member_id}:messages
  6. Store once: Cassandra group_messages table me message ki ek hi copy store hoti hai — {message_id, group_id, sender_id, content, timestamp}

Optimization yaad rakho: N members ke liye N copies mat banao — ek copy group_id ke saath store karo, aur retrieve karo (group_id, timestamp) index se. 1000 members wale group me bhi Cassandra write sirf 1 hoti hai; fanout 1000 WebSocket sends ya stream writes hote hain, jo parallel workers se <1s me ho jate hain.

WARNING: Group message bhejte time kabhi bhi saare members ke receive karne ka synchronously wait mat karo. Fanout-on-write with async delivery use karo — sender ko Cassandra write ke baad turant ACK mil jata hai, member delivery async (parallel workers se) hoti hai. Nahi to bade group me sender ka request timeout ho jayega.

06.6Deep Dive — Low Level

6.6 Media Upload (Image/Video)

100MB tak ki file server ke through bhejna bewakoofi hai — server ka bandwidth aur time dono barbaad hoga. Sahi tareeka: presigned URL — client file seedha S3 par upload kare, backend beech me na aaye.

  1. Request URL: Client mangta hai — POST /v1/media/upload/url with {file_type: 'image/jpeg', file_size: 2MB}
  2. Validate: Media Upload Service check karti hai — file size <= 100MB, type whitelist me hai (image/*, video/*, application/pdf)
  3. Presigned URL: Service 15 minute ke liye valid S3 PUT URL generate karti hai — s3://media-bucket/{user_id}/{message_id}/{filename}.jpg
  4. Return: Service deti hai — {upload_url, media_id}
  5. Direct upload: Client file seedha S3 par upload karta hai presigned URL se (badi files ke liye parallel upload)
  6. Send message: Client WebSocket se message bhejta hai — {type: 'image', receiver_id, media_id, thumbnail_url, metadata: {width, height, size}}
  7. Delivery: Chat Service message store karti hai jisme media_url S3 ki taraf point karta hai; receiver CDN URL se download karta hai — https://cdn.example.com/media/{media_id}
TIP: Direct S3 upload key optimization hai — latency backend se 5s se ghatkar direct 2s ho jati hai, aur 100MB files efficiently handle hoti hain. Upload complete hone par S3 Lambda trigger karta hai jo thumbnail banata hai — receiver ko pehle chhota thumbnail dikhta hai, full image click karne par CDN se aati hai. CDN ka cache hit rate 95% hai.

06.7Deep Dive — Low Level

6.7 Message History Retrieval

Chat kholte hi purane messages chahiye — lekin poora history ek saath nahi, pagination se. Pehle aakhri 50 messages, phir upar scroll karne par aur purane. Isi ko lazy loading kehte hain.

  1. Request: Client mangta hai — GET /v1/messages/{user_id}?limit=50&before={timestamp}
  2. Query: Chat Service Cassandra se query karti hai — dono directions ke messages ek hi partition me hote hain (sorted pair ki wajah se):
    Cassandra — History Query
    SELECT * FROM messages
WHERE (sender_id = {current_user} AND receiver_id = {user_id})
   OR (sender_id = {user_id} AND receiver_id = {current_user})
  AND timestamp < {before}
ORDER BY timestamp DESC
LIMIT 50;
  3. Model: Partition key = (user1_id, user2_id) sorted pair — taaki dono users ek hi partition query karein; clustering key = timestamp DESC
  4. Response: Service deti hai — {messages: [{message_id, sender_id, content, timestamp, status}], has_more: true, next_before: {oldest_timestamp}}
  5. Render: Client messages ko reverse order me dikhata hai (naya message neeche), aur upar scroll karne par lazy load karta hai

Kyun fast hai: Query ek hi partition ko hit karti hai (conversation_id se), aur clustering key ki wajah se messages pehle se timestamp ke hisaab se sorted hain — O(log N + 50) time me aakhri 50 messages mil jate hain. Cursor-based pagination hai (before=timestamp) — offset-based nahi, isliye 10,000 messages ke baad bhi slow nahi hota.

6.8 Last Seen & Online Status

Presence system ka poora raaz ek chhoti si cheez me hai: Redis key with 60 second expiry (TTL). Client har 30 second me ping bhejta hai, key zinda rehti hai; ping rukte hi 60 second me key expire — user apne aap offline.

  1. Heartbeat: Client har 30 second me WebSocket se ping bhejta hai
  2. Update: Chat Service Redis update karti hai — SET user:{user_id}:last_seen {current_timestamp} EX 60 (60s expiry)
  3. Online check: Agar last_seen key maujood hai aur uski age < 60s hai → user 'online' hai, nahi to 'offline'
  4. Last seen display: Jab User2 User1 ka status puche — GET user:{user1}:last_seen → key hai to "Last seen 5 min ago" calculate karo; expire ho gayi to "Last seen today at 10:30 AM" dikhao
  5. Broadcast: Jab User1 offline hota hai (WebSocket disconnect) → Redis Pub/Sub channel user:{user1}:presence par publish karo — {status: 'offline', last_seen: timestamp}
  6. Subscribers: User1 ke contacts jo online hain, unhe apne WebSocket connections se presence update milta hai → UI update hoke 'offline' dikhata hai
Redis — Presence Keys
# Har 30s heartbeat par:
SET user:user1:last_seen 1737364800 EX 60

# Status check:
GET user:user1:last_seen   -> "1737364800"  (online)
# key missing              -> offline, PostgreSQL se
#                             last_seen_timestamp dikhao

# Disconnect par broadcast:
PUBLISH user:user1:presence
  {"status":"offline","last_seen":1737364800}
TIP: Heartbeat-based presence with Redis TTL — client har 30s ping bhejta hai, server last_seen ko EX 60 ke saath update karta hai. Client mar jaye to TTL 60s me expire — automatic offline status. Koi manual cleanup nahi chahiye, Redis khud sambhal leta hai. Aur optimization: har heartbeat broadcast mat karo — sirf status change (online ↔ offline transitions) broadcast karo. Scaling: 100M active users × 1 heartbeat/30s = 3.3M updates/sec — Redis SET O(1) hai, sambhal leta hai.

6.9 Read Receipts & Delivery Status

Ticks ka system: sent (single tick) → delivered (double tick) → read (blue tick). Har state change ek event hai — Cassandra me status update hota hai aur sender ko WebSocket se tick bheja jata hai.

  • Sent (single tick): Jab message Cassandra me persist ho jata hai, sender ko sent receipt milti hai
  • Delivered (double tick): Jab message recipient tak pahuncha — ya to WebSocket se (online) ya Redis Stream me likha gaya (offline) — tab message ka status Cassandra me 'delivered' update hota hai aur sender ko double tick bheja jata hai
  • Read (blue tick): Jab recipient ki app message display karti hai (onVisible event), client bhejta hai POST /v1/messages/{message_id}/read → status='read' update → sender ko WebSocket se blue tick
  • Group read receipts: Har member ka read status alag track hota hai — {message_id → {user2: read, user3: delivered, user4: read}} — UI me dikhta hai "Read by 2 of 3"

Scale ka hisaab: 1B messages/day × 3 status updates (sent, delivered, read) = 3B writes/day. Cassandra isko sambhal leti hai — partition message_id se hoti hai, aur idempotency ke liye lightweight transactions use hote hain.

Optimization: Har message ke liye alag API call mat bhejo — read receipts ko batch karo: 10 message_ids ek hi request me. Isse API calls 10x kam ho jati hain.

6.11 WebSocket Reconnection & Sync

Network kabhi bhi toot sakta hai — train tunnel me gayi, WiFi badla, phone ka data off hua. Reconnection ka design isliye hai taaki koi message na khoye aur koi duplicate na dikhe.

  1. Disconnect: Network failure ki wajah se WebSocket connection toot jata hai
  2. Reconnect: Client handshake me bhejta hai — last_received_message_id ya last_sync_timestamp
  3. Fetch: Service missed messages nikaalti hai — Redis Stream se + Cassandra se WHERE timestamp > last_sync_timestamp ORDER BY timestamp
  4. Deliver: Missed messages ka batch chronological order me deliver hota hai
  5. Deduplicate: Client message_id (server-generated UUID) se dedupe karta hai — jo message pehle mil chuka hai wo dobara nahi dikhata
  6. Cleanup: Delivery acknowledge hone ke baad messages Redis Stream se delete — XDEL stream:user:{user_id}:messages {message_id}

9. Message Delivery Guarantee

Chat app ka sabse bada vaada: message kabhi lost nahi hoga. Guarantee ka naam hai at-least-once delivery — message kam se kam ek baar pahunchega, duplicate ho sakta hai. Duplicate se darr nahi — dedup se sambhalte hain.

At-Least-Once Delivery Strategy

  • Trigger: User message bhejta hai — system ensure karta hai ki wo kam se kam ek baar deliver ho (duplicate ho sakta hai)
  • Acknowledgment chain: Client → WebSocket Gateway (ack1) → Cassandra write (ack2) → Recipient delivery / stream write (ack3)
  • Client retry: Agar 5 second me ack1 nahi aaya to client wahi client_message_id se dobara bhejta hai
  • Server deduplication: Insert karne se pehle check karo ki message_id Cassandra me hai ya nahi — hai to ack return karo (idempotent)
  • Recipient deduplication: Client aakhri 1000 message_id ka set maintain karta hai — duplicate dikhe to ignore karo

11. Common Interview Questions

Lesson ke 10 interview Q&A — ye wahi sawaal hain jo interviewer sabse zyada puchte hain. Har jawab poora padho; FAQs tab me inke alawa 26 aur sawaal hain.

Q1. Recipient offline ho to message deliver kaise hoga?

Multi-layer offline handling: (1) Detection — message bhejte time Redis websocket_registry me recipient ka connection_id check karo, null mila to offline hai. (2) Redis Stream queueing — XADD stream:user:{recipient_id}:messages se message stream me likho, jab tak user online na aaye tab tak rehta hai. (3) Cassandra persistence — saath me Cassandra me bhi likho (Stream cache hai, Cassandra source of truth hai). (4) Push notification — FCM/APNS se "New message" notification. (5) Reconnect par — WebSocket connect hote hi XREAD stream:user:{recipient_id}:messages 0 se saare queued messages fetch karo, WebSocket se deliver karo, client acknowledge kare, phir XDEL se stream se delete karo. (6) Fallback — 7 din se purane messages stream se expire ho gaye to Cassandra se nikalo. Example: User A offline User B ko bhejta hai → Cassandra + Stream + push → B 1 ghante baad online aata hai → 15 queued messages milte hain → stream clear → ab naye messages real-time me milenge.

Q2. Read receipts aur delivery status scale par kaise implement karoge?

Event-driven status tracking: (1) Sent — message Cassandra me likhte hi status='sent', sender ko WebSocket se single tick. (2) Delivered — message recipient tak pahuncha (WebSocket se online ho, ya Stream me likha gaya offline ho) to Cassandra me status='delivered', sender ko double tick WebSocket event se — {message_id, status: 'delivered', delivered_at}. (3) Read — recipient ki app message display kare (onVisible/onScroll event) to client POST /v1/messages/{message_id}/read bhejta hai → status='read' → sender ko blue tick. (4) Group read receipts — groups ke liye Cassandra me map maintain karo — {message_id → {user2: {status: 'read', read_at}, user3: {status: 'delivered'}}} — query karke "Read by 5 of 10 members" dikhao. (5) Optimization — read receipts batch karo: ek message ke liye ek API call nahi, 10 message_ids ek request me. Scaling: 1B messages/day × 3 status updates = 3B writes/day — Cassandra partition by message_id se sambhal leti hai, idempotency ke liye lightweight transactions.

Q3. Message bhejte beech me WebSocket connection toot jaye to kya hoga?

Client-side retry with idempotency: (1) Client pehle client_message_id (UUID) generate karta hai. (2) Send — WebSocket se {type: 'message', client_message_id, receiver_id, content} bhejta hai. (3) ACK wait — server ACK ka wait karta hai — {client_message_id, server_message_id, status: 'sent'}. (4) Connection toote — 5 second me ACK nahi aaya to failure maan lo. (5) Reconnection — exponential backoff se reconnect (1s, 2s, 4s, 8s). (6) Retry — wahi client_message_id se dobara bhejo. (7) Server dedup — server check karta hai ki is client_message_id wala message Cassandra me hai ya nahi (lightweight transaction ya SELECT before INSERT) — hai to bina dobara insert kiye purana server_message_id return kar do. (8) Client reconciliation — client local DB me client_message_id → server_message_id mapping update karta hai. Edge case: message gaya lekin ACK network me kho gaya → client retry karta hai → server duplicate pehchan kar success return karta hai → client UI update karta hai. Result: at-least-once delivery, koi message lost nahi, dedup client side client_message_id + server_message_id mapping se.

Q4. Last seen aur online status efficiently kaise handle karoge?

Heartbeat-based presence: (1) Online detection — WebSocket connect hote hi Redis key user:{user_id}:status='online' set karo, aur user:{user_id}:last_seen current timestamp ke saath EX 60 (60s expiry). (2) Heartbeat — client har 30s ping bhejta hai, server last_seen update karta hai, TTL 60s reset karta hai. (3) Offline detection — 2 consecutive pings miss (60s) hue to last_seen key expire, user offline. (4) Last seen calculation — status query karte time GET user:{user_id}:last_seen — key hai to 'online', nahi hai to offline — PostgreSQL me disconnect par store kiya gaya last_seen_timestamp se "Last seen 2 hours ago" dikhao. (5) Presence broadcasting — offline hote hi Redis Pub/Sub channel user:{user_id}:presence par {status: 'offline', last_seen: timestamp} publish karo — saare subscribers (contacts) ko unke WebSocket se update milega. (6) Privacy — user last seen disable kar sakta hai, tab "Last seen recently" dikhao exact timestamp ki jagah. Optimization: har heartbeat broadcast mat karo (har 30s), sirf status change (online ↔ offline) broadcast karo. Scaling: 100M active users × 1 heartbeat/30s = 3.3M updates/sec — Redis SET O(1) hai aur Pub/Sub 100K msg/sec per instance handle karta hai.

Q5. Cassandra me message schema efficient queries ke liye kaise design karoge?

Wide-column model: (1) Partition key — conversation_id (do user_ids ka deterministic pair: sorted — taaki dono users ek hi partition query karein), jaise User A aur User B ke beech conversation → conversation_id = sha256(min(user_A, user_B) + max(user_A, user_B)). (2) Clustering key — timestamp DESC (messages naye se purane sort hote hain), pagination ke liye efficient range queries. (3) Query pattern — SELECT * FROM messages WHERE conversation_id = {id} AND timestamp < {before} ORDER BY timestamp DESC LIMIT 50 — single partition hit, O(log N + 50) time. (4) Denormalization — har row me sender_id aur receiver_id dono store karo bidirectional queries ke liye. (5) Write optimization — Cassandra writes ke liye optimized hai (append-only, no read-before-write), 100K writes/sec per node handle karti hai. (6) TTL — purane messages auto-delete 2 saal baad. Group messages: alag table group_messages — partition_key=group_id, clustering_key=timestamp DESC. Index strategy: secondary indexes ki zaroorat nahi, primary key design saare query patterns handle kar leta hai. Example: User A aur User B ke beech 1 saal me 10K messages → ek hi partition me store, aakhri 50 messages <10ms me milte hain.

Q6. Group messaging efficiently kaise implement karoge?

Fanout-on-write with optimization: (1) Ingestion — user group ko message bhejta hai {group_id: 'group_123', content: 'Hello'}. (2) Member retrieval — PostgreSQL se SELECT member_ids FROM groups WHERE group_id = 'group_123' → [user2, user3, user4, user5]. (3) Storage — Cassandra group_messages table me message ki ek hi copy likho — partition_key=group_id, clustering_key=timestamp DESC. (4) Fanout — har member ke liye: (a) Redis websocket_registry se online check karo, (b) online hai to WebSocket se turant deliver karo, (c) offline hai to Redis Stream stream:user:{member_id}:messages me group message_id ka pointer likho. (5) Read receipts — read_by set<uuid> se per-member read status track karo, "Read by 3 of 4" dikhao. Optimization: 4 members ke liye 4 copies mat banao — ek baar store karo group_id se, members SELECT * FROM group_messages WHERE group_id = 'group_123' ORDER BY timestamp DESC se retrieve karein. Bade groups (>100 members): fanout delivery paginate karo, async processing ke liye Kafka use karo taaki sender block na ho, 100 members ko parallel batches me bhejo. Example: 1000-member group, ek message → Cassandra me 1 write → 1000 members ko fanout (1000 WebSocket sends ya stream writes) → parallel workers se <1s me complete.

Q7. Media upload aur delivery strategy kya hai?

Direct S3 upload with presigned URLs: (1) Client request — POST /v1/media/upload/url with {file_type: 'image/jpeg', file_size: 5MB}. (2) Validation — Media Service check karti hai file_size <= 100MB, type whitelist me hai [image/*, video/*, application/pdf, audio/*]. (3) Presigned URL — S3 presigned PUT URL generate karo key media/{user_id}/{message_id}/{uuid}.jpg, 15 min valid. (4) Client upload — client file seedha S3 par upload karta hai backend bypass karke, progress bar dikhta hai. (5) Upload complete — S3 object creation par Lambda trigger hota hai, thumbnail generate karta hai aur media/{user_id}/{message_id}/thumb.jpg me store karta hai. (6) Message send — client chat message bhejta hai {type: 'image', media_id, media_url, thumbnail_url, metadata: {width: 1920, height: 1080, size: 5MB}}. (7) Delivery — recipient ko thumbnail_url milta hai (chhota, fast load), click karne par full image CDN se aati hai — https://cdn.example.com/media/{media_id}. (8) CDN — CloudFront edge locations par cache karta hai, 95% cache hit rate, S3 reads aur latency kam. Optimization: videos ke liye adaptive bitrate (MediaConvert se transcoding), images ke liye progressive JPEG. Security: expiry wale presigned URLs unauthorized access rokte hain. Example: User 20MB video bhejta hai → presigned URL 50ms me → S3 upload 30s me → Lambda 720p, 480p, 360p transcode karta hai (2 min) → recipient thumbnail turant load karta hai, video CDN se adaptive quality me stream hoti hai.

Q8. Typing indicators real-time me kaise implement karoge?

Ephemeral event broadcasting via WebSocket: (1) Typing start — user type karna shuru kare to client {type: 'typing_start', chat_id: {receiver_id}} WebSocket se bhejta hai. (2) Throttling — client typing events ko throttle karta hai (zyada se zyada 1 event per 3 seconds) taaki traffic kam ho. (3) Server broadcast — WebSocket Gateway check karta hai receiver online hai ya nahi, hai to receiver ke connection par broadcast karo {type: 'typing', user_id: {sender_id}}. (4) Client display — receiver ki UI "[Name] is typing..." indicator dikhati hai. (5) Typing stop — 3 second tak type na karo ya message bhej do to client {type: 'typing_stop'} bhejta hai, server broadcast karta hai, receiver indicator chhupata hai. (6) No persistence — typing events database ya Redis me store NAHI hote, poori tarah ephemeral hain (load kam hota hai). Group typing: same flow, lekin sender ke alawa saare online group members ko broadcast hota hai. Scaling: 100M concurrent users, 10% ek time par type kar rahe hain = 10M typing events, lekin 1 event per 3s throttle se = 3.3M events/sec — WebSocket Gateway direct forwarding se handle karta hai (koi DB write nahi). Alternative: Redis Pub/Sub — channel typing:{chat_id} par publish karo, subscribers ko update mile, lekin 1-to-1 chat ke liye WebSocket direct routing simple aur fast hai.

Q9. Message ordering kaise karoge aur race conditions kaise rokoge?

Server-assigned timestamps with Lamport clocks: (1) Client-side timestamp — client message bhejte time apna local_timestamp bhejta hai (optimistic UI update ke liye). (2) Server timestamp — server authoritative server_timestamp (millisecond precision) assign karta hai jab message receive hota hai — ordering isi se hoti hai. (3) Cassandra clustering — messages server_timestamp DESC clustering key se store hote hain, consistent ordering milti hai. (4) Race scenario — do messages ek saath aaye alag clients se (A ne M1 bheja, B ne M2, ek hi chat me). (5) Server serialization — WebSocket Gateway har chat ke messages ko sequentially process karta hai (queue ya single-threaded event loop per chat), arrival order se timestamps T1, T2 assign karta hai jahan T1 < T2. (6) Client reconciliation — clients ko temporarily alag order dikh sakta hai (optimistic UI), lekin Cassandra se fetch karne par sabko ek hi order dikhta hai (server_timestamp se). (7) Logical clocks — distributed servers ke beech causal ordering ke liye Lamport timestamps ya vector clocks use karo. Edge case: Client A ki ghadi 5 minute aage hai, future timestamp wala message bhejta hai → server client timestamp ignore karta hai, server_timestamp use karta hai → ordering kharab nahi hoti. Example: User A M1 bhejta hai 10:00:00.100 (client time), User B M2 bhejta hai 10:00:00.050 (client time) → server ko M1 pehle milta hai (T=1000), M2 baad me (T=1001) → saare clients ko M1 pehle, M2 baad me dikhta hai, client timestamps se koi farak nahi padta.

Q10. Chat data ke liye disaster recovery strategy kya hai?

Multi-region replication with backup: (1) Cassandra replication — primary region (us-east-1) me RF=3 (replication factor) multi-datacenter replication, async replication secondary region (us-west-2) me. (2) Write consistency — QUORUM writes (3 me se 2 replicas acknowledge karein) — durability aur latency ka balance. (3) Read consistency — ONE reads (sabse fast response) — chat ke liye eventual consistency acceptable hai. (4) Failure scenarios — 1 node fail ho to baaki 2 replicas requests serve karte hain, QUORUM se writes phir bhi succeed hote hain. (5) Region failover — primary region down ho to DNS failover secondary region (us-west-2) par <5 min me (RTO), secondary ke paas saara data replica hai (RPO=1 min, async replication lag). (6) Redis persistence — Redis AOF (Append-Only File) + RDB snapshots — Redis crash ho to snapshots + Cassandra se rebuild karo (offline messages). (7) S3 replication — media bucket ke liye cross-region replication enable karo, media dono regions me available. (8) Backup strategy — Cassandra ke daily snapshots S3 par, 30 din retention, point-in-time recovery possible. Testing: monthly DR drills — region failure simulate karo, failover automation validate karo. Example: Primary region outage → DNS 3 min me secondary par switch → users WebSockets se secondary region se reconnect → message history replicated Cassandra se load → <5 min disruption ke saath service chalti rehti hai.

Interview FAQs — 36 sawaal

Interview me sabse zyada puche jane wale 36 sawaal — har jawab wahi hai jo is SPA ke sections me detail me samjhaya gaya hai. Kisi bhi sawaal par click karke jawab kholo.

Q01 Chat app ke liye WebSocket kyun chahiye, HTTP polling kyun nahi?
HTTP polling me client ko baar-baar server se puchna padta hai 'koi naya message hai?' — 10M users har 1 second poll karein to 10M requests/sec ka unnecessary load ban jata hai. WebSocket ek baar connect hone ke baad persistent bidirectional connection deta hai — server khud message push kar sakta hai jab bhi aaye. Isse latency <100ms milti hai aur server load bahut kam hota hai. Isliye real-time messaging me WebSocket mandatory hai, polling kabhi nahi.
Q02 Recipient offline ho to message kaise deliver hota hai?
Teen layers ek saath kaam karte hain: pehle Redis websocket_registry check karo — connection_id null mila to recipient offline hai. Phir message ko Redis Stream me likho (XADD stream:user:{recipient_id}:messages) — stream 7 din tak message hold karti hai. Saath me Cassandra me bhi persist karo (Stream cache hai, Cassandra source of truth hai). Phir FCM/APNS se push notification bhejo. Jab recipient online aata hai, WebSocket connect hote hi XREAD se queued messages fetch hote hain, deliver hote hain, aur XDEL se stream se delete hote hain. 7 din se purane messages stream se expire ho gaye to Cassandra se fallback milta hai.
Q03 Read receipts aur delivery status scale par kaise implement karte hain?
Event-driven status tracking hoti hai: message Cassandra me likhte hi status='sent' aur sender ko single tick; recipient tak pahuncha (WebSocket ya Stream) to status='delivered' aur double tick; recipient ki app message display kare (onVisible event) to client POST /v1/messages/{message_id}/read bhejta hai aur sender ko blue tick milta hai. Groups me per-member map maintain hota hai aur UI 'Read by 5 of 10 members' dikhata hai. Optimization: receipts ko batch karo — 10 message_ids ek request me. Scale: 1B messages/day × 3 status updates = 3B writes/day, Cassandra partition by message_id se sambhal leti hai.
Q04 WebSocket connection beech me toot jaye to message lost hoga ya duplicate?
Na lost hoga, na duplicate dikhega — client-side retry with idempotency se. Client bhejne se pehle client_message_id (UUID) generate karta hai aur server ACK ka 5 second wait karta hai. ACK nahi aaya to exponential backoff (1s, 2s, 4s, 8s) se reconnect karke wahi client_message_id se dobara bhejta hai. Server insert se pehle check karta hai ki ye client_message_id Cassandra me hai ya nahi — hai to bina dobara insert kiye purana server_message_id return kar deta hai. Client apne paas last 1000 message_ids ka set rakhkar duplicate ignore bhi karta hai. Result: at-least-once delivery, zero loss.
Q05 Last seen aur online status efficiently kaise handle karte hain?
Heartbeat-based presence system: client har 30 second me WebSocket ping bhejta hai, server Redis me SET user:{user_id}:last_seen {timestamp} EX 60 karta hai. Key maujood hai aur age <60s hai to user online, nahi to offline — 2 consecutive pings miss hote hi key expire ho jati hai aur status apne aap offline ho jata hai, koi manual cleanup nahi chahiye. Offline hote hi Redis Pub/Sub channel user:{user_id}:presence par publish hota hai aur saare online contacts ko update mil jata hai. Privacy ke liye user last seen disable kar sakta hai — tab 'Last seen recently' dikhta hai. Scale: 100M users × 1 heartbeat/30s = 3.3M updates/sec, Redis SET O(1) hai isliye sambhal leta hai. Sirf status change broadcast karo, har heartbeat nahi.
Q06 Cassandra me message schema kaise design karte hain?
Wide-column model: partition key conversation_id hai — do user_ids ka deterministic sorted pair, jaise sha256(min(user_A, user_B) + max(user_A, user_B)) — taaki dono users ek hi partition query karein. Clustering key timestamp DESC hai — messages naye se purane sort hote hain aur pagination ke liye range queries efficient hoti hain. Query hoti hai: SELECT * FROM messages WHERE conversation_id = {id} AND timestamp < {before} ORDER BY timestamp DESC LIMIT 50 — single partition hit, O(log N + 50) time. Har row me sender_id aur receiver_id dono store karte hain (denormalization). Secondary indexes ki zaroorat nahi — primary key design saare query patterns handle kar leta hai. Group messages ke liye alag table group_messages hai, partition_key=group_id.
Q07 Group messaging efficiently kaise implement karte hain?
Fanout-on-write with store-once optimization: message bhejta hai to pehle Group DB se members nikalo, phir Cassandra group_messages table me message ki EK hi copy likho (partition_key=group_id). Phir har member ke liye online check karo — online hai to WebSocket se turant deliver, offline hai to uske Redis Stream me pointer likh do. 4 members ke liye 4 copies banana galat hai; 1000-member group me bhi Cassandra write sirf 1 hoti hai aur fanout 1000 sends parallel workers se <1s me ho jata hai. Bade groups (>100 members) me fanout paginate karo aur async processing ke liye Kafka use karo taaki sender block na ho. Read receipts read_by set<uuid> se track hote hain — 'Read by 3 of 4' dikhta hai.
Q08 Media upload aur delivery strategy kya hoti hai?
Direct S3 upload with presigned URLs: client POST /v1/media/upload/url bhejta hai (file_type, file_size), Media Service validate karti hai (<=100MB, whitelist type), phir 15 minute valid S3 presigned PUT URL generate karti hai. Client file seedha S3 par upload karta hai — backend beech me nahi aata, isliye latency 5s se 2s ho jati hai. Upload complete hote hi S3 Lambda trigger karta hai jo thumbnail banata hai. Phir client chat message bhejta hai jisme media_url aur thumbnail_url hote hain. Receiver ko pehle thumbnail dikhta hai, full media CDN (CloudFront, 95% cache hit rate) se aati hai. Videos ke liye adaptive bitrate transcoding hoti hai, images ke liye progressive JPEG.
Q09 Typing indicators real-time me kaise implement karte hain?
Ephemeral event broadcasting: user type karna shuru kare to client {type:'typing_start', chat_id} WebSocket se bhejta hai, lekin throttle ke saath — zyada se zyada 1 event per 3 seconds. Server check karta hai receiver online hai ya nahi, hai to uske connection par {type:'typing', user_id} broadcast karta hai aur receiver ki UI '[Name] is typing...' dikhati hai. 3 second rukne ya message bhejne par typing_stop jata hai. Typing events database ya Redis me KABHI store nahi hote — poori tarah ephemeral hain, warna 1B+ unnecessary writes/day ban jayenge. Groups me sender ke alawa saare online members ko broadcast hota hai. Scale: 100M users me 10% type kar rahe hon to bhi throttle se 3.3M events/sec rehte hain, WebSocket Gateway direct forwarding se handle kar leta hai.
Q10 Message ordering kaise karte hain aur race conditions kaise rokte hain?
Server-assigned timestamps: client apna local_timestamp bhejta hai sirf optimistic UI ke liye, lekin ordering hamesha server_timestamp (millisecond precision) se hoti hai. WebSocket Gateway har chat ke messages ko sequentially process karta hai (queue ya single-threaded event loop per chat) aur arrival order se timestamps assign karta hai. Cassandra me clustering key server_timestamp DESC hai, isliye fetch karne par sabko ek hi order dikhta hai. Agar client ki ghadi 5 minute aage hai aur wo future timestamp bhejta hai, server usko ignore karke apna timestamp use karta hai. Distributed servers ke beech causal ordering ke liye Lamport timestamps ya vector clocks use karte hain.
Q11 Chat data ki disaster recovery strategy kya hai?
Multi-region replication: primary region (us-east-1) me Cassandra RF=3, async replication secondary region (us-west-2) me. Writes QUORUM consistency (3 me se 2 acknowledge), reads ONE (fastest) — chat ke liye eventual consistency acceptable hai. 1 node fail ho to baaki 2 replicas serve karte hain. Region down ho to DNS failover <5 min me (RTO), data replica ki wajah se RPO <1 min hai. Redis ke liye AOF + RDB snapshots — crash ho to snapshots + Cassandra se rebuild. S3 media ke liye cross-region replication. Daily Cassandra snapshots S3 par, 30 din retention, point-in-time recovery possible. Monthly DR drills se failover automation validate karte hain.
Q12 Messages ke liye Cassandra kyun, PostgreSQL kyun nahi?
Messages write-heavy hain — 100B/day, matlab 1M+ writes/sec. PostgreSQL row-based relational database hai, is scale par writes aur storage dono me bottleneck ban jata hai. Cassandra wide-column, append-only aur write-optimized hai — 100K writes/sec per node handle karti hai, partition key se data distribute hota hai, aur TTL se purana data auto-delete hota hai. PostgreSQL sirf wahan use hota hai jahan relations aur constraints chahiye — User profiles aur Group metadata. Har database apni strength ke liye chuna gaya hai.
Q13 Redis Streams vs Kafka — offline queue ke liye Redis Streams kyun?
Redis Streams is design me isliye hai kyunki wo Redis ke andar hi hai — jahan websocket_registry aur presence data pehle se hai, wahi queue bhi mil jati hai, alag system chalane ki zaroorat nahi. XADD/XREAD/XDEL commands simple hain aur per-user stream (stream:user:{user_id}:messages) se consumer groups ke bina kaam chal jata hai. Kafka tab use karte jab fanout bahut bada ho (bade groups ke async processing ke liye lesson me Kafka ka naam aata hai) ya cross-service event streaming chahiye. Dono valid hain — interview me trade-off bolo, ek ko 'best' mat bolo.
Q14 Conversation_id deterministic kyun banana chahiye?
Kyunki User A User B ko message bhejta hai ya User B User A ko — dono cases me conversation ek hi hai. Agar conversation_id ko sorted pair se banaya jaye (min + max), to dono users hamesha ek hi partition query karte hain aur history dono taraf se ek jaisi milti hai. Agar random id hoti to A ki taraf aur B ki taraf alag partitions ban jate aur history merge karni padti. Deterministic id se single-partition query, O(log N + 50) read aur simple pagination milti hai.
Q15 At-least-once delivery kya hai aur exactly-once kyun nahi?
At-least-once ka matlab hai message kam se kam ek baar to pahunchega hi — duplicate ho sakta hai, lost nahi hoga. Exactly-once distributed system me bahut mehenga hai — iske liye distributed transactions aur complex coordination chahiye, aur network partitions me practically impossible ke kareeb hai. Chat me duplicate acceptable hai kyunki client message_id se dedupe kar leta hai aur user ko duplicate dikhta hi nahi. Isliye at-least-once + dedup sahi trade-off hai: simple, fast aur reliable.
Q16 100B messages/day ka system design karte time pehle kya sochna chahiye?
Pehle numbers se back-of-envelope calculation karo: 100B/day matlab ~1.16M messages/sec average, peak usse 2–3x. Phir CAP trade-off tay karo — chat me availability >> consistency. Phir write path socho — write-optimized store (Cassandra), read path — partition key se single-partition reads. Phir real-time layer — WebSocket sharding (100K connections per instance). Phir failure modes — offline queue, retry, dedup, DR. Interview me seedha components ginwane se pehle ye calculation bolna zaroori hai — isse pata chalta hai ki design numbers se nikla hai, ratta nahi.
Q17 WebSocket sharding kaise kaam karta hai?
Consistent hashing se: hash(user_id) % num_instances — har user hamesha usi gateway instance se judta hai jis par uska hash padta hai. Isse 100K connections per instance se 100M connections tak horizontal scaling hoti hai — instances badhao, load batt jata hai. Session continuity bhi bani rehti hai kyunki user reconnect par bhi usi instance par aata hai. Registry me server_instance store isiliye hota hai taaki message bhejte time pata chale ki recipient kis instance se juda hai.
Q18 Message history pagination cursor-based kyun hoti hai, offset-based kyun nahi?
Offset-based pagination (LIMIT 50 OFFSET 10000) me database ko 10,050 rows scan karni padti hain sirf aakhri 50 dene ke liye — jitna purana jao utna slow. Cursor-based pagination me before={timestamp} bhejte hain aur Cassandra clustering key (timestamp DESC) se seedha us point se 50 rows nikaal leti hai — O(log N + 50) time, chahe history 10K messages ki ho. Isliye chat apps me hamesha timestamp cursor use hota hai.
Q19 Media ke liye presigned URL kya hota hai aur kyun use karte hain?
Presigned URL ek time-limited signed URL hota hai jo client ko seedha S3 par file upload karne deta hai, bina backend server ke through jaaye. Backend sirf URL generate karta hai (50ms), file 100MB ki bhi ho to seedha S3 par jati hai. Isse backend ka bandwidth bachta hai, latency 5s se 2s ho jati hai, aur server upload ka bottleneck nahi banta. URL 15 minute me expire ho jata hai, isliye unauthorized access bhi nahi hota.
Q20 Presence system 100M users par kaise scale hota hai?
Do cheezein scale karti hain: pehle, heartbeat writes — 100M users × 1 ping/30s = 3.3M writes/sec, lekin Redis SET O(1) hai aur data Redis Cluster ke 16K slots me shard hota hai. Doosre, broadcasts — har heartbeat broadcast nahi hota, sirf online ↔ offline transitions broadcast hote hain, isliye traffic bahut kam ho jata hai. Pub/Sub per instance 100K msg/sec handle karta hai. Aur TTL-based expiry se koi manual cleanup nahi chahiye — dead clients apne aap offline ho jate hain.
Q21 Group me 256 members ki limit kyun hai?
WhatsApp ki limit 256 members hai — ye product decision bhi hai aur engineering trade-off bhi. Fanout cost members ke saath linearly badhti hai: 256 members matlab 1 message ke liye 256 deliveries. Limit na hoti to 10,000-member group me ek message 10,000 sends ban jata aur sender ka request ya fanout workers choke ho jate. Bade groups ke liye fanout paginate karna aur Kafka se async processing karna padta hai. Limit se worst-case fanout predictable rehta hai.
Q22 Message search ke liye Elasticsearch kyun, Cassandra se search kyun nahi?
Cassandra partition key se point queries aur range scans ke liye best hai, lekin full-text search (jaise 'hello world' jisme 'hello' ho) ke liye nahi bani — uske liye poora data scan karna padta. Elasticsearch inverted index banata hai aur content field ko analyze karke full-text match query chalata hai, highlights ke saath. Isliye messages async consumer se Elasticsearch me index hote hain. Trade-off: sirf aakhri 6 mahine index hote hain, purane messages ke liye Cassandra scan (slow) karna padta hai.
Q23 Client-side message queue kyun chahiye jab server par Redis Stream hai?
Kyunki user offline me bhi message type karke bhej sakta hai — us time na WebSocket hai na server tak raasta. Client ki local queue message ko device par hold karti hai aur online aate hi sync karti hai. Redis Stream server-side queue hai (recipient offline ho to), client queue sender-side queue hai (sender offline ho to). Dono milkar 'message kabhi lost nahi hoga' ka vaada poora karte hain. Local SQLite cache ke saath ye offline-first experience banata hai.
Q24 JWT token 7 din ka kyun hota hai?
JWT stateless hota hai — server ko har request par session database check nahi karna padta, token verify karke user_id nikal leta hai. Lekin token leak ho jaye to wo expiry tak valid rehta hai, isliye expiry kam rakhte hain — 7 din usability aur security ka balance hai. Isse zyada lamba hota to leak ka risk badhta, isse chhota hota to user ko baar-baar login karna padta. Logout par token revoke karne ke liye alag se denylist maintain karni padti hai, kyunki JWT khud revoke nahi hota.
Q25 Typing indicator ko database me store kyun nahi karte?
Kyunki typing events ephemeral hain — inka koi future use nahi hai, sirf usi pal ka UI state hai. Store karte to 100M users me 10% type kar rahe hon to bhi 1B+ unnecessary writes/day ban jate. Ye fire-and-forget events hain: WebSocket ya Pub/Sub se broadcast karo, 3 second baad bhool jao. Throttling (1 event per 3s) se traffic bhi control me rehta hai. Jo data dobara chahiye hi nahi, use store karna pure waste hai.
Q26 Cassandra me TTL ka kya use hai chat app me?
Do jagah: messages table me optional TTL — ephemeral messages ya 2 saal se purane messages auto-delete ho jate hain, isse storage 50% tak bachta hai. Aur Redis me last_seen key par EX 60 — presence system ka core hai. TTL ka matlab hai cleanup ka kaam database khud karta hai, tumhe cron job ya background deleter chalane ki zaroorat nahi padti.
Q27 CDN media delivery me kya role play karta hai?
Media (images/videos) CloudFront CDN se serve hota hai — file pehli baar S3 se aakar edge location par cache ho jati hai, phir us area ke saare users ko edge se hi milti hai. Cache hit rate 95% hai, matlab 95% requests S3 tak jaati hi nahi — origin load 95% kam aur latency globally kam. Thumbnail pehle load hota hai, full media click par — isse chat khulte hi fast lagti hai.
Q28 Message compression kyun zaroori hai?
Chat app zyada tar mobile par chalti hai — slow network, limited data. WebSocket messages ko zlib se compress karne par 3:1 ratio milta hai, matlab 66% bandwidth bachta hai. 100B messages/day par ye saving bahut badi hoti hai — server bandwidth cost aur user ka mobile data, dono bachte hain. Text messages compress bahut achhe se hote hain, isliye ye free jaisa optimization hai.
Q29 Reconnect par missed messages kaise milte hain bina duplicate ke?
Client reconnect karte time handshake me last_received_message_id ya last_sync_timestamp bhejta hai. Server Redis Stream se aur Cassandra se timestamp > last_sync_timestamp wale messages nikaalta hai aur chronological order me bhejta hai. Client har message ka server-generated message_id check karta hai — jo pehle mil chuka hai use ignore kar deta hai. Delivery acknowledge hone ke baad XDEL se stream se delete ho jata hai. Isse na message chhootta hai na duplicate dikhta hai.
Q30 Read receipts ko batch kyun karte hain?
Agar user 50 messages ek saath padhta hai aur har message ke liye alag POST /v1/messages/{id}/read bheje to 50 API calls ban jati hain. Batch karke 10 message_ids ek request me bhejne se calls 10x kam ho jati hain. 1B messages/day par ye saving bahut badi hai — server load, network aur battery, teeno bachte hain. Group read receipts me to batching aur bhi zaroori hai kyunki ek message ke N readers hote hain.
Q31 Chat app me CAP theorem kaise apply hota hai?
CAP ke hisaab se network partition ke time consistency aur availability me se ek chunni padti hai. Chat app availability chunta hai: message bhejna aur paana kabhi rukna nahi chahiye, chahe do replicas me message 1–2 second late sync ho. Isliye eventual consistency acceptable hai — Cassandra me writes QUORUM se hote hain aur reads ONE se, matlab padhne par thoda purana data mil sakta hai. User ko farak nahi padta agar message 100ms late dikhe, lekin farak padta hai agar message bheja hi na ja sake.
Q32 Load Balancer aur API Gateway alag kyun hain?
Load Balancer traffic ko multiple gateway instances me baanta hai (scaling ke liye), aur API Gateway har request par authentication, authorization, routing aur rate limiting karta hai (security aur control ke liye). Dono ka kaam alag hai: LB 'kahan bhejna hai' tay karta hai, Gateway 'bhejna hai ya nahi' tay karta hai. WebSocket upgrade bhi Gateway par hota hai — HTTP se WebSocket me switch yahin hota hai.
Q33 User Service aur Chat Service alag kyun hain?
Separation of concerns: User Service profiles, contacts aur settings sambhalta hai (PostgreSQL — relational data, kam writes). Chat Service real-time messaging sambhalta hai (WebSocket connections, routing, 1M+ msg/sec). Dono ka scale pattern alag hai — User Service ko zyada read replicas chahiye, Chat Service ko zyada gateway instances. Alag services hone se ek ko scale ya deploy karne par doosra affect nahi hota. Ye microservices ka basic principle hai.
Q34 Group read receipts me 'Read by 2 of 3' kaise calculate hota hai?
Cassandra group_messages table me read_by set<uuid> maintain hota hai — jab koi member message padhta hai to uska user_id set me add ho jata hai. UI ko chahiye: read_by ka size (kitno ne padha) aur total members ka count (Group DB se). 'Read by 2 of 3' matlab 3 members me se 2 ke user_ids read_by set me hain. Per-member status bhi map me rehta hai — {user2: read, user3: delivered, user4: read} — jisse detail view me har member ka status dikhaya ja sakta hai.
Q35 Offline message 7 din se purana ho jaye to kya hota hai?
Redis Stream me messages 7 din baad expire ho jate hain — stream memory bachane ke liye. Lekin message lost nahi hota kyunki wo Cassandra me bhi persist hota hai (source of truth). Jab user 7 din baad online aata hai, service pehle stream check karti hai, phir Cassandra se WHERE timestamp > last_sync_timestamp query karke purane messages nikaal leti hai. Thoda slow hota hai (Cassandra scan), lekin message mil jata hai. Yehi Stream + Cassandra ka dual-layer design hai.
Q36 Heartbeat 30 second ka kyun hai, 5 second ka kyun nahi?
Trade-off hai: heartbeat jitna frequent, presence utna accurate — lekin writes bhi utne zyada. 5 second par 100M users matlab 20M writes/sec — Redis par bahut zyada load. 30 second par 3.3M writes/sec banta hai jo Redis Cluster sambhal leta hai. Aur offline detection 60 second me ho jati hai (2 missed pings) — user experience ke liye kaafi hai, kyunki 'last seen 1 min ago' aur 'last seen 2 min ago' me koi farak nahi padta. Isliye 30s ping + 60s TTL sahi balance hai.
