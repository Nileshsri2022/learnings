01Requirements

Functional Requirements

Hotel booking app me user kya-kya kar sakega — ye 5 features poori system ki neev hain. Interview me pehle ye hi poochha jata hai: system ko karna kya hai?

Functional requirements matlab — system user ke liye kya-kya karega. Is lesson me hotel booking platform ke 5 core features hain, aur har feature ke peeche ek ya zyada services chhupi hain. Inhe yaad rakhne ka tareeka: user ki journey socho — account banao → hotel dhoondho → details dekho → payment karo → booking manage karo.

5 Core Features

  • Feature 1 — Account banao: User apna account register kar sakega, login/logout kar sakega, aur profile update kar sakega. Iske peeche User Service + PostgreSQL hota hai, JWT token se authentication hota hai.
  • Feature 2 — Hotel search karo: User naam, location aur dates ke basis par hotel search kar sakega, aur price, rating aur amenities jaise filters laga sakega. Ye search Elasticsearch ke geo queries se chalti hai.
  • Feature 3 — Hotel details dekho: User hotel ki poori detail dekh sakega — available rooms, unke prices, photos aur reviews. Photos S3 me stored hoti hain aur CDN se serve hoti hain.
  • Feature 4 — Payment karke booking confirm karo: User selected room aur dates ke liye payment karke booking confirm karega. Payment me idempotency hoti hai — double charge kabhi nahi.
  • Feature 5 — Apni bookings dekho aur manage karo: User apne profile par past aur future bookings dekh sakega, aur unhe cancel ya modify bhi kar sakega.

Interview me kaise bolo

Interviewer jab "functional requirements batao" kahe, to sirf list mat sunao — har feature ke saath ek line me ye bhi batao ki wo kaise implement hoga. Jaise: "Search Elasticsearch geo query se hoga, booking Redis distributed lock se hogi, payment idempotency key se hogi." Isse pata chalta hai ki tumne sirf feature nahi, poora design socha hai.

Yaad rakhne ki trick: 5 features = Account → Search → Details → Payment → Manage. Ye user journey ka order hai, aur isi order me aage ke sections (API design, HLD, LLD) bhi bane hain.

Non-Functional Requirements

System kitna bada hoga, kitna fast hoga, aur kitna reliable hoga — ye numbers poore design ko shape dete hain. 50M users, 100M searches/day, aur double booking bilkul nahi.

Scale — kitna bada system?

MetricNumberMatlab
Users50M usersGlobal registered users
Hotels1M hotelsDuniya bhar ki properties
Rooms10M+ roomsSaare hotels ke rooms milakar
Daily searches100M searches/day≈ 1,157 searches/sec average, peak par 3x
Daily bookings1M bookings/day≈ 11.5 bookings/sec average
Conversion rate1%100M searches → 1M bookings

Ye numbers isliye important hain kyunki inhi se pata chalta hai ki search aur booking ke liye alag-alag strategy chahiye. Search 100x zyada hoti hai booking se — isliye search ko fast aur highly available banana hai, jabki booking ko strongly consistent banana hai.

CAP Theorem — is system me kaise apply hota hai?

Is system ka sabse important design decision ye hai: Availability >>> Consistency — lekin dono jagah ek jaisa nahi.

  • Search ke liye availability: Search highly available honi chahiye. Agar ek hotel ki availability 1-2 second purani dikh jaye to chalega, lekin search down nahi honi chahiye. Isliye search Elasticsearch se hoti hai, jo eventually consistent hota hai.
  • Booking ke liye strong consistency: Booking me consistency se koi compromise nahi. Do users ko same room, same dates par kabhi book nahi karne dena — ye rule todna matlab overbooking, refund aur trust ka loss. Isliye booking me distributed locks + ACID transactions use hote hain.

Performance & Reliability targets

  • Search latency: Location, dates aur filters ke saath hotel search < 500ms me aani chahiye.
  • Booking consistency: Strong consistency — distributed locks se double booking roko.
  • Payment reliability: Exactly-once semantics, idempotency ke saath — double charging bilkul nahi.
  • Availability check: Room availability check < 300ms me honi chahiye (PostgreSQL query room_availability table par).
  • Booking creation: Lock acquisition + DB transaction + payment initiation milakar < 2s.
  • Payment processing: Gateway ka external call milakar < 5s.
Interview tip: Jab interviewer scale poochhe, to sirf numbers mat batao — unse kya design decision nikla, wo batao. Jaise: "100M searches/day ka matlab hai search ko Elasticsearch + Redis cache se serve karna, aur 1M bookings/day ka matlab hai booking path ko locks aur transactions se strongly consistent rakhna."

03Requirements

Core Entities

System ke 4 core entities — User, Hotel, Room, Booking. Inke fields aur inke beech ke relations se poora database schema banta hai.

Entities identify karna design ka teesra step hai. Har entity ke fields dhyaan se dekho — aage section 7 me inhi se poori PostgreSQL tables banengi.

Entity 1 — User

Customer jo hotel book karta hai. Fields: user_id, name, email, phone, password, preferences, booking_history[]. Email unique hota hai aur indexed hota hai (login aur uniqueness check ke liye). Password kabhi plain text me nahi — bcrypt hash me store hota hai.

Entity 2 — Hotel

Property jise user book karta hai. Fields: hotel_id, name, location (lat, lng), address, rating, amenities[], images[], description. Location lat/lng me isliye hai kyunki search geo-distance par chalti hai. Images S3/CDN ke URLs hote hain, khud database me binary nahi.

Entity 3 — Room

Hotel ke andar ki inventory. Fields: room_id, hotel_id, room_type (Deluxe, Suite, Standard), capacity, price, amenities[], availability calendar. Ek hotel ke multiple rooms ek hi type ke ho sakte hain — jaise 20 Deluxe rooms. Isi liye availability per-room per-date track hoti hai.

Entity 4 — Booking

Reservation — user, hotel aur room ko jodne wala record. Fields: booking_id, user_id, hotel_id, room_id, check_in_date, check_out_date, status, amount, payment_id. Status hota hai: PENDING_PAYMENT → CONFIRMED → COMPLETED, ya CANCELLED.

Entities ke beech relations

RelationTypeKaise
User → Booking1-to-manyEk user ki kai bookings; booking me user_id FK
Hotel → Room1-to-manyEk hotel ke kai rooms; room me hotel_id FK

Ye relations hi aage ke joins banate hain — jaise "meri bookings dikhao" query bookings ko hotels aur rooms se JOIN karti hai.

High Level Design

Poora system ek nazar me: User → API Gateway → alag-alag services → PostgreSQL, Elasticsearch, Redis aur Kafka. Neeche design diagram bhi hai.

High Level Design me 10 components hain. Data ka flow yaad rakho: Search ka rasta alag, booking ka rasta alag — search Elasticsearch se, booking PostgreSQL + Redis lock se.

Design Diagram — poora HLD ek tasveer me. Neeche har component detail me samjhaya gaya hai. Diagram me kuch detail sirf image me hai (service-to-database connections), isliye prose me har connection likha gaya hai.

Request ka flow — components

  • Users → LB + API Gateway: Authentication, authorization, rate limiting aur round robin routing. Har request pehle yahin aati hai.
  • User Service → User DB (PostgreSQL): User profiles, authentication aur preferences. JWT issue karta hai, refresh token Redis me rakhta hai.
  • Search Service → Elasticsearch: Hotel search geo queries aur filters (price, rating, amenities) ke saath. Search results yahin se aate hain.
  • Hotel DB (PostgreSQL): Hotel metadata, room types, pricing, images (S3/CDN references). Hotel ki source of truth yehi hai.
  • Review Service → Review DB: Hotel aur room reviews, ratings ke saath. Review likhne se pehle booking complete honi chahiye.
  • Booking Service → Booking DB + Redis Lock: Room availability check aur booking creation — distributed locks ke saath. Ye system ka sabse critical service hai.
  • Room Availability Service: Check karta hai ki room available hai ya nahi, aur booking hone par availability table update karta hai.
  • Payment Service → Payment Gateway: Payment processing acknowledgement aur idempotency handling ke saath.
  • Kafka: Event streaming — booking.created, booking.confirmed, booking.cancelled, payment.success events.
  • Notification Service: Kafka events consume karke user ko email/SMS/push notification bhejta hai.

Yaad rakhne wali one-liner

Poora flow — ek line meMemorize
Search hotels (Elasticsearch geo)
  → Check availability (Redis lock)
  → Book room (distributed lock)
  → Payment (idempotency)
  → Confirmation (Kafka events)

Ye one-liner interview ke shuru me bol do — interviewer ko turant pata chal jayega ki tumhe poora picture aata hai. Uske baad har step ko deep dive me kholo.

Design principle: Read path (search) aur write path (booking) alag rakho. Search eventually consistent ho sakti hai — Elasticsearch 1-2 second purana data dikhaye to chalega. Booking kabhi eventually consistent nahi ho sakti — wahan ACID transaction + lock chahiye.

06.1Deep Dive (LLD)

Step 1: User Registration & Authentication

Account kaise banta hai — register request se lekar JWT token tak. Email uniqueness, bcrypt hash aur refresh token — teeno yahin hain.

Booking se pehle user ko pehchanna zaroori hai — booking kiske naam par hai, payment kiski hai, notification kahan jayega. Isliye authentication flow sabse pehle aata hai.

Register flow — step by step

  1. User bhejta hai: POST /v1/users/register with {name: '[Name]', email: '[email]', password: 'pass123'}
  2. User Service validate karta hai: email unique hai ya nahi — SELECT * FROM users WHERE email = {email}. Email column UNIQUE + INDEXED hai.
  3. Service banata hai: PostgreSQL me user record — {user_id: UUID, name, email, password_hash: bcrypt(password), created_at}. Password kabhi plain text me store nahi hota, sirf bcrypt hash.
  4. Service generate karta hai: JWT token {user_id, email, exp: 7 days} ke saath, aur refresh token Redis me TTL ke saath store karta hai.
  5. Response: {user_id, token, refresh_token}
  6. Login: POST /v1/users/login with {email, password} → bcrypt hash validate karo → JWT wapas do.

Kyu aisa design hai?

  • bcrypt hash: Agar database leak bhi ho jaye to asli password nahi milta. Bcrypt slow hash hai — brute force karna mehenga padta hai.
  • JWT (7 din expiry): Har request par database me session dhoondhne ki zaroorat nahi — token khud batata hai ki user kaun hai. Expiry 7 din ki hai taaki stolen token hamesha kaam na kare.
  • Refresh token Redis me: Access token expire hone par user ko dobara login nahi karna padta — refresh token se naya access token mil jata hai. Redis me TTL hone se purane refresh tokens apne aap expire ho jate hain.
  • Email UNIQUE + INDEX: Do accounts ek hi email se nahi ban sakte, aur login ke time email lookup fast hota hai.
Interview me: "Password kaise store karte ho?" — jawab: bcrypt hash, kabhi plain text nahi. "Session kaise manage karte ho?" — jawab: stateless JWT + Redis me refresh token. Ye do line interviewer ko kaafi hain.

06.2Deep Dive (LLD)

Step 2: Hotel Search (Elasticsearch Geo + Filters)

100M searches/day kaise serve hoti hain — geocoding, Elasticsearch geo_distance query, filters aur Redis cache. Aur sabse important: ES availability check nahi karta.

User search karta hai: GET /v1/hotels/search?location=London&checkIn=2025-02-01&checkOut=2025-02-05&guests=2&priceMax=200. Iske peeche 6 steps hote hain.

Search flow — step by step

  1. Geocoding: Search Service location 'London' ko coordinates me badalta hai — (51.5074, -0.1278) — Google Geocoding API ya internal cache se. Agar user seedha lat/lng bhej de to geocoding skip ho jati hai.
  2. Elasticsearch query: Service ES ko ye query bhejta hai:
    Elasticsearch geo + filters queryES
    {
  'query': { 'bool': { 'filter': [
    { 'geo_distance': { 'distance': '20km',
        'location': { 'lat': 51.5074, 'lon': -0.1278 } } },
    { 'range': { 'price_per_night': { 'lte': 200 } } },
    { 'term': { 'min_guests': { 'lte': 2 } } }
  ] } },
  'sort': [ { '_geo_distance': { 'location': {...}, 'order': 'asc' } } ],
  'size': 50
}

    Matlab: 20km radius ke andar ke hotels, price ≤ 200, kam se kam 2 guests ki capacity — nearest pehle, zyada se zyada 50 results.

  3. Important note: Ye Elasticsearch query date availability check nahi karti — wo bahut complex hota. Ye sirf location + filters match karne wale hotels deti hai.
  4. Partial data: Service ES se partial hotel data leta hai — {hotel_id, name, location, price_range, rating, image_url}. Poori detail nahi, taaki response halka aur fast rahe.
  5. CDC sync: Hotel DB → Kafka → Elasticsearch indexer. Hotel DB me kuch bhi badle to 1-2 second me ES index update ho jata hai (Change Data Capture).
  6. Availability alag se: User hotel select karne ke baad client alag API call karta hai — GET /v1/hotels/{hotelId}/availability?checkIn=...&checkOut=....
  7. Caching: Popular location searches Redis me cache hoti hain, TTL = 10 min, key = hash(location, filters).
⚠ WARNING — kabhi mat bhoolna: Elasticsearch me availability check kabhi nahi karte. ES search ke liye hai (location + filters), transactional data ke liye nahi. Availability har booking ke saath badalti hai — use PostgreSQL room_availability table se pessimistic locks (SELECT ... FOR UPDATE) ke saath check karo.
💡 TIP — search optimization: Elasticsearch sirf static filters (location, price, amenities) par hotels deta hai, date availability nahi. Availability ki alag API isliye hai kyunki availability har booking par badalti hai — har baar ES reindex karna mehenga aur slow hota.

Kyu ES availability nahi check karta?

  • ES text + geo search ke liye optimized hai, dynamic availability ke liye nahi.
  • Availability har booking par badalti hai — har booking par ES reindex karna = high latency + high cost.
  • Behtar UX: pehle paas ke saare hotels dikhao, phir user jis hotel ko chune uski availability on-demand check karo.
  • Alternative jo recommend nahi hai: ES me availability bitmap store karna — high write volume aur inconsistency risk.

06.3Deep Dive (LLD)

Step 3: Hotel Details & Room Availability

Hotel select karne ke baad — poori detail Hotel DB se, photos CDN se, aur availability ek SQL query se jo har date check karti hai.

User hotel select karta hai: GET /v1/hotels/{hotel_id}. Phir availability check karta hai: GET /v1/hotels/{hotel_id}/rooms?checkIn=2025-02-01&checkOut=2025-02-05&guests=2.

Hotel details — kahan se aati hai?

  • Service Hotel DB se full detail fetch karta hai: {hotel_id, name, description, amenities, images[], address, geo_pos (lat, lng)}.
  • Images S3/Blob storage me hoti hain, URLs CDN se serve hote hain — fast global access ke liye.

Availability query — dil se samjho

Room Availability Service ye SQL chalata hai:

Availability check — SQLPostgreSQL
SELECT r.room_id, r.room_type, r.capacity, p.date, p.price
FROM rooms r
JOIN room_availability a
  ON r.room_id = a.room_id AND a.hotel_id = {hotel_id}
JOIN price_calendar p ON r.room_id = p.room_id
WHERE a.date BETWEEN '2025-02-01' AND '2025-02-05'
  AND a.status IN ('Available', 'Booked', 'Maintenance')
GROUP BY r.room_id
HAVING COUNT(CASE WHEN a.status = 'Available' THEN 1 END) = {num_nights}

Is query ki jaan hai HAVING clause: room tabhi available mana jata hai jab range ki har ek date par uska status 'Available' ho. 4 nights ki booking ke liye 4 dates available honi chahiye — 3 available + 1 booked = room nahi milega. Yehi logic double booking ko database level par rokta hai.

Total price kaise nikalta hai?

  • Service calculate karta hai: Total price = SUM(price_per_night) date range ke liye — har date ka apna price ho sakta hai (price_calendar table).
  • Dynamic pricing lagti hai agar zaroorat ho — jaise demand zyada ho to price upar.
  • Response: [{ room_id, room_type, capacity, total_price, available_count, amenities[], images[] }]
Alternative jo overcomplicated hai: Availability table ke saath Q-tree ya geohashing use karna — is design ke liye overkill hai. Simple per-date row model hi kaafi hai aur interview me yahi expect kiya jata hai. Complexity tabhi lao jab scale uski maang kare.

06.4Deep Dive (LLD)

Step 4: Booking Creation with Distributed Lock (Critical)

Is poore lesson ka sabse important step — double booking kaise rokte hain. Redis SETNX lock + PostgreSQL FOR UPDATE + ACID transaction, teeno layers ek saath.

User confirm karta hai: POST /v1/booking/roomId with {room_id: 'room_123', user_id, check_in: '2025-02-01', check_out: '2025-02-05', guests: 2}. Iske baad jo hota hai wo interview ka sabse poochha jaane wala topic hai.

Booking flow — step by step (kram mat bhoolna)

  1. PEHLE Redis distributed lock lo: SETNX lock:hotel:{hotel_id}:room:{room_id}:{check_in}:{check_out} {booking_attempt_id} EX 30 — 30 second expiry ke saath. Critical: Lock key me hotel_id, room_id aur FULL date range hona chahiye taaki concurrent bookings ruk sakein.
  2. Agar SETNX 0 de (lock pehle se hai): Error wapas do — 'Room currently being booked, please try again' (HTTP 409 Conflict). User dobara try karega.
  3. Agar SETNX 1 de (lock mil gaya): Aage badho, availability check karo.
  4. Double-check availability — pessimistic lock: SELECT status FROM room_availability WHERE room_id = {room_id} AND hotel_id = {hotel_id} AND date BETWEEN {check_in} AND {check_out} FOR UPDATE — row-level lock.
  5. Agar KOI bhi date 'Available' nahi hai: Lock release karo (DEL lock:...), 'Room not available' wapas do.
  6. Agar saari dates available hain: Transaction shuru karo:
    Atomic booking transactionACID
    BEGIN TRANSACTION;
(1) INSERT INTO bookings
    (booking_id, user_id, hotel_id, room_id,
     check_in, check_out, status='PENDING_PAYMENT',
     amount, created_at);
(2) UPDATE room_availability
    SET status='Booked', booking_id={booking_id}
    WHERE room_id={room_id}
      AND date BETWEEN {check_in} AND {check_out};
COMMIT;

    Dono operations ek hi transaction me — ya to dono honge, ya koi nahi. Aadhi booking kabhi nahi banti.

  7. Lock release karo: DEL lock:hotel:{hotel_id}:room:{room_id}:{check_in}:{check_out}
  8. Event publish karo: Kafka topic booking.created par {booking_id, user_id, hotel_id, room_id, dates, amount}.
  9. Payment Service ko bulao: Response do — {booking_id, payment_url, expires_at: now() + 15min}. Payment 15 minute me complete nahi hua to booking expire ho jayegi.

Lock timeout — agar service crash ho jaye to?

Agar service lock hold karte hue crash ho jaye, to Redis lock ko 30 second baad apne aap expire kar deta hai (EX 30) — deadlock kabhi nahi hota. Room hamesha ke liye lock nahi rehta.

⚠ CRITICAL: Double booking rokne ke liye Redis distributed lock database check se PEHLE lena hai. Lock key me hotel_id, room_id AUR full date range hona hi chahiye — SETNX lock:hotel:{id}:room:{id}:{checkIn}:{checkOut} EX 30. Iske bina race conditions se overbooking ho jayegi.
⚠ NEVER: Bookings ke liye eventual consistency kabhi use mat karo. ACID transactions use karo — BEGIN; INSERT booking; UPDATE room_availability; COMMIT;. Strong consistency zaroori hai — do users same room/dates kabhi book nahi kar sakte.
★ INTERVIEW FAVORITE: Interviewer hamesha poochhega — 'Double booking kaise rokte ho?' Jawab: (1) Redis SETNX lock date range ke saath, (2) PostgreSQL SELECT ... FOR UPDATE room_availability par, (3) INSERT booking + UPDATE availability ek hi transaction me, (4) Lock 30s me auto-expire — deadlock nahi.
★ Lock key design: lock:hotel:{hotel_id}:room:{room_id}:{checkIn}:{checkOut} — isme FULL date range hai. Kyu? Taaki overlapping dates ki concurrent bookings ruk sakein. Agar key me sirf room_id hota to alag-alag dates ki booking bhi block ho jati; agar date range na hoti to overlap wali booking nikal jati.

Dono locks kyu chahiye — Redis + PostgreSQL?

  • Redis lock fast hai (1-2ms): Zyada tar concurrent requests ko shuru me hi reject kar deta hai — database tak load hi nahi pahunchta.
  • PostgreSQL FOR UPDATE ACID guarantee deta hai: Transaction ke andar row-level lock pakka karta hai ki do transactions ek hi row ko ek saath change na karein.
  • Race example: User A aur B dono room_123 ko Feb 1-5 ke liye book karna chahte hain → A ka SETNX succeed → B ka SETNX fail → B ko 'being booked' dikhta hai → A ki booking complete → B retry kare to 'not available' dikhega → double booking nahi hoti.

Step 5: Payment Processing with Idempotency

User 'Pay' do baar click kare to bhi charge ek hi baar — idempotency key = booking_id, gateway guarantee + database UNIQUE constraint, teeno layers.

Booking create hone ke baad user payment gateway par redirect hota hai (Stripe/Razorpay) payment_url ke saath. Payment ke 15 minute hain — uske baad booking expire ho jati hai.

Payment flow — step by step

  1. Payment intent banao: Payment Service payment intent banata hai with idempotency_key = booking_id — ye ensure karta hai ki same booking ko do baar charge nahi kiya ja sakta.
  2. User payment complete karta hai: Payment Gateway card process karta hai, phir webhook bhejta hai — POST /webhooks/payment with {booking_id, payment_id, status: 'success', amount}.
  3. Webhook handler — 3 kaam:
    • (1) Webhook signature validate karo (security — koi fake webhook na bhej sake).
    • (2) Idempotency check karo: SELECT * FROM payments WHERE booking_id = {booking_id} — agar record pehle se hai to 200 OK wapas do (already processed).
    • (3) Transaction: BEGIN; INSERT INTO payments (payment_id, booking_id, amount, status='SUCCESS', gateway_response, created_at); UPDATE bookings SET status='CONFIRMED', payment_id={payment_id} WHERE booking_id={booking_id}; COMMIT;
  4. Events publish karo: Kafka topics payment.success aur booking.confirmed.
  5. Booking expiry set karo Redis me: SETEX booking:{booking_id}:expires 900 '1' (15 min TTL) — agar payment nahi aaya to background job booking cancel karke room release kar deta hai.
  6. Notification: Notification Service Kafka event consume karke confirmation email/SMS bhejta hai — booking details aur QR code ke saath.

Double charge kaise rukta hai — 3 layers

  • Layer 1 — Gateway idempotency: Same idempotency_key 24 ghante ke andar = gateway wahi payment_intent_id wapas deta hai, duplicate charge nahi.
  • Layer 2 — Database UNIQUE constraint: UNIQUE INDEX on payments(booking_id) — ek booking ka sirf ek payment record ho sakta hai. Do concurrent webhooks aayein to pehla INSERT succeed, doosra UNIQUE constraint par fail — gracefully handle hota hai.
  • Layer 3 — Webhook pehle check: Payment record pehle se hai to dobara process hi nahi karte — 200 OK wapas.

Example: User 'Pay' par double-click karta hai → Request 1 payment_intent_123 banata hai → Request 2 same idempotency_key ke saath → Gateway existing payment_intent_123 wapas deta hai → user ko ek hi baar charge hota hai.

★ INTERVIEW FAVORITE — zaroor bolna: Payment idempotency booking_id ko idempotency_key banakar. Payment gateway + database UNIQUE constraint milkar ensure karte hain ki user 'Pay' kitni bhi baar click kare ya webhook replay ho jaye — double charge kabhi nahi hoga.
Alternative: Payment se pehle distributed lock SETNX lock:payment:{booking_id} bhi lagaya ja sakta hai, lekin gateway idempotency + DB constraint simpler aur zyada reliable hai.

Step 7: View Bookings (Past & Future)

Meri bookings dikhao — JWT se user_id, ek JOIN query, aur Redis cache. Past vs future ka filter client ya service dono kar sakte hain.

User request karta hai: GET /v1/bookings with header {Authorization: Bearer {token}}.

Flow — step by step

  1. Booking Service JWT token decode karke user_id nikalta hai — URL me user_id bhejne ki zaroorat nahi, token hi kaafi hai.
  2. Service ye query chalata hai:
    My bookings — SQLPostgreSQL
    SELECT b.booking_id, b.hotel_id, h.name AS hotel_name,
       h.image_url, b.room_id, r.room_type,
       b.check_in, b.check_out, b.status, b.amount
FROM bookings b
JOIN hotels h ON b.hotel_id = h.hotel_id
JOIN rooms r ON b.room_id = r.room_id
WHERE b.user_id = {user_id}
ORDER BY b.created_at DESC
LIMIT 50
  3. Categorization: Future bookings (check_in > today) aur past bookings (check_out < today) — ye filter client-side ya service-side, dono jagah ho sakta hai.
  4. Caching: User ki booking list Redis me cache hoti hai — key user:{user_id}:bookings, TTL = 5 min. Nayi booking ya cancellation par cache invalidate hoti hai.
  5. Response: { bookings: [{ booking_id, hotel: {...}, room: {...}, dates: {...}, status, amount, can_cancel: boolean }] }

Kyu aisa design hai?

  • JWT se user_id: User apni hi bookings dekh sakta hai — doosre user ki bookings dekhne ka rasta hi nahi. Security token level par hai.
  • JOIN ek query me: Hotel ka naam aur room type alag-alag calls me lene ke bajaye ek hi JOIN me — N+1 query problem nahi hoti.
  • LIMIT 50: Poori history ek saath nahi — pagination se payload chhota rehta hai.
  • Cache TTL sirf 5 min: Booking list jaldi badalti hai (nayi booking, cancel) — lamba TTL stale data dikhayega. Isliye chhota TTL + har change par invalidation.
  • can_cancel flag: Client ko khud policy calculate nahi karni padti — service bata deta hai ki ye booking cancel ho sakti hai ya nahi.

Step 10: Notification Flow (Kafka Event-Driven)

Booking confirm hote hi email/SMS/push — Kafka events se. Consumer offset tabhi commit karta hai jab notification bhej di jaye — exactly-once delivery.

Notification Service khud kuch decide nahi karta — wo sirf Kafka events sunta hai aur un par action leta hai. Ye decoupling hi event-driven design ki taakat hai.

Kafka topics — kaun se events?

Booking Service aur Payment Service in topics par publish karte hain: booking.created, booking.confirmed, booking.cancelled, payment.success, payment.failed. Notification Service in sab topics ko alag-alag consumer groups se consume karta hai — reliability ke liye.

'booking.confirmed' event par kya hota hai?

  1. User ka email/phone User DB se fetch karo.
  2. Booking details Booking DB se fetch karo.
  3. Email template generate karo — QR code (booking_id encoded), hotel details, check-in instructions ke saath.
  4. Send karo — SendGrid/SES se email, Twilio se SMS.
  5. Notification log Notification DB me store karo.

Push aur reminder notifications

  • Reminder notifications: Scheduled jobs check-in se 1 din pehle reminder email/SMS bhejte hain booking details ke saath.

Agar send fail ho to offset commit nahi hota — retry par event dobara milega aur notification dobara bhejegi. Isse exactly-once delivery ensure hoti hai retry par bhi. Idempotency yahan bhi kaam aati hai — notification log check karke duplicate send roka ja sakta hai.

Scaling & Optimization

100M searches/day kaise handle hote hain — 12 techniques: geo sharding, locks, read replicas, CDN, Kafka, caching, rate limiting, partitioning aur CDC.

Scale ka matlab sirf "zyada servers" nahi hai — har bottleneck ka alag solution hai. Neeche 12 techniques hain, har ek kisi ek problem ko solve karti hai.

12 Techniques

  1. Elasticsearch Geo Sharding: Hotel index ko region se shard karo (US, EU, Asia) — parallel queries chalte hain, har region apna data serve karta hai.
  2. Redis Distributed Locks: SETNX with expiry — double booking race conditions roko, timeout par auto-release.
  3. Database Read Replicas: Read queries (search, view bookings) replicas par bhejo, writes primary par. Primary par load kam hota hai.
  4. CDN for Images: Hotel/room images edge locations se serve hoti hain — 95% cache hit rate, <50ms latency.
  5. Kafka Event Streaming: Async notifications, booking events, payment confirmations — services decouple hote hain.
  6. Caching Layer: Redis me search results (TTL=10min), user bookings (TTL=5min), hotel details (TTL=30min) cache karo.
  7. Connection Pooling: API servers 100-200 DB connections maintain karte hain — connection exhaustion nahi hota.
  8. API Rate Limiting: 100 req/min per user, token bucket se — abuse se bachao.
  9. Database Partitioning: Bookings table ko date se partition karo (monthly partitions) — query performance badhti hai, purana data archive karna easy hota hai.
  10. Lazy Loading: Hotel images on-demand load karo, search results paginate karo (50 per page) — payload chhota rehta hai.
  11. Geo-Based Routing: User ko nearest data center par bhejo (US-East, EU-West, Asia) — latency kam hoti hai.
  12. CDC Pipeline: PostgreSQL → Debezium → Kafka → Elasticsearch — real-time search index updates, 1-2 second me.

Search scaling ka math (interview me ye sunao)

  • 100M searches/day = 1,157 searches/sec average, peak 3x = 3,500 searches/sec.
  • 100 search service instances × 50 req/sec capacity = 5,000 req/sec headroom — peak se bhi zyada.
  • Cache hit rate 60-70% — matlab 100M me se 60-70M searches Redis se hi serve ho jati hain, Elasticsearch tak pahunchti hi nahi.
  • ES cluster: 10 data nodes + 3 master nodes, har region me 5 primary shards + 1 replica.
  • Cost estimate: ES cluster $5K/month, Redis $1K/month, API servers $3K/month = $9K/month search infrastructure ke liye.
💡 TIP — multi-region DR: Primary region us-east-1, warm standby us-west-2 streaming replication ke saath (lag <5s). Route53 health checks 2-5 minute me auto-failover karte hain. RPO=5s, RTO=5min. DR test har mahine karo.
💡 TIP — caching strategy: Search results (TTL=10min, 60% hit rate), hotel details (TTL=30min), user bookings (TTL=5min, changes par invalidate). Redis cluster 70% searches ko bina Elasticsearch/PostgreSQL chhue serve kar deta hai.

Query optimization — ES me 3 cheezein

  • Filter context use karo, query context nahi: { 'bool': { 'filter': [...] } } — faster aur cacheable, kyunki scoring calculate nahi hoti.
  • Scoring band karo geo queries ke liye: 'track_scores': false.
  • Sirf zaroori fields fetch karo: '_source': ['hotel_id', 'name', 'location', 'rating'] — payload chhota, response fast.

Common Interview Questions

Lesson ke 10 sabse important interview Q&A — har jawab poori detail me, race conditions se lekar disaster recovery tak. Inhe ratna nahi, samajhna hai.

Ye 10 sawaal is lesson ke interview Q&A section se hain. Har jawab ke andar wahi multi-layer reasoning hai jo interviewer dekhna chahta hai — sirf "kya" nahi, "kyu" aur "kaise" bhi.

Q1 How do you prevent double booking (two users booking same room for overlapping dates)?

Multi-layer approach: (1) Redis distributed lock availability check se PEHLE — SETNX lock:hotel:{hotel_id}:room:{room_id}:{check_in}:{check_out} {booking_attempt_id} EX 30, lock key me FULL date range hota hai. (2) Agar SETNX 0 de to 409 Conflict — 'Room being booked, try again'. (3) Agar SETNX 1 de to database me jao. (4) Double-check availability pessimistic lock se — SELECT status FROM room_availability WHERE room_id={room_id} AND date BETWEEN {check_in} AND {check_out} FOR UPDATE (row-level lock). (5) Agar koi date 'Available' nahi hai to Redis lock release karo, 'Not available' do. (6) Agar sab available hain to transaction — BEGIN; INSERT booking; UPDATE room_availability SET status='Booked', booking_id={id} WHERE room_id={room_id} AND date BETWEEN {dates}; COMMIT; (7) Redis lock release karo — DEL lock:... (8) Lock 30s me auto-expire hota hai agar service crash ho jaye — deadlock nahi.

Dono locks kyu? Redis fast hai (1-2ms) early rejection ke liye; PostgreSQL FOR UPDATE transaction ke andar ACID guarantee deta hai. Example race: User A aur B dono room_123 ko Feb 1-5 ke liye book karna chahte hain → A ka SETNX succeed → B ka SETNX fail → B ko 'being booked' dikhta hai → A complete karta hai → B retry kare to 'not available' — double booking nahi hoti.

Q2 How do you implement hotel search with location, dates, and price filters efficiently?

Elasticsearch geo_distance + compound filters: (1) User search karta hai — location='Paris', checkIn='2025-03-01', checkOut='2025-03-05', priceMax=200, guests=2. (2) Location geocode karo — (48.8566, 2.3522) — Google Geocoding API ya cached mappings se. (3) ES query: POST /hotels/_search with bool filter — geo_distance 20km, price_range.min lte 200, amenities terms ['WiFi'] — sort _geo_distance asc, size 50. (4) NOTE: ES sirf location + static filters match karne wale hotels deta hai, date availability check nahi karta (bahut complex). (5) Availability ke liye alag API call — GET /v1/hotels/{hotel_id}/availability?dates=... — room_availability table query hoti hai. (6) ES me availability bitmap store karna overcomplicated hai — high write volume, inconsistency risk, recommend nahi.

Kyu ye approach? (a) ES text + geo search ke liye optimized hai, dynamic availability ke liye nahi. (b) Availability har booking par badalti hai — har baar reindex karna high latency + cost. (c) Behtar UX — paas ke saare hotels dikhao, availability on-demand check karo. Caching: popular searches Redis me TTL=10min. CDC: PostgreSQL hotel updates → Kafka → ES indexer, search index 1-2s me fresh.

Q3 How do you ensure payment idempotency (prevent double charging if user clicks pay twice)?

Idempotency multiple layers par: (1) Client idempotency_key = booking_id generate karta hai payment se pehle. (2) Payment Service POST /payments with {booking_id, amount, idempotency_key: {booking_id}}. (3) Payment Gateway (Stripe/Razorpay) same idempotency_key use karta hai createPaymentIntent API ke liye. (4) Gateway guarantee: same idempotency_key 24h ke andar = wahi payment_intent_id wapas, duplicate charge nahi. (5) Database constraint: UNIQUE INDEX on payments(booking_id) — ek booking ka ek hi payment record. (6) Webhook handling: POST /webhooks/payment — (a) check karo SELECT * FROM payments WHERE booking_id = {booking_id}, agar hai to 200 OK (already processed), (b) nahi hai to transaction — INSERT payments + UPDATE bookings SET status='CONFIRMED', (c) race condition: do concurrent webhooks → pehla INSERT succeed, doosra UNIQUE constraint par fail — gracefully handle hota hai. (7) Kafka event sirf ek baar publish hota hai database constraint ki wajah se.

Example: User 'Pay' double-click karta hai → Request 1 payment_intent_123 banata hai → Request 2 same idempotency_key → Gateway existing payment_intent_123 deta hai → user ek hi baar charge hota hai. Alternative: distributed lock SETNX lock:payment:{booking_id} — lekin gateway idempotency + DB constraint simpler aur zyada reliable hai.

Q4 How do you handle room availability updates and booking modifications?

Availability updates: (1) Hotel admin update karta hai — PUT /v1/hotels/{hotel_id}/rooms/{room_id}/availability with {dates: ['2025-03-01', '2025-03-02'], status: 'Maintenance'}. (2) Validate karo: booked date ka status change nahi kar sakte. (3) Bulk update — UPDATE room_availability SET status={status} WHERE room_id={room_id} AND date IN ({dates}) AND status != 'Booked'. (4) Kafka event 'availability.updated' — cache invalidation ke liye. (5) Redis cached availability clear karo affected hotel/room ki.

Booking modification (date change): (1) User modify karta hai — PUT /v1/bookings/{booking_id} with {new_check_in, new_check_out}. (2) Validate: cancellation policy (kuch bookings non-refundable), nayi dates available hain ya nahi. (3) Distributed lock lo — SETNX lock:hotel:{hotel_id}:room:{room_id}:{new_check_in}:{new_check_out}. (4) Nayi availability check karo — SELECT ... FOR UPDATE. (5) Agar available ho to transaction: (a) purani dates release karo — status='Available', booking_id=NULL, (b) nayi dates book karo, (c) booking update karo — check_in, check_out, amount. (6) Lock release, (7) 'booking.modified' event publish karo.

Price adjustment edge cases: nayi dates mehengi hon to difference charge karo; sasti hon to partial refund; availability na ho to error + alternative dates ka suggestion do.

Q5 How do you implement the review and rating system with aggregation?

Review submission: (1) User submit karta hai — POST /v1/reviews with {hotel_id, booking_id, rating: 4.5, comment: 'Great location!', images: [file1, file2]}. (2) Validation: (a) booking exist karti hai aur user ki hi hai, (b) booking completed hai (check_out < today) — stay se pehle review nahi, (c) is booking par pehle review nahi hai — ek booking par ek hi review. (3) Images S3 par multi-part upload — s3://reviews/{review_id}/{image_id}.jpg, CDN URLs milte hain. (4) Insert review — {review_id, hotel_id, user_id, booking_id, rating, comment, images[], created_at, helpful_count: 0}.

Aggregation (async): (5) Background job — UPDATE hotels SET avg_rating = (SELECT AVG(rating) FROM reviews WHERE hotel_id={hotel_id}), review_count = (SELECT COUNT(*) FROM reviews WHERE hotel_id={hotel_id}). Behtar performance ke liye materialized view — CREATE MATERIALIZED VIEW hotel_ratings AS SELECT hotel_id, AVG(rating), COUNT(*) FROM reviews GROUP BY hotel_id — har 10 min refresh. (6) CDC pipeline: hotel.avg_rating update → Kafka → Elasticsearch indexer — search index update hota hai. (7) Moderation: ML service (AWS Comprehend / Cloud NLP) review text scan karta hai — profanity, spam, fake reviews — confidence > 0.8 ho to manual review ke liye flag. (8) Helpful votes: POST /v1/reviews/{review_id}/helpful — helpful_count badhta hai ranking ke liye. Display: GET /v1/hotels/{hotel_id}/reviews?sortBy=helpful&page=1&size=20 — helpful_count DESC ya created_at DESC. Alternative: Apache Flink real-time rating updates ke liye — lekin materialized view + periodic refresh simpler aur kaafi hai.

Q6 How do you handle time zones and date calculations for global hotels?

Strategy: (1) Database me saare timestamps UTC me store hote hain (PostgreSQL timestamp without timezone). (2) Hotels table me timezone column — hotel_timezone varchar(50) — jaise 'America/New_York', 'Europe/London' — IANA tz database se. (3) Check-in/check-out dates DATE type me store hoti hain (timestamp nahi) — hotel ki local date represent karti hain. (4) Business logic: user search kare to dates hotel ke local timezone me interpret hoti hain — 'Paris hotels for March 1-5' matlab Paris local dates, user ke timezone ki nahi. (5) Display: backend dates + hotel_timezone deta hai — {check_in: '2025-03-01', check_out: '2025-03-05', timezone: 'Europe/Paris'} — client dikhata hai 'Checking in March 1, 2025 (Paris time)'. (6) Availability calculation: room_availability.date hotel local date me hai — timezone conversion ki zaroorat hi nahi. (7) Payment deadlines UTC timestamp me — booking.payment_deadline = booking.created_at + 15 min (UTC) — user ko uske local timezone me dikhaya jata hai. (8) Notifications me explicit timezone — 'Check-in: March 1, 2025 at 3:00 PM CET'. (9) DST edge case: proper timezone library (moment-timezone / date-fns-tz) use karo, sirf UTC offset nahi — daylight saving apne aap handle hota hai.

Example: California ka user (UTC-8) London hotel (UTC+0) March 1-5 ke liye book karta hai → backend store karta hai {check_in: DATE '2025-03-01', check_out: DATE '2025-03-05', hotel_timezone: 'Europe/London', created_at: TIMESTAMP '2025-01-15 20:30:00 UTC'} → user dekhta hai 'Booking confirmed for March 1-5, 2025 (London time), made on Jan 15, 2025 12:30 PM PST'. Alternative: saari dates TIMESTAMPTZ me store karna — lekin DATE simpler hai kyunki check-in dates me time-of-day relevant nahi hai.

Q7 How do you implement cancellation policies and refund processing?

Multi-tier policy: (1) Policy rules per hotel/room store hote hain — cancellation_policy table {hotel_id, room_id, policy_type: 'flexible'/'moderate'/'strict', rules: jsonb}. (2) Flexible: 24h free, 12h tak 50%, uske baad no refund. Moderate: 72h free, 24h 50%, <24h no refund. Strict: 7 din free, <7 din no refund. (3) Booking creation par policy ka snapshot bookings.cancellation_policy jsonb me copy hota hai — agar policy baad me badle to user safe rehta hai. (4) User cancel karta hai — PUT /v1/bookings/{booking_id}/cancel with {reason: 'user_requested'}. (5) Refund calculate karo: (a) policy aur check_in fetch karo, (b) hours_until_checkin = (check_in - now()) ghanton me, (c) rules apply karo — ≥24h ho to 100%, ≥12h ho to 50%, warna 0. (6) Transaction: (a) UPDATE bookings SET status='CANCELLED', cancelled_at=now(), refund_amount={refund_amount}, refund_status='PROCESSING', (b) UPDATE room_availability SET status='Available', booking_id=NULL WHERE booking_id={booking_id}, (c) refund > 0 ho to INSERT INTO refunds (refund_id, booking_id, amount, status='PENDING'). (7) Async refund: background job gateway ko bhejta hai — stripe.refunds.create({payment_intent_id, amount}). (8) Webhook confirm karta hai — POST /webhooks/refund — refunds status 'COMPLETED', bookings.refund_status='REFUNDED'. (9) Notification: 'Booking cancelled, refund of ${amount} will appear in 5-7 business days'. (10) Kafka 'booking.cancelled' event.

Example: User Jan 1 ko March 1 check-in ke liye book karta hai (flexible policy) → Feb 28 ko cancel karta hai (1 din pehle) → 24 ghante bache hain → 100% refund → room available ho jata hai. Partial refunds: 3-night booking me 1 night cancel — per-night cancellation track karna padta hai, zyada complex hai. Abuse prevention: cancellation_rate = cancelled / total — last 10 bookings me >30% ho to account flag karo ya fee badhao.

Q8 How do you scale the search service to handle 100M searches per day?

Multi-tier scaling: (1) Elasticsearch cluster: 10 data nodes, 3 master nodes, hotel index region se shard (US, EU, Asia), har region me 5 primary shards + 1 replica. (2) Geo-based routing: API Gateway request ko nearest ES cluster par bhejta hai — US user → us-east-1, EU → eu-west-1 — latency 500ms se 50ms ho jati hai. (3) Caching: Redis popular searches cache karta hai — key hash(location, checkIn, checkOut, filters), TTL 10 min, hit rate ~60-70%, 100GB Redis cluster (10 nodes) ~10M cached searches store karta hai. (4) Query optimization: (a) filter context (query context nahi) — { 'bool': { 'filter': [...] } } — faster, cacheable, (b) geo queries ke liye scoring band — 'track_scores': false, (c) sirf zaroori fields fetch karo — '_source': ['hotel_id', 'name', 'location', 'rating']. (5) Rate limiting: per-user 100 searches/min, per-IP 1000 searches/min — scraping bots se bachao. (6) Read replicas: PostgreSQL primary + 5 read replicas har region me — ES se IDs milne ke baad hotel metadata replicas se aati hai. (7) CDN: hotel images CloudFront edge se — <50ms globally, 95% cache hit rate. (8) Load balancing: 100 search service instances ALB ke peeche, CPU >70% par auto-scaling. (9) Async indexing: hotel updates → Kafka → ES indexer consumer — write operations block nahi hote, eventual consistency 1-2s acceptable hai search ke liye. (10) Connection pooling: har instance 50 ES connections maintain karta hai (HTTP keep-alive). (11) Monitoring: Prometheus + Grafana — search latency p50/p95/p99, cache hit rate, ES cluster health — alert agar p95 >500ms.

Load math: 100M/day = 1,157/sec average, peak 3x = 3,500/sec. 100 instances × 50 req/sec = 5,000/sec headroom. Cost: ES $5K/month + Redis $1K/month + API servers $3K/month = $9K/month search infrastructure.

Q9 How do you handle overbooking scenarios and inventory management?

Inventory model: (1) Hotels ke ek hi type ke multiple rooms hote hain — jaise 20 Deluxe rooms. rooms table: {hotel_id, room_type, total_count: 20}, individual_rooms: {room_id, hotel_id, room_type, room_number: '101'}. (2) Availability tracking — do approaches: (a) Aggregate — room_availability_aggregate {hotel_id, room_type, date, available_count, booked_count} — faster queries, complex updates; (b) Individual — room_availability {room_id, date, status, booking_id} — simpler, zyada rows. (3) Booking validation: (a) user 'Deluxe room' book karta hai (pehle specific room_id nahi), (b) query — SELECT COUNT(*) as booked FROM room_availability WHERE hotel_id={hotel_id} AND room_type='Deluxe' AND date BETWEEN {dates} AND status='Booked', (c) check karo booked_count < total_deluxe_rooms ho range ki SAARI dates ke liye, (d) distributed lock lo — SETNX lock:hotel:{hotel_id}:room_type:Deluxe:{dates}, (e) specific room assign karo — SELECT room_id FROM rooms WHERE hotel_id={hotel_id} AND room_type='Deluxe' AND room_id NOT IN (SELECT room_id FROM room_availability WHERE date BETWEEN {dates} AND status='Booked') LIMIT 1 FOR UPDATE, (f) update karo — UPDATE room_availability SET status='Booked', booking_id={booking_id} WHERE room_id={assigned_room_id} AND date BETWEEN {dates}.

Controlled overbooking: (4) Kuch hotels jaan-bujhkar 5-10% overbook karte hain (airlines ki tarah) cancellations ko account karne ke liye — overselling_limit table {hotel_id, room_type, max_overbook_percent: 0.05} — booking allow karo agar booked_count <= total_count × 1.05. Risk mitigation: agar check-in day par asal me overbook ho jaye to hotel guest ko better room upgrade karta hai ya partner hotel me relocate karta hai — ye hotel ki responsibility hai. (5) Maintenance blocking: room_availability.status = 'Maintenance' → available_count se bahar. (6) Race condition edge case: last available room ke liye do bookings ek hi time par → distributed lock + database FOR UPDATE ensure karta hai ki sirf ek succeed hogi.

Example: Hotel ke 20 Deluxe rooms, March 1: 18 booked, 2 available → A aur B dono try karte hain → A lock leta hai → 2 available dekh kar room_123 assign karta hai → 19 booked → lock release → B lock leta hai → 1 available dekh kar room_124 assign karta hai → 20 booked → teesra user try kare to koi room available nahi.

Q10 What's your strategy for disaster recovery and data consistency?

Multi-region DR, RPO/RTO targets ke saath: (1) Primary region us-east-1, secondary us-west-2, tertiary eu-west-1. (2) Database replication: PostgreSQL primary us-east-1 me, streaming replication us-west-2 (warm standby) aur eu-west-1 (read replica) — replication lag <5 seconds normal load par. (3) RPO (Recovery Point Objective): 5 seconds — maximum data loss acceptable — synchronous replication se achieve hota hai. (4) RTO (Recovery Time Objective): 5 minutes — service restore karne ka time — Route53 health checks se automated failover. (5) Elasticsearch: multi-cluster setup, har region ka independent ES cluster, CDC pipeline (PostgreSQL → Kafka → ES) se sync — search ke liye eventual consistency acceptable hai. (6) Redis: Redis Sentinel automatic failover ke liye (master-slave replication), AOF (Append-Only File) persistence se data durability. (7) S3 cross-region replication: hotel images secondary region ke backup bucket me automatically replicate hote hain. (8) Kafka: multi-region setup, MirrorMaker events ko secondary Kafka cluster me replicate karta hai.

Failover procedure: (9) (a) Route53 health check primary region down detect karta hai (30s failed checks), (b) DNS automatically secondary region par point karta hai, (c) secondary PostgreSQL primary promote hota hai (pg_ctl promote), (d) secondary region ka API Gateway traffic lena shuru karta hai, (e) total downtime ~2-5 minutes DNS propagation ke liye. (10) Failover ke dauraan in-flight bookings fail ho sakti hain → retry mechanism + idempotency ensure karti hai ki double booking na ho — user ko temporary error dikhta hai → retry automatically naye region me succeed hota hai. (11) Testing: monthly DR drills — primary region failure simulate karo, verify karo RTO <5 min, gaps identify karo. (12) Backups: daily full backup + hourly incremental backups S3 Glacier me, retention 30 din, quarterly backup se disaster recovery test.

Example: Primary (us-east-1) 10:00 AM par down → Route53 10:00:30 par detect karta hai → failover shuru → us-west-2 10:02 par primary promote → DNS 10:03 par update → users 10:05 par naye region par → service restore, data loss <5 sec (last replicated 09:59:55). Cost: multi-region setup ~40% infrastructure cost badhata hai, lekin business continuity deta hai.

Interview FAQs — Hotel Booking System

Current-era interviews me hotel booking system se poochhe jaane wale sabse kaam ke 36 sawaal — har jawab wahi hai jo is lesson ke sections me detail me samjhaya gaya hai. Kisi bhi sawaal par click karke jawab kholo.

Q01 Double booking kaise rokte hain — poora flow kya hai?
Teen layers ek saath: pehle Redis distributed lock — SETNX lock:hotel:{hotel_id}:room:{room_id}:{check_in}:{check_out} EX 30 — lock key me full date range hota hai. Phir PostgreSQL me SELECT ... FOR UPDATE se availability double-check karo. Phir ek hi ACID transaction me INSERT booking + UPDATE room_availability SET status='Booked'. Lock 30 second me auto-expire hota hai, isliye deadlock nahi hota. Dono locks isliye chahiye kyunki Redis fast hai (1-2ms) early rejection ke liye, aur PostgreSQL transaction ke andar ACID guarantee deta hai.
Q02 Hotel search 100M searches/day par efficient kaise chalti hai?
Elasticsearch geo_distance query + compound filters se. Location geocode karke (51.5074, -0.1278) 20km radius, price range aur guests filter lagte hain, nearest pehle sort hota hai. ES sirf location aur static filters match karta hai — availability check nahi karta, wo alag API se hoti hai. Popular searches Redis me 10 min TTL ke saath cache hoti hain, hit rate 60-70% hai. ES cluster region se shard hota hai (US, EU, Asia) aur geo-routing se user nearest cluster par jata hai, latency 500ms se 50ms ho jati hai.
Q03 Payment idempotency ka matlab kya hai aur double charge kaise rukta hai?
Idempotency ka matlab hai: same request do baar aaye to bhi effect ek hi baar ho. Payment me idempotency_key = booking_id use hota hai. Gateway (Stripe/Razorpay) same key 24 ghante ke andar dekhe to wahi payment_intent_id wapas deta hai, duplicate charge nahi karta. Database me payments(booking_id) par UNIQUE constraint hai — ek booking ka ek hi payment record. Webhook handler pehle check karta hai ki payment record hai ya nahi — hai to 200 OK, dobara process nahi karta. User 'Pay' kitni bhi baar click kare, charge ek hi baar hota hai.
Q04 Room availability updates aur booking modifications kaise handle karte hain?
Hotel admin bulk update karta hai — UPDATE room_availability SET status={status} WHERE room_id={room_id} AND date IN ({dates}) AND status != 'Booked'. Ye last condition sabse important hai — booked dates kabhi override nahi hoti. Booking modify karne par nayi dates ke liye distributed lock lo, availability FOR UPDATE se check karo, phir ek transaction me purani dates release karo (status='Available'), nayi dates book karo aur booking update karo. Price ka farak ho to extra charge ya partial refund hota hai. Nayi dates na milen to error ke saath alternative dates suggest karo.
Q05 Review aur rating system aggregation ke saath kaise implement karte hain?
Review submit karne se pehle 3 validations: booking exist karti hai aur user ki hai, booking completed hai (check_out < today), aur is booking par pehle review nahi hai — ek booking par ek hi review. Rating aggregation background job se hoti hai — UPDATE hotels SET avg_rating = (SELECT AVG(rating) FROM reviews...). Performance ke liye materialized view use karo — CREATE MATERIALIZED VIEW hotel_ratings — har 10 minute refresh. CDC pipeline updated rating ko Elasticsearch tak pahunchata hai search ranking ke liye. ML service reviews ko scan karta hai profanity, spam aur fake reviews ke liye.
Q06 Global hotels ke liye time zones aur date calculations kaise handle karte hain?
Saare timestamps database me UTC me store hote hain. Hotels table me hotel_timezone column hota hai (IANA tz database, jaise 'Europe/London'). Check-in/check-out dates DATE type me store hoti hain — hotel ki local date. User search kare to dates hotel ke local timezone me interpret hoti hain, user ke timezone me nahi. Availability calculation me timezone conversion ki zaroorat hi nahi kyunki room_availability.date hotel local date hai. Payment deadlines UTC timestamp me store hote hain aur user ko uske local timezone me dikhaye jate hain. DST ke liye proper timezone library (moment-timezone) use karo, sirf UTC offset nahi.
Q07 Cancellation policies aur refund processing kaise implement karte hain?
Policy rules per hotel/room store hote hain — flexible (24h free, 12h tak 50%), moderate (72h free, 24h 50%), strict (7 din free). Booking banate time policy ka snapshot bookings.cancellation_policy me copy hota hai — policy baad me badle to user safe rehta hai. Refund hours_until_checkin se calculate hota hai. Cancellation ek transaction me hoti hai — bookings status CANCELLED + room_availability release. Refund async process hota hai — background job gateway ko refund bhejta hai, webhook confirm karta hai to status COMPLETED hota hai. Refund 5-7 business days me aata hai.
Q08 Search service 100M searches/day kaise scale karta hai?
Multi-tier strategy: ES cluster 10 data nodes + 3 master nodes, region se shard (US, EU, Asia), har region me 5 primary shards + 1 replica. Geo-based routing se user nearest cluster par jata hai. Redis cache — hit rate 60-70%, TTL 10 min, 100GB cluster ~10M cached searches. Query optimization: filter context use karo, track_scores false karo, sirf zaroori fields fetch karo. Rate limiting: per-user 100/min, per-IP 1000/min. 100 search instances ALB ke peeche, CPU >70% par auto-scaling. Load math: 1,157/sec average, peak 3,500/sec, capacity 5,000/sec. Cost ~$9K/month.
Q09 Overbooking scenarios aur inventory management kaise handle karte hain?
Hotels ke ek hi type ke multiple rooms hote hain — jaise 20 Deluxe rooms. Availability do tareekon se track hoti hai: aggregate (available_count/booked_count per date) ya individual (har room ki har date ki row). Booking se pehle check karo booked_count < total rooms ho range ki saari dates ke liye, phir distributed lock lo aur specific room assign karo (SELECT ... FOR UPDATE). Kuch hotels jaan-bujhkar 5-10% overbook karte hain cancellations ko account karne ke liye — overselling_limit table se control hota hai. Agar check-in day par asal me overbook ho jaye to hotel guest ko upgrade karta hai ya partner hotel me relocate karta hai.
Q10 Disaster recovery aur data consistency ki strategy kya hai?
Multi-region setup: primary us-east-1, warm standby us-west-2, tertiary eu-west-1. PostgreSQL streaming replication — lag <5 seconds. RPO 5 seconds (maximum data loss), RTO 5 minutes (service restore time). Route53 health checks 30 second failed checks par auto-failover karte hain — secondary promote hota hai, DNS update hota hai, total downtime 2-5 minute. Redis Sentinel automatic failover, AOF persistence. S3 cross-region replication images ke liye, Kafka MirrorMaker events ke liye. Failover ke dauraan in-flight bookings fail ho sakti hain — retry + idempotency se double booking nahi hoti. Monthly DR drills aur daily full + hourly incremental backups (30 din retention).
Q11 CAP theorem is hotel booking system me kaise apply hota hai?
CAP me trade-off hai: search ke liye Availability >>> Consistency, booking ke liye Consistency >>> Availability. Search highly available honi chahiye — 1-2 second purana data dikh jaye to chalega, lekin search down nahi honi chahiye, isliye Elasticsearch eventually consistent chalega. Booking me strong consistency zaroori hai — do users same room same dates kabhi book nahi kar sakte, isliye distributed locks + ACID transactions. Ye split design hi is system ki sabse important baat hai — ek hi consistency model dono jagah nahi chalta.
Q12 Elasticsearch me availability check kyu nahi karte?
Kyunki availability highly dynamic data hai — har booking par badalti hai. ES me availability store karoge to har booking par reindex karna padega — high latency, high cost aur inconsistency risk. ES text + geo search ke liye optimized hai, transactional data ke liye nahi. Isliye ES sirf location, price, rating aur amenities se hotels deta hai. Availability ke liye alag API hai jo PostgreSQL room_availability table ko query karti hai — wahan SELECT ... FOR UPDATE se strong consistency milti hai. Ye separation interview me zaroor bolna.
Q13 Redis lock aur database lock — dono kyu chahiye, ek kaafi nahi?
Redis lock fast hai (1-2ms) aur shuru me hi zyada tar concurrent requests ko reject kar deta hai — database tak load pahunchta hi nahi. Lekin Redis lock akela ACID guarantee nahi deta — Redis crash ho to lock ka state uncertain ho sakta hai. PostgreSQL SELECT ... FOR UPDATE transaction ke andar row-level lock deta hai — do transactions ek hi row ko ek saath change nahi kar sakti. Isliye dono: Redis pehli line of defence (fast rejection), PostgreSQL aakhiri guarantee (correctness). Sirf Redis use karoge to edge cases me double booking ho sakti hai; sirf DB lock use karoge to har concurrent request database tak pahunchegi aur slow hogi.
Q14 Lock key me full date range kyu include karte hain?
Lock key hoti hai lock:hotel:{hotel_id}:room:{room_id}:{check_in}:{check_out}. Full date range isliye kyunki overlapping dates ki bookings rokni hain. Agar key me sirf room_id hota to alag-alag dates ki bookings bhi block ho jati — concurrency kam ho jati. Agar date range na hoti to Feb 1-5 aur Feb 3-7 ki bookings ek saath nikal jati — overlap hone ke bawjood — aur double booking ho jati. Date range ke saath sirf overlapping bookings block hoti hain, non-overlapping bookings parallel chal sakti hain. Yehi granularity correctness aur performance dono deti hai.
Q15 Payment timeout 15 minute ka kya matlab hai?
Booking create hote hi user ko payment ke liye 15 minute milte hain. Booking status PENDING_PAYMENT hota hai aur Redis me SETEX booking:{booking_id}:expires 900 '1' set hota hai. 15 minute me payment nahi aaya to background job booking cancel karke room release kar deta hai — room_availability wapas 'Available' ho jati hai. Isse room hamesha ke liye block nahi rehta agar user payment chhod kar chala jaye. Payment complete hote hi expiry key delete ho jati hai aur booking CONFIRMED ho jati hai.
Q16 Idempotency key 24 ghante ke liye valid kyu hoti hai?
Payment gateway (Stripe/Razorpay) idempotency key ko 24 ghante tak yaad rakhta hai. Is duration me same key se dobara request aaye to gateway wahi payment_intent_id wapas deta hai — duplicate charge nahi hota. 24 ghante kaafi hain kyunki payment flow minute me complete hota hai; uske baad retry ka matlab naya payment hona chahiye. Database me payments(booking_id) UNIQUE constraint uske baad bhi hamesha ke liye protect karta hai — gateway ki 24h limit sirf gateway-level guarantee hai, database-level guarantee permanent hai.
Q17 CDC pipeline kya hai aur Elasticsearch kaise sync rehta hai?
CDC matlab Change Data Capture. Hotel DB (PostgreSQL) me kuch bhi badle — naya hotel, price change, rating update — to Debezium jaise tool se change capture hota hai, Kafka topic par event jata hai, aur Elasticsearch indexer consumer use event ko ES index me apply karta hai. Poora pipeline 1-2 second me complete hota hai. Isse search index hamesha fresh rehta hai bina search service ko database poll karne ke. Booking flow isse affect nahi hota — CDC async hai, write path block nahi hota.
Q18 Price calendar kya hai aur dynamic pricing kaise kaam karta hai?
Price calendar table hai {hotel_id, room_id, date, price, currency} — har room ki har date ka apna price. Composite PK (hotel_id, room_id, date) ensure karta hai ki ek date ka ek hi price ho. Dynamic pricing ML model se hoti hai — demand, season aur events dekh kar price adjust hota hai, jaise sheher me conference ho to +30%. Booking ka total price date range ke har din ke price ka SUM hota hai. Hotel admin bulk me dates update kar sakta hai, lekin booked dates kabhi override nahi hoti — UPDATE me AND status != 'Booked' condition hoti hai.
Q19 Room availability table per-room per-date row kyu rakhta hai?
Kyunki availability date-level granularity par decide hoti hai — ek room Feb 1 ko available ho sakta hai aur Feb 2 ko booked. Per-room per-date row se har date ka status alag se track hota hai, aur HAVING COUNT(available) = num_nights query se check hota hai ki range ki saari dates available hain ya nahi. Composite PK (hotel_id, room_id, date) duplicate rows rokta hai. Ye model simple hai, strongly consistent hai, aur SELECT ... FOR UPDATE se row-level lock lagta hai. 10M rooms × 365 dates badi table banti hai, isliye partitioning aur (room_id, date, status) index zaroori hai.
Q20 Composite primary key (hotel_id, room_id, date) kyu use hoti hai?
Composite PK ka matlab hai ki teeno columns milkar ek row ko uniquely identify karte hain. Price_calendar me isse ek room ki ek date ka sirf ek price ho sakta hai — duplicate price rows ban hi nahi sakte. Room_availability me isse ek room ki ek date ka sirf ek status ho sakta hai — do alag bookings ek hi row ko claim nahi kar sakti. Ye database-level guarantee hai — application code par depend nahi karta. Iske saath (hotel_id, date) ya (room_id, date, status) index lagta hai taaki range queries fast hon.
Q21 Hotels table me geo_pos par GIST index kyu lagta hai?
geo_pos geography(Point, 4326) type hai — latitude + longitude. Normal B-tree index lat/lng par range queries ke liye theek hai, lekin spatial queries (20km radius ke andar hotels) ke liye GIST index chahiye. GIST spatial data ko tree structure me organize karta hai — radius search me sirf relevant area ke rows scan hote hain, poori table nahi. Elasticsearch geo queries ke liye geo_point use karta hai, lekin PostgreSQL me geo_pos + GIST index backup ya direct spatial queries ke liye hai.
Q22 Read replicas ka use is system me kahan hota hai?
Read replicas read-heavy operations ke liye hain — hotel search ke baad hotel metadata fetch karna, user ki booking list dikhana, reviews list karna. Writes (booking create, payment, review submit) hamesha primary par jati hain. Isse primary par load kam hota hai aur read latency kam hoti hai — user ko nearest region ke replica se data milta hai. Search flow me ES se hotel IDs milne ke baad metadata replicas se aati hai. Dhyaan rakhna: replica data 1-2 second purana ho sakta hai (replication lag <5s) — booking jaise critical reads kabhi replica se nahi karte.
Q23 Kafka topics kaun se hain aur notification service kaise kaam karta hai?
Topics hain: booking.created, booking.confirmed, booking.cancelled, payment.success, payment.failed. Booking Service aur Payment Service in par publish karte hain. Notification Service in sab ko alag-alag consumer groups se consume karta hai — reliability ke liye. 'booking.confirmed' par ye User DB se email/phone fetch karta hai, Booking DB se details leta hai, QR code ke saath email template banata hai aur SendGrid/SES se email + Twilio se SMS bhejta hai. Push notifications FCM/APNS se aati hain. Consumer offset tabhi commit karta hai jab notification send ho jaye — exactly-once delivery.
Q24 Booking status lifecycle kya hai — PENDING_PAYMENT se COMPLETED tak?
Booking 4 states se guzarti hai: PENDING_PAYMENT (booking bani, payment baaki, 15 min timeout), CONFIRMED (payment success, webhook processed), COMPLETED (check-out date beet gayi — stay ho gaya), CANCELLED (user ya system ne cancel ki). Payment fail ho to booking PENDING_PAYMENT se expire hokar cancel ho jati hai aur room release ho jata hai. COMPLETED ke baad hi user review likh sakta hai. Status transitions hamesha transaction me hote hain — booking status aur room_availability status ek saath update hote hain, aadhe nahi.
Q25 Cancellation me policy snapshot kyu store karte hain?
Booking banate time hotel ki cancellation policy ka copy bookings.cancellation_policy (jsonb) me store hota hai. Isse user safe rehta hai — agar hotel booking ke baad policy strict kar de (jaise flexible se strict), to user ko purani policy ke hisaab se hi refund milta hai. Ye fairness aur legal protection dono hai. Refund calculation hamesha snapshot policy se hoti hai, current policy se nahi. Yehi pattern price ke liye bhi hai — booking ka amount booking time ka price hota hai, baad me price badle to farak nahi padta.
Q26 Controlled overbooking 5-10% kyu karte hain hotels?
Airlines ki tarah hotels bhi jaante hain ki 15-20% bookings cancel ho jati hain. Agar hotel 100% rooms hi beche to cancellation ke baad rooms khali reh jayenge — revenue loss. Isliye kuch hotels 5-10% zyada bookings lete hain (overselling_limit table, max_overbook_percent 0.05). Risk ye hai ki check-in day par asal me zyada guests aa jayein — tab hotel guest ko better room upgrade karta hai ya partner hotel me relocate karta hai, apne kharch par. Ye deliberate business decision hai, bug nahi — aur iska control system me hona chahiye, accidental overbooking se alag.
Q27 Geo sharding Elasticsearch me kaise kaam karta hai?
Hotel index ko region se shard kiya jata hai — US, EU, Asia alag shards. Har region me 5 primary shards + 1 replica hote hain. User search kare to API Gateway use nearest ES cluster par bhejta hai — US user us-east-1, EU user eu-west-1. Isse latency 500ms se 50ms ho jati hai aur ek region ka load doosre region ko affect nahi karta. Hotel updates CDC pipeline se saare regions ke clusters me sync hote hain. Sharding ke bina ek hi cluster par 100M searches/day ka load sambhalna mushkil hota.
Q28 Search cache TTL 10 minute — stale data ka risk nahi?
Risk hai, lekin acceptable hai — kyunki search results me availability hoti hi nahi, sirf hotel metadata (naam, location, price_range, rating). Ye data ghanton me badalta hai, second me nahi. 10 minute purana price_range dikh jaye to bhi user hotel select karne par availability API se fresh price dekh lega. Isliye cache TTL 10 min safe hai. Hotel metadata change ho to cache invalidate bhi hoti hai. User bookings ka TTL sirf 5 min hai kyunki wo jaldi badalti hai, aur hotel details ka 30 min. Har cache ka TTL us data ki change frequency ke hisaab se tay hota hai.
Q29 Rate limiting 100 req/min per user kyu hai?
Rate limiting abuse aur scraping se bachata hai. Token bucket algorithm se implement hota hai — har user ko 100 requests per minute ki bucket milti hai. Search API sabse zyada abuse hoti hai — bots 100M searches/day ka system scrape kar sakte hain. Per-IP limit 1000/min bhi hai. API Gateway par rate limiting lagti hai — service tak request pahunchne se pehle hi reject ho jati hai. Genuine user ko 100/min kaafi hai — ek user minute me 100 searches nahi karta.
Q30 Bookings table ko date se partition kyu karte hain?
Bookings table sabse tezi se badhti hai — 1M bookings/day matlab saal me 365M rows. Monthly partitions se har partition chhota rehta hai — query sirf relevant partition scan karti hai (partition pruning), poori table nahi. Purana data archive karna easy hota hai — purani partition ko alag storage par move karo ya drop karo. Index bhi chhote rehte hain. Partitioning ke bina 365M rows ki table par har query slow ho jayegi, aur backup bhi mushkil hoga.
Q31 Connection pooling kyu zaroori hai is system me?
Har API request par naya database connection banana mehenga hai — TCP handshake + authentication + memory. Connection pool pehle se 100-200 connections khol kar rakhta hai aur requests unhe share karti hain. Pool ke bina 100M searches/day par har request naya connection banayegi — database connection limit khatam ho jayegi aur naye requests fail honge. Pool size carefully set karna hota hai — bahut chhota ho to requests wait karengi, bahut bada ho to database par load badhega. Har service instance apna pool maintain karta hai.
Q32 CDN images ke liye 95% cache hit rate ka matlab kya hai?
Hotel aur room photos S3 me store hoti hain aur CloudFront CDN se serve hoti hain. 95% hit rate ka matlab hai ki 100 image requests me se 95 edge location (user ke paas ke server) se serve hoti hain — origin S3 tak jaane ki zaroorat nahi. Isse image load <50ms me hota hai globally. Sirf 5% requests origin tak jati hain (pehli baar ya cache expire hone par). Lazy loading ke saath milkar — images tabhi load hoti hain jab user scroll kare — page load fast rehta hai aur bandwidth bachta hai.
Q33 Review sirf completed booking par kyu likh sakte hain?
Teen wajah: pehli — fake reviews rokna. Koi bhi hotel ko bina stay kiye 5 star ya 1 star nahi de sakta. Doosri — review genuine experience par based hota hai — user ne asal me stay kiya hai. Teesri — ek booking par ek hi review (reviews.booking_id UNIQUE) — user dobara review nahi likh sakta. Validation me check hota hai: booking exist karti hai, user ki hai, check_out < today hai, aur pehle review nahi hai. Isse rating system trustworthy rehta hai aur search ranking sahi hoti hai.
Q34 Materialized view ratings ke liye kyu behtar hai?
Har review par poori reviews table ka AVG nikalna mehenga hai — popular hotel ke 100,000 reviews scan honge har baar. Materialized view pehle se calculate karke result store karti hai — CREATE MATERIALIZED VIEW hotel_ratings AS SELECT hotel_id, AVG(rating), COUNT(*) FROM reviews GROUP BY hotel_id — har 10 minute refresh hoti hai. Rating read karna instant ho jata hai. Rating 10 minute purani dikhna acceptable hai — search ranking ke liye real-time rating zaroori nahi. Real-time chahiye to Apache Flink use karo, lekin materialized view simpler aur kaafi hai.
Q35 Daylight saving time (DST) edge case kaise handle karte hain?
Sirf UTC offset use karoge to DST par galat time dikhega — jaise London me March me offset +0 se +1 ho jata hai. Isliye proper timezone library use karo — moment-timezone ya date-fns-tz — jo IANA tz database se DST rules jaanta hai. Hotels table me hotel_timezone column IANA naam store karta hai ('Europe/London'), offset nahi. Dates DATE type me store hoti hain (time-of-day nahi), isliye check-in dates DST se affect nahi hoti. Payment deadlines UTC timestamp me hote hain — display ke time user ke local timezone me convert hote hain library se.
Q36 Failover ke dauraan in-flight bookings ka kya hota hai?
Primary region down hote hi Route53 30 second me detect karta hai aur DNS secondary region par point karta hai. Jo bookings usi waqt process ho rahi thi, wo fail ho sakti hain — user ko temporary error dikhega. Lekin idempotency ki wajah se retry safe hai: booking retry kare to same booking_id se dobara charge nahi hoga, aur distributed lock + transaction ensure karte hain ki room do baar book na ho. User retry kare to booking naye region me succeed ho jati hai. Data loss <5 second hota hai (RPO) — synchronous replication ki wajah se. Total downtime 2-5 minute (RTO) DNS propagation ke liye. RPO aur RTO ka farak: RPO (Recovery Point Objective) batata hai kitna data loss acceptable hai — yahan <5 seconds; RTO (Recovery Time Objective) batata hai service restore karne me kitna time lagega — yahan <5 minutes. Dono monthly DR drills me test hote hain.
