OTT Platform Design — Netflix / Prime / Hotstar jaisa system

Ek line me yaad rakhna: Video upload (transcoding) → CDN delivery → Adaptive Streaming (HLS/DASH) → Low-latency playback → Subscription management → Analytics. Is lesson me poora OTT system design karenge — 200M users, 20M daily viewers, 10k videos, 400TB storage, 10 Tbps peak bandwidth — sab kuch Hinglish me, interview-ready.

Is lesson ka design diagram

Neeche wahi hand-drawn design diagram hai jo lesson me hai — isme Functional Requirements, Non-Functional Requirements, Core Entities, APIs, Estimation, High Level Design aur Deep Dive Design ek hi page par dikhaye gaye hain. Diagram ke andar likha hua chhota text yahan neeche sections me poora Hinglish me samjhaya gaya hai.

Diagram me kya-kya dikh raha hai

  • Upar left: Functional Requirements (account, search, alag-alag resolutions, bina buffering ke playback) aur Non-Functional Requirements (200M users, 10k videos, high availability > consistency, payment me strong consistency).
  • Upar right — Estimation: 10k videos — 720p: 10GB/hr, 1080p: 20GB/hr, 1440p: 30GB/hr; kul 40GB × 10k = 400k GB = 400TB. (Note: lesson ke text wale hisse me 720p 6GB/hr, 1080p 12GB/hr, 4K 24GB/hr diye hain — dono jagah ke numbers alag hain, ye farq §09 aur Trust Check me imaandari se likha hai.)
  • High Level Design: Clients → API Gateway (Routing, Rate Limiting, Authorization & Authentication) → User Service → User DB; Search Service → Video Metadata; Play Service → Blob Storage (video files + image files); Uploader → Video Metadata + Blob Storage.
  • Adaptive Streaming note: Switching sirf keyframes par hoti hai. Video segment 10 second ka hota hai; keyframe 0th second par set hota hai; usi keyframe point par client ki bandwidth dekhkar player agle segment ke liye wahi ya alag resolution maangta hai.
  • DASH vs HLS table (diagram me): Manifest format (MPD vs M3U8), Segment format, Bitrate Switching Control (DASH zyada flexible — multiple segments pre-fetch kar sakta hai; HLS sequential — ek time par ek segment), Default Keyframe Interval (DASH 2s–4s; HLS 6s–10s), Segment Loading, Latency (DASH-LL 1–3s; HLS-LL 2–6s).
  • Low / Deep Dive Design: CDN (manifest file + video chunks; cache miss par S3 se update), API Gateway (Load Balancing, Routing, Rate Limiting, Auth, Round Robin), User Service → User DB (MySQL: name, email, password, subscription status, expire date), Search Service → Elastic Search → CDC → Video Metadata (MongoDB), Redis, Play Service (response me manifest file bhejta hai), Subscription Service → Kafka → Consumer → User DB update, Payment Service → Payment DB (MySQL: paymentId, userId, status, subscriptionId) → Payment Gateway, Notification Service, Uploader → Chunker (encoded video ko 2–10 sec ke chhote segments me todta hai, .m3u8/.mpd manifest banata hai) → Kafka (video processing) → Video Encoder (.mp4 H.264/H.265, .ts, multiple bitrates: 480p, 720p, 1080p, 4K) → S3 (video files + image files).

01Requirements

Functional Requirements

Functional requirements matlab — system ko kya-kya karna chahiye. Interview me pehle ye 5 features bolte hain, phir scale ki baat karte hain.

5 features jo system me hone chahiye

  • Feature 1 — Account aur subscription: User account bana sake, login/logout kar sake, aur subscription plan choose kar sake (register, login, logout, subscription plans).
  • Feature 2 — Search aur discovery: User movies/shows ko product title ya naam se search karke dhoondh sake.
  • Feature 3 — Alag-alag resolutions: User video ko alag-alag resolutions me dekh sake — 1080p, 4K, 720p, 480p — device aur network ke hisaab se.
  • Feature 4 — Bina buffering ke playback: Video dekhte waqt nominal ya negligible buffering ho — adaptive streaming se quality apne aap adjust ho.
  • Feature 5 — Content upload: Content creators videos upload kar sakein — movies, series, documentaries — metadata ke saath.

Interview tip: Functional requirements batate waqt hamesha user aur creator dono ki taraf se socho — user dekhna chahta hai, creator upload karna chahta hai. Dono cover karo to poora lagta hai.

02Requirements

Non-Functional Requirements

Non-functional requirements matlab — system kis scale par aur kitni quality ke saath chalna chahiye. Yahi woh jagah hai jahan numbers bolte hain.

Scale

Performance & Availability

  • CAP Theorem: Highly available >> consistency. Video metadata ke liye eventual consistency chalegi — video dikhna band nahi hona chahiye, metadata thoda purana chalega.
  • Video Streaming: Low-latency streaming, adaptive bitrate ke saath (HLS/DASH).
  • Payment Consistency: Order aur payment wali jagah strong consistency chahiye — paise ka mamla hai, yahan eventual consistency nahi chalegi.
  • Buffering: Minimal buffering — 2–3 second se kam, kharab network par bhi smooth playback.
🎯 Interview favourite: Interview me NFR batate waqt CAP ka trade-off zaroor bolo: availability ko consistency se upar rakha hai — sirf payment/subscription wali jagah strong consistency. Ye ek line tumhe alag dikhati hai.

03Requirements

Core Entities

Core entities matlab — system ke andar kaun-kaun se main objects hain aur unme kya data hota hai. Database schema (§07) isi par banta hai.

  • Entity 1 — User: Customer — user_id, name, email, subscription_status, watch_history[], preferences.
  • Entity 2 — User Metadata: User ka extra data — device info, viewing patterns, subscription details.
  • Entity 3 — Video: Content — video_id, title, description, genre, duration, content_rating, release_date.
  • Entity 4 — Video Metadata & Static Image: Thumbnail, poster, metadata (actors, director, etc.), subtitles, audio tracks.

Interview me entities batate waqt har entity ke 4–5 main fields bol do — isse aage API aur schema design karna aasan ho jata hai, aur interviewer ko lagta hai tumne sochkar design kiya hai.

05Design

High Level Design

HLD matlab — bade-bade boxes aur unke beech ke teer. Neeche diagram bhi hai aur har box ka kaam bhi.

Request ka flow — user se video tak

  • Users → API Gateway: Load balancing, authentication, authorization, rate limiting — har request pehle yahin aati hai.
  • User Service → User DB: User profiles, authentication, preferences.
  • Search Service → Elasticsearch: Video search — title, genre, actors se full-text search.
  • Play Service: Video streaming ke liye manifest file (HLS/DASH) banata hai.
  • Uploader: Content creators raw video files Blob storage (S3) me upload karte hain.
  • Video Processing Pipeline: Transcoding, compression, multiple resolutions (4K, 1080p, 720p, 480p, 360p).
  • Video Metadata DB: Video metadata, thumbnail URLs, available resolutions, subtitle tracks store karta hai.
  • Blob Storage (S3): Raw uploaded videos aur transcoded video files — video_id/resolution/ ke hisaab se organized.
  • CDN: Video chunks edge caching ke saath deliver karta hai — low-latency global playback.

06.1Deep Dive — LLD

Step 1: Video Upload & Metadata

Sab kuch upload se shuru hota hai. Creator raw video bhejta hai, system use ID deta hai, S3 me rakhta hai aur metadata DB me entry karta hai.

  • Creator upload karta hai: Raw video file (jaise movie.mp4, 50GB 4K) + metadata — {title, description, genre, actors, duration, language}.
  • Uploader service — 3 kaam: (1) video_id generate karta hai (UUID), (2) S3 me multipart upload banata hai — s3://videos-raw/{video_id}/original.mp4, (3) Video Metadata DB me metadata store karta hai — {video_id, title, description, genre, duration, upload_status: 'PROCESSING', created_at}.
  • Upload complete hote hi: Lambda/SQS event trigger hota hai — {video_id, s3_path} ke saath. Yahi event aage transcoding pipeline ko jagata hai.
  • Metadata me kya-kya: Title, description, genre[], actors[], director, release_date, content_rating (PG-13, R), language[], subtitle_tracks[], audio_tracks[], thumbnail_url, poster_url.
  • Images alag se upload: Thumbnails aur posters S3 me — s3://video-images/{video_id}/thumbnail.jpg — aur CDN se serve hote hain.
🎯 Interview favourite: Multipart upload kyun? 50GB ki file ek hi request me nahi bhej sakte — tut jayegi. Multipart me file chhote tukdon me parallel upload hoti hai, aur beech me fail ho to sirf wahi tukda dobara bhejta hai.

06.2Deep Dive — LLD

Step 2: Video Transcoding Pipeline

Ye poore system ka sabse critical step hai — adaptive streaming isi par khada hai. Ek raw video se 5 resolutions, har ek ke 10-second segments, aur manifest file banti hai.

Trigger kaise hota hai

Lambda SQS message consume karta hai — {video_id, s3_path: 's3://videos-raw/{video_id}/original.mp4'}.

Transcoding service — 3 kaam

  • (1) Original video S3 se download karta hai.
  • (2) FFmpeg / AWS MediaConvert se multiple resolutions aur bitrates me transcode karta hai.
  • (3) Resolutions: 4K (3840×2160, 20 Mbps), 1080p (1920×1080, 8 Mbps), 720p (1280×720, 5 Mbps), 480p (854×480, 2.5 Mbps), 360p (640×360, 1 Mbps).

Har resolution ke liye — 4 steps

  • (a) Video transcode karo.
  • (b) 10-second chunks me todo (HLS/DASH ke liye).
  • (c) S3 me upload karo — s3://videos-processed/{video_id}/{resolution}/segment_001.ts, segment_002.ts, …
  • (d) Manifest file banao — master.m3u8 (HLS) ya master.mpd (DASH).

HLS vs DASH — ek line me

  • HLS (HTTP Live Streaming): Apple standard — .m3u8 playlist, .ts video segments.
  • DASH (Dynamic Adaptive Streaming over HTTP): MPEG standard — .mpd manifest, .m4s segments.

Chunker service: Video ko 10-second chunks me todta hai aur S3 me resolution ke hisaab se organize karke upload karta hai. Manifest file structure: Master playlist resolution-specific playlists ki taraf ishara karti hai, aur har resolution playlist me segment URLs ki list hoti hai.

Example master.m3u8
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=8000000,RESOLUTION=1920x1080
1080p/playlist.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1280x720
720p/playlist.m3u8
  • Video encoder: Alag-alag bitrates par compress karta hai — same resolution par kam bitrate matlab chhoti file, kam quality.
  • Metadata update: UPDATE video_metadata SET processing_status='COMPLETED', resolutions=['4K','1080p','720p','480p','360p'], manifest_url='s3://videos-processed/{video_id}/master.m3u8' WHERE video_id={video_id}
  • Transcoding time: 2-hour 4K movie ke liye ~30–60 min, GPU instances par parallel processing se.
  • Cost optimization: Transcoding ke liye spot instances use karo, queue depth ke hisaab se auto-scale karo.
⚠ Dhyaan do: NEVER transcode synchronously on upload. Hamesha async pipeline rakho: Upload → S3 → Kafka event → Workers → Transcoding → S3. 2-hour 4K movie transcode hone me 30–60 min lagte hain — user ko itni der rokna bewakoofi hai.

06.3Deep Dive — LLD

Step 3: Video Search (Elasticsearch)

Search itna fast kyun hota hai? Kyunki video metadata pehle se Elasticsearch me index hota hai — har search par database scan nahi hota.

User search karta hai: GET /v1/videos/search?q=Inception&genre=Sci-Fi&language=English

Search Service Elasticsearch se poochta hai — title, description, actors, director par full-text search.

Elasticsearch query
{ 'query': { 'bool': { 'must': [ { 'multi_match': { 'query': 'Inception',
  'fields': ['title^3', 'description', 'actors', 'director'] } } ],
  'filter': [ { 'term': { 'genre': 'Sci-Fi' } }, { 'term': { 'language': 'English' } } ] } },
  'sort': [ { 'popularity_score': 'desc' } ], 'size': 20 }
  • Popularity score: view_count, rating aur recency ka combination — offline calculate hota hai, periodic update hota hai.
  • Response: [{ video_id, title, thumbnail_url, duration, rating, genre }]
  • Caching: Popular searches Redis me cache hoti hain — TTL = 10 min.
  • CDC pipeline: Video Metadata DB → Kafka → Elasticsearch indexer — search index hamesha sync me rehta hai.
  • Index structure: Har video document me — video_id, title (text), description (text), genre (keyword), actors (text), language (keyword), popularity_score (float), release_date (date).

title^3 ka matlab: title me match hone par score 3 guna — title match description match se zyada important hai. Ye ek line interview me bolna achha lagta hai.

06.4Deep Dive — LLD

Step 4: Video Playback Request

User ne Play dabaya — ab kya hota hai? Video file seedha nahi milti; pehle subscription check hota hai, phir manifest URL milta hai, phir player segments download karta hai.

User clicks play: GET /api/v1/videos/{video_id}/play

Play Service — 4 steps

  • (1) User ka subscription status validate karta hai — active subscription hai ya nahi.
  • (2) Video Metadata DB se manifest URL nikalta hai — SELECT manifest_url, resolutions FROM video_metadata WHERE video_id={video_id}.
  • (3) CDN-signed URL generate karta hai — CloudFront signed URL, expiry = 4 hours.
  • (4) Client ko manifest URL wapas bhejta hai — { manifest_url: 'https://cdn.example.com/{video_id}/master.m3u8?Expires=...&Signature=...' }.

Client video player — 4 steps

  • (1) Master.m3u8 manifest fetch karta hai.
  • (2) Available resolutions aur bitrates parse karta hai.
  • (3) Network speed ke hisaab se initial resolution choose karta hai (adaptive bitrate logic).
  • (4) Video segments download karna shuru karta hai.
  • Adaptive streaming: Player buffer level aur network speed monitor karta hai, resolution dynamically switch karta hai (jaise 1080p → 720p agar network kharab ho).
  • Segment requests: GET https://cdn.example.com/{video_id}/1080p/segment_001.ts, segment_002.ts, … — har segment ~2–3 MB (10-second chunk).
  • CDN caching: Edge locations segments cache karte hain — popular content par 95%+ cache hit rate, <50ms latency.
  • Player buffering: 3–5 segments aage download karke rakhta hai (30–50 seconds) — network hilne par bhi smooth playback.
💡 Tip: Signed URL kyun? Manifest URL par expiry + signature lagane se koi bhi link copy karke free me video nahi dekh sakta — 4 ghante baad link bekaar. Yehi hotlinking se bachav hai.

06.5Deep Dive — LLD

Step 5: Adaptive Streaming — How it Works

Adaptive bitrate streaming (ABR) ka matlab — network jaisa, quality waisi. Player har segment ke baad bandwidth naapkar agla segment usi hisaab se maangta hai.

Player logic — 3 steps

  • (1) Download speed naapo — last segment download karne me laga time / segment size = throughput (Mbps).
  • (2) Available bandwidth estimate karo.
  • (3) Sahi resolution chuno — bandwidth > 8 Mbps → 1080p; 5–8 Mbps → 720p; 2.5–5 Mbps → 480p; <2.5 Mbps → 360p. (4K ke liye ~20 Mbps chahiye — ladder ke hisaab se.)
  • Switching: Player playlists (resolution levels) ke beech playback ke beech me seamlessly switch karta hai — bina rebuffering ke.
  • Buffer management: 20–40 second ka buffer rakho; agar buffer 10 second se neeche gir jaye to stalling rokne ke liye turant lower quality par jao.
  • Quality metrics — 3 cheezein track karo aur kam rakho: (1) Initial buffering time (pehla frame aane tak ka time), (2) Rebuffering events (playback ke beech rukna), (3) Bitrate switches (baar-baar switch hona = kharab UX).

Example scenario

User WiFi par dekh raha hai (8 Mbps) → Player 1080p choose karta hai → User chalta hai, WiFi 3 Mbps par gir jata hai → Player slow download detect karta hai → 480p par switch kar deta hai → Buffering smoothly chalti rehti hai.

Keyframe alignment: Video segments I-frames (keyframes) se shuru hone chahiye, taaki quality switching seamless ho.

Diagram wali baat — keyframe rule

Design diagram me saaf likha hai: (1) Switching sirf tab hoti hai jab keyframe 0th second par set ho, (2) Maan lo keyframe 0th second par set hai, (3) Us keyframe point par client ki bandwidth ke hisaab se player ya to purani resolution (1080) se continue karta hai, ya kisi aur resolution se resume karta hai. Matlab — har 10-second segment keyframe se shuru hota hai, isiliye player beech me resolution badal sakta hai bina video tode.

⚠ Dhyaan do: CRITICAL: Adaptive streaming ke liye keyframes segment boundaries (0th second) par hone chahiye. Iske bina quality switching par stuttering hota hai. FFmpeg: -g 300 -keyint_min 300 — 10-sec segments ke liye 30fps par 300 frames.
🎯 Interview favourite: Interviewers ALWAYS poochte hain: 'Adaptive bitrate streaming kaise kaam karta hai?' Jawab: (1) Multiple resolutions me transcode karo, (2) 10-sec segments me todo, (3) Manifest me saare options likho, (4) Player bandwidth naape, (5) Resolution dynamically choose kare, (6) Keyframes par seamlessly switch kare.

06.6Deep Dive — LLD

Step 6: CDN Architecture for Video Delivery

CDN ka kaam — video ko user ke sabse paas wale server se dena, origin (S3) se nahi. Isse latency 200ms se 10ms ho jati hai.

  • CDN setup: Origin = S3 bucket (s3://videos-processed/), Edge locations = CloudFront PoPs (200+ globally).
  • Request flow: (1) India ka user segment maangta hai — GET cdn.example.com/{video_id}/1080p/segment_050.ts, (2) DNS nearest edge (Mumbai PoP) par bhejta hai, (3) Edge cache check karta hai, (4) Miss hone par: Origin S3 (us-east-1) se fetch karta hai → 200ms, edge par 24 hours ke liye cache karta hai, (5) Hit hone par: Edge cache se serve karta hai → 10ms.
  • Cache hit ratio: Popular content (trending movies, recent releases) par 95%+.
  • Cache eviction: LRU (Least Recently Used) — popular content ko priority.
  • Origin shield: Edge aur origin ke beech ek aur caching layer — origin load 90% kam kar deta hai.
  • Compression: Manifest files (.m3u8, .mpd) par Gzip/Brotli compression — bandwidth bachta hai.
  • Security: Signed URLs with expiry — hotlinking aur unauthorized access rokte hain; URL 4 hours ke liye valid.
  • Monitoring: CloudWatch track karta hai — cache hit rate, error rate (4xx, 5xx), bandwidth usage, origin requests.
  • Cost: CDN bandwidth ~$0.085/GB — 10M users × 2 hours/day streaming = 20M hours × 3 GB/hour × $0.085 = $5.1M/month bandwidth.
💡 Tip: CDN optimization: 95% cache hit rate critical hai. Popular content (trending movies) release se pehle edges par pre-warm karo. Long-tail content on-demand cache karo. Isse origin bandwidth cost me ~$30M/month bachte hain.

Step 7: Subscription Management

Subscription wahi jagah hai jahan paise ka mamla hai — isliye yahan strong consistency, transactions aur idempotency, sab kuch chahiye.

User subscribes: POST /v1/subscriptions — {user_id, plan_id: 'premium', payment_method_id}.

Subscription Service — 3 steps

  • (1) Plan exists karta hai ya nahi validate karo — SELECT * FROM subscription_plans WHERE plan_id={plan_id}.
  • (2) Payment Gateway (Stripe/Razorpay) se payment intent banao — {amount, currency, customer_id, metadata: {user_id, plan_id}}.
  • (3) Client ko payment_url wapas do.

Payment success webhook

POST /webhooks/payment — {payment_id, status: 'success', metadata} aane par:

  • (1) Subscription Service: BEGIN TRANSACTION; INSERT INTO subscriptions (subscription_id, user_id, plan_id, status='ACTIVE', start_date=now(), end_date=now()+30days, payment_id); UPDATE users SET subscription_status='ACTIVE'; COMMIT;
  • (2) Kafka event publish karo — 'subscription.created'.

  • Cancellation: PUT /v1/subscriptions/{subscription_id}/cancel → UPDATE subscriptions SET status='CANCELLED', cancelled_at=now() — access end_date tak rehta hai.

Step 8: Watch History & Recommendations

User ne video kahan tak dekhi — ye data har 10 second me aata hai. 20M users × har 10 sec ek update = 2M writes/sec. Itna load sirf Redis + Cassandra sambhal sakte hain, PostgreSQL nahi.

  • Playback tracking: Client har 10 second me heartbeat bhejta hai — POST /v1/videos/{video_id}/progress — {user_id, current_time_seconds, device_id}.

08.1Streaming Protocols

HLS (HTTP Live Streaming) — Apple Standard

HLS Apple ka standard hai — .m3u8 playlist aur .ts segments. iOS, macOS aur zyada tar smart TVs par native support hai.

  • Format: Master playlist (.m3u8) → Resolution playlists (.m3u8) → Segments (.ts files, 10 sec each).
  • Master Playlist: #EXTM3U, #EXT-X-STREAM-INF:BANDWIDTH=8000000,RESOLUTION=1920x1080 → 1080p/playlist.m3u8, #EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1280x720 → 720p/playlist.m3u8.
  • Resolution Playlist: #EXTM3U, #EXT-X-TARGETDURATION:10, #EXTINF:10.0, → segment_001.ts, #EXTINF:10.0, → segment_002.ts.
  • Browser Support: Safari (native), Chrome/Firefox (hls.js library se).
  • Advantages: Wide support (iOS, macOS, most smart TVs), adaptive bitrate, reliable.

08.2Streaming Protocols

DASH (Dynamic Adaptive Streaming over HTTP) — MPEG Standard

DASH MPEG ka open standard hai — .mpd manifest (XML) aur .m4s segments. Codec ki koi pabandi nahi — H.264, H.265, VP9, sab chalte hain.

  • Format: Media Presentation Description (.mpd XML) → Segments (.m4s files).
  • MPD Structure: XML me har resolution ke liye <AdaptationSet>, <Representation> bitrate/resolution batata hai, <SegmentTemplate> segment URLs batata hai.
  • Browser Support: Chrome, Firefox, Edge (dash.js se) — Safari par NOT (Apple devices ke liye HLS use karo).
  • Advantages: Codec agnostic (H.264, H.265, VP9), DRM support, open standard.

Q1: Adaptive bitrate streaming kaise kaam karta hai?

Ye interview ka sabse zyada poochha jaane wala sawaal hai. Jawab 6 steps me do.

  • (1) Video preparation: Original video multiple resolutions me transcode hota hai — 4K/2160p at 20 Mbps, 1080p at 8 Mbps, 720p at 5 Mbps, 480p at 2.5 Mbps, 360p at 1 Mbps (FFmpeg/MediaConvert se).
  • (2) Segmentation: Har resolution 10-second chunks (segments) me todi jati hai.
  • (3) Manifest file: HLS master.m3u8 ya DASH master.mpd — saare available resolutions aur bitrates ki list.
  • (4) Player logic: (a) Client manifest maangta hai, (b) Segment download ka time naapkar bandwidth measure karta hai — bandwidth = segment_size / download_time, (c) Sahi resolution chunta hai — bandwidth > 8 Mbps → 1080p segments, 5–8 Mbps → 720p, 2.5–5 Mbps → 480p, <2.5 Mbps → 360p, (d) Segments sequentially download karta hai, (e) Buffer level (20–40 sec aage) monitor karta hai, (f) Bandwidth gire ya buffer khaali ho to agle segment ke liye lower resolution par switch karta hai.
  • (5) Seamless switching: Segments keyframes (I-frames at 0th second) par aligned hote hain — player playback ke beech me playlists switch karta hai bina rebuffering ke.
  • (6) Quality metrics: Initial buffering time, rebuffering events, bitrate switches (baar-baar switch = kharab UX) — teeno track karo.

Q3: Buffering kaise kam karte ho? Smooth playback kaise ensure karte ho?

Buffering rokne ke liye ek nahi, 11 layers hain — interview me 5–6 bolna kaafi hai, yahan saari di hain.

  • (1) Adaptive bitrate: Bandwidth girte hi quality auto-kam karo (8 Mbps → 1080p, 3 Mbps → 480p) — network hilne par stalling rokta hai.
  • (2) Buffering strategy: Player 20–40 sec ka buffer rakhta hai (3–5 segments aage download); buffer <10 sec ho to aggressive switch lower resolution par + segment prefetch badhao.
  • (3) CDN edge caching: Segments 200+ CloudFront PoPs par cache hote hain — 95% cache hit rate, <50ms latency (origin se 200ms ke muqable).
  • (4) Segment size: 10-sec segments (30-sec ke muqable) — fast quality switching, fast seeking, chhote chunks par network interruption ka kam asar.
  • (5) Preloading: Video start hote hi pehle 2–3 segments lower quality par download karo — instant playback, phir optimal quality par switch karo.
  • (6) Connection optimization: HTTP/2 multiplexing — parallel segment downloads, connection keep-alive se handshake overhead kam.
  • (7) Predictive prefetching: Series dekh raha hai to agle episode ke pehle 2 segments preload karo.
  • (8) Network condition monitoring: Player track karta hai — segment download time, throughput (Mbps), buffer level, packet loss — aur quality proactively adjust karta hai.
  • (9) Fallback quality: Ek hi quality par multiple segments fail hon to turant 2 levels neeche jao (1080p → 480p, gradual 1080p → 720p → 480p nahi).
  • (10) CDN failover: Edge location error (5xx) aaye to automatic retry — doosre PoP ya origin shield se.
  • (11) Client-side optimization: Hardware decoding (GPU) H.264/H.265 ke liye — CPU load kam; video.js/hls.js jaise optimized players smart buffering logic ke saath.

Quality metrics (targets): Initial buffering time — pehla frame aane tak ka time, target <2 sec. Rebuffering ratio — buffering me bita time / kul watch time, target <0.5%. Bitrate switches — baar-baar switch pareshan karta hai, target <5 switches per hour.

Example scenario: User dekhna shuru karta hai → Player 1080p maangta hai → Pehle 2 segments fast download hote hain (WiFi, buffer 20 sec) → User chalta hai, WiFi kamzor → Segment 3 slow download (detect hua) → Player segment 4 ke liye 720p par switch karta hai → Buffering bina ruke chalti rehti hai → User ko spinner kabhi dikhta hi nahi.

11.4Interview Q&A

Q4: Global video delivery ke liye CDN architecture kaise design karoge?

Multi-tier CDN — Origin → Origin Shield → Edge. Har layer ka ek kaam hai, aur har layer origin load kam karta hai.

  • (1) Origin: S3 buckets multiple regions me (us-east-1, eu-west-1, ap-south-1), cross-region replication — transcoded video segments store karte hain.
  • (2) Origin Shield: CloudFront feature — edge aur origin ke beech centralized caching layer; requests collapse karta hai (100 edge requests → 1 shield request origin ko), origin load 90% kam, cache hit rate behtar.
  • (3) Edge Locations: 200+ CloudFront PoPs globally (NYC, London, Mumbai, Tokyo, …), segments TTL = 24 hours ke saath cache karte hain, 95% requests bina origin hit ke serve karte hain.
  • (4) Request flow: Mumbai ka user segment maangta hai → DNS nearest edge (Mumbai PoP) par bhejta hai → Edge cache check karta hai (cache key: video_id/resolution/segment_number) → HIT ho to cached segment wapas (10–50ms) → MISS ho to Origin Shield (us-east-1) se maango → Shield cache check kare → miss ho to S3 se fetch karo → Shield cache kare + wapas bheje → Edge cache kare + wapas bheje (pehli baar 200ms, uske baad <50ms).
  • (5) Cache optimization: (a) Popular content (trending movies) — release se pehle edges par pre-warm karo, (b) Long-tail content — on-demand cache karo (pehli request slow, uske baad fast), (c) Purge strategy — segments tabhi invalidate karo jab video update ho (rare), nahi to TTL par bharosa karo.
  • (6) Geo-routing: Har region me S3 bucket (us-west-2, eu-west-1, ap-south-1) — CloudFront edge location ke hisaab se nearest origin se fetch karta hai, latency 60% kam (500ms → 200ms origin fetches ke liye).
  • (7) Signed URLs: CloudFront signed URLs, expiry = 4 hours — hotlinking aur unauthorized access rokte hain; signature validate karta hai ki user ka active subscription hai.
  • (8) Compression: Manifest files (.m3u8, .mpd) par Gzip/Brotli — 70% bandwidth bachta hai; video segments par nahi (wo pehle se compressed hain).
  • (9) HTTP/2: Multiplexing — ek hi connection par parallel segment downloads, handshake overhead kam.
  • (10) Monitoring: CloudWatch — cache hit rate (target >95%), origin requests (target <5%), error rate (4xx, 5xx <0.1%), bandwidth usage.

Cost calculation: 20M DAU × 2 hours × 5 Mbps / 8 = 25M GB/day = 750M GB/month → 750M GB × $0.085/GB = $63M/month CDN bandwidth. Optimization: Cache hit rate 95% → sirf 5% origin tak jata hai → $63M × 0.05 = $3.15M origin bandwidth cost. Q5: Filters (genre, actor, language) ke saath video search kaise implement karoge?

Elasticsearch par search — mapping, indexing, query, scoring, faceted search, autocomplete, caching — 9 steps.

  • (2) Indexing: Video metadata PostgreSQL se → Kafka CDC → Elasticsearch indexer — har video document saare searchable fields ke saath index hota hai.
  • (3) Search query: GET /v1/videos/search?q=Inception&genre=Sci-Fi&actor=[Actor]&language=English&sort=popularity → Backend ES query banata hai — multi_match on title^3, description, actors, director + filters (term genre, match actors, term language) + sort popularity_score desc + from 0, size 20.
  • (4) Scoring: (a) Text relevance — 'title^3' title matches ko description se 3 guna boost deta hai, (b) Popularity — popularity_score = log(view_count) + 0.5 × avg_rating + recency_boost, roz offline batch job se calculate hota hai, (c) Personalization (advanced) — user ne pehle jo genres dekhe unhe boost karo, ML model (collaborative filtering) se results re-rank karo.
  • (5) Faceted search: Aggregations add karo — genres, languages, rating buckets — UI filters ke liye counts wapas aate hain (jaise {Sci-Fi: 150, Action: 200, …}).
  • (6) Autocomplete: Alag index, edge_ngram tokenizer, type-ahead suggestions — har keystroke par query, 300ms debouncing ke saath.
  • (7) Caching: Redis popular queries cache karta hai — Key = hash(query_text + filters + sort), Value = JSON result, TTL = 10 min, cache hit rate 60–70%.
  • (8) Performance: ES cluster — 10 data nodes (5 primary shards, 1 replica each), query latency p95 <100ms 10M videos par.
  • (9) Index updates: Kafka se near real-time — naya video metadata bante hi 1–2 second me searchable.

Q6: Subscription management aur payment processing kaise handle karoge?

Subscription lifecycle — plans, payment flow, webhook, access control, auto-renewal, cancellation, billing history — aur 4 edge cases.

  • (1) Subscription plans: Table subscription_plans — {plan_id: 'basic', name: 'Basic', price: 9.99, currency: 'USD', max_resolution: '720p', max_screens: 1, billing_period: 'monthly'}. Plans: Basic ($9/mo, 720p, 1 screen), Standard ($13/mo, 1080p, 2 screens), Premium ($17/mo, 4K, 4 screens).
  • (2) User subscribes: POST /v1/subscriptions — {user_id, plan_id: 'premium', payment_method_id: 'pm_abc123'} (Stripe se).
  • (3) Payment flow: (a) Subscription Service Stripe API call karta hai — stripe.subscriptions.create({ customer: user.stripe_customer_id, items: [{price: plan.stripe_price_id}], payment_behavior: 'default_incomplete', expand: ['latest_invoice.payment_intent'] }), (b) Frontend par payment confirm karne ke liye client_secret wapas milta hai, (c) User browser me payment confirm karta hai (3D Secure agar zaroori ho), (d) Stripe webhook bhejta hai — POST /webhooks/stripe — {type: 'invoice.paid', subscription_id, payment_intent}.
  • (4) Webhook handling: (a) Signature validate karo (security), (b) Idempotency check — SELECT * FROM subscriptions WHERE stripe_subscription_id={subscription_id}, pehle se hai to 200 wapas do (already processed), (c) BEGIN TRANSACTION; INSERT INTO subscriptions (… status='ACTIVE', start_date=now(), end_date=now()+30days, stripe_subscription_id, stripe_payment_intent_id); UPDATE users SET subscription_status='ACTIVE', subscription_id={subscription_id}; COMMIT;, (d) Redis cache invalidate karo — DEL user:{user_id}:subscription, (e) Kafka 'subscription.created' publish karo → Notification Service welcome email bhejta hai.
  • (5) Access control: Video playback request par: (a) GET /v1/videos/{video_id}/play → subscription validate karo — SELECT status, end_date, plan_id FROM subscriptions WHERE user_id={user_id} AND status='ACTIVE', (b) Plan quality check — 4K maang raha hai par plan.max_resolution='1080p' hai to 403 + upgrade prompt, (c) Concurrent streams check — SELECT COUNT(*) FROM active_sessions WHERE user_id={user_id} — count >= plan.max_screens ho to 403 'Too many devices', (d) Signed CDN URL generate karo, expiry ke saath.
  • (6) Auto-renewal: (a) Stripe renewal date par automatic charge karta hai (start se 30 din baad), (b) Payment success → webhook 'invoice.paid' → UPDATE subscriptions SET end_date=end_date+30days, (c) Payment fail → webhook 'invoice.payment_failed' → Notification Service email bhejta hai, 7 din grace period, 3 baar retry, (d) Grace period ke baad — UPDATE subscriptions SET status='EXPIRED' → user free tier par downgrade (agar hai) ya blocked.
  • (7) Cancellation: PUT /v1/subscriptions/{subscription_id}/cancel → stripe.subscriptions.update({subscription_id, cancel_at_period_end: true}) → User ko end_date tak access rehta hai, phir status='CANCELLED'.
  • (8) Billing history: GET /v1/users/{user_id}/billing → Stripe API se fetch karo — stripe.invoices.list({customer: stripe_customer_id}) → user dashboard me dikhao.

Q7: 200M users ki watch history kaise track aur store karoge?

Scale ka hisaab: 20M DAU × har 10 sec ek update = 2M writes/sec. Is load ko Redis (hot) + Cassandra (persistent) sambhalte hain.

  • (1) Real-time progress tracking: Client har 10 second me heartbeat bhejta hai — POST /v1/videos/{video_id}/progress — {user_id, current_time_seconds: 1245, timestamp}.
  • (2) Redis for hot data: (a) Redis me likho — HSET watch_progress:{user_id}:{video_id} 'current_time' {current_time} 'last_updated' {timestamp} 'device_id' {device_id}, (b) TTL — EXPIRE watch_progress:{user_id}:{video_id} 604800 (7 din), purane sessions auto-cleanup, (c) Resume par padho — GET /v1/videos/{video_id}/play → HGET watch_progress:{user_id}:{video_id} 'current_time' → {resume_from: 1245} wapas do, client us position se seek karta hai.
  • (3) Cassandra for persistence: (a) Background job (har 60s) Redis se Cassandra me batch write karta hai, (b) Table schema — CREATE TABLE watch_history (user_id uuid, video_id uuid, watched_at timestamp, current_time int, completion_percentage int, device_type text, PRIMARY KEY (user_id, watched_at)) WITH CLUSTERING ORDER BY (watched_at DESC) — user_id se partition, user-specific queries fast, (c) INSERT — INSERT INTO watch_history (user_id, video_id, watched_at, current_time, completion_percentage, device_type) VALUES ({user_id}, {video_id}, now(), {current_time}, {percentage}, {device_type}).
  • (4) Analytics pipeline: (a) Kafka event stream — har progress update par 'video.watched' event publish karo — {user_id, video_id, session_id, current_time, duration_watched, timestamp, geo_location, device_type}, (b) Stream processing — Apache Flink/Spark Streaming events consume karke aggregations nikalta hai — total_watch_time, unique_viewers, completion_rate, drop-off_points, (c) Results analytics DB (BigQuery/Redshift) me dashboards ke liye.
  • (5) Recommendations: (a) Collaborative filtering — jin users ne X dekha, unhone Y bhi dekha, (b) Content-based — similar genre, actors, (c) ML model (TensorFlow) — watch_history (implicit feedback: dekha matlab positive signal), explicit ratings agar hon, search queries — par train karo, (d) Inference — batch job roz raat ko chalta hai, har user ke top 20 recommendations banata hai, Redis me store karta hai — SET recommendations:{user_id} '[video_ids]' EX 86400, (e) Real-time updates — user dekhte jaaye, recommendations incrementally update karo.
  • (6) Scalability: (a) Cassandra — user_id se partitioned, 200M users × 100 entries avg × 500 bytes = 10 TB, 3x replication = 30 TB, (b) Redis — sirf active sessions (10M concurrent users × 1 KB = 10 GB), (c) Cassandra write throughput — 20M DAU × 1 update/10s = 2M writes/sec, Cassandra 1M writes/sec per node deta hai, 3 nodes replication ke saath kaafi hain.
  • (7) Data retention: Cassandra rows par TTL — WITH default_time_to_live = 31536000 (1 year), purana data auto-delete.

Example: User 20:45 par pause karta hai → Client progress bhejta hai → Redis update hota hai → Background job Cassandra me sync karta hai → User agle din app kholta hai → Resume API Redis se poochta hai → last_position=1245s wapas milta hai → Player 20:45 se seek karta hai → Seamless resume.

Q8: Scale par video delivery cost kaise optimize karoge? (CDN, storage, transcoding)

Kul kharcha ~$63.2M/month se ~$32.1M/month tak — 49% bachat. Har layer ka hisaab neeche hai.

  • (1) CDN caching: 95% cache hit rate → sirf 5% requests origin tak jati hain, origin bandwidth cost 95% bachta hai. Cost: 20M DAU × 2h × 5Mbps / 8 = 25M GB/day → 750M GB/month, CDN $0.085/GB → $63M/month, Origin (5%) $0.023/GB → $63M × 0.05 × 0.023/0.085 = $0.86M/month, Total CDN: $63.86M/month → Optimization: Volume discounts negotiate karo (petabyte scale par 50% off) → ~$32M/month.
  • (2) Storage tiering: (a) Hot data (recent releases, popular content) — S3 Standard ($0.023/GB) → 20% catalog = 80 TB × $0.023 = $1,840/month, (b) Warm data (1-year old) — S3 Infrequent Access ($0.0125/GB) → 30% = 120 TB × $0.0125 = $1,500/month, (c) Cold data (>2 years old, rarely watched) — S3 Glacier ($0.004/GB) → 50% = 200 TB × $0.004 = $800/month, Total storage: $4,140/month vs $9,200 all-standard (55% savings).
  • (3) Transcoding optimization: (a) Spot instances — 70% transcoding workers EC2 spot par → 70% discount vs on-demand ($2.50/hr → $0.75/hr), Risk: Interruption → batch job idempotent hai, checkpoint se restart hota hai, (b) Auto-scaling — queue depth ke hisaab se workers 10–100 scale karo, average 30 instances × 24h × 30 days × $0.75 = $16,200/month, (c) Smart resolution selection — har content ko 4K me transcode mat karo (sirf blockbusters ko), 30% transcoding cost bachta hai.
  • (4) Compression: (a) H.265/HEVC — H.264 se 50% better compression, storage aur bandwidth 40% kam — 10k videos × 40GB → HEVC se 10k × 24GB = 240 TB vs 400 TB, savings: 160 TB × $0.023 = $3,680/month storage + proportional CDN savings, (b) AV1 (future) — HEVC se 30% better, par encoding 2x slow, abhi widely supported nahi.
  • (5) Lazy transcoding: Saare resolutions turant transcode mat karo — on-demand transcode karo jab maanga jaye (jaise sirf 1% log 4K dekhte hain), 40% transcoding cost bachta hai.
  • (6) Content pruning: 5 saal baad unpopular content delete karo (100 se kam baar dekha gaya), storage free hoti hai, $500/month bachta hai.
  • (7) Regional optimization: Content us S3 bucket me rakho jo main audience region ke sabse paas ho (US content us-east-1 me) — cross-region transfer cost kam.
  • (8) Manifest file compression: .m3u8 files par Gzip — 70% bachat → 10k videos × 10 KB × 0.7 — chhota par good practice.
  • (9) Reserved capacity: 50% baseline CDN bandwidth 1-year term ke liye reserve karo → on-demand se 30% discount.
  • (10) Monitoring and alerting: Cost per video, cost per user track karo, zombie resources band karo (unused transcoding workers, orphaned S3 objects).

Total monthly cost: Optimizations se pehle — CDN $63M + Storage $9K + Transcoding $50K + Misc $100K ≈ $63.2M → Optimizations ke baad — CDN $32M + Storage $4K + Transcoding $16K + Misc $50K ≈ $32.1M (49% savings).

Q9: Piracy rokne ke liye DRM (Digital Rights Management) kaise implement karoge?

DRM ka matlab — video encrypt karke bhejo, decrypt karne ki key sirf usi device ko do jiska subscription valid ho.

  • (1) DRM standards: (a) Widevine — Google standard, Chrome aur Android par, (b) FairPlay — Apple standard, Safari aur iOS par, (c) PlayReady — Microsoft standard, Edge aur Xbox par.
  • (2) Encryption: (a) Video segments transcoding ke time AES-128 ya AES-256 se encrypt hote hain, (b) Har segment alag encryption key se encrypt hota hai, (c) Encryption keys License Server par store hoti hain (AWS Elemental MediaPackage, BuyDRM, etc.).
  • (3) Key delivery: (a) Player manifest maangta hai → encrypted segment URLs + license_url milta hai, (b) Player decryption key maangta hai — GET {license_url} user_token aur device_id ke saath, (c) License Server validate karta hai — user ka active subscription hai, device registered hai (max 5 devices per user), DRM client installed hai (emulator/rooted device nahi), (d) Valid ho to decryption key device ki public key se encrypt karke wapas bhejta hai (sirf wahi device decrypt kar sakta hai), (e) Player segments memory me decrypt karke screen par render karta hai (encrypted buffer → decryption → display pipeline).
  • (4) Content protection: (a) HDCP (High-bandwidth Digital Content Protection) — HDMI se screen recording rokta hai, hardware se enforce hota hai, (b) Watermarking — invisible forensic watermark me user_id embed hota hai, leak ho to source trace ho sakta hai, (c) Screen capture blocking — DRM API screen recording apps ko block karta hai, screenshots me black screen dikhta hai.
  • (5) Offline downloads: (a) Encrypted segments local storage me download karo (mobile app), (b) License bhi download hoti hai, expiry ke saath (jaise 30 din), (c) Playback par license expiry validate karo, decrypt karke play karo, (d) Subscription khatam hote hi license invalid — downloaded content unplayable.
  • (6) Implementation: (a) Transcoding — FFmpeg with DRM packaging: ffmpeg -i input.mp4 -c:v libx264 -encryption_scheme cenc -encryption_key {key} -encryption_kid {key_id} output.mp4, (b) Manifest — HLS me #EXT-X-KEY:METHOD=SAMPLE-AES,URI={license_server_url},KEYFORMAT='com.apple.streamingkeydelivery', (c) Player — ExoPlayer (Android), AVPlayer (iOS), Shaka Player (web) DRM plugin ke saath.
  • (7) Multi-DRM: Teeno standards support karo cross-platform ke liye — Safari ho to FairPlay, Chrome ho to Widevine, Edge ho to PlayReady — unified license server (BuyDRM, Irdeto) jo teeno handle kare.
  • (8) Challenges: (a) Performance — decryption overhead ~5–10% CPU, hardware-accelerated decryption (GPU) use karo, (b) Compatibility — purane devices support nahi karte, lower DRM level ya no-DRM fallback, (c) Cost — license server $0.01–0.05 per view, 20M daily views = $200K–$1M/month.
  • (9) Anti-piracy: (a) Geofencing — VPNs block karo, content region ke hisaab se restrict karo, (b) Concurrent stream limits — ek saath max 2–4 devices, (c) Token expiry — signed URLs 4 hours ke liye valid, dobara authentication force hota hai.

Example: User play dabata hai → Player manifest maangta hai → Manifest me encrypted segment URLs + license_url → Player user_token ke saath license maangta hai → Server subscription + device validate karta hai → Decryption key (encrypted) wapas bhejta hai → Player device key se decrypt karta hai → Segments memory me decrypt hokar render hote hain → User video file save ya share nahi kar sakta.

💡 Tip: DRM for piracy prevention: Widevine (Chrome/Android), FairPlay (Apple), PlayReady (Microsoft). Segments encrypted, license server subscription + device validate karta hai. Cost $0.01–0.05 per view — par premium content ke liye essential hai.

Q10: Disaster recovery aur fault tolerance strategy kya hogi?

Multi-region DR with automated failover — RPO <5 seconds, RTO <10 minutes. Ye numbers interview me bolne layak hain.

  • (1) Architecture: Primary region us-east-1, Secondary us-west-2, Tertiary eu-west-1.
  • (2) Data replication: (a) PostgreSQL — Primary us-east-1 me, streaming replication us-west-2 (warm standby, lag <5s) aur eu-west-1 (read replica, lag <10s), (b) S3 — Cross-region replication (CRR) enabled, video segments teeno regions me minutes me replicate hote hain, (c) Redis — Redis Sentinel automatic failover ke liye, master-slave replication (lag <1s), AOF persistence durability ke liye, (d) Cassandra — Multi-DC deployment, replication_factor=3 saare regions me, LOCAL_QUORUM reads/writes ke liye.
  • (3) CDN resilience: CloudFront healthy origins par automatic route karta hai — us-east-1 S3 fail ho to CloudFront us-west-2 bucket se transparently fetch karta hai, user ko koi farq nahi padta.
  • (4) Failover procedure: (a) Health checks — Route53 har 30s me primary region check karta hai (TCP, HTTP, latency), (b) Trigger — 3 consecutive checks fail hon (90s) → Route53 DNS us-west-2 par point karta hai, (c) Database promotion — us-west-2 PostgreSQL primary ban jata hai (pg_ctl promote), ~2–3 min lagte hain, (d) Application servers — us-west-2 me auto-scaling groups pre-warmed (hamesha min 10% capacity running), 5 min me 100% tak scale ho jate hain, (e) DNS propagation — DNS TTL ke hisaab se 5–10 min, clients refresh karte jaate hain, progressive migration.
  • (5) RPO/RTO targets: (a) RPO (Recovery Point Objective) — <5 seconds data loss (streaming replication lag), (b) RTO (Recovery Time Objective) — <10 minutes service restoration.
  • (6) Service degradation: (a) Read-only mode — primary DB fail ho par replicas healthy hon to read-only serve karo — users dekh sakte hain, subscribe/update nahi, (b) CDN-only mode — saare origins down hon to sirf cached content serve karo (95% requests), naye uploads fail honge, (c) Graceful degradation — non-critical features (recommendations, continue watching) band karke load kam karo.
  • (7) Testing: (a) Monthly DR drills — primary region failure simulate karo, failover execute karo, RTO verify karo, (b) Chaos engineering — production me randomly instances terminate karo (low-traffic hours me), auto-recovery verify karo, (c) Game days — alag-alag failure scenarios simulate karo (DB corruption, CDN outage, DDoS attack).
  • (8) Monitoring: (a) Datadog/New Relic — real-time metrics (latency, error rate, throughput), (b) Alerts — PagerDuty critical issues par (DB lag >10s, API error rate >1%, CDN cache hit rate <90%), (c) Dashboards — Grafana: concurrent viewers, video playback errors, buffering ratio, DB replication lag.
  • (9) Backup and restore: (a) S3 — Versioning enabled, accidental deletes recoverable, (b) Database — roz full backup + hourly incremental S3 Glacier me, retention 30 din, (c) Point-in-time recovery — pichhle 7 din ke kisi bhi point par DB restore kar sakte ho, (d) Backup restore testing — har quarter backup se staging environment me restore karke data integrity verify karo.
  • (10) DDoS protection: (a) AWS Shield Advanced — L3/L4 DDoS se bachata hai, (b) CloudFront rate limiting — suspicious traffic geo-block karo, WAF rules malicious patterns block karte hain, (c) Auto-scaling — normal load se 10x tak ke traffic spikes absorb karo.

Example failure: Primary region (us-east-1) me 2:00 PM power outage → Route53 health checks 2:01:30 par fail → DNS 2:02 par us-west-2 par update → PostgreSQL 2:04 par promote → Users ko halki buffering (current segment cache se complete, agla segment us-west-2 se) → Service 2:10 PM par poori tarah restore → Data loss: in-flight requests ka <5s watch progress. Kul cost: Multi-region setup infrastructure cost 30–40% badhata hai — outage ke dauraan revenue loss se bachav hai (1 hour outage = $500K lost revenue + reputation damage).

Interview FAQs

36 interview FAQs — lesson ke apne Q&A se aur usse judde current-era sawaal. Har ek par click karo, poora jawab khulega.

Q01 Adaptive bitrate streaming (ABR) kya hai?
ABR me ek hi video kai resolutions (4K, 1080p, 720p, 480p, 360p) me transcode karke 10-second segments me toda jata hai. Player har segment ke baad network bandwidth naapkar agla segment usi hisaab se maangta hai — bandwidth zyada ho to 1080p, kam ho to 480p. Isse network hilne par bhi video rukta nahi, bas quality badal jati hai.
Q02 HLS aur DASH me kya farq hai?
HLS Apple ka standard hai — .m3u8 manifest + .ts segments, Safari/iOS par native support. DASH MPEG ka open standard hai — .mpd manifest (XML) + .m4s segments, codec agnostic (H.264, H.265, VP9). Production platforms dono serve karte hain — Apple devices ko HLS, baaki ko DASH.
Q03 Adaptive streaming me keyframe kyun zaroori hai?
Quality switch sirf keyframe (I-frame) par ho sakta hai, kyunki keyframe ke baad ke frames usi par dependent hote hain. Har 10-second segment keyframe se shuru hota hai (0th second par), isiliye player beech me resolution badal sakta hai bina video tode. Keyframe na ho to switching par stuttering hota hai — FFmpeg me -g 300 -keyint_min 300 use karte hain.
Q04 Transcoding pipeline ke steps kya hain?
Upload → S3 (multipart, s3://videos-raw/{video_id}/original.mp4) → Kafka event 'video.uploaded' → Lambda/Worker consume kare → FFmpeg/MediaConvert se 5 resolutions me transcode → har resolution ko 10-sec segments me todo → S3 me upload (s3://videos-processed/{video_id}/{resolution}/) → manifest file (master.m3u8/.mpd) banao → metadata update (processing_status='COMPLETED') → Elasticsearch index → CDN distribute.
Q05 Manifest file (master.m3u8 / master.mpd) kya hoti hai?
Manifest file video ki 'table of contents' hai — isme saare available resolutions aur unke bitrates likhe hote hain. HLS me master.m3u8 me #EXT-X-STREAM-INF lines hoti hain (BANDWIDTH + RESOLUTION ke saath), jo har resolution ki alag playlist ki taraf ishara karti hain. Player pehle manifest padhta hai, phir bandwidth ke hisaab se sahi playlist chunta hai.
Q06 CDN video delivery me kaise kaam karta hai?
Origin S3 bucket hai, edge locations 200+ CloudFront PoPs hain. User ka request DNS se nearest edge (jaise Mumbai PoP) par jata hai. Edge cache check karta hai — hit ho to 10ms me segment milta hai, miss ho to origin S3 se 200ms me fetch karke 24 ghante ke liye cache kar leta hai. Popular content par 95%+ cache hit rate milta hai.
Q07 Cache hit rate 95% ka matlab kya hai?
Matlab 100 me se 95 requests edge cache se serve hoti hain, sirf 5 origin (S3) tak jati hain. Isse origin load 95% kam hota hai aur latency 200ms se 10–50ms ho jati hai. Trending movies ko release se pehle edges par pre-warm karke hit rate aur bhi upar rakha jata hai.
Q08 Origin Shield kya hai?
Origin Shield CloudFront ki ek centralized caching layer hai jo edge aur origin ke beech baithti hai. 100 edge locations ek hi segment maangein to shield sirf 1 request origin ko bhejta hai — isse origin load 90% kam ho jata hai aur cache hit rate aur behtar hota hai.
Q09 Signed URL kyun use karte hain?
Signed URL par expiry (4 hours) aur signature hota hai — isse koi bhi manifest ya segment ka link copy karke free me video nahi dekh sakta. Signature validate karta hai ki user ka active subscription hai. 4 ghante baad link bekaar ho jata hai, dobara authentication chahiye. Yehi hotlinking se bachav hai.
Q10 Buffering kam karne ke 5 tareeke batao.
(1) Adaptive bitrate — bandwidth girte hi quality auto-kam karo. (2) CDN edge caching — 95% hit rate, <50ms latency. (3) 20–40 second ka buffer rakho — 3–5 segments aage download karo. (4) 10-sec segments — fast quality switching aur seeking. (5) Preloading — pehle 2–3 segments lower quality par turant download karo, phir optimal quality par switch karo.
Q11 Video segments 10 second ke kyun hote hain?
10 second ek sweet spot hai — chhote segments (2 sec) se quality switching aur seeking fast hoti hai par requests zyada banti hain; bade segments (30 sec) se requests kam par switching slow aur seeking me der hoti hai. 10 sec par har segment ~2–3 MB ka hota hai, switching fast rehti hai aur network interruption ka asar kam padta hai.
Q12 Elasticsearch query me 'title^3' ka matlab kya hai?
Ye boosting hai — title me match hone par score 3 guna milta hai, description ya actors me match se zyada. Kyunki user jab film ka naam type karta hai to title match sabse relevant hota hai. Isi tarah popularity_score se sort karke trending content upar dikhaya jata hai.
Q13 Popularity score kaise calculate hota hai?
Popularity score view_count, rating aur recency ka combination hai — jaise log(view_count) + 0.5 × avg_rating + recency_boost. Ye offline batch job se roz calculate hota hai aur Elasticsearch index me update hota hai, taaki search results relevance + popularity dono ke hisaab se rank hon.
Q14 Watch progress Redis me kyun store karte hain, PostgreSQL me kyun nahi?
20M users har 10 second me ek heartbeat bhejte hain — matlab 2M writes/sec. PostgreSQL itne writes nahi sambhal sakta. Redis 1ms latency par HSET karta hai (watch_progress:{user_id}:{video_id}, TTL 7 din), aur har 60 second me ek background job batch write karke Cassandra me persist karta hai. Hot data Redis me, durable data Cassandra me.
Q15 Resume playback kaise kaam karta hai?
Client har 10 second me heartbeat bhejta hai — current_time_seconds Redis me HSET hota hai. User dobara play dabaye to Play Service Redis se last current_time nikalta hai aur {resume_from: current_time} wapas bhejta hai — player usi position se seek kar deta hai. Redis me na mile to Cassandra se pichhla record padha jata hai.
Q16 Recommendation engine kaise kaam karta hai?
4 tareeke milkar chalte hain — (1) Collaborative filtering: jin users ne X dekha unhone Y bhi dekha. (2) Content-based: similar genre/actors. (3) ML model (TensorFlow): watch history, ratings aur search queries par train karke preferences predict karta hai. (4) Results Redis me per-user cache hote hain aur roz refresh hote hain.
Q17 Subscription plans kaise design karte hain?
Plans resolution aur screens se alag hote hain — Basic $9/mo (720p, 1 screen), Standard $13/mo (1080p, 2 screens), Premium $17/mo (4K, 4 screens). Plan table me plan_id, price, currency, max_resolution, max_screens aur billing_period hota hai. Playback par plan check hota hai — 4K maango aur plan Basic ho to 403 + upgrade prompt.
Q18 Payment webhook me idempotency check kyun zaroori hai?
Payment gateway webhook dobara bhej sakta hai (retry) — bina idempotency check ke ek hi payment par do subscriptions ban jayenge aur user do baar charge hoga. Isliye webhook aate hi pehle SELECT karte hain — stripe_subscription_id pehle se hai to turant 200 wapas do, dobara process mat karo. Signature validation bhi zaroori hai taaki fake webhook na chale.
Q19 Auto-renewal aur grace period kya hai?
Stripe renewal date par automatic charge karta hai. Payment success ho to end_date 30 din badh jata hai. Payment fail ho to 'invoice.payment_failed' webhook aata hai — notification bhejte hain, 3 baar retry karte hain, aur 7 din ka grace period dete hain. Grace period ke baad subscription EXPIRED ho jata hai aur user downgrade ho jata hai.
Q20 Video play par 403 Forbidden kab milta hai?
3 wajah se — (1) Subscription ACTIVE nahi hai ya end_date beet gaya. (2) Plan quality kam hai — 4K maanga par plan max 1080p hai. (3) Concurrent streams zyada hain — active_sessions count plan ke max_screens se zyada hai. Har case me 403 ke saath upgrade prompt dikhaya jata hai.
Q21 DRM kaise kaam karta hai? Widevine, FairPlay aur PlayReady me kya farq hai?
Video segments transcoding ke time AES-128/256 se encrypt hote hain, har segment ki alag key License Server par hoti hai. Player manifest se license_url lekar key maangta hai — server subscription aur device validate karke key device ki public key se encrypt karke deta hai. Widevine Google ka hai (Chrome/Android), FairPlay Apple ka (Safari/iOS), PlayReady Microsoft ka (Edge/Xbox) — production me teeno support karte hain (multi-DRM).
Q22 Offline downloads me DRM kaise kaam karta hai?
Mobile app encrypted segments local storage me download karti hai, saath me license bhi download hoti hai jiski expiry hoti hai (jaise 30 din). Playback par license expiry validate hoti hai — valid ho to decrypt karke play hota hai. Subscription khatam hote hi license invalid ho jati hai aur downloaded content unplayable ho jata hai. HDCP aur forensic watermark se screen recording bhi roki jati hai.
Q23 200M users, 20M DAU, 400TB storage — estimation kaise karte hain?
Pehle assumptions likho — 10k videos, har ek ~1 hour. Phir per-video hisaab — original 4K 24GB + transcoded (5 resolutions) ~16GB = 40GB per video. Kul storage = 10k × 40GB = 400TB. Daily traffic = 20M users × 2 hours × 5 Mbps = 9GB per user = 180 PB/day. Peak = DAU ka 10% concurrent (2M) × 5 Mbps = 10 Tbps. Interview me assumptions pehle bolo, phir hisaab.
Q24 Peak bandwidth 10 Tbps kaise nikla?
Prime time (8–11 PM) me DAU ka ~10% ek saath dekh raha hota hai — 20M ka 10% = 2M concurrent users. Average bitrate 5 Mbps hai (resolutions ka weighted average). 2M × 5 Mbps = 10,000,000 Mbps = 10 Tbps. Isi number se CDN aur origin capacity plan hoti hai.
Q25 Transcoding capacity 2400 videos/day kaise nikli?
50 GPU workers hain, 24 ghante chalte hain, aur 1-hour video transcode karne me ~30 min (0.5 hour) lagte hain. Capacity = 50 × 24 / 0.5 = 2400 videos/day. Roz sirf 100 naye videos upload hote hain — matlab 24 guna buffer hai, isliye backlog kabhi nahi banta. Queue depth badhe to workers 10 se 100 tak auto-scale hote hain.
Q26 Storage tiering se kitni bachat hoti hai?
20% hot data S3 Standard ($0.023/GB), 30% warm S3 Infrequent Access ($0.0125/GB), 50% cold S3 Glacier ($0.004/GB) me rakho to kul kharcha ~$4,140/month banta hai, jabki sab kuch Standard me rakhne par $9,200/month lagta — 55% bachat. S3 Lifecycle policies se view frequency ke hisaab se tiering automate kar do.
Q27 H.265/HEVC, H.264 aur AV1 me kya farq hai?
H.264 standard hai — har device par chalta hai, baseline compression. H.265/HEVC usse 50% better compression deta hai (chhoti file, same quality) — 4K/HDR ke liye best, par decoder support chahiye. AV1 HEVC se 30% aur better hai, par encoding 2 guna slow hai aur abhi har device par supported nahi — future standard hai.
Q28 CDN pre-warming kya hai?
Naye release (jaise naya season) se pehle uske segments ko edge locations par pehle se push kar dena — taaki launch ke pehle minute se hi users ko cache hit mile aur playback instant ho. Bina pre-warming ke pehle viewers ko origin se 200ms latency milegi aur origin par achanak load aayega.
Q29 Geo-sharding S3 buckets ka fayda kya hai?
Video files ko regional S3 buckets me rakho (us-east-1, eu-west-1, ap-south-1) — CDN har edge ke nearest origin se fetch karta hai. Isse origin fetch latency 60% kam hoti hai (500ms se 200ms) aur cross-region transfer cost bhi bachta hai.
Q30 OTT system me Kafka ke kaun-kaun se topics hote hain?
5 main topics — video.uploaded (transcoding trigger), video.transcoded (search index update), video.watched (analytics aur recommendations), subscription.created (notifications), subscription.renewed (user access update). Kafka se services decoupled rehti hain — har service apni speed par consume karti hai.
Q31 Cassandra watch history ka partition key user_id kyun hai?
Watch history hamesha ek user ke hisaab se padhi jati hai — 'is user ne kya-kya dekha'. user_id partition key hone se ek user ka saara data ek hi partition me rehta hai, query fast hoti hai. Clustering key watched_at DESC hai taaki latest pehle mile. 200M users × 100 entries × 500 bytes = 10 TB, 3x replication ke saath 30 TB.
Q32 Redis me kaun-kaun si keys hoti hain OTT system me?
4 main keys — watch_progress:{userId}:{videoId} (HASH, TTL 7 din), search:{hash(query+filters)} (JSON results, TTL 10 min), user:{userId}:subscription (JSON, TTL 1 hour), recommendations:{userId} (LIST of video_ids, TTL 24 hours). TTL isliye taaki purana data apne aap saaf ho jaye.
Q33 RPO aur RTO kya hain? OTT ke targets kya hain?
RPO (Recovery Point Objective) matlab kitna data loss acceptable hai — OTT me <5 seconds (streaming replication lag). RTO (Recovery Time Objective) matlab service kitni der me wapas aani chahiye — OTT me <10 minutes. Ye targets multi-region setup se milte hain — PostgreSQL streaming replication, S3 cross-region replication, Redis Sentinel failover.
Q34 Ek region down ho jaye to failover kaise hota hai?
Route53 har 30 second me primary region ke health checks karta hai. 3 consecutive checks fail hon (90 second) to DNS secondary region (us-west-2) par point kar deta hai. Wahan PostgreSQL promote hota hai (~2–3 min), auto-scaling groups pre-warmed 10% capacity se 5 min me 100% tak scale hote hain. DNS TTL ke hisaab se 5–10 min me saare users naye region par aa jate hain. Data loss <5 second ka hota hai.
Q35 CDN cost $32M/month tak kaise kam karte hain?
Bina optimization ke CDN $63M/month hota hai (750M GB × $0.085/GB). 95% cache hit rate se origin cost bachta hai, aur petabyte scale par volume discount negotiate karke 50% off milta hai — kul ~$32M/month. Saath me storage tiering ($4K), spot instances for transcoding ($16K) aur lazy transcoding se kul monthly kharcha ~$63.2M se ~$32.1M ho jata hai — 49% bachat.
Q36 Lazy transcoding kya hai?
Har video ke saare resolutions turant transcode karne ki jagah, sirf tab transcode karo jab koi us resolution ko maange. Sirf ~1% viewers 4K dekhte hain — baaki ke liye 4K transcode karna paise ki barbadi hai. Lazy transcoding se transcoding cost 40% tak kam hoti hai. Trade-off: pehle 4K viewer ko thoda wait karna pad sakta hai.
