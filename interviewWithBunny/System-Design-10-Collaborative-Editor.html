WebSocket session → Operations (insert/delete) → OT ya CRDT → Op-log persistence → Periodic snapshots → Eventual convergence

01Requirements

1. Functional Requirements

Pehle ye decide karo — system ko karna kya hai? Functional requirements matlab system ke features: user kya-kya kar payega. Interview me hamesha yahin se shuru karo.

  • Feature 1 — Documents banao, badlo, delete karo: User documents create, update aur delete kar sake, rich text formatting ke saath (bold, italic, headings, lists — sirf plain text nahi).
  • Feature 2 — Ek saath editing (concurrent editing): Multiple users ek hi document ko ek hi waqt par real-time me edit kar sakein — yahi is system ki jaan hai.
  • Feature 3 — Dusron ke changes real-time me dikhein: Har user ko dusre users ke changes turant dikhein, unke cursor positions aur presence (kaun online hai, kahan type kar raha hai) ke saath.
  • Feature 4 — Sharing aur permissions: Documents share kiye ja sakein — view only, edit, ya comment — alag-alag permission levels ke saath.
  • Feature 5 — Version history aur rollback: Document ke purane versions dekhe ja sakein aur kisi bhi purane version par wapas (rollback) jaya ja sake.
  • Feature 6 — Offline editing: Internet na ho to bhi user edit kar sake, aur connection wapas aate hi changes automatic sync ho jayein.
  • Feature 7 — Auto-save: Data loss na ho, isliye periodic snapshots — user ko baar-baar save dabane ki zaroorat na pade.

Interview me kaise bolo: "Sir, pehle functional requirements — create/update/delete docs with rich text, real-time concurrent editing, cursor + presence, sharing with view/edit/comment permissions, version history with rollback, offline editing with auto-sync, aur auto-save." Bas — 7 points, ek saans me.

2. Non-Functional Requirements

Features ke baad scale aur performance — system kitna bada hoga, kitna fast hona chahiye, aur consistency ka kya scene hai. Ye numbers interview me sabse zyada puche jaate hain.

Scale

MetricNumberMatlab
UsersMillionsLakhs-crore users, aur unke millions of documents
Concurrent editors (hot docs)50–100 usersEk hi document ko ek saath 50–100 log edit kar sakte hain
Document size1.02M charactersGoogle Docs ki limit — isse bada document support karna hai

Performance & Consistency

  • CAP Theorem: Availability & Consistency (formal document) — eventual consistency acceptable hai, bas guaranteed convergence chahiye. Matlab thodi der ke liye do users ko alag state dikh sakti hai, lekin end me sabka document ek hi hoga.
  • Latency: Updates live hone chahiye — <300ms me har client tak pahunch jayein, tabhi real-time collaboration ka feel aayega.
  • Convergence: Goal hai — strong eventual consistency. Matlab saare clients jinhone same set of operations dekhe hain, unka final document state bilkul identical hona chahiye.
Interview favourite: Interviewer hamesha poochta hai — 'CAP me kya choose karoge?' Jawab: Availability + Eventual Consistency. Kyunki document edit karte waqt user ko block nahi kar sakte; thodi der ka divergence acceptable hai, lekin convergence guaranteed honi chahiye.

Yaad rakhne wale numbers: 50–100 concurrent editors, 1.02M characters, <300ms latency. Ye teen numbers har jagah kaam aayenge — scaling section me bhi.

System ke 4 core entities hain. Ye section diagram se aaya hai — image me entities ke naam aur fields dikhaye gaye hain, detail yahan prose me di gayi hai.

2. Operation / Editop_id, doc_id, user_id, type (insert/delete), position, content, timestamp, client_versionHar ek edit ek operation hai — kaun, kahan, kya, kab
3. Snapshot / Versionversion_id, doc_id, snapshot_blob_path (S3), operations_count, timestampDocument ki ek point-in-time copy — S3 me stored, fast recovery ke liye

  • Document: Har document ka ek unique doc_id hota hai, ek owner_id, title, aur metadata (created_at, updated_at, permissions). Permissions batate hain kaun view kar sakta hai, kaun edit, kaun comment.
  • Operation: Ye system ki sabse important entity hai. Har keystroke (ya batch) ek operation hai — type insert ya delete, kis position par, kya content, kis user ne, kis time par, aur client ka version kya tha. Saare operations op-log me append-only store hote hain.
  • Snapshot: Har 50 operations ya 5 minute baad document ki poori copy S3 me save hoti hai — docs/{doc_id}/v{version}.txt. Isse document jaldi load hota hai: snapshot lo + uske baad ke chand operations replay karo, bas.
  • Cursor/Presence: Ye ephemeral data hai — matlab temporary. Cursor position har 100ms me badalti hai, isse DB me likhna bewakoofi hai. Ye Redis me 5 minute TTL ke saath rehta hai, aur disconnect hote hi delete ho jata hai.
Dhyaan do: Cursor positions ko KABHI database me persist mat karo. Cursor updates ephemeral hain (100 updates/sec/user tak) — Redis me 5 min TTL ke saath rakho, WebSocket se broadcast karo, disconnect par hata do.

4. API Designing

API design do hisso me bat-ta hai — normal document management (HTTP REST) aur real-time editing (WebSocket). Interview me dono ko alag-alag bolo, warna confuse ho jayega.

Document Management (REST APIs)

Real-Time Editing (WebSocket)

  • REST kyun, WebSocket kyun? Document banana, kholna, version dekhna — ye one-time kaam hain, REST se theek hain. Lekin editing continuous hai — har keystroke par HTTP request bhejna (polling) barbaadi hai. Isliye editing ke liye ek persistent WebSocket connection.

  • Broadcast: Server operation ko transform karke baaki saare connected clients ko bhejta hai — bhejne wale ko wapas nahi bhejta (uske paas already hai).

06.1Deep Dive (LLD)

Step 1: Document Creation & Loading

Document banana aur kholna — pehle REST, phir snapshot + op-log replay se current state banana.

Document create karo

  1. User create karta hai: POST /v1/api/docs/create with {title: 'Meeting Notes', owner_id: user_A}
  2. Document Metadata Service DB me likhta hai: INSERT INTO documents (doc_id, owner_id, title, created_at, updated_at, permissions) VALUES ({uuid}, {user_A}, 'Meeting Notes', now(), now(), '{}')
  3. Initial snapshot banta hai: S3 me docs/{doc_id}/v0.txt upload hota hai (empty content), aur reference store hota hai: INSERT INTO snapshots (snapshot_id, doc_id, version, blob_path, operations_since_last: 0, created_at)
  4. Response milta hai: {doc_id, edit_url: '/docs/{doc_id}/edit'}

Document kholo (load karo)

  1. User kholta hai: GET /v1/api/docs/{docId}
  2. Permissions check: SELECT permissions FROM documents WHERE doc_id={doc_id} — agar user owner nahi hai aur shared list me bhi nahi, to 403 Forbidden.
  3. Latest snapshot fetch karo: SELECT blob_path, version FROM snapshots WHERE doc_id={doc_id} ORDER BY version DESC LIMIT 1
  4. S3 se download karo: GET docs/{doc_id}/v0.txt → current content.
  5. Snapshot ke baad ke operations fetch karo: SELECT * FROM operations WHERE doc_id={doc_id} AND timestamp > {snapshot_timestamp} ORDER BY timestamp ASC
  6. Operations replay karo: Snapshot par operations apply karke current state banao (agar snapshot ke baad koi ops hain to).
  7. Return karo: {doc_id, content, current_version, permissions}

Key idea: Document load karne ka formula hai — latest snapshot + uske baad ke operations ka replay = current state. Snapshot na hota to hazaaron operations shuru se replay karne padte — slow. Snapshot se sirf chand operations replay karne padte hain — fast.

06.2Deep Dive (LLD)

Step 2: WebSocket Connection & Presence

Edit button dabate hi WebSocket khulta hai — yahi real-time collaboration ki neev hai.

  1. User 'Edit' click karta hai: Client WebSocket establish karta hai — WS /v1/api/docs/{doc_id}/edit with Authorization: Bearer {JWT}
  2. WebSocket Gateway: (1) Token authenticate karta hai, (2) Check karta hai user ke paas 'edit' permission hai ya nahi, (3) Session banata hai {session_id, user_id, doc_id, connected_at}
  3. Current state load karo: (a) Pehle Redis check karo — GET doc:{doc_id}:state, hit hua to cached state milti hai (1ms), (b) Miss hua to S3 se snapshot lao + op-log se recent operations replay karo, aur Redis me cache karo TTL=30 min ke saath.
  4. Initial state bhejo: Server → Client, WebSocket se: {type: 'init', content: {current_document_text}, current_version: 42, active_users: [{user_id, name, cursor_pos, color}]}
  5. Presence broadcast karo: Server → saare connected clients: {type: 'user_joined', user: {user_id: A, name: 'User A', color: '#FF5733'}}
  6. Client dikhata hai: Top bar me active users ki list, aur har user ke liye colored cursor indicators.

Redis hit vs miss ka farq: Hit = 1ms me state mil gayi. Miss = S3 snapshot + replay — phir bhi tens of milliseconds. Isiliye Redis ko canonical copy kehte hain — 90% reads wahin se serve hote hain.

06.3Deep Dive (LLD)

Step 3: Real-Time Editing — Operation Flow

User type karta hai — uske baad operation ka poora safar, client se server se baaki clients tak.

  1. User A type karta hai: insert(R, 29) — character 'R' position 29 par insert hota hai.
  2. Client optimistic update: 'R' turant local editor me dikh jata hai (server ka wait nahi), operation send karne ke liye queue hoti hai.
  3. Client operation bhejta hai, WebSocket se: {type: 'operation', op: {op_id: uuid(), type: 'insert', position: 29, content: 'R', client_version: 42, user_id: A, timestamp: now()}}
  4. WebSocket Gateway receive karta hai: Session active hai ya nahi validate karta hai, phir Document Editor Service ko forward karta hai.
  5. Document Editor Service: (1) Server timestamp aur sequence number assign karta hai, (2) Op-log me append karta hai: INSERT INTO operations (op_id, doc_id, user_id, type, position, content, client_version, server_version, timestamp), (3) Kafka 'doc.operations' topic me publish karta hai: {doc_id, op_id, type, position, content, user_id, server_version: 43}
  6. OT/CRDT Transformation — agar concurrent operations hain to (agle step me detail).
  7. Gateway broadcast karta hai: Transformed operation baaki saare connected clients (User B, C, D) ko, WebSocket se: {type: 'operation', op: {type: 'insert', position: 29, content: 'R', user_id: A}}
  8. Clients B, C, D apply karte hain: Operation receive karke apne local state me position 29 par apply karte hain — 'R' real-time me dikhne lagta hai.
Tip: Interview me is flow ko sequence me bolo — optimistic update → WebSocket send → server sequencing → op-log append → Kafka publish → broadcast → apply. Har step ka reason batao, sirf naam nahi.

06.4Deep Dive (LLD)

Step 4: Conflict Resolution — Operational Transformation (OT)

Do log ek saath edit karein to conflict hota hai — OT use transform karke solve karta hai. Ye poore lesson ka sabse important concept hai.

Scenario — 'abc' document, version 10

  • User A position 0 par type karta hai: insert('A', 0) → 'Aabc', server ko bhejta hai.
  • User B position 3 par type karta hai: insert('D', 3) → 'abcD', server ko bhejta hai.
  • Server dono receive karta hai: (1) A ki operation pehle aati hai (network timing), server_version: 11 assign hota hai, (2) B ki operation baad me aati hai, server_version: 12.

OT Service B ki operation ko transform karta hai

  1. Check: B ka client_version=10 hai, lekin server ab version 11 par hai (A ki op apply ho chuki).
  2. Transformation zaroori hai: B ne position 3 par insert karna chaha tha 'abc' me, lekin A ne position 0 par insert kar diya — document ab 'Aabc' hai (4 characters).
  3. B ki position transform karo: original position 3 + 1 (A ne pehle insert kiya) = nayi position 4.
  4. Transformed operation: insert('D', 4) ko 'Aabc' par apply karo → 'AabcD'.

Broadcast aur convergence

  • Broadcast: (1) A ki op B ko bhejo: insert('A', 0), (2) Transformed B ki op A ko bhejo: insert('D', 4), (3) Dono clients operations apply karte hain.
  • Final state: Dono clients 'AabcD' par converge karte hain — order server sequencing se guarantee hota hai.
Dhyaan do: CRITICAL: OT approach me operations ko central server se sequence karna HI padega. Server-assigned order ke bina clients operations ko alag-alag sequence me apply karenge → divergent states. Server version number hi operation order ka single source of truth hai.

Delete transformation ka example

User A: delete(2), User B: insert('X', 5) — agar A ka delete pehle execute hua to B ki position shift hoti hai: 5 → 4 (ek character position se pehle remove ho gaya).

Transform ke 2 golden rules: (1) Target position se pehle insert ho to target right shift hota hai (+1). (2) Target position se pehle delete ho to target left shift hota hai (−1). Lab 1 aur Lab 4 me ye khud try karo.

Diagram se: Diagram ke neeche OT diagram me yahi dikhaya hai — 'BC' se User A ka insert 'ABC' banata hai, User B ka insert 'BCD' banata hai, aur transform ke baad dono 'ABCD' par converge karte hain. Bina transform ke ek side 'ABDC' (INCONSISTENT) banta hai.

06.5Deep Dive (LLD)

Step 5: Alternative — CRDT Approach

CRDT dusra raasta hai — server sequencing ki zaroorat hi nahi, kyunki operations aise design kiye jaate hain ki kisi bhi order me apply karo, result same aaye.

  • CRDT kya hai: Conflict-Free Replicated Data Types — operations commutative hote hain (kisi bhi order me apply karo, same state).
  • Character-based CRDT: Har character ka unique ID hota hai (site_id + sequence_number): 'A' = {site: 1, seq: 1}, 'B' = {site: 1, seq: 2}.
  • User A insert karta hai: {site: 1, seq: 10, char: 'X', after: {site: 1, seq: 5}}, User B insert karta hai: {site: 2, seq: 5, char: 'Y', after: {site: 1, seq: 5}}
  • Dono operations kisi bhi order me apply ho sakte hain: (1) A phir B: ...X...Y..., (2) B phir A: ...Y...X..., (3) Conflict resolution: Deterministic ordering rule (jaise site_id tiebreaker) se final order same rehta hai.

Advantages

  • Central server sequencing ki zaroorat nahi.
  • Offline kaam karta hai (operations locally store hote hain).
  • Multi-master replication (multiple servers writes accept kar sakte hain).

Disadvantages

  • Zyada complex data structure (deletes ke liye tombstones).
  • Bada metadata overhead (har character ka unique ID).
  • Memory edit history ke saath badhti rehti hai.

Example — ABC → BCD

  • User A 'ABC' dekhta hai, position 0 par insert karta hai: 'AABC' (inconsistent mark hota hai).
  • User B 'ABC' dekhta hai, position 0 par delete karta hai: 'BC'.
  • OT se: Server sequence karta hai, dono 'BC' par converge karte hain.
  • CRDT se: Operations commute karte hain, dono 'BC' par converge karte hain (delete wins, ID ordering ke basis par).

Diagram se: Diagram ke neeche right side CRDT diagram me positions 0.25, 0.5, 0.75, 0.875 dikhaye gaye hain — ye fractional positions hain jo do characters ke beech me insert karne ke liye use hoti hain. Yehi CRDT ki khaasiyat hai — beech me jagah hamesha mil jati hai.

Step 6: Cursor & Presence Updates

Cursor aur presence — dusre users kahan type kar rahe hain, ye real-time me kaise dikhta hai?

  1. User A cursor move karta hai: Client cursor position change detect karta hai: {cursor_pos: 15, selection_start: 10, selection_end: 15}
  2. Throttling: Cursor updates har 100ms me batch hote hain (WebSocket traffic kam karne ke liye) — agar 100ms me koi change nahi to skip.
  3. Client bhejta hai, WebSocket se: {type: 'cursor', user_id: A, cursor_pos: 15, selection: {start: 10, end: 15}, timestamp}
  4. Gateway broadcast karta hai baaki clients (B, C, D) ko: {type: 'cursor_update', user: {user_id: A, name: 'User A', color: '#FF5733', cursor_pos: 15, selection: {start: 10, end: 15}}}
  5. Clients render karte hain: (1) Position 15 par colored cursor with label 'User A', (2) 10–15 tak selection highlight User A ke color me (semi-transparent), (3) Active users list me position update.
  6. Ephemeral data: Cursor positions DB me persist NAHI hoti (reconnect par dobara banti hain), Redis me TTL=5 min ke saath store hoti hain: HSET cursors:{doc_id} user:{user_id} '{cursor_pos, selection, timestamp}' EX 300
  7. User disconnect karta hai: Server cursor hata deta hai — DELETE cursors:{doc_id} user:{user_id}, broadcast karta hai {type: 'user_left', user_id: A} → baaki clients cursor indicator hata dete hain.

Cursor position kaise calculate hoti hai

Document text: 'Hello\nWorld' (\n = newline). User A ka cursor position 8 par hai ('World' ke andar). Client calculate karta hai: Line 1 = 'Hello\n' (6 chars), position 8 = line 2, column 2 (W-o). Text measure karke (canvas measureText ya DOM getBoundingClientRect): line 2 top = 20px, column 2 left = 15px. Phir cursor render hota hai us pixel position par, User A ke color me.

Throttling ka asar: Tez typing par har user 100 cursor updates/sec bhejta hai — bina throttle ke 10 users par 1000 messages/sec. 100ms throttle ke saath har user sirf 10 updates/sec bhejta hai — 10 users par 100 messages/sec — 90% kam traffic. Isi se 100+ concurrent editors per document possible hote hain.

Step 7: Auto-Save & Snapshot Creation

Auto-save ka matlab — user ko save dabana na pade, aur document khulne me bhi fast ho. Iske liye snapshots hain.

Snapshot kab banta hai — trigger

Do conditions, jo pehle aaye: har 50 operations ya har 5 minutes.

  • Background job check karta hai: SELECT COUNT(*) FROM operations WHERE doc_id={doc_id} AND timestamp > {last_snapshot_timestamp} — count ≥ 50 ho to snapshot trigger hota hai.

Reconciliation Service — snapshot kaise banata hai

  1. Latest snapshot fetch karo: GET S3 docs/{doc_id}/v{last_version}.txt
  2. Snapshot ke baad ke operations fetch karo: SELECT * FROM operations WHERE doc_id={doc_id} AND server_version > {last_version} ORDER BY server_version ASC
  3. Operations replay karo: Har operation sequentially apply karke current state reconstruct karo.
  4. Naya snapshot content generate karo.
  5. S3 me upload karo: PUT docs/{doc_id}/v{new_version}.txt (50 operations applied).
  6. Database update karo: INSERT INTO snapshots (snapshot_id, doc_id, version, blob_path, operations_since_last: 50, created_at: now()), UPDATE documents SET latest_snapshot_version={new_version}, updated_at=now()
  7. Redis cache update karo: SET doc:{doc_id}:state {current_content} EX 1800 (30 min TTL).
  8. Event publish karo: Kafka 'doc.snapshot_created' → {doc_id, version, operations_count: 50} analytics ke liye.

Snapshot se load kitna fast?

Snapshot fetch (50ms) + decompress (10ms) + 5 ops replay (5ms) = 65ms. Compare karo: 1000 ops shuru se replay karne me ~500ms lagte. Snapshot + gzip compression (70% size kam — 1000 chars → 300 bytes) se loading 8x fast ho jati hai.

Tip: Snapshot strategy optimization: Har 50 operations ya 5 minutes par snapshot banao. Isse storage cost aur replay time ka balance banta hai — 50 ops snapshot se max replay sirf 50 ops (~50ms) hota hai, jabki 10K ops replay karne me 5 seconds lagte hain.

Step 9: Offline Editing & Sync

Internet gaya to editing rukni nahi chahiye — offline changes local store hote hain, aur online aate hi OT se merge hote hain.

Offline jao — kya hota hai

  1. WebSocket connection close hota hai (network failure), client error/close event se detect karta hai.
  2. Client offline mode me chala jata hai: (1) Banner dikhata hai — 'Working offline, changes will sync when online', (2) Operations locally store karta hai — IndexedDB ya localStorage, (3) Editing chalti rehti hai (optimistic updates), (4) Saare operations queue hote hain: [{op_id, type, position, content, timestamp, client_version}]
  3. Local storage: SET offline_ops:{doc_id} [{op1, op2, op3, ...}], last_known_version: 42

Online wapas aao — sync ka flow

  1. Network restore hota hai, WebSocket automatic reconnect karta hai (exponential backoff se retry).
  2. Client sync request bhejta hai, WebSocket se: {type: 'sync_request', doc_id, last_known_version: 42, queued_operations_count: 5}
  3. Server respond karta hai: (1) Version 42 ke baad ke server operations fetch karta hai: SELECT * FROM operations WHERE doc_id={doc_id} AND server_version > 42 ORDER BY server_version, (2) Client ko bhejta hai: {type: 'sync_response', server_operations: [{op1, op2, ...}], current_version: 50}
  4. Client reconciliation: (1) Pehle server operations apply karo (OT se), (2) Local queued operations ko server ops ke against transform karo, (3) Transformed local operations server ko bhejo: {type: 'operations_batch', ops: [{transformed_op1, transformed_op2, ...}]}, (4) Server validate karke apply karta hai agar conflict na ho.
  5. Conflict ho to modal dikhta hai — 'Conflicts detected during sync, review changes' — user choose karta hai: keep local, keep server, ya manual merge.

Worked example — offline delete + online insert

User A offline hai: 'hello' delete karta hai position 0–5 par. Server state: 'hello world'. User B (online) '!!!' insert karta hai position 6 par → server state: 'hello !!!world'. User A reconnect karta hai: (1) Server bhejta hai insert('!!!', 6), (2) Client apply karta hai — 'hello' locally already delete ho chuka hai, to insert position transform hoti hai: 6 → 1 (5 chars pehle delete ho gaye), apply hota hai: '!!!world', (3) Client bhejta hai delete(0, 5), (4) Server receive karta hai — document hai 'hello !!!world', delete apply karta hai → '!!!world', (5) Saare clients '!!!world' par converge karte hain.

Tip: Offline editing sync: Operations locally store karo (IndexedDB), reconnect par (1) last_known_version ke baad ke server ops fetch karo, (2) local ops ko OT se transform karo, (3) transformed ops server par apply karo. Isse eventual consistency guarantee milti hai.

Step 10: Locking Protocol (Pessimistic — Optional)

Google Docs me locking nahi hoti — sab freely edit karte hain. Lekin kuch apps me ek paragraph ek waqt par ek hi user edit kar sake — wahan pessimistic locking chahiye.

ApproachKaiseKab
Optimistic (Git merge jaisa)Sab freely edit karo, conflicts OT/CRDT se resolve karoGoogle Docs ka default — real-time collaboration
Pessimistic (Banking jaisa)Edit karne se pehle section lock karoJahan strong locking zaroori ho — typical docs me nahi

Pessimistic locking kaise implement hoti hai

Step 14: Performance Optimization & Scaling

Scale par har layer ko optimize karna padta hai — gateway, Redis, op-log, snapshots, sab.

  • Redis as canonical copy: Short-lived cache (TTL 30 min) current document state ka — 90% read requests serve karta hai bina S3/DB ko chhede; TTL expire hone ya memory pressure par evict hota hai.
  • WebSocket Gateway scaling: Horizontal scaling — 10K connections per instance, connection count ke basis par auto-scale (target: 7K connections per instance, headroom ke liye).
  • Op-log partitioning: Operations table ko doc_id hash se partition karo — har partition documents ka subset handle karta hai, parallel processing possible hoti hai.
  • Snapshot compression: S3 upload se pehle gzip compress karo (storage cost 70% kam), read par decompress karo.
  • CDN for static assets: Editor UI, fonts, icons CloudFront se serve karo — fast global load times ke liye.
  • Operation batching: Client rapid keystrokes ko batch karta hai (jaise 'hello' type karne par 1 operation with 'hello', 5 alag chars nahi) agar typing speed > 5 chars/sec ho.
  • Lazy loading: Bahut bade docs (>100K chars) ke sections on-demand load karo — initial load me pehle 10K chars, baaki scroll karne par.
  • Garbage collection: Purane operations (>90 days) ka periodic cleanup — snapshots banne ke baad archive karo S3 Glacier me compliance ke liye.

Numbers yaad rakho: 10K connections/instance, 7K target, 90% Redis reads, 70% gzip saving, 5 chars/sec batching threshold, 10K chars initial load, 90 days archival.

9. Collaborative Editing Problem

Asli problem ko ek chhote example se samjho — 'ABC' document, do users, do operations, aur bina OT/CRDT ke kya gadbad hoti hai.

Problem scenario (diagram se)

Document content 'ABC' hai. User A aur User B ek saath edit karte hain (offline/concurrently):

  • User A ka operation: insert(R, 29) position 29 par — document banta hai 'ABC...R...' (A end me insert karta hai).
  • User B ka operation: delete(0) position 0 par — document banta hai 'BC' (B pehla character delete karta hai).
  • Challenge: In concurrent operations ko bina conflict ke merge kaise karo? Dono users ko alag-alag intermediate states dikh rahe hain.
  • Bina OT/CRDT ke: Naive merge ek user ke changes kho dega ya inconsistent state bana dega.

OT solution

  1. Server A ki op pehle receive karta hai, version 1 assign karta hai, B ko broadcast karta hai.
  2. Server B ki op receive karta hai, A ki op ke basis par transform karta hai: delete(0) ko transform ki zaroorat nahi kyunki A ne end me insert kiya tha.
  3. Dono clients operations ko server order me replay karte hain: A ka insert → B ka delete → 'BC...R...' par converge karte hain.

CRDT solution

  1. Har character ka unique ID hai: 'A'={1,1}, 'B'={1,2}, 'C'={1,3}.
  2. User A: 'R' insert karta hai ID {1,29} ke saath.
  3. User B: {1,1} delete karta hai.
  4. Operations commute karte hain: delete {1,1} 'A' ko remove karta hai, R ke insertion se koi farq nahi padta.
  5. Dono clients deterministically 'BC...R...' par converge karte hain.

Diagram se: Diagram ke 'Collaborative Editing: The Problem' wale hisse me yahi dikhaya hai — 'BC' se User A ka insert 'ABC' aur User B ka delete 'BCD' banata hai; bina resolution ke ek taraf 'ABDC' (INCONSISTENT, laal me) aur dusri taraf 'ABCD' banta hai. OT/CRDT ke baad dono taraf ek hi consistent state hoti hai.

Interview favourite: Interviewers ko ye pasand hai — 'Collaborative editing problem kaise solve hoti hai?' Walkthrough do: User A insert karta hai, User B delete karta hai concurrently → Server sequence karta hai (A pehle) → B ki position A ke insert ke basis par transform hoti hai → Dono clients server order me replay karte hain → same state par converge karte hain.

Key guarantee: Strong eventual consistency — saare clients jinhone operations ka same set dekha hai, woh identical state par converge karenge.

Q1OT kaise kaam karta hai concurrent editing ke conflicts resolve karne me?

OT concurrent operations ko transform karta hai — ek operation ke effect ko dusre ke hisaab se adjust karta hai. Scenario: Document 'hello', version 10. User A: insert('!', 5) → 'hello!'. User B: delete(1) → 'hllo'. Server A ko pehle receive karta hai (version 11), phir B ko (version 12). Jab B ki operation aati hai, server dekhta hai B ka client_version=10 hai lekin current server_version=11 hai (A ki op apply ho chuki). Transformation: B ne 'hello' me position 1 par delete karna chaha tha, lekin A ne position 5 par insert kiya (baad me), to delete position same rehti hai. Transformed B ki op: delete(1) valid hai. 'hello!' par apply karo → 'hllo!'. Broadcast: (1) A ka insert B ko bhejo, (2) B ka delete A ko bhejo. Dono clients server order me operations apply karte hain → 'hllo!' par converge karte hain.

Complex case: Agar A ne position 0 par insert kiya hota — insert('X', 0) → 'Xhello'. B ka delete(1) transform hoga: original target 'h' position 1 par tha, lekin ab 'h' position 2 par shift ho gaya (X pehle insert hua). Transformed op: delete(2). 'Xhello' par apply karo → 'Xello'.

Key rules: (1) Target position se pehle insert ho to target right shift (+1), (2) Target position se pehle delete ho to target left shift (−1), (3) Server-assigned order me operations apply karne se saare clients converge karte hain.

Server sequencing kyun? Central ordering ke bina Client A aur B operations ko alag-alag order me apply kar sakte hain → divergent states. Server operation sequence ka single source of truth hai.

Edge cases: (1) Same position par concurrent inserts → server arbitrarily order karta hai (jaise timestamp ya user_id se), (2) Overlapping deletes → pehla delete jeetta hai, dusra no-op ban jata hai ya position shift hoti hai. Production: Google Docs OT use karta hai, central server millions of concurrent operations per second handle karta hai, operation log replay aur versioning ke liye persist hota hai.

Q2CRDT kya hain aur OT se kaise alag hain?

CRDT (Conflict-Free Replicated Data Types) aise data structures hain jinki operations commute karti hain — kisi bhi order me apply karo, same state par converge karte hain. Character-based CRDT example: Har character ka unique ID = {site_id, sequence_number}. Document 'hello': 'h'={1,1}, 'e'={1,2}, 'l'={1,3}, 'l'={1,4}, 'o'={1,5}. User A offline hai: 'X' insert karta hai 'h' ke baad → {1,6} banata hai with position 'after {1,1}'. User B offline hai: {1,1} delete karta hai ('h' delete). Jab A aur B sync karte hain: (1) A, B ka delete apply karta hai — 'h'={1,1} remove hota hai, document 'ello' banta hai, X={1,6} 'after {1,1}' positioned hai → X beginning me jata hai → 'Xello', (2) B, A ka insert apply karta hai — X={1,6} 'after {1,1}' add hota hai lekin {1,1} delete ho chuka hai → deterministic rule: deleted anchor ki position par insert karo → 'Xello'. Dono 'Xello' par converge karte hain, operation order se koi farq nahi padta.

Key properties: (1) Commutativity: op1(op2(doc)) = op2(op1(doc)), (2) Associativity: (op1 ˆ op2) ˆ op3 = op1 ˆ (op2 ˆ op3), (3) Idempotency: same operation do baar apply karne ka koi extra effect nahi.

CRDT advantages: (1) Central server nahi chahiye (peer-to-peer), (2) Offline kaam karta hai (operations locally store karo, baad me sync karo), (3) Multi-master replication (multiple servers writes accept kar sakte hain), (4) Simple conflict resolution (operations commute karne ke liye design ki gayi hain).

CRDT disadvantages: (1) Badi memory: har character ka metadata (site_id, sequence) — 'hello' = 5 chars lekin CRDT structure = 5 objects with IDs + position pointers, (2) Tombstones: deleted characters invisible markers chhod jate hain jo time ke saath accumulate hote hain, garbage collection chahiye, (3) Complex data structure: CRDT aam taur par tree ya linked list use karta hai (jaise RGA — Replicated Growable Array), simple string ki jagah.

OT vs CRDT: OT — central server operations sequence karta hai, simple data structure (sirf text), chhoti memory, complex transformation functions, single point of failure. CRDT — decentralized (central server nahi), complex data structure (IDs + tombstones), badi memory, simple operations (transformation nahi), offline kaam karta hai. Production: Google Docs OT use karta hai (centralized architecture, millions of users), Figma CRDT use karta hai (offline design collaboration), Notion OT use karta hai (server ke saath real-time editing), Automerge library distributed apps ke liye CRDT implement karti hai.

Hybrid approach: Kuch systems real-time editing ke liye OT use karte hain (low latency, central server) + offline sync ke liye CRDT (local changes store karo, online aane par merge karo) — dono ka best. Example: Collaborative design tool (Figma) — User A offline: object ko 10px right move karta hai, User B offline: same object ko 5px up move karta hai. CRDT: Dono operations commute karte hain → final position (+10px right, +5px up) hoti hai, merge order se koi farq nahi. OT se: Server ko ek operation ko dusre ke basis par transform karna padta → zyada complex, connectivity chahiye.

Q3Offline editing aur reconnect par sync kaise handle karte ho?

Offline flow: (1) User document edit kar raha hai, WebSocket connection drop hoti hai (network failure), (2) Client detect karta hai: WebSocket onerror/onclose event fire hota hai, (3) Offline mode me jao: Banner dikhao 'Working offline, changes will sync when online', local storage enable karo, (4) User editing chalti rakhta hai: Saare operations locally store hote hain — IndexedDB.put('offline_ops', {doc_id, ops: [{op_id, type: 'insert', position: 10, content: 'hello', timestamp}]}), aur last_known_version: 42 bhi store hota hai (server se mila last version), (5) Optimistic UI: Changes turant editor me dikhte hain (offline hone ke bawjood).

Reconnect flow: (1) Network restore hota hai, WebSocket reconnect karta hai (auto-retry with exponential backoff: 1s, 2s, 4s, 8s, max 30s), (2) Client sync request bhejta hai: {type: 'sync_request', doc_id, last_known_version: 42, queued_ops_count: 5}, (3) Server respond karta hai: {type: 'sync_response', server_ops: [{op1, op2, op3}], current_version: 50}, (4) Server operations: woh ops jo client offline tha tab server par hue (dusre users se), (5) Client reconciliation: (a) Pehle server operations apply karo — ops 43–50 replay karo catch up karne ke liye, (b) Local queued operations ko OT se transform karo (server changes ke basis par positions adjust karo), (c) Transformed local ops apply karo, (d) Server ko bhejo: {type: 'operations_batch', ops: [{transformed_op1, transformed_op2}]}, (6) Server validate karta hai: operations latest state se conflict to nahi karte — valid hain to apply karo aur baaki users ko broadcast karo, invalid hain (rare) to reject karo aur full resync maango.

Conflict detection: Agar local op ki position document length se badi ho jaye server ops apply karne ke baad → conflict — modal dikhao 'Conflicts detected during sync', options: (a) Keep local changes (conflict area me server changes discard karo), (b) Keep server changes (local changes discard karo), (c) Manual merge (diff dikhao, user har change choose kare).

Example: User A offline: 'hello' delete karta hai position 0–5 par, server state: 'hello world'. User B (online): '!!!' insert karta hai position 6 par, server state: 'hello !!!world'. User A reconnect karta hai: (1) Server bhejta hai insert('!!!', 6), (2) Client apply karta hai — 'hello' locally already delete ho chuka hai, to insert position transform hoti hai: 6 → 1 (5 chars position 6 se pehle delete hue), apply hota hai: '!!!world', (3) Client bhejta hai delete(0, 5), (4) Server receive karta hai — document hai 'hello !!!world', delete apply karta hai → '!!!world', (5) Saare clients '!!!world' par converge karte hain.

Edge cases: (1) Bahut lambi offline period: Offline >24 hours with 1000s of operations ho to OT transformation skip karo, server se latest snapshot fetch karo, merge UI dikhao — local changes vs server state side-by-side, (2) Document delete ho gaya: Server par document delete hua offline rehte to reconnect par dikhao 'Document no longer exists, save local changes as new document?', (3) Permission revoke ho gayi: Offline rehte edit permission hat gayi to reconnect par operations ko 'suggested changes' me convert karo direct edits ki jagah.

Performance optimization: (1) Local operations compress karo: consecutive inserts merge karo ('h' + 'e' + 'l' + 'l' + 'o' → 'hello') bhejne se pehle, (2) Incremental sync: operations 50 ke batches me bhejo ek saath sab bhejne ki jagah (server overwhelm na ho), (3) Background sync: Service Worker use karo — browser tab band hone par bhi sync attempt kare. Production: Google Docs offline editing support karta hai Chrome extension + local storage se, online aane par OT transformation ke saath sync karta hai, unsolvable conflicts dikhata hai, aur version history se rollback deta hai.

Q4Cursor presence aur real-time cursor updates kaise implement karte ho?

Architecture: (1) Client cursor position track karta hai: Editor onChange event har cursor move par fire hota hai (arrow keys, mouse click, text selection), (2) Throttle updates: Cursor position changes har 100ms me batch karo — WebSocket flood na ho (user fast type kar raha hai = 10 chars/sec = 100 cursor updates/sec → throttle karke 10 updates/sec), (3) WebSocket se bhejo: {type: 'cursor', user_id: A, cursor_pos: 15, selection: {start: 10, end: 15}, timestamp}, (4) Server receive karta hai: Session active validate karta hai, user info nikalta hai (name, color session se), (5) Baaki ko broadcast karo: {type: 'cursor_update', user: {user_id: A, name: 'User A', color: '#FF5733', cursor_pos: 15, selection: {start: 10, end: 15}}}, (6) Baaki clients render karte hain: Position 15 par colored cursor indicator with label 'User A', 10–15 tak selection highlight semi-transparent color me.

Cursor positioning: Character position se pixel position calculate karo: (1) Document text: 'Hello\nWorld' (\n = newline), (2) User A ka cursor position 8 par hai ('World' ke andar), (3) Client calculate karta hai: Line 1 = 'Hello\n' (6 chars), position 8 = line 2, column 2 (W-o), (4) Text measure karo: canvas measureText() ya DOM getBoundingClientRect() use karo — line 2 top = 20px, column 2 left = 15px, (5) Cursor render karo: div at position absolute, top 20px, left 15px, borderLeft 2px solid #FF5733, label 'User A'. Selection rendering: Overlay div with semi-transparent background — position absolute, top 20px, left 10px (start), width 40px (end − start), height 20px (line height), background rgba(255,87,51,0.3).

Multiple users: Har user ko join par unique color assign karo: colors = ['#FF5733', '#33FF57', '#3357FF', '#FF33F5'], user_color = colors[user_id % colors.length], session me persist karo: Redis HSET session:{session_id} 'color' {color}, join par saare clients ko broadcast karo.

Ephemeral data: Cursor positions database me persist NAHI hoti (bahut frequent updates, durable data nahi), Redis me short TTL ke saath store hoti hain: HSET cursors:{doc_id} user:{user_id} '{cursor_pos: 15, selection: {...}, timestamp}' EX 300 (5 min), user disconnect hote hi auto-expire ho jati hain. User disconnect handling: WebSocket close event → server cursor hata deta hai: HDEL cursors:{doc_id} user:{user_id}, baaki clients ko broadcast karta hai {type: 'cursor_removed', user_id: A}, clients cursor indicator aur label hata dete hain.

Cursor transformation (OT): Jab operations apply hoti hain, cursor positions bhi adjust karni padti hain: User A ka cursor position 10 par hai, User B 'hello' insert karta hai position 5 par → A ki cursor position transform hoti hai: 10 → 15 (5 chars cursor se pehle insert hue), client B ki operation receive karte hi cursor position automatic adjust karta hai. Selection transformation: User A ne text 10–20 select kiya hai, User B chars 5–8 delete karta hai (selection se pehle 3 chars) → A ki selection transform hoti hai: (1) start: 10 → 7, (2) end: 20 → 17, adjusted selection: 7–17.

Mobile optimization: Mobile par cursor updates kam frequent hote hain (100ms ki jagah 200ms throttle), chhote cursor indicators (labels nahi, sirf dots), tap karke user name tooltip dikhta hai. Performance: Tez typing par har user 100 cursor updates/sec bhejta hai — bina throttle ke 10 users par 1000 messages/sec; 100ms throttle ke saath har user 10 updates/sec bhejta hai — 10 users par 100 messages/sec (90% reduction) — isse 100+ concurrent editors per document possible hote hain.

Example UI: Google Docs dikhata hai — user names ke saath colored cursors, user ke color me selection highlights, top-right corner me colors ke saath active users list, cursor par hover karo to user name dikhta hai agar label hidden ho. Advanced features: (1) Cursor following: Active list me user par click karo → uske cursor position par scroll ho jao, (2) Cursor hide: Dusre users ke cursors hide karne ka toggle agar distracting lage, (3) Collaborative editing analytics: track karo har user ka cursor har section me kitni der rehta hai (engagement metrics).

Q5Auto-save aur periodic snapshots kaise implement karte ho?

Snapshot trigger: Do conditions (jo pehle aaye): (1) Operation count: Document par har 50 operations, (2) Time-based: Last snapshot ke 5 minutes baad. Background job: Har minute chalta hai, saare active documents check karta hai: SELECT doc_id, COUNT(*) as op_count FROM operations WHERE timestamp > (SELECT max(created_at) FROM snapshots WHERE doc_id=operations.doc_id) GROUP BY doc_id HAVING COUNT(*) >= 50.

Snapshot creation flow: (1) Reconciliation Service pick karta hai: Job ya Kafka event se trigger hota hai {type: 'snapshot_needed', doc_id, op_count: 52}, (2) Last snapshot fetch karo: SELECT blob_path, version FROM snapshots WHERE doc_id={doc_id} ORDER BY version DESC LIMIT 1 → S3 path docs/{doc_id}/v10.txt milta hai, (3) Snapshot download karo: GET S3 docs/{doc_id}/v10.txt → base content 'Hello world', (4) Operations fetch karo: SELECT * FROM operations WHERE doc_id={doc_id} AND server_version > 10 ORDER BY server_version ASC → 52 operations, (5) Operations replay karo: FOR EACH op apply karo (insert/delete/format) → final content 'Hello world! This is a test.', (6) Validate karo: Document integrity check karo (koi negative position nahi, content length expected ke barabar), (7) Compress karo: gzip compress karo final content (size 70% kam hoti hai: 1000 chars → 300 bytes), (8) S3 me upload karo: PUT docs/{doc_id}/v11.txt.gz compressed content ke saath, (9) Database update karo: BEGIN TRANSACTION; INSERT INTO snapshots (snapshot_id, doc_id, version: 11, blob_path: 's3://...v11.txt.gz', operations_since_last: 52, created_at: now()); UPDATE documents SET latest_snapshot_version=11, updated_at=now(); COMMIT;, (10) Redis cache update karo: SET doc:{doc_id}:state {uncompressed_content} EX 1800 (30 min), (11) Event publish karo: Kafka 'doc.snapshot_created' → {doc_id, version: 11, op_count: 52} analytics ke liye.

Incremental snapshots: Poora document store karne ki jagah delta store karo: {base_version: 10, operations: [op1, op2, ...52]} — storage bachta hai lekin reconstruct slow hota hai; har 10 versions par full snapshot (versions 10, 20, 30, 40) fast recovery ke liye.

Auto-save indication: Client dikhata hai: (1) 'Saving...' indicator jab operations bheji jati hain, (2) 'Saved' with timestamp jab server acknowledge karta hai: {type: 'ack', op_id, server_version}, (3) 'All changes saved to Drive' jab 5 seconds idle ho, (4) 'Unsaved changes' agar WebSocket disconnect ho (operations locally queue hain).

Fast recovery: User document kholta hai: (1) Latest snapshot fetch karo: GET S3 docs/{doc_id}/v11.txt.gz, (2) Decompress karo: gunzip → 'Hello world! This is a test.', (3) Recent operations fetch karo: SELECT * FROM operations WHERE doc_id={doc_id} AND server_version > 11 (sirf snapshot ke baad ke ops), (4) Replay karo: 5 operations apply karo (last snapshot 2 min pehle bana tha) → current state, (5) Load time: Snapshot fetch (50ms) + decompress (10ms) + 5 ops replay (5ms) = 65ms vs 1000 ops shuru se replay karne me 500ms.

Garbage collection: Snapshots ke baad purane operations cleanup karo: (1) Operations archive karo: SELECT * FROM operations WHERE doc_id={doc_id} AND server_version <= {snapshot_version - 1000}, (2) S3 Glacier me store karo: PUT archive/{doc_id}/ops_2026_01.json.gz compressed ops ke saath, (3) Hot DB se delete karo, (4) Retention: Operations 90 days hot storage me rakho, phir archive karo, snapshots hamesha rakho.

Snapshot versioning: Har snapshot ek version hai: v1 (initial), v2 (50 ops ke baad), v3 (100 ops ke baad) — rollback enable karta hai: user 'Version history' click karta hai → v1, v2, v3 timestamps ke saath dikhte hain, kisi bhi version par restore kar sakta hai. Concurrent editing during snapshot: Snapshot creation background me hoti hai: (1) Snapshot generation ke dauran operations apply hoti rehti hain, (2) Snapshot specific server_version ki state capture karta hai (jaise version 62), (3) Naye operations (version 63+) snapshot complete hone ke baad apply hote hain, koi downtime nahi.

Production numbers: Google Docs roz ~100M snapshots generate karta hai saare documents me, average snapshot size 50KB (compressed), GCS (Google Cloud Storage) me store hote hain lifecycle management ke saath (hot → cold → archive), 99% users ke liye sub-second document loading enable karta hai.

Q6Version history aur rollback kaise handle karte ho?

Version creation: Automatic versioning snapshots se hoti hai: (1) Har 50 operations → naya snapshot = naya version, (2) Manual versions: user 'Name current version' click karta hai → label ke saath named snapshot banata hai (jaise 'Final draft v1'), (3) Timestamps: har version created_at store karta hai sorting aur display ke liye.

Version history fetch karna: User 'Version history' button click karta hai: GET /v1/api/docs/{doc_id}/versions → (1) Database query: SELECT snapshot_id, version, created_at, operations_since_last, created_by, label FROM snapshots WHERE doc_id={doc_id} ORDER BY version DESC LIMIT 50, (2) Users se join karke creator names lao, (3) Response: [{version: 11, created_at: '2026-01-22T10:30:00Z', label: null, created_by: 'system', ops_count: 52}, {version: 10, created_at: '10:25:00Z', label: 'Draft 1', created_by: 'User A', ops_count: 50}], (4) UI dikhata hai: version numbers, timestamps, creators, operation counts ke saath timeline.

Specific version dekhna: User version 10 click karta hai: GET /v1/api/docs/{doc_id}/version/10 → (1) Snapshot fetch karo: GET S3 docs/{doc_id}/v10.txt.gz, (2) Decompress karke return karo: {version: 10, content: 'Hello world', metadata: {created_at, created_by}}, (3) Display karo: Read-only preview with banner 'Viewing version 10 from 10:25 AM', (4) Changes dikhao: Current version vs selected version ka diff (additions green me, deletions red me highlight), (5) Navigation: 'Previous version' / 'Next version' buttons se history browse karo.

Version restore karna: User 'Restore this version' click karta hai: POST /v1/api/docs/{doc_id}/restore with {target_version: 10} → (1) Validate karo: user ke paas edit permission hai ya nahi, (2) Target version content fetch karo: GET S3 docs/{doc_id}/v10.txt.gz → 'Hello world', (3) Restore operation banao: {type: 'replace_all', content: {v10_content}, user_id, timestamp}, (4) Op-log me append karo: INSERT INTO operations (op_id, doc_id, type: 'restore', content, server_version: 63), (5) Naya snapshot banao: S3 me upload karo docs/{doc_id}/v12.txt.gz with v10 content (restored state naya version 12 ban jata hai), (6) Database update karo: INSERT INTO snapshots (version: 12, label: 'Restored from v10', created_by: user_id), (7) Active editors ko notify karo: WebSocket se broadcast {type: 'document_restored', from_version: 10, to_version: 12, by_user: 'User B'}, (8) Clients reload karte hain: Latest version (v12) fetch karo, local unsaved changes discard karo (confirmation prompt ke saath).

Version comparison: Side-by-side diff: User do versions select karta hai (v8 vs v10) → server diff compute karta hai: (1) Dono contents S3 se fetch karo, (2) Diff algorithm chalao (line-by-line changes compute karta hai), (3) Response: [{type: 'equal', text: 'Hello'}, {type: 'delete', text: 'old'}, {type: 'insert', text: 'world'}], (4) UI render karta hai: Side-by-side view with color coding (red=deleted, green=added, white=unchanged), (5) Merge option: Conflicting changes ke liye 'Accept left' / 'Accept right' / 'Accept both'.

Named versions: User versions ko milestones ke liye naam de sakta hai: (1) 'Name current version' click karo → modal name poochta hai, (2) POST /v1/api/docs/{doc_id}/versions with {label: 'Final draft before review'}, (3) Label ke saath snapshot banata hai, (4) Version history me special marker (star icon) ke saath dikhta hai. Auto-naming: System automatically versions ko naam deta hai: (1) Major edits: 'Version from 2 hours ago (50 operations)', (2) Daily: 'January 22, 2026 10:30 AM', (3) User-triggered: 'Saved by User A'.

Retention policy: Saare versions rakho: (1) 30 days: full access aur restore, (2) 90 days: view-only (direct restore nahi, content copy karna padega), (3) 1 year: Glacier me archived (retrieve karne me 12 hours lagte hain), (4) Forever: named versions kabhi expire nahi hote (user-marked important milestones).

Change attribution: Version history dikhata hai: (1) Kisne changes kiye: SELECT DISTINCT user_id FROM operations WHERE doc_id={doc_id} AND server_version BETWEEN {v8} AND {v10}, (2) Change summary: 'User A ne 500 words add kiye, User B ne 200 words delete kiye, User C ne 3 paragraphs format kiye', (3) Activity timeline: Time ke saath edit activity ka graph (operations/hour), (4) Detailed changes: Drill down karke har user ki individual operations dekho.

Optimizations: (1) Lazy loading: Version list load karo (50 most recent), purane versions scroll par load karo (pagination), (2) Thumbnail previews: Har version ke document ka image thumbnail generate karo (first page screenshot) visual navigation ke liye, (3) Fast diff: Consecutive versions ke beech precomputed diffs use karo on-demand compute karne ki jagah, (4) Compression: Purane versions zyada aggressively compress karo (gzip ki jagah bzip2) storage bachane ke liye. Mobile UX: Simplified version history — sirf major versions dikhao (daily snapshots), restore ke liye explanation ke saath confirmation chahiye, diff view side-by-side ki jagah inline changes dikhata hai (screen space kam hoti hai).

Production example: Google Docs saare documents ki version history store karta hai: roz millions of versions generate hote hain, 30 days ke andar kisi bhi point in time par rollback enable karta hai, named versions hamesha rakhe jate hain, change attribution exactly dikhata hai kisne har edit kiya timestamps ke saath.

Q7Reconciliation Service kya karta hai aur kaise implement karte ho?

Reconciliation Service data consistency ensure karta hai — operation log se canonical document state ko validate aur rebuild karke. Purpose: (1) Consistency validate karo: Operations sahi apply hui hain aur document state expectations se match karti hai, (2) Snapshots generate karo: Fast recovery ke liye periodic snapshots banao, (3) Anomalies detect karo: Corrupted operations ya invalid states identify karo, (4) State rebuild karo: Cache/snapshot kho jaye to op-log se document reconstruct karo.

Architecture: Kafka consumer + background jobs: (1) Kafka consumer: 'doc.operations' topic ko subscribe karta hai consumer group 'reconciliation-service' ke saath, har operation real-time me process karta hai, (2) Background jobs: Periodic full reconciliation nightly (2 AM) chalti hai saare documents validate karne ke liye.

Real-time reconciliation flow: (1) Operation publish hoti hai: Editor Service → Kafka 'doc.operations' topic: {doc_id, op_id, type: 'insert', position: 10, content: 'hello', user_id, server_version: 42, timestamp}, (2) Reconciliation Service consume karta hai: Kafka se operation event receive karta hai, (3) Operation validate karo: (a) Position valid check karo — position <= document_length (doc sirf 100 chars ka hai to position 1000 par insert nahi ho sakta), (b) User permissions check karo — DB query karke ensure karo user_id ke paas edit permission hai, (c) Sequence check karo — server_version pichle se 1 se badhta hai (koi gap nahi), (4) Metrics update karo: Counters increment karo {operations_processed, operations_by_doc, operations_by_user}, (5) Snapshot trigger check karo: SELECT COUNT(*) FROM operations WHERE doc_id={doc_id} AND timestamp > (SELECT max(created_at) FROM snapshots WHERE doc_id={doc_id}), count ≥ 50 ho to snapshot creation trigger karo.

Snapshot generation: (1) Last snapshot fetch karo: SELECT blob_path, version FROM snapshots WHERE doc_id={doc_id} ORDER BY version DESC LIMIT 1 → S3 path docs/{doc_id}/v10.txt.gz, (2) Download karo: GET S3 docs/{doc_id}/v10.txt.gz → base content, (3) Operations fetch karo: SELECT * FROM operations WHERE doc_id={doc_id} AND server_version > 10 ORDER BY server_version ASC → v10 ke baad 52 operations, (4) Operations replay karo: Har operation document par apply karo: (a) insert(10, 'hello') → position 10 par 'hello' insert karo, (b) delete(15, 3) → position 15 se 3 chars delete karo, (c) Har ek ke baad validate karo: position valid hai, content length expected ke barabar hai, (5) Checksum compute karo: Final content ka SHA256 hash integrity verification ke liye, (6) Snapshot upload karo: PUT S3 docs/{doc_id}/v11.txt.gz compressed content + checksum metadata ke saath, (7) DB update karo: INSERT INTO snapshots (snapshot_id, doc_id, version: 11, blob_path, checksum, operations_since_last: 52, created_at), (8) Redis update karo: SET doc:{doc_id}:state {content} EX 1800.

Anomaly detection: (1) Invalid position: Operation position > document length ho to error log karo, operation skip karo, document ko review ke liye flag karo: INSERT INTO reconciliation_errors (doc_id, op_id, error: 'Invalid position', severity: 'high'), (2) Sequence gap: server_version jump kare (42 → 44, 43 missing) to check karo operation 43 kho gayi ya nahi, Kafka offset se recovery attempt karo, (3) Checksum mismatch: Snapshot creation ke baad replay se checksum dobara compute karo vs stored checksum — mismatch ho to document state corrupt hai → admin ko alert karo, (4) Performance anomaly: Snapshot generation me >10 seconds lage to document bahut bada hai ya operations bahut complex hain → optimization ke liye flag karo.

Full reconciliation (nightly): (1) Trigger: 2 AM cron job (low traffic time), (2) Batch process: SELECT doc_id FROM documents WHERE updated_at > now() - INTERVAL '7 days' ORDER BY updated_at DESC → active documents, (3) Har document ke liye: (a) Last snapshot fetch karo, (b) Snapshot ke baad ke saare operations replay karo, (c) Checksum compute karo, (d) Redis cache se compare karo (agar exists karta hai), (e) Mismatch ho to naya snapshot generate karo, inconsistency log karo, (4) Report: {total_docs_checked: 10000, snapshots_created: 500, errors_detected: 2, total_time: '45 min'}, (5) Alerts: errors_detected > 10 ho to PagerDuty alert on-call engineer ko.

State rebuild: Document state kho jaye (Redis evict ho gaya, snapshot corrupt ho gaya): (1) Service ko request milti hai: GET /v1/api/docs/{doc_id}, (2) Shuru se operations fetch karo: SELECT * FROM operations WHERE doc_id={doc_id} ORDER BY server_version ASC, (3) Empty document se saare operations replay karo: '' se shuru karo, har insert/delete sequentially apply karo, (4) Snapshot generate karo: Current state S3 me save karo, (5) Redis me cache karo: SET doc:{doc_id}:state {content} EX 1800, (6) Time: 10K operations replay karne me ~5 seconds lagte hain (acceptable fallback).

Metrics & monitoring: (1) Grafana dashboards: operations/sec, snapshot creation rate, reconciliation errors, op-log replay time, (2) Alerts: reconciliation_errors > 10/hour ho to alert, snapshot_creation_time > 10 sec ho to alert (doc bahut bada hai), (3) SLIs: 99.9% operations 1 sec ke andar process hoti hain, 99% snapshots 5 sec ke andar bante hain. Scaling: (1) Kafka consumer parallelism: 10 consumer instances 10 partitions process karte hain (doc_id hash se partition), (2) Snapshot workers: 50 workers thread pool me snapshot generation concurrently handle karte hain, (3) Rate limiting: Max 100 snapshots/sec, S3 overload na ho — excess queue me jata hai. Error recovery: (1) Corrupted operation: Skip karo aur log karo, agle par continue karo, document ko 'inconsistent' mark karo manual review ke liye, (2) Database failure: Kafka events 7 days retain karta hai, recovery ke baad offset se replay karo, (3) S3 failure: Exponential backoff se snapshot upload retry karo, temporarily sirf Redis cache se serve karo.

Production: Google Docs reconciliation roz billions of operations process karta hai, millions of snapshots generate karta hai, inconsistencies detect aur auto-correct karta hai, 99.99% data integrity ensure karta hai, disaster recovery enable karta hai (kisi bhi document ko op-log se rebuild kar sakte ho).

Q8Is system ko 1 million concurrent editors tak kaise scale karoge?

1M concurrent editors ke liye har layer par horizontal scaling chahiye:

WebSocket Gateway scaling: (1) Capacity: Har instance 10K connections handle karta hai, 1M / 10K = 100 instances chahiye, (2) Load balancing: TCP load balancer (ELB/ALB) with sticky sessions (IP hash) — user ka WebSocket poori duration ek hi instance par rehta hai, (3) Auto-scaling: Connection count par scale karo, target 7K connections/instance (30% headroom), (4) Connection handling: HTTP se WebSocket upgrade, persistent TCP connections maintain karo, har 30 sec heartbeat disconnect detect karne ke liye, (5) Memory: 10K connections × 10 KB/connection = 100 MB per instance (manageable), (6) Network: 10K connections × 10 updates/sec × 500 bytes = 50 MB/sec = 400 Mbps per instance.

Document Editor Service scaling: (1) Stateless service: Har instance koi bhi document process kar sakta hai (koi affinity nahi), (2) Horizontal scaling: 1M users ke operations handle karne ke liye 200 instances, (3) Load distribution: Operations doc_id hash se partition hoti hain, Kafka topic me 100 partitions hain (redundancy ke liye 2 instances per partition), (4) Operation processing: Har instance 5K ops/sec process karta hai (1M users / 200 instances, average 1 operation per user per second maan kar), (5) Cache hit rate: Redis document state ke liye 95% cache hits deta hai, sirf 5% DB tak jate hain.

Redis scaling: (1) Redis Cluster: 50 nodes (master + replicas), har node 20K documents handle karta hai, (2) Sharding: doc_id hash se shard karo, hash(doc_id) % 50 = shard_id, (3) Memory: 1M active documents × 50 KB avg = 50 GB, replication (3x) ke saath = 150 GB total, (4) Throughput: 50 nodes × 100K ops/sec = 5M ops/sec capacity (1M users × 10 ops/sec = 10M ops/sec chahiye, to 100 nodes chahiye), (5) Eviction policy: LRU eviction with TTL=30 min document state ke liye — hot documents cached rehte hain, cold documents evict hokar S3 se dobara fetch hote hain.

Database (PostgreSQL) scaling: (1) Read replicas: 10 replicas read queries ke liye (operations fetch karna, user permissions, version history), (2) Write primary: 1 primary writes ke liye (op-log me operations append karna), (3) Sharding: Operations table ko doc_id hash se partition karo (100 shards), har shard 1% documents handle karta hai, (4) Write throughput: 1M users × 1 operation/sec = 1M ops/sec, batching ke saath (10 ops per transaction) = 100K transactions/sec, PostgreSQL ~10K txn/sec per shard handle karta hai, minimum 10 shards chahiye, (5) Connection pooling: Har API instance 200 connections maintain karta hai, 200 instances × 200 connections = 40K connections (PgBouncer use karo 500 connections per database tak pool karne ke liye).

Kafka scaling: (1) Cluster: 20 brokers with replication factor 3, (2) Partitions: 'doc.operations' topic ke liye 100 partitions — parallel consumption enable karta hai, (3) Throughput: 1M ops/sec × 500 bytes/op = 500 MB/sec write, Kafka 1 GB/sec per broker handle karta hai, 20 brokers = 20 GB/sec capacity (kaafi headroom), (4) Retention: 7 days retention (disaster recovery ke liye replay enable karta hai), (5) Consumers: 100 consumer instances (1 per partition) — Reconciliation Service, Notification Service, Analytics Service ke liye.

S3 scaling: (1) Snapshots: 1M active documents × 1 snapshot/5 min = 12M snapshots/hour = 3333 snapshots/sec, (2) S3 write capacity: 5500 requests/sec per prefix (doc_id ka pehla letter), multiple prefixes use karo (a/, b/, c/, ... z/) = 5500 × 26 = 143K writes/sec (sufficient), (3) Read capacity: Document opening = snapshot fetch, 1M users 10 min me docs kholte hain = 100K opens/min = 1666 ops/sec (limits ke andar), (4) CDN caching: CloudFront frequent snapshots cache karta hai (popular documents), 90% cache hit rate se S3 reads 10x kam ho jati hain.

Network bandwidth: (1) WebSocket traffic: 1M users × 10 ops/sec × 500 bytes = 5 GB/sec = 40 Gbps, (2) Kafka traffic: 500 MB/sec write + 500 MB/sec × 3 consumers = 2 GB/sec = 16 Gbps, (3) S3 traffic: 3333 snapshots/sec × 50 KB = 166 MB/sec = 1.3 Gbps, (4) Total: ~60 Gbps, AWS VPC with 100 Gbps capacity use karo.

Cost optimization: (1) Spot instances: WebSocket Gateway ke liye spot instances use karo (70% discount), interruption par graceful failover, (2) Reserved instances: Editor Service ke liye reserve karo (1-year commitment par 40% discount), (3) S3 lifecycle: Purane snapshots (>90 days) Glacier me move karo (10x sasta), (4) Compression: gzip snapshots (70% size kam) — S3 storage aur transfer costs bachata hai, (5) Total cost: 1M concurrent users ke liye ~$500K/month (WebSocket $200K + Databases $150K + Kafka $50K + S3 $50K + Network $50K).

Monitoring & observability: (1) Metrics: operations/sec, WebSocket connections, cache hit rate, snapshot generation time, error rate, (2) Dashboards: Grafana with real-time graphs per service, (3) Alerts: PagerDuty critical errors ke liye (DB down, Kafka lag >1 min, 5xx errors >1%), (4) Distributed tracing: Jaeger request tracing ke liye across services (WebSocket → Editor → Kafka → DB → S3).

Failure handling: (1) WebSocket instance failure: Client automatic dusre instance se reconnect karta hai (exponential backoff), sync karke missed operations catch up karta hai, (2) Editor Service failure: Kafka events retain karta hai, naya instance last committed offset se replay karta hai, (3) Redis failure: S3 se snapshots fetch karke + DB se recent operations replay karke fallback, (4) Database failure: Read replica ko primary banao (2–3 min RTO), Kafka events recovery ke baad replay ke liye retain karta hai, (5) S3 failure: Redis cache se serve karo (last 30 min ki activity cover karta hai), snapshot writes baad ke liye queue karo.

Production examples: Google Docs millions of concurrent editors handle karta hai similar architecture se, har layer par horizontally scale karta hai, millions of operations per document ke liye optimized custom OT algorithm use karta hai, 99.9% uptime maintain karta hai, bade events ke dauran peak loads handle karta hai (jaise large conferences ke liye collaborative planning).

Interview FAQs — 36 sawal-jawab

36 interview FAQs — lesson ke concepts aur unse jude sawal, har ek ka poora Hinglish jawab. Kisi bhi sawal par click karke jawab kholo.

Q01OT kya hai aur ye concurrent editing me kaam kaise karta hai?
OT matlab Operational Transformation. Jab do users ek saath edit karte hain to server unki operations ko transform karta hai — ek operation ke effect ko dusre ke hisaab se adjust karta hai. Jaise document 'abc' me User A position 0 par 'A' insert karta hai aur User B position 3 par 'D' insert karta hai, to server B ki position ko 3 se 4 kar deta hai (kyunki A ne pehle ek character insert kar diya). Dono clients 'AabcD' par converge karte hain. OT ke liye central server sequencing zaroori hai.
Q02CRDT kya hai aur OT se kaise alag hai?
CRDT matlab Conflict-Free Replicated Data Types. Isme operations aise design ki jati hain ki woh commute karein — kisi bhi order me apply karo, final state ek hi aaye. Har character ka unique ID hota hai (site_id + sequence). OT ko central server chahiye operations sequence karne ke liye, CRDT ko nahi — isliye CRDT offline aur peer-to-peer me behtar hai. Lekin CRDT me har character ka metadata hota hai, isliye memory zyada lagti hai aur deletes ke tombstones accumulate hote hain.
Q03Google Docs OT kyun use karta hai aur Figma CRDT kyun?
Google Docs centralized architecture hai — millions of users ek central server se connect hote hain, isliye OT perfect hai: simple data structure (sirf text), chhoti memory, server saare operations sequence karta hai. Figma offline-first design tool hai — designers bina internet ke kaam karte hain aur multi-master chahiye, isliye CRDT behtar hai: operations locally store hoti hain aur kisi bhi order me merge ho jati hain. Notion bhi OT use karta hai, Google Docs ki tarah.
Q04Real-time editing ke liye WebSocket kyun chahiye, HTTP polling kyun nahi?
HTTP polling me client har second server se poochta hai 'kuch naya hai?' — 1M users honge to 1M requests/sec, jinme se zyada tar khaali jayengi. WebSocket ek persistent connection hai — data sirf tabhi behta hai jab change hota hai, isliye 100x kam traffic. Plus WebSocket bidirectional hai: server bhi client ko push kar sakta hai bina pooche. Isi liye real-time collaboration ke liye WebSocket hi standard hai.
Q05Update latency 300ms se kam kaise achieve hoti hai?
Teen cheezein milke latency kam karti hain: pehle, optimistic updates — client server ka wait kiye bina type karte hi character dikha deta hai. Dusra, Redis canonical copy — document state 1ms me milti hai, DB/S3 tak jaana nahi padta. Teesra, WebSocket par direct broadcast — operation server se seedha baaki clients tak jati hai, bina kisi polling delay ke. Operation batching bhi madad karta hai: rapid keystrokes ek operation me batch ho jate hain.
Q06Strong eventual consistency ka matlab kya hai?
Matlab ye: thodi der ke liye do users ko alag document state dikh sakti hai (jaise ek ne abhi type kiya, dusre tak pahuncha nahi), lekin end me — jab saare operations sab tak pahunch jayein — sabka document bilkul identical hoga. 'Strong' isliye kehte hain kyunki convergence guaranteed hai, probabilistic nahi. OT me server sequencing aur CRDT me commutative operations ye guarantee dete hain.
Q07Op-log kya hai aur ye append-only kyun hota hai?
Op-log document ke saare operations ka record hai — har insert, delete, format, ek row ke roop me, server_version ke order me. Ye append-only hota hai: operations ko kabhi edit ya delete nahi karte, sirf add karte hain. Isse teen fayde hain: pehla, kisi bhi point se document rebuild kar sakte ho (snapshot + replay). Dusra, version history aur rollback possible hai. Teesra, audit trail milti hai — kisne kab kya change kiya. Index (doc_id, server_version) par hota hai taaki range queries fast hon.
Q08Snapshot kab banta hai — 50 operations ya 5 minutes?
Dono conditions me se jo pehle aaye: har 50 operations ke baad ya har 5 minutes ke baad. Background job har minute check karta hai — snapshot ke baad operations count 50 ya zyada ho to snapshot trigger hota hai. Is strategy se max replay sirf 50 operations ka hota hai (~50ms), jabki bina snapshot ke 10,000 operations replay karne me 5 seconds lagte. Storage cost aur replay time ka balance banta hai.
Q09Snapshot se document load fast kaise hota hai?
Bina snapshot ke document kholne par saare operations shuru se replay karne padte — 1000 ops ho to ~500ms. Snapshot ke saath: latest snapshot fetch karo S3 se (50ms), gzip decompress karo (10ms), aur snapshot ke baad ke sirf 5 operations replay karo (5ms) — total 65ms. Gzip compression se snapshot size 70% kam hoti hai (1000 chars sirf 300 bytes). Isliye Google Docs documents sub-second me khulte hain.
Q10Redis canonical copy ka matlab kya hai?
Redis me document ki current state ka ek copy rehta hai jo sabse fresh maana jata hai — TTL 30 minute ke saath. Jab user document kholta hai to pehle Redis check hota hai: hit hua to 1ms me state mil gayi, miss hua to S3 snapshot + op-log replay se state banakar Redis me cache kar dete hain. Isse 90% reads S3 aur DB ko chhue bina serve hote hain. Redis 'canonical' isliye hai kyunki saare editor instances isi copy ko source of truth mante hain.
Q11Cursor positions database me kyun store nahi karte?
Cursor har 100ms me badalta hai — ek user ek second me 10 baar cursor move kar sakta hai. Itni frequent updates ko database me likhna barbaadi hai: disk writes, index updates, aur data ka koi durable value bhi nahi (disconnect hote hi cursor ka koi matlab nahi). Isliye cursor Redis me rehta hai, 5 minute TTL ke saath, aur disconnect par delete ho jata hai. Ye ephemeral data hai — live dikhane ke liye, store karne ke liye nahi.
Q12Cursor throttling 100ms kyun hoti hai?
Bina throttle ke ek fast typist 100 cursor updates/sec bhejega. 10 users ho to 1000 messages/sec sirf cursors ke liye — WebSocket aur server dono par load. 100ms throttle se har user second me sirf 10 updates bhejta hai: 10 users par 100 se 10 messages/sec — 90% kam traffic. 100ms itna chhota hai ki user ko cursor movement me koi lag nahi dikhta. Mobile par 200ms throttle use hoti hai kyunki wahan bandwidth aur battery dono kam hote hain.
Q13Offline editing ka flow kya hai?
Jab WebSocket disconnect hota hai to client offline mode me chala jata hai: banner dikhata hai, operations IndexedDB ya localStorage me store karta hai, aur user editing chalti rakhta hai (optimistic updates). Har operation ke saath last_known_version bhi store hota hai (jaise 42). Reconnect par client server se version 42 ke baad ke operations mangta hai, unhe apply karta hai, apni local operations ko OT se transform karta hai, aur transformed operations server ko bhejta hai. Agar conflict ho to user ko keep-local, keep-server ya manual merge ka option milta hai.
Q14Reconnect par conflict aaye to kya hota hai?
Agar local operation ki position server operations apply karne ke baad document length se badi ho jaye, to conflict mana jata hai. Tab user ko ek modal dikhta hai — 'Conflicts detected during sync' — jisme teen options hote hain: keep local (server changes discard karo), keep server (local changes discard karo), ya manual merge (diff dekhkar har change choose karo). Aam taur par OT se conflicts automatic resolve ho jate hain; manual modal sirf rare cases me aata hai, jaise bahut lambi offline period ya delete hua document.
Q15Version history kaise kaam karti hai?
Har snapshot ek version hai — har 50 operations ya 5 minutes par naya snapshot banta hai, aur har snapshot ka version number badhta hai. User 'Version history' kholta hai to snapshots ki list milti hai: version number, timestamp, operations count, aur kisne banaya. Kisi version par click karke read-only preview dekh sakte ho, do versions ka diff dekh sakte ho (additions green, deletions red), aur named versions bhi bana sakte ho jaise 'Final draft v1' — named versions kabhi expire nahi hote.
Q16Rollback kaise hota hai — purana version wapas kaise laate hain?
Rollback purane version ko overwrite nahi karta. User version 3 par restore karna chahe to system v3 ka content S3 se laata hai aur use ek naye snapshot ke roop me save karta hai — matlab restored state naya version ban jati hai (jaise v12). Iske baad saare active editors ko WebSocket se notify kiya jata hai ki document restore hua hai, aur unke clients latest version reload karte hain. Isliye history kabhi delete nahi hoti aur galti se restore karne par bhi wapas ja sakte ho.
Q17Pessimistic locking kab use hoti hai?
Jab ek section ko ek waqt par sirf ek hi user edit kar sake — jaise banking ya legal documents me. Google Docs me ye default nahi hai; wahan optimistic approach hai (sab freely edit karo, conflicts OT se resolve karo). Pessimistic locking me user pehle section lock karta hai (Redis SETNX, 5 minute TTL), phir edit karta hai, phir lock release karta hai. Agar lock kisi aur ke paas hai to 'locked by User B' response milta hai. Trade-off: conflicts khatam, lekin flexibility kam.
Q18SETNX lock kaise kaam karta hai?
SETNX matlab 'set if not exists' — Redis me key tabhi set hoti hai jab woh pehle se na ho. Lock ke liye key hoti hai lock:doc:{doc_id}:{section_id} aur value hoti hai user_id, TTL 300 seconds ke saath. Agar SETNX success hua to lock tumhara hai; fail hua to kisi aur ke paas hai. TTL isliye hai taaki user disconnect ho jaye to lock apne aap 5 minute me expire ho jaye — warna section hamesha ke liye lock ho jayega.
Q19Reconciliation Service kya karta hai?
Ye system ka watchman hai: Kafka se har operation ko consume karta hai, validate karta hai (position document length se chhoti hai? user ke paas edit permission hai? server_version sequence me 1 se badh raha hai?), 50 operations hone par snapshot trigger karta hai, aur raat 2 baje saare active documents ka full reconciliation karta hai — snapshot + operations replay karke checksum compare karta hai. Agar kuch gadbad mile (invalid position, sequence gap, checksum mismatch) to operation skip karke error log karta hai aur admin ko alert karta hai.
Q20Nightly reconciliation raat 2 baje kyun chalti hai?
Raat 2 baje traffic sabse kam hota hai, isliye heavy validation kaam tab chalana safe hai. Nightly job pichle 7 din me update hue saare documents ko check karta hai: snapshot fetch karo, uske baad ke operations replay karo, checksum compute karo, Redis cache se compare karo. Mismatch mile to naya snapshot banao aur inconsistency log karo. Report banti hai — kitne documents check hue, kitne snapshots bane, kitne errors mile. Errors 10 se zyada ho to on-call engineer ko PagerDuty alert jata hai.
Q21Op-log ko partition kaise karte hain?
Operations table ko doc_id ke hash se partition karte hain — jaise hash(doc_id) % 100 se 100 partitions. Har partition documents ka ek subset handle karta hai, isliye queries aur writes parallel chal sakte hain. Iske bina ek hi badi table par saare documents ke operations likhe jayenge aur woh bottleneck ban jayegi. Kafka topic bhi aise hi partition hota hai (100 partitions), taaki 100 consumers parallel me process kar sakein.
Q221 million concurrent editors kaise scale karte hain?
Har layer par horizontal scaling: 100 WebSocket gateway instances (10K connections each), 200 editor service instances (5K ops/sec each), 50 Redis nodes (20K documents each), PostgreSQL me 100 shards aur 10 read replicas, Kafka me 20 brokers aur 100 partitions, S3 me 26 prefixes (5500 writes/sec each). Total bandwidth ~60 Gbps aur cost ~$500K/month. Har layer stateless ya sharded honi chahiye taaki instances add karte hi capacity badhe.
Q23Sticky sessions WebSocket ke liye kyun zaroori hain?
WebSocket ek persistent TCP connection hai — user ka connection ek specific gateway instance par khulta hai aur poori session wahi rehta hai. Agar load balancer har message ko alag instance par bhej de to session state (kaun sa user, kis document me hai) har baar dobara banana padega. Sticky sessions (IP hash) se user ka WebSocket hamesha usi instance par rehta hai. Instance mar jaye to client automatic dusre instance se reconnect karta hai aur sync karke missed operations catch up karta hai.
Q24Kafka is system me kya karta hai?
Kafka operations ka event stream hai jo editor service ko baaki consumers se decouple karta hai. Editor service operation ko Kafka topic 'doc.operations' me publish karta hai aur aage badh jata hai — use nahi pata kaun consume kar raha hai. Reconciliation Service snapshots banata hai, Notification Service alerts bhejta hai, Analytics Service metrics nikalta hai — sab apne pace par consume karte hain. Kafka 7 days tak events retain karta hai, isliye disaster recovery ke liye replay bhi possible hai.
Q25S3 me snapshot ka path format kya hai?
Snapshots docs/{doc_id}/v{version}.txt path par store hote hain, gzip compress karke. Purane operations archive/{doc_id}/ops_{year}_{month}.json.gz me jate hain. Lifecycle policy hai: 0–30 days Standard storage, 30–90 days Infrequent Access, 90 days ke baad Glacier — jo 10x sasta hai. 1M documents par 3333 snapshots/sec bante hain, isliye S3 prefixes (doc_id ka pehla letter) use karke write capacity 5500 se 143K requests/sec tak badhayi jati hai.
Q26Gzip compression se 70% size kaise bachta hai?
Text documents me bahut repetition hota hai — spaces, common words, formatting. Gzip in repeated patterns ko compress kar deta hai: 1000 characters ka document sirf 300 bytes me aa jata hai. Isse S3 storage cost kam hoti hai, network transfer fast hota hai, aur snapshot load karne me decompress karne me sirf 10ms lagte hain. Average snapshot size 50KB (compressed) hoti hai Google Docs me.
Q27Google Docs ki 1.02M characters limit kyun hai?
Bahut bade documents me har operation ka replay, har snapshot ka size, aur har client ka memory usage badh jata hai. 1.02M characters ki limit se system predictable rehta hai: snapshot size bounded rehti hai, replay time bounded rehta hai, aur lazy loading (pehle 10K chars, baaki scroll par) se bade docs bhi smoothly khulte hain. Isse bade documents ko user ko parts me todne ko kaha jata hai.
Q28Ek document par 50–100 concurrent editors ki limit kyun hai?
Har editor har second operations aur cursor updates bhejta hai. 100 editors ho to ek document par 1000 messages/sec aa sakte hain — broadcast karna, OT transform karna aur Redis update karna sab isi rate par chalna chahiye. Isse zyada editors ho to document ko shards me todna ya editors ko read-only mode me daalna padta hai. Aam documents me 5–10 editors hi hote hain; 50–100 sirf hot docs (jaise company-wide planning docs) me hote hain.
Q29Operation batching kya hai aur 5 chars/sec threshold kyun hai?
Jab user tezi se type karta hai to har keystroke par alag operation bhejna wasteful hai. Client dekhta hai: agar typing speed 5 chars/sec se zyada hai to consecutive keystrokes ko ek operation me batch kar deta hai — 'hello' type karne par 1 operation with 'hello', 5 alag operations nahi. Isse op-log size kam hoti hai, Kafka messages kam hote hain, aur server load kam hota hai. Slow typing par har character alag operation rehta hai taaki dusre users ko real-time feel mile.
Q30Bade documents me lazy loading kaise kaam karti hai?
100K characters se bade document ko ek saath load karna slow aur memory-heavy hai. Isliye initial load me sirf pehle 10K characters aate hain — user ko document turant dikhne lagta hai. Baaki sections user ke scroll karne par on-demand load hote hain. Snapshot bhi sections me todkar store kiya ja sakta hai. Isse initial load time kam hota hai aur browser memory bhi kam use hoti hai.
Q31Op-log archival kya hai — 90 days ke baad kya hota hai?
Operations hot database me sirf 90 days rehte hain. Uske baad woh S3 Glacier me archive ho jate hain (archive/{doc_id}/ops_{year}_{month}.json.gz), kyunki snapshots se document rebuild ho sakta hai — purane operations ki roz zaroorat nahi. Glacier 10x sasta hai, lekin retrieve karne me ghante lagte hain. Compliance ke liye archive zaroori hai: agar kabhi audit ho to purana history nikala ja sake.
Q32Server version aur client version me kya farq hai?
Client version woh version hai jo client ne operation banate waqt dekha tha (jaise 42). Server version woh sequence number hai jo server operation ko assign karta hai jab woh arrive hoti hai (jaise 43). Agar client_version server ke current version se peeche hai, to matlab beech me dusre users ki operations aa chuki hain — aur OT transform zaroori hai. Server version hi operation order ka single source of truth hai; saare clients operations ko server_version ke order me apply karte hain.
Q33Insert/delete transform ke rules kya hain?
Do simple rules hain. Pehla: target position se pehle insert hua to target right shift hota hai (+1) — jaise 'abc' me position 0 par 'A' insert hua to position 3 par insert karne wala 'D' position 4 par jayega. Dusra: target position se pehle delete hua to target left shift hota hai (−1) — jaise position 2 par delete hua to position 5 par insert karne wala 'X' position 4 par jayega. Target se baad me hua operation koi shift nahi karta. Yehi do rules poori OT ka core hain.
Q34Tombstones kya hain aur CRDT me problem kyun hain?
CRDT me jab character delete hota hai to woh turant memory se nahi hataya jata — uski jagah ek invisible marker reh jata hai jise tombstone kehte hain. Ye isliye zaroori hai taaki baad me aane wale operations (jo us character ko reference karte hain) sahi order me apply ho sakein. Lekin tombstones time ke saath accumulate hote hain aur memory badhate rehte hain. Isliye CRDT systems ko periodic garbage collection chahiye — jab saare clients ne delete dekh liya ho, tab tombstones safely delete kiye ja sakte hain.
Q35CAP theorem is system me kaise apply hota hai?
Is system me Availability aur Eventual Consistency choose ki jati hai, strong consistency ki jagah. Matlab network partition ya heavy load me bhi user edit kar sakta hai (availability), aur thodi der ke liye do users ko alag state dikh sakti hai (eventual consistency). Lekin convergence guaranteed hai — OT ya CRDT se end me sabka document ek hi hoga. Banking systems iske ulta karte hain (strong consistency, availability sacrifice), kyunki wahan ek bhi galat state acceptable nahi. Document editing me thodi der ka divergence acceptable hai.
Q36File replace karna normal edit se kaise alag hai?
File replace ek special operation hai — type 'replace_all'. User nayi file upload karta hai (DOCX, TXT, PDF), system text extract karta hai, aur poora content ek operation ke roop me op-log me likhta hai. Turant naya snapshot banta hai, Redis update hota hai, aur saare active editors ko WebSocket se notify kiya jata hai ki content replace hua hai — unke clients latest snapshot reload karte hain. Kyunki replace bhi ek operation hai, ye version history me dikhta hai aur rollback bhi possible hai.
