Notification System kya hai — poora flow ek line me

Ek notification system wo machine hai jo Netflix, Walmart aur Amazon jaisi companies ko har minute lakhon notifications — OTP, order update, email, push — bina khoye, sahi samay par, sahi channel par bhejne deti hai. Is lesson me hum ye poora system scratch se design karenge: Kafka, Outbox pattern, Redis aur microservices ke saath.

🎯 YAAD RAKHNE WALI EK LINE — Client triggers notification → API Gateway → Notification Svc validates template & user preferences → Kafka queue (prioritized) → Notification Queue consumers → Provider routing (Email/SMS/Push/In-app) → External services (Twilio/SendGrid/FCM/APNS) → Delivery status → Rate limiting → Reporting. Interview me ye ek line bol do, phir har step ko kholkar samjhao.

Chaaron channels, ek hi system

System chaar channels support karta hai — Email, SMS, Push notification aur In-app notification. Ek hi order-confirmation alag-alag users tak email se bhi ja sakti hai aur push se bhi; kaunsa channel chalega, ye user ki preference tay karti hai, sender ki marzi nahi.

  • Email — order confirmation, receipt, newsletter; provider SendGrid ya Amazon SES.
  • SMS — OTP, alerts; provider Twilio ya MSG91; ek SMS 160 characters ka hota hai, lamba message split ho jata hai.
  • Push — Android par FCM, iOS par APNS; user ke saare devices par fanout hota hai.
  • In-app — app ke andar ka notification inbox.

Design diagram — poora architecture ek nazar me

Neeche wala diagram is lesson ka HLD dikhata hai: clients (jaise Amazon/Uber) → API Gateway & Load Balancer → services (Template Svc, User Preference Svc, Notification Svc, Reporting Svc) → databases → Kafka (Notification Evt) → provider routing. Functional Requirements — system ko kya-kya karna hai

Koi bhi system design karne se pehle pehla sawaal: system ko karna kya hai? Is notification system ki 8 functional requirements hain — ye wahi list hai jo interview me tum whiteboard par pehle likhoge.

8 features

  • Feature 1 — Multi-channel delivery: email, SMS, push notifications aur in-app notifications — chaaron channels support karo.
  • Feature 2 — Templates: notification templates banao, update karo, manage karo — variables/placeholders ke saath (jaise {{name}}, {{order_id}}).
  • Feature 3 — User preferences: har user ki pasand per-channel aur per-type — promotional, transactional, alerts — alag se rakho.
  • Feature 4 — Immediate aur scheduled delivery: abhi bhejo ya future ke liye schedule karo (scheduled_at).
  • Feature 5 — Delivery status tracking: har notification ki status — PENDING, SCHEDULED, SENT, DELIVERED, FAILED, CANCELLED.
  • Feature 6 — Bulk notifications: campaigns aur announcements — lakhon recipients — rate limiting ke saath.
  • Feature 7 — Reporting aur analytics: delivery rates, open rates, click rates, failures — sab measure karo.
  • Feature 8 — Retry mechanism: failed delivery ko exponential backoff ke saath retry karo.

Interview me kaise bolo

Interviewer poochhe "requirements kya hongi?" to pehle ye 8 points bolkar scope bandh do — phir poochho "kuch aur add karna hai ya isi scope me design karun?" Ye clarification interviewer ko dikhata hai ki tum pehle soch kar design karte ho, seedha code par nahi koodte.

Non-Functional Requirements — scale, latency, reliability

Functional requirements batate hain kya karna hai; non-functional batate hain kis scale aur kis bharose ke saath karna hai. Is system ke numbers yaad rakhna — interview me yahi numbers tumhare design decisions ko justify karte hain.

Scale & Performance

  • Scale — 1M+ notifications/min peak par: Black Friday sale ya breaking-news alert ke time system ko har minute 10 lakh se zyada notifications bhejni padti hain. Ye number hi batata hai ki sync API se kaam nahi chalega — async queue (Kafka) chahiye.
  • CAP Theorem — Availability >> Consistency: notification ka status thoda late update ho jaye to chalega (eventual consistency acceptable hai), lekin system down nahi hona chahiye. Isliye availability ko consistency se upar rakho.

Latency & Reliability

  • Real-time delivery: high-priority notifications (OTP) 5–10 second ke andar pahunchni chahiye; transactional notifications me thoda delay acceptable hai.
  • Reliability — at-least-once delivery guarantee: koi bhi notification lost nahi honi chahiye. Fail ho jaye to retry karo — lekin kho mat. (Kaise? Outbox pattern — Section 08 me detail me.)

Ye numbers design ko kaise chalate hain

1M/min ka matlab hai ~16,000 notifications/sec — isliye Kafka topics ko priority ke hisaab se baanta gaya hai, consumers auto-scale hote hain, aur provider rate limits (Twilio 100 SMS/sec) ko token bucket se manage kiya jata hai. Har scaling technique (Section 16) inhi numbers ka jawab hai.

04Design ki neev

Core Entities — 7 tables/objects

System ki 7 core entities hain. Inhe yaad rakhne ka tareeka: kaun → kya → kaise → kis haal me — User, Preferences, Content, Template, DeliveryStatus, Outbox, Notifications table.

Entity 1 — User + Client

user_id, email, phone, device_tokens[] (FCM/APNS), preferences {channels, types, do_not_disturb} — har user ke paas email, phone aur ek se zyada device tokens ho sakte hain (phone + tablet + web).

Entity 2 — NotificationPreferences

user_id, channels {email: true, sms: false, push: true, inapp: true}, types {promotional: false, transactional: true, alerts: true}, do_not_disturb: false — user ne kya band kiya hai, ye yahan rakha hai. Bhejne se pehle har baar ye check hota hai.

Entity 3 — NotificationContent

notification_id, user_id (recipient_id), external_user_id, template_id, channel (EMAIL/SMS/PUSH/INAPP), payload {variables}, status (PENDING/SCHEDULED/SENT/DELIVERED/FAILED/CANCELLED), priority (high/normal/low), scheduled_at, created_at, metadata — ek notification ka poora record.

Entity 4 — Template

template_id, name, channel (EMAIL/SMS/PUSH/INAPP), subject (email ke liye), body ({{variable}} placeholders ke saath), variables[] (jaise [name, order_id]), version, is_active, created_at — template immutable versioning ke saath aata hai (Section 15 me detail).

Entity 5 — DeliveryStatus

delivery_id, notification_id, channel, provider (Twilio/SendGrid/FCM/APNS), provider_message_id, status (SENT/DELIVERED/FAILED), sent_at, delivered_at, error_message, retry_count — provider ne kya bola, kab bola, iska audit trail.

Entity 6 — Notifications_outbox

outbox_id, notification_id, event_type, payload, published (boolean), created_at — transactional outbox pattern ki jaan; isi se at-least-once delivery guarantee milti hai.

Entity 7 — Notifications table

notification_id, user_id (recipient_id), external_user_id, template_id, channel, payload, status, priority, scheduled_at, metadata — main table; har notification ka ek row.

05Design ki neev

API Designing — notifications, templates, preferences

3 API groups hain — notification bhejna, template manage karna, aur user preferences. Interview me in APIs ko likhte waqt request/response aur status codes bhi bolo.

Notification Operations

  • POST /api/v1/notifications — notification bhejo: {templateId, recipientId, variables, channels[], priority, scheduledAt}. Response: 200 OK {notificationId, status: 'PENDING'}.
  • GET /api/v1/notifications/{notificationId}/status — kisi notification ki delivery status lo: PENDING / SENT / DELIVERED / FAILED.

Template Management

  • POST /api/v1/templates — placeholders wala template banao.
  • GET /api/v1/templates — saare templates list karo (paginated).
  • GET /api/v1/templates/{templateId}/{version} — kisi template ka specific version lo (versioning ki wajah se).
  • CRUD — templates ka Create, Read, Update, Delete.

User Preferences

  • PUT /api/v1/preferences — user ki notification preferences update karo: {channels: {email: bool, sms: bool}, types: {promotional: bool}}.
  • CRUD — user preferences ka Create, Read, Update, Delete.

Gateway par validation

POST /api/v1/notifications aate hi API Gateway 3 cheezein check karta hai: (1) Authentication & Authorization (JWT token, API key), (2) Rate limiting — 100 req/min per client, (3) Route to Notification Svc. Gateway-level rate limit provider-level rate limit se alag hai — pehla client ko rokta hai, doosra provider ko bachata hai.

06Design ki neev

High Level Design (HLD) — services aur unke databases

HLD ek line me: clients → API Gateway & Load Balancer → Services → Databases, aur beech me Kafka (Notification Evt) async processing ke liye. Har service ka ek database hai — shared database nahi.

Services

  • Template Svc → Template DB: notification templates par CRUD operations aur version management.
  • User Preference Svc → UserPref DB: user preferences (channels, types, DND) manage karta hai; preferences ko Redis me cache karta hai (24h TTL).
  • Notification Svc → Notification Provider (Email/InApp/SMS/Push): core orchestrator — template aur preferences validate karta hai, phir Kafka me publish karta hai.
  • Notification Evt (MQ) — Kafka: async notification processing ke liye message queue; prioritized queues — critical, standard, promotional, bulk.
  • Reporting Svc: delivery metrics aur analytics track karta hai — sent, delivered, failed, open rates, click rates.

Flow dobara, HLD ki nazar se

Client (jaise Amazon/Uber) request bhejta hai → Gateway → Notification Svc template fetch karta hai (Template Svc se) aur preferences check karta hai (User Preference Svc / Redis se) → valid hai to Kafka topic me daalta hai → consumers provider tak pahunchate hain → Reporting Svc delivery status se metrics banata hai. Sync part sirf validation aur DB write tak hai; asli delivery async hai — isiliye 1M/min handle hota hai.

LLD Step 1 — Notification Creation & Template Rendering

Client se request aate hi 5 kaam hote hain: template fetch, variables validate, preferences check, template render, notification_id generate. Ek bhi step fail ho to request wahin ruk jati hai — Kafka tak nahi pahunchti.

Worked example — order confirmation

Client bhejta hai: POST /api/v1/notifications {templateId: 'order_confirmation', recipientId: 'user123', variables: {name: '[Name]', order_id: 'ORD456'}, channels: ['email', 'push'], priority: 'high'}

Step-by-step

  • API Gateway validation: (1) Authentication & Authorization (JWT token, API key), (2) Rate limiting (100 req/min per client), (3) Route to Notification Svc.
  • Template fetch: Template Svc read karta hai — SELECT * FROM templates WHERE template_id='order_confirmation' AND is_active=true. Template milta hai: {template_id, name: 'Order Confirmation', channel: 'EMAIL', subject: 'Order {{order_id}} confirmed', body: 'Hi {{name}}, your order {{order_id}} has been confirmed...', variables: ['name', 'order_id']}.
  • Variables validate: saare required variables present hain ya nahi check karo — {name: '[Name]', order_id: 'ORD456'}. Agar koi missing hai to 400 'Missing variable: name' return karo.
  • User preferences fetch: User Preference Svc pehle Redis cache check karta hai — GET user_pref:user123 → {channels: {email: true, sms: false, push: true}, types: {promotional: false, transactional: true}}. Cache miss ho to UserPref DB query karo aur result ko 24 hour TTL ke saath cache karo. Phir opt-in check: agar channels.email=false to email channel skip karo; agar types.promotional=false aur notification type promotional hai to poora notification skip karo.
  • Template render: placeholders replace karo — subject: 'Order ORD456 confirmed', body: 'Hi [Name], your order ORD456 has been confirmed...'. Result: {subject, body, channel: 'EMAIL'}.
  • notification_id generate (UUID): notification_id = 'NOTIF789'.
⚠ DHYAAN DO — Preferences check kabhi skip mat karo. email:false ho to email skip, do_not_disturb:true ho to sab skip, promotional:false ho to marketing skip. Ye sirf UX nahi hai — GDPR, CAN-SPAM (unsubscribe link) aur TCPA (SMS opt-in) compliance hai. Preferences Redis me 24h TTL ke saath cache karo.

Lab se try karo

Lab L2 (Template Renderer) me khud variables daalkar rendered subject/body dekho — aur ek variable chhupakar 400 error bhi dekho. Lab L6 (Preference Checker) me toggles badal kar dekho ki kaunsa channel skip hota hai.

LLD Step 2 — Transactional Outbox Pattern & Kafka Publishing

Ye poore lesson ka sabse important step hai — interview me sabse zyada poochha jane wala. Outbox pattern ke bina notification kho sakti hai; iske saath at-least-once delivery guarantee milti hai.

Transactional write — dono inserts ek hi transaction me

BEGIN TRANSACTION, phir (1) INSERT INTO notifications (notification_id: 'NOTIF789', user_id: 'user123', template_id, channel: 'EMAIL', payload: {subject, body, to: '[user]@example.com'}, status: 'PENDING', priority: 'high', created_at: now()), (2) INSERT INTO notifications_outbox (outbox_id, notification_id: 'NOTIF789', event_type: 'notification.created', payload: {notification_id, channel, priority, recipientId}, published: false), phir COMMIT — atomic: dono succeed honge ya dono fail.

⚠ DHYAAN DO — CRITICAL: Transactional Outbox pattern mandatory hai reliable notifications ke liye. Kafka ko publish karo hi mat jab tak DB write usi transaction me na hua ho. Agar Kafka succeed aur DB fail → notification lost (koi record hi nahi). Outbox guarantee: agar DB commit succeed hua, to message EVENTUALLY publish hoga (CDC polling + retry).

Dual-write problem — outbox kyun chahiye

  • Naive approach: pehle DB me INSERT karo, phir Kafka me publish karo.
  • Problem 1: Kafka publish succeed, DB write fail → notification lost (DB me record hi nahi).
  • Problem 2: DB write succeed, Kafka publish fail → notification atak gayi (kabhi bhejegi hi nahi).
  • Solution: Outbox — agar DB commit succeed hua, to message outbox me hai, aur CDC polling use EVENTUALLY publish kar degi.

CDC / Publisher service — outbox ko poll karna

SELECT * FROM notifications_outbox WHERE published=false ORDER BY created_at LIMIT 1000 (batch processing, har 100ms poll). Har unpublished record ke liye: (1) Kafka me publish karo — topic priority se tay hota hai: high → notifications.critical.email, normal → notifications.standard.email, low → notifications.promotional.email. Kafka.send(topic: 'notifications.critical.email', key: notification_id, value: payload). (2) Mark published: UPDATE notifications_outbox SET published=true, published_at=now() WHERE outbox_id={id}. (3) Agar Kafka fail ho jaye to published false hi rehta hai — agle poll me retry (at-least-once delivery).

Kafka topics hierarchy — prioritized queues

  • notifications.critical.{channel} — OTP, security alerts; immediately process, dedicated consumers.
  • notifications.standard.{channel} — order confirmations, shipping updates; 5 min SLA.
  • notifications.promotional.{channel} — marketing emails, newsletters; 30 min SLA.
  • notifications.bulk.{channel} — batch campaigns; low priority.
  • notifications.retry — failed deliveries, exponential backoff ke saath.
🎯 INTERVIEW FAVOURITE — Interviewer hamesha poochhta hai: 'Notification lost kaise rokoge?' Jawab: Outbox pattern — single transaction me INSERT notifications + INSERT outbox → COMMIT. CDC outbox poll karta hai (published=false) → Kafka me publish karta hai → published=true mark karta hai. At-least-once delivery + idempotent consumers = user ko exactly-once.

LLD Step 3 — Queue Processing & Provider Routing

Kafka me message aane ke baad consumers use uthate hain. Teen cheezein yahan hoti hain: idempotency check (duplicate roko), rate limiting (provider ko bachao), aur provider routing (sahi provider chuno).

Consumer groups — kaun kitne workers

  • Email consumers — 20 instances: notifications.*.email consume karte hain (critical: 10, standard: 20, promotional: 5).
  • SMS consumers — 15 instances: notifications.*.sms ke liye.
  • Push consumers — 10 instances: notifications.*.push ke liye.

Consumer ko message mila — phir kya

Consumer notifications.critical.email se message leta hai: {notification_id: 'NOTIF789', channel: 'EMAIL', payload: {subject, body, to: '[user]@example.com'}, priority: 'high'}.

Idempotency check — duplicate bhejna roko

Pehle delivery log check karo: SELECT COUNT(*) FROM delivery_status WHERE notification_id='NOTIF789' AND channel='EMAIL'. Agar record mil jaye to skip — already processed hai. Kafka at-least-once delivery deta hai, isliye duplicate message aa sakta hai; idempotency check se user ko duplicate email nahi jata.

🎯 INTERVIEW FAVOURITE — Idempotent consumers: delivery_status check karo (agar exists → skip). Kafka at-least-once delivery par duplicates bhej sakta hai (consumer restart, network retry). Idempotency ke bina user ko 5 duplicate emails milenge — bahut bura UX. Check: SELECT COUNT WHERE notification_id + channel.

Rate limiting — token bucket, Redis + Lua script

Bucket key: rate_limit:email:sendgrid, capacity: 100 tokens, refill: 100 tokens/sec (SendGrid limit). Atomic check Lua script se: tokens >= 1 ho to DECR karo aur aage badho, warna ruko. Provider limits: Twilio 100 SMS/sec, SendGrid 50 email/sec, FCM 10K push/sec.

Backpressure — Kafka buffer banta hai

Agar rate limited ho to consumer slow ho jata hai aur Kafka messages buffer karta hai (millions of messages ki capacity). Lag badhta hai — monitoring me dikhta hai — aur lag > 1000 ho to auto-scaling consumers badhata hai (lekin provider limit ke upar nahi ja sakta).

Provider routing — channel ke hisaab se

  • EMAIL → Email Svc Provider (SendGrid / Amazon SES)
  • SMS → SMS Svc Provider (Twilio / MSG91)
  • Push → In-app Svc Provider (Android ke liye FCM, iOS ke liye APNS)
  • OTP → OTP Svc (dedicated, high priority)

LLD Step 4 — Email Delivery (SendGrid / Amazon SES)

Email ka flow: render → SendGrid ko bhejo → status SENT mark karo → webhook se DELIVERED confirm karo. Dhyaan do — SendGrid ka 202 Accepted matlab delivered nahi hai, sirf accept hua hai.

Email Svc Provider — bhejne se pehle

Final email render karo: HTML body with CSS styling, plain text fallback, attachments (agar hon), aur promotional emails ke liye unsubscribe link (CAN-SPAM compliance).

SendGrid ko send karo

POST https://api.sendgrid.com/v3/mail/send with {personalizations: [{to: [{email: '[user]@example.com'}]}], from: {email: 'noreply@company.com', name: 'Company Name'}, subject: 'Order ORD456 confirmed', content: [{type: 'text/html', value: '<html>...'}]}. SendGrid response: 202 Accepted {id: 'msg_abc123'} — async hai, delivered ka matlab nahi hai.

Status update karo

UPDATE notifications SET status='SENT', sent_at=now() WHERE notification_id='NOTIF789', aur INSERT INTO delivery_status (delivery_id, notification_id: 'NOTIF789', channel: 'EMAIL', provider: 'SendGrid', provider_message_id: 'msg_abc123', status: 'SENT', sent_at: now()).

Webhooks — delivery confirmation

SendGrid webhook bhejta hai: POST /webhooks/sendgrid {event: 'delivered', sg_message_id: 'msg_abc123', timestamp}. Event types: delivered (inbox pahuncha), opened (1px image se track hota hai), clicked (link click), bounced (invalid address), spam (spam mark hua). Update: UPDATE delivery_status SET status='DELIVERED', delivered_at=now() WHERE provider_message_id='msg_abc123'.

LLD Step 5 — SMS Delivery (Twilio / MSG91)

SMS chhota hota hai, lekin uske apne rules hain: 160 characters ki limit, opt-out instructions, aur carrier-level statuses.

SMS Svc Provider — format karo

Message format karo — 160 characters ki limit single SMS ke liye; lamba message split ho jata hai. Opt-out instructions add karo: 'Reply STOP to unsubscribe' (TCPA compliance).

LLD Step 6 — Push Notification (FCM / APNS)

Push me ek khaas baat hai — ek user ke kayi devices hote hain, aur notification sab par jati hai (fanout). Aur token kharab ho jaye to retry nahi, token delete karo.

Device tokens fetch karo

SELECT device_tokens FROM users WHERE user_id='user123' → device_tokens: ['fcm_token_android_123', 'apns_token_ios_456'] — user ke multiple devices: phone, tablet.

FCM — Android / Web

POST https://fcm.googleapis.com/v1/projects/{project_id}/messages:send with {message: {token: 'fcm_token_android_123', notification: {title: 'Order Confirmed', body: 'Your order ORD456 has been confirmed'}, data: {order_id: 'ORD456', deep_link: 'app://orders/ORD456'}, android: {priority: 'high', notification: {sound: 'default', click_action: 'OPEN_ORDER'}}}}. FCM response: {name: 'projects/.../messages/0:1234567890'} (success).

APNS — iOS

LLD Step 7 — OTP Delivery (High Priority)

OTP sabse time-sensitive notification hai — user login screen par wait kar raha hai. Isliye OTP ke liye alag fast-track hai: dedicated service, dedicated queue, no rate limiting, <10 second delivery target.

OTP generate aur store karo

Fast-track delivery

  • notifications.critical.sms me publish karo — dedicated consumer group: 20 workers (standard ke 10 ke mukable).

LLD Step 8 — Retry Mechanism (Failed Deliveries)

Failure do tarah ki hoti hai — temporary (retry karo) aur permanent (retry mat karo). Farak samajhna hi retry design hai.

Failure scenarios

  • Provider timeout — Twilio ne 10 sec me respond nahi kiya.
  • Rate limit 429 — provider limit hit, bahut zyada requests.
  • Network error — connection refused.
  • Invalid recipient — email bounced, phone number invalid.

Retry strategy — exponential backoff

Temporary failure ho (timeout, rate limit, network error) to: 1st retry 1 min baad, 2nd retry 5 min baad, 3rd retry 15 min baad. Max 3 attempts, 30 minutes ke andar. Retry ke liye notifications.retry Kafka topic me publish karo, retry_count ke saath.

Retry consumer aur DLQ

Retry consumer notifications.retry consume karta hai. retry_count check karo: agar < 3 hai to redelivery try karo; agar >= 3 hai to DLQ (Dead Letter Queue) me daalo — notifications.dlq — manual investigation ke liye. Persistent failures par ops team ko alert karo.

Permanent failures — retry mat karo

  • Invalid recipient — email ke liye 550 User not found, SMS ke liye invalid phone number.
  • Unsubscribed user — user ne opt-out kiya hai, preference honor karo.
  • Token expired — APNS 410 Gone, device ne app uninstall kar diya.
  • Mark karo: UPDATE delivery_status SET status='FAILED', error_message='Invalid email address'.

Database Schema — 5 tables + Redis + Kafka topics

5 tables, Redis ke 4 key patterns, aur 6 Kafka topics. Har table ka purpose ek line me samjho — interview me schema likhte waqt columns ke saath indexes bhi bolo.

Notifications (main table)

  • notification_id — uuid PRIMARY KEY (poore system me unique identifier).
  • user_id / recipient_id — uuid (recipient, position tracking ke liye).
  • external_user_id — varchar(255) (client ka user ID, jaise Amazon customer ID).
  • template_id — uuid FK → Templates.
  • channel — enum (EMAIL, SMS, PUSH, INAPP).
  • payload — jsonb (rendered content: {subject, body, to, variables}).
  • status — enum (PENDING, SCHEDULED, SENT, DELIVERED, FAILED, CANCELLED).
  • priority — enum (critical/high, normal, low).
  • scheduled_at — timestamptz (nullable, scheduled notifications ke liye).
  • created_at — timestamptz. metadata — jsonb (campaign_id, tags).
  • Indexes: INDEX on (user_id, created_at), INDEX on (status, scheduled_at), INDEX on (template_id).

Notifications_outbox (transactional outbox pattern)

  • outbox_id — uuid PRIMARY KEY. notification_id — uuid FK → Notifications.
  • event_type — varchar(50) (jaise 'notification.created'). payload — jsonb (Kafka ke liye notification details).
  • published — boolean DEFAULT false (CDC polling isi ko check karta hai). published_at — timestamptz (nullable).
  • Purpose: at-least-once delivery ensure karta hai — agar DB commit succeed hua, to message eventually Kafka me publish hoga.
  • CDC/Publisher: WHERE published=false poll karta hai, Kafka me publish karta hai, published=true mark karta hai.

Templates — immutable versioning

  • Composite PK: (template_id, version) — immutable versioning.
  • template_id — uuid (saare versions me same ID). version — int (1 se shuru, update par increment).
  • name — varchar(255) (jaise 'Order Confirmation Email'). channel — enum (EMAIL, SMS, PUSH, INAPP).

  • variables — jsonb (required variables ki array: ['name', 'order_id']). is_active — boolean (sirf active templates use ho sakte hain).
  • Purpose: immutable versions — update par naya version banao (kabhi existing modify mat karo). Fayde: audit trail (exact content pata rahega jo bheja tha), A/B testing (50% v1, 50% v2), rollback (purana version dobara activate karo).

User_preferences (UserPref DB)

  • Enforcement: bhejne se pehle check karo — email:false ho to email channel skip; promotional:false ho to promo notifications skip.

  • delivery_id — uuid PRIMARY KEY. notification_id — uuid FK → Notifications (INDEXED).
  • channel — enum. provider — varchar(50) (SendGrid, Twilio, FCM, APNS).
  • provider_message_id — varchar(255) (provider ka external ID, jaise Twilio SID). provider_response — jsonb (debugging ke liye full response).

  • notifications.promotional.{channel} — marketing emails, newsletters, campaigns; 30 min SLA, 5–10 workers (rate limited).
  • notifications.bulk.{channel} — batch campaigns (100K+ recipients); low priority, rate limited.
  • notifications.retry — failed notifications, exponential backoff (1min, 5min, 15min).
  • user.preference — user preference update events; User Pref Consumer consume karke cache update karta hai.

Scaling & Optimization — 12 techniques

1M+ notifications/min handle karne ke liye 12 techniques. Har technique ek problem ka jawab hai — interview me technique ke saath problem aur number dono bolo.

  • Technique 1 — Transactional Outbox pattern: at-least-once delivery ensure karta hai (DB + Kafka write atomic), lost notifications rokta hai; CDC outbox poll karta hai → Kafka me publish karta hai → published mark karta hai.
  • Technique 2 — Prioritized Kafka topics: 4 priority levels (critical/standard/promotional/bulk); critical OTP <10s me process, promotional 30 min SLA; worker allocation 20/30/10/5 (critical/standard/promo/bulk).
  • Technique 3 — Rate limiting with token bucket: Redis atomic Lua script (tokens >= 1 check karo → DECR → aage badho); provider limits: Twilio 100 SMS/sec, SendGrid 50 email/sec; providers overwhelm nahi hote, Kafka ko backpressure milta hai.
  • Technique 4 — Template caching: Redis cache (template:{id}:{version}, 1 hour TTL), 95% hit rate; immutable versioning (update par naya version, existing kabhi modify nahi), A/B testing + rollback enable karta hai.
  • Technique 5 — User preference caching: Redis cache (user_pref:{userId}, 24 hour TTL); bhejne se pehle check karo (email:false → email skip); preference change par Kafka consumer cache update karta hai.
  • Technique 6 — Provider failover: multi-provider strategy (primary: SendGrid, fallback: Amazon SES for email); SendGrid fail ho ya rate limited ho to Amazon SES par route karo; circuit breaker pattern (failure rate >50% ho to circuit open karo, fallback use karo).
  • Technique 7 — Idempotent consumers: bhejne se pehle delivery_status check karo (exists → skip); Kafka at-least-once delivery duplicates bhej sakta hai; duplicate emails/SMS rokta hai.
  • Technique 8 — Database partitioning: Notifications table created_at se partition (monthly: notifications_2026_01, notifications_2026_02), delivery_status sent_at se partition; purani partitions S3 me archive (6 month retention).
  • Technique 9 — Batch processing for bulk notifications: bulk campaigns (100K+ recipients): notifications table me batch insert (1000 records ek baar me), SendGrid bulk API (1000 emails per call vs 1 email per call) — API calls 1000× kam.
  • Technique 10 — Kafka consumer auto-scaling: lag ke basis par auto-scale (lag > 1000 messages ho to consumer instances badhao); 100 partitions matlab 100 parallel consumers; throughput linearly scale hota hai.
  • Technique 11 — Webhook processing: async webhook handling (SendGrid/Twilio webhooks → delivery_status update); provider response ko block mat karo (turant 200 OK do, baad me process karo); batched DB updates (100 records ek saath update karo).
  • Technique 12 — Reporting aggregation: real-time: Redis counters (INCR sent_count:{date}, HINCRBY stats:{template_id} delivered 1); batch: hourly aggregation (Spark/Flink): SELECT template_id, COUNT(*) FROM delivery_status GROUP BY template_id; InfluxDB/BigQuery me store karo dashboards ke liye.

Common Interview Questions — 3 bade sawaal, poore jawab

Lesson ke 3 main interview questions — inke jawab lambe hain kyunki inme poora system chhupa hai. Inhe ratna nahi hai, samajhna hai: har jawab ek kahani hai — problem → solution → failure handling → result.

Q1. Koi notification lost na ho — at-least-once delivery guarantee kaise implement karoge?

(1) Dual-write problem: naive approach — pehle DB me INSERT, phir Kafka me publish. Dikkat: Kafka succeed + DB fail → notification lost (DB me record hi nahi); DB succeed + Kafka fail → notification atak gayi (kabhi bhejegi nahi). Network failures aur service crashes se inconsistency hoti hai.

(2) Outbox solution: single transaction — BEGIN TRANSACTION, INSERT INTO notifications (… status: 'PENDING' …), INSERT INTO notifications_outbox (… published: false …), COMMIT (atomic — dono succeed ya dono fail).

(3) CDC/Publisher: outbox poll karta hai — SELECT * FROM notifications_outbox WHERE published=false ORDER BY created_at LIMIT 1000. Har record ke liye topic priority + channel se tay hota hai (high + email → 'notifications.critical.email', normal + sms → 'notifications.standard.sms'). Publish karo; success ho to published=true mark karo; Kafka fail ho to published false rehta hai, agle poll (har 100ms) me retry. Guarantee: DB COMMIT succeed hua → message outbox me hai → eventually publish hoga.

(4) At-least-once semantics: Outbox → Kafka: at-least-once (CDC crash ho jaye Kafka success ke baad lekin published mark karne se pehle, to dobara publish hoga). Kafka → Consumer: at-least-once (consumer restart par Kafka redeliver kar sakta hai). Idempotency: consumer delivery_status check karta hai — SELECT COUNT(*) WHERE notification_id={id} AND channel={channel}, exists ho to skip.

(5) Exactly-once = at-least-once + idempotency: Outbox ensure karta hai message kabhi lost nahi hoga; idempotent consumers ensure karte hain message ek hi baar process hoga. Result: user ko notification exactly once milti hai, failures/retries ke bawjood.

(6) Failure handling: CDC Publisher crash → restart, dobara poll, unsent republish. Kafka partition leader fail → Kafka naya leader elect karta hai, publisher automatically retry karta hai. Consumer crash → Kafka message doosre consumer ko redeliver karta hai, idempotency check duplicate send rokta hai.

(7) Production example: user order karta hai → Order Service Notification API call karta hai → Outbox se order confirmation email DB me persist hoti hai → CDC 100ms me Kafka me bhejta hai → Email consumer 5 sec me SendGrid se deliver karta hai → koi bhi component crash ho jaye, notification eventually bhej di jati hai. Result: zero notification loss.

Q2. Millions notifications bhejte waqt rate limiting kaise handle karoge — providers overwhelm na hon?

(1) Provider limits: Twilio SMS 100 messages/sec per account; SendGrid Email 50 emails/sec (free tier), 10K/sec (paid); FCM Push 10K messages/sec; APNS ka documented limit nahi hai, best practice <5K/sec.

(2) Token Bucket algorithm: bucket me tokens hote hain (jaise 100 tokens); har send 1 token khata hai; tokens fixed rate se refill hote hain (100 tokens/sec); bucket khaali ho to refill ka wait karo.

(3) Redis implementation: bucket key rate_limit:email:sendgrid, capacity 100 tokens (max burst), refill rate 100 tokens/sec (SendGrid limit se match). Atomic Lua script (thread-safety ke liye): key lo, capacity aur refill rate lo, tokens = GET key ya capacity; agar tokens >= 1 ho to DECR karo, return 1 (proceed); warna return 0 (rate limited, wait). 10 sec idle ke baad bucket reset (EXPIRE key 10).

(4) Consumer flow: consumer Kafka se notification leta hai; bhejne se pehle rate limit check karta hai — redis.eval(lua_script, 'rate_limit:email:sendgrid', 100, 100). Result 1 ho to SendGrid se bhejo; 0 ho to 100ms sleep karke retry karo (busy wait) YA Kafka me wapas push karo (behtar — doosre consumers doosre messages process kar sakte hain).

(5) Backpressure to Kafka: saare consumers rate limited ho jayen to slow ho jate hain; Kafka messages buffer karta hai (millions ki capacity); lag badhta hai (monitoring me dikhta hai); lag > 1000 ho to consumers badhao (lekin provider limit ke upar nahi ja sakte); provider limit bottleneck hai to queue badhegi, delivery eventually hogi jab capacity milegi.

(6) Multi-provider strategy: primary SendGrid (50 emails/sec) + fallback Amazon SES (50 emails/sec) = total 100 emails/sec. Load balancing: round-robin ya weighted (SendGrid 70%, SES 30%). SendGrid rate limited ho to SES par route karo (circuit breaker).

(7) Priority handling: critical notifications (OTP) rate limiter bypass karte hain (wait nahi kar sakte, time-sensitive) — ya dedicated rate bucket (critical_rate_limit:sms:twilio, higher limit). Standard/promotional rate limit ke under aate hain (delay acceptable).

(8) Batching optimization: SendGrid bulk API — 1000 emails ek API call me (1 email per call ke bajaye). Effective rate: 50 API calls/sec × 1000 emails/call = 50K emails/sec. API overhead kam, throughput 1000× zyada.

(9) Monitoring: track karo — tokens available (0 par frequently nahi aana chahiye), rate limit events (kitni baar consumers wait karte hain), provider response times (slowdown detect karo). Alert: rate limit 10% se zyada time hit ho to capacity badhao (provider tier upgrade, fallback add karo).

Q3. Complete notification flow — creation se delivery tak, saare state transitions aur failure handling ke saath

(1) Trigger: user order karta hai; Order Service call karta hai — POST /api/v1/notifications {templateId: 'order_confirmation', recipientId: 'user123', variables: {name: '[Name]', order_id: 'ORD456', amount: '$49.99'}, channels: ['email', 'push'], priority: 'normal'}.

(2) Validation: request authenticate karo (API key/JWT); template fetch karo (SELECT * FROM templates WHERE template_id='order_confirmation' AND is_active=true); variables check karo ({name, order_id, amount} present hain, warna 400 error); preferences fetch karo (Redis GET user_pref:user123 → email true, push true, transactional true — order confirmation transactional hai, isliye allowed).

(3) Render: subject: 'Order ORD456 confirmed', body: 'Hi [Name], your order ORD456 for $49.99 has been confirmed...'; notification_id generate karo: 'NOTIF789'.

(4) Transactional write (Outbox): BEGIN TRANSACTION → INSERT notifications (status: 'PENDING') → INSERT notifications_outbox (published: false) → COMMIT. Response: 200 OK {notificationId: 'NOTIF789', status: 'PENDING'}.

(5) CDC polling: har 100ms poll — SELECT * FROM notifications_outbox WHERE published=false; Kafka me publish karo (notifications.standard.email, key: 'NOTIF789'); published=true mark karo.

(6) Email Consumer: notifications.standard.email subscribe karta hai; message milta hai; idempotency check (SELECT COUNT(*) FROM delivery_status WHERE notification_id='NOTIF789' AND channel='EMAIL' — 0 ho to aage badho); rate limit check (token bucket, tokens >= 1 ho to DECR); SendGrid POST karo; response: 202 Accepted {id: 'msg_sg123'}.

(7) Status update: UPDATE notifications SET status='SENT'; delivery_status me INSERT karo (provider: 'SendGrid', provider_message_id: 'msg_sg123', status: 'SENT').

(8) SendGrid webhook (async): kuch minute baad POST /webhooks/sendgrid {event: 'delivered', sg_message_id: 'msg_sg123'}; handler update karta hai — delivery_status DELIVERED, notifications DELIVERED.

(9) Push notification (parallel): channel='PUSH' ke liye same flow; FCM se bhejo; email aur push independent hain (ek fail ho to doosra phir bhi ja sakta hai).

(10) Failure — temporary: SendGrid timeout (10 sec no response) → consumer exception pakadta hai → notifications.retry me publish karta hai (retry_count: 1, scheduled_at: now() + 1 min) → retry consumer 1 min wait karke dobara try karta hai → phir fail ho to retry_count: 2, +5 min (exponential backoff) → max 3 retries → sab fail ho to DLQ (notifications.dlq), ops team ko alert.

(11) Failure — permanent: email bounce (invalid address) → SendGrid webhook {event: 'bounce', reason: 'Invalid email'} → delivery_status FAILED, notifications FAILED → retry mat karo (permanent failure) → optionally sender (Order Service) ko batao ki email fail hui.

(12) State transitions: PENDING (created, outbox me) → Kafka me published → SENT (provider ko mil gaya, confirmation ka wait) → DELIVERED (provider ne recipient tak delivery confirm ki) → FAILED (permanent failure, retry nahi) → CANCELLED (bhejne se pehle user ne cancel kiya).

Result: reliable delivery with state tracking, temporary failures ke liye retry, duplicates rokne ke liye idempotency, final delivery confirm karne ke liye webhooks, multi-channel support, complete audit trail.

Current-era interviews me notification system se poochhe jaane wale sabse kaam ke 36 sawaal — har jawab wahi hai jo is lesson ke sections me detail me samjhaya gaya hai. Kisi bhi sawaal par click karke jawab kholo.

Q01 Notification system kya hota hai, aur iski zaroorat kyun padti hai?
Notification system wo backend hai jo app se user tak messages pahunchata hai — OTP, order updates, alerts, marketing — chaar channels (email, SMS, push, in-app) par. Zaroorat isliye padti hai kyunki scale par (1M+ notifications/min) direct API calls se kaam nahi chalta: async queue, retry, rate limiting aur delivery tracking chahiye hoti hai, warna notifications kho jayengi ya provider block kar dega.
Q02 At-least-once, at-most-once aur exactly-once delivery me kya farak hai?
At-most-once matlab message zyada se zyada ek baar jayega — kho sakta hai, duplicate nahi hoga. At-least-once matlab message kam se kam ek baar jayega — khoega nahi, lekin duplicate aa sakta hai. Exactly-once matlab bilkul ek baar. Notification system me at-least-once + idempotent consumers use karte hain — Outbox se loss rokte hain, idempotency check se duplicate rokte hain — aur user ko effectively exactly-once milta hai.
Q03 Transactional Outbox pattern kya hai?
Ek pattern jisme notification aur uska outbox record ek hi database transaction me likhe jate hain: BEGIN TRANSACTION → INSERT notifications + INSERT notifications_outbox → COMMIT. Phir ek alag CDC/Publisher service outbox ko poll karke (published=false) messages Kafka me publish karta hai. Isse dual-write problem khatam hoti hai — DB commit succeed hua to message eventually publish hoga hi.
Q04 Dual-write problem kya hai?
Jab do systems ko alag-alag update karna ho — jaise pehle DB me INSERT, phir Kafka me publish — to beech me crash ho jaye to inconsistency hoti hai: Kafka succeed + DB fail → notification lost; DB succeed + Kafka fail → notification atak gayi. Outbox pattern dono writes ko ek transaction me bandhkar is problem ko solve karta hai.
Q05 CDC / Publisher service outbox pattern me kya karta hai?
CDC (Change Data Capture) / Publisher service outbox table ko har 100ms poll karta hai: SELECT * FROM notifications_outbox WHERE published=false ORDER BY created_at LIMIT 1000. Har record ke liye priority + channel se Kafka topic tay karke publish karta hai, phir published=true mark karta hai. Kafka fail ho to published false rehta hai aur agle poll me retry hota hai — isiliye at-least-once guarantee milti hai.
Q06 Kafka topics ko priority ke hisaab se kyun baanta gaya hai?
Kyunki har notification ki urgency alag hai: OTP ko 10 second me pahunchna hai, order confirmation ko 5 minute chalenge, marketing email ko 30 minute bhi chalenge. Alag topics (critical/standard/promotional/bulk) se har priority ko alag consumer group aur alag worker count milta hai — critical ko 20 workers, promotional ko 5–10. Isse ek bulk campaign OTP ko block nahi kar sakta.
Q07 Critical, standard, promotional aur bulk topics ki SLA kya hai?
Critical (OTP, security alerts): immediately, dedicated consumers, <10 sec delivery target. Standard (order confirmations, shipping updates): 5 min SLA, 20–30 workers. Promotional (marketing emails, newsletters): 30 min SLA, 5–10 workers, rate limited. Bulk (batch campaigns 100K+ recipients): low priority, rate limited. Retry topic alag hai: notifications.retry, exponential backoff (1/5/15 min) ke saath.
Q08 Token bucket algorithm kaise kaam karta hai?
Bucket me tokens hote hain — jaise 100 tokens. Har send 1 token khata hai. Tokens fixed rate se refill hote hain — jaise 100 tokens/sec. Bucket khaali ho to request ko wait karna padta hai. Isse burst bhi handle hota hai (bucket full ho to 100 sends ek saath) aur long-term rate bhi limit me rehta hai (100/sec se zyada nahi). Redis me bucket key hoti hai rate_limit:{channel}:{provider}.
Q09 Rate limiting me Redis Lua script kyun use hoti hai?
Kyunki token check aur DECR dono ek hi atomic operation me hone chahiye. Agar do consumers ek saath check karein aur dono ko token dikhe, to dono bhej denge — limit cross ho jayegi. Lua script Redis me atomically chalti hai: tokens >= 1 check karo → DECR karo → return 1 (proceed), warna return 0 (rate limited). Isse race condition khatam hoti hai.
Q10 Idempotency kya hai, aur consumer me kaise implement karte ho?
Idempotency matlab ek hi operation dobara karne par bhi result same rahe — user ko duplicate email na jaye. Implement: bhejne se pehle delivery_status check karo — SELECT COUNT(*) FROM delivery_status WHERE notification_id={id} AND channel={channel}. Agar record mil jaye to skip karo. Kafka at-least-once delivery deta hai, isliye duplicate message aana normal hai; idempotency check use rokta hai.
Q11 Delivery status ke states kya hain, aur transitions kaise hote hain?
States: PENDING (create hui, outbox me), SCHEDULED (future ke liye schedule), SENT (provider ko mil gayi, confirmation ka wait), DELIVERED (provider ne recipient tak delivery confirm ki), FAILED (permanent failure, retry nahi), CANCELLED (bhejne se pehle cancel). Flow: PENDING → Kafka publish → SENT → webhook se DELIVERED ya FAILED. Bounce ya invalid recipient par seedha FAILED.
Q12 Webhooks kyun chahiye? Provider ka 202 Accepted ka matlab kya hai?
SendGrid ka 202 Accepted matlab sirf ye hai ki usne tumhara request accept kar liya — delivered ka matlab nahi hai. Asli delivery status webhook se pata chalta hai: SendGrid POST /webhooks/sendgrid bhejta hai — event delivered/opened/clicked/bounced/spam. Webhook handler delivery_status update karta hai. Isi se open rate aur click rate bhi measure hote hain.
Q13 OTP delivery fast-track kyun hai, aur kaise implement hoti hai?
Kyunki user login screen par OTP ka wait kar raha hai — 10 second se zyada delay ho to user pareshan hota hai. Implement: priority 'critical' rakho, notifications.critical.sms topic me publish karo, dedicated consumer group (20 workers vs standard ke 10), OTP par rate limiting mat lagao, delivery target <10 seconds rakho. OTP Redis me 300 sec TTL ke saath store hota hai.
Q14 OTP ko Redis me kyun store karte hain, TTL kitna hota hai?
OTP ko fast verify karna hota hai — Redis in-memory hai, isliye GET millisecond me milta hai. Key hoti hai otp:{userId}:{purpose}, value 6-digit code, TTL 300 seconds (5 minute). 5 minute baad code expire — user ko resend karna padta hai. DB me store karna slow hota aur expiry ke liye alag cleanup chahiye hota.
Q15 Retry me exponential backoff kyun use karte hain, fixed delay kyun nahi?
Fixed delay se problem ye hai ki agar provider down hai to saare retries ek saath dobara aakar use aur daba denge (thundering herd). Exponential backoff (1 min → 5 min → 15 min) se load dheere-dheere wapas aata hai aur provider ko recover karne ka time milta hai. Max 3 attempts, 30 minute ke andar — uske baad DLQ me daal do.
Q16 DLQ (Dead Letter Queue) kya hai, kab use hoti hai?
DLQ wo Kafka topic hai (notifications.dlq) jahan wo messages jate hain jo max retries (3) ke baad bhi deliver nahi hue. Ye messages manual investigation ke liye rakhe jate hain — ops team dekhti hai ki problem kya thi (provider down tha? data galat tha?). DLQ se messages kabhi delete nahi hote bina dekhe — warna failure ka pata hi nahi chalega.
Q17 Temporary aur permanent failure me kya farak hai? Examples do.
Temporary failure wo hai jo retry se theek ho sakti hai: provider timeout (10 sec no response), rate limit 429, network error (connection refused). Permanent failure wo hai jo retry se kabhi theek nahi hogi: invalid recipient (550 User not found, invalid phone number), unsubscribed user (opt-out), token expired (APNS 410 Gone). Temporary ko exponential backoff se retry karo; permanent ko FAILED mark karke chhodo.
Q18 Template versioning immutable kyun hai?
Kyunki jab user ko email gaya, to baad me pata hona chahiye ki exact kaunsa content gaya tha — audit trail ke liye. Agar template modify kar di jaye to purana content kho jayega. Isliye update par naya version banta hai (composite PK: template_id + version). Fayde: audit trail, A/B testing (50% users ko v1, 50% ko v2), aur rollback (purana version dobara activate karo).
Q19 User preferences check karna mandatory kyun hai?
Teen wajah: pehli, user experience — jisne email band kiya use email bhejoge to wo spam mark karega ya app uninstall karega. Doosri, legal compliance — GDPR, CAN-SPAM (promotional email me unsubscribe link mandatory), TCPA (SMS ke liye opt-in mandatory). Teesri, cost — bhejega hi kyun jo user ne mana kiya? Preferences Redis me 24h TTL ke saath cache karte hain, aur bhejne se pehle har baar check karte hain.
Q20 DND (Do Not Disturb) mode kya hai?
DND ek user preference hai — do_not_disturb: true ho to user ko koi bhi notification nahi bheji jati, chahe channel on ho ya type allowed ho. Ye raat ke time ya focus hours ke liye hota hai. Enforcement bhejne se pehle hoti hai: DND check sabse pehle, phir channel check, phir type check.
Q21 FCM aur APNS me kya farak hai?
FCM (Firebase Cloud Messaging) Android aur Web ke liye hai — POST https://fcm.googleapis.com/v1/projects/{project_id}/messages:send, token-based, data payload + notification payload dono bhej sakte ho. APNS (Apple Push Notification Service) iOS ke liye hai — HTTP/2 par POST https://api.push.apple.com/3/device/{token}, apns-topic aur apns-priority headers chahiye. Dono ka error handling alag hai: APNS 410 Gone matlab token invalid hai.
Q22 APNS 410 Gone ka matlab kya hai, aur kya karna chahiye?
410 Gone matlab device ne app uninstall kar diya hai ya token ab valid nahi hai. Is par retry mat karo — permanent failure hai. Sahi action: token ko user ke device_tokens array se remove karo (UPDATE users SET device_tokens = array_remove(...)). Agar retry karoge to har baar fail hoga aur resources waste honge.
Q23 Multi-device fanout kya hai?
Ek user ke kayi devices hote hain — Android phone, iOS tablet, web browser. Push notification bhejte waqt har device token par alag send hota hai — ek hi notification 3 devices par jati hai. Har device ke liye delivery_status me alag record banta hai (FCM Android, APNS iOS, FCM Web) taaki har device ki delivery alag se track ho sake.
Q24 SendGrid bulk API se throughput 1000x kaise badhta hai?
Normal API se ek call me ek email jata hai — 50 calls/sec matlab 50 emails/sec. Bulk API se ek call me 1000 emails jate hain — 50 calls/sec × 1000 emails/call = 50,000 emails/sec. API calls 1000× kam ho jati hain, isliye throughput 1000× badhta hai. Bulk campaigns (100K+ recipients) ke liye ye mandatory hai — saath me DB me bhi batch insert karte hain (1000 records ek baar me).
Q25 Provider failover aur circuit breaker kaise kaam karta hai?
Multi-provider strategy: primary SendGrid, fallback Amazon SES (email ke liye). Agar SendGrid fail ho jaye ya rate limited ho jaye to traffic SES par route karo. Circuit breaker pattern: failure rate >50% ho to circuit OPEN kar do — matlab primary ko calls bhejna band karo, seedha fallback use karo. Circuit band hone par primary ko phir se try karte hain (half-open state) — theek ho gaya to wapas primary par.
Q26 Bulk notifications (100K+ recipients) kaise handle karte ho?
Teen cheezein: pehli, notifications table me batch insert — 1000 records ek baar me, ek-ek karke nahi. Doosri, SendGrid bulk API — 1000 emails per call, API calls 1000× kam. Teesri, notifications.bulk.{channel} topic — low priority, rate limited, taaki bulk campaign critical OTP ko block na kare. Bulk ko alag consumer group milta hai.
Q27 Database partitioning kyun karte hain? Monthly partitions ka matlab?
Notifications table har din lakhon rows badhti hai — ek hi table me saal bhar ka data query karna slow ho jayega. Isliye created_at se monthly partition karte hain: notifications_2026_01, notifications_2026_02, aise. Query sirf relevant partition me jati hai, isliye fast rehti hai. Purani partitions (6 month se purani) S3 me archive kar dete hain — hot database halki rehti hai.
Q28 Kafka consumer auto-scaling kis basis par hoti hai?
Lag ke basis par — lag matlab Kafka me kitne messages consume hone ke wait me hain. Agar lag > 1000 messages ho jaye to consumer instances badhao. 100 partitions hone ka matlab hai 100 parallel consumers tak scale kar sakte ho — throughput linearly badhta hai. Lekin yaad rakho: provider rate limit ke upar nahi ja sakte, isliye lag kabhi-kabhi capacity ki wajah se badhega, consumers badhane se nahi ghatega.
Q29 Backpressure kya hai, aur Kafka isme kya role nibhata hai?
Backpressure matlab jab downstream (provider) slow ho to upstream (consumers) bhi slow ho jayein, system crash na ho. Is system me: provider rate limited ho to consumer slow ho jata hai (sleep/retry), aur Kafka messages ko buffer kar leta hai — millions of messages ki capacity hai. Message lag badhta hai jo monitoring me dikhta hai. Bina Kafka ke, rate limit par requests fail ho jayengi ya memory bhar jayegi.
Q30 Reporting kaise hoti hai — real-time vs batch aggregation?
Real-time: Redis counters — INCR sent_count:{date} aur HINCRBY stats:{template_id} delivered 1 — har send/deliver par counter badhta hai, dashboard turant update hota hai. Batch: hourly aggregation Spark/Flink se — SELECT template_id, COUNT(*) FROM delivery_status GROUP BY template_id — aur result InfluxDB/BigQuery me store hota hai dashboards ke liye. Real-time approximate hota hai, batch accurate.
Q31 Scheduled notifications kaise implement karte hain?
Notification create karte waqt scheduled_at field me future time daal do aur status SCHEDULED rakho. Ek scheduler (ya Kafka delayed topic) scheduled_at aane par notification ko normal flow me daal deta hai — phir wahi outbox → Kafka → consumer flow chalta hai. Index on (status, scheduled_at) se due notifications fast milti hain.
Q32 Template me koi required variable missing ho to kya hota hai?
Notification Svc variables validate karta hai — saare required variables (jaise name, order_id) present hone chahiye. Agar koi missing hai to request wahin fail hoti hai: 400 'Missing variable: name' return hota hai, aur notification create hi nahi hoti. Isse adhoora email user tak kabhi nahi pahunchta.
Q33 API Gateway par kya-kya validation hoti hai?
Teen cheezein: (1) Authentication & Authorization — JWT token ya API key valid hai ya nahi. (2) Rate limiting — 100 req/min per client, zyada aaye to 429. (3) Routing — request ko Notification Svc tak pahunchana. Ye gateway-level rate limit provider-level rate limit se alag hai — pehla client ko control karta hai, doosra provider ko bachata hai.
Q34 CAP theorem ke hisaab se notification system me availability consistency se upar kyun hai?
Kyunki notification ka status thoda late update ho jaye to koi nuksan nahi hai — user ko farak nahi padta ki status 2 second late DELIVERED hua. Lekin agar system hi down ho jaye to OTP nahi pahunchega aur user login nahi kar payega. Isliye availability >> consistency: eventual consistency acceptable hai delivery status ke liye, downtime acceptable nahi hai.
Q35 1M notifications/min ka scale handle karne ke liye kya-kya chahiye?
Chaaron pillars: (1) Async architecture — Kafka prioritized topics, sync part sirf validation + DB write tak. (2) At-least-once + idempotency — Outbox pattern aur delivery_status check. (3) Rate limiting + backpressure — token bucket, multi-provider failover, Kafka buffer. (4) Caching + partitioning — Redis (preferences 24h, templates 1h, 95% hit rate), monthly DB partitions, consumer auto-scaling (lag > 1000 → scale). Inme se ek bhi missing ho to 1M/min par system toot jayega.
Q36 In-app notifications email/SMS se kaise alag hain?
In-app notifications app ke andar dikhti hain — user ko app kholna padta hai. Inke liye koi external provider nahi chahiye (SendGrid/Twilio jaise) — app ka apna notification inbox/table hi kaafi hai. Cost lagbhag zero hai, aur delivery guaranteed hai (koi provider failure nahi). Lekin user app na khole to notification dekhega hi nahi — isliye important cheezon (OTP) ke liye in-app kaam nahi karta, SMS/push chahiye.
