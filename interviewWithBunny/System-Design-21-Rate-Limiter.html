01Shuruaat

Functional Requirements

Rate limiter ka kaam ek line me: har client kitne requests bhej sakta hai, ek time window ke andar — ye limit karo. Client matlab User ID, API Key ya IP — teeno se pehchan sakte ho.

5 Functional Requirements

  • Feature 1 — Request limit: Ek client (User ID / API Key / IP ke hisaab se) ek time window me kitne requests kar sakta hai, ye limit karo. Jaise 100 requests per minute.
  • Feature 2 — Runtime configurable rules: Rate limit rules ko runtime par badla ja sake — bina redeploy kiye. Admin limit 100 se 200 kare to turant lagu ho, naya deploy nahi chahiye.
  • Feature 3 — 429 response: Limit cross ho jaaye to HTTP 429 Too Many Requests return karo, saath me Retry-After header — taaki client ko pata chale kab retry kare.
  • Feature 4 — Tier-based limits: Client tier ke hisaab se alag limit — Free: 100 req/min, Premium: 1000 req/min. Paid user ko zyada quota, free user ko kam.
  • Feature 5 — Tier-wise alag limiter: Free/Premium ke liye granular control — har tier ke liye alag limiter, alag rules, alag tuning.

Yaad rakhne wali baat: limit sirf number nahi hai — kis par lag rahi hai (user, API key, IP, endpoint) aur kab badal sakti hai (runtime), ye bhi requirement ka hissa hai.

Non-Functional Requirements

Rate limiter har request ke raaste me khada hota hai — isliye iski speed aur scale hi iski pehchan hai. Slow limiter poori API ko slow kar dega.

Scale & Performance

RequirementValueMatlab
Scale1 Million requests per second (rps)High-traffic APIs ke liye design — 10 lakh requests har second handle karne chahiye.
CAPAvailability >> ConsistencyEventual consistency chalegi. Thoda over-limit tolerate kar sakte ho — lekin API down nahi honi chahiye.
LatencyUltra low < 5ms per requestRate limit check se har request par 5ms se kam extra latency aani chahiye — limiter bottleneck nahi ban-na chahiye.

03Shuruaat

Core Entity

System me sirf 3 core entities hain — policy (rule), client (kaun hai), aur counter (kitna use ho gaya). Baaki sab inke aas-paas banta hai.

Entity 1 — RateLimitPolicy / Rules

Ye rule batata hai ki limit kya hai. Fields:

  • rule_id — rule ki unique pehchan (uuid)
  • subject_type — limit kis par lag rahi hai: USER / API_KEY / IP
  • subject_value — specific value, jaise user ID ya global (*)
  • limit — kitne requests, jaise 100
  • window — kitne time me, jaise 60 seconds
  • endpoint — kis endpoint par, jaise * (sab) ya /api/login (specific)
  • created_at — rule kab bana

Entity 2 — Client

  • client_id — client ki unique id
  • tier — FREE / PREMIUM (is se quota decide hota hai)
  • api_key — client ki key
  • quota — rate limit, jaise Free ke liye 100
  • created_at

Entity 3 — RequestCounter

Har client, har window ke liye request count track karta hai. Ye Redis me store hota hai taaki check fast ho — database se har request par count padhna bahut slow hoga. Counter hi wo state hai jise token bucket ya sliding window algorithms update karte hain.

Teeno ka rishta: Client request bhejta hai → RateLimitPolicy batati hai uski limit kya hai → RequestCounter batata hai ab tak kitna use ho chuka hai → allow ya 429.

API Designing

Rate limiter ke APIs do tarah ke hain — admin operations (rules banao, dekho, metrics lo) aur data path (har request par check). Is lesson me admin APIs diye gaye hain; data path ka flow §06.6 me hai.

Admin Operations — Rules banane ke liye

POST /v1/admin/rules — rule banao
POST /v1/admin/rules
Body: { subjectType, subjectValue, limit, window, endpoint }

Example:
{
  "subjectType": "USER",
  "subjectValue": "user123",
  "limit": 100,
  "window": 60,
  "endpoint": "/api/users"
}

Ye endpoint naya rate limit rule banata hai. Body me paanch cheezein: kis par limit (subjectType + subjectValue), kitni limit (limit), kitne time me (window — seconds me), aur kis endpoint par (endpoint).

GET /v1/admin/rules — rules dekho (CRUD)
GET /v1/admin/rules?clientId=xyz
→ us client ke saare rate limit rules return karta hai

Ek specific client ke rules dekhne ke liye — admin debugging aur support ke liye zaroori hai. "Mera limit kya hai?" ka jawab yahi API deti hai.

GET /v1/admin/rate-limit/metrics — monitoring
GET /v1/admin/rate-limit/metrics?resource={url}
→ us resource/endpoint ki rate limiting metrics

Monitoring ke liye: kitne requests aaye, kitne allow hue, kitne 429 mile — ye metrics is API se milti hain. Alerting aur capacity planning isi par banti hai (§08, Technique 10).

05Shuruaat

High Level Design (HLD)

Poora system ek line me: Client → Load Balancer → Rate Limiter (API Gateway ke saath) → Backend Svc. Rate limiter backend se pehle khada hai — sirf allowed requests hi backend tak pahunchti hain.

Architecture — request ka rasta

  • Client: User ya service jo API call karti hai (User ID / API Key / IP ke saath).
  • Load Balancer: Traffic ko multiple Rate Limiter instances par baant-ta hai, aur health checks karta hai — kharab instance ko traffic nahi deta.
  • Rate Limiter + API Gateway: Core component. Auth check karta hai, Redis se rate limit state poochta hai, aur limit enforce karta hai — allow kare to backend ko forward, warna 429.
  • Backend Svc: Protected API services (multiple instances). In tak sirf allowed requests pahunchti hain — abuse, overload aur bot traffic yahin ruk jaata hai.

Kaun se algorithms support karte hain

System 5 algorithms support karta hai — Fixed Window Counter, Sliding Window Log, Sliding Window Counter, Token Bucket (sabse common), Leaky Bucket. In sabki detail §06 me hai. Production me Token Bucket recommend kiya gaya hai.

06.1Deep Dive — LLD

Fixed Window Counter

Sabse simple algorithm: time ko fixed windows me kaato (har 60 second), har window me count karo, window badalte hi counter zero.

Kaise kaam karta hai

Time ko fixed windows me divide karo (jaise har 60s ek window). Har window me requests count karo. Jaise hi nayi window shuru ho, counter reset ho jaata hai.

Worked example — limit 100 requests, window 10:00:00–10:00:59

TimeCountDecision
10:00:1050 requestsAllow (50 < 100)
10:00:5899 requestsAllow (99 < 100)
10:01:00Counter reset → 0Nayi window shuru

Redis implementation

Fixed Window — Redis commands
Key:    rate_limit:{user_id}:{window_start_timestamp}
Value:  request count (integer)

INCR   rate_limit:user123:1706270400   # window 1706270400 se shuru
EXPIRE rate_limit:user123:1706270400 60  # window khatam hote hi auto-delete
GET    rate_limit:user123:1706270400   # current count padho
→ count < limit  → allow
→ count >= limit → reject 429

Pros aur Cons

  • Pros: Simple, implement karna aasan; low memory — har window ke liye sirf ek counter.
  • Cons — Boundary problem: Window ke edge par spike. 99 requests 10:00:59 par + 100 requests 10:01:00 par = 199 requests sirf 2 second me — jabki limit 100/min ki spirit thi. Ye is algorithm ki sabse badi kamzori hai.

Kab use karein: Simple internal APIs jahan thoda over-limit chalega. User-facing production APIs ke liye ye akela kaafi nahi hai — isiliye Token Bucket prefer karte hain.

06.2Deep Dive — LLD

Sliding Window Log

Sabse accurate algorithm: har request ka timestamp store karo, aur hamesha pichhle N seconds ke logs gino. Ye true rolling window hai — koi boundary problem nahi.

Kaise kaam karta hai

Har request ka timestamp store karo. Nayi request aane par dekho pichhle N seconds me kitne logs hain — agar count limit se kam hai to allow karo, warna reject.

Worked example — current time 10:00:45, window 60s, limit 100

  • Stored timestamps: [10:00:05, 10:00:12, 10:00:30, ...]
  • Filter: sirf wo timestamps jo >= 10:00:45 − 60s = 09:59:45 hain
  • Count: pichhle 60s me 85 requests → 85 < 100 → allow

Redis implementation — Sorted Set (ZSET)

Sliding Window Log — Redis ZSET commands
Key:     rate_limit_log:user123
Members: request_id (ya UUID)      Scores: timestamp (Unix time, seconds)

ZADD rate_limit_log:user123 {current_timestamp} {request_id}
ZREMRANGEBYSCORE rate_limit_log:user123 0 {current_timestamp - window_size}
  # window se purane logs saaf karo
ZCOUNT rate_limit_log:user123 {current_timestamp - 60} {current_timestamp}
  # pichhle 60 sec me kitne requests → count
→ count < limit → ZADD (allow + store)
→ count >= limit → reject 429

Pros aur Cons

  • Pros: Highly accurate — true rolling window, koi boundary problem nahi, perfect precision.
  • Cons: Expensive memory — har request ka timestamp store hota hai. 100 req/min × 10 lakh users = 100M timestamps. Cleanup overhead bhi hai — har request par purane logs hatane padte hain.

Kab use karein: Low-traffic critical APIs jahan accuracy sabse important hai — jaise fraud detection. High-traffic APIs ke liye memory cost bahut zyada hai.

06.3Deep Dive — LLD

Sliding Window Counter

Fixed window aur sliding window ka hybrid: current window aur previous window ka weighted count nikalo — kitna time current window me beet gaya, us hisaab se previous window ko weight do.

Kaise kaam karta hai

Do counters rakho — current window ka aur previous window ka. Weighted count = (previous count × (1 − elapsed%)) + current count. Elapsed% matlab current window kitni beet chuki hai.

Worked example — current time 10:00:45, limit 100

ValueNumber
Previous window (09:59:00–09:59:59)80 requests
Current window (10:00:00–10:00:59)30 requests
Elapsed in current window45 seconds = 75% of 60s
Weighted count(80 × (1 − 0.75)) + 30 = (80 × 0.25) + 30 = 20 + 30 = 50
Decision50 < 100 → allow

Redis implementation

Sliding Window Counter — two keys
Two Redis keys:
  rate_limit:user123:{current_window}
  rate_limit:user123:{previous_window}

elapsed_pct   = (current_time % window_size) / window_size
weighted_count = (prev_count × (1 - elapsed_pct)) + curr_count
→ weighted_count < limit → INCR current window (allow)
→ weighted_count >= limit → reject

Pros aur Cons

  • Pros: Fixed window se zyada accurate — boundary spikes smooth ho jaate hain. Sliding log se kam memory — sirf 2 counters, saare timestamps nahi.
  • Cons: Approximation hai — 100% accurate nahi (sliding log jaisi). Thoda complex — weighted calculation karna padta hai. Aur typical API rate limiting expectation se hamesha match nahi karta.

Kab use karein: Good middle ground — lekin industry me Token Bucket zyada adopt hua hai, isliye ye kam dikhta hai.

06.4Deep Dive — LLD

Token Bucket — MOST COMMON (Recommended)

Production standard: bucket me tokens hain, steady rate se refill hote hain; har request ek token khaati hai; token hai to allow, nahi to reject. Burst naturally support karta hai.

Kaise kaam karta hai

  • Bucket me tokens hain (capacity) — jaise 100 tokens.
  • Tokens steady rate se refill hote hain — jaise 10 tokens/sec.
  • Har request ek token consume karti hai. Token available hai → allow + consume. Nahi hai → reject.

Worked example — Capacity 100, Refill 10 tokens/sec

ScenarioKya hota hai
Burst: 1 sec me 100 requestsSaare 100 tokens consume → sab allow (burst supported)
10 sec baadBucket wapas 100 tokens (10 tokens/sec × 10 sec)
Steady: 10 req/sec sustainedAllow — refill rate se match karta hai (600 tokens/min)

Redis implementation — Lua script (atomicity ke liye)

Token check + decrement ek hi atomic operation me hona chahiye — isiliye Redis Lua script use hoti hai. Alag GET + DECR race condition dega (§09.2 aur Lab L5 dekho).

Token Bucket — Redis Lua script
local key = KEYS[1]
local capacity = tonumber(ARGV[1])      -- 100
local refill_rate = tonumber(ARGV[2])   -- 10 tokens/sec
local now = tonumber(ARGV[3])           -- current timestamp
local tokens = tonumber(redis.call('HGET', key, 'tokens')) or capacity
local last_refill = tonumber(redis.call('HGET', key, 'last_refill')) or now
local elapsed = now - last_refill
local refilled = math.min(capacity, tokens + (elapsed * refill_rate))
if refilled >= 1 then
  redis.call('HSET', key, 'tokens', refilled - 1)
  redis.call('HSET', key, 'last_refill', now)
  redis.call('EXPIRE', key, 3600)
  return 1  -- allow
else
  return 0  -- reject
end

Pros aur Cons

  • Pros: Bursts naturally support karta hai (capacity = burst size). Smooth refill — window boundary par achanak reset nahi. Widely used — AWS API Gateway, Stripe API. Real systems me proven.
  • Cons: Thoda complex state management — tokens + last_refill dono track karne padte hain.
★ INTERVIEW FAVOURITE

Token Bucket production standard hai (AWS, Stripe, GitHub). Burst support (capacity 100 = 100 instant requests), smooth refill (10 tokens/sec), koi boundary problem nahi. Implementation: Redis HASH {tokens, last_refill} + Lua script — atomic check + elapsed time se refill calculation.

06.5Deep Dive — LLD

Leaky Bucket

Token Bucket ka ulta socho: requests bucket (queue) me aati hain aur fixed rate se leak hokar process hoti hain. Bucket bhar gaya to nayi requests reject.

Kaise kaam karta hai

  • Requests bucket/queue me enter karti hain.
  • Wo fixed rate se leak out hoti hain (process hoti hain) — jaise 10 req/sec.
  • Bucket full ho jaaye to nayi requests reject ho jaati hain.

Worked example — Capacity 100, Leak rate 10 req/sec

ScenarioKya hota hai
50 requests ek saath aayeSab queue me — 10 req/sec se process, 5 sec me sab done
100 requests ek saath aaye100 queue (bucket full)
101st requestRejected — bucket full hai

Redis implementation — List (queue)

Leaky Bucket — Redis LIST
LPUSH rate_limit_queue:user123 {request_id}   # queue me daalo
LLEN  rate_limit_queue:user123               # queue size dekho
→ queue_size < capacity → allow (queue the request)
→ queue_size >= capacity → reject

Background processor (fixed rate 10/sec):
RPOP rate_limit_queue:user123  → process request

Pros aur Cons

  • Pros: Smooth output traffic — fixed processing rate. Traffic shaping ke liye achha — downstream overload rokta hai.
  • Cons: Requests delay ya drop ho sakti hain — synchronous APIs ke liye ideal nahi. Complex — queue + background processor chahiye. Typical API rate limiting expectation se match nahi karta.

Kab use karein: Traffic shaping ke liye, jahan downstream ko steady rate par load dena hai. Typical API rate limiting ke liye Token Bucket behtar hai.

Token Bucket vs Leaky Bucket — ek line me: Token Bucket me request turant allow hoti hai agar token hai (burst allowed); Leaky Bucket me request queue me rukti hai aur fixed rate se process hoti hai (output smooth, lekin delay).

Production Implementation (Token Bucket + Redis + Policy DB)

Theory se production tak: Client → Load Balancer → API Gateway (Rate Limiter logic) → Rate Limiter / Policy Svc → Policy DB (rules) + Redis (token state).

Complete request flow — step by step

  1. Client: GET /api/users bhejta hai — API key ya user session ke saath.
  2. API Gateway — Auth check: API key / JWT validate karta hai. Subject nikaalta hai: user_id='user123' ya api_key='key_abc'. Phir Rate Limiter ko call karta hai: check_rate_limit(user_id, endpoint='/api/users').
  3. Rate Limiter — Policy fetch: Pehle Policy Cache (Redis) dekhta hai: GET policy:user123 → {limit: 100, window: 60, refill_rate: 10}. Cache miss ho to Policy DB query: SELECT limit, window FROM rate_limit_rules WHERE subject_value='user123' AND endpoint='/api/users'. Result cache karta hai: SET policy:user123 {limit, window, refill_rate} EX 3600 (1 hour TTL).
  4. Token bucket check (Redis Lua script): EVAL lua_script 1 'rate_limit:user123' 100 10 {current_timestamp} — return 1 (allow) ya 0 (reject).
  5. Allowed (1): Backend Svc ko forward karo, response client ko do. Rejected (0): 429 return karo, headers ke saath:
    429 Too Many Requests — headers + body
    HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1712340788
Retry-After: 30

{
  "error": "rate_limit_exceeded",
  "message": "You have exceeded 100 requests/min. Retry after 30 seconds."
}

Policy updates — Write-through cache

  • Admin rule update karta hai: PUT /v1/admin/rules/{ruleId} {limit: 200}
  • Policy Svc DB update karta hai: UPDATE rate_limit_rules SET limit=200
  • Cache invalidate: DEL policy:user123 (agli request naya limit fetch karegi) ya write-through: SET policy:user123 {limit: 200, ...} (turant update)
  • Propagation: TTL-only approach me saare Rate Limiter instances ko naya policy 1 hour (cache TTL) me milta hai; write-through + Redis pub/sub se immediately (1 sec se bhi kam me — §08 Technique 12).
⚠ WARNING

CRITICAL: Rate limit check ke liye hamesha Redis Lua script use karo. Kabhi alag GET + DECR mat karo — race condition: 2 instances dono GET karengi, dono ko 1 token dikhega, dono DECR karengi → over-limit. Lua script Redis me atomically execute hoti hai (single-threaded), isliye distributed API Gateways ke beech race nahi hoti.

Multi-Tier Rate Limiting (Free vs Premium)

Ek hi limit sab par nahi lagti — har level par alag limit, aur koi bhi ek cross ho to 429. Strictest limit jeet-ti hai.

Tier-based rules

TierLimitWindowEndpoints
Free100 req/min60s['*'] (sab)
Premium1000 req/min60s['*']
Enterprise10000 req/min60sCustom limits per endpoint

Quota per-user hai ya shared? — galatfahmi saaf karo

Rule subject_type='TIER', subject_value='PREMIUM' dekh kar lag sakta hai ki saare premium users ki shared quota hai — aisa nahi hai. Aam taur par quota per-user track hoti hai:

  • subject_type='USER', subject_value='user123' — quota is user ki hai.
  • Tier lookup: SELECT tier FROM clients WHERE user_id='user123' → 'PREMIUM'
  • Rule fetch: SELECT limit FROM rate_limit_rules WHERE tier='PREMIUM' → 1000 req/min

Multi-level limiting — saare levels ek saath

LevelLimitKis liye
Per-user100 req/minIndividual user quota
Per-IP1000 req/minSingle IP abuse rokna
Per-API-key10000 req/minAPI key quota
Per-endpoint/api/login → 10 req/minBrute force rokna
Global1M req/secCluster capacity

★ INTERVIEW FAVOURITE

Multi-tier limiting: per-user (100/min), per-IP (1000/min), per-endpoint (login: 10/min), global (1M/sec cluster capacity) — sab check karo, strictest enforce karo. Is se abuse multiple levels par rukta hai: user quota + IP-based DDoS protection + endpoint brute-force prevention.

08Scaling & Optimization

Scaling & Optimization — 12 Techniques

1 Million rps, <5ms latency, aur Redis down ho to bhi API chalti rahe — ye 12 techniques milkar production-grade system banati hain.

Technique 1 — Redis Lua scripts for atomicity

Single atomic operation (check + decrement tokens). Race conditions rokta hai — multiple requests ek saath check kar rahi hon to bhi. Multiple Redis roundtrips se faster bhi hai.

Technique 2 — Policy caching

Rules Redis me cache (1 hour TTL), 99% cache hit rate — rules rarely change karte hain. Policy DB ka load 100× kam. Updates par write-through — immediate propagation.

Technique 3 — Token Bucket algorithm

Bursts naturally support karta hai (capacity = burst size), smooth refill (koi boundary problem nahi), production-proven — AWS, Stripe, GitHub sab Token Bucket use karte hain.

Technique 4 — Distributed rate limiting

Redis cluster (master + replicas). Consistent hashing — user123 hamesha same shard par route hota hai. Synchronization: Redis atomic operations se saare API Gateway instances ke beech consistency rehti hai.

Technique 5 — Multi-tier rate limiting

Multiple levels check karo (per-user, per-IP, per-endpoint, global) — strictest limit enforce karo. Tiered quotas: FREE 100, PREMIUM 1000, ENTERPRISE 10K.

Technique 6 — Horizontal scaling of API Gateway

Stateless API Gateway instances (10–100+). Redis shared state — saare instances same Redis check karte hain. Load balancer traffic baant-ta hai, CPU/latency ke hisaab se auto-scaling.

Technique 7 — Redis optimization

TTL inactive buckets ke liye (1 hour idle ke baad auto-expire, memory bache). Pipelining — multiple Redis commands ek batch me. Connection pooling — connections reuse karo, handshake overhead se bacho.

Technique 8 — Graceful degradation

Redis down ho to: Fail open (saare requests allow karo, error log karo) ya fail closed (sab 503 se reject karo — safer, lekin availability girti hai). Circuit breaker: Redis 10 baar fail ho to 30 sec ke liye circuit open — Redis checks skip karo.

Technique 9 — Rate limit headers

X-RateLimit-Limit: 100 (total quota), X-RateLimit-Remaining: 45 (bache hue), X-RateLimit-Reset: 1712340788 (kab reset hoga), Retry-After: 30 (kitna wait karein). Ye headers client ko backoff implement karne me madad karte hain.

Technique 10 — Monitoring & alerting

Track karo: request count, rejection rate (429 responses ka %), Redis latency (p50, p99), policy cache hit rate. Alert: rejection rate > 5% ho (attack ya galat limit ka sign), Redis latency > 10ms ho (performance degradation).

Technique 11 — Dynamic limit adjustment

Load ke hisaab se limits auto-scale karo — cluster 80% capacity par ho to limits 20% kam karo. DDoS protection — spike detect ho to temporary stricter limits. Allowlist — trusted IPs limits bypass kar sakti hain.

Technique 12 — Write-through cache updates

Policy change par: UPDATE DB + SET Redis cache (dono ek transaction me), phir Redis pub/sub publish karo: PUBLISH policy_update {rule_id}. API Gateway instances subscribe karke local cache invalidate karte hain — <1 sec propagation (TTL-only approach me 1 hour lagta).

⚠ WARNING

NEVER store rate limit state locally in API Gateway memory — restart par lost ho jaayega, aur instances ke beech consistency nahi rahegi. Hamesha Redis use karo (centralized state, atomic operations). Redis down ho to circuit breaker: fail open (allow all, log) ya fail closed (reject with 503, safer).

💡 TIP

Cache policy rules in Redis (1 hour TTL, 99% hit rate). Write-through on updates: UPDATE DB + SET cache + PUBLISH Redis pub/sub → API Gateways 1 sec se bhi kam me local cache invalidate karte hain. TTL-only approach se 1 hour tak stale limit rehti — isiliye write-through zaroori hai.

Interview Q1 — 5 Algorithms Compare karo

Interview ka sabse favourite sawaal: paanchon algorithms compare karo aur production ke liye ek chuno — kyun? Poora jawab yahan hai.

(1) Fixed Window Counter

Pros: Simple (single counter per window), low memory (ek int per user), fast (single INCR). Cons: Boundary problem — 100 req 10:00:59 par + 100 req 10:01:00 par = 200 req 2 sec me. Implementation: Redis INCR + EXPIRE. Use case: Simple internal APIs, user-facing nahi.

(2) Sliding Window Log

Pros: Highly accurate (true rolling window, koi boundary issue nahi), perfect precision. Cons: Expensive memory — har request ka timestamp store hota hai (100 req/min × 1M users = 100M timestamps), cleanup overhead (har request par ZREMRANGEBYSCORE). Implementation: Redis ZSET (ZADD, ZCOUNT, ZREMRANGEBYSCORE). Use case: Low-traffic critical APIs jahan accuracy crucial hai (fraud detection).

(3) Sliding Window Counter

Pros: Fixed window se zyada accurate (boundaries smooth), log se kam memory (2 counters vs saare timestamps). Cons: Approximation (100% accurate nahi), complexity (weighted calculation). Implementation: Two counters (current + previous window), weighted sum. Use case: Good middle ground, lekin widely adopted nahi (Token Bucket preferred).

(4) Token Bucket — RECOMMENDED

Pros: Bursts naturally support karta hai (capacity = burst size — 100 token bucket 100 instant requests allow karta hai, phir refill hota hai), smooth refill (10 tokens/sec = steady 600/min), production-proven (AWS API Gateway, Stripe, GitHub), spiky traffic achhe se handle karta hai. Cons: Thoda complex (tokens + last_refill track karna). Implementation: Redis HASH (tokens, last_refill) + Lua script (atomic check + refill calculation). Use case: Production APIs (sabse common choice).

(5) Leaky Bucket

Pros: Smooth output traffic (fixed processing rate), traffic shaping ke liye achha (downstream overload rokta hai). Cons: Requests delay/drop ho sakti hain (queuing), background processor chahiye (fixed rate par leak), sync APIs ke liye typical nahi. Implementation: Redis LIST (queue) + background worker. Use case: Traffic shaping, typical API rate limiting nahi.

Production choice: Token Bucket — kyun?

  1. Bursts support karta hai: User 100 requests ek saath karna chahta hai (batch operations) — Token Bucket allow karta hai; fixed/sliding window burst ke baad reject kar deta.
  2. Smooth refill: Window boundary par achanak reset nahi — user refill rate (10/sec) par continuously requests kar sakta hai.
  3. Industry standard: AWS, Stripe, GitHub sab use karte hain — billions of requests/day par proven.
  4. Good UX: Burst + refill user ko natural lagta hai.
  5. Reasonable complexity: Redis Lua script atomicity sambhal leta hai — fixed window se zyada complex nahi.

5 sec baadBucket me 50 tokens refill (10/sec × 5 sec)

Result: Flexible (bursts support), fair (smooth refill), production-ready (proven algorithm).

Interview Q2 — Distributed Rate Limiting (Redis)

10–100+ API Gateway instances, sabko same limit enforce karni hai — bina coordination ke race condition pakki hai. Iska jawab Redis + Lua script hai.

(1) Challenge

Multiple API Gateway instances (10–100+), har ek 10K req/sec handle kar raha hai. Sabko same limit enforce karni hai (100 req/min per user). Bina coordination ke race conditions hongi — 2 instances ek saath request allow kar dengi to user ko window me 101 requests mil jaayenge.

(2) Redis as shared state

Saare API Gateway instances same Redis cluster se connect hote hain. Token state Redis me hai: rate_limit:user123 → {tokens: 95, last_refill: 1706270445}. Har rate limit check Redis ko query karta hai — centralized truth.

(3) Race condition problem — alag GET + DECR se

StepKya hota hai
Request 1 (Instance A)GET tokens → 1 token bacha, allow karo
Request 2 (Instance B)Ek saath GET tokens → use bhi 1 token dikha, allow karo
Dono DECR karte hainResult: tokens = −1 (over-limit — race condition!)

(4) Solution — Redis Lua script (atomic execution)

Distributed check — Lua script (atomic)
lua_script = local key = KEYS[1]
  local capacity = tonumber(ARGV[1])
  local refill_rate = tonumber(ARGV[2])
  local now = tonumber(ARGV[3])
  local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
  local tokens = tonumber(bucket[1]) or capacity
  local last_refill = tonumber(bucket[2]) or now
  local elapsed = now - last_refill
  local refilled = math.min(capacity, tokens + (elapsed * refill_rate))
  if refilled >= 1 then
    redis.call('HMSET', key, 'tokens', refilled - 1, 'last_refill', now)
    redis.call('EXPIRE', key, 3600)
    return 1  -- allow
  else
    return 0  -- reject
  end

-- API Gateway call:
result = redis.eval(lua_script, 1, 'rate_limit:user123', 100, 10, current_timestamp)

Atomicity: Lua script ek hi atomic operation ki tarah chalti hai — beech me koi aur command interleave nahi kar sakti. Guarantee: sirf ek instance token decrement karegi, race condition khatam.

(5) Consistency guarantees

  • Redis single-threaded execution: Commands serially process hote hain (ek baar me ek).
  • Lua scripts: Atomically execute hoti hain (all-or-nothing), Redis Cluster me bhi.
  • Result: Bina locks ke distributed consistency. CAP tradeoff: Redis ke andar CP (consistent), poore system me AP (Redis down ho to fail open for availability).

(6) Redis Cluster — horizontal scaling

  • Multiple Redis shards (master + replicas).
  • Consistent hashing: hash(user_id) → shard — user123 hamesha same shard par route hota hai.
  • Reads replicas se ho sakte hain (master ka load kam); writes (EVAL / Lua) master par hi (consistency ke liye).
  • Replication lag < 1ms — lag ke dauraan halka over-limit acceptable hai.

(7) Performance optimization

  • Connection pooling: Har API Gateway 50 Redis connections maintain karta hai (reuse, handshake se bacho).
  • Pipelining: Multiple rate limit checks batch karo (10 users ke liye 10 EVAL ek round-trip me).
  • Redis latency: p99 < 5ms — rate limiting ke liye kaafi fast, bottleneck nahi banta.
  • Local cache: Policy rules (limit, refill_rate) locally cache karo — policy ke liye Redis query nahi, sirf token state check karo.

(8) Failure handling

  • Circuit breaker: 10 consecutive Redis failures ke baad 30 sec ke liye circuit open — us dauraan fail open (saare allow, error log) ya fail closed (503 se reject).
  • Auto-recovery: 30 sec baad half-open (ek request try karo), success ho to circuit close (normal resume).
  • Monitoring: Redis errors > 1% ho to alert, latency p99 > 10ms ho to scaling issue samjho.

(9) Multi-region

Har region me Redis: us-east-1, eu-west-1, asia-south-1 (low latency). Global rate limit: regions ke across aggregate karo (complex, eventual consistency) — ya per-region limit: 100 req/min per region (simpler, thoda relaxed global limit).

Result: Strong consistency (Redis atomic Lua), horizontal scale (Redis Cluster + multiple API Gateways), low latency (< 5ms), failures gracefully handle hote hain (circuit breaker).

Interview Q3 — Complete Request Flow

Client ki request se lekar 200 ya 429 tak — poora flow, policy lookup aur token check ke saath. Ye wo flow hai jo interviewer whiteboard par banwaata hai.

(1) Client request

GET /api/users — header: Authorization: Bearer {jwt_token}. Load Balancer round-robin se ek API Gateway instance par bhejta hai.

(2) API Gateway authentication

JWT nikaalo: token parse karo, signature validate karo, user_id: 'user123' extract karo. (Ya header X-API-Key se api_key nikaalo.)

(3) Rate Limiter — subject + policy lookup (caching ke saath)

  • Subject identify karo: user_id='user123', endpoint='/api/users'.
  • Redis cache check karo: policy:user123:/api/users — cache hit ho to policy = {limit: 100, window: 60, refill_rate: 10, enforce_by: 'USER'}.
  • Cache miss ho to Policy DB query karo:
    Policy lookup — SQL
    SELECT limit, window, refill_rate, enforce_by
FROM rate_limit_rules
WHERE (subject_type='USER' AND subject_value='user123' AND endpoint='/api/users')
   OR (subject_type='USER' AND subject_value='user123' AND endpoint='*')
   OR (subject_type='TIER' AND subject_value=(
        SELECT tier FROM clients WHERE user_id='user123') AND endpoint='*')

-- Pehla matching rule lo: specific endpoint > wildcard, user > tier
-- Cache: SET policy:user123:/api/users {limit: 100, window: 60, refill_rate: 10} EX 3600

(4) Token Bucket check — Redis Lua script

  • Prepare: key = 'rate_limit:user123:/api/users', capacity = 100, refill_rate = 10, now = current Unix timestamp.
  • Execute: result = redis.eval(lua_script, 1, key, capacity, refill_rate, now)
  • Lua logic: bucket fetch karo (tokens, last_refill). Refill calculate karo: elapsed = now − last_refill (jaise 5 sec). refilled = min(100, 90 + 5×10) = min(100, 140) = 100 tokens (capacity par cap). Check: refilled >= 1 (100 >= 1 → true). Consume: tokens = 100 − 1 = 99. Update: HMSET key tokens 99 last_refill now. Return 1 (allow).

(5) Request allowed — result = 1

  • Remaining = 99 tokens. Reset time: reset = now + (capacity − remaining) / refill_rate = now + (100 − 99) / 10 = now + 0.1 sec (bucket kab full refill hoga).
  • Backend Svc ko forward karo: GET /api/users, headers add karo: X-RateLimit-Limit: 100, X-RateLimit-Remaining: 99, X-RateLimit-Reset: {reset_timestamp}.
  • Backend response: {users: [...]} — client ko 200 OK data + rate limit headers ke saath.

(6) Request rejected — tokens 0 hain

Scenario: user ne pichhle 10 sec me 100 requests kar liye, tokens = 0. Lua script: refilled = min(100, 0 + 0×10) = 0 (abhi refill nahi hua, bahut jaldi hai). Check: refilled >= 1 → false. Return 0 (reject).

(7) Return 429 Too Many Requests

429 response — poora
Status: 429 Too Many Requests
Headers:
  X-RateLimit-Limit: 100
  X-RateLimit-Remaining: 0
  X-RateLimit-Reset: 1712340788
  Retry-After: 1   # ceil((1 - 0) / 10) = 1 sec
Body (JSON):
{
  "error": "rate_limit_exceeded",
  "message": "You have exceeded 100 requests per minute. Retry after 1 second.",
  "limit": 100,
  "remaining": 0,
  "reset_at": "2024-04-05T10:01:28Z"
}

Client behavior: 429 mile → Retry-After: 1 padho → 1 sec wait karo → retry karo
→ likely succeed (1 token refill ho gaya hoga).

  • Rate limit events log karo: {user_id, endpoint, allowed: false, tokens_remaining: 0, timestamp}

  • Track karo: rejection rate (kitne % requests reject hui), per-endpoint breakdown.
  • Dashboard alert: rejection rate > 5% ho to (attack ya misconfigured limit ka sign).

Result: Policy caching (fast lookup), atomic token check (race-free), proper 429 response (client backoff implement kar sake), monitoring (rate limiting ki visibility).

Q01Rate limiter kya hota hai aur kyun chahiye?
Rate limiter ek system hai jo har client (User ID, API Key ya IP) ke requests ko ek time window me limit karta hai. Ye backend ko abuse, overload, unfair usage, bot traffic, brute force attacks aur cost explosion se bachata hai. Bina rate limiter ke ek hi client hazaaron requests bhej kar poori API ko down kar sakta hai — isliye rate limiter har production API ke aage khada hota hai, API Gateway ke saath.
Q02Token Bucket kaise kaam karta hai?
Bucket me tokens hote hain (capacity — jaise 100). Tokens steady rate se refill hote hain (jaise 10 tokens/sec). Har request ek token consume karti hai. Token available hai to request allow hoti hai aur token ghata diya jaata hai; token nahi hai to 429 reject milta hai. Burst naturally support hota hai — 100 tokens ka bucket 100 instant requests allow kar deta hai, phir refill ka wait karna padta hai.
Q03Fixed Window Counter me boundary problem kya hai?
Fixed window time ko fixed hisso me kaat ta hai (har 60 sec). Window ke edge par spike ho jaata hai: 99 requests 10:00:59 par + 100 requests 10:01:00 par = 199 requests sirf 2 second me — jabki limit 100/min ki spirit thi. Har window alag count hoti hai, isliye edge par limit effectively double ho jaati hai. Isi problem ko Sliding Window aur Token Bucket solve karte hain.
Q04Sliding Window Log aur Sliding Window Counter me kya farq hai?
Sliding Window Log har request ka timestamp store karta hai (Redis ZSET) aur pichhle N seconds ke logs gin kar decide karta hai — 100% accurate true rolling window, lekin memory bahut mehenga (har timestamp store hota hai). Sliding Window Counter sirf 2 counters rakhta hai (current + previous window) aur weighted count nikaalta hai — (prev × (1 − elapsed%)) + current. Ye kam memory leta hai lekin approximation hai, 100% accurate nahi.
Q05Production API ke liye kaunsa algorithm choose karoge aur kyun?
Token Bucket — kyunki ye bursts naturally support karta hai (capacity = burst size), smooth refill deta hai (window boundary par achanak reset nahi), industry standard hai (AWS API Gateway, Stripe, GitHub sab use karte hain), aur Redis Lua script se atomic implementation aasan hai. Fixed Window me boundary problem hai, Sliding Log me memory cost bahut zyada hai, Leaky Bucket sync APIs ke liye ideal nahi hai.
Q06Token Bucket aur Leaky Bucket me kya farq hai?
Token Bucket me request turant allow hoti hai agar token hai — burst allowed hai, aur token khatam ho to reject. Leaky Bucket me request queue me rukti hai aur fixed rate se process hoti hai — output smooth hota hai lekin request ko delay hota hai. Token Bucket 'allow ya reject' karta hai, Leaky Bucket 'queue karke process' karta hai. API rate limiting ke liye Token Bucket behtar hai; traffic shaping (downstream ko steady load dena) ke liye Leaky Bucket.
Q07Redis Lua script kyun zaroori hai? Alag GET + DECR se kya problem hai?
Alag GET + DECR me race condition hoti hai: 2 API Gateway instances ek saath GET karengi, dono ko 1 token dikhega, dono allow kar dengi, dono DECR karengi — tokens −1 ho jaayenge (over-limit). Lua script Redis me ek hi atomic operation ki tarah chalti hai — beech me koi aur command interleave nahi kar sakti. Isliye check + refill + decrement ek saath, race-free hota hai. Ye distributed rate limiting ka sabse important point hai.
Q08Rate limit state Redis me kyun rakhte hain, database me kyun nahi?
Kyunki har request par check hota hai aur latency budget 5ms se kam hai. Redis in-memory hai aur p99 latency 5ms se kam deti hai; database query har request par bahut slow hogi. Dusra, Redis atomic operations (Lua script, INCR) deta hai jo race condition rokti hain — database me ye lock karke karna padega, jo slow aur complex hai. Policy rules ka source of truth DB me hai, lekin live token state Redis me.
Q09429 response me kaunse headers hone chahiye?
Chaar headers zaroori hain: X-RateLimit-Limit (total quota — jaise 100), X-RateLimit-Remaining (bache hue requests — jaise 0), X-RateLimit-Reset (Unix timestamp — limit kab reset hogi), aur Retry-After (kitne seconds wait karein). Body me error 'rate_limit_exceeded' aur message hota hai. Ye headers client ko exponential backoff implement karne me madad karte hain — bina inke client API ko baar-baar hammer karta rahega.
Q10Retry-After kaise calculate karte ho?
Retry-After = ceil((1 − remaining_tokens) / refill_rate). Example: remaining 0, refill 10 tokens/sec ho to ceil(1/10) = 1 second. Matlab 1 sec baad 1 token refill ho jaayega aur retry likely succeed karega. Client ko ye value padh kar utna wait karna chahiye, phir retry karna chahiye — turant retry karne se phir 429 milega.
Q11Rate limit rules runtime par kaise update karte ho bina redeploy kiye?
Admin PUT /v1/admin/rules/{ruleId} se DB me rule update karta hai, aur write-through cache se Redis cache bhi turant update hoti hai (SET policy:user123 {limit: 200, ...}). Saath me Redis pub/sub par PUBLISH policy_update hota hai — saari API Gateway instances subscribe karke apna local cache 1 sec se bhi kam me invalidate kar deti hain. TTL-only approach me naya limit 1 hour (cache TTL) baad milta, isliye write-through zaroori hai.
Q12Policy cache kya hai aur 99% hit rate ka matlab kya hai?
Policy rules (limit, window, refill_rate) Redis me JSON ki tarah cache hote hain — key policy:{subject}:{endpoint}, TTL 1 hour. Rules rarely change karte hain, isliye lagbhag har request par cache hit hota hai (99%). Is se Policy DB ka load 100× kam ho jaata hai — har request par DB query nahi karni padti. Cache miss par hi DB se rule laakar cache me set kiya jaata hai.
Q13Multi-tier rate limiting kya hai? Strictest limit ka matlab?
Ek hi request par multiple levels check hote hain — per-user (100/min), per-IP (1000/min), per-API-key (10000/min), per-endpoint (/api/login → 10/min), global (1M/sec). Agar koi bhi ek level cross ho to 429 milta hai, chahe baaki sab theek hon. Yahi 'strictest limit' ka matlab hai. Is se abuse multiple levels par rukta hai — user quota, IP-based DDoS, aur endpoint brute-force, teeno ek saath.
Q14Per-user quota aur shared (tenant) quota me kya farq hai?
Per-user quota me har user ki apni alag limit hoti hai (subject_type='USER', subject_value='user123'). Tenant quota me poore tenant ki shared limit hoti hai (enforce_by='TENANT_ID') — tenant ke saare users mil kar ek hi quota use karte hain. Rule subject_type='TIER' dekh kar shared quota samajhna galat hai — aam taur par tier se sirf limit value decide hoti hai (PREMIUM → 1000/min), quota phir bhi per-user track hoti hai.
Q15Free vs Premium vs Enterprise limits kya hain?
Free: 100 req/min, Premium: 1000 req/min, Enterprise: 10000 req/min — sabka window 60s aur endpoints ['*'] (sab endpoints). Enterprise me per-endpoint custom limits bhi ho sakte hain. Tier lookup clients table se hota hai (SELECT tier FROM clients WHERE user_id='user123'), phir us tier ka rule fetch karke limit apply hoti hai.
Q16Rate limiting me CAP tradeoff kya hai?
Availability >> Consistency. Eventual consistency acceptable hai — thoda over-limit (101 requests jab limit 100 hai) chalega, lekin API down nahi honi chahiye. Redis ke andar consistency strong hai (single-threaded + atomic Lua), lekin poore system me availability ko priority milti hai — isiliye Redis down hone par fail open ka option rakha jaata hai.
Q17Redis down ho jaaye to kya karte ho — fail open ya fail closed?
Dono options hain aur tradeoff hai. Fail open: saare requests allow karo, error log karo — availability bachti hai lekin abuse rok nahi paate. Fail closed: sab 503 se reject karo — safer hai lekin availability gir jaati hai. Circuit breaker use karte hain: Redis 10 baar fail ho to 30 sec ke liye circuit open, phir half-open karke ek request try karo, success ho to circuit close. Kaunsa choose karna hai, ye business risk par depend karta hai.
Q18Consistent hashing rate limiting me kyun use hota hai?
Redis Cluster me multiple shards hote hain. Consistent hashing (hash(user_id) → shard) se ek user hamesha same shard par route hota hai — uski token state ek hi jagah rehti hai, isliye check consistent rehta hai. Agar user har request par alag shard par jaata to uski state alag-alag jagah banti aur limit enforce hi nahi hoti.
Q19Sliding Window Counter ka weighted formula kya hai?
weighted_count = (previous_window_count × (1 − elapsed%)) + current_window_count. Example: previous window 80 requests, current window 30, current window 75% beet chuki (45 sec / 60 sec) → (80 × 0.25) + 30 = 20 + 30 = 50. 50 < 100 ho to allow. Formula me elapsed% = (current_time % window_size) / window_size. Ye fixed window ke boundary spike ko smooth kar deta hai.
Q20Token Bucket me burst aur sustained rate kaise nikaalte ho?
Burst size = capacity (jaise 100 tokens = 100 instant requests). Sustained rate = refill rate (jaise 10 tokens/sec = 10 req/sec continuously). Full refill time = capacity / refill rate (100/10 = 10 sec). Bucket khaali ho to 1 token ke liye 1/refill_rate second wait karna padta hai. Ye teeno hisaab interview me bina calculator ke poochhe jaate hain.
Q21API Gateway stateless kyun hota hai? State kahan rehti hai?
API Gateway instances stateless hote hain (10–100+) taaki horizontally scale ho sakein — koi bhi instance kisi bhi request ko handle kar sake. Saari shared state Redis me rehti hai (token state + policy cache). Isiliye gateway restart ho ya naya instance aaye, rate limit state lost nahi hoti aur saare instances same limit enforce karte hain.
Q22Rate limit check se kitni latency add hoti hai aur kaise kam rakhte ho?
Budget 5ms se kam hai. Iske liye: token state Redis me (p99 < 5ms), policy Redis cache me (DB query nahi), connection pooling (har gateway 50 Redis connections reuse karta hai), pipelining (multiple checks ek round-trip me), aur local cache for policy rules. Agar check slow ho jaaye to limiter khud bottleneck ban jaata hai — isliye latency p50/p99 monitor karte hain.
Q23Monitoring me kya-kya track karte ho? Alert kab bajta hai?
Track karte hain: request count, rejection rate (429 responses ka %), Redis latency (p50, p99), policy cache hit rate. Alert bajta hai jab rejection rate > 5% ho (attack ya galat limit ka sign) ya Redis latency > 10ms ho (performance degradation). Per-endpoint breakdown bhi dekhte hain — kaunsa endpoint sabse zyada reject ho raha hai.
Q24Dynamic limit adjustment kya hai?
Load ke hisaab se limits apne aap badalna. Jaise cluster 80% capacity par ho to limits 20% kam kar do; DDoS spike detect ho to temporary stricter limits laga do; trusted IPs ko allowlist karke limits bypass karne do. Ye static limits se ek kadam aage hai — system load ke hisaab se khud ko bachata hai.
Q25Rate limit headers client ke liye kyun important hain?
Headers (X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, Retry-After) se client ko pata chalta hai uska quota kitna hai, kitna bacha hai, aur kab retry kare. Is se client exponential backoff implement kar sakta hai — 429 milte hi wait karke retry kare, baar-baar request bhej kar API ko hammer na kare. Bina headers ke client andhere me retry karta hai.
Q26Leaky Bucket kab use karte ho, Token Bucket ke bajay?
Jab downstream ko steady rate par load dena ho — traffic shaping ke liye. Leaky Bucket output ko fixed rate par smooth karta hai, isliye downstream overload nahi hota. Lekin sync APIs ke liye ye ideal nahi hai kyunki requests queue me rukti hain (delay) ya drop hoti hain. Typical API rate limiting ke liye Token Bucket behtar hai.
Q27Fixed Window Counter kab acceptable hai?
Simple internal APIs ke liye jahan thoda over-limit chalega aur boundary spike se koi nuksaan nahi hai. User-facing production APIs ke liye akela kaafi nahi hai — wahan Token Bucket ya Sliding Window chahiye. Fixed Window ki taakat uski simplicity aur low memory hai — ek counter per window, ek INCR command.
Q28Rate limit rule ka lookup order kya hai — specific ya wildcard pehle?
Sabse specific rule pehle: endpoint-specific user rule (subject='user123', endpoint='/api/users') sabse pehle, phir user wildcard ('*'), phir tier rule (PREMIUM tier ka rule). SQL me teeno OR conditions se fetch karke pehla matching rule liya jaata hai — specific endpoint > wildcard, user > tier. Isi order se /api/login jaisi sensitive endpoints par strict limit lag paati hai.
Q29Redis ZSET me sliding window log kaise implement karte ho?
Key rate_limit_log:{subject} ek ZSET hai — member request_id (UUID), score timestamp (Unix seconds). Nayi request par: purane logs hatao (ZREMRANGEBYSCORE 0 {now − window}), count karo (ZCOUNT {now − 60} {now}), count < limit ho to ZADD karke allow karo, warna 429. Accurate hai lekin har request ka timestamp store hota hai — high-traffic APIs me memory bahut zyada ho jaata hai.
Q30Multi-region rate limiting kaise karte ho?
Har region me apna Redis hota hai (us-east-1, eu-west-1, asia-south-1) taaki latency kam rahe. Do options: global limit — regions ke across aggregate karo (complex, eventual consistency), ya per-region limit — 100 req/min per region (simpler, thoda relaxed global limit). Aam taur par per-region limit choose karte hain kyunki global aggregation me cross-region latency aur consistency dono mushkil hain.
Q31enforce_by field kya batata hai?
Ye batata hai limit kis scope me enforce ho rahi hai — USER (per-user quota), IP (per-IP quota), TENANT_ID (quota poore tenant ke across shared), ya API_KEY (per API key quota). Tenant_id ka matlab hai tenant ke saare users mil kar ek hi quota share karte hain — ek user poori quota kha jaaye to baaki users bhi block ho jaayenge.
Q32Rate limiter ko DDoS se bachane ke liye kya karte ho?
Multiple layers: per-IP limit (1000/min) se single IP abuse rukta hai, per-endpoint limit (/api/login 10/min) se brute force rukta hai, global limit (1M/sec) se cluster capacity bachti hai, dynamic adjustment se spike detect hote hi temporary stricter limits lag jaate hain, aur allowlist se trusted IPs ko bypass milta hai. Saath me rejection rate > 5% par alert bajta hai taaki team turant react kar sake.
Q33Token Bucket ki Redis key kya hoti hai aur TTL kyun 3600 hai?
Key hoti hai rate_limit:{subject}:{endpoint} — ek HASH jisme tokens aur last_refill store hote hain (jaise rate_limit:user123:/api/users → {tokens: 95, last_refill: 1706270445}). TTL 3600 sec (1 hour) isliye hai taaki inactive buckets auto-expire ho jaayein aur memory bache — jo user 1 hour se request nahi bhej raha, uski state rakhne ka koi matlab nahi.
Q34Rate limiting aur throttling me kya farq hai?
Rate limiting ek time window me kitne requests allowed hain ye decide karta hai (count-based — jaise 100/min, cross ho to 429). Throttling request ki speed ko control karta hai — Leaky Bucket jaisa, jahan requests ko fixed rate se process kiya jaata hai (delay karke). Dono ka goal ek hi hai — backend ko overload se bachana — lekin rate limiting 'kitne' par focus karta hai, throttling 'kis speed se' par.
Q35Rate limiter ko API Gateway me lagate hain ya alag service me?
Dono tareeke hote hain, lekin aam taur par rate limiting API Gateway ke andar ya uske saath ek alag Rate Limiter service me hoti hai. Lesson ka design: API Gateway request receive karta hai, auth check karta hai, phir Rate Limiter / Policy Svc ko call karta hai jo Redis se token check karta hai. Gateway me lagane ka fayda — har request gateway se guzarti hai, isliye koi request check se bach nahi sakti. Alag service me rakhne ka fayda — scaling aur policy management alag se ho sakta hai. Dono me state Redis me hi rehti hai.
Q36Interview me rate limiter design kaise shuru karte ho?
Pehle requirements saaf karo: functional (limit per client, runtime configurable, 429 + Retry-After, tier-based) aur non-functional (1M rps, availability >> consistency, <5ms latency). Phir entities (policy, client, counter), API design (admin APIs), HLD (client → LB → gateway+limiter → backend), phir 5 algorithms compare karke Token Bucket chuno, Redis Lua script se atomic implementation, schema (policy DB + Redis keys), aur ant me scaling (12 techniques) aur failure handling (circuit breaker, fail open/closed). Yehi order lesson ka hai — isi order me bolna interviewer ko structured lagta hai.
