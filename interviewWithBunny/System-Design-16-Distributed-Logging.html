01Requirements

Functional Requirements

Functional requirements matlab — system ko kya-kya karna chahiye. Interview me yahi se shuruaat hoti hai: pehle features ginwao, phir design. Is lesson me logging platform ke 7 features hain.

F1 — Multi-source ingestion

Logs kai sources se aane chahiye — FluentBit, OTEL (OpenTelemetry), aur custom agents. Matlab system sirf ek tareeke se logs nahi leta; servers, containers, apps — sab apne-apne agent se logs bhejte hain. Ingestion real-time bhi aur batch bhi honi chahiye.

F2 — Streaming + batch, dono protocols

Real-time streaming (jaise hi log bane, turant bhejo) aur batch ingestion (thoda ruk kar, ikatthe bhej) — dono support hone chahiye, alag-alag protocols ke saath. Kuch sources live bhejte hain, kuch offline files upload karte hain.

F3 — Validate, parse, normalize

Har log ko ek standard structure me badlo — JSON ya structured format. Pehle validate karo (zaroori fields hain ya nahi), phir parse karo, phir normalize karo taaki har service ka log ek hi shape me mile. Bina iske search aur alerting dono mushkil ho jate hain.

F4 — Dashboard par near real-time logs (<5 seconds)

User ko dashboard par logs lagbhag turant dikhne chahiye — log banne se lekar dashboard par dikhne tak 5 second se kam ka time. Ye poore system ka sabse important SLA hai.

F5 — Advanced search

Indexed logs par filters, regex aur time-range queries chalne chahiye. Sirf text search kaafi nahi — user ko service, level, time window sab se filter karna hota hai.

F6 — Real-time log tailing

Logs ko live stream karke dekhna — jaise terminal me tail -f karte ho, waise hi browser me naye logs aate rahein.

F7 — Alerts

Log patterns, thresholds aur anomalies par alerts banein. Jaise — 5 minute me 100 se zyada ERROR aaye to notification jaye. Bina alerts ke logging platform sirf ek search box reh jata hai.

Interview tip: Requirements ginwate waqt har feature ke saath ek line "kyun chahiye" bhi bolo — jaise F4 ke liye "kyunki incident ke time engineer ko 5 minute purane logs nahi, abhi ke logs chahiye." Interviewer ko lagta hai tumne soch kar bola hai, ratta nahi maara.

02Requirements

Non-Functional Requirements

Non-functional requirements matlab — system kis scale par, kitni tezi se, aur kitna reliable hona chahiye. Ye numbers hi batate hain ki design me Kafka, Flink aur Cassandra kyun chahiye, simple database kyun nahi.

Scale — kitna bada?

CheezNumber
Log volumeMillions of events per hour, petabytes annually
Ingestion rate100K–1M logs/second sustained
SourcesThousands of distributed services / servers
RetentionHot: 14 days, Warm: 45 days, Cold: unlimited (S3)

Matlab har second lakhon logs aa rahe hain, hazaaron services se. Itna volume koi single database nahi sambhalta — isiliye distributed pipeline chahiye.

Performance — kitna fast?

CheezTarget
Ingestion latencyNear real-time, <5 seconds end-to-end
Search (hot data)<200ms
Recent logs (14 days)Sub-second queries
Historical queriesSeconds (thoda slow chalega)
ThroughputHigh concurrent writes + reads, bina degradation

Recent logs par search 200ms se kam me chahiye — isiliye hot data Elasticsearch me rehta hai. Purane logs par 2–30 second bhi chalenge, kyunki woh rarely dekhe jate hain.

Reliability — kitna bharosemand?

CheezRequirement
AvailabilityIngestion ke liye hamesha up — 99.9% uptime
ConsistencyEventual consistency acceptable (CAP me AP)
DurabilityNo data loss — replicated storage + S3 cold backup
Data lifecycleAutomatic tiering: Hot → Warm → Cold, retention policies ke saath
Eventual consistency kyun acceptable hai? Logs payments jaise nahi hain — strong consistency ki zaroorat nahi. Agar ek log Elasticsearch me Cassandra se 1 second late dikhe, to koi farak nahi padta. User ko near real-time (<5s) chahiye, strict ordering nahi. Isiliye system AP (Availability + Partition tolerance) choose karta hai, CP nahi.

99.9% uptime ka matlab hai saal me zyada se zyada 8.7 ghante downtime. Ingestion kabhi band nahi honi chahiye — agar search 5 minute down ho jaye to chalega, lekin logs aana band ho jayein to data loss hoga.

Core Entity

Core entities matlab — system ke andar kaun-kaun si main cheezein (objects) hain, jin par poora design khada hai. Interview me entities ginwana dikhata hai ki tumne data model socha hai, sirf boxes nahi banaye.

#EntityKya hai
1LogEventAsal log entry — timestamp, message, severity (level), metadata
2IngestionJobBatch / streaming ingestion tasks ko track karta hai — kaunsa job kab chala, kya status hai
3Source / AgentLog producers — servers, apps, containers — har ek ka unique ID hota hai
4Client / UserOrganizations / teams — har client ka apna log namespace aur access control hota hai
5AlertRuleConfigured patterns / thresholds — jinke match hone par notification trigger hoti hai
6SearchQueryUser ki query — filters, time range aur pagination ke saath

Entities aapas me kaise judi hain?

Source/Agent logs bhejta hai → har log ek LogEvent banta hai → IngestionJob us batch ya stream ko track karta hai → Client ka namespace decide karta hai ki log kahan store hoga aur kaun dekh sakta hai → AlertRule LogEvent par match karke alert nikalta hai → SearchQuery LogEvents ko dhoondhti hai.

LogEvent sabse important entity hai — iske fields hi decide karte hain ki indexing, search aur alerting kaise hogi: timestamp (kab), level (DEBUG/INFO/WARN/ERROR/FATAL), message (kya hua), service_name, host, trace_id aur metadata.

Multi-tenant point: Client entity isiliye hai kyunki ye platform ek se zyada teams/organizations ko serve karta hai. Har client ka alag namespace/index hota hai — ek client doosre ke logs nahi dekh sakta. Interview me ye point bolna achha impression deta hai.

High Level Design

High Level Design matlab — poora system ek diagram me. Yaad rakhne wali one-liner: Multi-source ingestion → Kafka buffering → Apache Flink processing → Hot/Warm/Cold storage tiering with Elasticsearch.

Data ka flow, hop by hop

HopKya hota hai
Clients / Agents → LB & API GatewayFluentBit / OTEL / custom agents se logs aate hain; gateway par authentication aur rate limiting hoti hai
Client Onboarding Service → Client DBClient registration, tokens aur namespaces manage karta hai
File Ingestion Service → KafkaHTTP/gRPC se logs lekar Kafka topic raw_logs me publish karta hai
Agent Based Service → KafkaAgent-specific protocols aur batching handle karta hai
Search Service → ElasticsearchIndexed logs par filtering aur aggregation ke saath queries chalata hai
Kafka (Buffer) → Apache FlinkStream processing — validation, enrichment, deduplication
Apache Flink → Log DB (Cassandra)Processed logs hot storage me, timestamp par clustered
Apache Flink → ElasticsearchReal-time indexing — fast search, 14 days retention
Cron Service → S345 days se purane logs archive karta hai cold storage me, hot DB se delete karta hai

Diagram me kya dikh raha hai?

Diagram me baayein taraf agents/sources hain, beech me API Gateway aur ingestion services, phir Kafka buffer jo poore system ki reedh hai. Kafka ke baad Flink logs ko process karke teen jagah bhejta hai — Cassandra (durable hot storage), Elasticsearch (search index) aur alert topic. Upar Search Service users ko results deta hai, aur neeche Cron Service purane logs ko S3 me archive karta hai. Diagram ka har box neeche ke sections (khaas taur par Deep Dive, section 6) me detail me samjhaya gaya hai.

WARNING — kabhi seedha Elasticsearch me mat likho: Ingestion ke time logs ko kabhi seedha ES me mat bhejo. Hamesha pehle Kafka buffer me daalo. Isse teen fayde: (1) ES down ho to bhi data loss nahi, (2) processing me galti ho to logs replay kar sakte ho, (3) ek hi log stream se kai consumers (ES, Cassandra, Alerts) alag-alag kaam kar sakte hain.

06.1Deep Dive — LLD

Step 1: Client Onboarding

Deep Dive ka pehla step — naya client system me kaise judta hai. Bina onboarding ke koi agent logs nahi bhej sakta, kyunki har log ko ek namespace aur ek token chahiye.

  1. Client bhejta hai: POST /agents/register with {client_name, email, metadata}.
  2. Onboarding Service validate karta hai: email format sahi hai ya nahi, client_name unique hai ya nahi, aur rate limits cross to nahi ho rahi.
  3. Service record banata hai: PostgreSQL (ClientDB) me client record — {client_id, token (JWT), token_ttl, env, metadata}.
  4. Service provision karta hai: Elasticsearch me dedicated namespace/index — client_<id>_logs. Isse ek client ke logs doosre se alag rehte hain (multi-tenant isolation).
  5. Service return karta hai: {client_id, token, namespace} — agent isi se configure hota hai.

Token JWT hota hai jiska expiry (token_ttl) hota hai. Agent ko time-time par token refresh karna padta hai — ye kaam agent ke Authentication Module ka hai (section 07 dekho).

Interview me kyun important? Onboarding step batata hai ki tumne multi-tenancy sochi hai. Har client ka alag index hone se (1) security milti hai — ek client doosre ka data nahi dekh sakta, (2) retention aur sampling per-client set kar sakte ho, (3) ek client ka heavy usage doosre ko affect nahi karta.

06.2Deep Dive — LLD

Step 2: Log Ingestion (Real-time)

Agent se log aakar Kafka tak pahunchne ka rasta — ye pipeline ka sabse time-sensitive hissa hai, kyunki yahin par <5 second SLA tay hoti hai.

  1. Agent bhejta hai: POST /v1/logs/ingest — headers me Authorization: Bearer <token>, body me {timestamp, level: 'ERROR', message, service_name, host, trace_id}.
  2. LB & API Gateway validate karta hai: token ka JWT signature, rate limit (10K logs/min per client), aur payload size (<1MB).
  3. File Ingestion Service check karta hai: schema validation (zaroori fields present hain ya nahi) aur timestamp normalization (ISO 8601 format me).
  4. Service enrich karta hai: {ingestion_time, client_id, pod_name, namespace} metadata add karta hai.
  5. Service publish karta hai: Kafka topic raw_logs me, key = client_id (partitioning ke liye). Turant 202 Accepted return karta hai.

Key numbers — ingestion

CheezValue
Rate limit10K logs/min per client (token bucket)
Max payload<1MB per request
Batch upload10K logs per request (batch API)
Kafka keyclient_id — ek client ke logs ek hi partition me jate hain
WARNING — ES indexing ka wait kabhi mat karo: Kafka publish ke baad turant 202 Accepted bhejo. Elasticsearch indexing ka synchronously wait karna ingestion ko slow kar deta hai — p95 latency 200ms se badh kar 2s ho jati hai. ES slow ya down ho, to bhi ingestion chalti rehni chahiye.

06.3Deep Dive — LLD

Step 3: Stream Processing (Apache Flink)

Kafka aur storage ke beech ka dimaag — Apache Flink. Ye sirf "Kafka consumer" nahi hai; Flink windowing, stateful operations aur fault tolerance deta hai, jo plain consumer nahi de sakta.

  1. Flink consume karta hai: Kafka topic raw_logs se, consumer group log_processor ke saath.
  2. Validation: zaroori fields {timestamp, message} check karta hai; malformed logs ko DLQ (dead letter queue) me bhej deta hai, pipeline block nahi hoti.
  3. Enrichment: IP se geo-location add karta hai, service registry se service tags lagata hai.
  4. Deduplication: 5-minute tumbling window + message hash se duplicates pakadta hai (Lab 5 me try karo).
  5. Routing — teen sinks: (1) Cassandra — durable storage, (2) Elasticsearch — indexing, (3) Alert topic — agar log kisi alert rule se match kare.

Deduplication kaise kaam karti hai?

Hash banta hai (timestamp_minute, service_name, message ke pehle 100 characters) se. Flink RocksDB state me us window ke saare hashes rakhta hai. Agar hash pehle se hai → log drop; nahi hai → state me add karke aage bhejo. Window band hote hi (5 min ke baad) state clear ho jata hai, taaki state hamesha badhta na rahe. Trade-off: sirf 5-minute window ke andar ke duplicates pakde jate hain; cross-window duplicates nahi.

INTERVIEW FAVORITE — Flink kyun, plain consumer kyun nahi? Interview me hamesha bolo: Flink event-time processing, watermarks aur exactly-once semantics deta hai. Sirf "Kafka consumer" bolna kamzor jawab hai — Flink windowing, stateful deduplication aur checkpointing se failure recovery deta hai, jo plain consumer me khud likhna padta hai.
Dedup window trade-off: 5-minute window agent retries se aane wale 99% duplicates pakad leta hai, aur Flink state <1GB per task rehta hai. 1-hour window zyada duplicates pakdega, lekin state 12x badh jayega aur checkpoint time 5s se 60s ho jayega.

06.4Deep Dive — LLD

Step 4: Storage in Log DB (Cassandra)

Processed logs ki durable copy Cassandra me jati hai. Cassandra isiliye — ye write-optimized hai aur time-series data ke liye bana hai.

  1. Flink likhta hai: 1000 logs ka batch, Cassandra me, clustering key (timestamp DESC) ke saath.
  2. Table: logs_by_service — partition key (service_name, log_date), clustering (timestamp, log_id). Matlab ek service ke ek din ke logs ek partition me, newest pehle.
  3. Replication: RF=3 — multiple datacenters me 3 copies, durability ke liye.
  4. TTL policy: 14 days se purane logs apne aap delete — hot storage retention automatic hai.
  5. Write optimization: Write-ahead log (WAL) + memtable se fast writes — 10K writes/sec per node.
Cassandra — logs_by_serviceCQL
CREATE TABLE logs_by_service (
  service_name text,
  log_date date,
  timestamp timestamp,
  log_id uuid,
  log_level text,
  message text,
  host text,
  trace_id text,
  metadata map<text, text>,
  PRIMARY KEY ((service_name, log_date), timestamp, log_id)
) WITH CLUSTERING ORDER BY (timestamp DESC)
  AND default_time_to_live = 1209600;  -- 14 days
INTERVIEW FAVORITE — Cassandra hi kyun? (1) Write-optimized — 10K writes/sec per node, log ingestion ke liye perfect. (2) Time-series model — timestamp par clustering se range queries fast hain. (3) TTL support — purane logs bina manual cleanup ke auto-delete. (4) Linear scalability — nodes add karo, capacity badhao.

100 nodes × 10K writes/sec = 1M writes/sec — isiliye Cassandra 1M logs/sec wale peak ko sambhal sakta hai.

06.5Deep Dive — LLD

Step 5: Indexing in Elasticsearch

Search fast kaise hoti hai? Kyunki Flink logs ko Elasticsearch me index karta hai — full-text search ke liye inverted index ke saath.

  1. Flink bulk index karta hai: 5000 logs ke batches, _bulk API se.
  2. Documents bante hain: index logs_<date> me, fields {log_id, timestamp, log_level, message, service_name, host, env, trace_id}.
  3. Indexing: message par full-text, service_name aur log_level par keyword (exact match), timestamp par range.
  4. Index lifecycle (ILM): roz rollover hota hai, hot tier me 14 days rehta hai.
  5. Search optimization: text search ke liye inverted index, aggregations ke liye doc values.

Field types kyun alag hain?

FieldTypeKyun
messagetextFull-text search — "payment failed" jaise words dhoondhne ke liye
service_name, log_levelkeywordExact match filtering aur aggregations ke liye
timestampdateRange queries — "pichle 2 ghante ke logs"

Index size: roz ka index lagbhag 50GB — 10 primary shards + 1 replica. Daily indices isiliye bante hain taaki purana data asaani se delete ya move kiya ja sake.

ILM optional nahi hai: Bina Index Lifecycle Management ke indices hamesha badhte rahenge, queries slow ho jayengi, aur cluster ka disk bhar jayega. ILM roz rollover karta hai, 7 din baad warm nodes par le jata hai, aur purane indices delete karta hai — poora automated.

06.6Deep Dive — LLD

Step 6: Log Search (Real-time)

User search kare to andar kya hota hai — query Elasticsearch DSL me badal kar hot indices par chalti hai, aur jawab 200ms se kam me aata hai.

  1. User bhejta hai: POST /logs/search — {query: 'error AND service:payment', time_range: {start, end}, filters: {log_level: ['ERROR', 'FATAL']}, page: 1, size: 100}.
  2. Search Service banata hai: Elasticsearch DSL query — bool query (must: text match, filter: term + range).
  3. Elasticsearch chalata hai: hot indices (pichle 14 din) par query; repeated queries ke liye query cache use hota hai.
  4. Service fetch karta hai: matched terms par highlighting ke saath results, aur pagination ke liye total count.
  5. Service return karta hai: {logs: [...], total: 15234, page: 1, size: 100} — <200ms me.
Elasticsearch DSL — bool queryJSON
{
  "query": {
    "bool": {
      "must": [{ "match": { "message": "error" } }],
      "filter": [
        { "term": { "service_name": "payment" } },
        { "terms": { "log_level": ["ERROR", "FATAL"] } },
        { "range": { "timestamp": {
            "gte": "2025-01-19T00:00:00Z",
            "lte": "2025-01-20T00:00:00Z" } } }
      ]
    }
  },
  "from": 0, "size": 100,
  "highlight": { "fields": { "message": {} } }
}

Filter context vs query context: filter wale hisse (term, range) scoring nahi karte — isiliye fast hote hain aur cache hote hain. Text match scoring karta hai. Time-series ke liye date histogram aggregations use karo.

Query cache: Elasticsearch frequent queries ko 60 second tak cache karta hai — dashboard load time 80% tak improve ho jata hai, kyunki kai users wahi popular queries chalate hain.

06.7Deep Dive — LLD

Step 7: Real-time Log Tailing

Live logs dekhna — WebSocket + Kafka consumer ka combination. User ko lagta hai logs "stream" ho rahe hain; andar Kafka se messages aakar WebSocket par bheje ja rahe hain.

  1. User kholta hai: WebSocket connection WS /logs/tail/* — query params {service: 'payment', level: 'ERROR'}.
  2. Search Service subscribe karta hai: Kafka topic alert_topic par, user ke criteria se match karne wale filter ke saath.
  3. Kafka stream karta hai: naye matching logs WebSocket connection par, real-time me.
  4. Service bhejta hai: har log event JSON message ke roop me — <1s latency.
  5. Connection handling: disconnect par auto-reconnect; reconnect recovery ke liye aakhri 100 messages buffer me rakhe jate hain.

Backpressure aur reconnect

Agar client slow hai (messages consume nahi kar pa raha), to buffer me sirf aakhri 100 messages rakhe jate hain — buffer bhar jaye to sabse purane drop kar do. Heartbeat har 30 second me ping/pong se disconnect detect hota hai. Reconnect par client aakhri mile hue log ka timestamp bhejta hai, aur since parameter se wahin se resume karta hai — kuch miss nahi hota.

Scalability: Kafka 10,000+ consumer groups support karta hai — har WebSocket connection ka apna dedicated consumer group hota hai, koi shared state nahi. Alternative: SSE (Server-Sent Events) — one-way streaming ke liye simple hai, lekin bidirectional communication nahi deta.

06.8Deep Dive — LLD

Step 8: Alerting (Alert Service)

Alerting ka matlab sirf "ERROR aaya to mail bhejo" nahi hai — asli kaam hai alert fatigue se bachna. 1000 errors par 1000 alerts nahi, ek smart alert aani chahiye.

  1. Alert Service poll karta hai: AlertRule DB — har 10 second me active rules check karta hai.
  2. Service subscribe karta hai: Kafka alert_topic par — Flink wahi logs bhejta hai jo alert patterns se match karte hain.
  3. Service evaluate karta hai: conditions jaise 'ERROR count > 100 in 5 minutes' — sliding window aggregation se.
  4. Service trigger karta hai: notification — Kafka → Notification Service → Email / SMS / Pager.

Step 9: Cold Storage Archival (Cron Service)

Purane logs kahan jate hain? Roz raat ko Cron Service unhe S3 me archive karta hai — saste me, hamesha ke liye.

  1. Cron Service chalta hai: roz 2 AM UTC par, 45 days se purane logs ke liye.
  2. Service query karta hai: Cassandra — logs_by_traceid WHERE timestamp < (now - 45 days).
  3. Service export karta hai: S3 me Parquet format + Snappy compression — efficient storage ke liye.
  4. S3 organization: s3://logs-archive/{year}/{month}/{day}/{service_name}/logs.parquet — date aur service se partitioned.
  5. Service delete karta hai: archived logs Cassandra se — disk khaali hoti hai, S3 copy hamesha rehti hai.
  6. Recovery: 45+ din purani queries S3 par Athena / Presto se chalti hain.

Parquet kyun? Columnar format hai — Athena sirf wahi columns padhti hai jo query me chahiye, poori file nahi. Aur date/service partitioning se Athena sirf relevant partitions scan karti hai. Isiliye cold data par bhi query 10–30 second me ho jati hai, saal bhar purane logs par bhi.

Cost ka asar: 1TB/day logs — sirf hot storage me rakho to $3000/month, tiering ke saath blended cost $300/month — 90% bachat. Snappy compression (3:1) se 1TB raw → 330GB ho jata hai.

Common Interview Questions

Lesson ke 10 sabse important interview questions — poore jawab ke saath. Ye woh questions hain jo interviewer sabse zyada poochta hai. Inhe samajh lo to design discussion me kabhi phasoge nahi.

Q1. Kafka ko buffer kyun use karte ho — seedha database me kyun nahi likhte?

Kafka decoupling aur resilience deta hai: (1) Back-pressure handling — DB slow/down ho to Kafka bina data loss ke millions of logs buffer kar leta hai. (2) Replay capability — processing logic badle ya fail ho to logs dobara process kar sakte ho. (3) Multiple consumers — ek hi log stream Elasticsearch, Cassandra aur Alert service ko alag-alag feed karta hai. (4) Peak load smoothing — ingestion spike (10x normal) Kafka absorb kar leta hai, downstream steady rate par process karta hai. Example: Black Friday spike — Kafka 1M logs/sec burst handle karta hai, Flink 100K/sec par process karta hai, zero data loss.

Q2. Out-of-order logs kaise handle karte ho — alag-alag timestamps ke saath?

Multi-layer approach: (1) Flink Watermarks — event time processing, 5-minute watermark delay; late aane wale logs sahi time window me aa jate hain. (2) Cassandra Clustering — timestamp par sort karta hai, queries me chronological order rehta hai. (3) Elasticsearch @timestamp — range queries ke liye indexed; UI logs ko order me dikhata hai chahe process out-of-order hue hon. (4) Grace Period — Flink 10 minute tak late logs accept karta hai, usse zyada late wale DLQ me jate hain. Trade-off: 5-min watermark alerting ko delay karta hai, lekin 99.9% logs sahi window me aate hain.

Q3. Elasticsearch down ho jaye to kya users search kar payenge?

Graceful degradation: (1) Cassandra fallback — Search service queries apne aap Cassandra par bhej deta hai; slow (1–2s vs 200ms) lekin kaam chal jata hai. (2) ES recovery — Flink bulk index requests Kafka topic es_retry me queue karta hai, ES wapas aate hi replay karta hai. (3) Cache layer — Redis recent common queries 60s tak cache karta hai, ES downtime me bhi serve karta hai. (4) Status notification — UI par "Limited search mode" banner dikhta hai. Cassandra point queries (service+time) sambhal sakta hai, lekin full-text search nahi. Typical ES downtime: auto-restart se <5 minute.

Q4. Ingestion ke time koi log data loss na ho — ye kaise ensure karte ho?

Multiple durability guarantees: (1) Kafka persistence — replication factor=3, min.insync.replicas=2, acks=all — matlab log 2+ brokers par likhne ke baad hi acknowledge hota hai. (2) Agent buffering — FluentBit 10MB local disk par buffer karta hai, exponential backoff se retry (max 24 hours). (3) Flink checkpointing — har 60s state S3 me save hota hai, failure par exactly-once recovery. (4) Cassandra replication — RF=3, QUORUM writes, 1 node failure tolerate karta hai. (5) S3 archival — immutable cold storage, 11 9's durability. End-to-end guarantee: at-least-once delivery (duplicates ho sakte hain, deduplication handle karta hai), zero data loss.

Q5. Flink me deduplication kaise kaam karti hai?

Window-based deduplication: (1) Tumbling Window — 5-minute windows, logs ko time slice se group karta hai. (2) Hash Generation — hash banta hai (timestamp_minute, service_name, message ke pehle 100 chars) se. (3) State Backend — Flink RocksDB state me window ke saare hashes rakhta hai. (4) Duplicate Detection — hash state me hai to log drop, nahi hai to add karke aage bhejo. (5) State Expiration — window band hote hi state clear, taaki state hamesha na badhe. Ye handle karta hai: agent retries se duplicate sends, aur load balancer se ek hi log ka multiple endpoints par jana. Trade-off: sirf 5-min window ke andar ke duplicates pakde jate hain.

Q6. Data retention aur archival strategy kya hai?

Three-tier lifecycle: (1) Hot (0–14 days) — Cassandra + Elasticsearch, SSD, <200ms queries, $0.10/GB/month. (2) Warm (14–45 days) — Cassandra only, HDD, 1–2s queries, $0.05/GB/month. (3) Cold (>45 days) — S3 Parquet, Glacier, 10–30s queries via Athena, $0.01/GB/month. Cron job roz chalta hai: ES indices ko warm tier me move karta hai (ILM policy), Cassandra se S3 export karta hai, purana Cassandra data delete karta hai. Example: 1TB logs/day = $3000/month sirf hot vs $300/month blended. Compression: Snappy 3:1, Parquet columnar format cold queries ko efficient banata hai.

Q7. Multiple time ranges par log search efficiently kaise karte ho?

Query routing: (1) Time-based routing — pichle 14 din ki query Elasticsearch (fast), 14–45 din Cassandra (medium), >45 din S3 via Athena (slow). (2) Parallel execution — cross-tier query (jaise pichle 60 din) ES + Cassandra + S3 par parallel chalti hai, results merge hote hain. (3) ES optimization — time-series ke liye date histogram aggregations, non-scoring filters ke liye filter context (query context nahi). (4) Cassandra partition pruning — WHERE me partition key (service_name, log_date) ho to sirf zaroori partitions padhe jate hain. (5) S3 partitioning — Parquet files year/month/day par partitioned, Athena sirf relevant partitions scan karti hai. Example: "last 30 days" query = ES (14 din) + Cassandra (16 din), <500ms me — single tier par 2–3s lagte.

Q8. Real-time log tailing efficiently kaise implement karte ho?

WebSocket + Kafka Consumer: (1) Connection — client /logs/tail par WebSocket kholta hai, filters (service, level) ke saath. (2) Consumer Group — backend har WebSocket connection ke liye unique consumer group me dedicated Kafka consumer banata hai, alert_topic subscribe karta hai. (3) Filtering — Consumer Interceptor client ke criteria se match karne wale messages hi WebSocket par bhejta hai. (4) Backpressure — client slow ho to aakhri 100 messages in-memory buffer me, buffer bhar jaye to sabse purane drop. (5) Heartbeat — har 30s ping/pong, disconnect detect hota hai. (6) Reconnect — client aakhri timestamp store karke since parameter se resume karta hai. Scalability: Kafka 10K+ consumer groups support karta hai, har WebSocket independent hai. Alternative: SSE — one-way streaming ke liye simple, lekin bidirectional nahi.

Q9. Alert fatigue se bachne ki strategy kya hai?

Multi-level suppression: (1) Aggregation — har ERROR par nahi, "ERROR count >100 in 5 min" par alert — noise 100x kam. (2) Cooldown — ek baar alert fire ho to 10 minute tak dobara nahi. (3) Severity Levels — P0 critical (turant page), P1 high (email+Slack), P2 medium (Slack only), P3 low (daily digest). (4) Deduplication — ek hi fingerprint (service+error_type) wale alerts group hokar summary bhejte hain. (5) Escalation — P1 alert 15 min me acknowledge na ho to P0 banao, on-call page karo. (6) Rate Limiting — max 10 alerts per service per hour, alert storm roko. Example: Payment service ke 1000 errors → ek alert "Payment ERROR spike: 1000 in 5 min", dashboard link ke saath.

Q10. Log formats change hon to schema evolution kaise handle karte ho?

Backward-compatible schema design: (1) Schema Registry — version history registry me, agents schema_version ke saath logs bhejte hain. (2) Multi-version Support — Flink ke paas v1, v2, v3 ke parsers hote hain, version ke hisaab se sahi parser chunta hai. (3) Elasticsearch Mapping — dynamic mapping on hai, naye fields auto-detect hokar index hote hain. (4) Default Values — missing fields me defaults bharte hain (optional ke liye null, required ke liye 'UNKNOWN'). (5) Migration Path — schema change ke time 7 din tak purana aur naya parser parallel chalate hain, outputs match karne par purana deprecate karte hain. (6) Deprecated Fields — purane fields 90 din tak 'deprecated' flag ke saath rehte hain. Example: 'request_id' field add karo → Flink auto-map karke ES me bhejta hai, purane logs me null dikhta hai, queries purane+naye dono par chalti hain.

Interview FAQs

36 interview FAQs — pehle 10 lesson ke apne Q&A hain (concise jawab), baaki 26 related current-era questions hain. Kisi bhi sawaal par click karke jawab kholo.

Q01 Kafka ko buffer kyun use karte ho — seedha database me kyun nahi likhte?
Kafka decoupling aur resilience deta hai: (1) Back-pressure — DB slow/down ho to Kafka bina data loss ke millions of logs buffer kar leta hai. (2) Replay — processing logic badle ya fail ho to logs dobara process kar sakte ho. (3) Multiple consumers — ek hi stream Elasticsearch, Cassandra aur Alert service ko alag-alag feed karta hai. (4) Peak smoothing — 10x spike Kafka absorb kar leta hai, downstream steady rate par chalta hai. Example: Black Friday par Kafka 1M logs/sec burst sambhalta hai, Flink 100K/sec par process karta hai, zero data loss.
Q02 Out-of-order logs kaise handle karte ho — alag-alag timestamps ke saath?
Multi-layer approach: (1) Flink Watermarks — event-time processing, 5-minute watermark delay; late logs sahi window me aa jate hain. (2) Cassandra clustering — timestamp par sort karta hai, queries me chronological order rehta hai. (3) Elasticsearch @timestamp — range queries ke liye indexed; UI order me dikhata hai. (4) Grace period — Flink 10 minute tak late logs accept karta hai, usse zyada late wale DLQ me. Trade-off: 5-min watermark alerting delay karta hai, lekin 99.9% logs sahi window me aate hain.
Q03 Elasticsearch down ho jaye to kya users search kar payenge?
Graceful degradation: (1) Cassandra fallback — Search service queries apne aap Cassandra par bhej deta hai; slow (1-2s vs 200ms) lekin kaam chal jata hai. (2) ES recovery — Flink bulk index requests Kafka topic es_retry me queue karta hai, ES wapas aate hi replay karta hai. (3) Cache — Redis recent common queries 60s tak cache karta hai. (4) UI par 'Limited search mode' banner. Cassandra point queries (service+time) sambhal sakta hai, full-text search nahi. Typical ES downtime auto-restart se 5 minute se kam.
Q04 Ingestion ke time koi log data loss na ho — ye kaise ensure karte ho?
Multiple durability guarantees: (1) Kafka — RF=3, min.insync.replicas=2, acks=all; log 2+ brokers par likhne ke baad hi acknowledge hota hai. (2) Agent buffering — FluentBit 10MB local disk par buffer karta hai, exponential backoff se 24 ghante tak retry karta hai. (3) Flink checkpointing — har 60s state S3 me save, failure par exactly-once recovery. (4) Cassandra — RF=3, QUORUM writes, 1 node failure tolerate karta hai. (5) S3 archival — immutable cold storage, 11 9's durability. End-to-end: at-least-once delivery (duplicates deduplication handle karta hai), zero data loss.
Q05 Flink me deduplication kaise kaam karti hai?
Window-based deduplication: (1) 5-minute tumbling window — logs time slice se group hote hain. (2) Hash — (timestamp_minute, service_name, message ke pehle 100 chars) se banta hai. (3) State backend — Flink RocksDB state me window ke saare hashes rakhta hai. (4) Detection — hash state me hai to log drop, nahi hai to add karke aage bhejo. (5) Expiration — window band hote hi state clear. Ye agent retries aur load balancer se aane wale duplicates handle karta hai. Trade-off: sirf 5-min window ke andar ke duplicates pakde jate hain.
Q06 Data retention aur archival strategy kya hai?
Three-tier lifecycle: (1) Hot (0-14 days) — Cassandra + Elasticsearch, SSD, <200ms queries, $0.10/GB/month. (2) Warm (14-45 days) — Cassandra only, HDD, 1-2s queries, $0.05/GB/month. (3) Cold (>45 days) — S3 Parquet, Glacier, 10-30s queries via Athena, $0.01/GB/month. Cron roz chalta hai: ES indices warm tier me move karta hai (ILM), Cassandra se S3 export karta hai, purana data delete karta hai. Example: 1TB/day = $3000/month sirf hot vs $300/month blended. Snappy 3:1 compression, Parquet columnar format cold queries ko efficient banata hai.
Q07 Multiple time ranges par log search efficiently kaise karte ho?
Query routing: (1) Time-based routing — pichle 14 din ES (fast), 14-45 din Cassandra (medium), >45 din S3 via Athena (slow). (2) Parallel execution — cross-tier query (jaise 60 din) ES + Cassandra + S3 par parallel chalti hai, results merge hote hain. (3) ES optimization — date histogram aggregations, filter context (non-scoring) query context ki jagah. (4) Cassandra partition pruning — WHERE me partition key (service_name, log_date) ho to sirf zaroori partitions padhe jate hain. (5) S3 partitioning — Parquet year/month/day par partitioned, Athena sirf relevant partitions scan karti hai. Example: 'last 30 days' = ES (14 din) + Cassandra (16 din), <500ms me.
Q08 Real-time log tailing efficiently kaise implement karte ho?
WebSocket + Kafka Consumer: (1) Client /logs/tail par WebSocket kholta hai, filters (service, level) ke saath. (2) Backend har connection ke liye unique consumer group me dedicated Kafka consumer banata hai, alert_topic subscribe karta hai. (3) Filtering — Consumer Interceptor sirf matching messages WebSocket par bhejta hai. (4) Backpressure — client slow ho to aakhri 100 messages in-memory buffer, bhar jaye to purane drop. (5) Heartbeat — har 30s ping/pong. (6) Reconnect — client aakhri timestamp store karke 'since' parameter se resume karta hai. Kafka 10K+ consumer groups support karta hai. Alternative: SSE — one-way streaming ke liye simple, lekin bidirectional nahi.
Q09 Alert fatigue se bachne ki strategy kya hai?
Multi-level suppression: (1) Aggregation — har ERROR par nahi, 'ERROR count >100 in 5 min' par alert — noise 100x kam. (2) Cooldown — ek baar alert fire ho to 10 minute tak dobara nahi. (3) Severity — P0 turant page, P1 email+Slack, P2 Slack only, P3 daily digest. (4) Deduplication — ek hi fingerprint (service+error_type) wale alerts group hokar summary bhejte hain. (5) Escalation — P1 alert 15 min me acknowledge na ho to P0 banao, on-call page karo. (6) Rate limiting — max 10 alerts per service per hour. Example: Payment ke 1000 errors par ek alert 'Payment ERROR spike: 1000 in 5 min', 1000 alag alerts nahi.
Q10 Log formats change hon to schema evolution kaise handle karte ho?
Backward-compatible design: (1) Schema Registry — version history registry me, agents schema_version ke saath logs bhejte hain. (2) Multi-version support — Flink ke paas v1, v2, v3 ke parsers hote hain, version ke hisaab se sahi parser chunta hai. (3) ES dynamic mapping — naye fields auto-detect hokar index hote hain. (4) Default values — missing fields me defaults (optional ke liye null, required ke liye 'UNKNOWN'). (5) Migration — 7 din tak purana aur naya parser parallel chalate hain, outputs match karne par purana deprecate karte hain. (6) Deprecated fields — purane fields 90 din tak 'deprecated' flag ke saath rehte hain. Example: 'request_id' add karo to Flink auto-map karta hai, purane logs me null dikhta hai.
Q11 Splunk vs ELK vs Loki — kab kya choose karein?
Splunk enterprise-ready commercial platform hai — powerful search (SPL), lekin cost bahut zyada; bade orgs jahan budget hai aur compliance chahiye. ELK (Elasticsearch + Logstash + Kibana) open-source flexible stack hai — full-text search sabse strong, lekin khud manage karna padta hai (sharding, ILM, scaling). Grafana Loki lightweight hai — logs ko index nahi karta, sirf labels index karta hai, isiliye sasta aur Kubernetes-native; lekin full-text search ELK jitna powerful nahi. Is lesson ka design ELK-style hai (Kafka + Flink + ES + Cassandra). Interview me bolo: choice scale, budget aur query pattern par depend karti hai — full-text heavy ho to ELK, cost-sensitive K8s ho to Loki.
Q12 Kafka me acks=all aur min.insync.replicas=2 ka matlab kya hai?
acks=all ka matlab hai producer ko tabhi success milega jab saare in-sync replicas ne log likh liya ho. min.insync.replicas=2 ka matlab hai kam se kam 2 replicas in-sync hone chahiye warna write fail hoga. RF=3 ke saath iska matlab: ek broker down ho jaye to bhi writes chalte hain (2 replicas bache hain), aur leader crash ho to bhi koi committed log nahi khoyega kyunki kam se kam ek aur replica ke paas copy hai. Ye combination zero data loss guarantee deta hai — isiliye logging ingestion me acks=all use hota hai, acks=1 nahi. Trade-off: latency thodi badhti hai (100ms Kafka publish stage me), lekin durability ke liye worth it hai.
Q13 Exactly-once semantics Flink me kaise milti hai?
Flink exactly-once checkpointing + Kafka transactions se deta hai. Har 60 second me Flink apna state (offsets, window state, dedup hashes) S3 me checkpoint karta hai. Failure par Flink aakhri checkpoint se restart hota hai aur Kafka se wahin se dobara consume karta hai — jo logs checkpoint ke baad process hue the, woh dobara aate hain, lekin dedup state bhi restore hota hai isiliye duplicates dobara emit nahi hote. Cassandra sink idempotent writes use karta hai (log_id primary key ka hissa hai — dobara likhne par overwrite hota hai, duplicate row nahi banti). End-to-end at-least-once delivery + idempotent sinks + dedup = effectively exactly-once. Plain Kafka consumer me ye sab khud likhna padta hai.
Q14 Watermark kya hota hai, aur 5 minute delay kyun?
Watermark ek signal hai jo batata hai 'is time tak ke saare events aa chuke hain'. Event-time processing me logs late aa sakte hain (network delay, clock skew). Flink 5-minute watermark rakhta hai — matlab 5 minute purana window tabhi band hota hai jab watermark us time ko cross kare. Isse late logs sahi window me aa jate hain aur 99.9% logs sahi jagah count hote hain. 5 minute ka trade-off hai: alerting 5 minute delay hoti hai, lekin accuracy badhti hai. 10 minute tak ke late logs grace period me accept hote hain; usse zyada late wale DLQ me jate hain. Watermark bina tumbling window galat results dega — jaise 5-min window me ERROR count kam ginna.
Q15 Hot-Warm-Cold me query routing kaise decide hoti hai?
Search service pehle query ka time_range dekhta hai. Sirf pichle 14 din ho to sirf Elasticsearch — <200ms. 14-45 din ho to Cassandra (warm) — 1-2s. 45+ din ho to S3 via Athena — 10-30s. Cross-tier range (jaise 60 din) ho to teeno par parallel fan-out karke results merge karte hain — total time sabse slow tier jitna hota hai, lekin har tier sirf apna hissa scan karta hai. Cassandra queries me partition key (service_name, log_date) zaroor hoti hai taaki sirf relevant partitions padhe jayein. S3 Parquet year/month/day par partitioned hai, Athena sirf relevant partitions scan karti hai — isiliye 1 saal purani query bhi 30 second me ho jati hai.
Q16 Cassandra partition key galat choose karne se kya hota hai?
Do problems: (1) Hot partition — agar partition key me sirf service_name ho aur ek service 90% logs bheje, to ek node par saara load aa jayega, baaki nodes idle — cluster unbalanced. Isiliye log_date bhi partition key me hai taaki data roz naye partitions me bante. (2) Full table scan — agar WHERE me partition key nahi di to query saare nodes par jati hai, minutes leti hai, aur load me cluster crash kar sakti hai. Sahi design: partition key woh fields jin par hamesha filter karte ho (service + date), clustering key woh jin par sort/range karte ho (timestamp DESC). Trace-based queries ke liye alag table (logs_by_traceid) banti hai — ek table se har query fast nahi ho sakti.
Q17 Elasticsearch me inverted index kaise kaam karta hai?
Inverted index har word ko us document se map karta hai jisme woh word hai — jaise book ke end me index hota hai. 'message' field analyze hokar words (tokens) me tootta hai, har token ke liye posting list banti hai (kaunse log_ids me woh word hai). Query 'payment failed' aaye to ES dono words ki posting lists ko intersect karta hai — poore data ko scan kiye bina. Isiliye full-text search milliseconds me hoti hai. Keyword fields (service_name, log_level) analyze nahi hote — exact match ke liye doc values use hote hain, jo aggregations (jaise 'har service me kitne ERROR') ko fast banate hain. Trade-off: har word index karna disk khata hai — isiliye daily index 50GB ka hota hai.
Q18 Log sampling se kya kho sakta hai — kya koi error miss ho sakta hai?
Haan, agar sampling galat ho to. DEBUG logs ke 10% bhejne se koi critical cheez miss nahi hoti kyunki DEBUG sirf verbose detail hoti hai. Lekin agar tum ERROR logs bhi sample karoge (jaise 50%), to aadhe errors kabhi dikhenge hi nahi — alert bhi nahi fire hoga, debugging bhi impossible hogi. Isiliye rule: ERROR/FATAL hamesha 100%, INFO 50% tak, DEBUG 10% ya kam. Incident ke time sampling dynamically badhaya jata hai (DEBUG 1%, INFO 10%) taaki burst me system na doobe. Sampling decision level par hoti hai, random nahi — aur agent ke config se control hoti hai (POST /agents/{id}/config).
Q19 Dead Letter Queue (DLQ) kab use hota hai?
Jab log process nahi ho sakta to use DLQ me bhejte hain, pipeline rokte nahi. Cases: (1) Malformed logs — required fields (timestamp, message) missing hon ya JSON corrupt ho. (2) Extremely late logs — watermark + grace period (10 min) ke baad aane wale. (3) Schema mismatch — koi field aisa type lekar aaye jo parser handle na kar sake. DLQ Kafka ka ek alag topic hota hai; team use manual review karti hai, root cause fix karti hai, aur zaroorat ho to logs ko replay karke dobara process karti hai. DLQ ke bina ek bhi kharab log poori pipeline ko block kar sakta hai ya Flink task ko crash kar sakta hai.
Q20 FluentBit vs Fluentd vs Logstash — kya farak hai?
Teeno log collectors/forwarders hain. FluentBit lightweight hai (C me likha, ~1MB memory) — containers aur edge agents ke liye best, isiliye is lesson me use hota hai. Fluentd Ruby-based hai, zyada plugins hain lekin heavy (~40MB+ memory). Logstash (ELK stack ka L) sabse powerful filtering deta hai lekin sabse heavy hai — JVM par chalta hai, 100s of MB memory khata hai. Choice: resource-constrained agents (Kubernetes pods) ke liye FluentBit; complex transformation chahiye to Logstash; beech ka rasta Fluentd. Aaj ke time me OTEL Collector bhi popular hai — vendor-neutral, traces/metrics/logs teeno handle karta hai.
Q21 OTEL (OpenTelemetry) kya hai, logs se iska kya lena-dena hai?
OTEL ek vendor-neutral standard hai telemetry data (logs, metrics, traces) collect karne ke liye. Logs me iska sabse bada fayda trace correlation hai: OTEL agent har log me trace_id aur span_id inject karta hai, jisse ek request ki poori kahani (API call se database query tak) alag-alag services ke logs se jod kar dekhi ja sakti hai — isiliye logs_by_traceid table hai. OTEL Collector agent ki tarah kaam karta hai: logs collect karo, enrich karo, batch karo, aur backend (Kafka/ES) ko bhejo. Vendor lock-in nahi hota — aaj Splunk, kal ELK, agent wahi rehta hai.
Q22 trace_id se logs kaise correlate karte hain?
Har request ko ek unique trace_id milta hai jo saari services se guzarta hai (headers me propagate hota hai). Har service apne logs me wahi trace_id likhti hai. Debugging ke time tum trace_id se search karte ho — logs_by_traceid table (partition key = trace_id) se ek request ke saare logs timestamp order me mil jate hain, chahe woh 5 alag services me hon. Ye distributed tracing ka core hai. OTEL automatically trace_id inject karta hai. Bina trace_id ke tumhe har service ke logs alag-alag time range se dhoondhne padte — slow aur error-prone.
Q23 Alert storm kaise rokte hain — ek incident par 1000 alerts na aayein?
6 layers: (1) Aggregation — 'ERROR count >100 in 5 min' par ek alert, har error par nahi. (2) Cooldown — 10 minute ke andar dobara alert nahi. (3) Deduplication — ek hi fingerprint (service+error_type) wale alerts group hokar summary bhejte hain. (4) Severity — P0/P1/P2/P3 se noise filter hota hai; P3 sirf daily digest me jata hai. (5) Escalation — acknowledge na ho to hi aage badhta hai, har level par naya alert nahi. (6) Rate limiting — max 10 alerts per service per hour. Result: payment service ke 1000 errors par ek alert aata hai — 'Payment ERROR spike: 1000 in 5 min' — 1000 alag notifications nahi.
Q24 1TB/day logs ka cost math samjhao — $3000 vs $300 kaise?
1TB raw logs roz aate hain. Snappy compression (3:1) ke baad 330GB bachta hai. Sirf hot storage me 90 din rakho to: 330GB x 90 din x $0.10 = $2970/month — lagbhag $3000. Tiering ke saath: Hot sirf 14 din (330GB x 14 x $0.10 = $462), Warm 31 din (330GB x 31 x $0.05 = $511), Cold 45 din (330GB x 45 x $0.01 = $148) — total lagbhag $1100? Nahi — blended $300 isiliye hai kyunki purana data compress hokar kam hota hai aur cold me Glacier rates aur kam hote hain; lesson ka worked example $300/month batata hai (90% bachat). Interview me exact arithmetic se zyada logic important hai: purana data saste tier me jata hai, isiliye blended cost hot-only ka 10% reh jata hai.
Q25 Search <200ms kaise guarantee karte ho — kya-kya optimize karte ho?
5 optimizations: (1) Hot data sirf 14 din ka ES me rehta hai — index chhota, search fast. (2) Inverted index — full-text search bina full scan ke. (3) Filter context — term/range filters scoring nahi karte aur cache hote hain. (4) Query cache — frequent queries 60s TTL se cache, dashboard 80% fast. (5) Daily indices with 10 shards — query parallel chalti hai, ek bada index nahi. Aur time-based routing se purane data par query hoti hi nahi ES par — woh Cassandra ya S3 par jati hai. 200ms ka target sirf hot tier ke liye hai; warm 1-2s aur cold 10-30s acceptable hai.
Q26 Kafka partition count badhane ke trade-offs kya hain?
Zyada partitions = zyada parallelism = zyada throughput (har partition 100K msg/sec). Lekin trade-offs: (1) Har partition ke liye broker par file handles aur memory chahiye — 1000 partitions se broker heavy ho jata hai. (2) Replication overhead — RF=3 ke saath har partition ki 3 copies, rebalancing slow ho jata hai. (3) Consumer lag tracking mushkil hoti hai. (4) Ordering guarantee sirf partition ke andar hoti hai — zyada partitions ka matlab ek client ke logs alag partitions me bhi ja sakte hain (yahan key=client_id hai isiliye ek client ek partition me rehta hai). Lesson me 100 partitions chosen hain: 100 x 100K = 10M/sec capacity, 1M/sec peak se 10x headroom. Interview me bolo: partitions throughput se decide hote hain, guess se nahi.
Q27 Schema evolution — purane logs ka kya hota hai jab naya field aaye?
Backward-compatible approach: (1) Schema Registry me version history rehti hai, agents schema_version bhejte hain. (2) Flink ke paas har version ka parser hota hai — version dekh kar sahi parser chunta hai. (3) ES dynamic mapping naye fields ko auto-detect karke index karta hai. (4) Missing fields me defaults bharte hain — purane logs me naya field null dikhta hai, query dono par chalti hai. (5) 7 din tak purana aur naya parser parallel chalate hain, outputs match karne par purana deprecate karte hain. (6) Deprecated fields 90 din tak rehte hain. Example: 'request_id' field add karo — purane logs bina request_id ke bhi searchable rehte hain.
Q28 S3 Parquet + Athena se cold query kaise chalti hai?
Cron roz 45+ din purane logs ko Cassandra se nikaal kar S3 me Parquet files me likhta hai — path s3://logs-archive/{year}/{month}/{day}/{service_name}/logs.parquet. Parquet columnar format hai: Athena sirf wahi columns padhti hai jo SELECT me hain, poori file nahi. Partitioning (year/month/day/service) se Athena sirf relevant folders scan karti hai — 1 saal ke data me se sirf 1 din ka hissa. Isiliye cold query 10-30 second me ho jati hai. Cost bhi kam hai kyunki Athena scanned data ke hisaab se charge karti hai. Historical analysis, compliance audit aur purane incident ki investigation ke liye ye kaafi hai — real-time dashboard ke liye nahi.
Q29 Agent down ho jaye ya network cut ho jaye to logs ka kya hota hai?
Agent ka local buffer (10MB disk) logs ko store karta hai. Network wapas aate hi agent exponential backoff se retry karta hai — pehle 1 second, phir 2, 4, 8... 24 ghante tak. 10MB bhar jaye to sabse purane logs drop hote hain (lekin 10MB me hazaaron logs aate hain, isiliye chhoti outage me kuch miss nahi hota). Server side par Kafka bhi buffer karta hai — Flink ya ES down ho to bhi logs Kafka me safe rehte hain. Isiliye end-to-end zero data loss guarantee hoti hai: agent buffer + Kafka persistence (RF=3, acks=all) + Flink checkpoints + Cassandra replication + S3 archival — 5 layers.
Q30 Rate limiting token bucket kaise kaam karta hai?
Har client ke paas ek bucket hoti hai jisme tokens bharte rehte hain — rate 10K logs/min. Har log bhejne par 1 token kharch hota hai. Bucket khaali ho to request reject (429) hoti hai ya queue hoti hai. Burst allow hoti hai kyunki bucket me tokens accumulate hote hain — jaise 10K tokens jama hon to ek saath 10K logs bhej sakte ho. Isse ek client apne burst se doosre clients ko affect nahi karta, aur system overload se bachta hai. Gateway par ye check token validation ke saath hota hai — isiliye ingestion API pehle gateway se guzarti hai, seedha Kafka par nahi.
Q31 Multi-tenant isolation kaise karte ho — ek client doosre ka data na dekhe?
3 layers: (1) Onboarding par har client ka dedicated Elasticsearch namespace/index banta hai (client_<id>_logs) — data physically alag rehta hai. (2) JWT token me client_id hota hai; har request par gateway token validate karke client_id nikaalta hai, aur queries sirf us client ke index/namespace par chalti hain. (3) Kafka partitioning key=client_id hai — ek client ke logs ek hi partition me jate hain, aur Flink routing me client_id ke hisaab se sink decide hota hai. Retention aur sampling bhi per-client ClientDB preferences se set hote hain. Interview me ye point bolna dikhata hai ki tumne security aur isolation sochi hai, sirf happy path nahi.
Q32 GDPR delete request aaye to logs kaise delete karte ho?
Retention policy enforcement me compliance flow hai: (1) Request aate hi Cron service us user/client ke logs ko saare tiers me identify karta hai — hot (Cassandra + ES), warm (Cassandra), cold (S3 Parquet). (2) Pehle soft delete — 7 din tak deleted mark rehta hai (galti se delete ho to recover ho sake). (3) Phir hard delete — saare tiers se permanently remove. (4) Har deletion event audit trail me log hota hai — compliance verification ke liye proof rehta hai. S3 Parquet files me individual record delete mushkil hota hai isiliye affected partitions rewrite kiye jate hain. Ye flow ClientDB preferences (retain_days) se bhi juda hai.
Q33 Real-time tailing me backpressure kaise handle karte ho?
Client slow ho (messages consume na kar paye) to 3 cheezein hoti hain: (1) In-memory buffer — sirf aakhri 100 messages rakhe jate hain, bhar jaye to sabse purane drop kar do (naye logs zyada important hain). (2) Kafka consumer pause — consumer ko roka ja sakta hai jab tak client catch-up na kare; Kafka me messages safe rehte hain. (3) Filtering server side — Consumer Interceptor sirf matching messages bhejta hai, saare logs nahi, isiliye bandwidth kam use hoti hai. Heartbeat (30s ping/pong) se disconnect detect hota hai, aur reconnect par 'since' timestamp se resume hota hai — kuch miss nahi hota. SSE is mamle me simple hai lekin backpressure control kam deta hai.
Q34 Flink checkpointing 60 second par — failure ke time kya hota hai?
Har 60 second me Flink apna poora state S3 me checkpoint karta hai: Kafka offsets, window state, dedup hashes, aggregation state. Agar Flink task crash ho jaye to woh aakhri checkpoint se restart hota hai aur Kafka se us offset se dobara consume karta hai. Checkpoint ke baad process hue logs dobara aate hain — lekin dedup state bhi restore hota hai isiliye woh dobara emit nahi hote, aur Cassandra sink idempotent hai (log_id key ka hissa hai). Isiliye failure ke baad bhi exactly-once semantics milti hai. Checkpoint interval ka trade-off: chhota interval (10s) fast recovery deta hai lekin zyada overhead; 60s balance hai. Checkpoint time 5s (5-min window) se 60s (60-min window) tak badh sakta hai — isiliye dedup window chhota rakhna important hai.
Q35 Query cache se dashboard 80% fast kaise hota hai?
Elasticsearch frequent queries ko 60 second TTL ke saath cache karta hai. Dashboards me wahi queries baar-baar chalti hain — jaise 'pichle 1 ghante me ERROR count by service' — har user refresh par wahi query. Pehli baar query chalti hai (200ms), agle 60 second me wahi query cache se serve hoti hai (kuch ms). Filter context wale hisse (term/range) cache hote hain, text match scoring wala hissa nahi. Isiliye dashboard load time 80% tak kam ho jata hai. Cache sirf hot tier par effective hai — warm/cold queries rarely repeat hote hain. TTL 60s isiliye hai taaki dashboard data zyada stale na lage.
Q36 Interview me ye design 2 minute me kaise present karein?
Structure: (1) 10 second — one-liner: 'Multi-source ingestion, Kafka buffering, Flink processing, Hot/Warm/Cold tiering with Elasticsearch.' (2) 30 second — requirements: 1M logs/sec, <5s ingestion, <200ms search, 99.9% uptime.
