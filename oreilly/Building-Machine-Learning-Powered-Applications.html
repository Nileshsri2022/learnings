From Product Goal to ML Framing

ML project shuru karne se pehle sabse pehla kaam hai product goal ko ML ki bhasha me translate karna. Model banana aakhri step hai — pehle ye tay karo ki ML se kya hoga, kya possible hai, aur kaunsa data chahiye. Is chapter me wahi framing seekhenge, ML Editor case study ke saath.

ML kab use karein, kab nahi?

ML har problem ka jawab nahi hai. Agar kaam deterministic rules se ho sakta hai, to ML mat lagao. Book ka example: tax calculate karna — tax ke rules fixed hain, to wahan ML lagana bewakoofi hai, rules likhna behtar hai.

  • ML tab use karo jab rules likhna mushkil ho ya rules bahut zyada ho jaayein — jaise spam pehchanna, photo me cheez dhoondhna, ya user ko recommendation dena.
  • ML mat use karo jab exact, explainable aur 100% sahi jawab chahiye ho (tax, billing, legal calculation).
  • ML tab bhi mat use karo jab data hi nahi hai ya problem abhi clearly define hi nahi hui.

2-step framing

Product goal ko ML me badalne ke 2 steps hain:

  1. Product goal ko ML paradigm me frame karo — ye classification hai? regression? ranking? generation?
  2. Feasibility evaluate karo — kya data hai? kya model itna achha ho sakta hai ki product kaam kare? kya latency/cost allow karti hai?

Dono steps pehle karo, model baad me. Bahut se projects isliye fail hote hain kyunki framing hi galat thi — model achha bhi ho to product kaam nahi karta.

ML Editor — case study kya hai?

Poori book me ek hi running example hai: ML Editor — ek tool jo users ko behtar sawaal (questions) likhne me madad karta hai. Stack Exchange (Writing community) ke questions ka data use hota hai. Goal: question ki quality judge karke actionable suggestions dena — jaise "question lamba karo", "question marks kam karo".

Product goal: users ko behtar questions likhne me madad karna. ML framing: question ko high-score / low-score me classify karo (upvotes se weak label), phir us classifier se recommendations nikalo.

Yaad rakho: ML Editor sirf ek example hai — iske through book ke saare concepts (framing, plan, pipeline, data, training, debugging, deployment, monitoring) ek hi kahani me samjhaye gaye hain.

Estimate What Is Possible — ML kab use karein?

Koi bhi ML project shuru karne se pehle ye andaza lagao ki kya possible hai. Agar best-case model bhi product goal poora na kar paye, to project shuru karna hi bekaar hai.

Possibility kaise estimate karein?

  • Human performance dekho: agar insaan khud ye kaam achhe se nahi kar sakta, to model se bhi ummeed kam rakho. Question quality judge karna insaan ke liye bhi subjective hai — isliye ML Editor ka target 100% accuracy nahi, useful suggestions hain.
  • Simple baseline banao: pehle sabse simple tareeka try karo (heuristics, rules). Agar simple baseline hi kaafi achha hai, to shayad ML ki zaroorat hi nahi.
  • Impact bottleneck dhoondho: product ka sabse bada dard kahan hai? Wahi jagah ML lagao jahan impact sabse zyada ho. Har jagah ML ghusana galat hai.
  • State of the art dekho: aisi problem pehle kisi ne solve ki hai? Papers, open-source code, Kaggle — kya results mile the?

ML use karne ke 3 sawaal

  1. Kya problem rules se solve nahi ho sakti?
  2. Kya mere paas (ya bana sakta hoon) data hai jo input ko output se jodta hai?
  3. Kya model ki galtiyan acceptable hain — ya har galti mehngi padegi?

Teeno ka jawab "haan" ho, tabhi ML sahi choice hai. Tax example me pehla sawaal hi "nahi" hai — isliye wahan ML nahi.

Interview point: "Why ML?" ka jawab hamesha business/product se do, technology se nahi. Interviewer ye sunna chahta hai ki tumne ML ko default solution nahi banaya, soch-samajh kar chuna hai.

4 Tarah ke Models

Product goal ko ML me frame karne ka matlab hai — ye tay karna ki kaam kis type ka ML problem hai. Book 4 bade categories batati hai. Sahi category pehchanna hi aadhi framing hai.

1. Classification aur Regression

Classification: input ko ek category me daalo — jaise spam / not-spam, achha question / kharab question. Regression: number predict karo — jaise ghar ki keemat, ya question ko kitne upvotes milenge.

  • Isi me aate hain: time-series forecasting (aane wale time ka value predict karna) aur anomaly detection (aisa data dhoondhna jo normal se alag ho — jaise fraud).
  • ML Editor: classification — question high-score hai ya low-score.

2. Knowledge Extraction

Unstructured data (text, image, audio) se structured information nikaalna. Example: receipt ki photo se amount aur date nikaalna; text se naam, jagah, tareekh nikaalna (NER).

  • Images me: object detection (box banao cheez ke aas-paas) vs segmentation (har pixel ko label do — kaunsa pixel kis cheez ka hai).
  • Ye woh category hai jahan deep learning ne sabse bada farak dala hai.

3. Catalog Organization

Bade catalog ko organize karna — recommendations aur search. Do tareeke:

  • Collaborative filtering: "jin users ko ye pasand aaya, unhe wo bhi pasand aaya" — dusre users ke behaviour se seekho.
  • Content-based: item ki khaasiyat (features) se match karo — jaise similar articles suggest karna.

4. Generative Models

Naya content banana — text, image, audio generate karna. Book ki salah: generative se shuru mat karo. Ye sabse risky category hai — output unpredictable hota hai, evaluate karna mushkil hai, aur galtiyan mehngi padti hain. Pehle baaki 3 categories se kaam chalao; generative tabhi jab zaroorat pakki ho.

Supervised, Unsupervised, Weakly Supervised

  • Supervised: har example ke saath sahi label hai (jaise question + uska score). Sabse common, sabse reliable.
  • Unsupervised: koi label nahi — patterns khud dhoondho (clustering, dimensionality reduction).
  • Weakly supervised: labels hain par noisy/imperfect hain — jaise Stack Exchange ke upvotes ko "quality" ka label maan lena. ML Editor yahi use karta hai.

Data: Types, Availability aur Iteration

ML me sabse bada sach: model se zyada data matter karta hai. Framing karte waqt hi ye dekh lo ki data kis haalat me hai — warna aadhe raaste me pata chalega ki model ke paas seekhne ko kuch hai hi nahi.

Data availability ke 4 levels

  1. Labeled data: sahi labels ke saath tayyar data — sabse achha, sabse mehnga.
  2. Weakly labeled data: labels hain par imperfect — jaise upvotes, clicks, user behaviour. Sasta, par noise hai.
  3. Unlabeled data: sirf raw data, koi label nahi — label karna padega ya unsupervised tareeke use karne honge.
  4. Data acquire karna padega: data hai hi nahi — collect karna, khareedna, ya users se mangna padega. Sabse lamba raasta.

Datasets iterative hote hain

Dataset ek baar me perfect nahi banta. Research me dataset fixed hota hai; industry/product me dataset product ke saath badalta rehta hai — naya data aata hai, labels improve hote hain, naye cases add hote hain. Isliye dataset ko version karo, aur har iteration me use improve karo.

  • Pehla dataset chhota rakho — jo memory me aasani se aaye, jise jaldi explore kar sako.
  • Data se insights nikalo pehle (EDA), phir product banao — insights se pata chalta hai ki kya patterns hain.
  • Har iteration me ye poochho: "aur kaunsa data model ko behtar banayega?"

Data types — ek jhalak

Tabular (rows/columns), text, image, audio, video, time-series — har type ki apni vectorization aur modeling ki zaroorat hoti hai (detail Chapter 4 me). Framing ke waqt hi note kar lo ki tumhara data kis type ka hai, kyunki usi se model family tay hoti hai.

ML Editor Case Study: 3 Approaches

ML Editor ko banane ke 3 tareeke soche gaye — aur teeno ko compare karke hi pata chala ki kaunsa sahi hai. Ye framing ka sabse achha example hai: ek hi product goal, 3 alag ML framings.

Approach 1: End-to-end generative (seq2seq)

Poora question input lo, behtar question output do — ek hi neural model sab kuch kare. Sounds fancy, par problems:

  • Data: behtar question ke pairs (pehle → baad me) chahiye — aisa labeled data hai hi nahi.
  • Latency: bada model, dheema inference — typing karte waqt suggestions chahiye, 2 second ka wait nahi chalega.
  • Implementation: complex, debug karna mushkil, galti par control nahi.

Approach 2: Simplest heuristics ("Be the Algorithm")

Khud socho — achha question kaisa hota hai? Rules likho: prose simple ho, tone sahi ho, structure clear ho (question marks, length, readability). Ye Chapter 3 ka pehla prototype bana.

  • Fayda: turant kaam karta hai, explainable hai, koi training nahi chahiye.
  • Nuksaan: rules se aage nahi badh sakta — har nayi baat ke liye naya rule likhna padega.

Approach 3: Middle ground — classifier (CHUNA GAYA)

Question ko high/low quality me classify karo (random forest, <0.1s inference), phir classifier ki samajh se recommendations nikalo. Upvotes ko weak label banao.

  • Fast hai, simple hai, explainable features par chalta hai.
  • Classifier ka score user ko dikhaya ja sakta hai — feedback loop banta hai.
  • Book ka poora aage ka kaam isi approach par hai.
Lesson: sabse powerful model mat chuno — sabse simple model chuno jo product goal poora kare. Complexity tabhi badhao jab simple wala fail ho jaye.

Monica Rogati Interview: Project Kaise Chunein

Monica Rogati (data science leader) se interview — ML projects ko choose aur prioritize kaise karein. Ye chapter ka practical hissa hai.

Confidence thresholds — 90% / 50% rule

  • Jab model 90%+ confident ho, to uski prediction par action lo (auto-apply).
  • Jab confidence 50% ke aas-paas ho, to user ko dikhao ya human review me bhejo — model khud decide na kare.
  • Beech wale cases ke liye alag UX socho — har prediction ko ek jaise treat mat karo.

Impact bottleneck

Project chunte waqt ye dekho ki impact kahan atak raha hai — data ki kami se? model ki accuracy se? ya product me model ko dikhane ke tareeke se? Aksar bottleneck model nahi hota — data ya UX hota hai. Wahi pehle fix karo.

Strawman baseline

Shuru me ek strawman (jaan-bujh kar simple, kamzor baseline) banao — taaki har naye model ko usse compare kar sako. Bina baseline ke tumhe pata hi nahi chalega ki model waqai behtar hai ya sirf lag raha hai.

"Be the algorithm" aur labeling

  • Khud algorithm bano: data ko haath se dekho, label karo — tabhi pata chalega ki patterns kya hain.
  • Top 100 examples label karo — aksar top 100 se hi 80% coverage mil jata hai (common cases wahi hote hain).
  • Labeling se pehle domain samjho — bina domain samjhe label karna kachra labels deta hai.

Create a Plan

Framing ke baad plan banao — bina plan ke model banana andhere me teer chalana hai. Plan me 4 cheezein tay hoti hain: metrics, prior art, data sources, aur pehla pipeline.

Plan ke 4 pillars

  1. Metrics: success kaise naapoge? Business metric kya hai, model metric kya hai — aur dono ka connection kya hai?
  2. Prior art: kisi ne ye problem pehle solve ki hai? Unka code/model/data reuse kar sakte ho?
  3. Data: data kahan se aayega — open data, apna data, ya label karna padega?
  4. Pipeline: training pipeline aur inference pipeline — dono ka pehla simple version kya hoga?

ML Editor ka plan (example)

  • Data: Stack Exchange dump (XML) — questions + upvotes (weak label).
  • Model: scikit-learn text classification — simple se shuru.
  • Metrics: business metric = users ke questions ki quality badhna; model metric = precision (galat suggestion dena mehenga hai).
  • Pipeline: pehle training pipeline, phir inference pipeline — dono me same preprocessing (ye golden rule hai).

Simple model se shuru karo

Plan me likh lo: pehla model simple hoga. Simple model jaldi banta hai, jaldi debug hota hai, aur usse baseline milta hai. Complex model baad me — jab simple wala apni limit dikha de.

Training vs Inference pipeline: training me model seekhta hai, inference me wahi model predictions deta hai. Dono me preprocessing bilkul same honi chahiye — warna training-serving skew hoga (model ne kuch aur seekha, production me kuch aur aa raha hai).

Metrics: Business, Model, Freshness, Speed

Metrics 4 tarah ki hoti hain — aur sirf ek hi category hai jo asal me matter karti hai: business metrics. Baaki teeno uski seva me hain.

4 metric categories

  • Business metrics: product/business ka fayda — revenue, retention, user satisfaction, questions ki quality. Yehi ek matra metric hai jo asal me matter karti hai.
  • Model metrics: offline metrics — accuracy, precision, recall, F1, BLEU, cross-entropy. Ye tabhi useful hain jab ye business metric se correlate karein.
  • Freshness metrics: model kitna fresh hai — data kab ka hai, distribution shift to nahi hua?
  • Speed metrics: latency, throughput — model kitni der me jawab deta hai.

Guardrail metrics

Business metric ke saath guardrail metrics bhi rakho — aisi metrics jo bigadna nahi chahiye jab tum main metric improve karo. Example: recommendations ki precision badhate waqt ye bhi dekho ki kisi group ke users ke liye performance to nahi gir rahi.

Offline metric vs Product metric — connection zaroori hai

Offline metric (jaise BLEU ya cross-entropy) tabhi bharosa layak hai jab wo product metric ke saath chale. Book ka example: text generation me BLEU badhna zaroori nahi ki user ko behtar lage. Isliye hamesha check karo — model metric badhne par product metric bhi badhti hai ya nahi?

Reframing se modeling aasan banti hai

  • Word prediction ki jagah category classifier banao — problem aasan ho jati hai.
  • Threshold badlo: sirf high-confidence predictions dikhao.
  • Ek ki jagah 5 candidates dikhao — user khud chun le.
  • Precision vs recall: recommendations me precision zyada matter karta hai — galat suggestion dena, na dene se bura hai.

Freshness aur distribution shift

Duniya badalti hai, data badalta hai. Example: baarish me traffic pattern badal jata hai — purane data par trained model fail karega. ML Editor ko saal me ek baar retrain karna padta hai kyunki likhne ke trends badalte hain. Freshness metric ye batati hai ki model kab stale ho gaya.

Speed — latency budget

ML Editor pipeline ka budget 2 seconds se kam tha. LSTM 22ms leta tha, random forest sirf 7ms — isliye simple model jeeta. Speed sirf model ki nahi, poori pipeline ki hoti hai (preprocessing + inference + postprocessing).

Prior Art: Reproduce, Adapt, Iterate

Duniya me kisi ne tumhari problem jaisi problem pehle solve ki hogi. Prior art dhoondhna plan ka sabse time-bachane wala step hai — dobara wheel mat banao.

3-step adaptation

  1. Reproduce karo: pehle existing solution ko jaisa hai waisa chalao — unke data, unke code par. Agar reproduce nahi hota, to samjho ki kuch gadbad hai.
  2. Apne data ke kareeb lao: apne dataset par chalao, dekho kya toot-ta hai.
  3. Metrics par iterate karo: ab apne metrics ke hisaab se improve karo.

Book ka example: pix2code aur image captioning ke open-source implementations ko pehle reproduce kiya, phir apne kaam par adapt kiya.

Open data sources

  • Internet Archive, r/datasets, Kaggle, UCI Machine Learning Repository, Google Dataset Search, Common Crawl, Wikipedia lists — free data ke bade sources.
  • Open data se shuru karo — pehla prototype banane ke liye kaafi hota hai.

Domain expertise

Experts se seekho — domain ke logon se baat karo, khud data explore karo (EDA), aur khud label karo. Khud labeling karne se tumhe data ki asli samajh aati hai jo koi metric nahi de sakti.

Training vs Inference pipeline — functions

Plan me dono pipelines ke functions likh lo. Training pipeline: data load → clean → features → train → evaluate → save model. Inference pipeline: request validate → preprocess (same as training!) → predict → postprocess → return. Preprocessing dono me same — ye sabse common bug ki jad hai.

Build Your First End-to-End Pipeline

Plan ban gaya — ab pehla end-to-end pipeline banao. Rule: simplest scaffolding pehle. Pehle inference chalao, phir training. Pehle heuristics wala MVP banao, phir ML.

Scaffolding pehle, model baad me

Galti ye hoti hai ki log pehle model train karne lagte hain. Sahi kram:

  1. Inference pipeline pehle: input lo → process karo → output do. Model ki jagah pehle heuristic ya dummy output rakho.
  2. Heuristics as MVP: rules se pehla version chalao — user ko dikhao, feedback lo.
  3. Phir training pipeline: jab data flow pakka ho jaye, tab model train karo aur heuristic ki jagah lagao.

Isse tumhe jaldi pata chalta hai ki product kaam karta bhi hai ya nahi — model ke bina hi.

4 functions — poori pipeline

ML Editor ke pehle pipeline me 4 functions the:

  1. parse_arguments — command-line arguments padho.
  2. clean_input — input saaf karo (sirf ASCII characters rakho).
  3. preprocess_input — tokenize karo (nltk sent_tokenize / word_tokenize).
  4. get_suggestions — heuristics se suggestions nikalo.

Tokenization pitfalls

Text ko todna aasan nahi hai. Example: "Mr. O'Neill" — naive tokenizer "Mr." ko sentence ka ant samajh lega, aur "O'Neill" ko tod dega. Isliye achhi tokenization library use karo (nltk, spaCy), khud ka splitter mat likho.

Test workflow — 2 tarah ki testing

  • UX testing: kya user ko suggestions samajh aate hain? kya wo actionable hain?
  • Modeling results testing: kya suggestions sahi hain? Example: DCG@5 se DCG@3 par jaana — kam suggestions, zyada relevant.

Impact bottleneck — product side vs model side

Model achha ho, phir bhi product fail ho sakta hai. Example: paper acceptance prediction — model sahi ho, par user ko usse kya fayda? Doosri taraf credit scoring — model me bias ho to product harmful hai. Hamesha dono side dekho: model kitna achha hai aur product me uska asar kya hai.

Prototype evaluation — Flesch reading ease

Heuristic prototype me readability Flesch score se naapi gayi:

  • Simple question: 100.26 — "Very easy"
  • Convoluted (uljha hua) question: 47.58 — "Difficult"
  • Ek paragraph: 56.79 — "Fairly difficult"

Seekh: suggestions overwhelming ya irrelevant nahi hone chahiye — actionable hone chahiye. Highlight/underlining se user ko dikhao ki kya badalna hai, lambi list mat thopo.

Pehla Pipeline: 4 Functions aur Heuristics

Heuristic pipeline ka code kaisa dikhta hai? Ye section pehle prototype ki andar ki baat batata hai — taaki tum apna MVP aise hi bana sako.

get_suggestions — heuristics kya dekhte hain?

Heuristic version ye features dekhta tha:

  • told / said jaise reporting verbs — kya question me kaha-suni hai?
  • but / and — conjunctions ki frequency.
  • wh-adverbs (when, where, why) — sawaal wale words.
  • Average word length aur unique-word fraction — vocabulary diversity.
  • Syllables aur Flesch reading ease — readability score.

Heuristics ka fayda — fallback bhi hai

Acquire an Initial Dataset

Model se zyada dataset matter karta hai. Is chapter me dataset acquire karna, explore karna, quality check karna, label karna aur features banana — poora kaam hai.

Datasets iterative hote hain

Research me dataset fixed hota hai — ek baar download kiya, bas. Industry/product me dataset kabhi fixed nahi hota: naya data aata rehta hai, labels badalte hain, product badalta hai to data bhi badalta hai. Isliye dataset ko bhi version karo aur har iteration me improve karo.

Chhota se shuru karo

  • Pehla dataset chhota rakho — jo memory me aasani se aaye.
  • Insights nikalo pehle (EDA) — data kya keh raha hai, ye samjho.
  • Phir dheere-dheere badhao — poora data ek saath mat uthao.

ML Editor dataset — Stack Exchange dump

Stack Exchange ka XML dump parse kiya gaya (BeautifulSoup se parse_xml_to_csv). df.info() se pata chala:

  • Kul 33,650 posts
  • 3,584 posts jin ke koi answers nahi
  • 5,933 posts jin ke answers hain
  • 4,964 posts jin ke accepted answers hain

Summary statistics — pehli nazar me kya dikha?

  • Histograms se pata chala: high-score questions lagbhag 800 characters lambe hote hain — low-score se lambe.
  • Length hi pehla strong signal tha — jo aage feature bana (text_len).
  • Summary statistics se hi pata chalta hai ki data me kya patterns chhupe hain.

Explore and Label Efficiently

Saara data haath se label karna impossible hai. Tareeke:

  • Clustering (k-means) — similar examples ko group karo, phir har group ke kuch examples label karo.
  • Elbow / silhouette se clusters ki sankhya tay karo.
  • Be the Algorithm — khud data ko dekho, Bokeh interactive plots se explore karo, aur label karte waqt patterns dhoondho.

Vectorizing: Tabular, Text, Image

Model numbers samajhta hai, text/image nahi. Vectorizing ka matlab hai — har type ke data ko numbers (vectors) me badalna. Har type ka apna tareeka hai.

Tabular data

  • Normalize karo: zero-mean, unit-variance — taaki ek feature dusre ko daba na de.
  • One-hot encoding: categorical values (jaise city, category) ko 0/1 columns me badlo.
  • Date features: date ko tod do — day, month, weekday, "is_weekend" jaise features banao.
  • Leakage warning: normalizer ko sirf training data par fit karo — test data par fit karna leakage hai (Chapter 5 me detail).

Text data

  • Bag-of-Words: har word ki count — order bhool jao, sirf kaunse words aaye ye dekho.
  • TF-IDF: TfidfVectorizer — common words ko kam, rare-informative words ko zyada weight.
  • Word2Vec (2013): distributional hypothesis — "jo words ek jaise context me aate hain, unke matlab ek jaise hote hain." Words ko dense vectors me badlo.
  • fastText: sub-word information — rare/misspelled words ko bhi handle karta hai.
  • spaCy pretrained vectors, BERT / ULMFiT (2018): bade models se seekhe hue representations — transfer learning text me.

Image data

  • Images tensors hoti hain (height × width × channels).
  • Transfer learning: VGG / Inception jaise ImageNet par trained models ki penultimate layer (fc2) se features nikalo — khud se train karne ki zaroorat nahi.
  • Warning: pretrained model apne training data ka bias bhi laata hai — blindly bharosa mat karo.

Dimensionality reduction — visualize karo

  • t-SNE, UMAP: high-dimensional vectors ko 2D me dikhao — clusters dikhenge.
  • Hinton ka quote: visualization se pata chalta hai ki data me structure hai ya nahi — model se pehle aankh se dekho.

Features Banao: Patterns se Features

Features hi model ki "aankhein" hain — model wahi dekh sakta hai jo features dikhate hain. Data exploration se patterns dhoondho, phir un patterns ko features banao.

Feature generation ke tareeke

  • Raw value se behtar: Unix datetime (raw number) ki jagah day-of-week aur day-of-month alag features banao — model ko samajh aayega.
  • Feature crosses: do features ko milao — jaise DoW × DoM (day-of-week × day-of-month). Kuch patterns tabhi dikhte hain jab features combine hon.
  • "Model ko jawab mat do": aisa feature mat banao jo label ko seedha leak kare — jaise is_last_two_weekends binary agar wo label se seedha juda ho. Ye leakage hai.

ML Editor ke features

  • Action verbs — can / should jaise words ki frequency.
  • has_question — kya text me asal me question hai?
  • is_language_question — kya question English language ke baare me hai?
  • Normalized length — text_len ko normalize karke.
  • Title text — sirf body nahi, title bhi informative hai (baad me add kiya gaya).

Robert Munro interview — labeling ki samajh

  • Business problem pehle: labeling shuru karne se pehle ye tay karo ki kya solve karna hai.
  • Batch vs live constraints: batch labeling sasti hai, live (real-time) labeling me latency matter karti hai.
  • Kitne labels chahiye: rare category ke ~1,000 labels se shuru karo; bharosa karne ke liye ~10,000 chahiye.
  • Uncertainty sampling: model jin examples par unsure hai, unhe pehle label karo — sabse zyada fayda wahi se.
  • Error model aur labeling model: model ki galtiyon ka pattern dekho, aur labeling process ko bhi model karo.
  • Random-sample test set: test set hamesha random sample ho — warna validation jhooth bolega.
  • Drift tracking: data badal raha hai ya nahi, ye track karo.

Robert Munro — Figure Eight (ek badi data labeling company) ke pehle CTO, aur usse pehle AWS ki pehli native NLP aur machine translation services par product lead — se interview. Munro ne kai AI companies banayi hain aur top ML teams banayi hain. Is interview me woh batate hain ki dataset kaise banayein, label karein aur use karein — ye Chapter 4 ka practical hissa hai.

ML project kaise shuru karein? Business problem se

Shuruaat hamesha business problem se karo — wahi tumhe boundaries deta hai. ML Editor ka example lo: kya tum text ko submit hone ke baad edit kar rahe ho, ya user likhte waqt live suggestions de rahe ho? Pehle wale me tum requests ko batch me process kar sakte ho, dheema model bhi chalega. Doosre wale me model ko tez hona hi padega.

  • Live suggestions me seq2seq model nahi chalega — woh bahut dheema hota hai, aur aaj ke seq2seq models sentence-level se aage kaam hi nahi karte, aur unhe train karne ke liye bahut saara parallel text chahiye hota hai.
  • Tez solution ye hai ki classifier use karo aur uske important features ko suggestions ki tarah dikhao.
  • Pehle model se tumhe do cheezein chahiye: easy implementation aur results jin par bharosa kar sako — jaise bag-of-words features par naive Bayes.
  • Khud data ko dekho aur label karo — isse tumhe intuition milega ki problem kitni mushkil hai aur kaunsa solution fit baith sakta hai.

Kitna data chahiye? 1,000 se signal, 10,000 se bharosa

Data jama karte waqt tumhe ye guarantee karna hai ki dataset representative aur diverse ho. Pehle apne paas jo data hai use dekho — koi type kam to nahi hai? Agar koi type underrepresented hai, to uska aur data jama karo. Dataset ko cluster karke outliers dhoondhna is kaam ko tez kar deta hai.

  • Classification me rarer category ke lagbhag 1,000 labeled examples kaafi hote hain shuruaat ke liye — itne se tumhe itna signal mil jata hai ki tum jaan sako ki current modeling approach se aage badhna hai ya nahi.
  • Lagbhag 10,000 examples par tum apne models ki confidence par bharosa karna shuru kar sakte ho.
  • Jaise-jaise data badhta hai, accuracy dheere-dheere badhti hai — isse tumhe ek scaling curve milta hai. Har point par tumhe sirf curve ka aakhri hissa dekhna hai, jo batata hai ki aur data se abhi kitna fayda milega.
  • Zyaada cases me aur data label karna, model ko iterate karne se zyaada fayda deta hai.

Data gather aur label karne ka process — 3 smart tareeke

Apne current best model ko dekho aur samjho ki use kya pareshan kar raha hai — wahi se agla data dhoondho:

  • Uncertainty sampling: woh examples dhoondho jin par model sabse zyaada uncertain hai — jo uske decision boundary ke sabse kareeb hain — aur unke jaise aur examples training set me daalo.
  • Error model: model ki galtiyon ko hi label banao — har data point ko "predicted correctly" ya "predicted incorrectly" label karo. Phir in examples par ek error model train karo, use apne unlabeled data par chalao, aur woh examples label karo jin par error model kehta hai ki tumhara model fail hoga.
  • Labeling model: maan lo tumhare paas 10 lakh examples hain jinme se sirf 1,000 labeled hain. 1,000 randomly sampled labeled images aur 1,000 unlabeled images se ek training set banao, aur ek binary classifier train karo jo ye predict kare ki kaunsi image labeled hai. Phir is labeling model se woh data points dhoondho jo tumhare labeled data se sabse alag hain, aur unhe label karo.

Validate kaise karein ki model kuch useful seekh raha hai?

Ek common pitfall ye hai ki labeling ki mehnat dataset ke ek chhote hisse par hi lag jaye. Ho sakta hai tumhara model basketball par likhe articles se pareshan ho. Agar tum basketball articles hi label karte raho, to model basketball me bahut achha ho jayega — par baaki sab me kharab.

  • Isliye, data gather karne ki strategies use karte hue bhi, hamesha apne test set se randomly sample karke model ko validate karo.
  • Sabse achha tareeka ye hai ki deployed model ki performance kab drift kar rahi hai, use track karo — model ki uncertainty ko track karo, ya usse bhi behtar, use business metrics se jodo: kya tumhare usage metrics dheere-dheere neeche ja rahe hain?
  • Usage girna aur bhi wajah se ho sakta hai, par ye ek achha trigger hai — investigate karo aur zaroorat pade to training set update karo.
Lesson: data se shuru karo, model se nahi. 1,000 labels se signal, 10,000 se bharosa — aur jab model atak jaye, to pehle ye socho ki kaunsa data use chahiye, model ko tweak karne se pehle.

Train/Val/Test Split aur Data Leakage

Model ko judge karne ke liye data ko 3 hisso me baanto — aur baant-te waqt data leakage se bacho. Ye chapter ki sabse important cheez hai; interview me bhi sabse zyada poochhi jati hai.

Train / Validation / Test — kya kaam hai?

  • Training set (~70%): model isi par seekhta hai.
  • Validation set (~20%): hyperparameters tune karne aur model choose karne ke liye.
  • Test set (~10%): aakhri benchmark — sirf ek baar, ant me. Test par kabhi tune mat karo.

Data Leakage — 2 tarah

  • Temporal leakage: future ki information training me aa jaye. Example: booking prediction me previous_bookings ka snapshot — agar wo future bookings include kare, to leakage hai.
  • Sample contamination: train aur test me same entity aa jaye — jaise same student ya same author dono taraf ho. Model author ko pehchan kar yaad kar lega, generalize nahi karega.

ML Editor me leakage kaise roka?

Same author ke questions train aur test dono me na aayein — iske liye GroupShuffleSplit use kiya, OwnerUserId (author) ke hisaab se group karke. Random split se author dono taraf aa jata — aur validation jhooth bolta.

Bias-Variance Trade-off

Model ki galtiyan 2 tarah ki hoti hain — bias (underfitting) aur variance (overfitting). Dono ke beech sahi balance dhoondhna hi modeling hai.

Underfitting (High Bias)

Training set par hi performance kharab hai — model data se kuch seekh hi nahi paya. Matlab model bahut simple hai, ya features bekaar hain.

Overfitting (High Variance)

Training par bahut achha, validation par kharab — model ne training data ko rat liya, generalize nahi kiya. Matlab model bahut complex hai ya data kam hai.

Trade-off curve

Complexity badhao → bias ghata, variance badha. Ek point aata hai jahan total error minimum hota hai — wahi optimal point hai. Usse aage complexity badhana nuksaan hai.

  • ML Editor ke pehle model me validation > training tha — matlab underfitting ki taraf — complexity badha sakte hain.
  • Bias kam karne ke liye: zyada features, zyada complex model.
  • Variance kam karne ke liye: zyada data, regularization, simpler model (Chapter 6 me detail).

Accuracy, Precision, Recall, F1 — quick reminder

  • Accuracy: kul sahi predictions ka proportion. Imbalanced data me dhokha deti hai — 99% positive ho to hamesha positive predict karke bhi 99% accuracy aa jayegi.
  • Precision: jinhe positive kaha, unme se kitne asal me positive the.
  • Recall: jitne asal positive the, unme se kitne pakde gaye.
  • F1: precision aur recall ka harmonic mean.
Rare disease example: 1% se kam patients ko bimari hai — hamesha "healthy" predict karne wala model 99% accurate hoga, par bilkul bekaar hai. Isliye aggregate accuracy par bharosa mat karo — aage ke evaluation methods dekho.

Confusion Matrix, ROC, Calibration

Aggregate metrics dhokha dete hain. Model ko gehrai se samajhne ke liye 3 tools: Confusion Matrix, ROC Curve, Calibration Curve.

Confusion Matrix

Rows = true class, Columns = predicted class. Perfect model me sirf diagonal par values hongi.

  • ML Editor: model low-quality questions achhe se pakadta hai, par high-quality questions me se sirf aadhe hi sahi pehchanta hai.
  • Lekin jab model kehta hai "high quality", to aksar sahi hota hai (right column).
  • Ek column poora khaali ho to samjho — model wo class kabhi predict hi nahi karta. Rare class ke liye ye khatarnaak ho sakta hai (jaise loan default).
  • Speech example: "when" aur "where" confuse ho rahe the — symmetric off-diagonal values ne pakda. Extra data se fix hua.

ROC Curve

Threshold 0 se 1 tak badlo, har point par TPR (True Positive Rate) vs FPR (False Positive Rate) plot karo.

  • Diagonal line = random guessing. Usse upar hona chahiye.
  • AUC (Area Under Curve): random = 0.5, perfect = 1.0.
  • Product need ki lines lagao: ML Editor me FPR 10% se zyada nahi hona chahiye (galat suggestions se user ko nuksaan na ho). Ye line acceptable thresholds ko bahut kam kar deti hai.
  • Support team example: FPR tumhare staff ki capacity se tay hota hai — usse zyada false alarms handle nahi ho sakte.
python — ROC curve
from sklearn.metrics import roc_curve
fpr, tpr, thresholds = roc_curve(true_y, predicted_proba_y)

Calibration Curve

Kya model ki probability uske confidence ko sahi dikhati hai? Calibration plot: x-axis = predicted probability, y-axis = asal me kitne positive nikle. Perfect model = diagonal line.

  • ML Editor ka model 0.2–0.7 ke beech well-calibrated tha, bahar nahi — aur wo rarely hi us range ke bahar predict karta tha.
  • Ad serving (CTR prediction) me probabilities 0 ya 1 ke kareeb skewed hoti hain — calibration curve wahi dikhata hai.
  • Calibration tab matter karti hai jab tum score user ko dikhate ho (Chapter 7).

umap_features = umap_embedder.fit_transform(vectorized_features)

# Choose number of clusters and colormap
n_clusters=3
cmap = plt.get_cmap("Set2")
fig = plt.figure(figsize=(16, 10))


# Fit clustering algorithm to our vectorized features
clus = KMeans(n_clusters=n_clusters, random_state=10)
clusters = clus.fit_predict(vectorized_features)

# Plot the dimentionality reduced features on a 2D plane
plt.scatter(umap_features[:, 0], umap_features[:, 1], 
            c=[cmap(x/n_clusters) for x in clusters], s=40, alpha=.4)
plt.title('UMAP projection of questions, colored by clusters', fontsize=14);

# https://scikit-learn.org/stable/auto_examples/cluster/plot_kmeans_silhouette_analysis.html#sphx-glr-auto-examples-cluster-plot-kmeans-silhouette-analysis-py
range_n_clusters = [2, 3, 4, 5, 6]

to_clus = vectorized_features

for n_clusters in range_n_clusters:
    # Create a subplot with 1 row and 2 columns
    fig, (ax1, ax2) = plt.subplots(1, 2)
    fig.set_size_inches(18, 7)

    # The 1st subplot is the silhouette plot
    # The silhouette coefficient can range from -1, 1 but in this example all
    # lie within [-0.1, 1]
    ax1.set_xlim([-.3, .4])
    # The (n_clusters+1)*10 is for inserting blank space between silhouette
    # plots of individual clusters, to demarcate them clearly.
    ax1.set_ylim([0, len(to_clus) + (n_clusters + 1) * 10])

    # Initialize the clusterer with n_clusters value and a random generator
    # seed of 10 for reproducibility.
    clusterer = KMeans(n_clusters=n_clusters, random_state=10)
    cluster_labels = clusterer.fit_predict(to_clus)

    # The silhouette_score gives the average value for all the samples.
    # This gives a perspective into the density and separation of the formed
    # clusters
    silhouette_avg = silhouette_score(to_clus, cluster_labels, metric='cosine')
    print("For n_clusters =", n_clusters,
          "The average silhouette_score is :", silhouette_avg)

    # Compute the silhouette scores for each sample
    sample_silhouette_values = silhouette_samples(to_clus, cluster_labels, metric='cosine')

    y_lower = 10
    for i in range(n_clusters):
        # Aggregate the silhouette scores for samples belonging to
        # cluster i, and sort them
        ith_cluster_silhouette_values = \
            sample_silhouette_values[cluster_labels == i]

        ith_cluster_silhouette_values.sort()

        size_cluster_i = ith_cluster_silhouette_values.shape[0]
        y_upper = y_lower + size_cluster_i

        color = cmap(float(i) / n_clusters)
        ax1.fill_betweenx(np.arange(y_lower, y_upper),
                          0, ith_cluster_silhouette_values,
                          facecolor=color, edgecolor=color, alpha=0.7)

        # Label the silhouette plots with their cluster numbers at the middle
        ax1.text(-0.05, y_lower + 0.5 * size_cluster_i, str(i))

        # Compute the new y_lower for next plot
        y_lower = y_upper + 10  # 10 for the 0 samples

    ax1.set_title("The silhouette plot for the various clusters.")
    ax1.set_xlabel("The silhouette coefficient values")
    ax1.set_ylabel("Cluster label")

    ax1.axvline(x=silhouette_avg, color="red", linestyle="--")

    ax2.scatter(umap_features[:, 0], umap_features[:, 1], marker='.', s=30, lw=0, alpha=0.7,
                c=colors, edgecolor='k')

    # Labeling the clusters
    centerss = clusterer.cluster_centers_
    print(centerss.shape)
    centers = umap_embedder.transform(centerss)
    # Draw white circles at cluster centers
    ax2.scatter(centers[:, 0], centers[:, 1], marker='o',
                c="white", alpha=1, s=200, edgecolor='k')

    for i, c in enumerate(centers):
        ax2.scatter(c[0], c[1], marker='$%d$' % i, alpha=1,
                    s=50, edgecolor='k')

    ax2.set_title("The visualization of the clustered data.")
    ax2.set_xlabel("Feature space for the 1st feature")
    ax2.set_ylabel("Feature space for the 2nd feature")

    plt.suptitle(("Silhouette analysis for KMeans clustering on sample data "

Top-k Method aur Feature Importance

Numbers ke baad examples dekho. Top-k method aur feature importance — model kya seekh raha hai, ye jaanne ke 2 tareeke.

Top-k Method

k examples (10–15) chun kar dekho — 3 categories me:

  • k best: model ne sahi predict kiya aur confident tha — kaunsi features kaam kar rahi hain?
  • k worst: model galat tha aur confident tha — kya feature missing hai? ML Editor me "non-question" questions (jin me question hi nahi tha) model miss kar raha tha — question marks count karne wala feature add kiya gaya.
  • k most uncertain: probability 50% ke kareeb — training me ye conflicting labels ka sign hai (same jaisi examples, alag labels); validation me ye training data me gap ka sign hai.

ML Editor me top-k se pata chala: classifier text_len par bahut zyada rely karta hai — lambe questions ko achha, chhote ko kharab kehta hai. Ye kaafi nahi hai — aur features chahiye.

Dimensionality Reduction for Errors

  • Errors ko color karke plot karo (sahi/galat) — kharab regions dikhenge.
  • Clusters banao, har cluster par performance naapo — sabse kharab cluster ke examples dekho.

Feature Importance — seedha classifier se

Random forest me feature_importances_ se ranking milti hai. ML Editor ke top 10:

  • Baaki features aam words hain — model common words par rely kar raha hai, isliye generalize nahi kar pa raha.
  • Fix: zyada data, ya aise features jo sparse na hon (rare words ke bag-of-words me zyada tar values zero hoti hain).

Black-Box Explainers — LIME aur SHAP

Neural networks jaise complex models feature importance nahi dete. LIME / SHAP ek example ko perturb karke (words hata kar) dekhte hain ki prediction kaise badalti hai.

  • ML Editor: LIME ne ek question ko 52% probability ke saath high-quality kaha — par important words irrelevant lage.
  • 500 questions par LIME chalane se wahi trend dikha — model common words par atka hai.
  • Leakage pakadne ka tareeka: email classification me sabse predictive feature ek 3-letter internal code nikla — model content ko ignore karke label ko yaad kar raha tha! Feature importance ne leakage pakda.

Other Models — classification framework har jagah

  • Object detection: Jaccard index (overlap) se prediction sahi/galat tay karo, phir accuracy aur wahi methods.
  • Recommendations: har category ko ek class maan kar evaluate karo.
  • Generative models: data ko categories me baanto, har category par performance naapo — jaise sentence simplification me lambe sentences par performance kharab thi, to training data me lambe sentences badhaye.

Normal software me test pass = kaam kar raha hai. ML me pipeline bina error ke chal sakta hai aur phir bhi bilkul galat results de sakta hai. Model ko numbers chahiye — galat numbers bhi chal jayenge, bas predictions bekaar honge. Isliye sirf "code chala" kaafi nahi — outputs sahi hone chahiye.

  • KISS (Keep It Stupid Simple): jo chahiye wahi banao.
  • Python me pdb debugger use karo; University of Chicago ki debugging guide bhi useful hai.

Debug Wiring: Ek Example se Shuru

Wiring debug karne ka tareeka: ek example lo, use poori pipeline se guzaaro. Agar ek example bhi nahi behta, to poora dataset bekar hai.

Ek example se shuru — 3 checks

  1. Model prediction de sakta hai kya is example par?
  2. Model apne parameters update karke is example ko sahi predict kar sakta hai kya? (fit kar sakta hai?)
  3. Ye sab ek-do examples par karo — poora dataset nahi.

Kickstarter example: saari campaigns par train karne se pehle sirf 2 campaigns par check karo — prediction aati hai? sahi label fit hota hai? Agar model 2 examples bhi fit nahi kar sakta, to poora dataset fit karne ka sawaal hi nahi.

Silent failures — sabse khatarnaak

  • Data normalize nahi hua — model train to hoga, par fit nahi hoga.
  • Matrix ki shape galat — model input ko galat samjhega, phir bhi chalega.
  • Null values — model crash kar sakta hai ya bekaar output de sakta hai.

Inspection points — assembly line ki tarah

Pipeline ko assembly line samjho — har meaningful step ke baad product check karo. Inspection points:

  • Data loading: saare fields hain? null to nahi? range sahi hai? (jaise age negative to nahi?) — ML Editor me PostTypeId 5 wali undocumented rows mili, filter karni padi.
  • Cleaning / feature selection: zaroori info delete to nahi hui? label leak karne wala field to nahi reh gaya?
  • Feature generation: naye feature ki values populated hain? reasonable hain?
  • Data formatting: segmentation masks ka format — 255 vs 1 ki galti se mask khaali samjha jayega; classification labels me off-by-one se saare labels shift ho jayenge.
  • Model output: output ka type/shape sahi hai? Training ke dauraan output badal raha hai ya nahi? Agar output bilkul nahi badal raha, to model input ko use hi nahi kar raha.

Separate your concerns

Pipeline ko chhote functions me todo — har function ko alag test karo. Phir poori pipeline ko test karo. Modular code = aasan debugging.

def get_statistical_explanation(test_set, sample_size, model_pipeline, label_dict):
    sample_sentences = random.sample(test_set, sample_size)
    explainer = LimeTextExplainer()
    
    labels_to_sentences = defaultdict(list)
    contributors = defaultdict(dict)
    
    # First, find contributing words to each class
    for sentence in sample_sentences:
        probabilities = model_pipeline([sentence])
        curr_label = probabilities[0].argmax()
        labels_to_sentences[curr_label].append(sentence)
        exp = explainer.explain_instance(sentence, model_pipeline, num_features=6, labels=[curr_label])
        listed_explanation = exp.as_list(label=curr_label)
        
        for word,contributing_weight in listed_explanation:
            if word in contributors[curr_label]:
                contributors[curr_label][word].append(contributing_weight)
            else:
                contributors[curr_label][word] = [contributing_weight]    
    
    # average each word's contribution to a class, and sort them by impact
    average_contributions = {}
    sorted_contributions = {}
    for label,lexica in contributors.items():
        curr_label = label
        curr_lexica = lexica
        average_contributions[curr_label] = pd.Series(index=curr_lexica.keys())
        for word,scores in curr_lexica.items():
            average_contributions[curr_label].loc[word] = np.sum(np.array(scores))/sample_size
        detractors = average_contributions[curr_label].sort_values()
        supporters = average_contributions[curr_label].sort_values(ascending=False)
        sorted_contributions[label_dict[curr_label]] = {
            'detractors':detractors,
             'supporters': supporters
        }
    return sorted_contributions

Overfitting: Regularization aur Augmentation

Model training data par fit ho gaya — par validation par fail ho raha hai. Ab generalization debug karo: pehle task difficulty dekho, phir optimization, phir overfitting se lado.

Task Difficulty — 3 cheezein check karo

  • Data quality, quantity, diversity: har type ke kaafi examples hain? 100 breeds ke cats ke liye cat-vs-dog se bahut zyada data chahiye — classes badhne par data ki zaroorat exponentially badhti hai. Outliers hatao (agar production me nahi milenge) ya rakho (agar milenge to).
  • Data representation: kya features patterns ko dikhate hain? ML Editor me pehle sirf body text tha — title add karne se performance badhi, kyunki title bhi informative tha.
  • Model capacity: kya model hi galat hai? Random forest fail ho to pehle decision tree try karo aur uske splits dekho. Model bahut simple bhi ho sakta hai — tab complexity badhao. Prior art dekho (Chapter 2).

Optimization Problems — loss curve dekho

  • TensorBoard me loss plot karo — loss pehle tez, phir dheere kam hona chahiye.
  • Loss bahut dheere kam ho → learning rate badhao. Loss unstable ho → learning rate bahut zyada hai, kam karo.
  • Weights ki distribution dekho — kuch epochs tak stable rahe to learning rate badhao; bahut vary kare to kam karo.

Data Leakage (dobara — generalization ke context me)

Validation > training ho to khush hone se pehle leakage check karo. Note: training ke dauraan validation loss kabhi-kabhi training loss se behtar dikhta hai kyunki training loss poore epoch ka accumulate hota hai, validation loss epoch ke baad latest model par calculate hota hai — ye normal hai.

Overfitting se ladne ke tareeke

  • Regularization: model ki capacity par penalty. L1 (weights ke absolute value ka sum — uninformative features ko zero kar deta hai, feature selection jaisa) aur L2 (squared values ka sum). Neural nets me dropout (training me kuch neurons randomly ignore karo). Random forest me max depth kam karo, trees ki sankhya badhao.
  • Data augmentation: existing data ko thoda badal kar naya data banao (images: rotate, crop, darken). Training performance kam hogi, par validation badhega — kyunki model zyada varied inputs dekhta hai. Hurricane example: flooded roads detect karne ke liye training images ko darker/blurrier banaya — validation par performance badhi.
  • Dataset redesign: train/val split balanced nahi hai to dobara banao — mushkil examples dono taraf barabar hon. k-fold cross-validation use karo (k alag splits, har baar performance naapo).

Consider the Task at Hand

Agar sab try kar liya aur model generalize nahi kar raha, to ho sakta hai task hi ML ke liye sahi na ho — input me output predict karne ke liye kaafi information hi nahi hai. Random outputs ko random inputs se predict karna impossible hai — model training data rat sakta hai, par generalize nahi karega. Aise me Chapter 1 par wapas jao aur framing dobara socho.

Using Classifiers for Writing Recommendations

Ab trained classifier se actionable recommendations nikalo. Sirf "achha/kharab" batana kaafi nahi — user ko ye batana hai ki kya badle taaki question behtar ho jaye. 4 methods hain — bina model se lekar black-box explainer tak.

Method 1: Feature statistics (bina model ke)

Har feature ki average value har class ke liye nikalo. High-score questions me question marks kam hote hain — to rule banao: "agar tumhare question me question marks bahut zyada hain to kam karo." Pandas me: feats_labels.groupby("label").mean().

  • Example: num_chars high-score me 967, low-score me 822 — lambe questions ko zyada score milta hai.
  • Fayda: tez, robust, model run karne ki zaroorat nahi.

Method 2: Global feature importance

Feature importance se prioritize karo — sabse important features ki recommendations pehle dikhao. 30-feature model me top 5: num_chars (0.053), num_questions (0.051), num_periods (0.051), ADV (0.049), ADJ (0.049). Bottom: CONJ, SCONJ (0).

  • Nuksaan: aggregate statistics hain — har individual example par lagu nahi hoti. Kisi question me adverbs kam hain, phir bhi high score ho sakta hai.

Method 3: Model ka score dikhao

Class ki jagah calibrated probability (score) dikhao — predict_proba se. User score badhta dekh kar recommendations par bharosa karta hai. Score tabhi dikhao jab model well-calibrated ho (Chapter 5).

Method 4: Local feature importance (LIME)

Har individual example ke liye LIME se explanation nikalo — kaunsi feature ne score ko kitna upar/neeche kiya. Example: num_diff_words <= 88 ne score 0.038 kam kiya — matlab vocabulary diversity badhao to score badhega.

  • Nuksaan: slow — LIME default 500 perturbations karta hai, ek example par ~2 seconds. Typing karte waqt live suggestions nahi de sakte; submit par dena padega.
  • Trade-off: accuracy vs latency — product ki requirement se chuno.

def parse_explanations(exp_list):
    global FEATURE_DISPLAY_NAMES
    parsed_exps = []
    for feat_bound, impact in exp_list:
        conditions = feat_bound.split(" ")

        # We ignore doubly bounded conditions , e.g. 1 <= a < 3 because
        # they are harder to formulate as a recommendation
        if len(conditions) == 3:
            feat_name, order, threshold = conditions

            simple_order = simplify_order_sign(order)
            recommended_mod = get_recommended_modification(simple_order, impact)

            parsed_exps.append(
                {
                    "feature": feat_name,
                    "feature_display_name": FEATURE_DISPLAY_NAMES[feat_name],
                    "order": simple_order,
                    "threshold": threshold,
                    "impact": impact,
                    "recommendation": recommended_mod,
                }
            )
    return parsed_exps

def get_recommended_modification(simple_order, impact):
    bigger_than_threshold = simple_order == ">"
    has_positive_impact = impact > 0

    if bigger_than_threshold and has_positive_impact:
        return "No need to decrease"
    if not bigger_than_threshold and not has_positive_impact:
        return "Increase"
    if bigger_than_threshold and not has_positive_impact:
        return "Decrease"
    if not bigger_than_threshold and has_positive_impact:
        return "No need to increase"

def simplify_order_sign(order_sign):
    if order_sign in ["<=", "<"]:
        return "<"
    if order_sign in [">=", ">"]:
        return ">"
    return order_sign

Model Comparison: V1, V2, V3

ML Editor ke 3 model versions ko compare karo — aur dekho ki aggregate performance sab kuch nahi hai. Chuna gaya model wo nahi jo sabse accurate tha, wo jo recommendations ke liye sabse achha tha.

Requirements — recommendation model ke liye

  • Well-calibrated ho — probability ka matlab ho.
  • High precision ho — galat recommendations mehngi hain.
  • Features user ko samajh aayein — wahi recommendations banengi.
  • Fast ho — taaki LIME jaise explainer chala sakein.

V1: Report Card (heuristics)

Chapter 3 wala heuristic version — readability measurements dikhata tha. Comparison me shaamil nahi — ye sirf intuition banane ke liye tha.

V2: More Powerful, More Unclear

  • TF-IDF vectors + hand-made features. Precision 0.62, par calibration kharab.
  • Phir naye features add kiye: punctuation counts, part-of-speech counts, sentiment. Precision 0.63 — thoda behtar, calibration phir bhi kharab.
  • Problem: sabse important word-features "are" aur "what" the — user ko ye recommend nahi kar sakte ki "are kam likho". Vectorized features explainable nahi hain.

V3: Understandable Recommendations (CHUNA GAYA)

  • Sirf 30 hand-made features — punctuation counts, POS counts, sentiment, length. Koi TF-IDF nahi (7,000+ features ki jagah 30).
  • Precision 0.597 — aggregate me thoda kam, par calibration sabse behtar — 0.7 se upar ki probabilities bhi sahi hain.
  • Fast hai, explainable hai, aur score dikhane ke liye best hai. Isliye V3 deploy ke liye chuna gaya.

End-to-end recommendations — example

get_recommendation_and_prediction_from_text — input question lo, features nikalo, score predict karo, LIME explanation ko recommendations me badlo:

  • "I want to learn how models are made" → score 0.39 → "Increase question length, Increase vocabulary diversity, Increase frequency of question marks"
  • Recommendations follow karke question badhaya → score 0.48
  • Phir se follow kiya → score 0.53

Score badhta dekh kar user ko feedback milta hai — yahi ML Editor ka core loop hai.

Lesson: model choose karte waqt sirf accuracy mat dekho — calibration, explainability aur speed bhi dekho. Product goal ke hisaab se best model wohi hai jo product ko behtar banaye.

def get_multiple_calibration_plot(predicted_proba_arrays, true_y, figsize=(10, 8)):
    """
    Inspired by sklearn example
    https://scikit-learn.org/stable/auto_examples/calibration/plot_calibration_curve.html
    :param figsize: size of the output figure
    :param predicted_proba_y: the predicted probabilities of our model for each example
    :param true_y: the true value of the label
    :return: calibration plot
    """

    plt.figure(figsize=figsize)
    ax1 = plt.subplot2grid((3, 1), (0, 0), rowspan=2)
    ax2 = plt.subplot2grid((3, 1), (2, 0))

    ax1.plot([0, 1], [0, 1], "k:", label="Perfectly calibrated")
#     print("\tBrier: %1.3f" % clf_score)
    
    for i,predicted_proba_y in enumerate(predicted_proba_arrays):
        fraction_of_positives, mean_predicted_value = calibration_curve(
            true_y, predicted_proba_y, n_bins=10
        )

        ax1.plot(
            mean_predicted_value,
            fraction_of_positives,
            "s-",
            label = "Model %s" % (i + 1)
        )

        ax2.hist(
            predicted_proba_y,
            range=(0, 1),
            bins=10,
            histtype="step",
            label = "Model %s" % (i + 1),
            lw=2,
        )

    ax1.set_ylabel("Fraction of positives")
    ax1.set_xlim([0, 1])
    ax1.set_ylim([0, 1])
    ax1.legend(loc="lower right")
    ax1.set_title("Calibration plot")

    ax2.set_title("Probability distribution")
    ax2.set_xlabel("Mean predicted value")
    ax2.set_ylabel("Count")
    ax2.legend(loc="upper right", ncol=2)

    plt.tight_layout()

Considerations When Deploying Models

Model train ho gaya aur achha perform kar raha hai — kya deploy kar dein? Nahi. Deploy se pehle failure modes, bias, abuse aur dual-use par sochna padta hai. Training performance necessary hai, sufficient nahi.

Deploy se pehle 5 sawaal

  1. Data kaise collect hua tha?
  2. Model dataset se kya assumptions seekh raha hai?
  3. Dataset representative hai ya nahi?
  4. Kaam ka galat istemal kaise ho sakta hai?
  5. Model ka intended use aur scope kya hai?

Ye sawaal data ethics ke hain — field abhi evolve ho rahi hai. Gehrai ke liye O'Reilly ki report "Ethics and Data Science" (Mike Loukides et al.) dekho.

Data Ownership — 3 zimmedariyan

  • Data collection: kya tumhe legally data collect karne ka haq hai?
  • Data usage aur permission: kya users ko bataya ki unka data kyun aur kaise use hoga — aur kya wo agree hue?
  • Data storage: data kahan store hai, kisko access hai, kab delete hoga?

Europe me GDPR strict rules deta hai. Data breaches se trust tootta hai aur legal action hota hai — kam data collect karo to legal exposure bhi kam. ML Editor ne publicly available datasets use kiye, jo users ki agreement se collect hue the.

Data Bias — dataset kabhi neutral nahi hota

Dataset data collection decisions ka result hai — isliye har dataset biased hota hai. Model usi bias ko seekh kar reproduce karega.

  • CEO example: historical data me zyada tar Fortune 500 CEOs male the (Pew Research) — aise data par trained model "male hona" ko leadership ka predictor maan lega. Ye societal bias ko reinforce karna hai.
  • Measurement errors: har data point me uncertainty hai — model use ignore karke systematic errors propagate karta hai.
  • Representation: early face recognition datasets me zyada tar white men the — model un par achha, baaki par kharab.
  • Access: English text aasani se milta hai, baaki languages mushkil — isliye best language models English par hain. Ye gap khud ko reinforce karta hai.
Test set inclusive banao: test set production ka proxy hai. Har tarah ke user ke examples rakho — gender, age, language, sab. Deploy se pehle diverse users ko model try karne do aur feedback lo. Bias sabse zyada un logon ko nuksaan pahunchata hai jo pehle se disadvantaged hain.

Data Bias aur Feedback Loops

Bias sirf data me nahi — model ke behaviour me bhi paida hota hai. Feedback loops aur inclusive performance — deploy se pehle ye dono samajh lo.

Systemic Bias

Institutional policies ki wajah se kuch populations historical datasets me over/under-represented hain. Example: criminal arrest databases — model wahi bias aage badhayega. ProPublica ki "Machine Bias" report (Angwin et al.) — crime prediction me ML bias ka concrete example.

  • Feature hatana kaafi nahi: gender/ethnicity hata do, to bhi model biased rahega — kyunki ZIP code aur income jaise features usse strongly correlated hain.
  • Fairness constraints explicit karo: Zafar et al. ka p% rule — sensitive attribute wale aur bina wale groups ko positive outcome milne ka ratio kam se kam p:100 hona chahiye. Bias ko quantify karo, tabhi fix kar paoge.

Feedback Loops — khud ko reinforce karne wala model

User ne model ki recommendation follow ki → wo data training me gaya → agla model wahi recommendation aur zyada dega. Video recommendation example: pehle model ne cat videos thode zyada recommend kiye → users ne cat videos dekhe → agle model ne aur zyada cat videos recommend kiye → ant me sirf cat videos!

  • Clicks galat label hain: click ka matlab ye nahi ki user ko pasand aaya. Watch time behtar label hai — satisfaction se zyada correlate karta hai.
  • Par watch time optimize karne par bhi limit hai — maximum watch time ka matlab hai user poora din video dekhe. Kya ye goal sahi hai?
  • Feedback loops active users ko favour karte hain — zyada tar clicks kuch active users se aate hain, to model unhi ke liye optimize ho jata hai.

Inclusive Model Performance

Aggregate accuracy badhna kaafi nahi — har segment par performance dekho.

  • 2015 photo-tagging failure: ek automated system ne African American users ki photos ko "gorillas" tag kiya (BBC article) — representative test set na hone ka nateeja.
  • Facial recognition update: overall accuracy 90% → 92% hui, par 40+ ki women par performance gir gayi — aisa model deploy mat karo. Pehle representative data add karo, phir retrain karo.

Considering Context — Model Cards

User ko ye batana chahiye ki prediction kahan se aayi. Model Cards (Mitchell et al.) — model ke saath metadata: kis data par train hua, kis par test hua, intended use kya hai. ML Editor ka disclaimer: "Ye Writing Stack Exchange ke questions par train hua hai — us community ki preferences reflect kar sakta hai."

Adversaries, Abuse aur Dual-Use

Kuch users model ko harana chahenge — fraudsters, attackers. Aur kuch tumhara kaam galat kaam ke liye use karenge. Dono ke baare me deploy se pehle socho.

Defeating a Model — fraudsters se ladna

  • Fraud detection model ko fraudsters fool karna chahenge — jaise fake location se login karna.
  • Country-of-origin jaise features use karo to bias aayega (us desh ke genuine users par bhi shak) — aur attacker location fake karke bypass kar lega.
  • Defense: models ko regularly update karo — attackers adapt karte hain, tum bhi karo. Monitoring se naye patterns pakdo (Chapter 11), naye features banao.

Exploiting a Model — training data churaana

Model apne training data ko reflect karta hai. Attacker predictions ko observe karke training data ke baare me infer kar sakta hai.

  • Example: sirf 2 examples wala dataset — attacker arbitrary inputs dekar ye infer kar sakta hai ki kaunsi feature predictive hai.
  • ZIP code example: alag-alag ZIP codes se login try karke attacker users ke geographical distribution ka andaza laga sakta hai.
  • Simplest defense: rate limiting — ek user kitni requests kar sakta hai, ye limit karo. Silver bullet nahi hai (multiple accounts bana sakte hain), par attack ko mehenga karta hai.

Abuse aur Dual-Use

Dual-use = ek kaam ke liye banayi technology, dusre (galat) kaam me use ho.

  • Voice cloning model — doston jaisi awaaz banane ke liye — impersonation ke liye misuse ho sakta hai.
  • Face classification — smart doorbell ke liye bana, par city-wide surveillance me use ho sakta hai.
  • OpenAI ne apna powerful language model release nahi kiya tha — disinformation failane ke dar se ("Better Language Models and Their Implications").
  • Agar tumhe lagta hai tumhara kaam galat use ho sakta hai, to use reproduce karna mushkil banao ya community se discuss karo.

Chris Harland Interview (Textio) — Shipping Experiments

  • Guidance me precision > recall: galat advice dena bahut mehenga hai — kam, par sahi advice do. Users pehli advice se seekh kar aage khud apply karte hain.
  • Consistency zaroori: "200 words aur likho" kaha, user ne 150 likhe — to model apna mann nahi badal sakta aur "kam karo" nahi keh sakta.
  • Clarity: "stop words 50% kam karo" confusing hai; "in 3 sentences ko chhota karo" actionable hai.

  • Chhota dataset kaafi hai: 1,000 relevant documents se bahut kaam ho jata hai. Pehle bad model banao — use fix karne se product robust banta hai.
  • Production me: predictions users ko clearly dikhao, override karne do, aur feature values + predictions + overwrites log karo — monitoring ke liye.

Chris Harland Interview: Shipping Experiments

Chris Harland — Ph.D. physics, pehle Microsoft search team par, phir Textio me director of engineering — se interview. Textio augmented writing products banata hai jo users ko behtar job descriptions likhne me madad karte hain. Harland batate hain ki ML-powered product ko users tak kaise ship karein, aur accuracy se aage jaakar results ko kaise validate karein.

Guidance dena, prediction dena nahi hai — farq kya hai?

Jab tum sirf prediction karte ho — jaise sone ka rate kab badhega ya Twitter par kisko follow karein — to thodi variance chal jati hai. Lekin jab tum writing me guidance dete ho, to aisa nahi hai, kyunki tumhari recommendations ka bahut subtext hota hai.

  • Consistency zaroori hai: agar model kehta hai "200 aur words likho", to user ko us advice ko follow karne ka mauka milna chahiye. User ke 150 words likhne ke baad model apna mann nahi badal sakta aur ye nahi keh sakta ki word count kam karo.
  • Clarity zaroori hai: "stop words ko 50% se kam karo" ek confusing instruction hai, par "in 3 sentences ko chhota karo" zyada actionable hai.
  • Challenge ye hai ki performance banaye rakhte hue aise features use karo jo insaan ko samajh aayein.
  • Asal me, ML writing assistant user ko feature space me ek starting point se behtar point tak le jata hai — aur kabhi-kabhi is raaste me beech ke points pehle se bhi bure hote hain, jo user ke liye frustrating hota hai. Product ko in constraints ko dhyaan me rakh kar banana padta hai.

Guidance ke liye precision, recall se zyaada matter karta hai

Advice dene me precision, recall se bahut zyaada interesting hai. Recall ka matlab hota ki tum har possible relevant domain me advice do — aur kai irrelevant domains me bhi. Precision ka matlab hai ki tum kuch promising domains me advice do, baaki ko chhodo.

  • Advice dete waqt galat hone ki cost bahut high hoti hai — isliye precision sabse useful hai.
  • Users tumhare model ki pehle di hui recommendations se seekhte hain aur unhe bina prompt ke aage ke inputs par bhi apply karte hain — isse precision aur bhi important ho jata hai.
  • Ye bhi measure karo ki users tumhare factors ka asal me use karte hain ya nahi. Agar nahi karte, to samjho kyun nahi. Example: Textio ka "active to passive ratio" feature kam use hota tha — pata chala ki recommendation kaafi actionable nahi thi, to unhone un words ko hi highlight karna shuru kar diya jinke badalne ki recommendation thi.

Naye features kaise dhoondhein? Top-down aur bottom-up

Dono approaches kaam ki hain — ek domain knowledge se aata hai, doosra model ke andar jhaankne se:

  • Top-down (hypothesis investigation): domain knowledge se feature matching karo — ye product ya sales team se bhi aa sakta hai. Example hypothesis: "recruiting emails ke mystery aspect me kuch hai jo engagement badhata hai." Top-down me challenge ye hota hai ki us feature ko practical tareeke se extract karna — tabhi validate kar sakte ho ki feature predictive hai ya nahi.
  • Bottom-up (model ko introspect karo): classification pipeline ke andar dekho ki use kya predictive lagta hai. Agar tumhare paas text ka general representation hai — word vectors, tokens, parts-of-speech annotations — jise tum ensembles of models ko good/bad text classify karne ke liye dete ho, to kaunse features sabse predictive hain? Domain experts aksar in patterns ko model ki predictions se pehchanne me sabse behtar hote hain. Phir challenge ye hota hai ki in features ko insaan ke samajhne layak banao.

Model kab good enough hai? Chhota dataset, kharab model, aasan experiments

  • Chhota dataset kaafi hai: relevant language ke sirf 1,000 documents se bahut se use cases me kaam chal jata hai — is chhote set ko label karna worthwhile hai. Phir apne model ko out-of-sample data par test karo.
  • Experiments chalana aasan banao: tumhare product badalne ke ideas me se overwhelming majority ka net effect null hota hai — isliye naye features se thoda kam daro.
  • Kharab model banana theek hai — aur wahi se shuru karna chahiye. Kharab models ko fix karne se tumhara product problems ke against bahut zyaada robust banta hai aur tez evolve karta hai.

Production me model kaisa kar raha hai — kaise dekhein?

  • Production me model ki predictions ko users ko clearly dikhao aur unhe override karne do.
  • Feature values, predictions aur overwrites ko log karo — taaki tum unhe monitor kar sako aur baad me analyze kar sako.
  • Agar tumhara model ek score deta hai, to us score ko recommendations ke usage se compare karne ke tareeke dhoondho — ye ek extra signal hai. Example: agar tum predict kar rahe ho ki email khola jayega ya nahi, to users se ground truth data milna bahut valuable hota hai, taaki model ko improve kar sako.
  • Ultimate success metric customer success hai — jo sabse delayed hoti hai aur bahut se aur factors se influenced hoti hai.
Lesson: guidance me precision hi sab kuch hai — galat advice ki cost bahut high hoti hai, aur users tumhari advice ko aage bhi copy karte hain. Isliye pehle kharab model ship karo, experiments aasan banao, aur production me har prediction ko dikhao, log karo aur override karne do.

Choose Your Deployment Option

Model tayyar hai — ab users tak kaise pahunchayein? Deployment ke options: server-side (streaming/batch) ya client-side (on-device/browser) — aur hybrid federated learning. Choice requirements se tay hoti hai: latency, privacy, cost, complexity.

Server-Side Deployment — 2 workloads

  • Streaming: request aate hi process karo, turant jawab do.
  • Batch: requests ikattha karo, ek saath process karo, results store karo.

Streaming Application / API

Model ek endpoint hai — request aati hai, inference pipeline chalti hai, result wapas jata hai. Steps:

  1. Request validate karo (parameters, permissions).
  2. Additional data gather karo (user info wagera).
  3. Preprocess karo.
  4. Model run karo.
  5. Postprocess karo — results bounds me hain? confidence ke saath context do.
  6. Result return karo.
  • Nuksaan: traffic badhne par servers linearly badhane padte hain — automation chahiye (auto-scaling).
  • ML Editor ke liye Flask se chhota API kaafi tha — kuch users ke liye streaming best choice hai.
  • Streaming tab zaroori jab latency tight ho aur data sirf request time par mile — jaise ride-hailing me trip price (user location + driver availability tabhi pata chalti hai).

Batch Predictions

Predictions pehle se compute karo, store karo, jab zaroorat ho tab retrieve karo.

  • Example: lead scoring — sales team ko subah prospects ki list chahiye; raat me batch job chala kar list ready rakho.
  • Example: subah ki notifications prioritize karna — raat me saare unread emails process kar lo.
  • Fayda: resources allocate karna aasan, parallelize karna aasan, inference time par sirf retrieval (caching jaisa fayda).
  • Hybrid: jo precompute ho sake karo, baaki inference time par compute karo — par do pipelines maintain karni padti hain (complexity badhti hai).

Server vs Client vs Federated Learning

Server par chalana mehenga ho sakta hai aur central failure point banta hai. Client-side deployment me computation user ke device par hoti hai — iske apne fayde aur costs hain.

On Device

  • Phone/laptop ke processors ML ke liye optimized nahi hote — model chhota hona chahiye: pruning (near-zero weights hatao), quantization (weights ki precision kam karo), kam features.
  • TensorFlow Lite jaise tools model ko mobile layak banate hain.
  • Thodi accuracy lose hoti hai — jo products cutting-edge accuracy chahte hain, wo server par hi rahenge.
  • Kab chuno: predictive keyboard (offline chahiye), plant identifier (hike par network nahi), translation app (abroad network nahi) — yahan offline hona accuracy se zyada important hai.
  • Privacy: photo filter app me photos server par bhejna risky hai — on-device me data device se bahar hi nahi jata.
  • Rule of thumb: agar on-device inference time > server par bhej kar wapas laane ka time, to server behtar hai.

Browser Side — TensorFlow.js

  • Model browser me JavaScript se chalta hai — install nahi karna, page kholo aur model chalao.
  • WebGL se device ka GPU use hota hai — fast inference.
  • Infrastructure ko sirf web page + model weights serve karne hain.
  • Nuksaan: model har baar download hota hai (bandwidth cost) — isliye model kuch MB se chhota hona chahiye.
  • ML Editor ke liye: agar server costs badh jayein, to TensorFlow.js pehla option hoga.

Federated Learning — Hybrid Approach

Ek model sab ke liye — ya har user ka apna model? Federated learning me har client ke paas apna model hota hai, jo user ke data se seekhta hai aur aggregated (anonymized) updates server ko bhejta hai. Server sab updates se global model improve karke wapas bhejta hai.

  • Privacy: user ka data server par kabhi nahi jata — sirf model updates jaate hain.
  • Personalization: har user ka model uski writing style/behaviour ke hisaab se.
  • Example: Google Gboard — federated learning se next-word prediction (Hard et al.). Har user ki writing style alag hai — ek global model sab ke liye achha nahi ho sakta tha.
  • Cost: complexity zyada — har model ki performance aur anonymization ka khayal rakhna padta hai.
Decision framework: latency tight hai? → streaming. Data pehle se available hai? → batch. Privacy ya offline zaroori hai? → on-device/browser. Personalization + privacy dono? → federated. Prototype ke liye hamesha simplest se shuru karo — endpoint ya batch — aur tabhi complex bano jab zaroorat prove ho.

Build Safeguards for Models

Software me sawal ye nahi ki component fail hoga ya nahi — kab fail hoga. ML me bhi wahi: koi model 100% sahi nahi hota. Isliye fault tolerance banao — failures ko gracefully handle karo.

Engineer Around Failures — 3 jagah check karo

  1. Inputs: kya input sahi hai?
  2. Model confidence: kya model confident hai?
  3. Outputs: kya output reasonable hai?

Input Checks — Tests vs Checks

Tests (Chapter 6) predetermined inputs par code ko validate karte hain, code change hone par chalaye jate hain. Checks pipeline ka hissa hain — input ki quality ke hisaab se program ka flow badal dete hain (model chalao ya heuristic ya error do).

  • Check karo: (1) saare features present hain, (2) har feature ka type sahi hai, (3) values reasonable range me hain.
  • Check fail ho → model mat chalao. Core info missing hai to error return karo; nahi to heuristic par fallback karo — isiliye pehla heuristic sambhal kar rakho!

def validate_and_handle_request(question_data):

Output Checks

  • Output plausible range me hai? Age prediction 0–100+ ke beech honi chahiye — bahar ho to mat dikhao.
  • Output useful bhi honi chahiye — ML Editor agar kahe "sab kuch delete kar do", to wo useless (aur insulting) recommendation hai.
  • Output fail ho to heuristic ya simpler model par fallback karo — simple model ke errors complex model se alag hote hain (uncorrelated errors), isliye wo kuch examples sahi kar deta hai jo complex model galat karta hai.

Input/Output Checks aur Filtering Model

Input sahi ho, output reasonable ho — phir bhi model galat ho sakta hai. Isse pakadne ke 2 tareeke: confidence track karo, ya ek filtering model banao.

Confidence se detect karo

Classification model ki probability ko confidence maano — agar well-calibrated hai to low-confidence predictions mat dikhao. Par problem: kuch baar model high confidence ke saath galat hota hai. Aur confidence jaanne ke liye poora inference chalana padta hai — mehenga hai.

Filtering Model — mushkil inputs ko pehle hi roko

Ek chhota binary classifier banao jo predict kare: "kya main model is example par fail hoga?"

  • Training data: main model jin par sahi tha (label 0) vs jin par galat tha (label 1) — extra data collection nahi chahiye!
  • Filtering model ko fast hona chahiye aur hard cases ko achhe se pakadna chahiye.
  • Google Smart Reply me aisa hi triggering model hai — sirf ~11% emails suitable hote hain, baaki par main model chalaya hi nahi jata — infrastructure 10x bach jata hai.

Filtering model kab faydemand hai? — maths

Filtering model tabhi useful hai jab wo jitna time bachata hai, usse zyada time khud na le. Agar filtering model main model se 20x faster hai, to use 5% se zyada cases block karne honge tabhi fayda hai. Formula: block proportion > (filtering time / main model time).

python — filtering model train karna
def get_filtering_model(classifier, features, labels):
    predictions = classifier.predict(features)
    is_error = [pred != truth for pred, truth in zip(predictions, labels)]
    filtering_model = RandomForestClassifier()
    filtering_model.fit(features, is_error)
    return filtering_model

Filtering model ki precision bhi check karo — jo block kare, wo asal me hard hone chahiye. Kabhi-kabhi blocked examples ko bhi jaan-bujh kar jaane do aur dekho ki main model un par kaisa karta hai (Chapter 11 — monitoring).

Caching, Reproducibility, DAGs aur Feedback

Safeguards ke baad performance aur life cycle — model ko scale karo, update karo, aur users se feedback lo.

Scale to Multiple Users

  • Horizontal scaling: naye servers spin up karo — ML bhi aise hi scale hota hai.
  • GPU note: deep learning model ko GPU chahiye ho to application logic aur inference ko alag servers par rakho — GPU instances 10x mehenge hote hain; sirf inference ke liye GPU use karo, baaki saste instances par chalao.

Caching for ML

  • LRU cache: recent inputs aur unke outputs store karo — same input dobara aaye to model chalaye bina result do. Python me @lru_cache(maxsize=128). Sirf side-effect-free functions par lagao.
  • Caching by indexing: search systems me documents ko pehle se embed karke database me rakho — query aane par sirf query embed karo aur nearest embeddings dhoondho. Twitter aur Airbnb aise hi karte hain. Cache clear karna mat bhoolo jab model/data update ho.

Model aur Data Life Cycle Management

  • Reproducibility: har model/dataset pair ko unique ID do — har prediction ke saath log karo. Bina iske production bugs ko reproduce nahi kar sakte.
  • Resilience: naya model bina downtime ke load ho — naya server launch karo, traffic dheere-dheere shift karo (canary), kharab ho to rollback karo.
  • Pipeline flexibility: naya model aksar nayi preprocessing mangta hai — application version bhi log karo, taaki har prediction reproducible ho.

Data Processing aur DAGs

Training pipeline ko Directed Acyclic Graph (DAG) banao — har node ek processing step, har arrow ek dependency. Isse har step sahi order me, successfully chalega. Tools: Apache Airflow, Spotify Luigi. Pehle prototype me DAG overkill hai; jab regular retraining shuru ho, tab DAG time-bachane wala hota hai.

Ask for Feedback — explicit aur implicit

  • Explicit: prediction ke saath "was this useful?" poochho, ya user ko correction karne do — jaise Mint app me transaction categories edit kar sakte ho.
  • Implicit: user ke actions se infer karo — recommendation par click = useful (zyada tar). Aggregate me kaam karta hai, har case me nahi.
  • ML Editor me "Ask the question on Stack Overflow" button — jis suggestion par click hua, wo weak label hai ki suggestion kaafi achha tha.
  • Feedback se performance degradation sabse pehle pakda jata hai (Chapter 11).

  • Data scientists poori pipeline own karte hain: ideation, prototyping, ETL, training, metrics, sanity checks, A/B test, monitoring, redeploy — sab.
  • Platform team abstractions banati hai — taaki data scientists khud pipelines bana sakein, engineers ko one-off pipelines na banane padein.
  • Humans + algorithms: results sirf dikhao mat — users ko correct/adjust karne do. Isse feedback loop banta hai aur labeled data milta hai.
  • Internal tool: pipeline se Docker container banta hai, arguments validate hote hain, API expose hoti hai, dashboard banta hai — data scientists khud errors fix karte hain. Ownership se log simple aur robust models chunte hain, complex nahi.
  • Canary deployment: pehle ek instance par naya version, phir dheere-dheere sab par — dashboard par har version ke instances aur performance dikhti hai.

Monitor and Update Models

Model deploy ho gaya — ab monitor karo. Monitoring 3 sawaal poochta hai: kyun monitor karein? kaise monitor karein? monitoring se kya action lein?

Monitoring Saves Lives

Model ki health track karo — performance aur predictions ki quality. User habits badle to model ke results kharab honge — achhi monitoring se tumhe turant pata chalega.

Monitoring to Inform Refresh Rate

  • Models stale hote hain (Chapter 2 — freshness). Implicit feedback (clicks) se accuracy estimate karo — accuracy threshold se neeche gire to retrain trigger karo.
  • Retrain karne se pehle verify karo ki naya model behtar hai (aage — CI/CD for ML).

Monitor to Detect Abuse

  • Fraud/abuse detection me attackers actively model ko harana chahte hain — monitoring se attacks pakdo.
  • Example: bank login attempts achanak 10x badh jayein to alert — threshold-based ya anomaly detection model se.

Choose What to Monitor — Performance Metrics

  • Feature drift: input distribution badal rahi hai? Key features ke mean/variance monitor karo — training values se zyada drift ho to alert.
  • Output distribution: predictions ka distribution badla? Ye bhi degradation ka sign hai.
  • Ground truth problem: model ke action ke baad true outcome observe nahi kar sakte — jaise fraud model ne transaction block kar di, to pata hi nahi chalega ki wo asal me fraud tha ya nahi. Ye counterfactual evaluation hai.
  • Fix: chhote random subset par model mat chalao — unhe jaane do, phir unbiased distribution observe karke precision/recall estimate karo. Cost: kuch fraudulent transactions jaane do — par benchmarking ke liye faydemand. Medical jaise domains me ye allowed nahi hai.

Business Metrics — sabse important

Baaki saare metrics green hon, par users recommendations par click na karein — to product fail hai. CTR (click-through rate) jaise product metrics ko closely monitor karo. Granular feedback (har recommendation par click track) se pata chalta hai kaunsi recommendation useful thi — aur wahi data naye model ki training me kaam aata hai.

CI/CD, A/B Testing aur Multiarmed Bandits

Monitoring ne problem pakdi — ab naya model kaise deploy karein bina users ko nuksaan pahunchaye? Shadow mode, A/B testing, aur multiarmed bandits — experimentation ke 3 tareeke.

CI/CD for ML

CI = developers regularly code merge karte hain; CD = naye versions tez release karna. ML me challenge: test suite pass karna kaafi nahi — naya model test set par achha ho, phir bhi production me kharab ho sakta hai. Live performance hi aakhri judge hai.

Shadow Mode

Naya model purane ke parallel me chalao — dono predictions compute karo aur store karo, par application sirf purane model ki prediction use kare. Isse:

  • Naye model ki production performance estimate hoti hai — user experience badle bina.
  • Infrastructure bhi test hoti hai (naya model zyada complex ho to).
  • Ek kami: user ka response naye model par nahi dekh sakte — uske liye live deploy karna padega.

A/B Testing

Users ko 2 groups me baanto — control (purana model, bada group) aur treatment (naya model, chhota group). Kaafi time baad compare karo, behtar model chuno.

  • Groups similar hone chahiye — nahi to farak model ka nahi, cohort ka hoga.
  • Treatment group itna bada ho ki statistically meaningful ho, par itna chhota ho ki kharab model se kam users affect hon.
  • Duration: bahut chhoti ho to data kam; bahut lambi ho to users lose honge.
  • Statistical significance: sirf zyada CTR dekh kar decide mat karo — two-sample hypothesis tests use karo. Repeated significance testing mat karo (baar-baar check karke pehli significant result par rukna — significance ko overestimate karta hai).
  • Segments dekho: overall CTR badha, par ek segment ka CTR gir gaya — to deploy mat karo. Aur agar churn double ho gaya to bhi nahi.
  • Infrastructure: logged-in users par aasan (database me group store karo); logged-out users par mushkil (cookies/IP se identify karo, par user har session me same variant paaye — ye guarantee karna mushkil hai).
  • Bade scale par (Airbnb ERF, Uber XP, Wasabi) experimentation platforms banti hain — dozens of tests parallel chalte hain.

Multiarmed Bandits

A/B testing se flexible — continuously test karte hain, 2 se zyada variants par bhi. Zyada tar requests best-performing model ko jati hain; chhota hissa random alternatives ko — taaki pata chale ki koi aur model behtar to nahi ho gaya.

  • Contextual bandits: har user ke liye kaunsa model behtar hai, ye bhi seekhte hain (Stitch Fix ka overview dekho).

Book ka aakhri message

Deploy aur monitoring abhi bhi naya practice hai — par yehi verify karta hai ki models value de rahe hain. Poori book me sirf chhota hissa model training ka hai — zyada tar kaam data aur engineering ka hai. Data scientists ko modeling ke resources aasani se milte hain, par iske bahar ke kaam ke liye nahi — ye book wahi gap bharne ki koshish hai. Ab tumhare paas poori ML product life cycle ke tools hain — product goal se lekar monitoring tak.

F1Ant me · Interview FAQs
Interview FAQs
ML interviews (current era) ke liye — framing se lekar monitoring tak, 36 sawaal-jawaab. Har jawaab isi book ke concepts par aadharit hai.
Q01 ML project shuru karne se pehle sabse pehla step kya hai?
Product goal ko ML ki bhasha me translate karna — framing. Ye tay karo ki kaam classification hai, regression hai, ranking hai ya generation — aur kya ye feasible hai. Model banana aakhri step hai, pehla nahi. Bina framing ke model achha bhi ho to product fail ho sakta hai.
Q02 ML kab use NAHI karna chahiye?
Jab kaam deterministic rules se ho sakta hai — jaise tax calculation. Rules fixed hain, exact jawab chahiye, to ML bewakoofi hai. ML tab use karo jab rules likhna mushkil ho ya bahut zyada rules hon — jaise spam detection, recommendations, image recognition.
Q03 Classification aur regression me kya farak hai?
Classification me input ko ek category me daalte hain — spam/not-spam, high-quality/low-quality question. Regression me ek number predict karte hain — ghar ki keemat, ya question ko kitne upvotes milenge. Dono supervised learning hain; farak sirf output ka type hai.
Q04 Weakly labeled data kya hota hai?
Aise labels jo imperfect/noisy hon — jaise Stack Exchange ke upvotes ko question quality ka label maan lena. Upvotes quality ka perfect measure nahi hain, par kaafi signal dete hain aur saste me milte hain. ML Editor isi par chalta hai. Weak labels se shuru karo, perfect labels ka wait mat karo.
Q05 Business metric aur model metric me kya farak hai?
Business metric product ka fayda naapti hai — revenue, retention, user satisfaction. Model metric offline performance naapti hai — accuracy, precision, F1. Sirf business metric asal me matter karti hai; model metric tabhi useful hai jab wo business metric se correlate kare. BLEU badhna zaroori nahi ki user ko behtar lage.
Q06 Guardrail metric kya hoti hai?
Wo metric jo main metric improve karte waqt bigadni nahi chahiye. Example: recommendations ki precision badhate waqt check karo ki kisi user group ke liye performance to nahi gir rahi. Guardrail bina, ek metric ko optimize karna dusri jagah nuksaan pahuncha sakta hai.
Q07 Distribution shift kya hai aur isse kaise ladein?
Jab production ka data training data se alag ho jaye — jaise baarish me traffic pattern badal jata hai. Model stale ho jata hai. Ladne ke tareeke: freshness metrics monitor karo, regular retraining karo, aur distribution shift ko monitor karke alert lagao (Chapter 11).
Q08 Prior art ko reproduce karna kyun zaroori hai?
Kyunki bina reproduce kiye tumhe pata nahi chalega ki published solution asal me kaam karta bhi hai ya nahi, aur tumhara setup sahi hai ya nahi. 3 steps: reproduce karo → apne data par lao → apne metrics par iterate karo. Dobara wheel mat banao.
Q09 Training aur inference pipeline me preprocessing same kyun honi chahiye?
Kyunki model ne training me jo preprocessing dekhi, wahi inference me expect karta hai. Agar dono alag hon to training-serving skew hoga — model ne kuch aur seekha, production me kuch aur aa raha hai. Ye ML me sabse common aur mushkil bug hai.
Q10 Pehla pipeline heuristics se kyun banao?
Kyunki heuristics se turant MVP banta hai — user feedback milta hai, data flow test hota hai, aur model ki jagah kuch to chalta hai. Heuristic baad me fallback bhi banta hai (Chapter 10). Model pehle banao to hafton tak kuch dikhane layak nahi hota.
Q11 Tokenization me kya pitfalls hain?
Text ko todna tricky hai — "Mr. O'Neill" me naive tokenizer "Mr." ko sentence-end samajh lega aur "O'Neill" ko tod dega. Isliye nltk/spaCy jaise tested tokenizers use karo, khud ka splitter mat likho. Har preprocessing step ko visualize karke check karo.
Q12 Data Quality Rubric ke 3 dimensions kya hain?
Format (data kis format me hai, parse karna aasan hai?), Quality (saaf hai? missing values? noisy labels?), Quantity & Distribution (kaafi data hai? har class ke examples hain? distribution production jaisi hai?). Har naye dataset par ye teeno check karo.
Q13 TF-IDF, Bag-of-Words se kaise behtar hai?
Bag-of-Words sirf word counts deta hai. TF-IDF common words (the, is, are) ko kam weight aur rare-informative words ko zyada weight deta hai. Isliye text classification me TF-IDF aksar behtar perform karta hai. ML Editor ka pehla model TF-IDF par hi tha.
Q14 Word2Vec ka distributional hypothesis kya hai?
"Jo words ek jaise context me aate hain, unke matlab ek jaise hote hain." Word2Vec words ko dense vectors me badalta hai jahan similar words paas hote hain. Isse model words ke beech ka semantic relation samajh pata hai — bag-of-words me ye nahi hota.
Q15 Transfer learning images me kaise kaam karta hai?
ImageNet par trained models (VGG, Inception) ki penultimate layer se features nikaalo — khud se train karne ki zaroorat nahi. Ye features generic visual patterns samajhte hain. Warning: pretrained model apne training data ka bias bhi laata hai.
Q16 Feature crosses kya hain? Leakage se kaise bachein?
Do features ko milakar naya feature banana — jaise day-of-week × day-of-month. Kuch patterns tabhi dikhte hain jab features combine hon. Leakage se bachne ke liye aisa feature mat banao jo label ko seedha leak kare — jaise future ki information wala feature.
Q17 Train/validation/test split ka sahi ratio kya hai?
Aam taur par 70/20/10 — training 70%, validation 20% (tuning ke liye), test 10% (aakhri benchmark). Test set par kabhi tune mat karo — wo sirf ek baar, ant me use hota hai. Chhote datasets par k-fold cross-validation use karo.
Q18 Data leakage ke 2 types kya hain?
Temporal leakage — future ki information training me aa jaye (jaise future bookings ka snapshot). Sample contamination — train aur test me same entity aa jaye (jaise same author dono taraf). Dono se validation jhooth bolta hai — accuracy suspiciously zyada dikhti hai.
Q19 GroupShuffleSplit kab use karein?
Jab train/test split me koi entity dono taraf nahi aani chahiye — jaise ML Editor me same author ke questions. GroupShuffleSplit author (OwnerUserId) ke hisaab se group karke split karta hai, to author sirf ek taraf rehta hai. Random split se leakage hota.
Q20 Bias-variance trade-off kya hai?
Complexity badhao to bias (underfitting) ghata, variance (overfitting) badha. Ek optimal point hota hai jahan total error minimum hai. Training par kharab = high bias; training par achha par validation par kharab = high variance. ML Editor ke pehle model me validation > training tha — matlab complexity badha sakte the.
Q21 Accuracy imbalanced data me kyun dhokha deti hai?
Agar 99% cases positive hon, to hamesha positive predict karne wala model 99% accurate hoga — par bilkul bekaar hai. Isliye precision, recall, F1 dekho — aur confusion matrix se har class par performance check karo.
Q22 Precision vs recall — recommendations me kaunsa zyada important hai?
Precision — kyunki galat suggestion dena, na dene se bura hai. User galat advice par bharosa karke kharab question likh dega. Fraud detection me recall zyada matter karta hai (koi fraud miss na ho). Har product me trade-off alag hai — threshold se balance karo.
Q23 Confusion matrix se kya pata chalta hai?
Kaunsi class par model achha hai aur kaunsi par kharab. ML Editor me model low-quality questions achhe se pakadta tha, par high-quality me se sirf aadhe. Ek column khaali ho to samjho model wo class kabhi predict hi nahi karta — rare classes ke liye khatarnaak hai.
Q24 ROC curve aur AUC kya hain?
ROC curve threshold badal kar TPR vs FPR plot karti hai. Diagonal = random guessing. AUC area hai — random 0.5, perfect 1.0. Practical tip: sirf AUC mat dekho — product need ki lines lagao (jaise FPR ≤ 10%), kyunki wahi acceptable thresholds tay karti hain.
Q25 Calibration kya hai aur kab matter karti hai?
Calibration ka matlab hai ki model ki predicted probability uske asal confidence ko sahi dikhaye — 80% probability wale cases me se asal me ~80% positive hon. Ye tab matter karti hai jab tum score user ko dikhate ho (jaise ML Editor ka quality score). Calibration curve se check karo.
Q26 Top-k method kya hai?
Model ki k best, k worst aur k most uncertain predictions ko dekhna (k = 10–15). Best se pata chalta hai kaunsi features kaam kar rahi hain; worst se pata chalta hai kaunsi feature missing hai (jaise question-mark count); uncertain se pata chalta hai conflicting labels ya training data me gap.
Q27 LIME aur SHAP kya hain?
Black-box explainers — complex models (neural nets) ki predictions ko explain karte hain. Ek example ko perturb karke (words hata kar) dekhte hain ki prediction kaise badalti hai. ML Editor me LIME ne pakda ki model common words par rely kar raha hai — aur ek email classifier me LIME ne data leakage pakda tha.
Q28 ML debugging ke 3 steps kya hain?
1) Debug Wiring — kya data pipeline se beh raha hai? (ek example se shuru karo.) 2) Debug Training — kya model training data par fit ho sakta hai? 3) Debug Generalization — kya model unseen data par kaam karta hai? Steps skip mat karo — yehi sabse tez raasta hai.
Q29 Silent failure kya hai? Example do.
Jab pipeline bina error ke chale par results galat hon. Example: data normalize nahi hua — model train to hoga, par fit nahi hoga. Ya segmentation mask me 255 ki jagah 1 use kar diya — mask khaali samjha jayega. Isliye har step par data visualize karo aur tests likho.
Q30 ML code me kya-kya test karna chahiye?
Teen areas: 1) Data ingestion — parser DataFrame deta hai? columns hain? null to nahi? 2) Data processing — features ke types aur ranges sahi hain? 3) Model outputs — prediction shape sahi hai? probabilities 0–1 me hain? Ek regression test rakho jo kharab input par hamesha sahi jawab de.
Q31 Overfitting se kaise ladein? L1 vs L2 vs dropout?
L1 (weights ke absolute value par penalty) uninformative features ko zero kar deta hai — feature selection jaisa. L2 (squared weights) weights ko chhota rakhta hai. Dropout neural nets me training ke dauraan random neurons ignore karta hai. Random forest me max depth kam karo. Aur sabse effective: zyada data aur data augmentation.
Q32 Data augmentation kya hai?
Existing data ko thoda badal kar naya training data banana — images ko rotate/crop/darken karna. Training performance kam hoti hai, par validation badhta hai kyunki model zyada varied inputs dekhta hai. Hurricane example: training images ko darker/blurrier banaya to flooded roads par performance badhi.
Q33 Recommendations nikaalne ke 4 methods kya hain?
1) Feature statistics — class-wise average values se rules banao (bina model ke). 2) Global feature importance — important features ki recommendations pehle. 3) Model ka calibrated score dikhao. 4) Local feature importance (LIME) — har example ke liye personalized recommendations. Accuracy vs latency ka trade-off hai.
Q34 V3 model V2 se kyun behtar tha jabki uski precision kam thi (0.597 vs 0.63)?
Kyunki product goal recommendations dena tha, sirf classify karna nahi. V3 sirf 30 explainable features use karta tha, isliye uski calibration sabse behtar thi, wo fast tha, aur uski features se user ko samajh aane wali recommendations banti thi. V2 ke important features "are" aur "what" jaise words the — unse recommendation nahi banti.
Q35 Deployment options — streaming vs batch vs on-device vs federated?
Streaming: request aate hi jawab — latency tight ho to. Batch: pehle se compute karke store karo — data pehle se mile to. On-device: offline/privacy chahiye to — model chhota karna padta hai (pruning, quantization). Federated: har user ka apna model + privacy — jaise Gboard. Prototype ke liye streaming ya batch se shuru karo.
Q36 Filtering model kya hai aur kab faydemand hai?
Ek chhota classifier jo predict karta hai ki main model is example par fail hoga ya nahi — taaki mushkil inputs par main model chalaya hi na jaye. Google Smart Reply me triggering model se infrastructure 10x bacha. Faydemand tabhi jab filter karne se bachta time, filtering ke cost se zyada ho.
