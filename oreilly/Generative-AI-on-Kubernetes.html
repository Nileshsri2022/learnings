Preface — Production Mushkil Hai

Why We Wrote This Book — kitab kyun likhi gayi

Kitab ke hisaab se ab mushkil kaam model train karna ya API call karna nahi raha. Mushkil kaam hai generative AI ko reliably, economically aur safely production me chalana. Generative AI ko ek platform concern ke roop me dekha gaya hai, demo concern ke roop me nahi. Kubernetes isliye natural jagah hai kyunki woh pehle se scheduling, scaling, storage, networking, observability aur multi-tenancy sambhalta hai — AI workloads ko bas usi platform par theek se chalana seekhna hai.

Kubernetes — kya assume kiya gaya hai

Kitab assume karti hai ki reader ko clusters, pods, deployments, services aur namespaces ka working knowledge hai. Ye Kubernetes zero se nahi sikhati. AI-specific extensions — jaise GPU management, bade model files, lambi start-up times aur batch jobs — us base ke upar samjhaye gaye hain.

Generative AI — chhota itihaas

Ek chhota history diya gaya hai: 2014 me generative adversarial networks (GANs), 2017 me attention-based transformer, aur phir woh step-change jab large language models widely usable hue. Transformer ne ek general text engine possible banaya — aur uske baad engineering problem shift ho gayi: serving, data, cost aur control ki taraf.

02Shuruaat

Introduction — LLM aur Inference

ChatGPT ke public release se pehle bhi generative models the — lekin November 2022 ko phase transition mana gaya hai. Uske baad sawal badal gaya: "kya ye generate kar sakta hai?" se "hum ise sabke liye, hamesha, acceptable cost par kaise chalaye?" tak.

From GANs to ChatGPT

Generative models 2022 se pehle bhi maujood the, lekin ChatGPT ke public release ke baad ek general-purpose text model non-specialists ke liye usable ho gaya. Demand explode ho gayi — aur question badal gaya: generate karna nahi, balki use har kisi ke liye, har waqt, acceptable cost par chalana.

What Is a Large Language Model?

LLM ek bada neural network hai jo bahut bade text corpora par train karke next token predict karta hai, transformer par bana hua. Inference ke waqt woh human sense me "jaanta" nahi hai — woh prompt aur apne weights ke hisaab se sabse plausible continuation produce karta hai. Size, training data aur architecture sab matter karte hain, lekin serving behaviour kuch concrete quantities se govern hota hai: parameters, context length aur memory.

Inference — do phases

Poori kitab me do phases alag rakhi gayi hain:

  • Prefill: poora prompt ek saath process hota hai, compute-heavy hai, aur pehla token plus KV cache produce karta hai.
  • Decode: ek-ek token generate hota hai, memory-bandwidth-bound hai, aur KV cache ko reuse karta hai.

Ye split samjhata hai ki time-to-first-token (TTFT) aur inter-token latency alag behave kyun karte hain — aur batching aur caching itne important kyun hain.

KV Cache aur PagedAttention

KV cache pehle dekhe gaye tokens ke attention keys aur values store karta hai, taaki decode unhe dobara compute na kare. Ye context length aur batch size ke saath badhta hai aur GPU memory par haavi ho sakta hai. PagedAttention (vLLM se) ise fixed-size blocks me manage karta hai — operating-system pages ki tarah — taaki memory fragmentation par waste na ho aur bahut zyada concurrent sequences fit ho sakein.

A Short Overview of the GenAI Ecosystem

Field ko divisions me baanta gaya hai: model providers aur open models, serving engines, Kubernetes operators aur platforms, vector stores, observability tools aur agent frameworks. Kitab ka focus self-hosted, open-model path hai, ye note karte hue ki kab hosted API simpler choice hoti hai.

The Model Serving Landscape

Engines throughput, latency, features (jaise structured output, prefix caching, disaggregated serving) aur hardware support me alag hote hain. Kitab zyada tar examples ke liye vLLM ko standardise karti hai — kyunki ye widely used, fast aur OpenAI-compatible hai — aur alternatives jaise TensorRT-LLM, TGI, llama.cpp aur doosron ka naam passing me liya gaya hai.

Kubernetes for AI

Kubernetes ko AI workloads ka control plane kaha gaya hai — woh pehle se jaanta hai kaam ko place karna, restart karna, expose karna, scale karna aur tenants ko isolate karna. Naya kaam hai use GPUs, bade model files, lambi start-up times aur batch jobs ke baare me sikhana, jo ordinary web services nahi hain.

Kubernetes-Based Serving Solutions

  • KServe: model ka higher-level abstraction deta hai.
  • KServe LLM inference extension (llm-d): disaggregated prefill/decode aur smarter routing jodta hai.
  • Knative Serving: scale-to-zero deta hai.
  • Plain Deployment: full control deta hai — aur kitab ka Ch 1 ka starting point yahi hai.

Beyond Inference: Agentic Applications

Ek single completion sirf shuruaat hai. Asli applications calls ko chain karte hain, documents retrieve karte hain, tools call karte hain aur state rakhte hain — Ch 8–9 ki agentic applications.

The Cluster Environment

Poori kitab me ek local Kubernetes cluster istemal hota hai, jo Kind (Kubernetes in Docker) se banaya gaya hai, plus GPU support jahan GPU available ho — ya GPU chapters ke liye cloud cluster. CPU-only inference sabse chhote models ke liye possible hai, lekin kitab ka target nahi hai. Real inference ke liye GPU node chahiye.

Building the Model Server Image

Image official vLLM image par based hai, jisme model add kiya jata hai ya start-up par download hota hai. vLLM image me pehle se CUDA libraries aur Python dependencies hain. Ek Dockerfile/Containerfile configuration layer kar sakta hai. Key point: image ko reproducible rakho, aur bade weights ko har image layer me bake karne se bacho agar woh aksar change hote hain — ye theme Ch 2 me wapas aati hai.

Deploying the Model Server on Kubernetes

Ek Deployment banta hai — ek replica, GPU resource request, container port, aur model name aur serving options ke liye environment variables. Ek Service use cluster ke andar expose karta hai aur port-forward laptop tak. Har field samjhaya gaya hai: image, vLLM start karne wala command, GPU reserve karne wale resource limits, aur readiness/liveness considerations — jo Ch 4 me dobara aayenge, kyunki model server tab tak ready nahi hota jab tak model load na ho jaye, jisme minutes lag sakte hain.

Ch 2 · Model Data

Model ek file nahi hai — woh versioned artifacts ka set hai. Aur un artifacts ko pods tak pahunchana ek first-class deployment concern hai.

From Training to Inference

Training weights produce karta hai; inference unhe consume karta hai. Dono phases ki storage needs alag hain — training ko datasets aur checkpoints tak fast, shared access chahiye; inference ko final weights har node par chahiye jo model serve karta hai, jaldi aur reliably.

Understanding Model Artifacts

Model ek file nahi hai. Ye weight shards ka set hai (safetensors format kitab ke examples me), ek tokenizer, ek configuration file (config.json) aur instruction models ke liye ek chat template. Har artifact ka role samjhaya gaya hai — aur tokenizer ko model se exactly match karna chahiye, warna outputs galat honge.

Figure 2-2 — Hugging Face model repository layout · Ek model repository ke chaar hisse — sabka role alag hai, sab zaroori hain. (notes ke description se dobara banaya gaya diagram)

Quantisation and size

Wahi 3B model precision ke hisaab se disk aur GPU memory me bahut alag jagah leta hai — 16-bit me lagbhag 6 GB, 8-bit me lagbhag 3 GB, aur 4-bit me lagbhag 1.5–2 GB — aur uske saath output quality ka trade-off hota hai. Exact saving quantisation method par depend karti hai, aur kitab warn karti hai ki chhota model hamesha "wahi model" hai ye assume mat karo.

Figure 2-1 — Model file size by quantisation (3B model) · Precision ghatne par size lagbhag aadha-aadha hota jata hai — quality ka trade-off saath me hai. (notes ke description se dobara banaya gaya diagram)

Model Storage and the Model Registry

Hugging Face Hub example registry hai — public aur gated models ke saath, aur gated models jaise Llama ke liye access token chahiye. Registry source of truth hai; cluster ek cache hai, source nahi.

Model Data Delivery to Kubernetes

Naive approaches compare kiye gaye hain:

  • Weights ko container image me bake karna: simple hai, lekin image tens of gigabytes ki ho jati hai aur har model change par rebuild hoti hai.
  • Pod start-up par Hub se download: simple hai, lekin slow aur fragile hai — aur har replica alag se download karta hai.
  • PersistentVolume: shared hai, lekin storage class aur pre-population chahiye.
  • Aur neeche do purpose-built approaches.

Deploying with ModelCars

ModelCar ek container image hai jisme sirf model files hoti hain, jo KServe ModelCar tooling se banti hai. Model server pod ek init container ya sidecar chalata hai jo model ko ModelCar image se shared emptyDir volume me copy karta hai, taaki serving container files ko locally dekh sake. Chapter ka example Llama-3.2-3B ke liye ModelCar banata hai aur phir use Deployment me mount karta hai. Fayda: model images kisi bhi container image ki tarah versioned aur cached hoti hain, aur koi alag storage system nahi chahiye.

Kubernetes 1.31+ (kitab me versions alag-alag jagah alag diye gaye hain — neeche note dekhein) OCI image ko seedha volume ke roop me mount karna support karta hai, bina init container ke. Pod spec me image volume source ModelCar/OCI image ki taraf point karta hai, aur kubelet use model path par read-only mount karta hai. Ye cleanest current approach mana gaya hai jahan cluster support karta ho.

Teeno numbers yahan waise hi rakhe gaye hain — ek ko silently chunna galat hota. Feature recent aur version-gated hai; apne cluster ka version check karo.

Summary

Model data ek first-class deployment concern hai — registry, delivery mechanism aur pod spec ko model path, format aur version par agree karna chahiye.

Lessons Learned

  1. Models ko versioned artifacts ki tarah treat karo, haath se copy ki gayi files ki tarah nahi.
  2. Bade weights ko serving image me bake mat karo agar avoid kar sakte ho.
  3. ModelCars portable, image-based delivery dete hain jo kisi bhi cluster par kaam karta hai.
  4. OCI volumes jahan supported ho wahan simpler future hain — lekin pehle Kubernetes version check karo.

Ch 3 · Kubernetes and GPUs

GPUs expensive, scarce aur naive model me indivisible hain — ek GPU per pod. Unhe achhe se share aur schedule karna cost problem hai, sirf performance problem nahi.

Why Kubernetes Needs GPUs

CPUs transformer inference ke liye chahiye parallel floating-point throughput acceptable latency par nahi de sakte. GPUs hazaaron chhote cores aur high-bandwidth memory (HBM) dete hain — lekin woh expensive, scarce aur naive model me indivisible hain, isliye unhe share aur schedule karna cost problem hai, sirf performance problem nahi.

Sharing GPU Capacity

Teen mechanisms compare kiye gaye hain:

  • Time-slicing: GPU time-multiplexing se share hota hai — kai pods ek device share karte hain, har ek ko time ka slice milta hai. Simple hai, chhote bursty workloads ke liye kaam karta hai, lekin koi memory isolation nahi aur koi performance guarantee nahi.
  • Multi-Process Service (MPS): NVIDIA ka MPS multiple processes ko GPU zyada efficiently share karne deta hai — kuch workloads ke liye time-slicing se better utilisation, lekin memory abhi bhi shared hai.
  • Multi-Instance GPU (MIG): GPU physically isolated instances me partition ho jata hai, har ek ki apni memory aur compute. Hard isolation aur predictable performance, lekin partition sizes fixed hain aur GPU ko support karna chahiye.

Kitab ki guidance: bade production models ke liye whole GPUs istemal karo; sharing sirf chhote models, development ya multi-tenant cost saving ke liye.

Sharing GPUs with Dynamic Resource Allocation (DRA)

DRA accelerators ko fixed count ke bajay attributes (jaise memory ya compute capability) se request karne ka newer Kubernetes API hai. Ek ResourceClaim batata hai kya chahiye; ek driver (jaise NVIDIA DRA driver) use real device se match karta hai — MIG slice ya GPU ka fraction bhi. DRA fine-grained GPU sharing ka future mana gaya hai, lekin likhte waqt simple count-based request se newer aur kam universally supported tha.

Other GPU Details

Chapter GPU memory types samjhata hai, kyun HBM bandwidth decode ke liye matter karta hai, datacentre cards (jaise A100/H100, 80 GB) aur consumer cards me farak, aur kyun GPU ki sankhya aksar binding constraint hoti hai ki kaun se size ka model serve ho sakta hai.

Summary

GPUs scarce, expensive resource hain; Kubernetes unhe manage kar sakta hai — lekin sirf tab jab operator, device plugin aur pod requests sab sahi set up hon.

Lessons Learned

  1. Model server debug karne se pehle node par GPU capacity verify karo.
  2. Whole-GPU allocation sabse simple aur predictable hai.
  3. Sharing mechanisms isolation ke badle utilisation trade karte hain.
  4. DRA fractional GPUs ke liye promising hai — lekin driver aur Kubernetes version support check karo.

Security for Agents

Chapter ka central production concern identity aur authorisation hai. User ki taraf se kaam karne wale agent ko user se zyada privilege inherit nahi karna chahiye. Kitab samjhati hai:

14FAQs · Interview

FAQs — Interview Sawal-Jawab

36 interview-style sawal, kitab ke content par based. Har jawab Hinglish me, concept ke saath.

Q01LLM inference me prefill aur decode me kya farak hai?
Prefill poora prompt ek saath process karta hai, compute-heavy hai, aur pehla token plus KV cache produce karta hai. Decode ek-ek token generate karta hai, memory-bandwidth-bound hai, aur KV cache reuse karta hai. Isi liye TTFT aur inter-token latency alag behave karte hain.
Q02KV cache kya hai aur ye GPU memory kyun khata hai?
KV cache pehle dekhe gaye tokens ke attention keys aur values store karta hai taaki decode dobara compute na kare. Ye context length aur batch size ke saath badhta hai aur GPU memory dominate kar sakta hai. PagedAttention ise fixed-size blocks me manage karta hai, OS pages ki tarah.
Q03PagedAttention kya karta hai?
PagedAttention (vLLM se) KV cache ko fixed-size blocks me manage karta hai, taaki memory fragmentation par waste na ho aur bahut zyada concurrent sequences fit ho sakein.
Q04vLLM ko serving engine kyun chuna gaya hai kitab me?
Speed, continuous batching, PagedAttention aur OpenAI-compatible API ke liye. Alternatives TensorRT-LLM, TGI aur llama.cpp bhi naam liye gaye hain, lekin zyada tar examples vLLM par hain.
Q05Llama 3.2 3B model kyun chuna gaya running example ke liye?
Ye modest GPU par chal jata hai, phir bhi ek asli instruction model hai — 3B parameters, instruct-tuned, Hugging Face repo meta-llama/Llama-3.2-3B-Instruct me. Chhota model pipeline prove karta hai, usse pehle ki 70B budget kha jaye.
Q06Kind cluster kya hai?
Kind matlab Kubernetes in Docker — local Kubernetes cluster jo Docker containers me chalta hai. Kitab poori me isi local cluster ka istemal karti hai, GPU chapters ke liye cloud cluster ke saath.
Q07Model server ka image kaise banaya jata hai?
Official vLLM image par based image banti hai, jisme model add kiya jata hai ya start-up par download hota hai. vLLM image me pehle se CUDA libraries aur Python dependencies hain. Weights ko image layer me bake karne se bacho agar woh aksar change hote hain.
Q08Model artifacts me kya-kya hota hai?
Weight shards (safetensors format), tokenizer, config.json aur instruction models ke liye chat template. Tokenizer ko model se exactly match karna chahiye.
Q09Quantization se model size kaise badalta hai?
3B model 16-bit me lagbhag 6 GB, 8-bit me lagbhag 3 GB, aur 4-bit me lagbhag 1.5–2 GB leta hai — quality ke trade-off ke saath. Exact saving method par depend karti hai.
Q10ModelCar kya hai?
ModelCar ek container image hai jisme sirf model files hoti hain. Pod ek init container ya sidecar chalata hai jo model ko ModelCar image se shared emptyDir volume me copy karta hai, taaki serving container files ko locally dekh sake. Model images versioned aur cached hoti hain, jaise koi bhi container image.
Q11OCI volumes ModelCars se kaise alag hain?
OCI volumes me kubelet OCI image ko seedha volume ke roop me mount karta hai, bina init container ke — pod spec me image volume source point karta hai aur kubelet use read-only mount karta hai. Ye cleanest approach mana gaya hai jahan cluster support karta ho (Kubernetes 1.31+; kitab me 1.35, 1.33 aur 1.31 — teeno numbers alag jagah diye gaye hain).
Q12Kubernetes me GPU kaise request karte hain?
Pod spec me extended resource request karte hain — nvidia.com/gpu: 1. Scheduler tabhi place karta hai jab node par free GPU ho; device plugin GPU advertise karta hai; kubelet aur container runtime use container ke andar expose karte hain.
Q13NVIDIA GPU Operator kya karta hai?
Ye drivers, device plugin aur monitoring ko Kubernetes resources ke roop me install karta hai — Helm se install hota hai. Uske baad nodes GPU capacity report karte hain.
Q14Time-slicing, MPS aur MIG me kya farak hai?
Time-slicing GPU ko time-multiplexing se share karta hai — koi memory isolation nahi. MPS multiple processes ko zyada efficiently share karne deta hai, lekin memory shared rehti hai. MIG GPU ko physically isolated instances me partition karta hai — hard isolation aur predictable performance, lekin fixed slice sizes.
Q15Dynamic Resource Allocation (DRA) kya hai?
DRA accelerators ko fixed count ke bajay attributes (jaise memory ya compute capability) se request karne ka newer Kubernetes API hai. ResourceClaim batata hai kya chahiye; driver use real device — MIG slice ya GPU fraction — se match karta hai.
Q16GPU sharing kab istemal karna chahiye aur kab nahi?
Bade production models ke liye whole GPUs istemal karo. Sharing sirf chhote models, development ya multi-tenant cost saving ke liye hai.
Q17Production me model server ke probes kaise set karte hain?
Startup probe lamba failure threshold rakhta hai kyunki model loading me minutes lag sakte hain (example me 60 seconds initial delay). Readiness tabhi pass hoti hai jab model load ho jaye. Graceful shutdown in-flight requests ko drop hone se bachata hai.
Q18vLLM ke kaun se flags production me matter karte hain?
--max-model-len context aur KV cache cap karta hai, --gpu-memory-utilization GPU memory ka fraction cap karta hai (example 0.9), --max-num-seqs concurrent sequences cap karta hai, aur --enforce-eager/compilation trade-offs hote hain.
Q19Model ko rollout karne se pehle kaise evaluate karte hain?
Benchmark set par purane aur naye model ko same prompts bhejkar compare karte hain — accuracy/quality, TTFT, inter-token latency, throughput, error rate aur cost per request. Phir canary rollout: chhota traffic share, phir bada, phir full — rollback path ke saath.
Q20CPU-based HPA GPU inference ke liye kyun galat hai?
Kyunki GPU utilisation aur queue length matter karte hain, CPU nahi. KEDA Prometheus metric (waiting requests ya GPU utilisation) par scale karta hai, taaki replicas tab badhein jab queue badhe.
Q21Prefix-aware routing kya hai?
Prompt prefix share karne wale requests same replica par bheje jate hain, taaki prefix caching ka fayda mile. Load-aware routing me router har replica ki queue depth aur KV-cache usage jaanta hai aur kaam sabse kam loaded replica ko bhejta hai.
Q22TTFT aur TPOT kya hain?
TTFT (time to first token) pehla token stream hone tak ka time hai — prefill aur queueing se dominate hota hai. TPOT (time per output token) decode ke dauraan tokens ke beech ka gap hai.
Q23vLLM ke kaun se Prometheus metrics dekhne chahiye?
Running aur waiting requests, tokens processed, KV-cache usage, TTFT aur TPOT histograms, aur GPU cache usage. Inhe Prometheus scrape karta hai aur Grafana dashboard dikhata hai.
Q24Production me prompts log kyun nahi karne chahiye?
Kyunki prompts me personal ya sensitive data ho sakta hai. Logs me request ID, model name, prompt length aur latency breakdown rakho — full prompt ya completion text nahi.
Q25Output guarding kya hai?
Generated text ko return karne se pehle policy violations, hallucinated ya unsafe content aur PII ke liye check karna. Guard models aur TrustyAI project iske examples hain. Observability bina guarding ke bata sakti hai ki bura output hua, lekin use rok nahi sakti.
Q26Fine-tuning aur RAG me se kab kya chunna chahiye?
Knowledge baar-baar badalta ho ya cite karna ho to RAG; model ko naya skill, style ya task format sikhana ho to fine-tuning; dono chahiye hon to dono — RAG facts ke liye, fine-tuning behaviour ke liye.
Q27LoRA aur QLoRA me kya farak hai?
LoRA frozen weights ke upar chhota low-rank adapter update karta hai — far cheaper, adapter chhoti file hai jo swap ho sakti hai. QLoRA LoRA hai quantised base model ke saath — aur sasta, thodi quality cost ke saath. Kitab LoRA ko default recommend karti hai.
Q28Kubeflow Trainer kya karta hai?
Fine-tuning job ko Kubernetes Job ke roop me chalata hai — training pod, GPU allocation aur checkpoint output manage karta hai. Example me LoRA run hai, JSONL dataset aur checkpoints ke liye PersistentVolumeClaim ke saath.
Q29Gang scheduling kya hai aur kyun chahiye?
Job ke saare pods ek saath start hone chahiye ya koi nahi — taaki distributed training job kuch GPUs occupy karke baaki ka wait na kare. 4-pod job ka example Fig 7-2 me hai.
Q30Kueue kya hai?
Kubernetes ka queueing system — ClusterQueues, LocalQueues aur Cohort hierarchies. Idle queue se capacity borrow kar sakte hain, aur higher-priority job aane par lower-priority kaam preempt hota hai.
Q31Topology-aware scheduling kyun matter karta hai?
NUMA node ke andar ya NVLink par communication fast hai; nodes ke across Ethernet par slower; racks ke across aur slow. Distributed training ke workers ko paas me place karna chahiye — GPU sirf GPU nahi hota, uske neighbours matter karte hain.
Q32Agent aur simple application me kya farak hai?
Simple application ek prompt bhejta hai aur ek jawab dikhata hai. Agent prompt bhejta hai, tool call ka decision padhta hai, tool execute karta hai, result wapas feed karta hai, aur task poora hone tak repeat karta hai. Farak model nahi, uske aas-paas ka loop hai.
Q33MCP aur A2A me kya farak hai?
MCP agent-to-tool ke liye hai — tools, resources aur prompts discover aur expose karta hai. A2A agent-to-agent ke liye hai — agents agent card expose karte hain aur messages/tasks ke through delegate karte hain.
Q34Agents ke liye token exchange aur SPIFFE kya hain?
Token exchange (OAuth 2.0) me agent user ka token exchange karke scoped-down token leta hai jo sirf specific downstream service/action ke liye valid hota hai. SPIFFE/SPIRE me har pod ko cryptographic identity (SPIFFE ID) milti hai, bina long-lived secrets ke.
Q35Agent state ko persist kyun karna chahiye?
Agent ka run minutes ya hours chal sakta hai aur kai model calls span kar sakta hai. Har step ke baad checkpoint save karo — conversation history, tool results, plan — taaki crash ya pod restart ke baad last checkpoint se resume ho sake. Tool calls idempotent hone chahiye taaki retry par side effect dobara na ho.
Q36Prompt injection kya hai?
Ek prompt jo model ko uski instructions ignore karne par majboor karne ki koshish karta hai. Model output ko untrusted data ki tarah treat karna chahiye, commands ki tarah nahi — ye Afterword me production risk ke roop me discuss kiya gaya hai.
