Preface — kitab kaise bani aur kiske liye hai

Ye kitab is baat se shuru hoti hai ki prompt engineering sirf tricks ka bag nahi hai. Iske peeche kuch chhote, durable principles hain — aur poori kitab unhi principles ko samjhane ke liye likhi gayi hai. Lekhak dono ek bade code assistant par kaam karte hue mile, aur unhone paya ki LLMs ke baare me sochne ka unka tareeka us samay ke published advice se alag tha.

Kitab kaise bani

Lekhak batate hain ki unhone LLMs par kaam karte hue ek aisi soch develop ki jo sirf kisi ek provider ke interface ya fashion par based nahi thi. Unka focus is par tha ki language models asal me kaise behave karte hain — model ke andar kya hota hai, wo text ko kaise dekhta hai, aur us behaviour se kya conclusions nikalte hain. Isi liye kitab ke principles aaj bhi kaam karte hain, chahe model ka version badal jaye.

Kiske liye hai ye kitab

  • Developers aur technically-minded product log jo LLMs ke upar applications banana chahte hain.
  • Wo log jinhone prompting try karke dekha aur results uneven paye — kabhi kamaal, kabhi bekaar.
  • Machine learning ki pehle se training zaroori nahi hai, lekin code aur software banane me comfortable hona expected hai.
  • Ye kitab models ko scratch se train karne ke baare me nahi hai — ye unko use karke application banane ke baare me hai.

Tum kya seekhoge

Kitab ka arc teen hisso me hai: (1) LLMs kaise kaam karte hain — utna jitna ek builder ko chahiye; (2) prompt aur poori application design karna — model ke aas-paas ka system; (3) application ko reliable enough to ship banana — conversation, tools, workflows aur evaluation ke saath.

Ch 1 — Introduction to Prompt Engineering

ChatGPT ke public release ne LLMs ko achanak non-specialists ke liye visible bana diya. Prompt matlab wo text jo tum model ko dete ho — ek request, sawal, instruction, ya kisi document ki shuruaat jise model poora kare. Completion matlab wo text jo model badle me deta hai. Poori kitab isi simple exchange ke aas-paas banti hai.

LLMs Are Magic

Lekhak batate hain ki unhone model se aise kaam karwaye jo computer ke liye jaadui lagte the — likhna, summarise karna, translate karna, code likhna. Asli surprise is generality me hai: ek hi model, bina retraining ke, kai tasks kar sakta hai — bas task ko prompt me achhe se describe kar do. Yahi generality kitab ka subject hai.

Language Models: How Did We Get Here?

Early Language Models

Shuru ke language models statistical the: kuch words diye, to wo agla word predict karte the — text me patterns gin kar, jaise Markov-style counting ki kaunsa word kiske baad aata hai. Phir neural sequence-to-sequence models aaye jinhone richer representations seekhe.

GPT Enters the Scene

Decisive turn transformer aur phir GPT tha: bade models, huge text par train kiye gaye, sirf agle token ko predict karne ke simple goal se — aur is simple goal ka side effect tha broad abilities. GPT-3 ki scale ne few-shot prompting practical bana di: prompt me examples do, model pattern follow karta hai. ChatGPT ne phir is ability ko conversational aur widely accessible bana diya.

Prompt Engineering

Prompt engineering ki definition: model ke behaviour ko prompt aur surrounding application se shape karne ki kala, model ke weights badle bina.

Central metaphor — PlaywritingModel ko database ki tarah order mat do. Tum ek natak likhte ho jisme model ka ek role hai, aur wo us role ko nibhayega. Achha prompt ek scene, ek role, ek situation aur ek format set karta hai — taaki tumne jo document stage kiya hai, uska natural continuation wahi jawab ho jo tum chahte ho.

Conclusion — sophistication ke levels

Prompt engineering ke levels hain: ek single direct sawal se lekar staged documents tak, aur phir poori applications tak jo state, tools aur evaluation manage karti hain. Kitab in levels par order se chadhti hai.

Ch 2 — Understanding LLMs

LLM ek aisi machine hai jo tokens ki sequence dekh kar agle token ki probabilities assign karti hai aur unme se sample karti hai. Wo enormous text corpora par train hoti hai — kitab The Pile ko example dataset ke roop me naam deti hai — taaki uski predictions real writing ke patterns ko reflect karein.

Auto-Regressive Models

"Auto-regressive" ka matlab: model ek token generate karta hai, use wapas input me daalta hai, aur agla token generate karta hai. Lamba jawab step by step banta hai, aur har step sirf wo dekh sakta hai jo pehle aa chuka hai. Kyunki wo documents ko continue karne ke liye train hota hai, uski basic skill hai patterns aur repetitions ko pehchanna aur extend karna: agar prompt ek pattern set karta hai, model use aage badhayega. Isi se few-shot learning samajh me aati hai (examples pattern set karte hain) aur failures bhi (galat pattern set ho gaya to model use bhi follow karega).

How LLMs See the World — insaan se 3 farak

Difference 1: Deterministic Tokenizers

Text pehle tokens me split hoti hai ek fixed, deterministic procedure se (GPT tokenizer running example hai). Wahi string hamesha wahi tarah tokenise hoti hai. Token boundaries word boundaries se match karna zaroori nahi — common words aam taur par ek token hote hain, rare words tukdo me split ho jate hain.

Difference 2: LLMs Can't Slow Down and Examine Letters

Model token identities dekhta hai, token ke andar ke individual letters nahi — jab tak prompt unhe spell out na kare. Isi liye wo letters ginne, spelling, ya Scattergories jaise word games me kharab ho sakta hai jahan pehla letter matter karta hai — wo information use seedhe taur par visible hi nahi hoti.

Difference 3: LLMs See Text Differently

Wo insaan ki tarah meaning ke liye nahi padhta; wo surface statistical regularities par respond karta hai. Capitalisation, punctuation, spacing aur word order behaviour badal sakte hain — aise tareeke se jo insaan ko surprising lage — aur wahi request alag phrasing me alag quality ka jawab de sakti hai.

One Token at a Time — Counting Tokens aur Inertness

Kaam aur pricing ki unit token hai. Chapter token counting samjhata hai OpenAI ki tiktoken library aur Hugging Face tokenizer tools se. Model ka context window tokens me measure hota hai, words ya characters me nahi — isliye prompt budgeting tokens me karni hoti hai.

Temperature and Probabilities

Har step par model agle token par ek probability distribution deta hai. Temperature control karta hai ki us distribution se kitni sharply sample kiya jaye:

  • Low temperature (0 ke paas): sabse likely token lagbhag certain ho jata hai — output deterministic aur conservative.
  • High temperature: distribution flat ho jati hai — rare tokens ke choose hone ki chance badh jati hai, output varied aur zyada error-prone.
  • Top-p (nucleus sampling): related control — sampling ko un sabse chhote token set tak limit karta hai jinki probabilities ka sum p hota hai.

Practical guidance: factual, repeatable kaam ke liye low temperature; variety chahiye tabhi high temperature — aur high-temperature model se reproducibility ki ummeed kabhi mat rakho.

The Transformer Architecture

Simplified explanation: attention ki layers har token ki representation ko context ke dusre tokens se inform hone deti hain, taaki model long-range context use kar sake. "Attention game" lekhako ka illustration hai — tokens ek dusre par attend karte hain. Transformer poora prompt parallel me layers me process karta hai (kitab ke informal term me "minibrains"), har layer representation ko refine karti hai, aur phir agla token generate hota hai.

Human Thought Versus LLM Processing

Insaan sequentially sochta hai — ruk sakta hai, dobara padh sakta hai, plan aur revise kar sakta hai. Model har token ke liye ek single forward pass karta hai, sochne ke liye ruk nahi sakta — sirf tokens generate karke soch sakta hai (isi liye chain-of-thought kaam karta hai: wo model ko sochne ke liye tokens deta hai), aur uska koi alag planning step nahi hota. Uski intelligence wahi hai jo ek achhe document ke agle hisse ko predict karne me hoti hai.

Ch 3 — Moving to Chat

Ek base model jo sirf documents complete karta hai, wo chat assistant kaise bana? Jawab hai reinforcement learning from human feedback (RLHF). Ye chapter us process ko step by step kholta hai.

The Process of Building an RLHF Model

Step 1 — Supervised fine-tuning (SFT)

Base model ko desired behaviour ke examples par aur train karo — prompts ke human-written responses — taaki wo sirf text continue karne ke bajay helpfully answer karna seekhe.

Step 2 — Reward model

Ek alag model train karo jo responses ko score kare: insaan batate hain ki ek hi prompt ke do responses me se kaunsa behtar tha; reward model ek human preference function seekh leta hai.

Step 3 — RLHF model

Proximal policy optimisation (PPO) se chat model ko adjust karo taaki uske responses reward model ke hisab se high score karein, lekin supervised model se zyada door na bhatkein. Result: ek model jo helpful, honest aur harmless (HHH alignment) banne ki koshish karta hai — HHH alignment Anthropic ne introduce kiya tha.

Trade-offs — Alignment Tax aur baaki effects

  • Beware of the Alignment Tax: RLHF kuch tasks par raw capability ya knowledge kam kar sakta hai — alignment kuch breadth ki keemat par safe, helpful behaviour deta hai.
  • RLHF Packs a Lot of Bang for the Buck: lekhak zor dete hain ki thoda sa human feedback bhi base model ko useful product me badal deta hai — chhota investment, bada transformation.
  • Avoiding Idiosyncratic Behavior: model ek consistent persona seekhta hai, kisi ek document ki quirks imitate karne ke bajay.
  • Keeping LLMs Honest: RLHF uncertainty admit karne ko reward karta hai aur confident fabrication ko discourage karta hai — halanki hallucination poori tarah khatam nahi hoti.

A Play Within a Play

Ek conversation ek natak hai jisme model ka ek role hai. Managing conversations ka matlab hai transcript (poori message list) sambhalna aur har call par use dobara bhejna — kyunki model calls ke beech inert hai.

  • The Chat Format Versus The Model's Internal Format: API jo chat format dikhata hai, wo model ka internal format nahi hai — neeche, transcript special role markers aur separators ke saath ek token stream me serialize hoti hai. Lekin building ke liye message list hi working abstraction hai.
  • A Chat by Any Other Name: dusre providers alag role names aur formats use karte hain — kitab ChatML ko example deti hai, jo kuch open chat models me roles ke liye use hone wala markup hai. Concepts transfer hote hain.
  • Persisting Application State: model bhool jata hai, isliye application ko conversation aur baaki state (user preferences, task progress) khud store karni hoti hai — database ya session store me — aur prompt ko usse rebuild karna hota hai.
  • User Experience: interface application ki zimmedari hai, model ki nahi — tokens ko aate hi user ko stream karna, thinking dikhana, interruptions aur lambe turns handle karna.
  • Prompt Engineering as Playwriting: chapter wapas playwriting par aata hai — system message aur conversation history milkar wahi script hain jo model perform kar raha hai.

Stop sequence ka use: ek turn ko cleanly end karne ke liye stop sequence di jati hai, taaki model wahi ruke jahan turn khatam hona chahiye.

Ch 4 — Designing LLM Applications

Ye chapter kitab ka central model deta hai — the loop. Har LLM application isi loop ke aas-paas banti hai.

The Anatomy of the Loop

  1. The User's Problem: user ki apne domain me ek problem hai.
  2. Converting the User's Problem to the Model Domain: application us problem ko model ke domain me convert karti hai — matlab ek prompt me, ek document jise model complete kare. Ise lekhak "Little Red Riding Hood principle" kehte hain: user ki problem ko ek document-completion problem ke roop me recast karo jisme model achha hai. Running example: user ki request ko ek "homework problem" me convert karna — ek worked setup, ek clear sawal aur ek format do, taaki jawab natural completion ho.
  3. Using the LLM to Complete the Prompt: model ek feedforward pass karta hai aur completion deta hai.
  4. Transforming Back to User Domain: application completion ko wapas user ke domain me transform karti hai — parse karna, format karna, action lena — aur user ko dikhati hai.
  5. Repeat: user respond karta hai aur loop repeat hota hai, history aage carry hoti hai.

Loop ki complexity kai dimensions me badh sakti hai — turns ki sankhya, tools ki sankhya, context ki matra, branching — aur designer ko decide karna hota hai ki inme se kitna application manage karega aur kitna user.

Zooming In to the Feedforward Pass

Pass ke andar stages hote hain, aur har stage ek lever deta hai:

  • Tool Usage: model ko tools call karne do (functions, search, calculators, databases) taaki wo facts le sake aur actions kar sake jo text prediction se nahi ho sakte.
  • Retrieval-Augmented Generation (RAG): model ko call karne se pehle relevant documents retrieve karo aur prompt me paste karo, taaki model memory se nahi, supplied evidence se jawab de.
  • Chain of Thought: model se step by step reason karne ko kaho (ek reasoning preamble) taaki wo intermediate tokens generate kare jo final answer ko behtar banate hain.
  • Counting Tokens: prompt ka budget karo.
  • Prompting: us document ko assemble karna jo feed kiya jata hai.

The Chat Is a Transcript Document: chat bhi ek transcript document hi hai — poori conversation ek document ki tarah treat hoti hai jise model aage badhata hai.

Evaluating LLM Application Quality

Yahan introduce kiya gaya hai aur Chapter 10 me depth me treat kiya gaya hai: application ko "achha" ka criteria chahiye, tabhi use improve kiya ja sakta hai — correctness, usefulness, safety, latency aur cost, real examples par measure kiye gaye.

Ch 5 — Prompt Content

Sabse common failure hai unclear sawal. Is chapter ka pehla rule: sawal ko clear karo, phir content bharo. Prompt ka content kahan se aata hai, use kaise select aur organise karte hain — ye sab yahan hai.

Clarifying Your Question

Instructions ke rules of thumb: task, format aur constraints ke baare me specific raho; sirf ye mat batao ki kya nahi chahiye, ye batao ki kya chahiye; model ko ek role aur ek situation do; aur instruction ko us data se alag rakho jis par use kaam karna hai.

Worked example — book recommendation: vague "recommend a book" par generic jawab milta hai. Lekin jab prompt me reader ki taste, kya pasand aaya, kitni length aur tone chahiye, aur exact output format likha ho — to useful, specific recommendation milti hai. Farak sirf clarity ka hai.

Sources of Content — Static aur Dynamic

Prompt ka content do tarah ka hota hai:

  • Static content: developer ne likha fixed text — instructions aur templates.
  • Dynamic content: har call par badalne wala text — user ka input, retrieved documents, tool results, ya time aur date.

Dynamic content ko chaar dimensions me describe kiya gaya hai: purpose (kyun hai), preparability (taiyaar karne me kitna kaam), latency (fetch karne me kitna time) aur urgency (kitna fresh hona chahiye).

Selecting and Organizing Context

Saara context equally useful nahi hota. Context ke sources: conversation history, retrieved documents, tool outputs aur user ki apni files. Context retrieval ka kaam hai sahi pieces dhoondhna; dynamic context dhoondhne ka matlab hai task ke paas (proximity), related documents me, aur pichhle turns me dekhna.

Snippetizing Documents

Lambe documents ko snippets (chunks) me todna hota hai jo prompt me fit hon: window size, step/stride size (window har baar kitna aage badhta hai), aur overlap taaki koi fact boundary par split na ho.

Summarization

Jab material bahut lamba ho, paste karne ke bajay summarise karo. General summaries overview deti hain; specific summaries ek particular sawal ke liye zaroori details bachati hain. Hierarchical summarization me pieces ko summarise karke phir summaries ko summarise kiya jata hai — isse "rumour problem" se bachte hain, jahan ek detail summary se summary retell hote hue distort ho jati hai.

Few-Shot Prompting

Model ko prompt me input→output pairs ke examples do, taaki wo pattern infer kare. Examples ki formatting matter karti hai: consistent formatting, clear separators, aur examples jo real distribution se match karein. Few-shot examples ke liye Amazon book-reviews dataset aur ek Kaggle dataset ka naam liya gaya hai.

Teen drawbacks — yaad rakhne layak

  1. Drawback 1 — context ke saath scale nahi karta: har example tokens kharch karta hai, aur kitne fit ho sakte hain iski limit hai.
  2. Drawback 2 — model examples ki taraf bias ho jata hai: anchoring — model examples ki style, values aur errors copy karta hai; uski probability distribution us taraf khinch jati hai jo usne abhi dekha hai.
  3. Drawback 3 — spurious patterns suggest kar sakta hai: model wo rule infer kar sakta hai jo intended nahi tha — jaise ordering effects: wo seekh sakta hai ki pehla jawab hamesha simple case hota hai aur baad wale errors hote hain ("straightforward first, errors later" pattern), ya "happy path first, then unhappy path" ordering.

Remedy: examples carefully chuno, unhe vary karo, aur inferred rule ko check karo.

Ch 6 — Assembling the Prompt

Prompt assemble karna ek design decision hai — aur kitab ke mutabik sabse important decision document ka type chunna hai. Prompt ko kaise assemble karte hain, ye chapter step by step batata hai.

Anatomy of the Ideal Prompt

Ideal prompt ke parts:

  • Introduction — ye document kya hai.
  • Preamble — context aur instructions.
  • Body of content — task aur uska data.
  • Postscript — final instruction jis par model ko action lena hai.

Iske alawa uska ek recognisable start aur end hona chahiye — clear markers taaki model jaane uski completion kahan se shuru aur kahan khatam honi hai. Do problems se bachna hai: "lost in the middle" (lambe prompt ke beech ka material start ya end se kam attend kiya jata hai) aur "Valley of Meh" (prompt unfocused ho to quality me dip). Lambe prompts ke liye "sandwich" structure recommended hai — instructions shuru me aur phir end me bhi, data beech me.

What Kind of Document? — teen worked types

1. The Advice Conversation

Ek helpful conversation ka transcript — freeform, multi-round, natural, persona ke saath. Open-ended help ke liye achha, lekin structure me kamzor.

2. The Analytic Report

Sections wala structured report (scope, findings, conclusions, recommendations), table of contents aur Markdown headings ke saath. Achha jab jawab organised aur checkable hona chahiye.

3. The Structured Document

Fields aur slots wala document — jaise JSON, YAML ya XML — aksar "Artifacts" style system prompt ke saath. Achha jab output machine-readable hona chahiye.

Har type ke liye chapter format, editorial hints aur trade-offs describe karta hai.

Formatting Snippets

Snippets self-contained, labelled aur clear delimiters se separated hone chahiye. Composite strings ek pitfall hain — alag sources se strings jodne par aisa prompt ban sakta hai jiska matlab uske parts se alag ho. "More on inertness" wapas is point par aata hai: model sirf final assembled text dekhta hai.

Elastic Snippets

Ek technique jisme variable amount of material fixed token budget me fit hoti hai — snippets expand ya shrink kar sakte hain (jaise ellipsis "…" omitted material ke liye, ya full document ki jagah ek summary jab space tight ho). Prompt priority order se assemble hota hai taaki budget cut hone par sabse important snippets bach jayein.

Relationships Among Prompt Elements

Assembly ko teen relations govern karte hain:

  • Importance — kaunse elements sabse zyada matter karte hain aur space kam ho to kaunse bachne chahiye.
  • Position — element kahan baitha hai (start aur end sabse strong hote hain).
  • Dependency — kaunse elements kiske upar depend karte hain, taaki ek ko hatane se dusra na toote; incompatible elements combine nahi karne chahiye.

Putting It All Together — knapsack problem

Chapter poora prompt assemble karne ka walkthrough deta hai, use ek knapsack problem ke roop me treat karte hue: token budget me fit hone wala highest-value snippets ka set chuno. Greedy approaches practical approximations hain — additive greedy (best remaining snippet add karte jao jab tak full na ho) aur subtractive greedy (sab kuch se shuru karo aur least valuable hatate jao). Linear programming ko exact formulation ke roop me naam diya gaya hai. Assembled prompt phir wahi document hai jise model complete karta hai.

Ch 7 — Taming the Model

Prompts ki anatomy hoti hai, waise hi completions ki bhi anatomy hoti hai. Ye chapter batata hai ki model ke output ko kaise tame karein — aur uske andar jhankne ke liye logprobs kaise use karein.

Anatomy of the Ideal Completion

Achhi completion ke parts:

  • Preamble: aksar ek reasoning preamble — jawab se pehle step-by-step thinking. Chhota "fluff" preamble tokens waste karta hai, jabki reasoning preamble answers ko behtar banata hai. Structural boilerplate preamble useful hota hai jab output format fixed hona chahiye.
  • Recognizable Start and End: taaki application bata sake jawab kahan shuru aur kahan khatam hota hai.
  • Postscript: ek closing jise application strip kar sake ya use kar sake, jaise ek summary line.

Critical Points in the Prompt

Ye wo tokens hain jahan model ka choice outcome par sabse zyada asar dalta hai. Chapter sikhata hai ki unhe logprobs inspect karke aur prompt vary karke dhoondho, aur unhe unit tests ki tarah treat karo: wahan chhote changes ka bada effect hota hai.

How Good Is the Completion?

Test ye hai: kya completion sawal ka jawab deti hai, sahi format me, sahi content ke saath, aur confidence ke saath (uski probabilities se measure kiya gaya)?

Beyond the Text: Logprobs

API har generated token ke liye us token ki log probability (logprob) aur top alternatives ki logprobs return kar sakti hai. exp() se convert karke ordinary probability milti hai.

LLMs for Classification: model se "yes" ya "no" likhwane ke bajay, candidate tokens ki logprobs padho aur zyada probable ko chuno — logprob difference ek calibrated confidence measure hai. Gold standard known-correct answers ka set hai jisse classifier ko check karte hain: model ka chuna label gold label se compare karo aur accuracy measure karo, multi-label classification ke liye bhi. Logprobs se uncertainty detect kar sakte hain, critical points dhoondh sakte hain, aur voting implement kar sakte hain (n completions sample karo aur majority answer lo).

Ch 8 — Conversational Agency

Conversational agency ka matlab hai ek conversational system ki ability user ki taraf se act karne ki — sirf jawab dena nahi, balki reasoning aur tools use karke ek goal pursue karna, jabki user control me rahe.

Building a Conversational Agent

Agent chat model ke aas-paas ek loop hai — transcript bhejo, reply ya tool call lo, tool execute karo, result append karo, repeat karo. Worked example thermostat agent hai: user temperature badalne ko kehta hai, model function call karta hai use set karne ke liye, result wapas aata hai, aur model confirm karta hai. State application ko persist karni hoti hai (model kuch yaad nahi rakhta), aur conversation ko manage karna hota hai taaki transcript context window ke andar rahe.

Reasoning — Chain of Thought aur Reasoning Depth

Chain-of-thought main lever hai — model se act karne se pehle step by step sochne ko kaho, jo "reasoning depth" badhata hai. Trade-off: zyada reasoning tokens reliability badhate hain lekin time aur paise kharch karte hain. Techniques: reasoning ki "TL;DR" summaries, aur pause tokens (extra tokens jo model ko compute karne ke liye time dete hain). Benchmark evidence: chain-of-thought maths aur multi-step reasoning tasks par results improve karta hai, PaLM 540B model ko early demonstration ke roop me naam diya gaya hai.

Tool Usage

Tools wo functions hain jinhe model call kar sakta hai. Chapter batata hai ki modern models tool use ke liye kaise train kiye jate hain (function-calling training), tools kaise define karte hain, aur underlying mechanism kya hai — model ek structured function call (JSON) output karta hai, application use execute karti hai, aur result tool message ke roop me wapas feed hota hai. Guidelines for Tool Definitions

  • Har tool ko ek clear naam aur precise description do — wo kya karta hai aur kab use karna hai.
  • Arguments ko types, required/optional flags aur descriptions ke saath define karo.

Naming Tools and Arguments

Clear, descriptive, camelCase names use karo; lowercase-only ambiguous names avoid karo; names ko informative banao — model naam ko prompt ka part samajh kar padhta hai.

Dealing with Arguments

Model arguments hallucinate kar sakta hai (koi value invent kar de), galat type ki value de, ya placeholder use kar de. Application ko arguments validate karne chahiye, defaults dene chahiye, aur clear error return karni chahiye taaki model khud ko correct kar sake.

Dealing with Tool Errors

Error ko tool result ke roop me wapas do aur model ko retry karne do — poora turn fail karne ke bajay.

Executing "Dangerous" Tools

Jo tools duniya ko badalte hain (message bhejna, card charge karna, data delete karna) unhe confirmation step chahiye — application ko request intercept karni chahiye, user ko dikhana chahiye kya hone wala hai, aur sirf approval ke saath execute karna chahiye. Ch 10 — Evaluating LLM Applications

Evaluation task level se shuru hoti hai — poori application test karne se pehle har task ko alag se test karo — aur har task ke liye decide karo ki "achha" ka matlab kya hai: functional correctness, usefulness, safety, latency aur cost.

What Are We Even Testing?

Chapter teen test types alag karta hai: harness tests (fixed inputs par application chalao aur expected outputs se compare karo), regression tests (change ke baad purane tests dobara chalao taaki breakage pakdi jaye) aur prompts aur tasks ke liye unit tests. Offline Evaluation

Shipping se pehle ki evaluation, fixed examples par. Example suites examples ka collection hain, har ek me input aur gold-standard (known-correct) output hota hai; ye test suites se alag hain kyunki inhe exploration aur quality judge karne ke liye use kiya jata hai, sirf pass/fail ke liye nahi.

Finding Samples

Examples real usage se, edge cases ki directed exploration se, aur production logs se ikatthe karo. Sampling bias se bacho — jo examples aasani se milte hain, wo representative nahi hote.

Evaluating Solutions

  • Model ka output gold standard se compare karo (exact match, ya graded match).
  • Functional testing: kya output kaam karta hai — code ke liye, kya wo run hota hai; tool call ke liye, kya sahi tool sahi syntax se call hua.

  • SOMA assessment: kitab ka apna rubric — response ko simple pass/fail ke bajay ek scale par grade karta hai (SOMA mastery levels), taaki partial quality dikhai de.

Interview FAQs — Prompt Engineering for LLMs

36 sawal-jawab jo aaj ke interviews me is kitab ke topics par poochhe jate hain. Har jawab kitab ke content par based hai.

Q1Prompt engineering ka matlab kya hai, aur ye fine-tuning se kaise alag hai?

Prompt engineering ka matlab hai model ke behaviour ko prompt aur surrounding application se shape karna, model ke weights badle bina. Fine-tuning me model ke weights badalte hain — training hoti hai. Prompt engineering me tum document likhte ho, model ko stage karte ho, aur usi model se behtar output nikalte ho. Kitab ka central metaphor playwriting hai: tum natak likhte ho, model usme apna role nibhata hai.

Q2Playwriting metaphor ka matlab kya hai? Model ko order kyun nahi dena chahiye?

Playwriting metaphor ka matlab hai ki model ko database ki tarah order mat do — 'ye karo' kehne ke bajay ek scene, role, situation aur format set karo, taaki tumne jo document stage kiya hai uska natural continuation wahi jawab ho jo tum chahte ho. Model documents complete karta hai, instructions execute nahi karta. Achha prompt wo hai jisme answer document ka natural aage ka hissa lage.

Q3LLM ka basic kaam kya hai? Ye text kaise generate karta hai?

LLM ka basic kaam hai tokens ki sequence dekh kar agle token ki probabilities assign karna aur unme se sample karna. Ye auto-regressive hota hai — ek token generate karta hai, use wapas input me daalta hai, aur agla token generate karta hai. Lamba jawab step by step banta hai, aur har step sirf wo dekh sakta hai jo pehle aa chuka hai. Isi liye ye documents continue karne me achha hai.

Q4Token kya hota hai, aur prompt budgeting tokens me kyun karni chahiye?

Token text ka wo piece hai jisme model text ko split karta hai — deterministic tokenizer se. Common words aam taur par ek token hote hain, rare words tukdo me split hote hain. Model ka context window tokens me measure hota hai, words ya characters me nahi, isliye prompt budgeting tokens me karni hoti hai. Tiktoken library ya Hugging Face tokenizer se count kar sakte ho — jaise 'I am' 2 tokens, 'The meaning of life is 42.' 7 tokens.

Q5Inertness kya hai, aur application design par iska kya asar hota hai?

Inertness kitab ka term hai: model calls ke beech kuch nahi karta — uski koi memory, ongoing thought ya state nahi hoti. Jo kuch use chahiye, wo current call ke prompt me hona chahiye. Iska asar ye hai ki application ko conversation history aur baaki state khud store karni hoti hai aur har call par prompt me wapas dalni hoti hai. Prompt ek self-contained document hai.

Q6Temperature kya control karta hai? Factual kaam ke liye kaunsi temperature sahi hai?

Temperature control karta hai ki agle token ki probability distribution se kitni sharply sample kiya jaye. Low temperature (0 ke paas) sabse likely token ko almost certain bana deta hai — output deterministic aur conservative hota hai. High temperature distribution ko flat karta hai — rare tokens zyada likely ho jate hain, output varied aur error-prone hota hai. Factual, repeatable kaam ke liye low temperature use karo; variety chahiye tabhi high temperature, aur high-temperature model se reproducibility ki ummeed mat rakho.

Q7Model letters ginne ya spelling me kharab kyun hota hai?

Kyunki model token identities dekhta hai, token ke andar ke individual letters nahi — jab tak prompt unhe spell out na kare. Ye Chapter 2 ki Difference 2 hai: LLMs slow down karke letters examine nahi kar sakte. Isi liye wo letters ginne, spelling, ya Scattergories jaise word games me kharab ho sakta hai jahan pehla letter matter karta hai — wo information use seedhe taur par visible hi nahi hoti.

Q8RLHF kya hai? Iske teen steps kya hain?

RLHF matlab reinforcement learning from human feedback. Teen steps: (1) Supervised fine-tuning (SFT) — base model ko human-written desired responses par aur train karo; (2) Reward model — alag model train karo jo responses ko score kare, insaan ki rankings se human preference function seekh kar; (3) RLHF model — PPO se chat model ko adjust karo taaki uske responses reward model ke hisab se high score karein, lekin supervised model se zyada door na bhatkein. Result helpful, honest aur harmless (HHH) alignment hota hai.

Q9Alignment tax kya hai?

Alignment tax ye observation hai ki RLHF kuch tasks par raw capability ya knowledge kam kar sakta hai — alignment kuch breadth ki keemat par safe, helpful behaviour deta hai. Lekin lekhak zor dete hain ki RLHF 'packs a lot of bang for the buck' — thoda sa human feedback bhi base model ko useful product me badal deta hai. Alignment se model consistent persona bhi seekhta hai aur uncertainty admit karna bhi seekhta hai.

Q10Chat roles kaunse hote hain aur har ek ka kya kaam hai?

Chat roles hain: system — assistant ka behaviour set karne wali instructions, sabse pehle; developer — application developer ki instructions (naye APIs me); user — end user ke turns; assistant — model ke apne pichhle replies, history ke roop me wapas feed kiye jate hain; tool — tool se aaye results, taaki model dekh sake tool ko kya mila. Chat call in messages ki list hoti hai.

Q11Chat model aur completion model me kya farak hai?

Completion model document continue karta hai; chat model conversation me turn lene ke liye train hota hai. Instruct models beech ka step the — single turn me instructions follow karne ke liye fine-tune kiye gaye. Chat models dialogue ke liye unse aage nikal gaye, lekin kitab ka argument hai ki document ki tarah sochna chat ke andar bhi valuable rehta hai, aur completion model abhi bhi useful ho sakta hai jab task document finish karne ke roop me frame karna behtar ho.

Q12The Loop kya hai? Uske paanch steps batao.

The Loop kitab ka central model hai: (1) user ki apne domain me problem hoti hai; (2) application use model ke domain me convert karti hai — ek prompt, ek document; (3) model feedforward pass karta hai aur completion deta hai; (4) application completion ko wapas user ke domain me transform karti hai — parse, format, action; (5) user respond karta hai aur loop repeat hota hai, history aage carry hoti hai. 'Little Red Riding Hood principle' step 2 ka naam hai: problem ko document-completion problem me recast karo.

Q13Little Red Riding Hood principle kya hai?

Ye lekhako ka naam hai loop ke step 2 ke liye: user ki problem ko ek document-completion problem ke roop me recast karo jisme model achha hai. Running example me user ki request ko ek 'homework problem' me convert kiya jata hai — worked setup, clear sawal aur format do, taaki jawab natural completion ho. Yehi conversion poori application design ka core hai.

Q14RAG kya hai aur ye hallucination kam kaise karta hai?

RAG matlab retrieval-augmented generation: model ko call karne se pehle relevant documents retrieve karo aur prompt me paste karo, taaki model memory se nahi, supplied evidence se jawab de. Isse hallucination kam hoti hai kyunki model ko facts prompt me mil jate hain — wo outdated ya missing knowledge par guess nahi karta. Ye feedforward pass ka ek lever hai, tool usage aur chain-of-thought ke saath.

Q15Chain-of-thought kyun kaam karta hai?

Chain-of-thought kaam karta hai kyunki model har token ke liye ek single forward pass karta hai aur sochne ke liye ruk nahi sakta — sirf tokens generate karke soch sakta hai. Step-by-step reasoning likhne ko kehne se model ko intermediate tokens milte hain jinse final answer behtar hota hai. Ye Chapter 2 ki insight hai: human pause karke soch sakta hai, model sirf tokens generate karke.

Q16Static aur dynamic prompt content me kya farak hai?

Static content developer ka likha fixed text hai — instructions aur templates. Dynamic content har call par badalta hai — user ka input, retrieved documents, tool results, ya time aur date. Dynamic content ko chaar dimensions me describe karte hain: purpose (kyun hai), preparability (taiyaar karne me kitna kaam), latency (fetch karne me kitna time) aur urgency (kitna fresh hona chahiye). Jaise weather report ki urgency high hoti hai, email ki low se medium.

Q17Snippetizing kya hai? Window, stride aur overlap kyun matter karte hain?

Snippetizing ka matlab hai lambe documents ko chhote snippets (chunks) me todna jo prompt me fit hon. Window size batata hai snippet kitna bada hai, step/stride size batata hai window har baar kitna aage badhta hai, aur overlap isliye chahiye taaki koi fact boundary par split na ho. Bina overlap ke ek important fact do snippets ke beech me kat sakta hai aur model use miss kar sakta hai.

Q18Hierarchical summarization kya hai aur 'rumour problem' kya hai?

Hierarchical summarization me pieces ko summarise karke phir summaries ko summarise kiya jata hai, jab material prompt me fit na ho. 'Rumour problem' wo hai jahan ek detail summary se summary retell hote hue distort ho jati hai — jaise khel me afwah badalti hai. Hierarchical approach me har level par summary banti hai, lekin distortion ka risk rehta hai, isliye specific summaries me zaroori details bachani hoti hain.

Q19Few-shot prompting ke teen drawbacks kya hain?

Pehla: ye context ke saath scale nahi karta — har example tokens kharch karta hai, aur kitne fit ho sakte hain iski limit hai. Dusra: ye model ko examples ki taraf bias karta hai (anchoring) — model examples ki style, values aur errors copy karta hai. Teesra: ye spurious patterns suggest kar sakta hai — model wo rule infer kar sakta hai jo intended nahi tha, jaise ordering effects ('pehla hamesha simple, baad wale errors'). Remedy: examples carefully chuno, vary karo, aur inferred rule check karo.

Q20Ideal prompt ki anatomy kya hai?

Ideal prompt ke chaar parts hote hain: introduction (ye document kya hai), preamble (context aur instructions), body of content (task aur uska data), aur postscript (final instruction jis par model ko action lena hai). Iske alawa uska recognisable start aur end hona chahiye. Do problems se bachna hai: 'lost in the middle' (lambe prompt ke beech ka material kam attend hota hai) aur 'Valley of Meh' (unfocused prompt par quality dip). Lambe prompts ke liye sandwich structure recommended hai.

Q21Sandwich structure kya hai aur ye kyun kaam karta hai?

Sandwich structure me instructions shuru me aur phir end me bhi di jati hain, data beech me rehta hai. Ye isliye kaam karta hai kyunki model lambe prompt ke start aur end par zyada attend karta hai, beech par kam ('lost in the middle'). Instructions dono strong positions par rakhne se wo miss nahi hoti, aur data beech me safe rehta hai.

Q22'Lost in the middle' aur 'Valley of Meh' kya hain?

'Lost in the middle' ye observation hai ki lambe prompt ke beech ka material start ya end se kam attend kiya jata hai — beech ki information miss ho sakti hai. 'Valley of Meh' quality me dip hai jab prompt unfocused hota hai. Dono se bachne ke liye prompt ko focused rakho, important cheezein start ya end me rakho, aur sandwich structure use karo.

Q23Teen document types kaunse hain aur kaunsa kab use karna chahiye?

Teen types: (1) Advice conversation — helpful conversation ka transcript, freeform aur natural; open-ended help ke liye achha, structure me kamzor. (2) Analytic report — sections wala structured report (scope, findings, conclusions, recommendations); jab jawab organised aur checkable hona chahiye. (3) Structured document — JSON/YAML/XML jaise fields aur slots; jab output machine-readable hona chahiye. Kitab ke mutabik document type chunna sabse important prompt decision hai.

Q24Elastic snippets kya hain?

Elastic snippets ek technique hai jisme variable amount of material fixed token budget me fit hoti hai — snippets expand ya shrink kar sakte hain, jaise ellipsis '…' omitted material ke liye, ya full document ki jagah ek summary jab space tight ho. Prompt priority order se assemble hota hai taaki budget cut hone par sabse important snippets bach jayein.

Q25Prompt assembly ko knapsack problem kyun kaha gaya hai?

Kyunki prompt assemble karna matlab hai token budget me fit hone wala highest-value snippets ka set chunna — bilkul knapsack problem ki tarah. Greedy approaches practical approximations hain: additive greedy (best remaining snippet add karte jao jab tak full na ho) aur subtractive greedy (sab kuch se shuru karo aur least valuable hatate jao). Linear programming ko exact formulation ke roop me naam diya gaya hai.

Q26Critical points in the prompt kya hain aur unhe kaise dhoondhte hain?

Critical points wo tokens hain jahan model ka choice outcome par sabse zyada asar dalta hai. Unhe logprobs inspect karke aur prompt vary karke dhoondhte hain, aur unhe unit tests ki tarah treat karte hain — wahan chhote changes ka bada effect hota hai. Yehi points hain jahan prompt engineering ka sabse zyada leverage hota hai.

Q27Logprobs se classification kaise karte hain? Ye raw text se behtar kyun hai?

API har generated token ki logprob aur top alternatives return kar sakti hai. Model se 'yes' ya 'no' likhwane ke bajay, candidate tokens ki logprobs padho aur zyada probable ko chuno — exp(logprob) se ordinary probability milti hai. Logprob difference ek calibrated confidence measure hai. Raw text par bharosa karne se behtar hai kyunki tumhe model ki uncertainty dikhti hai: bada gap matlab jawab determined, chhota gap matlab genuine choice.

Q28Model chunne ka checklist kya hai?

Checklist: intelligence (task par capability — benchmarks aur try karke judge karo, brand se nahi), size aur speed (bada behtar lekin slow aur mehenga), cost (per-token pricing), latency, ease of use, functionality (tools, structured output, long context, fine-tuning support), providers (OpenAI, Google, Anthropic, Cohere, Mistral, LLaMA, Hugging Face open-source), aur special requirements (data privacy, language, modality). Practical advice: choice flexible rakho, LiteLLM jaisi thin abstraction use karo.

Q29Conversational agency kya hai?

Conversational agency ek conversational system ki ability hai user ki taraf se act karne ki — sirf jawab dena nahi, balki reasoning aur tools use karke ek goal pursue karna, jabki user control me rahe. Agent chat model ke aas-paas ek loop hai: transcript bhejo, reply ya tool call lo, tool execute karo, result append karo, repeat karo. Worked example thermostat agent hai.

Q30Tool definitions ke liye guidelines kya hain?

Har tool ko clear naam aur precise description do — wo kya karta hai aur kab use karna hai. Arguments ko types, required/optional flags aur descriptions ke saath define karo. Names clear, descriptive aur camelCase hone chahiye — model naam ko prompt ka part samajh kar padhta hai. Arguments validate karo, defaults do, aur error ko tool result ke roop me wapas do taaki model retry kar sake.

Q31Dangerous tools ko kaise handle karna chahiye?

Jo tools duniya ko badalte hain — message bhejna, card charge karna, data delete karna — unhe confirmation step chahiye. Application ko request intercept karni chahiye, user ko dikhana chahiye kya hone wala hai, aur sirf approval ke saath execute karna chahiye. Authorisation aur private information application ko handle karni chahiye, model ki discretion par chhodni nahi chahiye.

Q32ReAct kya hai aur ye workflows me kahan fit hota hai?

ReAct iterative reasoning aur action hai — model sochta hai, tool se act karta hai, result observe karta hai, aur repeat karta hai. Ye HotpotQA dataset aur ALFWorld par evaluate kiya gaya. ReAct se aage Reflexion hai (agent apni failures par reflect karta hai aur lesson store karta hai), plan-and-solve prompting, aur branch-solve-merge (problem split karo, parts solve karo, answers combine karo).

Q33Workflow aur conversational agent me se kab kya chunna chahiye?

Conversational agent open-ended, user-driven kaam ke liye achha hai; workflow behtar hai jab task repeatable ho, uske steps pata hon, aur wo reliable aur efficient hona chahiye. Trade-off generality versus strength hai: general agent kai cheezein kamzor tareeke se karta hai, specialised workflow ek cheez strongly karta hai. Advice: sabse narrow workflow se shuru karo jo problem solve kare, generality tabhi add karo jab zaroorat ho.

Q34SOMA assessment kya hai?

SOMA assessment kitab ka apna rubric hai: response ko simple pass/fail ke bajay ek scale par grade karta hai (SOMA mastery levels), taaki partial quality dikhai de. Ye offline evaluation ka part hai — gold-standard comparison aur functional testing ke saath. A/B testing bhi offline evaluation ke under aata hai: do versions ko wahi examples par chalao aur compare karo.

Q35Offline aur online evaluation me kya farak hai?

Offline evaluation shipping se pehle hoti hai, fixed example suites par — harness tests, regression tests, functional testing, LLM assessment, SOMA aur A/B testing. Online evaluation live traffic par hoti hai — metrics hain functional correctness, user acceptance (acceptance rate, thumbs-up/down), achieved impact, direct feedback aur incidental metrics (rephrase, retry, abandon). Offline fast iteration ke liye, online ground truth ke liye — dono ko balance me rakhna chahiye.

Q36Multimodality prompt engineering ko kaise badalti hai?

Multimodality ka matlab hai models jo text se zyada lete aur dete hain — images, audio, video. Image processing CNNs aur embedding models use karti hai taaki image ko representation me badla ja sake jise transformer use kar sake. Prompt me images bhi ho sakti hain text ke saath, aur user model ko picture dikha sakta hai ya bol sakta hai. Lekin wahi principles apply hote hain: model abhi bhi document complete karta hai, clear scene aur role chahiye, aur evaluation chahiye.
