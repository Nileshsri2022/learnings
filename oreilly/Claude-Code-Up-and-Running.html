Foreword

F.1 Snippet generation vs agentic development

Yeh kitaab ek ahem farq se shuru hoti hai: ek chatbot jo ek function likh de, woh agentic development nahi hai. Asli agent project ko padhta hai, kai steps ka plan banata hai, kai files badalta hai, tests chalata hai aur galti par dobara koshish karta hai.

Vibe coding — app ko shabdon me batana aur jo bhi ban jaye use maan lena — prototype ke liye aur un logon ke liye bahut kaam ki hai jo code nahi likhte. Lekin professional kaam ke liye yeh kaafi nahi, kyunki code ko maintain, secure, test, review aur team ke saath safely badalna padta hai.

F.2 Kitaab ki asli value — professional layer

Kitaab ki value us professional layer me hai: permissions aur trust boundaries, skills aur hooks, subagents aur agent teams, MCP integrations, aur review, testing, debugging aur pull-request wali discipline.

Poori kitaab me paanch sawaal saath chalte hain: kya delegate karna hai, kitni autonomy deni hai, agent ko kya context chahiye, uska kaam kaise verify karna hai, aur jab kuch galat ho to kaise recover karna hai.

Yeh kitaab sirf enthusiasts ke liye nahi, kaam karne wale developers ke liye likhi gayi hai.

Preface — lekhak ki framing

P.1 Kitaab ka maksad

Yeh kitaab feature catalogue nahi hai aur documentation ka dobara print bhi nahi. Yeh agentic development ki practice layer hai — agent ke saath kaise kaam karein jab agent implementation chalata hai aur insaan direction, verification aur judgment apne paas rakhta hai.

Lekhak ne saaf likha hai ki woh independent hai: kisi bhi vendor — chahe woh koi bhi badi company ho — se uska employment ya financial interest nahi hai. Isliye kitaab kisi ek tool ki tareef nahi, kaam karne ka tareeqa sikhati hai.

P.2 Audience — kiske liye hai

Audience woh developers hain jo code, terminal, tests, version control aur project structure se comfortable hain. Senior developers, tech leads aur architects ke liye bhi hai, jinhe team ki practice tay karni hoti hai.

Examples zyada tar JavaScript aur Python me hain, aur baad me bade Java aur React examples bhi aate hain. Isliye ek language se bandhna zaroori nahi — principle sab par lagta hai.

P.3 Teen scales — doghouse, cabin, skyscraper

Poori kitaab ko teen scales organise karte hain. Doghouse: chhota, casual, personal, temporary — inspection ki zyada zaroorat nahi. Cabin: modest lekin dependable — iske boundaries, tests, memory aur trust controls hain, aur is par baad me wapas aaya ja sakta hai. Skyscraper: enterprise kaam — coordination utna hi zaroori hai jitna code: reusable practices, CI/CD, security review, documentation aur -ilities (observability, maintainability, scalability).

Cabin aur skyscraper ke beech jaan-boojh kar koi intermediate 'office building' scale nahi hai, kyunki dividing line size nahi, coordination hai. Ek chhota sa kaam bhi skyscraper hai agar use shared coordination chahiye.

P.4 Chapter map — poori kitaab ka naksha

Chapter 1 agentic shift batata hai; Chapter 2 install aur authenticate; Chapter 3 prompting ko work request banana; Chapter 4 doghouse ko cabin me badalna; Chapter 5 permissions aur safety; Chapter 6 skills aur hooks; Chapter 7 MCP; Chapter 8 subagents, teams aur plugins; Chapter 9 prompt se pull request tak ka rasta; Chapter 10 review, testing, debugging aur recovery; Chapter 11 doosri surfaces, models, cost aur always-on agents.

P.5 Examples kaise use karein — pull-mode learning

Examples ko sirf padhna nahi — prompts ko type karke khud chalana hai, captured transcripts ko dekhna kaafi nahi. Results har run me badalte hain (notes me 'in my run' ka matlab hai captured outcome), isliye alag jawab milna failure nahi, expected hai. Companion repository har stage ki state preserve karta hai.

Pull-mode learning: zaroorat ke waqt agent se poochho — yeh kya hai, aise kyun, alternatives kya hain — aur maan lo ki yeh just-in-time learning adhoori hoti hai; gaps ko baad me jaan-boojh kar bharo.

Conventions: naye terms, URLs aur file names italics me; code constant-width type me; literally type karne wala text bold me; replaceable values italic constant-width me. Kitaab 2026 me likhi gayi jab tools tezi se badal rahe the; yeh Early Release hai aur reader update hone par kitaab bhi update hogi. Ek footnote batata hai ki Gemini CLI pehle ek doosre naam se jaana jata tha, aur Antigravity CLI likhne ke waqt ka current naam hai.

01Chapter 1

1. The Rise of Agentic Development

1.1 A Quick Vibe-Coding Exercise

Shuruaat ek mazedaar worked example se hoti hai — ek self-signed-certificate service. Pehle idea ek gag 'signing' certificate ka tha, jo badal kar Certificate of Ownership ban gaya: scanned signature aur ek QR code jo ek endpoint ke against verify hota hai.

Cryptography hi mushkil hissa tha: certificate generation ke liye ek crypto library aur PDF par stamp lagane ke liye ek PDF library, saath me X.509 details jo haath se karna tedious hai. Agent ki madad se kuch hi ghanton me ek working service ban gayi jo likhne ke waqt bhi chal rahi thi. Figure 1-1 us certificate-verification page ko dikhata hai — verification result aur certificate details ke saath.

Sub ko check karne layak banana aur haath se likhne layak banana, alag baatein hain — lekin is exercise se ek cheez saaf hoti hai: agent se certificate wala kaam ghanton me ho gaya, jabki details haath se likhna tedious hota.

1.2 Learning the Costs of Vibe Coding

Pehla version: na tests, na design choices ki explanation — aur lekhak aage badh gaya. Doghouse ke liye yeh acceptable tha, aur yahi vibe coding par justified scepticism ki jad hai.

Phir project evolve hua: controller / service / model structure, ek asli test suite jisme security-critical hisson ke liye property-based tests bhi the, aur integration tests wala ek analytics sub-package. Yeh crossing — throwaway se dependable tak — hi kitaab ka central move hai.

Maintenance cost ka argument: jo code likha gaya, use maintain, samajhna, test, debug, secure aur badalna bhi padega. Chapter me do estimates diye gaye hain — ek ke mutabik lifecycle cost ka lagbhag 60–70% maintenance hai, doosre ke mutabik lagbhag 40–80%. Aur ek aur argument: AI code badalne ki cost kam karta hai, to woh bachat code ko chhota aur clean rakhne me lagani chahiye, aur code pile karne me nahi.

1.3 Doghouses, Cabins, and Skyscrapers

Teen scales phir poori detail me: doghouse (chhota, temporary), cabin (dependable, wapas aane layak), skyscraper (coordination wala enterprise kaam). Figure 1-2 doghouse se cabin se skyscraper tak ki progression dikhata hai.

Cabin aur skyscraper ke beech ki line coordination hai, size nahi: ek chhota sa skyscraper-scale task bhi skyscraper hi hai agar use shared coordination chahiye. Certificate service ko ek fully built-out cabin ke roop me present kiya gaya hai — ek insaan plus ek agent, production tak le jaya gaya — aur Chapter 8 me is par wapas aaya jata hai.

Scales ko mix karna hi failure mode hai: cabin me doghouse ki aadatein, ya skyscraper me cabin ki aadatein — to kaam untested, unreviewed aur uncoordinated ban jata hai.

1.4 How Claude Code Works

Vocabulary — chaar shabd jo poori kitaab me aate hain. Model: reasoning engine jo servers par chalta hai (kitaab Fable, Opus aur Sonnet tiers ka naam leti hai). Harness: model ke aas-paas ka local program — agent loop, terminal interface, project context files, session handling, CLAUDE.md, tool calls, permission gates, MCP, hooks aur skills, aur workspace awareness. Coding agent: woh harness jo tools use karta hai; tool use hi use define karta hai. Surface: woh jagah jahan wahi model milta hai — terminal, desktop Code tab, web sandbox, IDE, GitHub, phone. Chat product aur Claude Code wahi model hain, alag harnesses se pahunche gaye.

Pehli wave vs agentic: 'spicy autocomplete' sirf lines complete karta hai, kuch decide nahi karta. Agent multi-step kaam plan karta hai, project padhta hai, decide karta hai kaunsi files badalni hain aur kis order me, pehle test karta hai, build chalata hai, failure padhta hai aur retry karta hai. Chatbot answers ke liye free hai; agent is liye hai ki kya banana hai, kaise banana hai aur kaise test karna hai — yeh decide kare, phir evaluation criteria ke against banaye aur refine kare.

Request loop: context load karo, plan banao, tools call karo (read, run, search, MCP), permissions check karo, output do, phir react aur evaluate karo aur repeat karo. Insaan ka kaam hai outcomes describe karna, actions inspect karna aur deliberately react karna — keystrokes dekhna nahi.

1.5 What This Book Covers

Jab change sasta ho jaye to kya badalta hai: refactoring se kam resistance (chapter ka example — teen hafte ka estimate ek restructuring ke liye teen minute me collapse ho gaya), dobara try karne ki willingness, second-pass review jo pehle pass ki issues pakadta hai, aur agent ek embedded tutor ke roop me pull-mode learning ke liye. Polyglot fluency practical ho jati hai (.py, .ts, .kt ek hi session me), isliye design principles, naming, patterns aur failure modes zyada matter karte hain, aur senior judgment zyada matter karta hai — design intuition ke bina ek junior plausible code bana sakta hai jisme subtle failures hon, isliye kitaab baar-baar kehti hai ki tool se poochho ki code clean aur maintainable hai ya nahi.

Agent teams ka preview (Chapter 8 me detail me): ek prompt se teen teammates wali team — ek tests aur coverage ke liye, ek security ke liye, ek documentation accuracy aur setup ke liye — parallel kaam karke ek report synthesise karti hai: kya badla, kya mila, aur insaan ko kya follow-up karna chahiye. Findings me ek silently skipped integration test (ek database concern kabhi exercise hi nahi hua), authentication aur file-path issues, aur README me stale versions, missing endpoints aur missing environment variables the. Sabse striking baat lekhak ke liye yeh thi ki kaam ko haath se decompose nahi karna pada. Yeh feature experimental hai, CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 se enable hota hai, aur badal sakta hai.

1.6 Summary

Chapter 1 ka saar: snippet generation aur agentic development alag hain; doghouse, cabin aur skyscraper scales ko mix mat karo; model, harness, coding agent aur surface ke shabd yaad rakho; aur request loop me insaan outcomes ka malik hai, keystrokes ka nahi.

Version command se verify karo, update command se update karo, global npm uninstall se uninstall karo. Agar install fail ho to chapter kehta hai pehle Node version check karo.

3. Talking to Claude Code

3.1 Prompts as Work Requests

Prompt ek sawaal nahi, kaam ki request hai — chaar elements ke saath: (1) kya banana hai, (2) kaise pata chalega ho gaya (acceptance criteria), (3) kya nahi karna (constraints), aur (4) kaise verify karna hai (tests ya checks).

Chapter ek vague request ('authentication add karo') ko ek specified request se contrast karta hai (login add karo, named files, named test, aur named verification ke saath). Vague prompt se vague code milta hai; specified prompt se check karne layak kaam milta hai.

LAB 1Prompt-as-work-request builder

Chapter 3 ke chaar elements bharo — lab ek tayyar work request banayega.

Yahan work request aayega.

3.2 The Clarification Pass

Banane se pehle agent se kaho ki woh sawaal poochhe — woh ambiguities surface karega (kaunsa framework, kaunsa storage, kaunse edge cases) aur insaan sirf un sawaalon ka jawab de jo matter karte hain.

Chapter ka example: ek clarification pass se lagbhag 45 minute me 7,000-word report bani, agent ne 7 sawaal poochhe, insaan ne 3 ke jawab diye, aur report ke claims ka 93% sources ke against verified hua. Clarification me lagaya waqt galat build se bachata hai.

3.3 Explain Like I'm Skeptical

Aisi explanation maango jo maan kar chale ki reader challenge karega — kya galat ho sakta hai, alternatives kya hain, har choice ke peeche kya evidence hai. Example: ek 1,700-word explanation skeptical version maangne par 1,000 words ki reh gayi, aur ek 100-line file 30 lines ki ho gayi — challenge karne se extra fat nikal jata hai.

3.4 Name Relevant Files

@-references aur explicit file names se agent ka attention narrow hota hai aur galat-file edits kam hote hain. Chapter ka example teen files naam karke deta hai aur use 26-line change aur 3 tests milte hain, broad rewrite ki jagah. Chhota, naam wala scope behtar hai.

3.5 Slash Commands Without a Catalog

Chapter 2 ki list ko ratne ki zaroorat nahi — /help aur Tab completion se commands discover karo, aur daily kaam ke chand commands use karo: /init, /compact, /cost, /review, /rewind, /memory.

3.6 Dial the Effort

Thinking keywords (Think, Think hard, Think harder, UltraThink) aur settings me effort slider. Figure 3-1 effort control dikhata hai. Zyada effort zyada tokens aur zyada waqt leta hai — design decisions ke liye worth hai, typo ke liye nahi. Chapter ek effort table deta hai jo task size ko sahi level se map karta hai.

3.7 What Counts as a Tool

Agent ki har call ek tool hai — file padhna, shell command chalana, web search, MCP server call — sab context aur cost ke against count hota hai. Chapter ka example: ek chhote task me 4 tools, ek bade task me 16 tools. Aur ek 1.2-million-token session ka cost $0.26 tha — point yeh hai ki cost ki unit minutes nahi, tokens hain.

3.8 Steering While It Works

Esc se interrupt karo, nayi instruction se redirect karo, ya khatam hone do aur review karo. Chapter har line par micro-steering ke against warn karta hai — loop tab best kaam karta hai jab insaan outcomes ke level par steer kare, keystrokes ke level par nahi.

3.9 Continuing a Conversation

/resume, /continue, aur transcript (Ctrl+R se search). Naya session sasta hota hai aur aksar lambi, stale conversation se behtar hota hai; /compact conversation summarise karke context reclaim karta hai, aur /clear fresh start deta hai.

3.10 Headless Mode

claude --print (dikhaaya gaya -p) se non-interactive use, --output-format se structured output, stderr redirect karke, aur result ko file me likhkar jaise /tmp/analysis.txt. Exit codes: 0 success, 1 failure, 2 usage error. Chapter ka example URLs ki list ko grep, wc, sort aur uniq se pipe karke count karta hai, aur ls -t se newest file dhoondhta hai. Headless mode scripts aur CI ke liye hai, exploratory kaam ke liye nahi.

echo $?   # 0 = success, 1 = failure, 2 = usage error

3.11 Plan Mode

Pehle plan maango, plan ko review karo, phir approve karo. Plan ek file hai jise insaan edit kar sakta hai; agent phir plan ke hisaab se banata hai. Chapter ka example: plan banane ka cost $0.00 tha (planning sasti hai) aur woh ek expensive galat build se bachata hai.

3.12 Output Styles

Default style ke alawa concise aur explanatory styles, aur settings me defined custom styles. Style ko task se match karo — fix ke liye terse, seekhne ke liye explanatory.

3.13 Conversations and the Context Window

Context window finite hai. Chapter models ke numbers deta hai (chhote task ke liye kuch hazaar tokens se bade task ke liye lakhon tokens tak), 90% warning threshold jahan agent compact karna shuru karta hai, aur rule ki jab conversation drift kar jaye to compacted session se fresh session behtar hota hai.

3.14 Summary

Prompts ko work requests likho, banane se pehle clarify karo, files ka naam lo, effort ko task ke hisaab se dial karo, outcome level par steer karo, aur headless aur plan modes ko deliberately use karo.

4.1 Build a Cabin

Chapter ke numbers: rebuild me lagbhag 3 ghante lagte hain, 5 files banti hain, aur test suite lagbhag 700 lines ki hoti hai lagbhag 800 lines application code ke against, jo 100 songs aur 12 artists ko cover karti hai.

4.2 Working Spec and Implementation Plan

Specification ke paanch sections hain (overview, requirements, design, tests, risks) aur use likhne ke baarah rules hain — har rule ek constraint hai jise agent ko respect karna hai, jaise badalne wali files ka naam aur har requirement ko prove karne wale tests.

Implementation plan nau steps ka hai, har step ke acceptance criteria ke saath (main feature ke liye chaar criteria, agle ke liye teen, phir do, phir ek, trivial step ke liye koi nahi, aur final step ke liye kul paanch) — chapter count ko risk ke hisaab se vary karta hai, ceremony ke hisaab se nahi.

4.3 Tests Before Features

Pehle test likho, use fail hote dekho, phir pass karwao. Chapter ki test table me chaar categories hain (unit, integration, property-based, end-to-end) aur run 25 of 26 tests passing (96.2%, ek failing) se sab 26 passing tak jata hai fix ke baad. Failing test ek boundary case hai (ek song jisme ek lyric line missing hai) jise doghouse ne chupchaap ignore kar diya tha.

4.4 Refactor for Clarity

Functions extract karo, intent ke hisaab se rename karo, dead code delete karo — chhote steps me, har step ke beech tests green rakhte hue. Chapter ka example paanch files ko teen, phir do, phir ek, aur finally wapas chaar files me refactor karta hai jab structure settle hota hai — point yeh hai ki file count clarity ka outcome hai, target nahi.

4.5 Add Docs

README ke paanch sections (kya hai, kaise chalaye, kaise test kare, kaise extend kare, kya supported nahi hai), plus docstrings aur changelog. Chapter stress karta hai ki agent ki likhi documentation ko code ke against verify karna chahiye, kyunki agent confidently aisi features describe kar dega jo exist hi nahi karti.

4.6 GitHub

Repository initialise karo, remote add karo, push karo, aur pull request kholo — chaar steps (naye repository ke liye teen, existing ke liye do, fork ke liye ek). Chapter .gitignore, README badge aur pehla issue cover karta hai, aur kehta hai ki repository cabin ka front door hai — agar README galat hai to cabin finish nahi hua.

4.7 Summary

Cabin ek doghouse hai jisme tests, spec, docs aur version control hain — woh minimum jo code ke liye chahiye jis par tum wapas aaoge.

Agent ko boundaries ke andar kaam karne ka trust diya jata hai, aur insaan result verify karta hai. Trust ek feeling nahi, permissions ka ek set hai. Chapter ka rule: agent reversible kaam bina poochhe kar sakta hai, aur irreversible kaam se pehle poochhna hi padega.

FInterview FAQs

Interview FAQs — 36 sawaal

Agentic coding, permissions, MCP, skills/hooks, subagents, PRs aur review/testing par interview-relevant sawaal.

Q1 Agentic development aur snippet generation me kya farq hai?

Snippet generation sirf code ka tukda deta hai; agentic development me agent project padhta hai, plan banata hai, kai files badalta hai, tests chalata hai aur galti par retry karta hai.

Q2 Vibe coding professional kaam ke liye kaafi kyun nahi hai?

Kyunki professional code ko maintain, secure, test, review aur team ke saath safely badalna padta hai — vibe coding me yeh layer missing hoti hai.

Q3 Doghouse, cabin aur skyscraper me kya farq hai?

Doghouse chhota aur temporary hai; cabin dependable hai (tests, docs, trust controls); skyscraper me coordination zaroori hai. Dividing line size nahi, coordination hai.

Q4 Model, harness, coding agent aur surface me kya farq hai?

Model reasoning engine hai; harness model ke aas-paas ka local program hai; coding agent woh harness hai jo tools use karta hai; surface woh jagah hai jahan model milta hai.

Q5 Claude Code install karne ke liye kya chahiye?

Node.js 18+, Git 2.28+, 4 GB RAM, ek terminal aur ek account. GitHub account ki zaroorat nahi hai.

Q6 Model kaise choose karein — Fable, Opus, Sonnet, Haiku?

Default (Sonnet) zyada tar kaam ke liye sahi hai; Opus mushkil design problems ke liye; Haiku saste repetitive tasks ke liye; Fable sabse capable aur sabse mehenga hai.

Q7 Prompt ko work request kaise banayein?

Chaar elements do: kya banana hai, acceptance criteria, constraints (kya nahi karna), aur verification (kaise check karenge).

Q8 Clarification pass kyun zaroori hai?

Kyunki banane se pehle agent ambiguities surface karta hai — framework, storage, edge cases — aur galat build se bachata hai. Example me 45 minute me 7,000-word report bani thi.

Q9 Thinking keywords kya hain aur kab use karein?

Think, Think hard, Think harder, UltraThink — effort badhate hain. Design decisions ke liye worth hain, typo ke liye nahi.

Q10 Context window bhar jaye to kya karein?

Pehle /compact se summarise karo; agar conversation drift kar gayi ho to fresh session behtar hai. 90% par warning milti hai.

Q11 Headless mode kya hai aur kab use karein?

claude --print se non-interactive run — scripts aur CI ke liye. Exit codes: 0 success, 1 failure, 2 usage error.

Q12 Plan mode ka fayda kya hai?

Plan pehle banta hai, insaan review aur edit kar sakta hai, phir agent plan ke hisaab se banata hai. Plan banana $0.00 ka tha example me — sasta insurance hai.

Q13 Cabin banane ke liye minimum kya chahiye?

Tests, working spec, documentation, version control aur accurate README — doghouse me yeh sab add kar do to cabin ban jata hai.

Q14 Tests pehle kyun likhne chahiye?

Pehle test likho, fail hote dekho, phir pass karwao. Isse boundary cases (jaise missing lyric line) pakde jate hain jo doghouse chupchaap ignore kar deta hai.

Q15 Permission ke teen modes kaunse hain?

Default (poochh kar karo), accept edits (file changes bina poochhe, commands se pehle poochho), plan mode (plan pehle, approval ke baad build).

Q16 Deny rule allow rule se kyun jeetta hai?

Kyunki safety ka rule hai: deny hamesha jeetta hai, aur sabse specific rule jeetta hai. Isi se dangerous actions block hote hain.

Q17 bypassPermissions kyun dangerous hai?

Yeh saare permission prompts skip kar deta hai — ek command se poora folder delete ho sakta hai. Uncommitted kaam ya secrets ho to kabhi use mat karo.

Q18 Branch-first development kyun zaroori hai?

Taaki kharab agent run ko discard kiya ja sake. Main par kabhi kaam mat karo; branch banao, review karo, phir merge ya delete karo.

Q19 Secret git history me chala jaye to kya karein?

Sirf file delete karna kaafi nahi — secret ko rotate karo, aur secret-scanning hook lagao taaki dobara na ho.

Q20 Skill aur slash command me kya farq hai?

Slash command canned prompt hai; skill ek directory hai jisme SKILL.md hoti hai jo agent ko workflow sikhati hai aur agent khud invoke kar sakta hai.

Q21 SKILL.md me kya hota hai?

Frontmatter (name aur description) aur body jo workflow sikhata hai. Path: .claude/skills//SKILL.md.

Q22 Bahut zyada skills rakhne se kya nuksaan hai?

Har skill context badhata hai aur agent galat skill pick kar sakta hai. Example me 12 skills ko 4 tak kaatne se fix hua.

Q23 Hook kya hai aur kab chalta hai?

Hook lifecycle event par chalne wala script hai — tool call se pehle/baad, session start/end, ya file edit par. Config .claude/settings.json me hoti hai.

Q24 Hook loudly fail kare to kya hota hai?

Woh agent ko block kar dega. Isliye hooks ko quietly fail karna chahiye ya bilkul fail nahi karna chahiye.

Q25 MCP kya hai aur kyun chahiye?

Model Context Protocol — ek standard jisse server tools, resources aur prompts expose karta hai aur koi bhi MCP client use kar sakta hai.

Q26 MCP ke paanch concepts kaunse hain?

Tools (actions), resources (data), prompts (templates), sampling (server ka sawaal), roots (allowed directories).

Q27 Credentials MCP config me kyun nahi likhne chahiye?

Kyunki config file leak ho sakti hai. Credentials environment variables ya secrets store me rakho; server ko clear error se fail hona chahiye.

Q28 Mandate kya hai? MockHub example se samjhao.

Mandate agent par bound hai — jaise ek order, ek customer, max total. Order MH-20260524-0003: $30.62 + $3.06 = $33.68, mandate ke andar.

Q29 SonarQube aur Context7 ko authority kyun kehte hain?

Kyunki 'good' ka matlab agent decide nahi karta — SonarQube quality ke liye aur Context7 current docs ke liye external authority hain.

Q30 Subagent kab use karna chahiye?

Jab task bounded ho aur context disposable ho — subagent apne context me kaam karke sirf summary wapas deta hai, jaise 200,000-token survey.

Q31 Agent team kab use karni chahiye?

Jab kaam parallelisable ho aur synthesis chahiye — teen teammates alag worktrees me, lead coordinate karta hai. Feature experimental hai.

Q32 Plugin kya hota hai?

Skills, hooks, commands aur MCP servers ka packaged set jo ek unit me install hota hai; marketplace uski registry hai.

Q33 Pull request ko unit of work kyun kehte hain?

Kyunki PR reviewable, reversible aur discussable hai — team use review, test aur revert kar sakti hai; edits ki stream ko nahi.

Q34 Design by Contract kya hai?

Preconditions, postconditions aur invariants se specify karna ki function ko kya karna hai — jaise total = subtotal + tax, aur kabhi negative nahi.

Q35 Seven layers of defence kaunse hain?

Agent self-check, compiler/linter, unit tests, integration tests, property-based tests, external authorities, human review — sasti se mehengi tak.

Q36 Agent kuch tod de to pehla step kya hai?

Ruko, last green commit par revert karo, aur chhote step se dobara shuru karo — agent se uske fix ko fix karne ko mat kaho.
