00.1Preface

Agent-Driven Development — ye book kis baare me hai

Ye book Claude Code ke baare me hai — lekin ye ek feature catalog nahi hai. Official docs woh kaam karte hain, aur woh kisi bhi printed book se tez update hote hain. Ye book is baare me hai ki kaam khud kaise badal jata hai jab tumhare terminal me ek agent baitha ho.

AgDD kya hai?

  • Agent-Driven Development (AgDD) woh practice hai jisme agent production ka kaam chalata hai, aur tum direction, success conditions, verification aur judgment chalate ho.
  • TDD me tests design ko drive karte hain, BDD me business behavior specs ko drive karta hai — AgDD me agent production work ko drive karta hai jabki tum direction ko drive karte ho.
  • Claude Code code bahut tez likh sakta hai. Woh repository inspect kar sakta hai, unfamiliar syntax samjha sakta hai, tests chala sakta hai, documentation update kar sakta hai, pull request review kar sakta hai, aur integrations ke through doosre systems se baat kar sakta hai.
  • Khatra ye hai: jo tool sab kuch kar sakta hai, woh har problem ko "ek prompt door" dikha deta hai. Is book ka nazariya ulta hai — agent jitna capable hota hai, developer ki judgment utni hi important hoti hai.

Ye book kiske liye hai?

  • Un developers ke liye jo pehle se software likhna jante hain aur samajhna chahte hain ki kya badalta hai jab ek coding agent ek asli project ke andar kaam kar sake.
  • Claude Code expert hona zaroori nahi, aur pehle se agentic tools use karna bhi zaroori nahi. Lekin code padhna, terminal commands chalana, tests, version control aur project structure samajhna aana chahiye.
  • Examples kai languages aur frameworks me ghumte hain — ek chhota JavaScript app, ek Python web app, aur bade Java aur React systems. Point stacks sikhana nahi hai; point ye dikhana hai ki stakes badalne par agentic workflow kaise badalta hai.
  • Senior developers, tech leads aur architects bhi intended audience hain. Pehle chapters jaan-bujhkar chhote se shuru hote hain, kyunki loop sabse saaf tab dikhta hai jab project chhota ho.

Pull-mode learning

  • Book me baar-baar "Ask Claude Code" sidebars aate hain — ye ek aadat sikhaate hain: jab koi term na samjho, poochho; jab generated code me koi syntax naya lage, poochho; jab Claude Code ek design doosre par chune, poochho kyun.
  • Sidebars teen roop me aate hain: What is this? (koi feature/syntax/pattern), Why this way? (is code me ye decision kyun), What are alternatives? (trade-off jab ek se zyada raaste hon).
  • Ye pull-mode learning hai — zaroorat ke pal me seekhna. Ye efficient hai kyunki sawaal asal kaam se juda hai. Ye adhoora bhi hai, kyunki asal kaam har prerequisite ko sahi order me nahi chhoota — gaps ko jaan-bujhkar bharna padta hai.
  • Claude Code tez badalta hai. Jab koi command, screenshot, pricing detail ya model naam drift karne wala lage, book uske aas-paas ka durable workflow sikhati hai, current button label ko timeless maan kar nahi.

Doghouse, cabin, skyscraper — book ka roadmap

Poori book me teen project scales baar-baar aate hain. Inhe abhi samajh lo — baaki ke saare chapters isi scale par khade hain.

Teen scales

  • Doghouse — chhota, casual, proportionate. Personal ho sakta hai, temporary ho sakta hai. Isse enterprise ceremony ki zaroorat nahi sirf isliye kyunki ek serious developer ne banaya hai.
  • Cabin — abhi bhi modest, lekin koi is par depend kar sakta hai. Isse boundaries, tests, project memory aur explicit trust decisions chahiye.
  • Skyscraper — enterprise-scale kaam. Coordination, reusable practices, CI/CD discipline, security review, operational awareness, aur aisi documentation chahiye jo doosron ke time ki izzat kare.
  • Khatra modes ko mix karne me hai. Doghouse ko skyscraper ki tarah banao, to bechara kutta kabhi sone ki jagah nahi payega. Skyscraper ko doghouse ki tarah banao, to failure modes mehenge padenge.

Chapters ka safar

  • Chapter 1 — Agent-Driven Development, teen scales, aur ye idea ki software work ki unit badal jati hai jab agent project ko inspect, change aur coordinate kar sake.
  • Chapter 2 — Claude Code install karo, authenticate karo, pehla session chalao, aur pehla doghouse example banao: ek chhota lyrics-trainer app.
  • Chapter 3 — Baatchit ko behtar karo jab project abhi chhota hai: prompts, clarification, slash commands, session continuity, plan mode, output style.
  • Chapter 4 — Pehla growing-pains moment: app abhi bhi chalta hai, lekin code ko tests, structure aur ek testable core chahiye.
  • Chapter 5 — Cabin work: permissions, safety boundaries, trust decisions, aur ek Python web app jahan agent ko saaf guardrails chahiye.
  • Chapter 6 — Skyscraper section ki shuruaat: reusable workflows — skills aur hooks, taaki bada project agent ko wahi cheezein baar-baar na sikhaye.
  • Chapter 7 — Ek agent ko specialized subagents, coordinated agent teams aur packaged plugins me badlo.
  • Chapter 8 — Apne banaye systems se un systems ki taraf jo tumhe mile hain: ek bade codebase ko samajhna jo tumne nahi likha.
  • Chapter 9 — Model Context Protocol (MCP) se Claude Code ko external systems se jodo.
  • Chapter 10 — Prompt se pull request tak: issues, review gates, aur wo discipline jo agentic work ko private terminal theater banne se roke.
  • Chapter 11 — Review, testing, debugging aur failure recovery jab pehla jawab kaafi na ho.
  • Chapter 12 — Terminal se aage: doosri surfaces, model/provider choices, cost aur context trade-offs.
Kaise padhna hai: pehli baar order me padhna sabse achha hai — book jaan-bujhkar cumulative hai. Doghouse chapter me jo decision fussy lage, wahi cabin chapter me zaroori aur skyscraper chapter me non-negotiable ho jata hai.

Companion repo

  • Code aur captured prompts companion examples repository me rehte hain (har code block ke upar uska GitHub link diya gaya hai). Repo pehle application ke hisaab se, phir chapter snapshot ke hisaab se organized hai — lyrics-trainer project me usi app ke Chapter 2, 3 aur 4 wale states hain.
  • Tutorial chapters tab sabse achhe kaam karte hain jab tum saath-saath type karo. Jab koi prompt asal me chalane layak ho, book "try this now" jaisa nudge deti hai. Captured prompts ("in my run") us machine ke records hain — unhe padho, aur agar chalao to expect karo ki tumhare results alag honge.

01.1Ch 1 · Agent-Driven Development

Agentic tools ne boundaries kaise mita di

Agentic coding tools un boundaries ko dhundhla kar dete hain jo pehle solid lagti thi: language, framework, domain, repository, yahan tak ki role bhi. Jab ek capable agent tumhare project ke andar kaam kar sake, to bottleneck har line type karna nahi rehta.

Asli bottleneck kya hai?

  • Bottleneck ab direction hai: outcome ka naam dena, success conditions tay karna, result check karna, aur decide karna ki pehla jawab kab kaafi nahi hai.
  • Is shift ke liye ek deliberate practice chahiye — wahi practice Agent-Driven Development (AgDD) hai. Agent production work chalata hai. Tum direction, verification aur judgment chalate ho.
  • Shuruaat me Claude Code aam lagta hai: repository wale folder me terminal kholo, request type karo, dekho woh files inspect kare, actions propose kare, permission wale hisse approve/reject karo, phir jo badla use test karo.

Problems naye nahi hain

  • Requirements abhi bhi drift karti hain. Tests abhi bhi sadte hain. Context abhi bhi gayab hota hai. CI abhi bhi sabse bure waqt par fail hota hai. Maintenance abhi bhi initial development se zyada kharcha karta hai.
  • Claude Code in problems ko gayab nahi karta. Woh badal deta hai ki production work kaun karta hai, kya evidence milta hai, aur galtiyan kahan chhup sakti hain. Kabhi purana kaam aasan ho jata hai, kabhi purani galtiyan tez ho jati hain.
  • Goal sirf "zyada code, zyada tez" nahi hai — ye field ka sabse aasan trap hai. Software economics me maintenance pehle se dominant tha: ek NIST executive guide ne maintenance ko total software cost ka 60–70% bataya tha, aur ek mashhoor software engineering book ne 40–80% ka range popular kiya tha.
  • AI is purani problem ko aur tez kar deta hai. Agar tum doguna code generate karte ho, to tumhare paas maintain karne ke liye doguna code hai. Har line jo tum rakhte ho, woh system ka hissa ban jati hai jise kisi ko samajhna, test karna, debug karna, secure karna aur badalna padega.
  • AgDD tabhi pay karta hai jab agent useful change ki cost kam kare, sirf typing ki cost nahi.
Yaad rakho: line count destiny nahi hai, lekin har kept line ek liability hai. Agent se doguna code likhwana tabhi fayda hai jab us code ko badalna, samajhna aur test karna bhi sasta ho.

Certificate-service — ek joke jo serious ho gaya

Book ki opening kahani ek joke project ki hai — aur wahi joke batata hai ki scale kab badalta hai aur methodology ko uske saath kab badalna chahiye.

Joke kya tha?

  • Kisi ne ek ebook kharidi aur sign karwana chaha — gag ke taur par ek Kindle aur felt marker thama diya. Digital signature se ebook sign karna possible tha: buyer ke liye ek Certificate of Ownership generate karo, us par scanned signature laga do, digitally sign kar do, aur ek QR code jod do jo verification endpoint par le jaye.
  • Result: ek self-signed (pdf) certificate, jo khud ke (digital) self-signed certificate se signed ho. Funny — lekin implement karna tedious tha: cryptography ke liye low-level libraries, PDF ke liye alag library, khud ke X.509 certificates set up karne padte.
  • Itna kaam is silly idea ko "weekend me bana lo" territory se nikaal kar backlog me daal deta — jahan silly ideas indefinite pade rehte hain.

Claude Code ne kya badla?

  • Claude Code aaya, aur barriers itne kam ho gaye ki poora kaam doable ho gaya. Kuch ghanton me ek working Spring Boot service taiyaar thi: scanned signature embedded, QR code verification endpoint se juda, PDF par X.509 digital signature, aur deployment me bhi madad.
  • Pehla version bilkul waisa tha jise experienced developers thode disdain se vibe coding kehte hain — aur is version ke liye woh label poori tarah sahi tha. Woh chalta tha. Joke ko asal kar diya. Architecture review ki zaroorat nahi thi.
  • Lekin wahan rukna possible nahi tha. Project PDFs, certificates, signatures, verification endpoints aur production deployment ko chhoota tha — itna real-world surface area ek clever afternoon par chhodne layak nahi tha.
  • Aaj woh service controller/service/model layers me banti hai, Java 25 par virtual threads ke saath chalti hai, security-critical hisso par property-based tests hain, aur analytics ka apna sub-package hai apne integration tests ke saath.
Sabak: project badla nahi — sirf bada hua. Lekin stakes badle, aur methodology ko uske saath badalna pada. Wahi transition poori book ka spine hai.

01.3Ch 1 · Agent-Driven Development

Teen scales: doghouse, cabin, skyscraper

Certificate-service sirf bada nahi hua — usne scale badla. Book projects ko teen categories me baantti hai, aur ye model poori book me kaam aata hai.

Teenon scales

  • Doghouse — chhota, casual, weekend me ship ho jata hai, aur koi inspect nahi karta. Yehi vibe coding ka sweet spot hai.
  • Cabin — modest lekin dependable. Iske explicit trust contracts hain, boundaries hain, aur ek testable core hai. Agar koi is par depend karta hai, to discipline lagti hai — size se farak nahi padta.
  • Skyscraper — full enterprise architecture. Coordination, verifiable CI/CD discipline, reusable workflows, security review aur operational visibility — sab matter karte hain.

Cabin aur skyscraper ke beech line kahan hai?

  • Line size nahi, coordination hai. Jis pal doosre logon ko project ke andar kaam karna pade — formal review gates, shared pipeline, aisi documentation jiss par doosre apna kaam karne ke liye depend karein — tum skyscraper territory me ho.
  • Ek chhota skyscraper abhi bhi skyscraper hai. Jab tak tum woh coordination line cross nahi karte, tum cabin hi bana rahe ho, chahe plumbing kitni bhi achhi ho jaye.
  • Certificate-service ek fully built-out cabin hai: ek vyakti, ek agent ke saath, ek chhote system ko production tak le gaya — bina enterprise ceremony ke.

Modes mix karne ki galti

  • Doghouse ko skyscraper ki tarah banao — architecture review boards, change-control processes, pehli keel se pehle chhe hafte ka design — to cheez kabhi banti hi nahi.
  • Skyscraper ko doghouse ki tarah banao — vibe-coded, koi tests nahi, Friday ko production deploy — to failure modes mehenge tareeke se fail honge.
  • Projects categories ke beech move kar sakte hain. Certificate-service ek joke se shuru hua, lekin jab woh asal tool bana, stakes badle aur methodology ko bhi badalna pada. Achhi khabar: Claude Code dono stages me aur unke beech ke transitions me madad kar sakta hai.

Terminal me agent — harness vs model

Claude Code ek Anthropic model ke aas-paas bana agentic coding harness hai. Ye farak samajhna zaroori hai, kyunki book ke zyada patterns harness patterns hain — model sirf ek knob hai.

Model vs harness

  • Model (jaise Fable, Opus ya Sonnet) reasoning LLM engine hai — woh hissa jo padhta hai, plan karta hai aur decide karta hai ki aage kya karna hai.
  • Claude Code (harness) engine ke aas-paas sab kuch hai: agent loop jo ek request ko multi-step kaam me badal deta hai, terminal interface, project context (files, session history, CLAUDE.md), tool calls (file reads, writes, shell commands, web searches), permission gates, MCP connections, lifecycle events par fire hone wale hooks, capabilities badhane wali skills, aur workspace awareness.

Ye chat nahi hai

  • Claude Desktop app aur Claude AI website chat tools hain — text type karo, response pao. Claude Code woh bhi kar sakta hai, lekin us tak limited nahi hai. Interactive conversation Claude Code ka point nahi hai — point woh loop hai jahan conversation inspected actions ki taraf le jati hai, ek working project ke andar files ke poore collection ke saath.
  • GitHub Copilot jaise tools autocomplete se shuru hue the — line by line ya block by block code complete karte hain. Agentic coding tools multi-step kaam plan karte hain: woh decide karte hain ki code se pehle test likhna hai ya nahi, ki tumhare describe kiye task ke liye asal me teen files ko ek specific order me chhoona padega.
  • Claude Code ka posture shuru se agentic hai: tum outcome describe karte ho, woh steps plan karta hai, actions leta hai, permission wali jagah par check karta hai, aur report karta hai ki usne kya kiya. Conversation kaam ka side effect hai, substance nahi.
Isliye ye farak matter karta hai: jab tum model badalte ho, harness patterns wahi rehte hain. Book ke patterns isiliye zyada tar transferable hain — chahe model ya surface badal jaye.

01.6Ch 1 · Agent-Driven Development

Request loop — kaam kaise hota hai

Request loop Claude Code ki mechanical foundation hai. AgDD us loop ke aas-paas ki discipline hai — kya poochhna hai, kya approve karna hai, kya test karna hai, kya reject karna hai, aur kaam kab us mode se bada ho gaya jisme tumne shuru kiya tha.

Loop ke steps

  1. Request karo — outcome describe karo.
  2. Context load karo — Claude Code relevant files padhta hai ("loads the context").
  3. Plan karo — implement karne ke steps plan karta hai.
  4. Tools use karo — aur files padhna, commands chalana, web search, MCP services ko call karna.
  5. Permission check — jab koi action aisi permission maange jo tumne nahi di, to woh ruk kar poochhta hai.
  6. Output do — jo kiya, woh produce karo aur tumhari reaction ka wait karo.
  7. React karo, evaluate karo, repeat karo — kaam iterative hai.

Visibility hi control hai

  • File reads scroll hote dikhte hain. Proposed edits apply hone se pehle dikhte hain. Jab agla step shell command ya file write ho, Claude Code rukta hai aur tumhare call ka wait karta hai.
  • Ye visibility hi loop ko steerable banati hai. Agar tum dekho ki woh kisi aisi direction me ja raha hai jo tumne intend nahi kiya, to interrupt kar sakte ho.
  • Isi liye ESC key tumhari dost hai — galat direction dikhte hi ESC dabao, kaam khatm hone ka wait karke undo karne ki koshish karne se behtar hai.

Agent teams — direction-mode, bade scale par

Claude Code ko ek-ek instruction dene wala single assistant hi rehna zaroori nahi hai. Independent pieces wale kaam ke liye woh ek chhoti team coordinate kar sakta hai — ye default workflow nahi hai, ye progression ka far end hai.

Ek example — teen teammates

  • Certificate-service repository par point karke, agent teams enable karke, ye high-level instruction di gayi: teen teammates banao — ek tests me coverage gaps review kare, ek code me security issues review kare, ek documentation ko accuracy aur missing setup notes ke liye update kare. Jahan possible ho parallel kaam karein, phir results synthesize karein.
  • Claude Code ne coordination call khud li, teeno ko parallel chalaya, aur findings synthesize ki: test reviewer ne ek integration test pakda jo silently skip ho raha tha; security reviewer ne authentication aur file-path issues flag kiye; docs teammate ne stale version numbers correct kiye aur missing endpoints document kiye.
  • Striking baat ye nahi thi ki Claude Code tests review kar sakta hai ya docs edit kar sakta hai — ek single session ye sab kar sakta hai. Striking baat ye thi ki kaam ko haath se decompose nahi karna pada. Outcome, teen perspectives aur synthesis ki zaroorat batayi gayi — Claude Code ne team banayi, kaam baanta, aur results wapas le aaya.

Lekin — cost aur limits

  • Agent team ke teammates apne tokens khud kharch karte hain — teen ki team single agent ke lagbhag teen guna rate par tokens kharch karti hai.
  • Agent teams is draft ke samay experimental hain, default se disabled hain — enable karne ke liye CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 set karna padta hai.
  • Ye sequential kaam ke liye sahi nahi hain, aur un changes ke liye bhi nahi jahan kai agents same files par ladenge.
  • Ye direction-mode hai, bade scale par: tum sirf output nahi maang rahe — tum work system design kar rahe ho: kaun problem ko dekhe, kaunsi perspectives matter karti hain, useful result kya hota hai, aur jawab kab human judgment ke liye wapas aana chahiye.
Order yaad rakho: agent teams Chapter 7 me wapas aati hain — single-agent workflow, project memory, testing pressure, permissions aur trust boundaries pehle aate hain.

Teen themes: tool, work aur tumhari role

Baaki ki book teen clusters par wapas aati rehti hai: tool, kaam, aur tumhari role. Ye aspirational nahi, operational hain — har ek ek discipline hai jiska apna failure mode hai.

1. Mechanics — tool

  • Claude Code ek agent-in-terminal harness hai. Mechanics jaanna (kaunse tools call kar sakta hai, request loop kaise kaam karta hai, permission gates kya hain, CLAUDE.md kya karta hai) foundational hai — jo samajhte nahi, use direct nahi kar sakte.
  • Mechanics tab sabse zyada matter karte hain jab woh workflow se jude hon, inventory ki tarah ratte hue nahi.

2. Kaam khud alag dikhta hai

  • Code mature hote hi tumhari role badalti hai. Doghouse me vibe coding chalti hai: outcome describe karo, Claude Code software banaye, check karo ki chalta hai, ship karo.
  • Cabin me level badhta hai: implementation se pehle design conversations, structure ko drive karne wale tests, durable project memory, deliberate reviews, explicit trust boundaries.

Request loop, nazar me

Session me pehli cheez jo notice karoge, woh ye hai ki Claude Code kitna kuch dikhata hai. File reads scroll hote hain. Proposed edits apply hone se pehle dikhte hain. Jab agla step shell command ya file write ho, to woh rukta hai aur tumhare call ka wait karta hai.

Prompts as work requests

Chapter 2 ne Claude Code chala diya. Ye chapter behtar kaam nikalne ke baare me hai — prompt se process ko direct karna.

Sawaal poochhna vs kaam dena — farak hai

  • Chhote, conversational prompts ki apni jagah hai. Existing project me pehli baar ghumte waqt "What does this project do?" ya "Where is the main entry point?" achhe hain — aur kyunki Claude Code pehle se hi tumhare project ke andar baitha hai, project samajhne ke liye files alag chat window me paste nahi karni padti.
  • Lekin system ke baare me sawaal poochhna aur implement karne ka task likhna alag cheezein hain. Task ke liye do-teen shabd type karke Enter dabana aur useful result ki ummeed karna kaam nahi karta. Vague task (jaise infamous "fix this bug") Claude Code ki imagination par bahut kuch chhod deta hai.
  • Jawaab casual baat band karna nahi hai — jawaab ye hai ki jis pal tum kuch badalwane ko kaho, us pal deliberate ho jao. "What options do you suggest for fixing this bug?" jaisi simple rephrasing bhi response quality me bada farak dalti hai.

Vague vs detailed — compare karo

prompt — vague ❌
fix the bug
prompt — detailed ✓
The user-registration form on /signup accepts an empty email field and

  • Ajeeb baat: lamba prompt aksar sasta bhi padta hai. Vague request Claude Code ko extra discovery rounds me bhejta hai ye samajhne ke liye ki tumhara matlab kya tha — aur extra rounds hi woh jagah hain jahan tokens jate hain (Chapter 12).

Success condition batao

  • Claude Code ko pata hona chahiye ki "done" ka matlab kya hai. Task ke hisaab se ye ho sakta hai: route 400 return kare, page bina overlapping text ke render ho, test command pass ho, ek file untouched rahe, migration ka rollback path ho.
  • Success conditions implementation ka kaise specify nahi karte — sirf result kaisa dikhna chahiye, ye batate hain. Baaki agent par chhod do.
  • Aur ye bhi bata do ki request underspecified ho to kya kare: "If there are multiple reasonable approaches, stop and ask me to choose. If anything about the current behavior is ambiguous, ask before editing." Ye do lines bahut madad karti hain — tum agent ke sahi guess karne ki ummeed nahi kar rahe; tum use permission de rahe ho ki woh decision lene se pehle ambiguity ki taraf point kare.

Over-specification se bacho

  • Achha prompt woh hai jis par ek careful colleague act kar sake — ya clarifying questions poochh sake. Agar result kai questions ho, to context add karo. Agar unhe koi judgment hi na chahiye ho, to dekh lo ki tum implementation ko over-specify to nahi kar rahe.
  • "Use these exact variable names, this exact control flow, and this exact helper function" aisa code de sakta hai jo prompt ko obey kare lekin goal miss kar de. Outcomes aur constraints par specific raho, implementation par nahi.
  • Constraint dete waqt do chhoti aadatein use kaam ka banati hain: pehle, woh batao jo chahiye, woh nahi jo mana hai — "Don't put business logic in the route handler" ye nahi batata ki code kahan jana chahiye; "Keep the route handler thin and put the logic in a service function" target ki taraf point karta hai. Doosre, constraint ke peeche ka reason do — "Keep the route handler thin so the logic can be tested without starting the web layer" ek stronger instruction hai, kyunki Claude Code reason se generalize karta hai aur un jagah par bhi consistent choices karta hai jinka tumhare prompt me zikr hi nahi tha.
  • Ek caution: recent models instructions ko literally lete hain aur ek case ko silently doosre par carry nahi karte. Agar tum ek handler me fix karte ho aur wahi fix har jagah chahiye, to kaho — "every handler, not just this one" — generalize karne ka bharosa mat karo. Scope woh cheez hai jo tum state karte ho, woh nahi jise tum infer karne ki ummeed karte ho.

Kyun zaroori tha?

Prompt — try this now

prompt — local persistence
Add local persistence to the lyrics-trainer. When the user advances to
a new line, save the current line index to localStorage. When the page
loads, check localStorage and resume from the saved position if one
exists. If the saved position is out of range for the current text,
fall back to line 0.
Success condition: reload the page after advancing a few lines and the
app resumes at the same line. Corrupt or out-of-range stored values
fall back safely to the first line.
Keep the current single-file structure. Add the storage logic where it
naturally fits, but don't extract modules or introduce a build step.
Before you start, do you have any questions for me? Is there anything
I'm missing? Are there any other options I've neglected?
  • Ye prompt chaar useful cheezein kar raha hai: woh behavior specify karta hai jo chahiye, ek edge case explain karta hai jo handle karna hai, success condition express karta hai, aur explicitly doghouse-mode structure preserve karta hai jisse humne shuru kiya tha. Ye kehna zaroori hai, warna Claude Code chapter ke ready hone se pehle architecture improve karne ki koshish kar sakta hai.
  • Meri run me Claude Code ne jo poochha gaya woh kiya — lekin pehle kuch questions poochhe: Next button end par wrap kare ya nahi? Usne point out kiya ki localStorage se wapas aaya value missing, non-numeric, float, negative ya out of range ho sakta hai — aur recommend kiya ki har edge case first line par collapse ho jaye. Usne ye bhi kaha ki key "text-agnostic" hai — stored index valid lagega chahe poem baad me swap ho jaye. Storage key ke liye uski recommendation maan li gayi.

Result — loadIndex()

  • Ek loadIndex() helper jo startup par ek baar chalta hai, purana let currentIndex = 0 replace kar deta hai. Storage key: "lyricsTrainer.lineIndex".
  • Har advance par ek line save hoti hai — Next handler me index update hone ke turant baad: localStorage.setItem(STORAGE_KEY, currentIndex).
  • Verify karo: page kholo, Next kuch baar click karo, counter ("Line N of 14") note karo, reload karo. Agar counter wahi line dikhaye, to persistence kaam kar gayi — aur notice karo ki sahi resume aisa lagta hai jaise kuch hua hi nahi, kyunki page reload se pehle aur baad me wahi line render karta hai. Counter hi ek cheez hai jo batata hai ki woh kaam kiya.

  • Save in teeno me se kuch nahi deta: woh exactly ek jagah hota hai, ek statement hai, aur localStorage.setItem(STORAGE_KEY, currentIndex) index update ke turant baad padhne me theek lagta hai. // Line-navigation core. No DOM, no storage — just the index state and the math
// around it, so the whole thing can be constructed and driven from tests.

// Coerce an arbitrary stored/initial value into a usable index. A valid value
// (an integer in [0, length)) is returned as-is; anything else — non-numeric,
// non-integer, negative, off the end, or absent — falls back to 0.
export function normalizeIndex(value, length) {
  const n = Number(value);
  if (!Number.isInteger(n) || n < 0 || n >= length) {
    return 0;
  }
  return n;
}

// A small stateful trainer over `lines`. Holds the current index internally and
// exposes just enough to render and advance.
export function createLineTrainer(lines, initialIndex = 0) {
  let index = normalizeIndex(initialIndex, lines.length);

  return {
    currentLine() {
      return lines[index];
    },
    currentIndex() {
      return index;
    },
    // Advance to the next line, wrapping back to the first after the last one,
    // and return the line now showing.
    next() {
      index = (index + 1) % lines.length;
      return lines[index];
    }
  };
}

// Reading and writing the resume position. Functions take a Storage-like
// object (anything with getItem/setItem) so the browser passes localStorage
// while tests pass a lightweight fake — no jsdom required.
import { normalizeIndex } from "./lineTrainer.js";

export const DEFAULT_KEY = "lyricsTrainer.lineIndex";

// Decide which line to resume on, reusing the core's validation rather than
// duplicating it: any invalid or absent saved value falls back to line 0.
export function loadSavedIndex(storage, lineCount, key = DEFAULT_KEY) {
  return normalizeIndex(storage.getItem(key), lineCount);
}

// Persist the current position.
export function saveIndex(storage, index, key = DEFAULT_KEY) {
  storage.setItem(key, String(index));
}

Interview FAQs

Claude Code aur agent-driven development par 40 interview-relevant sawaal-jawaab — book ke Chapters 1–4 aur overviews se. Har jawaab Hinglish me, seedha aur yaad rakhne layak.

Q01AgDD (Agent-Driven Development) kya hai? TDD/BDD se kaise alag hai?
AgDD woh practice hai jisme agent production work chalata hai aur developer direction, success conditions, verification aur judgment chalata hai. TDD me tests design ko drive karte hain, BDD me business behavior specs ko drive karta hai — AgDD me agent production ko drive karta hai. Farak ye hai ki kaun kya drive karta hai: tests, behavior, ya agent.
Q02Doghouse, cabin aur skyscraper ka matlab kya hai?
Ye project ke teen scales hain. Doghouse chhota, casual, weekend me ship hone wala hai — vibe coding ka sweet spot. Cabin modest lekin dependable hai — boundaries, tests, project memory aur explicit trust decisions chahiye. Skyscraper enterprise-scale hai — coordination, CI/CD discipline, reusable workflows, security review. Cabin aur skyscraper ke beech line size nahi, coordination hai.
Q03Claude Code aur Claude desktop app me kya farak hai?
Desktop app aur website chat tools hain — text type karo, response pao. Claude Code ek agentic harness hai: terminal ke andar baithkar files padhta hai, plan karta hai, tools call karta hai, changes karta hai aur permission maangta hai. Conversation kaam ka side effect hai, substance nahi.
Q04Claude Code vs GitHub Copilot — farak kya hai?
Copilot autocomplete se shuru hua tha — line by line ya block by block code complete karta hai. Claude Code agentic hai: outcome describe karo, woh multi-step plan banata hai, decide karta hai ki code se pehle test likhna hai ya nahi, aur teen files ko specific order me chhoota hai. Autocomplete vs multi-step planning — yehi core farak hai.
Q05Model aur harness me farak kyun matter karta hai?
Model (Fable/Opus/Sonnet) reasoning engine hai — padhta, plan karta, decide karta hai. Harness (Claude Code) engine ke aas-paas sab kuch hai: agent loop, terminal interface, project context, tool calls, permission gates, MCP, hooks, skills. Zyada patterns harness patterns hain — model badalne par bhi wahi rehte hain, isliye transferable hain.
Q06Claude Code install kaise karte hain?
Recommended tareeka native installer hai: macOS/Linux/WSL par `curl -fsSL https://claude.ai/install.sh | bash`, PowerShell par `irm https://claude.ai/install.ps1 | iex`, CMD par install.cmd wala command. Native installer background me auto-update hota hai. Verify karne ke liye `claude --version` aur `claude doctor` chalao. Homebrew, WinGet aur Linux package managers bhi available hain.
Q07claude doctor kya karta hai?
`claude doctor` local Claude Code setup ko check karta hai aur environment problems ko pakadta hai — chapter bhar galat cheez diagnose karne se pehle. Install ke baad kuch off lage to pehle yehi chalao.
Q08Subscription lu ya API key use karu?
Subscription se login recommended hai — browser me authenticate karo, credentials locally store hote hain. API key possible hai lekin jaldi mehenga padega, kyunki agentic work me codebase ke bade hisse baar-baar bheje jate hain. Pro se shuru karo, zaroorat pade to Max 5x ya Max 20x par upgrade karo. Koi free level nahi raha; Ollama se open source models ke saath harness chalana ek option hai.
Q09Session kahan se start karni chahiye?
Us directory se jisme kaam hai: `cd /path/to/your/project` phir `claude`. Welcome screen cwd, model, git branch aur shell dikhati hai — ye metadata tumhara pehla verification point hai agar baad me kuch unexpected ho.
Q10Status line customize kaise karte hain?
`/statusline` command chalao aur English me describe karo ki kya chahiye — jaise folder, model, branch, git status, time aur weather. Claude Code script likhta hai aur `~/.claude/settings.json` me wire kar deta hai. Dhyaan rakho: script har refresh par chalti hai, to slow cheez lag add kar deti hai.
Q11Request loop ke steps kya hain?
Describe outcome → context load karo → steps plan karo → tools use karo (files, commands, web, MCP) → permission check (writes/shell ke liye) → output do → react, evaluate, repeat. Read-only operations seedha return karti hain; writes aur shell commands permission gate se guzarte hain.
Q12ESC kab dabana hai?
Jis pal dikhe ki Claude Code kuch aisa kar raha hai jo tum nahi chahte — turant ESC dabao. Khatm hone ka wait karke undo karne ki koshish se ye bahut behtar hai. Visibility hi loop ko steerable banati hai.
Q13Achha prompt kaise likhte hain?
Prompt ko colleague ko likhe message jaisa banao: symptom, desired behavior, likely location, local conventions, boundaries — aur success condition. 'Fix the bug' vague hai; 'signup route empty email par 200 ke bajaye 400 return kare, @src/routes/auth.js me, existing validator style match kare' detailed hai. Lamba prompt aksar sasta bhi padta hai — vague prompt extra discovery rounds bhejta hai.
Q14Prompt me success condition kyun zaroori hai?
Claude Code ko pata hona chahiye ki 'done' ka matlab kya hai — route 400 return kare, page bina overlap ke render ho, test command pass ho, file untouched rahe, migration ka rollback path ho. Success conditions kaise implement karna hai ye nahi batati — sirf result kaisa dikhna chahiye. Baaki agent par chhod do.
Q15'If there are multiple approaches, stop and ask' — ye line kyun likhte hain?
Ye agent ko permission deti hai ki woh decision lene se pehle ambiguity ki taraf point kare. Tum sahi guess karne ki ummeed nahi kar rahe — tum use keh rahe ho ki commitment se pehle ruk kar poochhe. Underspecified request me ye do lines bahut madad karti hain.
Q16Over-specification se kya nuksaan hai?
'Use these exact variable names, this exact control flow' aisa code de sakta hai jo prompt obey kare lekin goal miss kar de. Outcomes aur constraints par specific raho, implementation par nahi. Agar flexibility doge to agent pleasantly surprise bhi kar sakta hai.
Q17@ file reference kyun use karte hain?
`@src/routes/auth.js` jaise references relevant files ko conversation me kheench lete hain aur important mark karte hain. Tum search ke tokens bachate ho aur Claude Code ko batate ho ki kin files ke saath kaam karna hai. `@` type karte hi matching paths offer hote hain, aur ek baar file mil jaye to session use yaad rakhta hai.
Q18Ask vs Request me farak kya hai?
Ask goal understanding ke liye hai — 'How does this app persist the current line?' Request goal action ke liye hai — 'Add validation to the signup route.' Zyada beginners request bahut jaldi kar dete hain. Pehle ask karo, phir request — aur dono ko alag prompts me rakho, warna confident edit galat explanation par ban jayega.
Q19Clarification pass kab karna hai?
Kisi bhi nontrivial change se pehle: 'Do you have any questions for me? Is there anything I'm missing? Are there any options I've neglected?' 'Format this file' ko iski zaroorat nahi; 'Move this app from SQLite to PostgreSQL' ko shayad hai.
Q20'Explain like I'm skeptical' kab use karte hain?
Jab AI tumse bahut jaldi agree kar raha lage, ya change ke peeche ka reasoning evaluate karna ho. Ye Claude Code ki overly confident aur overly agreeable tendency se ladta hai. Usse exact opposite argue karne ko bhi keh sakte ho — woh offend nahi hoga.
Q21/clear, /compact aur /context me farak kya hai?
`/clear` directory chhode bina fresh conversation shuru karta hai. `/compact` lambi conversation ko summarize karta hai taaki kam context pressure ke saath continue kar sakein. `/context` dikhata hai ki current context window kahan spend ho raha hai — system prompt, tools, memory, skills, messages, free space.
Q22/btw aur /branch kis kaam ke hain?
`/btw` chhote side questions ke liye hai jo current task ko derail nahi karte — jaise 'Why did you pick that library?' Agar aside asal discussion ban jaye, to `/branch` se nayi conversation split kar lo, working session contaminate kiye bina.
Q23/code-review kya karta hai?
Ye latest changes ko review karta hai aur issues report karta hai — pehle iska naam /simplify tha. Optional effort level de sakte ho. Kaam karne ke baad, accept karne se pehle ki checking move hai. Big-picture review prompt (poora app dobara dekho) isse broader hai — woh multiple changes ke baad sab kuch examine karta hai.
Q24Effort dial kya hai? xhigh kab use karte hain?
Effort intelligence ko speed aur token cost se trade karta hai: low, medium, high, xhigh, max, auto, aur ultracode (xhigh + automatic workflows). Coding aur agentic work ke liye xhigh se shuru karo; judgment wale kaam me high ka floor rakho; chhote tasks me medium/low kaafi hai. Kam effort hard problem par under-think karta hai; zyada effort easy task par over-engineer karta hai.
Q25Headless mode (claude -p) kahan use hota hai?
Jab Claude Code kisi doosre workflow ka hissa ho: `claude -p "explain this function"`, ya `git diff -- src | claude -p "review this diff for likely bugs"`. Scripts, CI aur code reviews me useful hai — doosre tool se code generate karwao, Claude Code se review karwao. `-c` ke saath pichhli conversation continue bhi kar sakte ho.
Q26Session resume kaise karte hain?
`claude -c` most recent conversation continue karta hai; `claude -r` specific earlier conversation kholta hai (session ID ya naam se); `claude -n "auth-refactor"` se session start karte waqt naam set karo; `/rename` se mid-flight rename karo. Session IDs random hote hain, isliye naam hi practical tareeka hai dobara dhoondhne ka.
Q27Plan Mode kab use karna chahiye?
Jab steps kai hon: multi-file changes, unfamiliar code, migrations ya broad refactoring, subtle behavior jahan galat interpretation plausible code de. Trigger: Shift+Tab do baar, `/plan`, ya seedha bolna — 'Let's make a plan before editing.' Plan approve hone tak disk par kuch nahi badalta.
Q28Output styles kya hain? Custom style kaise banate hain?
Default, Proactive, Explanatory aur Learning built-in styles hain — `/config` se badlo. Custom styles Markdown files hain: `~/.claude/output-styles` (personal) ya `.claude/output-styles` (project). Coding work ke liye `keep-coding-instructions: true` zaroor rakho, warna built-in software-engineering instructions gayab ho jayengi. Skeptical-senior-engineer style ek achha example hai.
Q29Context window kya hai? 1M tokens ka matlab kya hai?
Context window maximum tokens hai jo ek request me fit ho sakte hain. Har request me poori conversation history bhi jati hai, isliye har request pichhle se lamba hota jata hai. Purane models 100K–200K the; naye 1M ya zyada hain. Lekin pehle kuch hundred thousand tokens ke baad retrieval ki effectiveness par debate hai — bada window automatically behtar nahi hota.
Q30Auto-compaction se kaise bachein?
Compaction lossy hai aur inconvenient time par ho sakti hai. Manual `/compact` se sahi moment pick karo, aur instructions do ki kya preserve karna hai — architecture, test plan, decisions, TODOs. Compaction ke baad checkpoint maango: 'Summarize what you believe is true about this project now.' Important cheezein CLAUDE.md me save karo taaki dobara padhi ja sakein.
Q31localStorage persistence kaise kaam karta hai?
`loadIndex()` startup par stored value padhta hai aur validate karta hai — missing, non-numeric, float, negative ya out-of-range mile to line 0 return karta hai. Har advance par `localStorage.setItem(STORAGE_KEY, currentIndex)` save karta hai. Key 'text-agnostic' hai — poem swap ho jaye tab bhi stored index valid lagega.
Q32normalizeIndex kyun zaroori hai?
Ye arbitrary value ko usable index me coerce karta hai: valid integer `[0, length)` me ho to waisa ka waisa, baaki sab 0 par fall back. Iske bina corrupt ya out-of-range saved value app ko tod sakti hai. Yehi guard resume ko safe banata hai — aur isiliye ye core me hai, DOM glue me nahi.
Q33Demo aur test me farak kya hai?
Demo prove karta hai ki app ek baar kaam kiya — jab tum dekh rahe the. Tests automatically chalte hain aur outputs ko known results se check karte hain. Demo sabse mehanga aur unreliable tareeka hai — edge cases aur failure modes verify nahi karta.
Q34Testable code kya hota hai?
Woh code jise bina browser ke verify kar sakte ho. Lyrics-trainer me decision logic (lineTrainer.js, storage.js) modules me extract ki gayi; DOM glue (main.js) patla reh gaya. Litmus test: 'Kya main is behavior ko bina browser ke verify kar sakta hoon?' Agar nahi, to logic trapped hai.
Q35CLAUDE.md me kya likhna hai aur kya nahi?
Stable instructions likho: build/test commands, architecture notes, coding standards, workflow habits. Scrapbook mat banao — poori file har session ki shuruaat me context window me load hoti hai. README humans ke liye hai, CLAUDE.md agents ke liye hai. Badi file ko `@` imports se split karo.
Q36Auto memory kya hai? /memory kab chalana hai?
Auto memory Claude ke khud ke notes hain — `~/.claude/projects/<project>/memory/` me, corrections aur repeated patterns ke basis par. Ye machine-local hai, repo me check in nahi hoti. `/memory` command dikhata hai ki current session me kya load hua hai. Agar Claude koi ajeeb rule follow kare, to wahi se shuru karo — stale preference wahi milegi.
Q37CLAUDE.md vs AGENTS.md — farak kya hai?
Claude Code sirf CLAUDE.md padhta hai; Antigravity GEMINI.md aur AGENTS.md dono padhta hai. Agar dono files hon, to CLAUDE.md me `@AGENTS.md` import se connection explicit banao. `/init` AGENTS.md ko incorporate kar sakta hai, lekin check karo ki hua — rely mat karo.
Q38/add-dir kab use karte hain?
Jab project ek repository nahi ho — frontend API ke bagal me, library consuming app ke bagal me, ya naya project existing project ke model par banana ho. `/add-dir ../my-other-project` se doosri directory session me add hoti hai. Deliberately use karo — har expansion context khata hai.
Q39Vibe coding kab theek hai aur kab nahi?
Doghouse me theek hai — chhota, casual, koi depend nahi karta. Cabin me nahi — jahan koi depend kare, wahan tests, boundaries, project memory aur trust decisions chahiye. Skyscraper me to bilkul nahi — coordination, CI/CD, security review sab chahiye. Stakes se decide karo, size se nahi.
Q40Agent teams kab use karte hain, kab nahi?
Tab use karo jab kaam ke independent pieces hon aur teen perspectives (jaise test coverage, security, docs) parallel chahiye hon. Sequential kaam ya same files par ladne wale changes ke liye nahi. Yaad rakho: teen ki team lagbhag teen guna tokens kharch karti hai, aur teams experimental hain — `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` se enable hoti hain.
