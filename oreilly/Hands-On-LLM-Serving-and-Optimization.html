03.1Ch 1 — Model Serving ka Introduction

Model serving kya hai?

Model serving matlab hai trained model ko users, applications aur systems ke liye accessible banana — APIs, web services ya integrated workflows ke through — taaki wo naye, unseen data par predictions (inference) de sake. Kitab me model serving, model inference aur prediction ko interchangeably use kiya gaya hai.

Supply-chain analogy

Trained model ek manufactured product jaisa hai — agar use sahi latency, reliability aur cost ke saath deliver na kiya jaye, to uski business value bahut kam hai. Examples:

  • Amazon aur Netflix — users ke browse karte hi recommendations turant update karte hain.
  • Banks — checkout par fraudulent transactions ko turant block karte hain.
  • Airline chatbots — turant flight updates dete hain aur rebooking karte hain.

Agar serving down ho jaye, to business ruk jata hai.

Serving intimidating kyun lagti hai?

  1. Aisa lagta hai ki pehle deep training knowledge chahiye.
  2. Tutorial se world-class system tak ka koi clear learning path nahi tha.
  3. Frameworks, libraries aur vendors bahut zyada hain — choose karna mushkil hai.

Ye kitab inhi teen problems ka jawab hai.

Serving kis par focus karti hai

  • Deployment — hardware choice, model ko training ya open source se available karna.
  • Scalability aur availability — hazaaron se lakhon requests, consistent experience.
  • Latency — real-time cases ke liye milliseconds me jawab.
  • Monitoring — performance, data drift, system health.
  • Versioning — clients ko disturb kiye bina updates aur rollbacks.
  • Security — sensitive data ki hifazat, access control.
  • Cost-to-serve — kitab kehti hai ye sabse decisive factor hai.

Serving engineers aksar models ko black box ki tarah treat karte hain, kyunki vLLM aur TensorRT-LLM jaise frameworks execution ko abstract kar dete hain. Serving systems engineering, infrastructure design aur end-to-end performance optimization hai — naye learning algorithms invent karna nahi. Ek note ye bhi kehta hai ki LLM/Transformer ki knowledge LLM serving ke liye critical hai, kyunki serving ki har advance LLM execution ke kisi bottleneck ko target karti hai.

03.2Ch 1 — Model Serving ka Introduction

Model ki anatomy — 3 hisse

Ek model sirf data file nahi hai — ye ek executable program hai jisme execution logic aur metadata hota hai. Kitab model ko teen hisson me baantti hai.

(a) Model data

Weights, biases aur configuration — embeddings, classification ke liye label classes, max_batch_size, input/output tensors.

(b) Model architecture

Structure — layers ke types aur number, connections, operations, input kaise process hota hai.

(c) Model execution code

Architecture ko serving framework me initialise karta hai, weights load karta hai, predictions chalata hai.

Worked PyTorch example

Kitab PyTorch ke “Saving and Loading Models” tutorial se ek example deti hai. Architecture class TheModelClass (nn.Module) me ye layers hain: conv1 Conv2d(3,6,5), MaxPool2d(2,2), conv2 Conv2d(6,16,5), fc1 Linear(16*5*5,120), fc2 Linear(120,84), fc3 Linear(84,10). Forward pass me ReLU + pooling lagta hai, phir fully connected layers.

# weights save karo — sirf state dict
torch.save(model.state_dict(), "model_weights.pt")

# execution code: class banao, weights load karo
model = TheModelClass()
model.load_state_dict(torch.load("model_weights.pt", weights_only=True))
model.eval()
output = model(inputs)

Recommendation: architecture aur data ko alag-alag files me rakho — ek hi torch.save(model, ...) file me nahi. Isse partial loading kaam karti hai jab architecture thoda badle — non-matching keys skip ho sakti hain — jo fine-tuning, layers add karna aur scratch se retrain kiye bina incremental updates me madad karta hai.

Serving ke liye model files par jo optimizations lagte hain — khaas taur par LLMs ke liye — wo Ch. 6–7 me aate hain.

03.3Ch 1 — Model Serving ka Introduction

Model lifecycle — 6 stages

Model ki zindagi ek cycle hai — training se serving tak, aur phir wapas improvement ke through training tak. Serving is cycle ka stage 5 hai, lekin baaki stages ko samjhe bina serving samajh nahi aayegi.

Stage 1 — Data collection

Raw data users, sensors, logs, documents aur third parties se aata hai — phir clean, label aur curate kiya jata hai.

Stage 2 — Training aur fine-tuning

Foundation models pretrain hote hain, phir domain ke liye fine-tune hote hain.

Stage 3 — Evaluation

Offline metrics — accuracy, loss, task benchmarks — se production readiness check hoti hai.

Stage 4 — Deployment

Packaging, versioning, testing, integration.

Stage 5 — Serving

Is kitab ka focus — deployed model ko APIs/services ke through accessible banana, real-time ya large-scale inference ke liye.

Stage 6 — Optimization aur iteration

Production me performance, reliability aur cost ko continuously improve karna — production feedback se aage fine-tuning/retraining hoti hai aur cycle dobara shuru hoti hai.

Yaad rakho: training aur serving ke constraints, goals aur engineering challenges alag hain. Jo training ke liye sahi hai, wo serving ke liye sahi ho — ye zaroori nahi.

03.5Ch 1 — Model Serving ka Introduction

Serving kyun seekhein — 3 sawal, 3 jawab

Lekhakon ko aksar teen sawal poochhe jate hain. Har sawal ka jawab kitab deti hai — aur har jawab me ek trade-off chhupa hai.

Q1: “Hum pehle se AWS SageMaker/Bedrock aur Azure ML use karte hain, apna khud ka kyun banayein?”

Cloud hardware management, patching aur quick proof-of-concept ke liye achha hai — lekhakon ne AWS aur Azure par bahut se solutions banaye hain. Lekin:

  • Choose karne ke liye bahut saare products/features hain, aur existing infrastructure aur client apps ke saath integration ke liye engineering chahiye.
  • Vendor services ko bhi apne use case ke liye optimize karna padta hai.
  • SageMaker me hi single-model aur multi-model endpoints ke alag customization, trade-offs aur costs hain — design samjhe bina sub-optimal choose karna aasan hai, aur phir zyada paise lagte hain ya flexibility kho jati hai.

Q2: “Foundation LLMs hi kaafi hain — bas OpenAI/DeepSeek/Anthropic ko call karte hain, apna stack kyun maintain karein?”

Cost: business aksar har kaam ke liye ek LLM use nahi karte — jahan ho sake chhote, saste models use karte hain aur hard requests ke liye LLMs. Open-source LLM jaise DeepSeek ko AWS EC2 instance par chalana managed service jaise SageMaker se 30%–60% sasta ho sakta hai, aur EC2 instance reserve karne se lagbhag 70% discount mil sakta hai.

Typical chatbot: ek chhota intent-classification model triage ke liye, ek embedding model questions encode karke answers search karne ke liye, aur ek LLM requests ko backend API calls me todne aur friendly replies banane ke liye.

Data privacy/security: sensitive ya proprietary data in-house solution force kar sakta hai.

Fine-tuned models: zyada foundation vendors tumhara fine-tuned model serve nahi karte, ya bahut zyada charge karte hain — 2025 ki shuruaat tak, ek vendor apne fine-tuned model ko serve karne ke liye 50% zyada charge karta tha. Chhote models zyada powerful ho rahe hain aur fine-tuning, tez inference, zyada consistent results aur kam cost-to-serve dete hain.

Q3: “Apna stack banana mehenga hai, ye worth kyun hai?”

Cost reduction ek permanent effort hai — outsourcing hamesha business goals ko meet nahi karega, jaise-jaise technology aur infrastructure badalte hain. Do scenarios:

  • (a) Series A education startup — homework grade karna aur study plans banana. Shuruaat me managed provider (ek vendor LLM) se model validate karo; phir jab usage aur cost unsustainable badhe, to open-source LLMs, optimized frameworks aur tuned inference par jao.
  • (b) CRM company — emails, Slack, notes, voice calls, transcriptions aur structured CRM data par LLMs. High inference volume plus sensitive customer data — full outsourcing security risk hai aur cost escalator hai. Isliye in-house stack own karke optimize karna cost per inference kam kar sakta hai, GDPR/HIPAA meet kar sakta hai, aur latency par behtar control deta hai.

Counterweight bhi hai: in-house stack ke liye badi up-front hardware capital aur ongoing specialist engineers chahiye. Decision security/privacy, project maturity, expected scale aur operational complexity sustain karne ki ability par depend karta hai. Koi one-size-fits-all ya “eternal” architecture nahi hai — lekhakon ne fully outsourced (vendor LLM), self-managed on-premises (TensorFlow Serving, TorchServe, NVIDIA Triton, Ray), fully managed cloud (AWS Bedrock) aur deeply customized vendor solutions (AWS SageMaker) — sab use kiye hain. Goal ye hai ki fundamentals itne achhe se samjho ki nayi technology ko jaldi adopt kar sako — kisi framework ya vendor me lock hone se nahi.

Naively deploy kiya hua LLM demo me kaam kar sakta hai, lekin real load par fail ho jata hai — latency badhti hai, throughput hardware capacity se bahut neeche plateau kar jata hai, cost usage ke saath linearly ya usse bhi tezi se badhti hai, aur pilot economically ya operationally infeasible ho jata hai.

Optimization ka matlab: latency, throughput aur resource utilization improve karna — aur ye poochhna: kya hum saste hardware ka use kar sakte hain? Kya upgrade kiye bina throughput/latency improve kar sakte hain? Kya vendor ki LLM service ko poori tarah use kar rahe hain?

Example — vLLM se throughput 24x tak

vLLM UC Berkeley SkyLab ka high-throughput, low-latency LLM serving engine hai. Kitab iska example deti hai ki optimization se kya farq padta hai.

Sample launch

03.8Ch 1 — Model Serving ka Introduction

On-device (edge) serving

On-device serving me model user-side devices par chalta hai — smartphones, drones, robots, cameras, VR headsets — data jahan generate hota hai, wahin process hota hai, bina constant internet ke.

4 benefits

  • Cost-effective — constant cloud API fees nahi (example: smart speaker locally voice recognition karta hai).
  • Efficient — tez response, AI-optimized hardware par behtar power efficiency (example: mobile photo enhancement real time me).
  • Private — data device se kabhi bahar nahi jata (example: health/biometric data).
  • Personalised — user ke liye continuous on-device fine-tuning (example: keyboard typing style seekhta hai bina keystrokes upload kiye).

Model runtime

Specialised framework jo models ko hardware aur operating systems par efficiently execute karta hai — execution complexity abstract karta hai aur hardware-specific optimization/acceleration deta hai. Kai runtimes delegates support karte hain — compute-heavy operations CPU se GPU ya doosre accelerator par offload karte hain. Popular runtimes: LiteRT, ONNX Runtime (ORT), Core ML.

Model wrapper

Developer-written code jo application logic ko inference interfaces expose karta hai — preprocessing, model ko runtime me load karna, execute karna aur postprocessing ko encapsulate karta hai. Flow: app logic wrapper se model run karne ko kehta hai → wrapper data convert karke runtime ko call karta hai → runtime local hardware par execute karta hai.

Deployment workflow (Figure 1-4b)

  1. Train karo.
  2. Model ko runtime ke format me convert/compile karo — example: ai_edge_torch.convert(resnet18.eval(), sample_input) se LiteRT ke liye .tflite file banti hai.
  3. Target device par numerical accuracy validate karo — wahi inputs training server aur device dono par compare karke.
  4. Business requirements ke against performance measure karo.
  5. Model ko app install/update me package karo.

Qualcomm AI Hub jaise tools compilation, optimization aur validation ko automate karte hain.

Kab on-device sahi hai

  • Privacy-first workloads — biometrics, health, sensitive interactions.
  • Ultra-low-latency — gesture recognition, robotics control, AR/VR, real-time audio.
  • Disconnected/intermittent environments — industrial equipment, remote sensors, vehicles, drones.

03.9Ch 1 — Model Serving ka Introduction

Single-model service

Single-model service classic, sabse widely used cloud pattern hai (Figure 1-5): har model aur har version ek dedicated web service hota hai jo HTTP ya gRPC par prediction API expose karta hai. Front API requests ko backend workers/containers par route karta hai jo model execute karte hain.

Containerisation modern serving ki neev hai: container application ko uske dependencies, libraries aur configuration ke saath package karta hai taaki wo har jagah consistently chale. Docker sabse popular technology hai aur kitab bhar me use hoti hai.

Routing — round-robin kaafi nahi hai

Plain round-robin (c1, c2, c3 baari-baari) simple hai lekin ignore karta hai ki requests ki cost alag hoti hai — 5,000-token wali LLM request 100-token wali se bahut zyada time leti hai, aur high-resolution image chhoti image se zyada mehenga hai. Isliye ek container busy ho sakta hai jab agli request usi par route ho. Behtar routing choices:

  • Weighted round robin — bade servers ko zyada requests.
  • Least connections — sabse kam active connections wala container.
  • Least response time — sabse kam response time wala.
  • Dynamic load balancing — CPU, GPU, memory ya queue length dekh kar.

Scaling

  • Horizontal scaling / scaling out — instances add karo; autoscaling (jaise Kubernetes Horizontal Pod Autoscaling) CPU, memory, latency ya active-request thresholds cross hone par instances add karta hai.
  • Vertical scaling / scaling up — zyada powerful GPUs aur distributed serving, jab ek machine par model na aaye (example: GPT-4, Llama-2-70B).

Example command: Llama-2-13b ko 4 GPUs par vLLM se serve karna, tensor-parallel-size 4 ke saath. Recommendation: intra-node serving (ek machine par multiple GPUs) ko inter-node serving (multiple machines) par prefer karo — inter-node me network overhead, latency aur synchronization complexity badh jati hai.

Single-model default start kyun hai

  • Best performance — no resource contention, kam latency.
  • Har model independently scale hota hai.
  • Deployment aur debugging simpler — isolated logs, metrics, updates.
  • Reliability — ek model crash hone se doosre affect nahi hote.
  • Hardware ko per-model optimize kar sakte ho — cost control ke liye.

Kamzori: resource efficiency aur cost. Example: ek agent platform jisme 100 customers hain aur har customer 10 models deploy karta hai — 1,000 alag services chahiye honge. Maintain, patch, deploy aur monitor karna overwhelming ho jata hai, aur kai models kabhi use hi nahi hote — compute waste hota hai.

Multi-model service

Multi-model service ek container me kai models co-host karta hai — GPU/CPU aur memory share karte hue, traffic ke hisab se models ko dynamically load aur unload karta hai. Ideal tab hai jab kai models efficiently serve karne hon bina sabko ek saath memory me rakhe.

Inference backend

Kai model types ko black-box tareeke se unified prediction API ke through handle karta hai — andar har model type ke liye ek backend hota hai (TensorFlow, ONNX, PyTorch, etc.). Practice me ye aksar NVIDIA Triton Inference Server hota hai, jo disk aur memory ki limit tak koi bhi number ya mix of models manage kar sakta hai, aur TensorRT, TensorFlow GraphDef/SavedModel, ONNX, PyTorch, Caffe2 NetDef aur zyada par unified API deta hai.

Model cache management

Model ko storage se backend me load karta hai aur overload rokta hai — least-recently-used (LRU) cache rakh kar, resources zyada hone par sabse kam use hue models ko unload kar deta hai.

On-demand workflow — model A ke liye request

  1. Agar A pehle se loaded hai, to request backend ko forward karo.
  2. Agar nahi hai, to storage se download karke load karo, phir request forward karo.
  3. Agar memory/disk threshold se upar hai (example: 80% memory usage), to cache me sabse kam use hua model dhoondho, use unload karo aur cache aur disk se hata do.

Routing aur autoscaling problems (Figure 1-8)

  • (a) Us container par route karo jisme model pehle se loaded hai — nahi to cold start (model load hone ka wait) ya model swapping ka kharcha.
  • (b) Per-model scaling — “hot” models ko cold models se zyada instances chahiye.

Solution (Figure 1-9)

Model metadata me ek replica attribute add karo (us model ke kitne instances host karne hain) aur routing layer me ek route map (Model ↔ hosts) rakho. Example: model A jiska replica count 2 hai, containers C1 aur C3 par host hota hai, aur aage ki A requests C1 aur C3 par evenly route hoti hain. Router traffic ke hisab se replica count real time me adjust karta hai aur naye replica ke liye container choose karta hai — ye ek bin-packing problem hai.

Kab multi-model zaroori hai, kab mushkil

  • Zaroori: kai models ke liye sabse cost-efficient tareeka hai.
  • Mushkil: models ek GPU me fit hone ke liye bahut bade hon (share karne ki jagah nahi, frequent unloading, cold-start latency); individual models jinhe high traffic aur low latency chahiye aur loaded rehna hai (single-model behtar hai); alag security policies wale models; high operational complexity (cache management, per-model routing/scaling, compatibility, dependency conflicts).

Single- aur multi-model complementary hain — platforms dono ko combine karte hain.

LLM kaise kaam karta hai

Pipeline — prompt se token tak

Kitab ka example prompt hai: “Write a short introduction about the US capital city,”

  1. Tokenisation — text tokens (subword pieces) me toot jata hai.
  2. Embeddings — har token ID ek dense vector ban jata hai jo meaning aur context capture karta hai.
  3. Transformer stack — sequence process hoti hai (self-attention plus feed-forward layers, positional information ke saath).
  4. Output layer — agla token predict karta hai.
  5. Decoding (sampling) — agla token choose karta hai.
  6. Process autoregressively repeat hoti hai.

Prompt ke tokens: ['Write',' a',' short',' introduction',' about',' the',' US',' capital',' city',','] — aur unke IDs: [1100, 10930, 261, 4022, 22575, 1078, 290, 2952, 9029, 5030, 693].

08.1Ch 6 — Essential Optimization

Quantization — kam bits, kam memory

Quantization matlab weights (aur optionally activations/KV cache) ko kam bits me represent karna — model kam memory use karta hai, memory se kam data padhta hai, aur tez chal sakta hai — chhoti accuracy loss ki keemat par, rounding ki wajah se.

Precisions

PrecisionBytes per parameterNote
FP324 bytesFull precision — training default
FP16 / BF162 bytesServing ka common baseline
FP81 byteFloating-point, exponent ke saath — LLM weights/activations ki wide dynamic range ke liye behtar; H100-class hardware par supported
INT81 byteInteger — purane hardware par widely supported
INT40.5 bytesMemory phir aadhi — accuracy loss ka risk zyada

INT8 vs FP8: INT8 integer hai, purane hardware par widely supported; FP8 floating-point hai, exponent ke saath, LLM weights aur activations ki wide dynamic range ke liye behtar hai, aur H100-class hardware par supported hai. INT4 INT8 se memory phir aadhi kar deta hai, lekin accuracy loss ka risk zyada hota hai.

Symmetric vs asymmetric quantization

  • Symmetric — ek hi scale, zero point zero (simpler, symmetric distributions ke liye achha).
  • Asymmetric — scale plus zero point (skewed distributions ke liye behtar, jaise activations).

Granularity — scale kitne bade hisse par lagta hai

  • Per-tensor — poore tensor ke liye ek scale (sabse coarse, sabse tez, sabse kam accurate).
  • Per-channel — har channel ke liye ek scale (weights ke liye behtar).
  • Per-token — har token ke liye ek scale (activations ke liye behtar).
  • Per-group — weights ka ek group ek scale share karta hai (achha middle ground — example: group size 128).

QAT vs PTQ

  • Quantization-aware training (QAT) — training/fine-tuning ke dauraan quantization simulate karta hai, taaki model adapt kar le — best accuracy, lekin training data aur time chahiye.
  • Post-training quantization (PTQ) — trained model ko bina retraining ke quantize karta hai, calibration dataset use karke — practical default hai.

Weight-only vs weight-and-activation

  • Weight-only — sirf weights quantize hote hain (memory aur bandwidth bachta hai, activations FP16 me rehte hain). LLM serving ke liye common choice hai, kyunki decode weights par memory-bound hota hai.
  • Weight-and-activation — dono quantize hote hain (compute bhi bachta hai, lekin activations quantize karna mushkil hai aur accuracy zyada kho sakti hai).

Model weight quantization aur KV-cache quantization alag se treat hote hain: KV-cache quantization (jaise FP8 ya INT8 K aur V ke liye) wo memory bachata hai jo context length ke saath badhti hai.

Batching aur scheduling

Batching aur scheduling se GPU kabhi idle nahi rehta — aur har request apni speed se aage badhti hai.

  • Static batching — fixed batch, full hone ka wait karo (simple, time waste hota hai jab requests uneven aayein).
  • Dynamic batching — pichla batch khatam hote hi jo wait kar raha hai, uska batch banao.
  • Continuous batching — jaise hi slot khali ho, naya request admit karo (production standard, Ch. 2 se).
  • Chunked prefill — lambe prompt ka prefill chunks me baanto aur decode steps ke beech interleave karo, taaki lamba prompt doosri requests ko block na kare (chunk size jaise 512 ya 1,024 tokens typical hai).

  • Sequence scheduling aur preemption — KV cache bhar jaye to low-priority sequence preempt karo (swap out karo ya baad me recompute karo).
  • Priority scheduling — urgent requests pehle.
  • Fair scheduling — starvation roko, har user/class ko fair share do.

Parallelism — data, tensor, pipeline, expert

Parallelism ka core trade-off: model parallelism bada model fit karata hai aur per-token latency kam karta hai; data parallelism total throughput badhata hai.

  • Data parallelism — poora model kai GPUs par replicate karo, requests baanto (throughput ke liye best; ek GPU par na fit hone wale model ki koi madad nahi).
  • Tensor parallelism — har layer ki weight matrices GPUs par baanto (jaise tensor-parallel-size 2 ya 4), har layer par communication hoti hai (bade model ki latency ke liye best; NVLink jaise tez intra-node links chahiye).
  • Pipeline parallelism — layers GPUs par baanto, alag stages alag micro-batches process karte hain (throughput ke liye achha; pipeline bubbles aur latency add hoti hai).
  • Expert parallelism — mixture-of-experts model me alag experts alag GPUs par rakho.
  • Sequence parallelism — sequence dimension baanto.
  • Hybrid parallelism — upar wale combine karo (jaise node ke andar tensor parallelism, nodes ke beech pipeline parallelism, replicas par data parallelism).

Communication overhead (all-reduce, all-gather, point-to-point) parallelism ki cost hai — isliye intra-node ko inter-node par prefer kiya jata hai.

Memory optimization ka matlab hai: kam memory me zyada kaam, aur fragmentation se bachna.

  • Activation memory / checkpointing — gradient checkpointing recomputation ke badle memory bachata hai, jab prefill ke dauraan activations bade hon.

Speculative decoding

Speculative decoding me ek chhota, tez draft model ek saath kai tokens propose karta hai, aur bada target model un sab ko ek forward pass me verify karta hai — jo tokens match karte hain, wo accept hote hain, aur pehla mismatch correct ho jata hai.

Agar draft aksar sahi ho, to har bade-model pass me kai tokens bante hain — latency sharply gir jati hai.

Key choices

  • Draft model selection — chhota, tez, target ke saath well-aligned (jaise 7B target ke liye 0.5B draft).
  • Token-tree verification — sirf line nahi, candidate continuations ka tree propose karo aur ek saath verify karo — har pass me zyada accepted tokens.

Speculative decoding vLLM me

Draft-model configuration se enable karo, speculative tokens ki sankhya set karo (jaise 4–5), aur acceptance rate measure karo. Chapter ki guidance: high acceptance rate (50% se well upar) net win ke liye zaroori hai — poorly matched draft speculation ke bina se slow bhi ho sakta hai.

Interview FAQs — LLM Serving and Optimization

36 sawal-jawab jo aaj ke interviews me is kitab ke topics par poochhe jate hain. Har jawab kitab ke content par based hai.

Q1Model serving kya hai aur ye training se kaise alag hai?

Model serving matlab trained model ko users aur applications ke liye accessible banana — APIs ya web services ke through — taaki wo naye data par predictions de sake. Training model ko seekhne ke liye hoti hai — loss minimize karke parameters update karna, backpropagation ke saath. Serving sirf forward propagation karti hai — koi backpropagation ya weight updates nahi. Training high throughput aur bade batches prefer karti hai, serving low latency per request prefer karti hai. Dono ke constraints, goals aur engineering challenges alag hain.

Q2LLM serving traditional ML serving se kyun mushkil hai?

LLM serving me inputs aur outputs variable-length sequences hote hain, latency per-token hoti hai na ki per-request, memory sequence length ke saath badhti hai KV cache ki wajah se, aur throughput tokens per second me measure hoti hai. Sabse badi mushkil autoregressive generation hai — model ek token at a time generate karta hai, aur har token ke liye poora model padhna padta hai. Isliye LLM serving ke do alag phases hote hain — prefill aur decode — aur dono ko alag se optimize karna padta hai.

Q3Prefill aur decode me kya farq hai aur ye kyun matter karta hai?

Prefill phase me model poora prompt ek saath process karta hai — ye compute-heavy aur parallelizable hai, aur TTFT (time to first token) determine karta hai. Decode phase me model ek-ek token generate karta hai — har token ke liye poora model padhna padta hai, isliye ye memory-bandwidth-bound aur sequential hai, aur inter-token latency determine karta hai. Ye split isliye matter karta hai kyunki optimizations dono phases ko alag tareeke se target karte hain — jaise chunked prefill prefill ke liye aur quantization decode ke liye.

Q4TTFT aur TPOT kya hain aur inka user experience par kya asar hai?

TTFT (time to first token) wo time hai jo user ko pehla token dikhne me lagta hai — isse perceived latency decide hoti hai. TPOT (time per output token) har agle token ka time hai — isse streaming ki speed decide hoti hai. Formula hai: end-to-end latency = TTFT + TPOT × (N − 1), jahan N output tokens hain. Streaming on karne se user ko pehla token jaldi dikhta hai, to perceived latency kam lagti hai, chahe total time wahi ho. Chat applications me dono metrics monitor karni chahiye.

Q5KV cache kya hai aur ye itni memory kyun khata hai?

KV cache attention ke key aur value vectors ko store karta hai, taaki har naya token generate karte samay purane tokens ko dobara compute na karna pade. Isse decode tez hota hai — Qwen2.5-0.5B par 100 tokens 9.12 seconds se 3.14 seconds me aa gaye, lagbhag 2.9 guna tez. Lekin memory cost badhti hai — cache size batch size, sequence length, layers, heads aur hidden size ke saath linearly badhti hai. Lambi conversations ya bade batch me KV cache hi bottleneck ban jata hai. Solutions hain quantization, PagedAttention aur cache eviction policies.

Q6Quantization kya hai aur isse quality par kya asar padta hai?

Quantization model ke weights ko kam precision me store karna hai — jaise FP16 se INT8 ya INT4. Isse memory kam hoti hai aur inference tez hota hai, kyunki decode me kam bytes padhne padte hain. Quality loss aksar chhota hota hai agar sahi technique use karo — chapter ke tests me INT8/FP8 near-baseline quality dete hain lagbhag aadhi memory ke saath. INT4 sabse chhota size deta hai lekin quality drop bada ho sakta hai. Har model har quantization ko equally handle nahi karta — apne task par evaluate karke decide karo.

Q7Weight-only quantization aur weight-and-activation quantization me kya farq hai?

Weight-only quantization me sirf weights quantize hote hain — activations FP16 me rehte hain. Ye LLM serving ke liye common choice hai, kyunki decode weights par memory-bound hota hai — aadhe bytes padhne se latency girti hai. Weight-and-activation quantization me dono quantize hote hain — compute bhi bachta hai, lekin activations quantize karna mushkil hai aur accuracy zyada kho sakti hai. Chapter ke mutabiq pehle weight-only try karo, phir zaroorat ho to weight-and-activation.

Q8QAT aur PTQ me kya farq hai — kab kaunsa use karein?

QAT (quantization-aware training) me training ya fine-tuning ke dauraan quantization simulate ki jati hai, taaki model adapt kar le — best accuracy milti hai, lekin training data aur time chahiye. PTQ (post-training quantization) me trained model ko bina retraining ke quantize kiya jata hai, calibration dataset use karke — ye practical default hai. Zyada cases me PTQ kaafi hota hai; jab accuracy critical ho aur training budget ho, tab QAT socho.

Q9Pruning kya hai — unstructured aur structured pruning me kya farq hai?

Pruning matlab wo weights ya structures hata dena jo sabse kam contribute karte hain. Unstructured pruning me individual weights kahin se bhi hataye jate hain — sparse matrix banta hai, jise tez chalane ke liye sparse kernels chahiye. Structured pruning me poore channels, heads, layers ya neurons hataye jate hain — chhota dense model banta hai jo ordinary hardware par tez chalta hai. Criteria hote hain magnitude-based (sabse chhote weights), gradient-based, Hessian-based aur activation-based. Moderate pruning ratio quality ko baseline ke kareeb rakhta hai.

Q10Distillation kaise kaam karta hai — logit-based, feature-based aur relation-based me kya farq hai?

Distillation me ek chhota student model bade teacher model ki nakal karke train hota hai. Logit-based distillation me student teacher ki output probabilities se seekhta hai — soft probabilities bhi, jo tokens ke beech similarity batati hain — temperature aur KL-divergence loss ke saath. Feature-based me student teacher ki intermediate representations (hidden states, attention maps) match karta hai. Relation-based me student examples ya tokens ke beech ke relationships seekhta hai. Data distillation me teacher student ke liye training data generate ya label karta hai.

Q11Quantization, pruning aur distillation ko kis order me apply karna chahiye?

Chapter ka recommended order hai: pehle distill karo, phir prune karo, phir quantize karo. Har step ke baad re-evaluation zaroori hai, kyunki errors compound hote hain. Kab kaunsa use karein: quantization pehle — sabse aasan, sabse bada immediate win, kam risk. Pruning jab model structurally chhota hona ho ya quantization akela kaafi na ho. Distillation jab specific task ke liye bahut chhota model chahiye aur teacher outputs available hon. Teeno ko blindly apply mat karo — har step ke baad quality measure karo.

Q12Continuous batching static batching se behtar kyun hai?

Static batching me poora batch khatam hone ka wait karna padta hai, phir naye requests admit hote hain — GPU idle rehta hai jab requests uneven aayein. Continuous batching me jaise hi ek request khatam hoti hai, uski jagah nayi request running batch me aa jati hai — GPU kabhi idle nahi rehta. 2023 ke ek study ke mutabiq continuous batching se 23 guna tak zyada throughput mil sakta hai. Chapter ke example me 4 prompts batched 1.06 seconds me chale, jabki ek-ek karke 2.39 seconds lage — 2.2 guna speedup. Production serving me continuous batching standard hai.

Q13PagedAttention kya hai aur ye KV cache ki problem kaise solve karta hai?

PagedAttention vLLM ka tareeka hai KV cache ko fixed-size blocks (pages) me baantne ka — memory tabhi allocate hoti hai jab zaroorat ho, aur fragmentation avoid hota hai. Har sequence ke liye ek block table hoti hai, aur shared blocks ke liye copy-on-write hota hai. Isse GPU memory efficiently use hoti hai — bina PagedAttention ke KV cache ke liye bada contiguous chunk chahiye hota hai, jo waste karta hai. PagedAttention hi wajah hai ki vLLM Hugging Face se 17 guna tez ho sakta hai wahi model aur wahi task par.

Q14RadixAttention kya hai aur SGLang iska use kyun karta hai?

RadixAttention SGLang ka KV cache organisation hai — ek radix tree, jo token sequences se keyed hota hai. Shared prefixes ek baar store hote hain aur kai requests me reuse hote hain — jaise common system prompt, multi-turn chat history ya RAG me common documents. Isse shared context wale workloads me throughput bahut badhta hai. SGLang isliye best hai jab kai requests ek prefix share karein — agents, multi-turn chat aur few-shot prompts me.

Q15Speculative decoding kaise inference ko tez karta hai?

Speculative decoding me ek chhota draft model pehle kuch tokens guess karta hai, phir bada target model unhe ek saath verify karta hai. Jo tokens sahi hote hain, wo accept ho jate hain — isse ek step me multiple tokens generate hote hain. Isse 2–3 guna speedup mil sakta hai bina quality badle, kyunki final output bada model hi decide karta hai. Key choices hain draft model selection (chhota, tez, target ke saath well-aligned) aur token-tree verification. Acceptance rate 50% se well upar honi chahiye — poorly matched draft speculation ke bina se slow bhi ho sakta hai.

Q16Chunked prefill kya hai aur ye kab madad karta hai?

Chunked prefill me lambe prompt ka prefill chunks me toda jata hai — jaise 512 ya 1,024 tokens ke chunks — aur decode steps ke beech interleave kiya jata hai. Isse lamba prompt doosri requests ko block nahi karta. Bina chunked prefill ke, ek 10,000-token prompt ka prefill chalte samay baaki requests ko wait karna padta hai. Ye technique khaas taur par useful hai jab prompts ki length bahut vary karti ho — long-document RAG ya long-context chat me.

Q17Prefix caching kya hai aur isse TTFT kaise kam hota hai?

Prefix caching me shared prompt prefix ka KV cache reuse hota hai — jaise common system prompt ya wahi document. Jab doosri request wahi prefix lekar aati hai, to prefill dobara nahi hota — cached KV use hota hai — isliye TTFT sharply gir jata hai. Chapter ke Ch. 9 ke worked example me prefix caching se repeated-prefix prompts ka TTFT bahut kam hua aur maximum batch size badha. Ye tab sabse zyada madad karta hai jab prompts system prompt ya document share karte hain.

Q18Tensor parallelism aur data parallelism me kya farq hai?

Data parallelism me poora model kai GPUs par replicate hota hai aur requests baanti jati hain — throughput ke liye best, lekin ek GPU par na fit hone wale model ki koi madad nahi. Tensor parallelism me har layer ki weight matrices GPUs par baanti jati hain — bade model ki latency ke liye best, lekin har layer par communication hoti hai, isliye NVLink jaise tez intra-node links chahiye. Pipeline parallelism me layers GPUs par baante jate hain — throughput ke liye achha, lekin pipeline bubbles aur latency add hoti hai. Hybrid parallelism inhe combine karta hai.

Q19Disaggregated prefill aur decode kya hai?

Disaggregated prefill/decode me prefill aur decode ke liye alag GPU pools hote hain — KV cache prefill GPUs se decode GPUs ko transfer hota hai. Isse do phases interfere nahi karte: lamba prefill decode ko block nahi karta, aur decode ki memory-bandwidth needs prefill ko slow nahi karti. Cost hai KV cache transfer ka. Ye deployment pattern ab standard banta ja raha hai, khaas taur par jab TTFT aur inter-token latency dono ke alag SLOs hon.

Q20FlashAttention kya karta hai aur ye kyun fast hai?

FlashAttention attention ko tiles me compute karta hai, bina poora N×N attention matrix materialise kiye. Isse memory sequence length ke saath linearly badhti hai, quadratically nahi. Lambi sequences par ye bahut bada farq padta hai — bina FlashAttention ke 32k-token context ka attention matrix hi GPU memory kha jata hai. Ye memory-efficient attention ka sabse important example hai aur modern serving stacks ka standard hissa hai.

Q21vLLM, TensorRT-LLM, SGLang aur llama.cpp me se kaunsa kab choose karein?

vLLM best general-purpose choice hai GPU serving ke liye — PagedAttention, continuous batching, prefix caching, quantization, speculative decoding, LoRA serving — sab kuch. TensorRT-LLM NVIDIA GPUs par sabse tez hai jab compile time acceptable ho — model ko optimized engine me compile kiya jata hai. SGLang best hai jab kai requests ek prefix share karein — agents, multi-turn chat, common-document RAG. llama.cpp best hai CPU, edge aur local use ke liye — laptop ya phone-class device par. Decision framework: workload se shuru karo, must-have features list karo, final 2–3 ko real workload par benchmark karo, tabhi commit karo.

Q22Single-model aur multi-model serving me kya farq hai?

Single-model service me har model aur har version ek dedicated web service hota hai — best performance, no resource contention, kam latency, har model independently scale hota hai, debugging simple hai. Kamzori hai cost — 100 customers × 10 models matlab 1,000 alag services. Multi-model service me ek container me kai models co-host hote hain, GPU/CPU aur memory share karte hue, traffic ke hisab se dynamically load/unload hote hain — kai models ke liye sabse cost-efficient. Mushkil hoti hai jab models bahut bade hon, ya individual models ko high traffic aur low latency chahiye, ya alag security policies hon. Dono complementary hain — platforms dono combine karte hain.

Q23Multi-model serving me cold start kya hai aur isse kaise bachein?

Cold start tab hota hai jab request us model ke liye aati hai jo container me loaded nahi hai — model ko pehle storage se download aur load karna padta hai, jisme time lagta hai. Isse bachne ke tareeke: request ko us container par route karo jisme model pehle se loaded hai; hot models ke liye replica count badhao aur route map rakho; LRU cache me hot models ko loaded rakho; aur model load time ko measure karke SLOs me include karo. Chapter ka solution hai model metadata me replica attribute aur routing layer me route map (Model ↔ hosts).

Q24RAG application ke liye serving design me kya alag hota hai?

RAG me LLM ke alawa retrieval service aur vector store bhi serve karne hote hain. Design me chunk size (lagbhag 1,000 tokens), embedding model (jaise text-embedding-3-small), generation model (jaise gpt-4.1-nano), top-k retrieval aur prompt template — ye sab matter karte hain. Case study dikhata hai ki retrieval quality, chunking aur prompt inference engine jitne hi important hain. Context window badhne se (jaise 1-million-token context) RAG aur poora document prompt me stuff karne ke beech ka choice real decision ban gaya hai. CAG ek alternative hai — knowledge base ko ek baar KV cache me pre-load karo.

Q25CAG kya hai aur ye RAG se kab sasta padta hai?

CAG (Cache-Augmented Generation) me knowledge base ko ek baar KV cache me pre-load kiya jata hai, taaki repeated questions par har baar retrieval ya re-prefill ka kharcha na ho. Chapter ke numbers: CAG $0.007 per query vs RAG $0.013 per query — lagbhag aadhi cost. CAG tab jeet ta hai jab wahi knowledge base kai baar reuse ho aur KV cache me fit ho. RAG tab jeet ta hai jab knowledge base bada ho, badalta ho, ya rarely reuse ho.

Q26SLO kya hai aur serving me iska kya role hai?

SLO (service-level objective) wo target hai jo serving system ko meet karna hai — jaise p95/p99 latency targets, availability aur error rate. Optimize karne se pehle SLOs define karo aur unke against measure karo. Example: agar SLO hai ki p95 end-to-end latency 800 ms se kam ho, to batch size ka operating point wahi hai jahan throughput near-maximum ho lekin latency SLO ke andar rahe. Bina SLO ke optimization ka koi target nahi hota — tum hamesha aur tez karne ke peeche bhaagte rahoge.

Q27End-to-end latency ka formula kya hai?

End-to-end latency = TTFT + ITL × (N − 1), jahan N output tokens ki sankhya hai, TTFT time to first token hai aur ITL inter-token latency (TPOT) hai. Example: TTFT 104 ms, TPOT 25 ms, N = 100 tokens ho to end-to-end latency = 104 + 25 × 99 = 2,579 ms. Throughput tokens per second aur requests per second average output length ke through related hain. Ye formula isliye useful hai kyunki ye batata hai ki latency ka kitna hissa prefill se aur kitna decode se aata hai — aur kaunsi optimization kahan lagegi.

Q28GPU utilisation kam kyun hoti hai aur ise kaise badhayein?

GPU utilisation kam hoti hai jab GPU compute ya memory bandwidth ka poora use na ho — jaise chhote batches, sequential decode, ya prefill/decode interference ki wajah se. Badhane ke tareeke: batching aur continuous batching (GPU ko hamesha kaam do), prefix caching (repeat kaam avoid karo), quantization (kam bytes padho), speculative decoding (har pass me zyada tokens), aur disaggregated prefill/decode (do phases ko alag karo). Lekin utilisation badhane ke chakkar me latency SLO ko kharab mat karo — dono ka balance chahiye.

Q29Kubernetes me LLM serving ko autoscale kaise karte hain?

HorizontalPodAutoscaler (HPA) use karo — chapter ka example YAML deployment ko 3 se 15 replicas tak scale karta hai jab CPU utilisation 70% cross kare. GPU workloads me CPU ke alawa latency, active requests ya queue length par bhi scale kar sakte ho. Autoscaling ke saath rate limiting (Nginx me 50 requests per second, burst 5) aur payload caps (client_max_body_size 8m) bhi lagao, taaki ek abusive client service ko exhaust na kar de. Distributed serving ke liye Ray Serve use kar sakte ho — ek cluster kai models host karke unhe independently scale karta hai.

Q30Model ko 80 GB GPU par fit karne ke liye kya options hain?

Pehle memory nikalo: FP16 me lagbhag 2 bytes per parameter — 7B model 14 GB, 32B model 64 GB, 70B model 140 GB. Agar fit nahi hota to options hain: quantization — INT8 me memory aadhi (70B → 70 GB, fit ho jayega), INT4 me phir aadhi; tensor parallelism — model ko kai GPUs par baanto (jaise Llama-2-13b 4 GPUs par, tensor-parallel-size 4); offloading — KV cache ya weights ka hissa CPU memory par rakho; ya chhota model choose karo — chapter kehta hai chhota model jo good enough ho, aksar sahi choice hota hai. 70B FP16 ek 80 GB GPU par kabhi fit nahi hota.

Q31LoRA serving kya hai aur vLLM isse kaise support karta hai?

LoRA serving matlab ek base model par multiple LoRA adapters serve karna — har adapter ek alag task ya customer ke liye fine-tuned hota hai, lekin base model ek hi rehta hai. Isse memory bachti hai — har adapter ke liye poora model load nahi karna padta. vLLM multiple adapters ko ek base model par serve kar sakta hai. Ye multi-tenant serving ke liye bahut useful hai — jaise 100 customers ke alag-alag fine-tuned adapters ek hi base model par chalana.

Q32On-device serving kab sahi hai aur kab nahi?

On-device serving sahi hai jab privacy-first workload ho (biometrics, health), ultra-low latency chahiye ho (gesture recognition, robotics control, AR/VR), disconnected environment ho (industrial equipment, remote sensors, drones), ya IoT/robotics ho. Nahi sahi hai jab model bahut bada ho (har model fit nahi hota), power consumption zyada ho (real-time video upscaling), frequent updates chahiye hon (har device ko app update chahiye), ya hardware inconsistent ho (Apple Neural Engine ke liye optimize model Snapdragon par achha nahi chalta). Model runtime (LiteRT, ONNX Runtime, Core ML) aur model wrapper — ye do components hote hain.

Q33SageMaker par LLM serve karne ke kitne options hain?

Chapter 6 options compare karta hai: (1) Amazon Bedrock — managed foundation models, jaise Claude 3.5 Sonnet, sabse kam operational work. (2) SageMaker JumpStart — pre-built models, jaise Mistral 7B, quick start ke liye. (3) SageMaker DLC — TorchServe ya LMI container, jaise Llama 3.1 8B tensor-parallel degree 4 ke saath, tuned open-model serving ke liye. (4) BYOC — apna container LMI ke saath. (5) BYOI — apna inference code/image. (6) BYO Infrastructure — EKS/ECS par. Option ko control ki zaroorat se match karo — jitna zyada control chahiye, utna zyada operational kaam.

Q34Chaos testing kya hai aur serving me ye kyun zaroori hai?

Chaos testing matlab deliberate fault injection — jaan-bujh kar failures create karke dekhna ki system recover karta hai ya nahi. Serving me ye zaroori hai kyunki production me failures hote hi hain — GPU crash, network partition, model load failure, traffic spike. Design me retries with backoff, timeouts, circuit breakers, graceful degradation (chhote model par fall back ya cached answer), aur health checks hone chahiye. Chaos testing prove karta hai ki ye sab production se pehle kaam karte hain — nahi to pehli real failure par pata chalega.

Q35Constrained decoding aur structured output me kya farq hai?

Constrained decoding me output ko format follow karne par force kiya jata hai — JSON, grammar ya regex — har step par invalid tokens ko mask out karke. Structured output wahi idea ek feature ke roop me hai — schema ke saath JSON object return karna. Dono ka goal ek hi hai: AI applications me output aksar code ko pass hota hai — JSON, function calls, database queries — aur agar model invalid JSON de to pura system toot jata hai. Constrained decoding sabse reliable hai kyunki invalid output generate hi nahi hota.

Q36LLM serving ka future kahan ja raha hai?

Chapter 5 directions batata hai: agentic AI aur multi-agent systems — multi-step, tool-using, long-running agents jinke liye state, memory aur coordination chahiye; multimodal serving — text, image, audio, video ek model me; edge serving — phones aur robots par chhote models; federated serving — raw data share kiye bina organisations ke beech; sustainable serving — energy per token aur carbon cost. Serving ab core engineering discipline hai — Ch. 1–9 ke fundamentals — measure karna, bottlenecks samajhna, sahi technique choose karna — aage bhi transfer honge, chahe frameworks badal jayein.
