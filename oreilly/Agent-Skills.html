01Preface

Preface

Ye book un logon ke liye hai jinke paas pehle se ek working agent hai — aur ab uska kaam reliable aur repeatable banana hai. Is chapter me book ka maksad, audience aur istemal ka tareeka samjho.

01.1 Kis Ke Liye Hai Ye Book

Ye book pehla agent banane ke liye nahi hai. Ye unke liye hai jinke paas pehle se ek working agent hai aur jo chahte hain ki uska kaam reliable aur repeatable ho — har baar ek jaisa standard, ek jaisi quality.

Audience sirf engineers nahi hain. Non-engineers, managers aur domain experts bhi iske reader hain — kyunki Skill banane ka kaam aksar wahi log karte hain jo kaam ko sabse achhe se jaante hain, chahe wo code likhte hon ya nahi.

Yaad rakhne wali baat: agar tumhara agent abhi tak 'kabhi chalta hai, kabhi nahi' wale mode me hai, to ye book tumhare liye hai.

01.2 Book Kya Cover Karti Hai

Book ka central claim seedha hai: aaj ke agent stack me ek missing layer hai — ye define karne ka tareeka ki experts asal me kaise kaam karte hain. Model powerful hai, tools maujood hain, lekin 'kaam kis tarah se karna hai' ye likha hua kahin nahi hota.

Ye book us gap ko bharti hai — practical, hands-on guidance se, jo real projects se nikli hai. Theory kam, kaam ki cheezein zyada: Skill kaise design karein, kaise banayein, kaise test karein, aur business me kaise lagayein.

  • Part I — Skill design ki foundations: Skill kya hai, context window, aur banane ka tareeka.
  • Part II — Skills in practice: business blueprints, domain expertise, kaam ke patterns, aur real duniya ke examples.

01.3 Conventions Used In This Book

Book me program elements, commands aur file names ko ek consistent style me present kiya gaya hai, taaki padhte waqt turant samajh aaye ki kya code hai, kya command hai, aur kya file ka naam hai.

Jab bhi koi file ya folder dikhe, uska naam aur uski jagah saaf likhi hoti hai — kyunki Skill ka poora concept hi folder aur file structure par khada hai.

01.4 Code Examples Ka Istemal

Book ke code examples ko tum apne kaam me reuse kar sakte ho — attribution dena achha mana jata hai. Agar kisi example ko bade scale par istemal karna ho to permissions ke liye contact karne ka tareeka bhi diya gaya hai.

Matlab: examples padhne ke liye nahi, chalane aur badalne ke liye hain. Skill seekhne ka sabse tez tareeka hai ek example ko apne kaam par laga kar dekhna.

01.5 Online Learning Platform

Book ke saath online learning platform ka access bhi milta hai — wahan books, live training, videos aur certification ki taiyaari ka material milta hai.

Ye section isliye hai taaki tum book ko akela resource na samjho — aas-paas ka ecosystem bhi use karo, khaas taur par jab koi concept pehli baar mushkil lage.

01.6 How To Contact Us

Book se jude sawaal, sudhaar ya feedback ke liye contact karne ka tareeka diya gaya hai. Reader ka feedback agle edition aur updates me kaam aata hai.

Agar koi example tumhare setup par na chale, ya koi step confusing lage, to wahi feedback loop hai jo book ko behtar banata hai — bilkul waise hi jaise Skill ko test karke sudhara jata hai.

01.7 Acknowledgments

Book ke end me un sabka shukriya ada kiya gaya hai jinhone is kaam me madad ki — parivaar, sahkarmi aur dost — jinke support aur feedback ke bina ye book mumkin nahi hoti.

Ye chhota sa section ek badi baat batata hai: expertise akeli nahi banti. Har Skill ke peeche bhi aksar ek expert, ek reviewer aur ek team hoti hai.

02Part I — Foundations Of Skill Design

Chapter 1 — The Closed Gap

Agent ke paas taakat hai, lekin aadat nahi. Har baar wo kaam naye sire se improvise karta hai — isliye same request par bhi alag quality, alag steps, alag format. Is chapter me wo gap samjho jo Skill band karti hai.

02.1 Introduction

Agent matlab ek aisa model jo tools call kar sakta hai aur kisi goal ki taraf actions le sakta hai — sirf sawaal ka jawaab dena uski pehchan nahi hai.

Lekin is taakat ke saath ek badi problem hai: agent ke paas koi aadat (habit) nahi hoti. Wo har task ko pehli baar ki tarah karta hai, isliye result har baar badal sakta hai.

Ye loop hi agent ki pehchan hai: sochna, karna, dekhna — aur phir dobara sochna. Lekin is loop me kahin bhi ye nahi likha hota ki kaam kis standard se karna hai.

02.2 The Problem: Agents Without Habits

Aadat ka matlab hai: ek tay tareeka, jo baar-baar same quality de. Insaan ke paas aadat hoti hai — wo checklist follow karta hai, template use karta hai, galti se seekhta hai. Agent ke paas ye kuch nahi hota.

Iska nateeja: same request, alag result. Ek baar summary achhi, doosri baar bekaar. Ek baar steps poore, doosri baar aadhe. Format bhi har baar badal jata hai.

  • Quality badalti hai — koi guarantee nahi ki output hamesha ek jaisa hoga.
  • Steps badalte hain — agent har baar apna rasta khud chun-ta hai.
  • Format badalta hai — jahan template chahiye, wahan improvisation milti hai.
Problem model ki taakat ka nahi hai — problem ye hai ki kaam karne ka tareeka kahin likha hua hi nahi hai.

02.3 The Three Eras Of How Computers Learned To Do Things

Computer se kaam karane ke teen daur (eras) hain. Pehla: hum kaam karte the, software sirf tool tha. Doosra: deterministic software aur automation — fixed procedure code me likhi hoti thi, machine wahi dohrati thi. Teesra: prompting aur model-based kaam — model soch sakta hai, lekin uske paas follow karne ke liye koi stable procedure nahi hota.

Teesra daur sabse powerful hai — aur sabse unpredictable bhi. Model reason kar sakta hai, lekin 'kaise karna hai' uske paas likha hua nahi hota.

ReAct isi teesre daur ka core pattern hai: Reason → Act → Observe, aur phir wapas Reason. Model sochta hai, action leta hai, result dekhta hai, aur dobara sochta hai. Iska poora worked trace (sawaal–search–jawaab) Summary section me hai.

02.4 First, It Was Us

Pehle daur me insaan kaam karta tha, model madad karta tha. Workflow seedha tha: instruction aati thi, tool istemal hota tha, result milta tha — aur insaan har step par control me rehta tha.

Is daur me quality insaan ki expertise par depend karti thi — aur wo expertise insaan ke dimaag me thi, likhi hui nahi. Jab kaam machine ko dena shuru kiya, to wahi expertise kahin kho gayi.

02.5 The Gap

Gap matlab: general model capability aur ek specific job — jo ek specific standard se karna hai — ke beech ki khaali jagah. Is jagah par wo sab kuch rehta hai jo aam taur par documented nahi hota: expertise, sequence, checks aur judgment.

Model ko pata hai 'summary kya hoti hai'. Lekin use nahi pata ki tumhari team ki summary kaisi hoti hai — kaunse points pehle aate hain, kaunsa format chalta hai, kya check karna zaroori hai. Ye gap hi problem hai.

Live check

Gap ko ek line me pehchano: agar tum apne kaam ka tareeka ek naye team member ko likh kar nahi de sakte, to wo tareeka agent ko bhi nahi de sakte — wahi gap hai.

02.6 What A Skill Does

Skill is gap ko band karti hai. Wo kaam karne ka tareeka — steps, checks, examples, templates — ek packaged form me agent ko de deti hai, taaki agent har baar wahi tareeka follow kare.

Skill ka kaam model ko smart banana nahi hai. Skill ka kaam hai behaviour ko repeatable banana: same input, same procedure, same standard — har baar.

  • Skill procedure deti hai, sirf jawaab nahi.
  • Skill standard deti hai — kya achha hai, kya nahi.
  • Skill checks deti hai — output jaane se pehle verify ho.

02.7 What A Skill Is: A Folder With A Name

Skill ek naam wala folder hai, jiske centre me ek SKILL.md file hoti hai. Folder me instructions, examples, templates aur supporting material rehta hai. Jab kaam relevant ho, agent Skill ko load karta hai aur usko apni working procedure ki tarah follow karta hai.

folder

meeting-notes/
  SKILL.md  — naam, description, steps
  references/  — detail, jab zaroorat ho
  templates/  — output ka format
  examples/  — achhe output ke namune

Ye na koi naya model hai, na naya prompt, na naya tool — ye kaam karne ka ek packaged tareeka hai. Model wahi, tools wahi; farak sirf itna hai ki ab kaam ka tareeka likha hua hai.

SKILL.md hi Skill ki jaan hai — baaki sab supporting material hai, jo tabhi load hota hai jab zaroorat ho.

02.8 What To Expect From This Book

Aage ka rasta do hisso me baanta hai. Part I me foundations aur design hai — Skill kya hai, context window kaise sambhalein, aur Skill kaise banayein. Part II me practice hai — business blueprints, domain expertise ki packaging, kaam ke patterns, aur real duniya ka istemal.

Har chapter ek skill ki tarah hai: pehle concept, phir example, phir khud karke dekhna. Book ko kram se padho — aage ke chapters peeche wale par khade hain.

02.9 Final Note: What I Hope Sticks

Book ke end me ek seedhi si ummeed likhi hai: reader sirf ye poochhna band kare ki 'agent principle me kya kar sakta hai' — aur ye likhna shuru kare ki 'kaam kaise hona chahiye'.

Jis din tum apne kaam ka tareeka likh kar de doge, us din agent tumhare standard se kaam karne lagega. Skill wahi likha hua tareeka hai.

02.10 Summary

Is chapter ka nichod: agent powerful hai lekin uske paas aadat nahi; teeno eras ke baad bhi procedure likhne ki jagah khaali hai; Skill — ek naam wala folder jiske centre me SKILL.md hai — wahi gap band karti hai.

Worked example — tool call

Model ko ek get_weather function diya gaya — city aur units parameters ke saath. Phir request aayi: Lisbon ka mausam, Celsius me. Model ne structured tool call banaya: city=Lisbon, units=Celsius.

json
{
  "name": "get_weather",
  "arguments": {
    "city": "Lisbon",
    "units": "Celsius"
  }
}

Tool definition me teen cheezein hoti hain: function ka naam, plain-language description, aur parameters object — city (string) aur units (string, Celsius ya Fahrenheit) — dono required.

json
{
  "name": "get_weather",
  "description": "Get the current weather for a city.",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string" },
      "units": { "type": "string", "enum": ["Celsius", "Fahrenheit"] }
    },
    "required": ["city", "units"]
  }
}

Worked example — ReAct trace

Sawaal: 'What is the capital of Australia?' Model pehle khud se poochhta hai ki jawaab kya hai, phir search call karta hai, result milta hai — 'Canberra is the capital of Australia' — aur phir wahi jawaab deta hai. Reason → Act → Observe, ek saaf trace me.

03Part I — Foundations Of Skill Design

Chapter 2 — Skills: Designing For The Context Window

Skill ek package hai — lekin uski asli design challenge context window hai. Window finite hai, mehengi hai, aur bheed se bhari hai. Is chapter me Skill ki anatomy aur progressive disclosure samjho.

03.1 Introduction

Is chapter ka ek seedha sa aim hai, jo chapter ke 'What Is This Chapter About?' box me ek paragraph me likha hai: Agent Skill ko define karna, context window ke teen levels ko samjhna, aur ye samjhna ki Skill ka core ek plain instruction file kyun hoti hai — script nahi.

Aage badhne se pehle ek baat pakki kar lo: Skill koi magic file nahi hai. Wo ek design decision hai — kya context me rakha jaye, kya bahar rakha jaye, aur kab kya load ho.

03.2 What Is An Agent Skill?

Agent Skill matlab expertise ka ek self-contained package — instructions aur resources is tarah organise kiye gaye hain ki agent ek defined tarah ka kaam achhe se, baar-baar kar sake.

Skill ka test ek hi hai: kya agent isse wo kaam reliably karta hai? Agar haan, to Skill kaam ki hai — chahe wo chhoti ho ya badi. Agar nahi, to Skill ko sudharna hai, lamba karna nahi.

  • Skill defined kaam ke liye hoti hai — 'kuch bhi' ke liye nahi.
  • Skill khud ka package hoti hai — instructions + resources ek saath.
  • Skill ka maksad repeatability hai — ek baar nahi, har baar.

03.3 Two Perspectives On Agent Skills

Skill ko do nazariyon se dekho — dono sahi hain, aur dono zaroori hain.

User ki nazar se, Skill ek capability hai: 'X kaam waisa karo jaisa yahan hota hai.' User ko andar ki mechanism se matlab nahi — use result se matlab hai.

System ki nazar se, Skill selectively load hone wala context hai. System ye tay karta hai ki kab kya load ho — taaki context window bhari na ho aur reasoning kamzor na pade.

Dono nazariye ek saath rakhna hi achhi Skill design hai: user ko capability dikhe, system ko cost dikhe.

03.4 What An Agent Skill Looks Like

Bahari roop se Skill ek folder hai — lekin andar ka layout hi uski pehchan hai. Aam taur par folder me SKILL.md hoti hai, aur saath me supporting folders hote hain.

Ek real example: frontend-design Skill — jisme SKILL.md ke saath design ke references aur templates hote hain. Figure 2-4 me is Skill ka layout dikhaya gaya hai, jisme SKILL.md centre me hai.

03.5 The Anatomy Of A Skill

Skill ke teen hisse hote hain — aur teeno ka kaam alag hai:

  • Frontmatter — naam aur description. Ye discovery aur matching ke liye hai: agent (ya system) isi se tay karta hai ki ye Skill is kaam ke liye hai ya nahi.
  • Body instructions — kaam karne ki procedure, seedhe aur saaf shabdon me likhi hui. Ye Skill ka core hai.
  • Supporting files — detail, templates, references. Ye sirf tab load hote hain jab zaroorat ho.

Isi structure ko kehte hain progressive disclosure: pehle sirf jitna zaroori ho, utna dikhao — baaki maang par do. Skill ki body me link diya jata hai, detail copy nahi ki jati.

Live check

Anatomy check: kya tumhari Skill me frontmatter (naam + kab istemal ho), body (steps), aur supporting files (detail) — teeno alag-alag hain? Agar body me hi sab kuch bhar diya hai, to anatomy galat hai.

03.6 How A Skill Is Loaded

Loading stages me hoti hai — ek saath sab kuch nahi aata:

  1. Stage 1: sirf short description context me hoti hai — Skill discover hone ke liye itna hi kaafi hai.
  2. Stage 2: jab Skill select ho jaye, to poori SKILL.md load hoti hai.
  3. Stage 3: deeper reference material on demand load hota hai — jab agent ko uski zaroorat pade.

Har step Skill me naam se likha hota hai — agent ko guess nahi karna padta ki pehle kya, phir kya.

03.7 The Skill Is Not The Model

Ye farak samajhna sabse zaroori hai: Skill model nahi hai. Skill weights nahi badalti, aur model me koi nayi capability nahi jodti. Wo sirf working knowledge deti hai — context me.

Model wahi rehta hai, uski taakat wahi rehti hai. Skill sirf ye batati hai ki us taakat ko is kaam me kaise lagana hai — kis kram me, kis standard se, kis check ke saath.

Agar model koi kaam kar hi nahi sakta (capability hi nahi hai), to Skill use nahi sikha sakti. Skill procedure deti hai, capability nahi.

03.8 Context Windows: The Hardest Problem In Agent Design

Agent design ki sabse mushkil problem hai context window. Wo finite hai, costly hai, aur tool outputs, history aur doosre material se bhari rehti hai.

Isiliye sab kuch upar se load kar dena galat hai — jitna zyada bheed hogi, reasoning utni kamzor hogi. Chapter me 200,000-token window ka example diya gaya hai: agar Skill ko poora ek saath load kar do, to wo window ka ek bada hissa kha jayegi. Progressive disclosure se sirf description, phir core file, context me rehti hai — baaki tabhi aata hai jab zaroorat ho.

  • Window finite hai — har token ki jagah limited hai.
  • Window costly hai — zyada tokens matlab zyada cost aur slow kaam.
  • Window crowded hai — tools ke outputs aur history bhi wahi rehte hain.

03.9 Building Skills To Respect The Context Window

Context window ka samman karne ke design rules seedhe hain:

  1. Core file chhoti rakho — SKILL.md me sirf procedure ho, detail nahi.
  2. Detail alag files me rakho — references aur templates supporting files me.
  3. Link karo, repeat mat karo — ek hi baat do jagah likhne se window bhar jati hai.
  4. Deterministic steps ke liye scripts use karo — jo kaam har baar ek jaisa hai, use code se karwao.
  5. Agent ko fetch karne do — jo chahiye, jab chahiye, tabhi lao.

Ye rules Skill ko halka rakhte hain — aur halki Skill hi tez aur reliable hoti hai.

03.10 A Quick Example

Ek chhota sa example dekhte hain — branded-handout Skill. Iska frontmatter naam aur description deta hai: naam jaise branded-handout, aur description batati hai ki kab istemal ho — jab user branded handout, poster ya one-page summary maange.

yaml
---
name: branded-handout
description: Use when the user asks for a branded handout, poster, or one-page summary.
---

Follow the steps below to produce the handout.

Phir ek fragment batata hai ki agent ko shuru karne se pehle reference file kholni hai — ek link se detail core file se bahar defer ho jati hai:

markdown
Before starting, open references/brand.md
and follow the brand rules given there.

Aur phir ek agent transcript dikhata hai ki selective loading kaam kaise karti hai: agent Skill load karta hai, brand reference padhta hai, aur phir handout banata hai — pehle se sab kuch load karke nahi.

03.11 Testing And Iteration: The Heart Of The Skill Development Loop

Skill development ka core loop hai testing aur iteration. Skill likh kar chhod dena kaafi nahi — use aazmana padta hai:

  1. Real task par try karo — asal kaam par, toy example par nahi.
  2. Output ko inspect karo — kya standard par khara utra?
  3. Dhoondho agent kahan galat gaya — kaunsa step, kaunsa instruction kamzor tha?
  4. Instruction tight karo ya example/check jodo — aur dobara test karo.

Ye loop hi Skill ko behtar banata hai. Pehla version kabhi final nahi hota — har failure ek sudhaar ka mauka hai.

Testing ke bina Skill ek andaza hai. Testing ke saath wo ek verified procedure hai.

03.12 Skills Are Not Just A Different Name For Prompting

Ye confusion aam hai — lekin farak saaf hai. Prompt ad-hoc hota hai — ek conversation ke liye, ek baar ke liye. Skill persistent hoti hai — naam wali, discoverable, aur tasks aur agents ke paar reusable.

Prompt likh kar bhool jate ho. Skill likh kar rakhte ho, test karte ho, version karte ho, team se share karte ho. Prompt ek baar kaam karta hai; Skill har baar kaam karti hai.

  • Prompt: ek conversation, phir khatam.
  • Skill: persistent, named, discoverable.
  • Prompt: har baar naye sire se. Skill: reuse across tasks aur agents.

03.13 When A Skill Is Not Enough

Skill ki limits bhi samajh lo — teen cheezein Skill fix nahi kar sakti:

  • Missing model capability — jo model kar hi nahi sakta, wo Skill se nahi hoga.
  • Missing tool ya access — agar tool ya permission hi nahi hai, to procedure ka kya faayda?
  • Fundamentally underspecified task — agar kaam hi saaf define nahi hai, to Skill kya follow karegi?

In teen cases me Skill banane se pehle capability, tool ya task ki clarity par kaam karo. Skill procedure ka jawab hai — har problem ka nahi.

03.14 Summary

04Part I — Foundations Of Skill Design

Chapter 3 — Designing And Building Skills

Achhi Skill lambi nahi hoti — reliable hoti hai. Is chapter me Skill chun-ne, todne (decompose), likhne, organise karne aur maintain karne ka poora tareeka hai — saath me 85% rule, paanch stages, aur do comparison tables.

04.1 Introduction

Ab tak tum jaante ho Skill kya hai aur kaise load hoti hai. Ab sawaal hai: kaunsi Skill banayein, kaise banayein, aur kaise jaanein ki wo achhi hai? Ye chapter wahi design aur building ka kaam karta hai.

Is chapter me figures 3-1 se 3-8 aur tables 3-1 aur 3-2 hain — aur mashhoor 85% rule bhi. Har section ek decision hai, aur har decision ka test hai: kya agent isse kaam reliably karta hai?

04.2 What Makes A Skill Good

Achhi Skill ko length se nahi, reliability se naapa jata hai: kya agent isse kaam reliably karta hai? Achhi Skill chaar cheezein hoti hai:

  • Specific — ek defined kaam, saaf scope.
  • Action-oriented — 'kya karna hai' bataye, sirf 'kya hai' nahi.
  • Testable — output ko check kiya ja sake, success criteria saaf ho.
  • Agent ke liye likhi hui — reader agent hai, insaan nahi; isliye seedhi, plain language me.

Agar Skill padh kar agent ko samajh na aaye ki pehle kya karna hai, to Skill achhi nahi hai — chahe wo kitni bhi detailed kyun na ho.

04.3 How To Decide Which Skills To Build

Har kaam ki Skill mat banao. Skill us kaam ki banao jo repeated ho, painful ho ya high-value ho — aur jahan current agent output inconsistent ho.

Test seedha hai: kya ye kaam baar-baar hota hai? Kya isme galti mehngi padti hai? Kya agent ka output har baar alag aata hai? Teenon me se kisi ka jawaab 'haan' hai, to Skill candidate hai.

Ek baar ka kaam Skill nahi maangta — prompt kaafi hai. Skill us kaam ki hai jo dobara hoga.

04.4 When To Automate And When To Decompose

Do raaste hain — automate karo ya decompose karo. Automate karo jo deterministic aur stable hai: har baar ek jaisa, badalta nahi. Decompose karo jo variable, judgement-heavy ya multi-step hai — use chhote, verifiable steps me todo, jinhe Skill guide kar sake.

Galti ye hoti hai ki variable kaam ko automate karne ki koshish ki jati hai — aur phir edge cases par system toot-ta hai. Pehle decompose karo, phir jahan deterministic hissa mile, use automate karo.

04.5 The Case For Decomposition

Decomposition ke teen faayde hain:

  • Errors local hote hain — galti ek step me rehti hai, poore kaam me nahi failti.
  • Har step par check mumkin hai — aage badhne se pehle verify karo.
  • Kaam reusable hota hai — chhote steps doosri jagah bhi kaam aate hain.

Bada kaam todne se darr mat lagta — todne se hi control milta hai.

04.6 How To Decompose A Task

Decompose karne ka tareeka: task ko todo — inputs, steps, decision points, outputs me — aur har ek ka standard naam se likho.

Har step ke liye standard likho: 'achha output kaisa dikhta hai?' Agar standard nahi likha, to agent guess karega — aur guess galat hoga.

04.7 What To Write In A Skill

Skill me kya likhna hai — kram ye hai:

  1. Goal aur non-negotiables pehle — kaam kya hai, aur kya kabhi nahi todna.
  2. Sequence — steps kram se.
  3. Good output ke examples — agent ko dikhao 'achha' kaisa dikhta hai.
  4. Missing information par kya karein — jab kuch na mile, to agent kya kare: poochhe, skip kare, ya flag kare?

Sabse aam galti: non-negotiables end me likhna. Wo pehle aate hain — kyunki agent unhe sabse pehle padhta hai.

Example — meeting-notes Skill ka SKILL.md

Meeting-notes Skill ka frontmatter naam aur trigger description deta hai, phir body instruct karti hai: transcript padho, decisions/actions/owners nikalo, aur diye gaye template me notes likho.

yaml
---
name: meeting-notes
description: Use when the user asks for structured notes from a meeting transcript.
---

1. Read the transcript.
2. Extract decisions, actions and owners.
3. Write the notes in the given template.

Aur ek checklist-style Skill body batati hai ki Skill apne success criteria kaise likhti hai — output me kya-kya hona chahiye — taaki agent apna kaam khud check kar sake.

04.8 How To Handle Tasks With High Variance

High-variance tasks wo hain jahan har baar kaam alag dikhta hai. Inhe handle karne ka tareeka: stable procedure ko variable content se alag karo.

Procedure stable rehti hai — steps, checks, format. Content variable hota hai — har baar alag data, alag case. Har case ko script karne ki koshish mat karo; decision rules aur examples do, taaki agent naye case me bhi sahi faisla le sake.

Variance ka jawab zyada likhna nahi hai — variance ka jawab sahi jagah par rules aur examples dena hai.

04.9 How To Organize A Skill Library

Skill library ko domain aur task ke hisaab se organise karo — taaki sahi Skill sahi waqt par mil jaye.

  • Naam saaf ho — naam se hi pata chale Skill kya karti hai.
  • Description saaf ho — kab istemal ho, ye likha ho.
  • Domain ke hisaab se group karo — related Skills ek saath.

Library badi hone par bhi discovery aasan rehti hai — kyunki naam aur description hi search ka kaam karte hain.

04.10 Tools, Contexts, And Skill Design

Tools aur context Skill design ka hissa hain. Skill me likho: kaunse tools istemal karne hain, aur kya context chahiye.

Aur ek sakht rule: wo tools assume mat karo jo available nahi hain. Agar Skill kisi tool par depend karti hai jo agent ke paas nahi hai, to Skill fail hogi — procedure chahe kitni bhi achhi ho.

04.11 Building Skills That Are Composable

Composability matlab: chhoti Skills jo workflow me combine ho sakein — ek monolith (ek badi Skill) ke bajaye.

Chhoti Skill test karna aasan hai, reuse karna aasan hai, aur badalna aasan hai. Badi Skill me ek galti poori Skill ko tod deti hai — chhoti Skills me galti ek jagah rehti hai.

04.12 Skills As A Business Advantage

Business advantage isme hai: Skill expertise ko portable aur consistent bana deti hai — logon aur agents ke paar.

Ek expert ka tareeka ab sirf us expert ke paas nahi rehta — wo Skill ban kar team ke har member aur har agent ke paas pahunch jata hai. Isi se quality consistent hoti hai, aur expertise company ki asset banti hai.

04.13 When To Use Skills Versus Other Options

Skill har cheez ka jawab nahi hai. Doosre options se comparison karo — aur phir line kheencho. Table 3-1 me chaaro ka role saaf hai:

04.14 The Problem With Projects

Projects broad containers hote hain — unme bahut kuch rehta hai, lekin procedure nahi hoti. Project batata hai 'kya chal raha hai', lekin 'kaise karna hai' nahi batata.

Isliye Project Skill ka substitute nahi hai. Project me Skill reh sakti hai — lekin Project khud Skill nahi hai.

04.15 The Problem With MCPs

MCP servers tools aur access dete hain, procedure nahi. MCP se agent ko tool mil jata hai — lekin us tool ko kis kram me, kis standard se istemal karna hai, ye MCP nahi batata.

Tools hona aur tareeka hona — do alag cheezein hain. MCP pehla deta hai, Skill doosra.

04.16 The Problem With Subagents

Subagents delegation structure hain, procedure nahi. Subagent batata hai 'kaam kisko do' — lekin 'kaam kaise karo' nahi batata.

Delegate karna aur procedure dena — dono zaroori hain, lekin ek doosre ki jagah nahi le sakte. Subagent ke paas bhi Skill honi chahiye.

04.17 The Problem With Prompts

Prompts transient hote hain — ek conversation me likhe, phir khatam. Unme na naam hota hai, na discovery, na version, na test.

Prompt har baar naye sire se likhna padta hai — aur har baar thoda alag likha jata hai. Isi liye prompt se consistency nahi milti.

04.18 Where Do You Draw The Line?

Line kheenchnne ka rule seedha hai: agar kaam repeatable procedure hai, to Skill. Agar kaam one-off hai, to prompt. Agar kaam tools ki kami hai, to MCP. Agar kaam delegation hai, to subagent.

Jab doubt ho, to ye poochho: 'Kya ye kaam dobara hoga, aur kya iska standard likha ja sakta hai?' Haan hai to Skill banao — nahi hai to doosra option chuno.

Skill ko har jagah thopna bhi galat hai. Sahi option chunna hi achhi design hai.

  2. Stage 1 — First written procedure: tareeka pehli baar likha gaya.
  3. Stage 2 — Tested Skill with examples: Skill test hui, examples jude.
  4. Stage 3 — Shared Skill: team istemal kar rahi hai.
  5. Stage 4 — Maintained, versioned library: Skill maintain aur version ho rahi hai.

Chapter 5 — Packaging Domain Expertise

Domain expertise sirf facts nahi hoti — facts, procedures aur judgment ka combination hoti hai. Is chapter me expert ke dimaag se Skill banane ka tareeka hai — aur ek poora video-editing example, numbers ke saath.

06.1 Introduction

Ab tak tumne Skill ka structure aur blueprints dekhe. Ab sawaal hai: expert ke dimaag me jo knowledge hai, wo Skill me kaise aaye? Ye chapter wahi packaging ka kaam karta hai.

Domain expertise wo cheez hai jo expert ko expert banati hai — aur wo aksar likhi hui nahi hoti. Use nikaalna, structure dena aur Skill me band karna — yahi is chapter ka kaam hai.

06.2 What Counts As Domain Expertise

Domain expertise matlab facts, procedures aur judgment ka combination — jo expert ke output ko achha banata hai. Ye sirf wo facts nahi hain jo model pehle se jaanta hai.

Model ko facts pata hote hain. Expert ko ye pata hota hai ki kis fact ko kab istemal karna hai, kis kram me kaam karna hai, aur kya 'achha' mana jata hai. Wahi teeno milkar expertise banti hai — aur wahi teeno Skill me aane chahiye.

  • Facts — kya hai, kya terminology hai.
  • Procedures — kis kram me, kaise karna hai.
  • Judgment — kya achha hai, kya galat hai.

06.3 How To Turn An Expert's Knowledge Into A Skill

Expert ki knowledge ko Skill me badalne ke liye expert ke saath kaam karna padta hai — sirf interview lena kaafi nahi. Asal kaam ko observe karo, aur wo decisions capture karo jo aam taur par tacit (bina bole) rehte hain.

Expert aksar ye nahi bata sakta ki wo kya karta hai — kyunki wo kaam itni baar kar chuka hai ki tareeka aadat ban gaya hai. Isiliye observation zaroori hai: kaam karte hue dekho, phir poochho 'ye step kyun?'.

Expert se rules mat maango — expert ka kaam dekho, phir rules nikalo.

06.4 Skill Development: Working With A Domain Expert

Expert ke saath kaam karne ka tareeka: pehle observe karo, phir draft banao, phir test karo, aur phir expert se review karwao.

Expert ki sabse badi madad review me milti hai: agent ka output dikhao, aur poochho 'kya ye tumhare standard par hai?' Expert jahan 'nahi' kahe, wahi Skill sudharne ki jagah hai.

06.5 The Skill Development Loop

Expert ke saath development loop chaar steps ka hai:

  1. Draft — observation ya interview se draft banao.
  2. Test — real case par test karo.
  3. Expert review — expert output review kare.
  4. Revise — jahan agent diverge hua, Skill ko sudharo.

Ye loop tab tak chalta hai jab tak agent ka output expert ke standard par na aa jaye. Har cycle Skill ko expert ke kareeb le jata hai.

06.6 Types Of Knowledge

Knowledge teen tarah ki hoti hai — aur teeno ki Skill me alag jagah hai. Aage ke teen sections me har ek detail me hai.

Teeno ko alag samajhna zaroori hai — kyunki agent ki galti batati hai ki kaunsi knowledge missing hai.

06.7 Declarative Knowledge: Facts And Concepts

Declarative knowledge matlab facts, concepts, terminology aur reference material. Ye 'kya hai' ka jawab deti hai.

Is knowledge ki jagah Skill ke references me hai — core file me nahi. Facts ko reference file me rakho, aur core file se link karo. Jab agent ko fact chahiye, wo fetch kar lega.

Example: brand ke colour codes, product ke specifications, domain ki terminology — ye sab declarative hai.

06.8 Procedural Knowledge: Steps And Sequences

Procedural knowledge matlab steps, sequences aur decision rules. Ye 'kaise karna hai' ka jawab deti hai.

Is knowledge ki jagah Skill ke core body me hai — kyunki procedure hi Skill ka dil hai. Steps kram se likho, decision points saaf likho, aur har step ka standard likho.

Example: video edit karne ke steps, contract review ka kram, lead qualify karne ka sequence — ye sab procedural hai.

06.9 Evaluative Knowledge: How To Judge Quality

Evaluative knowledge matlab quality kaise judge karein — 'achha' kaisa dikhta hai, aur 'failure' kya mana jata hai.

Is knowledge ki jagah Skill ke checks aur rubrics me hai. Agent ko sirf kaam karna nahi sikhana — ye bhi sikhana hai ki kaam theek hua ya nahi, ye kaise pehchane.

Example: 'summary achhi hai' ka matlab kya hai? Kaunse points hone chahiye, kaunsa format, kya missing nahi hona chahiye — ye sab evaluative hai. Bina iske agent ko pata hi nahi chalega ki uska output theek hai ya nahi.

06.10 A Concrete Example: Video Editing

Ab ek poora worked example dekhte hain — video editing. Source material ek 10-minute-23-second ki workshop recording hai, Portuguese me, jiske saath transcript hai. Skill transcript ko parse karti hai, clips select karti hai, unhe order karti hai, aur timeline banati hai.

Clip selection ka rule: transcript ka sirf lagbhag 15% hissa load-bearing hota hai — baaki filler hota hai. Isiliye Skill agent ko kehti hai: sirf load-bearing passages rakho, baaki chhodo.

Clips aur timeline: clips lagbhag 10 seconds ke kaate jate hain. Worked example me chaar clips bante hain, aur kul edited material 53 minutes 8 seconds ka banta hai (notes ke mutaabik).

Skill ke non-negotiable invariants — jo kabhi nahi todne:

  • Kabhi quote invent mat karo — jo bola nahi gaya, wo likha nahi jayega.
  • Speaker ke argument ka order kabhi mat badlo — kram wahi rahega.
  • Har clip ko transcript se check karo — include karne se pehle verify karo.

Aur end me edited output ko judge karne ke liye ek rubric di gayi hai — taaki 'achha edit' ka matlab saaf ho, andaze par na ho.

Live check

Video-editing example ke numbers: source 10m 23s, load-bearing ~15%, clip ~10s, chaar clips, kul 53m 8s edited material (notes ke mutaabik). Invariants: no invented quotes, no order change, har clip transcript-verified.

06.11 How To Choose Between Declarative, Procedural, And Evaluative Knowledge

Teeno me se kya chahiye — ye is par depend karta hai ki agent kahan fail ho raha hai:

  • Facts missing hain? → declarative knowledge do (references).
  • Sequence galat hai? → procedural knowledge do (steps).
  • Judgment kharab hai? → evaluative knowledge do (checks, rubric).

Aksar teeno ka mix chahiye hota hai — aur chapter ke rules batate hain ki kis hisaab se mix karein. Pehle failure ko dekho, phir knowledge chuno. Ulta mat karo.

06.12 How To Extract And Structure Domain Knowledge

Knowledge nikaalne ke tareeke:

  • Shadowing — expert ke saath baith kar uska kaam dekho.
  • Past work review — achhe aur bure dono examples dekho, aur farak samjho.
  • Correction se seekhna — expert se rules likhwaane ke bajaye, agent ka output dikhao aur expert se corrections karwao. Har correction ek rule hai.

Structure dene ka tareeka: knowledge ko teeno types me baanto (declarative / procedural / evaluative), phir har type ko uski sahi jagah rakho — references, body, ya checks me.

Sabse tez tareeka: expert ko rules likhne ko mat kaho. Expert ko agent ki galti theek karne do — rules khud nikal aayenge.

06.13 What To Do When An Expert Cannot Articulate Their Knowledge

Aksar expert apni knowledge bol kar nahi bata sakta — kyunki wo tacit hai. Is case me examples aur counter-examples use karo.

Expert ko achha example dikhao aur poochho 'ye achha kyun hai?' Bura example dikhao aur poochho 'ye bura kyun hai?' Unke jawaab se rules infer karo. Aur corrections se rules banao — har correction ke peeche ek rule chhupa hota hai.

Agar expert kuch bol nahi pa raha, to uska kaam dekhna band mat karo — dekhna hi ek matra raasta hai.

06.14 Skills As A Form Of Documentation

Skills documentation ka ek form hain — lekin aisi documentation jo execute hoti hai, sirf padhi nahi jati.

Aam documentation likhi jati hai aur bhool jati hai. Skill wali documentation har baar chalti hai — agent use follow karta hai. Isiliye wo hamesha up-to-date rehti hai: agar documentation galat ho, to agent ka output galat hoga, aur koi turant pakad lega.

Matlab: Skill likhna documentation likhna hai — lekin aisi documentation jo khud ko test karti rehti hai.

06.15 The Delegation Problem

Delegation problem matlab: kaam agent ko de dena, bina shared standard ke. Tumne kaam de diya, agent ne kuch kar diya — lekin tumhe nahi pata wo tumhare standard par hai ya nahi.

Bina Skill ke delegation andha hota hai — tumhe har output ko khud check karna padta hai, jo delegation ka fayda hi khatm kar deta hai. Shared standard ke bina delegation kaam nahi karta.

06.16 A Simple Model Of The Skills Delegation Loop

Skills delegation loop ek cycle hai — paanch steps:

Cycle ka matlab: brief do, agent execute kare, output verify karo, galti mile to correct karo, aur correction ko Skill me update karo — taaki agli baar wahi galti na ho. Loop ka aakhri step hi Skill ko behtar banata hai.

Delegation loop me 'update the Skill' sabse important step hai — wahi delegation ko ek baar ke kaam se system me badalta hai.

06.17 Summary

Is chapter ka nichod: domain expertise = facts + procedures + judgment. Expert se knowledge nikaalne ke liye observe karo, corrections se rules banao, aur teeno knowledge types ko unki sahi jagah rakho (references / body / checks). 07.2 New Work Primitives

Input: transcript. Kaam: structure nikaalo — decisions, actions, quotes, timestamps. Output: structured artifact — jo source transcript se verify ho.

Input: dataset aur sawaal. Kaam: analysis karo — explicit methods ke saath. Output: analysis — checks ke saath, aur reproducible result.

Data analysis pattern me method likhna zaroori hai — kaise analyse kiya, kya assumptions thi. Reproducible ka matlab: dobara wahi steps chalao, to wahi result aaye. Bina method ke analysis par bharosa nahi kiya ja sakta.

  1. Surprise — kya Skill koi possibility ya approach batati hai jo tumne sochi hi nahi thi?

08.4 Safety Concerns

Safety sabse badi baat hai. Ek malicious Skill unintended actions karwa sakti hai ya data bahar bhej sakti hai — kyunki SKILL.md file agent ko keh sakti hai ki files padho, commands chalao, ya bahari services se contact karo.

  • SKILL.md poori padho — kya wo agent se kuch ajeeb karwa rahi hai?
  • Scripts check karo — kya wo sirf wahi karte hain jo likha hai?

  • Files accessed — Skill kin files ko chhoo sakti hai?
  • Pehla test isolated environment me, disposable copies par, limited access ke saath.

08.5 Insights from Effective Skills

Effective Skills se paanch design lessons nikalte hain — aur aage ke paanch sections me har ek detail me hai:

  • Preferences ko concrete banao.

08.6 Making a Preference Concrete

Preference tabhi useful hoti hai jab wo decision badle — aur wo bhi ek revisable process ke through. 'Mujhe achha design chahiye' preference nahi hai — wo wish hai.

Concrete preference aisi hoti hai: 'agar X ho, to Y karo; agar Z ho, to W karo.' Preference me decision rule hona chahiye — taaki agent ko pata chale ki is preference se kya badlega.

Example: frontend-design Skill me preference concrete thi — landing page ke liye oversized serif lettering, ek red italic word, aur ek specific editorial direction. Is preference se page ka look badla — aur wo badlaav inspect kiya ja sakta tha.

08.7 Teach the Skill When Not to Act

Skill ko sirf ye mat sikhao ki kab action lena hai — ye bhi sikhao ki kab nahi lena. Rule is form me likho: 'agar ye conditions hain, to X karo; agar nahi hain, to X skip karo.'

Example: ek design-engineering Skill me animation ka rubric tha — har animation ko batana padta hai ki wo kyun animate ho rahi hai. Valid purposes: spatial consistency, state indication, explanation, feedback, aur jarring changes rokna. Agar purpose sirf 'achha lagta hai' hai, aur user use baar-baar dekhega, to animate mat karo.

Bina 'when not to act' ke Skill har jagah action legi — aur har jagah action lena hi galti hai.

08.8 Document Skills Need Artifact-Suited Checks

Document Skills ke checks artifact ke hisaab se hone chahiye — generic check kaam nahi karta. Har artifact ka apna check hota hai.

Example: spreadsheet Skill — derived values ke liye formulas use karo aur workbook ko recalculate karo. Ek chhota sa excerpt ye rule sikhata hai: cell me computed total likhne ke bajaye formula likho, taaki inputs badalne par sheet dobara calculate ho.

Spreadsheet ka check formula ka hota hai; document ka check format ka; code ka check tests ka. Artifact badla, to check badla.

Check ko artifact se match karo — generic 'sab theek hai?' koi check nahi hai.

08.9 Keep Disclosure Depth to One Level

SKILL.md ko agent ko seedha usable content tak le jana chahiye — kisi aur index tak nahi. Disclosure depth ek level rakho.

Example: book-to-skill Skill — core frameworks aur chapter index SKILL.md me, detailed notes alag chapter files me, ek-level hierarchy me (SKILL.md seedha chapters/ch01-….md jaise files se link karti hai).

Chapter me ek study ka hawala hai: child Skills ki hierarchy jodne se koi reliable accuracy gain nahi mila — aur har routing decision ek mauka hota hai galat decide karne ka. Isiliye depth ek level rakho — zyada levels matlab zyada galti ke mauke.

08.10 Before the Agent Says 'Fixed'

Agent 'fixed' kehne se pehle verify kare — ye rule is section ka core hai. Do cheezein zaroori hain:

  • 'Done' ko rubric se define karo — 'done' ka matlab kya hai, ye likha ho.
  • Agent jo banata hai, use operate karke dikhao — banaya hai to chalakar dikhao.

Verification-before-completion Skill ka rule: agent ko observation ka naam batana padta hai jo uske claim ko support karta hai — aur sirf last, most specific claim accept hota hai. Example: 'Bug fixed' ke liye original symptom ka passing test chahiye. Aur evidence fresh hona chahiye.

Ek aur example: webapp-testing Skill — printable pages par images arrange karne wale chhote browser app par try ki gayi. Run me Playwright test script me 34 checks bane, us run me sab pass hue, saath me kai states ke screenshots bhi mile — jinme ek specific check tha ki chaar-image layout me saat images ko defined number of pages occupy karne chahiye.

Aur invoice reconciliation ka example: synthetic data par chhah invoices check kiye gaye — teen matched, teen exceptions unresolved rahe. Point ye hai: partial, honest report confident false completion se behtar hai.

Live check

'Fixed' kehne se pehle teen sawaal: observation kya hai? Evidence fresh hai? Test pass hua? Teenon 'haan' ho to hi 'done' kaho.

08.11 Bounded Reports

Bounded reports matlab reports jinki boundary pehle se tay ho — time-wise ya topic-wise. Boundary se report focused rehti hai aur kabhi khatam nahi hone wali nahi hoti.

Do tarah ki boundaries hain — aage ke do sections me har ek detail me hai: timeline-bound (time se bandhi) aur question-bound (sawaal se bandhi).

08.12 Timeline-Bound Briefs

Timeline-bound brief ka example hai monday-brief Skill — Monday subah ki briefing, ek two-link chain ke roop me:

Skill gracefully degrade karti hai jab connectors missing hon — matlab agar koi connector nahi hai, to Skill rukti nahi, batati hai ki kya missing hai aur baaki kaam kar leti hai.

Trigger phrases: 'Monday brief,' 'start my week,' aur 'what do I need to know this week' — inme se koi bhi bole, to Skill chal padti hai.

08.13 Question-Bound Reports

Question-bound report ka example hai research-report Skill — har source ko istemal se pehle grade kiya jata hai, scoring gates ke saath:

  • 10–12 — Tier-A: freely quote karo, is source se lead karo.
  • 7–9 — Tier-B: istemal karo, lekin key claims ko cross-check karo.
  • 7 se neeche — reject: istemal mat karo, cite mat karo.

Aur ek sakht rule: har non-trivial claim ke saath inline citation honi chahiye — aur us citation ka deep link seedha us verbatim passage par jana chahiye jo claim ko support karta hai. Bina citation ke claim, report me nahi aata.

  • Criteria-based verification integrate karo.
  • Time-wise ya topic-wise bounded reports istemal karo.

01Agent Skill kya hoti hai, ek line me?
Agent Skill expertise ka ek self-contained package hai — instructions aur resources is tarah organise kiye gaye hain ki agent ek defined tarah ka kaam achhe se, baar-baar kar sake. Ye ek naam wala folder hai, jiske centre me SKILL.md file hoti hai, aur saath me examples, templates aur supporting material rehta hai. Agent jab relevant kaam karta hai, to Skill load karta hai aur use apni working procedure ki tarah follow karta hai.


02Skill aur prompt me kya farak hai?
Prompt ad-hoc hota hai — ek conversation ke liye, ek baar ke liye likha jata hai aur phir khatam ho jata hai. Skill persistent hoti hai — naam wali, discoverable, aur tasks aur agents ke paar reusable. Prompt har baar naye sire se likhna padta hai, jabki Skill likh kar, test karke, version karke aur team se share karke rakhi jati hai. Isi liye prompt se consistency nahi milti, Skill se milti hai.


03SKILL.md me kya-kya hota hai?
SKILL.md me teen hisse hote hain: frontmatter (naam aur description — discovery aur matching ke liye), body instructions (kaam karne ki procedure, seedhe aur saaf shabdon me), aur supporting files ke links (detail, templates, references). Frontmatter se agent tay karta hai ki ye Skill is kaam ke liye hai ya nahi, body se use steps milte hain, aur supporting files tabhi load hoti hain jab zaroorat ho.


04Progressive disclosure kya hai aur kyun zaroori hai?
Progressive disclosure matlab: pehle sirf jitna zaroori ho, utna dikhao — baaki maang par do. Pehle sirf Skill ki short description context me hoti hai, phir select hone par poori SKILL.md load hoti hai, aur deeper reference material on demand aata hai. Ye isliye zaroori hai kyunki context window finite aur costly hai — sab kuch ek saath load kar doge to reasoning kamzor ho jayegi aur cost badhegi.


05Context window Skill design ko kaise affect karta hai?
Context window agent design ki sabse mushkil problem hai: wo finite hai, costly hai, aur tool outputs, history aur doosre material se bhari rehti hai. Isiliye Skill design ke rules hain — core file chhoti rakho, detail alag files me rakho, link karo repeat mat karo, deterministic steps ke liye scripts use karo, aur agent ko fetch karne do jo chahiye jab chahiye. Book me 200,000-token window ka example hai: poori Skill ek saath load karne se window ka bada hissa kharch ho jata hai.


06Achhi Skill ki pehchan kya hai?
Achhi Skill ko length se nahi, reliability se naapa jata hai: kya agent isse kaam reliably karta hai? Achhi Skill chaar cheezein hoti hai — specific (ek defined kaam, saaf scope), action-oriented ('kya karna hai' bataye), testable (output ko check kiya ja sake, success criteria saaf ho), aur agent ke liye likhi hui (reader agent hai, isliye seedhi plain language me). Agar padh kar agent ko samajh na aaye ki pehle kya karna hai, to Skill achhi nahi hai.


07Kaunsi Skill pehle banayein — kaise decide karein?
Us kaam ki Skill banao jo repeated ho, painful ho ya high-value ho — aur jahan current agent output inconsistent ho. Test seedha hai: kya ye kaam baar-baar hota hai? Kya isme galti mehngi padti hai? Kya agent ka output har baar alag aata hai? Teenon me se kisi ka jawaab 'haan' hai, to Skill candidate hai. Ek baar ka kaam Skill nahi maangta — uske liye prompt kaafi hai.


08Automate kab karein aur decompose kab karein?
Automate karo jo deterministic aur stable hai — har baar ek jaisa, badalta nahi. Decompose karo jo variable, judgement-heavy ya multi-step hai — use chhote, verifiable steps me todo jinhe Skill guide kar sake. Galti ye hoti hai ki variable kaam ko automate karne ki koshish ki jati hai, aur phir edge cases par system toot-ta hai. Pehle decompose karo, phir jahan deterministic hissa mile, use automate karo.


09Task ko decompose kaise karte hain?
Task ko chaar hisson me todo: inputs (kya chahiye shuru karne ke liye), steps (kram se kya karna hai), decision points (kahan faisla lena hai), aur outputs (kya standard se banana hai). Har ek ka standard naam se likho — 'achha output kaisa dikhta hai?' Decomposition ke teen faayde hain: errors local hote hain, har step par check mumkin hai, aur kaam reusable hota hai.


10Skill me kya likhna chahiye — kram kya hai?
Pehle goal aur non-negotiables likho — kaam kya hai aur kya kabhi nahi todna. Phir sequence — steps kram se. Phir good output ke examples — agent ko dikhao 'achha' kaisa dikhta hai. Aur aakhir me likho ki jab information missing ho to agent kya kare — poochhe, skip kare, ya flag kare. Sabse aam galti non-negotiables ko end me likhna hai — wo pehle aate hain kyunki agent unhe sabse pehle padhta hai.


1185% rule kya hai aur kaise istemal karein?
85% rule kehta hai: Skill banao un 85% cases ke liye jo routine aur repeatable hain, aur baaki 15% unusual cases insaan ke liye chhod do. Jo Skill common cases achhe se handle kar le, wo banane layak hai — chahe wo har edge case cover na kare. Agar tum 100% cover karne ki koshish karoge, to 15% edge cases par 85% waqt barbaad kar doge.


12Skill development ke paanch stages kaunse hain?
Stage 0 — ad-hoc prompt: kaam prompt se ho raha hai, kuch likha hua nahi. Stage 1 — first written procedure: tareeka pehli baar likha gaya. Stage 2 — tested Skill with examples: Skill test hui, examples jude. Stage 3 — shared Skill: team istemal kar rahi hai. Stage 4 — maintained, versioned library: Skill maintain aur version ho rahi hai. Har stage pehle wale par khada hai — skip karoge to foundation kamzor hoga.


13Skill ka scope kitna bada hona chahiye?
Best fit single task hai — jaise ek meeting-notes Skill. Single domain (related tasks ka group) bhi theek hai. Whole business area bahut bada scope hai — sirf bahut chhote set of related tasks ke liye. Whole company bahut broad hai — use split karo. Rule: scope jitna chhota, Skill utni reliable. Badi Skill me ek galti poori Skill ko tod deti hai.


14Skill, MCP, subagent aur prompt me kya farak hai?
Prompt one-off kaam ke liye hai. Subagent sub-task delegate karne ke liye hai — wo delegation structure hai, procedure nahi. MCP tools connect karne ke liye hai — wo tools aur access deta hai, procedure nahi. Skill repeatable procedure encode karne ke liye hai. Projects broad containers hain — unme procedure nahi hoti. Line kheenchnne ka rule: kaam repeatable procedure hai to Skill, one-off hai to prompt, tools ki kami hai to MCP, delegation hai to subagent.


15Skill library ko organise kaise karein?
Library ko domain aur task ke hisaab se organise karo. Naam saaf ho — naam se hi pata chale Skill kya karti hai. Description saaf ho — kab istemal ho, ye likha ho. Related Skills ko ek saath group karo. Library badi hone par bhi discovery aasan rehti hai kyunki naam aur description hi search ka kaam karte hain. Aur chhoti composable Skills banao — ek monolith ke bajaye.


16Composable Skills ka matlab kya hai?
Composable matlab: chhoti Skills jo workflow me combine ho sakein. Ek badi monolith Skill ke bajaye kai chhoti Skills banao, jinhe chain me joda ja sake. Chhoti Skill test karna aasan hai, reuse karna aasan hai, aur badalna aasan hai. Badi Skill me ek galti poori Skill ko tod deti hai — chhoti Skills me galti ek jagah rehti hai.


17Skill versioning aur maintenance kaise karte hain?
Har version ka naam aur number ho, taaki pata chale kya badla. Har badlaav changelog me likha jaye. Jab agent galat kare, to Skill review karo — failure hi maintenance ka trigger hai. Aur jo Skill ab kaam se match nahi karti, use retire kar do. Maintain na hone wali Skill dheere-dheere galat hone lagti hai — aur galat Skill, Skill na hone se bhi buri hoti hai.


18Business blueprints kya hain — kitne hain?
Blueprints reusable workflow patterns hain — kul aath: Meeting Translator, Project Translator, Brand Guardian, Brief Builder, Lead Processor, Contract Reviewer, Research Digest, aur Interview Digest. Har blueprint me problem, Skill ka kaam, inputs, steps aur output hota hai. Inke peeche ek meta-Skill hai — transcript ko structured, reusable artifact me badalne ki — jiska structure har blueprint me reuse hota hai. Blueprints starting patterns hain, fixed products nahi — inhe adapt karo.


19Workday audit kya hai aur kaise karte hain?
Workday audit me apne typical din ke tasks list karo, phir har task par teen-part test lagao: kya ye repeated hai? Kya ye painful ya inconsistent hai? Kya ise procedure ke roop me describe kiya ja sakta hai? Teenon ka jawaab haan hai, to wo Skill candidate hai. Audit ko paanch categories me sort karo: translate, check, build, process, aur review. Ye audit hi batata hai ki pehle kaunsi Skill banani hai.


20Skill ki value kaise measure karte hain — koi numbers hain?
Haan, book me ek baseline test ke numbers hain: Skill ke bina agent ne lagbhag double wall-clock time liya aur lagbhag 1.6x tokens istemal kiye — aur phir bhi result kam consistent tha. Skill-guided run tez thi, kam tokens me hui, aur consistent thi. Isliye Skill ki value sirf quality nahi hai — time aur token ki bachat bhi hai, saath me consistency. Teenon milkar Skill ka business case bante hain.


21Domain expertise kya hoti hai — sirf facts?
Nahi — domain expertise facts, procedures aur judgment ka combination hai, jo expert ke output ko achha banata hai. Model ko facts pata hote hain, expert ko ye pata hota hai ki kis fact ko kab istemal karna hai, kis kram me kaam karna hai, aur kya 'achha' mana jata hai. Teeno milkar expertise banti hai: declarative (facts), procedural (steps), aur evaluative (quality kaise judge karein).


22Teen tarah ki knowledge me kya farak hai?
Declarative knowledge matlab facts, concepts, terminology aur reference material — 'kya hai' ka jawab. Procedural knowledge matlab steps, sequences aur decision rules — 'kaise karna hai' ka jawab. Evaluative knowledge matlab quality kaise judge karein — 'achha' kaisa dikhta hai aur failure kya hai. Agent kahan fail ho raha hai, usse pata chalta hai kaunsi knowledge chahiye: facts missing hain to declarative, sequence galat hai to procedural, judgment kharab hai to evaluative.


23Expert apni knowledge bol nahi paaye to kya karein?
Examples aur counter-examples use karo. Expert ko achha example dikhao aur poochho 'ye achha kyun hai?', bura example dikhao aur poochho 'ye bura kyun hai?' Unke jawaab se rules infer karo. Aur agent ka output dikhakar corrections karwao — har correction ke peeche ek rule chhupa hota hai. Expert se rules likhwaane ki koshish mat karo; uska kaam dekho aur corrections se rules banao.


24Video-editing example se kya seekhne ko milta hai?
Example me 10-minute-23-second ki workshop recording ka transcript Skill se timeline me badla jata hai. Rule hai ki transcript ka sirf lagbhag 15% hissa load-bearing hota hai — baaki filler hai — isliye sirf load-bearing passages rakhe jate hain. Clips lagbhag 10 seconds ke kaate jate hain aur chaar clips bante hain. Invariants hain: kabhi quote invent mat karo, speaker ke argument ka order mat badlo, aur har clip ko transcript se check karo. Aur edited output ko judge karne ke liye ek rubric di gayi hai.


25Delegation problem kya hai aur Skills delegation loop kya hai?
Delegation problem matlab kaam agent ko de dena bina shared standard ke — tumhe har output khud check karna padta hai, jo delegation ka fayda hi khatm kar deta hai. Skills delegation loop iska jawab hai — paanch steps ka cycle: brief do, execute karwao, verify karo, galti mile to correct karo, aur correction ko Skill me update karo taaki agli baar wahi galti na ho. Loop ka aakhri step — Skill update — sabse important hai, wahi delegation ko ek baar ke kaam se system me badalta hai.


26Work patterns kaunse hain — paanch patterns kya karte hain?
Paanch patterns hain: Transcript Workflow (transcript se structured artifact, source se verified), Research Workflow (sawaal aur sources se sourced answer — findings, limits, next steps), File Creation Workflow (brief se file — document, handout, presentation — templates aur brand rules se checked), Data Analysis Workflow (dataset aur sawaal se analysis — explicit methods aur reproducible result), aur Multi-Skill Workflow (Skills chain me — har Skill ka output agle ka input, handoffs aur checks ke saath).


27Multi-Skill workflow me handoff kyun important hai?
Chain me har Skill ka output agle Skill ka input banta hai. Har handoff par check hota hai: kya output agle Skill ke standard par hai? Agar nahi, to wahi ruk jao — aage badhne se pehle theek karo. Chain utni hi mazboot hoti hai jitna uska sabse kamzor handoff. Bina handoff checks ke ek Skill ki galti poori chain me fail jati hai.


28Wild Skills kya hain aur unhe kaise filter karein?
Wild Skills wo hain jo doosron ne banayi hain — repositories, leaderboards aur posts me. Scale bahut bada hai: GitSkills dataset me July 2026 snapshot ke hisaab se lagbhag 3.8 million Skill files hain, deduplicate karne par lagbhag 1.88 million distinct contents. Filter karne ke teen filters hain: Surprise (koi nayi possibility batati hai?), Usefulness (concrete task me madad milti hai?), aur Verification cost (review aur repair karna khud kaam karne se sasta hai?). Pehla filter 100-star GitHub cutoff hai — lekin stars ko game kiya ja sakta hai, isliye ye guarantee nahi hai.


29Wild Skill istemal karne se pehle safety ke liye kya check karein?
Poori Skill inspect karo — SKILL.md, scripts, references, dependencies, aur files accessed — sab kuch. Ek malicious Skill unintended actions karwa sakti hai ya data bahar bhej sakti hai, kyunki SKILL.md agent ko keh sakti hai ki files padho, commands chalao, ya bahari services se contact karo. Pehle test karo disposable copies par, isolated environment me, limited access ke saath. Seedha real kaam par kabhi mat chalao. Scan ke numbers yaad rakho: 31,132 Skills me 26.1% dangerous aur 5.2% high-severity mile the.


30Preference ko concrete kaise banayein?
Preference tabhi useful hoti hai jab wo decision badle — aur wo bhi ek revisable process ke through. 'Mujhe achha design chahiye' preference nahi hai, wo wish hai. Concrete preference aisi hoti hai: 'agar X ho, to Y karo; agar Z ho, to W karo.' Example: frontend-design Skill me preference concrete thi — oversized serif lettering, ek red italic word, aur specific editorial direction — isse page ka look badla aur wo badlaav inspect kiya ja sakta tha.


31Skill ko 'kab action nahi lena' kyun sikhana chahiye?
Sirf 'kab action lo' sikhana kaafi nahi hai — 'kab mat lo' bhi sikhana padta hai. Rule is form me likho: 'agar ye conditions hain, to X karo; agar nahi hain, to X skip karo.' Example: animation ka rubric — har animation ko batana padta hai ki wo kyun animate ho rahi hai (spatial consistency, state indication, explanation, feedback, jarring changes rokna). Agar purpose sirf 'achha lagta hai' hai aur user use baar-baar dekhega, to animate mat karo. Bina is rule ke Skill har jagah action legi — aur wahi galti hai.


32Disclosure depth ek level kyun rakhni chahiye?
SKILL.md ko agent ko seedha usable content tak le jana chahiye — kisi aur index tak nahi. Book-to-skill Skill ka example hai: core frameworks aur chapter index SKILL.md me, detailed notes alag chapter files me, ek-level hierarchy me. Ek study ke mutaabik child Skills ki hierarchy jodne se koi reliable accuracy gain nahi mila — aur har routing decision ek mauka hota hai galat decide karne ka. Isiliye depth ek level rakho: zyada levels matlab zyada galti ke mauke.


33'Done' ko rubric se define karna kyun zaroori hai?
Bina rubric ke 'done' ka matlab agent khud tay karta hai — aur aksar galat tay karta hai. Rule hai: agent ko observation ka naam batana padta hai jo uske claim ko support karta hai, aur sirf last, most specific claim accept hota hai. Example: 'Bug fixed' ke liye original symptom ka passing test chahiye, aur evidence fresh hona chahiye. Aur agent jo banata hai, use operate karke dikhao — banaya hai to chalakar dikhao. Webapp-testing example me 34 Playwright checks bane aur sab pass hue.


34Bounded reports kya hain — timeline-bound aur question-bound me kya farak hai?
Bounded reports wo hain jinki boundary pehle se tay ho — time-wise ya topic-wise — taaki report focused rahe aur kabhi khatam na hone wali na ho. Timeline-bound ka example monday-brief Skill hai: Monday subah business-pulse snapshot (cash, sales, pipeline) plus week ahead (Calendar aur mail se) — ek one-page document me. Question-bound ka example research-report Skill hai: har source graded hota hai (10–12 Tier-A, 7–9 Tier-B, 7 se neeche reject) aur har non-trivial claim ke saath inline citation hoti hai jiska deep link verbatim passage par jata hai.


35Invoice reconciliation example se kya seekhne ko milta hai?
Example me synthetic data par chhah invoices check kiye gaye — teen matched, teen exceptions unresolved rahe. Point ye hai: partial, honest report confident false completion se behtar hai. Agent ko ye kehna chahiye ki 'teen ho gaye, teen baaki hain' — ye kehne ke bajaye ki 'sab ho gaya' jabki aadha kaam baaki hai. Honest partial completion hi Skill ki pehchan hai.


36Pehli Skill kaise banayein — kahan se shuru karein?
Chapter ki aakhri salaah hai: pehli Skill khud se scratch se banao — bina agent ya automation ke — taaki discipline seekh lo. Ek repeated, painful kaam chuno, uska tareeka likho (goal, non-negotiables, steps, examples, checks), real task par test karo, galti dhoondho, sudharo — aur jab reliable ho jaye, tab share karo. Pehli Skill chhoti honi chahiye — jaise meeting-notes — taaki loop poora dekh sako.
