Preface — Ye kitab kiske liye hai

Ye kitab Model Context Protocol (MCP) ke baare me hai — wo protocol jo language model ko sirf chat box se aage badha kar duniya par action lene wala agent bana deta hai. Kitab haath se, Python me, clients aur servers banate hue sikhati hai — sirf theory padh kar nahi.

Kin ke liye hai?

  • Working developers — jo Python pehle se jaante hain.
  • Engineers — jo AI tools, products aur applications banate hain.
  • Product managers — jo technology ka practical ground samajhna chahte hain.
  • Engineering leaders — jinhe apni team ke liye agentic systems evaluate karne hain.

Kitab ka guiding idea

MCP language model ko structured access deta hai — tools, data aur prompts tak — aur isi se model sirf jawab dene wala nahi, kaam karne wala ban jata hai. Kitab isi transition ko practical, engineering-first tareeke se sikhati hai, uski limits ke saath.

Chatbots se agents tak — RAG aur function calling

Pehle ke language-model products ek chat box the: model apne training data se jawab deta tha, aur aksar galat ya out-of-date hota tha. Uske baad har step ne model ko aur zyada kaam karne ki taakat di — pehle RAG, phir function calling, phir poore agents.

Teen steps ka progression

  • Basic chat: model seedha jawab deta hai — training data se, bina kisi fresh information ke.
  • RAG (retrieval-augmented generation): user ka query intercept hota hai, vector database search hoti hai, aur retrieved passages prompt me paste kar diye jate hain — lekin model sirf text hi produce karta hai.
  • Function calling: model structured tool definitions ki list se chun kar bahar ka code call kar sakta hai — fresh data laana, calculation chalana, ya koi action commit karna jaise message bhejna ya file likhna.

Function calling 2023 ke ChatGPT-plugins experiment ke baad OpenAI API ki first-class feature bani — us experiment ne security problems expose kiye the, isliye function calling ko carefully design kiya gaya.

02.2Ch 1 — Agentic AI aur MCP

Agent kya hai — ReAct loop

Kitab ek bade AI lab ke "Building Effective Agents" framing ko adopt karti hai: agent wo system hai jisme ek large language model apni process aur apne tools ke use ko khud dynamically direct karta hai — task complete karne ka tareeka wo khud control karta hai.

Tool kya hai?

Tool model ke bahar ka koi bhi code hai jise model chun kar invoke kar sakta hai. Tool ke bina model sirf text likh sakta hai; tool ke saath wo duniya par action le sakta hai.

ReAct — Reason, Act, Observe

Agent ki defining structure ek action–feedback loop hai: model reason karta hai, tool se act karta hai, result observe karta hai, aur phir dobara reason karta hai. Ye ReAct ke roop me formalize kiya gaya hai — Reason → Act → Observe — task poora hone tak repeat hota hai.

TIP

Model + tool automatically agent nahi ban jata. Agent ko surrounding loop, memory/context aur apna agla step khud plan karne ki aazadi bhi chahiye.

02.3Ch 1 — Agentic AI aur MCP

Agentic workflows vs agentic approach

Kitab fixed workflows aur genuinely agentic behaviour ke beech farak samjhati hai — ek hi task dono tareekon se kar ke: kisi text ki language detect karo, confidence score do, aur translate karo.

Paanch fixed workflows (path code decide karta hai)

  • Prompt chaining: fixed sequence — detect, phir translate. Kaam karta hai, lekin path pehle se tay hai.
  • Parallelization: kai model calls ek saath chalao aur results combine karo.
  • Routing: ek model call input ko classify karti hai, phir use exactly ek follow-up call ko bhej diya jata hai.
  • Orchestrator–worker: ek model task ko pieces me todta hai, worker model calls ko deta hai, phir answers aggregate karta hai.
  • Evaluator–optimizer: ek generating model aur ek evaluating model — evaluator feedback deta hai, output loop me revise hota hai.

Agentic approach (path model decide karta hai)

Model ko tools (language detection aur translation) aur goal dono de diye jate hain, aur wo khud plan karta hai: pehle detect karta hai, confidence padhta hai, phir translate karta hai. Farak ye hai ki path kaun decide karta hai — code, ya model.

Figure 1-4 me wahi goal model ko tools ke saath diya gaya hai — model khud decide karta hai ki pehle detect kare, phir confidence padhe, phir translate kare. Yehi farak hai: path code ne nahi, model ne tay kiya.

02.5Ch 1 — Agentic AI aur MCP

Agents ka use aur kya enable karta hai

Agents wahan use hote hain jahan task ko planning, decisions aur tool use chahiye — ek jawab nahi, multi-step kaam. Chapter supervised aur unsupervised agents me farak bhi batata hai.

Supervised vs unsupervised

  • Supervised agents: ek insaan dekhta aur steer karta hai (jaise IDE me).
  • Unsupervised agents: goal de kar chhod diya jata hai, wo khud chalte hain.

Examples

  • Coding agents — sabse common. Unsupervised: Claude Code aur OpenAI Codex CLI. Supervised: Cursor, Devin Desktop, aur VS Code me GitHub Copilot.
  • Research agents (deep-research style) — memory, web search aur sub-agents combine karte hain; ek bade AI lab ka Research agent built-in aur user tools ke saath.
  • Customer-service agents — bahut se abhi simple decision trees ya RAG chatbots hain, lekin agentic versions badh rahe hain.
  • Enterprise products ke andar copilots aur assistants.
  • Experimental uses: art projects, AI personalities (example: Bluesky par Void), 3D modelling, embodied/physical agents, aur agents jo doosre systems ke users ki tarah act karte hain.

Agents ko kya enable kiya — teen cheezein

  • Models kaafi achhe ho gaye — plan karna aur tools reliably use karna.
  • Surrounding engineering — tool definitions, context management, memory (short-term chat history aur long-term stored context dono), aur doosre agents ke saath coordinate karne ki ability.
  • Standard interfaces — taaki tools ko har model ke liye dobara na banana pade.

Chapter "Agentic Web" paper ko cite karta hai: agents autonomously act kar sakte hain, judgement use kar sakte hain, environmental feedback use kar sakte hain, doosre agents ke saath coordinate kar sakte hain, aur memory store kar sakte hain.

02.6Ch 1 — Agentic AI aur MCP

MCP ka role — M×N problem aur M+N fix

MCP se pehle har model application ko har tool ya data source ke liye apna connector banana padta tha: M models aur N tools ho to M×N connectors. MCP, Language Server Protocol (LSP) se inspired, ise ek common interface se badal deta hai.

Numbers se samjho

  • MCP se pehle: 3 models × 4 tools = 12 connectors (har pair ke liye alag).
  • MCP ke saath: har model ko ek MCP connector, har tool ko ek MCP server — 3 + 4 = 7 connections.

MCP model ke teen parts

  • Server — tools, prompts aur data provide karta hai, ek common interface se.
  • Client — host application aur server ke beech ka connector.
  • Transport — underlying communication channel.

Host application apne client se tools ki list maangti hai (list-tools operation), aur phir ek tool invoke karti hai (call-tool operation); server kaam karta hai aur result wapas deta hai.

Doosre protocols — competitor nahi, stack ka hissa

  • Google ka Agent-to-Agent (A2A) protocol — agents ke beech communication ke liye.
  • Agent Communication Protocol (ACP) — agent communication ke liye ek RESTful API.
  • Agent Network Protocol — China me develop hua, inter-agent communication ko aasan aur kam brittle banane ke liye.

Ye teeno agents ke aapas me baat karne ke baare me hain, jabki MCP agents ko traditional systems se tools ke through jodta hai. Chapter expect karta hai ki ye protocols ek overall stack ka hissa banenge, jisme individual agents bade multi-agent systems me participate karenge.

03.1Ch 2 — MCP ka Introduction

Context aur context engineering

MCP me context ka matlab hai koi bhi information jo query ke saath model ko di jaye — conversation history, retrieved documents, tool descriptions, system instructions. Context window model ki hard limit hai ki wo ek baar me kitna le sakta hai — tokens me measure hota hai.

Context engineering

Ek mashhoor AI researcher ne "context engineering" term popular kiya: window me kya jaye aur kaise structure ho, ye chunne ki craft — kyunki model jo dekh sakta hai, wahi wo kar sakta hai. MCP, is nazariye se, context ko standard tareeke se deliver karne ka protocol hai.

Isliye MCP sirf "tools jodne ka tareeka" nahi hai — ye context delivery ka standard hai. Agar context galat hai, to model ka decision bhi galat hoga, chahe model kitna bhi achha ho.

03.3Ch 2 — MCP ka Introduction

MCP ke 4 problems + adoption numbers

MCP chaar problems solve karta hai — aur adoption numbers batate hain ki ye kitni tezi se faila: likhte samay official MCP registry me 20,000 se zyada servers the.

Chaar problems

  • 1. Integrations (M×N problem): har pair ke liye connector banane ki jagah, har model aur har tool ke liye ek interface.
  • 2. Distribution: tool author ek MCP server publish karta hai aur koi bhi MCP client use kar sakta hai — har application ke liye alag packaging nahi.
  • 3. Two-way communication: protocol server ko client se wapas baat karne deta hai (jaise model se madad ya decision maangna) — sirf client ka server ko call karna nahi.
  • 4. Standardisation: tools, prompts aur resources har jagah ek hi tareeke se describe hote hain, isliye clients bina custom code ke discover aur use kar sakte hain.

Adoption — likhte samay ke numbers

  • MCP Discord community: 1,250+ members
  • Subreddits: lagbhag 46,000 weekly visitors
  • Specification ka GitHub repo: 8,900+ stars, 78+ active issues
  • Official MCP registry: 20,000+ servers
  • FastMCP version 1 official Python SDK me fold kar diya gaya

Sahi tool chunne ka rule

Plain command-line tool (example: GitHub CLI, gh) kabhi-kabhi MCP server se zyada token-efficient hota hai — aur skills (Markdown instructions jo model ko progressively disclose hoti hain) kabhi behtar mechanism hote hain. MCP har jagah sahi nahi hai.

Chapter me naam liye gaye real servers aur clients: AWS ke MCP servers, GitHub ka official server, Linear, Canva, Blender, Granola; clients: Cline, Cursor, GitHub Copilot aur Devin Desktop.

03.5Ch 2 — MCP ka Introduction

Architecture — host, client, server, primitives

MCP architecture ke teen parts hain: host application (jaise IDE ya Claude Desktop) ke andar ek ya zyada MCP clients hote hain; har client ek MCP server se connect hota hai. Local servers stdio use karte hain; remote servers Streamable HTTP.

Hosts aur clients

Host wo application hai jisse user interact karta hai; client server se connection manage karta hai, model ki requests route karta hai, aur results wapas deta hai. Client capabilities:

  • Sampling — server client/model se text generate karne ko keh sakta hai.
  • Roots — client server ko bata sakta hai ki wo kin directories ya URIs me kaam kar sakta hai.
  • Elicitation — server user se extra information maang sakta hai.

Sampling aur roots 2026-07-28 spec me deprecate kar diye gaye, lekin clients ko unhe kam se kam us version window tak support karna chahiye jo kitab deti hai ("through at least July" agle saal ka, jaise printed hai). Roots security boundary nahi hain — server ko un par bharosa karke model ko limit nahi karna chahiye.

Tool-choice — Auto, Manual, None

LLM providers teen tool-choice modes define karte hain. Chapter ek hi call ko teeno modes me dikhata hai aur batata hai ki har ek kab sahi hai — trade-off hai control vs model ki adaptability.

Teen modes

  • Auto (default): model khud decide karta hai ki tool call kare ya seedha answer de. Open-ended kaam ke liye best.
  • Manual ("required" ya "forced"): client ek tool ka naam deta hai jise model ko call karna hi hai. Useful jab agla step pehle se pata ho — jaise answer dene se pehle hamesha ek record lookup karna.

Rule of thumb: jab tumhe outcome pata ho, Manual use karo; jab path pata nahi, Auto use karo; jab tools ki zaroorat hi nahi, None use karo.

Server ko secure karna — threat model

MCP server attackers ke liye attractive hai kyunki wo model aur real system ke beech baithta hai — aur model ko (prompt injection se) aise tools call karne ke liye trick kiya ja sakta hai jo use nahi karne chahiye. Chapter ke defences, order me:

Defences

  • Model ya client se kuch bhi trust mat karo: har tool argument server side par validate karo (types, ranges, allowed values) — kyunki client security boundary nahi hai.
  • Tool poisoning aur prompt injection: model jo data padhta hai (file, web page, tool result) usme chhupa malicious instruction model se destructive tool call karwa sakta hai. Mitigations: tool descriptions ko hijack ho sakne wale instructions se free rakho, consequential actions ke liye confirmation maango, aur tool results ko data samjho.
  • Destructive tools: jo tools delete, overwrite ya send karte hain, unhe confirmation, dry-run modes ya narrow scope ke saath design karo — aur chapter recommend karta hai ki destructive operation expose hi mat karo jab tak client ko genuinely zaroorat na ho.
  • Authentication aur authorisation (OAuth 2.1): remote servers ko token maangna chahiye aur har request par check karna chahiye; chapter Python SDK server me OAuth resource server add karne ke steps batata hai — authorization server, scopes aur token validation ke saath.
  • Secrets: secrets kabhi log mat karo, tool results me kabhi wapas mat do, aur code ya config files ki jagah environment variables ya secret store me rakho.
  • Input validation aur rate limiting: inputs validate aur bound karo, aur expensive tools ko kitni baar call kiya ja sakta hai, use limit karo.
  • Logging aur auditing: tool calls log karo (secrets ke bina) taaki abuse baad me reconstruct kiya ja sake.
  • Sandboxing: server ko least privilege ke saath chalao — dedicated user, restricted directory, container — taaki compromised server machine ke baaki hisse tak na pahunch sake.

Ye list yaad rakhne layak hai: security ek feature nahi, server design ka hissa hai — pehle din se.

11.1Appendix — Decorators

Functions objects hain + decorators ki neev

Appendix isliye hai kyunki Chapters 5 aur 6 decorators (@mcp.tool(), @mcp.prompt(), @mcp.resource()) se servers banate hain — aur jis reader ne decorators nahi dekhe, wo kho jayega.

Teen foundational ideas

  • Functions are objects: function ko variable me assign kiya ja sakta hai, list me store kiya ja sakta hai, aur kisi bhi value ki tarah pass kiya ja sakta hai.
  • Functions can take functions as arguments: jo function doosra function receive karta hai, wo use call kar sakta hai — callbacks aur decorators ki basis.
  • Functions can return functions: function inner function define karke return kar sakta hai, jo enclosing scope ke variables ko yaad rakhta hai (closure) — ye mechanism hai jo decorator ko us function ka replacement return karne deta hai jise wo decorate karta hai.

Decorator kya hai?

Decorator ek function hai jo ek function leta hai aur naya function return karta hai — aam taur par ek wrapper jo original ko call karne se pehle aur baad me kuch karta hai. Function definition ke upar @name syntax us naam ko decorated result par reassign karne ka shorthand hai.

Appendix ke examples ek simple decorator banate hain jo function ko log ya time karta hai, phir dikhate hain ki @mcp.tool() wahi idea hai: ye plain Python function leta hai, uska naam, docstring aur annotations padhta hai, aur use MCP tool ke roop me register karta hai.

Decorators with arguments + metadata preserve karna

Jab decorator khud arguments leta hai (jaise @mcp.tool() apne parentheses ke saath), to ek aur level jud jata hai — aur metadata preserve karna MCP ke liye critical hai, kyunki tool ki description docstring se derive hoti hai.

Decorators with arguments

Jab decorator khud arguments leta hai, to ek aur level hota hai — ek function jo arguments leta hai aur actual decorator return karta hai. Isliye @mcp.tool() me parentheses hain: pehle arguments wala function call hota hai, phir wo decorator return karta hai.

Preserving function metadata

Wrapper original function ka naam aur docstring chhupa deta hai jab tak decorator unhe copy na kare. Standard tareeka functools.wraps helper hai, jo Appendix dikhata hai — kyunki MCP tool ki description docstring se derive karta hai, isliye jo decorator use kho de, wo bina description wala tool produce karega.

import functools

def my_decorator(func):
    @functools.wraps(func)   # naam + docstring preserve karo
    def wrapper(*args, **kwargs):
        print("call ho raha hai:", func.__name__)
        return func(*args, **kwargs)
    return wrapper

@my_decorator
def add(a: int, b: int) -> int:
    """Do numbers jodta hai."""
    return a + b

# functools.wraps ke bina: add.__name__ == "wrapper",
# docstring gayab — aur @mcp.tool() ko description nahi milti.

Interview FAQs — AI Agents with MCP

36 sawal-jawab jo aaj ke interviews me is kitab ke topics par poochhe jate hain. Har jawab kitab ke content par based hai.

Q1MCP kya hai aur ye language model ko kya deta hai?

MCP (Model Context Protocol) ek protocol hai jo language model ko tools, data aur prompts tak structured access deta hai. Iske bina model sirf apne training data se text generate kar sakta hai; MCP ke saath wo fresh data la sakta hai, calculations chala sakta hai, aur actions commit kar sakta hai — jaise message bhejna ya file likhna. MCP model ko chat box se agent banata hai.

Q2Agent aur chatbot me kya farak hai?

Chatbot ek baar me jawab deta hai — model apne training data se text generate karta hai. Agent ek action-feedback loop me kaam karta hai: model reason karta hai, tool se act karta hai, result observe karta hai, aur phir dobara reason karta hai (ReAct — Reason, Act, Observe). Agent ko surrounding loop, memory/context aur apna agla step khud plan karne ki aazadi bhi chahiye; sirf model plus tool agent nahi banata.

Q3ReAct loop kya hai aur ye kaise kaam karta hai?

ReAct ka matlab hai Reason, Act, Observe — baar-baar repeat hota hai jab tak task complete na ho. Model pehle reason karta hai ki agla step kya ho, phir tool se act karta hai, phir result observe karta hai, aur us observation ke basis par dobara reason karta hai. Kitab ka example: feature.py ke liye tests likhte samay agent loop 1 me file padhta hai, loop 2 me tests likhta hai, loop 3 me tests chalata hai aur failures dekh kar revise karta hai.

Q4M×N problem kya hai aur MCP use kaise solve karta hai?

MCP se pehle har model application ko har tool ke liye apna connector banana padta tha: M models aur N tools ho to M×N connectors. Kitab ka example: 3 models × 4 tools = 12 connectors. MCP ek common interface deta hai — har model ko ek MCP connector aur har tool ko ek MCP server — to 3 + 4 = 7 connections. Ye Language Server Protocol (LSP) se inspired hai.

Q5MCP ke teen parts kaun se hain?

Server — tools, prompts aur data provide karta hai ek common interface se. Client — host application aur server ke beech ka connector, jo connection manage karta hai aur model ki requests route karta hai. Transport — underlying communication channel, local ke liye stdio aur remote ke liye Streamable HTTP. Host application client se tools ki list maangti hai (list-tools) aur phir ek tool invoke karti hai (call-tool).

Q6Context aur context engineering ka matlab kya hai?

Context ka matlab hai koi bhi information jo query ke saath model ko di jaye — conversation history, retrieved documents, tool descriptions, system instructions. Context window model ki hard limit hai ki wo ek baar me kitna le sakta hai, tokens me measure hota hai. Context engineering is window me kya jaye aur kaise structure ho, ye chunne ki craft hai — kyunki model jo dekh sakta hai, wahi wo kar sakta hai. MCP context ko standard tareeke se deliver karne ka protocol hai.

Q7MCP protocol hai ya REST API?

MCP ek protocol hai, REST API nahi — ye distinction kitab me baar-baar aati hai. Protocol messages, lifecycle aur capabilities ke rules define karta hai; ye sirf HTTP endpoints ka set nahi hai. MCP LSP jaisa hai — client ek standard protocol me servers se baat karta hai — lekin MCP ke servers sirf local nahi, remote bhi ho sakte hain.

Q8MCP ke teen server primitives kaun se hain?

Tools — actions, jo model kar sakta hai: API call, code run, file likhna. Resources — data, jo model padh sakta hai: files, database rows, API responses. Prompts — reusable, templated instructions jo user ya model invoke kar sakta hai. Inke alawa do capabilities hain: completions (arguments ki autocompletion) aur logging (server client ko log messages bhej sakta hai).

Q9Sampling, roots aur elicitation kya hain?

Ye client capabilities hain jinhe server consume karta hai. Sampling: server client ke model se text generate karne ko kehta hai. Roots: client server ko batata hai ki wo kin directories ya URIs me kaam kar sakta hai. Elicitation: server user se extra information maangta hai, client form dikhata hai. Sampling aur roots 2026-07-28 spec me deprecate hue. Roots security boundary nahi hain — server ko un par bharosa karke model ko limit nahi karna chahiye.

Q10MCP lifecycle ke teen phases kaun se hain?

Initialization — client aur server versions aur capabilities exchange karte hain, highest common protocol version negotiate karte hain; agree na kar payein to connection fail ho jata hai. Operation — normal exchange: tools/list, tools/call, resources/read, prompts/get. Shutdown — client transport close karta hai, stdio ke liye server process terminate karta hai. 2026-07-28 spec me lifecycle stateless hai aur server ek discovery endpoint expose karta hai.

Q11MCP Inspector kya hai aur ye kyun important hai?

MCP Inspector server ka interactive debugger hai — web UI (terminal aur command-line variants ke saath) jo server ko inspect karta hai aur uske tools, prompts aur resources list karta hai. Ye pehla debugging tool hai jo har server author ko seekhna chahiye, aur testing ka pehla layer bhi hai: Inspector se server ke against haath se exercise karke toota schema ya galat description sabse tez dhoondha ja sakta hai.

Q12MCP client banane ke steps kya hain?

Python 3.13 aur uv package manager use karo, SDK add karo (uv add "mcp[cli]"), phir stdio_client, StdioServerParameters aur ClientSession se session kholo aur list_tools call karo. Phir Client class banao jo sessions aur tools store kare, mcp.json config se connect_to_servers likho (stdio ya remote), tool-use loop add karo jisme LLM call ho, aur ant me cleanup method likho taaki server processes leak na karein. Chapter ke Examples 3-1 se 3-12 ye poora flow step-by-step dikhate hain.

Q13mcp.json file kaisi hoti hai?

Ye ek JSON object hai jisme mcpServers key hoti hai. Har server entry ya to command deti hai (stdio ke liye, jaise uvx plus server package) ya url deti hai (remote Streamable-HTTP server ke liye). Client is file ko padhta hai taaki kaun se servers connect honge, ye data ho — code nahi. Lekin config ko untrusted input samjho: malicious config client ko aise server ki taraf point kar sakti hai jo data exfiltrate kare.

Q14Tool-use loop ka malik kaun hai — client ya server?

Loop ka malik client hai — MCP server sirf tool execute karta hai. Flow: model ko conversation plus tool definitions bhejo; agar wo text de to wo answer hai; agar wo tool call de to tool chalao aur result conversation me append karke model se dobara poochho. Loop par maximum iterations ka cap hona chahiye taaki confused model hamesha loop me na phanse. Chapter ka example trace dikhata hai ki model filesystem tool call karta hai, file contents receive karta hai, aur tabhi answer deta hai.

Q15Tool results ko handle karte samay kya dhyaan rakhna chahiye?

Tool result sirf text nahi hota — ye content blocks ki list hoti hai: text, images, audio aur embedded resources. Har block ko uske type ke hisab se handle karo: text model ko pass karo, binary content save ya display karo, resource ko fetch ya present karo. Content use karne se pehle result ka error flag check karo, kyunki server failure ko exception ki jagah in-band report kar sakta hai. Aur bade results ko truncate ya summarise karo — 100-kilobyte file blindly pass karne se user ka sawal context se crowd out ho jayega.

Q16Tool-choice ke teen modes kaun se hain aur kab kaun sa use karein?

Auto (default): model khud decide karta hai ki tool call kare ya seedha answer de — open-ended kaam ke liye best. Manual (required/forced): client ek tool ka naam deta hai jise model ko call karna hi hai — jab agla step pehle se pata ho, jaise answer se pehle hamesha record lookup karna. None: model ko tools call karne se mana hai, use apne knowledge se answer dena hai — final summary step ke liye ya jab tool use wasteful ya risky ho. Trade-off hai control vs model ki adaptability.

Q17MCP client me OAuth 2.1 ka flow kaise kaam karta hai?

Client server ko bina token ke request bhejta hai aur 401 response pata hai, jisme WWW-Authenticate header authorization server ki taraf point karta hai. Phir client OAuth dance karta hai — authorization URL, user consent, authorization code, token exchange (Python SDK me OAuthClientProvider aur AuthFlow/OAuthClientMetadata helpers) — aur token ke saath retry karta hai. Client tokens store karta hai, expire hone par refresh karta hai, aur browser me flow complete karne wala case bhi handle karta hai. Token lifecycle ka malik client hai; server sirf tokens validate karta hai.

Q18MCP server banane ke liye high-level aur low-level API me kya farak hai?

High level: MCPServer object banao, tools/prompts/resources decorators se add karo (@mcp.tool(), @mcp.prompt(), @mcp.resource()), aur mcp.run() se chalao — ye recommended starting point hai kyunki ye handler registration aur argument validation ka boilerplate hata deta hai. Low level: Server class se explicit handler registration — jab protocol ko exactly dikhana ho ya koi feature high-level API me expose na ho. Low level par tab jao jab unusual handlers ya custom transport behaviour chahiye.

Q19Achha MCP tool kaise design karein?

Tools ko verbs aur specific nouns se naam do, descriptions aise likho jo batayein ki tool kab use nahi karna — sirf kab use karna hai ye nahi — argument list chhoti rakho, aur kai fine tools ki jagah kuch coarse tools prefer karo kyunki model ko unme se chunna hota hai. Model sirf naam, description aur schema dekhta hai — aur kuch nahi — isliye description hi user interface hai. Tool errors ko proper error ke roop me return karo, success ke andar error message chhupa kar nahi.

Q20MCP prompts aur resources me kya farak hai?

Prompts reusable, templated instructions hain jo @mcp.prompt() se register hote hain aur messages ki list return karte hain — user client me prompt chunta hai, arguments bharta hai, aur client resulting messages ko model ko bhejta hai; server ko model ka reply kabhi nahi milta. Resources data hain jo URI par expose hote hain (@mcp.resource("uri://...")), resource template me ek variable hissa hota hai taaki ek handler kai resources serve kar sake — model ya user resource padhta hai aur content context ka hissa ban jata hai. Resources tool list me appear nahi hote.

Q21Lifespan kya hai aur ye kyun zaroori hai?

Lifespan ek context manager hai jo MCPServer constructor ko diya jata hai, server ki lifetime ke aas-paas set-up aur tear-down ke liye. Yield se pehle ka code start-up par chalta hai (jaise database connection kholna), yield ke baad ka code shut-down par chalta hai (connection close karna), aur start-up par banaya gaya object request context me store hota hai taaki tools use kar sakein. Iske bina har tool ko apna connection khud manage karna padta — slow aur error-prone.

Q22Elicitation aur sampling deprecate kyun hue?

Elicitation (server user se information maangta hai) aur sampling (server client ke model se text generate karwata hai) dono 2026-07-28 spec me deprecate hue. Chapter inhe cautiously use karne ko kehta hai. Kitab ka aim durable concepts sikhana hai jo version churn ke baad bhi kaam aayein — isliye in capabilities ko samajhna zaroori hai, lekin naye code me in par depend karna risky hai. Clients ko inhe kam se kam us version window tak support karna chahiye jo kitab deti hai.

Q23MCP server ko test karne ke chaar layers kaun se hain?

Pehla: MCP Inspector — server ke against haath se tools, prompts aur resources exercise karo. Doosra: manual client tests — real client session se connect karke tool call karke result check karo. Teesra: in-memory client — SDK ka in-memory transport ek hi process me client aur server banata hai, bina subprocess aur network, isliye tests fast aur hermetic hote hain. Chautha: unit tests (pytest) — tool functions ko seedha call karke assert karo, plus in-memory client se drive karne wala test. Inke upar Promptfoo-style tool evaluations add karo jo measure karte hain ki model sahi tool chun kar succeed hota hai ya nahi.

Q24Prompt injection aur tool poisoning se server ko kaise bachayein?

Pehle: model ya client se kuch bhi trust mat karo — har tool argument server side par validate karo. Doosra: tool descriptions ko hijack ho sakne wale instructions se free rakho, consequential actions ke liye confirmation maango, aur tool results ko data samjho — kyunki malicious instruction file, web page ya tool result me chhupa ho sakta hai jo model se destructive tool call karwa de. Teesra: destructive tools ko confirmation, dry-run modes ya narrow scope ke saath design karo — aur agar client ko genuinely zaroorat nahi, to destructive operation expose hi mat karo.

Q25MCP server ko share karne ke distribution paths kaun se hain?

Source code/repository — early development ya ek team ke liye, user repo clone karke chalata hai. Package (PyPI/uvx) — general use ke liye stable server, user naam se install karta hai. Container image — system dependencies wala ya remote server, user image pull karke chalata hai. MCP Registry — discovery ke liye, server ka metadata publish karo taaki clients dhoondh sakein. Hosted/remote server — kai users ke liye ya central control chahiye to, user URL se connect karta hai (OAuth ke saath agar required ho). README me configuration snippet dikhao jo user copy kar sake.

Q26JSON-RPC 2.0 ke teen message types kaun se hain?

Request — id hoti hai, response expect karta hai, doosri side se kuch karne ko kehta hai. Response — id request se match karti hai, result ya error ke saath jawab deta hai. Notification — koi id nahi, koi response nahi, one-way fire-and-forget message hai. MCP messages JSON objects hain jinme jsonrpc field "2.0" set hota hai. Client responses ko requests se id se match karta hai — isliye id ka sahi milna protocol ki correctness ke liye critical hai.

Q27Stdio aur Streamable HTTP transport me kya farak hai?

Stdio: client server ko subprocess ki tarah start karta hai aur standard input/output par baat karta hai — ek JSON-RPC message per line (newline-delimited JSON). Sirf local servers ke liye hai, aur stdout par logging nahi karni chahiye (stderr use karo) warna protocol stream corrupt ho jayega. Streamable HTTP: remote transport — client JSON-RPC request ko HTTP POST se bhejta hai, server plain JSON response ya server-sent events (SSE) ka stream deta hai; Mcp-Session-Id header se session identify hoti hai. Rule: local ho to stdio, remote ho to Streamable HTTP — server code wahi rehta hai.

Q28Mcp-Session-Id header ka kya kaam hai?

Streamable HTTP me server Mcp-Session-Id header se session assign kar sakta hai, jise client ko baad ki requests par wapas bhejna hota hai; client session ko explicitly end bhi kar sakta hai. Stdio sessions server process se tied hoti hain — ek process, ek session, process exit karte hi khatm. 2026-07-28 spec me transport by default stateless hai, isliye jise server ko sessions chahiye use unhe explicitly manage karna hota hai.

Q29Apna custom transport kab banana chahiye?

Sirf jab stdio aur Streamable HTTP genuinely fit na hon — jaise embedded device, message queue, ya browser. SDK ek chhota transport contract expose karta hai: read/write primitives, close operation aur session handling. Chapter ek transport scratch se implement karta hai jo in-process queue par JSON-RPC messages carry karta hai, Examples 8-20 se 8-28 me. Lekin custom transport maintenance burden hai aur use dono sides par implement karna hota hai — isliye pehle standard transports try karo.

Q30FastMCP kya hai aur iska SDK se kya relation hai?

FastMCP ek higher-level Python framework hai jiska version 1 official Python SDK me merge ho gaya. Chapter ise server likhne ka sabse tez tareeka batata hai jab SDK ka apna high-level API kaafi na ho — aur kai ideas (jaise lifespan aur context handling) ka source, jinhe SDK ne adopt kiya. Ye MCP ecosystem ka hissa hai, MCP Inspector, Registry aur Promptfoo jaise tools ke saath.

Q31MCP extensions kya hain — server instructions, output schemas, tool annotations?

Extensions protocol me additions hain jo core specification ka hissa nahi hain. Server instructions: ek field jisme server model ko guidance de sakta hai ki use kaise use kare. Output schemas: tool apne result ka shape declare karta hai taaki client use validate kar sake. Tool annotations: hints jaise 'ye tool read-only hai' ya 'ye tool destructive hai', jo model aur client ko decide karne me madad karte hain ki call karein ya pehle user se poochhein. Protocol deliberately extensible hai: server extra capabilities advertise kar sakta hai, aur jo client unhe samajhta nahi, wo safely ignore karta hai.

Q32MCP me contribute kaise karein?

Specification public GitHub repository me hai — changes specification pull requests ke roop me propose hote hain aur community me discuss hote hain (Discord, subreddits, GitHub issues aur discussions). SDKs open source hain — bug fix ya naya transport code ke roop me contribute kiya ja sakta hai. Registry naye servers accept karta hai. Pehle contribution ki advice: chhote se shuru karo — documentation fix, test, ya chhota server — aur proposal se pehle specification aur existing discussions padho, kyunki maintainers backward compatibility aur M×N simplification ko bahut heavily weigh karte hain.

Q33Python decorators ka MCP se kya relation hai?

MCP Python SDK servers decorators se bante hain: @mcp.tool(), @mcp.prompt(), @mcp.resource(). Decorator ek function hai jo ek function leta hai aur naya function (wrapper) return karta hai — @name syntax naam ko decorated result par reassign karne ka shorthand hai. @mcp.tool() plain Python function leta hai, uska naam, docstring aur annotations padhta hai, aur use MCP tool ke roop me register karta hai. Isliye decorators samajhna MCP servers banana samajhne ke liye zaroori hai — Appendix isi liye hai.

Q34functools.wraps kyun zaroori hai MCP tools ke liye?

Wrapper original function ka naam aur docstring chhupa deta hai jab tak decorator unhe copy na kare. Standard tareeka functools.wraps helper hai. MCP tool ki description docstring se derive karta hai — isliye jo decorator wraps use nahi karta, wo bina description wala tool produce karega, aur model ko samajh nahi aayega ki tool kab use karna hai. Decorators with arguments (jaise @mcp.tool() apne parentheses ke saath) me ek extra level hota hai: ek function jo arguments leta hai aur actual decorator return karta hai.

Q35MCP, A2A aur ACP me kya farak hai?

Ye competitor nahi, ek stack ke alag hisse hain. Google ka Agent-to-Agent (A2A) protocol, Agent Communication Protocol (ACP, agent communication ke liye RESTful API) aur Agent Network Protocol — ye teeno agents ke aapas me baat karne ke baare me hain. MCP agents ko traditional systems se tools ke through jodta hai. Chapter expect karta hai ki ye protocols ek overall stack ka hissa banenge, jisme individual agents bade multi-agent systems me participate karenge.

Q36Kitab ke hisab se MCP kab use nahi karna chahiye?

Jab plain API, command-line tool ya agent skills behtar hon. Example: GitHub CLI (gh) jaise plain command-line tool kabhi-kabhi MCP server se zyada token-efficient hota hai. Skills (Markdown instructions jo model ko progressively disclose hoti hain) bhi kabhi behtar mechanism hote hain. Kitab saaf kehti hai ki MCP har integration ka sahi jawab nahi hai — Chapter 2 aur Chapter 9 dono me ye decision rule discuss hoti hai. Sahi tool chunna hi engineering hai.
