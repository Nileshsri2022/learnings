Preface — Harness kya hai

2025 me AI-assisted development me muqabla model se hat kar Harness par aa gaya — model ke aas-paas ka woh system jo use kaam karne layak banata hai. Ye Preface batata hai ki Harness kya hai, uski teen layers kya hain, aur ye book kis ke liye hai — aur kis ke liye nahi.

01.1 — Ye book, abhi kyun?

Pehle muqabla is baat par tha ki kaunsa model sabse strong hai. 2025 me centre shift ho gaya — ab sawal ye hai ki model ke aas-paas ka system kitna reliable hai. Do concrete examples diye gaye hain:

  • July 2025 me Anthropic ne Claude Code ki technical details public talks aur engineering blog posts me share karni shuru ki.
  • July 2025 me hi Anthropic ki agent-engineering team ne ek article publish kiya — "Effective Harnesses for Long-Running Agents" — jiska daava tha ki ek reliable agent zyada tar ek reliable Harness hota hai, sirf ek strong model nahi.

Matlab: model achha hona zaroori hai, lekin kaafi nahi. Jo system model ko gher kar chalta hai, wahi decide karta hai ki agent lambe kaam me bharosemand rahega ya nahi.

01.2 — Harness kya hai

Harness ek single component nahi hai — ye model ke upar ki components ki ek layer hai. Isme aate hain:

  • Context manager — model ko kya dikhega, kitna dikhega
  • Tool registry — kaunse tools available hain aur kaise choose hote hain
  • Permission system — kya karne ki ijaazat hai, kya nahi
  • Message compressor — lambi history ko chhota karke context bachana
  • Lifecycle manager — agent ki zindagi: start, run, stop
Yaad rakhne wali baat

Model "dimaag" hai; Harness "shareer" hai — jo dimaag ko duniya ko dekhne, tools pakadne aur surakshit chalne deta hai. Model khud decide nahi karta ki codebase kaise search kare, context kaise organise kare, ya kya change karne ki ijaazat hai. Ye sab Harness ka kaam hai.

01.3 — Harness abhi kyun matter karta hai

Claude Code Harness idea ka reference implementation ban gaya, kyunki ye shuru se public me bana tha — uska source code open hai, uska engineering blog uske mechanisms samjhata hai. Isliye uski architecture ko padha, samjha aur dobara use kiya ja sakta hai — ek band (closed) product ki tarah nahi, jahan andar kya hai pata hi nahi chalta.

Yehi wajah hai ki poori book Claude Code ko case study ki tarah use karti hai: uske patterns ko samjho, phir apne products me reuse karo.

01.4 — Harness ki teen layers

↓
2. Runtime Environment — HarnessClaude Code ka agentic runtime — loop, context, tools, permissions

Upar application logic hai, beech me Harness (runtime) hai, neeche model hai. Har layer ka kaam alag hai — aur yahi separation poori book ki buniyaad hai.

01.5 — Ye book kiske liye hai

Ye book unke liye hai jo:

  • Claude Code ko heavy use karte hain aur sirf use karne se aage badh kar use samajhna chahte hain
  • Teams jo AI development tools bana rahi hain
  • AI-application engineers jo Claude Code ke patterns ko apne products me reuse karna chahte hain

01.6 — Kya cover nahi hai

Book saaf kehti hai ki ye kya nahi hai:

  • Ye prompt-engineering ki book nahi hai
  • Ye quick-start guide nahi hai
  • Ye Claude Code ke har feature ka survey nahi hai
  • Ye basic use sikhane ki koshish nahi karti — basic use aapko pehle se aana chahiye

01.7 — Book kaise organised hai

  • Chapter 1 — architecture ka overview
  • Chapters 2–6 — Harness ke main components, ek-ek karke: memory, Skills, sub-agents, Hooks, MCP
  • Chapters 7–9 — terminal se aage: headless/CI, Agent SDK, plugins
  • Chapter 10 — team practice: cost, debugging, security aur scale

01.8 — Badlaav ki raftaar par note

Book us waqt likhi gayi jab field bahut tezi se badal raha tha. Isliye version numbers, exact flags aur chhoti details badal sakti hain. Book ka kehna hai: design principles aur architecture kisi ek version ki syntax se zyada matter karte hain. Current details ke liye official documentation check karni chahiye. Ye baat is poori SPA par bhi laagu hoti hai — yahan principles diye gaye hain, har flag ki aaj ki exact spelling nahi.

01.9 — Conventions

Code blocks me commands aur code waise hi dikhaye gaye hain jaise print hue the; inline code ko monospace style me dikhaya gaya hai. Is SPA me bhi wahi style follow ki gayi hai — code blocks dark background me, monospace font me.

Chapter 1 — Claude Code as an Agent Framework

Claude Code ko chatbot samajhna galat hai. Ye ek agent framework hai — jiska core engine ek loop hai, jiske aas-paas context, tools aur permissions ki poori architecture khadi hai. Ye chapter us architecture ko layer by layer kholta hai.

02.1 — Teen mental shifts

Book teen dimaagi shifts se shuru hoti hai — sochne ka tareeka badlo, to kaam karne ka tareeka badal jata hai:

  • Code likhne se agent ko supervise karne tak — aap har line nahi likhte, aap agent ko direction dete ho aur uske kaam ko check karte ho
  • Prompt engineering se Harness engineering tak — ek clever sentence likhne se aage, poora system design karna
  • Tool use karne se system design karne tak — tool chalana nahi, tool ke aas-paas ka system banana

02.2 — Agentic Loop: core engine

Poori system ka core engine ek repeat hone wala cycle hai — Agentic Loop:

FIGURE 1.1 — Agentic Loop
Model sochta hai→ Tool choose karta hai→ Tool call karta hai→ Tool result milta hai→ Wapas sochta hai…
Loop tabhi rukta hai jab model decide kare ki goal poora ho gaya, ya koi limit (jaise maximum-turns limit) hit ho jaye.
Yahi loop woh behaviour possible banata hai jo ek single model call kabhi nahi kar sakti: "error padho, code search karo, fix try karo, test chalao, adjust karo" — har step ke baad dobara sochna.

Ek single model call sirf ek jawab deti hai. Loop khud ko correct kar sakta hai — galat raasta pakda to wapas aakar doosra try kar sakta hai.

02.3 — ReAct: reasoning pattern

Loop ReAct pattern follow karta hai — reasoning-then-acting:

  • Observe — current state ko dekho
  • Reason — agla step kya hona chahiye, ye socho
  • Act — tool ke through action lo
  • Observe — result dekho, phir repeat

One-shot answer se farak ye hai: one-shot answer khud ko correct nahi kar sakta. Loop kar sakta hai — kyunki har action ke baad use naya observation milta hai.

02.4 — Architecture overview

Claude Code ek TypeScript/Node.js application hai — CLI TypeScript me likha hai — jo Anthropic API ke upar bana hai. Do hisse hain:

  • Local runtime (Harness) — context, tools, permissions aur loop ko manage karta hai, aapki machine par chalta hai
  • Remote model — reasoning karta hai, API ke through pahuncha jata hai

02.6 — Five-Layer "Cake Model"

Poora system paanch stacked layers me samjha ja sakta hai — neeche se upar:

FIGURE 1.4 — Five-Layer Cake Model

4. Context LayerContext assemble aur compress karta hai

Har layer ko alag se samjha, tune aur replace kiya ja sakta hai. Ek layer badlo, baaki layers ko farak nahi padna chahiye — yahi achhi architecture ki pehchan hai.

02.7 — Tool Registry

Tools register hote hain — har tool ke saath:

  • Name — tool ka naam
  • Description — tool kya karta hai, kab use karna hai
  • Input schema — JSON Schema, jo batata hai ki tool ko kis format me input chahiye
Key baat

Model ko kisi tool ke hone ka pata hi nahi chalta jab tak woh registry me na ho aur uski description context me visible na ho. Isliye tool choose karna ek context-design problem hai: achhi description tool ko choose karwati hai; vague description use invisible bana deti hai.

02.8 — Permission System

Tool call execute hone se pehle, Claude Code permission rules check karta hai:

  • Kaunse tools allowed hain
  • Kaunsi files/directories allowed hain
  • Kaunsi commands allowed hain

Do decisions alag hain — model ka decision ("main ye chalana chahta hoon") aur Harness ka decision ("ye chalane ki ijaazat hai"). Model chaah bhi le, Harness mana kar sakta hai. Yahi separation security ki buniyaad hai.

02.9 — Two-Half Structure

02.11 — Summary

Chapter ka takeaway: Claude Code ko chatbot nahi, agent framework samjho. Uska core ek loop hai, uske aas-paas context stack, paanch layers, tool registry aur permission system hain — aur Harness deterministic hai jabki model probabilistic hai. Baaki poori book is Harness ko layer by layer kholti hai.

Chapter 2 — Memory System ki Engineering Practice

Har session ek khaali context window se shuru hota hai. Bina memory system ke model har baar project ko dobara seekhta hai, wahi galtiyaan dohrata hai, aur pehle ke decisions se contradict karta hai. Is chapter me memory ko ek file-based, hierarchical, budgeted system ki tarah design karna seekhaya gaya hai.

03.1 — Bhoolne ki problem

Har session khaali dimaag se shuru hota hai — model ko pichhle session ka kuch yaad nahi rehta. Iske nateeje:

  • Model project ko har baar dobara seekhta hai — waqt aur tokens dono waste
  • Wahi galtiyaan repeat hoti hain jo pehle fix ho chuki thi
  • Model pehle ke decisions se contradict karne lagta hai

Isliye memory koi "nice to have" feature nahi hai — lambe kaam ke liye ye zaroorat hai.

03.2 — Insani memory se seekh

Chapter insani memory ko model ki tarah use karta hai:

  • Short-term / working memory — current context window; jo abhi dimaag me hai
  • Long-term memory — disk par files; jo save karke rakha hai
  • Episodic memory — kisi specific session me kya hua tha
  • Semantic memory — project ke baare me general knowledge

Jaise insaan important cheezein likh kar rakhta hai taaki bhoole nahi, waise hi agent ko bhi likh kar rakhna padta hai.

03.3 — Claude Code kaise yaad rakhta hai

Memory model ke andar nahi hoti. Memory files me hoti hai — jo session start par context me load hoti hain, aur jahan configure ho, session ke dauraan dobara load hoti hain. Mechanism file-based aur explicit hai: koi hidden magic nahi, jo file hai wahi yaad hai.

03.5 — CLAUDE.md: project ka "README for the model"

CLAUDE.md ek Markdown file hai jo project root par rehti hai (aur hierarchy me parent directories aur .claude/ directories me bhi ho sakti hai). Ye automatically load hoti hai. Isme woh sab hona chahiye jo ek naye team member ko chahiye hota:

  • Project conventions — kaise code likha jata hai
  • Architecture — project kaise bana hai
  • Commands — install, dev, build, test kaise chalate hain
  • "Do not" rules — kya kabhi nahi karna
CLAUDE.md — minimal skeleton (description se dobara banaya gaya)markdown

## Commands

- Build: <build command>
- Test: <test command>

Code blocks book ke descriptions se dobara banaye gaye hain — verbatim hone ka daava nahi hai. Structure aur headings book ke bataye hue pattern ke hisaab se hain.

03.7 — "Likho ya dobara bolo" rule

Rule

Agar tum ek hi instruction ek se zyada sessions me repeat kar rahe ho, to use memory file me likh do. Agar woh ek-off baat hai, to session me bol do aur permanent memory ko pollute mat karo.

Ye rule memory ko saaf rakhne ka sabse aasan tareeka hai. Repeat hona = likhne layak. Ek baar ki baat = session me hi rehne do.

03.8 — Automatic memory

Claude Code khud apni memories likh sakta hai — jaise ek lambe session ke baad decisions ko summarize karke memory file me daal dena. Ye useful hai, lekin review zaroori hai: model ek galat conclusion ko utne hi confidence se record kar sakta hai jitna sahi ko. Auto-generated memory ko bina padhe trust mat karo.

03.9 — Memory ka khatra

Stale, contradictory ya bahut lambi memory, no memory se bhi buri hai:

  • Context waste hota hai — bekaar tokens load hote hain
  • Model mislead hota hai — purana rule follow karne lagta hai
  • Model outdated rule ko follow karke galat kaam kar deta hai

Remedy: regular pruning (purani cheezein hatao), decisions ko date karo (kab decide hua tha), aur jo rules ab laagu nahi hote unhe hata do.

03.10 — Memory Budget

Budget ki tarah socho — kitne tokens ki memory load karna worth hai? Rule of thumb:

  • Core CLAUDE.md ko chhota rakho — itni chhoti ki ek insaan use kuch minutes me padh sake
  • Detail ko imported files me rakho — jo sirf tab load hon jab relevant hon

Memory ka cost har session me chukana padta hai — har token jo load hota hai, woh har session me cost karta hai.

03.12 — Summary

Memory ek file-based, hierarchical, budgeted system hai. Jo repeat hota hai use likh do, jo stale hai use prune karo, aur core file ko chhota rakho. Memory model ke andar nahi — files me hai. Aur files tum control kar sakte ho.

Chapter 3 — Reusable Skills ki Engineering

Lamba prompt har session me paste karna wasteful hai, maintain karna mushkil hai, aur share karna lagbhag namumkin. Skill iska fix hai — ek packaged, versioned, reusable piece of knowledge jo sirf tab load hota hai jab zaroorat ho.

04.1 — Prompts ki problem

Ek lamba prompt jo har session me paste kiya jata hai, usme teen problems hain:

  • Wasteful — har baar context consume karta hai, har session me

Chapter 5 — Guidelines se Guardrails tak: Hooks se Control

CLAUDE.md me likha rule sirf ek suggestion hai — model use bhool sakta hai, galat padh sakta hai, ya baaton me aakar tod sakta hai. Hook enforcement layer hai: code jo automatically chalta hai aur jisse behes nahi ki ja sakti.

06.1 — Guidelines ki limits

Guideline ek suggestion hai. Model use:

  • Bhool sakta hai — lambi session me rule daba jata hai
  • Misread kar sakta hai — rule ka matlab galat samajh sakta hai
  • Talked out of it ho sakta hai — user ke kehne par rule tod sakta hai

Jo rule kabhi nahi tootna chahiye, use suggestion par chhodna galat design hai. Uske liye enforcement chahiye — aur wahi Hook hai.

06.2 — Hook kya hai

06.9 — Worked example: "No Direct Push to Main" Hook

# stdin se event JSON padho
event = json.load(sys.stdin)
command = event.get("tool_input", {}).get("command", "")

        }

else:
    print(json.dumps({}))  # allow — kuch mat kaho

12.3 — Agentic Loop: ek Möbius strip

FIGURE 2 — "An Elegant Möbius Strip"
Reasoning→ Tool invocation→ Result feedback→ Continued reasoning…
Loop ka koi end nahi — jaise Möbius strip ka koi ek side nahi hota. Reasoning tool ko bulata hai, result reasoning ko wapas bhejta hai, aur cycle chalta rehta hai.
"Reasoning → tool invocation → result feedback → continued reasoning" — ye loop trivial lag sakta hai, lekin ye Claude Code ke saare emergent complex behaviour ki buniyaad hai. Jab model ko ek bug diya jata hai, to woh sirf glance karke guess nahi karta — woh observe karta hai, hypothesise karta hai aur verify karta hai: error logs consult karta hai, relevant code search karta hai, context me delve karta hai, phir fix karta hai. Ye complex behaviour hard-code nahi hai — ye loop structure se emerge hota hai.

Author ka philosophical point: intelligence ek one-off flash nahi hai — ye continuous probing aur correction ka process hai. Engineer loop ke andar ke decisions me intervene nahi kar sakta; woh loop ki constraints design kar sakta hai:

  • Kya perceive kar sakta hai — tool whitelist
  • Kya yaad rakh sakta hai — CLAUDE.md + context management
  • Kya kar sakta hai — permission system
  • Kab rukna chahiye — max-turns + Hooks

Tum loop ke internal decisions ko control nahi karte; tum uski boundary conditions control karte ho. Yahi Harness engineering ka essence hai: behaviour ko program karna nahi, behaviour ko constrain karna.

Book ek tasveer se band hoti hai — ek ustaad kasai ki, jo effortless skill se kaat-ta hai. Woh sirf chaku nahi chalata — woh bail ki haddiyon ko samajhta hai, jaanta hai ki blade kahan enter karna chahiye aur kahan withdraw, aur sinews aur membranes ke beech barely perceptible gaps ko sense kar sakta hai. 14FAQs — Interview Sawal

  
FAQs — Interview Sawal-Jawab

  
36 sawal jo interview me ya kaam me poochhe jate hain — har ek ka seedha, real jawab. Koi placeholder nahi, har jawab book ke content par based hai.

  

    
Q01Harness kya hota hai?
Harness model ke upar ki components ki layer hai — context manager, tool registry, permission system, message compressor, lifecycle manager. Model "dimaag" hai, Harness "shareer" hai jo dimaag ko duniya dekhne, tools pakadne aur surakshit chalne deta hai. Reliable agent mostly reliable Harness hota hai, sirf strong model nahi.

    
Q02Prompt engineering aur Harness engineering me kya farak hai?
Prompt engineering ek clever sentence likhne par focus karti hai — single message ko optimise karna. Harness engineering poora system design karti hai — context, tools, permissions, loop, memory — jo agent ke aas-paas chalta hai. Prompt engineering Harness ka ek chhota hissa ban jati hai, poora kaam nahi.

    
Q03Agentic Loop kya hai aur ye kyun zaroori hai?
Agentic Loop ek repeat hone wala cycle hai: model sochta hai → tool choose karta hai → tool call karta hai → result milta hai → dobara sochta hai. Ye tabhi rukta hai jab goal poora ho ya max-turns limit hit ho. Yehi loop self-correction possible banata hai — ek single model call khud ko correct nahi kar sakti, loop kar sakta hai.

    
Q04ReAct pattern kya hai?
ReAct = reasoning-then-acting. Steps: observe (state dekho) → reason (agla step socho) → act (tool se action lo) → observe (result dekho) → repeat. One-shot answer se farak ye hai ki ReAct har action ke baad naye observation se seekh kar apna plan adjust kar sakta hai.

    
Q05Context Stack me layers kis order me hote hain?
Neeche se upar: (1) system prompt, (2) CLAUDE.md / memory files, (3) conversation history, (4) tool results, (5) current user message sabse upar. Model project ke baare me utna hi jaanta hai jitna is stack me load hai — zyada ya kam, dono nuksaan karte hain.

    
Q06Five-Layer Cake Model ki paanch layers kya hain?
Neeche se upar: (1) Model Layer — Claude model, (2) Runtime Layer — loop aur state manage karta hai, (3) Tool Layer — tools register aur execute karta hai, (4) Context Layer — context assemble aur compress karta hai, (5) Application Layer — CLI / user-facing behaviour. Har layer ko alag se samjha, tune aur replace kiya ja sakta hai.

    
Q07Tool Registry me tool kaise register hota hai aur description kyun matter karti hai?
Har tool naam, description aur input schema (JSON Schema) ke saath register hota hai. Model ko tool ke hone ka pata hi nahi chalta jab tak uski description context me visible na ho. Achhi description tool ko choose karwati hai; vague description use invisible bana deti hai — isliye tool choice ek context-design problem hai.

    
Q08Permission system model ke decision se kaise alag hai?
Model ka decision hai "main ye chalana chahta hoon"; Harness ka decision hai "ye chalane ki ijaazat hai". Tool call execute hone se pehle Harness rules check karta hai — kaunse tools, files/directories aur commands allowed hain. Model chaah bhi le, Harness mana kar sakta hai.

    
Q09Two-Half Structure ka matlab kya hai?
System ke do halves hain: Harness (local, deterministic, code me likha) aur model (remote, probabilistic). Harness ko deterministic aur testable rakhna chahiye, model ko open-ended reasoning karne dena chahiye. Model ko deterministic banane ki koshish mat karo, Harness ko "intelligent" banane ki koshish mat karo.

    
Q10Claude Code har session kyun "bhool" jata hai?
Kyunki har session ek khaali context window se shuru hota hai aur memory model ke andar nahi hoti — memory files me hoti hai. Bina memory system ke model har baar project dobara seekhta hai, galtiyaan repeat karta hai aur pehle ke decisions se contradict karta hai. Isliye CLAUDE.md aur memory files zaroori hain.

    
Q11CLAUDE.md me kya likhna chahiye?
Project conventions, architecture, commands (install/dev/build/test) aur "do not" rules — woh sab jo ek naye team member ko chahiye hota. Ye project ka "README for the model" hai — project root par rehti hai aur automatically load hoti hai.

    
Q12Memory hierarchy me precedence kaise kaam karta hai?
Memory files doosri files ko "@" import se refer kar sakti hain. Order: project CLAUDE.md, phir parent-directory CLAUDE.md, phir user-level memory — jahan conflict ho, zyada specific/local file jeetti hai. Hierarchy ko shallow aur explicit rakhna chahiye.

    
Q13"Write It Down or Say It Again" rule kya hai?
Agar ek instruction ek se zyada sessions me repeat kar rahe ho, to use memory file me likh do. Agar ek-off baat hai, to session me bol do aur permanent memory ko pollute mat karo. Repeat hona = likhne layak hone ka signal hai.

    
Q14Memory Budget kya hai?
Budget ki tarah sochna — kitne tokens ki memory load karna worth hai. Rule of thumb: core CLAUDE.md itni chhoti rakho ki insaan use kuch minutes me padh sake; detail imported files me rakho jo sirf relevant hone par load hon. Stale ya bahut lambi memory, no memory se bhi buri hoti hai.

    
Q15Skill kya hai aur ye prompt se behtar kyun hai?
Skill ek directory hai jisme SKILL.md (frontmatter: name + description) aur supporting files (scripts, references, templates) hote hain. Lamba prompt har session me context khata hai, copies diverge ho jati hain aur share karna mushkil hai. Skill packaged, versioned aur reusable hoti hai — aur sirf invoke hone par load hoti hai.

    
Q16Progressive Disclosure ke teen layers kya hain?
Layer 1 — metadata (naam + description), hamesha visible, cost sirf kuch lines. Layer 2 — SKILL.md body, sirf invoke hone par load hoti hai. Layer 3 — supporting files, sirf tab load hote hain jab instructions unki taraf point karein. Isse context chhota rehta hai.

    
Q17Skill ki description itni important kyun hai?
Description Skill ka "advertisement" hai — model use padh kar decide karta hai ki Skill ko kab invoke karna hai. Agar description me trigger saaf nahi likha, to model Skill ko use karega hi nahi. Description me hona chahiye: kya karta hai + kab use karna hai.

    
Q18Memory, Skill aur Sub-Agent me se kab kya use karein?
Decision rule: agar fact hai (project ke baare me hamesha true) to CLAUDE.md me daalo; agar repeat hone wala procedure hai to Skill banao; agar parallel ya isolated chunk of work hai to sub-agent ko delegate karo. Memory = facts, Skill = procedure, Sub-agent = delegated work.

    
Q19Sub-agent ke paanch modes kaunse hain?
(1) Explore — read-only exploration, koi change nahi. (2) Plan — plan banata hai, execute nahi karta. (3) General-purpose — full agent, read aur write dono. (4) Custom — project-specific prompt se defined. (5) Built-in / specialised — Claude Code ke saath aane wale agents, jaise Explore agent. Har mode ka permission aur tool set alag hai.

    
Q20Sub-agent main agent ko poora transcript kyun nahi lautata?
Kyunki poora transcript main agent ka context bhar dega — wahi problem jise solve karne ke liye delegation kiya tha. Sub-agent sirf summary lautata hai, isliye main context saaf rehta hai. Context isolation hi delegation ka main fayda hai.

    
Q21Delegation kab worth it hai aur kab nahi?
Worth it hai jab sub-agent ka kaam main context ko pollute karta, ya jab parallelism se wall-clock time bachta ho. Worth it nahi hai trivial task ke liye jo main agent ek-do tool calls me kar sakta hai — kyunki har sub-agent apna context le kar aata hai aur token use multiply karta hai.

    
Q22Hook kya hai aur ye guideline se kaise alag hai?
Guideline ek suggestion hai — model use bhool sakta hai ya tod sakta hai. Hook ek script hai jo agent loop ke defined point par automatically chalti hai, stdin se JSON input le kar stdout par allow/block/modify decision deti hai. Guidelines persuade karti hain, Hooks enforce karte hain.

    
Q23Chaar hook events kaunse hain?
(1) PreToolUse — tool execute hone se pehle, block ya modify kar sakta hai. (2) PostToolUse — tool ke baad, result check kar sakta hai. (3) UserPromptSubmit — prompt submit hone par, context add ya prompt block kar sakta hai. (4) Stop — agent rukne wala ho tab, continue karne ko keh sakta hai ya final check laga sakta hai.

    
Q24Hooks fail kyun hote hain? Debug kaise karein?
Zyada tar failures do wajah se: malformed JSON response ya script executable nahi hona. Debug karne ke liye: Hook ke input JSON ko file me log karo, script ko standalone sample JSON payload ke saath test karo, aur exit code / stdout format check karo.

    
Q25MCP kya hai? "USB for AI tools" ka matlab kya hai?
MCP (Model Context Protocol) ek open protocol hai jo standardise karta hai ki model client external tools aur data se kaise baat kare. Jaise USB standard ne har device ko har computer se connect kar diya, waise MCP har server ko har client se connect karta hai — bina N×M bespoke integrations ke.

    
Q26MCP ke teen primitives kya hain?
(1) Tools — functions jo model call kar sakta hai, jaise database query. (2) Resources — data jo model padh sakta hai, jaise file ya database schema. (3) Prompts — reusable prompt templates jo server offer karta hai. Tools sabse zyada use hote hain Claude Code me.

    
Q27MCP me stdio aur HTTP/SSE transport me kya farak hai?
stdio me server local subprocess ke roop me chalta hai — local tools ke liye sabse simple. HTTP/SSE me server remote hota hai aur network se baat hoti hai — shared ya team servers ke liye. stdio setup me simple hai, HTTP/SSE sharing me behtar hai lekin auth aur deployment chahiye.

    
Q28MCP server install karte waqt security ka kya dhyaan rakhein?
MCP servers tumhari permissions se chalte hain — malicious ya buggy server files padh sakta hai, commands chala sakta hai ya data exfiltrate kar sakta hai. Rules: sirf trusted servers install karo, least privilege do, credentials ko config file se bahar (environment variables me) rakho, aur enable karne se pehle review karo ki server kya expose karta hai.

    
Q29Headless mode kya hai? "claude -p" kaise kaam karta hai?
Headless mode me wahi agent loop bina insaan ke chalta hai — prompt command line se ya stdin se diya jata hai, agent chal kar result print karta hai. "-p" (print) flag non-interactive mode chalata hai. Isse Claude Code pair-programmer se CI worker ban jata hai.

    
Q30Text, JSON aur stream-JSON output formats me kya farak hai?
Text human-readable hai — insaan ke liye. JSON ek structured result object deta hai (result text, cost, duration) — CI job ke liye. stream-JSON har event par ek JSON object emit karta hai run ke dauraan — isse CI job progress stream kar sakta hai aur tool calls par real time me react kar sakta hai.

    
Q31Reviewer aur Fixer CI patterns me kya farak hai?
Reviewer CI job PR diff par chalta hai aur review comment post karta hai — kuch change nahi karta. Fixer failing test ya lint error fix karta hai aur PR kholta hai — change karta hai, isliye us par zyada constraints lagte hain: sirf failure se related files, aur merge se pehle review mandatory.

    
Q32Agent SDK kya hai? Claude Code se iska kya rishta hai?
Agent SDK Claude Code ka Harness hai, library ke roop me (Python aur TypeScript). Tum prompt, tools aur permissions dete ho, SDK agentic loop chalata hai. Agar Chapters 1–7 samajh gaye to SDK bhi samajh gaye — farak sirf interface ka hai: CLI ke bajaye programming API.

    
Q33Plugin kya hai aur plugin.json kyun zaroori hai?
Plugin ek directory hai jisme manifest (plugin.json) aur components (Skills, commands, agents, Hooks, MCP configs) hote hain. plugin.json manifest hai — naam, version, description, author aur components ki list. Ye plugin ka contract hai: batata hai ki install karne par tumhare Claude Code me kya add hoga.

    
Q34Plugin install karna trust decision kyun hai?
Kyunki plugin Hooks ship kar sakta hai jo code chalate hain aur MCP servers jo external systems tak pahunchte hain. Install karne se pehle plugin.json aur shipped scripts padho, trusted marketplace prefer karo, aur updates ko accept karne se pehle review karo.

    
Q35Team me Claude Code ka cost kaise control karein?
Pehle measure karo — per session, per task, per developer token usage log karo. Phir control karo: chhoti CLAUDE.md files, kam loaded Skills, chhote contexts, sub-agent budgets. Jo team cost measure nahi karti, woh cost se surprise hogi.

    
Q36Harness engineering ka essence ek line me kya hai?
Behaviour ko program karna nahi, behaviour ko constrain karna. Tum loop ke internal decisions control nahi karte — tum uski boundary conditions control karte ho: kya perceive kar sakta hai (tool whitelist), kya yaad rakh sakta hai (CLAUDE.md + context), kya kar sakta hai (permissions), aur kab rukna chahiye (max-turns + Hooks).
