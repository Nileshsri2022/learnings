01Part I — Foundations & Design

Chapter 1 — Introduction to Agents

Agent kya hai? Software jo environment ko perceive karta hai, reason karta hai, tools se act karta hai, aur results se seekh kar apne goal ki taraf badhta hai — ek jawaab dekar rukta nahi. Is chapter me definition, history, architecture, lifecycle, design compass aur pehla agent — sab kuch hai.

01.1 What Are AI Agents?

Book ki working definition ke chaar traits hain — inme se ek bhi missing ho to wo agent nahi hai:

  • Autonomy — step-by-step instruction ke bina khud kaam karta hai.
  • Goal orientation — sirf reply dene ke liye nahi, ek outcome ki taraf kaam karta hai.
  • Tool use — external systems me state padhta aur badalta hai.
  • Adaptivity — feedback se apna plan badalta hai.

Isi liye sirf jawaab dene wala chatbot agent nahi hai. Lekin ek research assistant agent hai — jo searches plan karta hai, sources check karta hai aur report draft karta hai. Farak ek jawaab aur ek poore kaam ke beech ka hai.

Loop hi agent ki pehchan hai: input aur context ko dekho, plan banao, tool chuno, use chalao, result dekho, state update karo — aur goal milne ya limit aane tak repeat karo. Har iteration ke saath latency, cost, context-window use aur failure ke chances badhte hain — isliye loop ko design karna hi agent design hai.

01.2 A Brief History of Agents

Agent ka idea naya nahi hai — uski lineage lambi hai:

  • 1950s–60s — symbolic agents aur planners.
  • 1980s–90s — reactive aur BDI (belief-desire-intention) agents.
  • 2010s — reinforcement-learning agents.
  • 2020 ke baad — LLM agents.

Milestones jinka zikr hai: Shakey the robot; Deep Blue; AlphaGo aur uska Move 37; OpenAI Five — aur phir 2022–2023 ka shift, jab large language models ne general-purpose reasoning, planning aur tool calling ko bina bespoke planning code ke accessible bana diya.

Sabak ye hai: pehle ke agents narrow aur brittle the kyunki reasoning haath se code karni padti thi. LLMs ne ek general reasoning layer de di — lekin tools, memory aur orchestration ab bhi engineer karne padte hain. Model ne reasoning ki problem hal ki, system ki problem nahi.

History ka matlab: agent ka idea 70 saal purana hai; naya sirf ye hai ki reasoning ab general-purpose hai. Baaki sab — tools, memory, safety — ab bhi tumhe banana hai.

01.3 Why Now?

Teen forces ek saath converge hui — isiliye agents abhi practical hue:

  1. Capable foundation models — long context windows ke saath.
  2. Mature tooling aur APIs — search, code execution, databases aur enterprise systems ke liye.
  3. Business pressure — knowledge work automate karne ki maang.

Aur costs bhi sharply giri hain. Book OpenAI pricing ka example deti hai: GPT-4 lagbhag $5 per million input tokens tha, jabki GPT-4o mini lagbhag $0.15 per million input tokens — lagbhag 33x ki girawat. Multi-step agents tabhi economically feasible hue jab har step ki cost itni gir gayi.

Matlab: agents abhi isliye kaam kar rahe hain kyunki model capable hai, tools taiyaar hain, aur har step sasta hai. Teenon me se ek bhi missing hota to agents abhi bhi demo hi rehte.

01.4 Agents Versus Other Technologies

Agent ko doosri technologies se confuse mat karo — farak saaf hai:

  • Versus chatbots: chatbot turn-by-turn respond karta hai; agent plan karta hai, state rakhta hai, tools call karta hai aur steps ke paar persist karta hai.
  • Versus RPA (robotic process automation): RPA fixed scripts follow karta hai aur screen ya process badalte hi toot jata hai; agent variation aur unstructured input se adapt karta hai.
  • Versus traditional software: aam code deterministic hota hai aur pehle se specify hota hai; agent probabilistic hota hai — isiliye use evaluation, guardrails aur human oversight chahiye.
  • Versus autonomous systems generally: agent autonomy ka software roop hai — physical robot se alag — lekin perception, planning aur safety ki zaroorat dono me ek jaisi hai.

01.5 The Architecture of Agent Systems

Agent system ke core components — ye wahi diagram hai jo Chapter 2 ki Figure 2-1 me dikhaya gaya hai:

  • Foundation model — reasoning ke liye.
  • Prompt / system instruction — role aur rules.
  • Tools — action ke liye.
  • Memory — short-term conversation aur long-term stored knowledge.
  • Orchestrator / loop — agla step decide karta hai.
  • Guardrails — limits aur safety.

Canonical loop ye hai: perceive → reason aur plan → tool select → execute → observe → state update → repeat — jab tak goal na mile ya limit na aaye. Model is system ka ek component hai, poora system nahi — ye baat book baar-baar kehti hai.

Architecture ka sabse aam galat-faith: model ko hi agent samajh lena. Model sirf reasoning karta hai; memory, tools, loop aur guardrails ke bina wo agent nahi hai.

01.7 The Agentic Design Compass

Compass metaphor chaar trade-offs ke liye hai — har ek me ek point chunna padta hai, aur koi universally sahi point nahi hai:

  • Autonomy versus control — agent kitna unsupervised kar sakta hai?
  • Capability versus reliability — zyada powerful behaviour ya zyada predictable behaviour?
  • Generality versus specialization — broad helper ya narrow expert?
  • Speed versus thoroughness — tez jawaab ya careful multi-step kaam?

Sahi point stakes, reversibility aur user ki error tolerance par depend karta hai. Jahan galti irreversible aur mehngi hai, wahan control aur reliability ki taraf jhuko. Jahan galti sasti aur reversible hai, wahan autonomy aur speed ki taraf ja sakte ho.

Compass ko design meeting me istemal karo: har trade-off par team se poochho 'hum kahan hain, aur kyun?' — agar jawaab nahi hai, to design abhi adhura hai.

01.8 Building Your First Agent

Worked example Python me LangChain ke saath hai. Steps:

  1. Install karo LangChain aur related packages.
  2. Agent banao — language model + ek tool, jaise web-search tool.
  3. Prompt define karo — agent ko uska role aur tools ka istemal kaise karna hai, ye batao.
  4. Run karo — ek sawaal par agent chalao aur trace inspect karo: thought, tool call aur observation.

Sabse important teaching point ye hai: trace hi debugging surface hai. Agar agent fail ho, to trace padho — dekho plan galat tha, tool choice galat thi, ya tool ka result galat tha. Bina trace ke tum andhere me debug kar rahe ho.

python
from langchain.agents import create_agent

# Tool: ek simple search function, tool ke roop me wrapped
def search(query: str) -> str:
    """Web par current jaankari dhoondho."""
    return search_api(query)

tools = [search]

# Agent: model + tools + role prompt
agent = create_agent(model, tools)
result = agent.invoke({
    "messages": [{"role": "user", "content": "Aaj ki top khabrein kya hain?"}]
})
# Trace me dikhega: Thought -> Tool call (search) -> Observation -> Answer

Is example me model pehle sochta hai, phir search tool ko JSON arguments ke saath call karta hai, tool observation return karta hai, aur phir model jawaab deta hai. Ye chaar-step trace hi agent ka 'dimaag' hai — use hamesha log karo.

Pehla agent chhota rakho — ek tool, ek workflow. Bada agent pehle din se mat banao; trace padhna seekho, phir scope badhao.

01.9 Conclusion

Is chapter ka nichod: agent autonomous, goal-directed, tool-using behaviour hai jo multiple steps me hota hai. History batati hai ki idea purana hai lekin economics aur generality nayi hai. Design compass aur lifecycle wahi structure dete hain jise baaki book istemal karti hai.

Aage badhne se pehle ye teen sawaal apne project par lagao: (1) kya mera system goal ki taraf steps leta hai ya sirf jawaab deta hai? (2) compass par mera point kahan hai — aur kyun? (3) lifecycle ka kaunsa stage main skip kar raha hoon?

02Part I — Foundations & Design

Chapter 2 — Designing Agent Systems

Design model choose karne ka naam nahi hai — wo trade-offs ki discipline hai. Is chapter me saat principles, build-vs-buy, value/feasibility/risk ka decision framework, aur 21 din me idea se pilot tak jaane ka sprint hai.

02.1 Principles of Agentic Design

Saat principles — har ek ke saath uski failure mode, agar use ignore karo to kya hoga:

  1. User aur outcome se shuru karo, model se nahi. Technically impressive agent jo time na bachaye ya errors na ghataaye, adopt nahi hoga.
  2. Failure ke liye design karo. Agent hallucinate karega, galat tool call karega, data galat padhega — retries, fallbacks aur human escalation banao.
  3. System ko observable banao. Prompts, tool calls, costs aur traces log karo taaki failures reproduce ho sakein.
  4. High-stakes decisions me humans ko control me rakho. Autonomy tabhi badhao jab trust earn ho.
  5. Context limits ka samman karo. Lambi history, bade tool outputs aur retrieved documents ek hi context window ke liye compete karte hain.
  6. Cost aur latency ko shuru se design karo. Har extra reasoning step aur tool call dono ko multiply karta hai.
  7. Minimal viable agent se iterate karo. Pehle narrow, reliable slice ship karo, measure karo, phir scope badhao.
Ye saat principles checklist ki tarah istemal karo — har design review me inme se har ek par ek line likho: 'humne iske liye kya kiya?'

02.2 Choosing What to Build

Decision framework ke chaar sawaal:

  • Value — kya task frequent, painful aur measurable hai?
  • Feasibility — kya data, tools aur APIs available hain?
  • Risk — agent galat ho to kya hoga?
  • Autonomy fit — kya task ko verifiable steps me toda ja sakta hai?

Achhe pehle candidates: high-volume, well-specified, reversible tasks jinke success criteria saaf hon. Kharab candidates: ambiguous, high-stakes, irreversible tasks jinka koi ground truth na ho.

Worked selection example: support-triage agent — jo tickets classify karta hai, knowledge base search karta hai aur replies draft karta hai — achha candidate hai, kyunki volume high hai, draft reviewable hai, aur accuracy measurable hai. Iske ulta fully autonomous refund agent kharab early candidate hai, kyunki action irreversible hai aur financially consequential hai.

Live check

Apne idea par chaaro sawaal lagao. Agar kisi ek ka jawaab kamzor hai, to idea abhi banane layak nahi hai — pehle use strong karo.

02.3 The Build Versus Buy Question

Kab build karo, kab buy karo:

  • Build karo jab agent core differentiator ho, jab data aur workflows proprietary hon, ya jab off-the-shelf tools accuracy ya compliance needs poori na kar sakein.
  • Buy karo / platform use karo jab need generic ho (jaise meeting summarization), jab speed customization se zyada matter kare, ya jab team me agent expertise na ho.
  • Hybrid aam hai: model aur observability layer buy karo, tools aur prompts build karo — kyunki wahi domain knowledge encode karte hain.

Total cost of ownership me sirf license fee nahi aati — model inference, engineering, evaluation, monitoring aur incident handling bhi aata hai. Jo team sirf license fee dekhti hai, wo budget me hamesha kam padti hai.

02.4 Designing Agent Systems in 21 Days

21-day sprint — idea se pilot tak, bina over-build kiye. Har phase ka exit criterion tay hai:

21 din ka matlab jaldi karna nahi hai — matlab hai scope chhota rakhna. Teen hafte me ek narrow pilot, teen mahine me ek bada system nahi.

02.5 Conclusion

Design ek discipline hai trade-offs ki, model choice ki nahi. Value define karo, autonomy deliberately chuno, failure aur observability ke liye design karo, aur scale karne se pehle ek chhote sprint me validate karo.

Aage badhne se pehle apne design doc me saat principles ka checklist banao — har principle ke saamne ek line likho ki tumne uske liye kya kiya. Jo principle khaali rahe, wahi tumhara agla kaam hai.

03Part II — Experience, Tools & Orchestration

Chapter 3 — User Experience Design for Agentic Systems

Agent ka UX sirf chat box nahi hai — wo expectations, time aur trust ko manage karne ka kaam hai. Is chapter me chaar interaction modalities, synchronous vs asynchronous, context retention, capability communication aur trust curve hai.

03.1 Interaction Modalities

Chaar modalities — har ek ki strengths aur limits:

  • Conversational chat: natural, flexible, familiar; open-ended questions aur iteration ke liye best; precise control aur complex state dikhane me weak.
  • Task-based / form-driven: user goal aur parameters specify karta hai, agent kaam karta hai, phir report karta hai; well-defined jobs ke liye best; exploration me weak.
  • Ambient / proactive: agent background me triggers par act karta hai (naya email, schedule change) aur results surface karta hai ya approval maangta hai; monitoring ke liye best; agar triggers opaque hon to surprise aur control kho dene ka risk.
  • Multimodal: voice, image aur text combined; hands-free ya visual tasks ke liye best; cost aur error modes badhata hai.

Sahi choice task structure, user expertise aur intermediate state dikhane ki zaroorat par depend karti hai. Kai products chat ko exploration ke liye aur task views ko tracking ke liye combine karte hain — ek hi modality sab kuch cover nahi karti.

03.2 Synchronous Versus Asynchronous Agents

Synchronous agents same session me seconds me jawaab dete hain. Inhe chahiye: fast responses, streaming, progress indicators aur partial results. Inki limit hai — user ke patience khatam hone se pehle kitne steps le sakte hain, ye limited hai.

Asynchronous agents minutes ya hours me kaam karte hain, completion par notify karte hain, aur lambi research ya multi-system kaam kar sakte hain. Inhe chahiye: task lists, status, cancellation, aur context ke saath resume karne ka tareeka.

AspectSynchronousAsynchronous
ImmediacyTurant jawaab, shared contextDer se jawaab, notify on completion
DepthLimited steps — user intezar nahi karegaLamba kaam, research, multi-system
NeedsStreaming, progress, partial resultsTask list, status, cancel, resume
RiskShallow answerUser ko lagta hai kaam ruk gaya hai

Design rules — chaaro yaad rakho:

  1. Progress honestly dikhao — kaunsa step, kaunsa tool, kya baaki hai.
  2. Kabhi fake progress mat dikhao — jhootha spinner trust todta hai.
  3. User ko interrupt, redirect ya cancel karne do.
  4. Interrupt hone par ab tak ka kaam preserve karo — dobara shuru se mat karwao.

03.3 Context Retention

Users expect karte hain ki agent conversation, preferences aur prior decisions yaad rakhe. Lekin unbounded memory accuracy, cost aur privacy ko nuksan pahunchati hai. Isliye teen levels design karo:

  • Session memory — current task ki memory.
  • Cross-session memory — preferences aur long-term facts, user ke control ke saath.
  • Task memory — in-progress job ka state.

Kya yaad hai, ye expose karo, edit aur delete karne do, aur purana context expire ya summarize karo. Book ki warning saaf hai: silent long-term memory trust ka risk hai — agar user ko pata chale ki agent ne kuch yaad rakha jo wo share karna hi nahi chahta tha, to wo agent use karna band kar dega.

Memory ka rule: jo yaad rakha hai, wo user ko dikhna chahiye — aur delete karne ka button bhi. Chhupi hui memory feature nahi, liability hai.

03.4 Communicating Agent Capabilities

Users wo use nahi kar sakte jo unhe pata hi nahi hai. Book ki recommendations:

  • Onboarding — teen se paanch concrete example tasks dikhao.
  • In-context suggestions — 'Main tumhara calendar bhi check kar sakta hoon' jaisi hints.
  • Capability cards ya help surface — tools aur limits ki list.
  • Honest failure messages — kya try kiya, kya missing hai, ye batao.

Over-promising, under-promising se bura hai: ek claimed capability jo fail ho jaye, trust ko usse tez todti hai jitna ek unclaimed capability jo kabhi use hi na hui ho. Isliye capability list me sirf wahi likho jo tested hai.

03.5 Building Trust

Trust chhote, verifiable steps me banta hai aur ek badi galti me khatm hota hai. Mechanisms:

  • Transparency — sources, reasoning summaries aur confidence dikhao.
  • Control — high-stakes actions par user se approval lo.
  • Consistency — same task, same quality.
  • Recovery — apologize karo, explain karo, corrected action offer karo, aur user ko verify karne do.

Trust curve linear nahi hai: early successes trust ko tez badhate hain, ek visible failure use sharply gira deta hai, aur recovery initial build se slow hoti hai — sirf tabhi jab aage ke tasks succeed hon aur failure explain ki gayi ho.

Live check

Trust ka test: kya tumhara agent apni galti explain karta hai aur corrected action offer karta hai? Agar nahi, to trust build nahi ho raha — sirf use ho raha hai.

03.6 Conclusion

Agents ke liye experience design expectations, time aur trust manage karne ka kaam hai. Task se match karne wali modality aur timing chuno, context ko transparently retain karo, capabilities honestly communicate karo, aur har interaction aise design karo ki user dekh sake, interrupt kar sake aur correct kar sake.

Aage badhne se pehle apne agent ka ek interaction likho — aur usme se user ke teen rights check karo: kya wo dekh sakta hai agent kya kar raha hai? Kya wo rok sakta hai? Kya wo correct kar sakta hai? Teenon ka jawaab haan hona chahiye.

Chapter 5 — Orchestration

Orchestration control layer hai — wo decide karta hai kaunsa agent act kare, kaunse tools dikhein, kis order me, aur kis context ke saath. Achha orchestrator ek modest model ko reliable bana deta hai; kharab orchestrator ek strong model ko unreliable bana deta hai.

05.1 Agent Types

Paanch types — farak ye hai ki wo kaise plan karte hain aur kitna state rakhte hain:

  • Reactive agents: current input par act karte hain, koi plan nahi; tez, simple.
  • Planning agents: goal ko steps me todte hain aur plan execute karte hain, observations se revise karte hain — jaise ReAct.
  • Memory-augmented agents: planning agents + users aur past tasks ki persistent memory.
  • Tool-specialized agents: ek narrow tool set ke aas-paas optimized — jaise code ya data analysis.
  • Multi-agent orchestrators: sub-agents coordinate karte hain — detail Chapter 8 me hai.

Type chun-ne ka rule: sabse simple type se shuru karo jo kaam kar jaye. Reactive se kaam chal jaye to planning mat jodo; planning se chal jaye to memory mat jodo. Har layer cost aur failure modes jodti hai.

05.2 Tool Selection

Model tools ko unki descriptions se select karta hai. Accuracy girti hai jab tool set badhta hai aur jab descriptions overlap karti hain. Techniques:

  • Active set chhota rakho — task ke hisaab se subset par route karo.
  • Descriptions me trigger condition likho — 'use jab user current prices poochhe'.
  • Sahi aur galat istemal ke examples do.
  • Structured output / function calling use karo — taaki arguments typed hon.

Agar do tools ek jaisa kaam karte hain, to unhe merge karo ya unka farak naam me explicit karo. Selection errors ko alag failure class ke roop me log karo — taaki pata chale ki problem model ki hai ya tool descriptions ki.

Tool selection ki galti aksar model ki galti nahi hoti — wo description ki galti hoti hai. Pehle description sudharo, model baad me badlo.

05.3 Tool Execution

Execution ke concerns:

  • Parallelism — independent calls ek step me, dependent calls sequence me.
  • Timeouts aur retries with backoff — har retry ke beech delay badhao.
  • Partial failure handle karo — ek tool fail ho jabki doosre succeed hon, to kya hoga?
  • Concise observations return karo — lambe tool outputs reasoning ke liye context window me jagah kha jate hain.

Pattern ye hai: arguments ko call se pehle validate karo, timeout ke saath execute karo, errors ko catch aur classify karo, aur short, structured result return karo — raw dump nahi. Raw dump context bhar deta hai aur model ko confuse karta hai.

Live check

Apne tool outputs ko dekho: kya wo short aur structured hain, ya poora raw dump aa raha hai? Agar dump hai, to context budget barbaad ho raha hai.

05.4 Tool Topologies

Tools aur agents kaise arrange hote hain — paanch topologies:

  • Single-agent, many tools: simplest, lekin zyada tools se selection degrade hoti hai.
  • Hierarchical: supervisor agent specialist sub-agents ko route karta hai, har ek ka chhota tool set hota hai.
  • Peer / swarm: agents ek doosre ko kaam pass karte hain, koi central controller nahi.
  • Pipeline / sequential: har stage pichhle stage ke output ko transform karta hai.
  • Hybrid: routing ke liye hierarchy + execution ke liye pipelines.

05.5 Context Engineering

Context wo sab kuch hai jo model dekhta hai: system prompt, user input, conversation history, tool outputs, retrieved documents aur memory. Ise engineer karna matlab:

  • Information ko relevance ke hisaab se order karna.
  • History ko summarize ya truncate karna.

06.1 Foundational Approaches to Memory

Memory ke chaar types:

  • Short-term / working memory: current conversation aur task state, context window me rehti hai; tez hai lekin limited hai aur session khatam hote hi kho jati hai.

  • Semantic memory: general knowledge, facts aur documents — aam taur par vector store ya knowledge graph me.
  • Procedural memory: learned skills aur workflows — prompts, playbooks ya fine-tuned behaviour ke roop me encode hoti hai.

Design questions — paanch sawaal har memory design me poochho:

  1. Kya store karna hai?
  2. Kaise index karna hai?
  3. Kab retrieve karna hai?
  4. Kab bhoolna hai?
  5. Kaun dekh sakta hai?

Forgetting ek feature hai, bug nahi: stale facts aur incorrect memories, no memory se bhi buri hoti hain. Jo memory update nahi hoti, wo jhooth bolna shuru kar deti hai.

06.2 Semantic Memory and Vector Stores

Chapter 7 — Learning in Agentic Systems

Agent do tarah se seekhta hai — weights badle bina (jo model dekhta hai use badal kar) aur weights badal kar (fine-tuning se). Pehle wala tez aur reversible hai, doosra persistent hai. Rule: pehle nonparametric try karo, phir fine-tune karo.

07.1 Nonparametric Learning

Nonparametric learning matlab model ke weights badle bina seekhna — jo model dekhta hai, use badal kar: prompt engineering, few-shot examples, retrieval (RAG), aur feedback ya stored trajectories se in-context adaptation.

Advantages: tez, sasta, reversible, aur training infrastructure nahi chahiye. Limits: context length se bounded hai; examples bhool sakte hain ya retrieved text se contradict ho sakte hain; aur underlying model asal me koi nayi skill acquire nahi karta — wo prompt ki duration ke liye uski imitation karta hai.

Techniques: task se similarity ke hisaab se best few-shot examples chun-na; successful trajectories ko playbooks ke roop me store karke retrieve karna; aur feedback se prompt ya tool description ko rewrite karna.

Table 7-1. Nonparametric versus parametric learning

DimensionNonparametricParametric

ReversibilityAasan — prompt edit karoMushkil — retrain karo

Nonparametric ki sabse badi taakat reversibility hai — galat prompt ko ek minute me theek kar sakte ho. Galat fine-tune ko theek karne me din lagte hain.

07.2 Parametric Learning: Fine-Tuning

Fine-tuning weights ko task data par badalta hai. Methods:

  • Supervised fine-tuning (SFT): prompt-response pairs par train karo; format, tone aur tool-calling conventions sikhane ka baseline hai.
  • LoRA (Low-Rank Adaptation): base model freeze karo aur chhoti low-rank adapter matrices train karo — book ka worked method. Key parameter rank r hai, jo adapter size control karta hai. Rank 4 sabse chhota, tez aur least expressive hai; rank 8 balanced default hai; rank 16 zyada expressive hai lekin slow aur overfitting-prone hai; rank 32 aur upar sirf complex domain adaptation me. LoRA practical default hai kyunki sasta, modular (adapters per task swap ho sakte hain) aur base model preserve karta hai.
  • Full fine-tuning: saare weights train karo; sabse zyada capability, lekin expensive, catastrophic forgetting ka risk, aur bada curated data chahiye.
  • DPO (Direct Preference Optimization): chosen aur rejected responses ke pairs par train karo, bina separate reward model ke; model ko behtar answer prefer karna sikhata hai. SFT format sikhata hai, DPO preference sikhata hai — aur SFT phir DPO aam sequence hai.
  • RLHF / RLAIF: human ya AI feedback se reinforcement learning; sabse strong alignment, lekin sabse complex aur expensive.
  • GRPO (Group Relative Policy Optimization) versus PPO: PPO value / critic model istemal karta hai — well understood lekin heavy; GRPO sampled outputs ke groups ko compare karta hai aur critic ko drop karta hai — isliye lighter hai aur reasoning aur tool-use training me zyada istemal ho raha hai, lekin tooling less mature hai.

Worked code: base model aur instruction pairs ka dataset load karo, LoRA adapter ko rank aur target-module list ke saath configure karo, trainer loop se train karo, adapter save karo, aur inference time par agent ke liye load karo. 12.2 Emerging Threat Vectors

Threat vectors — har ek ko alag se test karna chahiye:

  • Prompt injection: user input, documents ya tool outputs me embedded malicious instructions jo agent ko uske task se bhatkati hain.

  • Tool aur MCP compromise: malicious ya compromised tool ya MCP server jo false data return karta hai ya information exfiltrate karta hai.
  • Data exfiltration: agent ko trick karke sensitive data external tool ko bhejna ya kisi document me daalna.
  • Voice cloning aur social engineering: synthetic audio ya text se kisi person ko impersonate karke action authorize karwana; book me ek municipality case cite kiya gaya hai jahan voice cloning fraud attempt me $10,000 se $100,000 ka amount involved tha.
  • Model aur supply-chain attacks: poisoned training ya retrieval data, compromised libraries, aur vulnerable model-serving code.

  • Ek dealership chatbot ko manipulate karke $76,000 ki vehicle $1 me offer karwa di gayi.

12.4 Protecting Data

Data protections:

  • Code execution ko sandbox karo.
  • Agents ko tenant aur privilege ke hisaab se isolate karo.
  • Credentials rotate karo aur per tool scope karo.

Incident response ke liye agents ko chahiye: kill switch, agent ke credentials revoke karne ka tareeka, aur trace-based post-mortem. Bina kill switch ke agent ko rokne ka tareeka kya hai? Agar jawaab nahi hai, to incident ke waqt tumhare paas sirf ummeed hogi.

13.2 Aligning Stakeholders and Driving Adoption

Adoption tab fail hoti hai jab stakeholders aligned nahi hote — chahe agent kaam hi kyun na kare. Steps:

  • Stakeholders ko early involve karo — co-designers ke roop me, sirf testers ke roop me nahi.
  • Success metrics par agree karo — technical accuracy se aage: time saved, user satisfaction, error reduction.
  • Limits honestly communicate karo.
  • Training, feedback loops aur responsive support me invest karo.

Worked example: ek data-enrichment company ne apne coding assistant ka rollout chaar phases me kiya — 50 engineers ka pilot se shuru hua, aur measured success ke baad hi 400 se zyada logon ki team tak expand hua. Sabak: adoption ek co-evolution ki journey hai — log aur agents ek doosre ke saath adapt karte hain, ek saath nahi badalte.

Live check

Apne rollout plan ko dekho: kya pilot chhota hai aur expansion measured success par depend karta hai? Agar rollout ek hi big-bang hai, to adoption risk bahut zyada hai.

13.3 Scaling Collaboration

Agents scopes ke paar scale karte hain — personal se enterprise tak — aur har scope access, autonomy aur governance ko badal deta hai. Ek bade bank ke virtual assistant ka example diya gaya hai jo do billion se zyada customer interactions handle karta hai — ye dikhata hai ki ek well-governed assistant kis scale par operate kar sakta hai.

13.4 Shared Memory and Context Boundaries

Jab agents personal se team aur enterprise scope ki taraf badhte hain, to shared memory zyada powerful aur zyada sensitive — dono — ho jati hai. Rules:

  • Personal agents ke liye default isolated memory rakho.
  • Team memory ko team tak scope karo, explicit boundaries ke saath ki kya share hoga.
  • Decide karo memory upward flow karegi ya local rahegi (personal se team), aur wo flow visible banao.
  • Users ko dekhne, edit karne aur delete karne do — kya unke baare me yaad rakha gaya hai.

Ek team agent jo shared setting me ek private remark recall kar le, trust ko destroy kar deta hai — chahe recall technically correct hi kyun na ho. Memory ka context boundary trust ka boundary hai.

Shared memory ka test: kya tumhara agent ek user ki private baat doosre user ke saamne bol sakta hai? Agar haan, to memory boundaries missing hain.

13.5 Trust, Governance, and Compliance — The Lifecycle of Trust

Trust binary nahi hai — wo evolve karta hai. Shuruaat me wo chhoti successes se badhta hai; ek visible failure use reverse kar sakti hai. Book me ek example diya gaya hai: ek fintech company ne 2024 me lagbhag 700 customer-service roles ko AI chatbot se replace karne ka decision liya, jiske baad empathy aur nuanced judgment ki kami paayi gayi.

Trust build aur repair karne ke mechanisms:

  • Transparency — confidence aur reasoning ke baare me.
  • Progressive delegation — drafts aur suggestions se shuru karo, zyada autonomy sirf sustained success ke baad do.
  • Visible versioning aur change logs — kya badla, kab badla.
  • Trust repair — galti acknowledge karo, explain karo, correct karo, aur user ko verify karne do.

Trust lifecycle ka matlab: trust ek baar jeet kar khatam nahi hota. Har release, har failure, har repair use aage badhata ya peeche le jata hai. Isliye trust ko metric ki tarah track karo — Chapter 10 ke dashboards me.

Live check

Apne agent ki trust story likho: pichhli badi galti kya thi, use kaise repair kiya gaya, aur users ne kaise respond kiya? Agar ye kahani nahi hai, to trust track nahi ho raha.

13.6 Accountability Frameworks

Frameworks invent karne ke bajaye adopt karo:

  • NIST AI Risk Management Framework (AI RMF) — National Institute of Standards and Technology ka voluntary, risk-based approach, jisme downloadable profiles aur worksheets hain system risks map karne ke liye.
  • AI Impact Assessment Template — practitioners aur compliance experts ke saath co-design kiya gaya, EU AI Act aur NIST AI RMF se aligned — system purpose, stakeholder impacts, bias aur fairness checks document karne me guide karta hai.

Auditing: ethical audits structured evaluations hain ethical risks aur unintended consequences ke liye. Inme aata hai: outputs ka evaluation (kya actions goals aur ethical guidelines se align hain?), bias aur fairness checks, decision pathway analysis (agent recommendation tak kaise pahuncha?), aur stakeholder impact assessments. Behavioural assessments audits ko complement karte hain — agents ko real-world scenarios me observe karke, khaas taur par edge cases me.

Audits ongoing aur iterative hone chahiye, one-off nahi — aur independent third-party audits transparency badhate hain. Jo audit ek baar hua aur bhool gaya, wo audit nahi tha, wo event tha.

Logging aur traceability: decision logs (agent ne kyun decide kiya — inputs, intermediate reasoning, outcomes), user interaction logs (inputs aur responses timestamps ke saath), aur error aur failure logs (kab aur kyun agent fail hua ya unintended output diya). Traceability se auditors behaviour reconstruct kar sakte hain aur in sawaalon ka jawaab de sakte hain: agent ne ye outcome kyun recommend kiya? Kis data ne influence kiya? Kya external factors the — jaise API failures ya conflicting instructions? Logs ko protect karna zaroori hai, kyunki unme sensitive data ho sakta hai — aur wo usable aur actionable hone chahiye, sirf complete nahi.

13.7 Escalation Design and Oversight

Escalation wo policy aur infrastructure hai jo agents ko authority ke andar rakhti hai — khaas taur par high-stakes ya ambiguous cases me. Use technical systems aur organizational roles — dono me encode karna chahiye: agents ko defer karna chahiye, poochhna chahiye ya hand off karna chahiye jab confidence low ho, jab action irreversible ho, ya jab policy require kare.

Oversight proactive bhi hai: designated log ya committees agent behaviour monitor karte hain, escalations review karte hain, aur guardrails adjust karte hain. Achhi escalation trust banati hai — kyunki users jaante hain ki agent guess karne ke bajaye defer karega; aur escalated cases agent ko improve karne ke liye feedback source hote hain.

Escalation ka test: apne agent ko ek ambiguous, high-stakes sawaal do. Kya wo guess karta hai ya defer karta hai? Guess karna failure hai — defer karna design hai.

13.8 Privacy and Regulatory Compliance

Regulations — jo book me discuss hain:

  • EU AI Act — risk-based framework jo AI systems ko risk levels me categorize karta hai (minimal, high, unacceptable aur related tiers).
  • GDPR (General Data Protection Regulation) — data minimization, user consent aur personal data par rights.
  • CCPA (California Consumer Privacy Act) — California residents ko data protection aur transparency rights deta hai.
  • HIPAA (Health Insurance Portability and Accountability Act) — healthcare me patient data ke liye strict privacy aur security requirements.
  • Industry standards: PCI DSS payment processing ke liye aur SOX (Sarbanes-Oxley) financial reporting integrity ke liye.

Compliance practices:

  • Automated compliance gates — har build me scan karo disallowed content (jaise PII leakage) ke liye aur prompt tests validate karo.
  • Policy-as-code libraries (jaise Open Policy Agent) — data-use aur privacy rules ko code me likho.
  • Model cards aur datasheets — living build artifacts ke roop me generate karo, lineage, training-data statistics aur known limits ke saath.

Regulations tez evolve karte hain — isliye compliance ko continuously monitor karna chahiye, one-time checklist ke roop me treat mat karo. Jo compliance ek baar check hui aur bhool gayi, wo compliance nahi hai.

13.9 Conclusion: The Future of Human-Agent Teams

Book apna arc recap karke close karti hai: foundations aur design, user experience aur tools, orchestration, memory aur learning, multi-agent scaling, validation, monitoring aur improvement, security, aur aakhir me collaboration. Agents set-and-forget technologies nahi hain — unhe continuously evaluate, improve aur govern karna padta hai.

Future engineers, designers, ethicists, policymakers aur users ke collaboration par depend karta hai. Book ka closing action sequence hai:

  1. Experiment — low-risk domain me agent pilot karo.
  2. Measure — shuru karne se pehle success metrics define karo.
  3. Govern — oversight aur logging jaldi establish karo.
  4. Scale — trust aur autonomy thresholds par iterate karo.

Book ki closing aspiration — apne shabdon me: aise agentic systems banao jo sirf smart nahi, wise hon; sirf efficient nahi, just hon; aur sirf powerful nahi, trustworthy hon. Ye chaar words hi poori book ka test hain — har design decision par inhe lagao.

Live check

Aakhri check: apne agent ko chaar words par test karo — wise? just? powerful? trustworthy? Jo word fail ho, wahi tumhara agla kaam hai.

Interview FAQs


Building Applications with AI Agents par interview me sabse zyada poochhe jaane wale 36 sawaal — har jawaab is book ke content par based hai.




01AI agent kya hota hai — chatbot se kya farak hai?
Agent wo software hai jo environment ko perceive karta hai, reason karta hai, tools se act karta hai, aur results se seekh kar apne goal ki taraf badhta hai — ek jawaab dekar rukta nahi. Uske chaar traits hain: autonomy, goal orientation, tool use aur adaptivity. Chatbot sirf turn-by-turn respond karta hai; agent plan karta hai, state rakhta hai, tools call karta hai aur steps ke paar persist karta hai. Research assistant jo searches plan kare, sources check kare aur report draft kare — wo agent hai; sirf jawaab dene wala bot nahi.


02Agent ka canonical loop kya hai aur har iteration ki cost kya hoti hai?
Canonical loop hai: perceive → reason aur plan → tool select → execute → observe → state update → repeat, jab tak goal na mile ya limit na aaye. Har iteration ke saath latency, cost, context-window use aur failure ke chances badhte hain — isliye loop ko design karna hi agent design hai. Isi liye max steps ki limit lagana, concise observations return karna aur context ko curate karna zaroori hai.


03Agents abhi kyun practical hue — 'why now' ke teen forces kya hain?
Teen forces converge hui: capable foundation models with long context windows; mature tooling aur APIs for search, code execution, databases aur enterprise systems; aur business pressure for automation of knowledge work. Costs bhi sharply giri — GPT-4 lagbhag $5 per million input tokens se GPT-4o mini lagbhag $0.15 per million input tokens tak, lagbhag 33x ki girawat — jisse multi-step agents economically feasible hue.


04Agentic design compass ke chaar trade-offs kaunse hain?
Chaar trade-offs hain: autonomy versus control, capability versus reliability, generality versus specialization, aur speed versus thoroughness. Koi universally sahi point nahi hai — sahi point stakes, reversibility aur user ki error tolerance par depend karta hai. Jahan galti irreversible aur mehengi hai, wahan control aur reliability ki taraf jhuko; jahan galti sasti aur reversible hai, wahan autonomy aur speed ki taraf ja sakte ho.


05Agent application lifecycle ke paanch stages kaunse hain?
Paanch stages hain: Design (problem, users, success metric aur autonomy level chuno), Build (model, tools, prompts, memory banao), Validate (dataset aur human review se component aur end-to-end evaluation), Deploy (monitoring, fallbacks aur human checkpoints ke saath roll out), aur Improve (feedback collect karo, failures analyse karo, prompts/tools/models update karo). Validation aur monitoring afterthought nahi hain — wahi decide karte hain ki agent production me bharosa layak hai ya nahi.


06Agentic design ke saat principles kya hain?
Saat principles hain: user aur outcome se shuru karo, model se nahi; failure ke liye design karo; system ko observable banao; high-stakes decisions me humans ko control me rakho; context limits ka samman karo; cost aur latency ko shuru se design karo; aur minimal viable agent se iterate karo. Har principle ke saath ek failure mode hai — jaise observability ke bina failures reproduce hi nahi hote, aur failure ke liye design kiye bina pehli galti par system toot jata hai.


07Agent banane ke liye kaunsa task achha candidate hai aur kaunsa nahi?
Decision framework ke chaar sawaal hain: value (task frequent, painful aur measurable hai?), feasibility (data, tools aur APIs available hain?), risk (agent galat ho to kya hoga?), aur autonomy fit (task verifiable steps me toot sakta hai?). Achhe candidates high-volume, well-specified, reversible tasks hain — jaise support triage jisme draft reviewable hai. Kharab candidates ambiguous, high-stakes, irreversible tasks hain — jaise fully autonomous refund agent.


08Build vs buy ka decision kaise lein?
Build karo jab agent core differentiator ho, jab data aur workflows proprietary hon, ya jab off-the-shelf tools accuracy ya compliance needs poori na kar sakein. Buy karo jab need generic ho, jab speed customization se zyada matter kare, ya jab team me agent expertise na ho. Hybrid aam hai — model aur observability layer buy karo, tools aur prompts build karo. Total cost me license fee ke saath model inference, engineering, evaluation, monitoring aur incident handling bhi ginno.


0921-day sprint ka structure kya hai?
Sprint paanch phases me hai: Days 1–3 problem definition (interviews, task analysis, success metrics), Days 4–7 prototype (minimal agent, ek tool, ek workflow), Days 8–12 evaluation (test set, accuracy/latency/cost measure karo), Days 13–16 iteration (sabse badi failure class fix karo, guardrails jodo), Days 17–21 pilot (limited users, human review, feedback). Har phase ka exit criterion tay hai — aur sabse aam galti poora period model choice aur prompt tuning me bita dena hai, evaluation data neglect karke.


10Agent UX ki chaar interaction modalities kaunsi hain?
Chaar modalities hain: conversational chat (natural, flexible; open-ended questions ke liye best), task-based/form-driven (user goal specify karta hai, agent kaam karke report karta hai), ambient/proactive (agent background me triggers par act karta hai), aur multimodal (voice, image aur text combined). Sahi choice task structure, user expertise aur intermediate state dikhane ki zaroorat par depend karti hai — kai products chat aur task views ko combine karte hain.


11Synchronous aur asynchronous agents me kya farak hai?
Synchronous agents same session me seconds me jawaab dete hain — inhe fast responses, streaming, progress indicators aur partial results chahiye, aur steps limited hote hain. Asynchronous agents minutes ya hours me kaam karte hain, completion par notify karte hain — inhe task lists, status, cancellation aur context ke saath resume chahiye. Design rules: progress honestly dikhao, kabhi fake progress mat dikhao, user ko interrupt/redirect/cancel karne do, aur interrupt hone par ab tak ka kaam preserve karo.


12Agent me trust kaise banta hai aur trust curve kaisa hota hai?
Trust chhote, verifiable steps me banta hai aur ek badi galti me khatm hota hai. Mechanisms hain: transparency (sources, reasoning summaries, confidence), control (high-stakes actions par approval), consistency (same task, same quality), aur recovery (apologize, explain, corrected action offer karo, user verify kare). Trust curve linear nahi hai — early successes trust ko tez badhate hain, ek visible failure use sharply gira deta hai, aur recovery slow hoti hai, sirf tab jab aage ke tasks succeed hon aur failure explain ki gayi ho.


13Context retention ke teen levels kaunse hain aur silent memory kyun risky hai?
Teen levels hain: session memory (current task), cross-session memory (preferences aur long-term facts, user ke control ke saath), aur task memory (in-progress job ka state). Kya yaad hai, ye expose karo, edit aur delete karne do, aur purana context expire ya summarize karo. Silent long-term memory trust ka risk hai — agar user ko pata chale ki agent ne kuch yaad rakha jo wo share karna hi nahi chahta tha, to wo agent use karna band kar dega.


14LangChain me tool kya hota hai aur agent kaise banta hai?
Tool ek callable function hai jiska naam, description aur typed schema hota hai inputs ke liye. Model tools ko unki descriptions se chunta hai, isliye descriptions precise honi chahiye — kab istemal ho, kya return karega, units aur formats kya hain. Agent banane ke steps: function define karo, use tool ke roop me wrap karo, tools ki list ko agent constructor me model ke saath pass karo, aur invoke karo. Trace me model JSON arguments ke saath tool call emit karta hai, tool observation return karta hai, aur phir model jawaab deta hai. LangGraph explicit graphs deta hai nodes aur edges ke saath branching, loops aur human checkpoints ke liye.


15Tool descriptions achhi kaise likhein aur automated tool generation ke risks kya hain?
Achhi description me trigger condition likho ('use jab user current prices poochhe'), kya return karega ye likho, units aur formats likho, aur sahi aur galat istemal ke examples do. Automated generation OpenAPI specs, database schemas ya function signatures se tools bana sakta hai, lekin risks hain: vague descriptions, cryptic parameter names aur missing error handling. Rule hai: scaffold generate karo, phir haath se naam, description, examples aur error messages edit karo, aur agent ko dene se pehle tool ko isolation me test karo.


16Orchestration kya hai aur agent types kaunse hain?
Orchestration control layer hai — wo decide karta hai kaunsa agent act kare, kaunse tools visible hon, kis order me, aur kis context ke saath. Agent types paanch hain: reactive (current input par act, koi plan nahi), planning (goal ko steps me todte hain, jaise ReAct), memory-augmented (planning + persistent memory), tool-specialized (narrow tool set par optimized), aur multi-agent orchestrators (sub-agents coordinate karte hain). Achha orchestrator modest model ko reliable bana deta hai; kharab orchestrator strong model ko unreliable bana deta hai.


17Tool selection accuracy kaise badhayein jab tools zyada hon?
Accuracy girti hai jab tool set badhta hai aur descriptions overlap karti hain. Techniques: active set chhota rakho aur task ke hisaab se subset par route karo; descriptions me trigger condition likho; sahi aur galat istemal ke examples do; structured output/function calling use karo taaki arguments typed hon. Agar do tools ek jaisa kaam karte hain, to unhe merge karo ya farak naam me explicit karo. Selection errors ko alag failure class ke roop me log karo.


18Tool topologies kaunsi hain aur kaunsi kab chunni chahiye?
Paanch topologies hain: single-agent many tools (simplest, limited tool scale), hierarchical (supervisor specialist sub-agents ko route karta hai; complex multi-step tasks ke liye best), swarm/peer (resilient, flexible; exploratory research ke liye), pipeline/sequential (predictable, testable; document processing ke liye), aur hybrid (routing ke liye hierarchy + execution ke liye pipelines). Topology task ki complexity se chuno, fashion se nahi — simple task par hierarchy ka overhead faayda se zyada hoga.


19Context engineering kya hai aur context budget ka rule kya hai?
Context wo sab kuch hai jo model dekhta hai: system prompt, user input, conversation history, tool outputs, retrieved documents aur memory. Engineering matlab: information ko relevance se order karna, history ko summarize ya truncate karna, tool output ke sirf zaroori fields include karna, aur reasoning ke liye jagah reserve karna. Rule hai: context ek budget hai — history ya tool output par kharch kiya gaya har token reasoning ya answer ke liye available nahi hai — isliye orchestrator ko curate karna chahiye, accumulate nahi.


20Memory ke chaar types kaunse hain aur forgetting feature kyun hai?
Chaar types hain: short-term/working memory (context window me, session ke saath kho jati hai), episodic memory (past interactions aur outcomes, similarity ya time se retrievable), semantic memory (general knowledge, facts aur documents — vector store ya knowledge graph me), aur procedural memory (learned skills aur workflows — prompts, playbooks ya fine-tuned behaviour). Design ke paanch sawaal hain: kya store karna hai, kaise index karna hai, kab retrieve karna hai, kab bhoolna hai, aur kaun dekh sakta hai. Forgetting feature hai — stale facts aur incorrect memories, no memory se bhi buri hoti hain.


21Vector store aur RAG pipeline kaise kaam karta hai?
Embeddings text ko vectors me badal dete hain taaki similar meanings paas baithen. Pipeline hai: documents ko kuch sau tokens ke chunks me todo overlap ke saath, har chunk embed karo, vector + metadata (source, date, owner) store karo, query time par query embed karke top-k chunks retrieve karo, aur model ko do. Key parameters hain chunk size aur overlap, embedding model, distance metric (cosine similarity aam choice hai) aur top-k. Failure modes: fact ko boundary par todne wale chunks, plausible lekin irrelevant retrieval, aur stale documents ka fresh se upar rank karna.


22GraphRAG kya hai aur kab istemal karna chahiye?
GraphRAG knowledge graph ko retrieval ke saath combine karta hai: documents se entities aur relationships extract karke graph banao, related entities ki communities banao aur summarize karo, aur queries me graph traverse bhi karo aur vectors bhi search karo. Ye un sawaalon me madad karta hai jinhe relationships chahiye — jaise kaunse suppliers kaunse plants ko serve karte hain — jahan flat vector search disconnected passages return karta hai. Costs zyada hain, isliye GraphRAG tabhi justified hai jab relationships task ke centre me hon; sirf fact lookup ke liye vector RAG kaafi hai.


23Nonparametric aur parametric learning me kya farak hai?
Nonparametric learning weights badle bina seekhta hai — prompt engineering, few-shot examples, retrieval (RAG) aur stored trajectories se in-context adaptation. Ye tez, sasta aur reversible hai, lekin context length se bounded hai. Parametric learning weights badalta hai — fine-tuning se — jo slow aur persistent hai. Rule hai: pehle nonparametric try karo, phir fine-tune karo jab skill stable, repeated aur measurable ho aur prompt/retrieval changes plateau par aa gaye hon.


24LoRA kya hai aur rank 8 default kyun hai?
LoRA (Low-Rank Adaptation) me base model freeze karke chhoti low-rank adapter matrices train ki jati hain. Key parameter rank r hai: rank 4 sabse chhota, tez aur least expressive hai; rank 8 balanced default hai; rank 16 zyada expressive lekin slow aur overfitting-prone hai; rank 32 aur upar sirf complex domain adaptation me. LoRA practical default hai kyunki wo sasta, modular (adapters per task swap ho sakte hain) aur base model preserve karta hai. Evaluation task success, tool-call accuracy aur format compliance par karo — sirf training loss par nahi.


25SFT, DPO, RLHF aur GRPO me kya farak hai?
SFT (supervised fine-tuning) prompt-response pairs par train karta hai — format, tone aur tool-calling conventions sikhane ka baseline. DPO (Direct Preference Optimization) chosen aur rejected responses ke pairs par train karta hai bina separate reward model ke — preference sikhata hai; SFT phir DPO aam sequence hai. RLHF/RLAIF human ya AI feedback se reinforcement learning hai — sabse strong alignment, sabse complex aur expensive. GRPO (Group Relative Policy Optimization) sampled outputs ke groups ko compare karta hai aur critic ko drop karta hai — PPO se lighter hai aur reasoning aur tool-use training me zyada istemal ho raha hai, lekin tooling less mature hai.


26Multi-agent system kab banana chahiye aur coordination patterns kaunse hain?
Multi-agent tab banao jab tasks distinct skills me decompose hon, jab alag tools ya data access per role chahiye ho, ya jab kaam parallelize ho sake. Rule hai: ek agent se shuru karo aur tabhi split karo jab ek clear bottleneck measure ho — tool selection, context pressure ya skill conflict. Coordination patterns chaar hain: direct handoff, shared memory/blackboard, message passing, aur supervisor control. Communication structured honi chahiye — typed messages jinme task, inputs, expected output aur deadline ho — aur har handoff self-contained aur har result verifiable hona chahiye.


27Agent evaluation me outcome, process aur cost metrics kya hain?
Outcome metrics batate hain kya task succeed hua — jaise task success rate. Process metrics batate hain kya agent ne sahi tools, sahi order me, sahi arguments ke saath istemal kiye — jaise tool-call accuracy. Cost metrics batate hain tokens, tool calls, latency aur dollars — jaise cost per task. Teenon ko ek saath report karo, kyunki ek score trade-offs ko chhupa deta hai — task success 95% ho sakta hai jabki cost 3x ho. Component evaluation me retriever, tool selector, planner aur generator ko isolation me test karo — agar retriever galat hai to prompt tuning answer fix nahi karegi.


28Golden set kya hai aur deployment gates kaunse hain?
Golden set curated real tasks ka set hai expected outcomes ke saath — production logs aur expert review se banao. Deployment gates hain: minimum task-success threshold, tool-call accuracy floor, latency aur cost ceiling, safety aur refusal test pass, aur rollback plan. Example thresholds illustrative hain — golden set par kam se kam 95% tool recall — numbers ko per use case set karo, blindly copy mat karo. Deployment se pehle runbook, agent ka owner aur users ke liye feedback channel bhi chahiye.


29Monitoring stack me kaunse components hain aur OTel kyun zaroori hai?
Reference stack hai: OpenTelemetry (OTel) instrumentation aur traces ke liye, Prometheus metrics ke liye, Loki logs ke liye, Tempo distributed traces ke liye, aur Grafana dashboards aur alerts ke liye. OTel se har agent step — model call, tool call, retrieval — ek span me wrap hota hai jisme model, tool name, token counts aur latency attributes hote hain. Spans ke bina multi-step agent ek black box hai; spans ke saath expensive aur failing steps visible hote hain. Critical requirement hai ki traces, logs aur metrics IDs share karein taaki ek failing task end to end reconstruct ho sake.


30Distribution shifts kaunse hain aur kaise detect karein?
Chaar shifts hain: input shift (users naye tarah ke sawaal poochhne lage), tool shift (API ne schema ya results badal diye), data shift (documents badal gaye, retrieval alag facts return karne laga), aur model shift (provider ne model update kar diya). Detection ke liye statistical tests hain: Kolmogorov-Smirnov (KS) test, Kullback-Leibler (KL) divergence aur Population Stability Index (PSI). Rule hai: baseline set karo, schedule par test karo, aur kisi bhi sustained shift ko investigate karo — quality incident banne se pehle.


31Feedback pipeline aur failure taxonomy kya hai?
Feedback pipeline signals collect karti hai — explicit ratings, corrections, implicit behaviour, support tickets — har signal ko us trace se link karti hai jisne use produce kiya, failure classes me triage karti hai, aur sahi fix ki taraf route karti hai: prompt, tool, retrieval data, model ya UX. Book ki failure taxonomy me ye classes hain: wrong tool, wrong arguments, missing retrieval, hallucinated fact, poor plan, aur UX confusion. Triage hi bottleneck hai — bina taxonomy ke feedback pile hota rehta hai aur use nahi hota.


32MAESTRO threat model ki saat layers kaunsi hain?
Saat layers hain: foundation models (prompt injection, jailbreak), data operations (poisoned documents, leaked training data), agent frameworks (vulnerable orchestration code, insecure tool wiring), deployment and infrastructure (exposed APIs, weak auth), evaluation and observability (tampered metrics, leaked traces), security and compliance (missing audit, policy gaps), aur agent ecosystem (malicious third-party tools, compromised MCP servers). Attack kisi bhi layer se aa sakta hai — isliye defence har layer par chahiye.


33Prompt injection ke types kaunse hain aur indirect injection khaas kyun hai?
Types hain: direct prompt injection (user input me malicious instructions), indirect prompt injection (injection retrieved document ya tool result se aata hai — user se nahi), jailbreaks (crafted prompts jo safety instructions ignore karwate hain), tool/MCP compromise, data exfiltration, voice cloning aur social engineering, aur model/supply-chain attacks. Indirect injection khaas hai kyunki wo input filters ko bypass kar jata hai — injection user ne nahi, ek document ya tool ne bheja hai, jise system trusted manta hai.


34Agent security me defence in depth ka matlab kya hai?
Defence in depth matlab chhah layers par controls: input (validation, injection detection, rate limiting), model (system prompt, guardrails, output filtering), tool (allow-listing, approval for writes, argument validation), data (least privilege, encryption, redaction, access control), monitoring (anomaly detection, audit logs, alerting), aur governance (policies, training, incident response). Ek layer fail ho to doosri pakde. Agent-level controls me kill switch, credentials revoke karne ka tareeka aur trace-based post-mortem bhi aata hai.


35Human roles executor se governor tak kaise evolve karte hain?
Chaar roles hain: Executor (human har output review karta hai, autonomy minimal), Reviewer (key outputs spot-check karta hai, autonomy moderate), Collaborator (priorities guide karta hai, jointly annotate karta hai, autonomy high), aur Governor (policy set karta hai, decisions audit karta hai, autonomy governance rules ke andar). Interfaces, training aur governance ko role ke saath badalna chahiye — executor ko step-by-step guidance chahiye, governor ko policy screens, audit logs aur explainability tools.


36Agent adoption kaise drive karein aur scaling me governance kaise badhayein?
Adoption ke steps: stakeholders ko early co-designers ke roop me involve karo, success metrics par agree karo (time saved, user satisfaction, error reduction — sirf accuracy nahi), limits honestly communicate karo, aur training, feedback loops aur support me invest karo. Rollout chhote pilot se shuru karo aur measured success ke baad hi expand karo. Scope badhne ke saath governance bhi badhni chahiye — personal scope me user-managed preferences kaafi hain, organizational scope me governance board review chahiye.
