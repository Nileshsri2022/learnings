Preface — Ye kitab kis liye hai

Evaluation AI engineering ki ek central lekin under-taught skill hai — aur ye kitab use ek repeatable process banati hai.

Is kitab se kya ummeed rakhein

Evaluation AI engineering ki ek central lekin under-taught skill hai. Jo model likhne me sabse achha hai, woh har kaam me sabse achha ho — ye zaroori nahi. Teams ko systematic tareeke chahiye ye batane ke liye ki kya achha hai, kya kharab hai, failures kahan hain, aur aage kya badalna hai. Ye kitab un logon ke liye hai jinhe pehle se chal raha LLM system behtar banana hai — sirf naya system banana nahi.

Ye kitab kya nahi hai

  • Ye existing benchmark leaderboards ya academic papers ka survey nahi hai.
  • Ye model-building ki kitab nahi hai.
  • Ye sirf prompt engineering ka guide nahi hai.
  • Ye sikhati hai: quality ke baare me kaise sochein, human judgement ko ek loop me kaise laayein, aur phir us judgement ko automate karke scale par, baar-baar kaise lagayein.

Baar-baar aane wala workflow

Poori kitab ek hi chakkar par chalti hai — identify important problems → gather evidence → generate hypotheses → make a change → re-measure → iterate. Matlab: pehle important problem pehchano, saboot ikattha karo, andaza lagao ki kya galat hai, ek badlav karo, phir se measure karo, aur dobaara karo.

Ye kitab kahan se aayi

Preface me ye bhi saaf likha hai ki unhone zyadatar cheezein asli products ko evaluate karke seekhi hain, sirf theory padhkar nahi.

  • Evaluation theory ki gehri background zaroori nahi hai — kitab shuru se sikhati hai.

Ch 1 — Introduction: Evaluation kya hai

Evaluation ka matlab hai explicit judgement banana ki LLM system apna kaam, us specific situation me, kitna achha kar raha hai — benchmark score se aage.

Evaluation kya hai?

Evaluation ek discipline hai — explicit judgements banana ki LLM system apna kaam, us specific situation me jahan use hona hai, kitni achhi tarah kar raha hai. Ye teen cheezon se alag hai:

  • Code chal raha hai ya nahi — ye check karna ki code run hota hai, evaluation nahi hai.
  • Public benchmark — benchmark par high score ka matlab ye nahi ki system aapke specific user, task ya data par achha kaam karega.
  • Vibes — "lagta hai achha hai" koi evaluation nahi hai; judgement explicit aur repeatable hona chahiye.

Do examples jo baat samjhate hain

1. Airline chatbot case: ek airline ke chatbot ne ek yatri ko bataya ki woh flight ke baad bereavement discount ke liye apply karke reimbursement le sakta hai — jabki airline ki apni site par likha tha ki discount travel se pehle request karna hota hai. Chatbot ka jawab galat tha, aur airline ko iske liye zimmedar thehraya gaya. Sabaq: plausible-sounding lekin galat jawab ke asli legal aur financial consequences hote hain.

2. Dog wali website: LLM se kaha gaya ek aisi website ka code likho jo kutte ki tasveer render kare — aur jo code mila woh chala hi nahi. Ye failure turant dikh gaya. Kitab isse contrast karti hai un failures se jo mushkil se dikhte hain — galat facts, halki-si galat salah. Aasan failures pakadna aasan hai; chhupa hua galat hona hi asli khatra hai.

AI application ke lifecycle me evaluation

Evaluation ek aakhri check nahi hai — har stage par alag sawal, alag data, aur alag tarah ki galtiyan hoti hain:

StageIs stage par kya hota haiEvaluation ka focus
PretrainingFoundation model ko train karnaModel ki base capabilities — broad, general checks
Post-trainingFine-tuning / instruction tuning / alignmentInstruction follow karna, safety, alignment
Application developmentPrompting, retrieval, tools, agentsYahan engineer ka sabse zyada control hai — kitab ka focus yahi hai

Kitab ka focus application level par hai, kyunki wahan engineers ke paas sabse zyada control hota hai — prompt, retrieval, tools, agents sab badle ja sakte hain.

Kaun evaluate karta hai?

Koi ek group akele sab kuch nahi jaanta. Evaluation me ye sab shamil hote hain:

  • End users — jo system ko asal me istemal karte hain.
  • Engineers — jo system banate hain.
  • Domain experts / subject-matter experts (SMEs) — jo jaante hain ki us domain me sahi jawab kaisa dikhta hai.
  • Stakeholders — jo consequences jhelte hain.

Kitab ka kehna hai: domain experts ko process me jaldi laao — warna engineers aise metric ke liye optimize karenge jise experts trust hi nahi karte.

The Three Gulfs of Evaluation — chapter ka central model

Ye teen gulfs ek lens hain, checklist nahi. Achhi evaluation ka kaam hai teeno ko chhota karna.

Analyze–Measure–Improve Flywheel

Is loop ko chalte rehna hai — ek evaluation kaafi nahi, kyunki system, data aur users — teeno badalte rehte hain.

Kitab likhte hue lekhakon ne kya seekha

Evaluation pehle ek human problem hai, technical baad me — "achha" ka matlab tay karna, logon ko sehmat karna, aur asli outputs dekhne ki aadat banana. Aur ek humility bhi: jo method ek context me kaam kare, woh doosre me transfer ho — ye zaroori nahi.

Summary

Evaluation = explicit judgement, specific situation me. Benchmark ≠ real performance. Teen gulfs (execution, representation, assessment) har test ko distort kar sakte hain. Flywheel — analyze, measure, improve — ko baar-baar ghumao.

Ch 2 — LLMs aur Evaluation Basics

Agent ek system hai — model, prompt, tools, memory aur app code. Failure kisi bhi component se aa sakta hai, aur evaluation ko batana hoga ki kahan se aaya.

LLM agent ke components — poori kitab ki vocabulary

"Agent" sirf ek model nahi hai — ye ek system hai. Failure kisi bhi component se aa sakta hai, aur evaluation ko ye batana hoga ki failure kahan se aaya.

ComponentKya haiKahan fail ho sakta hai (Table 2-1)

Prompt / system promptModel ko diye gaye instructions aur contextAmbiguous prompt — model samjha hi nahi kya chahiye
ToolsFunctions ya APIs — web search, database queryGalat tool chuna, ya galat arguments diye
MemoryTurns ke paar yaad — short-term history + long-term stored factsPurana ya galat fact yaad raha
Application codeRetrieval, routing, guardrails, UIIrrelevant documents retrieve hue, ya guardrail ne galat roka

Prompting ke fundamentals

Prompt ek single string nahi hai — ye design choices ka set hai: system instructions, user ka message, examples (few-shot), formatting constraints, aur tool descriptions. Wording, order ya examples me chhota sa badlav output ko bahut badal sakta hai. Isliye prompt khud system ka hissa hai jise evaluate karna hai — koi fixed background condition nahi.

Running example — math tutor ka prompt

Chapter ek math tutor ke system prompt ko running example banata hai: ek prompt jo model ko helpful rehne ko kehta hai, wohi prompt jo model ko accurate rehne ko kehta hai — dono me takraav ho sakta hai. Helpful hone ke chakkar me model seedha jawab de de (student seekhe bina), accurate rehne ke chakkar me woh hint de. Evaluation ko tay karna hota hai ki kaunsa matter karta hai — aur yehi tay karna evaluation ka kaam hai.

Evaluation setups — 4 tareeke

SetupKya hota haiKab istemal karein
Offline evaluationFixed test inputs ko system ke ek version par chalakar score karnaDo versions ko same conditions me compare karne ke liye
Online evaluationProduction me asli users ko dekhna — thumbs up/down, retry, complaintsWild me regressions pakadne ke liye
Human evaluationLog outputs padhkar judge karte hainYe define karne ke liye ki 'achha' ka matlab kya hai — sabse flexible, lekin sabse slow aur mehenga
Automated evaluationCode checks aur LLM judgesTez aur sasta — lekin systematic tareeke se galat ho sakta hai

Zyadatar teams ko combination chahiye hota hai. Choice is baat par depend karti hai ki aap kya seekhna chahte hain: offline tests versions compare karne ke liye, online signals real-world regression ke liye, human judgement "achha" define karne ke liye.

Worked example — math tutor ko judge kaise karein

Chapter tutor ke system prompt ko dikhata hai, ek output dikhata hai, aur poochta hai: aap isko judge kaise karoge? Wahi output chaar cheezon par judge ho sakta hai — correctness (jawab sahi hai?), pedagogy (kya student ko seekhne me madad mili, ya sirf jawab mil gaya?), tone, aur safety. Criteria explicit kiye bina alag-alag judges disagree karenge — isliye criteria pehle likhna zaroori hai.

Putting It Together — shuru karne ki checklist

  1. Asli inputs ka ek chhota, representative set chuno.
  2. Un inputs ke liye kuch criteria define karo jo matter karte hain.
  3. Automate karne se pehle outputs ko khud dekho.
  4. Tabhi automated test banao.
Warning: ek bada, impressive-looking benchmark se shuru mat karo jo real task se match hi nahi karta. Chhota lekin real set, bade lekin irrelevant benchmark se behtar hai.

Summary

Agent = model + prompt + tools + memory + app code. Prompt system ka hissa hai. Offline, online, human aur automated — chaaron setups ka apna kaam hai. Pehle khud outputs dekho, phir automate karo.

Ch 3 — Error Analysis

Automated evaluator banane se pehle asli outputs ko dekho: label karo, group karo, gino — aur tab criteria banao. Ye flywheel ka Analyze step hai.

Error analysis kya hai?

Error analysis disciplined practice hai — asli outputs ko dekhna, galtiyon ko group karna, aur un groups se tay karna ki pehle kya fix karein. Ye flywheel ka "Analyze" step hai, aur kitab ka kehna hai ki ye automated evaluators banane se pehle aana chahiye — warna aap galat cheezon ke liye test automate kar doge.

Running example — real-estate CRM assistant

Users apne contacts, listings aur deals ke baare me sawal poochte hain; assistant ko CRM data se jawab dena chahiye, details invent nahi karni chahiye. Is example se chapter dikhata hai ki "assistant aksar galat hai" jaisi vague feeling kaise named, countable failure types me badalti hai.

Data ko label karna

Labels ek output me kya galat (ya sahi) hua, uske short, human-readable naam hain. Qualitative research se do coding techniques:

  • Open coding — bina pre-set categories ke outputs padhna aur jo failure dikhe use apne shabdon me likhna. Isse woh failure modes milte hain jinki aapne ummeed hi nahi ki thi.
  • Axial coding — un open codes ko chhote se set me group karna, aur unke beech ke relationships describe karna. Example: "hallucination" do hisson me bat-ta hai — "fact invent kiya" vs "retrieved document ko galat padha".

Advice: automate karne se pehle kam se kam kuch dozen examples label karo, aur labels ko domain experts ki bhasha ke kareeb rakho.

Error analysis ka process — step by step

Saturation: padhte raho jab tak naye traces se naye categories aana band na ho jaayein — ye signal hai ki us sample ke zyadatar failure modes dekh liye.

Labels se criteria tak

Ek label evaluation criterion ban jata hai jab use ek testable judgement ke roop me likha ja sake. Example: "jawab me sirf woh facts hone chahiye jo retrieved CRM records me dikhte hain" — ye ek aisa criterion hai jise human ya LLM judge naye outputs par laga sakta hai.

Do extremes se bacho: bahut vague criterion ("helpful bano") inconsistently apply hoga; bahut narrow criterion asli failure ko miss kar dega.

Eval set banane ke dimensions

Achha eval set un combinations ko cover karta hai jo production me asal me hote hain — sirf aasan wale nahi.

Apna eval set banana

  • Seed ke roop me lagbhag 100 real queries se shuru karo (chapter me diya gaya number).
  • Unhe label karo, aur labelled traces se eval set banao — labels, inputs aur expected behaviour ko saath rakho taaki set dobaara use ho sake.
  • Automate karne se pehle kam se kam kuch dozen examples label karo.
  • Labeling aur revision ke 2–3 rounds se guzro.
  • Pehle simple binary judgement (acceptable / unacceptable) use karo — fine-grained Likert scale se nahi, kyunki binary par sehmati banana aasan hai. Likert scale ki problems Chapter 4 me hain.

Summary

Pehle dekho, phir label karo, phir group karo, phir gino, phir criteria banao. ~100 real queries se seed lo, saturation tak padho, aur binary judgement se shuru karo.

04Part II · Analyze

Ch 4 — Collaborative Evaluation Practices

Domain experts source of truth hain, criteria par sehmati iterative process se banti hai, aur agreement ko chance se correct karke measure karo.

Kaun evaluate kare?

Jin logon ko pata hai ki sahi jawab kaisa dikhta hai (domain experts / SMEs), wohi source of truth hone chahiye — lekin aksar wohi log code nahi likhte. Chapter ek shared process ki baat karta hai jisme engineers, product log aur domain experts wahi traces dekhkar sehmat hote hain ki "achha" ka matlab kya hai. Warna engineers aise metric ke liye optimize karenge jise experts trust nahi karte.

The Benevolent Dictator model

Ek vyakti ko criteria aur disputed labels par final say di jati hai — taaki behes ant-heen na chale. Uska kaam saari labeling karna nahi hai; kaam hai decisions lena jo process ko aage badhayein aur criteria ko consistent rakhein.

  • Kab kaam karta hai: chhoti team, clear domain, trusted expert.
  • Kab nahi karta: jab uska judgement trusted na ho, ya domain ek vyakti ke liye bahut bada ho.

Collaborative evaluation workflow — 9 steps

Ye workflow explicitly iterative hai — criteria ka pehla draft galat hone ki ummeed rakhi jati hai.

Agreement measure karna — statistics

1. Percent agreement

Do raters kitne items par same label dete hain, uska fraction. Simple hai, lekin chance se hone wali agreement ko account nahi karta.

2. Kappa — chance-corrected measure (do raters ke liye)

Formula: kappa = (observed agreement − expected agreement) / (1 − expected agreement)

Worked example (chapter ka): 100 items, observed agreement Po = 0.85, chance se expected agreement Pe = 0.71, to kappa = (0.85 − 0.71) / (1 − 0.71) ≈ 0.48.

Kappa valueInterpretation (standard scale)
< 0Poor
0 – 0.20Slight
0.21 – 0.40Fair
0.41 – 0.60Moderate
0.61 – 0.80Substantial
0.81 – 1.00Almost perfect

Kitab ki advice: criterion par bharosa karne se pehle kam se kam 0.6 (substantial) ka target rakho. Aur ek warning: high percent agreement + low kappa (jaise 85% agreement lekin kappa 0.48) ek warning hai — matlab task ek common label se dominated hai.

3. Multi-rater kappa

Do se zyada raters ke liye kappa ka generalisation — wahi chance-corrected idea, kai raters par.

4. Weighted kappa

Ordered labels ke liye (jaise 1–5 scale) — 1 aur 2 ke beech disagreement, 1 aur 5 ke beech disagreement se kam serious mana jata hai.

5. Alpha — general agreement measure

Ek aur general measure jo missing data aur alag-alag tarah ke labels handle karta hai; chapter me iska common target ≥ 0.80 diya gaya hai.

Warning: Human aur LLM judge ko compare karne ke liye kappa use mat karo jaise woh do equal raters hon. LLM judge human expert nahi hai — human se agreement ka matlab ye nahi ki judge sahi hai.

Common pitfalls — 5 galtiyan

  1. Agreement ko goal banana — galat criterion par high agreement bhi galat hi hai; agreement ek diagnostic hai, goal nahi.
  2. Ek vyakti ki rai ka dominate karna — discussion me ek hi awaaz haavi ho jaye.
  3. Bina poora context dekhe label karna — trace, retrieved documents, user ki history — sab dekho.
  4. Likert scale ka istemal jab binary clear hota — binary judgement aksar saaf hota hai.
  5. Label ki wajah document na karna — agla vyakti seekh nahi payega ki label kyun diya gaya.

Worked example — Trace #23 (duplex listing)

Ek do-family house (duplex) ki listing par do evaluators disagree hue ki assistant ka jawab acceptable tha ya nahi. Discussion se pata chala ki criteria hi ambiguous the — "CRM data ka istemal" ka matlab kya hai, ye saaf nahi tha. Criteria ki ambiguity hi disagreement ki jad thi.

Summary

Collaborative evaluation shuru me slow hai, lekin yahi baad ki automation ko trustworthy banati hai. Criteria par sehmati banane me lagaya gaya samay us waqt payoff deta hai jab automated evaluator hazaaron traces par lagta hai. Target: kappa ≥ 0.6, alpha ≥ 0.80.

Rubric ke saath evaluator banana

Rubric ek likha hua description hai ki kisi criterion par Pass / Fail (ya score) ka matlab kya hai — examples ke saath. LLM judge follow kar sake, iske liye rubric aise likho:

  • Criterion ko ek sentence me likho.
  • 2–3 pass examples aur 2–3 fail examples do.
  • Ambiguous cases me kya karna hai, ye batao.
  • Judge ko bolo ki apne decision ko justify karne ke liye output se evidence quote kare.

Worked example — CRM "hallucination" criterion: judge ko check karna hai ki jawab ka har factual claim retrieved CRM records me dikhta hai ya nahi — agar koi ek claim bhi supported nahi hai, to jawab fail hai.

  3. Judge ko ek trace par chalao — input, output aur retrieved context dekar.

Ch 6 — Evaluating Multi-Turn Conversations

Single-turn tests multi-turn failures miss karte hain — session, turn aur coherence teeno measure karo, anchoring aur stale memory ko pakdo.

Multi-turn conversations mushkil kyun hain?

Single-turn test ek sawal aur ek jawab check karta hai. Asli conversation ek sequence hai — har turn pehle wale par depend karta hai, user apna mann badal sakta hai, aur shuru me ek galti poori conversation ko bigaad sakti hai. Chapter ka kehna hai ki zyadatar single-turn evals sabse important failures ko miss kar dete hain — jaise assistant ka user ki baat bhool jana, ya user ki galti ke peeche chalna.

Three dimensions of multi-turn evaluation

Ek system har turn par achha ho sakta hai aur phir bhi session level par fail ho sakta hai — jaise user se wahi sawal do baar poochna.

Anchoring — sabse common failure mode

Assistant pehle turn ki ek information (aksar ek galat assumption) par "anchor" kar leta hai aur user ke correct karne ke baad bhi usi par wapas aata rehta hai. Examples: user date ya preference correct karta hai, lekin assistant purani wali hi use karta rehta hai.

Memory ko evaluate karna — teen hisse

  • Storage — kya yaad rakha gaya.
  • Retrieval — jab zaroorat padi, kya recall hua.
  • Update / staleness — purane facts badalne par replace hote hain ya latke rehte hain.

Worked Example 6-1 — return window

User ek product (X1000) ke baare me poochta hai, assistant kehta hai return 15 din me hota hai; baad me user kehta hai return window 30 din hai — assistant ko apni memory update karni hai, 15 kehte rehna nahi.

Worked Example 6-2 — film ki pasand

User sci-fi film ke baare me baat kar raha hai aur assistant ek romantic comedy ("Love Llama" — chapter ka example title) suggest karta hai — assistant ne user ki stated preference ka istemal hi nahi kiya. Evaluation ko check karna hai ki assistant ki user ki pasand ki memory asal me use ho rahi hai ya nahi.

User simulators

Asli multi-turn data ikattha karna mehenga hai, isliye chapter simulated user banana sikhata hai — ek LLM jo user ka role play karta hai: ek goal, ek personality, aur kuch constraints ke saath. Simulator design ke liye ek 2024 ke adhyayan (AgentInstruct) aur ek aur 2024 ke adhyayan ka hawala diya gaya hai; ek aur kaam me 200,000 simulated conversations se ek system ko evaluate kiya gaya.

Key warning: Simulator bahut easy bhi ho sakta hai (kabhi mushkil sawal poochta hi nahi) ya bahut hard (aise sawal poochta hai jo asli user kabhi nahi poochta). Isliye simulator ko khud evaluate karna zaroori hai — jaise simulated conversations ko asli conversations se compare karke.

Perturbation testing

Robustness test karne ka tareeka: ek asli conversation lo aur ek chhota sa badlav karo — jaise date badlo, naam badlo, ya do turns ka order badlo — aur dekho ki system ka jawab us hisaab se badalta hai ya nahi. Chapter "brittleness score" introduce karta hai — kitni baar ek chhoti perturbation se output me bada, unjustified badlav aaya. High brittleness score ka matlab hai system un wording par over-sensitive hai jinse farak nahi padna chahiye.

Multi-turn evaluation workflow — 7 steps

  1. Session-level goal define karo.
  2. Conversations ikattha karo ya simulate karo.
  3. Har turn aur har session ko label karo.
  4. Teen dimensions measure karo (session, turn, coherence).
  5. Anchoring aur memory failures dhoondo.
  6. Perturbations se test karo.
  7. Sabse badi failure mode fix karo aur poora set dobaara chalao.

Summary

Single-turn evals multi-turn failures miss karte hain. Session, turn aur coherence — teeno measure karo. Anchoring aur stale memory sabse bade dushman hain. Simulator ko bhi evaluate karo, aur brittleness score se robustness dekho.

Ch 7 — Evaluating RAG

RAG ke do hisse — retrieval aur generation — independently fail hote hain. Dono ko alag measure karo, warna pata hi nahi chalega ki kya fix karna hai.

RAG kya hai?

RAG (Retrieval-Augmented Generation) ek aisa system hai jo documents retrieve karta hai (jaise knowledge base se) aur phir un documents ko context banakar jawab generate karta hai. Chapter zor deta hai: RAG ke do hisse independently fail ho sakte hain — retrieval (sahi documents dhoondhna) aur generation (unhe sahi tarah se use karna). Sirf end-to-end score ("final jawab sahi tha?") ye nahi bata sakta ki kaunsa hissa fail hua.

Generation ko evaluate karna — 4 criteria

  1. Faithfulness / groundedness — jawab ka har claim retrieved documents se supported hai?
  2. Correctness — jawab sahi hai?
  3. Completeness — poora sawal answer hua?
  4. Conciseness — irrelevant detail to nahi jodi gayi?

Lost in the middle: ek 2024 ke adhyayan me paya gaya ki LLMs lambe context window ke beech wale documents par kam dhyan dete hain — jaise 20 documents retrieve hue to beech wale kam use hote hain. Isliye retrieved documents ka order bhi matter karta hai.

End-to-end evaluation

Chapter kehta hai: system ko poora bhi measure karo (user ko sahi, useful jawab mila?) aur dono hisse alag-alag bhi — taaki pata chale ki retrieval fix karni hai ya generation. Ek common pattern: wahi sawal teen tareekon se chalao — (a) real retriever ke saath, (b) perfect retriever (gold documents) ke saath, (c) bina retriever ke — aur teeno ko compare karo. (a) aur (b) ka difference hi retrieval errors ki keemat hai.

Synthetic data for RAG

Labelled RAG data mehenga hai, isliye chapter documents se synthetic questions generate karna sikhata hai — jaise LLM se kaho ki ek document ko answer karne wala sawal likhe, phir check karo ki sawal us document se answer ho sakta hai ya nahi.

Warning: Synthetic questions aksar asli sawalon se aasan hote hain — bahut clean, bahut specific, aur asli users ke vague, multi-part sawalon ko reflect nahi karte. Isliye synthetic data se bade failures dhoondo, ise real data ka replacement mat samjho.

Context swapping — faithfulness ka test

Retrieved documents ko ek alag set se swap kar do (jaise kisi aur topic ke documents) aur dekho ki jawab badalta hai ya nahi. Agar jawab wahi rehta hai, to system retrieved documents ka istemal hi nahi kar raha — woh apni khud ki knowledge se jawab de raha hai.

RAG evaluation workflow — 6 steps

  1. Corpus aur questions define karo.
  2. Retrieval measure karo (precision / recall / MRR / NDCG).
  3. Generation measure karo (faithfulness, correctness).
  4. End-to-end measure karo.
  5. Coverage ke liye synthetic data try karo.
  6. Sabse bada gap (retrieval ya generation) fix karo aur dobaara measure karo.

Summary

RAG ke do hisse alag-alag fail hote hain — dono ko alag measure karo. Chunking ko measure karke chuno (256/128 example). Faithfulness ke liye judge ko documents do. Synthetic data sirf gross failures ke liye hai.

Ch 9 — CI/CD for LLM Agents

LLM outputs stochastic hote hain aur models badalte rehte hain — isliye CI/CD ka matlab hai behaviour ko visible aur reversible banana.

LLM agents ke liye CI/CD alag kyun hai?

Traditional software ke tests deterministic hote hain — wahi input, hamesha wahi output. LLM outputs stochastic hote hain, models aapke neeche badal jate hain (provider model update kar sakta hai), prompts badalte hain, data badalta hai. Chapter ek 2024 ke adhyayan se shuru hota hai: ek model ki prime-number identification par accuracy March 2023 me 84% se June 2023 me 51% ho gayi — model ka naam wahi, behaviour alag. Isse pata chalta hai ki model waisa hi rahega, ye assume nahi kar sakte.

Golden datasets

100–200 examples ka ek chhota, high-quality set jo system ke sabse important behaviours ko represent karta hai. Golden set har change par chalaya jata hai — har pull request, har prompt change, har model change — aur ise system ka "contract" mana jata hai: agar koi change golden set tod de, to woh ship nahi hoga. Advice: golden set ko stable rakho aur carefully label karo — noisy golden set achhe changes ko bhi block kar dega.

Regression testing

Naya version purane version se wahi eval set par compare karo, aur tay karo ki drop asal hai ya noise. Advice:

  • Regression test ke liye fixed seed / fixed temperature use karo (randomness kam karne ke liye).
  • Test ko ek se zyada baar chalao.
  • Sirf average score mat dekho — failures ko dekho. Ek chhota average drop kisi important subgroup par bade drop ko chhupa sakta hai.

import re

def guardrail(output: str) -> str:
    # Agar PII pattern mile to output ko block karo ya redact karo.
    if SSN_RE.search(output) or CARD_RE.search(output):

Ch 11 — Data Analysis for Traces

Traces ka pile hypotheses ki chhoti list me badlo — EDA, clustering, outliers, semantic search — aur ye kaam regularly karo.

Framing — traces ka pile, patterns ki zaroorat

Jab aapke paas kai traces hain (inputs, outputs, tool calls, latencies, costs, labels), to unme patterns dhoondhne ke liye data-analysis skills chahiye. Chapter 1970s se chali aa rahi exploratory data analysis (EDA) ki parampara par based hai — idea ye hai ki formal model fit karne se pehle data ko dekho, plot karo, aur sawal poochho.

Exploratory Data Analysis — 4 practical steps

  1. Scores / latencies / costs ki distribution dekho.
  2. Unhe samay ke saath plot karo.
  3. Unhe subgroups me todo (user, feature, model version ke hisaab se).
  4. Koi aisa badlav dhoondo jo kisi release ya model update ke saath coincide karta ho.

EDA hypotheses generate karne ke liye hai ("retriever badalne par failure rate badha") — unhe prove karne ke liye nahi.

Clustering

Traces ko similarity ke hisaab se group karna — jaise inputs ya outputs ko embed karke cluster karna — taaki similar failures ke groups mil sakein.

Warning: Ek cluster automatically ek failure mode nahi hota. Cluster similar inputs ka group ho sakta hai jo sab easy hain, ya ek surface feature share karte hain (jaise sab inputs me wahi word hai) lekin asal cause ek nahi. Worked example: "apologetic email" traces ka cluster — kai traces jahan assistant email me maafi maangta hai — jab human ne dekha to ye ek hi failure mode nikla: assistant problem fix karne ke bajay maafi maang raha tha.

Outlier detection — IQR method

IQR = Q3 − Q1 (75th percentile minus 25th percentile). Ek value outlier hai agar woh Q3 se 1.5 × IQR upar ya Q1 se 1.5 × IQR neeche ho.

Advice: latency, cost ya score ke hisaab se top aur bottom 1% traces ko dekho, aur unme se lagbhag 20 padho — aksar ye ek naya failure mode dhoondhne ke liye kaafi hota hai. Warning: outlier ek genuine rare case bhi ho sakta hai ya data error bhi — bina dekhe pata nahi chalega.

Semantic search

Embeddings se traces ko meaning ke hisaab se search karna, sirf keyword se nahi — jaise woh saare traces dhoondo jahan user refund ke baare me pooch raha tha, chahe usne "refund" word use hi na kiya ho. Chapter sikhata hai ki ek seed example (ek trace jo aapko pata hai failure hai) se similar traces kaise dhoondein, aur search se kisi specific failure mode ke liye test set kaise banayein.

Analysis ke liye AI assistants ka istemal

Chapter notebook me LLM (AI assistant) se traces analyze karne ki baat karta hai — patterns dhoondhna, cluster ko summarise karna, examples search karna, data plot karna. Advice: AI assistant finding, summarising, searching aur plotting me achha hai, lekin ye batane me nahi ki failure kyun hua — uske liye ab bhi ek human chahiye jo domain samajhta ho. Aur ek warning: assistant se labeling mat karwao — woh evaluator ka kaam hai, aur assistant ko judge wale hi biases mil jayenge.

Common pitfalls — 4 galtiyan

  1. Correlation ko causation samajhna — jaise "5 se zyada tool calls wale traces zyada fail hote hain" ye prove nahi karta ki tool calls failure ki wajah hain (ho sakta hai mushkil tasks ko zyada tool calls chahiye hote hon).
  2. Sirf average dekhna — koi subgroup buri tarah fail ho raha hai, ye miss ho jata hai.
  3. Chhote sample par over-fit karna.
  4. Analysis ko document na karna — agla vyakti reproduce nahi kar payega.

Summary

Data analysis "Analyze" step hai — scale par. Traces ke pile ko hypotheses ki chhoti list me badlo, aur ye kaam regularly (jaise weekly) karo — sirf tab nahi jab kuch toot jaye. Chapter ka rule of thumb: agar 20 traces dekhne ke baad bhi aap koi failure mode naam nahi de sakte, to aap galat jagah dekh rahe hain.

Ch 12 — Improving LLM Agents

Cost, quality aur latency — teeno ek saath optimize nahi hote. Prompt, fine-tuning, caching, routing ya distillation — jo failure ko address kare, woh chuno.

Cost–Quality–Latency tradeoff

Chapter ka central idea: teeno ko ek saath optimize nahi kar sakte — bada, zyada accurate model aam taur par slow aur mehenga hota hai; chhota, tez model sasta hota hai lekin kam accurate. Pehle wale chapters ki evaluation hi is tradeoff ko deliberately karne deti hai: quality ko evaluators se measure karo, latency (jawab me kitna samay laga) aur cost (har request ki keemat) — phir woh point chuno jo product ko suit kare.

Prompt optimisation

Prompt ko systematically improve karne ke tareeke — jaise DSPy, TextGrad aur OPRO (Optimisation by PROmpting) — ye evaluation scores ko objective banakar prompt variations par search karte hain.

Warning: Prompt optimisation eval set par over-fit kar sakta hai — prompt test set par behtar ho jata hai lekin production me nahi. Aur optimized prompt ko padhna ya maintain karna mushkil ho sakta hai.

Fine-tuning

Eval set ke labelled examples par ek chhote model ko train karna, taaki woh specific task seekh le. Chapter me:

  • LoRA / QLoRA — parameter-efficient fine-tuning, jisme sirf adapter weights ka chhota set train hota hai.
  • DPO / KTO — preference-based fine-tuning, jisme model ko achhe vs bure outputs ke pairs par train kiya jata hai (DPO = Direct Preference Optimisation, KTO = prospect-theory par based ek preference method).
  • DoorDash example: ek system jo outputs me details invent (hallucinate) kar raha tha — sahi examples par fine-tuning se hallucination rate kam hua.
  • Warning: fine-tuning model ko un tasks par bura bhi bana sakta hai jin par use train nahi kiya gaya (catastrophic forgetting).

Distillation

Ek bade "teacher" model se ek chhote "student" model ke liye training data generate karwana, taaki student specific task par teacher ko mimic karna seekh le. Distillation useful hai jab teacher production ke liye bahut mehenga ya slow ho — lekin student ko teacher ki galtiyan bhi milengi, isliye teacher ke outputs ko Chapter 5 ke evaluators se filter karna zaroori hai.

Caching

  • KV-cache (Fig. 12-1) — model ki internal state ko store karta hai, taaki repeated ya similar prompt ka jawab tez mile.
  • Prompt caching — provider prompt ke prefix ko cache karta hai, taaki lamba system prompt har request par dobaara process na karna pade. Chapter ke numbers: prompt caching se price lagbhag 90% kam aur latency lagbhag 10% kam ho sakti hai (chapter ke example me), kyunki cached hissa dobaara compute nahi hota.

Routing aur cascades

  • Routing — har request ko sabse saste model ko bhejo jo use handle kar sake (aasan sawal chhote model ko, mushkil sawal bade model ko), ek router jo difficulty predict karta hai. Chapter me RouteLLM ka hawala hai, jo apne experiments me bade model ki lagbhag 85% quality fraction of cost par report karta hai.
  • Cascades (Fig. 12-2) — pehle sasta model try karo, uske output ko confidence score ya evaluator se check karo, aur mehenga model sirf tab call karo jab sasta confident na ho. FrugalGPT ko cascade system ka example bataya gaya hai.

Confidence aur abstention

  • Logprobs (Fig. 12-3) — har token ki log-probability, model ki confidence ka signal hai ki jawab sahi hoga ya nahi.
  • Structured output — Worked Example 12-1: ek model ke structured-output feature ke saath (gpt-4o-2024-08-06), model ko force kiya jata hai ki woh ek JSON object de jisme confidence score (0–10) aur jawab ho. Concept sikhane wala excerpt: ek field jaise confidence: int jiska description hai "0-10, how confident are you in this answer?" — phir code confidence se tay karta hai ki jawab dikhana hai, bada model call karna hai, ya abstain karna hai ("I don't know" kehna).
  • Chapter ke example me lagbhag 90% high-confidence jawab sahi the — isliye confidence ek useful (lekin imperfect) signal hai.
  • Abstention — system ko "I don't know" kehna sikhana jab woh confident na ho — hallucinations kam karne ka tareeka hai, khaas taur par high-stakes sawalon me.

Putting It Together — poori kitab ka final workflow

  1. Error analysis se sabse badi failure mode dhoondo.
  2. Use automated evaluator se measure karo.
  3. Us failure ko address karne wali improvement technique chuno (prompt, retrieval, fine-tuning, caching, routing, …).
  4. Improvement ko held-out test set par measure karo — sirf quality nahi, cost aur latency bhi.
  5. CI/CD (Chapter 9) se ship karo aur production me monitor karo.
  6. Repeat.

Chapter zor deta hai: sabse sasta improvement aksar bada model nahi hota — behtar prompt, behtar retrieval, ya behtar data hota hai.

Summary / closing

Evaluation ek one-off project nahi hai, ye ek aadat hai. Reliable AI systems banane wali teams woh hain jo har hafte apne outputs ko dekhti hain, apne eval sets ko up to date rakhti hain, aur Analyze–Measure–Improve flywheel se chhote, measured improvements karti rehti hain.

FAQs — Interview Sawal-Jawab

Current-era interviews ke liye 36 sawal-jawab — har chapter se, kitab ke concepts, numbers aur examples par based. Har jawab khud me poora hai.

Q1Evaluation aur testing me kya farak hai?
Testing ye check karta hai ki code chal raha hai ya nahi — jaise unit test pass hua ya fail. Evaluation ye judge karta hai ki LLM system apna kaam, us specific situation me, kitna achha kar raha hai. Ek code perfectly chal sakta hai aur phir bhi galat jawab de sakta hai — woh evaluation hi pakadti hai. Benchmark score bhi testing jaisa hai: woh general capability batata hai, aapke specific user aur task par performance nahi.
Q2Benchmark par high score ka matlab system achha hai — ye kyun galat hai?
Benchmark ek fixed, clean test set par score hai. Aapka real task alag data, alag users aur alag edge cases ke saath aata hai. Chapter 1 ka Gulf of Representation yahi kehta hai: evaluation me kaam kaise represent hai, woh real-world se alag ho sakta hai. Isliye apne real inputs par apna eval set banao — benchmark se shuru mat karo.
Q3Three Gulfs of Evaluation kya hain? Interview me kaise samjhaun?
Teen gulfs: (1) Execution — jo test karna chahte ho vs system se asal me jo karwaya ja raha hai; (2) Representation — evaluation ka data/prompts/rubrics vs real-world situation; (3) Assessment — output kya hai vs use judge kaise kiya gaya. Ye ek lens hain, checklist nahi. Achhi evaluation teeno gulfs ko chhota karti hai. Example do: clean test data par achha score (representation gulf) ya LLM judge ka bias (assessment gulf).
Q4Analyze–Measure–Improve flywheel kaise kaam karta hai?
Analyze: asli outputs dekho, failure patterns dhoondo, tay karo kya matter karta hai. Measure: patterns ko repeatable automated checks banao. Improve: prompt, retrieval, model ya product badlo, phir dobaara measure karo. Loop ko chalte rehna hai — ek evaluation kaafi nahi, kyunki system, data aur users badalte rehte hain.
Q5LLM agent ke kaunse components evaluate karne hote hain?
Paanch: base LLM, prompt/system prompt, tools, memory, aur surrounding application code (retrieval, routing, guardrails, UI). Agent ek system hai — failure kisi bhi component se aa sakta hai. Evaluation ko batana hota hai ki failure kahan se aaya, taaki sahi cheez fix ho. Isiliye Table 2-1 har component ki failure modes list karti hai.
Q6Offline aur online evaluation me kya farak hai, aur dono kab chahiye?
Offline: fixed test inputs par version ko score karna — do versions compare karne ke liye. Online: production me asli users ko dekhna — thumbs up/down, retry, complaints — wild me regressions pakadne ke liye. Dono chahiye: offline comparison ke liye, online real-world detection ke liye. Human evaluation 'achha' define karne ke liye, automated evaluation scale ke liye.
Q7Prompt ko system ka hissa kyun mana jata hai?
Kyunki prompt sirf ek string nahi hai — system instructions, user message, few-shot examples, formatting constraints aur tool descriptions ka set hai. Wording ya order me chhota badlav output ko bahut badal sakta hai. Math tutor example dekho: helpful rehne ka instruction accurate rehne ke instruction se takra sakta hai. Isliye prompt change hote hi evaluation dobaara chalani chahiye.
Q8Error analysis automated evaluator banane se pehle kyun aani chahiye?
Kyunki bina dekhe aap nahi jaante ki kya galat ho raha hai. Agar pehle automated test bana liya, to aap galat cheezon ke liye test automate kar doge. Error analysis — asli outputs dekhna, label karna, group karna, ginna — batati hai ki kaunsi failures matter karti hain. Tabhi un par criteria aur evaluator banao.
Q9Open coding aur axial coding me kya farak hai?
Open coding: bina pre-set categories ke outputs padhna aur jo failure dikhe use apne shabdon me likhna — isse unexpected failure modes milte hain. Axial coding: un open codes ko chhote set me group karna aur unke beech relationships describe karna — jaise 'hallucination' ko 'fact invent kiya' vs 'retrieved document galat padha' me todna. Pehle open, phir axial.
Q10Eval set banane ke liye kitne examples chahiye aur kaise shuru karun?
Chapter kehta hai: lagbhag 100 real queries se seed lo, unhe label karo, aur labelled traces se eval set banao. Automate karne se pehle kam se kam kuch dozen examples label karo, 2–3 rounds me revise karo, aur pehle binary judgement (acceptable/unacceptable) use karo — Likert scale se nahi, kyunki binary par sehmati banana aasan hai.
Q11Eval set ke dimensions kya hote hain? Tuple ka matlab kya hai?
Task ko dimensions par describe karo — CRM example me Feature (product ka kaunsa hissa), Client persona (first-time buyer, investor, seller) aur Scenario (jaise pehle ho chuki viewing ke baare me poochna). Ek test case in dimensions ke values ka combination hai — ek 'tuple'. Achha eval set un combinations ko cover karta hai jo production me asal me hote hain, sirf aasan wale nahi.
Q12Saturation ka matlab kya hai error analysis me?
Jab tak naye traces padhne se naye categories aana band na ho jaayein, tab tak padhte raho. Ye signal hai ki us sample ke zyadatar failure modes dekh liye. Saturation ke baad bhi naye failure modes production me mil sakte hain — isiliye eval set ko badhate rehna hota hai, har production failure ke liye 5–10 naye examples jodkar.
Q13Benevolent Dictator model kya hai aur kab kaam karta hai?
Ek vyakti ko criteria aur disputed labels par final say di jati hai, taaki behes ant-heen na chale. Uska kaam saari labeling karna nahi, decisions lena hai. Ye tab kaam karta hai jab team chhoti ho, domain clear ho aur expert trusted ho. Tab nahi karta jab uska judgement trusted na ho ya domain ek vyakti ke liye bahut bada ho.
Q14Kappa kya hai aur percent agreement se behtar kyun hai?
Percent agreement sirf ye batata hai ki do raters kitne items par sehmat hue — chance se hone wali agreement ko ignore karta hai. Kappa chance-corrected hai: kappa = (observed − expected) / (1 − expected). Example: 100 items, Po 0.85, Pe 0.71, to kappa ≈ 0.48 (moderate). 85% agreement ke saath kappa 0.48 ek warning hai — task ek common label se dominated hai. Target: kam se kam 0.6.
Q15Kappa scale ke bands kaunse hain?
Standard scale: <0 poor, 0–0.20 slight, 0.21–0.40 fair, 0.41–0.60 moderate, 0.61–0.80 substantial, 0.81–1.00 almost perfect. Kitab ki advice: criterion par bharosa karne se pehle kam se kam 0.6 (substantial) chahiye. Multi-rater kappa do se zyada raters ke liye hai, weighted kappa ordered labels (1–5) ke liye, aur alpha ek general measure hai jiska target ≥ 0.80 hai.
Q16Human aur LLM judge ko kappa se compare karna kyun galat hai?
Kyunki LLM judge human expert ke barabar ka rater nahi hai. Human se agreement ka matlab ye nahi ki judge sahi hai — dono ek hi galat tareeke se judge kar sakte hain. Judge ko human labels ke against accuracy metrics (TPR/TNR) se measure karo, agreement se nahi.
Q17LLM-as-judge kya hai aur rubric kaise likhte hain?
LLM-as-judge ek aur LLM se output ko rubric ke against score karwana hai. Achhi rubric: criterion ek sentence me, 2–3 pass examples, 2–3 fail examples, ambiguous cases me kya karna hai, aur judge ko evidence quote karne ko kaho. CRM hallucination criterion: jawab ka har factual claim retrieved records me hona chahiye, warna fail.
Q18Evaluator ko evaluate karna kyun zaroori hai?
Kyunki automated evaluator khud galat ho sakta hai. Uske scores par bharosa karne se pehle human labels ke against uski accuracy measure karo — TPR = TP/(TP+FN), TNR = TN/(TN+FP), precision, recall, F1, accuracy. High-stakes criterion ke liye TPR aur TNR dono 90% se upar hone chahiye. Judge jo bahut strict hai, uski TNR high lekin TPR low hogi.
Q19Train/Dev/Test split evaluator ke liye kaise karte hain?
Train 10–20% — rubric aur judge prompt develop karne ke liye. Dev 40–45% — judge ko measure karne aur iterate karne ke liye. Test 40–45% — sirf ek baar, unbiased estimate ke liye. Test set par tuning mat karo — warna evaluator kagaz par achha dikhega, production me fail hoga.
Q20LLM judges ke chaar biases kaunse hain aur unhe kaise test karte hain?
Position bias (pehle wale ko prefer karna), verbosity bias (lambe ko prefer karna), self-enhancement bias (apne model family ko prefer karna), sycophancy/style bias (polite ya achhi formatting ko prefer karna, chahe galat ho). Har ek ka test ek hi hai: bias ko hatakar wahi judgement dobaara chalao — order swap karo, jawab chhota karo — aur dekho verdict flip hota hai ya nahi.
Q21Rogan–Gladen estimator kya hai?
Ye judge ki imperfect TPR/TNR ke liye observed pass rate ko correct karta hai: theta_hat = (observed rate + TNR − 1) / (TPR + TNR − 1). Kitab ke example me corrected estimate ~0.87 tha, bootstrap CI (B = 20,000) ~[0.81, 0.93]. Interval 0.85 threshold ko straddle karta tha, isliye ship ka decision clear-cut nahi tha — zyada labelled data ya behtar judge chahiye tha.
Q22Multi-turn evaluation single-turn se alag kyun hai?
Single-turn ek sawal-jawab check karta hai; asli conversation ek sequence hai jahan har turn pehle wale par depend karta hai. Single-turn evals sabse important failures miss kar dete hain — jaise assistant ka user ki baat bhool jana ya user ki galti ke peeche chalna. Isliye teen dimensions measure karo: session-level, turn-level aur coherence.
Q23Anchoring kya hai? Example do.
Assistant pehle turn ki ek information (aksar galat assumption) par atak jata hai aur user ke correct karne ke baad bhi usi par wapas aata hai. Example: user kehta hai return window 30 din hai, lekin assistant 15 din kehta rehta hai. Ye multi-turn ka sabse common failure mode hai. Lab 8 me ise live dekho.
Q24User simulator kya hai aur use evaluate kyun karna hai?
Simulated user ek LLM hai jo user ka role play karta hai — goal, personality aur constraints ke saath. Asli multi-turn data mehenga hai, isliye simulators se conversations generate karte hain (ek kaam me 200,000 simulated conversations use hui). Lekin simulator khud bahut easy ya bahut hard ho sakta hai — isliye use bhi evaluate karo, jaise simulated conversations ko asli se compare karke.
Q25Perturbation testing aur brittleness score kya hai?
Ek asli conversation me chhota badlav karo — date badlo, naam badlo, turns ka order badlo — aur dekho ki system ka jawab sahi tareeke se badalta hai ya nahi. Brittleness score batata hai ki kitni baar chhoti perturbation se output me bada, unjustified badlav aaya. High score ka matlab system un wording par over-sensitive hai jinse farak nahi padna chahiye.
Q26RAG me retrieval aur generation ko alag kyun measure karte hain?
Kyunki dono independently fail ho sakte hain. Sirf end-to-end score ('final jawab sahi tha?') ye nahi bata sakta ki retrieval fail hui ya generation. Dono ko alag measure karo — retrieval par precision/recall/MRR/NDCG, generation par faithfulness, correctness, completeness, conciseness. Phir pata chalega ki kya fix karna hai.
Q27Precision, recall, MRR aur NDCG me kya farak hai?
Precision = mile hue documents me se kitne relevant the. Recall = kul relevant documents me se kitne mile. Dono set ke liye hain. MRR = pehle relevant document ki rank ka reciprocal (1/rank) ka average — ranked list ke liye. NDCG = rank-aware measure jo relevant documents ko upar rakhne par reward deta hai; perfect ranking = 1.0.
Q28Lost in the middle kya hai?
Ek 2024 ke adhyayan me paya gaya ki LLMs lambe context window ke beech wale documents par kam dhyan dete hain — jaise 20 documents retrieve hue to beech wale kam use hote hain. Isliye retrieved documents ka order bhi matter karta hai. RAG system design karte hue iska dhyan rakho.
Q29Synthetic data RAG ke liye kab useful hai aur kab nahi?
Synthetic questions documents se generate karke coverage badha sakte ho — gross failures dhoondhne ke liye useful hai. Lekin synthetic questions aksar asli sawalon se aasan hote hain — bahut clean, bahut specific, asli users ke vague multi-part sawalon ko reflect nahi karte. Isliye ye real data ka replacement nahi hai.
Q30Tool use evaluate karte hue chaar stages kaunse hain?
Tool selection (sahi tool chunna), argument generation (arguments sahi bharna), tool execution (tool call karke result lena), aur handling of tool outputs (result ko final jawab me sahi use karna). Har stage alag fail ho sakta hai, aur ek stage ki failure doosri jaisi dikh sakti hai — isliye stage-wise label aur measure karo.
Q31Transition-failure heatmap se kya seekhte hain?
Heatmap dikhata hai ki ek stage ki failure ne kitni baar agle stage ki failure ko janm diya. Kitab ke numbers: ExecTool 12, GenArgs 8, HandleOut 7, aur GenArgs → ExecTool transition 12 — hotspot hai argument-generation errors jo execution failures paida kar rahi hain. Advice: hotspot ko pehle fix karo.
Q32Prompt injection ke teen types kaunse hain?
Direct injection — user khud model se galat kaam karwana chahta hai. Indirect injection — injection kisi document ya tool output me hai jo model padhta hai. Tool-output injection — koi tool malicious instructions wapas deta hai. Har type ko alag se test karo, known injection attempts ke set ke saath, aur check karo ki system injection follow karta hai ya ignore karta hai.
Q33Golden dataset kya hai aur kitna bada hona chahiye?
100–200 high-quality examples ka set jo system ke sabse important behaviours ko represent karta hai. Har change par chalaya jata hai — har PR, har prompt change, har model change — aur ise system ka 'contract' mana jata hai. Agar change golden set tod de, to ship nahi hoga. Golden set ko stable rakho aur carefully label karo.
Q34LLM agents ke liye CI/CD traditional software se alag kyun hai?
Traditional tests deterministic hote hain — wahi input, wahi output. LLM outputs stochastic hote hain, provider model update kar sakta hai, prompts aur data badalte hain. Ek adhyayan me model ki prime-number accuracy March 2023 me 84% se June 2023 me 51% ho gayi — naam wahi, behaviour alag. Isliye CI/CD me golden sets, fixed seed/temperature regression tests, guardrails, version pinning aur rollback plan chahiye.
Q35Guardrails kya hain? Kya woh evaluation ki jagah le sakte hain?
Guardrails production me code checks hain jo bad outputs ko user tak pahunchne se pehle pakadte hain — jaise PII guardrail SSN ya credit-card patterns ko block karta hai. Nahi, woh evaluation ka substitute nahi hain — woh safety net hain, sabse kharab cases pakadte hain, lekin system ko achha nahi banate.
Q36Production monitoring me kya dekhna chahiye?
Pass rate, latency, cost, error rate aur user feedback — Table 9-2 ke signals. Human review ke liye traces ka 1–5% sample karo, aur sirf 5–7 evaluators track karo (darjanon nahi) taaki team action le sake. Har production failure ke liye eval set me 5–10 naye examples jodo. 'West Berkeley' vs 'Berkeley West' wala example yaad rakho — chhoti wording change se systematic failure sirf monitoring se pakda gaya.
