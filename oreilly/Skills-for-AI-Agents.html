Expertise Doesn't Transfer — Likha Hua Gyaan

Recorded history ke zyada tar hisse me, agar tum chahte the ki koi kaam tumhare jaise kare, to tumhe uske paas khade hokar dikhana padta tha. Lohar ka apprentice lohar ko dekh kar seekhta tha. Gyaan us insaan ke shareer me rehta tha jiske paas woh tha — aur use move karne ka ek hi tareeka tha: paas khade hokar "rub off" hone do. Ye slow tha, scale nahi karta tha, aur jab expert mar jata tha, to uska bahut sa gyaan bhi mar jata tha.

Likhnay ki koshishein — ek ke baad ek format

Isliye humne expertise likhne ke tareeke invent kiye — har format ek hi koshish thi: gyaan ko insaan ke dimaag se nikaal kar kahi aisi jagah rakhna jahan use reuse, share, version aur naye insaan ko handover kiya ja sake, bina original expert ke kamre me hone ki zaroorat.

  • Apprenticeship → manual → textbook → operating procedure → field guide → runbook → internal wiki → Notion page → Confluence space → har GitHub repo ke root me README.md
  • Har format ne wahi ek kaam karne ki koshish ki — aur koi bhi poori tarah kaam nahi kiya.

Ye formats kyun fail hue?

  • Manual hamesha thoda upar ya neeche rehta tha — ya to itna general ki specific situation me kuch batata hi nahi, ya itna specific ki kuch badalte hi obsolete ho jata.
  • Wiki likhne ke ek hafte baad stale ho jati thi.
  • Runbook maan leta tha ki tum woh sab pehle se jaante ho jo usme likha hi nahi.
  • Onboarding doc woh process batata tha jo ab exist hi nahi karta.
  • Har organization ke paas kahi ek folder hai bhara hua un documents se jinhe koi padhta nahi kyunki koi unpar bharosa nahi karta — aur asli institutional knowledge ab bhi teen logon ke Slack messages aur ek senior engineer ki memory me rehta hai.

Chhupa hua assumption: "Reader is human"

In sab formats me ek khamosh assumption chhupa tha — itna deeply baked ki 5,000 saal tak kisi ne use naam hi nahi diya: reader insaan hai. Manual kaam karne ka tareeka batata hai — kaam karta nahi. Woh shelf par, server par ya shared drive par wait karta hai jab tak koi insaan aakar use padhe, interpret kare, gaps bhare, judgment lagaye aur phir actually execute kare. Document process ka specification hai. Insaan processor hai. Insaan ke bina document inert hai — sirf marks on a page, ek aisi cheez ko describe karte hue jo ho hi nahi rahi.

Aur phir ye assumption optional ho gaya. Pehli baar, document ke dusre end par woh cheez hai jo document ko execute kar sakti hai — sirf interpret, summarize ya explain nahi, execute. Shelf ab shelf nahi raha. Woh ek queue ban gaya hai. Aur isse "kuch likhna" ka matlab hi badal jata hai.

Interview tip: "Reader is human" wala point book ka sabse important insight hai. Agar interviewer poochhe ki skills alag kyun hain, to jawab ye hai — format nahi badla, reader badla.

Machines ko Samjhana — 70 Saal ka Safar

Jab hum manuals likh rahe the, tab hum machines ko padhna bhi sikha rahe the. Computing ka itihaas, ek angle se dekho to, instructions ke aur human hote jaane ka itihaas hai. Har layer of abstraction ne programming ki language ko machine se ek kadam door aur ordinary thought ke ek kadam kareeb kar diya.

Chaar eras — instructions kaise badle

  • 1950s — Machine code: ones aur zeros ki lambi strings, ya hexadecimal shorthand. Tum task describe nahi kar rahe the — tum box ke andar physical switches flip kar rahe the, ek aisi language me jo poori tarah hardware ke liye design thi. Typo ho to machine tumhe misunderstand nahi karti — woh exactly wohi karti hai jo tumne kaha, jo almost hamesha aur bura hota hai.
  • Late 1950s — Assembly: pehli real translation. 10110000 01100001 ki jagah MOV AL, 61h — "value 0x61 ko register AL me move karo". Ab instruction me ek verb tha. Ek shabd jo zor se padha ja sakta tha. Programming switches arrange karna band hokar, barely, sentences likhna ban gayi.
  • High-level languages: FORTRAN (1957), COBOL (1959), ALGOL, BASIC (1964), C (1972), phir C++ (1985), Python (1991), Java aur JavaScript (1995). print("hello") CPU ko seedha kuch nahi kehta — compiler ya interpreter ko batata hai ki tumhara matlab kya tha. Ek non-programmer bhi if age > 18: print("adult") padh kar andaza laga sakta hai kya ho raha hai. Instructions machine ke liye nahi, dusre insaan ke liye likhi jaane lagi — machine chup-chap sunti rehti thi.
  • 2000s–2010s — APIs: tum software scratch se nahi likhte the — tum glue likhte the un services ke beech jo dusron ne pehle se banayi thi. POST /users {"name": "[Name]", "role": "engineer"} code nahi hai machine code ki tarah — ye ek request hai, lagbhag jaise kisi ke desk par note chhodna. Tum CPU ko nahi, dusre system ko bata rahe ho ki tum kya chahte ho, aur bharosa kar rahe ho ki woh figure out kar lega.
Book me diye gaye code examples — instructions kaise human hoti gayi

Book me printed code, jaisa ka taisa. "[Name]" placeholder hai — book me ek example naam tha.

10110000 01100001          # machine code (1950s) — switches flip karna
MOV AL, 61h               # assembly — pehli baar ek verb
print("hello")            # high-level — compiler ko matlab batana
if age > 18: print("adult")   # non-programmer bhi andaza laga sakta hai
POST /users {"name": "[Name]", "role": "engineer"}   # API — ek request, desk par note jaisi

Lekin ek deewaar ab bhi thi

Har generation me woh log badhte gaye jo computers ke liye working instructions likh sakte the — 1950s me kuch sau specialists se lekar 2000s me millions of professional programmers, aur 2010s tak laptop aur ek afternoon wala koi bhi. Lekin phir bhi ek deewaar thi: sabse human-friendly API call bhi woh cheez nahi hai jo tum kisi colleague se kabhi asal me kahoge. Kisi ne kabhi colleague ki taraf mud kar POST /users nahi kaha — aur agar kaha, to samajh lo woh computer par bahut der se baitha hai aur use break chahiye. Instructions human hoti ja rahi thi, lekin human tak pahunchi nahi thi. Abhi nahi.

Structured code aur ordinary language ke beech ka aakhri gap ziddi tarike se bana raha. Aur dusri taraf, humans humans ke liye manuals likhte rahe — SOPs, wikis, playbooks, onboarding docs. Do tarah ke written instructions, 50 saal parallel develop hote hue. Ek machine ke liye likha gaya jo dheere-dheere human hota gaya. Dusra humans ke liye likha gaya jo shuru se human tha. Do tracks, saath-saath chalte hue, kabhi touch kiye bina. Woh milne wale the.

The Collision — Prompting

30 November 2022 ko do tracks aakhir me mile (phir se — "sort of"). OpenAI ne ChatGPT release kiya, aur pehli baar internet connection wala koi bhi insaan ordinary English me open-ended instruction likh sakta tha — lagbhag kisi bhi domain me — aur bina links aur webpages me scroll kiye kuch useful wapas pa sakta tha. Instruction ko MOV AL, 61h ya POST /users ya print("hello") jaisa dikhne ki zaroorat nahi thi. Woh aisi lag sakti thi: "2008 financial crisis ko mujhe aise samjhao jaise main ek smart 12 saal ka bachha hun" — aur jawab aa jata tha, aur woh, sab odds ke against, kaafi achha hota tha.

70 saal ka gap — ek narrow sense me — band hua

  • ChatGPT 5 din me 1 million users tak pahuncha. Do mahine me 100 million.
  • Uske baad ke saal me Google ka global search traffic lagbhag 8% gir gaya — log machines se woh sawaal poochhne lage jo pehle search bar me type karte the.
  • Jo cheez tum computer me type karte the, aur jo cheez computer samajh kar seedha jawab de sakta tha — woh achanak ek hi cheez ban gayi.
  • Machine code aur ordinary language ke alag tracks aakhir me converge ho gaye. Machines ke liye likhi instructions aur humans ke liye likhi instructions ek hi format me collapse ho gayi: plain language — woh cheez jo tum coworker se bina aankh jhapkaye keh sakte ho.

Aur lagbhag turant, logon ne discover kiya ki tum kaise type karte ho, isse farak padta hai.

Yaad rakho: Book "converged (again, sort of)" kehta hai — ye convergence narrow sense me hai. Model abhi bhi sirf text generate kar raha hai, kaam nahi kar raha. Kaam karne ke liye tool calling chahiye — Section 01.6 dekho.

Prompting Becomes a Discipline

Agar tum ChatGPT se kehte "is article ko summarize karo", to tumhe ek summary milti thi. Theek-thaak, kuch khaas nahi. Lekin agar tum kehte "ek senior magazine editor ki tarah act karo, ye article padho aur teen sentences me summary likho jo thesis, sabse strong evidence aur author ka conclusion capture kare. Direct raho. Hedge mat karo" — to tumhe noticeably behtar output milta tha. Wahi model. Wahi article. Dramatically different output. Ek hi variable tha — request ki framing.

Prompt engineering ki techniques

Is idea ne ki behtar prompts se behtar output milta hai, ek poori discipline paida kar di — prompt engineering — jo agle do saal tak AI discourse par dominate karti rahi. Kuch famous techniques:

  • Few-Shot Learning (2020): apni cheez maangne se pehle model ko examples do.
  • Chain-of-Thought Prompting (2022): model ko step by step sochne ko kaho.
  • Self-consistency (2022): multiple answers sample karo aur majority vote lo.
  • Tree of Thoughts (2023), ReAct (2022), Reflexion, Self-Refine: sab clever hacks jo ek brilliant lekin slippery system se zyada reliability nikaalne ke liye the.

In techniques me se zyada tar tumhare padhte-padte dated lagengi, aur koi baat nahi. Jo matter karta tha woh koi specific trick nahi thi. Jo matter karta tha woh ye hai jo poori discipline ne quietly establish kiya — teen cheezein jin par is book ka baaki sab kuch khada hai.

Teen lessons jo sab kuch badal deti hain

  • 1. Output ki quality, input ki quality se directly judi hai. Pehle assumption thi ki language model ek oracle hai — ya to woh cheez kar sakta hai ya nahi. Prompt engineering ne dikhaya ki wahi model, wahi capabilities ke saath, request ko frame karne aur context me kya daala — us par wildly different outputs de sakta hai. Output ki quality input side ka design problem thi.
  • 2. Ye models instructions follow kar sakte hain. Sirf achhe responses nahi — tum inhe specific instructions bhi de sakte the, jaise "pehle content ko summarize karo, phir key points identify karo, phir unhe bullet points me list karo".
  • 3. AI system ko behtar banana ab non-engineer bhi kar sakta tha. Prompting se pehle, AI model ko apne use case ke liye behtar banana matlab tha naya model train karna — specialized hardware, bade datasets, aur PhD wala knowledge. Prompting ne performance improvement ko desk par 10 minute ka kaam bana diya: prompt likho, output padho, kya galat hai notice karo, prompt rewrite karo, phir try karo. Pehli baar, domain expertise wala insaan — lawyer, analyst, PM, teacher — engineer ke through gaye bina AI system ko improve kar sakta tha.

Prompt engineering ko ek search ya navigation process ki tarah frame karna useful hai — possibilities ke space me navigate karna. Ek AI engineer ne isse evocatively describe kiya: "prompt as a portal". Ek aur definition: "Prompt engineering is the process of searching through program space to find the program that empirically seems to perform best on your target task." Prompting ek skill thi, trick nahi.

Interview tip: "Prompting ek skill hai, trick nahi" — aur teen lessons (input quality, instruction following, non-engineer access) interview me poochhe jate hain. Inhe apne shabdon me samjha pao to achha impression padta hai.

The Ceiling — Intelligence vs Agency

Prompt engineering ne AI se interact karne ka tareeka transform kar diya, lekin uski ek clear ceiling thi. Tum prompt kitna bhi carefully likh lo, tum model se kaam describe karwa rahe the, karwa nahi rahe the. Tum model ko prompt kar sakte the ki customer return process karne ka tareeka explain kare, apology email draft kare, refund policy outline kare. Tum use actual refund issue nahi karwa sakte the. Tum use woh SQL query describe karwa sakte the jo Q3 revenue nikaalegi. Tum use query run nahi karwa sakte the. Model tumhe task ke edge tak extraordinary eloquence ke saath le ja sakta tha — aur phir ruk jata tha, kyunki task ko aise system tak pahunchna tha jise model chhoo hi nahi sakta tha.

Intelligence aur agency ke beech ka gap

Ye jaanne aur karne ke beech ka gap hai. Prompting, apni saari sophistication ke saath, kabhi woh mechanism nahi ban sakta tha jisse ye gap band ho, kyunki woh poori tarah model ke text-generation loop ke andar operate karta hai. Model ke paas button click karne, API hit karne, script run karne ya file bhejne ka koi mechanism nahi tha. Model ek brain in a jar tha: jar ke andar extraordinarily capable, aur jar ke bahar ki har cheez se poori tarah sealed off.

Lekin jaanne aur karne ke beech ka gap narrow zaroor hua. Pehli baar itihaas me, ek machine lagbhag kisi bhi task ko fluent human language me describe kar sakti thi. Lekin task describe karna aur task perform karna ek hi cheez nahi hai — aur unke beech ki doori, woh last mile jo hamesha expertise ko execution se alag karta raha hai, ab bhi wahan thi. Use band karne ke liye model ko haath chahiye the.

Yaad rakho: "Brain in a jar" — ye phrase book me baar-baar aati hai. Iska matlab: model ke paas intelligence hai lekin agency nahi. Tool calling ne jar me pehla connection banaya (Section 01.6).

Tool Calling — Model ko Haath Mil Gaye

Ek large language model (LLM) akela tumhara calendar check nahi kar sakta, database query nahi kar sakta, message bhi nahi bhej sakta. Woh sirf aur text produce kar sakta hai. Is flatland se bahar nikalne ke liye — text-in, text-out — ek bridge chahiye tha, jo appropriate responses produce karne ki ability ko real-world action me translate kar sake. Woh bridge February 2023 me aaya, ChatGPT release ke teen mahine bhi nahi hue the.

The Paper That Changed Everything — Toolformer

February 2023 me, Meta AI aur ek European university ke researchers ne ek paper publish kiya: "Toolformer: Language Models Can Teach Themselves to Use Tools." Core finding striking thi: tum language model ko external system use karne ke kuch examples dikha sakte the (jaise wikipedia, translation), aur model khud seekh jata tha ki jab use bahar se help chahiye ho, to waisi hi request produce kare. Model ko ye samajh nahi thi ki "tool" kya hota hai, lekin woh pattern seekh gaya: jab main aisi problem face karun jo text se solve nahi hoti (math problem, aaj ki date, ya koi fact jiske baare me sure nahi hun), to mujhe ek specially formatted sentence produce karni chahiye jo signal kare "bahar ke system se help maango". Is simple idea ne woh seed plant kiya jo aage aaya.

Research se Product — OpenAI Function Calling

13 June 2023 ko OpenAI ne is idea ko product bana diya: "function calling". GPT-4 aur GPT-3.5 Turbo ke updated versions release hue, specifically trained (instruction tuning ke through) ki woh pehchan saken kab function use karna hai, aur phir clean organized text outputs produce karen jinse traditional code ke through function trigger kiya ja sake. Baad me iska naam tool calling ho gaya.

Function calling vs Tool calling: Log dono terms interchangeably use karte hain, aur wajah hai — concept rebrand hua. OpenAI ke original June 2023 API me parameter ka naam "functions" tha. December 2023 tak use deprecate karke "tools" se replace kar diya gaya. Naam badalna cosmetic nahi tha: "function" narrow, code-centric capability imply karta hai. "Tool" zyada broad aur accurate metaphor hai — tool web search ho sakta hai, code interpreter, file reader, database connection, ya haan, function bhi. Language ka shift ambition ka shift reflect karta tha: models sirf functions call nahi kar rahe the, woh tools use kar rahe the — jaise craftsperson kaam ke hisaab se alag instruments pick karta hai. Anthropic, Google aur open-source projects ne bhi "tool calling" ko standard term apna liya.

Five-step tool calling loop — travel assistant example

Concrete example: tum ek travel assistant bana rahe ho. Tum chahte ho AI destination city ka weather check kar sake jab koi poochhe. Step by step kya hota hai:

  • Step 1 — Tum tools describe karte ho: Model ko user ka question dikhane se pehle, tum use batate ho ki kaunse tools available hain. Jaise kisi ko capabilities ka menu dena. Travel assistant ke liye tum ek tool describe karte ho "get_weather" — jo city name input leta hai aur current weather conditions return karta hai. Ye description JSON schema me likhi jati hai. Tum ek menu item likh rahe ho — naam aur kya chahiye iska description.
  • Step 2 — User question poochhta hai: "Main agle hafte Lisbon jaane ke baare me soch raha hun. Wahan ka weather kaisa hai?"
  • Step 3 — Model tool use karne ka faisla karta hai: Guess karne ki jagah (jo woh kar nahi sakta — training data ka cutoff hai), model pehchanta hai ki "get_weather" tool helpful hoga. To normal text response ki jagah, woh ek structured request produce karta hai: get_weather call karo, argument city = "Lisbon". Critical part: model weather check nahi karta. Uske paas internet connect karne ya code run karne ki ability nahi hai. Woh sirf ek structured text produce karta hai jo kehta hai "mujhe lagta hai ye tool in inputs ke saath call hona chahiye". Woh intent declare karta hai — jaise doctor prescription likhta hai; doctor dawai nahi banata, woh likhta hai kya karna chahiye, pharmacist use fulfill karta hai.
  • Step 4 — Tumhara code function execute karta hai: Tumhari application — jo code tumne model ke aas-paas likha hai — structured request dekhta hai, actual weather API call karta hai, aur wapas pata hai: "Lisbon, 22°C, partly cloudy, 15% chance of rain."
  • Step 5 — Result model ke paas wapas jata hai: Tumhara code weather data model ke context me feed karta hai. Ab model ke paas real, current information hai. Woh user ko jawab deta hai: "Lisbon agle hafte bahut achha lag raha hai — 22°C aur mostly sunny, sirf halki baarish ka chance. Shaam ke liye light layer pack kar lena."

Ye five-step loop — tools describe karo, question lo, model tool request kare, code execute kare, result wapas feed ho — function calling ka beating heart hai. Isi mechanism ne aakhir me brain in a jar ko bahari duniya se connect kiya.

Tool calling ne sab kuch kyun badal diya?

Tool calling seismic shift thi kyunki isne model ko tumhari application ke workflow ke center me decision-maker bana diya. Traditional software me har path deterministic tha: human programmer pehle se decide karta tha ki application har possible path par kya karega. Agar user ye click kare, to woh karo. Agar ye condition meet ho, to ye code run karo. Har decision hardwired tha. Tool calling ne ek fundamentally alag tarah ka software introduce kiya — jahan ek non-deterministic system (model, jo reason karta hai aur improvise karta hai) center me baithta hai, aur deterministic systems (tumhara code, APIs, databases) uske haath-pair ka kaam karte hain. Model steering wheel nahi pakadta — tumhara code ab bhi reliable infrastructure deta hai — lekin woh decide karta hai situation ke hisaab se kaunsa "tool" uthana hai. Isse software me ek naya contract bana: deterministic systems haath-pair hain, model judgment aur interpretation deta hai. Task describe karne aur execute karne ke beech ka ye bridge is poori book ki foundation hai.

Structured Outputs — Ek Related Unlock

Function calling ke saath-saath ek aur capability mature hui jo mention karne layak hai: structured outputs. Isse pehle, model se predictable format me data return karwana ek constant battle thi. New Capability, New Problems

Apni saari power ke saath, tool calling ne ek nayi class ki headaches introduce kar di. Model hamesha sahi tool nahi pick karta, aur hamesha sahi tareeke se use bhi nahi karta. Ye failures aksar subtle aur debug karne me mushkil hote the.

Agents — ReAct aur Agent Loop

Tool calling ne model ko haath de diye. Lekin haath akele goals pursue nahi karte — woh single actions execute karte hain. "Ek tool call execute karo" se "ye poora kaam mere liye kar do" tak pahunchne ke liye, aise system ki zaroorat hai jo actions ko chain me jod sake, observe kar sake kya hua, aur decide kar sake aage kya karna hai — bina human ke next step decide kiye. Woh system hai agent.

ReAct: Reason + Action

Late 2022 me, researchers ne ek important pattern formalize kiya ek paper me — "ReAct: Synergizing Reasoning and Acting in Language Models". Idea simple tha: model ko ya to sochne ya act karne (tool use karne) par force karne ki jagah, use dono ko interleave karne do. Model ek thought produce karta hai — text jo ek "action" declare karta hai — action execute hoti hai (tool use hota hai, tool calling ke rudimentary version ke saath), result wapas feed hota hai, aur loop tab tak chalta hai jab tak model na kahe ki ho gaya.

Model se ek aisa sawaal poochho jo woh apni training data se answer nahi kar sakta — jaise "Apple Remote ke alawa, aur kaunsa device us program ko control kar sakta hai jise Apple Remote originally control karne ke liye design kiya gaya tha?" — to tumhe aisi trajectory dikhegi:

ReAct trajectory — book me jaisa printed hai

Model text produce karta hai ek structured pattern me; jab action chahiye hoti hai, surrounding code (harness) us text ko parse karta hai, indicated tool execute karta hai, aur results wapas context me inject karta hai.

Thought 1: I need to search Apple Remote and find what program it was designed to control.
Act 1: Search[Apple Remote]
Obs 1: ...originally designed to control the Front Row media center program...
Thought 2: Now I need to find what else can control Front Row.
Act 2: Search Front Row (software)
Obs 2: ...controlled by an Apple Remote or the keyboard function keys.
Act 3: Finish[keyboard function keys]

The Agent Loop — agent asal me kya hai?

Online hype se pare, agent asal me ye hai: ek LLM kuch tools se connected, ek loop me chal raha, ek kaam karke phir decide kar raha hai aage kya karna hai. Bas. Yehi poori cheez hai. Ye chhota lagta hai jab tak tum baith kar socho nahi ki ye kya badalta hai. Prompt engineering ke saath tumhe ek response milta tha. Tool calling ke saath ek action milta tha. Agent ke saath tumhe ek system milta hai jo chain kar sakta hai: search → read → synthesize → write/plan → code → test → debug → iterate — sab bina human ke next step decide kiye. Is point par, LLMs sirf questions answer nahi kar rahe the — woh goals pursue kar rahe the.

Production agents routers ki tarah behave karte hain

Production me sabse effective agents routers ki tarah behave karte hain. Woh ek intent receive karte hain, use classify karte hain, aur kaam ko specialized tools ko dispatch kar dete hain: web search module, code executor, memory lookup, database writer. Insight ye nahi hai ki model ko sab kuch pata hona chahiye — insight ye hai ki model ko pata ho kaunsa tool kis problem ke liye aur kab use karna hai.

Interview tip: "Agent kya hai?" — jawab ek line me: "LLM + tools + loop." Agar interviewer aur detail maange, to ReAct ka Thought → Act → Obs pattern aur router wali baat add karo.

Why a Folder with a Markdown File Is the Answer

Hum sab agree kar sakte hain ki kisi task me tum jitna zyada domain knowledge laoge, us domain me tumhare outputs utne hi behtar honge. Agents ke liye bhi wahi sach hai. Product management ka ek concrete case lo.

Generic agent vs skill wala agent — PRD example

Ek generic agent se kaho "ek naye onboarding flow ke liye product requirements document (PRD) likho". Tumhe kuch aisa milega jo kisi bhi naye onboarding flow ke liye PRD jaisa lage. Reasonable problem statement. Plausible user stories. Waisa doc jo ek contractor apne pehle hafte me produce karega, usse pehle ki woh tumhare product ke baare me kuch jaane — kaunsa user segment onboarding par churn karta hai, pichhle quarter kaunse experiments chalaye aur unhone kya bataya, kaunsa engineer aankh roll karega agar "success metrics" me numerator aur denominator na ho, tumhare VP of Product problem ko kis framework me frame karwana chahte hain, 2024 me tumne kya try kiya jo kaam nahi kiya aur kyun koi uske baare me phir se sunna nahi chahta. Agent fluent hai. Woh informed nahi hai. Output competent aur forgettable hai — jo PRD review me roughly wrong ke barabar hai.

Ab agent ko ek folder do. Usme: tumhare sabse recent teen PRDs, tumhare VP of Product ne likha ek page ka guide ki team problems ko kaise frame karti hai, experiments ki ek chhoti list jo tumhari team ne product ke is hisse me chalaye aur har ek ne kya sikhaya, tumhari team ki "good" success metrics ki definition do examples aur ek cautionary tale ke saath, aur ek script jo pichhle quarter ke funnel numbers PostHog se pull karta hai. Ab tumhe ek PRD milta hai jo tumhari team ka PRD lagta hai. Woh judgment jo tumhari team ke senior PM ko develop karne me shayad 4 saal lage, folder me baitha hai, aur agent use kar raha hai.

Woh folder ek skill hai. Aur pehle output aur dusre ke beech ka farak hi is poori book ka topic hai. Bottleneck ab intelligence nahi hai. Bottleneck ye hai ki context-specific expertise ke bina intelligence aisa kaam produce karta hai jo competent lekin forgettable hota hai. Ek capable generalist jise pata hi nahi ki "yahan kaam aise hota hai".

The story so far — ek line me

Prompting ne gap ko model ki capabilities se uske interface tak move kiya. Bottleneck action karne ki inability thi. Tool calling ne gap ko interface se actions tak move kiya. Bottleneck ban gaya kaunsa tool pick karna hai, kaise use karna hai, aur use multiple times effectively kaise use karna hai. Agents ne gap ko actions se choices tak move kiya. Bottleneck ban gaya expertise — tumhare specific context me "good" kaisa dikhta hai. Hum is ladder ke aakhri gap par aa gaye hain: general-purpose agent aur useful agent ke beech ka gap. Intelligence aur expertise ke beech ka gap. Aur sawaal — expertise ko agent tak kaise transfer karein? — ka jawab wahi hai jo humans ke liye hamesha se raha hai: likh do.

A Folder with Markdown Instructions is All You Need

Expertise transfer karne ke liye, tum use ek markdown file me likhte ho aur ek folder me daal dete ho. Bas. Wahi cheez jo humans 5,000 saal se kar rahe hain expertise ko ek dimaag se dusre dimaag me move karne ke liye — plain language me instructions compose karna aur unhe kahi rakhna jahan reader unhe dhoondh sake — wahi cheez agents ke liye bhi kaam karti hai. Format nahi badla. Intended reader badla.

Ek SKILL.md ek manual hai. Structurally, ye wahi tarah ka document hai jo ek senior PM apne pehle din par junior hire ko deta hai (markdown text me likha, pdf ki jagah), wahi tarah ka document jo ek cook apni kitchen wall par tape karta hai, wahi tarah ka document jo ek sysadmin likhta hai jab woh 3am par page hokar thak jata hai. Isme technically kuch novel nahi hai. Tum ek perfectly achhi skill notebook me pencil se draft kar sakte ho. Novelty isme hai ki kaun, ya kya, use padh raha hai. Isi liye book baar-baar kehta hai ki jawab comically simple lagta hai. Kyunki hai. Expertise ke liye naya format invent karne ki zaroorat nahi thi. Format hamare paas tha. Markdown — sirf ek plain text file kuch special features ke saath. Plain language me likhi ek text file, ek folder me save ki hui, optionally ek-do scripts ke saath (jo tools ka kaam karte hain) aur kuch reference files. Bas.

Har format jo humne pehle try kiya — wiki, runbook, onboarding doc — woh pehle se hi skill banne ki koshish kar raha tha. Woh ban nahi sakta tha, kyunki available reader sirf ek human tha jo inevitably distract ho jata, step four bhool jata, step seven memory se kar deta, aur kaam ek ghante late ship karta. Ab ek aisa reader hai jo distract nahi hota, steps skip nahi karta, aur half-remember nahi karta. Aur woh format jo hamesha se sense banata tha — "yahan kaam aise hota hai" — use aakhir me ek useful jagah mil gayi.

Yaad rakho: "Format nahi badla, reader badla" — ye line poori book ka thesis hai. Skill ek naya technology nahi hai; ye woh moment hai jab ek purani cheez ko aakhir me apni dusri audience mil gayi.

Inside SKILL.md

Har skill ko ek SKILL.md file chahiye. Ye woh document hai jo agent padhta hai jab skill activate hoti hai, aur ye ekmatra file hai jo strictly required hai — baaki sab optional scaffolding hai uske aas-paas. TIP — SKILL.md filename ALL CAPS me likho: Wajah ye hai ki ye ek aisi file hai jo deterministically padhni hai aur agent tool me hardcoded hai. All-caps convention ye signal karta hai. To SKILL.md file ka naam capitalise karna mat bhoolna!

Ek achhi SKILL.md kaisi hoti hai?

Ek achhi SKILL.md ek aisi recipe jaisi padhti hai jo kisi ne likhi ho jisne kaam sau baar kiya ho. Woh agent ko batati hai: kaunse inputs expect karne hain, kaunse steps follow karne hain, kaunse outputs produce karne hain, aur kin pitfalls par nazar rakhni hai. Woh format requirements, quality standards aur edge cases ke baare me explicit hoti hai jo itni baar aate hain ki mention karne layak hain.

Concrete example — email-writing skill

Maano tum apne kaam me do tarah ke email likhne me irritating amount of time spend karte ho. Pehla internal kind — team ko quick updates, manager ko status notes, kabhi-kabhi dusre department ke peer ko "hey, just looping you in". Dusra external kind — clients ko replies, prospects ko intro emails, woh careful follow-ups ek call ke baad jahan kuch theek se land nahi hua. Tum ye saalon se kar rahe ho. Tumhe feel hai. Internal emails chhote hote hain, lowercase-friendly, aur context assume karte hain. Client emails warm lekin specific hote hain, "circle back" jaisi phrases se bachte hain, apology ki jagah answer se lead karte hain, aur hamesha — hamesha — "let me know!" ki jagah ek clear next step ke saath close karte hain. Ye sab kahin likha nahi hai. Ye tumhare dimaag me rehta hai, aur bure dinon me jab tum thake hue hote ho aur email thoda flat nikal jata hai, to tumhe woh gap feel hota hai — tum achhe din par kaise likhte, aur tumne asal me kaise likha.

Skill woh hai jo tum tab banate ho jab tum decide karte ho ki woh "good day" judgment kahi rakh do jahan use reuse kiya ja sake. Tum ek folder banate ho. Uska naam rakhte ho email-writing. Uske andar SKILL.md naam ki file banate ho. Aur us file ke upar, YAML ke ek chhote block me, naam aur chhoti description likhte ho:

---
name: email-writing
description: Drafts emails in [Name]'s voice for both internal team
updates and external client correspondence. Use when the user asks to
"write an email", "draft a reply", "send an update", or pastes
an email thread to respond to.

Uske neeche actual instructions likhte ho:

SKILL.md — email-writing instructions (book me jaisa printed hai)

Book me printed SKILL.md example, poora — jaisa ka taisa.

## Instructions

Identify the recipient type before drafting. If the email is to a
teammate or internal stakeholder,
follow the **Internal** rules. If it is to a client, prospect, or
external partner, follow the **External** rules.

### Step 1
- Determine if email is internal or external

### Step 2
- Implement rules for appropriate email

#### Internal emails
  - Lowercase opener, no greeting line.
  - Three sentences maximum unless the topic genuinely needs more.
  - Assume shared context — do not re-explain background the recipient
already has.

#### External emails
  - Open with the answer or update, not "I hope you're doing well."
  - Warm but specific; avoid the word "circle."
  - Close with a single concrete next step the recipient can act on
(not "let me know!").

### Step 3
#### Bad-news or missed-deadline emails
  - Name the issue directly in the first sentence — do not bury it.
  - State what is being done about it before any apology or context.

### Step 4
#### Before sending
  - Confirm the email contains exactly one next step.
  - Confirm tone matches recipient type per Step 2.

Bas. Yehi skill hai. Mechanically, ye ek folder hai jisme ek markdown file hai. Tum poori cheez notebook me pencil se draft karke transcribe kar sakte the. Na compilation step hai, na SDK, na special editor, na koi schema memorize karna hai — YAML header ke upar-neeche wale teen dashes ke alawa. Aur phir bhi, isne woh sab kuch capture kar liya jo tumhare dimaag me rehta hai jab tum achhe din par emails likhte ho. Agent ko ye folder do, aur use email draft karne ko kaho, aur jo email woh draft karega woh noticeably zyada tumhare jaisa lagega, usse jo woh folder ke bina produce karta. Inside the Context Window

Ye samajhne ke liye ki instructions paste karna scale par kyun fail hota hai, tumhe woh surface dekhni hogi jahan agent asal me sochta hai. Ye surface hai context window — text ka ek finite buffer jo agent ki working memory ka kaam karta hai. Jab agent ek session start karta hai, to uska context window khaali nahi hota. User ek character bhi type kare, usse pehle buffer me kai alag pieces of text load ho chuke hote hain.

Session start hote hi buffer me kya hota hai?

  • System prompt: Instruction set jo define karta hai ki agent general me kaise behave kare — persona, rules, defaults, formatting preferences, escalation policies. Ye agent banane wale ne likha hota hai, user ne nahi, aur ye har turn me buffer ke upar baithta hai. Agent ke hisaab se ye kuch sau tokens se lekar kai hazaar tak ho sakta hai.
  • Tool descriptions: Agent ko tools free me nahi milte — use bataya jata hai ki woh exist karte hain. Har tool ke liye buffer me description hoti hai — tool kya karta hai, kaunse arguments leta hai, kya return karta hai, aur kab use karna chahiye. Kuch achhe se described tools kuch sau tokens hote hain. Ek realistic agent — read-email, send-email, search-calendar, create-event, search-files, read-file, write-file, search-web, aur aadha dozen domain-specific tools — kuch bhi karne se pehle kai hazaar tokens le chuka hota hai.
  • User ka message: User ne asal me jo type kiya. Usually chhota.

Is baseline me optional elements add ho sakte hain — memory files, domain knowledge aur dusre — lekin hum us approach ke effect par focus karte hain jiske against ye chapter argue kar raha hai: skills ko seedha system prompt me paste karna.

Baseline kaise badhti hai — ek skill se pachaas tak

Tumhare paas ek skill hai, email-writing. Instructions shayad 300 tokens. System prompt me paste karo. Buffer baseline 300 tokens badhti hai. Theek hai. Dusri skill likhte ho — meeting-notes. 600 tokens. Paste karo. Baseline ab 1,000 tokens bhaari ho gayi. Teesri — calendar-triage. 500. Chauthi, paanchvi, samajh gaye. Jab tum dus skills likh chuke hote ho — jo koi bhi working professional kuch mahino me naturally accumulate kar lega — to system prompt me 6,000 se 10,000 tokens ki skill instructions baithi hoti hain. Jab tum pachaas likh chuke hote ho — jo ek real job handle karne wale agent ke liye perfectly reasonable number hai — to 30,000 se 50,000 tokens use me hain. Aur woh har token har turn me buffer me hai, chahe user kuch bhi poochh raha ho. Agle turn me bhi, aur uske agle turn me bhi — kyunki system prompt turns ke beech clear nahi hota — woh floor hai jis par har turn banta hai.

Cap fixed hai — working room shrink hoti hai

Context window ka ek fixed cap hai. Har model ka ek hota hai — 128k tokens se lekar 1 million tak, model par depend karta hai — aur woh cap text ki total amount hai jo model ek saath padh sakta hai. Baseline har skill ke saath badhti hai, working room utni hi shrink hoti hai, aur curve flat nahi hoti. Agar baseline 50,000 tokens ki skill instructions hai, usse pehle ki user kuch bole, to 200,000-token window wale model par tumhare paas 150,000 tokens ki working room hai — minus tool descriptions, minus conversation history aur tool results (jo model ko har sawaal ka jawab dene ke liye padhne padte hain) jaise-jaise woh accumulate hote hain. Chhote model par, tum pehle user message padhne se pehle hi zyada tar window use kar chuke ho. Yehi woh problem hai jise skills-as-folders solve karne ke liye design ki gayi hain — aur agla section batata hai kaise.

Interview tip: Context window ka math interview me strong point hai: 1 skill = 300 tokens, 10 skills = 6–10k tokens, 50 skills = 30–50k tokens. Aur system prompt turns ke beech clear nahi hota — ye floor hai, har turn wahi se banta hai.

Progressive Disclosure — Teen Levels

To sawaal: folder ki ceremony kyun? Jawab ke liye hume limited context window ko circumvent karne ka tareeka dekhna hoga. Skills ye karti hain agent ko sahi cheez, sahi moment par, sahi amount me dekar. Uske liye chahiye progressive disclosure.

Progressive disclosure kya hai?

Progressive disclosure interface design se liya gaya ek pattern hai jahan information sirf tab reveal ki jati hai jab user (ya is case me agent) ko uski zaroorat ho. Runtime par, agent ko har available skill ka sirf metadata dikhta hai (file ke upar wala YAML!) — uska naam aur ek chhoti description. Bas itna hi kaafi hai agent ko ye jaanne ke liye ki skill exist karti hai aur roughly kya karti hai. Sau skills ke liye ye kuch hazaar tokens cost karta hai — crowded context window me bhi manageable. Jab agent determine karta hai ki skill current task ke liye relevant hai, to woh poori SKILL.md padhta hai. Ab detailed instructions context me hain, agent ke next steps ko guide kar rahi hain. Woh instructions additional files ko reference kar sakti hain — style guide, template, example output — agent unhe bhi padhta hai, lekin sirf zaroorat padne par. Kisi bhi point par poori skill library memory me nahi baithti. Context window me sirf woh hota hai jo turant relevant hai.

Disclosure ke teen levels

Skills disclosure ka ek three-level system use karti hain, jo ensure karta hai ki specialized expertise available ho bina context window overload kiye:

  • First Level — YAML Frontmatter (SKILL.md ka upar wala hissa): Ye metadata hamesha agent ke system prompt me load rehta hai, aur bas itni information deta hai ki agent jaan sake ki skill kab relevant hai.
  • Second Level — SKILL.md ka Body: Poori instructions aur guidance sirf tab load hoti hain jab agent determine kare ki skill current task ke liye relevant hai.
  • Third Level — Linked Files: Additional files — jaise scripts, references ya assets — skill directory ke andar bundled hote hain, aur agent unhe discover karke load karta hai sirf jab use task complete karne ke liye unki zaroorat ho.

To sawaal ka jawab — "hum file ke upar ye weird YAML notation kyun use karte hain?" — ye hai ki woh important purpose serve karta hai: agent ko batana ki skill kya hai, kya karti hai, kab use karni hai aur uski key capabilities kya hain, aur baaki ka load kab karna hai ye agent ke decision par chhod dena. Isi tarah tum agent ko sau skills se equip kar sakte ho bina uski performance degrade kiye. Skills disk par files ke roop me exist karti hain, aur agent ki file-reading capability just-in-time knowledge retrieval ka mechanism ban jati hai. Ye bilkul waisa hai jaise ek human professional kaam karta hai: tum office ki har procedure manual memorize nahi karte, lekin tum jaante ho woh kahan hain aur kab unhe dekhna hai.

To hum progressive disclosure se context window protect kar sakte hain aur skill sirf tab load karte hain jab zaroorat ho — agent jaan sakta hai ki kaunsi skills available hain, lekin woh meat sirf tab load karega jab user ki request uski demand kare. Theek hai, agar agent woh pull karta hai jo use chahiye, jab chahiye, to woh kis tarah ki files pull kar sakta hai? Aage wahi baat hai.

Yaad rakho: Teen levels — metadata (hamesha loaded) → SKILL.md body (activation par) → linked files (demand par). Yehi progressive disclosure hai. Interview me ye teen levels bol pao to concept pakka hai.

Scripts — Reproducible Behaviour

Progressive disclosure ke saath, agent skill folder me haath daal kar woh leta hai jo use chahiye. SKILL.md entry point hai, lekin skills ko complex tasks karne ki asli potential dene ke liye aur chahiye. Uske aas-paas ki scaffolding — chapter ke shuru me sketch kiye gaye teen optional folders — hi hai jisse zyada tar skills apna real kaam kar pati hain.

Beyond the three folders: Teen optional folders — scripts/, references/, assets/ — conventions hain, allowed cheezon ka poora set nahi. Published Agent Skills standard explicitly aur jagah chhodta hai. Wahi teen folders isliye use hote hain, ye nahi ki woh kahin hardcoded hain — isliye ki woh cleanly map karte hain un teen kaamon par jo skill ko asal me karne hote hain: code run karo, background material padho, aur final output me pieces use karo. Zyada tar skills ko kabhi chauthe folder ki zaroorat nahi padti, aur bina wajah ek invent karna sirf shape add karta hai, function nahi. Jab tum ek add karo, to yaad rakho agent ko folder names ki koi built-in awareness nahi hai conventions se pare; woh directory me navigate karega kyunki SKILL.md ne use kaha, isliye nahi ki directory exist karti hai. Ek unreferenced folder dead weight hai. Ek genuine restriction flag karne layak hai: skill folder ke andar koi README.md nahi. Documentation SKILL.md me ya references/ ke andar belong karti hai. Skill folder ke bahar repo-level README, GitHub browse karne wale human visitors ke liye, theek hai — aur recommended hai.

Scripts ka kaam — ek example

Ab ek alag skill imagine karo jo workshops ke liye ya social media par share karne ke liye custom PDF handouts generate kar sakti hai. Agar user kisi bhi tarah ka cheatsheet, guide ya action document maange, to skill activate hogi aur precise specifications follow karke ek branded handout generate karegi. Agent kuch SKILL.md file padhta hai, source material gather karta hai, use sections me organize karta hai, aur polished PDF produce karne ke liye — students ko dene ya overly enthusiastic LinkedIn posts par share karne ke liye — scripts use kar sakta hai.

Branded-handout folder ke andar, hum ek scripts/ subdirectory add karte hain. Usme ek chhoti Python file — maan lo create-handout.py — jo ek .json format (structured file) ki file leti hai jo agent ne produce ki hai aur use final artifact me badal deti hai. Woh title, sections, callouts, code blocks aur footer notes padhti hai. Ek finished PDF banati hai aur use sahi folder me save karti hai. SKILL.md ko us process ki har line explain karne ki zaroorat nahi hai. Use sirf agent ko batana hai ki content kis shape me prepare karna hai aur script kab use karna hai: ek baar handout content expected JSON structure me organize ho jaye, to handout generator run karo.

Prose judgment ke liye, code repeatable kaam ke liye

Agent judgment-heavy kaam me achha hai: decide karna handout me kya belong karta hai, useful headings chunna, messy source ko clear teaching artifact me compress karna, aur material ko direct instructional language me likhna. Script repeatable production kaam me achha hai: wahi fonts, spacing, borders, accent colors, page size, file naming pattern aur PDF export process — har baar same. Script skill ko ek reliable handrail deta hai jab bhi output ko sirf text ka block nahi, ek real artifact banna hota hai. Useful handout design karna fuzzy hai, jabki wahi brand system ko print-ready PDF me render karna precise hai. Skills dono ko deliberately use karti hain: judgment ke liye prose, aur un hisson ke liye code jo har baar same behave karne chahiye.

Script ya Tool? — rule of thumb: Script scripts/ me rehta hai aur bash ke through run hota hai jab skill use call kare. Uska code kabhi context me enter nahi karta; sirf uska output karta hai. Cost: invoke karne tak zero tokens. Tool — koi bhi MCP connection samet — har turn me system prompt me advertise hota hai. Cost: upfront context tokens, kahin se bhi callable. Rule: agar woh bahari duniya se baat karta hai (Gmail, calendar, database), to use tool banao. Agar woh data par local deterministic kaam hai jo agent ke paas pehle se hai (validate, parse, format), to use script banao.

Context Isn't Free — Context Rot

Ab tak hum jaante hain ki context window ka ek cap hai, aur progressive disclosure tumhe cap ke neeche rakhta hai — lekin ye kahani ka sirf aadha hissa hai. Woh aadha jo tum dekh sakte ho, cap hai. Context Rot — Chroma Research (2025)

Iska sabse clear (aur famous) evidence 2025 ki ek report se aata hai — Chroma Research ki. Atharah state-of-the-art models — Claude 4, GPT-4.1, Gemini 2.5, Qwen3 — aur deliberately simple tasks ki ek range me, wahi pattern baar-baar dikha: jaise input length badhti hai, performance increasingly unreliable hoti jati hai, un tasks par bhi jinhe wahi models chhoti lengths par trivially solve kar lete hain. Lesson jo hume dhyaan dena chahiye: relevant information buffer me present hai ya nahi — sirf ye matter nahi karta. Zyada matter karta hai ki uske aas-paas kya baitha hai. Do prompts jisme wahi answer ho, answer ke aas-paas kya hai us par bahut alag behaviour produce kar sakte hain. Ab ise wapas agent loop me le aao.

Agent loop ke dauraan context accumulation

Jaise pehle kaha, agent session start karta hai system prompt, tool descriptions aur user ke message ke saath (shayad kuch skills ke naam aur definitions?) — aur us point se buffer sirf badhta hai. Har tool call, call aur uska result add karta hai. Har file jo agent padhta hai, file ke contents add karti hai. Har search, har retrieved chunk, har page jo sub-question answer karne ke liye pull kiya gaya — sab session ke baaki hisse ke liye buffer me rehta hai. Ek bees-step agent loop session ko shuru ke kuch hazaar tokens se aasani se pachaas ya ek lakh tokens tak pahuncha sakta hai, bina kisi ke kuch galat kiye. Ye accumulation unavoidable hai. Loops me text produce karke aur tools use karke tasks execute karne wale agents ki nature hi context heavy hai by default. Agent ko apne prior steps padhne hote hain taaki woh jaan sake usne kya try kiya aur kya seekha. Tum real kaam karke buffer pristine nahi rakh sakte.

Jo tum kar sakte ho woh ye hai ki shuru me buffer me kya enter hota hai, uske baare me deliberate raho. Aur yahan skills ke liye ek strong case dikhta hai.

Progressive disclosure skills ko context efficient banata hai

Progressive disclosure pehle is chapter me cap ke neeche zyada skills fit karne ke tareeke ke roop me introduce hua tha. Woh framing sach hai, lekin woh jo ho raha hai use undersell karta hai. Gehra purpose ye hai ki buffer ko poore session me lean rakha jaye, kyunki lean buffer behtar outputs produce karta hai. Skills, jis tarah is chapter ne describe ki hain, system level par apply ki gayi ek discipline hain jo agent ko bias karti hai relevant cheez padhne ki taraf aur baaki ko chhodne ki taraf. Agar email-writing skill, meeting-notes skill, calendar-triage skill aur 47 aur skills sab system prompt me paste kar di jayein (plus tool descriptions aur baaki), to "Portugal ki capital kya hai?" ka jawab dene wala agent sirf tokens waste nahi kar raha hota. Chroma results ke hisaab se, woh us agent se measurably worse hota jo bina un skills ke loaded hai — kyunki irrelevant guidance khud ek distractor hai. Iska cost real hai, chahe buffer me jagah bachti ho.

Skills, folders ke roop me jise agent prompt me bake karne ki jagah padhta hai, agent ki apni reading capability ko lekar use ek context management mechanism me badal deti hain. Jo load hota hai woh flight me decide hota hai, relevance se, ek skill ek baar me. System prompt advertise karta hai kya available hai. Agent woh reach karta hai jo task me fit hota hai. Baaki sab disk par rehta hai, jahan woh context ko crowd nahi kar sakta.

Yaad rakho: Context rot ka matlab: lamba context sirf mehenga nahi hai, woh output ko worse bhi banata hai — irrelevant cheezein distractor ban jati hain. Isliye lean buffer sirf cost saving nahi, quality strategy hai.

Conclusion — Aage Kya Aayega

Chapter ek claim ke saath khula tha: skills kaam karti hain kyunki woh pehli form factor hain jo ground up us constraint ke aas-paas design ki gayi hain jo agent ki har cheez ko govern karta hai — uska context window. Har part ka ek kaam hai

  • Skill ek folder hai kyunki folder pieces ko disk par rehne deta hai jab tak unki zaroorat na ho.
  • Progressive disclosure isse effectively kaam karwata hai, on-demand activation ke through context window protect karke.
  • Scripts deterministic kaam ko buffer se bahar rakhte hain — agent script run karta hai aur output padhta hai, lekin code khud kabhi context me enter nahi karta.
  • References disk par rehte hain jab tak situation unhe call na kare (jaise skill ke main body me instruct kiya gaya ho).
  • Assets kaam ke dauraan khole jate hain, usse pehle nahi.
  • Format ka har hissa, kuch had tak, buffer ko us par focused rakhne ke liye exist karta hai jo current task ko asal me chahiye.

Ab hum samajhte hain ki challenge kya hai, skills kaise kaam karti hain aur kyun, to hum visualize karna shuru kar sakte hain ki unke saath productively kaam karna kya matlab rakhta hai. F1End Matter · Interview FAQs
Interview FAQs
Skills / agents interviews (current era) ke liye — tool calling se lekar context rot tak, 30 sawaal-jawaab. Har jawaab isi book ke concepts par aadharit hai.
Q01 Skill kya hoti hai?
Ek skill ek folder hai jisme ek SKILL.md file hoti hai — aur optionally scripts/, references/ aur assets/ folders. Folder me woh expertise likhi hoti hai jo pehle kisi ke dimaag me rehti thi — instructions, rules, examples, templates. Agent folder ko padhta hai aur kaam usi tareeke se karta hai jaise tum karte ho. Book ke words me: skill woh hai jo 'good day' judgment ko reusable jagah par rakh deta hai.
Q02 SKILL.md kya hai? Aur filename ALL CAPS me kyun likhte hain?
SKILL.md skill ki core file hai — woh document jo agent padhta hai jab skill activate hoti hai, aur ekmatra file jo strictly required hai. Upar YAML frontmatter (naam + description) aur neeche actual instructions hote hain. Filename ALL CAPS me isliye likhte hain kyunki file deterministically padhni hai aur agent tool me hardcoded hai — all-caps convention ye signal karta hai.
Q03 YAML frontmatter ka kaam kya hai?
YAML frontmatter SKILL.md ke upar ka chhota block hai — teen dashes ke beech skill ka naam, description aur metadata. Agent is metadata ko dekh kar decide karta hai ki skill current task ke liye relevant hai ya nahi. Ye progressive disclosure ka Level 1 hai: metadata hamesha loaded rehta hai, poori instructions sirf tab load hoti hain jab skill relevant ho.
Q04 Progressive disclosure kya hai? Uske teen levels kaunse hain?
Progressive disclosure ka matlab hai — information sirf tab reveal karo jab zaroorat ho. Teen levels: Level 1 — YAML frontmatter (metadata), hamesha loaded; Level 2 — SKILL.md ka body, sirf tab load hota hai jab skill relevant ho; Level 3 — linked files (scripts, references, assets), sirf tab load hote hain jab situation unki demand kare. Isi se agent sau skills ke saath bhi context window overload kiye bina kaam kar sakta hai.
Q05 Context window kya hai?
Context window text ka ek finite buffer hai jo agent ki working memory ka kaam karta hai — total amount of text jo model ek saath padh sakta hai. Har model ka ek fixed cap hota hai (128k se 1M tokens tak). Session start hote hi buffer me system prompt, tool descriptions aur user ka message load ho chuke hote hain — aur har tool call, file read aur search buffer ko aur bhar deta hai.
Q06 System prompt me saari skills paste karne se kya problem hai?
Ek skill (300 tokens) theek hai. Dus skills 6,000–10,000 tokens ban jati hain. Pachaas skills 30,000–50,000 tokens. Aur system prompt turns ke beech clear nahi hota — woh floor hai jis par har turn banta hai. To har turn me hazaron tokens irrelevant instructions padhe jate hain, working room shrink hoti hai, aur — Chroma Research ke hisaab se — irrelevant guidance output quality ko bhi degrade karti hai. Isi liye skills folders me rehti hain, system prompt me nahi.
Q07 Tool calling kya hai? Uska 5-step loop samjhao.
Tool calling woh mechanism hai jisse model text ke bahar action le sakta hai. 5-step loop: 1. Developer tools describe karta hai (JSON schema); 2. User question poochhta hai; 3. Model tool use karne ka faisla karke structured request produce karta hai (model khud tool execute nahi karta — sirf intent declare karta hai); 4. Tumhara code function execute karta hai (jaise weather API call); 5. Result model ke context me wapas feed hota hai, aur model informed jawab deta hai. Lab L1 me Lisbon weather example ke saath ye loop try karo.
Q08 Function calling aur tool calling me kya farak hai?
Concept wahi hai — naam rebrand hua. OpenAI ke June 2023 API me parameter ka naam 'functions' tha; December 2023 tak use deprecate karke 'tools' se replace kar diya gaya. 'Function' narrow, code-centric capability imply karta hai; 'Tool' zyada broad hai — web search, code interpreter, file reader, database connection, ya function — sab tools hain. Industry (Anthropic, Google, open-source) ne 'tool calling' ko standard term apna liya.
Q09 Toolformer paper kya tha?
February 2023 me Meta AI aur ek European university ke researchers ka paper — 'Toolformer: Language Models Can Teach Themselves to Use Tools'. Finding: model ko external system use karne ke kuch examples dikhao, aur woh khud seekh jata hai ki jab use bahar se help chahiye ho, to waisi request produce kare. Is simple idea ne tool calling ka seed plant kiya. OpenAI ne June 2023 me use product bana diya (function calling).
Q10 Agent kya hai? Ek line me batao.
Ek line me: LLM + tools + loop. Agent ek LLM hai jo kuch tools se connected hai, ek loop me chal raha hai — ek kaam karke phir decide karta hai aage kya karna hai. Prompt engineering se ek response milta tha, tool calling se ek action, agent se poora goal pursuit milta hai: search → read → synthesize → write → code → test → debug → iterate — bina human ke next step decide kiye.
Q11 ReAct kya hai? Thought, Act, Obs ka matlab?
ReAct (late 2022) ek pattern hai jahan model sochna aur act karna interleave karta hai: Thought (text — kya karna hai), Act (tool use — jaise Search[...]), Obs (tool ka result wapas context me). Loop tab tak chalta hai jab tak model Finish na kahe. Book ka example: Apple Remote wale sawaal par Thought 1 → Act 1 → Obs 1 → Thought 2 → Act 2 → Obs 2 → Finish. Lab L5 me ye loop step by step chalao.
Q12 Prompt engineering aur skills me kya farak hai?
Prompt engineering single interaction ko behtar banati hai — prompt likho, output padho, rewrite karo. Skills expertise ko package karti hain — folder me likhi hui instructions, examples aur scripts jo agent har baar use kar sakta hai, bina tumhe prompt dobara likhne ki zaroorat. Prompting ne bataya ki output quality input quality par depend karti hai; skills us insight ko reusable format me badal deti hain. Aur prompting ki ceiling thi — model describe kar sakta tha, kar nahi sakta tha. Skills + tools + agent loop us ceiling ko todte hain.
Q13 Structured outputs kya hain?
Structured outputs guarantee karte hain ki model ka response ek exact schema follow kare — jaise sentiment = 'positive', key_topics = ['shipping speed', 'packaging'], recommendation = 'yes'. Isse pehle model JSON ko markdown me wrap kar deta tha ya field names badal deta tha. Tool calling models ko actions lene deti hai; structured outputs models ko aisa data produce karne deti hain jise dusra software reliably consume kar sake.
Q14 Context rot kya hai?
Context rot Chroma Research (2025) ki finding hai: jaise input length badhti hai, models ki performance simple tasks par bhi unreliable hoti jati hai — chahe relevant information buffer me present ho. Matter karta hai ki answer ke aas-paas kya baitha hai. 200K-token window ka matlab ye nahi ki model 150,000 tokens ko utni cleanly handle karta hai jitni 5,000 ko. Isi liye lean buffer sirf cost saving nahi, quality strategy hai. Lab L7 me context length slider se ye dekho.
Q15 Script aur tool me kab kaunsa use karna chahiye?
Rule of thumb: agar kaam bahari duniya se baat karta hai (Gmail, calendar, database), to use tool banao — tool har turn me system prompt me advertise hota hai. Agar kaam local deterministic hai data par jo agent ke paas pehle se hai (validate, parse, format), to use script banao — script scripts/ me rehta hai, bash se run hota hai, uska code kabhi context me enter nahi karta, sirf output karta hai. Cost: invoke karne tak zero tokens.
Q16 References aur assets me kya farak hai?
References agent padhta hai apne behaviour ko shape karne ke liye — jaise style-guide.md, kaam hone se pehle. Assets agent output me use karta hai — jaise logo, icons, templates — kaam ke dauraan. Reference kaam ko influence karti hai; asset kaam ka hissa ban jata hai. Dono ke moments alag hain, isliye folders alag hain.
Q17 Skill folder me README.md kyun nahi rakhte?
Published Agent Skills standard ke hisaab se, skill folder ke andar README.md allowed nahi hai. Documentation SKILL.md me ya references/ ke andar belong karti hai. Skill folder ke bahar repo-level README, GitHub browse karne wale human visitors ke liye, theek hai — aur recommended hai. Aur yaad rakho: agent ko folder names ki koi built-in awareness nahi hai — woh directory me navigate karega kyunki SKILL.md ne use kaha, isliye nahi ki directory exist karti hai. Unreferenced folder dead weight hai.
Q18 Agent Skills standard kya hai?
Agent Skills ek open standard hai (Anthropic ne popularize kiya, Claude ke creators) jo skill folders ke liye conventions define karta hai: SKILL.md + YAML frontmatter, scripts/, references/, assets/ folders. Book is standard ke concepts par based hai — progressive disclosure ka three-level system usi guide se aata hai. Standard explicitly aur folders ki jagah chhodta hai, lekin wahi teen sabse common hain kyunki woh skill ke teen kaamon se map karte hain: code run karo, background material padho, output me pieces use karo.
Q19 Skill kab activate hoti hai?
Runtime par agent ko har skill ka sirf metadata (YAML frontmatter) dikhta hai. Jab agent determine karta hai ki skill current task ke liye relevant hai — naam aur description ko user ki request se match karke — to woh poori SKILL.md padhta hai. Phir instructions me reference hone par linked files load hoti hain. Kisi bhi point par poori skill library memory me nahi baithti.
Q20 Model galat tool kyun pick karta hai?
Book ka customer support example: customer 'blue sneakers wale order' ka status poochhta hai, aur model search_products call kar deta hai (catalog browse) jabki lookup_order sahi tha (shipment track). Ya model lookup_order call karta hai lekin order number hallucinate kar deta hai jo message me tha hi nahi. Wajah: tool descriptions ambiguous hoti hain. Fix tool descriptions likhne ki design discipline me hai — tool ko clearly describe karo ki kab use karna hai aur kab nahi. Lab L6 me ye scenario try karo.
Q21 Intelligence vs agency ka gap kya hai?
Intelligence ka matlab hai task ko describe aur samajh sakna; agency ka matlab hai task ko asal me kar sakna. Prompting se model describe kar sakta tha — refund policy explain kar sakta tha — lekin refund issue nahi kar sakta tha. Tool calling ne agency ka pehla hissa diya (haath), agents ne use goal pursuit me badla. Skills us agency ko expertise deti hain — taaki model kaam tumhare tareeke se kare, kisi bhi tareeke se nahi.
Q22 'Brain in a jar' ka matlab kya hai?
Ye book ki phrase hai: model jar ke andar extraordinarily capable tha, lekin jar ke bahar ki har cheez se sealed off — woh button click nahi kar sakta tha, API hit nahi kar sakta tha, script run nahi kar sakta tha. Tool calling ne jar me pehla connection banaya. Prompting, tool calling, agents — har layer ne jar ko thoda aur khola.
Q23 'Reader is human' assumption ka kya matlab hai?
5,000 saal se expertise likhne ke har format — manual, wiki, runbook, onboarding doc — ne assume kiya ki reader insaan hai: document kaam batayega, insaan kaam karega. Document specification tha, insaan processor tha. Ab ye assumption optional ho gayi — document ke dusre end par woh cheez hai jo document ko execute kar sakti hai. Shelf ab shelf nahi raha, woh ek queue ban gaya hai. Format nahi badla, reader badla.
Q24 Context window ka tokens wala math samjhao.
Ek skill ~300 tokens. Dus skills = 6,000–10,000 tokens. Pachaas skills = 30,000–50,000 tokens. Ye sab system prompt me har turn me baitha rehta hai — turns ke beech clear nahi hota. 200,000-token window par 50,000-token baseline ka matlab hai 25% window pehle user message se pehle hi use. Progressive disclosure se baseline sirf metadata tak simat jati hai — sau skills ke liye bhi sirf kuch hazaar tokens. Lab L3 calculator se khud hisaab lagao.
Q25 Achhi skill kaise likhte hain? Signs kya hain?
Book ke hisaab se, achhi SKILL.md ek aisi recipe jaisi padhti hai jo kisi ne likhi ho jisne kaam sau baar kiya ho: inputs clear hon, steps explicit hon, outputs define hon, format requirements aur quality standards likhe hon, aur edge cases mention hon. Aur system level par, achhi skill buffer me apni jagah earn karti hai — progressive disclosure follow karti hai, zaroori cheez SKILL.md me rakhti hai, detail references/ me, deterministic kaam scripts/ me, aur output pieces assets/ me. Yehi Chapter 3 (Building Skills) ka topic hai — jo is Early Release me nahi hai.
Q26 Skills aur MCP (Model Context Protocol) me kya farak hai?
Book me MCP cover nahi hai — ye sawaal book ke bahar ka hai, lekin concept se juda hai. MCP tools ko connect karne ka protocol hai — model ko bahari systems tak pahunch deta hai (jaise Gmail, database). Skills expertise package karne ka format hai — model ko batata hai kaam kaise karna hai. Dono saath kaam karte hain: MCP haath deta hai, skills judgment deti hain. Book ka 'script vs tool' wala rule yahan bhi apply hota hai: bahari duniya se baat karne wali cheez tool hoti hai.
Q27 Skills ki limitations kya hain? (Two Honest Hedges)
Pehla hedge: gap narrow hua hai, vanish nahi hua — ab bhi tasks hain jinhe perfectly achhi skill wala agent bhi galat karega, domains hain jahan judgment likha hi nahi ja sakta, aur cases hain jahan human loop me rehna chahiye. Dusra hedge: skills current endpoint hain, final nahi — har layer ko agli layer ne replace kiya; skills ke baad bhi kuch aur aayega, ek richer ya zyada dynamic format. Point ye nahi ki skills hamesha ke liye hain — point ye hai ki abhi, is moment me, ye sabse consequential format hai.
Q28 PRD example se skill ka farak kaise samjhein?
Generic agent se PRD maango to woh kisi bhi onboarding flow ka PRD dega — reasonable, plausible, forgettable. Skill wale agent ko folder do (teen recent PRDs, VP ka framing guide, experiments ki list, success metrics ki definition, PostHog se funnel numbers pull karne wali script) to PRD tumhari team ka PRD lagta hai. Farak expertise ka hai — woh judgment jo senior PM ko 4 saal me develop hui, folder me baithi hai. Lab L8 me dono outputs side by side compare karo.
Q29 Skills aur RAG me kya farak hai?
RAG (Retrieval-Augmented Generation) model ko relevant documents retrieve karke context me daalta hai — knowledge dene ka tareeka. Skills expertise package karne ka tareeka hain — sirf knowledge nahi, instructions, steps, rules, scripts aur templates bhi. RAG batata hai 'kya pata hai'; skill batati hai 'kaam kaise karna hai'. Dono progressive disclosure jaisi hi soch share karte hain — sirf relevant cheez load karo — lekin skill ek poori form factor hai, sirf retrieval nahi.
Q30 Skills ka future kya hai? Aage kya aayega?
Book kehta hai skills aakhri shabd nahi hongi — kuch aur aayega, ek richer format, ek zyada dynamic format, kuch jiska humne abhi naam bhi nahi rakha. Machine code assembly aane par disappear nahi hua; prompting tool calling aane par disappear nahi hua — woh agle layer ka hissa ban gaya. Skills bhi agle format ka hissa ban jayengi. Lekin abhi, is moment me, folder me rakhi markdown file human expertise ko transfer aur automate karne ka ek generation ka sabse consequential format hai. Chapter 7 (Skills in the Wild) is direction me dekhega — jo is Early Release me nahi hai.
