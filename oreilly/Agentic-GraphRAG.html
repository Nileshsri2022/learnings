Preface — Demo se Production tak

Ek polished agent demo aur ek production system — jiss par service-level agreement (SLA) daav par laga ho — ke beech ka gap zyada tar teams ke andaze se bada hai. Ye kitab us gap ko bharne ke baare me hai: graph-based architecture se agents ko bharosemand banana.

Kitab kyun likhi gayi

Ek single-shot chatbot screenshot me theek lagta hai, lekin usme production ki capability nahi hoti. Ek prompt-chained agent toot jata hai jab use ek dozen steps tak state carry karni ho, conflicting sources ko reconcile karna ho, ya aisi jagah action lena ho jahan ek galat API call ka asli paisa lagta ho.

Capable engineers baar-baar usi deewar se takra rahe the aur usi tools ko utha rahe the — zyada context, bada model, lamba prompt, ek aur framework. Scaffolding uncha hota gaya; failure modes bas ek manzil upar shift ho gaye.

Core thesis — graph kyun

Graph-based architectures is loop ko todte hain, isliye nahi ki graphs koi jaadu hain, balki isliye ki wo do cheezein inspectable (dekhne aur jaanchne layak) bana dete hain jinme agents sabse zyada galti karte hain: agent kya jaanta hai aur agent kya kar raha hai. Jab ye dono prompt window me tokens ka ek blob rehne ke bajaye alag structures ban jayein, to agent-reliability ki kai problems seedhi process-design problems lagne lagti hain — aur process design karna field ko aata hai.

Timing bhi sahi hai: models behtar hote ja rahe hain, knowledge-graph tooling academic phase se nikal kar deployable ho gayi hai, aur GraphRAG, dual-graph architecture aur semantic backpropagation jaise integration patterns ab itne concrete ho gaye hain ki unpar production code likha ja sake.

Kaun padhe

  • Intermediate-to-advanced practitioners — engineers jinhone koi LLM feature ship kiya ho.
  • Data engineers aur architects — knowledge graphs par kaam karne wale.
  • Platform / SRE engineers — jinhe production me bharose layak agents chahiye.

Prerequisites: Python me comfort, basic graph-database concepts, aur LLMs + retrieval-augmented generation (RAG) se working familiarity. Deep knowledge-graph experience pehle se hona zaroori nahi hai.

Kitab kaise navigate karein

  • Part I (Ch. 1–2) — why aur architecture.
  • Part II (Ch. 3–4) — system ka knowledge aur memory banana (digital twin).
  • Part III (Ch. 5–6) — reasoning, planning aur tool use.
  • Part IV (Ch. 7–8) — evaluation, self-evolution, deployment aur optimisation.

Samay kam ho to pehle Ch. 1, 2 aur 5 padho; banana hai to Ch. 3 se shuru karo.

Chapter 1 — Enterprise Agentic AI ka Crisis

Subah 3 baje ek alert aata hai, ek AI incident copilot pehle se chal raha hai, aur wo galat fix suggest karta hai. Agent bewakoof nahi tha — wo andha tha. Uske paas system ka koi structured model hi nahi tha.

The 3 AM Incident — ek worked story

Acme Corp me on-call SRE subah 3 baje PagerDuty alert se jagta hai: checkout latency 2-second threshold se upar chali gayi hai. Ek AI 'incident copilot' agent pehle se chal raha hai. Wo sahi pehchanta hai ki database load me hai, lekin database ko scale up karne ki salah deta hai — galat fix. Asli wajah ek runaway batch job hai jo subah 2:47 baje shuru hua tha aur inventory table ko lock kar raha hai. Engineer use manually 47 minutes me fix karta hai. Agent ki salah se lagbhag $2,400 ka bekaar scaling kharcha hota, aur lock fix bhi nahi hota. Sabak: agent bewakoof nahi tha; wo andha tha — uske paas system ka koi structured model nahi tha.

The Pattern of Failure — teen baar-baar wale failure modes

  • Confident wrong answers — hallucinated runbook steps, invent kiye hue API parameters. Jaise ek customer-support agent ne ek $50,000 ka enterprise discount quote kar diya jo tha hi nahi, kyunki usne ek draft pricing document retrieve kar liya tha — $50,000 ki revenue exposure.
  • Context collapse — agent kuch tool calls ke baad pehle wali constraint bhool jata hai — jaise ek change ko dobara apply kar dena jise rollback karne ko kaha gaya tha.
  • Action without understanding — wo ek destructive command execute kar deta hai — peak traffic ke dauran ek service restart — kyunki koi guardrail us action ko uske blast radius se jodta hi nahi.

Ek survey figure: 2,300 enterprise AI projects me se sirf lagbhag 15–20% production tak pahunche, aur unme se lagbhag ek-chauthai ko baad me rollback kar diya gaya.

Ek hospital system ka case study bhi diya hai: ek agent ne same first name wale do patients ko mila diya — isliye kitab retrieval se pehle entity resolution ki baat karti hai.

Why Naive Agents Fail — teen gaps

1. The Data Gap: enterprise knowledge wikis, runbooks, tickets, code aur dashboards me bikra hota hai; chunks par vector search wo text deta hai jo similar hai, wo nahi jo sach ya current hai. Example: agent ne 2023 ka runbook retrieve kiya ek aisi service ke liye jo 2024 me rewrite ho chuki thi, aur ek wiki page jo live configuration se contradict karta tha.

2. The Reasoning Gap: LLMs pattern completion me achhe hain, multi-hop, stateful reasoning me kamzor — ek aise system par jise wo dekh hi nahi sakte. Agent symptoms list kar sakta tha, lekin 'batch job → table lock → connection pool exhaustion → checkout latency' wali chain nahi bana sakta tha, kyunki wo chain kisi ek document me thi hi nahi.

3. The Action Gap: tools flat lists of functions ki tarah expose hote hain — preconditions, side effects ya dependencies ka koi model nahi — isliye agent safe action aur dangerous action me farak nahi kar sakta, aur tool fail hone par recover bhi nahi kar sakta.

The Three Pillars: GraphRAG, Reasoning, Agency

  • GraphRAG — knowledge graph me grounded retrieval, taaki answers entities aur relationships tak traceable rahein.
  • Reasoning — graph par explicit, inspectable planning.
  • Agency — bounded, audited action, aise tools se jinke effects graph me modelled hain.

Kitab ki definition: 'agentic GraphRAG' in teeno ka combination hai — sirf graph index ke saath RAG nahi.

Chapter 2 — Agentic Graph Architecture Foundations

Graph kya hai, asal me? Nodes, edges aur properties — aur edge ka type hi knowledge hai. Is chapter me kitab ke teen graphs, dual-graph architecture aur agentic loop ki neev padti hai.

Graph kya hai, asal me?

Ek graph hota hai: nodes (entities — services, log, incidents, documents), edges (typed relationships — 'depends on', 'caused by', 'fixed by') aur properties (nodes aur edges par key–value attributes, jaise kisi service ka owner ya document ki date). Kitab zor deti hai: edge ka type hi knowledge hai — 'depends on' aur 'is a copy of' alag facts hain, aur ek vector store unme farak nahi kar sakta.

The Three Graphs of Agentic GraphRAG

1. Knowledge Graph — duniya ka durable model: Acme ke systems ke baare me kya sach hai (services, dependencies, owners, runbooks, past incidents). Ye dheere badalta hai, curated hota hai, aur retrieval ke liye ground truth ka source hai.

2. Action Graph — agent kya kar raha hai, iska model: current plan ek directed acyclic graph ke roop me, har step ek node (tool, inputs, expected outcome, status ke saath); edges dependencies hain ('step B ko step A ka output chahiye'). Ye tez badalta hai, har task ke liye banta hai, aur task khatm hone par discard ya archive kar diya jata hai.

3. Memory Graph — kya hua, iska model: past episodes, unke outcomes, aur unse distilled lessons, knowledge graph se linked (jaise 'ye fix is incident type par is service ke liye kaam kiya'). Ye agent ki long-term memory hai aur learning ki basis.

Teen graphs kaise interact karte hain

Ek query pehle knowledge graph ko chhooti hai (kya sach hai), planner action graph banata hai (kya karna hai), execution ke results memory graph me likhe jate hain (kya hua), aur memory graph wapas knowledge graph me feed karta hai (kya seekha — jaise incident ke dauran mili ek nayi dependency). Kitab is loop ko yahan outline me 'semantic backpropagation' kehti hai — detail Ch. 7 me hai.

The Dual-Graph Architecture

Kitab ka central architectural claim: knowledge graph aur action graph ko alag rakho, beech me ek well-defined interface ke saath. Dono ko mila dene se (transient plan state ko durable facts wale graph me store karna) 'state bleed' hota hai: plan ki ek temporary assumption permanent fact ban jati hai. Dono graphs sirf explicit, typed links se judte hain (jaise ek action step kisi knowledge node ko 'reads' karta hai, ya verification ke baad use 'updates' karta hai).

GraphRAG: Retrieval Over Graphs

Flat RAG chunks ko vector similarity se retrieve karta hai; GraphRAG ek subgraph retrieve karta hai — sawaal se relevant entities, unke neighbours aur beech ke paths — aur wo structured context LLM ko deta hai. Multi-hop sawaalon ke liye yahi farak padta hai.

Flat RAG se GraphRAG tak ek spectrum hai: keyword search → vector search → hybrid search → graph-enhanced retrieval (vector search + graph expansion) → full GraphRAG (community / subgraph summarisation). Kitab ka kehna hai: zyada tar enterprises ko graph-enhanced retrieval se shuru karna chahiye, aur community summarisation sirf wahi add karni chahiye jahan sawaal waqai use maangte hon.

The Agentic Loop

Perceive (alert aur graph padho) → Plan (action graph banao) → Act (tools call karo) → Observe (result memory graph me likho) → Reflect (plan ko graph se check karo) → repeat. Loop hi reliability ki unit hai: har iteration correct karne ka mauka hai, drift karne ka nahi.

ReAct, Plan-and-Execute, aur Reflection

  • ReAct — reasoning aur acting ko interleave karta hai (exploratory diagnosis ke liye achha, lambe plans ke liye kharab kyunki check karne layak koi global plan nahi hota).
  • Plan-and-Execute — pehle poora plan likhta hai, phir execute karta hai (auditable, multi-step kaam ke liye achha, duniya badal jaye to brittle).
  • Reflection — ek critic step jo plan aur result ko graph se check karta hai (kitab ka preferred default, keemat: extra LLM calls).

Acme agent Plan-and-Execute with reflection use karta hai.

Worked examples — numbers ke saath

Multi-hop retrieval comparison: sawaal — 'Tuesday ko checkout outage kis service ki wajah se hua, aur uska owner kaun hai?' Flat vector RAG ne 5 chunks diye, jinme se 2 relevant the, aur 0.85 confidence ke saath galat service (database) batayi. GraphRAG ne 12 nodes / 18 edges ka subgraph retrieve kiya (incident → service → dependency → owner) aur sahi jawab diya, path evidence ke roop me dikhaya. Comparison: flat RAG — 5 me se 2 chunks relevant, galat jawab; GraphRAG — sahi jawab, 3 hops ka traceable path.

Doosri comparison: 'payment service slow kyun hai?' — 50 sawaalon ke chhote Acme test set par flat RAG precision 0.62, GraphRAG precision 0.89. Improvement ki wajah: graph expansion ne missing intermediate node (shared connection pool) add kar diya.

Stack cost / latency sketch: ek ReAct step lagbhag 1.2 seconds LLM time; poora Plan-and-Execute-with-reflection loop 4–6 seconds. Extra seconds auditability khareedte hain.

Acme sizing: production graph baad ke chapters ke worked examples me lagbhag 1,247 services/nodes ka bataya gaya hai; yahan pehla prototype lagbhag 120 nodes (services, owners, runbooks) ka hai.

04Part II — Setup: Building the Digital Twin

Chapter 3 — Graph-Based Knowledge Modeling (Digital Twin)

Digital twin system ki copy nahi hai — wo un relationships ka model hai jin par diagnosis aur action ke faisle depend karte hain. Rule: wo model karo jo agent ko decide karne ke liye chahiye, wo sab nahi jo exist karta hai.

The Digital Twin

Acme ke production system ka ek graph model — itna faithful ki agent asli system ke baare me reason kar sake: services, unki dependencies, owners, runbooks, incidents, aur unhe jodne wali configuration. Twin data ki copy nahi hai; wo un relationships ka model hai jo diagnosis aur action ke liye matter karte hain. Kitab ka rule: model what the agent needs to decide, not everything that exists.

Designing the Schema — schema-first, ingest-first nahi

Un sawaalon se shuru karo jinke jawab agent ko dene hain ('kaunsi service down hai?', 'uska owner kaun hai?', 'haal me kya badla?') aur peeche ki taraf kaam karke un entities aur relationships tak pahuncho jo un sawaalon ko chahiye. Schema-first, not ingest-first: bina schema ke ingest karne se ek hairball graph banta hai jo kisi sawaal ka jawab nahi deta.

Entities and Relationships

Acme schema ke core node labels: Service, Team, Person (owner/on-call), Runbook, Incident, Change (deployment/config change) aur Document. Core relationship types: DEPENDS_ON, OWNS, ON_CALL_FOR, DESCRIBED_BY (service → runbook), CAUSED_BY, FIXED_BY aur CHANGED (change → service). Har relationship type ki defined direction aur meaning hai. Kitab generic edges jaise 'RELATED_TO' se mana karti hai — wo koi information nahi dete.

Properties and Constraints

Har Service ke paas name, environment, criticality (1–5) aur owner hota hai; har Incident ke paas severity, start time aur status. Neo4j me constraints (service name + environment par uniqueness) graph ke liye database schema ke barabar hain — ye duplicate nodes rokte hain, jo galat jawabon ka sabse common source hai.

Building the Knowledge Graph — teen ingestion sources

  • Runbooks aur wikis: chunk kiye jate hain, lekin har chunk us service se linked hota hai jise wo describe karta hai aur un entities se bhi jinka wo zikr karta hai — taaki retrieval chunk ke saath uska graph neighbourhood bhi de sake. Stale documents ko 'last verified' property se flag kiya jata hai aur down-weight kiya jata hai.
  • Tickets aur incidents: Incident nodes me parse kiye jate hain — severity, timeline, resolution ke saath — involved services aur unhe resolve karne wale fix (FIXED_BY) se linked. Incident history hi baad me memory graph ka raw material banti hai.
  • Code aur configuration: service dependencies code (import / call graphs) aur configuration (Kubernetes manifests, Terraform) se extract ki jati hain, haath se draw nahi ki jati. Kitab zor deti hai: haath se banaye dependency maps sad jate hain; extracted wale current rehte hain.

Entity Resolution and Deduplication

Ek hi service kai naamo se dikhti hai ('checkout', 'checkout-svc', 'checkout-service', 'Checkout Service'). Kitab ki pipeline: normalise (lowercase, suffixes hatao) → block (token share karne wale candidate pairs) → score (string similarity + graph me shared neighbours — do nodes jo same services par depend karte hain, unke same service hone ki possibility zyada hai) → merge (uncertain band ke scores human-review queue me). Graph-neighbour signal hi key insight hai: sirf text similarity galat cheezein merge kar deti hai.

Validating the Graph — chaar checks

  • Completeness — kya har production service ka owner aur runbook hai?
  • Consistency — kya dependencies me aise cycles hain jo nahi hone chahiye?
  • Freshness — kya koi 'last verified' date 90 din se purani hai?
  • Connectivity — kya orphan nodes hain jinke koi edges nahi?

Har check ke liye kitab ek Cypher query deti hai.

Querying the Graph — Cypher Patterns for Agents

Agent ko parameterised Cypher patterns ki ek chhoti library chahiye, free-form Cypher generation nahi: ek service ki dependencies (ek hop aur do hops), owner/on-call, ek service ke recent incidents, ek service ke liye haal me kya badla, aur ek symptom ka runbook. Free-form Cypher risk hai (LLM aisi query likh sakta hai jo poora graph return kar de, ya galat ho, aur use check karne ka koi tareeka nahi).

Vector Search in Neo4j — hybrid retrieval

Embeddings Document/chunk nodes par Neo4j vector index me store hote hain, taaki ek hi query vector similarity ('is sawaal jaise chunks') ko graph traversal ('aur is service se linked') ke saath combine kar sake. Ye hybrid hi kitab ka recommended retrieval default hai.

Worked examples — numbers ke saath

Schema-sizing example: Acme prototype 1,400 documents se shuru hota hai, jinse extraction ke baad 1,847 entities aur 312,847 relationships bante hain — relationship count me code-derived dependency edges ka bolbala hai. (Yahi 312,847 figure baad ke chapters me Acme graph ke size ke roop me dobara aata hai.)

Entity-resolution example: 23,412 raw name mentions collapse hokar 1,847 canonical entities ban gaye; 94 candidate merges human review ke liye flag hue, jinme se 78 sachhe duplicates the aur 16 alag services the jo sirf name stem share karte the. Automatic merges ki precision 98.7% aur recall 96.4% hand-labelled Acme sample par.

Freshness example: 8,241 documents check kiye gaye; 1,842 (22.3%) 90 din se purane the bina verification ke — delete karne ke bajaye retrieval me down-weight kiye gaye.

Retrieval comparison (chapter ka central experiment): 50 test questions par flat vector RAG precision 0.62, graph-enhanced retrieval 0.89, full GraphRAG with community summaries 0.94 — lekin cost ke saath: average latency flat 1.6 s, graph-enhanced 2.3 s, full GraphRAG 4.2 s; average cost per query $0.0009 (flat), $0.023 (graph-enhanced), $1.20 (full — community-summary LLM calls dominate karte hain). Recommendation: graph-enhanced retrieval default, full GraphRAG sirf jahan sawaal multi-hop synthesis maange.

Validation example: completeness check me pehle ingest me 312 services bina owner ke aur 47 bina runbook ke mile; cleanup pass ke baad ye 12 aur 3 reh gaye. Connectivity check me 892 orphan nodes mile, zyada tar documents jinki service link parse nahi hui thi.

Cost arithmetic: 1,250,000 queries/day par $0.023 vs $1.20 ka farak hota hai $1,471/day vs $1,500,000/day (kitab ki illustrative arithmetic) — isliye community summarisation ko cache aur reuse karna hai, har query par compute nahi.

Chapter 4 — Agentic Graph Memory Systems

LLM ka context window working memory hai, memory nahi. Turn window se nikla, to lesson bhi saath nikal gaya — jab tak system use kahi structured jagah likh na de. Memory hi reactive agent ko experienced agent banati hai.

Why Agents Forget

Ek LLM ka context window working memory hai, memory nahi. Jab ek turn window se bahar jata hai, lesson bhi saath chala jata hai — jab tak system use kahi structured jagah na likhe. Kitab ka example: Acme agent ne ek hi connection-pool incident ek mahine me teen baar fix kiya, har baar scratch se, kyunki pehle fix ka koi record bacha hi nahi.

The Three Kinds of Memory

1. Episodic Memory — kisi specific episode me kya hua: incident, liye gaye steps, outcome, samay. Episode node ke roop me store hoti hai, Incident, services, actions aur unke results se linked. Ye specific aur dated hoti hai.

2. Semantic Memory — kai episodes se distilled, aam taur par kya sach hai — jaise 'checkout service par connection-pool exhaustion aam taur par runaway batch job ki wajah se hota hai'. Lesson / Fact node ke roop me store hoti hai, knowledge graph (service aur symptom) se linked, confidence ke saath jo confirming episodes se badhta hai aur contradictions se girta hai.

3. Procedural Memory — cheezein kaise karni hain: runbook jaisa agent ne execute karna seekha — steps ka order, beech ke checks, failure modes. Procedure node ke roop me store hoti hai, kaam karne wale action graph ke steps se linked.

The Memory Graph

Ek hi graph jisme teeno kinds hain, typed links ke saath: ek Episode ek Lesson ko 'supports' karta hai; ek Lesson ek Procedure ko 'refines' karta hai; ek Procedure ek Service par 'applies to' hota hai. Memory graph episodes ke liye append-only hai; lessons aur procedures versioned hote hain, kabhi in place overwrite nahi hote — taaki agent dekh sake ki ek lesson badla aur kyun.

Building the Memory Graph — Capturing Episodes

Har task ke baad agent ek Episode node likhta hai: task, plan (archived action graph ka link), har tool call aur uska result, aur final outcome (success / failure / partial). Capture automatic aur structured hai; sirf free-text transcript episode nahi hai.

Distilling Lessons

Periodically (kitab ke design me, same type ke har 10 episodes ke baad, ya nightly) ek LLM similar episodes ka cluster padhta hai aur ek Lesson node propose karta hai — ek generalisation, confidence score aur supporting episodes ke links ke saath. Lesson knowledge graph me tabhi promote hoti hai jab wo verification check pass kare (Ch. 7 dekho). Kitab jaldi distil karne se mana karti hai: teen episodes se rule nahi banta.

Forgetting and Consolidation

Memory hamesha ke liye nahi rakhi jati. Episodes retrieval priority me decay karte hain (delete nahi hote) jab tak wo kisi lesson se linked na hon; lessons contradict hone par decay karte hain; procedures archive ho jate hain jab unka service retire ho jaye. Consolidation wo nightly job hai jo lessons ko re-score karta hai, duplicates merge karta hai, aur un episodes ko prune karta hai jinhone kabhi kisi lesson me contribute nahi kiya. Point: forgetting ek feature hai — ek memory jo kabhi nahi bhoolti, stale lessons retrieve karti hai.

Memory Retrieval — Recency, Relevance, Importance

Jab agent ek naye incident ka saamna karta hai, to wo memories ko ek combined score se retrieve karta hai. Recency: episode kitna recent hai (exponential decay, Acme configuration me half-life 30 din). Relevance: current incident ke service/symptom nodes se memory ke nodes tak graph distance. Importance: episode ke outcome ka weight (severity-1 incident ka successful fix ek routine success se zyada score karta hai). Teeno ko weighted sum me combine kiya jata hai — Acme configuration me weights 0.3 / 0.5 / 0.2 — aur top-k memories planner ke context me inject ki jati hain, unki provenance (episode IDs) ke saath, taaki agent unhe check kar sake.

Memory and the Action Graph

Planner action graph likhne se pehle memory graph padhta hai — 'ye pehle dekha gaya hai kya, aur kya kaam kiya tha?' — aur executor har step ke baad usme wapas likhta hai, taaki ek plan mid-flight ek memory se correct ho sake ('pichhli baar step 2 isliye fail hua kyunki service abhi drain nahi hui thi; ek drain check add karo').

Chapter 5 — Reasoning and Planning

Planning ek graph search problem hai, text-generation problem nahi — plan possible actions ke graph me ek path hai, aur LLM ka kaam use search karna hai, invent karna nahi. Jo plan graph me draw nahi ho sakta, wo guess hai.

The Planning Problem

Goal diya hai ('checkout latency ko 2 seconds se neeche lao') aur knowledge graph diya hai — to ek aisa sequence of steps banao jo correct, safe aur checkable ho. Kitab ka claim: planning ek graph search problem hai, text-generation problem nahi — plan possible actions ke graph me ek path hai, aur LLM ka kaam use search karna hai, invent karna nahi.

Decomposing a Goal into Steps

Goal ko knowledge graph me peeche ki taraf walk karke decompose karo — goal state (latency normal) se current state (latency high) tak, dependencies use karke: latency fix karne ke liye connection pool free karna hoga; pool free karne ke liye batch job rokna hoga; rokne ke liye use identify karna hoga. Har decomposition step ko apna precondition aur expected effect naam se batana hoga, taaki plan execute karne se pehle check ho sake.

Graph-Guided Planning

Planner graph se involved entities ke liye query karta hai, memory graph se relevant procedures retrieve karta hai, aur un pieces se action graph assemble karta hai. Graph plan ko constrain karta hai: ek step jiska knowledge graph me goal tak koi edge nahi hai, valid step nahi hai. Kitab ka rule: agar plan ko graph me path ki tarah draw nahi kiya ja sakta, to wo ek guess hai.

Planning with Constraints

Hard constraints (peak traffic me kabhi service restart mat karo; kabhi data delete mat karo; bina approval ke $500 se zyada kharch mat karo) knowledge graph me Constraint nodes ke roop me store hote hain aur execution se pehle action graph ke har step ke against check kiye jate hain. Soft constraints (sabse sasta fix prefer karo; sabse kam disruptive fix prefer karo) candidate plans ko rank karne ke liye use hote hain. Hard constraint violate karne wala plan reject hota hai, repair nahi.

Multi-Hop Reasoning

'Is outage ki wajah kaunsa change tha?' jaise sawaal hop-by-hop traverse karke answer kiye jate hain, har hop ka evidence record karke. Kitab iski tulna LLM se ek shot me jawab maangne se karti hai — jo ek plausible-sounding chain deta hai jiska graph me koi basis ho bhi sakta hai, nahi bhi. Har hop ek query hai, aur chain hi answer ki provenance hai.

Reasoning with Uncertainty — Confidence and Provenance

Har conclusion ke saath ek confidence hoti hai (retrieval score aur LLM ke self-assessment se combined number) aur provenance (wo graph nodes aur documents jinse ye aaya). Low-confidence conclusions flag hote hain, aur agent ko ya to aur evidence ikattha karna hota hai (ek aur hop, ek aur tool call) ya escalate karna hota hai. Acme configuration me threshold: 0.7 se neeche — aur evidence ikattha karo; 0.5 se neeche — human se poochho.

When to Ask a Human

Escalation ek designed behaviour hai, failure nahi. Triggers: hard-constraint violation, confidence 0.5 se neeche, irreversible action, approval threshold se upar cost, ya aisi novel situation jiska memory graph me koi precedent nahi. Escalation message me plan, evidence aur specific question hona chahiye — sirf 'mujhe madad chahiye' nahi.

Chapter 6 — Agentic Graph-Based Tool Orchestration

Tools prompt me nahi, graph me hone chahiye. MCP interface hai, ~5 tools tak pre-selection discipline hai, aur idempotency + compensation hi tool use ko production ke layak safe banate hain.

Tools as Graph Nodes

Har tool knowledge graph me ek node hai — properties ke saath (name, description, inputs, outputs, cost, latency, risk level) aur edges ke saath: jin services par wo act karta hai (ACTS_ON), jo data wo padhta hai (READS), aur jin tools se pehle ya baad me use chalna hai (PRECEDES). Tool selection phir ek graph query hai, prompt-listing problem nahi.

The Model Context Protocol (MCP)

MCP wo standard hai jise kitab tools ke liye use karti hai. Ek MCP server tools, resources aur prompts ko ek defined protocol par expose karta hai; ek MCP client (agent) unhe discover karta hai aur call karta hai. Kitab ka point: MCP tool ki implementation ko agent ki reasoning se alag karta hai, taaki tools ko agent ke prompts se independent add, version aur audit kiya ja sake.

MCP Servers and Clients

Acme MCP server aise tools expose karta hai jaise get_service_status, stop_job, restart_service aur get_recent_incidents; client LangGraph agent hai, jo startup par tools list karta hai aur unhe naam se JSON arguments ke saath call karta hai. Server tool run karne se pehle arguments validate karta hai aur permissions enforce karta hai — agent koi aisa tool call nahi kar sakta jo use grant nahi hua.

Tool Selection — From 100 Tools to 5

Core problem: prompt me 100 tools hon to LLM ki tool-choice accuracy collapse ho jati hai aur prompt tool descriptions se bhar jata hai. Kitab ka solution graph-based pre-selection hai: goal aur current action-graph step ko lekar tool graph me query karo — relevant services aur step ke action type se linked tools — relevance aur past success (memory graph se) ke hisaab se rank karo, aur prompt me sirf top 5 daalo. Baaki 95 ek doosri, explicit lookup se available rehte hain agar top 5 me sahi tool na ho.

Prompt Bloat and Tool Choice

Chapter ka experiment collapse ko quantify karta hai: tool count badhne par accuracy girti hai aur cost tezi se badhti hai. Kitab ka rule of thumb: prompt me tool list 10 se neeche rakho, ideally 5 par — aur poora tool catalogue graph me rakho, prompt me nahi.

Tool Composition and Chaining

Tools action graph se compose hote hain — ek step ka output agle step ka input hota hai, data flow graph me record hota hai. Kitab teen patterns alag karti hai: sequential composition (A phir B), parallel composition (A aur B, independent), aur conditional composition (B sirf tab jab A ka result kisi condition ko meet kare) — har ek action graph me ek pattern ke roop me dikhaya gaya hai.

Error Handling and Retries

Tool call teen tareekon se fail ho sakta hai — transient (backoff ke saath retry karo), invalid arguments (retry mat karo; re-plan karo), aur permission denied (retry mat karo; escalate karo). Retries bounded hain (3 attempts, exponential backoff 1 second se shuru) aur har attempt memory graph me record hoti hai. Non-idempotent action ko repeat karne wala retry mana hai.

Idempotency and Compensation

Ek idempotent tool ko safely retry kiya ja sakta hai (status padhna, pehle se ruka hua job rokna); ek non-idempotent tool (customer ko charge karna, data delete karna) ko guard karna hota hai — ya to call se pehle ek check se ('ye pehle se ho to nahi gaya?') ya ek compensation action se jo use undo kare ('saga' pattern: har step ka ek named compensating step hota hai, aur failure par compensations reverse order me chalte hain). Acme example ek deployment hai: agar step 3 fail ho, to steps 2 aur 1 compensate hote hain (traffic wapas shift karo, phir purana version restore karo).

Skills: Packaging Expertise

Ek 'skill' ek recurring job ke liye tools, prompts, procedures aur constraints ka packaged bundle hai — jaise 'diagnose latency' skill jo status, log aur incident tools ko memory graph ki procedure aur relevant constraints ke saath bundle karti hai. Skills reuse ki unit hain: har agent ko har tool sikhane ke bajaye, use uske job ki skills do. Skill graph me ek node ke roop me store hoti hai, apne tools aur procedures se linked, aur code ki tarah versioned hoti hai.

Chapter 7 — Self-Evolution and Evaluation

Static agent decay karta hai — system badalta hai, agent frozen rehta hai. Evaluation hi evolution ki precondition hai; semantic backpropagation errors ko unke source par fix karta hai; aur self-modification guardrails se bandha hona chahiye.

Why Static Agents Decay

Jis system ke liye agent bana tha, wo badalta hai — services rename hote hain, runbooks update hote hain, dependencies shift hote hain — aur ek agent jiska knowledge graph aur procedures frozen hain, decay karta hai. Kitab ka example: ek runbook change ne ek service ka naam badal diya, jisse agent ki retrieval teen hafton tak miss karti rahi, kyunki koi evaluation chal hi nahi rahi thi.

The Evaluation Problem

Agent ko evaluate karna classifier ko evaluate karne se mushkil hai — output ek plan aur actions ka set hai, ek label nahi, aur ek plan aise tareekon se galat ho sakta hai jo text-similarity score dekh hi nahi sakta. Kitab ka jawab: graph ke against evaluate karo — kya plan grounded tha, kya constraints respect hue, kya outcome expected effect se match kiya?

Building a Golden Dataset

Known-good answers wale test tasks ka set, asli past incidents se bana. Har item me incident, sahi diagnosis, sahi plan aur expected outcome record hota hai. Acme golden dataset me kitab ke worked examples me 50 incidents hain (incident history se liye gaye, SRE team ne hand-check kiye). Ye versioned hai, aur agent, graph ya prompts me har change par dobara run kiya jata hai.

Metrics That Matter — Task Success, Groundedness, Cost

  • Task success: kya agent ne goal achieve kiya (jaise latency 15 minutes me 2 s se neeche restore hui)?
  • Groundedness: kya plan ka har step kisi graph edge ya cited document tak traceable tha (kitab ki definition of a 'grounded' step — aur wo metric jise wo sabse zyada care karta hai)?
  • Cost: tokens, LLM calls, wall-clock time aur dollars per task.
  • Safety (chauthi, implicit family): constraint violations aur escalations.

LLM-as-Judge

Ek LLM agent ke output ko ek rubric (groundedness, correctness, safety) ke against grade karta hai, graph ko evidence ke roop me lekar. Kitab warn karti hai: judge agent ke blind spots share karta hai, isliye judge ke verdicts ko sample karke humans check karte hain, aur judge kabhi production change ka sole gate nahi hota.

Human Evaluation

Agent ke tasks ka ek sample (Acme design me 10% tasks, aur 100% escalations aur failures) ek SRE review karta hai, jo plan aur outcome ko score karta hai aur review ko Lesson ke roop me memory graph me likhta hai. Human review hi ground truth hai jo LLM judge ko calibrate karta hai.

The Self-Evolution Loop

Wo loop jo system ko self-improving banata hai — evaluate (golden dataset chalao) → diagnose (failing plan ke steps ko graph me trace karke pata lagao agent kahan fail hua) → propose (ek change generate karo: naya lesson, corrected procedure, naya constraint, reworded tool description) → verify (change ko golden dataset aur shadow run se test karo) → deploy (ya roll back karo).

Semantic Backpropagation

Kitab ka naam diagnosis step ke liye. Jaise neural network me backpropagation blame ko weights ko assign karta hai, waise hi semantic backpropagation blame ko graph nodes ko assign karta hai: ek failed plan ko action graph se peeche trace karke us knowledge-graph node tak pahuncha jata hai jisne galat fact diya tha (stale runbook, missing dependency, mis-scored lesson), aur fix usi node par apply hota hai. Error prompt me patch nahi hoti; wo graph me apne source par fix hoti hai.

Proposing Changes

Changes graph edits ke roop me propose hote hain (Lesson node add karo, Procedure ka step order update karo, Constraint add karo, relationship correct karo), ek justification ke saath jo edit ko failing episodes se link karti hai. LLM propose karta hai; wo apply nahi karta.

Verifying Changes

Proposed change ko test kiya jata hai — golden dataset ko graph ki sandbox copy par change apply karke dobara run karke, aur live traffic par shadow run se (agent ka plan compute hota hai lekin execute nahi hota, aur human ke action se compare hota hai). Change ko golden-dataset score improve karna hota hai bina kisi pehle se passing item ko regress kiye — kitab ka rule: 'no regressions, or the change does not ship'.

Rolling Back

Har change graph me versioned hota hai, taaki production me regression karne wala deployed change affected nodes ke previous version ko restore karke roll back ho sake. Rollback khud ek Episode ke roop me record hota hai, taaki system seekhe ki wo change kharab tha.

Guardrails for Self-Modification

Agent lessons, procedures aur tool descriptions me changes propose kar sakta hai, lekin hard constraints, permissions, ya apna evaluation rubric nahi badal sakta; unke liye human chahiye. Kitab ki line: agent seekh sakta hai, lekin apne rules khud nahi likh sakta.

Ek self-evolution cycle ke baad (batch-job incident ke liye corrected procedure, plus ek naya constraint) scores badhkar 84% task success, 91% groundedness, $0.38 per task — cost isliye giri kyunki agent kam wasted steps leta hai.

Chapter 8 — Optimization

Optimisation premature nahi hai — agent ke liye cost aur latency correctness issues hain, kyunki ek slow ya mehenga agent ko users bypass kar denge. Cache karo, chhote kaam chhote models ko do, graph ko index aur partition karo, sab trace karo.

The Cost of Intelligence

Har LLM call, har graph query aur har tool call ki cost hoti hai — tokens, time aur dollars me — aur ek agent jo har task par dozens of calls karta hai, production volume par mehenga padta hai. Kitab ki framing: optimisation premature nahi hai — agent ke liye cost aur latency correctness issues hain, kyunki ek slow ya mehenga agent ko uske users bypass kar denge.

Latency, Cost, and Quality — teen-way trade-off

Kitab ka rule: intelligence wahi kharch karo jahan matter karta hai (planning, aur pehli diagnosis) aur baaki jagah jitna kam ho sake (status checks, formatting, summarisation). Acme numbers neeche worked examples me hain.

Caching — teen levels

1. Prompt Caching: prompt ka wo prefix reuse karo jo calls ke beech nahi badalta (system prompt, tool descriptions, graph context ka stable part). Kitab repeated planning calls me 40–60% input tokens ki kami report karti hai jahan stable prefix dominate karta hai.

2. Semantic Caching: sawaal ka jawab uske meaning se cache karo, exact text se nahi — agar naya sawaal cached sawaal se kaafi similar ho (Acme configuration me embedding similarity 0.95 se upar) aur same entities ke baare me ho, to cached answer uski provenance ke saath return karo, aur cache hit record karo. Risk: graph badalne ke baad stale cache — isliye cache entries invalidate hoti hain jab unke supporting graph nodes badal jayein.

3. Graph Caching: expensive graph queries ke results cache karo (jaise kisi busy service ka 2-hop neighbourhood, ya community summary) aur invalidate karo jab underlying nodes badal jayein. Kitab ka point: graph khud batata hai kya invalidate karna hai — cache key wo nodes ka set hai jinhe query ne touch kiya.

Model Selection and Routing — Small Models for Small Jobs

Har step ko sabse bada model nahi chahiye. Router planning aur pehli diagnosis ko large model ko bhejta hai, aur classification, extraction, formatting aur simple lookups ko small model ko (ya deterministic function ko jahan model ki zaroorat hi nahi). Kitab ki Acme routing table neeche di hai.

Scaling the Graph — Indexing and Partitioning

Graph badhne par jo queries matter karti hain, wo index ki jati hain (embeddings par vector index, names par full-text index, aur incident lookups ke liye (service, timestamp) pair par index), aur graph ko domain se partition kiya jata hai (har business domain ke liye ek partition, cross-partition edges explicit aur kam). Kitab warn karti hai: bina index wali 2-hop query ke saath ek single, unpartitioned graph hi sabse common production performance failure hai.

Observability — Tracing the Agentic Loop

Agentic loop ki har iteration ek span ke roop me trace hoti hai (perceive / plan / act / observe / reflect), usme read/written graph nodes, called tools, used tokens aur har step ki latency attached hoti hai. Trace hi debugging tool hai: jab agent fail hota hai, to trace dikhata hai kaunsa step, kaunsa graph node aur kaunsa tool call responsible tha. Kitab OpenTelemetry-style tracing recommend karti hai, trace ID ko memory graph ke Episode node se link karke.

Worked examples — numbers ke saath

Cost arithmetic: Acme agent 1,250,000 tasks/day (kitab ka illustrative volume) par average 12 LLM calls per task, $0.012 per call se $180,000/day kharch karta hai; is chapter ki optimisations (caching, routing, kam calls) ke baad average girkar 4 calls per task, $0.008 per call ho jata hai, ya $40,000/day — ek saving jise kitab us farak ke roop me present karti hai jo ek system ko ship karwata hai aur doosre ko cost ki wajah se band karwata hai. (Ye kitab ke illustrative figures hain.)

Prompt-caching example: planning prompt 24,000 tokens ka hai, jinme se 18,000 stable prefix hain (system prompt + tool descriptions + stable graph context); prompt caching se billable input girkar lagbhag 6,000 fresh tokens + discounted cached-prefix charge ho jata hai — kitab ki measurements me input tokens par 40–60% saving.

Semantic-caching example: Acme traffic ke ek hafte me 31% sawaal semantically identical the (similarity > 0.95) pehle poochhe gaye sawaal se, same entities ke baare me; unhe cache se serve karne se 23% LLM calls bache, hafte me 2 cache-staleness errors ke saath (dono pakde gaye kyunki cached answer ke provenance nodes badal gaye the aur cache entry agle check par invalidate ho gayi — kitab isse provenance-based invalidation ki dalil banati hai).

Routing example: classification/extraction steps ko small model par route karne se unki cost $0.012 se $0.001 per call aur latency 1.2 s se 0.3 s ho gayi, Acme golden dataset par accuracy me koi measured drop nahi (large model ab bhi planning aur diagnosis ke liye use hota hai, jahan small model try karne par accuracy 92% se 71% gir gayi thi planner comparison me).

Scaling example: unindexed Acme graph par 2-hop neighbourhood query 312,847 relationships par 4.7 seconds leti thi; (service, timestamp) index add karne aur domain se partition karne ke baad 89 ms ho gayi. Interview FAQs — Agentic GraphRAG

Current-era interviews me agentic GraphRAG se poochhe jaane wale sabse kaam ke 36 sawaal — har jawab wahi hai jo is SPA ke book sections me detail me samjhaya gaya hai. Kisi bhi sawaal par click karke jawab kholo.

Q01 Agentic GraphRAG kya hai — sirf RAG + graph nahi?
Teen pillars ka combination hai: GraphRAG (knowledge graph me grounded retrieval), Reasoning (graph par explicit, inspectable planning) aur Agency (bounded, audited action, tools jinke effects graph me modelled hain). Sirf graph index ke saath RAG ko kitab agentic GraphRAG nahi kehti.
Q02 GraphRAG flat RAG se multi-hop sawaalon me behtar kyun hai?
Flat RAG vector similarity se chunks deta hai — jo similar hai, wo sach ya current ho zaroori nahi. GraphRAG ek subgraph retrieve karta hai: relevant entities, unke neighbours aur beech ke paths. Kitab ke example me sawaal 'Tuesday ko checkout outage kis service ki wajah se hua?' par flat RAG ne 5 me se 2 relevant chunks diye aur galat service batayi (confidence 0.85); GraphRAG ne 12 nodes / 18 edges ka subgraph dekar sahi jawab diya, 3 hops ka path evidence ke saath.
Q03 Teen graphs kaunse hain aur har ek kya model karta hai?
Knowledge Graph — duniya (durable facts, curated, slow-changing). Action Graph — current task ka plan, DAG ke roop me (per-task, transient). Memory Graph — past experience: episodes, lessons, procedures (append-only episodes, versioned lessons). Teeno alag hain aur typed interfaces se judte hain.
Q04 Dual-graph architecture kya hai aur state bleed kya hota hai?
Knowledge graph aur action graph ko alag rakhna, beech me ek well-defined interface ke saath. Agar transient plan state ko durable facts wale graph me mila do, to plan ki temporary assumption permanent fact ban jati hai — yahi 'state bleed' hai. Dono sirf explicit typed links se judte hain ('reads', 'updates after verification').
Q05 Semantic backpropagation kya hai?
Neural network me backpropagation blame ko weights ko deta hai; waise hi semantic backpropagation blame ko graph nodes ko deta hai. Failed plan ko action graph se peeche trace karke us knowledge-graph node tak pahuncha jata hai jisne galat fact diya (stale runbook, missing dependency, mis-scored lesson), aur fix usi node par apply hota hai — prompt me patch nahi.
Q06 Digital twin kya hai — system ki copy?
Nahi. Digital twin system ki copy nahi hai; wo un relationships ka model hai jo diagnosis aur action ke faisle ke liye matter karte hain — services, dependencies, owners, runbooks, incidents, configuration. Rule: model what the agent needs to decide, not everything that exists.
Q07 Schema-first design kyun — ingest-first me kya kharabi hai?
Ingest-first (bina schema ke data bharna) ek hairball graph banata hai jo kisi sawaal ka jawab nahi deta. Schema-first me pehle un sawaalon se shuru karte hain jinke jawab agent ko dene hain, phir peeche ki taraf entities, relationships aur constraints tay karte hain, phir ingest karte hain.
Q08 Entity resolution me graph-neighbour signal kyun zaroori hai?
Ek hi service kai naamo se dikhti hai ('checkout', 'checkout-svc', 'checkout-service'). Sirf text similarity galat cheezein merge kar deti hai. Kitab ki pipeline: normalise → block → score (text similarity 0.4 + shared neighbours 0.5 + same owner 0.1) → merge (threshold 0.85) ya human review (band 0.65–0.85). Do nodes jo same services par depend karte hain, unke same service hone ki possibility zyada hoti hai.
Q09 Graph ko validate kaise karte hain — chaar checks kaunse hain?
Completeness (har production service ka owner aur runbook hai?), Consistency (dependencies me galat cycles to nahi?), Freshness (koi 'last verified' date 90 din se purani to nahi?), Connectivity (orphan nodes to nahi?). Pehle ingest me 312 services bina owner ke, 47 bina runbook ke aur 892 orphan nodes mile the.
Q10 Hybrid retrieval kya hai aur ye default kyun hai?
Ek hi query me vector similarity ('is sawaal jaise chunks') aur graph traversal ('aur is service se linked') combine karna — embeddings Neo4j vector index me Document/chunk nodes par store hote hain. 50 questions par: flat 0.62 precision, graph-enhanced 0.89, full GraphRAG 0.94 — lekin full ki cost $1.20/query hai, isliye graph-enhanced (0.89, $0.023) default hai.
Q11 Memory ke teen kinds kaunse hain?
Episodic — kisi specific episode me kya hua (dated, specific). Semantic — kai episodes se distilled aam sach, confidence ke saath. Procedural — kaise karna hai: steps ka order, beech ke checks, failure modes. Memory graph teeno ko typed links se jodta hai: Episode 'supports' Lesson, Lesson 'refines' Procedure.
Q12 Agent ko bhoolna kyun chahiye — forgetting feature kaise hai?
Episodes retrieval priority me decay karte hain (delete nahi hote) jab tak lesson se linked na hon; lessons contradiction par decay karte hain; procedures service retire hone par archive hote hain. Ek memory jo kabhi nahi bhoolti, stale lessons retrieve karti hai. Nightly consolidation duplicates merge karta hai aur unused episodes archive karta hai.
Q13 Memory retrieval me recency, relevance aur importance kaise combine hote hain?
Weighted sum: recency 0.3 (half-life 30 din), relevance 0.5 (graph distance), importance 0.2 (outcome severity). Kitab ke example me Episode A (0.9, 0.8, 0.7 → 0.82) Episode B (0.4, 0.9, 0.9 → 0.73) se pehle aata hai — kyunki A bahut zyada recent hai. Weights policy choice hain, kaanoon nahi.
Q14 Lesson kab distil karni chahiye — kitne episodes chahiye?
3 se kam supporting episodes — distil mat karo. 3–9 — candidate lesson, low confidence. 10+ — verification ke baad promote karo. Kitab warn karti hai: teen episodes se rule nahi banta. Ek lesson jo ek hi mislabelled episode se bani thi, usne payment incidents ka score 31% tak gira diya tha.
Q15 Planning graph search kaise hai — text generation kyun nahi?
Plan possible actions ke graph me ek path hai; LLM ka kaam use search karna hai, invent karna nahi. Goal ko graph me peeche walk karke decompose karo (latency normal ← pool free ← job roko ← job identify karo). Har step ka precondition aur expected effect hona chahiye. Rule: agar plan graph me path ki tarah draw nahi ho sakta, to wo guess hai.
Q16 Hard constraints vs soft constraints me kya farak hai?
Hard constraints (peak me restart nahi, data delete nahi, $500 approval threshold) Constraint nodes me store hote hain aur har step ke against check hote hain — violation par plan reject hota hai, repair nahi. Soft constraints (sabse sasta, sabse kam disruptive) candidate plans ko rank karte hain — violation par sirf rank neeche jata hai.
Q17 Agent ko human se kab poochhna chahiye?
Escalation designed behaviour hai, failure nahi. Triggers: hard-constraint violation, confidence 0.5 se neeche, irreversible action, cost $500 se upar, ya koi novel situation jiska memory graph me precedent nahi. Escalation message me plan, evidence aur specific question hona chahiye.
Q18 Confidence kaise combine hoti hai aur thresholds kya hain?
Retrieval score aur LLM self-assessment ka weighted average (weights 0.6/0.4). Example: 0.82 aur 0.78 → 0.80, jo 0.7 se upar hai — agent aage badhta hai. 0.7 se neeche — aur evidence ikattha karo. 0.5 se neeche — human se poochho.
Q19 Graph-guided planner prompt-only planner se kitna behtar hai?
50 test incidents par graph-guided planner ne 46 cases (92%) me valid plan banaya, prompt-only ne 31 (62%). Graph-guided ne 4 cases me human se poochha — chaaro waqai ambiguous the; prompt-only ne 2 me poochha aur 17 me galat tareeke se aage badh gaya. Keemat: 3 LLM calls + 4 graph queries, ~6 seconds vs 1 call, ~1.2 seconds.
Q20 ReAct vs Plan-and-Execute vs Reflection — kaunsa kab?
ReAct — exploratory diagnosis ke liye achha, lambe plans ke liye kharab (koi global plan nahi, drifts). Plan-and-Execute — auditable multi-step kaam ke liye achha, duniya badal jaye to brittle. Reflection — critic step plan aur result ko graph se check karta hai; kitab ka preferred default, keemat extra LLM calls. Acme agent Plan-and-Execute with reflection use karta hai.
Q21 MCP kya hai aur tools ko graph me rakhne ka fayda kya hai?
Model Context Protocol — standard jisme MCP server tools, resources aur prompts expose karta hai aur agent (client) unhe discover karke call karta hai. Har tool graph me ek node hai (properties: name, description, inputs, outputs, cost, latency, risk; edges: ACTS_ON, READS, PRECEDES). Tool selection phir graph query hai, prompt-listing problem nahi. Server arguments validate karta hai aur permissions enforce karta hai.
Q22 100 tools se 5 tools tak — accuracy kaise badalti hai?
200 test tasks par: 5 tools → 96% accuracy, ~1,200 tokens, $0.012/task; 25 → 87%; 50 → 78%; 100 → 67%, ~24,000 tokens, $0.24/task. Solution: goal aur action-graph step se graph query karke relevance + past success se rank karo, top 5 hi prompt me daalo. Baaki 95 explicit lookup se available rehte hain.
Q23 Idempotency aur saga pattern kya hain?
Idempotent tool ko safely retry kiya ja sakta hai (status padhna, pehle se ruka job rokna). Non-idempotent tool (charge karna, data delete karna) ko guard karo — pehle check ya compensation action se. Saga pattern: har step ka named compensating step hota hai; failure par compensations reverse order me chalte hain. Example: 3-step deployment fail hone par step 2 (traffic wapas, 1.8 s) aur step 1 (purana version restore, 4.2 s) compensate hue — 6.0 seconds me wapas.
Q24 Tool call fail hone par retry kab karo, kab nahi?
Transient failure — backoff ke saath retry, max 3 attempts (1 s se shuru, exponential). Invalid arguments — retry mat karo, re-plan karo. Permission denied — retry mat karo, escalate karo. Har attempt memory graph me record hoti hai. Non-idempotent action ko repeat karne wala retry mana hai.
Q25 Skill kya hai — tools se alag kaise?
Skill ek recurring job ke liye tools, prompts, procedures aur constraints ka packaged bundle hai — jaise 'diagnose latency' skill jo status, log aur incident tools ko memory-graph procedure aur 'no restarts at peak' constraint ke saath bundle karti hai. Skills reuse ki unit hain, graph me node ke roop me store hoti hain aur code ki tarah versioned hoti hain.
Q26 Golden dataset kya hai aur kyun versioned hota hai?
Known-good answers wale test tasks ka set, asli past incidents se bana — har item me incident, sahi diagnosis, sahi plan, expected outcome. Acme dataset me 50 incidents hain, SRE team ne hand-check kiye. Agent, graph ya prompts me har change par dobara run kiya jata hai. Ye evaluation ka ground truth hai.
Q27 Groundedness kyun sabse important metric hai?
Groundedness naapti hai ki plan ka har step kisi graph edge ya cited document tak traceable tha ya nahi. Task success aur cost ke saath ye teeno metric families hain (chauthi: safety — constraint violations, escalations). Ek plan jo goal achieve kar le lekin grounded na ho, wo luck hai — dobara bharosa nahi kiya ja sakta.
Q28 LLM-as-judge ki kya limitation hai?
Judge agent ke blind spots share karta hai. 100 tasks par judge human reviewers se groundedness me 89% aur correctness me 82% agree karta tha; disagreements un cases me concentrate the jahan graph khud galat tha. Isliye judge ke verdicts ko sample karke humans check karte hain, aur judge kabhi production change ka sole gate nahi hota.
Q29 Self-evolution loop ke paanch steps kaunse hain — aur ek cycle se scores kitne badle?
Evaluate (golden dataset chalao) → Diagnose (failing plan ke steps ko graph me trace karke pata lagao kahan fail hua — semantic backpropagation) → Propose (graph edit generate karo: naya lesson, corrected procedure, naya constraint) → Verify (sandbox copy + shadow run se test karo) → Deploy (ya roll back karo). Rule: 'no regressions, or the change does not ship'. Ek cycle ke baad scores: task success 62% → 84%, groundedness 71% → 91%, cost $0.42 → $0.38/task — cost isliye giri kyunki agent kam wasted steps leta hai. Payment incidents ka score ek galat lesson retire karne se 31% → 78% ho gaya.
Q30 Agent kya badal sakta hai aur kya nahi?
Badal sakta hai: lessons, procedures, tool descriptions. Nahi badal sakta: hard constraints, permissions, apna evaluation rubric — unke liye human chahiye. Kitab ki line: agent seekh sakta hai, lekin apne rules khud nahi likh sakta.
Q31 Shadow run kya hai?
Proposed change ko live traffic par test karna bina execute kiye: agent ka plan compute hota hai lekin execute nahi hota, aur human ke action se compare hota hai. Example: tool-selection ranking ka change 1,247 live tasks par shadow-run hua — 23 cases me tool choice badalti, 18 improve, 5 worsen — net gain 13, isliye deploy hua aur 5 worsened cases golden dataset me add kar diye gaye.
Q32 Rollback kaise kaam karta hai?
Har change graph me versioned hota hai. Production me regression karne wala change affected nodes ka previous version restore karke roll back hota hai — example me ek over-generalised lesson 4 minutes me roll back hua. Rollback khud ek Episode ke roop me record hota hai, taaki system seekhe ki wo change kharab tha.
Q33 Prompt caching, semantic caching aur graph caching me kya farak hai?
Prompt caching — prompt ka stable prefix reuse karo (input tokens me 40–60% saving). Semantic caching — sawaal ka jawab meaning se cache karo (similarity > 0.95, same entities) — 23% LLM calls bachte hain; invalidation graph-node change par. Graph caching — expensive graph queries ke results cache karo; cache key wo nodes ka set hai jinhe query ne touch kiya.
Q34 Model routing kaise kaam karta hai — small models kab?
Router planning aur pehli diagnosis ko large model ko bhejta hai; classification, extraction, formatting ko small model ko; simple lookups ko deterministic function ko (koi model nahi). Small model par routing se classification/extraction ki cost $0.012 se $0.001 aur latency 1.2 s se 0.3 s ho gayi, golden dataset par accuracy drop nahi hua. Lekin planning me small model try karne par accuracy 92% se 71% gir gayi thi.
Q35 Graph scale karne par 2-hop query 4.7 seconds se 89 ms kaise hui?
Do cheezein: (service, timestamp) pair par index add karna aur graph ko domain-wise partition karna (cross-partition edges explicit aur kam). Bina index wali 2-hop query ke saath single unpartitioned graph hi sabse common production performance failure hai. Full-graph community-summary query (12.4 s) ko pre-compute karke cache karna chahiye, har query par run nahi.
Q36 Production checklist ke 10 items kaunse hain?
(1) Golden dataset bina regressions ke pass. (2) Groundedness 0.9 se upar. (3) Hard constraints MCP server se enforce. (4) Har irreversible action ke liye human approval ya named exception. (5) Memory graph episodes capture kar raha hai, consolidation chal rahi hai. (6) Evaluation schedule par chalti hai. (7) Traces episodes se linked, 90 din retain. (8) Cost/latency dashboarded, alerts ke saath. (9) Har graph change ka rollback test hua. (10) Permissions minimum, quarterly review.
