Ch 1 — From AI to Agent Systems

AI ka matlab sirf model nahi hai. Ye chapter AI ki history se shuru hota hai aur wahan tak jata hai jahan model ke aas-paas poora system banta hai — retrieval, tools, memory, state, stopping rules, validation aur observability ke saath.

1.1 AI ki origins aur evolution

AI woh broad field hai jisme systems aise tasks karte hain jo human intelligence se jude hote hain — patterns pehchanna, predictions karna, language samajhna, content generate karna ya actions plan karna.

Ye safar rule-based systems (deterministic, apne rules ke bahar brittle) se shuru hua, phir 1990s–2000s me machine learning aayi (data se patterns seekhna — supervised, unsupervised aur reinforcement learning), phir deep learning (multi-layer neural networks jo raw input se feature hierarchies seekhte hain), aur phir large language models — bahut bade text corpora par train hoke likely next token predict karna, jisme in-context learning, instruction following aur code generation dikha.

Field ke examples — practice me

  • Recommendation engines — behaviour aur preferences se products suggest karte hain.
  • Fraud detection — unusual transactions flag karta hai.
  • Code assistants — code complete karte hain aur improvements suggest karte hain.
  • Medical imaging — scans me tumours detect karta hai.
  • Autonomous vehicles — surroundings sense karke us par act karte hain.

1.2 Generative AI aur LLMs

Machine learning: system hand-written rules se nahi, data se improve hota hai. Deep learning: layered networks progressively zyada abstract features seekhte hain. Generative AI: systems jo learned patterns se naya content banate hain — text, code, images, audio ya video. Large language model: huge text corpora par train hua generative model; iska core operation hai next token predict karna, jo scale par fluent, useful language use ko support karta hai.

1.3 RAG aur tool use — model akela system nahi hai

Model akela abhi bhi system nahi hai. RAG generation se pehle current, external knowledge supply karta hai, taaki answers retrieved evidence me grounded hon, sirf training memory par depend na karein. Tools model ko act karne dete hain: API call karna, database query karna, documents search karna ya computation run karna — aur surrounding application request execute karke result wapas deti hai. Combination — language understanding + retrieval + tool use — hi text generator ko useful working component banata hai.

1.4 Kya cheez system ko agentic banati hai

Agent woh system hai jo intermediate steps ke through ek goal pursue karta hai: controlled workflow ke andar AI model use karke decide karna, act karna, results observe karna aur stopping condition milne tak continue karna. Pattern hai agent loop:

Chatbot ek sawal ka jawab deta hai; agent ek task ke through kaam karta hai — jaise pull request review karna — kai linked steps lekar. System ko agentic model nahi, uske aas-paas ka runtime banata hai: goals, tools, memory, state, stopping rules, validation aur observability.

1.5 Prompting se architecture tak

Prompt ek model call ka input hai; architecture poora system hai — prompts, retrieval, tools, memory, state, validation, evaluation aur observability — is tarah design kiya gaya ki probabilistic part deterministic controls se contained rahe. Kitab ka recurring point: architecture, model choice nahi, agent system ko reliable banata hai.

Ch 2 — LLM Internals and Output Generation

Model ke andar kya hota hai, ye samajhna hi design ki shuruaat hai: tokens, embeddings, transformer, context window, next-token prediction, decoding controls — aur phir non-determinism aur hallucination se kaise deal karein.

2.1 Tokens, embeddings aur meaning

Token text ki chhoti unit hai — ek word, word ka hissa, punctuation ya koi aur fragment, tokenizer par depend karta hai. Tokenization text ko tokens me todti hai, phir wo numbers me convert hote hain. Example: word "unbelievable" tokenize hota hai "un", "believ", "able" me. Kitab ki example table me token positions: "Hello" token 1, "world" token 2, "This" token 3, "is" token 4.

Token limits token budgets hain, word counts nahi: ek lamba word kai tokens kha sakta hai, isliye request ki asli cost aur size tokens me measure hoti hai.

Embedding ek token, sentence ya document ke liye numerical vector hai jo similar meanings ko paas rakhta hai. Kitab ke small vectors:

WordVector
dog[0.92, 0.85, 0.10]
cat[0.88, 0.82, 0.12]
car[0.15, 0.20, 0.91]

Dog aur cat paas hain, car door hai. Sentence embedding poore sentence ya paragraph ka meaning capture karta hai aur semantic search ka base hai: similar meaning wale do sentences ke vectors similar hote hain, chahe words alag hon.

2.2 Transformer architecture

Transformers ne recurrent networks (RNNs) aur LSTMs ko replace kiya, jo text ko ek token at a time process karte the aur long-range dependencies me struggle karte the — kyunki transformer tokens ko parallel me process karta hai aur attention use karta hai. Core operation: token embeddings lo, position information add karo (parallel processing me word order kho jata hai), phir sequence ko stacked transformer layers se pass karo, har layer self-attention + feed-forward network combine karta hai. Self-attention model ko tokens ko ek doosre se relate karne deta hai — jaise decide karna ki sentence me pronoun "it" "the animal" ko refer karta hai ya "the food" ko, surrounding context ko weigh karke. Transformer modern LLMs ke peeche ki architecture hai; bidirectional encoding wale models ne uski power dikhayi, jabki generative models generation ke liye decoder side use karte hain.

2.3 Context window

Context window maximum tokenised input + output hai jo model ek request me handle kar sakta hai. Worked example: 8,000-token window wala model, 3,000-token prompt aur 500-token response — total 3,500 tokens use, 4,500 tokens free rehte hain. Window me kya jata hai — instructions, user input, retrieved chunks, memory, tool results, examples aur output requirements — ye design decision hai jise context engineering kehte hain: relevant information add karna help karta hai, lekin zyada irrelevant information quality degrade karti hai.

2.4 Next-token prediction

Generation next-token prediction hai: har step par model apni vocabulary par probability distribution deta hai aur decoding strategy next token pick karti hai, jo append hokar agle token ko predict karne me use hota hai. Kitab ke example me, word "Python" ke baad distribution hai: Python 0.40, Java 0.30, C++ 0.20, Rust 0.10. Ye token by token repeat hota hai jab tak stop condition na mile — isliye output probable continuation hai, retrieved fact nahi.

2.5 Temperature, top-k aur top-p

  • Temperature distribution ko reshape karta hai — low temperature most likely tokens ko favour karta hai (conservative, repeatable), high temperature distribution ko flat karta hai aur rare tokens ko zyada likely banata hai (zyada varied, kam predictable).
  • Top-k sampling candidates ko k most likely tokens tak restrict karta hai (example: k = 3, A, B aur C rakhta hai, baaki discard).
  • Top-p (nucleus) sampling tokens ka smallest set rakhta hai jinki cumulative probability chosen threshold tak pahunche (example: p = 0.90, A, B, C aur D rakhta hai).
  • Greedy decoding hamesha highest-probability token leta hai aur fully deterministic hai; stochastic decoding distribution se sample karta hai aur deterministic nahi hai.

Deterministic output factual ya structured tasks ke liye sahi hai; stochastic output brainstorming ya creative variation ke liye suit karta hai.

2.6 Non-determinism aur variability

Agents me non-determinism isliye matter karta hai kyunki ye cascade karta hai: ek thoda alag model output tool call badal sakta hai, jo retrieved data badalta hai, jo agla decision badalta hai. Lambe agent runs drift kar sakte hain; design answer hai loop ko bound karna — step limits, validation, state checks aur explicit stopping rules — aur realistic inputs se test karna, repeatability assume karne ke bajay.

2.7 Hallucination — 5 causes aur mitigations

Hallucination woh output hai jo plausible lagta hai lekin incorrect, unsupported ya fabricated hai. Paanch causes: (1) training me missing ya incomplete knowledge; (2) ambiguous prompts jo model ko guess karne par majboor karte hain; (3) sampling randomness; (4) misleading ya noisy context; (5) model ki tendency confident, fluent completions dene ki.

Mitigations practical hain, magical nahi: retrieved evidence me output ground karo (RAG), prompts ko explicit constraints aur uncertainty ke saath frame karo, model ko authoritative tools aur sources of truth se connect karo, outputs ko schemas aur rules ke against validate karo, aur real test cases se evaluate karo. Chapter ki selection guidance: model ko task ke risk se choose karo, headline capability se nahi.

2.8 Imperfect outputs ke liye design

Model galat ho sakta hai — ye assume karke design karo: validation, step limits, state checks aur stopping rules system me hone chahiye, prompt me wishful thinking nahi.

NOTE

Model ka output probable continuation hai, fact nahi. Isliye har output ko validate karo, har loop ko bound karo, aur har decision ko log karo.

Ch 3 — Prompt Engineering in LLM Systems

Prompt ek one-off text nahi hai — production me ye ek system layer hai. Ye chapter system prompts, few-shot, chain-of-thought, structured output, versioning aur prompt safety ko cover karta hai.

3.1 Prompt ki definition aur role

Prompt model ko bheja gaya complete input hai: instructions, context, examples aur constraints. Ye system ka control interface hai — role, task, expected format aur boundaries set karta hai. Prompt engineering is input ko deliberately design karne ki practice hai, aur production me ye ek system layer hai, one-off text nahi.

3.2–3.3 System prompts

System prompt high-priority instruction layer hai jo role, rules, style aur behavioural boundaries define karta hai, user message ke upar baitha hota hai. Iske components: Role (model ko kya act karna hai); Task (kya karna hai); Rules (constraints aur boundaries); Format (expected output shape); Tone (jawab ka style).

Chhota system prompt ("You are a helpful assistant") generic behaviour deta hai; specific prompt ("You are a senior Java code reviewer. Analyze code changes for security, correctness, and maintainability. Respond only in JSON format.") constrained, task-shaped behaviour deta hai. Worked contrast: document summarise karne ko kaho to plain assistant ek paragraph deta hai, jabki five-bullet summary ka instruction dene par exactly five bullets milte hain. System prompts matter karte hain kyunki ye model ko sabse pehle dikhte hain aur poori conversation me persist karte hain.

3.4–3.5 Few-shot, zero-shot, one-shot

Few-shot prompting worked examples deta hai taaki model pattern, format ya behaviour infer kare. Example: ek support ticket "Billing question" label ke saath, phir naya ticket ("I need to reset my password") jise model "Technical support" classify karta hai. Zero-shot sirf instruction deta hai, koi example nahi; one-shot ek example deta hai; few-shot kai examples deta hai. Zyada examples format reliability badhate hain, lekin har example tokens aur context space khata hai — isliye choice reliability vs cost ka trade-off hai.

3.6 Chain-of-thought (CoT) prompting

CoT model se kehta hai answer se pehle intermediate steps se kaam kare, jo reasoning tasks par accuracy badhata hai — kitab ka example multi-digit numbers ka column step by step add karna hai, total guess karne ke bajay. Reasoning ko internal rakha ja sakta hai aur sirf final answer return kiya ja sakta hai — ye production-safe form hai: reasoning result ko help karta hai, lekin user verified outcome dekhta hai. Caution: CoT correctness ki guarantee nahi hai, aur uska reasoning text evidence ki tarah treat nahi karna chahiye.

3.7–3.8 Structured output

Structured output model ko defined format — normally JSON — me constrain karta hai, taaki software use parse aur validate kar sake. Kitab ka example ek chhota JSON object hai jisme "summary" aur "issues" fields hain, issues me file, line aur severity entries hain. System me structured output schema ke against validate hota hai: missing field, galat type ya unexpected severity value reject hota hai, silently accept nahi hota. Validation failure system signal hai, cosmetic problem nahi.

{
  "summary": "3 files reviewed, 2 findings",
  "issues": [
    {
      "file": "OrderService.java",
      "line": 42,
      "severity": "high"
    }
  ]
}

3.9–3.10 Prompt versioning

Prompt versioning prompt changes ko time ke saath track karta hai taaki behaviour test, compare, debug aur roll back kiya ja sake — prompts ko code ki tarah treat kiya jata hai, versions, review aur regression testing ke saath. Kitab ka version record ek JSON object hai jisme fields hain: version ("v1.2.0"), prompt text, model, temperature aur timestamp. Prompt change ek behaviour change hai aur kisi bhi code change ki tarah test hona chahiye.

3.11 Prompting as a system layer

Prompt ek system layer hai — iska matlab hai versioning, testing, review aur ownership. Prompt change karna behaviour change karna hai.

3.12 Common prompting mistakes

  • Vague instructions; koi output format nahi.
  • Format-sensitive task ke liye koi examples nahi.
  • Prompt ko irrelevant context se overload karna.
  • Critical instructions ko lambe context me aisi jagah rakhna jahan wo kho jayein.
  • Model ke output par validation ke bina trust karna.
  • Prompts ko test kiye bina badalna.

3.13 Prompt safety aur injection risks

Prompt injection woh failure mode hai jahan user input, retrieved content ya external data trusted instructions ko override karne ya model ko manipulate karne ki koshish karta hai. Defences layered hain — retrieved aur user content ko data treat karo, instructions nahi; inputs ko validate aur filter karo; system instructions ko untrusted content se alag rakho; model kya cause kar sakta hai use restrict karo; aur har output ko use karne se pehle validate karo.

NOTE

Prompt change = behaviour change. Har prompt change ko code change ki tarah test karo, version karo, aur roll back karne layak rakho.

Ch 4 — LLMs as System Components

Model propose karta hai; application dispose karti hai. Ye chapter application boundary, function calling, tool calling, evaluation aur observability ko samjhata hai — LLM ko ek controlled component ki tarah treat karna.

4.1 Application boundary ke andar LLM

Application boundary woh controlled software layer hai jo model ke aas-paas hoti hai, jahan validation, permissions, orchestration, tool execution, retrieval, memory aur observability enforce hote hain. Model proposes; application disposes. Model output ko kabhi action ki tarah trust nahi kiya jata: ye ek request hai jise application validate, authorise, execute ya reject kar sakti hai.

4.2–4.3 Function calling — ek controlled contract

Function calling structured pattern hai jisme model predefined function ke arguments return karta hai, jise application execute kar sakti hai. Example: get_weather function jisme location parameter hai ("Berlin") — model function name aur arguments ke saath JSON-style call deta hai, aur application arguments validate karke function execute karti hai aur result model ko wapas deti hai. Contract hai function definition — name, description, parameters aur required fields — aur model us contract tak constrained rehta hai.

4.4–4.5 Tool calling — workflow

Tool calling function calling ko generalise karta hai — koi bhi external capability (API, database, search, calculation). Workflow:

Order example: model get_order_details call karta hai, order_id "ORD-12345" ke saath, aur order ka status, items aur total receive karta hai, jise wo user ko jawab dene me use karta hai. Model backend ko kabhi directly touch nahi karta.

4.6 Jab tool use agent jaisa lagne lage

Jab tool use repeated aur stateful ho jata hai — model tool call karta hai, result observe karta hai, agla step decide karta hai aur goal ki taraf continue karta hai — to ye agent jaisa lagne lagta hai. "LLM with tools" aur "agent" ke beech ki boundary ek spectrum hai, aur wahi controls (validation, authorisation, step limits, logging) dono taraf apply hote hain.

4.7–4.10 LLM evaluation — silent regressions ko pakadna

Evaluation woh tareeka hai jisse team ko pata chalta hai ki LLM component abhi bhi theek behave kar raha hai ya nahi. Automatic evaluation deterministic checks use karta hai (jaise schema validity ya exact-match answers); human evaluation me log quality judge karte hain; LLM-as-a-judge me ek aur model rubric ke against output score karta hai.

Kitab ki evaluation table 4 categories cover karti hai:

CategoryKya check hota hai
PromptClarity, completeness, format
ModelAccuracy, consistency, hallucination rate
ToolSahi tool choice, sahi arguments, failure handling
SystemLatency, cost, end-to-end success

Practice me evaluation ka matlab hai: realistic cases ka chhota dataset banao, har change par run karo, aur regression ko failing test ki tarah treat karo. Silent regressions — behaviour jo bina kisi error ke degrade ho jaye — wahi failure hai jise evaluation pakadne ke liye hai; bina iske, prompt ya model change system ko chupchaap worse bana sakta hai.

4.11–4.13 LLM observability — trust ki foundation

Observability model aur agent behaviour ki visibility hai: prompts, model calls, retrieved context, tool calls, token usage, latency, cost aur evaluation signals. Ye trust ki foundation hai kyunki ye "model ne kaha" ko traceable record me badal deta hai — kya poochha gaya, kya retrieve hua, kya call hua aur kya wapas mila. Practice me iska matlab hai: prompt aur response metadata log karo (full secrets zaroori nahi), har call par token counts aur costs record karo, aur har step ko request identifier se correlate karo.

NOTE

Model output action nahi, request hai. Har request validate hogi, authorise hogi, phir execute ya reject hogi — ye application boundary ka kaam hai, model ka nahi.

Ch 5 — RAG Systems (Retrieval-Augmented Generation)

RAG ka matlab hai: generate karne se pehle relevant external information retrieve karo aur model ke context me daalo — taaki answers evidence me grounded hon, training memory me nahi.

5.1–5.2 RAG kya hai aur pipeline

RAG isliye matter karta hai kyunki ye current knowledge add karta hai, hallucination kam karta hai, private data support karta hai, aur answers ko auditable banata hai — model ko kaha ja sakta hai ki sirf supplied context se answer de.

Kitab ka code sketch (Java-style) ingestion aur retrieval steps dikhata hai: query embed karo, vector store search karo, top-k chunks retrieve karo, unhe prompt me assemble karo, phir model call karo.

5.3 Document ingestion aur chunking

Chunking retrieval quality decide karta hai. Chunks chhote, coherent aur self-contained hone chahiye; kitab ka example lagbhag 100 tokens ke chunks, 20-token overlap ke saath use karta hai taaki sentence boundary par aadha na kate. Paanch focused chunks bees noisy chunks se behtar hain: zyada context cost, latency aur distraction badhata hai, aur model galat passage use kar sakta hai.

5.4 Embeddings aur vector search

Query aur chunks embedding model se vectors me convert hote hain, aur similarity — normally cosine similarity, jo vectors ke beech ka angle measure karta hai — chunks ko rank karti hai. Example scores: Doc 1 — 0.89, Doc 2 — 0.66, Doc 3 — 0.15 — isliye Doc 1 best match hai aur Doc 3 lagbhag irrelevant hai. Embedding model swap kiya ja sakta hai, lekin poora index phir se re-embed karna padega, kyunki alag models ke vectors comparable nahi hote.

5.5 Retrieval strategies

  • Semantic (vector) search — meaning dhoondhta hai.
  • Keyword search (BM25) — exact terms dhoondhta hai; codes, names aur identifiers ke liye strong hai.
  • Hybrid search — dono combine karta hai, better recall aur precision ke liye.
  • Metadata filtering — document type, topic, owner, product, date, language ya source se search narrow karta hai.
  • Re-ranking — retrieved candidates ko stronger model se reorder karta hai, LLM tak pahunchne se pehle.
  • GraphRAG — knowledge graph add karta hai taaki retrieval entities ke beech ke relationships follow kar sake — example: service se uske owner tak, owner se uski dependencies tak.

5.6–5.7 Retrieval quality aur failure modes

Failure modes concrete hain: retrieval irrelevant chunks deta hai; bahut zyada noise deta hai; sahi document missing hai; model retrieved context ko ignore karke memory se answer deta hai; ya context khud contradictory hai. Design answers: kam lekin behtar retrieve karo, model ko instruct karo ki sirf supplied context se answer de, evidence na ho to "I don't know" kahe, aur log karo ki kya retrieve hua taaki failures diagnose ho sakein.

6.1–6.2 Agent definition aur agent loop

7.1–7.2 Tools aur tool design — contract design hai

Tool calling broader pattern hai jisme model structured instruction ke through capability request karta hai. Tool orchestration controlled process hai: tools expose karna, requests validate karna, execute karna, errors handle karna aur results wapas dena.

Tool design contract design hai: har tool ka naam, description, input schema, output schema, ownership aur risk classification hoti hai. Kitab ki Code Review Agent ke liye tool-selection table me paanch tools hain:

7.7 Tool performance aur cost

7.8–7.11 MCP — Model Context Protocol

7.12 MCP security considerations

Ch 8 — Planning and Execution Control

Multi-step tasks ek model call se solve nahi hote: system ko decide karna padega kya karna hai, kis order me, aur kaise pata chalega ki kaam ho gaya. Bina plan ke agent step by step react karta hai aur drift kar sakta hai, kaam repeat kar sakta hai ya jaldi ruk sakta hai.

8.1–8.2 Planning kyun matter karti hai aur approaches

Plan ek explicit, checkable structure hai: steps, dependencies, expected outputs aur stopping condition. Teen approaches:

  • Plan-then-execute — model pehle poora plan banata hai, phir runtime use step by step execute karta hai — plan kuch hone se pehle inspectable hota hai.
  • Interleaved planning — planning aur execution alternate karte hain, taaki plan tool results se adapt kare — ye ReAct style hai.
  • Hierarchical planning — high-level plan sub-plans me tootta hai, har ek ke apne steps hote hain.

Kitab ki planning table paanch dimensions cover karti hai: Goal (plan ko kya achieve karna hai), Steps (ordered actions), Dependencies (kaunse steps ko kaunse pehle ke results chahiye), Constraints (limits jaise time, cost aur permissions) aur Success criteria (system ko kaise pata chalega ki plan kaam kar gaya).

8.3 Plan representation — structured data, free text nahi

Kyunki plan structured data hai, runtime use validate kar sakta hai, deterministically execute kar sakta hai, progress track kar sakta hai, aur step fail hone par stop ya re-plan kar sakta hai. 8.4–8.5 Execution control aur ReAct

Execution control runtime ka kaam hai: steps order me run karo, dependencies respect karo, step aur time limits enforce karo, lack of progress detect karo, failures handle karo, aur decide karo kab stop, retry, re-plan ya human ko escalate karna hai. ReAct interleaved pattern hai: model reason karta hai, act karta hai, result observe karta hai aur phir se reason karta hai. Kitab ka ReAct pseudocode loop: jab tak done nahi aur steps bache hain — agle action ke baare me reason karo, use execute karo, result observe karo, state update karo, aur check karo ki goal meet hua ya nahi.

8.6 Plan failure ko handle karna

Step fail ho sakta hai kyunki tool fail hua, arguments invalid the, retrieved data missing tha, ya model ne unusable output diya. Runtime ke options: retry (sirf transient failures ke liye, limit ke saath), re-plan (jo seekha usse plan badlo), fall back (simpler ya degraded path use karo), ya stop aur failure report karo clear reason ke saath. Jo plan execute nahi ho sakta, use failure ki tarah visible hona chahiye, silently success ki tarah treat nahi karna chahiye.

8.8–8.10 Anti-patterns, checklist aur planning as system capability

Anti-patterns: aise task ke liye sab kuch up front plan karna jise adaptation chahiye; stable task ke liye har step ke baad re-plan karna; model ko aise steps invent karne dena jinka koi tool ya validation nahi hai; aur koi stopping condition na hona. Execution-control checklist: explicit goal; bounded steps; validated tool calls; progress detection; failure handling; aur definition of done clear hona.

9.1–9.2 Agents ko memory kyun chahiye aur types

9.3–9.4 Short-term vs long-term memory

12.4 Model selection aur routing

12.8–12.10 Timeouts, retries, circuit breakers, bulkheads aur load management

Har external call ko timeout chahiye; retries sirf transient failures par aur bounded. Circuit breakers failing dependency ko kuch time ke liye call karna band kar dete hain taaki system safely degrade kare, baar-baar fail karne ke bajay; bulkheads failures isolate karte hain taaki ek failing component shared resources exhaust na kare. Load management queues, backpressure (system safely process na kar paye to requests slow, queue ya reject karna) aur rate limits use karta hai.

12.11–12.13 Cost budgets, performance metrics aur observability

Budgets set karo per request, per user aur per time period; cost track karo per request, per workflow aur per model; spending threshold cross karne par alert karo; aur budget exhaust hone par gracefully stop ya degrade karo. Kitab ki cost-metrics table me paanch measures hain: cost per request, cost per workflow, token usage per step, cache hit rate aur model-call count. Performance metrics: end-to-end latency, step latency, token usage, cost per request, error rate, retry rate aur cache hit rate — percentiles (p95 aur p99) report karo, sirf averages nahi, kyunki averages slow tail ko chhupa dete hain.

Performance ke liye observability ka matlab hai: har step ki duration, token counts, cost aur outcome record karo, taaki team slow ya expensive step dhoondh sake, guess karne ke bajay.

Ch 13 — Multi-Agent Systems

Multiple agents tabhi use karo jab responsibility boundaries real hon. Single well-controlled workflow jo task solve kar de, woh kai agents se behtar hai jo sirf coordination cost add karte hain. Bahut se so-called multi-agent systems unnecessary complexity hain, impressive terminology me lipti hui.

13.1 Kab multiple agents use karein

Multiple agents tabhi jab boundaries real hon — alag data access, alag evaluation criteria, alag security constraints ya alag execution lifecycles. Agar ek workflow kaam kar jaye to wahi behtar hai.

13.2–13.3 Architectures aur coordination

Architectures: centralised (planner ya orchestrator kaam assign karta hai aur results combine karta hai — reason karna aasan); distributed (agents events, shared memory, queues ya workflow steps se communicate karte hain — long-running ya asynchronous tasks ke liye behtar, lekin operationally zyada complex); aur hierarchical (coordinator specialists ko delegate karta hai, jo aage delegate kar sakte hain). Coordination-patterns table me chaar patterns hain: centralised orchestration (ek coordinator workflow ka owner), peer-to-peer (agents directly communicate karte hain), hierarchical (coordinators aur specialists ki layers) aur event-driven (agents shared bus par events par react karte hain).

13.4–13.5 Communication, shared state aur handoffs

Agents structured messages exchange karte hain, free text nahi — message me sender, recipient, type, payload aur correlation identifier hota hai, taaki flow trace aur validate ho sake. Shared state explicit honi chahiye: kaunsa state ka hissa kis ka hai, kaun use change kar sakta hai, aur conflicts kaise resolve hote hain. Handoffs ek agent se doosre agent ko kaam pass karte hain, poore context ke saath jo agle agent ko chahiye — handoff-state table me paanch items hain: task description, current state, completed steps, pending decisions aur relevant evidence.

13.6 Multi-agent failure modes

Failure modes multi-agent designs ke liye specific hain: coordination failures (agents disagree karte hain aur koi decision ka owner nahi hai); handoff failures (agents ke beech context lost ya corrupt ho jata hai); cascading failures (ek agent ki error doosron tak propagate hoti hai); aur inconsistent state (do agents truth ke alag versions par act karte hain). Design answers: deterministic ownership aur conflict policies (example: security finding style finding ko override karta hai, ya agents disagree karein to human decide karta hai), bounded retries, aur har decision ka ek accountable owner.

13.7–13.9 Evaluation, security aur design principles

Evaluation poore system ko cover kare, sirf har agent ko nahi: end-to-end success, handoff quality, coordination overhead, total cost aur total latency. Security: har agent ki apni permissions hoti hain, aur agent ko doosre agent ki authority inherit nahi karni chahiye sirf isliye kyunki use usse message mila hai; messages ko kisi bhi untrusted input ki tarah validate kiya jata hai. Design principles: responsibility se split karo, fashion se nahi; agents ki sankhya chhoti rakho; coordination explicit banao; har decision ko deterministically own karo; aur coordination cost ko quality gain ke against measure karo.

13.10–13.11 Code Review Agent ka multi-agent version

Multi-agent version me split hai: Retrieval Agent (merge-request metadata, changed files, diffs, tickets aur standards fetch karta hai), Analysis Agent (changes examine karta hai), Security Agent (authentication, authorisation, injection risks, unsafe dependencies, sensitive data) aur Review Agent (findings aggregate karta hai, duplicates remove karta hai, severity rank karta hai aur structured output return karta hai). Har part ko prompt, test, evaluate aur observe karna aasan hai — aur weak final review ko us specific part tak trace kiya ja sakta hai jo fail hua.

14.4–14.5 Offline vs online evaluation

Online evaluation real use ke dauraan behaviour track karta hai: output validity, tool failure rate, retry count, latency, cost, user feedback, escalation rate, false-positive reports, accepted aur rejected recommendations, aur repeated failure patterns. Dono complementary hain — offline controlled aur repeatable hai, online woh cases dekhta hai jo test sets miss karte hain.

14.6 LLM-as-a-judge

LLM-as-a-judge ek model se doosre model ke output ko defined rubric ke against score karwata hai. Kitab ka example rubric correctness, completeness aur grounding ko 1–5 scale par score karta hai, aur ek review finding jo technically correct hai lekin evidence se unsupported hai, grounding par low score karti hai. Example judge output ek JSON-style object hai jisme correctness, completeness aur grounding ke scores, overall score 3, aur ek comment hai jo explain karta hai ki finding correct hai lekin evidence weak hai. Judge calls cache ki jati hain, kyunki same output ko dobara judge karna paisa waste karta hai.

14.7 Human evaluation

Human evaluation quality dimensions ke liye ground truth hai jinhe automation score nahi kar sakta: kya review comment helpful hai, kya recommendation team ki architecture me fit hoti hai, aur kya summary point miss karta hai. Human review samples par hoti hai, clear rubrics ke saath aur subjective judgement wali jagah multiple reviewers ke saath.

14.8–14.10 Metrics, regression testing aur automation

Regression testing: har prompt, model ya tool change evaluation suite run karta hai, aur metric me drop release ko block karta hai. Kitab ka regression example: ek prompt change ne loop iterations 40% badha diye — naye prompt ne zyada steps, zyada cost aur zyada latency produce ki, bina better quality ke — aur regression test ne use pakad liya. Evaluation automation ka matlab hai pipeline har change par run hoti hai, results ko us code aur prompt versions ke saath store karti hai jinhone use produce kiya, aur dashboards produce karti hai, logs nahi jinhe koi padhta nahi.

Ch 15 — Observability in AI Systems (Logs, Metrics, Traces)

Observability signals se system behaviour samajhne ki ability hai — logs, metrics, traces, prompts, model calls, tool calls, retrieval steps, token usage, cost aur evaluation results. Agent systems probabilistic hain: bina iske, kharab answer ek mystery hai; iske saath, team dekh sakti hai kya poochha gaya, kya retrieve hua, kya call hua aur kya wapas mila — aur woh specific step fix kar sakti hai jo fail hua.

15.1–15.4 Logs, metrics aur traces

Logs request ki kahani preserve karte hain; metrics kai requests ke across patterns dikhate hain; traces ek request ke steps ko connect karte hain. Kitab ka log example ek JSON-style record hai: request id "req-8127", timestamp, user id, action, tool name, model name, token counts, latency aur status — aur rule hai pehle metadata log karo (kya hua, kaunsa tool, kitna time, kitne tokens, kitni cost) aur full content sirf wahan jahan safe aur useful ho, kyunki logs se secrets ya personal data leak nahi hone chahiye.

Metrics (kitab ki table): request count, error rate, latency (p50, p95, p99), token usage, cost per request, tool failure rate, validation failure rate aur user-feedback rate. Alerting rules concrete hain: alert karo jab error rate 5 minutes ke liye 5% se zyada ho, jab p95 latency apna threshold cross kare, ya jab validation failures spike karein. Alert ko diagnosable cause ki taraf point karna chahiye, sirf ye announce nahi karna chahiye ki kuch galat hai.

Trace ek record hai ki single request system se kaise guzri; span uske andar ek timed operation hai (model call, retrieval step, tool call, validation step, database query). Kitab ka trace example: trace id "b3f1", request id, aur spans — retrieval (142 ms), model call (734 ms), tool call aur validation, har ek ki apni duration aur status. Trace ek retry bhi dikhata hai: ek tool call jo "PARTIAL_SUCCESS" return karta hai, reason "RETRIEVAL_TIMEOUT_SOFT", ek retry ke baad — aur ek note ki tool "portfolio-analyzer-v1" version 1.4.2 ne total latency ka 12% contribute kiya (example me 142 tokens). Correlation request id aur trace id se hoti hai, har component se carry ki jati hai.

15.5 LLM observability

LLM observability model-specific slice hai: prompts, model calls, retrieved context, tool calls, token usage, latency, cost aur evaluation signals, per call record kiye jate hain taaki team kisi bhi answer ke liye jawab de sake — "kaunsa model, kaunsa prompt version, kaunsa context, kaunse tools, aur kitni cost?"

15.6–15.8 Architecture, logging best practices, metrics aur alerting

Observability layer runtime ke bagal me baithti hai, har component se structured logs, metrics aur traces collect karti hai, aur dashboards, alerts aur evaluation pipelines ko feed karti hai. Kitab ki observability-tools table me chaar kinds hain: logging (structured event records), metrics (aggregated measurements aur dashboards), tracing (distributed request traces) aur evaluation (quality scoring aur regression tracking). Best practices: free text ke bajay structured data (JSON) log karo; har record me request, trace aur user identifiers include karo; actions ke saath decisions bhi log karo (agent ne tool kyun choose kiya ya kyun ruka); secrets redact karo; aur logs ko production incidents debug karne layak time tak rakho.

15.9–15.14 Tracing in practice, anti-patterns aur 7 rules

Anti-patterns: sirf final answer log karna; secrets samet sab kuch log karna; alerts ke bina metrics; model call par rukne wale traces; aur observability data jise koi dekhta hi nahi. Observability ke liye saat architect's rules: content se pehle metadata log karo; sab kuch request aur trace id se correlate karo; latency, cost aur quality ko ek saath measure karo; sirf errors par nahi, behaviour par alert karo; poore workflow ke traces rakho; evaluation data ko observability ka hissa banao; aur signals ko regularly review karo, sirf incidents ke dauraan nahi.

NOTE

Bina observability ke, kharab answer ek mystery hai. Iske saath, team woh specific step dekh aur fix kar sakti hai jo fail hua — isliye log metadata pehle, content baad me.

Ch 18 — The Future of Agent Systems

Ye chapter explicitly prophecy nahi hai: ye field ka snapshot hai, jaisa 2026 me khada hai, real systems me pehle se dikh rahe patterns ke base par. Future sirf bade models se define nahi hoga.

18.1 Single agents se multi-agent systems tak

Ek agent se shuru karo; split tabhi karo jab responsibility boundaries real hon. Code Review Agent evolve hokar Retrieval Agent, Analysis Agent, Security Agent aur Review Agent ban sakta hai — har ek ka narrower job, jise prompt, test, evaluate aur observe karna aasan hai — lekin coordination ko phir shared state ya message passing, decisions ki clear ownership, aur agents disagree karein to deterministic policy chahiye, warna architecture accountable owner ke bina ek debate club ban jata hai. Centralised coordination ko reason karna aasan hai; distributed coordination long-running ya asynchronous tasks ke liye behtar scale karta hai lekin operational complexity add karta hai.

18.2 Memory ki badhti hui role

Memory supporting feature se core component banegi, layered: short-term (current task), session (current interaction), long-term (durable knowledge) aur organisational (reusable policies aur rules). Mushkil hissa hai sahi slice ko sahi time par retrieve karna, versioning, scoping, freshness aur deletion rules ke saath; ownership, source, freshness aur deletion rules ke bina memory liability ban jati hai.

18.3 Enterprise systems ke saath stronger integration

Agents workflow ke bagal me assistants se uske andar controlled participants banenge — tickets inspect karna, documents padhna, customer history check karna, internal APIs call karna, status update karna, draft banana, pull request kholna ya validation job trigger karna. Isse bar badhta hai: authentication aur authorisation, audit logging aur traceability mandatory ho jate hain, aur model-generated tool call kabhi backend system ko directly nahi jana chahiye. Trust boundaries explicitly design karni hongi: kuch agents read-only, kuch approval ke liye drafting, kuch low-risk tasks automatically execute karte hue, kuch sensitive systems se poori tarah blocked.

18.4–18.5 Structured interaction aur tool platforms/registries

Software ko contracts chahiye. Tool definitions prompt fragments ke bajay formal interface descriptions banengi; organisations shared tool catalogs maintain karengi — schema, ownership, risk classification, permission requirements, examples, expected outputs aur failure modes ke saath. Kitab ka registry example get_file_diff hai, developer platform team ki ownership me, read-only, repository read permission chahiye, human approval nahi chahiye, caller identity, arguments, latency, response size aur failure reason log karta hai, version v2 par hai, v1 defined retirement date tak available hai. Tool versioning matter karta hai kyunki ek tool version ke against kaam karne wala prompt fields badalne par break ho sakta hai.

18.6–18.7 Evaluation as continuous process aur human-in-the-loop

Evaluation continuous hoti hai: offline datasets (golden examples, adversarial cases, regression tests) plus real traffic ki online evaluation (validity, tool failure rate, retry count, latency, cost, user feedback, escalation rate, false positives, accepted aur rejected recommendations). Evaluation data dashboards, regression tests, prompt revisions, retrieval tuning, tool improvements aur model-routing decisions me feed honi chahiye — unread logs me gayab nahi honi chahiye. Human-in-the-loop: fully autonomous systems hamesha sahi goal nahi hote. Agent evidence collect karta hai, recommendation prepare karta hai, draft generate karta hai, risk classify karta hai ya action propose karta hai; human approve, edit, reject ya escalate karta hai. Approval workflows system features hain, states (pending, approved, rejected, expired, escalated), evidence dikhane wala interface, audit logs, timeout behaviour aur override rules ke saath. Human feedback learning signal bhi hai jo prompts, retrieval, evaluation datasets aur tools ko improve karta hai.

18.9–18.10 Architecture ki role aur practical perspective

Prompt behaviour influence kar sakta hai, model capability improve kar sakta hai, tool reach extend kar sakta hai — lekin architecture decide karta hai ki pieces kaise interact karte hain, boundaries kahan hain, kya allowed hai, kya reject hota hai, kya log hota hai aur failure par kya hota hai. Practical perspective: narrow workflow se shuru karo, task define karo, data aur tools decide karo, decide karo kaunse actions ko approval chahiye, output contract define karo, evaluation jaldi add karo aur observability pehle version se, aur pehla version boring aur inspectable rakho — clear inputs, outputs, logs, contracts aur failure behaviour. Sabse common mistake hai final architecture bahut jaldi bana lena (multiple agents, lambe prompts, broad tool access, persistent memory, complex routing) core workflow prove hone se pehle, kyunki phir har failure ke bahut saare possible causes hote hain. Memory tab add karo jab repeated context quality improve kare, retrieval jab external knowledge chahiye, tools jab controlled access chahiye, multi-agent structure jab responsibility boundaries ek workflow se badi ho jayein, approval jab risk ko judgement chahiye, aur model routing jab cost, latency ya quality steps ke across vary kare.

18.11–18.12 Kya build karna hai aage aur closing thoughts

Sabse bada possible agent banane ke bajay ek real workflow ko strengthen karo — contract explicit banao, model response validate karo, itna trace data store karo ki reconstruct ho sake answer kaise produce hua, phir grounding, tool control, memory, evaluation improve karo aur (sirf tab jab workflow ek agent se badi ho jaye) multi-agent orchestration. Code Review Agent ke liye agla practical version persistent memory, vector-backed retrieval layer, tool registry, evaluation pipeline aur approval workflow add karta hai, review comments automatically post karne se pehle.

Closing thought: agentic AI systems magic nahi hain; ye probabilistic models ke aas-paas bane software systems hain. Sabse strong systems model ko unlimited freedom nahi denge; ye model capability ko engineering control ke saath combine karenge — model ko reason karne dena lekin silently execute nahi karne dena, tools ko sirf validated contracts se act karne dena, memory ko sirf lifecycle aur access rules ke saath preserve karna, aur kaam automate karna jabki humans loop me rahein jahan accountability matter karta hai. Agentic AI software engineering ko replace nahi karta; ye uska standard badhata hai.

Interview FAQs — Systems Thinking for Agentic AI

36 sawal-jawab jo aaj ke interviews me is kitab ke topics par poochhe jate hain. Har jawab kitab ke content par based hai.

Q1Agentic AI kya hai, aur ye normal chatbot se kaise alag hai?

Agentic AI woh system hai jo ek goal pursue karta hai: state interpret karta hai, decide karta hai, act karta hai (tool call ya retrieval), observe karta hai, state update karta hai, aur stopping condition tak continue karta hai. Normal chatbot sirf ek reply deta hai; agent ek bounded loop me kaam karta hai — tools, memory, retrieval aur guardrails ke saath. Kitab ka central claim: agentic AI controlled software hai jo probabilistic model ke aas-paas bana hai — architecture, model size nahi, production-readiness decide karta hai.

Q2Agent loop kya hota hai? Uske steps kya hain?

Agent loop ek repeated pattern hai: state interpret karo → decide karo → act karo ya retrieve karo → observe karo → state update karo → decide karo continue karna hai ya nahi. Har iteration me runtime decide karta hai continue karna hai ya rukna hai. Loop ko bounded rakhna padta hai — step limit, time limit, retry limit aur cost limit se — warna agent infinite loop me atak sakta hai ya budget kha sakta hai.

Q3Prompt aur system prompt me kya farak hai?

Prompt model ko bheja gaya input hai — instructions, context, examples aur constraints. System prompt high-priority instruction layer hai jo role, rules, style aur behavioural boundaries define karta hai. System prompt user input se zyada trusted hota hai, aur retrieved content ya user text use override nahi kar sakta — yahi trust boundary ka base hai.

Q4Token kya hai aur context window kyun matter karti hai?

Token text ki chhoti unit hai — word, word ka hissa ya punctuation. Context window maximum tokenised input + output hai jo model ek request me process kar sakta hai. Kitab ka example: 8,000-token window me prompt 3,000 aur response 500 reserve karne ke baad sirf 4,500 tokens bachte hain retrieved context ke liye — matlab ~45 chunks (100-token chunks) ya ~11 chunks (400-token chunks). Budget ek design decision hai, afterthought nahi.

Q5Temperature, top-k aur top-p kya karte hain? Production me kaunsa use karein?

Temperature token probability distribution ko reshape karta hai — low temperature (0 ke kareeb) deterministic output deta hai, high temperature diverse lekin unpredictable. Top-k sirf k most likely tokens rakhta hai; top-p smallest set rakhta hai jinki cumulative probability threshold tak pahunche. Kitab ka example distribution: Python 0.40, Java 0.30, C++ 0.20, Rust 0.10. Code review jaisi deterministic tasks ke liye low temperature sahi hai; creative tasks ke liye high temperature.

Q6RAG kya hai aur ye hallucination kaise kam karta hai?

RAG (Retrieval-Augmented Generation) generation se pehle relevant external information ko model ke context me retrieve karta hai. Pipeline: ingestion → chunking → embedding → indexing → retrieval → filtering → re-ranking → context assembly → generation → evaluation. Grounding se output supplied evidence se tie hota hai, isliye model invent karne ke bajay retrieved facts par base karta hai. Lekin RAG hallucination khatam nahi karta — sirf kam karta hai; isliye output validation aur evidence checks zaroori rehte hain.

Q7Embedding aur cosine similarity kya hain?

Embedding text ka numerical vector hai jo uska meaning capture karta hai. Cosine similarity do vectors ke beech ke angle se unki similarity measure karti hai — angle chhota matlab meaning kareeb. Kitab ka example: dog [0.92, 0.85, 0.10] aur cat [0.88, 0.82, 0.12] kareeb hain, car [0.15, 0.20, 0.91] door hai. Retrieval me query aur chunks ke embeddings compare karke relevant chunks dhoondhe jate hain.

Q8Chunking me chunk size aur overlap kaise choose karein?

Kitab ka rule: chunks ~100 tokens, 20-token overlap. Chhote chunks precise hain lekin context kho dete hain; bade chunks context rakhte hain lekin noise badhate hain. Overlap boundary information ko survive karne deta hai — code function ko beech me todna evidence kharab karta hai. Chunk boundaries semantic honi chahiye (function, section), arbitrary token count par nahi.

Q9Hybrid search kya hai aur BM25 kyun abhi bhi relevant hai?

Hybrid search semantic search (embeddings, meaning) aur keyword search (BM25 — term frequency aur relevance se ranking) ko combine karta hai. BM25 exact terms, codes aur identifiers ke liye behtar hai; semantic search synonyms aur paraphrase ke liye. Kitab ka example: Doc 1 semantic 0.89, Doc 2 0.66, Doc 3 0.15 — hybrid weights se dono signals milkar final ranking banate hain. Re-ranker phir top candidates ko dobara order karta hai.

Q10Tool calling aur function calling me kya farak hai?

Function calling structured pattern hai jisme model predefined function ke arguments return karta hai, jise application execute kar sakti hai. Tool calling broad pattern hai jisme model structured instruction se external capability request karta hai. Dono me model sirf request karta hai — execute application karti hai, validated contract ke against. Model-generated tool call kabhi backend system ko directly nahi jani chahiye.

Q11MCP kya hai aur tool registry kyun chahiye?

MCP (Model Context Protocol) standard tareeka hai tools, resources aur prompts ko AI applications tak consistent contract se expose karne ka. Tool registry available tools aur unki definitions ki managed list hai — schema, ownership, risk classification, permission requirements, examples, expected outputs aur failure modes ke saath. Kitab ka registry example get_file_diff hai: read-only, repository read permission, version v2, v1 defined retirement date tak available. Tool versioning matter karta hai kyunki prompt ek tool version ke against kaam karke fields badalne par break ho sakta hai.

Q12Guardrail kya hai? Ye prompt instruction se kaise alag hai?

Guardrail control hai jo AI behaviour ko constrain karta hai — validation, permissions, policies, approval gates, filtering ya runtime enforcement se. Kitab ka rule: guardrail code hai, prompt instruction nahi. Example: har finding check hoti hai — file merge request me exist karni chahiye, severity allowed set (HIGH/MEDIUM/LOW) me honi chahiye, evidence actual diff ko reference karna chahiye. Evidence ke bina finding InvalidModelOutputException ke saath reject hoti hai.

Q13Prompt injection kya hai aur isse kaise bachein?

Prompt injection user input, retrieved content ya external data ka trusted instructions ko override karne ya behaviour manipulate karne ka attempt hai. Defence: trust boundaries — retrieved content aur user input ko data treat karo, instructions nahi; tool calls ko validated contracts se execute karo; sensitive actions ke liye approval gates rakho; aur output ko schema validation se check karo. Kitab ka principle: model ke output ko kabhi blindly trust nahi karna — har boundary par validate karo.

Q14Agent memory ke types kya hain aur scoping kyun matter karti hai?

Memory ke chaar scopes hain: short-term (current task), session (current interaction), long-term (durable knowledge) aur organisational (reusable policies aur rules). Har entry ko owner, source, freshness aur deletion rules chahiye. Scoping matter karti hai kyunki user memory doosre user ko leak nahi honi chahiye, secrets kabhi memory me nahi aane chahiye, aur stale memory galat decisions deti hai. Bina lifecycle ke memory liability ban jati hai.

Q15Structured output kyun zaroori hai? JSON schema kaise help karta hai?

Structured output (jaise JSON) software ko model ke output ko reliably parse aur validate karne deta hai. Kitab ka review example: summary (3 files reviewed, 2 findings), findings array (file, line, severity, category, explanation, evidence, recommendation) aur metadata. Schema validation check karta hai ki output required format aur rules satisfy karta hai ya nahi — aur invalid output par ek baar correction prompt ke saath retry hota hai, phir visibly fail.

Q16ReAct pattern kya hai?

ReAct reasoning aur action ko combine karta hai — decide, act, observe, continue. Agent pehle reason karta hai (kya karna hai), phir action leta hai (tool call ya retrieval), phir result observe karta hai aur agla step decide karta hai. Ye agent loop ka core pattern hai: har step me reasoning aur observation se agla decision banta hai, blind sequence nahi chalti.

Q17Multi-agent system kab use karna chahiye aur kab nahi?

Multiple agents tabhi jab responsibility boundaries real hon — alag data access, alag evaluation criteria, alag security constraints ya alag execution lifecycles. Agar ek workflow kaam kar jaye to wahi behtar hai. Kitab kehta hai bahut se so-called multi-agent systems unnecessary complexity hain. Split karne par coordination cost aati hai — shared state, handoffs, conflict policies — jo quality gain se zyada nahi honi chahiye.

Q18Multi-agent systems ke failure modes kya hain?

Chaar specific failure modes: coordination failures (agents disagree karein aur koi decision owner nahi), handoff failures (agents ke beech context lost ya corrupt ho), cascading failures (ek agent ki error doosron tak propagate ho), aur inconsistent state (do agents truth ke alag versions par act karein). Design answers: deterministic ownership aur conflict policies, bounded retries, aur har decision ka ek accountable owner.

Q19LLM-as-a-judge kya hai aur iske risks kya hain?

LLM-as-a-judge ek model se doosre model ke output ko defined rubric ke against score karwata hai. Kitab ka rubric correctness, completeness aur grounding ko 1–5 scale par score karta hai; example judge output me overall score 3 hai. Risks: judge apne style ki taraf biased ho sakta hai, domain nuance miss kar sakta hai, inconsistent ho sakta hai. Isliye judge scores ko human judgement ke against calibrate karo, judge ki reasoning log karo, aur judge calls cache karo.

Q20Offline aur online evaluation me kya farak hai?

Offline evaluation dataset ko release se pehle run karta hai — prompts, models, retrieval strategies compare karta hai aur regressions pakadta hai. Online evaluation real use ke dauraan behaviour track karta hai — output validity, tool failure rate, latency, cost, user feedback, escalation rate. Dono complementary hain: offline controlled aur repeatable hai, online woh cases dekhta hai jo test sets miss karte hain. Kitab ka regression example: prompt change ne loop iterations 40% badha diye — offline test ne pakad liya.

Q21Observability kya hai? Logs, metrics aur traces me kya farak hai?

Observability signals se system behaviour samajhne ki ability hai. Logs request ki kahani preserve karte hain (kitab ka example: req-8127, tool, model, tokens, latency, status). Metrics kai requests ke across patterns dikhate hain (error rate, p50/p95/p99 latency, cost per request). Traces ek request ke steps ko connect karte hain — trace id b3f1 me retrieval 142 ms, model call 734 ms, tool call PARTIAL_SUCCESS. Bina observability ke kharab answer mystery hai; iske saath team woh step fix kar sakti hai jo fail hua.

Q22Alerting ke liye kaunse thresholds use karein?

Kitab ke concrete rules: alert karo jab error rate 5 minutes ke liye 5% se zyada ho, jab p95 latency apna threshold cross kare, ya jab validation failures spike karein. Alert ko diagnosable cause ki taraf point karna chahiye, sirf ye announce nahi karna chahiye ki kuch galat hai. Sirf errors par nahi, behaviour par alert karo — aur signals ko regularly review karo, sirf incidents ke dauraan nahi.

Q23Human-in-the-loop kab zaroori hai?

Jab stakes high hon, actions irreversible hon, ya judgement chahiye ho. Agent evidence collect karta hai, recommendation prepare karta hai, draft generate karta hai, risk classify karta hai ya action propose karta hai; human approve, edit, reject ya escalate karta hai. Approval workflows system features hain — states (pending, approved, rejected, expired, escalated), evidence dikhane wala interface, audit logs, timeout behaviour aur override rules ke saath. Human feedback learning signal bhi hai.

Q24Agent system ka budget kaise design karein?

Budgets design decision hain: per review at most 30 seconds, at most 5 model calls, at most 10 files, at most 5 retrieved chunks, at most 5 findings, at most 12 steps (Code Review Agent example). Budget hit hone par system gracefully degrade kare — jo complete hua use return karo, reason ke saath — silently fail nahi. Partial output explicitly batana chahiye: 4 me se 3 files review hui to output ye kahe.

Q25Code Review Agent ka end-to-end flow kya hai?

Merge request load karo → changed files list karo → diffs retrieve karo → standards retrieve karo → analyse karo → findings validate karo → structured output banao → log karo aur return karo. Boundaries: agent merge requests, diffs, standards aur coverage data read kar sakta hai; code merge nahi kar sakta, deployment approve nahi kar sakta, security warnings suppress nahi kar sakta. Evaluation metrics: finding precision, recall, evidence validity aur user acceptance.

Q26Spring Boot me Code Review Agent kaise implement hota hai?

Maven project, Java 17 aur Spring Boot 3.x. Java records data carry karte hain — ReviewRequest, ReviewIssue, ReviewResult. Tool layer (SourceControlTools: getMergeRequest, listChangedFiles, getFileDiff), retrieval layer (RetrievalService: query embed karo, vector store search karo, top-k chunks return karo), reasoning layer (AgentReasoner: structured analysis return karta hai), guardrails (code me validation), AgentService (loop run karta hai), aur REST API POST /api/reviews. First run: session-001, 8 steps, 2 files reviewed, 2 findings.

Q27Current agent systems ki sabse badi limits kya hain?

Kitab saat limits batata hai: non-determinism (wahi diff ek run me medium-risk, doosri me low-risk), hallucination (permission check helper me hai lekin agent claim karta hai missing hai), shallow ya brittle reasoning, prompt sensitivity (ek word badalne se noisy findings), context quality (irrelevant info ya purana standard), tool reliability (truncated diff, fail hota coverage tool), aur evaluation difficulty (comment technically correct lekin unhelpful). Ye limits engineering ka kaam define karti hain — production system ko assume karna chahiye ki model fail ho sakta hai.

Q28Model routing kya hai aur kab use karein?

Model routing alag tasks ke liye alag models select karna hai — cost, latency, capability, risk ya required quality ke hisab se. Simple tasks (classification, extraction) chhote saste model par, complex reasoning bade model par. Routing tab add karo jab cost, latency ya quality steps ke across vary kare. Har route ke liye evaluation chahiye — routing decision khud ek design decision hai jo measure honi chahiye.

Q29Agent system me security kaise design karein?

Pehla rule: model ke output ko kabhi blindly trust nahi karna. Har agent ki apni permissions hoti hain; agent ko doosre agent ki authority inherit nahi karni chahiye sirf isliye kyunki use usse message mila hai. Tool calls validated contracts se execute hote hain. Secrets vault me, configuration me nahi. Audit logging aur traceability mandatory hain. Trust boundaries explicitly design karo: kuch agents read-only, kuch approval ke liye drafting, kuch low-risk tasks automatically execute karte hue.

Q30Evaluation dataset kaise banayein?

Real examples se: known issues, known non-issues, expected severity aur acceptable explanations ke saath — adversarial cases (change jo risky lagta hai lekin safe hai) aur edge cases samet. Code Review Agent ke worked example me datasets PORT-CR-1047 aur PORT-CR-1052 use hote hain. Datasets versioned aur refreshed hone chahiye — stale dataset current behaviour measure karna band kar deta hai. Sirf apne khud likhe examples se evaluate karna anti-pattern hai.

Q31Trace aur span kya hain? Distributed tracing kyun zaroori hai?

Trace ek record hai ki single request system se kaise guzri; span uske andar ek timed operation hai — model call, retrieval step, tool call, validation step, database query. Har span ki apni duration aur status hoti hai. Correlation request id aur trace id se hoti hai, har component se carry ki jati hai. Distributed tracing zaroori hai kyunki agent workflow me kai steps hote hain — bina trace ke pata nahi chalta kaunsa step slow ya fail hua.

Q32Agent system banate waqt sabse common mistake kya hai?

Final architecture bahut jaldi bana lena — multiple agents, lambe prompts, broad tool access, persistent memory, complex routing — core workflow prove hone se pehle. Phir har failure ke bahut saare possible causes hote hain. Kitab ka rule: narrow workflow se shuru karo, pehla version boring aur inspectable rakho — clear inputs, outputs, logs, contracts aur failure behaviour. Memory tab add karo jab repeated context quality improve kare, multi-agent tab jab responsibility boundaries ek workflow se badi ho jayein.

Q33Context engineering kya hai aur context assembly kaise karein?

Context engineering model ke context me kya jayega, use design karna hai. Context assembly me select aur arrange karte hain: instructions, input, retrieved chunks, memory, tool results aur output requirements. Kitab ka rule: context me sirf wahi dalo jo task ke liye relevant hai — irrelevant context noise badhata hai aur 'lost in the middle' problem deta hai (model beech ke context ko bhool jata hai). Har token ka budget hota hai, isliye assembly ek design decision hai.

Q34Agent system ki quality kaise measure karein? Kaunse metrics matter karte hain?

Chhah dimensions: correctness (output sahi hai?), completeness (sab cover karta hai?), grounding (evidence se supported hai?), safety (harmful ya unauthorised actions avoid?), efficiency (latency, cost, token use), aur user experience (output useful aur usable hai?). Koi single score in sab ko capture nahi karta. Code Review Agent ke metrics: finding precision, recall, evidence validity aur user acceptance (developers kitni findings accept karte hain).

Q35Fallback aur circuit breaker agent systems me kaise kaam karte hain?

Fallback controlled alternative behaviour hai jab model, retrieval step, tool ya workflow fail ho ya unsafe ho jaye — jaise retrieval fail hone par bina context ke aage badhne ke bajay explicitly batana ki kya check nahi hua. Circuit breaker resilience pattern hai — failing dependency ko kuch time ke liye call karna band karo taaki system safely degrade kare. Dono ka goal ek hi hai: failure visible aur controlled ho, silent nahi.

Q36Agentic AI ka future kya hai — kya sirf bade models se define hoga?

Nahi — kitab kehta hai future sirf bade models se define nahi hoga. Patterns pehle se dikh rahe hain: memory core component banegi, enterprise systems ke saath stronger integration hoga, tool platforms aur registries formal honge, evaluation continuous process banegi, aur human-in-the-loop approval workflows standard honge. Sabse strong systems model ko unlimited freedom nahi denge — model capability ko engineering control ke saath combine karenge. Agentic AI software engineering ko replace nahi karta; ye uska standard badhata hai.
