Chapter 1 · AI Applications and Their LifecycleSection 01

AI Application kya hai?

AI application matlab aisi software application jo generative AI models ke upar bane features deti hai. ChatGPT ke November 2022 me aane ke baad poori software industry badal gayi — startups aur badi companies sab AI applications banane ki race me lag gayi. Lekin is race me ek baat yaad rakhni hai: traditional software engineering ki best practices abhi bhi relevant hain — bahut log bekaar me wheel reinvent kar rahe hain.

“The question of whether Machines Can Think (…) is about as relevant as the question of whether Submarines Can Swim.”
— [Name]

AI application ka matlab kya hai?

AI application koi bhi software hai jo artificial intelligence models par bane features provide karta hai. Aisi applications banana cross-functional kaam hai — developers, data scientists aur domain experts ko saath kaam karna padta hai.

  • AI ka matlab yahan Generative AI hai: technically AI me rule-based systems se lekar neural networks tak sab aata hai, lekin aaj ke time me jab log AI kehte hain to unka matlab Generative AI hota hai. Ye book bhi yahi convention follow karti hai — jab bhi AI application likha hai, matlab generative models se bani application hai.
  • Generative models nayi content generate karte hain — text, image, audio ya video. AI applications inhi capabilities ko features me badal kar value create karte hain.
  • Traditional ML se farak: fraud detection ya recommendation engine jaise traditional models ka output True/False ya ek confidence score hota hai. Generative model ka output koi bhi text ho sakta hai — isliye inke challenges aur strategies alag hain.
  • AI coding assistants se bani apps AI applications nahi hain — lekin coding assistants khud AI applications hain, kyunki wo generative capabilities ko user-facing feature banate hain.
  • AI application zaroori nahi ki AI user ko dikhe — process background me bhi chal sakta hai. Par use AI application market tabhi karo jab AI relatively obvious ho.

Foundational Models — building block

Generative models ka zyada use hone wala naam hai foundation models — bade, pre-trained models jo bahut saare kaam ke liye adapt kiye ja sakte hain. Traditional ML models ek specific task ke liye train hote hain; foundation models general-purpose hote hain — bina retrain kiye bahut saare contexts me use ho sakte hain. Isi liye ye AI applications ke fundamental building block hain.

Large Language Models (LLMs) inka sabse famous example hain — sirf text par focus karte hain. Lekin foundation models sirf text tak limited nahi — multimodal bhi hote hain, jo text, image, audio aur video sab samajh aur generate kar sakte hain.

LLMs kaise kaam karte hain?

LLM ek probabilistic text completion engine hai — input text (prompt) do, wo uska completion predict karta hai, probability ke hisaab se. Ye basic samajh AI applications ke challenges samajhne ke liye kaafi hai — book LLM ke andar ki deep technical detail me nahi jaati.

Tokens — words nahi, tokens

LLMs words par nahi, tokens par kaam karte hain. Pehle characters use hote the, par wo inefficient tha — har character ke liye ek prediction chahiye thi. Isliye text ko tokens me baanta gaya — ek token ek character, ek word, ya word ka ek hissa ho sakta hai. Example: cooking ko cook + ing me baanta jata hai, dono hisso ka apna matlab hai.

Encoding ka common algorithm hai Byte Pair Encoding (BPE) — bade text corpus par train hoke ye seekhta hai ki tokens ko sabse efficiently kaise jodein. Isse LLM agla token zyada efficiently predict kar pata hai aur model compact rehta hai.

WARNING: Zyada tar AI APIs token ke hisaab se bill karti hain — isliye ye samajhna vital hai ki words ≠ tokens, aur tokens ki sankhya aksar words se bahut zyada hoti hai.

Transformer aur attention

Aaj ke zyada tar LLMs transformer architecture follow karte hain (2017 ke mashhoor “Attention Is All You Need” paper se). Attention mechanism ki wajah se LLM sirf aakhri word nahi, poora input consider karke output predict karta hai.

Non-deterministic hona — feature, bug nahi

LLMs agla token chunne ke liye alag-alag decoding strategies use karte hain, aur inme aksar ek random element hota hai. Matlab: ek hi prompt par model hamesha ek jaisa output nahi deta.

  • Retry kar sakte ho: jawab pasand na aaye to dobara try karo — yehi ChatGPT jaisi interfaces me sab karte hain.
  • Creativity: sabse probable continuation na chunne se output novel ya surprising lagta hai. Example: “The meal was absolutely…” ka high-probability continuation hai “delicious”, par model kabhi “a symphony of flavors where the basil played the cello” bhi likh sakta hai.
  • Downside: yahi randomness inconsistencies (contradicting jawab) aur hallucination (facts par based nahi, aise jawab) bhi paida karti hai. Isliye AI applications banana matlab in negative side effects ko manage karna — aur platform ka kaam hai iske liye sahi tools dena.

Text generation ki power

Text generation sunne me simple lagta hai, par ye bahut powerful capability hai. Bahut se kaam completion me reframe ho jate hain — translation, summarization, code generation. Example: prompt “In Python, a hello world program looks like…” ka completion print('Hello World') hota hai — matlab code generation bhi completion hi hai.

AI Applications ke Use Cases

Models ki capabilities tezi se badh rahi hain, par use cases unse peeche hain. Bahut se enterprises bina deep use-case focus ke AI me “all in” ho gaye. Isliye adoption-driving use cases ko pehchanana aur prioritize karna ek vital strategic imperative hai.

Adoption ke 3 criteria: (1) kaam valuable ho, (2) output ki quality validate karna easy ho, (3) loop me ek motivated human ho jo quality check kare aur feedback de. Jahan ye teeno milte hain, wahan GenAI adoption sabse tezi se hota hai.

Coding

GenAI ka breakthrough use case. Code expensive bhi hai aur valuable bhi — koi bhi improvement bottom line par asar dalta hai. Quality validate karna easy hai — code run hota hai ya compile hota hai, quality tools aur metrics hain. Aur loop me motivated human hai jo output check karta hai.

  • AI auto-completion: developer faster likhta hai; snippet pasand na aaye to type karte raho, AI naya snippet banata rahega; acceptable snippet par Tab dabao. Ye acceptance hi quality ka excellent signal hai.
  • AI-powered IDEs: poora IDE own karne se zyada customization aur control milta hai — isliye Visual Studio Code ke bahut se forks bane.
  • Autonomous Coding Agents (Vibe Coding): task describe karo, AI sab kar dega. POCs aur ideas spike karne ke liye amazing hai. Lekin ye small, focused changes ke idea ke bilkul against hai — production quality ke liye bahut kaam chahiye. Irony ye hai ki wahi purani achhi practices — quality aur documentation — in agents ki success predict karti hain.

Image aur video production

Content generation image/video GenAI ke pehle use cases me se ek tha. Lambi videos me context maintain karna mushkil tha, par frontier labs ise solve kar rahe hain. Content moderation iska ulta side hai — inappropriate content detect karke hatana, aur Generative AI se moderation karna ek naya tool hai. Clip creation simple hai — short-form video (TikTok jaisi platforms) ke liye purani content ko reuse karna lucrative market hai, quality creator ke taste ya views se quickly samajh aati hai.

Writing

Writing bahut bada field hai — har niche ki apni quality aur style hai, isliye koi global writing quality nahi hoti.

  • Summarization: pehle use cases me se ek — bade text ko chhota karna, human fact-check kar sakta hai.
  • Technical writing: coding se closely related — style guides, specific vocabulary, structure, legislation aur regulations — quality ke hard rules hain, feedback possible hai.
  • Creative writing: narrative structures apply hote hain, par use cases limited hain.

Transcription aur Translation

Language element ki wajah se LLMs ke liye natural fit hai. Aaj 2026 me technology companies me meeting me notes lene wala koi dikhta hi nahi — meeting summarization tools ne productivity bahut badha di hai. Translation me LLMs ne machine translation ko easy aur accessible bana diya hai, par behtar hai specific translation models use karo aur native speaker se validation lo.

Education

GenAI Socratic methods se seekhane me excellent hai — sawaal puchho, jawab pao, follow-up karo, apni pace par deep dive karo. Stupid sawaal puchhne par humiliation ka zero risk — isliye AI Tutors ban rahe hain. Lekin bina expert ke rabbit holes me kho jaana easy hai — dusri learning methods ke saath combine karne par powerful tool hai.

Information aggregation

Chat with your Documents pehle use cases me se ek tha — documents upload karo, unke baare me sawaal puchho. Aaj ye enterprise search me pahunch gaya hai, uske saare problems ke saath. Deep Research promising hai — computers humans se bahut fast read/write karte hain, isliye huge amounts of unstructured data aggregate karke research questions ka jawab de sakte hain.

Data organization

Unstructured data ko structure karna AI applications ki strength hai — jaise legal team ke liye internal contracts se data nikaalna. Business domain ko samajh kar Ontology banana aur use data ka semantic layer banana powerful capability hai — abhi early stage par hai, par explore karne layak hai.

Workflow automation

Enterprises ne yahan bahut focus kiya hai. Lekin RPA ki tarah — sabse buri cheez automate karna wo hai jo exist hi nahi karni chahiye thi. Pehle processes aur value streams map karo, phir workflows banao. Seedha full auto karna aksar galti hai; business ke saath co-build karna behtar shuruaat hai.

Customer Support early use case tha — expensive aur valuable, par poor quality validate karna mushkil, aur pehle se bahut optimisation ho chuka tha. AI Agents long tail of customer support me effective hain, par bahut si flagship success stories baad me debunk hui hain.

Aage aur bhi bahut se use cases aayenge — aur experience ke saath unki success ki probability bhi badhegi.

Pattern: LLM Chat Interfaces

LLM ek text completion engine hai — use text ka snippet do, wo use continue karta hai. Humans ke liye ye interaction natural nahi hai. Isi liye chat interface wala abstraction ChatGPT ki early popularity ka bada reason bana.

Human ko sawaal “What is your favorite food?” ko text ki shuruaat “My favorite food is…” me frame karna padta — ye natural nahi hai. Chat interface is abstraction ko ek familiar conversational experience ke peeche chhupa deta hai (Figure 1-2).

Chat interface ke peeche kya hota hai?

Sabse simple form me ye aisa dikhta hai:

chat — system, user aur assistant messages
System Message: You are a helpful assistant
User: What do you recommend I have to eat?
Assistant: ...
  • Role-based tokens: APIs sirf text concatenate nahi karti — special tokens se signal karti hain ki text system ka hai, user ka hai ya assistant ka. Instruction fine-tuning ke dauraan LLM ne in tokens ke baare me seekha hai, isliye expected format follow karne ki likelihood badhti hai.
  • Full conversation history: sirf latest message nahi, poori history pass karna common practice hai — isse LLM ko conversation yaad rehta hai.
  • Context window limit: LLM ek limit tak hi text (tokens) process kar sakta hai. History limit cross kare to purane messages drop karne padenge ya conversation summarize karni padegi.

Sirf chat wrap karne ki value kam hai

Aaj leading LLM providers (OpenAI, Anthropic, Google) khud dedicated chat endpoints dete hain, isliye sirf plain LLM interaction ko chat interface se wrap karne wali dedicated application banane ki value kam hai. Lekin chat interface ek common interaction pattern hai — complex AI applications me bhi use hota hai.

Pattern: Retrieval Augmented Generation (RAG)

LLMs ka knowledge sirf training time tak ka hota hai. Kisi specific domain ya problem space ka knowledge — jaise kisi internal system ki documentation — training data me probably nahi tha. RAG isi problem ko solve karta hai: runtime par specific knowledge fetch karo aur LLM ko additional input ke roop me do.

RAG se hallucination kam hoti hai aur training cut-offs overcome hote hain. Ye technique pehli baar Meta ne 2020 ke paper “Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks” me introduce ki thi.

RAG ke 3 steps

Naam se hi pata chalta hai — RAG 3 steps me kaam karta hai (Figure 1-3): pehle retrieval step user input se additional information nikaalta hai, phir initial input ko retrieved information se augment kiya jata hai, aur phir LLM additional information ko consider karke final response generate karta hai.

Knowledge base aur vector databases

RAG me information source ko knowledge base kehte hain — simplest form me ye sirf ek database hai. Lekin RAG ko kisi bhi information retrieval technique ke saath combine kar sakte ho, isliye ye bahut powerful pattern hai aur bahut saari variations me exist karta hai.

  • Vector databases ke saath synergy: foundation models aur vector databases dono text ko tokens (embedding models se) me transform karte hain, jo vectors ke roop me store hote hain. Similar vectors query karne se semantically similar entries milti hain — keyword match nahi. Example: car search karne par automobile ya vehicle wali entries bhi mil sakti hain.
  • Off-the-shelf solutions: OpenAI Knowledge ya AWS Bedrock Knowledge Bases jaise solutions simple Q&A chatbots ke liye valuable hain — PDF upload karo, complexity abstract ho jati hai. Lekin jab domain data simple tabular data se aage badhta hai aur complex understanding aur data modeling chahiye, to ye solutions jaldi apni limit par pahunch jate hain.
  • RAG variations: Agentic RAG, multimodal RAG, adaptive RAG, speculative RAG — RAG ek fundamental pattern hai jo complex AI applications me variations ke saath use hota hai.

Note: vector databases ko Chapter 5 me aur detail me cover kiya gaya hai (book ka cross-reference).

Pattern: AI Agents aur Graphs

RAG ke baad agla pattern hai AI Agents — LLM ke saath tools connect karke use actions karne do. Agent ka matlab: apne environment ko perceive karna aur actuators se act karna. Software ke terms me: agent runtime par khud decide karta hai ki agla step kya hoga.

Example ke liye socho tum ek email inbox process karne ke liye agent bana rahe ho. Ye function email ko analyze karta hai aur decide karta hai ki wo spam hai ya important:

Example 1-1 — email processor (book me printed code)
def process(email):
    prompt = f"""
        You are an email processor.
        Is the following email spam or important?
        {email}
        Please answer with either "spam" or "important".
    """
    response = send_to_llm(prompt)
    if response == "spam":
        mark_as_spam(email)
    elif response == "important":
        mark_as_important(email)

Is function me do cheezein hain jo agent ko agent banati hain:

  • LLM ko tool ke roop me call: send_to_llm function string input le kar output deta hai — LLM ko ek action ke roop me treat kiya gaya.
  • Decision aur action: LLM ke response ke basis par agent khud decide karta hai ki email ko mark_as_spam karna hai ya mark_as_important — phir wo action execute karta hai.
Ye example me LLM ki zaroorat nahi hai — email ko keywords ya classifier se bhi process kar sakte hain. Isliye ye ek AI application hai, par necessarily ek achha AI use case nahi. Lekin isse agent ke mechanics samajhne me help milti hai.

Tools aur framework evolution

Early days me LLM ke paas tools ke roop me sirf text hota tha — tool invoke karna ek messy string-matching exercise tha. Aaj LLM providers ne native tool calling APIs me tools daal diye hain, jo structured output return karte hain. Isse LLMs aur agents ko bahut bada boost mila hai.

  • Tools = parameterised functions: LLM ko diye gaye tools functions hote hain, jinke naam aur parameters LLM ko diye gaye hote hain — LLM decide karta hai ki kaunsa tool kab call karna hai.
  • Frameworks: OpenAI Agents SDK aur Google Agent SDK jaise vendor SDKs ke alawa open-source vendor-agnostic frameworks hain — LangGraph, Pydantic AI aur CrewAI.
  • Pydantic AI version me same email processor 4 lines me likha ja sakta hai — tool calling aur structured output framework handle karta hai:
Example 1-2 — Pydantic AI version (book me printed code)
from pydantic_ai import Agent, RunContext

email_agent = Agent('openai:gpt-4o', result_type=str)

@email_agent.tool
async def mark_as_spam(ctx: RunContext, email: str):
    ...

@email_agent.tool
async def mark_as_important(ctx: RunContext, email: str):
    ...

async def process(email: str):
    await email_agent.run(
        f"Is the following email spam or important?
{email}"
    )

Raw agent autonomous hota hai — control flow runtime par define hota hai, har step par LLM decide karta hai ki aage kya karna hai. Lekin usi autonomy ki wajah se wo inefficient path le sakta hai ya endless loops me phans sakta hai. Isliye control flow ko restrict karna hota hai.

Graph-based AI Agents

Graph-based agents me agent flow ek state machine (graph) hota hai — autonomy sirf transitions par milti hai. Ye raw agent se zyada predictable aur reliable hote hain. Example: Deep Research Agent (Perplexity) me Planner sub-questions banata hai, Researcher agent ko query karta hai, Result Evaluator quality check karta hai, aur Report Writer final report banata hai (Figure 1-4).

Orchestrated AI Workflows

Orchestrated workflow me saare steps fixed order me execute hote hain — koi autonomy nahi. Ye deterministic tasks ke liye perfect hai, jaise unstructured data se structured data nikaalna. Workflow engines (Airflow, Argo) ye saare features out of the box dete hain: checkpointing, error handling, parallel execution, retries, monitoring.

Composite AI Architectures

Real applications me patterns combine hote hain: graph-based agent me RAG stage ho sakta hai, uske baad chat interface, aur multi-agent architecture me LLM-based tools aur agents saath kaam kar sakte hain. Isliye patterns ko toolbox samjho — problem ko kisi ek pattern me force mat karo. Multi-agent systems me tasks ko sub-tasks me baanta jata hai, aur unhe coordinate karne ke liye standardised protocols exist karte hain (jo Chapter 8 me explore kiye gaye hain).

AI Application Development Lifecycle

AI applications banane ka process traditional software engineering se bahut similar hai. Bespoke training jaise specialised cases ko chhod kar, AI Engineering sabse zyada software engineering se milti hai — isliye is section me traditional software engineering practices apply hoti hain, sirf AI-specific parts par dhyaan dete hue.

Lifecycle ke 5 phases hain, aur ye ek iterative loop hai — phases repeat hote hain, phases ke beech me transitions hote hain, aur is loop ke through learning hoti hai (Figure 1-5).

1. Discovery & Planning

Har project business value se shuru hota hai — application ka purpose aur goal kya hai? Isme development teams aur business teams (business analysts, domain experts, end users) saath kaam karte hain. Cross-functional requirements — security, compliance, accuracy — is phase me early align karna chahiye.

MVP (Minimum Viable Product) is phase ka best friend hai — ek product jo abhi complete nahi hai, par use karke user feedback ke through learn kar sakte ho. Ye approach AI applications ke liye bhi kaam karti hai — sab kuch final hone ka wait mat karo.

2. Design & Development

Design me application ka architecture, interfaces aur components decide hote hain — tools, knowledge bases, aur inke beech interaction. Tech choices (programming language, framework, LLM provider) decide hote hain. Prompt engineering yahan ek iterative experimental process hai — alag-alag prompts try karna aur unke output compare karna, best prompt chunna.

3. Testing — sabse alag phase

Testing AI applications me sabse different phase hai. LLM non-deterministic hota hai, isliye traditional unit tests ka pass/fail yahan kaam nahi karta. Iske bajaye Evals use hote hain — evaluation datasets aur multiple confidence scores (accuracy, coherence, safety) ke saath. Testing me experimentation loop hota hai: change karo, eval metrics par measure karo, aur pata karo ki change se metrics kaise relate karte hain — relation aksar non-obvious hota hai.

4. Deployment

AI applications ko microservices ki tarah deploy kiya jata hai — independently deploy aur scale kar sakte ho, autoscaling aur canary releases use kar sakte ho. Deployment me platform ka bahut bada role hai.

5. Operations & Monitoring

Production me application ki health, latency, aur resource use monitor karna hota hai. AI-specific monitoring me do cheezein important hain:

  • Token consumption — production me sabse bada variable cost; har feature ki token usage measure karni chahiye.
  • Online evaluation — production behavior ko eval dataset ke against evaluate karna, kyunki production behavior eval dataset se alag ho sakta hai. Drift detect karna — jab production performance eval performance se alag ho jaye.
  • Tracing — prompts, responses aur tool calls ko track karna — explainability aur auditability ke liye vital hai.

DevOps se AI Engineering tak

AI application lifecycle samajhne ke liye pehle DevOps ko samajhna zaroori hai — kyunki AI Engineering ka bahut saara kaam DevOps ke evolution par based hai.

DevOps — 2000s ke end se

DevOps late 2000s me emerge hua — development aur operations teams ke beech ke gap ko bridge karne ke liye. Traditional software development me dev aur ops alag teams hote the, jo slow aur error-prone tha. DevOps ne CI/CD pipelines, agile methodologies, aur cross-functional teams introduce kiye — small, rapid iterations aur continuous delivery.

DevOps ki success ka measure hai DORA metrics — deployment frequency, lead time for changes, change failure rate, aur time to restore service. Ye metrics batate hain ki DevOps practices kitni mature hain.

MLOps — DevOps + ML

MLOps DevOps practices ko ML lifecycle par apply karta hai — data versioning, model training, model serving, aur model monitoring. MLOps ka focus predictive models par tha — traditional ML models jo train kiye jate the aur deploy kiye jate the.

AI Engineering — foundation models se applications

AI Engineering poori AI application lifecycle ko cover karta hai — discovery se lekar operations tak. MLOps predictive models par focus karta tha; AI Engineering foundation models se applications banane par focus karta hai. GenAIOps term bhi exist karta hai, par iski recognition kam hai.

DevOps ka principle “You build it, you run it” yahan bhi apply hota hai — autonomous team poori lifecycle ki responsible hoti hai. Iske liye team ko bahut si expertise chahiye: data engineering, AI modeling, software engineering, aur DevOps. Isi liye golden path aur sensible defaults ke saath central platform entry barrier ko kam karta hai.

Fast-changing ecosystem

AI ecosystem itni tezi se badal raha hai ki naya LLM kal aaj se cheaper aur faster ho sakta hai. Isliye teams ko independently switch karne ki capability chahiye — bina lengthy coordination ke. Yehi platform ka kaam hai: teams ko autonomy dena taaki wo fast-moving ecosystem ke saath keep up kar sakein.

AI Applications vs Microservices

AI applications aur microservices me bahut overlap hai — aur ye achhi khabar hai. Matlab hai ki traditional software engineering ki best practices AI applications par bhi apply hoti hain, aur existing platform capabilities ko reuse kiya ja sakta hai.

Similarities — dono me kya common hai?

  • Independently deployable unit: dono ek business capability ko implement karte hain, manageable size me.
  • Containerize aur stateless: dono ko containerize kiya ja sakta hai, stateless hote hain, aur defined API (RESTful) ke through communicate karte hain.
  • APIs consume karna: dono dusri services ki APIs consume karte hain — AI application LLM APIs consume karta hai.
  • Errors propagate hote hain: dono me errors propagate hote hain — isliye circuit breakers, retries aur fallbacks jaise patterns apply hote hain.

AI-specific differences — kya alag hai?

  • Non-deterministic aur unreliable output: LLM ka output har baar alag ho sakta hai — isliye AI applications ka behavior unpredictable hota hai.
  • Business value planning mushkil: accuracy vary karti hai, safety aur hallucination ke risks hain — isliye ROI predict karna mushkil hai.
  • Hard to test: traditional unit tests kaam nahi karte — evals use karne padte hain.
  • Agents ka control flow unpredictable: agent runtime par decide karta hai ki agla step kya hoga — isse debug karna, explain karna, aur security/compliance/cost risks manage karna mushkil ho jata hai.
  • LLM black box hai: model ke andar kya hota hai, pata nahi — aur frequent releases aate hain, model-specific tuning chahiye hoti hai. Drop-in replacement nahi hota.
  • High latency: LLM calls typical API calls se bahut slow hote hain — isliye user experience aur timeout handling alag tareeke se sochna padta hai.

Platform kya hai?

AI applications banane ke liye teams ko bahut si expertise chahiye — aur “You build it, you run it” ka matlab hai ki team poori lifecycle ki responsible hai. Isse team ki cognitive load badhti hai, aur value delivery slow ho jati hai. Platform Engineering isi problem ko solve karta hai.

“Improving daily work is even more important than doing daily work.”

Platform Engineering kyun?

DevOps aur cloud ke saath Platform Engineering ne traction gain kiya hai. Idea simple hai: centralised services aur tools banao jo teams ki cognitive load kam karein, taaki wo value delivery par focus kar sakein.

  • Team Topologies: Platform Team ka kaam hai Stream-Aligned Teams ki cognitive load kam karna — taaki stream-aligned teams product features deliver karne par focus kar sakein.
  • Cloud kyun kaafi nahi: cloud low-level, general-purpose building blocks deta hai — out-of-the-box solution nahi. Is gap ko close karna hi platform engineering hai.
  • Platform as a Product: platform ko ek internal product ki tarah treat karo — users (developers) ki needs samjho, aur unke liye compelling product banao.

Platform ki definition

Book me di gayi mashhoor definition hai:

“A digital platform is a foundation of self-service APIs, tools, services, knowledge and support which are arranged as a compelling internal product. Autonomous delivery teams can make use of the platform to deliver product features at a higher pace, with reduced coordination.”

Is definition ke key aspects hain:

  • Infrastructure se zyada: platform sirf infrastructure nahi hai — ye APIs, tools, services, knowledge aur support ka foundation hai.
  • Self-service: teams bina central team ke wait kiye, khud provision aur configure kar sakte hain — backlog coupling avoid hoti hai.
  • Compelling internal product: adoption value se jeeto, mandate se nahi — agar platform compelling hai to teams khud use karenge.
  • Goal = autonomy + speed: autonomous delivery teams higher pace par product features deliver karein, kam coordination ke saath.

Platform Anti-patterns

Platform banate time kuch common galtiyan hain — inhe anti-patterns kehte hain. Inhe pehchan kar avoid karna platform engineering ka ek important hissa hai. Book me 10 anti-patterns diye gaye hain.

1. Golden Cage

Golden path se koi deviation nahi — teams ko golden path ke bahar jaane ki permission nahi. Ye innovation ko block karta hai. Golden path hona chahiye, par escape hatches bhi hone chahiye.

2. Enforcing Mandates instead of Winning Adoption

Mandate ka matlab hai user needs miss ho rahi hain. Agar teams platform use nahi kar rahi, to gaps bharo — mandate mat lagao. Adoption value se jeeto.

3. Self-service with Approval

Har approval delivery ko slow karta hai. Self-service ka matlab hai bina approval ke provision karna — approval ka matlab hai self-service nahi hai.

4. Obscure Self-service

Complex, poorly documented, slow ya flaky self-service — black box ban jata hai. Teams ko samajh nahi aata ki self-service kaise use karein, to wo central team par depend karte hain.

5. Backlog Coupling

Stream-aligned teams platform backlog se constrained hain — unhe platform team ki priority ka wait karna padta hai. Isse delivery slow hoti hai.

6. Separate Special Runtime for AI Applications

AI apps = services jo LLM APIs call karte hain — unke liye alag runtime banane ka matlab hai wheel reinvent karna. Teams ko naye defaults seekhne padte hain, aur worst case me duplication hoti hai.

7. Over-Focusing on Prompt Management

Prompts ki reusability limited hai — naye models robust hain, prompts text hain, use-case aur model specific hain. Prompts ko version control me code ke paas rakho. Exception: prompt hints via MCP server — wo share karne layak hain.

8. Delegating Complexity to Users

Platform ka kaam cognitive load kam karna hai — complexity user ko dena matlab platform fail ho gaya. Agar platform complex hai, to wo platform nahi hai.

9. Using a Platform to Hide Organisational Issues

Data governance ka example: platform se organisational issues ko subvert mat karo — better defaults ke liye lobbying karo. Platform organisational problems ko chhupa nahi sakta.

10. Reimplementing Existing Tools

Pehle real problem samjho, existing tools use karo. Major gap ho tabhi reimplement ya improve karo — bekaar me wheel reinvent mat karo.

Interview FAQs

AI Engineering aur Platform Engineering interviews ke liye 40 relevant sawaal-jawaab — is book ke concepts par based.

AI application kya hai?

AI application wo software hai jo generative AI models par bane features deti hai — jaise chat, RAG, ya agents. Traditional ML (fraud detection) se farak ye hai ki generative model ka output koi bhi text ho sakta hai, sirf True/False ya score nahi.

Foundation model kya hai?

Foundation model bada, pre-trained, general-purpose model hota hai jo bahut saare kaam ke liye adapt kiya ja sakta hai — traditional ML models ek specific task ke liye train hote hain. LLM iska sabse famous example hai.

LLM kaise kaam karta hai?

LLM ek probabilistic text completion engine hai — prompt do, wo agla token probability ke hisaab se predict karta hai. Transformer architecture aur attention mechanism use karta hai, jo poora input consider karta hai.

Token kya hai? Words se kya farak hai?

LLMs words par nahi, tokens par kaam karte hain. Ek token ek character, ek word, ya word ka hissa ho sakta hai — jaise cooking ko cook + ing me baanta jata hai (BPE). Words ≠ tokens, aur tokens ki sankhya aksar words se zyada hoti hai — aur APIs token se bill karti hain.

LLM non-deterministic kyun hota hai?

Decoding strategies me random element hota hai — isliye ek hi prompt par model hamesha ek jaisa output nahi deta. Isse creativity milti hai, par inconsistencies aur hallucination bhi aati hain.

Hallucination kya hai aur kaise kam karein?

Hallucination matlab LLM ka aisa jawab jo facts par based nahi hai. Kam karne ke tareeke: RAG (domain knowledge dena), guardrails, prompt engineering, aur human-in-the-loop.

RAG kya hai? 3 steps kya hain?

RAG (Retrieval Augmented Generation) me runtime par knowledge fetch karke LLM ko additional input diya jata hai. 3 steps: Retrieval (knowledge base se info nikaalna), Augment (input ko retrieved info se badhana), Generate (LLM se final response banana).

RAG vs fine-tuning — kab kya use karein?

RAG jab domain knowledge chahiye aur data frequently badalta hai. Fine-tuning last resort hai — jab prompt engineering aur RAG kaafi na ho, kyunki isme expertise aur resources chahiye.

AI agent kya hai?

Agent wo software hai jo apne environment ko perceive karke actuators se act karta hai — runtime par khud decide karta hai ki agla step kya hoga. Tools (parameterised functions) use karke actions karta hai.

Raw Agent vs Graph Agent me kya farak hai?

Raw Agent fully autonomous hota hai — har step par LLM decide karta hai, isliye inefficient path ya endless loops ka risk hai. Graph Agent me flow ek state machine (graph) hota hai — autonomy sirf transitions par milti hai, isliye zyada predictable aur reliable hota hai.

Orchestrated Workflow kya hai?

Workflow me saare steps fixed order me execute hote hain — koi autonomy nahi. Deterministic tasks (jaise unstructured data se structured data nikaalna) ke liye perfect hai. Workflow engines (Airflow, Argo) checkpointing, retries aur monitoring out of the box dete hain.

Multi-agent systems kab use karein?

Jab task ko sub-tasks me baanta ja sake aur alag agents alag sub-tasks handle karein — jaise Deep Research me Planner, Researcher, Result Evaluator aur Report Writer. Coordination ke liye standardised protocols chahiye.

AI application lifecycle ke 5 phases kya hain?

1. Discovery & Planning (business value, MVP), 2. Design & Development (architecture, prompt engineering), 3. Testing (Evals, experimentation loop), 4. Deployment (microservice jaisa), 5. Operations & Monitoring (token cost, online eval, drift, tracing). Ye iterative loop hai.

Evals kya hain? Testing se kaise alag hain?

Evals evaluation datasets aur multiple confidence scores (accuracy, coherence, safety) ke saath quality measure karte hain. Traditional unit tests pass/fail dete hain; LLM non-deterministic hota hai, isliye evals scores dete hain, pass/fail nahi.

Evaluation Driven Development kya hai?

Criteria upfront define karo, phir build karo — har change ko eval metrics par measure karo. Bina metrics ke tum andhere me kaam kar rahe ho.

Online vs offline evaluation me kya farak hai?

Offline evaluation eval dataset par hoti hai (development me). Online evaluation production behavior par hoti hai — kyunki production behavior eval dataset se alag ho sakta hai. Drift tab hota hai jab production performance eval performance se alag ho jaye.

Tracing kyun zaroori hai?

Tracing prompts, responses aur tool calls ko track karta hai — debugging, user behavior samajhne, aur compliance/audit ke liye vital hai. Bina tracing ke agent ka behavior explain karna mushkil hai.

AI app vs microservice — similarities kya hain?

Dono independently deployable hain, containerize ho sakte hain, stateless hain, defined API (RESTful) se communicate karte hain, aur dusri services ki APIs consume karte hain. Errors dono me propagate hote hain — circuit breakers, retries aur fallbacks apply hote hain.

AI app vs microservice — differences kya hain?

AI apps ka output non-deterministic aur unreliable hota hai; business value planning mushkil hai; testing ke liye evals chahiye; agents ka control flow unpredictable hai; LLM black box hai aur frequent releases aate hain; latency high hoti hai.

Guardrails kya hain?

Guardrails policies aur automated checks hote hain jo harmful ya incorrect output ko rokte hain — traditional checks aur LLM-as-judge dono use kar sakte ho.

Prompt engineering vs fine-tuning?

Prompt engineering accuracy improve karne ka pehla step hai — prompt ko refine karo. Fine-tuning last resort hai — jab prompt engineering aur RAG kaafi na ho, kyunki isme expertise aur resources chahiye.

Platform kya hai?

Platform self-service APIs, tools, services, knowledge aur support ka foundation hai, jo compelling internal product ki tarah arrange kiya gaya ho — autonomous delivery teams isse higher pace par product features deliver karein, kam coordination ke saath.

Platform as a Product ka matlab kya hai?

Platform ko internal product ki tarah treat karo — users (developers) ki needs samjho, aur unke liye compelling product banao. Adoption value se jeeto, mandate se nahi.

Cognitive load kya hai? Platform kaise kam karta hai?

Cognitive load wo mental effort hai jo team ko poori lifecycle handle karne me lagta hai. “You build it, you run it” se load badhta hai — platform centralised services aur tools dekar load kam karta hai, taaki teams value delivery par focus kar sakein.

Golden Path vs Golden Cage me kya farak hai?

Golden Path opinionated defaults + escape hatches hain — teams jaldi shuru kar sakte hain aur chaaho to customize kar sakte hain. Golden Cage me koi deviation allowed nahi — innovation block hoti hai.

Self-service ka matlab kya hai? Approval kyun anti-pattern hai?

Self-service ka matlab hai bina central team ke wait kiye, khud provision aur configure karna. Har approval delivery ko slow karta hai — approval ka matlab hai self-service nahi hai.

Backlog Coupling kya hai?

Jab stream-aligned teams platform backlog se constrained hain — unhe platform team ki priority ka wait karna padta hai. Isse delivery slow hoti hai. Self-service aur autonomy isse kam karte hain.

Pareto 80/20 platform me kaise apply hota hai?

20% capabilities jo 80% teams use karte hain, unpar focus karo. Pehchanna: stream teams ki needs samjho (XY Problem se bacho), common patterns samjho, aur variety of use cases support karo.

Mise-en-place principle kya hai?

French cuisine ka concept — “everything in its place”. Chef cooking se pehle saare ingredients aur tools ready rakhta hai. Waise hi platform: lifecycle bhar ki capabilities ready rakho, teams apni zaroorat ke hisaab se chunein.

Omakase principle kya hai?

Japanese concept — “I’ll leave it up to you” / chef’s choice. Naye logon ko nahi pata hota ki “good” kya hai — isliye platform team (chef) best ingredients chunti hai. Experience badhne par teams apne taste se extend kar sakti hain.

Escape hatches / Sharp Tools kya hain?

Escape hatches layered API design hain — jahan next lower layer tak access mile. Teams golden path se bahar ja sakti hain jab zaroorat ho. Bina escape hatches ke golden path golden cage ban jata hai.

Grim Wrapper kya hai? Leaky abstraction kya hai?

Grim Wrapper ek abstraction hai jo complexity ko chhupa nahi pata aur evolution ke saath nahi chal pata. Leaky abstraction ka example: LLM providers ko common interface ke peeche abstract karna — har provider ke unique features hote hain, jo common interface me fit nahi hote.

Two-way door principle kya hai?

Two-way door decisions (reversible) fast lo, one-way door decisions (irreversible) carefully lo. Failures ko learning mana jata hai — reversible decisions me galti karna theek hai.

Diátaxis framework ke 4 types kya hain?

1. Tutorials (beginners, step-by-step), 2. How-to guides (experienced, task kaise karein), 3. Reference (API definitions, lookup map), 4. Explanation (concepts aur principles, kyun).

Docs as Code kya hai?

Docs ko code ke paas rakho, same tools aur process use karo — update workflow ka hissa bane. Code se docs generate karo (docstrings), tests se code samples — sync guarantee milti hai.

IDP vs Data Platform vs MLOps Platform — AI platform kahan fit hota hai?

IDP software engineers ke liye (runtime, CI/CD, logging, auth); Data Platforms data teams ke liye (ingestion, storage, governance); MLOps traditional ML lifecycle ke liye. AI platform inhe extend karta hai — scratch se nahi banata, existing capabilities reuse karta hai.

Noisy neighbour problem kya hai?

Shared services me ek team zyada resources kha jaye to dusri teams affect hoti hain. Solution: rate limits, quotas aur prioritisation — fair use ensure karna.

Shared responsibility model (compliance) kya hai?

Platform team platform khud compliant banaye; stream-aligned teams apni apps compliant banayein aur platform ko compliant tareeke se use karein; independent audits se verify karo. Compliance ko gatekeeping mat banao.

God Agent anti-pattern kyun hai?

Ek agent jo sab kuch karta hai — domain complex hai, ek agent sab kuch handle nahi kar sakta, 2026 me ye poor results deta hai. Chhote, specialised subsystems behtar hote hain.

AI for AI’s Sake — kab LLM mat use karo?

Jab kaam deterministic rules se ho sakta hai — jaise acronyms expand karna ya if-statements se logic — to LLM mat use karo. LLM expensive aur unpredictable hai; deterministic solution jahan kaam kare, wahi use karo.
