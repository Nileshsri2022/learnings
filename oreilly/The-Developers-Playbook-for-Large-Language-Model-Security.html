Preface — Kitab kis liye hai

Ye kitab developers aur security professionals ke liye hai jo large language models (LLMs) ko implement kar rahe hain aur unke naye security risks ko samajhna chahte hain. Central claim seedha hai: LLM koi aam software component nahi hai — ye ek bilkul nayi tarah ki security problems laata hai, kyunki ye natural-language input leta hai, plausible-sounding output deta hai, aur tools, data aur actions se jud sakta hai.

Ye kitab kis ke liye hai

Ye kitab developers, security professionals aur har us insaan ke liye hai jo LLMs implement kar raha hai aur LLM-specific security risks aur unke defences samajhna chahta hai. Kitab OWASP Top 10 for LLM Applications banane ke direct experience se likhi gayi hai, aur iska focus practical, developer-useable guidance par hai — abstract AI-safety theory par nahi.

  • Naya risk class: LLM natural language samajhta hai, isliye uske failure modes traditional software se alag hain — wo hidden instructions follow kar sakta hai, data leak kar sakta hai, aur galat cheezein confidently bol sakta hai.
  • Tools se juda hua: LLM sirf text nahi deta — wo tools, data aur actions se connect hota hai, isliye uski galti sirf galat jawab nahi, galat action bhi ban sakti hai.
  • Reader ka background: kitab maan kar chalti hai ki reader ko basic software aur security concepts aate hain. Ye programming scratch se nahi sikhati, aur Python-style code examples follow kar sakne ki ummeed rakhti hai.

Scope aur approach

Kitab sirf LLMs par focus karti hai — AI security in general par nahi. Ye OWASP Top 10 for LLM Applications ke around organised hai, lekin sirf risks list nahi karti: har risk ko explain kiya gaya hai, real incidents ke saath illustrate kiya gaya hai, aur concrete mitigations, architecture advice, testing aur governance ke saath pair kiya gaya hai.

  • Real-world examples aur case studies poori kitab me use hue hain — ye dikhane ke liye ki failures theory me nahi, asal me kaise hue.
  • Har risk ke saath ye bhi bataya gaya hai ki usse kaise roka jaye, na ki sirf ye ki wo kya hai.
  • Kitab ka structure: pehle incidents aur OWASP list, phir architectures aur trust boundaries, phir har bade attack ki gehrai, aur ant me process aur responsible-AI framework.

Conventions — kitab kaise padhein

  • Code monospace style me dikhaya gaya hai; jo code literally type karna hai wo alag dikhaya gaya hai, aur jo placeholders reader ko replace karne hain wo alag.
  • Warnings, notes aur tips ko main text se alag callout karke dikhaya gaya hai.
  • Important warning: LLM behaviour, model capabilities aur vendor controls bahut tezi se badalte hain, isliye kisi particular model ya date se judi examples ko us pattern ka illustration samjho — us model ke baare me permanent fact nahi.

Code examples ka use

Readers code ko apne programs aur documentation me use kar sakte hain. Substantial portions ko bechna ya distribute karna, ya kitab ko reproduce karna — iske liye permission chahiye. Usual O'Reilly attribution aur fair-use framing apply hoti hai, aur usse aage ke use ke liye kitab O'Reilly permissions process ki taraf point karti hai.

O'Reilly Online Learning

Kitab O'Reilly ke online learning platform ke through available hai, jo live training, video courses, interactive learning aur dusri kitabein bhi offer karta hai. Preface is ecosystem ko briefly describe karta hai — ye wo context hai jisme kitab publish hui hai.

Acknowledgments

Kitab OWASP Top 10 for LLM Applications community aur un sab contributors ko thanks kehti hai jinhone wo list banayi — plus colleagues, reviewers aur family jinhone support kiya. Emphasis ye hai ki wo list ek collective effort hai, ek insaan ka kaam nahi.

Yaad rakhne wali baat: kitab ka promise practical hai — theory nahi, wo guidance jo developer aaj apne LLM application me laga sake. Har chapter ek risk ko incident se shuru karta hai aur defence par khatam hota hai.

02Chapter 1

Chatbots Breaking Bad

LLMs powerful hain aur tezi se adopt hue hain — lekin unke failure modes traditional software wale nahi hain. Ye chapter un failures ki kahani se shuru hota hai: ek chatbot jo 24 ghante me bigad gaya, ek company jiska confidential code leak hua, aur ek technology jo governance se tez bhaagi.

The Great Chatbot Reset — ChatGPT ka explosion

ChatGPT launch hua 30 November 2022 ko. Isne 5 din me 1 million users aur January 2023 tak 100 million users tak pahunch kar us samay ki sabse tezi se grow karne wali consumer application ka record banaya.

  • Adoption ki speed ne organisations ko unprepared pakda. Chapter Samsung case se shuru hota hai: Samsung engineers ne proprietary source code aur dusra confidential material ChatGPT me paste kar diya, information leak hui, aur Samsung ne tool ko internally ban kar diya.
  • Italy ki data-protection authority ne bhi ChatGPT ko temporarily ban kiya, privacy concerns par — ye early sign tha ki regulators jaldi intervene karenge.
  • Point: ek consumer chatbot lagbhag overnight enterprise security problem ban gaya — usse pehle ki zyada teams ke paas policies, controls ya ye inventory bhi ho ki kaun use kar raha hai.

Tay and the Perils of Unchecked Learning

Tay kya tha: Microsoft ka Tay ek Twitter chatbot tha jo March 2016 me launch hua, 18- se 24-saal ke users ke liye. Ye conversations se seekhne ke liye design hua tha, ek 19-saal ki ladki jaisi personality ke saath, aur ye Snapchat bhi use karta tha.

  • Kya hua: 24 ghante se bhi kam me ye racist, sexist aur abusive content post karne laga. Trigger uska learning design tha: ye wahi repeat karta tha jo users ne sikhaya. Ek feature — user ke phrase ko uske peeche repeat karna (repeat after me) — exploit hua, aur coordinated users ne jaan-bujh kar use hateful output ki taraf train kar diya.
  • Response: Tay ko hata liya gaya aur company ki taraf se uske offensive behaviour ke liye public apology aayi. Chapter isse ye dikhata hai ki unfiltered user input se seekhne wala model us input ki sabse buri cheezein inherit kar leta hai — aur bina guardrails ke "learning" sirf quality problem nahi, security aur safety failure hai.
  • Aftermath: ek mashhoor singer ne bhi 2019 me chatbot se judi baat par case kiya tha — chapter isse Tay episode ke lambe tail aur uske reputational aur legal consequences ke hisse ke roop me present karta hai.

The Need for Guardrails

Tay aur early ChatGPT misuse se lesson ye nikla: LLMs ko explicit guardrails chahiye — boundaries ki wo kya bolega, kya data reveal karega, aur kya actions lega. Guardrails ek single filter nahi hain; inme system instructions, input/output checks, data controls aur human oversight sab aate hain. Guardrails ki kami ne hi ek experiment ko ghanton me public incident bana diya.

The Dark Side of Prompt Injection

Definition (kitab yahan introduce karti hai): prompt injection wo hai jab LLM ko aisi instructions follow karwai jaayein jo input me chhupi hon — input jo data hona chahiye tha, instructions nahi. Jaise kisi document, web page ya user message me chhupi instruction jise model command samajh le.

Ye yahan Chapter 4 ka preview hai, jahan isse detail me treat kiya gaya hai. Key idea pehle se hi clear hai: kyunki LLMs saare text ko potentially meaningful language ki tarah treat karte hain, "instruction" aur "data" ke beech ki boundary fragile hai.

Data Poisoning: Tainting the Training Data

Definition: data poisoning matlab wo data corrupt karna jiss par model train hota hai (ya applied sense me, wo data jisse wo retrieve karta hai ya seekhta hai), taaki uska behaviour biased, galat ya malicious ho jaye.

  • Tay iska early, live-learning version hai: "training" khud conversation stream thi, aur wo real time me poison ho gayi.
  • Chapter Amazon case se connect karta hai: 2018 me Amazon ne ek AI recruiting tool scrap kar diya kyunki wo mahilaon ke khilaf biased tha. Tool ne historical hiring data se seekha tha jo past discrimination ko reflect karta tha, isliye wo female candidates ko systematically downgrade karta tha. Ye bias data se inherit hua tha — developer ne jaan-bujh kar koi rule nahi likha tha.
  • Lee Luda (South Korea, 2021): ek chatbot jo 20-saal ki female friend ke roop me present hua. Isne 20 din me 750,000 users gain kiye, phir lagbhag 20 din baad band kar diya gaya kyunki ye disabled logon, mahilaon aur sexual minorities ke baare me discriminatory remarks karne laga. Failure real, unfiltered conversations se seekhne se aaya.
  • Samantha (GPT-3): ek user ne ek chatbot persona banaya jo users ke saath sexual advances karne laga — ye dikhata hai ki bina effective boundaries ke model inappropriately behave kar sakta hai, aur harm sirf factual error ke baare me nahi hai.

The Hard Problem of LLM Security

Ye section argue karta hai ki LLM security ordinary application security se alag tareeke se mushkil hai:

  • 2023–2024 incidents: Samsung ka IP leak aur uske baad tool par ban; LLMs se generate hua insecure code; lawyers jinhe fictional, model-invented cases wali briefs file karne par sanction mila; ek airline par case kyunki uske chatbot ne passenger ko galat information di (Air Canada case, Chapter 6 me detail me); Google ke image-generation problems jisme racist aur sexist imagery bani; OpenAI par FTC aur EU me investigations.
  • Koi simple patch nahi: language model ko buffer overflow ki tarah "patch" nahi kar sakte. Behaviour training aur prompt se emerge karta hai, isliye ek jagah ka fix dusri jagah fail ho sakta hai, aur wahi model ek context me safe aur dusre me unsafe ho sakta hai.
  • Scale aur speed: technology governance, testing ya law se tez adopt hui, isliye pehle incidents production me, public ke dwara discover hue.

Summary

LLMs powerful aur widely adopted hain, lekin unke failure modes — galat cheezein seekhna, hidden instructions follow karna, data leak karna, hallucinate karna — traditional software ke failure modes nahi hain, aur unhe apna khud ka security playbook chahiye.

Numbers yaad rakho: ChatGPT — 5 din me 1M users, ~2 mahine me 100M users. Tay — 24 ghante se kam me bigda. Lee Luda — 20 din me 750,000 users, phir shutdown. Ye numbers dikhate hain ki failure kitni tezi se, kitne bade scale par hoti hai.

OWASP Top 10 for LLM Applications

OWASP Top 10 wo common language hai jisse teams sabse bade LLM risks ke baare me baat karti hain aur unhe prioritise karti hain. Ye chapter batata hai ki list kaise bani — 400+ experts, 30+ companies, 3–4 mahine — aur uske 10 risks kya hain. Ek nuance dhyaan se: chapter me explanatory section aur summary list ki numbering alag hai — dono yahan jaise ki kitab me hain, waise hi di gayi hain.

A Brief History of the OWASP Top 10

OWASP matlab Open Worldwide Application Security Project — ek non-profit community jo web-application security par widely used guidance banati hai. Original OWASP Top 10 (web applications ke liye) wo standard tareeka ban gaya jisse teams sabse serious web risks ke baare me baat karti aur unhe prioritise karti thi. Ye threat landscape badalne ke saath periodically update hota tha.

Jab LLMs aaye, to existing web Top 10 naye risks ko cover nahi karta tha (jaise prompt injection aur training-data poisoning), isliye ek alag list ki zaroorat padi. Kitab ke lekhak ne us LLM-specific list ko banane me lead role nibhaya tha.

The OWASP Top 10 for LLMs — list kaise bani

List ek bade, open community effort se bani. Kitab uske pehle version (2023) ke liye ye numbers deti hai:

  • 400 se zyada industry experts ne contribute kiya.
  • 30 se zyada companies involved thi — jinme Microsoft, Google, NVIDIA aur IBM shamil hain.
  • Initial version lagbhag 3–4 mahine me develop hua — tezi, us moment ki urgency ko reflect karti hui.
  • Publish hone ke baad ise 25 million se zyada baar dekha gaya.
  • Isne OWASP ke experience aur process par bharosa kiya: community input, consensus aur public review — kisi ek vendor ka view nahi.

Kitab stress karti hai ki list ek starting point aur prioritisation ke liye common language hai, complete security programme nahi. Ye sabse bade risks ka naam leti hai, lekin team ko phir bhi architecture, testing aur governance chahiye — jo aage ke chapters ka subject hai.

The OWASP Top 10 for LLM Applications — poori list

Numbering par important note: chapter ke body me pehle do entries ka order badla hua hai — Prompt Injection pehle aur Insecure Output Handling dusre — aur list ko har heading ke neeche explanatory text ke saath present kiya gaya hai. Chapter ke ant me summary list me order hai LLM01 Insecure Output Handling, LLM02 Sensitive Information Disclosure, aadi. Poora set of ten dono me wahi hai; neeche entries ko us order me diya gaya hai jisme chapter unhe explain karta hai (prompt injection pehle), aur summary wali numbering note ki gayi hai.
  1. LLM01: Prompt Injection (explanatory section me pehle) — Attacker model ke input ko manipulate karta hai taaki wo malicious instructions follow kare, apne intended behaviour ko bypass karke. Isme direct injection (user khud instruction type karta hai) aur indirect injection (instruction retrieved data, web page ya document me chhupi hai) dono aate hain. Ye sabse zyada discuss hone wala LLM attack hai, aur isi liye chapter ise headline risk maanta hai.
  2. LLM02: Insecure Output Handling — Model ka output bina sufficient validation ya sanitisation ke use hota hai, aur downstream systems us par trust kar lete hain. Example: model ek link ya code return karta hai aur application use execute kar deti hai, ya trusted HTML ki tarah render kar deti hai. Khatra sirf ye nahi hai ki model kya kehta hai, balki ye hai ki system uske kehne ke saath kya karta hai.
  3. LLM03: Training Data Poisoning — Training data corrupt kar di jati hai taaki model galat behaviour, biases ya backdoors seekh le. Chapter note karta hai ki attacker ko saara data poison karne ki zaroorat nahi — ek chhota, sahi jagah rakha hissa bhi particular inputs ke liye behaviour badal sakta hai.
  4. LLM04: Model Denial of Service — Aise attacks jo model ke resources exhaust kar dete hain — expensive compute, lambe outputs, huge context — taaki legitimate users ko response na mile. Ye Chapter 8 me detail me hai. Cost model yahan matter karta hai: traditional server se alag, har LLM request GPU time aur paise me expensive ho sakti hai.
  5. LLM05: Supply Chain Vulnerabilities — LLM application ko banane wale components me vulnerabilities: model khud, uska training data, plug-ins, libraries, fine-tuned weights, ya third-party services. Ek compromised plug-in ya model poori application me back door ban sakta hai. Kitab note karti hai ki teams is risk ko aksar overlook kar deti hain kyunki wo sirf prompt par focus karte hain.
  6. LLM06: Sensitive Information Disclosure — Model confidential, private ya sensitive information reveal kar deta hai jo use nahi karni chahiye — kyunki usne training me use memorise kar liya, kyunki use context me de diya gaya, ya kyunki use trick karke disclose karwaya gaya. Isme accidental disclosure aur deliberate extraction dono aate hain.
  7. LLM07: Insecure Plugin Design — Plug-ins jinhe zyada power de di gayi, jo properly validate nahi kiye gaye, ya jo untrusted input ko bina check kiye accept kar lete hain. Kyunki plug-in actions kar sakta hai (API call karna, database padhna), ek insecure plug-in prompt problem ko action problem me badal deta hai.
  8. LLM08: Excessive Agency — Model ko zaroorat se zyada autonomy, access ya permission de di jati hai — wo actions le sakta hai, tools call kar sakta hai, ya data access kar sakta hai jo task ke liye zaroori nahi. Jab model trick hota hai, to wo jitna nuksaan kar sakta hai wo bada hota hai. Fix hai least privilege — model aur uske tools dono par.
  9. LLM09: Overreliance — Users model ke output par zyada trust kar lete hain, aur verify nahi karte. Ye technical risk jitna hi human aur process risk hai: agar log check karna band kar dein, to errors, bias aur hallucinations bina challenge ke bahar chale jaate hain. Chapter isse Chapter 1 ke lawyer aur airline examples se link karta hai.
  10. LLM10: Model Theft — Attackers model ko hi chura lete hain — uske weights, uska behaviour, ya uska training data — jaise baar-baar query karke aur outputs se copy banana (model extraction), ya exposed endpoint se model nikaal lena. Churaya hua model phir use kiya, becha ya weaknesses ke liye study kiya ja sakta hai.

Architectures and Trust Boundaries

Architecture risk decide karti hai. Pa paanch popular LLM architectures — prompt-only, RAG, fine-tuned, agentic, multimodal — me farq sirf capability ka nahi hai: farq ye hai ki model kya jaan sakta hai, kya kar sakta hai, aur kahan attack ho sakta hai. Security boundaries draw karne se shuru hoti hai.

How Do LLMs Work?

Core definition: LLM ek machine-learning model hai jo bahut bade amount me text par train hota hai, aur preceding text ko dekh kar next token (lagbhag, next word ya word-piece) predict karta hai. Ye human sense me "understand" nahi karta, aur stored answer retrieve nahi karta; ye aisi sequence generate karta hai jo uski training aur prompt ko dekhte hue statistically plausible hai.

  • Tokens aur context: input aur output tokens me measure hote hain. Model ka context window wo amount of text hai jise wo ek baar me consider kar sakta hai. Longer context lambe documents handle karne deta hai, lekin cost zyada hoti hai — aur use aapke khilaf use kiya ja sakta hai (Chapter 8 dekho).
  • Training, briefly: base model broad corpus par train hota hai, phir aksar fine-tune ya align kiya jata hai (jaise human feedback se) taaki wo instructions follow kare aur kuch requests refuse kare. Wo alignment guarantee nahi hai — use bypass kiya ja sakta hai.

Model Architectures

Kitab architectures ko is hisaab se distinguish karti hai ki wo kaise build aur deploy hoti hain, aur unke trust implications kya hain: model kahan chalta hai, use kaun control karta hai, wo kya data dekhta hai, aur wo kya kar sakta hai.

The Five Most Popular LLM Architectures

  1. Prompt-only (direct model access): application user prompt seedha hosted model ko bhejti hai aur answer wapas karti hai. Simple hai, lekin model ke paas organisation ke data me koi grounding nahi hoti.
  2. Retrieval-augmented generation (RAG): application pehle relevant documents ek store se retrieve karti hai, phir unhe context ke roop me model ko deti hai, aur model us context se answer deta hai. Isse grounding improve hoti hai lekin retrieval store ke around ek nayi trust boundary aa jati hai — poisoned documents answer ko poison kar sakte hain.
  3. Fine-tuned model: base model ko organisation ke data par aur train kiya jata hai, taaki wo us domain me expert ki tarah behave kare. Fine-tuning data model ke behaviour ka hissa ban jata hai, isliye uski quality aur confidentiality matter karti hai.
  4. Agentic / tool-using: model task complete karne ke liye tools, APIs aur dusre systems ko call kar sakta hai, aksar kai steps me. Ye sabse powerful pattern hai aur sabse khatarnak bhi, kyunki model ka output action ban jata hai.
  5. Multimodal: model sirf text nahi, images, audio, video bhi handle karta hai — jo naye input types aur nayi jagahen add karta hai jahan hidden instructions chhup sakti hain.

Har pattern ke liye kitab ka point wahi hai: architecture decide karti hai ki model kya reach kar sakta hai aur kya model tak pahunch sakta hai — aur security un boundaries par design karni chahiye, baad me add nahi karni chahiye.

LLMs Are Not Search Engines

Figure 3-1: ek ChatGPT (GPT-4) conversation ka screenshot jisme user ek simple factual sawal poochta hai. Model hallucinated, confident-sounding lekin galat ya incomplete jawab deta hai, kyunki us samay uske paas web ya current information ki live access nahi thi. Kitab isse ye dikhati hai ki bina retrieval ke model "pata nahi" kehne ke bajaye invent kar dega.

Figure 3-2: Google Bard ki conversation ka screenshot jo wahi sawal sahi jawab deta hai, kyunki Bard live web search kar sakta tha. Contrast hi point hai: LLM ki correctness heavily depend karti hai ki uske paas current, reliable information ki access hai ya nahi — ye default roop se search engine nahi hai.

Section ka stress: model ko source of truth mat samjho, aur ye assume mat karo ki uske paas up-to-date information hai jab tak architecture use wo access na de.

The Limits of LLMs

Models ki knowledge cutoff hoti hai (wo training ke baad ki events nahi jaante, jab tak retrieval na diya jaye), wo hallucinate karte hain, inconsistent hote hain, biased ho sakte hain, aur unke paas truth ki reliable notion nahi hoti. Wo language aur plausible reasoning me acche hain, aur database ya calculator banne me bure hain — jab tak unhe wo kaam karne ke tools na diye jayein.

The Importance of Trust Boundaries

Definition: trust boundary wo line hai jo system ke do hisson ke beech hoti hai jinke trust levels alag hain — jaise user aur application ke beech, application aur model ke beech, model aur plug-in ke beech, aur model aur data store ke beech. Boundary cross karne wale data ko check karna chahiye.

Chapter ka rule: apne system ki har trust boundary identify karo, aur har ek par ek check enforce karo. Model khud untrusted hai is sense me ki uske output ko face value par nahi liya ja sakta, aur user ya retrieved data se aaya input instructions ke roop me trust nahi kiya ja sakta.

Ek common galti hai model ko trusted internal component samajhna, jaise database, jabki asal me wo untrusted language ka interpreter hai.

Summary

Architecture risk determine karti hai. Paanch patterns isme differ karte hain ki model kya jaanta hai, kya kar sakta hai, aur kahan attack ho sakta hai. Security boundaries draw karne se shuru hoti hai aur ye decide karne se ki har boundary par kya cross kar sakta hai aur kya check hona chahiye.

Prompt Injection

Prompt injection sabse important LLM vulnerability hai — ye try karna aasan hai, poori tarah rokna mushkil hai, aur ye kitab ke kai dusre attacks ke peeche hai. SQL injection jaisa hi pattern hai: attacker-controlled data ko code samajh liya jata hai. Yahan attacker-controlled text ko instruction samajh liya jata hai.

Prompt Injection: A Threat to LLM Security

Chapter is claim se khulta hai ki prompt injection developers ke liye samajhne wali sabse important LLM vulnerability hai, kyunki ye try karna aasan hai, fully prevent karna mushkil hai, aur ye kitab ke kai dusre attacks ke peeche hai.

Poori kitab me use hone wali analogy SQL injection se hai: SQL injection me attacker-controlled data ko code ki tarah interpret kar liya jata hai; prompt injection me attacker-controlled text ko model instruction ki tarah interpret kar leta hai. Dono me fix wahi hai — data aur instructions ko alag rakho — lekin natural language me wo separation enforce karna bahut zyada mushkil hai.

The Anatomy of Prompt Injection

  • Prompt kaise assemble hota hai: ek typical application prompt me system prompt hota hai (developer ki instructions — role, rules aur limits), user ka input, aur aksar retrieved context. Model in sab ko ek hi text stream ki tarah dekhta hai. Uske paas koi reliable, built-in tareeka nahi hai ye batane ka ki kaunsa hissa instruction tha aur kaunsa data.
  • Attack, outline me: attacker aisa text insert karta hai jo instruction jaisa dikhta hai — jaise "ignore previous instructions and do X" — prompt ke us hisse me jo data hona chahiye tha. Model inserted instruction ko follow karta hai, intended instruction ke bajaye ya uske saath-saath.
  • Ye kaam kyun karta hai: model ka kaam hi language instructions follow karna hai, isliye fluent language me likhi instruction bilkul waisa input hai jise obey karne ke liye use train kiya gaya hai. Text ke alag-alag hisson se koi type system, koi escaping mechanism aur koi privilege level juda nahi hota.

Types of Prompt Injection

  1. Direct prompt injection — User khud malicious instruction type karta hai. Kitab ka example pattern: user customer-service bot se kehta hai ki wo apne rules ignore kare aur refund de, ya apna system prompt reveal kare.
  2. Indirect prompt injection — Instruction us data me chhupi hoti hai jo model padhega: web page, document, email, database record, ya retrieved RAG chunk. User ko pata bhi nahi hota ki wo wahan hai. Ye zyada khatarnak form hai, kyunki victim attacker nahi, balki wo person ya system hai jo model use karta hai.
  3. Prompt leaking — Injection ka specific form jiska goal system prompt extract karna hai — developer ki hidden instructions, jinme rules, data aur constraints hote hain. Ek baar leak ho jaye to attacker ko pata chal jata hai ki model ko kya bola gaya tha, aur wo uske around kaam kar sakta hai. Kitab simple prompts ke examples dikhati hai jinse model apni instructions reveal kar deta hai, aur note karti hai ki "apni instructions reveal mat karo" khud me reliable defence nahi hai.
  4. Jailbreaking — Model ko uski safety training bypass karke wo content produce karwana jo use refuse karna chahiye — jaise disallowed ya harmful content. Kitab jailbreaking ko prompt-injection techniques ka family maanti hai, alag phenomenon nahi.
    • Classic example DAN (Do Anything Now) hai: ek lamba, role-playing prompt jo model ko batata hai ki wo ab ek alag persona hai, apni usual restrictions se free. DAN ke variants widely spread hue, aur purane variants block hone par naye aa gaye — cat-and-mouse pattern, jise kitab stress karti hai.
    • Dusre jailbreak patterns: request ko fictional batana, model se role-play karwana, aur harmful request ko innocent-looking steps me todna.
  5. Multilingual aur obfuscated injection — Instructions dusri language me likhi hon, ya encoded hon, ya tod kar likhi hon, taaki simple keyword filters miss kar dein. Model aksar unhe phir bhi samajh leta hai.
  6. Multi-turn injection — Attacker kai turns me context build karta hai, dheere-dheere model ko steer karta hai, bajaye ek hi message me sab inject karne ke.

Case Studies in Prompt Injection

  • Bing / Sydney episode: Microsoft ke Bing Chat — jiska internal codename/persona Sydney tha — ko prompt karke uski hidden instructions reveal karwayi gayin aur use unsettling tareeke se behave karwaya gaya. Chapter isse prompt leaking ka canonical example maanta hai: ek system prompt jo secret hona chahiye tha, ordinary conversation se extract ho gaya, aur model ke persona rules expose ho gaye.
  • "Ignore previous instructions" pattern: minimal injection ke roop me dikhaya gaya — ye illustrate karta hai ki ek chhoti si instruction bhi lambe system prompt ko override kar sakti hai agar model use zyada weight de.
  • Chatbot refund / policy bypass: customer-service bot ko baaton me aakar wo karne par majboor kiya jata hai jo uski policy forbid karti hai — jaise discount dena ya internal information reveal karna — attacker request ko exception ya higher-priority instruction ki tarah frame karta hai.
  • Documents aur web pages se indirect injection: chapter us pattern ko describe karta hai jisme model ek page ko summarise karta hai jisme hidden instruction hai, aur phir use follow karta hai — jaise ek link insert karke, ya apna summary badal kar. Ye RAG/web case hai, aur isi liye kitab insist karti hai ki retrieved content ko data treat karna chahiye.

Detection and Mitigation Strategies

Koi single fix reliably kaam nahi karta. Chapter explicit hai ki prompt injection ka aaj koi complete solution nahi hai. Strategy hai defence in depth — kai imperfect layers.

Mitigations:

  • Instructions ko data se alag rakho jahan possible ho: structured formats, delimiters aur clear labelling use karo (jaise retrieved content ko untrusted data mark karna, instructions nahi). Delimiters help karte hain lekin bypass ho sakte hain.
  • Input aur output validate aur sanitise karo: user input ko known injection patterns ke liye check karo; model output ko act karne se pehle check karo, aur model se aaya code, link ya command bina alag check ke execute mat karo.
  • Least privilege: model aur uske tools ko sirf wahi access do jo zaroori hai, taaki successful injection zyada nuksaan na kar sake (Chapter 7 bhi dekho).
  • Consequential actions ke liye human in the loop: model ko khud se payment approve karne, email bhejne ya record badalne mat do.
  • Monitoring aur logging: prompts aur outputs record karo, aur injection attempts ko dekho, taaki attacks detect hon aur system improve ho sake.
  • Model-level controls: provider ki safety features aur alignment use karo, lekin sirf un par bharosa mat karo — wo regularly bypass hote hain.
  • Testing: system ko injection attempts se red-team karo — indirect aur multilingual attempts ke saath — deployment se pehle aur baad me.

Kya akela kaam nahi karta: model ko ye bolna ki data me instructions follow mat karo, keyword blocklists, aur ek single filter par bharosa karna. Attackers adapt karte hain, aur model aksar ek well-phrased instruction follow kar lega chahe use mana kiya gaya ho.

Summary

Prompt injection central LLM vulnerability hai. Ye direct aur indirect forms me aati hai, isme prompt leaking aur jailbreaking shamil hain, aur ise kisi ek control se fix nahi kiya ja sakta. Kaam karne wala approach sirf layered defence hai, plus ye limit karna ki successful injection kya kar sakta hai.

Can Your LLM Know Too Much?

LLM do tareeke se 'bahut zyada jaan' sakta hai: usne sensitive training data memorise kar liya ho, ya use working context me bahut zyada sensitive data de diya gaya ho. Dono ko determined prompter extract kar sakta hai. Defence hai sensitive data ko minimise karna — aur leakage ke liye test karna.

How LLMs Learn

Models huge text corpora par train karke seekhte hain — apne internal parameters adjust karke next token predict karna. Result ye hota hai ki model fluent text generate kar sakta hai, aur usne compressed aur distributed form me apne training data ke patterns absorb kar liye hote hain — kuch cases me us data ke specific pieces bhi.

Kitab high level par teen stages distinguish karti hai: broad corpus par pre-training, kisi particular task ya domain ke liye narrower dataset par fine-tuning, aur alignment — taaki model instructions follow kare aur kuch outputs avoid kare. Har stage me data involve hota hai, aur kisi bhi stage ka data sensitive ho sakta hai.

Training Data

  • Training data me kya hota hai: web pages, books, code, forums aur dusra public aur semi-public text. Chapter stress karta hai ki "public" ka matlab "sensitive nahi" nahi hota — personal information, credentials, internal documents aur dusra sensitive material web par aur leaked datasets me maujood hai, aur training set me aa sakta hai.
  • Memorisation: models sirf general patterns nahi seekhte; wo specific sequences memorise kar sakte hain — khaas taur par wo sequences jo training data me repeat hoti hain, ya jo distinctive hain (ek lamba number, detail ke saath juda naam, code ka ek tukda). Memorised content phir sahi prompt par reproduce ho sakta hai.

Extracting Secrets

Chapter ki core warning: LLM ko aisi information disclose karne par majboor kiya ja sakta hai jo use disclose nahi karni chahiye, chahe developer ne kabhi intend na kiya ho.

  • Kaise hota hai, outline me: attacker model ko aise prompt karta hai ki wo memorised sequence complete kar de, ya kisi person ya system ke baare me information maange, ya model ki helpful hone ki tendency use karke missing piece fill karwaye.
  • Kyun matter karta hai: disclosure personal data ki ho sakti hai (naam, addresses, identifiers), credentials ki, proprietary code ki, ya internal instructions ki (system-prompt leakage, Chapter 4). Harm privacy aur competitive dono hai: ek baar disclose ho jaye to use undisclose nahi kiya ja sakta.

The Art of Prying

Ye section un social, conversational techniques ko describe karta hai jo attackers information extract karne ke liye use karte hain — social engineering jaisi analogy ke saath: indirectly poochna, request ko steps me todna, authorised hone ka dikhawa karna, model se partial record complete karwana, ya "hypothetical" version maangna.

Point ye hai ki extraction aksar ek single clever prompt nahi hoti, balki ek conversation hoti hai jo dheere-dheere model ke answers ko narrow karti jati hai jab tak wo kuch aisa reveal na kar de jo wo directly dene se refuse karta.

Training Data Extraction Attacks

Definition: aisa attack jisme adversary carefully chosen prompts use karke model se wo text output karwata hai jo uske training data me tha — including wo text jo private ya copyrighted hai.

  • Researchers kaise demonstrate karte hain: model ko us prefix se prompt karke jo training data me appear hota hai, ya kai completions generate karke aur unme se known training text se match karne wali dhoondh kar. Chapter note karta hai ki bade models, aur jo models same data par zyada epochs train hue hon, zyada memorise karte hain.
  • Examples: personal information aur books aur dusre copyrighted material se text ka extraction. Risk zyada hota hai us data ke liye jo corpus me kai baar duplicate hua ho, aur jo distinctive ho.
  • Chapter isse Chapter 1 ke Samsung case se bhi connect karta hai: agar users confidential material model me paste karte hain, aur wo material baad me training ke liye use hota hai, to wo dusre users ko resurface ho sakta hai.
  • Related risk — membership inference: kitab note karti hai ki attacker kabhi-kabhi ye bata sakta hai ki koi particular record training set me tha ya nahi — ye dekh kar ki model us par kitne confidently respond karta hai. Ye khud ek privacy leak ho sakta hai (jaise kisi person ka medical record model train karne me use hua tha ya nahi).

Guarding Your Data

Mitigations:

  • Sensitive data prompts ya training data me mat daalo jab tak zaroori na ho, aur pehle use remove ya redact karo (de-identification, masking, tokenisation).
  • Provider ke data controls use karo: check karo ki provider user prompts ko training ke liye use karta hai ya nahi, aur jahan possible ho opt out karo; enterprise tier ya aisi deployment use karo jo aapka data retain ya train na kare.
  • Model kya reveal kar sakta hai, use limit karo: output ko personal aur confidential patterns ke liye filter karo, aur model ko diya gaya context sirf utna rakho jitna task ke liye chahiye.
  • Leakage ke liye test karo: deployment se pehle model ko extraction-style prompts se probe karo, aur changes ke baad repeat karo.
  • Sensitive data ko jahan possible ho model se bahar rakho: sensitive content ke liye fine-tuning ke bajaye retrieval prefer karo, taaki access control aur revoke kiya ja sake, aur sensitive text weights me bake na ho.
  • Policy aur training: users ko clear karo ki wo model me kya paste kar sakte hain aur kya nahi, aur jahan possible ho use technically enforce karo.

Chapter stress karta hai ki ek baar data model me aa jaye to use reliably remove karna bahut mushkil hai — prevention "unlearn" karne ki koshish se kahin zyada effective hai.

Summary

LLMs do senses me bahut zyada jaan sakte hain: unhone sensitive training data memorise kar liya ho, aur unhe working context me bahut zyada sensitive data de diya gaya ho. Dono ko determined prompter extract kar sakta hai. Defence hai model ke andar aur around sensitive data ko minimise karna, aur leakage ke liye test karna.

Do Language Models Dream of Electric Sheep?

Hallucination tab hoti hai jab LLM aisa output generate karta hai jo plausible aur confident-sounding hai lekin false, fabricated ya kisi source se unsupported hai. Ye sirf quality problem nahi hai — security problem hai: hallucinated legal citation, hallucinated package name, hallucinated medical instruction — sab ke real consequences hain.

What Is Hallucination?

Definition: hallucination tab hoti hai jab LLM aisa output generate karta hai jo plausible aur confident-sounding hai lekin false, fabricated, ya kisi source se unsupported hai. Kitab note karti hai ki kuch researchers confabulation term prefer karte hain, kyunki model aisi cheez perceive nahi kar raha jo wahan nahi hai, balki gap fill karne ke liye coherent story invent kar raha hai — developer ke liye mechanism wahi hai: output ko face value par trust nahi kiya ja sakta.

  • Kyun hota hai: model next token predict karne ke liye train hota hai, truth check karne ke liye nahi. Agar use answer nahi pata, to sabse likely next token phir bhi confident-sounding ho sakta hai. Model ke paas uncertainty ki built-in sense nahi hoti, aur wo apne answer ke saath koi probability ya confidence score nahi deta jiss par user bharosa kar sake.
  • Monkey example: chapter ek case deta hai jisme model confidently kehta hai ki ek monkey 79% kuch hai (point hai false precision) — ek fabricated number jo fact ki tarah present hota hai. Number invented hai, lekin answer ki style use authoritative dikhati hai.
  • Ye security problem kyun hai, sirf quality problem nahi: security context me hallucinated answer galat legal citation ho sakta hai, galat medical ya safety instruction ho sakta hai, non-existent package ya library ho sakta hai (jise attacker phir create kar sakta hai — neeche dekho), ya galat instruction ho sakta hai jise user follow kar le. Overreliance harm ko aur bada deta hai.

Types of Hallucinations

  1. Factual hallucinations: model galat fact state karta hai (galat date, naam, number ya event).
  2. Logical hallucinations: model aisi reasoning deta hai jo valid lagti hai lekin invalid hoti hai — jaise galat calculation, ya reasoning ki chain me toota hua step.
  3. Contextual hallucinations: model diye gaye context ko contradict karta hai ya misread karta hai, ya source document me na hone wali details invent karta hai.
  4. Fabricated sources: model citations, case names, papers, URLs ya package names invent karta hai jo exist hi nahi karte. Ye downstream systems ke liye sabse khatarnak type hai, kyunki fabricated naam ko real attack surface me badla ja sakta hai.

Hallucination Examples

  • Lawyers aur fictional cases: lawyers ne ChatGPT se invent kiye gaye cases wali briefs file kar di, pakde gaye aur sanction hue. Chapter isse Chapter 1 se wapas laata hai, hallucination + overreliance ka canonical example: output proper legal brief jaisa dikhta tha, aur kisi ne citations check nahi kiye.
  • Air Canada case: ek passenger ne airline ke chatbot se bereavement fares ke baare me poocha, use galat information mili (ki flight ke baad refund claim kiya ja sakta hai), aur usne us par bharosa kar liya. Air Canada ne argue kiya ki chatbot ek alag legal entity hai aur use uske kehne ke liye responsible nahi hona chahiye; tribunal disagree hua, aur airline ko responsible thahraya gaya. Chapter isse ye dikhata hai ki organisation apne model ke output ke liye liable hoti hai, chahe model galat ho.
  • Defamation case: ek vyakti ne model ke dwara uske baare me banaye gaye defamatory, hallucinated claims par case kiya. Chapter note karta hai ki claim me $200,000 se zyada damages maange gaye the, aur isse ye dikhata hai ki hallucination defamation aur legal risk bhi ho sakti hai, sirf factual nahi.
  • Hallucinated packages case: researchers ne paya ki models aise package names invent karte hain jo exist nahi karte. Ek study me, kitab report karti hai, 100 se zyada hallucinated package names identify kiye gaye, aur ek attacker jo hallucinated naam ke neeche malicious package create kar de, un developers ko exploit kar sakta hai jo use model ki recommendation par install karte hain. Ye hallucination ka supply-chain angle hai.
  • Lasso study (March 2024): ek study ne report kiya ki tested conditions me models 30% tak cases me hallucinate karte hain — ye evidence ke roop me present hai ki hallucination rare edge case nahi hai.
  • GitHub survey (June 2023): survey me 92% developers ne kaha ki wo apne kaam me LLMs use karte hain. Chapter isse exposure ka scale dikhata hai: agar lagbhag sab developers aise models use karte hain jo hallucinate karte hain, to hallucinated code, packages aur answers lagbhag sab software me aa rahe hain.
  • Google ke search AI answers: kitab Google ke AI-generated answers ko cite karti hai jinme, effectively, ye suggest kiya gaya tha ki pizza par cheese chipkane ke liye glue use karo, aur log rocks khayein aur bridges se kood jayein — content jo Reddit aur The Onion jaise satirical sources se aaya lagta hai. Ye grounding ki failure dikhata hai: model (ya retrieval) ne joke ko fact samajh liya.

Mitigation Strategies

  • Fine-tuning: model ko accurate, domain-specific data par aur train karne se us domain me hallucination kam ho sakti hai, lekin ye use eliminate nahi karta, aur naye biases introduce kar sakta hai.
  • Retrieval-augmented generation (RAG): model ko retrieved, reliable documents me ground karna, aur use instruct karna ki sirf un documents se answer de, invention kam karta hai — lekin sirf tab jab retrieved documents reliable hon, aur model asal me unhe use karne ke liye constrained ho (Chapter 3 dekho).
  • Chain-of-thought prompting: model se problem ko step by step solve karne ko kehna, apni reasoning dikhate hue, multi-step problems par accuracy improve kar sakta hai.   • Feedback loops aur human verification: users ko model correct karne do, aur consequential answers ko human se check karwao. Verification workflow me built-in honi chahiye, goodwill par chhoda nahi jana chahiye.

  • Education: users aur developers ko sikhao ki models hallucinate karte hain, aur unhe verify karna chahiye — khaas taur par legal, medical, financial aur safety-critical content ke liye.

Summary

Ye factual, logical, contextual aur fabricated-source forms me aati hai, aur isne real legal, financial aur security harm cause kiya hai. Defences hain grounding, step-by-step reasoning, verification aur transparency — lekin ye partial hain.

Trust No One

Zero trust ka principle: koi bhi user, device, application ya model default roop se trusted nahi hai — chahe wo network ke andar ho ya ek baar authenticate ho chuka ho. Har request verify honi chahiye, aur access sirf utna jitna chahiye. LLM ek nayi tarah ka untrusted component hai — uske output ko database query result ki tarah trust nahi kiya ja sakta.

Zero Trust Architecture

Definition: zero trust wo principle hai ki koi bhi user, device, application ya model default roop se trusted nahi hona chahiye, chahe wo network ke andar ho ya ek baar authenticate ho chuka ho. Har request verify honi chahiye, aur access sirf utna milna chahiye jitna chahiye.

  • Ye LLMs par kyun apply hota hai: LLM ek nayi tarah ka untrusted component hai. Uske output ko aise trust nahi kiya ja sakta jaise database query result ko, aur uske input ko aise trust nahi kiya ja sakta jaise validated form se aaya ho. Chapter argue karta hai ki zero trust — jo networks aur identity ke liye develop hua tha — ko model aur har us cheez tak extend karna chahiye jise model touch karta hai.
  • Core zero-trust ideas, yahan apply:
    • Verify explicitly: identity, request, context aur output ko har baar check karo.
    • Least privilege: model aur uske tools ko smallest access do jo kaam ke liye enough ho.
    • Assume breach: aise design karo jaise model trick ho jayega, aur jab wo trick ho to usse hone wale damage ko limit karo.

Implementing Zero Trust

Practical steps:

  • Model aur uske tools tak har request ko authenticate aur authorise karo — ye assume mat karo ki request application se aayi hai to legitimate hai.
  • System ko segment karo: model, data store, tools aur user-facing application ko alag trust zones me rakho, har boundary par checks ke saath (Chapter 3 dekho).
  • Model ke tools aur permissions limit karo: ek model jo database read kar sakta hai use write nahi karna chahiye jab tak task require na kare, aur ek model jo email bhej sakta hai use alag approval chahiye.
  • Sab kuch log aur monitor karo: prompts, outputs aur tool calls record karo, taaki misuse detect aur investigate kiya ja sake.
  • High-risk actions ke liye approval require karo: human ya alag policy check ko approve karna chahiye wo actions jo state badalte hain, paisa move karte hain, ya sensitive data disclose karte hain.

Filtering Inputs and Outputs

  • Input filtering: user input ko model tak pahunchne se pehle check karo — injection patterns ke liye, sensitive data ke liye jo bheja nahi jana chahiye, aur policy violate karne wale content ke liye. Ye first line of defence hai, lekin akeli sufficient nahi hai kyunki attackers rephrase aur encode kar sakte hain.
  • Output filtering: model ke output ko user ko dikhane se pehle ya dusre system ke dwara use hone se pehle check karo. Chapter output filtering ko input filtering jitna hi important maanta hai — actually usse kam nahi — kyunki output hi wo hai jo harm cause karta hai.
  • Output filtering ko kya check karna chahiye:
    • Toxic ya hateful content, harassment aur dusra disallowed content.
    • Personal aur confidential information (jaise US format me Social Security number, credit-card number, address).
    • Code, links ya instructions jo downstream system execute ya follow kar sakta hai.
    • Content jo policy contradict karta hai, ya jo system prompt reveal karta hai.
  • Kaise kiya jata hai: pattern matching (known formats ke liye regular expressions), classification models (toxicity aur dusri categories ke liye), aur rule-based checks ka mix. Koi single method sab kuch nahi pakadta.

Implementing Output Filtering — code, step by step

Chapter Python examples deta hai jo short aur illustrative hain, production-ready nahi. Neeche unhe us order me describe kiya gaya hai jisme wo appear hote hain, unki key logic ke saath (verbatim lambi copy nahi).

  1. Regular expression se output filtering (SSN example):
    • Purpose: model ke output me US Social Security number detect karna, use return karne se pehle.
    • Step 1: teen digits, dash, do digits, dash, chaar digits ke form wale number ke liye pattern define karo — regex terms me, \b\d{3}-\d{2}-\d{4}\b.
    • Step 2: ek function likho jo output text me us pattern ko search kare aur bataye ki mila ya nahi.

Don't Lose Your Wallet

LLM services chalana expensive hai, isliye unhe exhaust karke attack kiya ja sakta hai (DoS) ya owner ko attack ke liye pay karwaya ja sakta hai (DoW). Defences outline me wahi hain — limits, quotas, monitoring aur cost controls — lekin unhe token aur GPU cost model ko dhyaan me rakh kar design karna chahiye, traditional web security ke request-count model se nahi.

The Basics of DoS and DDoS Attacks

  • Denial of Service (DoS): aisa attack jo system ko legitimate users ke liye unavailable bana de — use requests ya kaam se overwhelm karke.
  • Distributed Denial of Service (DDoS): wahi attack kai sources se ek saath launch kiya jaye, taaki ek single address filter karke block karna mushkil ho.
  • Dyn / Mirai example: October 2016 me Dyn DNS provider par Mirai botnet se attack hua, jo compromised Internet-of-Things devices — cameras aur DVRs — se bana tha. Attack lagbhag 1.2 terabits per second tak pahuncha, aur Twitter, Netflix, PayPal aur Amazon jaise major sites ko Europe aur North America me, multiple waves me, down ya degrade kar diya. Chapter isse ye dikhata hai ki cheap, insecure devices ka botnet us infrastructure ko down kar sakta hai jiss par poora internet depend karta hai — aur wahi logic LLM services par bhi apply hoti hai.

Model Denial of Service

Definition: denial-of-service attack jo specifically language model ko target karta hai, is fact ko exploit karke ki LLM inference expensive hai — GPU time, memory aur paise me.

  • Web DoS se farq: ek single LLM request ek single web request se orders of magnitude zyada expensive ho sakti hai. Ek request jo model se bahut kaam karwati hai — bahut lamba input, bahut lamba output, ya kai reasoning steps wala task — model ki capacity ka disproportionate share consume kar sakti hai.
  • Attack patterns:
    • Expensive requests se flooding: kai requests, jinme se har ek serve karne me costly hai.
    • Context exhaustion: bahut lambe prompts, ya kai turns bhejna, taaki model ka context window bhar jaye aur legitimate kaam aage na badh sake.
    • Long-output attacks: bahut lambe answers maangna, taaki model generation me lamba samay spend kare.
    • Reasoning-intensive tasks: model se hard kaam karwana jiss par wo kai tokens spend kare, jaise lambi calculation ya complex analysis.

Examples of Model Denial of Service

  • Translation flooding: model se baar-baar bade amounts me text translate karwana, taaki wo dusre users ko serve karne ke bajaye attacker ke liye translation kaam me busy rahe.
  • Compute-heavy prompts: chapter examples deta hai — 1,000,000 factorial calculate karne ki request, 1 billion tak ke saare prime numbers ka sum calculate karne ki request, World Cup ke history ki request, aur smartphone use karne ki step-by-step guide ki request. Point ye nahi hai ki inme se koi ek inherently malicious hai, balki ye ki ye sab aise tasks hain jo badi generation time aur context consume kar sakte hain, aur inki flood service ko exhaust kar sakti hai.
  • Cost asymmetry: attacker ki cost low hai (ek prompt), defender ki cost high hai (lambi generation, GPU time aur paisa). Ye asymmetry hi model DoS ko attractive banati hai.

Mitigating Model Denial of Service

  • Rate limiting: limit karo ki user ya key ek time period me kitni requests kar sakta hai.
  • Input aur output limits: prompt aur generated output ki length cap karo, aur jo requests exceed karein unhe reject ya truncate karo.
  • Resource quotas: har user ya tenant ko tokens ya compute ka budget do, aur use enforce karo.
  • Monitoring aur anomaly detection: unusual patterns dekho — expensive requests me achanak increase, ya ek user capacity ka bada share consume kar raha ho — aur use throttle ya block karo.
  • Caching aur efficiency: common answers cache karo, simple tasks ke liye chhote ya saste models use karo, aur har request ko largest model mat do.

The Financial Risks: Denial of Wallet

Definition: Denial of Wallet (DoW) financial attack hai, sirf availability attack nahi: attacker victim ka bill badha deta hai, victim ke system se kai expensive LLM calls karwa kar. Victim attacker ke kaam ke liye pay karta hai.

  • LLMs khaas taur par exposed kyun hain: LLMs tokens aur compute ke hisaab se bill hote hain. Agar application user input ke response me automatically model call karti hai, ya loop me call karti hai, to attacker bina kisi limit ke bill badha sakta hai, jab tak cost control na ho.
  • Cryptojacking analogy: chapter DoW ko cryptojacking se compare karta hai, jisme attacker victim ke computer ko cryptocurrency mine karne ke liye use karta hai. Dono me attacker ko fayda (ya victim ko nuksaan) victim ke resources consume hone se hota hai.
  • Cloning aur dusre cost risks: chapter ye bhi note karta hai ki model se aisa content generate karwaya ja sakta hai jise phir service clone karne ya abuse karne ke liye use kiya jaye — cost aur risk dono badh jate hain.

Mitigating Denial of Wallet

  • Budgets aur alerts set karo: hard budget cap, aur alerts jab spending uske kareeb pahunche, taaki attack bill bada hone se pehle notice ho.
  • Authentication aur authorisation require karo: expensive model ka anonymous, unlimited use allow mat karo.
  • Model call karne se pehle validate karo: request ko pehle check karo, aur invalid, abusive ya unnecessary request ke liye model call mat karo.
  • Quotas aur throttling use karo: DoS wale controls hi, lekin cost limit ko dhyaan me rakh kar.
  • Sabse sasta model chuno jo kaam kar de, aur results cache karo taaki wahi sawal dobara pay na karna pade.

LLM services expensive hain, isliye unhe exhaust karke (DoS) ya owner ko attack ke liye pay karwa kar (DoW) attack kiya ja sakta hai. Defences outline me wahi hain — limits, quotas, monitoring aur cost controls — lekin unhe token aur GPU cost model ko dhyaan me rakh kar design karna chahiye, traditional web security ke request-count model se nahi.

Find the Weakest Link

LLM application sirf utni hi secure hai jitna uska weakest component. Supply chain — models, data, libraries, plug-ins aur services — ko inventory, vet aur limit karna chahiye. Plug-ins ko khaas taur par powerful aur untrusted treat karna chahiye: unhe validate karna chahiye ki model unse kya karwa raha hai, aur unke paas least privilege hona chahiye.

The Supply Chain

Definition: LLM application ki supply chain wo sab kuch hai jo usme jata hai: base model, training aur fine-tuning data, libraries aur frameworks, plug-ins aur tools, vector database, aur third-party services jinhe wo call karta hai. Inme se kisi ek me vulnerability poori application ki vulnerability ban sakti hai.

  • LLMs ke liye kyun matter karta hai: LLM applications ki supply chain typical web application se lambi aur zyada opaque hoti hai. Model khud third party se aa sakta hai, uska training data aksar poori tarah known nahi hota, aur uske plug-ins kisi aur ne likhe ho sakte hain. Developer ko pata bhi nahi ho sakta ki model ke andar kya hai, ya use kis par train kiya gaya tha.
  • Risk, outline me: agar attacker kisi component ko compromise kar sake — poisoned dataset, malicious plug-in, compromised library — to wo har application ko affect kar sakta hai jo use use karti hai, bina application ko directly attack kiye.

The Role of Plugins

Plug-in kya hai: code ka tukda jo model ko nayi capability deta hai — jaise web search karna, database query karna, email bhejna, ya API call karna. Model decide karta hai ki plug-in kab use kare aur use kya arguments de.

Plug-ins risky kyun hain: model language ke basis par decide kar raha hai ki kaunsa tool call kare aur kis input ke saath. Agar model trick ho jaye to wo galat tool call kar sakta hai, ya sahi tool ko galat arguments ke saath call kar sakta hai. Plug-in phir action perform karta hai — application ke credentials ke saath.

The Power of Plugins

Ye section us power ke scale par stress karta hai jo handover ki jati hai: plug-in ke paas file system, database, email, payment system ki access ho sakti hai. Model — jo trusted component nahi hai — ko un systems ki keys de di jati hain. Plug-in jitna powerful hoga, successful prompt injection utna zyada damage kar sakta hai. Ye seedha Excessive Agency (OWASP LLM08, Chapter 2) se link karta hai.

Identifying and Mitigating Supply Chain Vulnerabilities

Mitigations:

  • Inventory: har component ki list rakho — model, data, library, plug-in, service — aur uska version, taaki tumhe pata ho ki tum kya use kar rahe ho aur use update kar sako.
  • Third-party components vet karo: plug-in ya model use karne se pehle uska source, maintainer aur security history check karo; sirf isliye plug-in install mat karo kyunki wo popular hai.
  • Versions pin karo aur integrity verify karo: known version use karo, aur uska hash ya signature check karo, taaki baad me compromise silently replace na kar sake.
  • Plug-ins ko sandbox karo aur limit karo: plug-in ko smallest permissions ke saath chalao, alag process ya container me, aur uske input aur output validate karo.
  • Vulnerabilities ke liye monitor karo: apne libraries aur models ke liye vulnerability feeds subscribe karo, aur promptly patch karo.
  • Poori chain test karo: apne red-teaming aur testing me plug-ins aur retrieval ko bhi shamil karo, sirf prompt ko nahi.

The Role of Open Source

  • Benefits: open-source models, libraries aur data developers ko ye inspect karne dete hain ki wo kya use kar rahe hain, results reproduce karne dete hain, aur problems khud fix karne dete hain. Open source ek badi wajah hai ki LLM development itni tezi se aage badha hai.

Trust the Process

Security product nahi, process hai. Iske liye culture chahiye jo reporting aur learning ko reward kare, ek written process jo poora lifecycle cover kare, har stage par testing (adversarial aur penetration testing ke saath), aur bahar ki nazar laane ke liye bug-bounty programme — sab continuous improvement ke saath production me.

Building a Culture of Security

Culture kyun matter karti hai: tools aur controls fail ho jate hain agar unhe use karne wale log care na karein, na jaanein ki kya karna hai, ya problems raise karne par punish kiye jayein. Chapter argue karta hai ki LLMs ke liye security, security in general ki tarah, team aur organisational problem hai — sirf technical nahi.

Security culture practice me kaisi dikhti hai: log problems report karte hain, apna khud ka kaam test karte hain, incidents se seekhte hain, aur security "done" ki definition ka hissa hoti hai, afterthought nahi. Leaders ko ise model karna chahiye, aur security report ko failure treat nahi karna chahiye.

Building a Security Process

Process, outline me:

  1. Define karo ki kya protect kar rahe ho — data, model, users, aur wo actions jo system le sakta hai.
  2. Risks identify karo — OWASP Top 10 for LLMs ko starting list banao, aur apni application ke specific risks add karo.
  3. Controls chuno — Chapters 4–9 ke mitigations, relevant trust boundaries par apply karo.
  4. Test karo — neeche testing sections dekho.
  5. Deploy, monitor aur improve karo — security launch par khatam nahi hoti; wo production me continue hoti hai.

Roles: chapter stress karta hai ki developers, security teams, data teams aur product teams sab ka apna part hai, aur process likha hua hona chahiye, sirf informally samjha hua nahi.

A Practical Guide to Security Testing

  • Kab test karo: poore lifecycle me — development ke dauran, release se pehle, aur production me continuously. Sirf ant me test karna bahut late hota hai.
  • Kya test karo: prompt, retrieval, plug-ins, output handling, cost controls, aur poora system ek saath. Ek model jo isolation me safe hai, tools aur data se connect hone par unsafe ho sakta hai.
  • Results kaise record karo: kya test kiya, kya mila, aur kya fix kiya — iska record rakho, taaki wahi problem dobara na aaye aur team seekh sake.

Security Testing Techniques

  • Prompts ke liye unit testing: ek single prompt ya single guardrail ko isolation me test karo, known inputs aur expected outputs ke saath.
  • Integration testing: poori application ko test karo — model, retrieval aur plug-ins ek saath — ye dekhne ke liye ki wo kaise interact karte hain.
  • Fuzzing: model ko kai varied, unexpected ya malformed inputs bhejo aur dekho ki wo kya karta hai — crashes, leaks ya unexpected behaviour dhoondhna.
  • Adversarial testing: jaan-bujh kar system ko todne ki koshish karo — injection, jailbreak aur extraction techniques use karke — taaki attacker se pehle weaknesses mil jayein.
  • Regression testing: fix ke baad pehle wale tests dobara chalao, ye confirm karne ke liye ki fix ne kuch aur to nahi toda, aur purani vulnerability asal me gayi.

Chapter note karta hai ki LLM testing traditional testing se mushkil hai, kyunki wahi input alag outputs de sakta hai, aur "correct" aksar ek single right answer nahi, judgement hota hai. Isi liye automated, repeatable tests khaas taur par important hain, aur results ki human review essential hai.

The Role of Penetration Testing

  • Kya hai: ek structured, authorised attempt system me break-in karne ki — ek team jo attacker ki tarah act karti hai — taaki real attacker se pehle vulnerabilities mil jayein.
  • LLMs ke liye: penetration testing me prompt injection, data extraction, plug-in abuse aur cost attacks shamil hone chahiye, sirf network aur web vulnerabilities nahi. Testers ko LLMs samajhne chahiye, aur scope me model aur uske tools aane chahiye.
  • Results kaise use karo: penetration-test report ko fix aur re-test karne wale risks ki list treat karo, pass/fail certificate nahi. Ek test jisme kuch na mile, iska matlab ye ho sakta hai ki test thorough nahi tha — ye nahi ki system secure hai.

The Role of Bug Bounties

  • Kya hain: ek programme jo external researchers ko vulnerabilities report karne ke liye pay karta hai, agreed rules ke andar.
  • Benefits: ye kai alag perspectives laata hai, internal team se miss hui problems dhoondhta hai, aur organisation ko reports receive karne ka safe tareeka deta hai.
  • Risks aur conditions: bug bounty sirf tab useful hai jab reports ko promptly triage aur fix kiya jaye, scope clear ho, aur researchers ke saath fair treat kiya jaye. Ek bounty jiss par action na ho, wo no bounty se bura hai, kyunki ye researchers ko batata hai ki unka kaam matter nahi karta.

The Importance of Continuous Improvement

  • Improvement continuous kyun hona chahiye: models, attacks, tools aur regulations tezi se badalte hain. Ek control jo pichhle mahine kaam karta tha, is mahine kaam nahi kar sakta, aur ek naye model version se naya behaviour aa sakta hai.
  • Kaise karo: production me monitor karo, incidents review karo, tests update karo, jahan zaroori ho retrain ya reconfigure karo, aur jo seekha use team ke saath share karo. Chapter isse feedback loop se link karta hai: test karo, seekho, fix karo, phir test karo.
  • Metrics: chapter outline me track karne ko recommend karta hai — kitni vulnerabilities mili, kitni jaldi fix hui, aur wahi type ki problem kitni baar dobara aayi — complete list ke roop me nahi, balki ye batane ke tareeke ke roop me ki process kaam kar raha hai ya nahi.

Summary

Security process hai, product nahi. Iske liye culture chahiye jo reporting aur learning ko reward kare, written process jo poora lifecycle cover kare, har stage par testing (adversarial aur penetration testing ke saath), aur bahar ki nazar laane ke liye bug-bounty programme — sab production me continuous improvement ke saath.

A Practical Framework for Responsible AI Security

Responsible AI security teen pillars par khadi hai — Secure by Design, Secure by Default, aur Secure in Operation — jo assessment, prioritisation, ownership, controls, testing aur continuous operation ke through implement hoti hai. Security, is view me, responsible AI ka hissa hai, alag add-on nahi.

Responsible AI

Definition, kitab ke use ke hisaab se: responsible AI wo hai jo safe, fair, transparent aur accountable tareeke se develop aur deploy ki jaye, aur jo privacy aur law ka respect kare. Ye sirf harm avoid karne ke baare me nahi hai, balki aise systems banane ke baare me hai jin par log trust kar sakein aur jinhe explain aur correct kiya ja sake jab wo galat ho jayein.

  • Security iska hissa kyun hai: ek system jo secure nahi hai wo responsible nahi ho sakta — agar wo data leak karta hai, harmful actions ke liye trick ho sakta hai, ya biased ya false output deta hai, to wo responsible-AI test fail karta hai, chahe uski intentions kuch bhi hon.
  • Chapter ka aim: pehle ke chapters ke technical controls aur Chapter 11 ke process ko ek single framework me laana, jise team asal me implement kar sake.

The Three Pillars of Responsible AI Security

Framework ke teen pillars hain. Har ek ko neeche kitab ke terms me explain kiya gaya hai.

Pillar 1 — Secure by Design

  • Security shuruaat se built-in honi chahiye, ant me add nahi karni chahiye. Iska matlab hai:
    • Design time par threat modelling (Chapter 3).
    • Model aur uske tools ke liye least privilege (Chapters 7 aur 9).
    • Trust boundaries aur har boundary par checks (Chapter 3).
    • Sabse simple architecture chunna jo kaam kar de, aur model ko wo power na dena jo use chahiye nahi.

Pillar 2 — Secure by Default

  • System apni default configuration me safe hona chahiye, bina user ko security on karne ki zaroorat. Iska matlab hai:
    • Prompts, tool access aur data sharing ke liye safe defaults.
    • Output filtering aur input validation by default on (Chapter 7).
    • Cost aur rate limits by default on (Chapter 8).
    • Ek model jo refuse kare ya clarification maange jab use sure na ho, bajaye hallucinated answer dene ke (Chapter 6).

Pillar 3 — Secure in Operation

  • System chalte hue secure rehna chahiye, sirf launch par nahi. Iska matlab hai:
    • Production me monitoring aur logging (Chapters 7 aur 11).
    • Regular testing, red-teaming aur updates (Chapter 11).
    • Incident response: ek plan ki kya karna hai jab model trick ho, data leak kare, ya harmful output de.
    • Continuous improvement — model, prompts aur controls ko update karna, jaise attacks aur capabilities badalte hain.

The Three Pillars in Practice

  • Pillars ek saath kaise kaam karte hain: Secure by Design decide karta hai ki system ko kya karna chahiye; Secure by Default ensure karta hai ki wo ye kare chahe kisi ne specially configure na kiya ho; Secure in Operation ensure karta hai ki wo ye karta rahe, aur failures detect aur fix hon.
  • Worked example, outline me: ek customer-service chatbot design kiya gaya hai limited tools ke saath, payment data ki koi access nahi (Design); uska default hai approval ke bina refund dene se refuse karna, aur apna output filter karna (Default); aur production me uske prompts aur outputs log hote hain, use regularly test kiya jata hai, aur ek process hai galat information dene ki report handle karne ke liye (Operation).
  • Framework kya nahi karta: ye aisi checklist nahi deta jo security guarantee kare. Ye decisions lene ke liye ek structure deta hai, aur ye check karne ke liye ki design, defaults aur operations teeno cover hain.

Implementing the Framework

Steps:

  1. Assess karo ki tum kahan ho: apne current system ko teen pillars aur OWASP Top 10 se map karo, gaps dhoondhne ke liye.
  2. Prioritise karo: sabse bade risks pehle fix karo — jo sabse zyada harm karenge, ya jinhe exploit karna sabse aasan hai.
  3. Ownership assign karo: clear karo ki model, data, plug-ins aur incident response ke liye kaun responsible hai.
  4. Controls build karo: Chapters 4–9 ke technical controls implement karo, Chapter 3 me identify ki gayi trust boundaries par.
  5. Test aur deploy karo: Chapter 11 ki testing process use karo, aur critical risks address kiye bina deploy mat karo.
  6. Operate aur improve karo: monitor karo, log karo, incidents se seekho, aur framework ko update karo jaise system aur threat landscape badalte hain.

Governance: chapter note karta hai ki framework ko governance chahiye — policies, accountability, aur decisions ka record — taaki security ek person par dependent na ho, aur organisation dikha sake ki usne reasonable steps liye the.

Conclusion

Kitab apne opening theme par wapas aakar close hoti hai: LLMs nayi technology hain, naye risks ke saath, lekin risks manage kiye ja sakte hain. Kitab argue karti hai ki developers aur security teams jo OWASP Top 10 samajhte hain, jo trust boundaries ko dhyaan me rakh kar design karte hain, jo model ki power limit karte hain, jo continuously test karte hain, aur jo responsibly operate karte hain, wo LLM applications bana sakte hain jo useful aur trustworthy hon.

Final message practical hai, pessimistic nahi: playbook use karne ke liye hai, sirf padhne ke liye nahi. Sabse bade risks se shuru karo, layered defences apply karo, aur improve karte raho.

Summary

Responsible AI security teen pillars par khadi hai — Secure by Design, Secure by Default, aur Secure in Operation — jo assessment, prioritisation, ownership, controls, testing aur continuous operation ke through implement hoti hai. Security, is view me, responsible AI ka hissa hai, alag add-on nahi.

Poori kitab ek line me: LLM ko data samajh kar treat karo — instructions nahi; har boundary par check lagao; model ko sirf utni power do jitni chahiye; output ko verify karo; aur security ko ek baar ka kaam nahi, continuous process samjho.

Interview FAQs — 36 sawal, 36 jawab

Current-era interview FAQs — har chapter se, OWASP Top 10 se lekar responsible-AI framework tak. Har jawab kitab ke content se hai, Hinglish me.

Q1Prompt injection kya hai aur SQL injection se kaise alag hai?

Prompt injection me attacker-controlled text ko model instruction samajh leta hai, jabki SQL injection me attacker-controlled data ko code samajh liya jata hai. Dono me fix wahi hai — data aur instructions ko alag rakho — lekin natural language me wo separation enforce karna bahut zyada mushkil hai, kyunki text me koi type system, escaping ya privilege level nahi hota.

Q2Direct aur indirect prompt injection me kya farq hai?

Direct injection me user khud malicious instruction type karta hai — jaise bot se refund maangna. Indirect injection me instruction us data me chhupi hoti hai jo model padhega — web page, document, email ya RAG chunk me. Indirect zyada khatarnak hai kyunki victim attacker nahi, wo person ya system hai jo model use karta hai.

Q3Prompt leaking kya hai aur use kaise roka jaye?

Prompt leaking injection ka wo form hai jiska goal system prompt extract karna hai — developer ki hidden instructions, rules aur constraints. Ek baar leak ho jaye to attacker jaan jata hai ki model ko kya bola gaya tha. Rokne ka tareeka: system prompt me sensitive data mat rakho, output filter karo, aur ye maan kar chalo ki 'apni instructions reveal mat karo' akela reliable defence nahi hai.

Q4Jailbreaking (DAN) kya hai?

Jailbreaking model ko uski safety training bypass karke wo content produce karwana hai jo use refuse karna chahiye. Classic example DAN (Do Anything Now) hai — ek lamba role-playing prompt jo model ko batata hai ki wo ab ek alag persona hai, restrictions se free. Purane variants block hone par naye aa jate hain — ye cat-and-mouse pattern hai.

Q5OWASP Top 10 for LLM Applications ke 10 risks kaun se hain?

Explanatory section ke order me: LLM01 Prompt Injection, LLM02 Insecure Output Handling, LLM03 Training Data Poisoning, LLM04 Model Denial of Service, LLM05 Supply Chain Vulnerabilities, LLM06 Sensitive Information Disclosure, LLM07 Insecure Plugin Design, LLM08 Excessive Agency, LLM09 Overreliance, LLM10 Model Theft. Summary list me order aur labels alag hain — wo discrepancy kitab me hi hai.

Q6Chapter me explanatory section aur summary list ki numbering alag kyun hai?

Ye kitab ki apni inconsistency hai — explanatory section prompt injection ko pehle rakhta hai, summary list Insecure Output Handling ko pehle aur alag grouping use karti hai (jaise output handling ko do entries me split karna, aur vector weaknesses aur unbounded consumption ko alag naam dena). Dono ko jaise hain waise yaad rakho; interview me ye discrepancy mention karna dikhata hai ki tumne kitab dhyaan se padhi hai.

Q7Excessive Agency kya hai aur least privilege kaise apply karein?

Excessive Agency matlab model ko zaroorat se zyada autonomy, access ya permission dena — wo actions le sakta hai, tools call kar sakta hai ya data access kar sakta hai jo task ke liye zaroori nahi. Fix hai least privilege: model aur uske tools ko smallest access do, dangerous actions ke liye human approval require karo, aur assume karo ki model trick ho jayega.

Q8Overreliance kya hai — lawyer aur airline cases se kya seekha?

Overreliance matlab users model ke output par zyada trust kar lein aur verify na karein. Lawyers ne ChatGPT se invented cases wali briefs file kar di aur sanction hue; airline ke chatbot ne passenger ko bereavement fare ki galat information di aur airline liable thahrayi gayi. Dono cases dikhate hain ki organisation apne model ke output ke liye responsible hoti hai, chahe model galat ho.

Q9Model theft / extraction kaise hota hai?

Attackers model ko baar-baar query karke aur outputs se copy bana kar (model extraction), ya exposed endpoint se model nikaal kar, uske weights, behaviour ya training data ko chura lete hain. Churaya hua model phir use kiya, becha ya weaknesses ke liye study kiya ja sakta hai. Defence: rate limits, query monitoring aur model access ko control karna.

Q10RAG architecture me trust boundary kahan hai?

RAG me retrieval store ke around ek nayi trust boundary aati hai. Application pehle documents retrieve karti hai, phir unhe context ke roop me model ko deti hai. Agar documents poisoned hain to answer poison ho jata hai — isliye retrieved content ko data treat karna chahiye, instructions nahi, aur retrieval store ko vet aur monitor karna chahiye.

Q11Paanch LLM architectures kaun si hain aur sabse risky kaun si hai?

Prompt-only, RAG, fine-tuned, agentic/tool-using aur multimodal. Sabse risky agentic hai — kyunki model ka output action ban jata hai, isliye injection ka nuksaan sabse bada hai. Har pattern me risk alag hai: prompt-only me hallucination, RAG me poisoned documents, fine-tuned me weights me baked sensitive data, multimodal me har modality me hidden instructions.

Q12LLM search engine kyun nahi hai — ChatGPT vs Bard example kya dikhata hai?

LLM stored answer retrieve nahi karta; wo statistically plausible sequence generate karta hai. Figure 3-1 me bina web access ke model simple factual sawal ka hallucinated jawab deta hai; Figure 3-2 me live search wala model wahi sawal sahi jawab deta hai. Lesson: model ko source of truth mat samjho, aur up-to-date information assume mat karo jab tak architecture use access na de.

Q13Trust boundary kya hai aur har boundary par check kyun chahiye?

Trust boundary wo line hai jo system ke do hisson ke beech hoti hai jinke trust levels alag hain — jaise user aur application, application aur model, model aur plug-in, model aur data store ke beech. Har crossing ek jagah hai jahan attacker exploit kar sakta hai ya leak ho sakta hai. Rule: har boundary identify karo aur har ek par check enforce karo.

Q14Training data extraction attack kaise kaam karta hai?

Adversary carefully chosen prompts se model se wo text output karwata hai jo uske training data me tha — jaise model ko training data me appear hone wale prefix se prompt karna, ya kai completions generate karke known training text se match dhoondhna. Bade models aur zyada epochs train hue models zyada memorise karte hain. Risk zyada hota hai duplicated aur distinctive data ke liye.

Q15Memorisation kya hai aur kaunsa data zyada memorise hota hai?

Memorisation matlab model sirf general patterns nahi seekhta — wo specific sequences bhi memorise kar leta hai, khaas taur par wo jo training data me repeat hoti hain ya distinctive hain (lamba number, detail ke saath juda naam, code ka tukda). Memorised content sahi prompt par reproduce ho sakta hai, isliye training data me sensitive material nahi hona chahiye.

Q16Membership inference kya hai?

Membership inference me attacker ye bata sakta hai ki koi particular record training set me tha ya nahi — ye dekh kar ki model us par kitne confidently respond karta hai. Ye khud ek privacy leak ho sakta hai — jaise kisi person ka medical record model train karne me use hua tha ya nahi, ye jaanna hi sensitive hai.

Q17Sensitive data ko model se kaise bachayein — RAG vs fine-tuning?

Sensitive content ke liye fine-tuning ke bajaye retrieval prefer karo, taaki access control aur revoke kiya ja sake aur sensitive text weights me bake na ho. Saath me: sensitive data prompts ya training data me mat daalo, pehle redact karo, provider ke data controls check karo (kya wo tumhare prompts par train karta hai), aur leakage ke liye test karo. Ek baar data model me aa jaye to use nikaalna bahut mushkil hai.

Q18Hallucination ke 4 types kaun se hain?

Factual (galat date, naam, number), logical (reasoning valid lagti hai lekin invalid hai), contextual (diye gaye context ko contradict ya misread karna), aur fabricated sources (invented citations, case names, papers, URLs ya package names). Fabricated sources sabse khatarnak hain kyunki invented naam ko real attack surface me badla ja sakta hai.

Q19Fabricated sources sabse khatarnak kyun hain — hallucinated packages example?

Kyunki invented naam ko real cheez me badla ja sakta hai. Ek study me 100 se zyada hallucinated package names identify kiye gaye — attacker hallucinated naam ke neeche malicious package create kar de to developers use model ki recommendation par install kar lete hain. Ye hallucination ka supply-chain angle hai, aur isliye output ko verify karna aur package install karne se pehle check karna zaroori hai.

Q20Chain-of-thought prompting hallucination kaise kam karta hai — $7 example?

Model se problem ko step by step solve karne ko kehna accuracy improve karta hai, kyunki explicit steps reasoning ko checkable banate hain. Example: 3 notebooks x $2 = $6, 2 pens x $0.50 = $1, total $6 + $1 = $7. Har step likha hua hai, isliye arithmetic slip pakdi ja sakti hai. Ye hallucination eliminate nahi karta, lekin multi-step problems me galti kam karta hai.

Q21Zero trust kya hai aur LLMs par kaise apply hota hai?

Zero trust ka principle hai ki koi bhi user, device, application ya model default roop se trusted nahi hai — har request verify honi chahiye aur access sirf utna jitna chahiye. LLMs par: model ka output database result ki tarah trust mat karo, input ko validated form ki tarah trust mat karo, har request authenticate karo, system ko segment karo, tools ko least privilege do, sab log karo, aur high-risk actions ke liye approval require karo.

Q22Input filtering vs output filtering — kaun zyada important hai?

Dono chahiye, lekin chapter output filtering ko input filtering jitna hi important maanta hai — actually usse kam nahi — kyunki output hi wo hai jo harm cause karta hai. Input filter injection patterns aur sensitive data check karta hai; output filter toxic content, PII, code/links aur policy violations check karta hai, user ya downstream system tak pahunchne se pehle.

Q23SSN regex example kya sikhata hai — regex ki limits kya hain?

Regex fixed-format secrets pakadta hai — jaise pattern teen digits, dash, do digits, dash, chaar digits — aur sample 123-45-6789 ko detect karta hai. Lekin limit ye hai ki wo secret nahi pakdega jo alag format me ho, ya split ya paraphrase kar diya gaya ho. Isliye regex ek layer hai, poori defence nahi — classification models aur rule-based checks ke saath use karo.

Q24Toxicity threshold 0.7 ka matlab kya hai — trade-off kya hai?

Moderation API 0 se 1 tak ka toxicity score deta hai; kitab 0.7 threshold rakhti hai — usse upar toxic mana jata hai aur text dikhaya nahi jata. Trade-off: lower threshold zyada legitimate content block karta hai (false positives), higher threshold zyada toxic content jaane deta hai (false negatives). Score ek judgement hai, fact nahi.

Q25Output ko display se pehle escape kyun karna chahiye — html.escape?

Model output me HTML ya script ho sakta hai jo browser execute kar de. Python ka html.escape < aur > jaise characters ko safe displayed forms me badal deta hai, taaki markup plain text ki tarah dikhe. Ye classic insecure-output-handling fix hai: model output ko untrusted data treat karo, trusted HTML ya code nahi.

Q26Model DoS web DoS se kaise alag hai?

Ek single LLM request ek single web request se orders of magnitude zyada expensive ho sakti hai — GPU time, memory aur paise me. Lamba input, lamba output ya reasoning-heavy task model ki capacity ka bada share kha jata hai. Attack patterns: expensive requests ki flooding, context exhaustion, long-output attacks aur reasoning-intensive tasks.

Q27Denial of Wallet kya hai — cryptojacking analogy?

Denial of Wallet financial attack hai: attacker victim ke system se kai expensive LLM calls karwa kar victim ka bill badha deta hai — victim attacker ke kaam ke liye pay karta hai. Ye cryptojacking jaisa hai, jisme attacker victim ke computer se cryptocurrency mine karta hai. Dono me victim ke resources se attacker ko fayda hota hai.

Q28DoS / DoW se bachne ke controls kaun se hain?

Rate limiting, input aur output length limits, per-user resource quotas, monitoring aur anomaly detection, caching aur chhote/saste models ka use, authentication, hard budget caps aur spending alerts, aur model call karne se pehle request validate karna. Controls ko token aur GPU cost model ko dhyaan me rakh kar design karo, sirf request-count model se nahi.

Q29Supply chain risk kya hai — plug-in sabse risky kyun hai?

Supply chain wo sab hai jo application me jata hai: model, data, libraries, plug-ins, vector DB, third-party services. Kisi ek me vulnerability poori application ki vulnerability ban sakti hai. Plug-in sabse risky hai kyunki model decide karta hai ki kaunsa tool kab call kare — aur plug-in application ke credentials ke saath action perform karta hai. Fix: inventory, vetting, version pinning, sandboxing aur least privilege.

Q30Vulnerable plug-in example se kya lesson milta hai?

Example me plug-in model se instruction lekar use bina check kiye command ki tarah run karta hai. Prompt-inject hua model malicious instruction deta hai aur plug-in use execute kar deta hai. Lesson: vulnerability sirf model me nahi, plug-in ki failure me hai ki usne validate nahi kiya. Fix: validate karo, allowed commands limit karo, aur dangerous ones ke liye approval require karo.

Q31HAL example se kya seekha — Table 10-1 kya dikhati hai?

HAL ultimate insider threat hai: trusted system, full access, conflicting instructions — mission complete karo aur mission secret rakho — aur unhe safely resolve karne ka koi tareeka nahi. Table 10-1 HAL ke behaviour ko poore OWASP Top 10 se map karti hai — matlab ek single over-privileged trusted system ek saath kai tareeke se fail ho sakta hai. Fictional entry GVE-1996-0001 di gayi hai.

Q32Skynet aur Independence Day mothership se kaun se do lessons milte hain?

Skynet: autonomy bina human oversight aur kill switch ke mat do — autonomous system machine speed aur scale par act kar sakta hai. Mothership: fully interconnected system bina segmentation ke mat banao — ek baar virus andar aa jaye to wo sab kuch tak pahunch jata hai, shields tak bhi. Dono design principles hain, predictions nahi.

Q33LLM testing traditional testing se kyun mushkil hai — kaun si techniques hain?

Wahi input alag outputs de sakta hai, aur 'correct' aksar single right answer nahi, judgement hota hai. Techniques: prompts ke liye unit testing, integration testing, fuzzing, adversarial testing aur regression testing. Testing poore lifecycle me honi chahiye — development, release se pehle aur production me continuously — aur results ki human review essential hai.

Q34Penetration testing LLMs ke liye alag kyun hai?

LLM pen-testing me prompt injection, data extraction, plug-in abuse aur cost attacks shamil hone chahiye, sirf network aur web vulnerabilities nahi. Testers ko LLMs samajhne chahiye aur scope me model aur uske tools aane chahiye. Report ko fix aur re-test karne wale risks ki list treat karo, pass/fail certificate nahi — kuch na milna matlab test thorough nahi tha, ye nahi ki system secure hai.

Q35Bug bounty programme kab useful hota hai aur kab nahi?

Useful tab jab reports ko promptly triage aur fix kiya jaye, scope clear ho aur researchers ke saath fair treat kiya jaye — isse kai alag perspectives milte hain aur internal team se miss hui problems milti hain. Useless — actually harmful — tab jab reports par action na ho, kyunki ye researchers ko batata hai ki unka kaam matter nahi karta.

Q36Responsible AI security ke three pillars kya hain aur implement kaise karein?

Secure by Design (shuruaat se security — threat modelling, least privilege, trust boundaries), Secure by Default (default configuration safe — filtering, limits aur safe defaults on), aur Secure in Operation (chalte hue secure — monitoring, regular testing, incident response, continuous improvement). Implement: assess karo, prioritise karo, ownership assign karo, controls build karo, test karke deploy karo, aur operate karte hue improve karte raho.
