Yahan koi ek lambi kitaab nahi hai; har topic ke liye duniya bhar ki badi tech companies ke engineers ne jo likha aur bola hai, uske links ek jagah jama kiye gaye hain.

  • System design interview hai? Interview wale part ke notes aur Architecture wale part ke real-world diagrams dekho, phir Talk wale section ki scaling kahaniyan suno.

02Principle — Buniyadi Siddhant

Bade systems se seekhe gaye sabak

Scalability seekhne se pehle kuch buniyadi sach samajh lo — ye wo sabak hain jo bade systems banane walon ne saalon ki mehnat aur galtiyon ke baad likhe hain. Inme se har article ek principle ko gehraai se samjhata hai.

Giant-scale services ka sabak ye hai ki bade system ka design chhote system ko bada karne se nahi banta — uske liye alag soch chahiye: failure ko normal maano, har cheez ko loosely coupled rakho, aur har component ko independently scale hone do.

Achhi API ka design utna hi important hai jitna andar ka code — API ek baar publish ho gayi to use badalna mushkil hota hai, isliye pehle se soch-samajh kar banao: naam saaf rakho, chhota surface rakho, aur galtiyon ko gracefully handle karo.

Chaos engineering ka matlab hai jaan-boojh kar apne system me failure daal kar dekhna ki wo kaise react karta hai — taaki asli failure ke time tumhe surprise na mile. Isi soch se Twelve-Factor App aur Clean Architecture jaise tareeke aaye: config ko code se alag rakho, dependencies saaf rakho, aur business logic ko frameworks se azaad rakho.

Yaad rakhne wali baat: Principle wale articles theory nahi hain — ye bade systems ke andar kaam karne walon ke field notes hain. Interview me jab tum "kyun" ka jawab in principles se doge, to tumhara design sirf diagram nahi, soch lagega.

03Principle — Buniyadi Siddhant

CAP theorem, consistency aur transactions

CAP theorem distributed systems ka sabse important trade-off hai: ek distributed system ek hi time par Consistency, Availability aur Partition tolerance — teeno — poori tarah nahi de sakta. Network partition hone par tumhe chunna padta hai: ya to consistency (har read latest data de) ya availability (har request ka jawab mile). Isi liye databases ko CP ya AP kaha jata hai — dono me se ek side chunni padti hai.

ACID vs BASE isi trade-off ka database wala roop hai. ACID (Atomicity, Consistency, Isolation, Durability) strong guarantees deta hai — banking jaise kaam ke liye sahi. BASE (Basically Available, Soft state, Eventually consistent) availability aur scale ko pehle rakhta hai — social feed, shopping cart jaise kaam ke liye sahi.

Eventual consistency ka matlab hai ki likhne ke turant baad har replica par same data nahi milega, par thodi der me sab sync ho jayenge. Interview me ye batana zaroori hai ki tumhare system me kitni der ki inconsistency chalegi — aur use kaise handle karoge.

Isolation levels batate hain ki ek saath chalne wale transactions ek doosre ko kitna dekh sakte hain — strict level slow par safe hota hai, loose level fast par dirty read jaisi problems la sakta hai. Aur bade clusters me data loss ki probability kabhi zero nahi hoti — isliye replication aur backup ka design pehle se sochna padta hai. Distributed transactions se bachne ke tareeke (sagas, idempotency, outbox pattern) bhi isi liye important hain.

Interview me kaise istemal karein

  • Har design me pehle poochho: consistency chahiye ya availability? Jawab se database aur replication strategy tay hogi.
  • Strong consistency ka matlab hai slow writes aur zyada coordination — cost batana mat bhoolo.
  • Eventual consistency chun rahe ho to batao ki user ko stale data dikhne par kya hoga.

04Principle — Buniyadi Siddhant

Data: SQL vs NoSQL, sharding aur hashing

Data ke liye ek hi database har kaam ke liye sahi nahi hota — isiliye polyglot persistence ka concept hai: alag kaam ke liye alag database. Transactions ke liye relational (SQL), flexible documents ke liye document store, lightning-fast lookups ke liye key-value, aur connections ke liye graph database.

SQL vs NoSQL ka faisla data ke shape aur access pattern par hota hai: fixed schema aur joins chahiye to SQL; horizontal scale aur flexible schema chahiye to NoSQL. Badi companies dono ko saath istemal karti hain — aur is chunav ke peeche ke trade-offs samajhna interview ka favourite sawaal hai.

Sharding ka matlab hai data ko tukdon me baant kar alag-alag machines par rakhna. Range-based sharding me data ki key ke hisaab se range banti hai (jaise user ID 1–1M ek shard par), hash-based me key ko hash karke shard chuna jata hai. Dono ke apne nuksaan hain: range me hot shard banta hai, hash me range queries mushkil hoti hain.

Consistent hashing is problem ka elegant hal hai: nodes ko ek ring par rakho, aur har key ko ring par apne se agle node par bhej do. Node add ya remove hone par sirf uske paas wali keys move hoti hain — poora data dobara distribute nahi karna padta. Isi ke variations (virtual nodes, bounded loads) aaj ke caches aur storage systems me istemal hote hain. Hashing trick se bhi savdhaan raho — hash collisions aur uneven distribution se bade scale par nuksaan hota hai.

05Principle — Buniyadi Siddhant

Stateless, scale-out aur performance ki buniyad

Stateless vs stateful — scale karne ka pehla faisla yahi hai. Stateless server koi session apne paas nahi rakhta, isliye uske aage kitne bhi servers laga do, load balancer kisi ko bhi request de sakta hai. Stateful server ko usi user ki agli request bhi usi ko milni chahiye — isliye state ko bahar nikaal kar cache ya database me rakhna scale karne ka raasta hai.

Scale up vs scale out: scale up matlab ek hi machine ko bada karna (zyada CPU/RAM) — aasan hai par ek limit ke baad mehenga aur risky ho jata hai. Scale out matlab machines ki ginti badhana — sasta aur fault-tolerant, par coordination (consistency, distributed transactions) ki keemat chukani padti hai.

Cache is king: sabse sasta performance improvement aksar caching hota hai — par anti-caching bhi yaad rakho: cache galat ho to stale data, cache stampede aur invalidation ki problems aati hain. Cache kab, kya aur kitni der rakhe — ye teen sawaal har design me poochho.

Latency numbers har engineer ko yaad hone chahiye: memory se data lena nanoseconds ka kaam hai, disk se milliseconds ka, aur network round-trip usse bhi zyada. Ye numbers hi batate hain ki kyun cache, CDN aur batching itne powerful hain. Aur jab system slow ho, to bottlenecks ki list se shuru karo — database, CPU, IO, network — andaza lagane ke bajay measure karo.

Monolith vs microservices: Dono ke apne fayde hain. Monolith se shuru karna aksar sahi hota hai — jab team aur scale badhe, tab boundaries ke hisaab se todna. Pehle din se microservices banana over-engineering hoti hai.

06Principle — Buniyadi Siddhant

Reliability, simplicity aur engineering wisdom

Bade systems banane ka sabse bada sabak ye hai ki failure normal hai — use rokne ki koshish ke saath-saath usse gracefully jhelne ka design bhi chahiye. Partial failures accept karo: ek service down ho to poora system down nahi hona chahiye — degraded mode me chalao, retry with backoff karo, aur user ko saaf batao.

Design for resiliency, self-healing, scale-out aur evolution: ye chaar siddhant har design ke peeche hone chahiye. Resiliency matlab failure se wapas aana; self-healing matlab system khud recover kare; scale-out matlab load badhne par capacity badhana aasan ho; evolution matlab aaj ka design kal ki zaroorat ke hisaab se badal sake.

Over-engineering se bacho: har problem ke liye distributed system mat banao. Solid, proven technologies istemal karo, wheel dobara invent mat karo, aur complexity ko ek jagah jama karne ke bajay baant do. Over-reusing (har cheez ko generic bana dena) bhi utna hi nuksaan karta hai jitna code duplicate karna.

Performance ek feature hai: use end me "optimize kar lenge" keh kar mat chhodo — workflow ka hissa banao, measure karo, aur automate karo. Galtiyon se seekho: badi companies ne apni sabse badi outages ke baad jo postmortem likhe, wo is list me hain — unhe padhna sabse sasti seekh hai.

07Scalability

Microservices aur orchestration

Microservices ka matlab hai ek bade application ko chhote, independent services me todna — har service ka apna data, apni deployment aur apni team. Fayda: har service alag scale ho sakti hai, alag technology istemal kar sakti hai, aur ek service ka failure doosri ko nahi giraata. Keemat: distributed system ki saari mushkilein — network latency, service discovery, distributed transactions, observability.

Orchestration ka matlab hai in services ko chalana aur coordinate karna. Containers (Docker) har service ko ek jaise package me bandhte hain, aur Kubernetes un containers ko deploy, scale aur heal karta hai. Service mesh (jaise Istio) services ke beech ki communication, security aur traffic control sambhalta hai.

Badi companies ke case studies is section me hain — kisne monolith se microservices ki taraf kaise badha, Kubernetes ko production me kaise chalaya, aur kahan microservices ne nuksaan bhi pahunchaya. Domain-oriented design yaad rakho: service boundaries business domains ke hisaab se banao, database tables ke hisaab se nahi.

Interview tip: "Microservices use karenge" kehna kaafi nahi hai — batao ki services ke beech data kaise sync hoga, ek service down ho to kya hoga, aur deployment aur rollback kaise hoga.

08Scalability

Distributed caching

Cache ka matlab hai mehenga kaam ek baar karke uska result saste me dobara dena. Distributed cache me ye result kai machines par baanta jata hai, taaki koi bhi server kisi bhi cached value tak pahunch sake. Bade scale par caching ke bina system chal hi nahi sakta — database har request par hit ho to wo pehla bottleneck banta hai.

Cache strategies: cache-aside (application pehle cache dekhe, miss ho to DB se laa kar cache bhare), write-through (likhte time cache aur DB dono update), write-behind (pehle cache, baad me DB), aur refresh-ahead. Har strategy me staleness aur complexity ka alag trade-off hai.

Eviction aur consistency: cache bhar jaye to kya nikalein — LRU (least recently used), LFU, TTL? Aur jab data badle to cache kaise invalid karein — ye do sawaal har caching design ke centre me hain. Badi companies ke case studies dikhate hain ki kaise cache warming, consistent hashing aur cache smearing se stampede aur hot keys se bacha jata hai.

CDN aur HTTP caching bhi isi ka hissa hai — static content ko user ke paas wale edge server se serve karo, origin tak request hi na jaye. Browser cache, proxy cache aur CDN mil kar page load ko seconds se milliseconds me le aate hain.

Key numbers

  • Cache hit ho to response microseconds me milta hai; database hit ho to milliseconds me — 1000x ka fark ho sakta hai.
  • Cache stampede se bachne ke liye request coalescing aur staggered expiry istemal karo.

Distributed locking

Jab kai servers ek hi resource par ek saath kaam karein, to distributed lock chahiye — ek aisa tareeka jisse ek time par sirf ek hi process us resource ko badal sake. Single machine par ye mutex se ho jata hai; distributed system me iske liye alag service chahiye.

Chubby aur ZooKeeper is kaam ke classic systems hain — ye consensus (Paxos/Raft) ke upar lock service dete hain. Redis se bhi lock banaya ja sakta hai (SETNX + expiry), par usme fencing aur clock skew ki savdhani chahiye — warna do processes ek saath lock pakad sakte hain.

Lock lene se pehle hamesha poochho: kya lock chahiye hi? Kai baar idempotent operations, optimistic concurrency ya queue-based serialization lock se behtar hal hote hain. Lock ka timeout aur dead-lock se bachav design me pehle se rakho.

10Scalability

Distributed tracing aur measuring

Ek request jab 50 microservices se guzarti hai, to ye pata lagana ki time kahan gaya, distributed tracing ke bina namumkin hai. Har request ko ek trace ID milta hai, har service apna span banati hai, aur end me poora timeline dikhta hai — kahan slow hua, kahan error aaya.

Zipkin, Canopy aur aise tools traces collect karke visualize karte hain. Inke saath metrics (StatsD jaise) batate hain ki system overall kaisa chal raha hai — request rate, error rate, latency percentiles. Golden signals yaad rakho: latency, traffic, errors, saturation.

Measure karna isliye zaroori hai kyunki bina measurement ke optimization andaza hota hai. Interview me "kaise pata chalega ki system slow hai?" ka jawab tracing aur metrics se do — na ki "logs dekh lenge" se.

Distributed scheduling

Scheduling ka matlab hai kaam ko sahi time par, sahi machine par chalana. Single machine ka cron aasan hai; distributed system me chahiye ki ek hi job do baar na chale, fail hone par retry ho, aur load sab machines par bante.

Messaging, queuing aur event streaming

Message queues aur event streaming services ko ek doosre se azaad karte hain: producer message bhej kar bhool jata hai, consumer apni speed se process karta hai. Isse system bursty load jhel leta hai, aur ek service down ho to messages queue me safe rehte hain.

Kafka is duniya ka sabse bada naam hai — distributed log ki tarah kaam karta hai: messages ko topics aur partitions me baant kar store karta hai, aur consumers apni offset se padhte hain. Isi liye Kafka streaming, event sourcing aur audit log — teeno ka kaam karta hai.

Event-driven design me har state change ek event hota hai, aur services events par react karti hain. Event sourcing me to events hi source of truth hote hain — current state ko events ko replay karke banaya jata hai. Pub-sub me ek publisher ke message kai subscribers tak jaate hain, bina publisher ko pata chale ki kaun sun raha hai.

Exactly-once delivery practically mushkil hai — aam taur par at-least-once delivery + idempotent consumers ka combination istemal hota hai. Deduplication (idempotency keys, dedup stores) isi liye har messaging design ka hissa hona chahiye.

Queue vs streaming — kab kya?

  • Task queue (jaise email bhejna): message ek baar process ho, phir khatm — simple queue kaafi hai.
  • Event streaming (jaise user activity): events ko dobara padhna ho, kai consumers hon, replay chahiye — Kafka jaisi log-based system chahiye.

Circuit breaker

Circuit breaker ek electrical circuit breaker jaisa hai: jab downstream service baar-baar fail hone lage, to breaker "open" ho jata hai aur requests ko turant fail kar deta hai — bina downstream ko aur load diye. Isse do fayde hote hain: caller ko turant jawab milta hai (timeout ka wait nahi), aur failing service ko recover hone ka time milta hai.

Teen states: closed (sab normal — requests ja rahi hain), open (requests turant fail — fallback chalao), half-open (thodi requests try karo — agar chal gayi to closed, nahi to wapas open). Thresholds (kitne failures par open ho, kitni der baad half-open try kare) ko apne system ke hisaab se tune karo.

Circuit breaker akela kaafi nahi hai — use timeout, retry with backoff aur bulkhead ke saath istemal karo. Aur fallback hamesha rakho: cache se purana data dikhao, ya feature ko gracefully band kar do.

Interview FAQs

36 FAQs — aaj ke era ke system design interviews me poochhe jaane wale sawaal, seedhe jawab ke saath. Sawaal par tap karo, jawab khulega.

01Scalability aur performance me kya fark hai?
Performance ka matlab hai ek user ke liye system kitna fast hai (latency, throughput). Scalability ka matlab hai load badhne par system kaisa behave karta hai — 100 users par fast system 1 lakh users par bhi fast rahe, yahi scalability hai. Ek system fast ho sakta hai par scalable nahi (single machine par optimized), ya scalable ho sakta hai par slow (har request par zyada overhead). Interview me pehle ye diagnose karo ki problem kaunsi hai, phir hal batao.
02CAP theorem ko interview me kaise samjhau?
Simple tareeke se: distributed system me jab network partition ho (machines ke beech connection toote), to tumhe chunna padta hai — ya to consistency (har read latest data de, chahe kuch requests fail hon) ya availability (har request ka jawab mile, chahe data thoda purana ho). Dono ek saath nahi milte. Example do: bank transfer CP chunega, social feed AP chunega. Aur batao ki partition na ho to teeno mil sakte hain — CAP sirf partition ke time ka trade-off hai.
03Consistent hashing kyun use hota hai, simple modulo hashing kyun nahi?
Simple modulo (key % N) me jab node add ya remove ho, to lagbhag saari keys dobara distribute hoti hain — cache to poora khaali ho jata hai. Consistent hashing me nodes aur keys ek ring par hote hain; node badalne par sirf uske paas wali keys move hoti hain (lagbhag K/N keys). Isi liye caches, distributed storage aur load balancers me consistent hashing istemal hota hai. Virtual nodes se distribution aur bhi uniform hota hai.
04Cache-aside, write-through aur write-behind me kya fark hai?
Cache-aside me application pehle cache dekhta hai, miss ho to DB se laa kar cache bharta hai — sabse common, par pehli request slow hoti hai. Write-through me likhte time cache aur DB dono update hote hain — data hamesha fresh, par write slow. Write-behind me pehle cache me likho, DB me baad me — sabse tez write, par crash ho to data loss ka risk. Chunav data ki criticality par karo: paise ka data write-through, feed ka data cache-aside.
05Microservices kab use karne chahiye aur kab nahi?
Microservices tab jab team badi ho, services ko alag scale karna ho, alag deploy cycles hon, ya ek service ka failure doosri ko na giraye. Monolith tab jab team chhoti ho, domain abhi clear na ho, ya system abhi ban raha ho — monolith se shuru karna aasan hota hai aur baad me boundaries ke hisaab se todna behtar hota hai. Pehle din se microservices banana over-engineering hai — distributed system ki saari mushkilein (network, observability, transactions) free me mil jati hain.
06Sharding ke liye shard key kaise chunein?
Shard key wahi chuno jis par tumhare zyada tar queries chalte hain aur jo data ko evenly baante. User_id aksar achha hota hai (har user ka data ek shard par). Range-based se range queries tez hoti hain par hot shard banta hai; hash-based se load uniform rehta hai par range queries mushkil hoti hain. Hamesha data skew ke baare me socho — celebrity users ya bade sheher ek shard ko overload kar sakte hain. Iska hal hai composite key ya sub-sharding.
07Load balancing ke algorithms me se kaunsa kab use karein?
Round robin jab saare servers barabar hon aur saare requests barabar hon. Least connections jab requests ki processing time alag ho (kuch requests bhaari, kuch halki) — jo server khaali hai use request do. Weighted jab servers ki takat alag ho. Consistent hashing jab session stickiness chahiye (same user hamesha same server). Latency-based jab servers alag regions me hon. Interview me algorithm ke saath uski wajah batao.
08Circuit breaker, retry aur timeout — teeno ka kya role hai?
Timeout batata hai ki kab rukna hai (har remote call par limit lagao). Retry batata hai ki fail hone par dobara try karna hai ya nahi (sirf idempotent operations par, backoff + jitter ke saath). Circuit breaker batata hai ki kab try karna hi band kar dena hai (downstream baar-baar fail ho raha ho to use saans do). Teeno mil kar kaam karte hain: timeout ke bina retry hang karega, breaker ke bina retry failing service ko aur gira dega, aur fallback ke bina user ko error ke alawa kuch nahi milega.
09Rate limiting ke liye token bucket fixed window se behtar kyun hai?
Fixed window me window ke end aur start par burst ho sakta hai — jaise 59th second par 100 requests aur 61st second par 100 requests, matlab 2 second me 200 requests jabki limit 100/minute thi. Token bucket me tokens steady rate par refill hote hain aur capacity tak burst allow karta hai, par average rate kabhi limit se zyada nahi hota. Sliding window bhi is problem ko hal karta hai. Distributed rate limiting ke liye shared counter (Redis) ya approximate algorithms istemal hote hain.
10Kafka aur normal message queue (jaise RabbitMQ) me kya fark hai?
Normal queue me message ek baar consume hote hi khatm ho jata hai — ye task distribution ke liye sahi hai. Kafka ek distributed log hai — messages store rehte hain, kai consumers alag-alag offset se padh sakte hain, aur purane messages ko replay kiya ja sakta hai. Isliye Kafka streaming, event sourcing aur audit ke liye behtar hai, jabki simple queue task queue ke liye halki aur aasan hoti hai. Chunav is par karo ki message ko dobara padhna hai ya nahi.
11SQL vs NoSQL — interview me faisla kaise sunau?
Pehle data aur access pattern poochho: fixed schema aur joins chahiye? Strong consistency chahiye? Ya flexible schema, horizontal scale aur high write throughput chahiye? Phir batao: transactions aur relations ke liye SQL, flexible documents ke liye document store, lightning-fast lookups ke liye key-value, relationships ke liye graph. Aur ye bhi batao ki badi companies dono ko saath istemal karti hain (polyglot persistence) — ek database har kaam ke liye nahi hota.
12Eventual consistency ka matlab kya hai aur ye kab chalegi?
Eventual consistency ka matlab hai ki likhne ke turant baad har replica par same data nahi milega, par thodi der me (milliseconds se seconds) sab sync ho jayenge. Ye tab chalegi jab stale data se koi nuksaan na ho — jaise social feed, likes count, product reviews. Nahi chalegi jab galti ki keemat zyada ho — jaise bank balance, ticket booking, inventory. Interview me hamesha batao ki inconsistency kitni der rahegi aur user ko kya dikhega.
13CDN kaise kaam karta hai aur kab use karein?
CDN (Content Delivery Network) static content ko duniya bhar ke edge servers par cache karta hai, taaki user ko content sabse paas wale server se mile — latency kam, origin server par load kam. Images, videos, CSS/JS aur static pages ke liye CDN lagbhag hamesha istemal hota hai. Dynamic content ke liye bhi CDN edge caching aur connection optimization karta hai. CDN chunne ke peeche ka logic hai: data ko user ke paas le jao, user ko data ke paas mat bulao.
14Database replication lag se kaise nipte?
Replication lag ka matlab hai primary par likha data replica par abhi nahi pahuncha. Isse nipatne ke tareeke: critical reads (jaise apni profile edit ke baad) ko primary se padho (read-your-writes consistency), baaki reads replicas se; lag ko monitor karo aur alert lagao; ya semi-sync replication istemal karo jisme replica confirm kare tabhi write success mane. Interview me ye nuance batana important hai — "replica se padh lo" kehna kaafi nahi, lag ka plan bhi batao.
15Autoscaling me kya dhyaan rakhna chahiye?
Pehle, application stateless honi chahiye — naya server aate hi traffic le sake. Doosra, scale-up ka time (cooldown) samjho — server ready hone me minutes lagte hain, isliye sudden spike ke liye predictive scaling ya over-provisioning chahiye. Teesra, scale-down karte time connections gracefully drain karo. Chautha, metrics sahi chuno — CPU ke bajay request queue ya latency par scale karna aksar behtar hota hai.
16Distributed tracing kyun zaroori hai?
Jab ek request 50 microservices se guzarti hai, to bina tracing ke ye pata lagana namumkin hai ki time kahan gaya. Har request ko ek trace ID milta hai, har service apna span banati hai, aur end me poora timeline dikhta hai — kahan slow hua, kahan error aaya. Metrics batate hain ki system kaisa chal raha hai, traces batate hain ki ek khaas request ke saath kya hua. Dono mil kar observability bante hain — logs, metrics, traces, teeno chahiye.
17Failover aur disaster recovery me kya fark hai?
Failover ek automatic process hai — primary fail ho to backup apne aap kaam sambhal le (seconds-minutes). Disaster recovery ek bada plan hai — poora region ya data centre down ho to kaise wapas aayenge (RTO: kitni der me wapas, RPO: kitna data kho sakta hai). Failover ko regular test karna chahiye (drills), warna jab zaroorat padegi tab pata chalega ki wo kaam hi nahi karta. Split-brain se bachne ke liye fencing aur quorum zaroori hain.
18Garbage collection tuning ke liye kya jaanna chahiye?
Pehle ye samjho ki GC pauses tumhare latency ko kaise affect karte hain — p99 latency aksar GC pauses se banti hai. Phir collector chuno: throughput chahiye to parallel, low latency chahiye to concurrent (G1, ZGC). Heap ko sahi size do — bahut chhota heap baar-baar GC karega, bahut bada heap lambi pauses dega. Aur allocation rate kam karo — kam objects banao, to GC ko kam kaam karna padega. Memory leak ko heap growth se pehchano.
19Event sourcing kya hai aur kab use karein?
Event sourcing me current state store nahi ki jati — har change ek event ki tarah store hota hai, aur current state ko events ko replay karke banaya jata hai. Fayda: poora history milta hai, audit aasan hai, aur past ki kisi bhi state ko dobara bana sakte ho. Keemat: complexity, storage, aur events ka versioning. Ye tab use karo jab audit trail ya time-travel zaroori ho (finance, orders) — har system me nahi.
20Exactly-once delivery sach me possible hai?
Practically, pure exactly-once delivery mushkil hai — network me message kho sakta hai ya duplicate ho sakta hai. Aam hal hai at-least-once delivery + idempotent consumers: har message ke saath ek unique idempotency key bhejo, consumer pehle check kare ki ye key process ho chuki hai ya nahi. Kafka me idempotent producer aur transactions se effectively-once milta hai. Interview me ye bolna ki "exactly-once guarantee denge" bina idempotency ke — galat jawab hai.
21Brotli gzip se behtar kyun hai?
Brotli text (HTML, CSS, JavaScript) ko gzip se 15-25% zyada compress karta hai, kyunki isme badi dictionary aur better algorithm hai. Isse page load tez hota hai aur bandwidth bachta hai. Static content par pre-compress karke serve karna sabse faydemand hai. Dynamic content par compression level ko latency ke hisaab se tune karo — zyada compression me CPU zyada lagta hai.
22Big Data platform ke main components kya hote hain?
Chaar hisse: ingestion (data andar lao — Kafka, batch jobs), storage (saste me store karo — HDFS, S3, data lake), processing (compute karo — Spark, Hive, Presto), aur discovery/governance (data catalog, lineage, access control). Inke upar analytics, ML aur experimentation platforms bante hain. Bina discovery aur lineage ke data lake, data swamp ban jata hai — data to hai, par koi dhoondh nahi sakta.
23ML system design me kya alag hota hai?
Normal system design ke upar ML me teen cheezein aur jud jati hain: data pipeline (training data kahan se aayega, kaise saaf hoga), feature store (training aur serving me same features hon), aur model lifecycle (training, evaluation, deployment, monitoring, rollback). Sabse common galti hai training-serving skew — training me jo features the, serving me wahi hone chahiye. Aur data drift par nazar rakho: data badalte hi model ki accuracy girti hai.
24System design interview me framework kaise istemal karun?
Ek fixed framework yaad rakho: 1) Requirements clarify karo (sawaal poochho, scope tay karo), 2) Scale ka andaza lagao (users, reads/writes per second, storage — numbers se), 3) API define karo, 4) High-level design banao (main components aur unke beech data flow), 5) Components me deep dive karo (database schema, caching, sharding), 6) Bottlenecks aur trade-offs batao. Har step par interviewer se confirm karte raho — ye conversation hai, presentation nahi.
25What happens when you type google.com — iska achha jawab kya hai?
Step-by-step batao: DNS lookup (browser cache → OS cache → resolver → root/TLD/authoritative), TCP handshake, TLS handshake, HTTP request, load balancer, web server, application, cache/database, response, browser rendering. Har step par ek trade-off ya detail jodo: DNS caching kyun, TLS me kya hota hai, CDN kahan aata hai, keep-alive kya hai. Ye sawaal isliye poochha jata hai ki tum system ko end-to-end dekhte ho ya nahi.
26Monolith se microservices me migrate kaise karein?
Ek saath poora rewrite mat karo — strangler fig pattern istemal karo: naye features ko alag service ke roop me banao, aur purane monolith ke hisse ko ek-ek karke nikaalte jao, anti-corruption layer ke saath. Pehle wo hisse nikalo jo sabse zyada alag scale hote hain ya alag team ke hain. Har step par monolith aur nayi service saath chalte hain, isliye migration me system kabhi down nahi hota.
27Database sharding aur partitioning me kya fark hai?
Partitioning ek database ke andar data ko tukdon me baantna hai (table partitions) — ye ek machine par bhi ho sakta hai. Sharding partitioning ka distributed roop hai — har shard ek alag machine/database hota hai. Sharding se write throughput aur storage — dono — scale hote hain, par cross-shard queries aur transactions mushkil ho jate hain. Partitioning se query performance sudharti hai (partition pruning) bina distributed complexity ke.
28Observability ke teen pillars kya hain?
Logs (kya hua — events ka record), metrics (kitna hua — numbers over time), aur traces (kahan hua — request ka end-to-end journey). Logs bina structure ke search nahi hote, isliye structured logging (JSON + trace ID) rakho. Metrics se alerts bante hain (golden signals: latency, traffic, errors, saturation). Traces se ek khaas request ki kahani milti hai. Teeno mil kar observability bante hain — koi ek kaafi nahi.
29Backpressure kya hai aur kyun zaroori hai?
Backpressure ka matlab hai jab downstream slow ho, to upstream ko batana ki dheere bhejo — warna queue bhar jayegi aur system crash ho jayega. Iske tareeke: bounded queues (bhar jaye to reject karo), load shedding (kam important requests chhodo), aur rate limiting. Bina backpressure ke ek slow service poore system ko gira deti hai — isiliye har queue aur har buffer ka size soch-samajh kar tay karo.
30Idempotency kyun zaroori hai?
Network unreliable hai — request kho sakti hai, timeout ho sakta hai, ya do baar pahunch sakti hai. Idempotent operation wahi hai jise ek baar chalao ya das baar, result ek hi ho. Payment, booking aur order jaise kaam me idempotency key (unique request ID) bhejo — server pehle check kare ki ye request process ho chuki hai ya nahi. Bina idempotency ke retry karna khatarnak hai — ek payment do baar kat sakti hai.
31Time series database normal database se alag kyun hota hai?
Time series data time ke order me aata hai, purana data rarely badalta hai, aur queries aksar time-range aur aggregation par hoti hain. Time series databases isi pattern ke liye optimize hote hain: time-based partitioning, compression, automatic downsampling aur retention. Metrics aur monitoring ke liye yehi sahi tool hai — general database se ye kaam mehenga aur slow padta hai.
32Code review ko effective kaise banayein?
Review ko chhota rakho (200-400 lines se zyada ek baar me review mat karo), feedback ko constructive aur specific rakho (kya aur kyun), aur automation se repetitive kaam hatao (linting, formatting, tests). Feedback ladders istemal karo — kaunsa comment blocking hai aur kaunsa suggestion, ye saaf batao. Code review ka maqsad sirf bugs pakadna nahi hai — knowledge sharing aur collective ownership bhi hai.
33Scaling teams me sabse badi galti kya hoti hai?
Ye sochna ki team ka size badhana hi scaling hai. Asliyat me scaling ka matlab hai team ka output aur value badhana — jo clear ownership, autonomous teams, achhe tools aur decision-making framework se hota hai. Doosri galti hai communication ko ignore karna — team badhte hi coordination cost badhti hai, isliye docs, RFCs aur clear APIs (teams ke beech bhi) zaroori hain.
34Bulkhead pattern kya hai?
Bulkhead ka naam jahaz se aaya hai — jahaz me alag compartments hote hain taaki ek me paani bhare to poora jahaz na doobe. Software me iska matlab hai resources ko alag karna: alag thread pools, alag connection pools, alag queues — taaki ek dependency ya ek feature ki problem doosre ko na chhooe. Jaise payment service ka thread pool search service se alag ho, to payment slow ho to bhi search chalta rahe.
35Graceful degradation kya hai?
Graceful degradation ka matlab hai jab system par load ya failure aaye, to poora band hone ke bajay kam features ke saath chalta rahe — core kaam chale, fancy features band hon. Jaise recommendations na mile to bhi product page dikhe, ya video ki quality kam ho jaye par playback ruke nahi. Iske liye pehle se tay karo ki kaunse features critical hain aur kaunse optional — aur load shedding ko automate karo.
36Latency numbers har engineer ko kyun yaad hone chahiye?
Kyunki ye numbers hi design ke faisle tay karte hain: L1 cache 0.5ns, RAM 100ns, SSD 150µs, disk 10ms, network round-trip 0.5ms (same data centre) se 150ms (internet). Inse pata chalta hai ki cache kyun 1000x tez hai, network calls kyun batch karne chahiye, aur disk seek kyun avoid karni chahiye. Interview me jab tum kehte ho "cache lagayenge", to ye numbers tumhare faisle ki wajah batate hain.
