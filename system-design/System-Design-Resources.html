Video Processing

Video aaj ke internet ka sabse bada hissa hai — Netflix, YouTube, Facebook Live, sab video par chalte hain. Video processing ka matlab hai: video ko record karna, alag-alag quality me convert karna (transcoding), store karna, aur duniya bhar ke users tak bina rukawat pahunchana. Interview me ye topic isliye poochha jata hai kyunki isme storage, bandwidth, CDN, encoding aur real-time streaming — sab kuch ek saath aata hai.

Samajhne wali pehli baat: raw video bahut bada hota hai. Ek ghante ki HD video bina compress kiye GBs me hoti hai. Isliye video ko chhote-chhote chunks me toda jata hai, har chunk ko alag quality (1080p, 720p, 480p) me encode kiya jata hai, aur user ki internet speed ke hisaab se sahi quality serve ki jati hai — isko adaptive bitrate streaming kehte hain.

Key points — kya seekhna hai

  • Transcoding: ek video ko kai formats aur resolutions me convert karna, taaki har device par chale.
  • Shot-based encoding: Netflix ka tareeka — har scene ki complexity ke hisaab se alag bitrate, taaki quality zyada aur size kam ho.
  • Live broadcasting: live video me delay kam rakhna sabse badi challenge hai — encoding, upload aur distribution pipeline ko milliseconds me kaam karna padta hai.
  • Storage aur CDN: video files ko object storage me rakhna aur CDN ke edge servers se serve karna, taaki user ke paas ka server video de.

Cluster and Workflow Management

Jab hazaaron machines par hazaaron jobs chalte hain, to unhe manage karne ke liye cluster management aur workflow orchestration chahiye hoti hai. Cluster management ka matlab hai: machines ko pool karna, unpar jobs schedule karna, fail hui machine se job dusri machine par bhejna, aur resources (CPU, memory) ko sahi tareeke se baantna. Workflow management ka matlab hai: ek bade kaam ko chhote steps me todna, steps ke beech dependency sambhalna, aur retry/failure handle karna.

Interview me ye topic distributed systems ki gehrai dikhata hai — scheduler kaise kaam karta hai, autoscaling kaise hoti hai, aur ek job fail ho to system kaise recover karta hai. Google, Facebook aur Netflix ke real systems iske best examples hain.

Key points — kya seekhna hai

  • Scheduling: kaunsi job kis machine par chalegi — bin-packing, priority aur fairness ke saath.
  • Autoscaling: load badhe to machines badhao, load ghate to kam karo — Google Autopilot iska classic example hai.
  • Workflow orchestration: Netflix Conductor jaise tools — DAG of tasks, har task ka state, retry aur timeout.
  • Capacity management: pure data center ko ek computer ki tarah dekhna — Meta ka global capacity management isi soch par hai.
  • Container services: Amazon EC2 container service ke peeche ka design — containers ko cluster par chalana.

Intra-Service Messaging

Microservices me services aapas me baat kaise karte hain — yahi intra-service messaging hai. Do tareeke hain: synchronous (ek service dusri ko turant call karti hai, jaise REST/gRPC) aur asynchronous (message queue ke through, jaise Kafka/SQS). Asynchronous messaging system ko loosely coupled banata hai — ek service slow ho ya down ho, dusri apna kaam karti rehti hai.

Is topic me teen cheezein sabse important hain: message queue kya hoti hai, idempotency (ek hi kaam do baar ho jaye to double charge na ho), aur async task computing (bade kaam ko background me chalana).

Key points — kya seekhna hai

  • Message queue: producer message bhejta hai, queue use store karti hai, consumer apni speed se process karta hai — decoupling ka core pattern.
  • Idempotency: payment jaise kaam me ek request do baar aaye to bhi effect ek hi baar ho — idempotency key se.
  • Async computing: user ko turant response do, bhaari kaam background workers ko do — Meta ka async computing isi ka example hai.

Message Queue Antipattern

Database ko message queue ki tarah use karna ek classic antipattern hai — matlab aisa tareeka jo pehli nazar me kaam karta dikhe, lekin scale par system ko barbaad kar de. Kai teams shuruaat me sochti hain: "table me row daal do, worker poll karke uthayega" — lekin database polling, locking aur ordering ke liye bani hi nahi hai.

Interview me ye topic isliye important hai kyunki ye dikhata hai ki aapko pata hai ki har tool ka sahi use kya hai. Database ka kaam data store karna hai; queue ka kaam message deliver karna hai — dono ki guarantees alag hain.

Key points — kya seekhna hai

  • Polling ki cost: worker baar-baar table check karta hai — CPU aur database dono par bekaar load.
  • Locking aur race: do workers ek hi row uthayein to double processing — queue me ye problem built-in solve hoti hai.
  • Ordering aur priority: database me FIFO order aur priority guarantee karna mushkil hai; queue me ye first-class feature hai.
  • Scaling: queue horizontal scale hoti hai; database-as-queue me database hi bottleneck ban jata hai.

Service Mesh

Jab microservices ki ginti sau se hazaar ho jati hai, to service-to-service communication ko manage karna ek alag hi problem ban jata hai — service discovery, load balancing, retries, security, observability. Service mesh iska solution hai: har service ke saath ek sidecar proxy (jaise Envoy) lagta hai, aur saara traffic us proxy se hota hai. Application code ko ye sab pata hi nahi chalta.

Service mesh ke do hisse hote hain: data plane (sidecar proxies — jo traffic handle karte hain) aur control plane (jo proxies ko configure karta hai — routing rules, security policies). Kubernetes ke saath service mesh aaj ka standard hai.

Key points — kya seekhna hai

  • Sidecar pattern: har service ke saath ek proxy container — traffic control, bina code badle.
  • Data plane vs control plane: data plane traffic chalata hai, control plane policy batata hai.
  • Progressive delivery: canary releases aur traffic splitting — nayi version ko pehle 1% users par test karo.
  • mTLS aur security: service-to-service traffic automatic encrypt hota hai.

Distributed File System

Ek machine ki disk bhar jaye to kya karo? Files ko kai machines par baant do — yahi distributed file system hai. Iska kaam hai: files ko chunks me todna, har chunk ki copies (replicas) alag machines par rakhna, aur user ko ek hi filesystem jaisa experience dena — chahe file kahin bhi stored ho. Ceph iska sabse famous open-source example hai, aur Amazon S3 iska cloud version hai.

Interview me S3 se related sawaal aam hain — S3 ka performance kaise badhayein, object expiry kaise kaam karta hai, aur bade files ko kaise handle karein.

Key points — kya seekhna hai

  • Chunking aur replication: badi file ko chhote chunks me todo, har chunk ke 3 copies alag machines par rakho.
  • Metadata management: kaunsi file kahan hai — ye track karna hi sabse mushkil hissa hai.
  • S3 performance: key prefix ko randomise karo taaki load ek partition par na pade; multipart upload se badi files fast upload karo.
  • Object lifecycle: purane objects ko automatically cheaper storage ya delete — expiry rules se.

Time Series Databases

Time series data wo data hai jo time ke saath badalta hai — server metrics, stock prices, IoT sensor readings, user activity. Normal database iske liye slow padti hai kyunki isme writes bahut zyada hote hain aur queries hamesha time-range par hoti hain ("pichle 1 ghante ka CPU usage dikhao"). Time series databases (TSDB) isi ke liye optimise hoti hain: fast writes, time-based compression, aur downsampling.

Pinterest, Uber aur Facebook ne apne TSDB khud banaye — Goku, AresDB aur Gorilla. Inke papers padhna interview me bahut fayda deta hai kyunki ye dikhate hain ki real scale par time series data kaise handle hota hai.

Key points — kya seekhna hai

  • Write-heavy workload: TSDB me reads se zyada writes hote hain — isliye storage engine alag hota hai (LSM-tree based).
  • Compression: time series data me values aapas me milti-julti hoti hain — delta encoding se 10x tak compress hota hai (Gorilla paper).
  • Downsampling: purana data coarse granularity me store karo — 1-second data ko 1-minute averages me badal do.
  • Relational vs NoSQL: kai cases me Postgres jaise relational DB bhi time series ke liye kaam karta hai — TimescaleDB isi idea par hai.

Rate Limiting

Rate limiting ka matlab hai: ek user ya service ek time me kitni requests bhej sakta hai, uski limit lagana. Ye system ko abuse aur overload se bachata hai — agar ek client hazaaron requests bhej de to baaki users ka system slow na ho. Har bade API (Twitter, Stripe, GitHub) me rate limiting hoti hai.

Do concepts yahan sabse important hain: rate limiting algorithms (token bucket, leaky bucket, fixed window, sliding window) aur circuit breaker (jab downstream service fail ho rahi ho to use aur requests bhejna band kar do, taaki wo recover kar sake).

Key points — kya seekhna hai

  • Token bucket: bucket me tokens bharte rehte hain; har request ek token khati hai; bucket khaali ho to request reject — burst allow karta hai.
  • Leaky bucket: requests fixed rate se bahar nikalti hain — burst smooth ho jata hai.
  • Fixed vs sliding window: fixed window me boundary par double burst ho sakta hai; sliding window isse rokta hai.
  • Circuit breaker: failure rate badhe to circuit "open" — requests turant fail, downstream ko saans lene ka time; thodi der baad "half-open" se test.
  • Distributed rate limiting: ek se zyada servers ho to counter kahan rakhein — Redis jaise shared store me.

In Memory Database - Redis

Redis ek in-memory data store hai — data RAM me rehta hai, isliye disk-based database se 100x fast hota hai. Iska use caching, session storage, leaderboards, rate limiting aur message queues me hota hai. Redis sirf key-value store nahi hai — isme strings, lists, sets, sorted sets, hashes aur streams jaise data structures hain.

Interview me Redis se related sawaal aam hain: caching patterns, Redis Cluster kaise kaam karta hai (sharding + replication + failover), aur Redis ko kab use karein aur kab nahi.

Key points — kya seekhna hai

  • Data structures: sorted sets se leaderboard, sets se unique visitors, streams se event log — har problem ke liye sahi structure.
  • Persistence: Redis in-memory hai lekin RDB snapshots aur AOF logs se data disk par bhi save hota hai.
  • Cluster: 16384 hash slots — har key ek slot me, slots nodes par bante hain; node fail ho to replica promote hota hai.
  • Eviction: memory bhar jaye to kaunsi key nikalein — LRU, LFU, ya TTL-based policies.

Network Protocols

System design ki neev network protocols hain — HTTP, TCP, QUIC, WebSockets, WebRTC. Interview me jab aap "browser me URL type karne par kya hota hai" batate ho, to yehi protocols kaam aate hain. Har protocol ka ek trade-off hai: TCP reliable hai lekin slow start hota hai; QUIC/HTTP3 fast hai kyunki handshake kam hai; WebSockets real-time duplex communication dete hain.

Is section me wo papers aur articles hain jo protocols ko depth me samjhate hain — TCP congestion avoidance ka classic paper, HTTP/1.1 vs HTTP/2 ka head-of-line blocking, aur QUIC ka past-present-future.

Key points — kya seekhna hai

  • TCP: 3-way handshake, congestion control (slow start, AIMD), aur head-of-line blocking ki problem.
  • HTTP/2 aur HTTP/3: multiplexing se head-of-line blocking khatm; QUIC UDP par chalta hai, handshake 0-RTT tak kam.
  • WebSockets: ek baar connection bane to dono taraf se real-time messages — chat apps ka backbone.
  • WebRTC: browser-to-browser direct media streaming — video calls bina server ke (signalling ke baad).
  • Dynamic Source Routing: QUIC ke upar routing — Facebook ka research.

Subscription Management System

Subscription system wo hai jo Netflix, Adobe aur Spotify jaise products chalata hai — plans, billing cycles, upgrades/downgrades, trials, renewals aur cancellations. Ye dekhne me simple lagta hai, lekin andar bahut complexity hai: ek user ka plan badle to billing kaise adjust ho (proration), renewal fail ho to retry kaise ho (dunning), aur alag-alag deshon ke tax aur currency kaise handle hon.

Netflix ka rule-based platform iska best real example hai — lakhon SKUs (plans) ko rules se manage karna, bina har plan ke liye alag code likhe.

Key points — kya seekhna hai

  • Plans as data, not code: har plan ke rules (price, features, region) config me hon, code me nahi — naya plan bina deploy ke launch ho.
  • Proration: beech mahine me plan badle to paise ka hisaab — bacha hua time credit, naya plan charge.
  • Dunning: payment fail ho to smart retries — card expire hua to user ko notify, grace period do.
  • Idempotency: renewal ek hi baar charge ho — duplicate charge se bacho (section 03 dekho).

Resources — kya padhna hai

Google Docs

Google Docs jaise real-time collaborative editor ko design karna system design interview ka ek classic sawaal hai. Isme sabse mushkil problem hai: do log ek hi document ko ek saath edit karein to dono ke changes bina conflict ke merge kaise hon? Iska jawab hai Operational Transformation (OT) ya CRDT — aise algorithms jo concurrent edits ko sahi order me lagate hain.

Iske alawa Docs me cursor positions, comments, version history aur offline editing bhi hoti hai — har ek apne aap me ek design problem hai.

Key points — kya seekhna hai

  • Operational Transformation (OT): ek user ka operation dusre ke operation ke context me transform hota hai — taaki dono ka final document ek jaisa ho.
  • CRDT: OT ka modern alternative — conflict-free replicated data types, jahan merge hamesha deterministic hota hai.
  • Real-time sync: WebSockets se har keystroke server tak, phir baaki collaborators tak — milliseconds me.
  • Presence: kaun kahan type kar raha hai — coloured cursors aur selections.

API Design

API design wo skill hai jo har system design interview me kaam aati hai — aapka API kaisa dikhega, yehi aapke design ki pehchan hai. Achha API simple, consistent aur versioned hota hai. REST ke rules (resources, HTTP verbs, status codes), pagination, filtering, idempotency aur rate limiting — sab API design ka hissa hain.

Airbnb ka API design article iska best practical example hai — services ko kaise design karein taaki wo scale par bhi samajhne me aasan rahein. Swagger (OpenAPI) se API ko document karna bhi isi topic me aata hai.

Key points — kya seekhna hai

  • REST principles: resources nouns hon, verbs HTTP methods hon; /users/123/orders jaisa hierarchical design.
  • Versioning: /v1, /v2 — purane clients tode bina API badlo.
  • Pagination aur filtering: badi lists ko cursor-based pagination se do — offset-based slow hota hai.
  • Idempotency: POST ko idempotent banao (idempotency key) taaki retry se duplicate na bane.
  • Documentation: OpenAPI/Swagger se contract pehle likho, code baad me.

NoSQL Database Internals

NoSQL databases kaise kaam karte hain — ye samajhna system design ki gehrai hai. Cassandra, BigTable aur DynamoDB — teeno ke papers distributed systems ke foundation hain. Inme common ideas hain: consistent hashing se data distribution, replication se availability, aur tunable consistency.

DynamoDB ka paper (Amazon Dynamo) to distributed systems ka sabse zyada cite kiya gaya paper hai — isme consistent hashing, vector clocks aur gossip protocol ka use hai. Cassandra ne BigTable ka data model aur Dynamo ka distribution model combine kiya.

Key points — kya seekhna hai

  • Consistent hashing: node add/remove ho to sirf thoda data move ho — ring par nodes aur keys.

Database Replication

Distributed Transactions consistency Patterns

Ek transaction me kai services involved hon to consistency kaise rakhein? Monolith me database transaction kaam karta tha; microservices me 2PC (two-phase commit) bahut slow aur blocking hota hai. Isliye saga pattern aur transactional outbox jaise patterns use hote hain.

  • Transactional outbox: dual-write problem ka solution — DB write aur message publish ek hi transaction me.
  • Idempotency: retry par double effect na ho — har pattern ke saath idempotency chahiye.

Caching system design ka sabse powerful aur sabse zyada poochha jaane wala topic hai. Idea simple hai: baar-baar chahiye hone wala data fast storage (memory) me rakho, taaki database tak na jana pade. Lekin cache ke saath problems aati hain: stale data, cache stampede (cache khaali ho to saari requests database par), aur eviction (memory bhar jaye to kya nikalein).

Uber 40 million reads per second integrated cache se serve karta hai — ye article dikhata hai ki caching ko system ka first-class citizen kaise banayein, na ki baad me lagaya gaya jugaad.

Key points — kya seekhna hai

  • Cache-aside: app pehle cache dekhti hai, miss ho to DB se laati hai aur cache me daalti hai — sabse common pattern.
  • Write-through vs write-back: write-through me har write cache + DB dono me; write-back me pehle cache, baad me DB (fast, lekin data loss ka risk).
  • TTL aur eviction: har key ki expiry; memory bhar jaye to LRU/LFU se nikalo.
  • Cache stampede: popular key expire ho to hazaaron requests ek saath DB par — lock ya early refresh se roko.
  • CDN as cache: static content ko edge par cache karo — section 37 dekho.

Distributed consensus

Distributed consensus ka matlab hai: kai machines ek baat par agree kaise karein — kaun leader hai, kaunsi value sahi hai, kis order me writes hue? Ye distributed systems ki sabse mushkil problem hai, aur iske do famous algorithms hain: Paxos aur Raft. Raft ko isliye banaya gaya tha kyunki Paxos samajhna bahut mushkil tha — Raft understandable hone ke liye design kiya gaya.

Interview me consensus directly kam poochha jata hai, lekin iska use har jagah hota hai — etcd (Kubernetes ka store) Raft use karta hai, aur leader election har distributed system me chahiye hota hai.

Key points — kya seekhna hai

  • Leader election: nodes me se ek leader chuno — leader hi writes accept kare.
  • Quorum: majority (n/2 + 1) nodes agree karein to decision final — minority fail ho to bhi system chale.
  • Log replication: leader apna log followers ko bhejta hai — sabka state ek jaisa rehta hai.
  • Split-brain: network partition me do leaders na ban jayein — quorum isse rokta hai.
  • CAP se rishta: consensus strong consistency deta hai, lekin partition me availability kam hoti hai.

Authorization

Design a social media app like Instagram

Instagram jaisa social media app design karna — ye system design interview ka sabse popular sawaal hai. Core features hain: photo/video upload karna, feed dekhna (jin logon ko follow karte ho unke posts), like aur comment karna, aur explore/search. Scale bahut bada hai — arabon users, har din arabon photos.

Requirements

  • Functional: photo/video upload, feed generation, follow/unfollow, like, comment, search, notifications.
  • Non-functional: feed fast load ho (p99 latency < 500ms), highly available ho, photos kabhi na khoyein (durability), aur bade scale par chale.

Back-of-envelope

  • 500M daily active users, har user roz 2 photos upload kare → 1B photos/day.
  • Har photo average 200KB (compressed) → 200TB/day nayi storage; 5 saal me ~365PB (replication ke saath aur zyada).
  • Feed reads: har user roz 50 baar feed khole → 25B feed requests/day ≈ 300K QPS.

High-level design

  • Upload: client → API server → object storage (S3 jaisa) me original photo; phir async workers alag sizes banate hain (thumbnail, medium, HD) aur CDN par push karte hain.
  • Metadata: photo ki metadata (user, caption, time) relational DB ya wide-column store me.
  • Feed: do tareeke — fanout on write (post hote hi followers ke feed me daal do; celebrities ke liye mushkil) ya fanout on read (feed khulte hi followed users ke posts nikalo). Practical solution: hybrid — normal users ke liye fanout on write, celebrities ke liye fanout on read.
  • Graph: follow relationships ke liye graph store ya sharded relational DB.
  • Cache: hot feeds aur popular photos Redis me; CDN se media serve karo.

Deep dive — kya discuss karo

  • Feed ranking: sirf time order nahi — relevance (interaction history, recency, relationship strength) se rank karo.
  • Celebrity problem: ek celebrity ke 100M followers hon to fanout on write 100M writes karta hai — isliye hybrid approach.
  • Consistency: like ka count eventual consistent chalega; photo upload ke baad turant dikhna chahiye (read-your-own-write).
  • Notifications: async queue se — like/comment par fanout.

Bottlenecks aur trade-offs

Feed generation sabse bada bottleneck hai — precompute (fanout on write) se read fast hoti hai lekin write mehenga; fanout on read se write sasta lekin read slow. Storage cost vs latency ka trade-off hai. Sharding user ID se karo, taaki ek user ka saara data ek shard par ho.

Interview me kya dhyaan rakho

Pehle scope clarify karo — sirf feed aur upload, ya stories/reels bhi? Numbers jaldi nikalo. Celebrity problem zaroor discuss karo — interviewer yahi check karta hai. Feed ranking ka zikr karo, bina ML me ghuse.

Design a seat-booking system like BookMyShow

BookMyShow jaisa seat-booking system — movie ya event ke seats book karna. Is sawaal ki jaan hai concurrency: ek hi seat ko do log ek saath book na kar payein. Baaki sab — movie listings, theatre selection, payment — straightforward hai.

Requirements

  • Functional: movies/events dekhna, theatre aur showtime chunna, seat map dekhna, seat select karke book karna, payment karna, ticket (QR) paana, booking cancel karna.
  • Non-functional: ek seat sirf ek ko mile (strong consistency), booking fast ho, popular movie release par traffic spike handle ho, payment reliable ho.

Back-of-envelope

  • 10M daily users, 5% book karte hain → 500K bookings/day; peak (badi release) par 10x spike → ~60 bookings/sec average, peak par ~600/sec.
  • Har booking ~1KB metadata → 500MB/day — storage chhota hai; scale ka pressure concurrency par hai, storage par nahi.

High-level design

  • Seat inventory: har show ke seats ki state (available / held / booked) — in-memory store (Redis) me rakho taaki lock fast ho.
  • Hold + timeout: user seat select kare to 5-10 minute ke liye hold karo (TTL ke saath); payment ho to booked, timeout ho to release.
  • Booking service: seat hold karne ke liye distributed lock ya atomic operation (Redis SETNX / Lua script) — race condition na ho.
  • Payment: payment gateway se — payment confirm hote hi booking confirm, warna hold release.
  • Read path: movie/theatre listings ko cache karo — ye data rarely badalta hai.

Deep dive — kya discuss karo

  • Race condition: do users ek hi seat select karein — atomic check-and-set se sirf ek ko mile. Database transaction se bhi kar sakte ho, lekin Redis fast hai.
  • Hold expiry: TTL-based — payment na ho to seat wapas aaye. Expiry ke liye background job ya Redis key expiry.
  • Idempotency: payment retry ho to double booking na ho — idempotency key.
  • Waiting list: sold-out show ke liye waitlist — cancellation par notify karo.

Bottlenecks aur trade-offs

Seat state ka strong consistency chahiye — isliye seat inventory ko shard karo (show ID se). Peak load par queue lagao — users ko "waiting room" me rakho taaki system crash na ho. Payment third-party par depend karta hai — timeout aur retry policy saaf rakho.

Interview me kya dhyaan rakho

Concurrency par sabse zyada time do — yahi is sawaal ka core hai. "Seat hold" ka concept zaroor batana. Payment flow ko overcomplicate mat karo — gateway ko black box mano.

Design a ticket booking system like IRCTC

IRCTC jaisa ticket booking system — train tickets book karna. BookMyShow se milta-julta hai, lekin scale aur complexity zyada hai: lakhon trains, waiting list (WL), RAC, tatkal ka flash sale jaisa load, aur refunds. IRCTC duniya ke sabse zyada traffic wale booking systems me se ek hai — tatkal khulte hi lakhon log ek saath aate hain.

Requirements

  • Functional: trains search karna (source-destination-date), berth/seat availability dekhna, ticket book karna, PNR status, cancellation aur refund, tatkal booking, waiting list aur RAC.
  • Non-functional: tatkal par extreme spike handle ho, ek berth ek hi passenger ko mile, payment reliable ho, PNR lookup fast ho.

Back-of-envelope

  • ~1.5M tickets/day; tatkal window (10 baje) par 10 minute me ~200K bookings → ~350 bookings/sec peak, lekin search QPS usse 100x zyada hota hai.
  • Har ticket ~2KB → 3GB/day — storage chhota; problem concurrency aur search ka hai.

High-level design

  • Search: train schedule aur availability ko read-optimised store me rakho — availability ko cache karo, lekin tatkal me cache TTL bahut chhota rakho.
  • Inventory: har train-date ke berths ki state — Redis me atomic counters (available berths per class).
  • Booking flow: berth hold (TTL) → payment → confirm → PNR generate → ticket. Payment fail ho to hold release.
  • Waiting list: confirmed berth na ho to WL number do; cancellation par WL auto-upgrade (background job).
  • Queue: tatkal spike par requests ko queue karo — user ko token number do, "aapki baari aane par" notify karo.

Deep dive — kya discuss karo

  • Tatkal flash sale: queue + rate limiting — sabko ek saath andar mat aane do; virtual waiting room.
  • Berth allocation logic: lower berth preference (senior citizens), same coach me family ko paas ki berth — allocation algorithm.
  • WL/RAC state machine: WL → RAC → Confirmed transitions — background workers se.
  • Refund: cancellation par refund async — payment gateway ko request, status track karo.

Bottlenecks aur trade-offs

Search QPS sabse bada load hai — search ko booking se alag scale karo. Berth inventory ka strong consistency chahiye — sharding train+date se. Tatkal me fairness vs speed ka trade-off — queue se fairness milti hai.

Interview me kya dhyaan rakho

IRCTC ko BookMyShow se alag kya banata hai, wo batana — WL/RAC aur tatkal spike. Ye do cheezein batayi to answer stand out karega.

Design a cloud solution provider like Amazon Web Services

AWS jaisa cloud provider design karna — ye sawaal poori cloud ki samajh mangta hai: compute (EC2), storage (S3), networking (VPC), aur billing — sab ek saath. Interviewer ye nahi chahta ki aap AWS ko dobara banao; wo chahta hai ki aap cloud ke core building blocks aur unke trade-offs samjho.

Requirements

  • Functional: virtual machines launch karna (EC2), object storage (S3), virtual networks (VPC), auto-scaling, load balancing, billing/metering, IAM (access control).
  • Non-functional: multi-tenancy (ek customer dusre ka data na dekhe), high availability (region/zone level), elastic scaling, pay-per-use billing.

Back-of-envelope

  • 1M customers, har customer average 10 VMs → 10M VMs; har VM ka metadata ~1KB → 10GB metadata — control plane ka data chhota hai, asli scale data plane (traffic) ka hai.
  • S3: exabytes of storage — isliye erasure coding aur multi-region replication chahiye.

High-level design

  • Regions aur Availability Zones: har region me 3+ AZs — har AZ alag data center; control plane region-level, data plane AZ-level.
  • Compute (EC2): hypervisor par VMs — placement service decide kare kaunsi VM kis physical host par chalegi (bin-packing + anti-affinity).
  • Storage (S3): objects ko chunks me todo, erasure coding se parity banao, chunks ko alag AZs me rakho.
  • Networking (VPC): software-defined networking — virtual routers, security groups, NAT gateways.
  • Control plane vs data plane: control plane (API, provisioning) slow aur consistent; data plane (traffic) fast aur distributed.
  • Billing: har service usage meter kare — events ko stream karke aggregate karo.

Deep dive — kya discuss karo

  • Multi-tenancy aur isolation: hypervisor isolation, VPC isolation, aur noisy neighbour problem (CPU credits, QoS).
  • Auto-scaling: metrics (CPU, requests) par based — scale-out aur scale-in policies, cooldown.
  • Failure domains: AZ fail ho to traffic dusre AZ me — health checks aur DNS-based failover.
  • IAM: fine-grained permissions — policy evaluation har request par.

Bottlenecks aur trade-offs

Control plane ka scale — lakhon API calls/sec handle karna; isliye control plane ko sharded aur cached rakho. Data plane me network bandwidth bottleneck hoti hai — isliye placement me network locality ka dhyaan rakho. Consistency vs availability: control plane me strong consistency, data plane me eventual.

Interview me kya dhyaan rakho

Poora AWS design mat karo — scope chun lo: "main EC2 + S3 + VPC par focus karta hoon". Regions/AZs ka concept zaroor batana — yahi cloud ka core hai.

Design an analytics system like Google Analytics

Google Analytics jaisa system — websites par lage tracking code se events collect karna, unhe process karke dashboards dikhana: kitne visitors, kahan se aaye, kya kiya. Is sawaal ki jaan hai massive event ingestion — arabon events roz, aur unpar fast aggregations.

Requirements

  • Functional: websites se events collect karna (pageview, click, purchase), real-time aur historical dashboards, funnels aur segments, custom reports, data export.
  • Non-functional: arabon events/day ingest karo, dashboards fast load hon (seconds me), data loss na ho, aur cost control me rahe.

Back-of-envelope

  • 10M websites × average 10K events/day = 100B events/day ≈ 1.2M events/sec.
  • Har event ~500 bytes → 50TB/day raw; 1 saal ka retention → ~18PB (compression ke baad ~5PB).
  • Dashboard queries: har user kuch reports dekhta hai — reads writes se bahut kam hain.

High-level design

  • Collection: websites par JS snippet → tracking pixel/beacon → edge collectors (global, anycast) → Kafka jaisi durable queue.
  • Stream processing: events ko enrich karo (geo, device, bot filter), phir do raaste — real-time path (5-min aggregates) aur batch path (hourly/daily aggregates).
  • Storage: raw events object storage me (cheap); aggregates OLAP store me (ClickHouse/BigQuery jaisa columnar store) — fast queries ke liye.
  • Pre-aggregation: dashboards pehle se compute kiye hue aggregates padhte hain — raw data par query nahi hoti.
  • Sampling: bahut bade accounts ke liye sampled data — 1% sample se bhi trends sahi nikalte hain.

Deep dive — kya discuss karo

  • Lambda architecture: speed layer (real-time, approximate) + batch layer (accurate, delayed) — dono ka merge.
  • Bot filtering: bots ko kaise pehchano — user-agent, behaviour patterns, IP reputation.
  • Sessionization: events ko sessions me jodna — 30-min inactivity se session toot-ta hai.
  • Privacy: PII store mat karo — IP ko anonymise karo (last octet hatana), GDPR compliance.

Bottlenecks aur trade-offs

Ingestion sabse bada bottleneck hai — collectors ko global edge par rakho aur queue se decouple karo. Query latency vs freshness ka trade-off: real-time data approximate hota hai, accurate data delayed. Storage cost vs retention: purana data downsample karo (hourly → daily).

Interview me kya dhyaan rakho

Lambda architecture ka naam zaroor lo — interviewer ko pata chalta hai ki aapne real analytics systems dekhe hain. Pre-aggregation par zor do — "dashboard raw data par query nahi karta" ye line answer ko strong banati hai.

Design an anomaly detection system like PagerDuty

PagerDuty jaisa anomaly detection system — services se alerts aayein, system decide kare ki kaunsa alert serious hai, sahi engineer ko sahi time par notify kare, aur alert storm ko handle kare. Is sawaal me alerting, on-call management aur incident lifecycle — teeno aate hain.

Requirements

  • Non-functional: alert kabhi na khoye (critical alerts ki delivery guarantee), notification seconds me pahunche, alert storm me bhi system chale.

Back-of-envelope

  • 10K customers × 100 services × 10 alerts/day = 10M alerts/day ≈ 120/sec — lekin storm me 100x spike ho sakta hai.
  • Har alert ~1KB → 10GB/day — storage chhota; problem delivery reliability aur deduplication ka hai.

High-level design

  • Ingestion: monitoring tools (Prometheus, Datadog) se webhooks/API se alerts aayein → durable queue (alert kabhi na khoye).
  • Deduplication: same alert baar-baar aaye to ek incident banao — dedup key (service + alert type) se.
  • Grouping: related alerts ko ek incident me jodo — correlation (same service, same time window).
  • Routing: service → escalation policy → on-call schedule — kaun on-call hai, ye schedule se nikalo.
  • Notification: SMS, call, push, email — priority ke hisaab se; acknowledgement na mile to escalate karo (5 min → next person → manager).
  • Suppression: maintenance window me alerts suppress karo — planned downtime par alert na baje.

Deep dive — kya discuss karo

  • Alert fatigue: bahut alerts aayein to engineers ignore karne lagte hain — severity tuning aur grouping se kam karo.
  • Anomaly detection: static thresholds se aage — baseline seekh kar usse deviation par alert karo (section 27 dekho).
  • Delivery guarantee: notification at-least-once — provider fail ho to dusre provider se bhejo (multi-provider).
  • Incident timeline: har action ka audit log — postmortem ke liye.

Bottlenecks aur trade-offs

Alert storm sabse bada risk hai — ek outage par hazaaron alerts aate hain; grouping aur rate limiting se handle karo. Notification latency vs reliability: SMS fast hai lekin costly; push cheap hai lekin unreliable — critical alerts ke liye multi-channel.

Interview me kya dhyaan rakho

Dedup aur escalation — ye do features batana zaroori hai, warna answer generic lagta hai. "Alert kabhi na khoye" — iske liye durable queue ka zikr karo.

Design a payments gateway like Stripe

Stripe jaisa payments gateway — merchants ki websites se payments lena, card networks aur banks se baat karna, aur paise sahi account me pahunchana. Is sawaal ki jaan hai correctness aur security — ek bhi payment double charge na ho, ek bhi payment khoye nahi, aur card details kabhi leak na hon.

Requirements

  • Functional: card payments lena, refunds karna, subscriptions handle karna, webhooks se merchants ko notify karna, fraud detection, multi-currency support.
  • Non-functional: ek payment exactly once process ho, PCI-DSS compliance (card data secure), high availability (payment down ho to business ruk jata hai), aur audit trail har transaction ka.

Back-of-envelope

  • 1M merchants, average 1K payments/day → 1B payments/day ≈ 12K/sec; peak par 5x.
  • Har payment ~2KB metadata → 2TB/day — storage manageable; asli challenge consistency aur fraud detection ka hai.

High-level design

  • API layer: merchants ki requests — idempotency key ke saath (retry par duplicate charge nahi).
  • Payment processing: card details ko tokenise karo (asli card number kabhi store mat karo — PCI scope kam hota hai); token ko card network/bank ko bhejo.
  • Ledger: double-entry bookkeeping — har payment ke do entries (debit + credit) — paise ka hisaab hamesha balance ho.
  • State machine: payment ki states — created → authorised → captured → settled / failed / refunded — har transition logged.

Design a file management system like Amazon S3

Amazon S3 jaisa file management system — unlimited objects store karna, 11 nines (99.999999999%) durability ke saath. Is sawaal ki jaan hai scale aur durability — exabytes of data, aur ek bhi file kabhi na khoye. Section 07 me distributed file system ka intro hai — yahan S3 ka poora design hai.

Requirements

  • Functional: objects upload/download karna (buckets + keys), versioning, lifecycle rules (purana data cheaper storage me), access control, multipart upload, presigned URLs.
  • Non-functional: 11 nines durability, high availability, unlimited scale, aur strong read-after-write consistency (S3 ab ye deta hai).

Back-of-envelope

  • 100 trillion objects, average size 1MB → 100 exabytes — is scale par sirf distributed design chalta hai.
  • Requests: 1M/sec — metadata aur data path ko alag scale karna padta hai.

High-level design

  • Data path: object ko chunks me todo (e.g. 64MB) → erasure coding se parity chunks banao → chunks ko alag drives/AZs par rakho — koi drive fail ho to bhi data recover ho.
  • Metadata: bucket + key → chunk locations — metadata store (distributed, strongly consistent) — yehi S3 ka "brain" hai.
  • Durability: erasure coding + cross-AZ replication — 11 nines isi se aati hai.
  • Multipart upload: badi file ko parts me upload karo — har part alag se, fail ho to sirf wo part dobara.
  • Presigned URLs: temporary access — bina credentials share kiye file download karwao.
  • Lifecycle: rules se objects ko S3 Standard → Infrequent Access → Glacier me bhejo — cost bachao.

Deep dive — kya discuss karo

  • Erasure coding vs replication: 3x replication me 3x storage; erasure coding me ~1.4x storage aur utni hi durability — cost ka bada farak.
  • Consistency: S3 pehle eventual consistent tha, ab strong read-after-write hai — metadata store strong consistency se aati hai.
  • Key design: key prefix se partitioning hoti hai — sequential keys (timestamps) se hot partition banta hai; prefix ko randomise karo.
  • Versioning: har overwrite naya version banaye — accidental delete se bacho.

Bottlenecks aur trade-offs

Metadata store sabse bada bottleneck hai — isliye metadata ko sharded aur cached rakho. Durability vs cost: zyada copies = zyada cost; erasure coding beech ka rasta hai. Latency vs durability: har write ko kai AZs me confirm karna slow hota hai — quorum writes se balance karo.

Design an emailing service like GMail

GMail jaisa emailing service — emails bhejna, receive karna, store karna, search karna aur spam filter karna. Is sawaal me do alag duniya hain: andar ka system (storage, search, labels) aur bahar ki duniya (SMTP protocol se dusre providers se baat karna).

Requirements

  • Functional: email compose/send karna, inbox dekhna, labels aur folders, search karna, attachments, spam filtering, threads (conversations).
  • Non-functional: email kabhi na khoye, search milliseconds me ho, spam 99%+ pakda jaye, aur 15GB+ storage per user ho.

Back-of-envelope

  • 1.5B users, har user roz 20 emails receive kare → 30B emails/day ≈ 350K/sec.
  • Har email average 50KB (attachments ke saath) → 1.5PB/day — storage ka scale bahut bada hai; attachments ko dedupe karo (same file dobara store mat karo).

High-level design

  • SMTP gateway: bahar se emails SMTP se aayein — receive karo, spam check karo, phir user ke mailbox me daalo.
  • Storage: emails ko sharded store me rakho (user ID se) — metadata (from, to, subject, date) alag, body aur attachments object storage me.
  • Search: inverted index (Elasticsearch jaisa) — har user ka index alag shard par.
  • Spam filtering: ML models + rules — sender reputation, content analysis, user feedback (spam button se training).
  • Threads: subject aur references headers se emails ko conversation me jodo.
  • Attachments: content-hash se dedupe karo — 100 logon ko same file aayi to ek hi copy store ho.
  • Send path: user send kare → queue → SMTP se recipient ke provider ko bhejo → retry with backoff (recipient down ho to).

Deep dive — kya discuss karo

  • Spam: precision vs recall — genuine email spam me jaye to bura; spam inbox me aaye to bhi bura. User feedback loop se model improve karo.
  • Search at scale: har user ka alag index — query sirf uske shard par chalti hai.
  • Delivery guarantees: email khoye nahi — queue durable ho, retries hon, aur bounce notifications hon.
  • Labels vs folders: ek email kai labels me ho sakta hai — labels zyada flexible hain.

Bottlenecks aur trade-offs

Storage cost sabse bada hai — dedup aur compression se bachao. Spam filtering me latency vs accuracy — synchronous check fast hona chahiye, heavy ML async me. Search index ka freshness — nayi email turant search me aani chahiye (near-real-time indexing).

Interview me kya dhyaan rakho

SMTP ka zikr karo — bahar ki duniya se baat karne ka protocol. Spam filtering aur search — ye do features batana zaroori hai, warna answer generic email client jaisa lagega.

  • Ads: live stream me ads insert karna — server-side ad insertion (SSAI) se, segment level par.

Bottlenecks aur trade-offs

61Interview FAQs

Interview FAQs

System design interviews me sabse zyada poochhe jaane wale 36 sawaal — har sawaal par click karo, jawab khulega.

Q01System design interview me sabse pehle kya karna chahiye?

Pehle requirements clarify karo — interviewer se poochho ki kaunsa feature in-scope hai, kitne users hain, aur kya constraints hain. Bina scope samjhe design shuru karna sabse badi galti hai. 5 minute clarification me lagana bilkul sahi hai — interviewer ko pata chalta hai ki aap soch kar design karte ho, guess karke nahi.

Q02Back-of-envelope estimation me kaunse numbers yaad rakhne chahiye?

Ye approximations yaad rakho: 1M requests/day ≈ 12 requests/sec; 1KB = 1000 bytes (approx); 1 char ≈ 1 byte; 1 photo ≈ 200KB; 1 video minute ≈ 10MB (HD); 1 day = 86400 seconds; 1 month ≈ 30 din; 1 saal ≈ 365 din. Peak traffic average ka 2-3x hota hai — design hamesha peak par karo. Storage ke liye replication factor (3x) jodna mat bhoolo.

Q03SQL vs NoSQL — kab kaunsa chunna hai?

SQL chunno jab data structured ho, relationships hon, aur ACID transactions chahiye hon (payments, orders, bookings). NoSQL chunno jab scale bahut bada ho, schema flexible ho, aur eventual consistency chalegi (feeds, sessions, time-series data, catalogs). Interview me dono ka trade-off batana — ek ko 'best' mat kaho, use case ke hisaab se chuno.

Q04Caching me cache-aside aur write-through me kya farak hai?

Cache-aside me app pehle cache dekhti hai, miss ho to DB se laati hai aur cache me daalti hai — writes seedhe DB me jate hain. Write-through me har write pehle cache me phir turant DB me jata hai — dono hamesha sync rehte hain. Cache-aside read-heavy systems ke liye best hai; write-through tab jab data loss bilkul nahi chalega aur cache hamesha fresh hona chahiye.

Q05Load balancer L4 aur L7 me kya farak hai?

L4 load balancer transport layer (TCP/UDP) par kaam karta hai — IP aur port dekh kar decide karta hai, bahut fast hota hai. L7 load balancer application layer (HTTP) par kaam karta hai — URL, headers aur cookies dekh kar smart routing karta hai (jaise /api ko ek pool, /static ko dusre pool). L7 zyada flexible hai lekin thoda slow; L4 zyada fast lekin kam smart.

Q06CAP theorem ko interview me kaise samjhau?

CAP kehta hai: network partition ke time Consistency aur Availability me se ek chunna padta hai — dono ek saath nahi mil sakte. Partition nahi hai to teeno mil sakte hain. Interview me ye batana: payment system me consistency chunenge (paise galat nahi hone chahiye), social feed me availability chunenge (feed thodi stale chalegi). Har system ka CAP choice uske use case se aata hai.

Q07Consistent hashing kya hai aur kyun zaroori hai?

Consistent hashing me nodes aur keys ek hi ring par hote hain — har key us node par jati hai jo ring par uske baad aata hai. Node add ya remove ho to sirf uske paas wali keys move hoti hain (lagbhag 1/N data), jabki normal hashing (key % N) me N badalte hi lagbhag saara data move hota hai. Caching, distributed storage aur load balancing me yehi use hota hai. Lab 7 me live simulate karke dekho.

Q08Message queue aur pub-sub me kya farak hai?

Message queue me ek message ek hi consumer ko milta hai (competing consumers) — task distribution ke liye hai. Pub-sub me ek message saare subscribers ko milta hai — event notification ke liye hai. Queue me message process hote hi delete ho jata hai; Kafka jaisi log-based systems me messages retention tak rehte hain aur replay ho sakte hain. Lab 6 me apne use case ke hisaab se decide karke dekho.

Q09Database sharding kaise karte hain aur kya problems aati hain?

Sharding me data ko kai database servers par baantte hain — shard key (jaise user ID) se decide hota hai kaunsa data kis shard par jayega. Problems: cross-shard queries slow hoti hain (joins nahi chalte), rebalancing mushkil hota hai (shard add karne par data move karna), aur hot shard ban sakta hai (ek celebrity ka data ek shard par). Range-based sharding se hot spots bante hain; hash-based se distribution barabar hoti hai lekin range queries mushkil hoti hain.

Q10Rate limiting ke algorithms kaunse hain?

Chaar main algorithms hain: Token Bucket (bucket me tokens bharte hain, burst allow karta hai), Leaky Bucket (fixed rate se requests bahar nikalti hain, burst smooth hota hai), Fixed Window Counter (har minute me N requests — window boundary par double burst ki problem), aur Sliding Window Log/Counter (boundary problem solve karta hai). Token bucket sabse popular hai. Distributed rate limiting ke liye counters Redis jaise shared store me rakho. Lab 3 me token bucket live try karo.

Q11Microservices kab use karne chahiye aur kab nahi?

Microservices tab jab team badi ho (alag teams alag services deploy karein), scale alag-alag ho (ek service ko zyada resources chahiye), aur technology alag chahiye. Monolith tab jab team chhoti ho, product naya ho, aur domain abhi clear na ho. Sabse badi galti hai shuru se microservices banana — pehle monolith banao, boundaries clear hone par todo. Uber ka nanoservices antipattern iska example hai.

Q12Saga pattern kya hai aur 2PC se behtar kyun hai?

Saga me ek badi transaction ko chhote steps me todte hain — har step ka ek compensating action hota hai (undo karne ke liye). Koi step fail ho to pehle wale steps ko compensate karo. 2PC (two-phase commit) me saare participants lock hote hain jab tak sab agree na karein — slow aur blocking hai, aur ek participant fail ho to sab ruk jate hain. Saga me koi lock nahi hota, isliye microservices me saga standard hai.

Q13CDN kaise kaam karta hai?

CDN duniya bhar me edge servers rakhta hai — content (images, videos, JS/CSS) ko user ke paas wale server par cache karta hai. User request kare to paas wala edge server content deta hai (cache hit) — origin server tak jana hi nahi padta. Cache miss ho to edge origin se laata hai aur store kar leta hai. Isse latency kam hoti hai aur origin ka load kam hota hai. Netflix ka Open Connect bhi isi idea par hai.

Q14WebSockets aur HTTP polling me kya farak hai?

HTTP polling me client baar-baar server se poochhta hai 'kuch naya hai?' — bekaar requests hoti hain. WebSockets me ek baar connection banta hai aur dono taraf se real-time messages aate-jate hain — chat apps, live tracking aur gaming me yahi use hota hai. Long polling beech ka rasta hai — server request ko tab tak rok kar rakhta hai jab tak naya data na aaye. Real-time ke liye WebSockets best hain.

Q15Database replication me sync aur async me kya farak hai?

Synchronous replication me har write primary aur replica dono par confirm hone ke baad hi success milta hai — strong consistency, lekin writes slow hote hain aur replica slow ho to primary bhi slow ho jata hai. Asynchronous replication me primary pehle confirm karta hai, replica baad me sync hota hai — writes fast, lekin replication lag hota hai (kuch seconds purana data dikh sakta hai). Read-heavy systems me async common hai; payments me sync chahiye hota hai.

Q16Cache stampede kya hai aur kaise rokte hain?

Cache stampede tab hota hai jab ek popular key expire hoti hai aur hazaaron requests ek saath database par gir jati hain — database crash ho sakta hai. Rokne ke tareeke: (1) lock lagao — sirf ek request DB se laaye, baaki wait karein; (2) early refresh — key expire hone se pehle hi background me refresh karo; (3) stale-while-revalidate — purana cached data dikhate raho, background me naya lao. Interview me ye batana dikhata hai ki aapne caching ko depth me socha hai.

Q17Eventual consistency ka matlab kya hai?

Eventual consistency ka matlab hai: write ke turant baad saare replicas par naya data nahi dikhega, lekin kuch time baad (agar koi naya write na ho) sab replicas ek jaise ho jayenge. Social media likes, feeds aur recommendations me ye chalti hai — user ko thoda purana data dikhe to koi nuksaan nahi. Payments aur inventory me ye nahi chalegi — wahan strong consistency chahiye. CAP theorem se iska gehra rishta hai.

Q18System design me bottlenecks kaise pehchante hain?

Har component ki capacity nikalo — QPS, storage, bandwidth, CPU — aur dekho kaunsa pehle saturate hoga. Common bottlenecks: single database (reads/writes), single point of failure, hot partition (ek shard par zyada load), synchronous calls (ek slow service sabko slow kar deti hai), aur cache miss rate. Interview me har design ke ant me 'bottleneck kya hai' zaroor batana — interviewer yahi dekhna chahta hai ki aapne socha hai ki system kahan tootega.

Q19API design me versioning kyun zaroori hai?

API badalti rehti hai — naye fields aate hain, purane hatate hain. Bina versioning ke purane clients toot jayenge. Versioning ke tareeke: URL me (/v1, /v2), header me, ya query param me. Rule hai: breaking changes ke liye naya version banao, backward-compatible changes (naya optional field) purane version me bhi chal sakte hain. Purane versions ko deprecate karne ka timeline bhi batana chahiye.

Q20Idempotency kya hai aur payments me kyun zaroori hai?

Idempotency ka matlab hai: ek hi operation do baar karo to effect ek hi baar ho. Payments me network fail ho to client retry karta hai — bina idempotency ke do baar charge ho jayega. Solution: har request ke saath idempotency key bhejo; server pehli baar process kare, dobara wahi key aaye to purana result wapas de (dobara charge mat karo). Stripe jaise gateways isi par chalte hain.

Q21Distributed tracing kya hai aur kyun chahiye?

Ek user request kai microservices se guzarti hai — jab kuch slow ya fail ho to pata kaise chalega ki kahan time laga? Distributed tracing me har request ko ek trace ID milta hai, aur har service apna span (kitna time laga) record karti hai. Jaeger ya Zipkin jaise tools se poora request flow ek timeline me dikhta hai. Bina tracing ke microservices me debugging andhere me teer chalane jaisa hai.

Q22Leader election kya hai?

Distributed system me kai nodes me se ek leader chunna — leader hi writes accept kare aur decisions le. Raft aur Paxos jaise consensus algorithms se leader election hoti hai: nodes vote karte hain, majority (quorum) se leader banta hai. Leader fail ho to naya election hota hai. Kafka, etcd aur Kubernetes — sab me leader election hoti hai. Split-brain se bachne ke liye quorum zaroori hai.

Q23Horizontal vs vertical scaling me kya farak hai?

Vertical scaling (scale-up) ka matlab hai: ek hi machine ko aur powerful banana — zyada CPU, zyada RAM. Aasan hai lekin limit hoti hai (ek machine kitni badi ho sakti hai) aur single point of failure rehta hai. Horizontal scaling (scale-out) ka matlab hai: aur machines add karna — load baantna. Zyada complex hai (sharding, load balancing chahiye) lekin practically unlimited scale deta hai. Modern systems horizontal scaling use karte hain.

Q24Thundering herd problem kya hai?

Thundering herd tab hota hai jab bahut saare clients/processes ek saath ek hi resource ke liye jaag jayein — jaise cache expire hote hi hazaaron requests DB par, ya ek service restart hote hi saare clients reconnect karein. Solution: jitter (random delay) add karo, requests ko stagger karo, aur cache stampede wale tareeke use karo. Interview me ye term bolna dikhata hai ki aapne real-world failures dekhe hain.

Q25Database me indexing kaise kaam karta hai?

Index ek alag data structure (B-tree) hai jo queries ko fast banata hai — bina index ke database ko poori table scan karni padti hai. Lekin har index ki keemat hai: writes slow hote hain (har index update karna padta hai) aur storage badhta hai. Rule: jahan WHERE, JOIN ya ORDER BY me use hota hai, wahan index banao; har column par index mat banao. Interview me ye batana ki aapne index ke trade-offs soche hain.

Q26Fanout on write vs fanout on read — kab kaunsa?

Fanout on write me post hote hi saare followers ke feed me daal do — read fast hoti hai (feed pehle se ready), lekin write mehenga hai (celebrity ke 100M followers = 100M writes). Fanout on read me feed khulte hi followed users ke posts nikalo — write sasta, lekin read slow. Practical solution hybrid hai: normal users ke liye fanout on write, celebrities ke liye fanout on read. Instagram/Twitter ka design yahi hai.

Q27Circuit breaker pattern kya hai?

Circuit breaker ek failing service ko aur requests bhejna band kar deta hai — taaki wo recover kar sake aur baaki system bhi na gire. Teen states hoti hain: closed (normal), open (requests turant fail, downstream ko call mat karo), half-open (thodi requests bhej kar test karo, sahi ho to closed). Ye cascading failures rokta hai — ek service down ho to poora system down na ho. Microservices me ye must-have pattern hai.

Q28Object storage aur block storage me kya farak hai?

Block storage (EBS jaisa) ek virtual hard disk hai — OS use file system ki tarah treat karta hai, low latency, lekin ek hi machine (ya AZ) se attach hota hai. Object storage (S3 jaisa) HTTP API se objects (files) store karta hai — unlimited scale, high durability, lekin latency zyada aur file system jaisa nahi. Databases ke liye block storage, photos/videos/backups ke liye object storage. Dono ka use case alag hai.

Q29System design interview me time kaise manage karein?

45-minute interview ko aise baanto: 5 min requirements clarify karo, 5 min back-of-envelope estimation, 10 min high-level design, 15 min deep dive (database, caching, scaling), 5 min bottlenecks aur trade-offs, 5 min wrap-up. Ek hi component par atak mat jao — interviewer ko poora design dekhna hai. Agar time kam bache to deep dive chhota karo, lekin high-level design poora dikhao. Lab 8 ka timer isi practice ke liye hai.

Q30Sharding key kaise chunni chahiye?

Achhi shard key wo hai jo: (1) data ko barabar baante (hot shard na bane), (2) aapki common queries shard key par hon (cross-shard queries na hon), aur (3) kabhi na badle (user ID achhi hai, email bura hai kyunki badal sakta hai). Celebrity problem se bacho — ek bahut popular user ka saara data ek shard par aa jaye to wo shard overload ho jata hai. Hash-based sharding se distribution barabar hoti hai; range-based se range queries fast hoti hain.

Q31Event sourcing kya hai?

Event sourcing me current state store karne ki jagah saare events store karte hain — state events ko replay karke banti hai. Fayda: poora history milta hai (audit, debugging, time travel), aur kisi bhi time ki state bana sakte ho. Nuksaan: events bahut hote hain (storage), aur replay slow ho sakta hai (isliye snapshots bhi rakho). Banking aur order systems me ye pattern common hai — har transaction ek event hai.

Q32How to prepare for system design interviews in 2026?

Pehle fundamentals pakke karo — CAP theorem, caching, load balancing, databases, messaging — phir 15-20 classic problems (URL shortener, Twitter, WhatsApp, YouTube, Uber) ko framework se solve karo. Har problem ko likh kar practice karo, sirf padh kar nahi. Is SPA ke 20 questions aur 8 labs isi practice ke liye hain. Mock interviews karo — bol kar design karna, likh kar design karne se alag skill hai.

Q33Load balancing algorithms kaunse hain aur kab kaunsa use karein?

Round Robin — sabse simple, barabar baantta hai; jab saare servers barabar hon. Least Connections — kam busy server ko request do; jab requests ka time alag-alag ho. Weighted Round Robin — powerful servers ko zyada requests; jab servers ki capacity alag ho. IP Hash — ek user ki saari requests ek hi server par; jab session server par ho. Least Response Time — sabse fast respond karne wale ko do. Lab 2 me inhe simulate karke dekho.

Q34Database me read replicas kaise kaam karte hain?

Primary database par writes hote hain, replicas par sirf reads — replicas primary ke changes ko replicate karte hain (async ya sync). Isse read load baant jata hai. Lekin replication lag hota hai — user ne abhi likha, turant padhe to purana data dikh sakta hai. Solution: user apna khud ka data primary se padhe (read-your-own-write), baaki data replicas se. Failover me replica primary ban jata hai.

Q35What is the difference between latency and throughput?

Latency ka matlab hai: ek request ko jawab milne me kitna time laga (milliseconds). Throughput ka matlab hai: ek second me kitni requests handle hui (requests/sec). Dono alag hain — ek system ki latency kam ho sakti hai lekin throughput bhi kam (ek hi request fast, lekin ek saath kam requests). Interview me dono ko alag discuss karo: latency ke liye caching aur CDN, throughput ke liye horizontal scaling aur async processing.

Q36How do you handle a sudden traffic spike (flash sale)?

Teen tareeke: (1) Pehle se prepare karo — cache warm karo, auto-scaling rules set karo, load test karo. (2) Spike ke time traffic ko control karo — queue lagao (virtual waiting room), non-critical features band karo (recommendations, reviews), aur rate limiting lagao. (3) Read/write ko alag karo — reads ko cache aur replicas se serve karo, taaki writes ke liye database khaali rahe. IRCTC tatkal aur e-commerce sale events isi pattern par chalte hain.
