01Core Concepts

Scalability

Scalability matlab hai: load badhne par system ki performance na gire — users 100 se 10 lakh ho jayein, tab bhi response time aur reliability bani rahe.

Do tareeke hain scale karne ke. Vertical scaling (scale up) — ek hi machine ko zyada powerful banao (zyada CPU/RAM). Aasan hai, lekin ek limit ke baad mehenga aur ek hi machine SPOF ban jati hai. Horizontal scaling (scale out) — zyada machines jodo aur load baanto. Yehi aaj ke bade systems ka rasta hai, lekin iske liye load balancing, stateless services aur data partitioning chahiye.

Interview me ye sawaal hamesha aata hai: "System ko 10x load ke liye kaise scale karoge?" Jawab me pehle bottleneck dhoondo (CPU? database? network?), phir batayo kya horizontal scale hoga, kahan cache lagega, aur kahan async queue aayegi.

  • Elasticity: load ke hisaab se resources apne aap badhna-ghatna (auto-scaling).
  • Stateless services: har request kisi bhi server par ja sake — scale out ki pehli shart.
  • Database scaling: read replicas, sharding, caching — sirf app server badhane se kaam nahi chalta.
Sourcehttps://algomaster.io/learn/system-design/scalability

02Core Concepts

Availability

Availability matlab hai: system kitne samay tak up aur reachable rehta hai. Ise "nines" me naapa jata hai — 99.9% matlab saal me ~8.7 ghante downtime, 99.99% matlab ~52 minute.

High availability ke liye redundancy chahiye: har component ka backup ho, koi single point of failure na ho. Load balancer ke peeche kayi servers, alag availability zones me replicas, aur health checks jo kharab server ko traffic se hata dein.

Availability aur consistency ke beech hamesha tradeoff hota hai (CAP theorem). Interview me availability ka number maangna mat bhoolo — "99.9% chahiye ya 99.99%?" — kyunki har extra nine ka cost bahut zyada hota hai.

  • SLA / SLO: availability ka vaada (SLA) aur andar ka target (SLO) alag cheezein hain.
  • Failover: primary girte hi standby ka zimma sambhalna — automatic hona chahiye.
  • Health checks + circuit breaker: kharab component ko turant alag karo.
Sourcehttps://algomaster.io/learn/system-design/availability

Reliability

Reliability matlab hai: system galat haalaton me bhi sahi kaam kare — hardware fail ho, network toote, ya load achanak badhe, tab bhi data na khoye aur galat jawab na de.

Availability "kitni der up raha" batati hai, reliability "up rehte hue kitna sahi kaam kiya" batati hai. Reliable system me fault tolerance hoti hai (kuch parts fail hone par bhi kaam chalta rahe), durability hoti hai (likha hua data kabhi na khoye) aur recoverability hoti hai (fail hone ke baad jaldi wapas aana).

  • Redundancy + replication: data ki kayi copies, alag machines/zones me.
  • Idempotency: retry karne par bhi ek hi asar — double charge ya double order nahi.
  • Graceful degradation: kuch features band karke core kaam chalate raho.
  • Testing: chaos testing, game days — fail hone ka rehearsal pehle se karo.
Sourcehttps://algomaster.io/learn/system-design/reliability

Single Point of Failure (SPOF)

SPOF matlab hai: system ka wo ek hissa jiske girte hi poora system gir jaye. Interview me har design ke baad khud se poochho — "yahan SPOF kya hai?"

Aam SPOF: ek hi database server, ek hi load balancer, ek hi availability zone, ek hi third-party service jis par sab kuch nirbhar hai. Hal hai redundancy — har critical component ki kam se kam do copies, alag zones me, aur automatic failover.

Har SPOF khatam karna mehenga hota hai, isliye pehle pata lagao ki kaunsa SPOF sabse zyada nuksaan dega. Interviewer ko dikhana hai ki tumne har component par ye sawaal poochha hai.

  • Load balancer khud SPOF na bane: active-passive pair ya DNS-based failover rakho.
  • Database: primary + standby replica, automatic promotion.
  • Zone/region: ek zone girne par doosre zone se kaam chale.
Sourcehttps://algomaster.io/learn/system-design/single-point-of-failure-spof

05Core Concepts

Latency vs Throughput vs Bandwidth

Latency = ek request ko jaane-aane me kitna samay laga. Throughput = ek samay me kitne requests/kitna data handle hua. Bandwidth = pipe kitna chauda hai, matlab maximum data rate.

Teeno alag hain. Highway ki misaal: bandwidth = kitni lanes hain, latency = ek gaadi ko paar karne me kitna samay, throughput = ek ghante me kitni gaadiyan paar hui. Lanes badhane se throughput badhta hai, lekin ek gaadi ki speed (latency) nahi badhti.

  • Latency kam karo: caching, CDN, database ke paas compute, chhote payloads.
  • Throughput badhao: horizontal scaling, connection pooling, batching, async processing.
  • Interview me: pehle batayo kaunsa metric matter karta hai — video call me latency, file upload me throughput.
Sourcehttps://algomaster.io/learn/system-design/latency-vs-throughput

Consistent Hashing

Consistent hashing keys ko servers par is tarah baant-ta hai ki server aane-jaane par sirf thoda sa data hile. Normal hashing (key % N) me ek server badalte hi lagbhag saara data dobara map hota hai — consistent hashing me sirf 1/N hissa hilta hai.

Kaam aise karta hai: servers aur keys dono ko ek hi hash ring par rakho. Har key apne hash ke baad clockwise pehle server ko milti hai. Server hatane par sirf uski keys agle server ko jati hain; naya server aane par sirf uske hisse ki keys hilti hain.

  • Virtual nodes: har server ke kayi virtual points ring par — load barabar banta hai, warna kisi server par zyada keys gir sakti hain.
  • Kahan use hota hai: distributed cache (Memcached), Dynamo/Cassandra jaisi databases, CDN routing.
  • Is repo me poora code hai: Java aur Python dono me — "Code Implementations" wale hisse me dekho, aur Lab 1 me ring ko live chalao.

CAP Theorem

CAP theorem kehta hai: distributed system me Consistency, Availability aur Partition Tolerance — teeno ek saath poori tarah nahi mil sakte. Network partition (machines ke beech sampark tootna) aayega hi, isliye asal me chunav Consistency aur Availability ke beech hota hai.

CP systems (jaise ZooKeeper, etcd): partition me kuch requests rok dete hain, lekin data hamesha consistent rehta hai. AP systems (jaise Dynamo, Cassandra): partition me bhi jawab dete hain, lekin data thoda purana ya alag ho sakta hai — baad me sync hota hai (eventual consistency).

  • Interview me: "CP ya AP?" ka jawab system ki zaroorat se do — payment me consistency, social feed me availability.
  • PACELC: CAP ka extension — partition na hone par bhi latency aur consistency ke beech chunav hota hai.
  • Eventual consistency: thodi der me sab replicas ek jaise ho jayein — kaafi systems ke liye kaafi hai.
Sourcehttps://algomaster.io/learn/system-design/cap-theorem

Failover

Failover matlab hai: primary component fail hote hi uska backup apne aap zimma sambhal le — bina insan ke haath lagaye, aur bina (ya kam se kam) downtime ke.

Do mashhoor tareeke: active-passive — standby chupchaap data sync karta rehta hai, primary girte hi active ho jata hai; active-active — dono ek saath traffic lete hain, ek girne par doosra saara load utha leta hai. Active-active behtar hai lekin data sync aur conflict handle karna mushkil hota hai.

  • Detection: heartbeat/health checks se pata chale ki primary gaya — jaldi aur sahi (galat alarm se flip-flop na ho).
  • Promotion: standby ko primary banana — split-brain se bacho (dono khud ko primary samjhein).
  • Failback: purana primary theek hone par wapas kaise laoge, bina data khoye.
Sourcehttps://www.druva.com/glossary/what-is-a-failover-definition-and-related-faqs

Fault Tolerance

Fault tolerance matlab hai: kuch parts kharab hone par bhi system poori tarah kaam karta rahe — user ko pata bhi na chale ki andar kuch toota hai.

Iske liye teen cheezein chahiye: redundancy (backup copies), isolation (ek failure doosre hisse me na phaile — bulkheads, circuit breakers) aur self-healing (kharab node ko hata kar naya node apne aap banana).

  • Replication: data aur compute dono ki copies — leader-follower ya quorum based.
  • Circuit breaker: kharab service ko baar-baar call karke use aur na dabao; thodi der baad retry karo.
  • Retry + timeout + backoff: halke failures khud theek ho jate hain; retry me exponential backoff rakho.
  • Chaos engineering: jaan-boojh kar failure daal kar dekho ki system sach me tolerant hai ya sirf kagaz par.

OSI Model

OSI model network ko 7 layers me baant-ta hai — Physical, Data Link, Network, Transport, Session, Presentation, Application. Har layer sirf apne kaam ki zimmedar hai.

Interview me zyada tar 3 layers kaam aati hain: Network (IP) — packet kahan jayega; Transport (TCP/UDP) — packet sahi aur kram me pahunchega ya nahi; Application (HTTP, DNS) — asal data kya hai. Baaki layers ka naam aur ek-line kaam aana chahiye.

  • Layer 3 — Network: IP addressing aur routing.
  • Layer 4 — Transport: TCP (reliable, ordered) vs UDP (fast, best-effort).
  • Layer 7 — Application: HTTP/HTTPS, DNS, WebSocket, SMTP.
  • Load balancer kahan baithta hai: L4 (transport-level) ya L7 (application-level, content dekh kar route karta hai).
Sourcehttps://algomaster.io/learn/system-design/osi

IP Addresses

IP address har device ka network wala pata hai. IPv4 32-bit (4.3 billion addresses — khatam hone ke kareeb) aur IPv6 128-bit (lagbhag anant) hota hai.

Public IP internet par dikhta hai, private IP sirf apne network ke andar (ghar/office). NAT ek public IP ke peeche kayi private devices ko internet se jodta hai. Static IP badalta nahi (servers ke liye), dynamic IP DHCP se milta hai aur badal sakta hai.

  • Subnetting: bade network ko chhote hisso me baantna — security aur routing ke liye.
  • DNS: naam (google.com) ko IP me badalta hai — IP yaad rakhna mushkil, naam aasan.
  • Load balancing se rishta: ek domain ke peeche kayi IPs ho sakti hain (DNS round robin).

Domain Name System (DNS)

DNS internet ki phonebook hai — domain naam ko IP address me badalta hai. Browser pehle DNS se poochhta hai, phir us IP se judta hai.

DNS hierarchical hai: root servers → TLD servers (.com) → authoritative servers (domain ka asal record). Caching har level par hoti hai, isliye har baar poora safar nahi karna padta. TTL batata hai ki record kitni der cache rahe.

  • A/AAAA record: naam → IPv4/IPv6. CNAME: ek naam doosre naam ka alias.
  • DNS se load balancing: ek naam ke kayi IPs — har query par alag IP (round robin), ya user ke location ke hisaab se najdeeki IP (geo-DNS).
  • Failover: kharab server ka IP DNS se hata do — lekin TTL tak purana IP cache me reh sakta hai, isliye DNS failover slow hota hai.

Proxy vs Reverse Proxy

Proxy (forward proxy) client ki taraf baithta hai — client ki pehchan chhupata hai, requests filter karta hai. Reverse proxy server ki taraf baithta hai — client ko pata bhi nahi chalta, server ki pehchan chhupti hai aur load banta hai.

Reverse proxy system design ka hero hai: load balancing, SSL termination, caching, compression, rate limiting — sab yahi karta hai. Nginx aur HAProxy iske mashhoor examples hain.

  • Forward proxy ke fayde: content filtering, anonymity, geo-restriction bypass, caching.
  • Reverse proxy ke fayde: server chhupana, ek entry point, SSL ek jagah, static content serve karna.
  • Interview me: "Load balancer kahan rakhoge?" ka jawab aksar reverse proxy hi hota hai.

14Networking Fundamentals

HTTP / HTTPS

HTTP web ka protocol hai — request/response, stateless. HTTPS wahi HTTP hai, bas TLS encryption ke saath — beech me koi data padh ya badal nahi sakta.

HTTP/1.1 me har connection par ek request (keep-alive se behtar), HTTP/2 me multiplexing — ek connection par kayi requests ek saath, header compression. HTTP/3 UDP/QUIC par chalta hai, connection aur tez banta hai.

  • Methods: GET (padho), POST (banao), PUT/PATCH (badlo), DELETE (hatao).
  • Status codes: 2xx success, 3xx redirect, 4xx client ki galti, 5xx server ki galti.
  • Stateless: har request apne saath zaroori info laye — server session yaad nahi rakhta (scale out ke liye zaroori).

15Networking Fundamentals

TCP vs UDP

TCP reliable hai — connection pehle, phir data kram me, khoya packet dobara bhejta hai. UDP tez hai — bina connection ke packet bhej do, mile ya na mile, kram ki guarantee nahi.

TCP chahiye jahan sahi data zaroori hai — web pages, files, database. UDP chahiye jahan speed zaroori hai aur thoda nuksaan chalega — video calls, gaming, live streaming, DNS queries.

  • TCP handshake: 3-way (SYN, SYN-ACK, ACK) — isliye connection banane me samay lagta hai.
  • Flow + congestion control: TCP receiver aur network ko dabata nahi — dheere-dheere speed badhata hai.
  • QUIC/HTTP/3: UDP par TCP jaisi reliability banata hai — handshake bhi tez.

Load Balancing

Load balancer aane wale traffic ko kayi servers par baant-ta hai taaki koi ek server dab na jaye aur koi server khaali na baithe. Yehi horizontal scaling ki jaan hai.

Algorithms: Round Robin — baari-baari; Weighted RR — taakat ke hisaab se; Least Connections — jiske paas kam kaam, use do; IP Hash — ek client hamesha ek hi server par (session stickiness); Least Response Time — jo tez jawab de, use do.

  • L4 vs L7: L4 transport level par (IP/port), L7 content dekh kar (URL, header, cookie).
  • Health checks: kharab server ko list se hatao — load balancer ka sabse zaroori kaam.

Checksums

Checksum data ki integrity check karne ka tareeka hai — bhejnewala data ka ek chhota hash saath bhejta hai, paane wala dobara hash karke milata hai. Mismatch matlab data raaste me badal gaya ya kharab hua.

Network packets (TCP checksum), files (MD5/SHA), databases — har jagah checksums hain. Ye galti pakadte hain, sudharte nahi — sudhar ke liye retransmission ya error-correcting codes chahiye.

  • CRC: network/storage me aam — burst errors pakadne me achha.
  • Hash (MD5/SHA): file download verify karne ke liye — ek bit badle to hash poora badal jata hai.
  • Interview me: data transfer ya storage design me "corruption kaise pakdoge?" ka jawab checksum hai.

18API Fundamentals

APIs — What is an API?

API matlab do software ke beech baat-cheet ka contract — tum kya bhejoge, wo kya dega, aur galti par kya hoga. Andar kaise kaam karta hai, ye chhupa rehta hai.

System design me APIs hi services ko jodti hain. Achhi API ke saaf contracts, versioning, pagination, rate limits aur dhang ke error codes hote hain. API design karte samay socho: kaun use karega, kitna load aayega, aur aage badalne par purane clients toote nahi.

  • REST: HTTP + JSON, resources par based — sabse aam.
  • GraphQL: client khud bataye use kya chahiye — over/under-fetching khatam.
  • gRPC: binary, tez, microservices ke beech — contract .proto file se.
  • Webhooks: server khud event par tumhe bulaye — polling khatam.

19API Fundamentals

API Gateway

API Gateway saari services ka ek hi darwaza hai. Client ek jagah request bhejta hai, gateway use sahi service tak pahunchata hai — auth, rate limiting, logging aur routing sab yahin hota hai.

Bina gateway ke har client ko har service ka pata, har service me auth, aur har jagah rate limit lagana padta — microservices me ye kharcha aur risk dono badhata hai. Gateway ye sab ek jagah samet deta hai.

  • Kaam: routing, authentication/authorization, rate limiting, request/response transformation, caching, monitoring.
  • Khatare: gateway khud SPOF ban sakta hai — isliye use bhi redundant rakho aur halka rakho (business logic gateway me mat daalo).
  • Examples: Kong, AWS API Gateway, Nginx, Zuul/Spring Cloud Gateway.

REST vs GraphQL

REST me har resource ka apna endpoint hota hai (GET /users/1, GET /users/1/posts). GraphQL me ek endpoint hota hai aur client query me likhta hai use kya chahiye.

REST aasan aur cache-friendly hai, lekin mobile jaise clients ko kayi calls karni padti hain (over-fetching ya under-fetching). GraphQL ek call me exact data deta hai, lekin caching mushkil, query ki complexity control karni padti hai, aur file upload jaisi cheezein ajeeb lagti hain.

  • REST lo jab: public APIs, caching zaroori ho, team chhoti ho, resources saaf hon.
  • GraphQL lo jab: client alag-alag data maange, mobile app ho, frontend tezi se badal raha ho.
  • Interview me: "Kaunsa aur kyun?" — jawab hamesha use-case se do, "naya hai isliye" se nahi.

WebSockets

WebSocket client aur server ke beech ek khula, do-tarfa connection hai — server jab chahe data bhej sakta hai, client ko baar-baar poochhna nahi padta. HTTP request/response se bilkul alag soch hai.

Consistent Hashing — Code

Ye code hash ring banata hai: har server ke 3 virtual nodes ring par rakhe jate hain, aur har key apne hash ke baad clockwise pehle server ko milti hai.

Kaise kaam karta hai

  • hash(key): MD5 se 32-bit hash nikalta hai — key aur server dono ko isi se ring par jagah milti hai.
  • addServer: server ke naam + "-0", "-1", "-2" ke hash ring me daalta hai (virtual nodes) — load barabar banta hai.
  • getServer: key ka hash nikaal kar usse bada pehla ring entry dhoondhta hai (ceilingEntry); na mile to ring ke pehle node par wrap hota hai.
  • removeServer: server ke saare virtual nodes ring se hata deta hai — sirf uski keys hilti hain, baaki sab wahi rehte hain.

Java vs Python farak: Java me TreeMap (sorted map) ceilingEntry deta hai; Python me dict + sorted list aur bisect use hota hai. Logic ek jaisa hai. Example me 6 servers (S0–S5), phir S6 joda aur S2 hataya jata hai — UserA/UserB ka server badalta hai ya nahi, ye ring par depend karta hai.

Interview tip: poochha jata hai — "ek server add hone par kitna data move hoga?" Jawab: sirf 1/(N+1) hissa, kyunki sirf naye server ke hisse ki keys hilti hain.

package implementations.java.consistent_hashing;

import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.*;

public class ConsistentHashing {
    private final int numReplicas; // Number of virtual nodes per server
    private final TreeMap<Long, String> ring; // Hash ring storing virtual nodes
    private final Set<String> servers; // Set of physical servers

    public ConsistentHashing(List<String> servers, int numReplicas) {
        this.numReplicas = numReplicas;
        this.ring = new TreeMap<>();
        this.servers = new HashSet<>();

        // Add each server to the hash ring
        for (String server : servers) {
            addServer(server);
        }
    }

    private long hash(String key) {
        try {
            MessageDigest md = MessageDigest.getInstance("MD5");
            md.update(key.getBytes());
            byte[] digest = md.digest();
            return ((long) (digest[0] & 0xFF) << 24) |
                   ((long) (digest[1] & 0xFF) << 16) |
                   ((long) (digest[2] & 0xFF) << 8) |
                   ((long) (digest[3] & 0xFF));
        } catch (NoSuchAlgorithmException e) {
            throw new RuntimeException("MD5 algorithm not found", e);
        }
    }

    public void addServer(String server) {
        servers.add(server);
        for (int i = 0; i < numReplicas; i++) {
            long hash = hash(server + "-" + i); // Unique hash for each virtual node
            ring.put(hash, server);
        }
    }

    public void removeServer(String server) {
        if (servers.remove(server)) {
            for (int i = 0; i < numReplicas; i++) {
                long hash = hash(server + "-" + i);
                ring.remove(hash);
            }
        }
    }

    public String getServer(String key) {
        if (ring.isEmpty()) {
            return null; // No servers available
        }

        long hash = hash(key);
        // Find the closest server in a clockwise direction
        Map.Entry<Long, String> entry = ring.ceilingEntry(hash);
        if (entry == null) {
            // If we exceed the highest node, wrap around to the first node
            entry = ring.firstEntry();
        }
        return entry.getValue();
    }

    public static void main(String[] args) {
        List<String> servers = Arrays.asList("S0", "S1", "S2", "S3", "S4", "S5");
        ConsistentHashing ch = new ConsistentHashing(servers, 3);

        // Step 2: Assign requests (keys) to servers
        System.out.println("UserA is assigned to: " + ch.getServer("UserA"));
        System.out.println("UserB is assigned to: " + ch.getServer("UserB"));

        // Step 3: Add a new server dynamically
        ch.addServer("S6");
        System.out.println("UserA is now assigned to: " + ch.getServer("UserA"));

        // Step 4: Remove a server dynamically
        ch.removeServer("S2");
        System.out.println("UserB is now assigned to: " + ch.getServer("UserB"));
    }
}

import hashlib
import bisect

class ConsistentHashing:
    def __init__(self, servers, num_replicas=3):
        """
        Initializes the consistent hashing ring.

        - servers: List of initial server names (e.g., ["S0", "S1", "S2"])
        - num_replicas: Number of virtual nodes per server for better load balancing
        """
        self.num_replicas = num_replicas  # Number of virtual nodes per server
        self.ring = {}  # Hash ring storing virtual node mappings
        self.sorted_keys = []  # Sorted list of hash values (positions) on the ring
        self.servers = set()  # Set of physical servers (used for tracking)

        # Add each server to the hash ring
        for server in servers:
            self.add_server(server)

    def _hash(self, key):
        """Computes a hash value for a given key using MD5."""
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def add_server(self, server):
        """
        Adds a server to the hash ring along with its virtual nodes.

        - Each virtual node is a different hash of the server ID to distribute load.
        - The server is hashed multiple times and placed at different positions.
        """
        self.servers.add(server)
        for i in range(self.num_replicas):  # Creating multiple virtual nodes
            hash_val = self._hash(f"{server}-{i}")  # Unique hash for each virtual node
            self.ring[hash_val] = server  # Map hash to the server
            bisect.insort(self.sorted_keys, hash_val)  # Maintain a sorted list for efficient lookup

    def remove_server(self, server):
        """
        Removes a server and all its virtual nodes from the hash ring.
        """
        if server in self.servers:
            self.servers.remove(server)
            for i in range(self.num_replicas):
                hash_val = self._hash(f"{server}-{i}")  # Remove each virtual node's hash
                self.ring.pop(hash_val, None)  # Delete from hash ring
                self.sorted_keys.remove(hash_val)  # Remove from sorted key list

    def get_server(self, key):
        """
        Finds the closest server for a given key.

        - Hash the key to get its position on the ring.
        - Move clockwise to find the nearest server.
        - If it exceeds the last node, wrap around to the first node.
        """
        if not self.ring:
            return None  # No servers available

        hash_val = self._hash(key)  # Hash the key
        index = bisect.bisect(self.sorted_keys, hash_val) % len(self.sorted_keys)  # Locate nearest server
        return self.ring[self.sorted_keys[index]]  # Return the assigned server

import java.util.List;

public class RoundRobin {

Token Bucket Rate Limiting — Code

Bucket me tokens bharte rehte hain; har request ek token kharch karti hai. Token na ho to request mana. Burst allow karta hai — bucket bhara ho to ek saath kayi requests chal sakti hain.

  • refill: guzre samay ke hisaab se tokens jodta hai (fillRate tokens/sec), lekin capacity se zyada nahi.
  • allowRequest: pehle refill karo, phir dekho token hai ya nahi — hai to ghatao aur allow karo.
  • Java: allowRequest(int tokens) — ek request kayi tokens bhi maang sakti hai (bhaari request). Python: default 1 token.
  • Kab use karein: burst chahiye ho lekin average rate control me rahe — API rate limits ka sabse aam algorithm.

Example: capacity 10, fill rate 1/sec — pehle 10 requests turant allow, phir har second 1 token bhar ta hai.

Java Implementation

Java — TokenBucket.java
package implementations.java.rate_limiting;

import java.time.Instant;

public class TokenBucket {
    private final long capacity;        // Maximum number of tokens the bucket can hold
    private final double fillRate;      // Rate at which tokens are added to the bucket (tokens per second)
    private double tokens;              // Current number of tokens in the bucket
    private Instant lastRefillTimestamp; // Last time we refilled the bucket

    public TokenBucket(long capacity, double fillRate) {
        this.capacity = capacity;
        this.fillRate = fillRate;
        this.tokens = capacity;  // Start with a full bucket
        this.lastRefillTimestamp = Instant.now();
    }

    public synchronized boolean allowRequest(int tokens) {
        refill();  // First, add any new tokens based on elapsed time

        if (this.tokens < tokens) {
            return false;  // Not enough tokens, deny the request
        }

        this.tokens -= tokens;  // Consume the tokens
        return true;  // Allow the request
    }

    private void refill() {
        Instant now = Instant.now();
        // Calculate how many tokens to add based on the time elapsed
        double tokensToAdd = (now.toEpochMilli() - lastRefillTimestamp.toEpochMilli()) * fillRate / 1000.0;
        this.tokens = Math.min(capacity, this.tokens + tokensToAdd);  // Add tokens, but don't exceed capacity
        this.lastRefillTimestamp = now;
    }
}

Leaky Bucket Rate Limiting — Code

Bucket me requests bharo, wo steady rate se bahar nikle (leak). Burst aaye to bucket bhar jata hai, extra requests mana ho jati hain — bahar jaane ki rate hamesha ek jaisi rehti hai.

  • leak(): guzre samay × leakRate ke hisaab se queue se purani requests nikaalta hai.
  • allowRequest: pehle leak karo, phir dekho bucket me jagah hai ya nahi — hai to request jodo.
  • Token Bucket se fark: Token Bucket burst ko aane deta hai (bucket bhara ho to), Leaky Bucket bahar jaane ko steady rakhta hai — downstream ko hamesha ek jaisi rate milti hai.
  • Kab use karein: downstream system ko steady load chahiye ho — jaise message processing ya network traffic shaping.

Java Implementation

package implementations.java.rate_limiting;

import java.time.Instant;
import java.util.LinkedList;
import java.util.Queue;

public class LeakyBucket {
    private final long capacity;        // Maximum number of requests the bucket can hold
    private final double leakRate;      // Rate at which requests leak out of the bucket (requests per second)
    private final Queue<Instant> bucket; // Queue to hold timestamps of requests
    private Instant lastLeakTimestamp;   // Last time we leaked from the bucket

    public LeakyBucket(long capacity, double leakRate) {
        this.capacity = capacity;
        this.leakRate = leakRate;
        this.bucket = new LinkedList<>();
        this.lastLeakTimestamp = Instant.now();
    }

    public synchronized boolean allowRequest() {
        leak();  // First, leak out any requests based on elapsed time

        if (bucket.size() < capacity) {
            bucket.offer(Instant.now());  // Add the new request to the bucket
            return true;  // Allow the request
        }
        return false;  // Bucket is full, deny the request
    }

    private void leak() {
        Instant now = Instant.now();
        long elapsedMillis = now.toEpochMilli() - lastLeakTimestamp.toEpochMilli();
        int leakedItems = (int) (elapsedMillis * leakRate / 1000.0);  // Calculate how many items should have leaked

        // Remove the leaked items from the bucket
        for (int i = 0; i < leakedItems && !bucket.isEmpty(); i++) {
            bucket.poll();
        }

        lastLeakTimestamp = now;
    }
}

    private final long maxRequestsPerWindow; // Maximum number of requests allowed per window
    private long currentWindowStart;         // Start time of the current window
    private long requestCount;               // Number of requests in the current window

            currentWindowStart = now;  // Start a new window
            requestCount = 0;          // Reset the count for the new window
        }

            requestCount++;  // Increment the count for this window
            return true;     // Allow the request
        }
        return false;  // We've exceeded the limit for this window, deny the request
    }

    private final long maxRequestsPerWindow;  // Maximum number of requests allowed in the window
    private long currentWindowStart;          // Start time of the current window
    private long previousWindowCount;         // Number of requests in the previous window
    private long currentWindowCount;          // Number of requests in the current window

    public SlidingWindowCounter(long windowSizeInSeconds, long maxRequestsPerWindow) {
        this.windowSizeInSeconds = windowSizeInSeconds;
        this.maxRequestsPerWindow = maxRequestsPerWindow;
        this.currentWindowStart = Instant.now().getEpochSecond();
        this.previousWindowCount = 0;
        this.currentWindowCount = 0;
    }

    public synchronized boolean allowRequest() {
        long now = Instant.now().getEpochSecond();
        long timePassedInWindow = now - currentWindowStart;

        // Check if we've moved to a new window
        if (timePassedInWindow >= windowSizeInSeconds) {
            previousWindowCount = currentWindowCount;
            currentWindowCount = 0;
            currentWindowStart = now;
            timePassedInWindow = 0;
        }

        // Calculate the weighted count of requests
        double weightedCount = previousWindowCount * ((windowSizeInSeconds - timePassedInWindow) / (double) windowSizeInSeconds)
                + currentWindowCount;

        if (weightedCount < maxRequestsPerWindow) {
            currentWindowCount++;  // Increment the count for this window
            return true;           // Allow the request
        }
        return false;  // We've exceeded the limit, deny the request
    }    
}

import time

class SlidingWindowCounter:
    def __init__(self, window_size, max_requests):
        self.window_size = window_size  # Size of the sliding window in seconds
        self.max_requests = max_requests  # Maximum number of requests per window
        self.current_window = time.time() // window_size
        self.request_count = 0
        self.previous_count = 0

    def allow_request(self):
        now = time.time()
        window = now // self.window_size

        # If we've moved to a new window, update the counts
        if window != self.current_window:
            self.previous_count = self.request_count
            self.request_count = 0
            self.current_window = window

        # Calculate the weighted request count
        window_elapsed = (now % self.window_size) / self.window_size
        threshold = self.previous_count * (1 - window_elapsed) + self.request_count

        # Check if we're within the limit
        if threshold < self.max_requests:
            self.request_count += 1
            return True
        return False

Interview FAQs — 36 Sawaal Jawaab

System design interview me aksar poochhe jaane wale sawaal — har jawab me concept ke saath interview wali soch bhi hai.

Q1 System design interview me sabse pehle kya karna chahiye?
Sawaal poochhna — turant design shuru mat karo. Functional requirements (kya banana hai), non-functional (kitne users, kitna data, latency, availability), aur scope (kya nahi banana) pehle tay karo. Interviewer tumhare sawaal se hi samajh jata hai ki tum senior ho ya nahi.
Q2 Scalability ka matlab sirf zyada servers jodna hai?
Nahi. Servers jodna sirf ek hissa hai. Database scaling, caching, async queues, stateless services aur bottlenecks hatana — sab mil kar scalability banti hai. Sirf app servers badhaoge to database hi gir jayega.
Q3 CAP theorem interview me kaise use karein?
Har design me batayo ki tum CP chun rahe ho ya AP — aur kyun. Payment/inventory me consistency (CP), feed/likes me availability (AP). 'Teeno chahiye' bolna galat jawab hai — theorem kehta hai teeno ek saath nahi milte.
Q4 Consistent hashing kyun zaroori hai? Normal hash se kya problem hai?
Normal hash (key % N) me ek server badalte hi lagbhag saara data dobara map hota hai. Consistent hashing me sirf 1/N hissa hilta hai. Distributed cache aur databases me server aana-jana aam hai, isliye ye bahut matter karta hai.
Q5 Load balancer ke algorithms me se kaunsa kab use karein?
Servers barabar hon to Round Robin; taakat alag ho to Weighted RR; connections lambe hon to Least Connections; session ek server par chahiye to IP Hash; speed badalti ho to Least Response Time. Interview me algorithm ka naam ke saath 'kyun' bhi bolo.
Q6 Rate limiting ke 5 algorithms me kya fark hai?
Token Bucket burst allow karta hai; Leaky Bucket steady rate rakhta hai; Fixed Window aasan hai lekin boundary burst hota hai; Sliding Window Log sabse sahi hai lekin memory zyada; Sliding Window Counter beech ka rasta hai — production me sabse aam.
Q7 Cache kab lagana chahiye aur kab nahi?
Jab reads zyada hon, data baar-baar poochha jaye aur thoda purana chal jaye — tab cache lagao. Har request par badalne wala data, ya jo data kabhi dobara nahi poochha jayega, use cache mat karo. Aur cache lagate hi invalidation ka plan bhi batao.
Q8 Cache stampede kya hai aur isse kaise bachein?
Jab ek hot key expire hote hi hazaaron requests ek saath database par toot padein. Hal: ek request ko lock lekar cache bharne do (baaki stale data lein), ya expiry se pehle background me refresh karo (refresh-ahead).
Q9 SQL vs NoSQL — interview me kaise faisla karein?
Data structured ho, joins aur transactions zaroori hon to SQL. Data bahut bada ho, schema badalta rahe, aur eventual consistency chale to NoSQL. Aksar dono ka mix banta hai — orders SQL me, sessions/feed NoSQL me.
Q10 Sharding ki shard key galat chuni to kya hoga?
Hotspot ban jayega — ek shard par saara load, baaki khaali. Aur cross-shard queries badh jayengi. Achhi key wohi hai jo data barabar baante aur aam queries ek hi shard me rahein. Interview me shard key ka faisla sabse zyada number deta hai.
Q11 Microservices kab banana chahiye aur kab monolith hi theek hai?
Team badi ho, alag hisson ko alag scale/deploy karna ho, aur domain saaf ho — tab microservices. Chhoti team, MVP, ya domain abhi unclear ho — tab monolith. Microservices complexity free me nahi milti — service discovery, tracing, distributed transactions sab sambhalne padte hain.
Q12 Eventual consistency ka matlab data galat hoga?
Nahi — matlab hai data thodi der me sahi ho jayega. Likhte hi har jagah naya data nahi dikhega, lekin kuch second me sab replicas ek jaise ho jayenge. Likes, comments, feed — inme ye chal jata hai. Payment me nahi chalta.
Q13 Message queue aur pub/sub me kya fark hai?
Queue me ek message ek hi consumer ko milta hai (kaam baantna). Pub/sub me ek event saare subscribers ko milta hai (khabar phailana). Queue kaam ke liye, pub/sub events ke liye. Kafka dono ka mix hai.
Q14 Idempotency key kaise kaam karti hai?
Client har request ke saath ek unique key bhejta hai. Server key aur uska result store karta hai. Wahi key dobara aaye to kaam dobara kiye bina purana result de deta hai. Payment APIs me retry safe banane ka yahi tareeka hai.
Q15 WebSocket scale karna mushkil kyun hai?
Kyunki connection stateful hota hai — ek user ek specific server se juda rehta hai. Server badle to connection tootta hai. Hal: sticky sessions + servers ke beech pub/sub backbone, taaki message kisi bhi server se sahi user tak pahunche.
Q16 Fanout on write vs fanout on read — kaunsa kab?
Fanout on write: likhte hi sab followers ki feed me daal do — reads tez, writes bhaari. Fanout on read: padhte samay jodo — writes halki, reads dheemi. Celebrity (lakhon followers) ke liye write fanout namumkin hai — isliye hybrid use hota hai.
Q17 Database replication lag se kya problem hoti hai?
Replica primary se peeche rehta hai — user abhi likh kar padhe to use purana data dikh sakta hai. Hal: apne writes khud primary se padho (read-your-own-writes), ya critical reads primary se karo.
Q18 Bloom filter kahan use hota hai?
Database ya cache se poochhne se pehle check karo — key hai bhi ya nahi. 'Nahi hai' ka jawab 100% sahi hota hai, isliye faltu lookups bachte hain. Cassandra, Bigtable aur username availability check me use hota hai.
Q19 Circuit breaker aur retry me kya fark hai?
Retry kehta hai 'dobara try karo' — halki kharabi me kaam aata hai. Circuit breaker kehta hai 'ruk jao, service kharab hai' — jab kharabi badi ho to retry se service aur dab jati hai. Dono saath use hote hain: retry with backoff + circuit breaker.
Q20 Distributed lock kyun mushkil hai?
Kyunki lock holder mar jaye to lock kaun chhode, aur network partition me do log ek hi lock le lein to kya ho — ye sab sambhalna padta hai. Fencing token ke bina purana holder galat data likh sakta hai. Isliye pehle socho: lock sach me chahiye ya unique constraint/idempotency se kaam chal jayega?
Q21 Gossip protocol kahan use hota hai?
Cluster membership aur failure detection me — Cassandra, Consul jaise systems me har node thode nodes ko batata hai, khabar phail jati hai. Koi central server nahi chahiye, isliye SPOF nahi banta.
Q22 CDN se dynamic content bhi serve ho sakta hai?
Haan — API responses bhi edge par cache ho sakte hain, lekin TTL chhota rakho aur invalidation ka plan rakho. Static content (images, videos, JS) ke liye CDN lagbhag hamesha lagana chahiye.
Q23 API Gateway khud SPOF kyun ban sakta hai?
Kyunki saara traffic ek hi jagah se guzarta hai. Isliye gateway ko redundant rakho (kayi instances, alag zones) aur halka rakho — business logic gateway me mat daalo, warna wo dheema aur mushkil ho jayega.
Q24 Long polling aur WebSocket me kaunsa chunein?
Updates kam hon aur infra simple chahiye to long polling. Updates lagatar hon (chat, live scores) to WebSocket. Long polling HTTP hi hai — proxy aur firewall se aasani se guzarta hai; WebSocket ko stateful connection sambhalna padta hai.
Q25 System design me estimates kaise lagayein?
Pehle users nikalo, phir per-user activity (requests/day), phir per-second (QPS) — peak ke liye 2-3x. Storage: per record size × count × saal. Bandwidth: QPS × response size. Gol numbers rakho (10 lakh users, 100 bytes) — exact number nahi, order of magnitude chahiye.
Q26 Interview me tradeoff kaise bolein?
Har bade faisle ke baad ek line bolo: 'Iska tradeoff ye hai — X milega, Y dena padega.' Jaise: 'Cache lagayenge to reads tez hongi, lekin stale data ka risk hoga, isliye TTL 5 minute rakhenge.' Ye ek line tumhe senior dikhati hai.
Q27 Sharding aur partitioning me kya fark hai?
Partitioning ek hi database ke andar table ko hisson me baantna hai. Sharding alag-alag machines par data baantna hai. Partitioning aasan hai, sharding zyada powerful aur zyada mushkil — joins, transactions aur rebalancing sab mushkil ho jate hain.
Q28 Paxos aur Raft me kya fark hai?
Dono consensus algorithms hain — kayi machines ek faisle par sehmat hon. Paxos pehla aur mushkil hai; Raft usi ka aasan aur samajhne layak version hai. Interview me Raft ka naam aur quorum (majority) ka idea kaafi hai.
Q29 Kafka aur RabbitMQ me kaunsa kab?
Kafka: bahut zyada throughput, event log, stream processing — data pipeline ke liye. RabbitMQ: aasan routing, kam throughput, traditional queues — task distribution ke liye. Throughput aur retention dekho, phir chuno.
Q30 Two-phase commit (2PC) kyun kam use hota hai?
Kyunki ye blocking hai — coordinator mare to sab atak jate hain, aur latency bahut zyada hoti hai. Isliye aaj saga pattern zyada use hota hai: har step ka compensating action rakho, fail ho to wapas karo.
Q31 System design seekhne ka sahi kram kya hai?
Pehle neev: scalability, CAP, latency/throughput. Phir components: database, cache, queue, load balancer. Phir patterns: microservices, event-driven. Phir problems: pehle easy (URL shortener, rate limiter), phir medium (chat, feed), phir hard (Uber, Google Docs). Har problem khud banao — sirf dekhne se nahi aata.
Q32 Designing Data-Intensive Applications kitab kyun padhni chahiye?
Kyunki ye kitab 'kya' nahi, 'kyun' sikhati hai — storage engines kaise kaam karte hain, replication kyun mushkil hai, transactions ke peeche kya hai. Iske baad har design sawaal ka jawab gehrai se de sakte ho.
Q33 Interview me time kam pad jaye to kya karein?
Requirements aur high-level design par zyada samay do — deep dive me ek-do hisse gehrai se karo, har hisse me nahi. Ant me bottlenecks zaroor bolo — 'time khatam ho gaya, lekin 10x par ye tootega' kehna bhi number deta hai.
Q34 Notifications duplicate kyun jaati hain aur kaise rokein?
At-least-once delivery me event dobara mil sakta hai. Hal: har notification ko ek unique event ID do, receiver pehle check kare ki ye ID pehle process hui ya nahi (deduplication), aur saare sends idempotent rakho.
Q35 Hot key problem kya hai aur iska hal kya hai?
Jab ek key (jaise celebrity ka profile) par saara load aa jaye to uska cache node ya shard dab jata hai. Hal: hot key ko kayi nodes par replicate karo, local cache lagao, ya key ko split karke suffix jodo.
Q36 Read replicas kitne rakhne chahiye?
Reads ke hisaab se — jitne chahiye utne, lekin har replica lag bhi badhata hai aur cost bhi. Shuruaat me 2-3, reads badhein to aur jodo. Writes ke liye replica nahi, sharding chahiye.
