System design itna bada topic kyun hai?

02Shuruaat

Interview Tips — Constraints clear karo, user cases pehchano

Interview ki shuruaat me kuch minutes interviewer se sawaal poochho aur scope par agree karo. Jo requirements interviewer ne shuru me nahi batayi, unhe bhi nikalna tumhara kaam hai. Seedha design karna shuru kar dena sabse badi galti hai.

User cases kya hote hain?

User cases system ke main functions batate hain — user system se kya-kya kar sakega. Jaise TinyURL me: URL short karna, short URL kholna, analytics dekhna. Har user case ko likh lo, phir design usi par banao.

Constraints kya hote hain?

Constraints system ka scale batate hain. Ye numbers interviewer se poochho ya khud assume karke batao:

  • Requests per second — kitne requests aayenge? (read vs write alag-alag)
  • Requests ke types — kaunse operations honge, kis ratio me?
  • Data written per second — kitna data likha jayega?
  • Data read per second — kitna data padha jayega?

Back-of-envelope estimation

Constraints se storage aur bandwidth nikalo. Example: 100 million naye URLs roz, har URL 500 bytes → 50 GB roz, 5 saal me ~90 TB. Aise hisaab interviewer ko dikhate hain ki tum scale soch rahe ho. Lab 1 me ye calculator khud try karo.

Galtiyan jo avoid karni hain

  • Scope agree kiye bina design shuru karna.
  • Ek hi solution par atak jana — alternatives batao aur trade-offs discuss karo.
  • Numbers ka andaza lagaye bina "scale kar lenge" kehna.
  • Interviewer se baat na karna — interview ek discussion hai, monologue nahi.

03Shuruaat

Interview Tips — High-level architecture design

Constraints clear hone ke baad important components aur unke beech ke connections sketch karo — detail me jaaye bina. Ek scalable system me aam taur par ye hote hain: webserver (load balancer), service (service partition), database (primary/secondary cluster, saath me cache).

High-level design ka flow

  • Client se load balancer — traffic ko multiple webservers par baanto.
  • Webserver / API layer — request validate karo, auth check karo, service ko bhejo.
  • Service layer — business logic; zaroorat par service ko parts me baanto (service partition).
  • Database — primary/secondary cluster; read ke liye replicas, write ke liye primary.
  • Cache — hot data ke liye, database par load kam karne ke liye.

Kya sketch karna hai, kya nahi?

Boxes aur arrows se data flow dikhana hai — request kahan se aati hai, kahan jaati hai, response kaise wapas aata hai. Har box ke andar ka detail abhi nahi — wo component design (section 04) me aata hai. Diagram saaf hona chahiye: interviewer ko 30 second me samajh aana chahiye ki system kaise kaam karta hai.

Scale ke liye standard building blocks

  • Load balancer — traffic distribute karta hai, server down ho to traffic hatata hai.
  • CDN — static content user ke paas rakhta hai, latency kam karta hai.
  • Message queue — slow ya heavy kaam ko async karta hai.
  • Cache — read-heavy data ke liye.
  • Database sharding / replication — data aur read load baantne ke liye.

04Shuruaat

Interview Tips — Component design

High-level design ke baad har component ka detail design banta hai. Is stage par interviewer dekhta hai ki tum gehrai me soch sakte ho ya nahi.

Har component ke liye APIs likho

Har component ke liye specific APIs likhni hoti hain. Example: TinyURL ke liye POST /shorten (long URL → short URL) aur GET /{shortCode} (short URL → redirect). API ke inputs, outputs aur error cases batao.

Ek function ka detailed OOD design

Kisi ek function ke liye detailed object oriented design bhi maanga ja sakta hai — classes, unke attributes aur methods, aur unke beech ke relationships. OOD wale sections (29–30) me iska poora tareeka hai.

Database schema design karo

Database ke liye schema banao: tables, columns, primary keys, indexes. Example: URL table me short code primary key hoga, long URL aur created_at columns honge. Index kis column par lagega, ye bhi batao — jahan search hoga, wahan index hoga.

Bottlenecks aur trade-offs

Component design karte hue ye bhi batao: bottleneck kahan aayega, aur use kaise handle karoge. Har choice ka trade-off hota hai — consistency vs availability, speed vs storage, simple vs scalable. Interviewer ko ye sunna hota hai ki tum trade-offs samajhte ho.

Products and Systems — Google ke papers

Google ke 5 foundational papers

  • MapReduce: Simplified Data Processing on Large Clusters — bade data ko hazaaron machines par process karne ka tareeka: map (kaam baanto) phir reduce (result jodo).

Products and Systems — Data stores aur messaging

Har system design interview me koi na koi data store chunna padta hai. Ye 8 intros tumhe batate hain ki kaunsa tool kab use hota hai — cache, NoSQL, search, queue aur coordination.

  • Introduction to Memcached — distributed in-memory cache: key-value, fast reads, data loss acceptable ho to.
  • Cassandra Introduction Features — wide-column NoSQL: write-heavy, multi-datacenter, eventually consistent.
  • Introduction to HBase — Bigtable-style store: Hadoop par, strong consistency, range scans.
  • Introduction to MongoDB — document database: flexible schema, JSON jaisi documents.
  • Introduction to Redis — in-memory data structures: strings, lists, sets, sorted sets; cache + queue + leaderboard sab me kaam aata hai.
  • Storm — real-time stream processing: data aate hi process karo.
  • Introduction to Zookeeper — coordination service: configuration, leader election, distributed locks.
  • Kafka — distributed message log: high-throughput events, replay possible.

Chunne ka simple rule

  • Fast reads, data loss chalta hai → cache (Memcached / Redis).
  • Write-heavy, huge scale → Cassandra / HBase.
  • Flexible documents → MongoDB.
  • Events aur logs → Kafka.
  • Coordination → Zookeeper.
  • Real-time stream → Storm.

Design a CDN network

CDN (Content Delivery Network) ka kaam hai content ko user ke sabse paas wale server se dena, taaki latency kam ho aur origin server par load na pade. Static content — images, videos, CSS, JS — CDN ka main kaam hai.

Requirements

  • Static files (images, video, JS/CSS) duniya bhar ke users ko fast milni chahiye.
  • Origin server par load kam hona chahiye.
  • Content update ho to purana cached content expire hona chahiye (invalidation).

High-level design

  • Edge servers (PoPs) — duniya bhar me chhote servers; user ke sabse paas wala edge request handle karta hai.
  • Cache hit — file edge par hai to wahin se mil jaati hai, origin tak jaane ki zaroorat nahi.
  • Cache miss — edge file ko origin se laata hai, store karta hai, phir user ko deta hai.
  • DNS-based routing — user ko paas wale edge ka IP milta hai (anycast ya GeoDNS).

Key decisions

  • Push vs pull: pull-CDN me edge pehli request par origin se laata hai (simple); push-CDN me content pehle se edge par daal diya jata hai (live events ke liye).
  • TTL: har file ki expiry — chhoti TTL = fresh content, badi TTL = kam origin load.
  • Invalidation: file update hone par edge caches ko batana padta hai, warna users ko purana content dikhega.

Reference

  • Globally Distributed Content Delivery

Design a Google Docs system

Google Docs jaisa system — kai log ek hi document ko ek saath edit karein, aur sabko real-time me changes dikhein. Iska sabse mushkil hissa hai concurrent edits ko bina conflict ke merge karna.

Requirements

  • Multiple users ek document ko simultaneously edit kar sakte hain.
  • Har user ko doosron ke changes real-time me dikhne chahiye (low latency).
  • Document ka ek consistent final state hona chahiye — kisi ka likha hua kho na jaye.
  • Offline edits bhi baad me merge honi chahiye.

High-level design

  • WebSocket connection — har client server se persistent connection rakhta hai, changes turant bhejne ke liye.
  • Operations, poora document nahi — har keystroke ek chhota operation hota hai (insert/delete), poora document baar-baar nahi bheja jata.
  • Server operations ko order karta hai — sab clients ko operations ek hi order me milte hain, isliye sabka document ek jaisa rehta hai.
  • Document store — document ka current state aur operation history database me.

Core concept — Operational Transformation / Differential Sync

Do users ek hi jagah edit karein to unke operations transform karke merge kiye jate hain. Example: ek user "Hello" ke baad "X" jodta hai, doosra "Hello" ke pehle "Y" jodta hai — dono operations ko adjust karke final text "YXHello" banta hai. Isi ko differential synchronization kehte hain.

Design a random ID generation system

Distributed systems me unique IDs generate karni hoti hain — bina central coordinator ke, bina collision ke, aur high throughput par. Har request par ek ID banti hai, to system ko har second lakhs IDs deni hoti hain.

Requirements

  • Har ID globally unique honi chahiye.
  • IDs roughly time-ordered hon to achha hai (database indexing ke liye).
  • High throughput — har second lakhon IDs.
  • 64-bit me fit ho to best hai.

Approach — Snowflake style (Twitter ka design)

64-bit ID ko parts me baanto:

  • 41 bits — timestamp (millisecond precision, ek epoch se).
  • 10 bits — machine ID (datacenter + worker — 1024 machines tak).
  • 12 bits — sequence number (ek millisecond me 4096 IDs tak).

Har machine apni ID khud bana sakti hai — kisi central server se poochhne ki zaroorat nahi, isliye ye fast hai aur single point of failure nahi hai.

Trade-offs aur alternatives

  • UUID (random 128-bit) — simple hai, lekin time-ordered nahi, aur 128-bit bada hai.
  • Database auto-increment — simple hai, lekin single database bottleneck ban jata hai aur scale nahi hota.
  • Clock skew — agar machine ki clock peeche ho jaye to duplicate IDs ban sakti hain; isliye clock sync aur wait karna padta hai.

Design a key-value database

Key-value database — key do, value lo. Sabse simple data model, lekin scale par isme hi sabse zyada design decisions hoti hain: data kahan store hoga, replication kaise hoga, consistency kitni hogi.

Requirements

  • get(key) aur put(key, value) operations.
  • High availability — system hamesha likhne/padhne layak rahe.
  • Scale — data aur traffic badhne par nodes add karte jao.
  • Fault tolerance — nodes down ho to data na khoye.

High-level design (Dynamo style)

  • Consistent hashing — keys ko ring par baanto, har node ring ka ek hissa sambhalta hai. Node add/remove karne par sirf paas wala data move hota hai.
  • Replication — har key ki copy N nodes par (N=3 aam hai). Ek node down ho to doosre se data mil jata hai.
  • Quorum — write tab success maano jab W nodes ne likh liya, read tab success jab R nodes ne jawab diya. W + R > N ho to strong consistency milti hai.
  • Versioning — ek hi key ke do versions ho sakte hain (concurrent writes); vector clocks se pata chalta hai kaunsa naya hai, conflict ho to application resolve karti hai.

Storage engine

Data disk par kaise likha jata hai: memtable (memory me buffer) + SSTable (disk par sorted files) — write fast hota hai kyunki pehle memory me likha jata hai, phir batch me disk par flush hota hai. Ye LSM-tree design hai.

Design the Facebook news feed function

News feed — user khole to uske doston aur pages ki latest posts, rank karke, ek feed me dikhein. Ye social network ka sabse zyada poochha jaane wala design question hai.

Requirements

  • User ko apne connections ki posts dikhni chahiye, nayi pehle.
  • Feed ranked honi chahiye — relevant posts upar.
  • Scale — crores users, har second lakhon posts.
  • Post karte hi followers ko dikhni chahiye (near real-time).

Do approaches — Fan-out on write vs Fan-out on read

  • Fan-out on write (push): koi post kare to turant uske saare followers ke feed me daal do. Read fast hoti hai (feed pehle se taiyaar hai), lekin celebrity ke lakhon followers hon to ek post par lakhon writes padte hain.
  • Fan-out on read (pull): feed kholne par doston ki posts nikaal kar rank karo. Write sasta hai, lekin read slow hoti hai — har baar rank karna padta hai.
  • Hybrid (real systems ka tareeka): normal users ke liye push, celebrity (lakhon followers) ke liye pull. Dono ka best combination.

Components

  • Post service — post create karo, media store karo.
  • Feed service — har user ki feed (post IDs ki list) maintain karo.
  • Ranking — recency, engagement, relationship strength se score karo.
  • Cache — hot feeds memory me rakho.

Design the Facebook timeline function

Timeline — ek user ki poori history, time order me: posts, photos, life events, sab kuch ek page par. News feed se farq ye hai ki timeline ek user ki hoti hai (uski profile), feed doston ki posts ka mix hoti hai.

Requirements

  • Ek user ki saari activity time order me dikhni chahiye.
  • Saal/month ke hisaab se jump kar sakna chahiye (archive).
  • Profile khulte hi fast load honi chahiye.
  • Privacy — sirf allowed log hi dekh sakein.

Design idea — Denormalization

Timeline ka core idea hai denormalization: data ko likhte time hi timeline ke hisaab se arrange kar do, taaki padhte time join na karna pade. Har user ke liye uski timeline ka data pehle se taiyaar rakho (materialized view jaisa). Storage zyada lagega, lekin read bahut fast hogi.

Components

  • Activity store — har user action ek event ki tarah store hota hai (post, photo, like, event).
  • Timeline index — user ID + timestamp se uski activity nikaalo.

Design a garbage collection system

Garbage collection — wo memory free karo jo program ab use nahi kar raha. Har language runtime (Java, Go, Python) ke andar yehi system chalta hai. Interview me tumse ek simple GC design karne ko kaha ja sakta hai.

Requirements

  • Jo objects ab reachable nahi hain (koi reference nahi), unki memory free karo.
  • Program chalte hue kaam karna chahiye — zyada pause nahi hona chahiye.
  • Memory leak na ho, aur live objects kabhi free na hon.

Approach — Mark and Sweep

  • Mark: roots (global variables, stack) se shuru karke saare reachable objects ko mark karo — graph traversal jaisa.
  • Sweep: jo objects mark nahi hue, unki memory free kar do.
  • Problem: mark-sweep ke time program rukta hai (stop-the-world pause). Isliye real GCs incremental ya concurrent hote hain — thoda-thoda karke collect karte hain.

Doosre approaches

  • Reference counting: har object ka count rakho — count zero hote hi free kar do. Simple hai, lekin circular references (A → B → A) leak kar jate hain.
  • Generational GC: naye objects zyada marte hain — isliye heap ko young aur old generation me baanto; young ko baar-baar, old ko kabhi-kabhi collect karo.
  • Copying collector: live objects ko nayi jagah copy kar do, purani jagah poori free — fragmentation bhi khatm ho jata hai.

Design a cache system

Cache system — hot data ko memory me rakho, taaki database tak jaane ki zaroorat na pade. Har bade system ke peeche ek cache hota hai — bina cache ke scale karna mushkil hai.

Requirements

  • Read latency milliseconds se microseconds me aani chahiye.
  • Database par load kam hona chahiye.
  • Cache full ho jaye to kya evict karna hai, ye policy honi chahiye.
  • Data update ho to cache stale na rahe.

High-level design

  • Cache-aside (lazy loading): app pehle cache dekhti hai; miss ho to database se laakar cache me daalti hai. Sabse aam pattern.
  • Write-through: likhte time cache aur database dono update karo — cache hamesha fresh rehta hai.
  • Write-back: pehle cache me likho, baad me async database me — fast hai, lekin crash par data kho sakta hai.
  • Eviction: LRU (sabse purana use hua hatado) ya LFU (sabse kam use hua hatado). LRU sabse aam hai.

Distributed cache

Ek machine ka cache kaafi nahi — consistent hashing se keys ko kai cache nodes par baanto. Node down ho to uska data doosre nodes se ya database se mile. Hot keys (ek key par bahut requests) ke liye replication chahiye, warna ek node overload ho jayega.

Cache stampede

Popular key expire hote hi hazaaron requests ek saath database par padti hain — isse bachne ke liye lock lagao (ek request database jaye, baaki wait karein) ya expiry se pehle hi refresh karo.

OOD interview me tumse ek system ya component ka object oriented design maanga jata hai — jaise parking lot, elevator, ya card game. Approach system design jaisa hi hai, lekin level classes aur objects ka hota hai.

  • Design patterns use karo — taaki design kai applications me reuse ho sake.

F1Interview FAQs

Interview FAQs — 36 sawaal-jawaab

System design interview me sabse zyada poochhe jaane wale sawaal — estimation, CAP, caching, sharding, fan-out, OOD aur time management.

Q01System design interview me sabse pehle kya karna chahiye?
Sabse pehle constraints clear karo aur user cases pehchano. Interviewer se scope par agree karo — kitne users, kitne requests, kya features. Bina scope ke design karna sabse badi galti hai; interviewer yehi dekhna chahta hai ki tum sawaal poochhte ho ya seedha code karne lagte ho.
Q02Back-of-envelope estimation me kaunse numbers yaad rakhne chahiye?
Ye numbers har interview me kaam aate hain: memory se read ~100 nanoseconds, SSD se read ~100 microseconds, network round trip ~1-2 milliseconds, disk seek ~10 milliseconds. 1 million requests roz matlab ~12 requests per second. Storage: 1 TB = 1000 GB. Ye andaze se tum scale ka hisaab lagate ho.
Q03CAP theorem simple words me kya hai?
CAP kehta hai ki network partition ke time tum consistency aur availability me se sirf ek chun sakte ho. Bank jaisa system consistency chunta hai (galat balance nahi chalega), social media availability chunta hai (thoda purana data chalega). Partition nahi hai to teeno mil sakte hain.
Q04Consistent hashing kyun use hota hai?
Jab nodes add ya remove hote hain to simple hashing me har key ki jagah badal jati hai — poora data dobara distribute karna padta hai. Consistent hashing me sirf paas wala data move hota hai, isliye cache aur databases me yehi use hota hai. Lab 4 me khud try karo.
Q05Load balancer kya karta hai?
Load balancer aane wale traffic ko multiple servers par baantta hai, taaki koi ek server overload na ho. Agar ek server down ho jaye to traffic usse hatakar doosron par bhej deta hai. Health check karke sirf healthy servers ko traffic deta hai.
Q06Cache-aside aur write-through me kya farq hai?
Cache-aside me app pehle cache dekhti hai; miss ho to database se laakar cache me daalti hai — simple hai, lekin pehli request slow hoti hai. Write-through me likhte time cache aur database dono update hote hain — cache hamesha fresh rehta hai, lekin har write slow hoti hai.
Q07SQL vs NoSQL kab chunna chahiye?
Jab data structured hai, relations hain, aur strong consistency chahiye (bank, booking) to SQL. Jab scale bahut bada hai, schema flexible hai, ya availability zyada important hai (feed, logs, sessions) to NoSQL. Dono ka mix bhi aam hai — SQL main data ke liye, NoSQL cache ya analytics ke liye.
Q08Database sharding kya hai?
Sharding matlab data ko kai databases par baantna — jaise users ko user ID ke hisaab se alag shards par rakho. Ek database ki limit aane par sharding se scale hota hai. Mushkil hissa hai cross-shard queries aur rebalancing jab shard add ho.
Q09Fan-out on write aur fan-out on read me kya farq hai?
Fan-out on write me post karte hi saare followers ki feed me daal do — read fast, write mehenga. Fan-out on read me feed kholne par doston ki posts nikaal kar rank karo — write sasta, read slow. Real systems hybrid use karte hain: normal users ke liye push, celebrities ke liye pull.
Q10CDN kaise kaam karta hai?
CDN duniya bhar me edge servers rakhta hai. User ke sabse paas wala edge content deta hai — cache hit ho to origin tak jaane ki zaroorat nahi. Miss ho to edge origin se laakar store kar leta hai. Isse latency kam hoti hai aur origin par load kam padta hai.
Q11Message queue kab use karni chahiye?
Jab kaam turant karne ki zaroorat nahi ho — jaise email bhejna, notification, analytics, image resize. Queue se producer aur consumer alag ho jate hain: traffic spike aaye to queue bhar jati hai, workers dheere-dheere process karte hain. System crash ho to bhi kaam khoya nahi.
Q12Microservices vs monolith — kab kya?
Shuruaat me monolith theek hai — simple hai, deploy karna aasan hai. Jab team badi ho jaye, alag parts alag speed se badalne hon, ya ek part ko alag scale karna ho, tab microservices socho. Microservices me network calls, distributed transactions aur monitoring ki complexity badh jati hai.
Q13Rate limiter kaise design karte hain?
Har user/IP ke liye ek time window me allowed requests gin lo. Token bucket algorithm aam hai: bucket me tokens bharte rehte hain, har request ek token khati hai; bucket khali ho to request reject. Counter Redis me rakha jata hai taaki saare servers ek hi count dekhein.
Q14How to handle a celebrity (hot key) problem?
Jab ek key par bahut zyada requests aati hain (celebrity ki post), to us key wala node overload ho jata hai. Solutions: hot data ko kai nodes par replicate karo, cache layer me daalo, ya request ko alag servers par baanto. Fan-out on read bhi isi problem ka jawab hai.
Q15Eventual consistency ka matlab kya hai?
Eventual consistency ka matlab hai ki write ke turant baad saare replicas ek jaise nahi honge, lekin kuch time baad sab sync ho jayenge. Social media likes aur feed me ye chalta hai — lekin bank balance me nahi. Iska fayda hai high availability aur low latency.
Q16Replication aur sharding me kya farq hai?
Replication matlab ek hi data ki kai copies — availability aur read scale ke liye. Sharding matlab data ko parts me baantna — storage aur write scale ke liye. Dono aksar saath use hote hain: har shard ki kai copies banti hain.
Q17News feed me ranking kaise hoti hai?
Ranking me kai signals hote hain: recency (nayi post upar), engagement (likes/comments zyada to upar), relationship (kareebi dost ki post upar), aur content type (photo/video vs text). Har signal ka weight hota hai; final score se feed sort hoti hai.
Q18TinyURL me short code collision kaise handle karte hain?
Do tareeke hain: counter + base62 encode karo (collision hoga hi nahi, kyunki counter unique hai), ya random code banao aur database me check karo ki pehle se hai ya nahi — hai to dobara banao. Counter wala tareeka predictable hai, random wala guess karna mushkil hota hai.
Q19WebSocket aur HTTP polling me kya farq hai?
Polling me client baar-baar server se poochhta hai 'kuch naya hai?' — bahut requests waste hoti hain. WebSocket me ek persistent connection khul jata hai aur server khud message bhej deta hai jab kuch naya ho. Chat aur real-time apps me WebSocket hi use hota hai.
Q20Search engine me inverted index kya hai?
Inverted index ek map hota hai: word → kaunse documents me hai. Query aane par har word ke documents nikaal kar intersect karte hain. Isse arabon pages me search milliseconds me ho jata hai — bina index ke har page scan karna padta.
Q21Recommendation system me cold start kya hai?
Cold start matlab naya user ya nayi item — uska koi history nahi hai, to personalized recommendation nahi ban sakti. Solution: naye users ko popular/trending items dikhao, nayi items ko thoda boost do taaki data mile, aur content-based signals (category, tags) use karo.
Q22Garbage collection me mark-and-sweep kya hai?
Mark phase me roots se reachable saare objects ko mark karo, sweep phase me jo mark nahi hue unki memory free kar do. Problem hai pause — mark-sweep ke time program rukta hai. Isliye real GCs generational ya concurrent hote hain.
Q23Web crawler me politeness kyun important hai?
Agar crawler ek site ko ek saath hazaaron requests bhej de to wo site down ho jayegi — ye DDoS jaisa hoga. Isliye robots.txt follow karo, ek domain par delay rakho, aur crawl rate limit karo. Badi companies ke crawlers isi liye respect kiye jate hain.
Q24Chat me message order kaise maintain hoti hai?
Har conversation me har message ko sequence number milta hai. Receiver messages ko sequence ke hisaab se sort karke dikhata hai. Agar koi message miss ho jaye to sequence gap se pata chal jata hai aur client dobara sync kar leta hai.
Q25OOD interview me classes kaise pehchante hain?
Noun ko class banao, verb ko method banao. Scenario ke har core object ke liye ek class: Parking Lot me ParkingLot, ParkingSpot, Vehicle, Ticket. Relationships dekho — composition (ek ke andar kai), inheritance (ek doosre ka type), aur singleton (sirf ek instance).
Q26Singleton pattern kab use karte hain?
Jab ek class ka poore system me sirf ek instance hona chahiye — jaise configuration, connection pool, ya logger. Interview me ye bhi batao ki singleton testing me mushkil karta hai, isliye har jagah use mat karo.
Q27System design interview me time kaise manage karein?
45 minute ka interview aam taur par is tarah banta hai: 5 minute requirements aur scope, 5 minute estimation, 15 minute high-level design, 15 minute component detail aur bottlenecks, 5 minute wrap-up aur trade-offs. Har stage par interviewer se baat karte raho — chupchaap design karna galat hai.
Q28Database me index kab lagana chahiye?
Jis column par search, filter ya join hota hai, wahan index lagao — read fast ho jati hai. Lekin har index write ko slow karta hai (index bhi update hota hai) aur storage leta hai. Isliye sirf zaroori columns par index lagao, har column par nahi.
Q29How to design for failure?
Har component fail ho sakta hai — ye assume karke design karo. Load balancer ke peeche kai servers, database ka replica, cache miss par database fallback, aur message queue se retry. Circuit breaker lagao taaki ek fail hua service poore system ko na giraye.
Q30Horizontal vs vertical scaling me kya farq hai?
Vertical scaling matlab ek hi machine ko powerful banao (zyada RAM/CPU) — aasan hai lekin limit hai aur costly hai. Horizontal scaling matlab aur machines add karo — mushkil hai (data baantna, coordination) lekin practically unlimited hai. Bade systems horizontal scaling use karte hain.
Q31Why is denormalization used in timeline design?
Timeline padhte time joins nahi karne padte — data likhte time hi timeline ke hisaab se arrange kar diya jata hai. Storage zyada lagta hai, lekin read bahut fast hoti hai. Read-heavy systems (feed, timeline) me ye trade-off faydemand hai.
Q32How do you estimate storage for a photo sharing app?
Roz ki photos × avg photo size × din = total storage. Example: 10 million photos roz, har photo 2 MB → 20 TB roz, saal me ~7 PB. Lekin har photo ke 3 sizes bante hain (thumbnail, medium, original) to ~3x kar lo. Purani photos ko cold storage me bhejkar cost kam ki ja sakti hai.
Q33What is a Bloom filter and where is it used?
Bloom filter ek memory-efficient structure hai jo batata hai ki koi item 'shayad hai' ya 'pakka nahi hai'. Crawler me ye check karne ke liye use hota hai ki URL pehle crawl ho chuki ya nahi — bina saari URLs store kiye. False positive ho sakta hai, false negative nahi.
Q34How to prevent cache stampede?
Jab popular key expire hoti hai to hazaaron requests ek saath database par padti hain. Roko: lock lagao (sirf ek request database jaye, baaki wait karein), expiry se pehle hi background me refresh karo, ya random jitter ke saath expiry lagao taaki saari keys ek saath expire na hon.
Q35What should I say if I don't know an answer in the interview?
Seedha bolo 'ye mujhe nahi pata, lekin main is tarah sochunga...' aur apna reasoning dikhao. Interviewer ko perfect answer nahi, thinking process dekhni hoti hai. Guess karke galat answer dena, accept karne se zyada nuksan karta hai.
Q36How is a trending system different from top-k?
Top-k sirf sabse zyada count wale items nikaalta hai. Trending me velocity matter karti hai — kaunsa topic achanak badh raha hai, pichhle average ke muqable. Isliye trending me rolling window aur baseline comparison hoti hai, sirf count nahi.
